# Bajutsu と Maestro の比較

> Bajutsu と [Maestro](https://maestro.dev/) が一致する点と、分かれる点をまとめます。Maestro は
> 形の上で Bajutsu にもっとも近いツールです。どちらもオープンソースで、YAML Ain't Markup
> Language（YAML）で記述するブラックボックスの E2E（end-to-end）自動化フレームワークであり、
> iOS と Android と web にまたがります。両者を比べると、この分野に共通する性質と、Bajutsu が
> 意図して選んだ性質とを切り分けられます。

関連: [concepts](concepts.md) · [vision](vision.md) · [ai-boundary](ai-boundary.md) ·
[selectors](selectors.md) · [dsl-grammar](dsl-grammar.md)

---

## それぞれのツールの姿

**Maestro** は mobile.dev による、モバイルと web の UI（ユーザーインタフェース）自動化
フレームワークです。YAML で書いた**フロー**を解釈する 1 つの Java バイナリとして配布されます。
バイナリは端末に小さなコンパニオンドライバアプリをインストールし、アクセシビリティツリーを
操作します。オープンソースの CLI（コマンドラインインタフェース）の周りには、商用製品が 2 つ
あります。デスクトップの作成環境である Maestro Studio と、ホスト型のデバイスファームである
Maestro Cloud です。Maestro は自らの思想を「腕の長さの距離を保つ自動化」と表現し、不安定さへの
**組み込みの寛容さ**を掲げます。

**Bajutsu** は、バックエンド非依存のドライバの上に立つ、自然言語駆動の E2E テストツールです。
シナリオの作成と失敗の調査には AI を使います。合否を決めるのは決定的なランナーです。Bajutsu は
自らの思想を**決定性優先**と表現します。固定 sleep を置かず、曖昧なセレクタは任意の 1 件に
解決せず失敗します。

どちらも Apache 2.0 ライセンスです。どちらもテストをプレーンな YAML として保存し、チームは
プルリクエストでレビューできます。両者が分かれるのは、1 つの問いにおいてです。**合格という
判定は、何に依存してよいのか。**

## この比較の作り方

以下の記述は、宣伝文ではなく一次資料に基づきます。

| 対象 | 資料 | 読んだ版 |
|---|---|---|
| Maestro | ドキュメントリポジトリ `mobile-dev-inc/maestro-docs` | 2026-08-26 のコミット |
| Maestro | ソースリポジトリ `mobile-dev-inc/Maestro` | `VERSION_NAME=2.10.0` |
| Bajutsu | 本リポジトリの `docs/` と `roadmaps/` とソース | 現在の `main` |

ドキュメントとソースが食い違うときは、ソースを採ります。後述の

`maestro-client` の `Maestro.kt` から読み取ったものです。散文にその記述はありません。

## 共通する土台

どちらのツールの特色に見えるものも、多くはこの分野に共通する性質です。以下の表のどの行も、
一方の優位を示しません。

| 能力 | Maestro | Bajutsu |
|---|---|---|
| レビュー可能な YAML でテストを書き、コンパイル不要 | ✅ | ✅ |
| アクセシビリティツリー経由のブラックボックス操作 | ✅ | ✅ |
| 1 つのシナリオ形式で iOS と Android と web を対象にする | ✅ | ✅ |
| 新しいバックエンドなしで Flutter と React Native に対応 | ✅ | ✅ |
| 固定 sleep ではなく条件待ち | ✅ | ✅ |
| 引数を取る再利用可能なサブフロー（コンポーネント） | ✅ | ✅ |
| タグによるスイートの選択 | ✅ | ✅ |
| 前処理と後処理のフック | ✅ | ✅ |
| スクリーンショットのベースラインによる視覚回帰 | ✅ | ✅ |
| JUnit XML と単体で開ける HTML レポート | ✅ | ✅ |
| 実行ごとの `manifest.json` による成果物の索引 | ✅ | ✅ |
| 画面録画と端末ログの取得 | ✅ | ✅ |
| コーディングエージェント向けの Model Context Protocol（MCP）サーバ | ✅ | ✅ |
| GUI の作成環境 | Studio（デスクトップ） | `serve`（ブラウザ） |

## 分かれ目は、判定が何に依存してよいか

3 つの仕組みが、それぞれのツールの性格を決めます。ほかの違いは、すべてここから派生します。

### セレクタの解決

Maestro はセレクタを**最初の一致**に解決します。`Maestro.kt` の `findElementWithTimeout` は
`filter(hierarchy.aggregate()).firstOrNull()` を呼びます。`index` セレクタは、作成者が別の
1 件を選ぶために存在します。1 画面に「カートに追加」ボタンが 3 つあっても、素の `tapOn` は
成功します。フィルタが最初に並べたものをタップします。

Bajutsu はセレクタを**ちょうど 1 要素に解決するか、失敗する**かのどちらかです。候補が 2 件
以上あると `AmbiguousSelector` を送出します
（[selectors](selectors.md#resolve_uniqueelements-sel---element)）。Bajutsu の `index` は、
一意でないと作成者が承知している集合に対する、意図的な例外指定です。任意のボタンをタップして
しまうシナリオは、作成中に失敗します。誤った理由で合格することがありません。

この取り引きは双方向です。Maestro の規則は、最初のフローが早く動く助けになります。Bajutsu の
規則は、緑のスイートが持つ意味を重くします。

### リトライと寛容さ

Maestro は不安定さを、吸収すべき環境の事実として扱います。その姿勢は 4 つの仕組みに表れます。

- `retry` は、ブロックを最大 3 回まで再実行します。
- `retryTapIfNoChange` は、画面が変わらなかったタップをやり直します。
- `optional: true` は、フロー全体を落とさずにステップの失敗を許します。
- Maestro Cloud の**スマートリトライ**は、同じ端末モデルで前回成功していた赤いフローを、
  作成者の関与なしに再実行します。

Bajutsu の文法には、リトライの構文がどこにもありません（[dsl-grammar](dsl-grammar.md)）。判定が
ぶれることは、診断すべき欠陥です。`flakiness` と `audit --history` の 2 つのコマンドは、ぶれを
覆い隠すのではなく、順位付けして説明するために存在します。

その代償は Maestro 自身のドキュメントが述べています。フローを `retry` で包むと「50％ しか
動作しないボタンのような、アプリの本当の不安定さを隠しかねない」と書かれています。

### 判定経路の AI

Maestro は、フローが実行時に呼べる AI コマンドを 3 つ追加しました。`assertWithAI` は自然言語の
表明をスクリーンショットに対して評価します。`assertNoDefectsWithAI` は画面の視覚的な不具合を
点検します。`extractTextWithAI` は画面上の値を読み取って変数に入れます。3 つとも既定が
`optional: true` です。LLM（大規模言語モデル）の答えが確率的だからです。

モデル自体は **Maestro Cloud が管理**します。アカウントが前提になります。Maestro は
`MAESTRO_CLI_AI_KEY` と `MAESTRO_CLI_AI_MODEL` の 2 つの変数を廃止しました。そのためチームは、
自前のキーを渡すこともモデルを選ぶこともできません。

Bajutsu は、その構成を設計として禁じます。第一原則 1 は、`run` と CI（継続的インテグレーション）の
ゲートから LLM を締め出します。[ai-boundary](ai-boundary.md) は、その分離をテスト済みの性質として
記録しています。LLM を使いたい場合も、資格情報とプロバイダはチームの手元に残ります。Claude へは
4 つの方法で到達します。Anthropic API（アプリケーションプログラミングインタフェース）、
Amazon Bedrock、`ant` CLI、Claude Code CLI です。`provider: none` と書けば、その方針を
リポジトリ自身に明記できます。

ここから 2 つの帰結が出ます。Bajutsu の CI 実行はトークンを消費せず、第三者に到達しません。
AI アサーションに頼る Maestro のスイートは、実行時にベンダーの可用性と価格に依存します。

## 機能の比較

### プラットフォームと実行環境

| 観点 | Maestro | Bajutsu |
|---|---|---|
| iOS | シミュレータ。ドキュメントも一通り揃う | シミュレータで実機同等の検証済み。実機経路は実装済み（BE-0238）だが、署名は進行中（BE-0288） |
| Android | エミュレータと実機の両方 | エミュレータで CI 検証済み |
| web | Chromium。Beta 扱いで、ロケールは `en-US` 固定、ビューポートも既定値 | Playwright。毎コミットの Linux ゲートで実行 |
| デスクトップ OS | macOS と Windows と Linux | macOS と Linux。Windows の記述はない |
| 実行時の前提 | Java 17 または 21 | uv 経由の Python 3.13 |
| インストール | `curl` 1 行、Homebrew、または `.zip` | クローンして `make setup`。PyPI（Python Package Index）に未公開 |
| 端末側の部品 | 両プラットフォームでコンパニオンドライバアプリ | Android はビルド済みの UI Automator サーバ、iOS は XCUITest ランナー |

この表では、到達範囲と最初の 5 分の手軽さで Maestro が勝ります。Windows 対応と公開バイナリに
相当するものは、今日の Bajutsu にはありません。

### 操作（アクション）

Maestro は 48 種類のコマンドを定義します。Bajutsu は約 40 種類のアクションを定義します。重なりが
大きいので、表には片方だけが持つものを挙げます。

| Maestro のみ | Bajutsu のみ |
|---|---|
| `setOrientation`（端末の向きを変える） | `push`（プッシュ通知を配信する） |
| `setDarkMode` / `toggleDarkMode` / `assertDarkMode` / `assertLightMode` | `overrideStatusBar` / `clearStatusBar`（撮影用にステータスバーを固定する） |
| `setAirplaneMode` / `toggleAirplaneMode` | `http`（エンドポイントを呼び、本文を変数に保存する） |
| `addMedia`（メディアピッカー用にギャラリーへ投入する） | `totp`（時刻ベースのワンタイムパスワードを計算する） |
| `travel`（経路に沿った移動を模擬する） | `email`（メールボックスを監視して値を取り出す） |
| `evalScript` / `runScript`（任意の JavaScript） | `generate`（乱数または現在時刻の値） |
| `inputRandomNumber` と `faker` ライブラリ | `web`（WebView の DOM 文脈に入る） |
| | `drag` と `pinch` と `rotate` を一級のジェスチャとして扱う |
| | フォーカス中のフィールドへの `select` / `copy` / `clear` / `delete` |
| | `setPickerValue`（iOS のホイールピッカーを行で指定する） |
| | `manual`（記録した人手の介入。再生時は明示的に失敗する） |

傾向は表全体で一貫します。Maestro は**端末の状態**を広く覆います。向き、テーマ、無線、
ギャラリーです。Bajutsu は**テストデータの配線**を広く覆います。ワンタイムパスワード、
メールボックス、生成値、エンドポイント直呼びです。Bajutsu はそれらをスクリプトではなく、
宣言的なステップとして表します。

### セレクタ

| セレクタの系統 | Maestro | Bajutsu |
|---|---|---|
| 識別子 | `id`（既定で正規表現） | `id`（リストで各プラットフォームの綴りを OR 指定）、`idMatches`（glob） |
| 表示テキスト | `text`（既定で正規表現） | `label`、`labelMatches`（正規表現）、`value` |
| コンテナへの限定 | `childOf`、`containsChild`、`containsDescendants` | `within`（入れ子可能） |
| 画面上の位置関係 | `above`、`below`、`leftOf`、`rightOf` | — |
| web 固有 | `css`（Cascading Style Sheets）セレクタ | —（`web` 文脈は `data-testid` を識別子に正規化する） |
| 要素の寸法 | `width`、`height`、`tolerance` | — |
| 種別（traits） | `text`、`long-text`、`square` | 正規化した trait 語彙 |
| 要素の状態 | `enabled`、`checked`、`focused`、`selected` | `enabled` / `disabled` / `selected` のアサーションで確認 |
| 複数一致の n 番目 | `index`（日常的な曖昧さ解消手段） | `index`（意図的な最終手段） |
| 2 件以上一致したとき | 最初の 1 件に解決する | `AmbiguousSelector` を送出する |

セレクタ言語は Maestro のほうが豊かです。位置関係のセレクタは、隣接要素を足がかりにして、
識別子をまったく持たないコントロールにも届きます。Bajutsu に相当する機能はなく、提案中の
ロードマップ項目もありません。本リポジトリの答えは、アプリ側の識別子を直すことであり、
`doctor` と `coverage` の 2 つがその方向に押し出します。

その答えは、チームが所有するアプリには通ります。サードパーティの画面には通りません。誰も
手を入れられないレガシー画面にも通りません。

### 制御フローとデータと再利用

| 能力 | Maestro | Bajutsu |
|---|---|---|
| 条件分岐 | `when`（`visible` / `notVisible` / `platform` / JavaScript 式） | `if`（条件は任意のアサーション） |
| 回数指定のループ | `repeat: { times: N }` | — |
| 条件付きループ | `repeat: { while: … }` | — |
| 一致要素の反復 | `index` と JavaScript で自作する | セレクタに対する `forEach` |
| サブルーチン | `runFlow`（`file` または `commands`）と `env` | `use`（コンポーネントファイルと名前付き引数） |
| データ駆動 | JavaScript で手書きする | `data` の行、または `dataFile` の CSV（comma-separated values） |
| 前処理と後処理 | `onFlowStart` / `onFlowComplete` | `before` と `after`（`on: always` / `success` / `error`） |
| 予測不能な割り込み画面 | ステップ単位の `optional: true` | `interrupts`（任意の位置で日和見的に照合する） |
| 変数 | `env`、CLI、`MAESTRO_` 接頭辞のシェル変数から `${VAR}` | `${vars.*}`、`${data.*}`、`${secrets.*}` |
| スクリプトの逃げ道 | GraalJS サンドボックス、HTTP クライアント、`faker` | 設計として持たない |

同じ必要に対して、両者は正反対の答えを出します。Maestro は作成者に JavaScript エンジンを渡し、
普通のプログラミングで隙間を埋めさせます。Bajutsu は逃げ道を拒みます。代わりに、繰り返し
現れる必要ごとに一級のステップを増やします。そうすることで `codegen`、`audit`、`impact` が、
シナリオを静的に読み続けられます。

この拒否は、2 つの利便性を Bajutsu から奪っています。回数指定のループと条件付きループの
どちらにも、文法上の表現がありません。扱うロードマップ項目もありません。

### アサーション

| アサーション | Maestro | Bajutsu |
|---|---|---|
| 要素の可視と不在 | `assertVisible` / `assertNotVisible` | `exists`（`negate` 付き） |
| テキストの内容 | `text` セレクタに畳み込まれる | `value` と `label`（`equals` / `contains` / `matches`） |
| 要素の個数 | — | `count`（`equals` / `atLeast` / `atMost`） |
| 操作可能な状態 | 状態セレクタに畳み込まれる | `enabled` / `disabled` / `selected` |
| スクリーンショットのベースライン | `assertScreenshot`（`cropOn` と閾値） | `visual`（要素スコープ、マスク、2 種類の比較エンジン） |
| 要素ツリーのベースライン | — | `golden` |
| クリップボードの内容 | `copyTextFrom` と JavaScript で読む | `clipboard` |
| 通信が発生したこと | — | `request` |
| 順序付きの通信の集合 | — | `requestSequence` |
| 分析イベントの送出 | — | `event` |
| 応答が JSON Schema に適合すること | — | `responseSchema` |
| 任意の真偽値 | `assertTrue`（JavaScript 式） | — |
| 自然言語の主張 | `assertWithAI`（確率的で、既定は optional） | —（第一原則 1 が禁じる） |

### ネットワーク

比較の中でもっとも大きな 1 つの差であり、向きは Bajutsu に有利です。

Maestro には**ネットワークの層がありません**。ドキュメントリポジトリとソースの双方を検索しても、
通信の傍受、スタブ、通信のアサーションのいずれも見つかりません。フローは JavaScript からエンドポイントを
呼んでデータを用意できます。アプリ側が Maestro を検知して、自らモックサーバを向くこともできます。
どちらも、実行中にアプリが行う通信そのものには届きません。

Bajutsu はネットワークをシナリオの一部として扱います（[network](network.md)）。

- `mocks` は、一致した通信をプロトコル内でスタブし、ステータスとヘッダと本文と遅延を返します。
- `network.filter` は、観測対象を指定ドメインに絞ります。
- `request`、`requestSequence`、`event` の 3 つは、アプリが実際に送った内容を検証します。
- `responseSchema` は、取得した応答本文を JSON Schema で検証します。
- `wait: { until: { request } }` は、画面ではなく通信を待ちます。
- `redact` は、資格情報を含むヘッダをディスク書き出し前に伏せます。

この一覧から 2 つの必要が導けます。オフラインのスイートを組みたいチームには、Maestro に経路が
ありません。分析イベントを検証したいチームにも、経路がありません。Bajutsu はどちらにも直接
答えます。

### 証跡とレポート

| 観点 | Maestro | Bajutsu |
|---|---|---|
| レポート形式 | JUnit XML、HTML、`html-detailed` | `manifest.json`、JUnit XML、Common Test Report Format（CTRF）の JSON、対話的 HTML |
| 成功した実行のスクリーンショット | `--analyze` か明示的な `takeScreenshot` がなければ取らない | `capturePolicy` の規則が求めるものを取る |
| 取得ポリシー | コマンドごとにその場で書く | 操作・イベント・エラーに紐づく再利用可能な規則 |
| 動画 | `startRecording` / `stopRecording` と `maestro record` | `video` の区間取得 |
| 端末ログ | logcat、シミュレータログ、XCTest ログ | `deviceLog` と `appTrace` の区間取得 |
| クラッシュと ANR の報告 | フローごとに収集する | 端末ログを通じて確認する |
| 失敗ステップの要素ツリー | `screen-hierarchy/` の JSON | `elements`（任意で `rawTree` も） |
| ステップ単位の帰属 | `commands.json` | `manifest.json` と `actionLog` |
| タッチの到達確認 | — | `--touch-markers` がアプリの受け取ったタッチを描画する |
| 秘密情報の伏せ字 | `label` はコンソールから隠すが、デバッグログには残る | `redact` がログと要素ツリーと通信を書き出し前に伏せる |

レポートはほぼ同等です。同等でない行が 2 つあります。Bajutsu の伏せ字は表示上の配慮ではなく、
保存時点の保証です。`capturePolicy` は「毎回 X のときに取る」を規則に変え、2 回目以降の実行が
手を借りずに同じ証跡を再現します。

### スイート全体の分析

Bajutsu は、Maestro に相当機能のない読み取り専用の分析層を備えます。以下のコマンドはすべて
助言的です。端末も要らず、モデルにも到達せず、CI を止めることもありません。

| コマンド | 何を報告するか |
|---|---|
| `audit` | シナリオの再現性。静的な採点、または反復実行と差分による採点 |
| `audit --history` | 指紋が同じまま判定がぶれたシナリオ。端末 OS のバージョンごとに集計 |
| `flakiness` | ぶれの大きいシナリオを、悪い順に並べた順位 |
| `coverage` | 宣言された識別子の名前空間のうち、スイートが実際に触れている範囲 |
| `impact` | `git` の差分が危険にさらすシナリオのステップ |
| `stats` | スイート全体の傾向。合格率と所要時間と失敗の集中箇所 |
| `triage` | 実行が赤くなった理由と、最小の修正案 |
| `codegen` | シナリオを XCUITest / Playwright / UI Automator のネイティブテストにしたもの |
| `export` | 実行を可搬な `.zip` にまとめたもの |

Maestro のもっとも近い機能は、CLI ではなく Maestro Cloud にあります。しかも答える問いが違います。
スマートリトライは、ぶれを順位付けするのではなく**抑え込み**ます。スイートの網羅状況を地図に
する機能も、差分からテストを選ぶ機能も、ネイティブテストを出力する機能も、Maestro にはありません。

`triage` にも相当機能はありません。赤い実行の文脈を組み立て、規則ベースのエージェント、または
`--ai` 指定の Claude で診断します。そのうえで `renameId`、`addIndex`、`raiseTimeout` の
いずれかの構造化された修正を提案します。`--apply` を付けると、差分を確認したうえでシナリオに
適用します。

### AI 機能

| 観点 | Maestro | Bajutsu |
|---|---|---|
| 自然言語のゴールからの作成 | MCP サーバとコーディングエージェント経由 | 一級のコマンド `record` |
| 自律的な探索 | — | 幅優先で画面地図を作る `crawl` |
| 失敗の診断 | `--analyze` が知見レポートを生成する | `triage`（規則ベース、または `--ai`） |
| モデルが評価するアサーション | `assertWithAI` と `assertNoDefectsWithAI` | 第一原則 1 が禁じる |
| モデルの提供元 | Maestro Cloud の管理。アカウントが前提 | Anthropic API、Bedrock、`ant`、Claude Code のいずれか（チーム自身のもの） |
| AI を完全に切る手段 | AI コマンドを呼ばない運用 | `provider: none` と、AI を含まない基本インストール |
| トークンと費用の会計 | — | 帰属付きの台帳と利用状況ダッシュボード |
| MCP のツール | 9 種類。クラウド投入と端末ビューアを含む | 2 種類と、資源としての実行証跡 |

MCP サーバは Maestro のほうが強力です。`inspect_screen`、インライン YAML を渡せる `run`、
`cheat_sheet`、組み込みの Maestro Viewer が揃います。この 4 つがコーディングエージェントに
緊密な作成ループを与えます。Bajutsu の 2 ツールはそこに届きません。

|---|---|---|
| マネージドのデバイスファーム | Maestro Cloud（実行のたびに初期化） | — |

## Bajutsu が強い点

**決定性が推奨ではなく強制になっています。** `AmbiguousSelector` と、リトライ構文の不在と、
能力プリフライトが揃うことで、緑の実行がアプリについての証拠になります。Maestro の最初一致の
解決とリトライ群は、緑の実行の証拠力を弱めます。

**ネットワークがシナリオの一部です。** 宣言的なモック、通信と順序のアサーション、分析
イベントのアサーション、応答のスキーマ検証。これらに相当する機能が Maestro にはありません。
オフラインのスイートは、一方では組めて、他方では組めません。

**LLM は判定に触れず、資格情報はチームから出ません。** Bajutsu の AI 分離はテスト済みの性質で、
停止スイッチも文書化されています。Maestro の AI アサーションはフローの中で動き、ベンダーが
管理するモデルとベンダーが発行するアカウントを使います。

**スイートに分析層が付きます。** 無料の CLI に、ぶれの順位付けと網羅の地図が入っています。
差分からの影響分析、傾向のダッシュボード、自己修復の triage も同じ CLI にあります。Maestro の
もっとも近い機能は有料でホスト型であり、ぶれの説明ではなく抑制を狙います。

**codegen が出口になります。** 通ったシナリオから XCUITest、Playwright、UI Automator の
ネイティブテストを生成できます。チームは書いたフローを捨てずに Bajutsu を離れられます。
Maestro にこれはありません。

**証跡が呼び出し箇所ではなく方針です。** `capturePolicy` の規則と保存時点の伏せ字により、
2 回目の実行が同じ証跡を再現します。作成者の手間も、資格情報の漏れもありません。

**ドキュメントが二言語で、根拠に紐づいています。** どのページも、振る舞いの背後にある実装と
ロードマップ項目を、英語と日本語の双方で示します。

## Bajutsu が弱い点

**導入の費用がはるかに大きいです。** Maestro は `curl` 1 行と `.yaml` ファイル 1 つです。
Bajutsu は Git のクローンと uv 一式、そして iOS では Xcode でビルドする XCUITest
ランナーを要します。公開パッケージがないため、5 分で試せる人がいません。

**エコシステムが事実上ありません。** スター 5 つ、フォーク 0、コミュニティなし、名前の出ている
採用企業なしです。Maestro の 15,500 スターの裏には、回答済みの質問と記事と実例があり、新しい
チームはそれに日々頼れます。

**Windows に対応していません。** Maestro は macOS、Windows、Linux を文書化しています。
Bajutsu には Windows 対応の記述がなく、計画も示されていません。この穴は、Android 開発者の
相当数を最初から締め出します。

**実機の守備範囲が薄いです。** Maestro は Android の実機を日常的に操作します。Bajutsu の
Android 検証はエミュレータのみです。iOS の実機経路も、BE-0288 で署名の作業が進行中です。

**セレクタ言語が狭いです。** Maestro の位置関係セレクタは、隣接要素を足がかりに、識別子のない
コントロールへ届きます。Bajutsu には位置のセレクタ、CSS セレクタ、寸法の照合のいずれも
ありません。
提案中のロードマップ項目もありません。サードパーティやレガシーの画面をテストする手間が、
その分だけ増えます。

**よくあるループが書けません。** Maestro の `repeat` は固定回数と `while` 条件の両方を覆います。
Bajutsu の `forEach` は一致要素の反復だけです。「追加を 5 回押す」も「受信箱が空になるまで
削除する」も、直接の書き方がありません。

**端末状態の制御に穴があります。** 向き、ダークモード、機内モードのいずれも欠けており、
ロードマップにも現れません。横向きレイアウトやダークテーマやオフライン動作を検証したい
スイートは、今日その状態変化を表現できません。

**マネージドのクラウドがありません。** 並列のホスト端末、ネイティブなマージ阻止、Slack 通知
の 3 つが対象です。Maestro ではこれらを購入でき、Bajutsu では自作することになります。

**スクリプトの逃げ道がありません。** この拒否は意図的で、静的解析を守っています。同時に、
本当に新しい必要が出たときはロードマップ項目を待つことになります。Maestro の作成者なら
JavaScript を 6 行書いて済ませます。

## どちらを選ぶか

| こういうチーム | 向いているのは |
|---|---|
| 今日の午後に最初のフローを動かしたい | Maestro |
| Windows からスイートを回している | Maestro |
| ホスト型の並列端末とマージ阻止が今すぐ要る | Maestro |
| 識別子のないサードパーティやレガシーの画面を試験する | Maestro |
| 向き、ダークモード、機内モードが要る | Maestro |
| 画面や資格情報をベンダーに送れない | Bajutsu |
| 不安定なテストをリトライではなく欠陥として扱う | Bajutsu |
| 通信や分析イベントを検証する | Bajutsu |
| スタブ応答で動くオフラインのスイートが要る | Bajutsu |
| 網羅と影響とぶれの分析を CI に置きたい | Bajutsu |

## 埋める価値のある穴

この比較から、6 つの穴が浮かびます。どれも具体的で範囲が限られ、担当するロードマップ項目も
ありません。どれも第一原則を守ったまま、Maestro を選ぶ理由を 1 つ減らせます。

1. **位置関係のセレクタ。** `above`、`below`、`leftOf`、`rightOf` の 4 種です。ドライバが
   すでに報告している要素のフレームに対して解決します。曖昧なら失敗する規則は保たれるので、
   決定性は損なわれません。
2. **回数指定と条件付きのループ。** `times` を取る `repeat` と、条件にアサーションを取る
   `while` です。`scroll` の `maxScrolls` と同じ上限を置けば、ループは必ず終わります。
3. **端末の向き。** 能力トークンの背後に置く `setOrientation` ステップです。既存のプリフライトが、
   実行できないバックエンドを事前に弾きます。
4. **ダークモードの制御とアサーション。** 向きと同じ形です。テーマをまたぐ視覚回帰を意味のある
   ものにする前提でもあります。
5. **機内モード。** オフライン試験の欠けた半分です。`mocks` は応答をスタブできますが、無線を
   切るステップがありません。
6. **公開パッケージ。** `pip install bajutsu` が通るまで、評価はどれもクローンと実行環境の用意から始まります。

最初の 5 つは作成機能です。6 つ目は、最初の 5 つに誰かがたどり着けるかどうかを決めます。
