# Roadmap status ページの絞り込みショートカットとテーブルページング

> ステータス: 実装完了
> 対象: `scripts/build_roadmap_dashboard.py`（Roadmap status ダッシュボード生成スクリプト）
> 関連: [BE-0094（ダッシュボード本体）](../../roadmaps/BE-0094-roadmap-status-dashboard/BE-0094-roadmap-status-dashboard.md)・
> [BE-0219（検索）](../../roadmaps/BE-0219-roadmap-dashboard-search/BE-0219-roadmap-dashboard-search.md)・
> [BE-0311（テーブルビュー）](../../roadmaps/BE-0311-roadmap-dashboard-table-view/BE-0311-roadmap-dashboard-table-view.md)

Roadmap status ページに、未完了項目だけを一発で絞り込むショートカットボタンと、カテゴリの一括展開・折りたたみボタン、
テーブルビューのページングを追加します。カード表示の初期状態や各ステータスチップの初期 ON/OFF は変更しません。

## 1. なにをつくるのか

フィルタ行（`.be-filters`）に、既存の検索ボックス・ステータスチップに加えて次の 2 つのボタンを追加します。

- **「未完了のみ表示」ボタン。** クリックすると、Approved と In progress の 2 チップだけを ON にします。
  同時に、Implemented・Deferred・Rejected の 3 チップを OFF にします。すでにこの組み合わせになっているときは、
  クリックすると 5 チップすべてを ON に戻します（初期状態への復帰）。ボタンのラベルは、現在のチップの組み合わせに
  応じて「未完了のみ表示」と「すべて表示」を切り替えます。
- **「すべて展開」「すべて折りたたむ」ボタン。** クリックした瞬間に、画面上のすべてのカテゴリ（`.be-cat`）を
  展開または折りたたみます。この操作の結果は、カテゴリ見出しの個別クリックや、チップ・検索の変更によって
  上書きされてかまいません。見出しを 1 個ずつクリックして開閉する現在の挙動は変えません。それに加えて、
  一括操作の手段を用意します。

テーブルビュー（`.be-table-view`）に、1 ページ 50 行のページングを追加します。

- ページ送りは、テーブル下部に並ぶ番号付きボタン（`1 2 3 … 9`）で行います。
- ページングの対象は、検索ボックスとステータスチップによる絞り込みを通過した行だけです。絞り込みで
  一致した行が 50 行以下なら、ページ送りボタンは 1 個（現在ページ）だけになります。
- 列見出しをクリックしてソート順を変えたとき、検索文字列を変えたとき、ステータスチップを切り替えたときは、
  いずれも 1 ページ目に戻ります。ページ番号ボタンを押したときは、ページだけが変わります。絞り込みやソート順は
  変わりません。

カードビュー（`.be-cards-view`）にはページングを追加しません。カテゴリごとの折りたたみと、後述する絞り込み
ショートカットを組み合わせれば、一度に展開されるカード枚数は現実的な範囲に収まります。テーブルビューだけは、
絞り込みなしで登録済みの全項目（本稿執筆時点で 398 件）を一度に 1 枚のテーブルへ展開してしまいます。

### やらないこと

- **ステータスチップの初期 ON/OFF を変更しません。** Implemented を含む 5 チップは、これまでどおりページを
  開いた直後は全部 ON のままにします。「未完了のみ表示」ボタンは、読者が能動的にクリックしたときだけ働く
  ショートカットです。初期状態そのものは変えません。
- **URL クエリパラメータでの初期フィルタ指定を実装しません。** 「このリンクを開けば Approved 一覧が見える」
  という共有手段は、今回のスコープに含めません。テーブルビューの絞り込み結果を GitHub Issue やチャットで
  共有したい要求が具体的に出てきた時点で、別の提案として検討します。
- **カードビューへのページングを追加しません。** カテゴリ単位の「もっと見る」ボタンのような仕組みは導入しません。
- **1 ページあたりの件数を読者が選べるようにしません。** 50 件固定とします。
- **ページ番号ボタンの省略表記（`1 2 … 8 9`）を実装しません。** ページ数を決めるのは、絞り込みをかけない
  ときのテーブル全体（登録済みの全項目）です。Implemented バケットだけではありません。本稿執筆時点の
  ページ数は最大 9 です。9 個のボタンをそのまま並べても崩れません。項目数が大きく増えてページ数が
  二桁に達したら、省略表記の要否をあらためて検討します。

## 2. なぜつくるのか

Roadmap status ページは、公開後に確認したところ、着地直後はどのカテゴリも見出しと進捗バーだけの折りたたみ
状態でした（BE-0094 の設計どおり）。カードは 1 枚も見えません。Approved は「Platform support」
「Device-cloud execution」など 10 個のカテゴリに分散しています。読者が見出しを 1 個ずつクリックして展開しない
限り、その多くは画面に現れません。実際にブラウザで検証したところ、13 件の Approved は、ステータスチップで
絞り込めば正しく全件描画されます（データの欠落ではありません）。原因は「初期表示で何も展開されていないこと」です。
読者はこれを「プロポーザルが表示されていない」と捉えていました。

同時に、ページ全体では 398 件（Implemented 370・In progress 6・Approved 13・Deferred 6・Rejected 3）が
登録されています。ステータスチップを外して絞り込みを解除する、あるいは Implemented のような大きなバケットに
絞ると、一度に数百枚のカードや行が展開されます。テーブルビューは、検索・チップによる絞り込みをかけない限り、
常に 398 行をそのまま 1 枚のテーブルへ描画します。ページングが存在しないため、読者は目的の行を探すのに
延々とスクロールするか、列ソートに頼るほかありません。

この 2 つの症状は、「初期状態のカード折りたたみ」という BE-0094 の設計自体が壊れているために起きているのでは
ありません。折りたたみを解いて全体を見渡す手段が、見出しを 1 個ずつクリックするか、チップを 1 個ずつ外すことしか
ないために起きています。加えて、折りたたみを解いた先に量を制御する手段、つまりページングがないためでもあります。
したがって対策は、初期状態を変えることではありません。「未完了だけを一発で見る」「一括で開閉する」「テーブルは
1 ページに収まる量だけ見せる」という操作を追加すれば足ります。

## 3. どう実現するか

生成スクリプトは 1 ファイル（`scripts/build_roadmap_dashboard.py`）にまとまっています。このファイルには、
Python 側のマークアップ生成（`render_html()`・`_table()`）が収まっています。同じファイルに、インライン CSS
（`_STYLE`）とインライン JavaScript（`_SCRIPT`）も収まっています。今回の変更も、この 3 か所に閉じます。
ビルド時に計算できる値（カテゴリ数、Bucket 名）は Python 側で埋め込みます。絞り込み結果に応じて変わる値
（ページ数、どの行を隠すか）は、既存の `apply()` と同じくクライアント側の JavaScript で計算します。

### 未完了のみ表示ボタン

`render_html()`（`scripts/build_roadmap_dashboard.py:629` 付近）で、チップ生成の直後に次のボタンを
1 個追加します。チップ列（`.be-chips`）と並べて配置します。

```html
<button type="button" class="be-quickfilter" data-state="all">未完了のみ表示</button>
```

`data-state` 属性は、JavaScript 側が現在の表示状態（`all` / `open`）を記録する場所です。ラベルの
出し分けにも使います。ここでいう「未完了」は、Approved と In progress の 2 バケットに限ります。
`_topic_progress()`（`scripts/build_roadmap_dashboard.py:193`）は「outstanding」という値を使います。これは、
Rejected 以外（つまり Deferred を含む）を指します。この「未完了」は、それとは異なるボタン専用の狭い定義です。
Deferred は、意図して保留された項目です。「いま着手すべきものを探す」という本ボタンの用途に含めると、
Approved・In progress の信号が薄まります。両者を混同しないよう、実装ではこのボタンの対象バケットを専用の
定数として定義します。名前は `OPEN_BUCKETS = ("Approved", "In progress")` のように、それとわかるものに
します。この定数は `_SCRIPT` 内に置き、`_topic_progress()` 側の「outstanding」計算とは独立させます。

`_SCRIPT`（`scripts/build_roadmap_dashboard.py:887` 以下）に次のロジックを追加します。

- `apply()`（`scripts/build_roadmap_dashboard.py:914`）は、バケット名をキーに ON/OFF を持つ `on`
  オブジェクトを読んでいます。ボタンのクリックハンドラからも、この `on` を直接書き換えます。
- クリックされた瞬間の `on` の状態が「Approved と In progress だけ true、残り 3 バケットが false」と
  一致するかどうかを判定します。一致していなければ、その状態に書き換えます。一致していれば、5 バケットすべてを
  true に戻します（初期状態への復帰）。
- 対応するチェックボックス（`.be-check`）の `checked` プロパティを、書き換えた `on` の値に同期させます
  （チップの見た目とボタンの状態がずれないようにするためです）。
- 最後に、既存の `apply()` を呼びます。カードの表示・非表示と、カテゴリの展開状態を再計算させるためです。
  折りたたみ判定（`setCollapsed`, `scripts/build_roadmap_dashboard.py:906` 付近）は、チップの ON/OFF だけを
  見ています。そのため、この経路を通しても既存のロジックをそのまま利用できます。
- ボタンのラベルと `data-state` は、`apply()` の末尾でチップの状態を見て毎回更新します。チップを個別に
  クリックして、手動で「Approved と In progress だけ ON」の組み合わせを作った場合も、ラベルは
  「すべて表示」に自動で切り替わります。

### 一括展開・折りたたみボタン

同じ `.be-filters` 内に、次の 2 ボタンを追加します。

```html
<button type="button" class="be-expand-all">すべて展開</button>
<button type="button" class="be-collapse-all">すべて折りたたむ</button>
```

`_SCRIPT` 側では、それぞれのクリックハンドラで `document.querySelectorAll('.be-cat')` を全走査します。
既存の `setCollapsed(cat, false)` / `setCollapsed(cat, true)` を呼ぶだけです。この操作の結果は、
次にチップや検索を変更したときの `apply()` の再計算で上書きされます。見出しを 1 個ずつクリックする現在の
挙動（`scripts/build_roadmap_dashboard.py:968` 付近）と、同じ関数を再利用します。そのため、開閉状態の
内部表現（`is-collapsed` クラス）を 2 通りに増やす必要はありません。

### テーブルビューのページング

`_table()`（`scripts/build_roadmap_dashboard.py:259`）が返す HTML の直後に、ページ送り用のコンテナを
1 個追加します。

```html
<nav class="be-pager" aria-label="テーブルのページ送り"></nav>
```

ボタン自体は、Python 側では生成しません。絞り込みで一致する行数がページ数を決めるため、ページ数は実行時に
しか定まりません。空のコンテナだけを描画し、JavaScript が `<button data-page="1">1</button>` を必要な数だけ
動的に追加します。

`_SCRIPT` に次の要素を追加します。

- 定数 `TABLE_PAGE_SIZE = 50` と、現在のページを保持する変数 `tablePage`（初期値 1）。
- 関数 `matchedRows()`：`tbody.children` のうち、既存の絞り込みロジックが `is-hidden` を付けていない行を
  返します。検索とチップの両方を通過した行を、現在の DOM 順（＝現在のソート順）のまま配列で返します。
- 関数 `renderPager(total)`：`total` 件を `TABLE_PAGE_SIZE` で割ったページ数だけ、`.be-pager` の中身を
  作り直します。現在ページが新しいページ数を超えていれば、`tablePage` を末尾ページに丸めます。現在ページの
  ボタンには `aria-current="page"` を付けます。クリックされたら `tablePage` を更新して、次のステップへ進みます。
- 関数 `applyTablePaging()`：`matchedRows()` を呼び、`renderPager()` でページ送りボタンを更新します。
  そのうえで、`(tablePage - 1) * TABLE_PAGE_SIZE` 番目から `TABLE_PAGE_SIZE` 件だけを残します。それ以外の行に
  `is-paged-out` クラスを付けます。`is-hidden`（絞り込みで非該当）と `is-paged-out`（絞り込みには一致したが
  今のページに含まれない）は、別のクラスとして扱います。`_STYLE` 側では、両方とも `display:none` にします。
- `apply()`（`scripts/build_roadmap_dashboard.py:914`）の末尾にも処理を追加します。`rows.forEach` で
  `is-hidden` を付け終えた直後に、`tablePage = 1; applyTablePaging();` を呼びます。こうして、検索文字列や
  チップを変えるたびに 1 ページ目へ戻ります。
- `sortBy()`（`scripts/build_roadmap_dashboard.py:993`）にも処理を追加します。`tbody` の子要素を
  並べ替えた直後に、同様に `tablePage = 1; applyTablePaging();` を呼びます。

テーブルビュー（`.be-table-view`）は、最初から `is-hidden` が付いた状態で描画されます。この初期状態は
`render_html()`（`scripts/build_roadmap_dashboard.py:712`）が作ります。そのため、JavaScript が無効な環境
では、読者はそもそもこのビューへ切り替えられません。BE-0311 で確認済みのこの前提により、ページングは
no-JS 対応を別途作り込む必要がありません。no-JS 対応とは、JavaScript が動かない場合に全行を見せる配慮を
指します。ページングを実現する `is-paged-out` クラスは、JavaScript が実行されたときにしか付与されません。

## 4. 検討した代替案と、採らなかった理由

| 案 | 概要 | 採らなかった理由 |
|---|---|---|
| 初期状態で Implemented チップを OFF にする | ページを開いた直後から Implemented 以外（Approved・In progress・Deferred・Rejected）を含むカテゴリを自動展開させ、表示件数も 28 件に絞ります | BE-0094 が定めた「5 チップとも初期状態は ON」という前提を書き換えることになり、この設計に慣れている既存の読者の体験を変えてしまいます。同じ効果は、能動的にクリックする「未完了のみ表示」ボタンでも得られます |
| URL クエリパラメータでの初期フィルタ指定(例 `?status=approved`) | ページを開いた時点でクエリ文字列を読み、該当チップだけ ON にした状態で描画します | 「このリンクを開けば絞り込み済みの一覧が見える」という共有の要求は今回具体的に出ていません。実装するとページ読み込み時の初期化処理が増え、テストすべき状態遷移も増えます。将来、GitHub Issue やチャットへの共有が具体的な要求として挙がった時点で、別の提案として起こします |
| カードビューにもカテゴリ単位の「もっと見る」ボタンを追加する | 72 件の Platform support のような大きなカテゴリで、最初は上位 N 件だけ描画し、残りをボタンで開きます | カテゴリはすでに折りたたみで整理されており、絞り込みをかければ展開されるカード枚数は現実的な範囲に収まります。無条件に 398 行を並べてしまうテーブルビューと違い、カードビューの「一度に多すぎる」問題は本稿の調査では確認できませんでした |
| 「未完了のみ表示」の対象に Deferred を含める | `_topic_progress()` の「outstanding」(Rejected 以外)と揃え、Approved・In progress・Deferred の 3 バケットを対象にします | Deferred は着手を意図して保留した項目であり、「今すぐ手を付けるべきものを探す」というボタンの用途に含めると、Approved・In progress という直近のシグナルが薄まります |
| 1 ページあたりの件数を 25 / 50 / 100 / 全件から選べるようにする | 読者が自分でページサイズを選択する UI 要素を追加します | 現時点でその柔軟性を要求する具体的な理由がありません。UI 要素と実装・テストの手間が増えるだけで、50 件固定でも当面の「一度に多すぎる」問題は解消します |

## 実装時の追記

- 「すべて展開」ボタンを押した直後に検索やチップを変更すると、展開状態は `apply()` の再計算で
  上書きされます。手順 6 でブラウザから実際に操作して確認したところ、この上書きは既存の見出しクリックと
  同じ挙動だったので、意外な動きにはなりませんでした。
- テーブルのページ送りボタンには、既存の `.be-view-btn` ではなく `.be-issue` 系の小さな枠線ボタンに
  近い専用のスタイル（`.be-pager-btn`）を用意しました。1〜9 個の数字ボタンを並べるので、トグル的な
  `.be-viewtoggle` ではなく単体の枠線ボタンとして収まりよく仕上げました。
- ページ送りは、絞り込みで一致した行が 50 行以下でも「1」ボタンを 1 個だけ表示します（本稿どおり）。
  最初の実装ではページ数が 1 のとき早期リターンしてボタンを 0 個にしてしまっていましたが、手順 4 の
  ブラウザ確認で気づいて修正しました。
- 手順 6 で `make docs-serve` を実行したところ、本稿のスコープと無関係な既存の不具合に遭遇しました。
  `docs/api/config.md` は古いモジュールパス `bajutsu.config` を参照しています。実際のモジュールは
  `bajutsu.common.config` にあり、`mkdocstrings` はそれを見つけられずビルド全体が失敗します。確認のため
  ローカルで一時的にパスを直して検証し、確認後は元に戻しました（コミットはしていません）。この不具合自体は
  別タスクとして切り出しました。
- PR レビューで、テストがロジックを検証しておらず自己参照になっている指摘を受けました。`OPEN_BUCKETS` の
  期待値を、スクリプト側の JS リテラルの文字列一致だけで見ていました。`bri.BUCKETS`（チップの `data-filter`
  値の源）という真実の情報源とは突き合わせておらず、バケット名の変更を検知できない状態でした。パースした
  値を `bri.BUCKETS` と突き合わせる形に直しました。あわせて、「緩やかな一致」を謳う docstring の下で
  実際には完全一致だったアサーションも、正規表現による緩やかな一致に直しました。
- 同じレビューで、本稿 1 章の例示と「やらないこと」の節が、ページ数の分母を Implemented バケットだけと
  取り違えていた指摘も受けました。正しい分母は絞り込みをかけないときのテーブル全体（登録済みの全項目）で、
  本稿執筆時点のページ数は最大 9 です。該当箇所（`1 2 3 … 8` の例示と「最大 8」の記述）を修正しました。
- 本稿は当初、全体を常体（だ・である調）で書いていましたが、`japanese-document-writing` スキルと
  `CLAUDE.md` が定める「産出するすべての日本語は敬体で書く」という規範に反していたため、レビューの
  指摘を受けて全体を敬体（ですます調）に書き直しました。
