# Web UI ツアー：実機 Simulator を操作し、あらゆる証跡を収集する

これは **実機 Simulator で Bajutsu を評価する iOS 開発者**向けのデモです。ローカルの Web UI
（[`bajutsu serve`](../../docs/ja/cli.md)）を使って Simulator を起動し、showcase アプリに対して
シナリオを実行し、各実行が捕捉する証跡をブラウザで辿ります。証跡は、スクリーンショット、動画、
デバイスログ、通信、ビジュアルリグレッションの差分、システムアラート処理です。**合否の判定に AI が
介在することは一切ありません**。

まずセットアップ不要で同じ流れを見たい場合（Mac/Simulator 不要）は、
[60秒ツアー](../tour/README.ja.md) を実行してください: `uv run python demos/tour/tour.py`。

## 前提条件

- Xcode と起動できる Simulator のある macOS（`open -a Simulator`）。
- XCUITest ランナー。Web UI が必要時にビルドしますが、事前にビルドすることもできます:
  `make -C demos/showcase runner-build`。
- システムアラート部分のみ: `ANTHROPIC_API_KEY`（環境変数か gitignore された `.env`）。それ以外は
  完全に決定論的で、キーは不要です。

アプリを先にビルドする必要は**ありません**。`.app` が無い初回には、設定された `build` コマンドを Web UI が
実行し、選んだデバイスへインストールします。

## Web UI を起動する

```bash
make -C demos webui                  # http://127.0.0.1:8765  （変更は PORT=8766）
```

このターゲットはリポジトリ直下の `make serve` をラップし、[`showcase.config.yaml`](showcase.config.yaml) を
バインドします。この設定が Web UI を showcase の各アプリと、その [`scenarios/`](scenarios) にある
シナリオに向けます。表示された URL を開いてください。

> Web UI は必ず `make serve`（素の `bajutsu serve` ではなく）経由で起動してください。ラッパーが
> バックエンドの依存を必要時にインストールするので、クローン直後でも
> `no available actuator among ['xcuitest']` で失敗しません。

## ツアーの流れ

UI には 2 つのタブがあります。**Replay**（シナリオを決定論的に実行し、レポートを見る）と **Record**
（自然言語の目標からエージェントでシナリオを著作する）です。以下のツアーは、特記なき限り Replay で行います。

### 1. シナリオを実行してレポートを読む

**Replay → Run** で、`showcase-swiftui` アプリと、一覧から Simulator を選びます。停止中の Simulator は
自動で起動され、「booted」はすでに起動中のものを指します。`smoke.yaml` を選んで **Run** を押すと、
ライブログにデバイスの起動、初回のアプリのビルドとインストール、シナリオの実行が順に流れます。
完了すると、対話的な**レポート**が埋め込み表示されます。

レポートの **Result** パネルを開くと、各ステップに、操作対象の**スクリーンショット**と**アクセシビリティ
ツリー**が、一致した要素をハイライトした状態で表示されます。**Expectations** テーブルには、合否を決めた
機械的なアサーションが並びます。これが中心的な約束であり、ステップごとに監査できる決定論的な判定です。

### 2. 通信の記録（観測、そしてモック）

showcase は **BajutsuKit** をリンクしているので、アプリが行う各 HTTP(S) のやり取りを TLS の*後*で捕捉
します（プロキシも CA も不要）。通信を行うシナリオ（Stable カタログの `stable.refresh` や Log タブの
`log.submit`）を実行すると、レポートに **Network** タブが増えます。タブには各やり取り（メソッド、URL、
ステータス、所要時間、ヘッダ、ボディ）が並びます。あるリクエストは意図的に秘匿ヘッダとボディフィールドを
載せているので、redaction がそれらをその場でマスクする様子も見えます。

次に [`network_mock.yaml`](scenarios/network_mock.yaml) を実行します。同じ画面ですが、`mocks:` ルールが
実エンドポイントの代わりに定型のレスポンスを返します。Network タブはそのやり取りを **mocked** と示します。
ライブ依存のない決定論的な通信です。

### 3. ビジュアルリグレッション：UI からベースラインを承認する

[`visual.yaml`](scenarios/visual.yaml) を実行します。初回は**ベースラインが無い**ため `visual` の期待は
意図的に失敗し、レポートには捕捉したスクリーンショットと **「Approve as baseline」**ボタンが表示されます。
クリックすると、そのスクリーンショットが baselines フォルダへ昇格します。

再実行すると、今度はそのベースラインと**ピクセル比較**して合格します。後で画面がずれた場合は、レポートが
差分割合つきの**並列差分**（swipe / onion / blend モード）を表示します。`threshold` がアンチエイリアスの
揺れを許容し、`exclude` の矩形が変動領域（時計、ステータスバー、フローティングのタブバー）をマスクします。
UIKit と SwiftUI の双子は同じ画面を描きますがピクセル単位では一致しないので、それぞれが自分の
ベースライン一式を持ちます。

> CLI での同じ承認手順: `make -C demos/showcase vrt` のあと `vrt-approve`。

### 4. SpringBoard のシステムアラートを突破する

iOS バックエンドのアクセシビリティ照会は前面アプリしか見えないため、iOS のシステムプロンプト（権限ダイアログ）は
実行を静かにブロックします。**Dismiss alerts** を有効（既定）にして
[`permission.yaml`](scenarios/permission.yaml) を実行すると、Permissions タブが通知のプロンプトを出します。
反応型のアラートガードは、SpringBoard へのアクセシビリティ照会とタップで応答します。スクリーンショットも
モデルの往復も `ANTHROPIC_API_KEY` も要りません。ガードは全経路が決定的です。レポートの手順テーブルには、
タップしたボタンのラベルを伴う**「system alert dismissed」**の行が出ます。

どのプロンプトを想定し、そこで何と答えるかは、シナリオ自身の宣言です。
`interrupts` のエントリ `{ systemAlert: notifications, choice: grant }` なら通知のプロンプトを許可し、
`choice: deny` なら拒否します。どのエントリも特定できないアラートには手を触れず、止まったステップの失敗理由で
そのボタンを名指しします。

### 5. 動画とデバイスログ

シナリオはどれもシナリオ全体の画面録画を記録するので、どの実行のレポートにも **Video** タブ（シークバー
付き）と **Log** タブ（検索できるデバイスログ）が、`os_signpost` 区間のアプリ **Trace** とともに付きます。
[`modals.yaml`](scenarios/modals.yaml) を実行すると、4 種類のモーダルが開いて閉じる様子で動画がとりわけ
読みやすくなります。「X のたびに記録」をルールとして一度書けば、AI なしで毎回再現されます。証跡が
設定で決まります。

### 6. 自然言語から新しいシナリオを著作する（Record タブ）

**Record** タブに切り替えます。目標（「3番目の馬を開いて Favorite をオンにする」）を入力し、アプリと
エージェントを選んで **Record** を押します。エージェントがライブ画面を読み、一手ずつ提案します
（推論、アクションの順にストリーミングされます）。実行されたステップは決定論的なシナリオとして書き出され、
編集して **Save** し、Replay タブから再生できます。

`showcase-swiftui-noax` アプリを選ぶと、アプリが識別子を一切公開しないときにエージェントが
stability ladder を下っていく様子が見えます。showcase が示すために作られた、アクセシビリティの A/B です。
これは Tier 1（AI 著作）から Tier 2（決定論的再生）への受け渡しでもあり、アーキテクチャ全体が
一つのウィンドウに収まっています。

## このデモが示すもの

- **信頼でき、監査できる一つの判定**：合否は機械的なアサーションだけで決まり、それを裏付ける
  スクリーンショット、要素ツリー、通信、動画が各ステップに添付されます。
- **証跡の幅広さ**：UI の状態、通信（観測とモック）、ビジュアルリグレッション、システムアラート、動画、
  ログを、その場限りのスクリプトではなく再利用可能なルールで捕捉します。
- **AI は役立つところに、判定には決して**：著作（Record）とアラート処理は*操作*を補助し、ゲートは決定論
  のままです。
