## はじめに

Bajutsu のロードマップワークフローは、意図的に二段階に分かれています。
[`ideation`](../../.claude/skills/ideation/SKILL.md) スキルは BE（Bajutsu Evolution）項目の提案を
**執筆**し、ロードマップのファイルで手を止めます。[`implement-be`](../../.claude/skills/implement-be/SKILL.md)
スキルは、番号の付いた既存の項目をその ID から**出荷**します。この二つは、構造上かならず直列になります。
恒久的な `BE-NNNN` の ID は、提案 PR が `main` にマージされた**後**に初めて採番されるからです
（[BE-0089](../BE-0089-merge-time-be-id-allocation/BE-0089-merge-time-be-id-allocation-ja.md)）。
そのため、提案がマージされるまでは、本物の ID の下で実装を始められません。

この項目は、**三つめ**のスキルとして `propose-and-build` を追加します。想定するのは、小さくスコープの
定まった機能に対して、著者が十分な確信を持っている場合です。著者は提案とその実装を同時に書き、
ロードマップ項目、コード、テストをまとめて運ぶ **1 つの BE 作成 PR** として着地させます。

このスキルは `ideation` / `implement-be` を置き換えません。BE-0089 のマージ時採番も変えません。項目は
PR が生きているあいだ、`BE-XXXX` のプレースホルダを保ち続けます。PR がマージされた瞬間に、通常の提案と
まったく同じように、CI が本物の ID を採番します。設計をコードより先にレビューしたいケースでは、これまで
どおり直列の経路が既定のままです。

## 動機

### 直列の経路には実際の待ち時間があり、小さな項目ではそれが純粋なオーバーヘッドになる

`ideation` → マージ → 採番 → `implement-be` という連鎖は、既定として妥当です。コードを書く前に、設計を
レビューに通すことを強制します。実際に出荷される項目にだけ番号を使うので、`BE-NNNN` の連番も隙間なく
保てます（BE-0089）。しかしこの連鎖は、二つの活動を直列にしてしまいます。小さくリスクの低い機能では、
著者がその両方をすでに頭の中に完成した形で持っていることが多いからです。そうした項目でも、著者は次の
手順を踏まなければなりません。

1. `ideation` を実行し、提案 PR を開いて、マージされるのを**待つ**。
2. `roadmap-id` ワークフローが `main` 上で `BE-NNNN` を採番するのを待つ。
3. そこで初めて `implement-be BE-NNNN` を実行し、手順 1 で持っていた文脈をすべて立て直す。

手順 1 と手順 3 のあいだの待ちは、著者が今すぐ作れる変更にとっては空白の時間です。手順 3 では、文脈を
取り戻すためのコストも払います。提案、関連箇所、周辺コードを読み直すコストです。このコストは、
ideation の段階ですでに払っています。プライムディレクティブのどれも、この直列化を要求していません。
直列化は ID 採番のタイミングから派生したもので、正しさの必要から来たものではありません。

### マージ時採番は 1 つの PR の形を決めるが、1 つの PR を妨げはしない

「提案と並べてコードも書き、両方まとめて着地させればよい」という素朴な解決は、BE-0089 とぶつかるように
見えます。PR がマージされるまで、項目に本物の ID がないからです。しかし、二つの事実を分けて見れば、
ぶつかりません。

第一に、`implement-be` の PR が通常持つ二つの仕上げは、どちらも番号を必要とするわけではありません。

- 項目を `Status: Implemented` にする処理と、`Implementing PR` 行を記録する処理は、状態と PR 番号だけに
  依存します。ID には依存しません。そのため項目は、`BE-XXXX` のプレースホルダを保ったまま
  `Status: Implemented` に到達できます。
- `roadmap-id` ワークフローが、マージ時にプレースホルダを採番後の `BE-NNNN` へ書き換えます。項目は、
  マージ後の手直しなしに、採番されて Implemented の状態で着地します。
- 番号を本当に必要とするのは、`[BE-NNNN]` タイトルプレフィックスだけです。BE 作成 PR は、これを持つ
  必要がありません。`scripts/lint_pr.py` がタイトルチェックを働かせるのは、ブランチ名が本物の ID を
  含む場合だけです。`claude/<topic>` のようなブランチは、ID を含みません。素の scoped タイトルは、
  あらゆる提案 PR と同じく、ここでも正しい形です。

第二に、採番スクリプト（[`scripts/allocate_roadmap_ids.py`](../../scripts/allocate_roadmap_ids.py)）は、
`BE-XXXX` → `BE-NNNN` の書き換えを**項目自身のディレクトリの中だけ**で行います。リポジトリ全体は
走査しません。したがって、マージ時採番がこのフローに課す制約は一つです。`BE-XXXX` のプレースホルダが、
項目自身のファイル以外のどこにも現れてはなりません。実装コード、テスト、コメント、別の場所のドキュメントに
書かれたプレースホルダは、マージを越えて、`main` に古い参照として残ります。

このように、マージ時採番は、ID が現れてよい場所を定めることで 1 つの PR の*形を決めます*。1 つの PR を
退けるわけではありません。

### なぜドキュメントの注記ではなくスキルにするのか

1 つの PR のフローには、小さく正確で、間違えやすい規律があります。

- プレースホルダの ID を、項目自身のファイルに閉じ込めます。
- 番号を待たずに、プレースホルダの上で `Status: Implemented` にします。
- タイトルを素のまま保ちます。
- `roadmap-id` を実際に発火させる経路でマージします。

このフローをスキルとして符号化すれば、安全な経路がそのまま楽な経路になります。`ideation` と
`implement-be` も、それぞれのフローを同じやり方で符号化しており、既存の二つのスキルは変更されず、
単一の役目のまま保たれます。

## 詳細設計

`propose-and-build` は、二つの既存スキルの**合成**です。どちらかを書き直すものではありません。
`ideation` の執筆規則と `implement-be` の実装および昇格の規則を、そのまま再利用します。新しい内容は
三つだけです。1 つの PR の段取り、ID を閉じ込める不変条件、*いつ*これを使うかについての
プライムディレクティブ由来のガードレールです。

### 1 つの PR とそのライフサイクル

```
                 （小さくスコープの定まった機能に著者が確信を持っている）
                                    │
                                    ▼
   1 本のブランチ: claude/<topic>   base: main
     roadmaps/BE-XXXX-<slug>/  @ Status: Implemented   （プレースホルダ ID。BE-XXXX は
     提案仕様に対するコード + テスト                       項目自身のファイルの中だけ）
     素の scoped タイトル、[BE-…] プレフィックスなし
                                    │
                                    │  人が PR を開き、Implementing PR 行の番号は
                                    │  追いの push で埋め、そのうえでマージする
                                    ▼
   roadmap-id が main 上で BE-NNNN を採番（BE-0089）
     · BE-XXXX-<slug>/ → BE-NNNN-<slug>/ にリネーム
     · 項目自身のファイルの中で BE-XXXX → BE-NNNN を書き換え
                                    │
                                    ▼
   項目は採番されて Implemented の状態で着地。マージ後の手直しなし
```

`BE-XXXX` のプレースホルダは、PR のレビュー全体を通じて生きています。番号が確定する唯一の地点は、
マージです。番号を*いつ*採番するかは何も変わらないので、この設計は BE-0089 と両立します。スキルは、
マージ時の書き換えが仕上がった項目を着地させるように、PR を整えるだけです。

### 作業分解（MECE）

1. **SKILL.md を執筆する。** `.claude/skills/propose-and-build/SKILL.md` を作成します。フロントマターと、
   以下の各フェーズを構造とする本文を持たせます。
   - フロントマターには、`name: propose-and-build` と、BE-0103 に沿った既定の `model:` を置きます。
     `description` には、「提案と実装を同時に作る」「BE とコードを一緒に書く」といったトリガー句を
     含めます。
   - 本文は、`ideation` と `implement-be` の内容を複製せず、リンクで参照します。
2. **フェーズ A：提案を執筆する（`ideation` の規則に委譲）。** `claude/<topic>` を `origin/main` から
   切ります。`make new-roadmap-item` で、`BE-XXXX-<slug>/` を `Status: Approved` として scaffold
   します。内容は [`document-writing`](../../.claude/skills/document-writing/SKILL.md) スキルに従って埋め、
   日本語側は [`japanese-document-writing`](../../.claude/skills/japanese-document-writing/SKILL.md)
   に従って整えます。作業は `ideation` と同一であり、スキルは再掲せず、そのことを述べます。
3. **フェーズ B：プレースホルダに対して実装する（`implement-be` ステップ 3〜9 に委譲）。** **同じ
   ブランチ**で、`BE-XXXX-<slug>/` の提案を仕様として扱います。`implement-be` のうち、コードを読み込む
   ステップ、計画して確認するステップ、テスト付きで実装するステップ、差分をレビューするステップを
   実行します。そのうえで、昇格ステップを**この時点で**実行します。`Status` と PR 番号は、ID に依存
   しないからです。
   - 両言語のファイルで `Status: Implemented` に変え、`Progress` のチェックを付けます。`BE-XXXX` の
     プレースホルダは保ちます。
   - `Implementing PR` 行を追加します。PR 番号はフェーズ B のあいだ存在しないので、行の番号は、人が
     PR を開いたあとの追いの push で埋めます。`implement-be` がステップ 8 の埋めをステップ 10 に先送り
     するのと同じやり方です。
   - 二つの処理は先送りします。番号か、マージ後にしか存在しない Issue が必要だからです。一つは
     `[BE-NNNN]` タイトルプレフィックスで、PR は素の scoped タイトルのままにします。もう一つは
     トラッキング Issue の自己アサインです。[BE-0109](../BE-0109-roadmap-tracking-issues/BE-0109-roadmap-tracking-issues-ja.md)
     の Issue は、番号の付いた項目が `main` に存在してから作成されます。
   - これは、ID がマージ時にのみ採番される BE 作成 PR です。そのため、スキルはこの PR を自動では
     作成しません。ブランチを push して、人が開くのに委ねます（BE-0230）。PR は製品コードを含むので、
     Draft として開きます。
4. **唯一の不変条件：プレースホルダの ID を閉じ込める。** スキルは、`BE-XXXX` が項目自身のディレクトリ
   （`roadmaps/BE-XXXX-<slug>/`）**以外のどこにも**現れてはならないと、はっきり述べます。採番が、その
   ディレクトリだけを書き換えるからです。コードでは、機能を名前で参照します。ID は、採番が直す唯一の
   場所であるロードマップ項目に置きます。ほかの場所に書いた参照は、`main` に古いまま残ります。CI は、
   それを捉えません。ロードマップのフォーマットチェックは、`roadmaps/` の中しか歩かないからです。
5. **マージは採番を発火させねばならない。** 既定の `GITHUB_TOKEN`（ネイティブ auto-merge）によるマージは、
   `push` 起動のワークフローを再発火させません。その場合は `roadmap-id` が走らず、PR はコードごと
   `BE-XXXX` が未採番のまま `main` に着地します。スキルは、これを注記します。PR は、`roadmap-id` を発火
   させる経路でマージしなければなりません。手動マージか、ロードマップ App トークンでの auto-merge です。
   素の `ideation` 提案も、すでに同じ制約の下にあります。ここでは、実装が項目とともに着地するぶん、
   制約がより重く効きます。
6. **ガードレールとスコープ（プライムディレクティブ由来）。** スキルは、*いつ*これを使い、いつ使わない
   かを、はっきり述べます。
   - 使うのは、小さくスコープの定まった項目で、著者が設計をレビューで大きく変えるとは見込んでいない
     場合に限ります。1 つの PR は、設計のチェックポイントをコードレビューと一体にします。そのため、
     マージは提案と実装を一度に受け入れます。スキルは、これを許容したトレードオフとして明記します。
     設計が本当に不確かなときは、直列の経路に戻すよう述べます。
   - このスキルは、執筆*と*実装の両方を行います。製品コードに一切触れない `ideation` とは違い、
     `bajutsu/` / `BajutsuKit/` / テストを `implement-be` の規則の下で**変更します**。スキルは、
     フェーズ A が執筆のみにとどまり、製品コードはフェーズ B でだけ現れることを明示します。
   - 三つのプライムディレクティブは、`implement-be` の場合とまったく同じように効きます。`run` / CI の
     判定経路に LLM を置かないこと、決定性を最優先すること、アプリ非依存の設定に寄せることです。
     スキルは人間とエージェントの手順にすぎず、CI に自動化を足しません。そのため、どのゲートにも新しい
     仕組みを持ち込みません。
7. **ドキュメント。** [`docs/ai-development.md`](../../docs/ai-development.md)（と `docs/ja/` の対応版）に
   ある、三つのスキルの三角形と、コントリビュータ向けチュートリアルを、スキルと歩調を合わせます。
   `ideation` は執筆のみ、`implement-be` は番号付き項目の出荷、`propose-and-build` は両方を 1 つの PR で
   行います。三つの SKILL.md の `References` を相互リンクします。

### 機械的に検証できる成果

このスキルは手順です。決定的な成果は、PR が生み出したものに既存のゲートを当てたものになります。
`make check` が緑であること。ID が採番されたあと、ロードマップダッシュボードが `Status: Implemented` を
反映していること。CI の `pr-title` チェックのとおり、BE 作成ブランチが保つべき素の scoped タイトルで
あること。このチェックは、ブランチが本物の ID を含む場合にだけ働きます。このフローのブランチは、
決して含みません。

新しいチェッカーは足しません。スキルの正しさは、すでにゲートされている `implement-be` の終状態と、
SKILL.md が符号化する ID を閉じ込める不変条件に帰着します。

## 検討した代替案

- **何もせず、`ideation` → `implement-be` の厳密な直列分割を保つ案。** 安全な既定であり、ほとんどの項目
  では今も正しい選択です。*唯一の*選択肢としてだけ、却下します。著者が今すぐ作れる小さな項目に、避けられる
  待ち時間と文脈の取り直しを課すからです（動機を参照）。
- **一時的な二本の PR のスタック（この項目の元の設計）。** スタックは、提案 PR と、その提案ブランチに
  積んだ実装 PR、そして提案がマージされたあとに実装を `main` へリベースして付け替える引き継ぎで構成
  します。これは、`propose-and-build` が最初に出荷された形です（#848）。スタックの目的は、実装を仕上げる
  前に本物の ID を取り戻すことでした。実装 PR は `[BE-NNNN]` タイトルプレフィックスを取れて、固まった
  仕様に対してリベースできます。スキル自身のスコープ、つまり著者が確信を持つ小さな設計では、この二つの
  見返りはどちらも成り立ちません。プレフィックスは不要です。BE 作成 PR は素のタイトルを保つからです。
  固め直すべき仕様もありません。一方でスタックには、二本目のブランチ、提案の変化に追随して draft PR を
  リベースし続ける手間、ベースの付け替え、間違えやすい引き継ぎのリベースという費用がかかります。1 つの
  PR の設計（#1304）は、これらをすべて取り除き、規則を一つ加えるだけで済ませます。加えるのは、
  プレースホルダの ID を閉じ込める規則です。この設計が、スタック案に取って代わりました。
- **`BE-XXXX` の規律を持たない巨大な単一 PR の案。** ブランチ運用は最も単純です。この項目が今採る設計
  そのものでもありますが、それは ID を閉じ込める不変条件が*あってこそ*です。不変条件がなければ、実装に
  書かれた ID が `main` に古いまま残ります。採番が、項目自身のディレクトリしか書き換えないからです。
  この不変条件が、単一 PR を単に単純なものではなく、安全なものにします。そのためスキルは、不変条件を
  慣習ではなく厳格な規則として述べます。
- **ID を早く採番する案（PR オープン時または承認時）。** PR が最初から本物の番号を持てるので、
  `[BE-NNNN]` プレフィックスを最初から取れます。しかしこの案は、BE-0089 が閉じたまさにその決定を開き直し
  ます。項目が受理される前に番号を使うことになり、PR が却下されると ID が連番でなくなります。
  リポジトリ全体の不変条件にスキル単位の例外を設けるのは、それが買う素のタイトルよりも悪い取引です。
  却下します。
- **ID を閉じ込める不変条件を CI で強制する案。** このチェックは、プレースホルダ項目自身のディレクトリの
  外に `BE-XXXX` が現れないことを確かめます。唯一の規則をゲートにできる点で魅力的です。しかし、
  リポジトリ全体の `BE-XXXX` 走査は、本当に古い参照を、正当なプレースホルダの自己参照、散文中の例、
  タイトルプレフィックスの例から見分けなければなりません。ロードマップのフォーマットチェックが
  `roadmaps/` の中ですでにかわしているのと、同じ誤検出の面です。見送ります。スキルは、まず不変条件を
  規律として述べます。範囲を絞ったチェックは、フローが実証されてからの後続候補です。
