## はじめに

`bajutsu serve` は、Python 標準ライブラリだけで作った小規模なブラウザランチャです。シナリオとアプリの一覧を表示し、ワンクリックでシナリオを実行し、実行ログをストリーミングし、レポートを表示します。[Tier 1](../../docs/ja/glossary.md#2-つの層) の利便機能であり、CI ゲートには含まれません。予定している GUI エディタ（可視編集と要素ピッカー）の基盤にもなります。

## 動機

CLI が契約ではありますが、シナリオを書いて再実行する手段としては必ずしも使いやすくありません。1 回の実行のたびに、`run` / `record` の適切なフラグを思い出し、アプリと Simulator を選び、バイナリが古ければ先にビルドする必要があります。その後、生成された `report.html` を手で開きます。この手間は、ツールが安く回せるようにしたいループ（書く、実行する、レポートを見る、直す）をまさに妨げます。

小さなランチャがこの手間を取り除きます。アプリとシナリオを選んでクリックすれば、出力がストリームされ、レポートが表示されます。レポートの相対アセットリンクが解決するよう、実行の証跡も配信します。あくまで Tier 1 の利便機能であり、CI ゲートには含めません。予定する GUI エディタ（[BE-0013](../BE-0013-scenario-gui-editor/BE-0013-scenario-gui-editor-ja.md)）や、より充実した record フローの置き場所にもなります。

## 詳細設計

実装は `bajutsu/serve/` にあります。起動は必ず `make serve` で行い、`bajutsu serve` を直接呼ばないでください。`make` のラッパが idb backend の依存（idb クライアントと `idb_companion`）をオンデマンドで導入します。素の `serve` はこの手順を飛ばすので、実行が `no available actuator` で失敗します。

サーバは標準ライブラリだけで構成します。`127.0.0.1` にバインドした `ThreadingHTTPServer` で、network collector と同じ方式です。シングルページアプリのシェルと CSS / JS は、`bajutsu/templates/serve.*` から 1 つの自己完結 HTML レスポンスにインライン化します。`/static` ルートは別途設けません。CLI の上に 2 つのトップレベルタブを置きます。

* **Record** は、自然言語のゴールからシナリオを生成します。`python -m bajutsu record …` を起動し、エージェントのターンごとの進捗をストリームします。結果は、選択したアプリの設定済みシナリオディレクトリに自動命名で書き出し、既存ファイルは上書きしません。
* **Replay** は、`python -m bajutsu run …` でシナリオを実行し、完了時に生成された `report.html` を埋め込みます。**History** 一覧から過去の実行を再表示できます。**Approve** ボタンは、撮影したスクリーンショットを `visual` ベースラインへ昇格します（`POST /api/approve`）。

各リクエストは、バックグラウンドスレッドで CLI を起動します（`run_job`）。ジョブは次の 4 手順で進みます。

1. 選択した Simulator を並列に起動します。
2. アプリのバイナリが無ければ、オンデマンドでビルドします（config の `apps.<name>.build`）。
3. コマンドを実行し、結合出力を 1 行ずつ取り込みます。
4. 取り込んだ出力から、生成された `runs/<id>` を解析します。

ジョブはキャンセル可能です。起動される子プロセスは serve プロセスの環境を継承します。`idb` クライアントが解決するよう、venv の `bin` を `PATH` の先頭に付けます。

アプリ差分は config に閉じます。アプリのドロップダウン、アプリのシナリオディレクトリ、ビルドコマンド、`appPath` はすべて `apps.<name>` 由来なので、サーバ自体は app-agnostic です。`--config` は任意です。`--root` に閉じたファイルブラウザから、UI 上で config ファイルを開けます。

決定性は保たれます。このサーバが pass/fail を判定することは一切ありません。UI は決定的な `run` をシェル経由で呼ぶだけです。ループに入る AI は、`record`（Tier 1）とオプトインのアラートガードのみです。UI が設定する唯一のシークレット `ANTHROPIC_API_KEY` は、そのセッション中だけメモリに保持し、ディスクには書きません。起動したジョブがこのシークレットを継承します。

## 検討した代替案

* **重量級の Web フレームワーク（Flask / FastAPI）と、ビルドステップを伴うフロントエンド。** 不採用です。localhost のオーサリング利便機能のために、依存の重さや別のアセットパイプラインを抱える理由はありません。標準ライブラリの `ThreadingHTTPServer` とインライン化したテンプレートなら、まっさらなクローンからインストールでき、既存の network collector とも揃います。
* **ネイティブのデスクトップアプリやインプロセス GUI。** 不採用です。ブラウザはすでに普遍的で、追加のツールキットが要りません。ランナーがすでに生成する自己完結の `report.html` もそのまま表示できます。レポート表示を作り直さず、既存のレポートを再利用します。
* **CLI を起動せず、インプロセスでデバイスを駆動する。** 不採用です。同じ `run` / `record` コマンドをシェル経由で呼べば、CLI が唯一の契約のままなので、UI が CI の挙動から乖離しません。キャンセルと分離も自然に得られます。
