## はじめに

このBE項目は、push前のローカルレビュー工程を、1つの役割から2つの役割に分割します。この工程は、「Claude review」のGitHub Actionsワークフローの契約（[BE-0203][]）をすでに模倣しています。

- **Fable**が担うレビュー・計画役は、[`.github/claude-review-prompt.md`](../../.github/claude-review-prompt.md)に基づいて指摘を分類し、修正指示を書き出します。
- **SonnetまたはOpus**が担う実装役は、その指示をそのまま適用します。

さらに、CIワークフロー自体の起動条件を、pushごとの自動実行から、オープン・再オープン時の自動実行と明示的な依頼による実行に絞り込みます。そのうえで、レビューと修正のサイクルに回数の上限を設けます。目指す結果は、レビューコメントがゼロに収束するPRです。実質的に終わりのないライブサイクルは目指しません。

## 動機

実際のPRでは、「Claude review」の指摘に対応してpushしても、収束しないことがよくあります。ボット（[`.github/workflows/claude-review.yml`][claude-review.yml]）はpushのたびに自動的に再レビューし（`pull_request: types: [opened, synchronize, reopened]`）、修正そのものに新たな指摘を出すことがあります。そのため、修正・push・レビューのサイクルが収まらずに繰り返され続ける場合があります。

`implement-be`は、PRを「静かで緑」の状態まで導くフォローアップループを走らせています。このループは、次の3つの条件がそろって初めて停止します。

- CIが緑になっている。
- レビューに`CHANGES_REQUESTED`が付いていない。
- 2回連続のポーリングで新しいコメントが見つからない。

ボットが毎回何かを見つけ続ける限り、3番目の条件は成立せず、ループには他の出口がありません。レビュー契約はすでに2回、機能面への影響だけに絞る厳格な重大度の下限まで引き締められました。ボットも、より厳しく判定するためにOpusで動いています。それでも堂々巡りが起こるのは、これらの変更が契約のルールを引き締めたにすぎないからです。ライブサイクルを無制限に走らせてしまう手順そのものは、直っていません。

このリポジトリには、この穴をふさぐための仕組みがすでにあります。pushの前に同じ契約をローカルで模倣するセルフレビューです。この工程は`ideation`のステップ5（本家の手順）、`pr-followup`のステップ4、`propose-and-build`のフェーズAに置かれ、`implement-be`のステップ7と12が引き継いでいます。工程は自分自身を3ラウンドで打ち切っており、その根拠は今回の課題そのものを述べています。LLM（大規模言語モデル）によるレビュアーは完全に決定論的ではなく、自分自身の直前の修正が原因で生じた新たな指摘を、毎ラウンド出しかねないというものです。

ところが、この工程は今、1体の新規サブエージェントに、契約に照らした指摘出しと、見つけた指摘の修正を両方担わせています。この兼任が、堂々巡りを生んでいる可能性があります。自分の指摘を自分で直すエージェントは、その1件のコメントを黙らせる最小限の修正で済ませがちです。すると隣接する問題が残り、次のラウンドの自分自身か、push後のライブのボットが、その問題を再び見つけます。

`fable`は、このリポジトリのツール（`tests/test_skill_models.py`の`KNOWN_ALIASES`）がすでに認識しているClaude Codeのモデル別名です。しかし現時点では、どの役割にも割り当てられていません。判断だけを行い、実装はしないレビュー・計画役に適した別名です。

「何を変えるべきか」と「実際に変える」を分離すれば、各ラウンドは指摘を先送りせず、実際に消化できるはずです。それによって、ローカルの工程はpushの前に収束します。ライブのボット自身の再レビューサイクルが始まる頻度も、下がるはずです。

ただし、残存リスクは取り除かれるわけではなく、抑えられるにすぎません。ローカルの工程を鋭くしても、ライブのボットが何も新しく見つけないことは保証できないためです。そのため、フォローアップループにはライブサイクル自体にも明示的な回数上限を設けます。上限に達したら、人間にエスカレーションします。マージコンフリクトがすでに受けている扱いと同じで、無制限に反復を続けることはありません。

## 詳細設計

1. **`ideation`のステップ5：本家のセルフレビューを2つの役割に分割する。** 今のステップは、1体のサブエージェントに、契約の全レンズに照らした批評と、見つけた指摘の修正を両方担わせています。これを2つのパスに分割します。
   - レビュー・計画役は、重大度の下限を超える指摘を、文章表現のレンズと機能面のレンズの両方にわたって洗い出します。それぞれを、具体的な修正指示（ファイル、正確な位置、正確な変更内容）か、真の設計変更を要するエスカレーションのいずれかに分類します。この役はファイルを一切編集しません。
   - 実装役は、与えられた修正指示をそのまま適用するだけです。重大度を自分で再判定せず、範囲も広げません。指示が安全でないか誤っていると判断した場合は、黙って別の対応をせず、その旨を報告します。

   ループは、更新後の差分に対して新しいレビュー・計画役を走らせ、そのラウンドで見送った指摘とその根拠を次のラウンドに引き継ぎます。既存の3ラウンド上限は保ちます。この上限はもともとレビューの回数を数えており、修正の試行数ではないため、回数自体は変わりません。
2. **`pr-followup`のステップ4：同じ分割を引き継ぐ。** このステップは、すでに`ideation`のステップ5の手順を、3点の差分を付けて実行しています。差分は、`origin/main`に対する新規差分の代わりにローカル差分を使うこと、`roadmaps/`への絞り込みをしないこと、PR自体の議論とエスカレーション先を使うことです。ここをユニット1の2ロール手順に向け直します。エスカレーションの表現は、「真の設計変更を要する指摘」から「レビュー・計画役によるエスカレーション」に改め、分類済みの出力形式に合わせます。
3. **`pr-followup`のステップ5：ライブの確認を明示的に依頼する。** ユニット2のセルフレビューがクリーンで返ってきた（エスカレーションではない）pushの後、PRに`@claude review`を含むコメントを投稿します。これは、ワークフローがすでに備えているオンデマンドの依頼経路で、ライブの確認を依頼するものです。ユニット6で取り除く自動トリガーには頼りません。

   今の依頼経路は`prompt`を空のまま渡すため、アクションのデフォルトの`@claude`メンション処理に委ねられます。そのためユニット6では、コメントイベントに対しても、契約のプロンプトと既出の指摘の入力の両方を渡す必要があります。「レビュー入力の算出」ステップは、現状では`pull_request`イベントでしかこの2つを組み立てません。渡さなければ、依頼したレビューは次のものを持たないまま走ります。
   - `.github/claude-review-prompt.md`
   - その重大度の下限
   - `🤖 **Claude Code**`の接頭辞
   - PRにすでに投稿済みの指摘を再投稿しないための重複排除

   今回の反復で何もpushしていない場合や、セルフレビューがクリーンにならずエスカレーションした場合は、依頼を見送ります。どちらの場合も、PRはレビューできる安定した状態にないためです。

   投稿したあとは、レビューが実際に走ったことを確認し、走っていなければエスカレーションします。ワークフローは、コメント投稿者が`OWNER`/`MEMBER`/`COLLABORATOR`のいずれでもなければ、PR上に何の痕跡も残さずに依頼を捨てます。ユニット5が、その無反応を「指摘なしのポーリング」と読み違えてしまうためです。確認するのは実行そのものではなくジョブです。trusted actorの判定はジョブの`if:`にあるので、依頼が捨てられても実行自体は作られ、`claude review`ジョブが`skipped`のままgreenで終わります。実行は、依頼したアカウントと作成時刻で探します（たとえば`gh run list --workflow "Claude review" --event issue_comment --user <アカウント> --created ">＜時刻＞"`。時刻はコメント投稿前に控えておきます）。コメント起因の実行はデフォルトブランチに対して走るため、`--branch`では見つかりません。そのうえで、`gh run view`でジョブの結果を読みます。
4. **`propose-and-build`のフェーズA：参照によって同じ分割を引き継ぐ。** このフェーズのセルフレビューは、`ideation`のステップ5を短くまとめ直したものです。1体のサブエージェントが批評と修正の両方を担うという記述をやめ、ユニット1の2ロール手順を参照するように改めます。フェーズBと`implement-be`のステップ12は、すでに`ideation`のステップ5か`pr-followup`を名前で参照しています。そのため、個別の編集なしにユニット1から3までを引き継ぎます。

   `implement-be`のステップ7は引き継ぎません。1体構成そのものを本文で述べ直しているためです（「新規サブエージェントに本文として渡す」と、その「この手順との2点の差分」）。この記述を2ロール手順に向け直し、契約の本文と、ステップ8と10が未了であるという但し書きを、どちらの役割が受け取るのかを明記します。
5. **`implement-be`のステップ12：回数上限でライブサイクルを抑える。** ループの「2回連続で指摘なし」という停止条件は、今は「人間かボットかを問わず、新しいレビューコメントが付かなかった」ことを意味します。人間の側はそのまま残し、ボットの側を改めます。ポーリングが静かなのは、新しい人間のレビューコメントが見つからず、かつ次のいずれかに当てはまる場合です。今回の反復でライブレビューを依頼しなかったか、依頼したレビューが何も新しく見つけなかった場合です。

   ループがすでに持つレビュー待ち（20回）とCI待ち（30回）の上限に並べて、3つ目のカウンターを追加します。ある反復が「ローカルのセルフレビューはクリーンで、ライブレビューを依頼したが、次のポーリングで新しいレビューコメントが見つかった」と報告するたびに、カウンターを1つ増やします。ライブレビューがクリーンで返ってきたら、リセットします。上限は、ローカルのセルフレビューループ自体の上限に合わせて3とします。

   3回目に達したら、ループを止めて、人間にサマリー付きでエスカレーションします。無制限に反復を続けることはありません。この条件は、ループの既存のエスカレーション条件に並べて追加します。既存の条件は、`pr-followup`が設計変更を要すると判断したコメント、マージコンフリクト、未対応のスレッドが一度もなかった状態での`CHANGES_REQUESTED`です。
6. **`.github/workflows/claude-review.yml`：自動トリガーを絞り込む。** `pull_request`トリガーの`types`から`synchronize`を外し、`opened`と`reopened`だけを残します。
   - 同じ変更のなかで、`prose-companion`ジョブの`github.event_name == 'pull_request'`という条件も、オンデマンドのコメントイベントまで広げます。広げなければ、オープンのイベントより後に出た文章表現だけの指摘を適用するジョブがなくなり、BE-0343が以後のすべてのレビューで機能しなくなります。
   - 以後のすべての確認は、ワークフローがすでに備えている`@claude review`というコメント経由のオンデマンド経路を通じて依頼します。この経路は`OWNER`/`MEMBER`/`COLLABORATOR`にすでに限定されており、通常はユニット3が依頼を発行します。
   - ファイル冒頭のコメントブロックも、この新しい運用モデルを説明するように改めます。このワークフローを削除せず残す理由も、明示します。フォークからのPRや、これらのClaude Codeスキル群を経由しない直接のcommitは、ローカルのセルフレビューの工程を一度も通りません。ワークフローを残さなければ、レビューを一切受けられなくなります。
   - 「レビュー入力（既出の指摘）の算出」ステップも、コメントイベントまで広げます。今は`github.event_name == 'pull_request'`で絞られているため、そのままではオンデマンドの実行が既出の指摘を空のまま始めてしまい、決着済みの指摘を再投稿します。
   - あわせて、`cancel-in-progress`が`pull_request`に対してのみ真であることにも触れます。短い間隔でオンデマンドの依頼が2回出ると、後の実行が前の実行を打ち消さず、並行して走ります。
7. **`docs/ai-development.md`とその日本語ミラー：分割とトリガー変更を記録する。** 「モデルと推論エフォートの適正化」の節に、新しい小節を追加します。小節には次の内容を記録します。
   - ローカル工程のレビュー・計画役としてFableを指名すること。
   - 実装役はSonnet基本とし、製品コードに触れる場合はOpusとするルール。
   - CIトリガーの絞り込みと、その後ろ盾としての位置づけの根拠。

   この節には、「PRレビュー」を中位（`sonnet`）に位置づけるタスクと能力の対応表がすでにあります。小節では、その項目との関係も明記します。既存の項目が指すのは、依頼を受けて他者のPR全体を読んで意見を返す作業です。この項目のレビュー・計画役は、ローカルのセルフレビュー工程の内側で指摘を分類するだけの別の作業です。この違いを明示しなければ、2つの項目が同じ問いに矛盾する答えを出しているように読めてしまいます。

   日本語ミラーは、英語からの機械的な翻訳ではなく、このリポジトリの日本語文章規範のもとで新たに書き下ろします。
8. **影響を受ける4つの`SKILL.md`アダプター：使用するモデルを明記する。** `ideation`、`pr-followup`、`propose-and-build`、`implement-be`のそれぞれの既存の本文に一行を追加します。レビュー・計画役には`fable`を、実装役には`sonnet`か`opus`を指名します。どちらを選ぶかは、このリポジトリのモデル階層の規約が他の場面ですでに使っている、作業内容による重みづけに従います。`roadmaps/`や`docs/`に収まる修正は中位のままで、製品コードに触れる修正は重位に上がります。いずれの追加も、各スキルの全体的なデフォルト値である`SKILL.md`のフロントマターの`model:`キーそのものは変更しません。

## 検討した代替案

**自動トリガーをpushごとのままにし、ローカルの工程を鋭くするだけで、CIが見つける指摘を減らす。** 見送りました。ローカルの工程が自分自身の契約に照らして指摘ゼロまで到達しても、ライブのボット自身の非決定性が、次のpushで新たな些細な指摘を出さないことまでは保証できません。この代替案は堂々巡りの頻度を下げるだけで、上限を設けるわけではありません。最悪の場合、ライブサイクルは無制限に走り続けます。

**ローカルの工程が信頼できるようになった段階で、「Claude review」のGitHub Actionsワークフローを完全に廃止する。** 見送りました。理由は2つあります。フォークからのPRは、設計上レビュー用の認証情報付きでチェックアウトされません（フォークからの通常の`pull_request`イベントはシークレットを一切運ばないためです）。また、これらのClaude Codeスキル群を経由しない直接のcommit（人間が直接pushする場合など）も、ローカルのセルフレビュー工程を一度も通りません。どちらも、頻度の低いレビューを得るのではなく、唯一のレビューをまるごと失うことになります。

**ローカルの工程の役割は分割せず、`implement-be`でライブサイクルの総反復回数だけに上限を設ける。** 見送りました。回数上限だけでは、無制限のループという症状を止めるにとどまります。ローカルの工程がそもそも修正不足になっている原因には、手を付けません。指摘を出した本人と同じモデルは、その1件のコメントを黙らせる最小限の修正で済ませがちです。これが、pushのたびにライブのボットが隣接する何かを見つけ続ける一因になっている可能性が高いためです。
