## はじめに

`serve` の Web UI では、実行中の run job（`bajutsu run` によるシナリオ一式の実行）を操作者が途中で
キャンセルできます。今の実装では、このキャンセルは判定結果を書き出す前にプロセスをその場で終了させます。
キャンセルされた run は実行履歴に何も残さず、最初から実行されなかったかのように消えます。

本項目は、この終了を強制的なものから協調的なものに変えます。run のパイプラインは安全な境界で
キャンセル要求に気付きます。完了していなかった[シナリオ](../../docs/ja/glossary.md#scenario-authoring)
をすべて、理由 `"cancelled"` の失敗として確定させます。そのうえで、通常の失敗した run と同じ
`manifest.json`、`report.html`、データベースの記録を書き出します。シナリオの実行を開始した後に
キャンセルされた run は、こうして必ず失敗した run として履歴に残り、記録の空白を作りません。

## 動機

Web UI の Cancel ボタンは `Job.cancelled` をセットし、run プロセスのプロセスグループ全体に
`SIGTERM` を送ります。送信するのは [`jobs.py:99`](../../bajutsu/serve/jobs.py) の `cancel_job` で、
[`jobs.py:79`](../../bajutsu/serve/jobs.py) を経由します。Python は `SIGTERM` を受け取ると、既定では
自前の終了処理を一切実行せずにプロセスを即座に終了させます。

そのため `bajutsu run` のサブプロセスは、たいていシナリオの実行中という中途半端な地点で終了します。
`pipeline.py` の `run_and_report` が `_assemble_report` を呼んで `manifest.json` を書き出すよりも前に、
消えてしまいます。プロセスが最後の1行 `PASS/FAIL  runs/<id>/manifest.json` を出力するよりも前でもあります。

この最後の1行が、履歴保存の要です。`jobs.py` の `_persist_run` は、run の `RunRecord` を `serve` の
データベースに書き込みます。run の id は、正規表現 `_RUN_ID_RE`（[`jobs.py:39`](../../bajutsu/serve/jobs.py)）
でこの1行にマッチさせて知ります。job がこの行を一度も出力しなかったとき、`_persist_run` は即座に
return し、何も永続化しません（[`jobs.py:279`](../../bajutsu/serve/jobs.py)）。

実行中にキャンセルされた run は、`manifest.json` も `report.html` もデータベースの行も残しません。
run 履歴一覧にも、フレーキネスのランキングにも、triage ビュー
（[BE-0147](../BE-0147-serve-triage/BE-0147-serve-triage-ja.md)）にも現れません。まるで一度も
実行されなかったかのように扱われます。

止まってしまったシナリオ一式や動きの遅いシナリオ一式をキャンセルした操作者は、それを試みたという
記録そのものを失います。履歴上では、「このシナリオはまだ一度も実行されていない」のか「実行を始めたが
キャンセルされた」のかを区別できません。この違いは、同じ操作者や別のメンバーが後で「このシナリオに
カバレッジはあるのか」を確かめたいときに重要になります。

キャンセルした試みを失敗した run として記録すれば、この空白は解消します。キャンセルされた run が
成功扱いになるわけではないので、操作者はもともと選んでいた以上の負担を負いません。run 履歴を
利用する側にも、空白ではなく一貫した答えが届きます。利用する側とは、ダッシュボード、フレーキネスの
ランキング、夜間バッチの実行結果の確認などです。

## 詳細設計

キャンセルは、ランナー自身が短い猶予期間の範囲内で完結させる協調的な終了に変わります。`SIGTERM` が
その場でプロセスを終わらせる今の動作とは異なります。

- **シグナルを捕まえ、それで終了しない。** `bajutsu run` のエントリーポイントに `SIGTERM` ハンドラーを
  追加します。ハンドラーは `threading.Event` をセットします。Python の既定の挙動（即時終了）には
  頼りません。
- **プロセスグループ全体ではなく、まず run プロセス自身にだけシグナルを送る。** `serve/jobs.py` は、
  `run`、`record`、`crawl` のどの job も自身のセッションで起動します（`start_new_session=True`）。
  - 今のキャンセル経路は、このグループ化を利用しています。`_terminate` のグループ全体への `killpg` は、
    `record` job の実行エージェントが起動する子プロセス（`claude -p`）を、孤立させずに回収します
    （[`jobs.py:71`](../../bajutsu/serve/jobs.py)、[`jobs.py:417`](../../bajutsu/serve/jobs.py)）。
  - `run` job では、同じグループにバックエンドドライバーも含まれます。シナリオが実際に操作している
    Playwright 起動のブラウザや、`xcodebuild test` プロセスです。
  - グループ全体を殺すと、実行中のシナリオの下でこのドライバーも一緒に殺されます。シナリオは、次の
    安全な境界より前にクラッシュします。これは、本項目が取り除こうとしているまさにその唐突な失敗です。
  - そこで `run` job のキャンセル経路は、まずリーダープロセスだけにシグナルを送ります
    （`proc.send_signal`）。グループ全体には送りません。ドライバーは、ランナー自身が次の境界で
    イベントに気付くまで動き続けます。ランナーは、自分の通常のシナリオ終了処理を通じてドライバーを
    後始末します。
  - リーダーが終了した後も、キャンセル経路はグループ全体に `killpg` を送ります。リーダーの終了は、
    正常な終了でも、後述する猶予期間切れのエスカレーションでも構いません。後始末より長く生き残った
    ドライバーの子プロセスは、孤立させられるのではなく回収されます。
  - どちらの経路を使うべきかを判断するには、今の `Job` に無い判別材料が必要です。`Job` には job の
    種別を表すフィールドがありません（[`state.py:54`](../../bajutsu/serve/state.py)）。また
    `job.proc` は、オンデマンドビルドのサブプロセスと起動された run のどちらか一方を保持します
    （[`state.py:71`](../../bajutsu/serve/state.py)、[`jobs.py:192`](../../bajutsu/serve/jobs.py)）。
    本項目はこの判別材料を新たに追加します。リーダーだけにシグナルを送る経路は、`job.proc` が run
    自身であるときにだけ適用します。
  - `_terminate` のグループ全体への `killpg` は、`record` job、`crawl` job、`run` job のビルド段階に
    ついて、今のまま残ります。本項目はこれらを変更しません。
- **安全な境界でイベントを確認する。** ランナーは3つの場所でイベントを確認します。1つ目は、`run_all`
  のディスパッチループ（[`pipeline.py:822`](../../bajutsu/runner/pipeline.py)）における各シナリオの
  先頭です。2つ目は、シナリオ内の各ステップの間です。3つ目は、既存のすべての条件待ちを支える
  ポーリングループの中です。
  - 条件待ちをしているシナリオは、次のポーリングの間隔でキャンセルに気付きます。
  - 単一のドライバー呼び出しの中で止まっているシナリオは、その呼び出しが返るまで気付けません。該当する
    呼び出しは、`xcuitest` の HTTP リクエスト、`adb` の `subprocess.run`、Playwright の呼び出しです。
  - そのため、後述する猶予期間は、こうした呼び出しのうちもっとも長いものより長く取る必要があります。
    そうしないと、協調的な終了ではなくエスカレーションのほうが先に起きます。
  - 新しい待機は追加しません。境界のある既存のポーリングループに、終了条件を1つ追加するだけです。
- **キャンセルされたシナリオは、失敗したシナリオとして扱う。** こうして中断されたシナリオは、
  `RunResult(ok=False, failure="cancelled", ...)` になります。イベントがすでにセットされていたために
  一度も開始しなかったシナリオも同じです。`pipeline.py` は、クラッシュやプリフライトの失敗に対して
  すでにこの形を作っています（[`pipeline.py:271,281,313,545`](../../bajutsu/runner/pipeline.py)）。
  - `run_all` はこれまでと変わらず、宣言順にシナリオ1つにつき1つの結果を返します。後段の処理は、
    キャンセルが起きたことを知る必要がありません。
  - 長いシナリオ一式の早い段階でキャンセルした操作者には、一度も実行されなかったシナリオもすべて、
    レポート上とフレーキネスのランキング上の両方で失敗として数えられます。
  - これは、キャンセルされた run をそもそも失敗として扱うことの当然の帰結です。キャンセルが実行前に
    届いたシナリオだけを特別に除外するものではありません。
- **`run_all` より後段に変更は不要。** `run_and_report` は、完結していて通常の run と見分けがつかない
  `results` のリストを受け取ります。`_assemble_report` は、`manifest.json`、`report.html`、JUnit の XML
  を通常の run と同じ手順で書き出します。
  - 少なくとも1つのシナリオが `ok=False` を持つため、`manifest["ok"]` はすでに `False` になります
    （[`manifest.py:145`](../../bajutsu/report/manifest.py)）。
  - `_finish`（[`run.py:746`](../../bajutsu/cli/commands/run.py)）は、他の失敗した run と同じく
    `FAIL <manifest>` の行を出力して、終了コード1で終わります。
  - したがって `_RUN_ID_RE` はマッチし、`_persist_run` は他の失敗と同じように run を記録します。
    データベースへの書き込み処理そのものに変更は要りません。
- **終了は、`serve` が見ていなくても境界内に収まる。** `SIGTERM` ハンドラーは、`serve` 専用の関門の
  内側ではなく、`bajutsu run` のエントリーポイントに存在します。`cancel_job` が送る `SIGTERM` だけでなく、
  プロセスが受け取るどの `SIGTERM` にも応答します。`docker stop`、systemd の unit 停止、CI 側のジョブ
  キャンセルなどが該当します。
  - **`serve` 側の境界は外部から与えられます。** シグナルを送った後、`serve` はリクエストのスレッドとは
    別のところで猶予期間を進めます。期限を過ぎると、グループ全体への今の無条件の `killpg` に
    エスカレーションします。`record` の human-in-the-loop ハンドオフが、同じ保証をすでに守っています
    （[BE-0179](../BE-0179-record-human-handoff/BE-0179-record-human-handoff-ja.md)）。
  - **猶予期間はリクエストをブロックできません。** `POST /api/jobs/{job_id}/cancel` は `cancel_job` を
    同期的に呼び出します（[`routes.py:492`](../../bajutsu/serve/routes.py)、
    [`reads.py:636`](../../bajutsu/serve/operations/reads.py)）。猶予期間は前項の単一のドライバー
    呼び出しより長く取る必要があり、`xcuitest` の HTTP タイムアウトや `xcodebuild test` では数十秒に
    及びます。その間レスポンスをブロックすると、Cancel ボタンは応答がないまま止まって見えます。
    操作者はもう一度クリックしてしまいます。
  - **`cancel_job` は、シグナルを送った時点で今と同じように即座に return します。** 猶予期間とその
    エスカレーションは、`proc.wait()`（[`jobs.py:445`](../../bajutsu/serve/jobs.py)）をすでに担っている
    job 側のスレッドとは別のタイマー上で進みます。
  - **`serve` を経由せずに実行した `run` には、外部のエスカレーション役がいません。** そこでハンドラー
    自身が、同じ境界を自分に課します。イベントがセットされた時点で内部の2つ目のタイマーを起動します。
    その期限までに協調的な終了が完了しなければ、`SIGTERM` の既定の挙動を復元してシグナルを再送します。
    本当に止まってしまったランナーは、本項目を導入する前と同じように終了します。シグナルを受け取った
    後も、いつまでも生き続けることはありません。
  - **2つの期限は、互いに無関係に決めてはなりません。** ハンドラー側の内部期限が `serve` 側の猶予期間
    より短かったとします。run は、`_assemble_report` がマニフェストを書く前に自ら終了します。本項目が
    取り除こうとしているまさにその記録の空白を、ごく普通の `serve` からのキャンセルでも再現してしまいます。
    `serve` 側の猶予期間がいくら長くても、すでに自ら終了した run を救えないからです。
  - **ハンドラーは、受け取った猶予期間から自分の期限を決めます。** `cancel_job` は、自身の猶予期間を
    起動した run に渡します（ジョブの spec 上の環境変数として）。ハンドラーは、受け取った値より必ず
    長くなるように内部期限を決めます。独立に選んだ定数にはしません。
  - **`serve` を経由せずに実行する `run` は、固定の既定値にフォールバックします。** この値を受け取らない
    からです。既定値は、もっとも長いドライバー呼び出しを単独で乗り切れるだけの長さを持ちます。
  - どちらの場合も、キャンセル要求が今の即時終了より遅れるのは、猶予期間1回分までです。
- **対象は `run` job のみ。** 本項目が対象とするのは、`run` job と、クロスブラウザのマトリクス実行に
  おける各エンジンのパスです。`run_matrix_and_report` はエンジンごとに `run_all` を1回呼び、各パスは
  同じ `RunResult` の形を返します。
  - エンジンのループ（[`pipeline.py:938`](../../bajutsu/runner/pipeline.py)）も、次のパスを始める前に
    イベントを確認します。
  - 各パスはまず `device_pool` をまるごと1つ組み立てます。環境の解決、デバイスカタログの読み込み、
    デバイスごとのコレクターの起動までを事前に行います
    （[`run.py:653`](../../bajutsu/cli/commands/run.py)、[`pool.py:128`](../../bajutsu/runner/pool.py)）。
  - この確認がなければ、最初のエンジンの途中でキャンセルしても、run が終わるまでに残りのすべての
    エンジンの立ち上げと後始末を待たされます。マトリクス実行では猶予期間を超えてしまいます。
  - `record` job と `crawl` job には、保存すべき pass/fail の判定がありません。`record.py` は
    シナリオファイルを執筆するだけで、`RunResult` もマニフェストも一切作りません。
  - これらの job をキャンセルしたときの動作は、今のまま変わりません。`Job.cancelled` がセットされ、
    プロセスが終了します。キャンセルされた `record` job や `crawl` job を別の方法で可視化すべきかどうかは、
    本項目の範囲外の別の課題です。
  - この対象範囲が決めているのは、協調的な終了をどの job **種別**が受けるかです。どの `SIGTERM`
    **送信者**がそれを引き起こすかは決めていません。`bajutsu run` のエントリーポイントに追加する
    ハンドラー（前項）は、`serve` の Cancel ボタンだけでなく、どの送信者にも応答します。
- **パイプラインが始まる前は、キャンセルは今もその場で強制終了になる。** `_run_job` は、run プロセスを
  起動するより前に、デバイスの起動とアプリのビルドを行います（[`jobs.py:399,401`](../../bajutsu/serve/jobs.py)）。
  `_register_proc`（[`jobs.py:85`](../../bajutsu/serve/jobs.py)）は、登録が済む前にキャンセルされた
  プロセスをその場で強制終了します。
  - `_register_proc` の呼び出し元は、`proc.wait()` でプロセスを回収するだけです。`proc.stdout` は
    一度も読みません。
  - この狭い競合状態を協調的な終了に乗せると、ランナーは、誰も読んでいない満杯のパイプへの書き込みで
    ブロックされます。
  - デバイスの起動中、アプリのビルド中、あるいはこの短い登録前の間にキャンセルした場合は、今の動作の
    ままです。`Job.cancelled` がセットされ、プロセスはその場で強制終了され、何も残りません。
  - 本項目が埋める空白は、run がシナリオの実行を始めた後のものです。始める前の間は対象外です。

本設計はプライムディレクティブをそのまま満たします。キャンセルされた run が受け取る判定は、あくまで
決定的なパイプラインから来ます。完了しなかったシナリオは失敗と判定されるだけで、大規模言語モデル
（LLM）が判定するわけではありません。新しい不確定な待機は追加しません。境界のある既存の待機に、終了
条件を1つ追加するだけです。そして、ここにアプリ固有の要素はありません。シグナルの扱いも `RunResult` の
形も、どのターゲットでも同じです。

## 検討した代替案

- **キャンセルされた job が run id を一度も生成しなかったとき、`serve/jobs.py` の中で FAIL の
  `RunRecord` を作り出す。** 採用しません。
  - Replay ビューや triage ビューが依拠する証拠が何もない「失敗」という行だけが、データベースに
    残ります。`manifest.json`、`report.html`、スクリーンショット、各ステップの証拠のいずれもありません。
    リンク先が何もないラベルになってしまいます。
  - この作り出しは、ランナーではなく Web UI の job 層にあります。`serve` を経由せず直接実行した
    `bajutsu run` には、何の効果もありません。
- **ステップやポーリングの境界ではなく、シナリオの途中で即座に中断する。** 採用しません。
  - アクチュエーションの途中や、ネットワークの通信内容を証拠として書き込んでいる途中で止めると、
    ドライバーのセッションや保存済みのファイルが不整合な状態のまま残りかねません。
  - これは決定性優先と対立します。プライムディレクティブ2は固定の sleep を禁じており、同じ理屈で、
    実行中のアクチュエーションを任意の地点で切り落とすことも禁じます。
  - 現在のステップ、ポーリングの間隔、ドライバー呼び出しのいずれかが終わるのを待てば、パイプラインが
    もともと一時停止を許容している地点で止められます。待ち時間は、せいぜい1回分のポーリング間隔か
    1回のドライバー呼び出し分で、シナリオ自身のタイムアウトほどではありません。
- **キャンセルを、成功・失敗とは別の第三の run レベルの判定として扱う。** 本項目では採用しません。
  - キャンセルされた run をシナリオ一式の失敗として数えることは、操作者が履歴を読むときの感覚と
    一致します。キャンセルされた run は成功ではありません。
  - `failure: "cancelled"` は、アサーションの失敗とは異なるラベルやアイコンをレポートと Web UI が示す
    ために必要な情報を、すでに与えています。
  - 新しい判定の種類を追加すると、データベースのスキーマ、フレーキネスのランキング
    （[BE-0049](../BE-0049-determinism-flakiness-audit/BE-0049-determinism-flakiness-audit-ja.md)）、
    `ok: bool` を前提とするすべてのレポートのレンダラーに影響が及びます。
- **`SIGINT` も捕捉し、ターミナルから Ctrl-C でキャンセルした素の `bajutsu run` にも同じ扱いを与える。**
  本項目の範囲外とします。
  - 本項目が結び付けるのは `SIGTERM` だけです。これだけで、外部からのキャンセル経路はすべて届きます。
    `serve` の Cancel ボタン、`docker stop`、systemd、CI 側のジョブキャンセルです。
  - 仕組みは同じ「シグナルからイベントへの橋渡し」です。後続の項目が同じ `threading.Event` に
    `SIGINT` を結び付けるだけで済み、新たな設計は不要です。

## 進捗

> 開発の進行に合わせて常に最新の状態に保ってください。チェックリストは *詳細設計* の MECE な
> 作業分解（作業の単位ごとに 1 つ）に対応し、ログには変更内容と時期（古い順）を PR へのリンクと
> ともに記録します。

- [x] `bajutsu/cancellation.py` に、キャンセルに関する語彙をすべて集めました。このモジュールは Bajutsu の
  何もインポートしないので、決定的なコア、コマンドライン、`serve` のどこからでも参照できます。保持するのは
  4つです。ランナーが読む `CancelSource`、ポーリングループが送出する `RunCancelled`、失敗理由の綴り
  `"cancelled"`、`bajutsu run` のエントリーポイントが設置する `graceful_sigterm()` コンテキスト
  マネージャーです。ハンドラーは送り手を問わず応えます。猶予窓のあいだに届いた2回目の `SIGTERM` は、
  エスカレーションせずに吸収します。Cancel を2回押した操作者が、manifest を失うことはありません。
- [x] `Job` には、job の種別を表す1つのフィールドではなく、2つのフィールドを置きました。詳細設計は、
  job の種別を表すフィールドか、同じ問いに答える判別材料のどちらかを許していました。後者を選んだ形です。
  `graceful_cancel` は、「この job が起動するプロセスは協調的にキャンセルに応える」というディスパッチャー
  側の宣言を運びます。宣言はジョブの spec に載るので、worker も同じように登録します。`proc_graceful` は、
  「いま登録されているサブプロセスがその run 自身かどうか」という生の事実を運びます。この2つの組が、
  2つの段階を分けます。今の強制終了のままにする `run` job のオンデマンドビルド段階と、run 本体です。
- [x] `cancel_job` は、`proc_graceful` が立っているあいだ、`_request_graceful_stop` を通じて先頭の
  プロセスだけにシグナルを送ります。`_run_job` は、リーダーが終了した後にプロセスグループを `killpg`
  で掃きます。`_pgid_of` は、リーダーが生きているうちにそのグループを読みます。回収された pid は、
  掃く時点では別の持ち主のものになりうるからです。`record`、`crawl`、triage の job とビルド段階は、
  `_terminate` のグループ全体への強制終了のままです。
- [x] パイプラインは、次の場所でイベントを読みます。
  - `_ScenarioRunner.run_one` の先頭
  - `_StepRunner.exec_steps` の各ステップ境界
  - `waits.py` の6つのポーリングループすべて（`for`、`gone`、`request`、`screenChanged`、および settle
    の2経路）
  - ステップ単位の `assert` がポーリングする `_poll_asserts`
  - メールボックスをポーリングする `_do_email`

  `email` ステップは、3つ目のポーリングするステップ種別です。待ち時間の上限をシナリオ自身が決める
  ので、ワンタイムパスワードの待ちは、猶予窓をゆうに越える長さになりえます。どの確認も、それぞれの
  条件確認の**後ろ**に置きました。そのポーリングで条件を満たした待ちは、今までどおり成功します。
  `_settle_extract_read` は、判断のうえで対象から外しました。条件を判定するのではなく、読み取りを
  settle させるものであり、同じ待ちの下限がすでに上限を与えているからです。
- [x] `RunCancelled` は `run_scenario` まで巻き戻り、そこで `failure: "cancelled"` を記録します。
  ポーリングループごとの脱出は、戻り値の形を増やさず1行で済みます。巻き戻りが通過する sink の後始末は、
  シナリオの interval を今までどおり確定させます。一度も開始しなかったシナリオは、最初のリースを試みる
  前に `run_one` が失敗させます。シナリオ末尾の `expect` は、判断のうえで最後まで走らせます。全ステップが
  成功したシナリオには、キャンセルというラベルではなく本物の合否を残すためです。
- [x] `_request_graceful_stop` は、猶予窓のためのデーモンの `threading.Timer` を起動します。`POST
  /api/jobs/{job_id}/cancel` は、シグナルを送った時点で今までどおり返ります。期限を過ぎると、
  `_escalate` がグループ全体へ SIGTERM を送り、グループがそれで後始末を終える短い窓を与えます。そのうえで
  SIGKILL で run を終わらせます。
  - 詳細設計は、このエスカレーションを「今の無条件でグループ全体への `killpg`」と書いていました。run が
    SIGTERM に協調的に応えるようになった今、それを無条件のままに保つのが最後の SIGKILL です。
  - ハンドラーは設計上2回目のシグナルを吸収します。Python を実行できないところまで固まった run は、
    そのハンドラーすら走らせないので、どちらの SIGTERM にも応えません。Web UI から終わらせられない
    job が操作者に残ることになり、今より悪い状態です。
  - グループ全体への SIGTERM を SIGKILL の手前に残したのは、リーダーが自身の後始末に到達していない
    ためです。リーダーが止めるはずだったドライバーの子プロセスは、まだ生きています。いきなり強制終了
    したドライバーは、次の run のために Simulator を固まった状態で残しかねません。
  - エスカレーションは、まずプロセスがまだ動いているかを確認します。猶予窓の内側で自分を閉じた run は、
    後から発火したタイマーで殺されることはありません。
- [x] ハンドラーの内部期限は `handler_deadline(grace_seconds())` で、受け取った猶予窓に固定の余裕を足した
  値です。イベントを立てると `signal.setitimer` でこの期限を張り、`SIGALRM` ハンドラーが `SIGTERM` の
  既定の挙動を復元して再送出することで実行します。
  - 第2のスレッドではなくインターバルタイマーにしたのは、既定の挙動の復元がメインスレッドでしか許され
    ないからです。Python のシグナルハンドラーが走るのが、まさにそのメインスレッドです。
  - `_spawn_env` は、`graceful_cancel` の job の起動先へ `BAJUTSU_CANCEL_GRACE` を渡します。`serve` を
    経由しない `run` は値を受け取らず、既定の90秒にフォールバックします。
  - この窓に収まらなければならないのは、1つではなく2つです。1つ目は、最長の単一のドライバー呼び出し
    です。XCUITest チャネルの30秒のアクチュエーションタイムアウト、あるいは BE-0207 のリトライに乗る
    読み取りの60秒の復旧タイムアウトです。2つ目は、その後ろに続くシャットダウンの尻尾です。残るシナリオを
    失敗させ、レポートを組み立て、`serve` が run の id を読む合否の行を出力します。
  - 呼び出しと同じ長さの窓では、この尻尾に何も残りません。60秒の読み取りで止まっている run は、
    manifest を書けないまま終わらせられかねません。
- [x] `run_matrix_and_report` は、エンジンのパスとパスのあいだでイベントを読みます。走らなかったエンジンの
  シナリオをすべて失敗させ、レポートからそのエンジンを落とすことはしません。
  - 落とす形には、詳細設計が想定していなかった落とし穴があります。結果から抜けたエンジンは、そのシナリオ
    の合否も一緒に持ち去ります。すると manifest の全件合格の `ok` は、実際に走ったパスだけを集約します。
  - 最初のエンジンが全件合格した直後にキャンセルが届くと、要求された作業の大半を実行していない run が
    `PASS` として記録されます。この項目が消そうとしている「静かな欠落」が、そのまま裏返った形です。
  - 飛ばしたエンジンとシナリオの組ごとに、キャンセルの結果を1件ずつ作ります。集約は純粋なままで、
    matrix も欠けません。`cancelled` と表示されたセルが、「その軸は要求されたが実行されなかった」ことを
    そのまま示します。
  - そうして失敗させたエンジンは、ループがログに記録します。
- [x] テストで確認しました。協調的にキャンセルされた run も `FAIL runs/<id>/manifest.json` の行を出力します。
  そのため `run_job` はそこから `job.run_id` を読み取り、`_persist_run` が `ok=False` で run を記録します。
  データベースへの書き込み経路に変更はありません。

### 実装して確定したこと

- **リースの立ち上げ中に届いたキャンセルは、そのリースが返るまで気付きません。** キャンセルのイベントは、
  ステップループとその条件待ちには届きます。その下のデバイスの立ち上げには届きません。XCUITest の
  コールド起動中にキャンセルが来た場合は、その起動を待ち切ってから、シナリオの最初の境界が失敗させます。
  上限はリース自身の準備完了の上限で、猶予窓を過ぎれば `serve` のエスカレーションがいずれにせよ適用
  されます。パイプラインがシナリオを始める前に届いたキャンセルについて、詳細設計がすでに受け入れている
  のと同じ性質の残余です。
- **Web UI 側に、詳細設計が挙げていなかった配線が必要でした。** `serve.panels.mjs` は、Replay タブの run
  ペインと Record タブのその場実行の両方で、`setReport` へ届く前に `j.cancelled` で打ち切っていました。
  そのままでは、キャンセルされた run が書くようになったレポートが、Cancel ボタンのすぐ隣という当の画面で
  見えないままになります。
  - どちらのハンドラーも、早期に返さず処理を続けるようにしました。run は `cancelled` の表示を保った
    まま、レポート、`open full report` のリンク、triage のバーを得ます。
  - 詳細設計は、`_persist_run` と履歴のサマリーが「変更なしで」読めることを、下流は何も動かす必要が
    ないという意味で書いていました。run の記録についてはそのとおりでしたが、ログの隣のペインについては
    違いました。
- **バックエンドのクラッシュ再試行ループもイベントを読みます。** 再試行はリースを取り直します。XCUITest
  では、その立ち上げがコールド再生成に強制 erase を上乗せしたものになります。キャンセルした側が待って
  いる猶予窓を越えるだけの長さがあり、manifest を書く前に run が終わらせられてしまいかねません。
  - そのため、キャンセルされた run は復旧を打ち切り、クラッシュしたシナリオをその場で失敗させます。
    すでに得た合否は、すべて残します。
  - 失敗の理由には、まったく使い切っていない予算ではなく、キャンセルを書きます。
  - 詳細設計が挙げた境界の一覧に、クラッシュの経路は入っていません。この経路は、一覧が挙げるディスパッチ
    ループではなく、`run_one` の内側から `lease()` に到達します。
- **キャンセルされたシナリオは、完了したステップだけを記録します。** 中断されたステップは、ステップ
  ループがその結果を追加する前に例外を送出します。そのためレポートには、完了したステップが並びます。
  そうでなければ、試みたが結果は不明という状態でレンダリングするしかないステップが1つ混じります。
