## はじめに

本提案は、[BE-0066 の Web クロール](../BE-0066-web-crawl/BE-0066-web-crawl-ja.md)を、**複数のブラウザで同時に**走らせます。独立したフロンティアの作業が重なり合い、1 つの画面マップを、実時間ベースで大幅に短縮して構築できます。本提案は、[BE-0064（複数シミュレータでの並列クロール）](../BE-0064-parallel-crawl/BE-0064-parallel-crawl-ja.md)の Web 版です。BE-0064 も BE-0066 も、この交点を後続項目としてすでに名指ししています。「並列 Web クロールは、この項目と並列クロール軸との交点であり、両者が揃えば後続できる」という記述です。

iOS と同じく、クロールは Tier 1 の探索と発見のツールにとどまり、CI ゲートにはなりません。並列化されるのは**スケジューリングだけ**です。画面同一性、遷移、クラッシュの判定は、従来とまったく同じに行われます。

各ワーカーは、それぞれ自分の**ブラウザプロセス**（起動した Playwright の `Browser`）を持ちます。1 つの共有ブラウザ内の `BrowserContext` レーンは使いません。ここでの狙いは**高速化**、つまり 1 つの共有画面マップをより速く構築することです。クロスエンジンの網羅は狙いではありません。同じアプリを異なるエンジン（Chromium / Firefox / WebKit）で走らせ、エンジン固有の差異を洗い出す機能は別物です。後述のとおり、スコープ外とします。

## 動機

現在の Web クロールは逐次実行です。1 つのブラウザで 1 画面ずつ探索します。1 画面あたりのコストを支配するのは、マシンを遊ばせてしまう、レイテンシ律速の 2 つの待ちです。BE-0064 が iOS で挙げた 2 つと同じものを、Web の形で示します。

1. **AI ガイドの往復。** `--guide ai` では、新しく発見した画面ごとに、1 回以上のモデル呼び出し（操作プロポーザ）が走ります。これらはネットワーク往復です。
2. **ブラウザとページの操作。** 未探索画面へ到達するには、クリーンな初期状態へ `reset` し、記録済みパスを再生します（途中の JS ダイアログを処理しながら）。続いて操作を実行し、`observe` します。各遷移、操作、観測はブラウザとネットワークを待ちます。再生コストは、画面の深さとともに増えます。

どちらの待ちも、独立したブラウザ間できれいに重なります。そのため、AI のレート上限やコーディネータの競合が支配的になるまで、実時間はおおよそワーカー数に応じて減ります。

**並列クロールを最も低摩擦で活かせるのが Web です。** Mac もエミュレータも要らず、既存の Linux の `make check` / CI ゲート上で動きます（[BE-0041](../BE-0041-web-playwright-backend/BE-0041-web-playwright-backend-ja.md)）。速いクロールを、CI 内の発見ステップとしてそのまま回せます。ブラウザプロセスは、端末の起動なしに数秒で立ち上がります。N レーンを用意するコストも小さくなります。

`run` は、すでにレーンで並列化されています（[BE-0054](../BE-0054-web-backend-completion/BE-0054-web-backend-completion-ja.md) がプールの Web 分岐を N レーンへ一般化します）。クロールだけが、いまだ 1 つのブラウザに固定された、唯一の Tier 1 経路です。この固定が、`record` の入口として、また全画面のカバレッジ計測の実行として、クロールを使いにくくしています（[DESIGN §7.2](../../DESIGN.md)、[BE-0038](../BE-0038-autonomous-crawl-exploration/BE-0038-autonomous-crawl-exploration-ja.md) 動機 #2）。

## 詳細設計

### コーディネータとワーカー

**コーディネータ**が、ロック下で共有の画面マップとフロンティアを保持します。BE-0064 とまったく同じです。共有状態は次のとおりです。

- `nodes` と `edges`
- `path_to`（各画面への再生可能なパス）
- `pending`（画面ごとの未試行操作）
- `visited`
- 予算カウンタ

**N ワーカー**は、それぞれ対象アプリを読み込んだブラウザプロセスを 1 つ持ちます。

各ワーカーのループは次のとおりです。

1. **ロック。** 同じ決定的規則（`path_to` が最短、次に fingerprint）で最安のフロンティアエントリを選びます。操作を 1 つ取り出し、実行中の印を付けます。**アンロック。**
2. 自分のブラウザ上で `reset` し、`path_to[fp]` を再生し（途中の JS ダイアログを決定的なダイアログ自動ハンドラで処理しながら）、操作を実行し、`observe` します。
3. **ロック。** エッジ、クラッシュ、ダイアログを記録します。遷移先が新規なら、ノード、`path_to`、`pending` を追加し、その画面にいる間に当該ブラウザでガイドを実行します。**アンロック。**

こうして、ガイドの AI 呼び出しがワーカー間で並行に走ります。これが主たる短縮要因です。**フォワードウォーク**の最適化は、ワーカーごとに保たれます。ワーカーは、未試行操作がなくなるまで、今いる画面を操作し続けます。バックトラック（reset と再生）は、別のフロンティアエントリへ到達するときだけです。これは現在の 1 ブラウザ戦略そのもので、各ワーカー上で動くだけです。

### レーンはブラウザプロセス、リセットごとのクリーン状態は新しいコンテキスト

ワーカーの永続的なレーンは、1 つの**ブラウザプロセス**です。障害時に、コーディネータが強制終了して再起動する単位です（後述）。一方、反復ごとの `reset` は**ブラウザの再起動ではありません**。ワーカーのブラウザ内に新しい `BrowserContext` を作ることです。`erase` に相当し、ほぼ無コストです。

設計は、BE-0066 の既存の Web リセットの継ぎ目をそのまま再利用します。`reset` は、すでに新しいコンテキストへの `driver.navigate()` にすぎず、[`runner/pool.py`](../../bajutsu/runner/pool.py) の `_web_relauncher` と同じです。「ブラウザプロセスを分ける」コストは、画面ごとではなく、**ワーカーごと**（および障害ごと）のブラウザ起動 1 回です。

### 決定性の境界（要点）

画面の*同一性*（fingerprint）、遷移判定、クラッシュ判定、画面マップの内容は、要素ツリーの純粋な決定的関数のままで、変わりません。Web のクラッシュ判定は、BE-0066 の決定的シグナルを保ちます。

- `page.on("pageerror")` による未捕捉 JS 例外
- メインフレームの HTTP 4xx/5xx ステータス
- 空の DOM

いずれも LLM の判断ではありません。AI は、依然として「何を試すか」だけを選び、判定は下しません（[prime directive #1](../../CLAUDE.md)）。

並列化で緩むのは、**探索順序**と、**記録される正準 `path_to`** の 2 つです。どのワーカーが画面に先に到達するかは、スケジュールに依存します。アプリ自体に非決定性があると、記録されるパス（およびタイブレークされた発見順）は、実行ごとに変わりえます。決定的なアプリでは、発見されるノードとエッジの*集合*は不変で、順序とパスのメタデータだけが変わります。

この緩みが許容されるのは、クロールが **Tier 1 であり、合否ではなく発見成果物を出力する**からです。BE-0038 と BE-0064 が、すでに同じ理由を挙げています。決定的な*副産物*は、その保証を保ちます。記録されたクラッシュ再現やフローのパスは、Web の `run` で AI なしの Tier 2 リグレッションとして、今までどおり再生できます。

### インターフェース

* **CLI：** `bajutsu crawl --backend web --workers N`（既定は `1`。現在の逐次 Web クロールです）。各ワーカーは、自分のブラウザプロセスを起動します。Web には端末がありません。BE-0064 の `--udid a,b,c` プールとは違い、ワーカー数だけでレーン集合の大きさが決まります。このオプションは、BE-0054 の単一レーン Web プール（ダミー udid 1 つ、`workers = 1`）を N へ一般化します。すべてのワーカーは、設定された 1 つのエンジンを使います。クロスエンジンのファンアウトはスコープ外です（検討した代替案を参照）。
* **WebUI（serve）：** Crawl タブの Web ターゲットに、ワーカー数の指定を加えます。Web にはシミュレータ選択のような端末の複数選択がないので、数値入力にします。ライブの画面マップは、すでに共有マップから配信されるので、描画側の変更は不要です。BE-0064 と同じです。
* **予算と停止：** `--max-screens` と `--max-steps` は、ロック下で確認する共有カウンタにします。フロンティアが空になるか予算に達したら停止し、同じ `stop_reason` を報告します。
* **障害の隔離：** ブラウザが固まったワーカーは、現在のフロンティアエントリを破棄します。固まる原因は、タイムアウトする遷移、レンダラのクラッシュ、固まったページ、解決しなくなった再生です。ワーカーは、自分のブラウザプロセスを破棄して再起動してから続行します。1 つの不調がクロール全体を沈めません。プロセス単位のレーンがコストに見合うのは、ここです。コーディネータは、他のワーカーに触れずに、1 ワーカーのブラウザだけを強制終了できます。BE-0064 のシミュレータ単位の隔離の Web 版です。

### Web プールの再利用（BE-0054）

本項目は、BE-0054 が N レーンへ一般化する [`runner/pool.py`](../../bajutsu/runner/pool.py) の Web 分岐を土台にします。唯一の違いは、レーンの隔離単位です。

- 本項目のクロールレーンは、1 つのブラウザプロセスです。クロールはわざとクラッシュや固まりを誘発するので、障害隔離のためにこの単位を選びます。
- BE-0054 の `run` レーンは、`BrowserContext` です。より安価で、独立シナリオには十分です。

どちらも「Web プールの N レーン」であり、単位は用途ごとに選びます。

## 検討した代替案

* **別プロセスではなく `BrowserContext` レーン（BE-0054 の `run` モデル）。** クロールでは却下します。N 個のコンテキストは、1 つのブラウザプロセスを共有します。あるレーンでの固まったページ、暴走スクリプト、ブラウザプロセスのクラッシュが、全レーンを止めるか、巻き込んで落とします。クロールの仕事がまさにクラッシュや固まりの誘発である以上、この結果は許容できません。別プロセスなら、OS レベルの障害隔離と、レーン単位の強制終了と再起動が得られます。BE-0064 のシミュレータ単位の隔離に倣えます。リセットごとの安価な `erase` には、各ワーカーのブラウザ*内*の新しいコンテキストを、引き続き使います。
* **クロスエンジンのファンアウト**（同じアプリを Chromium / Firefox / WebKit で同時にクロール）。別機能であり、高速化ではなく、クロスブラウザの互換性発見です。共有フロンティアではなく、差分を取るための N 個の*独立*マップが必要になります。本項目は、設定された 1 エンジンの N プロセスで、1 つのマップを速く作ります。将来のクロスブラウザクロール項目が、本項目と組み合わさる可能性はあります。エンジンごとに本並列クロールを走らせ、マップを差分する形です。その機能をここに畳み込むと、共有フロンティアモデルと決定性の筋の両方が濁ります。
* **サイトの静的分割**（各ワーカーに URL サブツリーを割り当てる）。BE-0064 と同じく却下します。グラフは動的に発見されるので、事前に分割を計算できません。静的な分割では、ワーカーが遊ぶか、冗長に探索してしまいます。
* **独立クロールを後で統合**（各ワーカーが入口から個別にクロールし、最後に重複排除する）。BE-0064 と同じく却下します。共有画面の冗長な再探索が膨大になります。共有フロンティアこそが、作業を重複なく分担させる仕組みです。
* **1 つのブラウザでの非同期化**（ブラウザを増やさず、AI 呼び出しだけ重ねる）。AI レイテンシには効きますが、ブラウザとページの操作には効きません。障害隔離も得られず、1 ページでは 2 画面を同時に操作できません。ブラウザプールが本質的な手段です。後で組み合わせる価値はありますが、非同期化は代替になりません。
* **本項目を BE-0064 に畳み込む。** 却下します。BE-0064 は、iOS シミュレータ（simctl の reset と再生、起動済み端末プール）を前提に書かれています。Web は、ブラウザプロセスのレーン、コンテキストによるリセット、BE-0066 の Web クラッシュとダイアログの意味論を使います。別の設計面です。BE-0066 が BE-0038 に対して持つ「同じ軸、別プラットフォーム → 別項目」の関係と同じで、BE-0066 自身が、並列 Web クロールを後続の交点として名指ししています。
