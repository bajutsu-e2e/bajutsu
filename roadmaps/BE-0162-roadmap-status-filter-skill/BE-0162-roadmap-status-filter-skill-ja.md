## はじめに

ロードマップ（BE）項目を `Status` で絞り込んで一覧する Claude Code スキルを追加します。AI セッションは、
`roadmaps/README.md` を全文読まなくても、「`Approved` の項目すべて」（あるいは `In progress`、
`Implemented`、`Deferred`、`Rejected`）を見渡せます。

スキルは状態を引数に取り、`ID`、タイトル、`Topic`、項目ファイルのパスを 1 つの表で出力します。Claude は
その表から、必要な項目だけを開けます。

## 動機

`roadmaps/README.md` はすべての BE 項目の索引です。4 つの状態のバケットと多くのトピックにまたがって
100 を超える項目を抱え、700 行を超える規模に育ちました。たとえば未着手の提案だけを知りたいセッションに
とって、今の選択肢はどちらも不十分です。

- **索引を全文読む**：生成された表が数百行分そのまま文脈に載ります。大半はいまの作業と無関係で、
  トークンを消費し、必要な数行を埋もれさせます。
- **README を手作業で `grep` する**：機能はしますが、セッションごとにコマンドを組み直すことになります。
  README はバケット別・トピック別の表構成なので、「提案だけをファイルパス付きで」という射影を `grep`
  だけで整えるのも面倒です。

索引は、[`scripts/build_roadmap_index.py`](../../scripts/build_roadmap_index.py)が各項目自身のメタデータ
（`Status`、`Topic`、タイトル）から生成しています（BE-0043、BE-0078）。状態フィルタが必要とするのも、
その同じメタデータです。機械可読で、権威のある情報源だからです。AI セッションが欲しい射影
（「`Approved` の行をパス付きで」）は、リポジトリがすでに解析しているデータに対する小さな決定論的な
クエリであり、新たな情報源ではありません。

引数で状態を指定できる的の絞れたスキルがあれば、どのセッションも、この問いを一貫した低トークンの方法で
投げられます。返ってくるのは、必要な行と、次に読むべきファイルパスです。

## 詳細設計

作業は互いに排他で網羅的な（MECE）3 つの単位に分かれます。

### 1. 決定論的な状態フィルタクエリ

新たな解析器を足さずに、索引生成器がすでに持つメタデータ解析を再利用します。
`scripts/build_roadmap_index.py` は（`roadmap_ids.iter_item_dirs` と `metadata_fields` を通じて）
すべての `roadmaps/BE-*/` 項目の `| Field | Value |` ブロックを読み取っています。
そのブロックから `Status`、
`Topic`、H1 タイトルを取り出します。スキルはこれを小さなクエリとして呼びます。形は次の 2 通りです。

- 薄い CLI エントリポイント（例：`python scripts/roadmap_query.py --status Approved`）。共通の解析処理を
  `build_roadmap_index.py` から取り出し、インポート可能なヘルパーにして呼びます。
- その処理を包む新しい `make` ターゲット。

クエリの仕様は次のとおりです。

- `Status` の値を 1 つ取ります（`Approved`、`In progress`、`Implemented`、`Deferred`、`Rejected`）。
  大文字小文字を区別せずに照合し、既知の集合に対して検証します。未知の状態のときは、空の表ではなく有効な
  値を表示して、非ゼロで終了します。
- `ID`、`Item`（タイトル）、`Topic`、`Path`（項目の英語版 `.md` ファイルへの相対パス）を列に持つ
  Markdown の表を出力します。出力を安定させるため、`Topic`、次いで `ID` の順に整列します。
- 純粋かつオフラインで動きます。`gh`、ネットワーク、LLM のいずれも使わず、`roadmaps/` 以下のファイルを読むだけ
  です。

プレースホルダ（`BE-0162`）の項目も、他と同じく `Status` と `Topic` を読み取ります。進行中の提案も
フィルタに現れ、`ID` の欄にはプレースホルダが表示されます。

### 2. スキルの定義

スキルは `.claude/skills/roadmap-status/`（名称は未定）に置き、既存の `ideation`、`implement-be`、
`japanese-tech-writing` スキルと並べます。性質は次の 3 つです。

- **読み取り専用で Claude 向け**です。セッションのためにロードマップを見渡すだけで、項目の起草、実装、
  変更はしません。ファイルも編集しません。
- 状態を引数に取り、単位 1 のクエリを呼び出して、その表をセッションに返します。Claude は表を見て、全文を
  開く項目を選びます。
- 有効な状態の一覧を、フロントマターと本文に記します。出力される `Path` 列が、提案全文を読むために次に
  `Read` する対象であることも記します。

### 3. テストとドキュメント

- クエリに対するテストは、2 点を確認します。各状態で絞り込むと、その状態をメタデータに持つ項目がちょうど
  返ること。未知の状態がきれいに失敗すること。既存のロードマップ形式テストや索引テストと同じ形で、
  `tests/test_roadmap_*` が自然な置き場所です。
- [`docs/ai-development.md`](../../docs/ai-development.md)に短い記述を足し、セッションがこのスキルの
  存在を知れるようにします。置き場所は、モデルと reasoning effort のティア分けの記述（BE-0103）の隣です。

**プライムディレクティブとの整合。** これはドキュメントに対するコントリビュータ向けツールです。Tier-2 の
`run` / CI ゲートに LLM は入りません（第 1 原則）。クエリは決定論的でオフラインです（第 2 原則）。
触れるのは `roadmaps/` のメタデータだけなので、アプリ非依存です（第 3 原則）。

## 検討した代替案

- **セッションに README を `grep` させる。** 新しいコードは不要です。ただし、セッションごとにコマンドを
  導き直し、README のバケット別の表から欲しい射影を組み立て直すことになります。結果は一貫せず、誤りも
  生じやすくなります。再利用でき低トークンな形は、メタデータに対する名前付きスキルです。
- **項目メタデータではなく生成済みの索引表を対象にする。** README の表は情報源ではなく、レンダリング結果
  です。表を対象にすると、フィルタが索引の再生成に依存してしまいます。生成器と同じく各項目自身の
  メタデータを読むほうが権威のある経路で、編集の途中でも正しさを保ちます。
- **代わりに GitHub Pages のロードマップダッシュボード（BE-0094）を拡張する。** ダッシュボードは
  ブラウザ上の人間に向けたもので、ネットワーク取得なしに行を文脈に載せたい AI セッションの役には立ち
  ません。読み手と面が異なるので、重複ではなく補完の関係にあります。
- **トピックやテキストなどでも絞れる汎用のロードマップ検索スキル。** 機能は広がりますが、`Status` で
  絞ることに的を絞ったこの項目の範囲外です。豊富なフィルタは、このスキルが有用だと分かってから、別項目
  として続けられます。
