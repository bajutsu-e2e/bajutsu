## はじめに

`.searchable` など SwiftUI 標準要素のツリー表現が壊れていないかを、実機で継続的に確認します。

## 動機

セレクタ解決は決定性の核です。セレクタはちょうど 1 要素にマッチします。0 件は「不在」、2 件以上は ambiguous エラーです。これらの判断はすべて、`IdbDriver.query()` が idb の `ui describe-all` から正規化した要素ツリーに対して下されます。したがって、run ループ*全体*の正しさは、その正規化の精度以上にはなりません。

標準的な SwiftUI コントロールが、私たちの想定どおりにツリーに現れない場合を考えます。識別子が違う、trait が欠ける、コンテナが子要素を呑み込んでしまう、といった場合です。そのコントロールを対象に書いたシナリオは、要素を黙って見つけられないか、さらに悪いことに別の要素にマッチします。

DESIGN §11 はすでに、2 つの具体的な症状を記録しています。

- **名指しされた精度リスク**：`.searchable` など SwiftUI 標準要素が挙げられています。
- **遷移中のほぼ空のツリー**：画面は描画済みでも、idb が識別子なしの 1 要素だけを返す例が観測されています。

`IdbDriver.query()` は、2 つ目の症状を、上限付きでゲート付きのリトライ（`_max_seen` / `_READY_MIN`）で緩和しています。このリトライは*一過性*への防御です。ある SwiftUI コントロールの*落ち着いた*ツリーが、シナリオの想定どおりの形かどうかは教えてくれません。リトライの注記自体、本層では意図的にマスクしない「8 秒級の病的ケース」を指して終わっています。

欠けているのは、実アプリが使う SwiftUI コントロールの定常状態の表現がずれていないことを、実機で継続的に確認する仕組みです。この仕組みがあれば、idb や iOS、あるいはコントロールの作り方の回帰が、失敗するチェックとして現れます。仕組みがなければ、回帰は現場でフレーキーなシナリオや誤ったシナリオとして現れます。

## 詳細設計

本提案は、シナリオが実際に依存する SwiftUI コントロールについて、期待される正規化ツリーを固定する、維持されたオンデバイス fixture です。fixture は、idb をすでに検証している重めの e2e 経路で実行します。高速な PR 単位ゲートでは実行しません。

- **サンプルアプリ内のコントロールカタログ画面。** デモアプリ（`demos/`）に、対象とする標準 SwiftUI コントロールを並べた画面を持たせます。コントロールは、`.searchable`、`List`、`NavigationStack`、`TextField`、トグル、セグメントコントロールなどです。それぞれに、アプリの id 名前空間から安定した `accessibilityIdentifier` を与えます。アプリ単位の識別子はアプリ側の事柄なので、fixture が動かすのは特定の本番アプリではなく*正規化*そのものです。ツールは app-agnostic のままです。
- **正規化ツリーの golden（期待値）。** 各コントロールについて、期待される `Element` の形を、チェックインされた期待値として記録します。形は、`Selector` セマンティクスが依存するフィールドで構成します。`identifier`、`label`、`traits`、`value`、妥当な `frame` です。チェックはアプリをその画面へ駆動し、`query()` を呼び、正規化ツリーを golden と照合します。このアサーションは機械チェック可能なので、LLM を介さず決定性ゲートに収まります。
- **落ち着いた状態と一過性を明示的に区別する。** チェックは、既存の条件待機経路で画面を待ち（固定 sleep なし）、その後*落ち着いた*ツリーに対して照合します。`_max_seen` ゲート付きリトライは、引き続き遷移中の空を吸収します。本提案の golden が対象とするのは、そのリトライが役目を終えた後の定常状態です。2 つの関心事は分離されたままで、どちらも他方をマスクしません。
- **ずれは失敗するアサーションとして表面化する。** idb や iOS リリース、あるいはコントロールの構成が、正規化された形を変えたとします。このとき golden のアサーションは、e2e 経路で失敗します。失敗には、どのコントロールのどのフィールドが動いたかを示す具体的な差分が付きます。アサーションがなければ、変更は、要素を見つけられなくなった現場のシナリオとして漏れ出します。この項目は、BE-0005 のバージョン監視と自然に対になります。BE-0005 は*どの* idb が入っているかを見張り、本項目は idb が*何を生み出すか*を見張ります。

ここに、セレクタの厳格さを緩めるものはありません。ambiguous な一致は依然として失敗し、不在も依然として失敗します。golden アサーションは厳密な比較です。

### コントロールカタログ画面

このカタログは、新しく作るアプリではありません。サンプルアプリ（`demos/features/app/BajutsuSample/`）がすでに備えている標準コントロールの一群を、golden の対象として明示的に据えるものです。`RootView.swift` の `MainTabView` が、カタログに必要な画面をすでに配線しています。各画面は `launchEnv`（`SAMPLE_TAB`）で単独に起動できるので、チェックは UI をたどらずに目的の画面へ直接駆動できます。

- **`ControlsView`（`SAMPLE_TAB=controls`）** は値コントロールの一群です。`Toggle`（`ctrl.toggle`、要素を素のスイッチにするための `.labelsHidden()`）、`Stepper`（`ctrl.stepper`）、刻みを付けた `Slider`（`ctrl.slider`）、セグメントごとの `Button` で組んだ単一選択セグメント（`ctrl.segment.one` から `ctrl.segment.three`）、`Menu`（`ctrl.menu`、その項目はシステムのポップオーバーからラベルで指定します）、そして有効と恒久的に無効の `Button` の対（`ctrl.button` と `ctrl.buttonDisabled`）が並びます。各コントロールは自身の状態を兄弟の `ctrl.<name>.value` 結果ラベルへ写します。
- **`ListsNavView`（`SAMPLE_TAB=lists`）** は動機で名指しされたコンテナ系コントロールです。`NavigationStack`、`.searchable` 相当の `TextField`（`lists.search`）、データ由来の id を持つ `NavigationLink` 行（`lists.row.<id>`）からなる `List`（`lists.list`）、そして `EditButton`（`lists.edit`）です。「コンテナが子要素を呑み込む」や「`.searchable` が誤った識別子を報告する」という症状が実際に現れるのはここです。

これらの id は、アプリ自身の名前空間に由来します。既存の `ControlsView` と `ListsNavView` のシナリオがすでに使っている、`ctrl` と `lists` の接頭辞です。現在、[`demos/features/demo.config.yaml`](../../demos/features/demo.config.yaml) の `idNamespaces` には `home`、`list`、`comp` などが並んでいますが、`ctrl` と `lists` は**含まれていません**。したがって、カタログを配線するには、その 2 つの接頭辞をそこへ足します。変更は一行の設定です。提案がリポジトリの現状に即すよう、ここに明記しておきます。

カタログが動かすのは、idb が `Toggle` や `List` をどう `Element` へ正規化するかです。特定のアプリが選んだ名前は対象外です。

将来、固定する価値のあるコントロール型が現れ、それを載せる既存画面がない場合を考えます。その場合は、安定した `accessibilityIdentifier` を与えてカタログに追加します。対象面は広がりますが、仕組みは変わりません。

カタログを別の fixture アプリではなく既存のサンプルアプリ内に置くことには、もう 1 つ利点があります。e2e ジョブがすでに行うビルドと起動とインストールが、追加の費用なしでカタログにも及びます。

### golden の形式とアサーション

各コントロールの期待値は、1 つの `base.Element`（`bajutsu/drivers/base.py`）です。これは `query()` が生み出す形そのものなので、照合は間にアダプタを挟まない、値どうしの比較になります。

golden は、選択と操作を左右する per-element のフィールドを記録します。そのうち 4 つは、`base.matches` が参照する `identifier`、`label`、`traits`、`value` です。5 つ目は `frame` です。`matches` は `frame` を読みませんが、`find_all` の `within`（幾何的な包含）と idb の座標タップは `frame` に依存します。そのため、正規化形を固定する価値があります。

- `identifier` は `id` と `idMatches` のセレクタキーです。最も比重の大きいフィールドで、厳密に照合します。ここのずれが、まさに「後で要素が見つからなくなる」障害そのものです。
- `label` は `label` と `labelMatches` のキーです。厳密に照合します（カタログでは固定の英語文字列で、ローカライズされた値や実行時の値ではありません）。
- `traits` は `idb._traits` が正規化したトークン（AX 型を `_norm_type` したものに、`notEnabled` や `selected` を加えたもの）です。trait の順序で golden がフレーキーにならないよう、集合として照合します。`ctrl.buttonDisabled` が `base.Trait.NOT_ENABLED` を、選択中のセグメントが `base.Trait.SELECTED` を必ず帯びるべき、というのがここで効きます。
- `value` は `value` セレクタキーです。`ctrl.<name>.value` の写しラベルにより、画面の初期状態では固定で決定的な文字列になります。
- `frame` は `base.matches` は参照しませんが、`find_all` の `within` スコープと座標タップが依存します。寛容に照合します（後述の「実行場所と検証計画」を参照）。

golden ファイルは、カタログのシナリオの隣、`demos/features/app/scenarios/` の下に置きます。コントロール別または画面別に分けた `goldens/` サブフォルダを使い、たとえば `goldens/controls.json` とします。ファイルはチェックインした JSON で、`parse_describe_all` が出力する `base.Element` の辞書そのものです。したがって、golden の更新は、フレーム許容を適用して記録した `query()` のスナップショットにほかなりません。

アサーションは、1 本の決定的な流れです。

1. `launchEnv` で画面へ駆動します。
2. 画面が落ち着くのを待ちます（後述）。
3. `IdbDriver.query()` を呼びます。
4. 正規化ツリーを、コントロール id ごとにフィールド単位で golden と照合します。

比較は決定的ですが、**辞書全体の等価判定ではなくフィールドごと**です。`identifier`、`label`、`value` は厳密に照合します。`traits` は集合一致（順序非依存）、`frame` は後述の寛容な幾何チェックです。経路のどこにも LLM はありません。run と CI の判定が求める決定性の規律に、そのまま収まります。

### 落ち着いた状態と一過性

チェックは、固定時間の sleep を一切しません。既存の条件待機経路で待ちます。つまり `IdbDriver.wait_for(sel, timeout)` が、目的画面の既知のアンカー（たとえば `ctrl.title` や `lists.list`）が現れるまで `query()` をポーリングします。その後に初めて、ツリーを撮って照合します。

これにより golden は、既存の 2 つの一過性への防御ときれいに分離され、どちらも他方をマスクしません。

- `query()` の `_max_seen` ゲート付きリトライ（`_is_transient_empty` と `_READY_MIN`）は、アサーションの下で引き続き idb の遷移中のほぼ空のツリーを吸収します。golden が照合するのはそのリトライが返すツリー、つまり落ち着いた定常状態です。一過性を捕まえるのは golden の役目ではありません。
- **BE-0087**（idb のアクション settle、進行中）は補完する軸です。あちらはアクションの効果が落ち着いた後にアサーションすることを保証します。BE-0006 は落ち着いたツリーがどんな形かを固定し、BE-0087 はそれを待つことを固定します。一方の回帰はもう一方の回帰を隠すことなく、それ自身のチェックで失敗します。BE-0006 の golden は静止した画面で読むので、settle はそこで検証中の変数ではありません。

### ずれの差分

idb や iOS リリース、あるいはコントロールの構成が、正規化出力の形を変えたとします。このとき golden アサーションは、e2e 経路で、フィールド単位の具体的な差分とともに失敗します。差分の例は、「`ctrl.toggle`: traits expected `{switch}` got `{button}`」や「`lists.search`: identifier expected `lists.search` got `null`」です。どのコントロールのどのフィールドが動いたかを名指しします。

差分は、現場で静かに起きる障害の一群を、位置の特定された、声を上げるビルド失敗へ変えます。その障害とは、シナリオが要素を黙って見つけられなくなること、あるいは別の要素にマッチすることです。修正は明白です。`idb.py` の正規化器を意図的に更新し、同じレビュー済みの変更で golden を撮り直します。そうでなければ、本物の idb や iOS の回帰だと認めます。

golden は、**BE-0005**（idb_companion バージョン監視、実装済み）と明快な接合面で対になります。BE-0005 は、*どの* idb が入っているかを見張り、バージョン範囲を固定します。BE-0006 は、*その idb が何を生み出すか*を見張ります。

BE-0005 の毎週の `idb-monitor.yml` は、すでに smoke シナリオを最新の companion で `parse_describe_all` に通しています。カタログ golden を同じ間隔で走らせれば、「スキーマが変わった」という曖昧な smoke の失敗を、動いた具体的なフィールドへと変えられます。

### 実行場所と検証計画

golden アサーションは、重めのオンデバイス経路で走り、高速な PR 単位ゲートでは決して走りません。`make -C demos/features e2e` や [`.github/workflows/e2e.yml`](../../.github/workflows/e2e.yml) の `smoke` ジョブと同じ、macOS と Simulator の面を使います。この面は、すでにサンプルアプリをビルドして Simulator を起動し、アプリをインストールし、実際の idb を通してシナリオを走らせています。

カタログ golden は、そこにシナリオとして追加します。BE-0005 の毎週の監視へ加えるのも自然です。metered な macOS 分を消費するのは、デバイスに関係する PR と所定の間隔のときだけで、`make check` は手つかずのままです。

唯一の本当の緊張は `frame` です。正確なピクセル座標は、デバイス、ランタイム、スケール、セーフエリアのインセットによって変わります。厳密に照合すると、構造的にフレーキーになります。これは、アサーションは本物の回帰のときだけ失敗すべきだという、決定性の指針の趣旨に反します。

解決は、**同一性は厳密に、形状は寛容に**です。`identifier`、`label`、`traits`、`value` は厳密に比較します。`frame` は妥当性だけを確認します。幅と高さが非ゼロであること、そして要素が画面の境界内に収まっていることです。包含判定には、`within` セレクタがすでに使う `base._contains` と同じものを再利用します。これで、重要な障害を、デバイスの正確なピクセルに固定せずに捕まえられます。重要な障害とは、要素がゼロフレームに潰れることと、コンテナが子要素をもう囲まないことです。

検証計画は、次の 3 段階です。

1. 各カタログ画面へ駆動し、`query()` を撮ります。
2. 同一性と状態の 4 フィールドを golden と厳密に、`frame` を境界内で照合します。
3. 不一致があれば、前述のフィールド単位の差分を出します。

## 検討した代替案

- **既存のシナリオ別 e2e デモに頼る。** デモシナリオは、すでに実機で idb に触れます。ただし、アサーションの対象はアプリの挙動であって、各コントロール型の正規化ツリーではありません。たとえば、`.searchable` が識別子を報告する仕方に限った回帰は、現行のどのシナリオも壊さないまま、次に書かれるシナリオを壊しうるのです。専用のコントロールカタログは、表現そのものをテスト対象にします。
- **`query()` を強化して奇妙なツリーを修復する。** 想定外の SwiftUI の形を、「期待される」形へ正規化経路内で書き換えるヒューリスティックを足すこともできます。ヒューリスティックは、ずれを報告せず隠します。決定性が要となる経路に、アプリ固有の推測も載せます。golden に照合し、正規化器を意図的に更新するほうが、`query()` を単純に、変更をレビュー済みに保てます。
- **実アプリの全画面をスナップショットする。** 全画面のスナップショットは、網羅性は最大ですが、脆くアプリ固有です。チェックを 1 つのアプリの進化する UI に結び付け、ツールレベルの保証にアプリ単位の事柄を再導入します。標準コントロールに絞ったカタログのほうが安定し、app-agnostic を保てます。
