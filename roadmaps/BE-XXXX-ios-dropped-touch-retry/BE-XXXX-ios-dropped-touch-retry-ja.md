## はじめに

iOS Simulator では、XCUITest が合成したタッチがテスト対象のアプリに届かないことがあります。
それでも XCUITest はタッチを届けたと報告するので、`tap` ステップは何もしないまま成功します。
本提案では、XCUITest バックエンドがこの取りこぼしを Simulator 自身のログから検出します。
そのうえで、タッチを最大 2 回まで打ち直します。2 回打ち直しても取りこぼした場合は、取りこぼしを理由として名指ししてステップを失敗させます。

取りこぼしの原因は 1 つで、外から観測できます。XCUITest のテスト管理プロセス（`testmanagerd`）は、
タッチを合成するたびに新しい仮想タッチデジタイザーを `backboardd` に接続します。`backboardd` は、
タッチをアプリへ振り分ける Simulator のプロセスです。この `backboardd` が、まれに 1 つのデジタイザーを
2 つのサービスとして登録します。すると touch down が片方のサービスのタッチ状態に入り、残りのイベントは
もう片方に入ります。`backboardd` は残りのイベントを捨ててその旨をログに残し、デジタイザーが外れるときに
途中まで届いたタッチをキャンセルします。アプリが受け取るのはキャンセルされたタッチなので、どのコントロールも
反応しません。このログ行はタッチ 1 回ごとの決定的なシグナルです。本提案は、runner が合成するすべての
タッチについて、このシグナルを判定に変えます。

## 動機

取りこぼされたタッチは誤った成功を生みます。決定的なゲートにとって、もっとも高くつく結果です。
タッチを取りこぼしたステップは成功を報告します。誰かが気付くかどうかは、シナリオがその後に何を確かめるかで
決まります。後続の `wait` が時間切れになれば、取りこぼしは別のステップの失敗として現れます。
後続の確認がないシナリオは、何も検証しないまま成功し続けます。

取りこぼしは仮定の話ではありません。CI の `app-crash (xcuitest)` ジョブは、アプリをクラッシュさせる
ボタンをタップし、次のステップが失敗することを期待するシナリオを実行します。このジョブは
[#2154](https://github.com/bajutsu-e2e/bajutsu/pull/2154) で 2 回続けて失敗しました。クラッシュボタンの
タップがアプリに届かず、失敗するはずのシナリオが成功したためです。その後の実行では、
`actuation (xcuitest)` ジョブが `paste_system_alert` のタブを開くタップを取りこぼしました。20 秒後には、
そのステップの `wait` が時間切れになりました。採取したすべての取りこぼしで、Simulator の統合ログに同じ行が出ています。

| 実行 | 取りこぼしたタッチ | `backboardd` のログ行 |
|---|---|---|
| 38198619020、attempt 1 | クラッシュボタン（最初のタップ） | `digitizer event … from unsupported service` の後に `skipping event` |
| 38198619020、attempt 2 | クラッシュボタン（最初のタップ） | `unknown digitizer` の後に `skipping event` |
| 38241318813、attempt 1 | `perm` タブ（実行開始から 62 秒後） | `unknown digitizer` の後に `skipping event` |

3 件目と同じ実行の正常なタップ 82 回には、これらの行が 1 つも出ていません。シグナルと取りこぼしは
1 対 1 で対応しています。ログの詳しい分析は [#2157](https://github.com/bajutsu-e2e/bajutsu/issues/2157) に
あります。

最初の 2 件からは「セッションの最初のタッチだけが取りこぼされる」と読めます。しかし、この競合は最初の
タッチに限りません。3 件目は先にウォームアップのタッチを済ませた後で起きており、デジタイザーの接続も 32 ミリ秒で
終わっていました。このため、ウォームアップのタッチでは競合を防げません（ウォームアップを試した
[#2160](https://github.com/bajutsu-e2e/bajutsu/pull/2160) はクローズしました）。タッチの合成をやめることも
できません。XCUITest には、アプリを操作する手段がほかにないからです。

取りこぼしたタッチを打ち直しても安全です。デジタイザーが外れるときに `backboardd` が途中までのタッチを
キャンセルするので、アプリが完了したタッチを見ることはありません。コントロールは反応せず、
ジェスチャー認識も完了しません。したがって、2 回目のタッチが 1 回目の操作を二重に実行することはありません。ただしこれは、1 つの判定が
ちょうど 1 回の合成タッチを対象にしている場合に限ります。以下の設計は、この条件を保証します。

この変更が入ったかどうかは、2 か所で確かめられます。1 つは実行の証跡で、打ち直したタッチが、それを要した
操作に結び付けて記録されます。もう 1 つは iOS CI の繰り返し実行で、上で挙げた誤った成功が再発しなくなります。
`app-crash (xcuitest)` は、クラッシュボタンを押さないまま成功しなくなります。

## 詳細設計

### 対象範囲

runner のエンドポイントのうち、タッチを合成するものはすべて対象にします。具体的には、`/tap`（ハンドル指定、
座標指定、タップ回数指定、長押し）、`/gesture`（ピンチと回転）、`/swipe`、`/scroll`、ピッカーホイールの
調整、システムアラートのボタンのタップです。文字入力はタッチデジタイザーではなくキーイベントを使うので、
対象外とします。

既存の動作のうち 2 つは、1 つの判定の中に複数のタッチを入れてしまうので、設計で取り除きます。
1 つ目は `/gesture` です。シナリオが `BAJUTSU_GESTURE_RETRY=1` を設定すると、runner の中でピンチや回転を最大 4 回実行します（打ち直しは最大 3 回です）。ユニット 4 で、ドライバー側の打ち直しが入った後にこのループを廃止し、打ち直しをドライバー側に一本化します。
2 つ目は runner の割り込み監視です。割り込み監視は、外側の操作の途中でアラートのボタンをタップしたり、
通知バナーをスワイプして消したりします。これらのタッチには、後で述べる専用の印を付けます。

ピッカーホイールの調整は、1 回の呼び出しで複数のドラッグを合成することがあります。それでも打ち直しは
安全です。調整は目標の値を指定する操作なので、同じ値への 2 回目の調整は、1 回目で設定した値を変えません。

この仕組みは、XCUITest バックエンドで iOS Simulator を使うすべての実行で、設定なしで動きます。誤った成功は
誰も注意していない場所で起きるので、利用者が有効にするのを待っていては守れません。実機は対象外です。
実機の統合ログは同じ方法ではホストに届かず、実機での取りこぼしも観測されていません。

### runner は合成の前後に印を出す

runner（`BajutsuKit/Runner/Sources/XcuitestElementProvider.swift`）の対象ハンドラーは、タッチの合成を
挟んで 2 行の `os_log` を出します。出力先は専用のサブシステムとカテゴリーです。

```
bajutsu.synthesis begin <id>
bajutsu.synthesis end <id>
```

`<id>` は runner が持つカウンターで、runner プロセスが生きている間は一意です。割り込み監視も、
自分のタッチを同じ形の印で囲み、専用の ID を振ります。割り込み監視の印は、割り込んだ外側の操作の区間の
内側で入れ子になります。対象エンドポイントの応答には、
省略可能な `synthesisId` フィールドを足します（`BajutsuKit/Sources/BajutsuRunner/openapi.yaml`）。
割り込み監視が処理した `labels` と `banners` を返す応答には、`tappedAlerts` と同じく、要素ごとに
対応する配列を足します。対象は `/interruptionPolicy/drain` の応答と、同じ記録を取り込む `tap` と
`resolveAlerts` の応答です。配列には、各要素の元になった割り込み監視のタッチの合成 ID を入れます。
応答にこのフィールドがなければ、タッチは合成されていません（ハンドルが古くなっていた場合など）。
その場合、検証するものはありません。

### ホストは Simulator のログを監視する

XCUITest の環境（`bajutsu/common/platform_lifecycle/environments/xcuitest/`）は、デバイスのセッションごとに
`xcrun simctl spawn <udid> log stream` プロセスを 1 つ起動します。起動するのは runner と同時です。このプロセスは、runner の
サブシステムと `backboardd` の `TouchEvents` カテゴリーに絞り込みます。証跡の `deviceLog` 採取は、同じ
コマンドをすでに組み立てています（`bajutsu/common/evidence/intervals/_functions.py` の `device_log_cmd`）。
パーサーはストリームを小さな表に変換します。表には、合成 ID ごとの開始時刻と終了時刻、取りこぼしの行ごとの
時刻を記録します。

パーサーは、取りこぼしの行を、その時刻にいちばん内側で開いている区間に帰属させます。割り込み監視のタッチが
取りこぼされても、外側の操作が取りこぼしと判定されることはありません。

パーサーは、`backboardd` の次の 3 種類のメッセージを取りこぼしと分類します。

- `unknown digitizer`
- `digitizer event for display <main> from unsupported service`
- `didn't see a previous touch down or range-in event … skipping event`

### 合成ごとの判定

対象エンドポイントが `synthesisId` 付きで応答すると、ドライバーはその ID の判定をモニターに問い合わせます。
モニターはその ID の終了印を待ちます。この待ちは上限付きの条件待ちで、固定時間の待ちではありません。
その後、次の 3 つのいずれかの判定を返します。

| 判定 | 意味 | ドライバーの対応 |
|---|---|---|
| `delivered` | その ID の開始印と終了印の間に、取りこぼしの行がない。 | そのまま進めます。 |
| `dropped` | その区間に、取りこぼしの行が 1 つ以上ある。 | 同じリクエストを打ち直します。 |
| `unverified` | 終了印が上限時間内に届かなかった。 | そのまま進め、判定を記録します。 |

`unverified` の判定では、実行は現在と同じ動きをします。ログの流れが止まっても、健全なシナリオが
失敗することはありません。上限時間は、ユニット 1 の実測から決めます。

割り込み監視のタッチが取りこぼされても、打ち直しはしません。
バナーのスワイプは、割り込みを処理したと答える前に消えたことを確かめ、消えていなければ処理を断ります。
アラートは、処理したと答えた後も残っていれば、XCUITest が次の操作で割り込み監視を再び呼び出します。
取りこぼされたボタンのタップは、そこで押し直されます。変わるのはレポートです。
アラートへの応答やバナーの消去は、その表示に対して割り込み監視が合成したタッチがすべて取りこぼされた場合に限り、
未確認として報告します。こうして実行は、
アプリに届いていない応答を「答えた」と報告しなくなります。

### 打ち直し、それでも届かなければ名指しで失敗させる

`XcuitestDriver`（`bajutsu/common/drivers/xcuitest/xcuitest_driver.py`）は、`dropped` と判定されたリクエストを
最大 2 回まで打ち直します。打ち直しは元のリクエストと同じ経路を通ります。`stale` の応答で起きるハンドルの
再解決（BE-0289）も、この経路に含まれます。3 回目も `dropped` なら、新しい `TouchNotDelivered` エラーを
送出します。エラーの理由には、セレクターではなく Simulator の競合を書きます。要素が見つからなかった失敗と
取り違えないためです。

実行の証跡に残る各操作の記録には、その操作がたどった判定を加えます。打ち直したタップは、ふつうのタップでは
なく、取りこぼしの記録とともにレポートに現れます。

### 基本方針との関係

- **AI は判定しない。** 判定は決まったログメッセージと時刻から下し、大規模言語モデル（LLM）は使いません。
- **決定性を優先する。** モニターは終了印という条件を、上限付きで待ちます。上限付きの打ち直しは、
  BE-0289 の古いハンドルに対する上限付きの再試行と同じ形です。
- **アプリに依存しない。** シグナルは `backboardd` と runner から得ます。テスト対象のアプリからは何も得ません。

### 作業分割

1. **CI ホストで印の経路を実測する。** 使い捨ての runner ビルドから印を出します。そのうえで、iOS CI ホストで
   2 つの値を記録します。1 つは、終了印が出てからホストに届くまでの遅れです。もう 1 つは、`backboardd` の行が、それより
   後に出た runner の印よりも遅れて届くことがあるかどうかです。前者で上限時間を決めます。後者で、判定が
   到着順を比べてよいか、時刻を比べる必要があるかを決めます。2 本指のピンチや回転が取りこぼされた場合にも、同じ `backboardd` の行が出ることを確かめます。
2. **runner の印と `synthesisId`。** 対象のすべてのハンドラーと、割り込み監視のタッチに `os_log` の印を
   足します。`openapi.yaml` と対象の応答には、省略可能な `synthesisId` フィールドを足します。
   割り込み監視のタッチの ID は、`labels` と `banners` を返すすべての応答
   （`/interruptionPolicy/drain`、`tap`、`resolveAlerts`）に、要素ごとに対応する配列として足します。
   ID のカウンターと応答のフィールドは `swift test` で検証します。
3. **ホストのログモニター。** `log stream` プロセスをデバイスのセッションに合わせて起動と停止し、出力を解析して
   判定を返します。取りこぼしの行はいちばん内側の区間に帰属させ、割り込み監視が合成したタッチがすべて取りこぼされた表示への応答は、
   未確認として報告します。パーサー、入れ子、3 種類の判定は、記録したストリームを使って高速スイートで
   検証します。
4. **ドライバーの打ち直しと `TouchNotDelivered`。** 対象の操作のたびに判定を確かめ、最大 2 回まで打ち直し、
   それでも届かなければ新しいエラーを送出します。判定は操作の証跡に記録します。`/gesture` の `BAJUTSU_GESTURE_RETRY` のループを廃止し、`demos/showcase/scenarios/gestures_multitouch.yaml` からその有効化設定とコメントを削除します。打ち直しの上限とエラーは、
   偽のモニターを使って高速スイートで検証します。
5. **ドキュメント。** 判定と打ち直し、新しいエラーを `docs/` とその `docs/ja/` ミラーに書きます。XCUITest の
   操作の経路を説明している `DESIGN.md` や `docs/architecture.md` の箇所も更新します。
6. **CI で確かめる。** `app-crash (xcuitest)` と `actuation (xcuitest)` を繰り返し実行します。誤った成功や
   取り違えた時間切れの代わりに、打ち直しが記録されることを確かめます。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| runner が配信を始める前にウォームアップのタッチを打つ | 競合は最初のタッチに限りません。ウォームアップを実装した [#2160](https://github.com/bajutsu-e2e/bajutsu/pull/2160) でも、同じ CI 実行の後半のタップが取りこぼされました。 |
| ホストの時刻で突き合わせ、一定の猶予を置く | 固定の待ちは基本方針 2 に反します。遅いホストでは猶予が切れた後に取りこぼしの行が届き、見落とすこともあります。 |
| ステップの境界でまとめてログを調べる | タッチごとのコストは下がりますが、取りこぼしがわかるのは後続の操作が動いた後です。その時点ではタッチを安全に打ち直せないので、ステップを失敗させることしかできません。 |
| 取りこぼしたら打ち直さずに失敗させる | 誤った成功は消えますが、競合に当たったシナリオはどれもフレークとして失敗し続けます。アプリはキャンセルされたタッチを受け取っているので、打ち直しは安全です。 |
| 取りこぼしを証跡に記録するだけにする | 誤った成功が残ります。取りこぼしに気付けるのは、実行後に証跡を読んだ人だけです。 |
| 設定で明示的に有効にする | 誤った成功は誰も予期しない場所で起きるので、有効にした利用者、つまりすでに競合を知っている利用者しか守れません。 |
