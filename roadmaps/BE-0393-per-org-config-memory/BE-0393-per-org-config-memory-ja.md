## はじめに

この項目は、org ごとに「前回使った config」を永続的に覚えさせます。そして、config を必要とする
セッションへその内容を復元します。メンバーは、org の config が入った状態から作業を始められます。
org は Bajutsu のマルチテナンシーの単位です。GitHub login がサインインするテナントであり、org 単位の
値が紐づく範囲でもあります。登録済みプロジェクト、AI プロバイダ設定、シークレット、監査ログはすでに
そう紐づいています
（[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md)）。バインド済みの
config は、記録もされず、どこにも紐づいていない唯一の値です。今はプロセス全体でバインドが1つ
です。そのためサインインしたメンバーが見るのは、プロセスがたまたま最後に持っていた状態です。
たいていは空なので、作業を始めるには bundle を upload しなおすことになります。

この項目は、1つのバインドが混ぜてしまっている2つの問いを分けます。**記録の置き場**は org です。
その org が前回どの config を使ったかは、メンバーが共有する値であり、どのセッションよりも長く残る
べき値です。**動いているバインドの範囲**はセッションです。同じ org の2人が同時に作業できなければ
なりませんし、片方の config 切り替えが、もう片方の run の足元を動かしてはなりません。自分の
バインドを持たないセッションは、org が覚えている config を継承します。したがって何も変えない2人は、
同じ config と同じ target の一覧を見ます。共同作業の場合です。そのうえでどちらも、相手を乱さずに
別のものをバインドできます。開発者のマシンで動く単一テナントの `serve` が持つ org とセッションは、どちらも
1つです。したがって振る舞いは変わりません。

## 動機

今は org としてサインインしても、config が空の状態から始まります。`serve` はバインド済みの config を、
プロセス全体で1組のフィールドに持っています（[`bajutsu/serve/state.py`](../../bajutsu/serve/state.py)）。
内訳は次の6つです。

- config ファイルのパス
- 相対パスの解決元となるディレクトリ
- Git 由来の provenance
- 実行時にバインドした Git source かどうかのフラグ
- 由来となった upload 済み bundle
- バインドした org

`--config` なしで起動したデプロイでは、どれも設定されていません。そのため各セッションが最初に
メンバーへ求めるのは、前のセッションですでに済ませた作業です。upload、Git spec の指定、
ファイルブラウザでの選択のいずれかです。
[target](../../docs/ja/glossary.md#target-app-device) の一覧すら、その前には出ません。

必要な記録の置き場は、Bajutsu にすでにあります。ただし、書き込んでいません。**プロジェクト**とは
config source への名前付きのバインドであり、org ごとに保持されます。保持する内容は locator と、その
org が active にしているプロジェクトです。locator が指すのは、Git source、ローカルファイル、SHA-256
の content hash で指す upload 済み bundle のいずれかです
（[BE-0225](../BE-0225-config-project-hub/BE-0225-config-project-hub-ja.md)）。プロジェクトを
切り替えると、config は live で再バインドされます。upload 済み bundle も対象です。bundle のバイト列は
content hash のもとで永続的に保存されているからです
（[BE-0243](../BE-0243-upload-bundle-durable-storage/BE-0243-upload-bundle-durable-storage-ja.md)）。

それでも記録が実際には空のままである理由は、3つの欠落です。1つめは、メンバーが実際に行うバインドが
プロジェクトを登録しないことです。対象は、ファイルブラウザからのバインド、Git からのバインド、
bundle の upload、compose された artifact のバインドの4つです。その org が何をバインドしたのかは、
どこにも残りません。2つめは、データベース版のレジストリが active なプロジェクトを持つ場所です。
テーブルではなくプロセス内の辞書に持っています。org を持つデプロイの形が、active だった
プロジェクトを忘れる形になっています。3つめは、起動時の config が `default` org のもとにだけ自動
登録されることです。マルチテナントのデプロイでは、`default` 以外の org は最初のエントリを持ちません。

3つの欠落を埋めれば、org が前回使った config は復元できるようになります。しかし、復元しても安全に
はなりません。1つのプロセスが持つバインドは1つです。org B のメンバーがサインインしたときに org B の
config を復元すると、org A から config を奪います。org A の run、record、crawl は、同じフィールドを
通してシナリオやアプリケーションのパスを解決しているからです。あるメンバー自身のサインインが、別の
テナントの失敗した run になります。同じ衝突は、復元がなくても1つの org の中で起きます。今のままだと、
あるブランチの bundle をバインドしたメンバーは、同じ org の同僚全員の config を実行中に差し替えます。
したがって変えるべきものはバインドそのものであり、必要な範囲は org ではなくセッションです。org ごとの
バインドはテナントをまたぐ衝突を消しますが、org の中の衝突は残します。そして残るほうが、同じ
プロジェクトをテストしようとしている2人に降りかかる衝突です。

一方で、記録が必要とする範囲は org です。バインドの周囲の seam は、すでにどれも org 単位で解決して
います。リクエストが解決するストレージの束（`for_org`）、並列実行の上限、オブジェクトストアの
prefix がその例です。org ごとのプロバイダ設定もそうです
（[BE-0229](../BE-0229-per-org-provider-settings-resolution/BE-0229-per-org-provider-settings-resolution-ja.md)）。
バインドは、他をすべて acting org から解決するリクエスト経路に残った、最後の暗黙のグローバル
です。そして記録の置き場としては、プロジェクトのレジストリがその org 単位のストアにあたります。

upload の手間が消えることの他に、2つの結果が付いてきます。1つは、デプロイが1つの config で
メンバーを直列化しなくなることです。2つの org も、1つの org の2人も、互いのバインドを上書きせず
同時に作業できます。もう1つは、バインドの所有 org が疑いなく決まることです。今のグローバルな
バインドが強いている target の所有権の問いは、これで決まります。アプリケーションプログラミングインタ
フェース（API）経由でバインドされた config はバインドした org のものであり、その `orgs:` ブロックは
何も分割しません
（[BE-0375](../BE-0375-serve-org-lifecycle-management/BE-0375-serve-org-lifecycle-management-ja.md)）。
今はその規則を、1つだけのグローバルなバインドに所有者のタグを付けて表しています。

この項目は、ロードマップの未整理のアイデアも吸収します。サインイン直後に、その org の active な
プロジェクトへ直接遷移させるというアイデアです。そのアイデアは遷移先がすでにあることを前提にして
いました。遷移先がない理由は上の3つの欠落であり、以下のユニットがその遷移先を作ります。

## 詳細設計

ここには決定的な `run` の経路に触れる変更はなく、AI の呼び出しもどこにも増えません。バインドは
データです。その復元は、参照と実体化のどちらも機械的に検査できます（第1の prime directive）。
ユニット1とユニット2は、単一テナントのデプロイでは振る舞いを変えないリファクタです。ユニット3から5
は、その2つに依存しません。バインドの記録、active なプロジェクトの永続化、ローカルキャッシュからの
bundle の復元は、今の1つだけのバインドに対しても追加できます。この3つだけでも、プロジェクトを手で
切り替えてよいメンバーにとっては upload のやり直しが消えます。ユニット1、2、6、7 は、それを
「config が最初から入っている」状態に変えるためのものです。

### 1. 散らばった6つのフィールドを1つのバインドの値にする

まとまって初めてバインドになるフィールドを、1つの不変な `ConfigBinding` の値にまとめます。対象は
`config`、`cwd`、`config_provenance`、`upload`、`git_config_from_api`、`config_org` の6つです。
`ServeState` には、その値を持つフィールドを1つだけ置きます。今のバインドは、まとめて書かなければ
ならない6つの可変な属性です。実際にどのバインダもすべてを設定しています。`release_upload` は、古い
bundle のディレクトリが次のバインドへ漏れないよう、そのうち3つをクリアします。値をまるごと
入れ替える形にすれば、中途半端な組み合わせは表現できなくなります。さらにユニット2がセッションごとに持つ
対象も、6つではなく1つになります。振る舞いは変わりません。serve のモジュールに散る `state.config`
の約46箇所と `state.cwd` の約24箇所の読み出しは、この値のフィールドを読む形に移ります。

### 2. セッションごとのバインドと、その org を通した解決

1つだけのバインドのフィールドを、ログインセッションと **acting org** の組から `ConfigBinding` への
対応に置き換えます。セッションは、メンバー自身の作業が起きる範囲です。したがって、あるセッションで
行ったバインドはそのセッションにだけ見えます。同僚のセッションも、同じメンバーの別マシンの
セッションも、それぞれが持っていたものを保ちます。セッションの枠は、セッションの終了とともに落ちます。
落とす場所は、セッションストアがすでに行っている revoke と、対応が自分で持つ上限です。上限があるので、
静かになったセッションがたまるプロセスでも、対応は無限には育たず古いバインドから追い出されます。
key に acting org を加える理由は、セッションが
acting org を変えうることです。ある org として作ったバインドが、別の org として答えるわけには
いきません。target の所有権は org に乗っています。そのため org の変更をまたいで残ったバインドは、
ある org の target を、別の org として来たリクエストへ渡してしまいます。セッションのバインドはセッションとともに消えます。残るのは org が覚えて
いる config（ユニット4）であり、次のセッションはそれを継承します（ユニット6）。

各バインドは、それを行った org を引き続き記録します。target の所有権はセッションではなく org の
問いだからです。API 経由でバインドされた config は、バインドした org のものです。そのため
`targets_for` はその org を、グローバルなタグではなくバインドから読みます。起動時の config は、今の意味のまま **フォールバックのバインド**になります。自分の
バインドを持たず、継承する config もないセッションは、`serve` が起動した config を読みます。その
`orgs:` ブロックは、今と同じように target を org 間で分割します。

バインドを読む場所は、どれもセッションを持つリクエストの中とは限りません。actor をそもそも
受け取らない読み出しが5つあります。`config_content`、`server_settings`、`active_key_env`、
使用量台帳のパス、シナリオのディレクトリを解決する `_scenarios_dir_for` です。しかもそのうち2つは、
デプロイ全体の答えを求めています。そこで、5つそれぞれを明示的に決めます。メンバーが何に対して作業して
いるかを報告する3つは、暗黙のバインドではなくセッションのバインドを解決します。config の表示、
サーバ設定タブが示す `hasConfig`／`configSource`／config のパス、シナリオのディレクトリです。
このうち2つは、ハンドラからセッションを受け取ります。シナリオのディレクトリは受け取れません。
`_scenarios_dir_for` へ届く経路は、`ServeState` が `self` を包んで1度だけ作り、`for_org` がどの org へも
同じものを返すクロージャです。したがってクロージャが動く時点でハンドラは視界にありません。そこで
セッションを見る形にする seam は、シナリオストア側の解決になります。リクエストはすでにセッションを
持ってそこへ届いています。デプロイを説明する残りの2つ、
有効なキーの環境変数と使用量台帳は、フォールバックのバインドを読むと明記します。
このユニットが消すのは暗黙のデフォルトなので、都合の悪い読み出しのためにそれを1つ残せば、バグは
そのまま残ります。

run が、あとの再バインドに追随するわけにはいきません。しかし今は、部分的に追随します。job の
コマンドラインは `--config` を持つので、run が読む config ファイルは dispatch の時点で固定です。
worker の run は、config のテキスト自体を materials で運びます。一方で作業ディレクトリは固定されて
いません。`Job.cwd` のデフォルト値は `None` で、どの dispatcher も設定しません。そのため spawn は `popen`
の時点で `state.cwd` を読みます。登録から spawn までの窓、つまりデバイスの起動やその場のビルドが
開けたままにする窓で再バインドが起きると、すでに受け付けた run の作業ディレクトリが動きます。この
ユニットはその窓を閉じます。enqueue の時点でセッションのバインドを job に取り込み、取り込んだ値から
spawn します。

### 3. すべてのバインドが org のプロジェクトを記録する

4つのバインドのそれぞれが、acting org のもとにプロジェクトを登録し、その org が覚えている config に
します。対象は
ファイルブラウザからのバインド、Git からのバインド、bundle の upload、compose された artifact の
バインドです。レジストリの `add` は名前について冪等で、既存の名前の source は張り替えます。そのため
同じプロジェクトを何度バインドしても、重複と衝突は起きません。永続的な記録を作るのはこのユニット
です。これがなければ、ユニット2の対応は毎回の起動時に空です。

名前の付け方は、起動時の config がすでに導いている識別（`launch_project_identity`）を拡張して
使います。
その識別は、config のパスと provenance から決まります。Git source はリポジトリとパスで、upload は
ファイル名で自分を名乗ります。プロジェクトのページを一度も開かないメンバーにも、読める名前の
エントリが残ります。

### 4. active なプロジェクトを org ごとに永続化する

データベース版のレジストリに、org ごとの永続的な active なプロジェクトを持たせます。これで再起動でも
落ちません。ファイル版のローカルレジストリは、すでに JSON のストアへ active なプロジェクトを永続化
しています。データベース版はプロセス内の辞書に持っています。形は、BE-0229 がプロバイダ設定に使って
いる形と同じにします。`provider_settings` テーブルが `org_id` で紐づいている理由は、まさにこれ
です。`orgs` の行に `active_project_id` の列を置けば、org ごとの active なプロジェクトは1つだと
構造で決まります。広いテーブルへの一意制約は要りません。あわせて、起動時の登録では
`default` org の固定を外します。マルチテナントのデプロイでは、起動時の config へ到達できる org の
ために登録します。

### 5. オブジェクトストアなしで upload 済み bundle を復元する

upload 由来のプロジェクトを再度 active にするとき、オブジェクトストアを要求する前にローカルの
展開キャッシュを見ます。今の再 active 化は、オブジェクトストアが設定されていないと、キャッシュを
見る前に「復元元がない」と返します。しかし展開済みの bundle は content hash のもとでそのキャッシュ
に残っています。そのディレクトリは再起動をまたいで残ります。キャッシュへの命中は、設定済みの
デプロイがすでに通る経路です。結果として、オブジェクトストアを持たない可能性がもっとも高い
デプロイの形が、ディスク上に持っている bundle を復元できない形になっています。ローカルや単一
ノードの `serve` がそれにあたります。キャッシュの経路を守っている content hash の検証は、そのまま
残します。hash はクライアントが形を決められる、保存済みのプロジェクトのレコードから来ます。だから
パスの一部となる前に検証されます（BE-0243）。このユニットが変えるのはフォールバックの順序だけで、その
検証は緩めません。

### 6. 最初に必要になった時点で遅延復元する

リクエストがバインドを必要とし、セッションの枠が空のときに復元します。復元元は、そのセッションが
acting org としている org の active なプロジェクトです。サインインの最中ではなく、最初の必要が
生じた時点で復元します。その理由は2つあります。1つは、サインインが Git source や bundle の
ネットワーク取得を待つべきではないことです。もう1つは、サインインなしでも acting org が変わりうる
ことです。セッション単位の org 選択は別に進行中であり、サインインだけを見て書いたトリガはそれを
取りこぼします。「このセッションはこの org のバインドをまだ持たない」をきっかけにすれば、どちらの
入り口も名指しせずに扱えます。

復元は best-effort であり、復元を必要としないリクエストを失敗させません。ローカルファイルの移動、
到達できないリポジトリ、追い出された bundle のいずれでも、そのセッションはバインドを持たないまま
残ります。理由はログに出ます。これは起動時の org の seed がデータベースの読み取り失敗に対して
取っている姿勢と同じです。失敗した復元は、そのセッションとその org について再試行しません。そのため
失敗し続ける source を毎リクエストで取得しにいくことはありません。

### 7. メンバーに見える形

セッションがどの config にバインドしているか、そしてその由来を、ヘッダに出します。org のバッジが
すでに置かれている場所です。由来は3つあり、メンバーが見分けられるようにします。このセッションで
自分がバインドしたもの、org が覚えている config として継承したもの、デプロイの起動時の config です。
別のものをバインドすると、同僚の次のセッションが継承する config も変わります。だからバインドする
場所でそのことを伝えます。復元は、それが代わりに行っているバインドと同じように監査ログへ残します。

### テスト

どのユニットも決定的で、Simulator なしでテストできます。対象は8つです。値がまるごと入れ替わること。
1つの org の2つのセッションが同時に別々のバインドを持つこと。バインドがプロジェクトを記録すること。
active なプロジェクトが再起動を模した操作をまたいで残ること。オブジェクトストアなしでキャッシュから
bundle が復元されること。新しいセッションが org の覚えている config を継承すること。失敗した復元が
「バインドなし」に落ちて再試行しないこと。再バインドの前に enqueue した job が、取り込んだ config と
作業ディレクトリで spawn すること。

## 検討した代替案

**グローバルなバインドを保ったまま、「前回の config を復元する」ボタンを置く。** upload のやり直しを
消す最小の変更です。まずバインドごとにプロジェクトを記録し（ユニット3）、メンバーがクリック1回で
再バインドできるようにします。自動では再バインドしないので、テナントをまたぐ危険には触れません。
一方で、1つのバインドの後ろにすべてのテナントを直列化する形も残ります。2つの org は依然として互いを
上書きします。しかもデプロイがすでに知っている config へ戻るために、メンバーは操作を1つ行うことに
なります。到達点ではなく、ユニット3から5が着地したあとの中間状態として残す価値があります。

**グローバルなバインドを保ったまま、条件付きで自動復元する。** 何もバインドされていないとき、または
バインド済みの config の所有者が acting org と一致するときにだけ復元します。よくある場合の危険は
避けられますが、一般の場合は避けられません。2つの org が同時に動いていれば1つのバインドを取り合い、
後にバインドしたほうが先のほうの見えるものを決めます。しかも条件は、健全さを保つうえで読み出し
ごとの再確認が必要です。それはユニット2のセッションごとの解決を、データ構造ではなくガードで
書いたものです。

**セッションごとではなく、org ごとの動くバインドにする。** org ごとにバインドを1つ持ち、その org の
メンバーが共有する形です。変更は小さくなります。対応の key はどのリクエストもすでに解決している値
であり、動くバインドがそのまま記録になるので、記録のための別の範囲も要りません。この形はテナントを
またぐ衝突を消し、org の中の衝突は残します。あるブランチの bundle をバインドしたメンバーが、同じ
org の同僚全員の config を差し替えます。それは、1つのプロジェクトを2人でテストする場合そのもの
です。採用した設計でも共有はそのまま標準の動きですが、共有される可変の枠ではなく継承で実現します。何も
バインドしないセッションは org が覚えている config を見るので、どちらかが意図して分岐しないかぎり
同僚の見るものは一致します。org ごとのバインドが得るのは、持ち回る範囲が1つ減ることです。その代償
は、同僚の切り替えと障害を区別できなくなることです。

**プロジェクトのレジストリではなく、org ごとの config の列を持つ。** 「この org が最後に使った
config source」を org の行へ直接持たせる案です。それならユニット3とユニット4は要りません。
一方でプロジェクトの
レジストリと重複します。レジストリはすでに、3種類の source すべてについて同じ locator を org ごとに
保存しています。しかもそれぞれを実体化し、ページと切り替えも持っています。2つ目のストアは、やがて
1つ目と食い違います。メンバーがプロジェクトを切り替えれば列が古くなり、得るものはありません。

**バインドをブラウザに覚えさせる。** クライアント側に locator を持ち、読み込み時に送り直す形なら、
サーバの変更は要りません。同時に、サーバが何をバインドするかの決定を、クライアントが形を決められる
値へ委ねることになります。locator はバインド時に検証している入力そのものです。したがって復元のたびに、
信頼できない値へその検証をやり直すことになります。しかも記録は org ごとではなくブラウザごと
です。2台目のマシンのメンバーや、同じ org の同僚は、また空から始めます。

**サインインの最中に復元する。** 理由はユニット6のとおりです。サインインが不要な取得を待つことに
なり、サインインだけを見るトリガはセッション内での org の変更を取りこぼします。
