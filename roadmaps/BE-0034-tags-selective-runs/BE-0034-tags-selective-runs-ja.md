## はじめに

シナリオの `tags` を `--tag`/`--exclude` でサブセット実行します（include/exclude、exclude 優先、`select_scenarios`）。サブセット実行は、CI の段階的な実行に利用できます。

## 動機

スイートが大きくなると、毎回すべてのシナリオを実行すべきではなくなります。run ごとに、望ましいサブセットが異なります。

- マージ前のゲートで実行したいのは、高速なスモークのサブセットです。
- ナイトリーで実行したいのは、全件です。
- 機能ブランチで実行したいのは、その機能に関わるシナリオだけです。
- フレーキーなシナリオやプラットフォーム固有のシナリオを、ある run から除外したいこともあります。

選択の仕組みがないと、選べるのは「この 1 ファイルを実行」か「全部実行」しかありません。不格好なファイル構成を強い、段階的な CI パイプラインを不可能にします。そこで、シナリオファイルを分割したり再編成したりすることなく、シナリオにラベルを付け、ランタイムにラベルでサブセットを選べるようにしたいのです。

## 詳細設計

各シナリオは、任意の `tags` リストを持ちます（`bajutsu/scenario/` の `Scenario`）。タグは、`smoke` や `checkout` のような自由形式のラベルです。CLI は `--tag` と `--exclude` を提供し、いずれもカンマ区切りのリストです。これらは、CLI がシナリオ全件をロードして展開し終えた後に適用されます。そのため、選択はデータ駆動展開とコンポーネント展開を経たすべてのシナリオを見ます。

`select_scenarios` は、次の両方を満たすシナリオを残します。

- シナリオが少なくとも 1 つの `--tag` を持つ（または `--tag` 未指定）ことです。
- シナリオのタグのいずれも、`--exclude` に現れないことです。

`--exclude` が `--tag` より優先されます。

フィルタリングは、純粋なメタデータ選択です。宣言順を保ち、シナリオを変更しません。フィルタが何も選ばなかった場合、CLI は空のスイートを実行せず、明確なメッセージとともにクリーンに終了します。

選択は決定的な run ループの完全に前で行われるため、選ばれたシナリオの実行のしかたや合否には影響しません。タグは、選択以外の意味を持ちません。

## 検討した代替案

**サブセットごとに 1 ファイル（ファイル構成で選択を表現する）。** 不採用です。シナリオの選択をその置き場所に結び付けます。シナリオが複数のサブセットに属するとき（たとえば `smoke` と `checkout` の両方）に重複を強い、サブセットの組み合わせが増えると破綻します。タグなら、シナリオを自然なファイルに置いたまま、複数のサブセットに同時に属させられます。

**include だけの選択（`--exclude` なし）。** 不採用です。小さな集合の除外（「遅いものを除く全部」）に、欲しいタグをすべて列挙させることになります。両方向をサポートし、`--exclude` を優先させれば、段階的なパイプラインを自然にカバーできます。広く include し、既知のいくつかを引く形です。

**タグに対するクエリ／式言語（ブール結合）。** 必要に対して過剰なため、不採用です。明確な優先規則を持つカンマ区切りの include/exclude リストで、段階的 CI のユースケースをカバーできます。完全な式文法のパース面と曖昧さは避けられます。具体的な必要が現れたら、より豊かな文法を後から重ねられます。
