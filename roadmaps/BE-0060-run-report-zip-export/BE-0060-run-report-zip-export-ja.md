## はじめに

本項目は、`run` が出力した実行ディレクトリを、1 つの `.zip` として取り出す手段を 1 ステップで提供します。zip には、`report.html`、その `manifest.json`、`junit.xml`、実行した `scenario.yaml`、そして証跡のすべてを含めます。証跡は、スクリーンショット、動画、`network.json`、`device.log` などです。

提供面は 2 つで、どちらも共通の**アーカイバ 1 つ**を呼びます。

- `bajutsu serve` の Web UI に置く**ダウンロード**ボタン。run ごとに、History の一覧と Replay の結果画面に置きます。
- **CLI**。インラインで固める `bajutsu run --zip` と、既存の run を後から固める `bajutsu export <run>` です。

zip は、`runs/<id>/` ディレクトリ全体を、最上位の `<id>/` フォルダの下に梱包します。`report.html` が証跡を指す**相対**リンクが、オフラインで解決します。サーバなしで、ダブルクリックするだけでレポートが開きます。

本項目は、Tier-1 の利便機能です。どこにも LLM を足さず、`run` の合否には一切触れません。run がすでに適用した機密のスクラブを、そのまま引き継ぎます。

## 動機

`run` の出力は、それだけで完結し、自己記述的です。決定的なランナーが、`report.html`、`manifest.json`、`junit.xml`、実行したシナリオ、証跡ツリーを書き出します。ところが、その一式は**出力したマシンの中に閉じ込められた**ままです。完全なコピーを外へ持ち出す手段が、一級の機能として用意されていません。この欠落は、具体的に 4 つの場面で効きます。

1. **`report.html` だけでは持ち運べません。** レポートは、証跡（スクリーンショット、区間の動画、`network.json`）を**相対**リンクで参照します。ローカル Web UI が証跡を配信するのは、一部にはそのリンクを解決するためです（[BE-0011](../BE-0011-local-web-ui-serve/BE-0011-local-web-ui-serve-ja.md)）。HTML だけを取り出すと、画像が壊れ、動画も開けないレポートになります。動くレポートを移すには、ディレクトリを丸ごと、配置を保ったまま移すしかありません。
2. **失敗の共有は日常的な要求です。** 不具合チケットに run を添付する、Mac も Simulator も持たない同僚に渡す、リリース時の run をオフラインの記録として残す。どれも、持ち運べる 1 つのファイルを必要とします。今は、手作業で `zip -r runs/<id>` を打つしかありません。誤ったルートから固めると相対リンクが壊れるので、間違えやすい方法です。そのシェルの前にいない人は、使うこともできません。
3. **ホスト型やリモートの `serve` では、ブラウザからファイルシステムに触れません。** `serve` は、リモートの worker や共有ホストで動くことがあります（[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md)、[BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md)）。その場合、`runs/` ディレクトリは利用者の手元ではなく、そのマシン上にあります。ブラウザの利用者には、完全な run を取り出す手段が**ありません**。埋め込まれたレポートを見ることはできても、持ち帰れません。この穴を塞げるのは、ダウンロード用のエンドポイントだけです。
4. **CI は、レポートを 1 つのアーティファクトとして扱いたいものです。** zip があれば、CI から実行結果を上げる作業は、1 つのファイルに対する 1 回の `upload-artifact` で済みます。zip がなければ、ディレクトリツリーのまま送り、相対配置が保たれることを期待するしかありません。`bajutsu run --zip` は、合否を出したのと同じコマンドの中で、「アーティファクトを作る」ところまでを担います。

アーカイブを扱うコードは、現在のコードベースに存在しません。`zipfile`、`tarfile`、`make_archive` の利用は、どこにもありません。本項目は、レポートサブシステムに欠けている**エクスポート**側の半分を補います。純粋な梱包の関心事なので、決定性優先の原則とは構造上ぶつかりません。

## 詳細設計

### アーカイバ 1 つ、提供面 2 つ

アーカイバを 1 つだけ用意し、これが共有の中核になります。`run_dir` を渡すと、そのディレクトリの中身の zip を作ります。CLI と `serve` の両方が呼ぶので、「run の zip」に何が入るかが、2 つの提供面で食い違うことはありません。

アーカイバの置き場所は、既存のレポート書き出し（`bajutsu/report/`）の、`manifest.py` や `html.py` の隣です。実装は stdlib の `zipfile` に乗せ、依存を足しません。`serve` が stdlib のみで動くことや、ゲートを依存の軽いまま保つ方針と揃います。

### 梱包範囲は run ディレクトリ全体

zip には、`runs/<id>/` の下にあるものをすべて入れます。`report.html`、`manifest.json`、`junit.xml`、実行した `scenario.yaml`、シナリオごととステップごとの証跡ファイルです。

エントリ名は、**run ディレクトリからの相対にし、最上位に `<id>/` フォルダを 1 つ置きます**。展開すると `<id>/report.html` が現れ、証跡は `serve` が配信するときと同じ配置に並びます。そのため、レポートの相対リンクはそのまま解決します。単体の HTML ではなく、ディレクトリを丸ごと固める理由は、ここにあります。

ディレクトリの走査は**ソート順**で行い、ファイルの mtime を固定値に揃えてもかまいません。そうすれば、同じ run ディレクトリから再現可能な zip が得られます。ただし、バイト単位の一致は、証跡（[DESIGN §2](../../DESIGN.md)）と違って、ここでは契約ではありません。あれば望ましい程度のものです。

### CLI の提供面

2 つのコマンドが、同じアーカイバを共有します。

* **`bajutsu run … --zip`。** run が終わってレポートを書き出したあと、続けて `runs/<id>.zip` を出力し、そのパスを表示します。CI に向いた形で、1 つのコマンドで合否とアップロード用のアーティファクトの両方が得られます。フラグの処理は、決定的な合否が決まった**あと**に走るので、合否に影響を与えられません。
* **`bajutsu export <run-id|path> [-o out.zip]`。** すでにある run を固める、単独のコマンドです。共有アーカイバの自然な置き場所で、「前にやった run の zip がほしい」という要望に答えます。出力先の既定は、run ディレクトリと同じ階層の `runs/<id>.zip` です。`-o/--output` で変更できます。既存のファイルがあるとき、`--force` なしでは上書きを拒みます。`record` が黙って上書きしないのと、同じ作法です。

コマンド名の細部は、小さな未決事項です。本質は、両方が同じアーカイバを呼ぶことにあります。

### serve の提供面

新しいエンドポイント `GET /runs/<id>/archive.zip` が、`Content-Type: application/zip` と `Content-Disposition: attachment; filename="<id>.zip"` を付けて、zip を返します。

配信は、**既存の `ArtifactStore` 抽象**（`bajutsu/serve/artifacts.py`）を通します。この抽象は、run ファイルへのアクセスをすでに閉じ込め、パストラバーサルを防いでいます。インターフェースに `archive(run_id)` メソッドを足します。`LocalArtifactStore` は、閉じ込めた run ディレクトリを走査して実装します。将来のホスト型ストアは、自分の側で実装します。ファイルを持つ worker が、そこで固めます。この境界を再利用すれば、ハンドラがファイルシステムに直接触れずに済みます。

UI では、**ダウンロード**ボタンを、**History** の一覧と **Replay** の結果画面の、埋め込みレポート（[BE-0011](../BE-0011-local-web-ui-serve/BE-0011-local-web-ui-serve-ja.md)）の脇に置きます。1 回押せば、`<id>.zip` がダウンロードされます。run が大きい場合（動画と多数のスクリーンショット）は、ストアが zip を一時ファイルに作ってストリーミングします。zip 全体が RAM に載ることはないので、メモリを抑えられます。

### 決定性、ゲート、機密

* **LLM なし、合否への影響なし。** エクスポートは、決定的な `run` がすでに出力した成果物を、事後に梱包するだけです。`run` の合否は、zip より前に、zip とは独立に決まります。`--zip` は、合否のあとに梱包の一手を足します。prime directive の 1 と 2（[CLAUDE.md](../../CLAUDE.md)）は、構造上保たれます。
* **Linux でテストできます。** ディレクトリの zip 化に、Simulator は要りません。アーカイバとエンドポイントは、フィクスチャの run ディレクトリを相手に、既存の Linux ゲートで単体テストできます。
* **機密はスクラブされたままです。** run は、成果物から機密の値をすでに redact しています（[BE-0032](../BE-0032-secret-variables/BE-0032-secret-variables-ja.md)）。zip はディスク上のものを梱包するだけなので、そのスクラブを引き継ぎ、新たに何かを混入させません。アーカイバは、**run ディレクトリだけ**を固めます。`.env`、設定、run ディレクトリより上のものには、決して手を伸ばしません。

### テストの契約（機械でチェックできる）

Simulator を要しないテストが、アーカイバとエンドポイントを固定します。

- (a) zip が、単一の `<id>/` ルートの下に、run ディレクトリのツリーをちょうど含みます。
- (b) `report.html` と、それが参照する資産がすべて存在し、相対リンクが解決します。
- (c) run ディレクトリの外のものが混入しません。
- (d) 既知の機密の値が、zip のどのバイトにも現れません。
- (e) `serve` のエンドポイントが `application/zip` と `attachment` を付け、`ArtifactStore` を介して解決します。パストラバーサルは起きえないままです。

### スコープ外

- 複数 run の一括梱包。
- 軽量な「レポートと参照資産だけ」の部分集合（「検討した代替案」を参照）。
- クラウドへのアップロードと共有リンク。ホスティングの関心事です（[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md) と [BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md)）。
- 古い run の保持と掃除。

## 検討した代替案

* **`report.html` だけを zip する（自己完結した単一ファイル）。** 既定としては却下しました。レポートは証跡を相対パスで参照するため（[BE-0011](../BE-0011-local-web-ui-serve/BE-0011-local-web-ui-serve-ja.md)）、HTML 単体ではスクリーンショットも動画も network ログも失われます。レポートを実際に持ち運べるようにするのは、run 全体の zip です。サイズが気になる場面に向けて、「レポートと、それが参照する資産だけ」の軽量版を後から足すことはできます。それは上に乗せる最適化で、安全な既定ではありません。
* **利用者に `zip -r runs/<id>` を促す。** ローカルの Mac のシェルでは動きますが、欠点が 3 つあります。(a) ファイルシステムに触れない、ホスト型やリモートの `serve` の**ブラウザ**利用者には、何も提供できません。(b) 手作業で間違えやすく、誤ったルートから固めると、レポートの相対リンクが壊れます。(c)「run の zip とは何か」について、UI と CI が共有できる安定した契約が残りません。内部配置の決まった組み込みのアーカイバが、この 3 つをまとめて解決します。
* **別のアーカイブ形式や、外部の梱包用依存。** 却下しました。stdlib の `zipfile` はどこでも使え、どの OS でもダブルクリックで開け、依存を足しません。`serve` が stdlib のみであることや、ゲートを依存の軽いまま保つ方針と揃います。tarball は、共有されたレポートが届きうる Windows の利用者には扱いにくいでしょう。
* **常に `run` の中で zip を作る（フラグなし）。** 却下しました。大半の run は zip を必要とせず、すべての CI の run に I/O とディスクを足すことになります。エクスポートは、オプトイン（`--zip`）か、必要なときだけ（`export` と serve のボタン）にとどめます。
* **「実行レポートのエクスポートと共有」という専用トピックの新設。** 見送りました。単一の項目のためにトピックを切らないという [BE-0055](../BE-0055-operational-logging/BE-0055-operational-logging-ja.md) の先例にならい、本項目は当面「オーサリング体験」の下に置きます。兄弟となる項目（クラウドアップロード、共有リンク、別のエクスポート形式）が現れたら、そのときに専用トピックを切り出せます。
