## はじめに

セルフホスト向けのサーバーバックエンド（[BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md)）は、
テストジョブを Mac ワーカーのプールへ分配します。ワーカーは、Postgres の `jobs` テーブルに支えられた**単一**のキューから、
ジョブをリースします。この方式は、全ワーカーが全ジョブを実行できる場合にうまく動きます。

**構成の異なる**プールでは、この方式が破綻します。ターゲットが iOS 18 を必要とするジョブは、iOS 17 しかインストールされていないワーカーに
割り当ててはなりません。iPad 専用のシナリオも、iPhone 専用のワーカーに割り当ててはなりません。

この提案は**能力に基づくキューの振り分け**を導入します。ジョブを実行できるワーカーだけが、そのジョブをリースするようにします。
BE-0016 の「単一ノードをプールへ育てる」作業から切り出した項目です。

## 動機

現実の Mac プールが均一であることはまれです。マシンごとにインストールされている iOS ランタイムは異なります。
iPad 向けに整えたものもあれば、iPhone 向けのものもあります。ランタイムの追加と廃止に伴って、フリートの構成は時とともに変わっていきます。

区別のない単一キューでは、全ワーカーが全ジョブをリースできます。ターゲットが必要とするランタイムやデバイス種別を持たないワーカーが、
そのジョブを取り上げることがあります。すると実行は失敗しますが、本物の欠陥によるものではなく、誤ったマシンへ振り分けられたことによる失敗です。
プールが大きく多様になるほど、この振り分け誤りは例外ではなく常態になります。

したがって振り分けは、**ワーカーの能力**を尊重しなければなりません。ジョブを載せるキューは、ターゲットが宣言するデバイスに一致していなければなりません。
ワーカーは、自分が処理できるジョブだけを引き取らなければなりません。これにより、決定的な判定が正直に保たれます。
失敗はアプリが正しく振る舞わなかったことを意味し、スケジューラが非互換のマシンへジョブを送ったことを意味しません。

## 詳細設計

振り分けが決めるのは、*どの*空きワーカーがジョブを取り上げるかです。決定的な `run` は**変えません**。
同じシナリオを能力のあるワーカーで実行すれば、同じ判定になります。作業分解は次のとおりです。

1. **ワーカーの能力を宣言する。** 各 `bajutsu worker` は、リース時に自分が処理できる能力を通知します。
   能力は、インストール済みの iOS ランタイムと、`ios18` や `ipad` といったデバイス種別です。
   能力の集合はワーカーの Simulator 在庫から導き、固定したい場合の運用者による上書きも用意します。
2. **能力別のキューへ振り分ける。** 制御プレーンは、ジョブのターゲットを、そのデバイスが必要とする能力へ対応づけます。
   そして、一致する論理キュー（`q:ios18`、`q:ipad`）へ積みます。キューは引き続き Postgres の `jobs` テーブルです。
   能力は、新しいストアではなく、行の振り分けキーになります。
3. **能力を考慮したリース。** `POST /api/worker/lease` は、リースするワーカーが通知した能力を必要とするジョブへ、候補を絞り込みます。
   これにより、ワーカーは自分が実行できるジョブだけをリースします。既存のリース・ハートビート・回収の経路
   （[BE-0106](../BE-0106-post-completion-worker-model/BE-0106-post-completion-worker-model-ja.md)）と、そのまま組み合わさります。
   回収は、ジョブを元の能力キューへ戻します。
4. **フォールバックと振り分け不能のジョブ。** 必要とする能力をプール内のどのワーカーも通知していないジョブが、黙って宙づりになってはなりません。
   そうしたジョブはキューに残し、振り分け不能として運用者へ知らせます。非互換のワーカーにリースさせたり、捨てたりはしません。
5. **capability 軸としての `backend`（idb か web か）。** iOS ランタイムとデバイス種別に加え、ワーカーの **backend** 自体が1つの能力です。
   Mac の idb ワーカーは `backend=idb` を通知します。Linux の web ワーカーコンテナ
   （[BE-0173](../BE-0173-slim-web-worker-image/BE-0173-slim-web-worker-image-ja.md)）は `backend=web` を通知します。
   ジョブのターゲット backend は、必要能力のキーの一部になります。そのため、`web` のジョブは web ワーカーだけが、
   `idb` のジョブは Mac ワーカーだけがリースし、両者は決して交差しません。

   これは、上記の軸と同じ通知・振り分け・絞り込みの仕組みに、`backend` を1つの次元として加えるだけです。
   効いてくるのは、プールが backend を混在させたときです。均質なプールは影響を受けません。

**検証。** 振り分けの判断（ターゲットから能力、能力からキューへ）とリースの絞り込みは Python 側に面を持ち、
Simulator を使わず単体テストします。テストは次の3つを確かめます。

- `ios18` を必要とするジョブが、iOS 17 しか持たないワーカーへ提示されないこと。
- iPad のジョブが、iPhone 専用のワーカーへ提示されないこと。
- 能力を持つワーカーがいないジョブが、キューに残って振り分けられないこと。

全体としての振り分けは、複数デバイスのプールで手動で検証します。構成の異なるフリートが、各能力の作業を適切なマシンへ流し込むことを確認します。

## 検討した代替案

- **単一キューのまま、非互換のワーカーへ振り分けられたジョブを失敗させる。** 却下します。スケジューリングの穴を不必要なテスト失敗に変え、
  決定的な判定への信頼を損ないます。互換性は、run ではなくスケジューラが担うべきです。
- **ワーカーに何でもリースさせ、不一致なら再投入する。** 却下します。実行できないと分かってから再投入すると、希少なプールでリースの一巡を無駄にします。
  ライブロック（ジョブが実行できないワーカー間を跳ね返り続ける）に陥りかねません。リース時に絞り込めば、無駄な試行を避けられます。
- **運用者によるワーカーごとの静的なキュー割り当て。** 主たる仕組みとしては却下します。能力をワーカーの実際の Simulator 在庫から導けば、
  フリートの構成が変わっても、手作業の割り当てなしに振り分けが正しく保たれます。固定用の運用者による上書きは残します。
