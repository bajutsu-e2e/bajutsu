## はじめに

この項目は、3 つの保証を明示的で強制されたものにします。1 つ目は、Bajutsu の AI 経路（`record`、`triage`、`--dismiss-alerts`）が、ユーザー自身の API キーとプロバイダの下で動くことです。2 つ目は、モデルへ送るものがすべて、先に既存の秘匿化（redaction）層を通ることです。3 つ目は、オーサリング／調査エージェントの背後のプロバイダが差し替え可能であることです。これは信頼とデータ取り扱いの保証であって、ランタイムの検査ではありません。いずれにせよ、ゲートは AI 非依存のままです。

## 動機

2026 年の具体的な競合の変化が、この項目を際立たせました。Maestro は AI 機能を**クラウド管理**モデルへ移しました。BYO キー（bring-your-own-key）は廃止され、`MAESTRO_CLI_AI_KEY` ／ `MAESTRO_CLI_AI_MODEL` は非推奨になりました。AI コマンドは不透明な「第三者 AI プロバイダ」を通じて Maestro Cloud にルーティングされ、利用には Maestro アカウントが必要です。テスト対象アプリのスクリーンショットが、ユーザーの管理下にないベンダーサービスへ送られます。規制業界やプライバシーに敏感なチームにとって、これは強い導入の障壁です。

Bajutsu はすでにその逆です。AI 経路はユーザー自身の `ANTHROPIC_API_KEY` を使ってローカルで動き、決定的なゲートはモデルをまったく呼びません。しかし今日、これは**創発的な性質**であって、文書化され強制された約束ではありません。導入を検討する側は保証を指し示せず、一部は実際に強制されていません。秘匿化は書き出される*証跡*には適用されます。ところが、`record` ／ `triage` ／ `--dismiss-alerts` の最中にモデルへ送るスクリーンショットや要素ツリーを、先に秘匿化する保証はありません。

この項目は、「あなたの AI、あなたのキー、あなたのデータ」を、偶然から第一級の検証可能な性質へと変えます。ベンダークラウドの AI との直接的な対比です。

## 詳細設計

この節は提案粒度で書きます。3 つの保証を述べ、いずれもすでに存在する継ぎ目の上に築きます。

- **プロバイダは差し替え可能。** `Agent` ／ `claude_agent` 抽象（`bajutsu/agent.py`、`bajutsu/claude_agent.py`）は、すでにモデル呼び出しを隔離しています。プロバイダ設定（`defaults` ／ `targets.<name>` の下）を形式化し、エンドポイント、モデル、キーの取得元を明示的かつ差し替え可能にします。たとえば、オーサリング／triage エージェントを自己ホストのゲートウェイや社内プロキシへ向けられます。Claude（Anthropic）はデフォルトのままで、それを弱めるものはここにありません。
- **AI 入力への秘匿化。** `record` ／ `triage` ／ `--dismiss-alerts` に渡すスクリーンショット、要素ツリー、ログは、*プロセスを離れる前に* `bajutsu/redaction.py` を通します。その保証は文書化します。これで、「証跡は秘匿化される」と「モデルが見るものは秘匿化される」の隙間を塞ぎます。
- **キーがなければ AI なし（フェイルクローズ）。** AI 経路は明示的に設定されたキーを要求し、ホストされたデフォルトへ黙ってフォールバックしません。キーの不在は明確なエラーであって、誰かのクラウドへの静かな往復ではありません。

この項目は厳密に Tier-1 側に留まります。`run` については何も変えません。pass/fail は機械のみのままで、ゲートにモデルは追加されません。新種の検査ではなく、具体的な強制を伴う信頼／ポジショニングの機能です。

以下に、各保証の実装レベルの設計を示します。

### プロバイダ設定

現在、プロバイダは**環境変数のみ**で決まります。対象は、`bajutsu/anthropic_client.py` の `BAJUTSU_AI_PROVIDER`、`ANTHROPIC_API_KEY`、`BAJUTSU_BEDROCK_MODEL`、および AWS の資格情報チェーンです。これを、他の設定と同じく解決される任意の `ai` ブロックとして形式化します。`defaults.ai` に置き、`targets.<name>.ai` で上書きできます。

```yaml
defaults:
  ai:
    provider: anthropic                      # anthropic（既定） | bedrock
    model: claude-opus-4-8                    # 任意: その経路の既定モデルを上書き
    baseUrl: https://ai-gateway.internal/v1  # 任意: 自己ホストのゲートウェイ / 社内プロキシ（anthropic）
    keyEnv: ANTHROPIC_API_KEY                 # キーを保持する環境変数の「名前」。キーの値そのものは置かない
```

- **キーは設定ファイルに置きません。** `keyEnv` は環境変数の名前を指すだけで、値は呼び出し時に環境から読みます。そのため、秘密がリポジトリやアップロードされたバンドルに入りません（CLAUDE.md）。`baseUrl` は、Anthropic SDK を自己ホストのゲートウェイやプロキシへ向けます（`Anthropic(base_url=…, api_key=os.environ[keyEnv])`）。Bedrock は AWS の資格情報チェーンのままです。
- **設定が先、環境変数はフォールバック。** すべての AI 経路が共有する単一のファクトリは、`provider()` ／ `make_client()` ／ `resolve_model()` です。このファクトリは、解決済みの `ai` 設定を先に読み、無ければ現状の環境変数へフォールバックします。そのため、既存の構成はそのまま動きます。このブロックは `Effective` に解決されるので、CLI と `serve` は一つの真実を共有します。
- **アプリ非依存。** 変えるのはコードではなく設定です。エージェントや locator の呼び出し箇所には手を入れません。

### AI 入力の秘匿化とスクリーンショットの限界

run スコープの `Redactor`（`bajutsu/redaction.py`）は、対象の `redact` キーと解決済みの秘密値から構築します。構築のしかたは、証跡の書き出しが `bajutsu/evidence.py` で既に行っているものと同じです。この `Redactor` を、プロセスを離れる前の**テキスト系**のモデル入力に適用します。

- **record**：`claude_agent._render` ／ `_user_content`。画面の要素一覧（`label` ／ `value` ／ `traits`）は、ユーザーメッセージへ描画する前に `redact_elements` で秘匿化します。
- **triage**：`TriageContext.elements` と失敗のテキストを、プロンプトの組み立て前に秘匿化します。
- **任意の AI 経路に渡す自由テキストやログ**：`redact_text` で秘匿化します。これは `--dismiss-alerts` も含みます。`--dismiss-alerts` は、スクリーンショットに**加えて**小さなテキストブロックを送ります。中身は、画像サイズと、任意でユーザー指定もありうる `--alert-instruction` です。この instruction も `redact_text` に通します。

**正直な限界：スクリーンショットは画像であり、`redaction.py` はテキストや要素ツリーは隠せても画素は隠せません。** record、triage、dismiss-alerts はいずれもスクリーンショットを送ります。スクリーンショットは秘匿化できません。したがって、保証は二段構えです。

1. **テキスト系**入力（要素ツリー、ログ）は、送信前に秘匿化されます。
2. スクリーンショットを含む**すべて**の入力は、**ユーザーが設定したプロバイダ／エンドポイント**にのみ送られ、ベンダーの既定先には決して送られません。したがって、スクリーンショットが、ユーザーの信頼境界を越えることはありません。

画素まで通信に乗せたくないチームには、任意の `ai.sendScreenshots: false`（精度を犠牲にしたテキストのみモード）を用意します。画素レベルの画像秘匿化は別の、はるかに大きな取り組みであり、ここでは対象外とします。

### フェイルクローズ

AI のエントリポイント（`record`、`triage`、`--dismiss-alerts`）は、選択したプロバイダに使える資格情報がないとき、プロバイダ別の明確なエラーで即座に失敗します。ここでいう「無いとき」とは、`anthropic_client.credential_gap()` が非 None の場合です。ホストされた既定先へフォールバックするクライアントは、決して構築しません。

これは、既存の `crawl` ／ `run` の「ゲートするか警告する」を、オーサリング／調査の経路では厳密なフェイルクローズへと締めるものです。キーの不在は、誰かのクラウドへの静かな往復ではなく、対処可能なエラーです。

### 検証

いずれも高速ゲート内で機械的に検査できます。SDK クライアントはすでに注入可能（`make_client(client=…)`）なので、実 API は不要です。`run` ／ CI ゲートに LLM を載せるテストもありません。

- **プロバイダ解決。** 記録用の fake クライアントで、次の 3 点を確認します。エンドポイント／モデル／キー環境変数名が `ai` 設定から解決されること、設定が環境変数に優先すること、環境変数フォールバックが効くことです。
- **AI 入力の秘匿化。** 既知の秘密を（要素の `value` ／ `label` とテキストに）含む `Observation` ／ `TriageContext` を、入力ビルダーに通します。注入クライアントの受け取るペイロードを検査し、秘匿化済みであることを確認します。
- **フェイルクローズ。** プロバイダの資格情報がない状態で、各エントリポイントが明確なエラーで終了し、注入クライアントが一度も呼ばれないことを確認します。

## 検討した代替案

* **ホストされた便利キー／マネージド AI を提供する（Maestro の方向）。** 不採用です。Bajutsu を差別化しているまさにそのベンダークラウドとデータ流出の懸念を再現し、BYO キーの約束をぼかします。ここでの利便性は、売っているものそのものを犠牲にします。
* **暗黙のままにする（現状）。** 不十分として不採用です。保証が導入候補者にとって読み取れません。AI 入力への秘匿化の部分も、今日は実際に保証されていません。そのため、「あなたのデータはあなたのもの」は、まだ書面で約束できません。
* **ツールに同梱する完全なローカル／オフラインモデルの選択肢。** ここでは対象外です。プロバイダ抽象によって、自己ホストのエンドポイントへ向けることは可能になります。しかし、モデルを同梱して支援することは、別個ではるかに大きなコミットメントです。
