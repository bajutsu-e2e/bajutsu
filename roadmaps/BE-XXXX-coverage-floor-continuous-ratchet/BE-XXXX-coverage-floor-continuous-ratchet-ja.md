## はじめに

`make check` のカバレッジフロア（`Makefile` の `--cov-fail-under`）は、誰かがスイートを計測し、
弱い箇所へテストを書き、数値を手で書き換えるという手順を踏んだときにしか動きません。
[BE-0117](../BE-0117-coverage-floor-ratchet/BE-0117-coverage-floor-ratchet-ja.md) が一度だけ実行した
手順です。本項目は、この手順を1回限りの作業ではなく2つの常設チェックにします。計測したカバレッジ
がフロアから大きく離れたときに知らせるアドバイザリと、1つのファイルのカバレッジを絶対に下げさせ
ない per-file のフロアです。後者は、BE-0067 が指摘して先送りにしたモジュール単位の見落としに
対応します。

## 動機

高速スイート（`pytest -m "not web and not ondevice"`、branch coverage 込み）を今計測すると、
`--cov-fail-under=89` のフロアに対して全体で93％のカバレッジが出ます。ゲートが求める値と、スイート
がすでに達成している値のあいだに4ポイントの差があります。この差はそのまま、リグレッションが
隠れられる余地です。カバレッジを3ポイント落とす変更でも、このゲートはまだ通ります。しかも、その
低下に誰かが気づく仕組みや、その差を埋めるためにフロアを上げるよう促す仕組みが、今は何もありません。

グローバルな1つの割合はまた、[BE-0067](../BE-0067-code-quality-gate-hardening/BE-0067-code-quality-gate-hardening-ja.md)
の branch coverage 導入がまだ完全には解消していない弱点も隠します。パッケージ全体を1つの数値で
見る、という弱点です。ファイル単位の branch coverage は今日、65％から136ファイルにわたる100％
まで幅があります。最低は `bajutsu/cli/commands/doctor.py` の65％で、これは数行を超えるファイルの
なかでの最低です（`__main__.py` の、一度も import されない4行は0％です）。80％を下回る他の
ファイルには、`bajutsu/serve/operations/_common.py`（69％）、`bajutsu/report/richtext.py`
（72％）、`bajutsu/runner/mailbox.py`（73％）、`bajutsu/serve/upload_artifacts.py`（76％）が
含まれます。
これらのどれも、`make check` がゲートとしている単一の `TOTAL` 行からは見えません。コードベース
全体では93％とフロアを十分に上回っているため、あるファイルが65％から40％へ落ちても、グローバルな
フロアはその低下を吸収してなお通ってしまうと考えられます。

## 詳細設計

`test` ターゲットがすでに書き出している `coverage.json` を、それぞれ独立した2つのチェックが
読みます。

1. **フロアからの乖離を知らせるアドバイザリです。** 新しいスクリプトが `test` の実行ごとに
   `coverage.json` の `totals.percent_covered` と `Makefile` の `--cov-fail-under` の値を比較し、
   その差が2ポイントを超えた時点で、現在の計測値とフロアの値を名指ししたリマインダーを表示します。
   ビルドを失敗させることはありません。これは `make lint-pr` 自身のアドバイザリと同じパターンで
   す。チェックして表示はしますが、ゲートにはしません。フロアを上げるためにPRを1つ費やすかどうか
   は、機械的にではなく人が決めることだからです。
2. **絶対に下がらない per-file のフロアです。** チェックイン済みのスナップショット（たとえば
   `coverage-floors.json`）が、ある程度以上の文数を持つソースファイルごとに存在します。各エントリ
   は、この項目のチェックを直前に実行した時点の branch coverage の割合を、余裕を持たせて少し
   切り下げた値で記録します。`make check` の新しいステップはチェックのみを行います。`format` と `format-check`
   の分割を踏襲し、あるファイルの現在の計測値がその記録済みフロアを下回った時点で失敗しますが、
   スナップショットへの書き込みは一切行いません。別に用意する `make coverage-floors` ターゲットが、
   各ファイルの現在の（より高い）カバレッジへスナップショットを再計算して書き換えます。これは人が
   意図的に実行し、カバレッジが上がった際にコミットするものであり、`make format` がチェックのみの
   ゲートとは別の意図的な作業として存在するのと同じ関係です。`doctor.py` は65％を出発点とした
   フロアをそのまま持ち、今日のグローバルな89％まで無理に引き上げられることはありません。どの
   ファイルも、自分が出発した値からしか上がらず、静かに下がることは決してなく、しかも `make check`
   の最中に自動で変わることも決してない、というのが要点です。

どちらのチェックも、既存の `test` ターゲットが実行し終えたあとに `coverage.json` を読むだけで、
スイートを再実行したり、2度目のカバレッジ収集を追加したりはしません。

## 検討した代替案

- **グローバルなフロアを91％か92％まで、1回限り上げる** —
  [BE-0117](../BE-0117-coverage-floor-ratchet/BE-0117-coverage-floor-ratchet-ja.md) の手順をそのまま
  繰り返すだけであり、却下します。カバレッジが次に改善したとき、誰かが再び数値を上げないかぎり、
  同じ差がまた開いてしまいます。本項目のアドバイザリチェックは、次の差が次の見直しより早く気づかれ
  るように存在します。
- **per-file のフロアを、下限だけでなく上限としても機械的に強制する**（ファイルのカバレッジが
  上がったのに同じPRでスナップショットを更新しなければ失敗させる）— 却下します。それでは、
  カバレッジを改善したという、本項目が促したい行動そのものを理由に、コントリビューターのPRを
  失敗させてしまいます。このフロアが止めるのは低下だけであり、上昇を止めることは決してありません。
- **すべてのファイルの初期フロアを、今日のグローバルな89％に設定する** — 却下します。それでは
  *動機* に挙げた89％未満のファイル（`doctor.py` をはじめとする各ファイル）すべてで `make check` が
  ただちに失敗し、本項目を landing するPRが、無関係な弱いファイルすべてを先に直す義務になって
  しまいます。各ファイルのフロアをその時点の実測値から出発させれば、landing するPRは既存のものを
  壊さずに追加するだけで済みます。
- **フロアからの乖離アドバイザリを、差が2ポイントを超えた時点で機械的に失敗させる** — 却下します。
  機械的な失敗は、その差を広げたという「罪」だけを理由に、たまたま十分にテストされたコードを
  追加した無関係なPRを止めてしまいます。アドバイザリのままにすれば、それ自体が問題ではない作業を
  止めることなく、同じ信号を伝えられます。
