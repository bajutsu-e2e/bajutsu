## はじめに

web（Playwright）[バックエンド](../../docs/ja/glossary.md#driver-backend-actuator-platform)では、`swipe`
ステップがページをスクロールしません。このジェスチャーは、本来スクロールを意図したものです。方向指定形式の
`swipe: { on, direction }` は、画面外のコンテンツを表示させるためのクロスプラットフォーム共通の手段です。
オーサリングエージェントにも「スクロールして要素を表示させるには swipe を使う」と指示しています。それでも
web では、このステップは何も動かしません。

本提案は、web バックエンドの `swipe` に本物のスクロールを実行させます。ジェスチャーを、実際にスクロールを
起こす入力プリミティブへ振り分けます。この振り分けは、ブラウザの入力モード（ポインターかタッチか）で
分岐する構造にします。モバイルエミュレーションのモードが用意されたあとも、正しく動くようにするためです。
そのモードは、対になる **web-device-mode-emulation** 項目が用意します。

## 動機

`swipe` は、シナリオスキーマ（`bajutsu/scenario/models/actions.py`）の 1 アクションで、すべての
バックエンドが共有します。方向指定形式は、要素を解決し、バックエンド非依存のジェスチャー計算
（`bajutsu/orchestrator/actions/handlers/gestures.py`）で `(from, to)` の移動量を求めます。そのあと
`driver.swipe(from, to)` を呼びます。

idb バックエンドは、この呼び出しを `idb ui swipe … --duration 0.2` に変換します。OS が本物のドラッグとして
認識するので、リストやスクロールビューがスクロールします。一方 Playwright バックエンド
（`bajutsu/drivers/playwright.py`）は、`swipe` を素の**マウスドラッグ**（`mouse.move → down → move → up`）
として実装しています。

マウスドラッグは、通常の web ページをスクロールしません。テキストを選択したり、カスタムのドラッグ可能な
要素を動かしたりはしますが、ブラウザのスクロールコンテナはこれに反応しません。結果として、web では次の
3 つのことが起きます。

- **record が意図どおりに動かないシナリオを生成する。** エージェントは「スクロールには swipe を使う」という
  指示に従い、画面外のコントロールを表示させるために `swipe` を発行します。しかし、記録されたステップは
  何もスクロールしません。後続のタップが誤った要素に当たったり、要素を解決できずに失敗したりします。
- **`run` が同じ無効操作を再生する。** record と `run` は、唯一の `swipe` ハンドラを共有しています。そのため、
  iOS ではスクロールするシナリオが、web では黙ってスクロールに失敗します。ジェスチャーを実行できない
  バックエンドが、ツールの約束する決定性を損ないます。
- **`codegen` が同じ欠陥を出力する。** `bajutsu/codegen_playwright.py` の `_emit_swipe_direction` は
  同一のマウスドラッグ列を生成します。生成された Playwright テストも、無効操作を引き継ぎます。

この挙動は直接検証しました。オーケストレーターが計算するのと同じ `(from, to)` で `PlaywrightDriver.swipe()`
を動かし、高さ 3000px のページに対して実ヘッドレス Chromium 上で試しました。`window.scrollY` は `0` の
ままでした。同じ移動量の `page.mouse.wheel()` は、期待どおりページをスクロールさせました。

このギャップが問題なのは、スクロールが、自明でないページの前提条件だからです。長いフォーム、フィード、
設定の一覧など、折り返しの下に届く必要があるシナリオは、今の web では静かに壊れています。

## 詳細設計

修正の方針は、web バックエンドの `swipe` を、スクロールを起こす入力プリミティブへ振り分けることです。
その振り分けは**入力モードで分岐**させます。デスクトップのポインターブラウザとタッチ（モバイル）ブラウザの
双方で、正しく動くようにするためです。正しいプリミティブは、モードによって異なります。

- **デスクトップ（ポインター）モード**：`page.mouse.wheel(delta_x, delta_y)` を使います。wheel イベントは
  ブラウザの本物のスクロールコンテナを駆動します（前述のとおり検証済み）。ユーザーがホイールやトラック
  パッドでスクロールする操作に対応します。
  `swipe` の方向は、wheel の移動量に対応づけます。`up` の swipe は、コンテンツが上へ動く操作、つまり
  ユーザーがサーフェスを上へ押す操作です。これはページを**下へ**スクロールさせ（`delta_y` が正）、物理的な
  ジェスチャーと向きが一致します。移動量は、ジェスチャー計算がすでに求めている画面相対の距離から決めます。
- **タッチ（モバイル）モード**：Chrome DevTools Protocol (CDP) のタッチドラッグを使います。これは `pinch` と
  `rotate` がすでに使っている経路（`_touch_drag` → `Input.dispatchTouchEvent`）とまったく同じです。
  タッチページをスクロールさせるのは、本物のタッチドラッグです。合成 DOM イベントと違い、ページの
  タッチとジェスチャーのリスナーを発火させます。`swipe` は、2 つの端点を 1 本指に畳んだうえで
  `_touch_drag` を再利用します。

**モードの選択。** 分岐は、アクティブなブラウザコンテキストでタッチ入力が有効かどうかで決めます。見るのは、
コンテキストを生成したときの `has_touch` の値です。Playwright の Python 版 `BrowserContext` は、この値の
公開 getter を持ちません。`new_context()` の生成時オプションにすぎないからです。そのためドライバーは、
コンテキストから読み戻さず、生成時にタッチモードを（`self._context` と並べて）覚えておきます。

`self._context` は、2 つの独立した箇所で生成されます。

- `_start_browser` のスタータークロージャ（初回の起動と `relaunch()`）
- `_new_context()`（`reset_context()` と録画用の差し替え）

したがって、対になる項目は、`has_touch` の設定とキャッシュしたタッチモードの更新を**両方**で行う必要が
あります。`relaunch()` は `_new_context()` ではなくスターターを通ります。片方だけを更新すると、新しく
生成されたコンテキストとキャッシュしたモードが食い違うおそれがあります。

今日の web バックエンドは、常に素のデスクトップコンテキストを起動します（`has_touch` は false）。本提案は、
**デスクトップ（wheel）**の経路を実挙動として出荷します。タッチ経路は、コンテキストをタッチ用に設定できる
ようになった時点で自動的に有効になるよう、分岐を配線しておきます。

その設定を用意するのは、対になる **web-device-mode-emulation** 項目の役割です。viewport、`is_mobile`、
`has_touch` を備えた、デスクトップ／モバイルのデバイスモードです。本項目はそのモードを導入しません。
のちの書き直しなしに両者が組み合わさるよう、振り分けを対応できる状態にしておきます。

**座標形式は変えません。** `swipe: { from, to }` は、ドキュメント（`docs/scenarios.md`）に書かれたとおり、
素のドラッグという最終手段のままにします。カスタムの canvas、マップのパン、ドラッグハンドルなど、文字
どおりのポインタードラッグ自体が意図である場合のためのものです。他のバックエンドで座標形式が占める位置と
同じです（[BE-0025](../BE-0025-coordinate-swipe-generation/BE-0025-coordinate-swipe-generation-ja.md)
を参照）。変わるのは、意味が「スクロール」である方向指定形式 `{ on, direction }` だけです。

**要素アンカーのポインタードラッグのための `drag` アクションを新設します。** 方向指定 `swipe` をスクロールに
再定義したことで、実在する出荷済みのユースケースが行き場を失いました。要素を**セレクタで**掴んで、方向へ
ドラッグする操作です。リサイズ用の仕切りやスライダーのつまみが例になります。web では、従来の方向指定
swipe のマウスドラッグに依存していました。serve-UI の `panel-resize` dogfood が、まさにこれです。

座標形式では代替できません。生ピクセルのみを取り、セレクタ解決を持たないからです。そこで実装では、
第一級の `drag: { on, direction, amount? }` アクションを追加しました。方向指定 `swipe` と同じ端点計算を
共有します。振り分け先は `driver.scroll` ではなく、`driver.swipe`（本物のポインタードラッグ）です。web では、
掴んだ要素を動かす `page.mouse` のドラッグになります。iOS と Android では、OS の本物のドラッグがすでに
スクロールとハンドル移動を兼ねます。そのため、`drag` と方向指定 `swipe` は一致します。

codegen は、`drag` を各バックエンドで出力します。web は `page.mouse` のドラッグです。iOS と Android は、
方向指定 swipe が出す `swipeX()` / `swipe(Direction, …)` です。

**codegen の整合。** `bajutsu/codegen_playwright.py` の `_emit_swipe_direction` を更新し、方向指定形式に
対して対応する wheel スクロール（例：`page.mouse.wheel(...)`）を出力させます。これにより、生成された
Playwright テストは `run` とまったく同じようにスクロールします。構造的な「シナリオからテストへ」の写像を
忠実に保つ方針で、他のエミッターについて BE-0025 や BE-0085 が守っているのと同じ原則です。

作業分解（MECE）：

1. **`PlaywrightDriver.swipe` の入力モード分岐**：コンテキストのタッチモードで分岐します。デスクトップは
   `mouse.wheel`、タッチは `_touch_drag`（1 本指）です。今日の実挙動はデスクトップ経路です。
2. **方向から wheel 移動量への対応づけ**：ジェスチャー計算の `(from, to)`、方向、`amount` を、物理的に
   正しい向きと距離でスクロールする wheel の `(delta_x, delta_y)` に変換します。
3. **codegen の整合**：`bajutsu/codegen_playwright.py` の `_emit_swipe_direction` を更新し、方向指定形式に
   wheel スクロールを出力します。座標形式はドラッグのままです。
4. **テスト**：`tests/test_playwright.py::test_swipe` のマウス呼び出し列のアサーションを、本物のスクロール
   効果を確認するものに置き換えます。確認するのは `window.scrollY` や対象の `scrollTop` の変化です。
   方向から移動量への符号の対応づけも検証します。`tests/test_codegen_playwright.py` の codegen テストも
   追加または調整します。
5. **ドキュメント**：`docs/scenarios.md`（と日本語ミラー）および `docs/drivers.md` に、web バックエンドが
   方向指定の `swipe` をどう実現するかを記します。デスクトップでは wheel スクロール、タッチコンテキストでは
   タッチドラッグです。座標形式の記述はそのまま保ちます。

以下のとおり、いずれもプライムディレクティブの範囲内です。

- **決定性。** 振り分けは、解決済みのジェスチャーから wheel またはタッチ入力への固定的な写像です。モデルには
  問い合わせず、`run`／CI ゲートには手を触れません。wheel スクロールは、置き換え対象のマウスドラッグと
  同じく再現可能です。
- **アプリ非依存。** アプリごとの設定はなく、写像はすべての web ターゲットで同一です。デスクトップ／
  モバイルの**モード**は、アプリごとのジェスチャーロジックではなく、ターゲット単位のブラウザ設定（対になる
  項目）です。
- **バックエンド非依存のコア。** シナリオスキーマと共有のジェスチャー計算は変わりません。変わるのは、web
  ドライバーによるジェスチャーの実現と、その codegen エミッターだけです。アーキテクチャがこのために
  用意しているバックエンドごとの継ぎ目そのものです。

## 検討した代替案

- **常に CDP タッチドラッグを使う（モード分岐をやめる）。** 単一のタッチドラッグ経路は、ページのタッチ
  ハンドラを発火させます。しかし、デスクトップのポインターコンテキストでは、合成したタッチドラッグが
  デスクトップページの期待する wheel スクロールの挙動に対応しません。期待される挙動は、慣性、オーバー
  スクロール、wheel 専用リスナーです。また、ターゲットがデスクトップとして扱うデバイス上で、エミュレートした
  入力をタッチだと偽って伝えてしまいます。却下します。入力モードはデスクトップとモバイルで実際に異なり、
  それこそが分岐の存在理由だからです。
- **`page.evaluate` 経由の `element.scrollIntoView()` / `scrollBy()`。** 注入した JS でスクロールするのは
  確実です。しかし、ブラウザの本物の入力経路を迂回するので、ページのスクロール、wheel、タッチのリスナーが
  一度も発火しません。ドライバーは、`pinch` と `rotate` について合成 DOM イベントを退ける際に、同じ反対理由を
  すでに記しています。ユーザーが実際にスクロールする挙動からも乖離します。忠実さを利便性と引き換えに
  するため、却下します。
- **マウスドラッグを残し、web の `swipe` はスクロールしないと明記する。** 却下します。クロスプラットフォームの
  アクションが、着地済みのバックエンドで静かに壊れたままになります。record も、実態と食い違うシナリオを
  出し続けます。
