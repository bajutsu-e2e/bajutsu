## はじめに

`serve` は、1 つの API 面の背後で、2 つの HTTP バックエンドを動かしています。1 つは、標準ライブラリの `http.server` によるハンドラ（`bajutsu/serve/handler.py`）です。もう 1 つは、FastAPI アプリ（`bajutsu/serve/server/app.py`）です。すべてのエンドポイントは、2 回宣言されています。

- 標準ライブラリのハンドラの `do_GET` / `do_POST` にある、`match path` の 1 分岐として（`handler.py:186-444`）
- `app.py:122-490` の `@app.get` / `@app.post` / `@app.delete` ルートとして

どちらの宣言も、同じ `bajutsu.serve.operations`（`ops`）関数へディスパッチします。

次の 4 つも、両方のバックエンドでそれぞれ独立に再実装されています（`handler.py:61-69,121-170,273-290` と `app.py:69-118`）。

- リクエストレベルの認証ゲート
- クロスサイトリクエストフォージェリ（CSRF）対策の `Origin` チェック
- `Host` allowlist
- レスポンスを堅牢化するヘッダ

本項目では、手動管理の 2 つのルートテーブルと、その周囲で重複しているセキュリティ実施を、両方のバックエンドが参照する 1 つの宣言的なレジストリに置き換えます。

## 動機

2 つのルートテーブルは、すでに気づかれないまま drift しています。次のエンドポイントは、標準ライブラリのハンドラには存在しますが、FastAPI アプリには対応するものがありません。FastAPI バックエンドでデプロイした環境では、これらが 404 になります。しかも、それが意図的なものかどうかを宣言しているコードは、どこにもありません。

- `GET /flakiness`（`handler.py:237`）
- `GET /api/ant/login` と `POST /api/ant/login`（`handler.py:214,352`）
- `POST /api/enrich`（`handler.py:382`）
- `POST /api/codegen`（`handler.py:376`）
- `POST /api/capture/start`、`POST /api/capture/mark`、`POST /api/capture/finish`、`GET /api/capture/screenshot`（`handler.py:388-393,266`）
- `POST /api/jobs/{id}/respond-human`（`handler.py:414`）
- `GET /runs/{id}/archive.zip`（`handler.py:264`）

最後のエンドポイントは、補足が必要です。FastAPI アプリの `GET /runs/{rel:path}`（`app.py:128`）は、run の静的な成果物をパスで返します。ただし、標準ライブラリのハンドラの `_serve_run_archive` のようには、`archive.zip` を特別扱いしません。そのため、このパスへのリクエストは、zip を生成する代わりに `ops.run_file` に渡ります。`ops.run_file` は、`archive.zip` という名前のファイルそのものを探しにいってしまいます。

このうちのいくつかは、設計上ローカル限定であってもおかしくありません。`/api/capture/*` は、start、mark、finish の一連の流れの間、プロセス内に `Driver` のインスタンスを保持し続けます。標準ライブラリのハンドラの単一プロセスモデルでは成立しますが、水平スケールした FastAPI デプロイでは成立しない可能性があります。`/api/ant/login` は、ローカルの CLI をシェルアウトして呼び出します。

しかし、どのエンドポイントが意図的にローカル限定で、どれが単に実装漏れなのかを、コードのどこも述べていません。このギャップも、2 つの `match` / ルートの一覧を手作業で突き合わせて見つけました。宣言を読んで判明したものではありません。

今後、どちらか一方のバックエンドにだけエンドポイントを追加し、もう一方への反映を忘れても、同じように気づかれずに失敗します。発見できるのは、300 行ほどの 2 つのファイルを手作業で突き合わせたときだけです。

認証、CSRF、Host、ヘッダの重複した実施には、これよりも鋭いリスクがあります。両バックエンドのセキュリティ上の振る舞いが一致するには、2 つのコピーを手作業でバイト単位まで一致させ続ける必要があります。一致しているかどうかを検証するものは、何もありません。これは、単なる機能の欠落ではなく、セキュリティに関わる乖離につながりうる潜在的な経路です。

この 2 つの問題は、根が同じです。1 つの振る舞いを、同期の必要な 2 つの独立した実装として持ってしまっていることです。直し方も同じです。単一のソースオブトゥルースを、重複させる代わりに、そのまま実行可能にします。

## 詳細設計

この作業は、両バックエンドが現在すでに提供しているすべてのルートについて、挙動を変えません。変わるのは、各ルートテーブルのデータがどこに存在するかだけです。現在気づかれないまま起きている drift を、grep できる明示的な宣言に変えます。作業は、MECE な 5 つの部分からなります。

1. **単一の宣言的なルートレジストリ。** 1 つのテーブルを導入します。各エントリは、HTTP メソッド、パスパターン、ディスパッチ先の `ops.*` 呼び出し可能オブジェクト、ルートごとの小さなフラグの集合を持ちます。
   - パスパターンは、変数を含むパスセグメントについて、2 つのバックエンドの書き方の違いを吸収します。たとえば、FastAPI は `/api/jobs/{job_id}` と書きます。`handler.py` は、`path.startswith(...)` / `endswith(...)` による手動のマッチングを使います。
   - `needs_actor` は、ハンドラがリクエスト元の identity を解決して渡す必要があるかどうかを表します。
   - `off_loop` は、SSE ストリーミングやファイル配信のように、統一された JSON レスポンスのヘルパーを経由しないルートを表します。
   - `local_only` は、ポイント 4 で述べます。

   このレジストリは、両バックエンドが走査する単一のソースオブトゥルースです。レジストリ自体は、リクエストを実行しません。
2. **標準ライブラリのハンドラはレジストリからディスパッチする。** `do_GET` / `do_POST` / `do_DELETE`（`handler.py:181-429,431-`）は、手書きの `match path` の代わりに、このレジストリを走査します。パスパラメータを解決してから、現在の各ケースと同じ方法で、対になる `ops` 関数を呼び出します。ルートごとのフラグ（`needs_actor`、`off_loop`）は、現在は各ケースに書き出されている条件分岐を、そのまま駆動します。対象は、`self._actor()` の呼び出しと、ストリーミングか `self._json(...)` かの切り替えです。
3. **`make_app` はレジストリから FastAPI のルートを生成する。** `bajutsu/serve/server/app.py` のルート宣言（`app.py:122-490`）を、同じレジストリを走査するループに置き換えます。ループは、各エントリを `app.get` / `app.post` / `app.delete` として登録します。`local_only` のエントリは、ポイント 4 のとおりスキップします。エンドポイントごとに手書きしていた `@app.<method>` デコレータは、なくなります。
4. **`local_only` によって、気づかれない drift を宣言に変える。** *動機* で挙げた、FastAPI アプリに欠けているエンドポイントを、すべて洗い出して判定します。一覧のどれがどちらに分類されるかは、本項目では事前に決め打ちしません。この判定自体が、作業の一部です。
   - 設計上本当にローカル限定であるものには、レジストリ上で `local_only=True` と印を付けます。例は、`Driver` のプロセス内での寿命を持つ `/api/capture/*` と、ローカル CLI へのシェルアウトを持つ `/api/ant/login` です。ポイント 3 の FastAPI 生成処理は、意図的にこれをスキップします。読み手は、レジストリを検索するだけで、一覧とその理由を確認できます。
   - そのような理由がないと判明したエンドポイントは、通常の FastAPI ルートとして補います。ギャップは、そのまま解消します。
5. **重複した認証、CSRF、Host、ヘッダの実施を、共有の 1 つの gate ヘルパーにまとめる。** `handler.py` の次の 3 つは、機能的には、`app.py:69-118` の `gate` ミドルウェアと `_hardened` ヘルパーと同一です。
   - 堅牢化ヘッダ（`handler.py:61-69`）
   - 認証チェックの `_gate`（`handler.py:121-170`）
   - `_csrf_ok` / `_host_ok`（`handler.py:273-290`）

   このポリシーの実装を 1 つだけ切り出します。各バックエンドがリクエストのヘッダ、Cookie、メソッド、パスをどう読み取り、レスポンスをどう書き出すかは、パラメータ化します。`handler.py` と `app.py` の両方が、この共有実装を呼び出します。これにより、セキュリティ上の振る舞いは、2 回ではなく 1 回だけ定義されます。

## 検討した代替案

- **2 つのルートテーブルと 2 つのセキュリティ実施のコピーを手動管理のリストのまま残し、互いに drift したら失敗するテストを追加する。** 主な修正としては却下します。テストが drift を検出するのは、事後です。それも、誰かが drift の出荷前にテストを走らせることを覚えていた場合に限られます。本項目のきっかけとなったギャップも、検出されないまま出荷済みでした。しかも、テストは重複を取り除かず、重複を監視するだけです。単一のレジストリであれば、drift する元のリストが 1 つしか残りません。2 つのバックエンドは、構造的に drift しようがなくなります。
- **レジストリを構築せず、現在欠けているエンドポイントだけを、`app.py` へ手作業で補う。** 却下します。現在判明しているギャップは塞げます。しかし、誰かが次にエンドポイントを追加するときには、同じ手作業の重複がそのまま残ります。同じ種類の drift が再発します。また、重複した認証、CSRF、Host、ヘッダのロジックにも手を付けないままになります。これは、*動機* で述べたとおり、より鋭いリスクです。

  [#1108](https://github.com/bajutsu-e2e/bajutsu/pull/1108) で実装しました。フレームワークに
  依存しない新しいモジュール `bajutsu/serve/routes.py` に、1 つの `ROUTES` テーブル（凍結
  データクラス `Route`、バックエンド中立の `RequestCtx` プロトコル、`{name}` / `{name:path}` の
  テンプレートマッチャ）を置き、各ルートの `ops.*` 呼び出しをルートごとのアダプタ
  `handle(state, ctx)` にまとめました。`handler.py` の `do_GET` / `do_POST` / `do_DELETE` は、この
  テーブルからディスパッチします。挙動は変えていません。Part 1 の草案からの逸脱として、`needs_actor`
  フラグは実装しませんでした。ルートがアクターを解決するかどうかはアダプタのクロージャ内ですでに
  表現されており、独立したフラグを設けると同じ事実の情報源が二重になる（この項目が取り除こうと
  している食い違いそのもの）ためです。`off_loop` と `local_only` は残し（クロージャでは表現できない
  ため）、`content_type` はテキスト応答を選びます。`off_loop` のルート（SSE、ファイル配信、生の
  アップロード、OAuth、ログイン、インデックス）はここで宣言しつつ、各バックエンドの個別処理のまま
  にしています。Part 3（`app.py` をレジストリから生成する）と Part 4（`local_only` による FastAPI
  側で欠けているエンドポイントの判定）は次のスライスで実装します。
- 2026-07-15 — Part 3〜4（`app.py` のレジストリからの生成と判定）を
  [#1115](https://github.com/bajutsu-e2e/bajutsu/pull/1115) で実装し、この項目を完了しました。
  `make_app` は `ROUTES` を走査し、`handle` を持ち `local_only` でない各エントリを登録するようになり、
  手書きの `@app.<method>` デコレータ約 40 個を置き換えました。`off_loop` のルート（インデックス、
  ES モジュールのフロントエンド、run ファイルの配信とレンジ配信とアーカイブ配信、Server-Sent Events
  （SSE）、OAuth、ログイン、生のアップロード）は各バックエンドの個別処理のまま残しています。バックエンドに
  中立な `_FastapiCtx` は標準ライブラリ側の `_StdlibCtx` と対になります。Part 4 の判定では、`/api/ant/login`
  （マシン全体で共有される資格情報を書き込むため、ホスティング時はすでに 403 を返します）と
  `/api/capture/*`（start・mark・finish をまたいでプロセス内の `Driver` を保持します）に `local_only=True`
  の印を付けて生成の対象から外し、それ以外で `app.py` に欠けていたエンドポイント、すなわち `/flakiness`、
  `/api/enrich`、`/api/codegen`、`/api/jobs/{id}/respond-human`、これまで一度も移植されていなかった
  `/api/scenario/apply-selector` と `/api/scenario/enrich-apply`、そして個別処理で補った
  `/runs/{id}/archive.zip` を配信するようにして、静かな食い違いを塞ぎました。パスパラメータの `unquote` は
  レジストリのクロージャから各 ctx へ移し（`path_param` は両バックエンドともデコード済みのセグメントを
  返します）、percent エンコードされたセグメントが `ops` の呼び出しに届くまでの扱いで 2 つのバックエンドが
  食い違わないようにしました。挙動は変えていませんが、ホスティング側のバックエンドは不正なリクエスト本体を
  FastAPI の 422 ではなく標準ライブラリ側と同じ 400 で拒否するようになり（テストで固定されていなかった
  エラー経路を意図的に揃えました）、`?purge` は Part 2 ですでに出荷済みの標準ライブラリの `== "true"` の
  契約に従います（Web UI は `?purge` を送りません）。
