## Introduction

Replace the layout behind the roadmap dashboard's relationship view with a transit-map arrangement:
one horizontal row per topic, the row's items placed along it in identifier order, and a curved line
joining every pair of items that stand in a relation. The view keeps everything
[BE-0335](../BE-0335-roadmap-dashboard-relationship-graph/BE-0335-roadmap-dashboard-relationship-graph.md)
gave it — the same three relations read from the same metadata, the same status colours, and the same
composition with the search box and status chips — and changes only where the items sit and how a
reader moves through them. The view is renamed from Graph to Map to match what it now shows.

Two things follow from the new arrangement. The layout becomes a pure function of each item's topic
and identifier, so it is computed once at build time in Python and shipped as finished Scalable
Vector Graphics (SVG) coordinates, and the browser runs no force simulation at all. And because every
item now has a place a reader can predict, pointing at one is enough to read it: a caption line under
the map names the item under the pointer and its status, while the map dims everything except that
item, its lines, and the items on the other end of them.

## Motivation

The force-directed layout answers "what is the shape of this graph" and little else. It settles into
one large cluster with small components scattered around it, and the position of any single item
carries no meaning a reader can rely on: an item sits where the simulation pushed it, so the same
question asked twice — "where is the item I was looking at" — has a different answer after every
change to the roadmap. A reader looking for one item has to hunt for it rather than know where to
look.

A transit map trades that away for a fixed, readable address. Its rows are the topics a reader
already browses by in Cards view, so the eye lands on the right row immediately; along a row, items
run in identifier order, so an item's neighbours are the items proposed around the same time. What
was a hairball becomes a picture with an index: the reader who knows an item's topic knows its row,
and the reader who knows its number knows roughly how far along the row to look.

The rearrangement also removes the one part of the view that could not be checked. A force
simulation's output is only as good as its parameters, so the picture had to be judged by eye after
every change to them, and no test could pin its correctness. Coordinates derived from topic and
identifier are ordinary data: a test can assert that an item's row is its topic's row, that a row's
items ascend by identifier, and that every line ends on two drawn items.

This is a documentation-site change, so it stays clear of every prime directive
([`CLAUDE.md`](../../CLAUDE.md)). No large language model (LLM) sits anywhere near the page, no `run`
or continuous integration (CI) verdict path passes through it, and the layout is generic over
whatever items the metadata produces, so nothing about it is specific to an application under test.
Moving the layout out of the browser and into the build strengthens determinism rather than bending
it: the same roadmap now yields identical coordinates, checked by a test rather than trusted.

## Detailed design

The relationship view is generated by
[`scripts/build_roadmap_dashboard.py`](../../scripts/build_roadmap_dashboard.py), which today emits
the nodes and edges as a JavaScript Object Notation (JSON) payload and lets an inline script lay them
out. The work is mutually exclusive, collectively exhaustive (MECE) across these units:

1. **Build-time layout.** Add a pure function mapping the drawn items to coordinates: group them by
   topic, order the topics the way the shared index already orders them, sort each topic's items by
   identifier, and place a row's *i*-th item at a fixed step along that row. The function takes the
   items and returns the rows, the node positions, and the drawing's dimensions, with no input beyond
   the metadata — so the same roadmap always produces the same coordinates, and a test can assert
   them.
2. **Packing each row independently, and saying so.** Place an item at the *i*-th slot of its own row
   rather than at its rank among all drawn items. One shared identifier axis across every row is the
   more informative arrangement, because a column then means the same moment in every row, and it is
   what a roadmap of ten items would use. It does not survive this roadmap's scale: roughly 200 drawn
   items on one axis is a drawing some 14,000 pixels wide, nearly all of it the whitespace of rows
   holding a handful of items each. Packing each row to its own items keeps the drawing near a
   seventh of that width, at the cost of columns no longer lining up across rows. The caption states
   the arrangement plainly — items run in identifier order **within a row** — so no reader infers an
   alignment the drawing does not have.
3. **Rows.** Render one row per topic that has at least one drawn item: a horizontal rule spanning
   the plot, and the topic's name right-aligned in a left gutter. A topic with no drawn item gets no
   row, so the map carries no empty lines.
4. **Curved connectors.** Render each relation as a path rather than a straight line, in the shape
   its endpoints call for: an arc bulging above the row when both items share it, and a curve leaving
   one row horizontally and arriving at the other horizontally when they do not. Both read as one
   continuous line rather than a diagonal cutting across the rows. Keep BE-0335's edge semantics
   unchanged — a mutual `Related` pair is one undirected line, while `Origin` and `Superseded by`
   stay directed and keep their arrowhead and dash pattern.
5. **Nodes.** Render each item as a link holding three pieces: a transparent circle wide enough to be
   an easy pointer and touch target, a smaller visible dot in its status colour, and its identifier as
   a label beneath. The link points at the item's file on GitHub, so a node stays reachable by
   keyboard and openable in a new tab.
6. **Pointing at an item.** On hover or focus, dim every node and line except that item, the lines
   touching it, and the items on their far ends, and write the item's identifier, title, and status
   into a caption line below the map. The line is a live region carrying a default sentence, so a
   reader using a screen reader hears what a sighted reader sees, and the map is never silently
   uninformative.
7. **Retiring the simulation.** Delete the force simulation, the fit-to-box pass, and the drag, pan,
   and zoom handling from the inline script; what remains is the filter composition and the pointing
   behaviour above. A map with a fixed address for every item need not be dragged, and its container
   scrolls, so panning and zooming lose their purpose along with the simulation that made them
   necessary. This removes roughly two hundred lines of browser code, and with them the only part of
   the page whose output no test could pin.
8. **Fitting the drawing on the page.** Wrap the map in a container that scrolls horizontally, and
   give the drawing a minimum width equal to its natural size, so it is never scaled below the size
   its labels were drawn for. The reader scrolls a wide map rather than squinting at a shrunken one.
9. **Renaming the view.** Rename the third toggle entry from Graph to Map, and update the page's
   introductory prose to describe the arrangement. The stored preference keeps its key and its
   `graph` value, so a reader who chose this view before the change still lands on it.
10. **Tests.** Replace BE-0335's payload tests with tests over the layout: every drawn item is placed
    exactly once, an item's row is its topic's row, each row's items ascend by identifier, every
    path's endpoints are drawn items, no row is emitted for a topic without items, and the whole
    drawing fits inside the reported dimensions. These need no browser, so the gate stays fast and
    free of any LLM.

`docs/` needs no matching edit: the pages that mention the dashboard describe what it is for, not
which views it offers or how they are drawn. Should a future sentence there enumerate them, it is
updated in the same change ([BE-0113](../BE-0113-design-doc-realignment/BE-0113-design-doc-realignment.md)).

## Alternatives considered

- **Keep the force-directed layout and add map-like controls to it** — zoom buttons, a minimap, a
  detail panel. Rejected: the complaint this arrangement answers is that an item has no fixed place,
  and no control around a simulation gives it one. Navigation aids would make an unpredictable
  picture easier to move around, not easier to read.
- **One shared identifier axis across every row.** Rejected at this roadmap's scale for the reason in
  unit 2 — a drawing some 14,000 pixels wide, most of it empty. Worth revisiting only if the drawn
  set shrinks by an order of magnitude, which the roadmap's direction makes unlikely.
- **Order each row by something other than the identifier** — by how many relations an item has, so
  the busiest lead, or by status. Rejected: an identifier is the one key a reader already knows before
  opening the page, which is what makes a position predictable. Relation count and status both change
  as the roadmap changes, moving an item that did not change at all.
- **Keep both layouts, as a fourth view.** Rejected: the dashboard would then carry two answers to one
  question, and this item argues the force-directed one is the weaker of the two. Retiring it removes
  its code as well, rather than leaving an unused simulation to maintain.
