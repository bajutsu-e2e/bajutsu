## はじめに

ロードマップダッシュボードの関係図表示について、その配置を路線図の形に置き換えます。トピックごとに
横1行を引き、その行の項目を ID 順に並べ、関係を持つ項目どうしを曲線でつなぐ形です。
[BE-0335](../BE-0335-roadmap-dashboard-relationship-graph/BE-0335-roadmap-dashboard-relationship-graph-ja.md)
が与えたものは、そのまま残ります。同じメタデータから読む3つの関係も、状態ごとの色も、検索ボックスと
ステータスチップとの組み合わせも変わりません。変わるのは、項目がどこに置かれるか、そして読者がどう
たどるかだけです。表示の名前は、示すものに合わせて Graph から Map に改めます。

新しい配置からは2つのことが導かれます。1つは、レイアウトが各項目のトピックと ID だけで決まる純粋な
関数になることです。計算はビルド時に Python が1度だけ行い、完成したスケーラブルベクターグラフィックス
（SVG）の座標として配信できます。ブラウザは力学モデルのシミュレーションをまったく動かしません。
もう1つは、すべての項目が読者に予測できる位置を持つため、指し示すだけで内容が読めるようになることです。
ポインタを重ねた項目の名前と状態が図の下のキャプション行に出て、その項目と、つながっている線と、線の
先の項目以外は暗くなります。

## 動機

力学モデルの配置が答えるのは「このグラフの形はどうなっているか」であり、それ以外にはほとんど答えません。
配置は1つの大きな塊とその周りに散らばる小さな成分に落ち着き、個々の項目の位置は読者が頼れる意味を
持ちません。項目はシミュレーションに押された場所に座るので、「さっき見ていた項目はどこか」という
同じ問いの答えが、ロードマップが変わるたびに変わります。1つの項目を探したい読者は、どこを見ればよいかを
知るのではなく、探し回ることになります。

路線図は、それと引き換えに、読める固定の住所を項目へ与えます。行はトピックであり、読者が Cards 表示で
すでにたどっている区分なので、目当ての行にはすぐ目が届きます。行の中では項目が ID 順に並ぶので、隣に
いるのは近い時期に提案された項目です。もつれた塊だった図が、索引を持つ絵になります。項目のトピックを
知っていれば行が分かり、番号を知っていれば行のどのあたりを見ればよいかが分かります。

配置を変えることで、検査できなかった部分も1つ消えます。力学モデルの出力はパラメータの出来次第なので、
パラメータを変えるたびに図を目で見て判断するほかなく、その正しさをテストで固定できませんでした。
トピックと ID から導いた座標は、ただのデータです。項目の行がそのトピックの行であること、行の中で項目が
ID の昇順に並ぶこと、どの線も描かれた項目2つで終わることを、テストで主張できます。

この変更はドキュメントサイトに閉じるので、どの絶対的指針（[`CLAUDE.md`](../../CLAUDE.md)）にも
抵触しません。大規模言語モデル（LLM）はこのページの近くに一切現れず、`run` や継続的
インテグレーション（CI）の合否判定の経路もここを通らず、レイアウトはメタデータが生む項目に対して
汎用なので、テスト対象のアプリケーション固有の要素も持ちません。配置をブラウザからビルドへ移すことは、
決定性を曲げるのではなく強めます。同じロードマップからは同じ座標が出るようになり、それを信頼ではなく
テストで確かめられます。

## 詳細設計

関係図表示は [`scripts/build_roadmap_dashboard.py`](../../scripts/build_roadmap_dashboard.py) が
生成します。現在はノードと辺を JavaScript Object Notation（JSON）として出力し、配置はインラインの
スクリプトに任せています。作業は、互いに重複がなく全体を覆う（MECE な）次の単位に分かれます。

1. **ビルド時のレイアウト計算**。描く項目を座標へ写す純粋な関数を追加します。項目をトピックごとに
   まとめ、トピックの順序は共有インデックスがすでに持つ順に従い、各トピックの項目を ID 順に並べ、
   行の *i* 番目の項目をその行の一定の間隔の位置に置きます。関数が受け取るのは項目だけで、返すのは
   行と、ノードの位置と、図全体の寸法です。メタデータ以外の入力を持たないので、同じロードマップからは
   常に同じ座標が出て、テストでそれを主張できます。
2. **行ごとに詰めること、そしてそれを明記すること**。項目は、描かれる全項目の中での順位ではなく、
   自分の行の *i* 番目の位置に置きます。すべての行で1本の共通した ID 軸を使うほうが、情報量では
   優れています。同じ列が、どの行でも同じ時期を意味するからです。10件程度のロードマップならその形に
   なるでしょう。しかし、この規模では成り立ちません。約200件を1本の軸に並べると、図の幅は約14,000
   ピクセルになり、そのほとんどは、数件しか持たない行の余白です。行ごとに自分の項目だけを詰めれば、
   幅はその7分の1程度に収まります。代償として、列は行をまたいでそろわなくなります。キャプションには
   配置をそのまま書きます。項目が ID 順に並ぶのは**行の中**である、と明記することで、図にない
   そろい方を読者が読み取ることはなくなります。
3. **行**。描く項目を1つ以上持つトピックごとに、1本の行を描きます。図の幅いっぱいに引いた罫線と、
   左の余白に右寄せで置いたトピック名です。描く項目を持たないトピックには行を与えないので、空の行は
   図に現れません。
4. **曲線のつなぎ**。関係は直線ではなくパスで描き、両端の位置に応じて形を変えます。2つの項目が同じ行に
   あれば行の上に膨らむ弧を、別の行にあれば一方の行から水平に出て他方の行へ水平に入る曲線を描きます。
   どちらも、行を横切る斜め線ではなく1本の連続した線として読めます。辺の意味は BE-0335 のまま変えません。
   相互に張られた `関連` は1本の無向線で、`由来` と `後継` は有向のままで、矢じりと破線の種類も
   そのままです。
5. **ノード**。各項目は、3つの部品を持つリンクとして描きます。ポインタでもタッチでも押しやすい大きさの
   透明な円、状態の色を持つ小さなドット、そしてその下に置く ID のラベルです。リンク先は項目の GitHub 上の
   ファイルなので、キーボードからも辿れ、新しいタブでも開けます。
6. **項目を指し示したとき**。ポインタを重ねるかフォーカスを当てると、その項目と、触れている線と、線の
   反対側の項目以外のノードと線が暗くなり、図の下のキャプション行にその項目の ID、タイトル、状態が
   書き込まれます。この行は既定の文を持つライブリージョンなので、スクリーンリーダーを使う読者にも、
   目で見る読者と同じ内容が伝わり、図が黙って何も語らない状態になりません。
7. **シミュレーションの撤去**。力学モデルの計算、キャンバスに収めるための拡大縮小、そしてドラッグ・
   平行移動・拡大縮小の処理を、インラインスクリプトから削除します。残るのは、絞り込みとの組み合わせと、
   上の指し示しの挙動です。すべての項目が固定の住所を持つ地図は、ドラッグする必要がありません。
   容器の側がスクロールするので、平行移動と拡大縮小も、それらを必要にしていたシミュレーションと一緒に
   役目を終えます。これによって約200行のブラウザ側のコードが消え、同時に、出力をテストで固定できな
   かった唯一の部分もなくなります。
8. **図をページに収めること**。地図は横方向にスクロールする容器で包み、図には自然な大きさと同じ最小幅を
   与えます。こうすれば、ラベルが読めるように描いた大きさより小さく縮められることがありません。読者は、
   縮んだ図を目を細めて見るのではなく、広い図をスクロールします。
9. **表示の改名**。表示切り替えの3つ目を Graph から Map に改め、ページ冒頭の説明文も配置を説明する
   ものに書き換えます。保存する設定はキーも `graph` という値もそのままにするので、この変更より前に
   この表示を選んでいた読者は、変わらずこの表示にたどり着きます。
10. **テスト**。BE-0335 のペイロードのテストを、レイアウトのテストに置き換えます。描く項目がちょうど
    1度ずつ配置されること、項目の行がそのトピックの行であること、行の中で項目が ID の昇順に並ぶこと、
    どのパスの両端も描かれた項目であること、項目を持たないトピックの行が出力されないこと、そして図
    全体が申告した寸法に収まることを確かめます。ブラウザを必要としないので、ゲートは速いまま、LLM とも
    無縁のままです。

[`docs/`](../../docs/README.md) 配下のドキュメントに対応する修正は必要ありません。ダッシュボードに
言及しているページは、ダッシュボードが何のためのものかを説明していて、どの表示を備えるかも、どう
描かれるかも書いていないからです。将来そこに表示を列挙する記述が生まれたときは、同じ変更で更新します
（[BE-0113](../BE-0113-design-doc-realignment/BE-0113-design-doc-realignment-ja.md)）。

## 検討した代替案

- **力学モデルの配置を残したまま、地図らしい操作部品を足す**。ズームボタン、ミニマップ、詳細パネルと
  いったものです。採用しませんでした。この配置が答えようとしている不満は、項目に固定の位置がないこと
  であり、シミュレーションの周りにどんな部品を置いても位置は定まりません。操作の補助は、予測できない
  絵を動かしやすくはしますが、読みやすくはしません。
- **すべての行で1本の共通した ID 軸を使う**。この規模では採用しませんでした。理由は作業単位2に書いた
  とおりで、幅が約14,000ピクセルになり、そのほとんどが余白になるためです。描く項目が桁違いに減れば
  再考の余地がありますが、ロードマップの方向からするとその見込みは薄いといえます。
- **行の中の順序を ID 以外にする**。関係の数の多い順に並べて中心の項目を先頭に置く案や、状態順に
  並べる案です。採用しませんでした。ID は、読者がページを開く前からすでに知っている唯一の手がかりで
  あり、位置が予測できるのはそのおかげです。関係の数も状態もロードマップが変われば変わるので、
  何も変わっていない項目まで動いてしまいます。
- **両方のレイアウトを残し、4つ目の表示にする**。採用しませんでした。1つの問いに対する答えを
  ダッシュボードが2つ抱えることになり、しかもこの項目は、力学モデルのほうが劣ると主張しています。
  撤去すればそのコードも一緒に消え、使われないシミュレーションを保守し続けずに済みます。
