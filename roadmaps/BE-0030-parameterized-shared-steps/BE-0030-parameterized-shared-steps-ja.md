## はじめに

`use` ステップで引数付きの再利用部品（component）を定義して呼び出し、`${params.*}` を展開します（`expand_components`）。`setup` プレリュード（引数なし）と併用できます。ログインなどの共通手順の重複を排除できます。

## 動機

多くのシナリオは、ログイン、オンボーディングの承認、特定画面への遷移といった共通の前半部分を共有しています。これを各シナリオにコピーすると、同じ手順が何十回も繰り返されます。フローが変わると同期が崩れ、ファイルも肥大化します。

既存の `setup` プレリュード（固定の共通フローをシナリオの前に差し込む仕組み）は、引数なしのケースを扱えます。ただし、呼び出しごとに値を変えられません。シナリオごとに異なるユーザーでログインしたい場合や、異なるタブへ遷移したい場合に、引数を渡す手段がないのです。

そこで、引数を取る再利用可能なステップ単位が必要です。1 つの定義を多くの呼び出し箇所で使い回し、値を呼び出しごとに埋められるようにします。

## 詳細設計

[*コンポーネント*](../../docs/ja/glossary.md#scenario-authoring)は、再利用可能でパラメータ化されたステップ列で、単一のマッピングとして独立したファイルに定義します。マッピングは、呼び出し側が渡すべき引数名を並べた `params` リストと、それらを `${params.<name>}` として参照する `steps` から成ります（`bajutsu/scenario/` の `Component`）。シナリオは `use` ステップ（`use: { component: <file>, with: { <name>: <value>, … } }`）で呼び出し、宣言された各 param に `with` で値を渡します。

展開は、ランタイムのアクションではなく、純粋なコンパイル時マクロです。run の前に `expand_components` が全シナリオを走査し、各 `use` ステップをその場で、参照先コンポーネントの steps に置き換えます。`with` の値は、共通の `${...}` 補間プリミティブ（`interp.interpolate`、キーは `params.<name>`）で置換します。

コンポーネントは、それ自体がさらに別のコンポーネントを `use` できるため、展開は再帰します。次の場合は、いずれもハードエラーです。

- 参照の循環
- 不足または未知の param
- 宣言されていない param を指す、未解決の `${params.*}` トークン
- `max_depth` を超えるネスト

展開後は `use` ステップが一切残りません。決定的なランナーは常に、展開済みのプレーンなステップだけを見るため、決定性は損なわれません。`use` は、引数なしの `setup` プレリュードと併用できます。ロード時の同じパスで、プレリュードを前置し（`apply_setups`）、コンポーネントを展開します。

## 検討した代替案

**ランタイムでの call/return（コンポーネントをランナーが入り込むサブルーチンとして扱う）。** 不採用です。挙動上の利点がないのに、コールスタックと実行中フレームの状態を run ループに持ち込みます。オーサリングの糖衣構文と実行の境界も曖昧になります。コンパイル時展開なら、ランナーはフラットなステップだけを見るため、実行されるシナリオはレポートに表示されるものと完全に一致します。

**インライン限定の再利用（YAML アンカー／ファイルへのテンプレートエンジン適用）。** 不採用です。アンカーは 1 ファイル内のテキストを複製できても、ファイルをまたげず、名前付き引数もきれいには扱えません。汎用テンプレートエンジンは、シナリオファイルに任意のロジックを招き入れます。明示的な `params` 契約を持つ名前付きコンポーネントのほうが、範囲が狭いです。しかも検証され（未知または不足の param は失敗する）、入力を自己文書化します。
