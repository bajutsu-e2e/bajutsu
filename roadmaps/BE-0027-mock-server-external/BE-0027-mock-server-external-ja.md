## はじめに

config スキーマのみ存在します。宣言的な in-protocol `mocks`（実装済み）に置き換えられており、外部サーバ方式が必要かどうかは未決定です。

## 動機

決定的な E2E run には、ネットワークを制御下に置くことが欠かせません。同じリクエストに毎回同じレスポンスが返らなければ、合否を再現できなくなるからです。config はすでに、その一手段として `mockServer` スキーマ（`cmd` / `port` / `stubs`）を備えています。run の傍らで外部モックサーバのプロセスを起動し、アプリをそこへ向ける方式です。アプリを本物のバックエンドではなく `localhost:<port>` に接続させ、サーバが定型のレスポンスを返す、という想定でした。

その後、同じ要求は別の仕組みで満たされました。シナリオレベルの `mocks` は、Bajutsu 自身のネットワーク経路の内側で横取りする、宣言的な in-protocol スタブです。実装済みで、実機で検証されています。起動、ヘルスチェック、後始末を要する第二のプロセスなしに、オフラインで決定的なレスポンスを提供します。

そのため、本項目で未決なのは「外部サーバをどう作るか」ではなく「そもそも必要か」です。この問いが、本項目をスケジュール済みではなく**保留**としている理由です。

## 詳細設計

採用が決まった時点で具体化します。今日存在するのはスキーマ（`config.py` の `MockServer`: `cmd` / `port` / `stubs`）だけで、ランタイム上の効果はありません。

本項目は**保留**のため、設計は意図的に詰めていません。仮に採用するなら、in-protocol `mocks` がすでに満たしている基準を満たす必要があります。

- **決定性。** 外部サーバは、シナリオ開始前に既知の準備完了状態まで立ち上げます。終了後に確実に後始末されたことも検証します。固定 `sleep` は使いません。準備完了またはヘルスの条件で待ち、「条件待ちのみ」に従います。アプリが最初に呼ぶ時点でまだ待ち受けていないことがあるプロセスは、プロジェクトが禁じるフレーク性をまさに再導入してしまいます。
- **アプリ非依存の config。** 配置は現状のまま（`apps.<name>.mockServer`）とします。アプリ単位のモック配線は config に置き、ランナーはアプリ間で不変に保ちます。
- **LLM フリーのゲート。** モックサーバは決定的なプロセスなので、「LLM を run/CI ゲートに入れない」というプライムディレクティブには触れません。

**採用する**のは、in-protocol `mocks` では賄えない具体的な必要が現れた場合に限ります。たとえば、宣言的なスタブとして表現するには状態やプロトコルが重すぎるバックエンドです。本物の gRPC や WebSocket サーバや、アプリが多数のリクエストにまたがって駆動するステートフルなセッションが該当します。さらに、in-protocol スタブの記述言語を拡張するより、既存のモックサーバ実装を再利用するほうが本当に単純な場合に限ります。そうした必要がない限り、スキーマは文書化された未配線のプレースホルダのまま残ります。

## 検討した代替案

**いま外部サーバを実装する。** 今回は却下しました。管理すべきプロセス（起動、準備完了、後始末）と、ネットワーク挙動の第二の源が増えます。その必要は、実装済みの in-protocol `mocks` がすでに満たしています。動機となるユースケースなしに先回りして作ると、複雑さだけを抱え込むことになります。

**`mockServer` スキーマを完全に削除する。** 検討しましたが、残しました。このスキーマは実在する設計上の代替案を文書化しており、未配線である限りコストはかかりません。削除すればその選択肢を捨て、将来の担い手に形を再発見させることになります。`architecture.md` が「スキーマのみ、未配線」と明示した状態で保留のまま保持するのが、誠実な落としどころです。
