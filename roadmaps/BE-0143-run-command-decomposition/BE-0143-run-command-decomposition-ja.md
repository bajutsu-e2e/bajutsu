## はじめに

すべてのシナリオの合否を決める `run` コマンドは、418 行の 1 関数として実装されています。
本項目では、そのオプション宣言とオーケストレーションの各ステップを、同じ CLI 面の裏側で
まとまりのある補助関数へ切り出します。決定的コアの中で最も重みのあるこのコマンドが、挙動を
変えずに、読みやすく、独立してテストできる形になります。

## 動機

`bajutsu/cli/commands/run.py:186` から始まる `run` 関数は、`bajutsu/cli/commands/run.py:603`
まで続きます（`register` は 604 行目から始まります）。1 つの関数本体が 418 行あり、次の 2 つの
部分に分かれます。

- **約 118 行（186〜303 行目）** は、このコマンドの広大なフラグ面に対応する `typer.Option`
  宣言です。
- **残りの約 300 行（304〜601 行目）** は、オーケストレーションです。関数は次のステップを
  順に実行します。
  1. effective 設定を解決し、必要ならアプリをビルドする。
  2. `--headed`、`--browser`、`--browsers` を解決する。
  3. シナリオを読み込み、`--tag` と `--exclude` で絞り込む。
  4. actuator を選択し、`--browsers` マトリクスがその actuator に合うかを検証する。
  5. デバイスレーンを解決する。
  6. alert-guard ファクトリを構築する。
  7. baseline、schema、golden の各ディレクトリを解決する。
  8. 開始 webhook を発火する。
  9. launch server を起動する。
  10. 単一エンジンの経路とクロスブラウザマトリクスの経路のどちらを取るかをディスパッチする。
  11. 判定結果、終了 webhook、任意の `--zip` アーティファクト、AI 使用量サマリを出力する。

この規模の関数には、3 つの問題があります。

- 最初から最後まで読み通すのが難しい。
- 「コマンド全体を実行する」より細かい粒度でテストできない。
- 変更のリスクが高い。本体のどこか一箇所を編集するだけで、それまでの 300 行で積み上げてきた
  状態に触れてしまう。

規模は M です。各ステージの境界は、コード自身のコメントにすでに現れています。たとえば
「Validate the backend before touching the Simulator CLIs」や「Mocks ride the network channel」
です。そのため、切り出しは大部分が再設計ではなく、命名と移動の作業になります。

## 詳細設計

この作業は挙動を変えずに行います。`run` の CLI 面は変更しません。フラグ、デフォルト値、終了
コード、標準出力と標準エラー出力は、そのままです。cli-command-coverage 項目で追加するカバレッジ
を先に着地させ、この分解に検証用の安全網を持たせます。作業は独立した 2 つの軸に分解します。

- **オプション宣言のグルーピング。** 約 118 行の `typer.Option(...)` 宣言
  （`bajutsu/cli/commands/run.py:186`〜`303`）は、並び順にすでに現れているまとまりに分けられます。
  - target と scenario の選択
  - backend と device の選択
  - browser と engine の選択
  - baseline、schema、golden の各ディレクトリの上書き
  - レポートと出力のフラグ（`--progress`、`--zip`、`--runs-dir`）

  `typer.Option` の呼び出しはシグネチャの中に置く必要があるので、宣言を別関数にする必要は
  ありません。シグネチャ自体は、より明確なセクションコメントで整理できます。`run` が再展開する
  少数の `dataclass` ベースのオプションバンドルにまとめる方法もあります。どちらの方法でも、
  `typer` の introspection を壊さず、フラグ面を二重管理しないことが条件です。この二重管理は、
  兄弟項目の serve-cli-flag-mirror-drift が扱う裏返しの問題です。`serve` 側は現在、この同じ面を
  手作業で複製しています。
- **オーケストレーションステップの切り出し。** 約 300 行の本体を、このファイルに既存の
  `_resolve_*`、`_scenario_files`、`_expand_file` といった補助関数と並ぶ形で、補助関数へ
  分解します。各補助関数はプレーンなデータを受け取って返すので、Simulator なしでユニット
  テストできます。
  - 設定とビルドの解決（`_load_effective_with_source` の呼び出しから `build_if_missing` まで）
  - browser と engine の解決（`--headed`、`_resolve_browser`、`_parse_browsers`）。一部は
    すでに切り出し済みです。
  - シナリオの読み込みと `--tag` / `--exclude` による絞り込み（`--erase` の上書きを含む）
  - backend と actuator の選択、および web 以外での `--browsers` マトリクスの検証
  - デバイスレーンの解決と `--dismiss-alerts` の上書き
  - alert-guard ファクトリの構築（`_guard_for` クロージャとその credential-gap チェック）
  - baseline、schema、golden の各ディレクトリの解決（すでに切り出し済みです。新しいステップへ
    配線します）
  - 単一エンジンとクロスブラウザマトリクスのディスパッチ（`run_pass` / `device_pool` /
    `run_and_report` / `run_matrix_and_report` の分岐）
  - 実行後のレポーティング（判定結果の出力、終了 webhook、`--zip` パッケージング、AI 使用量
    サマリ）

  こうすると、`run` 自体はこれらの補助関数を順に呼び出す薄いシーケンスになります。それぞれの
  補助関数は、cli-command-coverage 項目が追加する高速テストで独立して検証できます。

## 検討した代替案

- **`run` を 1 関数のまま残し、コメントで各ステージを区切るにとどめる。** 却下します。
  この関数には、各ステージの境界に説明的なコメントがすでに付いています（前述のとおり）。
  このコメントは、境界が認識されていながら、コードとしては表現されていないことを示しています。
  コメントだけでは、ステージを独立してテストしたり、単独で安全に変更したりできるようには
  なりません。
- **オーケストレーションを共有状態上のメソッド群として持つ `Runner` クラスを導入する。** 今回の
  作業としては却下します。このクラスは、大きな面を残したまま、`self` を介した暗黙の共有状態を
  持つメソッド群に散らすだけです。本項目が志向するプレーンなデータを扱う補助関数のほうが、
  単体でのテストも理解も容易です。切り出した補助関数が、関数引数として渡すには収まりが悪い
  ほどの共有コンテキストを必要とすると判明した場合にのみ、改めて検討する価値があります。
- **切り出しとカバレッジ追加を 1 つの PR で行う。** 却下します。既存のテスト網がない状態で
  リファクタリングすると、切り出しが挙動を保ったかどうかを判別しづらくなります。
  cli-command-coverage 項目を先に進めることで、この作業を検証する安全網を確保します。
