## はじめに

bajutsu がテスト対象アプリに伝えられることは、起動時の一度だけです。`BajutsuKit` は
`startIfEnabled()` で起動環境を読み、それ以降 bajutsu から何も聞きません。アプリが持つ唯一の経路は
送信方向で、しかも投げっぱなしです。そのためアプリ内の機能はプロセスの生存期間中ずっと固定され、
シナリオの「途中で」変わる必要のある機能は、変われません。この項目では、欠けている向きを足します。
bajutsu が走っているアプリへコマンドを届ける経路であり、アプリがすでに話しているコレクタへのポーリング
として作るので、テスト対象アプリの内部にポートを開きません。この経路が運ぶのは操作の指示だけで、
判断は運びません。したがって決定的な判定には影響しません。

## 動機

すでに出荷した機能 1 つと、進行中の設計 1 つが、欠けている向きによって同じ形で限界に当たり、
同じ形で諦めています。

1 つはアプリ内のタッチ可視化です。[BE-0371](../BE-0371-visualize-touches-in-app/BE-0371-visualize-touches-in-app-ja.md)
が `bajutsu run --touch-markers` として出荷しています。アプリが受け取ったタッチの位置にマーカーを描き、跡は次のジェスチャまで残るので、ステップのスクリーンショットにも写ります。ここが
`visual` アサーションと衝突します。`visual` はスクリーンショットを、リポジトリに置いたベースライン画像と
比較しますが、マーカーはまさにその比較が読む画像に描き込まれるからです。本来あるべき振る舞いは、その
撮影のあいだだけ跡を隠し、終わったら戻すことです。しかし起動環境が唯一の入力なので、`--touch-markers` は
代わりに、スクリーンショットで合否を決めるシナリオをまるごと飛ばします。問題より粒度が粗く、しかも調査している当人が見たかったまさに
そのシナリオのタッチ証跡を失います。

もう 1 つ、リクエストのスタブも同じ形で縛られています。`BajutsuNet.startIfEnabled()` はシナリオの規則を
起動環境から一度だけ読み込むので（`BajutsuKit/Sources/BajutsuKit/BajutsuNet.swift:29`）、前半では
ある応答を、後半では別の応答を返したいシナリオを表現できません。規則は最初のステップが走る前に
焼き付いています。回避策はシナリオを 2 つに割ってアプリを再起動させることですが、1 つのユーザー体験が
2 つになり、その体験が積み上げてきた状態も失われます。

どちらの限界も、それらの機能の作り込み不足ではありません。同じ 1 つの基礎機能が欠けているだけです。
そして、その基礎機能がこれまで作られてこなかった理由も、暗示で済まさずはっきり書くべきです。受信方向の
経路とは、アプリの外にあるものが、走っているアプリの振る舞いを変えられるという意味です。これは便利だから
付け足す類のものではなく、意図して導入し、固く閉じるべき能力です。

## 詳細設計

設計は、安価な実装を可能にする 1 つの事実から始まります。アプリと bajutsu は**すでに認証済みの HTTP
関係を持っており**、その片方向しか使っていません。`NetworkCollector`
（`bajutsu/evidence/network.py:116`）はループバック上で `BaseHTTPRequestHandler` を動かし、run ごとの
トークンを発行し（`:207`）、そのトークンを持たない POST を拒みます。比較は定数時間で行います
（`check_token`、`:167`）。アプリはコレクタの URL とトークンを `BAJUTSU_COLLECTOR` と
`BAJUTSU_COLLECTOR_TOKEN` で受け取り、exchange はコレクタのルートパスへ、transition は `/transitions` へ POST します（`:305`）。
そしてハンドラの `do_GET` は存在しますが、`200` を返すだけで何もしていません（`:315-317`）。

つまりこの経路には、新しいサーバ、新しいポート、新しい認証方式のいずれも要りません。
要るのは、遊んでいる `GET` の裏に置くキューだけです。

### 形

**bajutsu が積み、アプリが取りに来て、アプリが完了を返します。** コマンドは、機能の名前と取るべき状態を
示す小さな JSON です。アプリはコレクタに保留中のコマンドを問い合わせ、受け取ったものを適用し、すでに
使っている送信経路で完了を報告します。ほかは何も変わりません。アプリはソケットを開かず、コレクタを
すでに守っているトークンがコマンドも守ります。

完了報告は飾りではありません。この経路をプライム原則 2 の正しい側に留めるものです。コマンドを送って
「十分な時間」眠る呼び出し側は、まさに原則が禁じる固定 sleep になってしまいます。そうではなく、実行
ループは**完了報告を条件待ち**し、届かなければはっきり失敗します。これによりコマンドは、次のステップの
前に効いたことが証明されるか、さもなければステップがその旨を述べて失敗します。タッチマーカーの件が
願望ではなく正しくなるのも、この性質によります。アプリが跡を隠したと確認してからでなければ、
スクリーンショットは撮られません。

### この経路が決してなってはいけないもの

伝送方式よりも、次の 3 つの境界のほうが重要です。

**判断を運ばないこと。** コマンドは機能の名前と状態を示します。この経路の上にあるものが、ステップの
合否に影響してはならず、どのアサーションもここから読んではなりません。さもなければテスト対象アプリが
自らの判定に加わってしまい、プライム原則 1 が禁じるところです。より鋭く言えば、`run` のゲートは
機械的に検査可能で、かつアプリに依存しないままでなければなりません。

**求められない限り無効であり、起動環境だけよりも固く閉じること。** `BajutsuKit` をリリースビルドに
組み込み、起動環境のガードを頼りにしている採用者は、そうでなければ、環境変数 1 つでアプリ自身の
振る舞いの遠隔操作が有効になるバイナリを出荷することになります。`BajutsuKit` の README は現在、
パッケージをリリースビルドから外すか、`BAJUTSU_COLLECTOR` のガードに頼るかの二択を示しています。
この項目は後者を退けます。そのガードこそが十分でなくなるからです。リリースビルドからの締め出しは
二択の一方ではなく必須の前提になるので、README もその言葉で書き直さなければなりません。

**アプリをテストしやすくする手段にならないこと。** この経路が制御するのは、bajutsu 自身のアプリ内計測
（可視化、スタブの表）であって、アプリケーションの状態に手を伸ばすためのものではありません。アプリの
データを仕込んだり画面遷移を操作したりするコマンドは、アプリ固有の知識をツールへ持ち込み、伝送方式が
何を許すかに関わらずプライム原則 3 を壊します。

### ポーリングの代償

ポーリングは、リスナーを持たないことをレイテンシで買います。コマンドが効くのは、早くても次のポーリングの
ときです。タッチマーカーの件では、そのレイテンシはスクリーンショットを比較するステップごとに 1 回、
完了待ちの後ろで直列に払われます。調査用のフラグとしては許容できますが、すべてのステップに載る機能で
あれば許容できません。ポーリングはテスト対象アプリの中でタイマーも回すので、経路が有効なときだけ動かす
必要があり、遊んでいるポーリングがアプリ自身のタイミングを乱さないことを実装で示さなければなりません。
アプリ自身のタイミングは、テストがまさに測っているものです。

もう 1 つ、誰かが驚く前に書いておくべき結合があります。タッチ可視化は今日、コレクタを必要としません。
ネットワーク機能を一切使わない素の録画実行が通常の使いどころです。コマンドをコレクタ経由にすると、
シナリオ途中の制御を望むシナリオは、本来なら要らないコレクタも起動することになります。代替案である
専用の第 2 のエンドポイントは、独立性を、守るべきサーバが 2 つになる代償で買います。この項目がその案を
採らない理由は *検討した代替案* に記録します。

### 作業分解

以下の単位は、互いに排他で、全体を尽くしています（MECE）。

| 単位 | 作業 |
|---|---|
| 1 | キュー：`NetworkCollector` に保留コマンドの一覧、それを引き取る認証付き `GET`、そして完了報告のエンドポイントを置く。完了報告のエンドポイントは `do_POST` の catch-all より前で照合する。catch-all はそれ以外のパスをすべてネットワークの exchange として保存するので、後ろに置くと完了報告が `request` アサーションの読む exchange に入ってしまう。完了報告はコマンドを「適用したか」を伝え、適用できなかったときはアプリ自身の理由も運ぶ。したがって「適用した」と「引き取ったが適用できなかった」が、単位 3 の待ちに同じ知らせとして届くことはない。トークン検査は今日 `do_POST` が行っているのとまったく同じように適用し、`clear()` は exchange と並んで保留キューも落とすので、あるシナリオが引き取らせずに終えたコマンドが次のシナリオへ配送されることはない |
| 2 | アプリ側：`BajutsuKit` にポーリングとコマンドの振り分けを置く。明示的なビルド設定で選ばないかぎりコンパイルされず、コンパイルされた場合も専用の起動環境キーで有効化し、キーがなければ何もしない。つまり起動環境が唯一の防壁になることはない。完了報告は既存の報告用セッションで POST する |
| 3 | 待ち：実行ループに完了報告の条件待ちを置き、タイムアウトでははっきり失敗させる。最初のコマンドとして、スクリーンショットを比較するステップの前後で BE-0371 のタッチ可視化を切り替え、`--touch-markers` が今おこなっているシナリオまるごとの飛ばしを置き換える。待ちはパイプラインがすでに駆動している `Collector` プロトコルを通ってアプリへ届くので、この単位ではどのコレクタが経路を持つのかも定め、持たないコレクタに対して発行されたコマンドは、黙って飛ばすのではなくはっきり失敗させる |
| 4 | 2 つめのコマンド：シナリオ途中でスタブの表を差し替え、シナリオを 2 つに割らずにモック応答を変えられるようにする |
| 5 | 日英両言語のドキュメント：経路、有効化キー、上記の境界、そしてこの経路が必須にするリリースビルドの締め出し |

## 検討した代替案

**アプリの中にリスナーを開く。** テスト対象アプリの中に小さな HTTP サーバを立てれば、コマンドを直接
受け取れ、ポーリングのレイテンシもありません。この案を退けた理由は工学面ではなく、セキュリティの境界に
あります。テスト対象アプリケーションの内部で待ち受けるソケットは、ループバックのクライアントによる
ポーリングよりも実質的に大きい面です。専用のポート割り当てと端末ごとの転送も必要になり、認証を
間違えたときの帰結は、端末上の何からでもコマンドを受け付けるアプリです。ポーリングが払うレイテンシは
小さく上限もありますが、リスナーが増やす面はどちらでもありません。

**コレクタから独立した、専用の制御サーバを別に立てる。** 上に書いた結合は解けます。シナリオ途中の制御を
望む run が、ネットワークのコレクタを起動しなくて済みます。一方で、正しく作らねばならない認証付き
サーバが 2 つになり、トークン、ループバックへの束縛、ポート衝突の処理、定数時間比較を、もう一度書くことに
なります。コレクタのサーバを再利用するほうが変更は小さく、結合が実際に問題となったなら、エンドポイントを
後から分けるのは限定的な手直しで済みます。アプリ側のコマンド振り分けは、どのサーバが答えたかを気に
しないからです。

**マーカーの座標を報告し、その領域をビジュアル比較から除外する。** アプリはすでに持っている送信経路で
各マーカーの矩形を POST でき、比較はその領域を除外できます。受信方向の経路は要りません。この案は
却下しました。ジェスチャが落ちたまさにその領域で比較を盲目にしてしまい、そこは通常、そのアサーションが
確かめるために存在する領域です。しかも、それを黙って行います。加えて、証跡専用の機能を判定の経路に
載せ、機械的に検査可能なアサーションが何を見てよいかを決めてしまいます。

**シナリオ単位の粒度で留める。** これが現状であり、無価値ではありません。アプリはシナリオごとに、
そのシナリオ自身の起動環境で終了と再起動を経ます。温存したランナーを再利用する経路
（`_resume_warm`、[BE-0291](../BE-0291-xcuitest-runner-reuse-across-scenarios/BE-0291-xcuitest-runner-reuse-across-scenarios-ja.md)）
でもコールドの経路でも同じなので、機能はすでに無償でシナリオごとに変えられます。それでもさらに進める
理由は、動機に挙げた 2 つの事例がどちらも 1 つのシナリオの「内側」にあり、その体験自身が積み上げた
状態こそが試験対象であって、割ってしまうと試験しているものが変わってしまうからです。
