## はじめに

この項目は、側方チャネル（side channel）のユーティリティステップを 2 つ追加します。
[BE-0036](../BE-0036-utility-steps/BE-0036-utility-steps-ja.md) の `http` スライスが出荷されたあとに、
切り出したものです。`totp` は、時刻ベースのワンタイムパスワードをローカルで生成します。`email` は、
テスト用メールボックスをポーリングして受信コードを抽出します。どちらも帯域外の認証値を run に取り込み、
実際のログインフローを自動化できるようにします。

## 動機

実アプリのログインフローは、パスワードを入力するだけで済むことはまれです。多くの場合、UI 自身では
供給できない側方チャネルが必要になります。たとえば、認証アプリからのワンタイムパスワード（OTP）や、
メールまたは SMS で届く二要素認証（2FA）コードです。

`http`（BE-0036）は、HTTP エンドポイントから取得する値をすでにカバーしています。しかし、一般的な 2FA の
ケースの値は、認証アプリや実際の受信箱から来ます。これらの値を取り込む手段がなければ、最も重要な
フロー（サインイン、アカウント検証、パスワードリセット）を決定的に自動化できません。著者には、
2 つの選択肢しかありません。テストビルドで 2FA を無効化すると、実際の経路を検証しなくなります。
値を手で貼り付けると、再現できません。

**競合の文脈（Maestro）。** Maestro は同じニーズを、JavaScript の逃げ道で満たします。コードの計算や
メールボックスのポーリングを、`runScript` / `evalScript` で行います。機能はしますが、ロジックが
レビュー可能な YAML の外、つまり汎用コードに移ります。そのコードがフローに与える影響は、レポートから
は不透明です。[BE-0033](../BE-0033-scenario-variables-control-flow/BE-0033-scenario-variables-control-flow-ja.md)
は、制御フローについて同じトレードオフを回避しました。

Bajutsu の賭けは、目的特化で監査可能な少数のステップ（`totp` / `email`）です。各ステップは値を決定的に
`${vars.*}` へ生成し、シナリオとレポートの中で見えたままにします。違いは、スクリプトの逃げ道と LLM
のどちらも使わずに、ログインフローの能力を提供することです。これにより、ゲートは決定的なまま、フローはレビュー
可能なままになります。

## 詳細設計

既存の `${vars.*}` 名前空間（[scenarios](../../docs/ja/scenarios.md#ランタイム変数-vars)）へ値を
生成するステップを 2 つ追加します。後続の `type` / `assert` ステップは、その値を決定的に消費します。

```yaml
- totp: { secret: "${secrets.TOTP_SEED}", into: { var: code } }   # RFC 6238 の時刻ベース OTP
- type: { text: "${vars.code}", into: { id: auth.code } }
```

```yaml
- email: { match: { to: "test@example.com", subjectMatches: "code" }, extract: { var: code, bodyMatches: "[0-9]{6}" }, timeout: 30 }
- type: { text: "${vars.code}", into: { id: auth.otp } }
```

マッピングと契約：

- **`totp`** はシード（種）から、時刻ベースのワンタイムパスワードをローカルで計算します（RFC 6238）。
  純粋な計算なので、シードとクロックが与えられれば完全に決定的で、ネットワークは不要です。
- **`email`** は、一致するメッセージが届くまでテスト用メールボックス API をポーリングし、コードを
  抽出します。この待機は **`timeout` 必須の条件待機**で、他のすべての待機と同じルールです。固定
  sleep と無限ポーリングは使いません。タイムアウトはステップ失敗です。

シークレット（TOTP シード、メールボックスの認証情報、API のベース URL）は `${secrets.X}` として参照し、
config で宣言します。そのためシナリオファイルが保持するのはトークンだけで、値は保持しません。値は
証跡で自動的にマスクされます。複数シナリオで共有するエンドポイント設定は `targets.<name>` に置きます。

prime directive の保持：

- **run パス上に LLM を置かない。** 各ステップは決定的な計算か、決定的な一致です。`totp` は算術で、
  `email` は正規表現による抽出です。合否判定は引き続き、機械チェック可能なアサーションのみから得ます。
  run／CI ゲートは AI 非依存のままです。
- **決定性。** `email` は、上限のある timeout 付きの条件で待ち、sleep は使いません。`totp` は即時です。
  外部メールボックスが不安定な場合は、黙った誤った値ではなく、きれいなステップ失敗として表面化します。
- **アプリ非依存。** ステップとその配線はアプリをまたいで同一です。異なるのはエンドポイントとシークレット
  だけです。
- **codegen。** これらのステップはアプリではなく bajutsu ランナーで動き、XCUITest 等価物がありません。
  そのため codegen はラベル付き `// TODO` を出力します
  （[BE-0026](../BE-0026-shrink-unsupported-syntax/BE-0026-shrink-unsupported-syntax-ja.md) に従います）。

### email ステップのメールボックス面

`totp` スライスが先送りにした未決の設計点は、`email` が*どのメールボックス*と話すか、でした。決定は、
プロバイダ固有のクライアントではなく **汎用 HTTP ポーリングメールボックス**です。ステップは設定した
エンドポイントを `GET` し、受信箱を JSON で受け取ります。そこから待っているメッセージを絞り込み、
正規表現でコードを抽出します。

この設計は `http` ステップの HTTP 配管（BE-0036）を再利用します。ツールはプロバイダ非依存のままです。
HTTP API で読める受信箱ならどれでも動き、Mailosaur、MailSlurp、チーム自前のテスト用 SMTP-to-HTTP
ブリッジなどが該当します。プロバイダ SDK への依存も増えません。

**設定（`targets.<name>.mailbox`）。** エンドポイントと、そのレスポンスの読み方を config に置きます。
そのためシナリオはアプリ非依存で、認証情報も持ちません。

```yaml
apps:
  myapp:
    mailbox:
      url: "${secrets.MAILBOX_URL}"        # 受信箱エンドポイント（GET）。クエリや box id を含んでよい
      headers: { Authorization: "Bearer ${secrets.MAILBOX_TOKEN}" }
      # このプロバイダの JSON の読み方（レスポンスへのドット区切りパス）。プロバイダ固有コードは不要
      messages: "items"                     # メッセージ配列へのパス（既定：ルートの配列）
      fields: { to: "to", subject: "subject", body: "text", receivedAt: "receivedAt" }
```

既定値は、よくある「`to` / `subject` / `body` / `receivedAt` を持つメッセージの配列」という形に合わせます。
したがって、その形に従う API では `messages` / `fields` のマッピングは一切不要です。マッピングは、
名前の異なるレスポンスをコード変更なしに吸収するためだけに存在します。

**ステップの契約。**

```yaml
- email:
    match: { to: "test@example.com", subjectMatches: "verification" }   # どのメッセージを待つか
    extract: { var: code, bodyMatches: "[0-9]{6}" }                     # 値を vars.code へ取り出す
    timeout: 30
```

- **`match`** はメッセージを選びます。`to`（完全一致）、`subject`（完全一致）／`subjectMatches`
  （正規表現）を AND で組み合わせます。少なくとも 1 つの条件が必要です。何にでも一致する `email` は、
  空のセレクタと同様に、読み込み時に却下します。
- **`extract`** は、一致したメッセージの本文から値を `${vars.<var>}` へ取り出します。`bodyMatches` は
  正規表現で、その **最初のキャプチャグループ**（無ければマッチ全体）が値になります。値は実行時の
  `vars.*` にだけ存在します。記録されるシナリオは、`totp` / `http` の `saveBody` と同様に `${vars.*}`
  トークンを保持するので、値は manifest／レポートに入りません。
- **`timeout`**（必須、秒）はポーリングの上限です。他のすべての待機と同じ条件待機のルールに従い、
  固定 sleep と無限ポーリングは使いません。

**決定性のうち重要な点。**

- **ステップ開始*後*に届いたメールだけを数えます。** ステップは、開始時点に存在した**メッセージ id** の
  集合を記録し、その id を無視します。そのため、以前の run が受信箱に残した古いコードと一致することは
  ありません。判定には、プロバイダの `receivedAt` とローカルの run クロックの比較ではなく、id を使います。
  メールボックスのクロックと runner のクロックが一致している必要がないので、**スキューに強い**設計です。
  プロバイダ id を持たないメッセージには、内容ハッシュの安定 id を与えます。そのため、基準集合でも区別できます。
- **待っているメッセージは一意。** 開始後という境界があれば、想定するのは新着の一致メッセージがちょうど
  1 件の場合です。複数が一致した場合は **`receivedAt` が最新のもの**を採用し、同時刻ならメッセージ id で
  安定にタイブレークします。結果は到着順の競合に左右されません。`receivedAt` は、この順序付けにだけ
  使います。開始後の判定には使いません。
- **上限つきポーリング。** 一致するか `timeout` の期限に達するまで、fetch と判定を繰り返します。これは
  他の待機と同じ条件待機で、固定 sleep ではありません。次の 3 つはいずれも**きれいなステップ失敗**に
  なり、黙った誤った値にはなりません。タイムアウト、`extract` の正規表現が本文に当たらない一致
  メッセージ、2xx 以外の fetch です。

**ゲート検証可能性。** fetch は、注入可能な HTTP 関数（`http` ステップのクライアント、または `RunFn`
風の継ぎ目）の背後に置きます。そのため、ポーリングループ、開始後フィルタ、match／extract、最新優先の
タイブレーク、タイムアウトのすべてを、捏造したメールボックスレスポンスに対してユニットテストできます。
ネットワークは不要です。モックする面はライブの HTTP 呼び出しだけで、許可された「外部 API 呼び出し」の
例外にあたります。`http` のテストのしかたと同じです。

## 検討した代替案

- **テストビルドで 2FA／OTP を無効化し、側方チャネルを丸ごと省く。** 最も単純で、スモークテストには
  十分です。しかし、実際の認証経路を検証しなくなります。その経路は、まさに最もカバーする価値のある
  フローです。唯一の選択肢としては却下します。ビルドがテスト用バイパスを提供することはあってよい
  ですが、ツールがそれを要求すべきではありません。
- **`mocks` で OTP／メールプロバイダをモックする。** `mocks` はアプリ*自身*の送信トラフィックを
  スタブします。したがって、アプリ自身が発行して観測するリクエストでコードが届く場合には機能します。
  値が帯域外のチャネル（認証アプリや実際の受信箱）から来る場合には役立たず、それが一般的な 2FA の
  ケースです。置き換えではなく補完として維持します。
- **すべてを `http`（BE-0036）で済ませる。** `http` はエンドポイントから値を取得します。バックエンド
  発行のトークンはカバーしますが、ローカル計算の TOTP も、ポーリングする受信箱もカバーしません。
  HTTP のケースには引き続き `http` を使い、残りを `totp` / `email` がカバーします。（`email` は内部で
  `http` の HTTP 配管を*再利用*します。そのうえで、一回限りの `http` 取得では表現できないポーリング、
  match／extract、開始後の決定性境界を加えます。）
- **プロバイダ固有のメールボックスクライアント（Mailosaur／MailSlurp の SDK）。** 1 つのプロバイダに
  対しては最速で組めます。しかし、ツールをそのベンダの SDK と API に縛り、2 つ目のプロバイダには 2 つ目の
  クライアントが要ります。却下し、フィールドパスを設定できる汎用 HTTP の面を採ります。汎用の面なら、
  どのプロバイダの JSON 受信箱も依存を増やさず読めます。HTTP 以外の API しか持たないプロバイダも、
  小さなブリッジを前段に置けば扱えます。
- **生の IMAP メールボックスをポーリングする。** テストメール用プロバイダなしに、実際の受信箱へ当たれ
  ます。しかし、IMAP クライアントと認証情報の扱いを抱え込みます。本文を得るための MIME パースも、それ
  自体が一つの面になります。見送ります。HTTP メールボックスが、動機となる 2FA フローの使うテスト
  プロバイダのケースをカバーします。IMAP ソースは、需要が出れば、同じ `email` ステップの契約の背後に
  後から追加できます。

## 進捗

- [x] `totp` ステップ。base32 のシークレットから RFC 6238 のコードを計算して `${vars.*}` に書き込みます（`bajutsu/totp.py`）。デバイスにもネットワークにも触れません。
