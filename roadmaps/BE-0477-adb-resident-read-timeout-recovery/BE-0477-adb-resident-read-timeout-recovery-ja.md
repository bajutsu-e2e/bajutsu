## はじめに

画面の読み取りが一度遅れただけで、Android の実行が常駐 UI Automator サーバーを失うことはなくなりました。常駐 UI Automator サーバーは、画面の読み取りと操作を担うために Bajutsu が端末で動かし続けるインストルメンテーションのプロセスです。これまでは、1回の読み取りがホストの 5 秒の待ち時間を超えると、そのリースの残りがすべて `uiautomator dump` に切り替わっていました。

この項目では、端末側のすべての待ちへ上限を設け、読み取りがホストの待ち時間に収まるようにしました。チャネルを手放す前に読み取りを再試行し、サーバーも再起動します。それでも切り替わった場合は、実行の成果物に記録します。

## 動機

Android の実行では、数回に1回の割合で、途中に次の警告が出ていました。どのシナリオで起きるかは決まっていませんでした。

```text
resident hierarchy read failed (resident channel unreachable on port <port>: timed out); falling
back to 'uiautomator dump' for reads and coordinate injection for gestures, for the rest of this lease
```

そのあとの非 ASCII の `type` ステップは失敗します。`uiautomator dump` の経路では、その文字列を入力できないためです。同じエミュレータで同じシナリオを流し直すと通りました。

原因は、チャネルの両端で待ち時間が食い違っていたことです。`UiDevice.waitForIdle()` は既定で最大 10 秒待ちます。アクセシビリティイベントを出し続ける画面では、上限いっぱいまで待ちます。1回の `GET /source` は、この待ちを 12 回実行していました。

| 場所 | 待ちの回数 |
|---|---|
| `respondSource` の dump の前 | 1 |
| 4 回の安定確認の dump のあいだ | 3 |
| 各 dump の内部（`dumpWindowHierarchy` が 2 回呼ぶ） | 8 |

API 34 のエミュレータで、時計アプリのストップウォッチを動かした画面を使って測定しました。1回の読み取りは、ホストの待ち時間 5 秒に対して 120.9 秒かかりました。サーバーの起動も、200 秒待っても完了しませんでした。

1回の時間切れの代償が大きくなる事情が、ほかに 3 つありました。

- **ドライバが時間切れをチャネルの消失として扱っていました。** サーバーは生きていて処理を続けていても、リースの残りが切り替わりました。
- **単純な再試行では解決しません。** サーバーは1度に1つの接続だけを処理し、ホストが諦めたことを応答を書き込むときまで知りません。そのため新しい接続は、置き換えるはずのリクエストが終わるまで待たされます。
- **こうした画面では、切り替え先の経路は遅いだけでは済みません。** `uiautomator dump` は `ERROR: could not get idle state` で失敗します。測定では、この失敗に 66 秒を費やしたうえで、空のツリーを返しました。

keepalive 接続の再利用も原因の候補でしたが、原因ではありませんでした。`_channel` は例外が起きた接続を必ず破棄します。この振る舞いはテストで固定しました。

この変更のあとは、更新が止まらない画面でも実行は常駐チャネルにとどまり、各読み取りはホストの待ち時間内に返ります。測定した画面の読み取りは約 3.6 秒になったので、読者はこの数値で確かめられます。切り替わった実行は、`manifest.json` にその旨が残ります。

## 詳細設計

### 作業単位 1：待ちの予算

`bajutsu/common/backend_cli/adb_resident/budgets.py` に、両端の数値を置きます。ホストは待ちを伴うリクエストに予算を `budgetMs` として付けて送ります。サーバーは、これより大きい値を求められても自身の既定値を超えません。

| 名前 | 値 | 意味 |
|---|---|---|
| `READ_TIMEOUT_S` | 5.0 秒 | 読み取りに対するホストのソケットの待ち時間（変更なし） |
| `WAIT_BUDGET_MS` | 3,500 ミリ秒 | 1 回のリクエストが端末側で待ちに使える時間 |
| `ACTION_TIMEOUT_S` | 10.0 秒 | `/act` と `/type` に対するホストのソケットの待ち時間（変更なし） |

`waitForIdle` に引数を渡すだけでは足りません。`dumpWindowHierarchy` の内部にある 2 回の待ちには、引数が届かないためです。そこでサーバーの `WaitBudget` クラスは、両方の待ちが参照する `Configurator.waitForIdleTimeout` を設定します。この設定はプロセス全体に効きますが、サーバーは1度に1つのリクエストだけを処理するので問題ありません。

`WaitBudget` は予算を次のように配分します。

- 1 回の idle 待ちは最大 1 秒です。最初の待ちが、読み取りマークの待ちに必要な時間を使い切らないようにするためです。
- dump の内部にある 2 回の待ちは、残りの時間を分け合います。
- 予算を使い切ると、`settled` はそれ以上 dump を取らず、手元のツリーを返します。

これらの上限は待ちを打ち切るだけで、固定時間の sleep には置き換えません。画面が idle になれば、待ちはすぐに解けます。dump は最低 1 回実行され、途中で中断できません。エミュレータでの実際の dump は数十ミリ秒だったので、残りの 1.5 秒には十分な余裕があります。

`POST /act` は、操作を注入する前に同じ予算を使います。操作が届いたあとは、反映の確認に最大 500 ミリ秒、返すツリーに最大 1.5 秒を使います。長押しの時間はホストの待ち時間に加算します。押している間、サーバーは応答できないためです。

`tests/test_adb_resident_budgets.py` が両端の整合を保ちます。ゲートは Kotlin をビルドしないので、テストはサーバーのソースから定数を読み取り、各エンドポイントの待ちが待ち時間に収まることを確かめます。`WaitBudget` の外に `device.waitForIdle()` が増えた場合も、このテストが失敗します。

### 作業単位 2：各段階の所要時間

`WaitBudget` は、各リクエストの時間の内訳を `BajutsuResidentServer` タグでログに出します。

```text
source waits: idle=1074ms dump=2140ms idle=330ms dump=25ms total=3570ms budget=3500ms
```

この行は応答より先に出力するので、ホストが諦めたリクエストでも記録が残ります。予算を使い切ったリクエストは警告レベルで、それ以外はデバッグレベルで出力します。

### 作業単位 3：時間切れからの回復

時間切れでは、`AdbResidentError` の派生クラスである `AdbResidentTimeout` を送出するようにしました。接続の拒否や切断では、これまでどおり親クラスを送出します。`ResidentServer` は両者を次のように扱います。

| 障害 | リースの動作 |
|---|---|
| 時間切れ | 新しい接続で読み直し、次にサーバーを再起動してもう一度読みます |
| ここまでの手順のあとも時間切れ | サーバーを止めて `uiautomator dump` に切り替えます |
| 接続の拒否や切断（どの段階でも） | この項目より前と同じく、サーバーを止めてすぐに切り替えます |

サーバーの再起動は連続 2 回までです。読み取りが 1 回目で答えると、この回数は 0 に戻ります。この上限がないと、再起動したサーバーが 1 回だけ答えてまた固まる場合に、毎回の読み取りが再起動を払い続け、切り替えに到達しません。運用者が停止時の診断を有効にしていれば、リースは再起動の前に端末の状態を取得します。再起動すると、固まったサーバーの状態が失われるためです。

読み取りは端末の状態を変えないので、繰り返しても安全です。切り替える前にサーバーを止めるのは、生きているサーバーの横で dump を取ると空のツリーが返るためです。再起動すると転送先のポートが変わるので、チャネルの各関数は呼び出しのたびにポートを読みます。

再起動したサーバーは、読み取りマークの初期値を端末の現在時刻から取ります。そのため再起動後の最初の読み取りは、待っている操作より新しいものとして扱われます。新しいセッションは操作のあとに dump を取るので、この扱いは正しいものです。

再試行の回数と再起動の可否は、`nativeZ` と同じ場所に置いたターゲットの設定で決めます。

```yaml
driver:
  residentRecovery:
    readRetries: 1   # 0 から 5。既定は 1
    restart: true    # 既定は true
```

### 作業単位 4：非 ASCII の文字列のためにサーバーを立ち上げ直す

dump の経路は読み取りとタップはできますが、非 ASCII の文字列は入力できません。そこで、チャネルを失った状態で非 ASCII の `type` ステップが来たら、先にサーバーを立ち上げ直します。起動に失敗したときだけ、従来のエラーで失敗します。この試みはチャネルを失うごとに 1 回だけなので、以降のステップが失敗する起動の時間を繰り返し払うことはありません。

デバイスグループのドライバは 1 つのサーバーを共有します。そのため、あるドライバの失ったサーバーを、別のドライバが立ち上げ直すことがあります。各ドライバは読み取りの最初にサーバーの状態を確かめ、動いていればチャネルに戻ります。戻るときは失う前の状態を復元するので、古いサーバーに `/act` がないという記録は保たれます。

### 作業単位 5：実行の成果物への記録

ドライバは、任意で実装する新しいプロトコル `ChannelHealthReporter` を通じて報告します。`manifest.json` の `schemaVersion` は 18 になります。

| フィールド | 場所 | 意味 |
|---|---|---|
| `warnings` | 各ステップ | そのステップ中のチャネルの出来事（回復、喪失、復帰） |
| `channel_degraded` | 各シナリオ | シナリオの終了時に dump の経路で読んでいた理由。正常なら空 |
| `channel_notes` | 各シナリオ | 最後のステップのあとにチャネルで起きた出来事 |

切り替え先の経路で通ったシナリオは、`channel_degraded` で見つけられます。判定の経路はこれらのフィールドを読まないので、実行の結果は変わりません（第一原則 1）。

### 制限

- リースの開始時に起動しなかったサーバーは、記録はしますが立ち上げ直しません。立ち上げ直す対象のチャネルをドライバが持っていないためです。作業単位 1 の上限により、この起動の失敗自体は大きく減るはずです。
- 1 回の dump がそれ自体で止まった場合は、中断できないのでホストの待ち時間を超えることがあります。この場合の回復は作業単位 3 が担います。
- 更新が止まらない画面の読み取りは約 3.6 秒かかります。遅くはなりますが、読み取りは成功します。
- 固まったサーバーからの回復には、1 回の読み取りで約 18 秒かかります。内訳は 2 回の時間切れと再起動です。
- ここまでの経路は 1 台の API 34 エミュレータで確かめました。Android の E2E レーンではまだ実行していません。

## 検討した代替案

- **ホストの待ち時間を延ばす。** 最悪値を上回るには 120 秒より長くする必要があり、固まったサーバーがステップをその時間だけ止めてしまいます。ライブラリの既定値が変われば、この値は上限でもなくなります。
- **`waitForIdle` に待ち時間を渡すだけにする。** `dumpWindowHierarchy` の内部にある 2 回の待ちは 10 秒のまま残るので、最初の dump でホストの待ち時間を超えてしまいます。
- **dump を別スレッドで実行し、期限で `503` を返す。** dump も打ち切れますが、後続のリクエストはそのスレッドの終了を待つ必要があります。2 つの走査がぶつかる可能性があるためです。まれに止まる dump には、作業単位 3 がはるかに少ない仕組みで対応できます。
- **予算を両端で別々に定義し、手で揃える。** リクエストで予算を送れば、数値の持ち主はホストだけになります。サーバーの既定値は、予算のないリクエストのためだけに残しています。
- **あらゆるチャネルの障害で再試行する。** 接続の拒否はサーバーが応答できないことを示しています。再試行しても、以降の読み取りがいずれ使う dump への切り替えが遅れるだけです。
