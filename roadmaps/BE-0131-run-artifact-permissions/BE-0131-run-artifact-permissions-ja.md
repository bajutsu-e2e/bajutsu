## はじめに

Bajutsu は、実行の証跡を実行ディレクトリ配下に書き込みます。証跡には、スクリーンショット、アクセシビリティ要素のダンプ、`network.json`、シナリオのコピーが含まれます。このディレクトリは、プロセスのデフォルト umask のまま作成されます。一般的な `022` umask の環境では、ディレクトリは `0755`、ファイルは `0644` となり、同一ホスト上の他アカウントから読める状態になります。

## 動機

`bajutsu/evidence.py` は、実行ディレクトリのツリーを素の `Path.mkdir` 呼び出し（`step_dir.mkdir(parents=True, exist_ok=True)` や `scenario_dir.mkdir(parents=True, exist_ok=True)` など）で作成します。スクリーンショットや要素ダンプ、インターバル録画も、通常のファイル書き込みでツリー内に配置しています。`bajutsu/network.py` が `network.json` へ捕捉した通信を書き出す処理も同様です。

いずれの呼び出しも、明示的な `mode` を渡していません。そのため、実際のパーミッションはプロセスの umask 任せになり、多くの環境ではデフォルトで他ユーザーから読める状態です。

これは、すでに悪用された脆弱性ではなく、ハードニングの抜け穴です。実行の証跡には、Bajutsu が他の箇所で意図的に保護している類の機微な情報が含まれ得ます。

- `network.json` には、リクエスト・レスポンスの本文やヘッダーが載ることがあります。ルールに基づいてマスクはしていますが、マスキングはあくまでベストエフォートの denylist です。あらゆる将来のヘッダーやボディの形を網羅する保証はありません。
- スクリーンショットやシナリオ自体の証跡にも、撮影時点で画面に表示されていた、マスク済みまたは未マスクのテキストが写り得ます。

深刻度は中程度です。実行ディレクトリを読むには、同一ホスト上の別アカウントが必要です。ただし、共有 CI ランナーはまさにその隣接関係が起こり得る環境であり、BE-0032 がログに対してすでに防いでいるのと同じ脅威モデルです。

## 詳細設計

書き込む内容や合否判定の仕組みには手を加えず、ランナーが証跡を作成する際のパーミッションだけを絞ります。

- 実行ディレクトリのトップレベルを、最初に作成する時点で `0700`（所有者のみ読み書き実行可）にします。これにより、配下のすべてのパスが、世界読み取り不可な親ディレクトリを継承します。
- 機微な内容を含み得るファイルは、書き込み時点で `0600`（所有者のみ読み書き可）にします。対象は、`network.json`、コピーしたシナリオ、アクセシビリティ要素ダンプ（`elements.json`）、スクリーンショットです。ディレクトリのパーミッションだけでアクセスを制限するのではなく、ファイル単位でも制限します。
- バックエンド間で統一して適用します。idb と Playwright はどちらも同じ `evidence.py` / `network.py` の経路で書き込むため、修正はドライバごとではなく、共有のランナーコードに一度だけ入れます。
- 移植性を保ちます。`Path.mkdir(mode=...)` や明示的なモード付きの `os.open`（あるいは作成直後の `os.chmod`）は、macOS と Linux で同じように動作します。決定的ゲートが必要とする範囲は、これで足ります。

## 検討した代替案

- **コードで強制する代わりに umask の要件をドキュメント化する。** 却下しました。この方法は、すべての運用者・CI イメージが適切に厳しい umask を設定していることに依存します。これは、Bajutsu が他の箇所で避けている「ホストの周辺設定に依存する」種類の前提そのものです。作成時にモードを強制すれば、この保証は無条件に成り立ちます。
- **証跡を保存時に暗号化する。** 過剰な対策として、却下しました。ここでの脅威は、世界読み取り可能なファイルを別のローカルアカウントが読むことであり、ディスクの盗難ではありません。ファイルモードの制限であれば、鍵管理などの複雑さを増やさずに、この脅威へ直接対処できます。
- **パーミッションを制限する代わりにマスキングをより積極的に行う。** 代替ではなく補完だと考え、却下しました。マスキングは、漏えいした証跡が明かす内容を減らせます。しかし、あらゆる機微な値を網羅できる保証はなく、証跡を読める人を制限する必要性そのものはなくなりません。

- [x] 新規実行で作成した実行ディレクトリと機微なファイルが制限されたモードになっていることを
      検証するテストを追加する（`tests/test_artifact_perms.py`、`tests/runner/test_pipeline.py`、
      `tests/test_evidence.py`）。

- `bajutsu/artifact_perms.py`（`make_run_dir` / `restrict_file`。書き込み後に chmod するため
  モードは umask に依存しません）を新設し、共有のランナーコードから呼び出しました
  （run ディレクトリと `scenario.yaml`、`network.json` は `runner/pipeline.py`、スクリーンショットと
  `elements.json` は `evidence.py`）。これにより idb と Playwright を一度の実装で保護します。
  振る舞いは `docs/evidence.md` とその日本語版に記載しました。
- レビュー対応（PR #630）: `elements.json` も制限対象に加えました（アクセシビリティダンプは本項目の
  対象範囲です）。run ディレクトリを CLI ディスパッチの時点で、デバイスプールが配下に何かを作成する前
  （Playwright の `_video_tmp` など）に所有者のみで作成し、世界読み取り可能なウィンドウをなくしました。
  さらに `make_run_dir` でシンボリックリンクの run ディレクトリを拒否します（run id は予測可能な
  タイムスタンプのため、書き込み可能な runs ディレクトリでは `chmod` を別の対象へ誘導され得ます）。
