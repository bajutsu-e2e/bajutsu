## はじめに

`IdbDriver`（`bajutsu/drivers/idb.py`）と `AdbDriver`（`bajutsu/drivers/adb.py`）は、座標ベースの
デバイスバックエンド二つです。どちらもデバイスからアクセシビリティツリーをダンプし、`Element` へ
正規化します。どちらも、解決したフレームの中心をタップして操作します。

この二つのファイルは、決定性に直結する読み取り経路も共有しており、共有部分はほぼ一字一句同一です。
一時的な空ツリーへのリトライ、安定待ちのループ、安定キーへの射影、未検出時の解決ループが対象です。

本項目は、この共有ロジックを一つの基底クラス `CoordinateTreeDriver` へ抽出します。各バックエンドは、
自分のツリー取得方法とアクチュエーターだけを供給します。

## 動機

二つのバックエンドには、90 行ほどのほぼ一字一句の重複があります。重複しているのは、ドライバ層の
なかで決定性がもっとも重要な部分です。読み取った直後のツリーが本物の画面なのか、デバイスの遷移途中に
生じた一時的なものなのかを判断するロジックだからです。

- 6 つのチューニング定数のうち 5 つは、値もコメントも同一です。対象は `_READY_MIN`、
  `_EMPTY_RETRIES`、`_EMPTY_BACKOFF_S`、`_EMPTY_BACKOFF_MAX_S`、`_SETTLE_MAX_POLLS` です
  （`bajutsu/drivers/idb.py:213-218`、`bajutsu/drivers/adb.py:202-215`）。
  残る `_SETTLE_POLL_S` はその後乖離しており、idb は `0.05`、adb は `0.0` です。BE-0234 で、adb の
  約 2.4 秒の読み取り自体がループを律速するため、adb の poll を 0 に調整しました。そのため共有基底では、
  この 1 つだけをバックエンドごとの値として残します。
- 型エイリアス `_StableKey` も同一です（`bajutsu/drivers/idb.py:24`、`bajutsu/drivers/adb.py:64`）。
- `query()` のリトライループは、包んでいる describe 呼び出しを除いて一字一句同一です
  （`bajutsu/drivers/idb.py:229-246`、`bajutsu/drivers/adb.py:248-263`）。
- `_is_transient_empty`、`_empty_backoff`、`_settle`、`_stable_key`、`_resolve` は、いずれも
  同一のロジックです。`AdbDriver._settle` のドキュメンテーション文字列は「idb's logic」と書いており
  （`bajutsu/drivers/adb.py:292-311`）、重複の存在を自ら認めています。

ロジックが重複したままだと、一時的な空ツリーの判定への修正を二度行う必要があります。たとえば、
バックオフの上限を締め直す修正や、新しいフレーキーな挙動の判明後に `_READY_MIN` を調整する修正です。
修正は二つのファイルに入り、どちらかのバックエンドを触った人が加えます。二回目の修正を強制する仕組みは
ありません。二つの読み取り経路は、静かに乖離するおそれがあります。その結果、アプリ側の事情と無関係に、
あるシナリオが iOS と Android で異なる挙動を示す事態も起こり得ます。

これはドライバ層で最大の、もっとも正しさに直結する重複です。一箇所へ引き上げれば、「二重に直すことを
忘れない」が「一度直せば両方のバックエンドが引き継ぐ」に変わります。

## 詳細設計

作業は挙動を変えない純粋な引き上げで、独立した単位に分けられます。

1. **`bajutsu/drivers/` に `CoordinateTreeDriver` を導入する。** `base.py` と並ぶ独自のモジュール、
   たとえば `coordinate_tree.py` に置きます。現時点で同一のものは、すべてここに持たせます。
   - 共有する 5 つのチューニング定数（`_SETTLE_POLL_S` はバックエンドごとの値のままにします）
   - `_StableKey` エイリアス
   - `query()`、`_settle`、`_stable_key`、`_is_transient_empty`、`_empty_backoff`、`_resolve`

   これらは現状、コンストラクタが管理する状態（`_max_seen`、`_last_stable_key`）を閉じ込めています。
   そのため、この状態も基底クラスが持ちます。
2. **基底クラスに、抽象フックを一つだけ与える（`_describe()`）。** 手順 1 の処理は、すでにいずれも
   `_describe()` を呼び出しています（`idb.py:285-286`、`adb.py:265-266`）。これを抽象メソッド
   （または `NotImplementedError` を送出するスタブ）にすることが、共有ロジックとバックエンド固有の
   argv・パース処理とのあいだの唯一の境界です。各サブクラスは、自分の describe だけを実装します。
   - idb：`ui describe-all` と JSON パース（`parse_describe_all`）
   - adb：`uiautomator dump` と XML パース（`parse_hierarchy`）
3. **`IdbDriver` と `AdbDriver` を基底クラスの子クラスに付け替える。** それぞれから共有部分を削除し、
   本当にバックエンド固有のものだけを残します。
   - idb：tap・swipe・text の argv ビルダーと、gRPC 経由のコンパニオン text 処理
   - adb：スクロールしての表示範囲内取得のリトライ（`_scroll_into_view` と `_scroll_toward`。
     idb には対応する処理がありません）、sendevent によるダブルタップ処理、自分のアクチュエーター

   `_resolve` は共有のまま残します。adb の `_resolve_frame_and_screen` は、`_resolve` の上に
   スクロールしての表示範囲内取得を重ねています。この層は adb 固有であり、共有の `_resolve` を
   重複させずに組み合わさっています。
4. **`XcuitestDriver` と `PlaywrightDriver` には手を入れない。** どちらも自分の読み取りモデルを
   持っています。XCUITest はネイティブの条件待ち機能、Playwright は DOM クエリです。どちらにも、
   一時的な空ツリーや安定待ちに相当するヒューリスティックはありません。この引き上げの対象外であり、
   新しい基底クラスへ無理に載せるべきではありません。
5. **両方のバックエンドで共有の挙動が同一であることを確認するテストを追加する。** 対象は次の三つです。
   - 一時的な空ツリーへのリトライ（劣化したツリーの後に、より豊かなツリーが続く場合）
   - 指数バックオフのスケジュール
   - 安定待ちループのキャッシュヒットとキャッシュミスの経路

   テストは、`IdbDriver` と `AdbDriver` のフェイクをまたいでパラメータ化します（あるいは別の形で
   共有します）。基底クラスへの将来の変更を、各ドライバが持つテストのコピーではなく、両方の
   サブクラスに対してまとめて検証するためです。

決定性についての補足です。この引き上げは、`_resolve` の意味を変えません。一意な一致が必要であり、
曖昧な一致（2 件以上）は `AmbiguousSelector` によって即座に失敗します。本項目はコードを移動する
だけで、「見つかった」「曖昧である」の意味は変えません。どちらのバックエンドの読み取り経路についても、
既存のテストは変更なしに新しい基底クラスに対して通るはずです。この結果が、引き上げで挙動が保たれた
ことの裏付けになります。

## 検討した代替案

- **基底クラスではなくミックスインにする。** 共有する状態とメソッドは、どちらの形でも持たせられます。
  ミックスインなら、`IdbDriver` と `AdbDriver` が将来別の基底クラスと組み合わせる必要が生じたときに
  柔軟です。本項目は素直な基底クラスを選びます。抽象フック `_describe()` は、ミックスインの契約より
  「サブクラスが完成させるテンプレートメソッド」として自然に読めるからです。将来、多重継承が明らかに
  有利になる事情が生じれば、ミックスインも妥当な代替案です。
- **規約によって重複の乖離を防ぐ（お互いを指すコメントを置くだけ）。** 却下しました。これはまさに
  現状そのものです。`AdbDriver._settle` のドキュメンテーション文字列は、すでに「idb's logic」という
  コメントレベルの言及を持っています。本項目が問題視する乖離のリスクは、規約だけでは、共有基底クラス
  のようには二回目の修正を強制できない点にあります。
- **重複を残したまま、バックエンド横断のテストだけを追加する。** 却下しました。テストは事後的に
  乖離を検出できますが、乖離の原因である二重修正の負担は取り除けません。引き上げとテストは、代替では
  なく補完の関係にあります。詳細設計の手順 5 で、テストを別項目に切り出さず本項目に含めているのは
  このためです。

### 詳細設計からの乖離（実装時に判明）

「動機」節は 2026 年 7 月に書かれた時点で、`_settle` を二つのドライバのあいだで一字一句同一だと説明
していました。しかし実装時点では、adb の `_settle` は壁時計の締め切り（`_SETTLE_DEADLINE_S`）へ変更
済みで、idb は固定回数のポーリング（`_SETTLE_MAX_POLLS`）のままでした。チューニング定数が乖離した
だけではなく、挙動そのものが異なる状態です。

提案どおりに `_settle` を引き上げると、一方のバックエンドをもう一方の戦略へ合わせることになります。
それは「挙動を変えない純粋な引き上げ」という前提に反するため、`_settle` はバックエンドごとに残しました。

詳細設計のそれ以外の要素は、計画どおりに引き上げました。対象は、残り 4 つの共有定数、`_StableKey`、
`query()`、`_stable_key`、`_is_transient_empty`、`_empty_backoff`、`_resolve` です。`wait_for` も
一字一句同一だったため、同じ作業のなかで引き上げました。どちらのバックエンドの読み取り経路についても、
既存のテストは変更なしに新しい基底クラスに対して通っています。
