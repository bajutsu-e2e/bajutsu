## はじめに

AI が自律的に画面遷移をクロールして画面マップを生成し、クラッシュと到達不能な状態を報告します。[Tier 1](../../docs/ja/glossary.md#2-つの層) の `record` 機能を拡張します。

`record` は*目的指向*です。1 つの自然言語ゴールに向かって AI が探索し、1 本の決定的シナリオを書き出します（[recording.md](../../docs/ja/recording.md)）。`crawl` は*幅優先*です。到達できる画面をできる限り体系的に巡り、画面と画面間の遷移のグラフを構築して、見つけたものを報告します。これは探索と発見のためのツールであって、合否ゲートには決してなりません。

## 動機

現在のオーサリング経路は、「テストしたいフローをすでに知っている」ことを前提にしています。`record` にゴール（「ログインして設定を開く」）を渡せば、その経路のシナリオが得られます。書くべき内容が分かっている段階では正しい道具です。ただし 3 つの空白が残り、クロールがそれを埋めます。

**1. オーサリング前の発見。** 新しいアプリのオンボーディングには、per-app の [`apps.<name>`](../../DESIGN.md) config と [BE-0024 doctor / onboarding](../BE-0024-doctor-onboarding/BE-0024-doctor-onboarding-ja.md) が関わります。ここで最も難しい問いは、「そもそもどんなフローが存在し、どの画面をテストする価値があるのか」です。今は、この問いに手作業でアプリを読んで答えるしかありません。クロールは画面マップを生成します。到達できる各画面の代表スクリーンショットと要素ダンプを添えた、ラベル付きの一覧です。マップは、「アプリを知らない」を「40 画面ある、どれにシナリオを書くか選べ」に変えます。これは `record` の自然な入口です。発見された各画面と、そこへの最短経路が、そのままシード（種）となるゴールになります。

**2. アプリ全体のカバレッジ計測。** [DESIGN §7.2](../../DESIGN.md) は、`doctor --app` がアクセシビリティ識別子のカバレッジを、入口画面と宣言済み deeplink で開ける画面に限って計測すると明言しています。さらに、`doctor --app <name> --from <runId>` モードをすでに想定しています。このモードは、過去の run が残した画面ごとの `elements` ダンプを再利用して、アプリ全体のカバレッジを正直に算出します。クロールは、そのダンプを生み出す run そのものです。§7.2 の「測定範囲の正直さ」という約束を実体化します。カバレッジは、推測ではなく、クロールが実際に到達した全画面に対して算出できます。

**3. 堅牢性のスモークテスト。** 体系的なクロールは、手書きした数本のハッピーパスよりはるかに広くアプリを操作します。シナリオテストが決して訪れないクラッシュ、ハング、行き止まりが表面化します。これが「App Explorer / Robo test」的な価値で、本項目の由来である Autify VAX の価値です。「*この*順序で*あれ*を押すとアプリが落ちる」を、ユーザーより先に捕まえます。安価で広範で、オーサリングが要りません。

**この機能を Bajutsu で行う意義は、決定性の境界そのものにあります。** クロールは本質的に非決定的です。探索順序も AI の選択もアプリの状態も、run ごとに変わります。そのため、クロール自体が CI ゲートになることは決してありません（[prime directive #1](../../CLAUDE.md): *AI は著者であり失敗時の調査役であって、判定者ではない*）。汎用のモンキーやエクスプローラに対して Bajutsu が加える価値は、クロールの*副産物*が一級の決定的シナリオである点です。クラッシュの再現経路と、発見した各フローを、プレーンな YAML として書き出します。ユーザーがその YAML をレビューし、コミットすれば、`run` が AI なしで [Tier 2](../../docs/ja/glossary.md#2-つの層) の回帰として再実行できます。したがって、クラッシュは CI に*届きます*。フレーキーなクロールとしてではなく、コミット済みの再現シナリオとして届きます。これはツールの他の部分と同じハブモデルです。シナリオが共有の成果物であり、AI が一度だけ書き、以後は決定的ランナーが所有します。

## 詳細設計

### コマンド面

`record` のフラグに倣った、新しい Tier 1 コマンドです。

```
bajutsu crawl --app <name>
    [--max-screens N] [--max-steps N] [--budget DURATION] [--max-depth N]
    [--seed <deeplink> ...]          # 起動画面以外の追加の入口
    [--guide ai|off]                 # AI で優先度付け/入力補完するか
    [--backend idb] [--udid booted] [--dismiss-alerts]
    [--out runs/<runId>]
```

`record` と同様に、`crawl` は *AI ライブ*の経路であり、決定的ゲートの一部ではありません（[DESIGN §3.1](../../DESIGN.md)）。`--guide off` なら、クロールは後述の識別子駆動ヒューリスティックだけで動き、`ANTHROPIC_API_KEY` を必要としません。`--guide ai` は、その上に任意のエージェントを重ねます。いずれにせよ、AI が合否を決めることはありません。

### 状態モデル

グラフのノードは状態です。クロールが訪れる各画面は**状態フィンガープリント**へ縮約され、同じ画面の再訪を、再探索ではなく「認識」できるようにします。フィンガープリントは `driver.query()`（[`drivers/base.py`](../../bajutsu/drivers/base.py)）から導きます。

- **主：** 画面上に存在する `accessibilityIdentifier` の集合をソートしてハッシュ化したもの。識別子は非ローカライズかつデータ由来（[DESIGN §7.3](../../DESIGN.md)）なので、このフィンガープリントは locale や軽微な内容差に対して安定します。id ベースのセレクタを決定的にする性質が、id ベースの状態同定も決定的にします。
- **フォールバック（id が乏しい画面）：** id を持つ要素が少なすぎる場合、クロールは操作可能要素の `(traits, frame バケット)` に対する構造ハッシュへフォールバックします。このハッシュは安定性が下がるため、stability ladder の正直さの規約（[DESIGN §5](../../DESIGN.md)）に倣って report に明示します。

フィンガープリントがグラフのノード識別子です。各ノードは、代表スクリーンショット、`elements` ダンプ、id 集合を保持します。これらは、§7.2 が必要とする画面ごとの成果物そのものです。

### フロンティアとアクション選択

グラフのエッジはアクションです。ある状態からの**候補エッジ**は、その操作可能要素、つまり `button` / `link` / `textField` / `searchField` の traits を持つ要素です。`id` を持つ要素を優先します（stability ladder, [DESIGN §5](../../DESIGN.md)）。クロールは、未探索の `(状態, アクション)` 対のフロンティアを保持し、幅優先で巡回します。1 状態内の候補順序は決定的で、id でソートします。そのため、変更のないアプリを 2 回クロールすると、アプリ自身の非決定性が許す限り、同じ順序で探索します。これは、得られるマップの再現性のために重要です。

テキストフィールドには入力値が要ります。`--guide off` では、trait ごとに固定の安全なプレースホルダを使います。`--guide ai` では、任意のエージェントが文脈に合った入力を供給します。後述のとおり、これも Tier 1 のままです。

### その場での後戻りではなく、決定的リプレイによる巡回

アプリの遷移は通常は不可逆です。タップを確実に「元に戻す」ことはできません。逆方向にナビゲートするとフレーキーになるため、クロールはそれを試みません。クロールは、`run` が任意の状態へ到達するのと同じ方法で、フロンティアのノードを再訪します。**クリーン環境へ erase し、そのノードへの既知の最短経路をリプレイします**（[DESIGN §2](../../DESIGN.md) 環境のクリーン化、[`simctl.py`](../../bajutsu/simctl.py) の erase/boot/launch）。

各エッジは記録済みの `Step` なので、入口画面から発見済みノードへの経路は、*それ自体が決定的シナリオ*です。リプレイにはオーケストレータの `_do_action` / `_wait`（[`orchestrator.py`](../../bajutsu/orchestrator.py)）を再利用し、ノードに着地します。クロールは、そこから次の未試行アクションを取ります。これにより、巡回全体を、ツールがすでに持つ決定性フレンドリなプリミティブの上に保てます。すべてのノードには、コミット可能でリプレイ可能な到達経路が、最初から付随します。

アクション間は、条件待機（`screenChanged` / 対象要素）で待ち、固定 sleep は使いません（[DESIGN §6.3](../../DESIGN.md)）。

### クラッシュと行き詰まり状態の検出

各アクションの後、クロールは、アプリが健全であることを決定的に確認し、見つけた状態を次の 3 つに分類します。

- **クラッシュ：** アプリプロセスが、もはやフォアグラウンドにないか、生存していない状態です。`simctl`/env の pid チェックで確認します。a11y ツリーが、アプリ内容のない素のウィンドウに collapse した状態も含みます。この状態とシステムアラートは、[`record.py`](../../bajutsu/record.py) の `_shows_app_ui` を再利用して区別します。システムアラートは、既存のアラートガードが代わりにクリアします。クラッシュ時は、既存の `result:error` 安全網（[DESIGN §9](../../DESIGN.md)）で全証跡を取得します。そのうえで、リプレイした経路を**最小の再現シナリオ**として書き出します。
- **行き詰まり / 行き止まり：** 操作可能要素がない状態、または、条件待機の予算内でどの候補アクションも画面変化を起こさない状態。
- **到達不能：** *期待された*のに到達されなかった状態。期待の出どころは 2 つです。1 つは宣言済み deeplink で、開くのに失敗した `--seed` や config の deeplink です。もう 1 つは、アプリが宣言した id 名前空間（[DESIGN §7.3](../../DESIGN.md)）のうち、その画面がマップに一度も現れなかったものです。これらは失敗ではなく空白として報告します。

これらの分類は、いずれも LLM の判断ではありません。クラッシュはプロセスの事実です。「行き詰まり」は、「どのエッジも状態フィンガープリントを変えなかった」ことです。「到達不能」は、宣言済みと観測済みの集合差です。AI は判定に関与しません。

### 任意の AI レイヤ

`--guide ai` のレイヤは、厳密に Tier 1 です。クロールは、AI が一切なくても有用です。このレイヤを有効にした場合、エージェント（既存の [`Agent` プロトコル](../../bajutsu/agent_protocols.py)の拡張）は*探索を導く*だけで、結果を評価することは決してありません。

- **フロンティアの優先度付け：** 候補アクションを関心度（例：「概要」より「購入手続き」）で並べ替えます。単純な幅優先の代わりに、限られた予算を有効に使います。
- **現実的な入力の供給：** テキストフィールドに、妥当そうなメールアドレスや検索語を入れます。
- **近重複状態の併合：** 構造フィンガープリントなら分けてしまう状態（例：行がデータ違いだけのリスト）をまとめます。

このレイヤは、`record` の基盤（`_screenshot_bytes`、アラートガード周り、`_execute_with_recovery`）を直接再利用します。境界は堅固です。エージェントは*何を探索するか*に影響します。*何が起きたか*は、上記の決定的チェックが決めます。

### 出力

すべては、既存の `manifest.json`（[DESIGN §9](../../DESIGN.md)）と並んで `runs/<runId>/` 配下に出ます。

- **画面マップ：** `screenmap.json`（ノードとエッジ）に加え、`report.html` にレンダリングしたグラフ（Mermaid/Graphviz）。各ノードは、スクリーンショットと `elements` ダンプにリンクします。
- **クラッシュレポート：** 各クラッシュと、その再現 `Scenario`。`dump_scenarios` で YAML として書き出し、`run` で直接実行できます。
- **候補シナリオ：** 発見したフローごとに、ユーザーが本物のテストへ昇格できる下書きシナリオ。すべての AI オーサリングと同様に、これらは人間レビュー用の*提案*として出します。コミット済み YAML に黙って書き込むことはしません（[DESIGN §6.5](../../DESIGN.md)）。
- **カバレッジ供給：** `doctor --app <name> --from <runId>` がアプリ全体のカバレッジに使う、画面ごとの `elements` ダンプ（[DESIGN §7.2](../../DESIGN.md)）。

### 他項目との関係

- **`record`**（[recording.md](../../docs/ja/recording.md)）：クロールは幅優先の補完であり、発見した画面が `record` のゴールのシードになります。両者は、ループ、アラート処理、証跡周りを共有します。
- **[BE-0012 アクションキャプチャ record](../BE-0012-action-capture-record/BE-0012-action-capture-record-ja.md) / [BE-0014 record の切り分け](../BE-0014-record-demarcation/BE-0014-record-demarcation-ja.md)：** これらの項目は、*人間駆動*のキャプチャと、AI `record` からの切り分けを扱います。クロールは第 3 の、完全に自律的なオーサリング入口であり、それらと並べて切り分けるべきです。
- **[BE-0024 doctor / onboarding](../BE-0024-doctor-onboarding/BE-0024-doctor-onboarding-ja.md)：** クロールは、doctor の §7.2 計測が必要とするアプリ全体カバレッジの入力を供給します。

## 検討した代替案

**純粋なランダム「モンキー」テスト**（Android Monkey や UIAutomation のファジングのようなランダムタップ）。作るのは容易で、クラッシュのあぶり出しは得意です。ただし、きれいな画面マップを生まず、id の安定性を尊重せず、経路が再現できません。そのため `record` や `doctor` に供給できず、決定的な再現も書き出せません。体系的な id 駆動の幅優先巡回を優先します。ランダムなファズモードは、識別子がほぼない座標専用アプリ向けのフォールバックとしてのみ、残す価値があります。

**純粋な AI 自由探索**（「すべて探索して」のような曖昧なゴールで `record` をそのまま再利用）。LLM は、明示的な状態グラフを持たずにターンごとにさまよいます。ループし、再訪し、重複排除もカバレッジ計測もできません。遅く、高価でもあります。クロールには、明示的な状態モデルとフロンティアが必要です。AI は、その上の*任意のガイド*であってエンジンではなく、いずれにせよ結果からは排除されます。

**クロール自体を CI / Tier 2 ゲートにする**（「クロールがクラッシュを見つけたらビルドを落とす」）。クラッシュ検出は決定的なので、魅力的な案です。ただし、クロールの*経路*は非決定的です。フレーキーで変化するクロールを必須ゲートにするのは、determinism-first に反します（[DESIGN §2](../../DESIGN.md)）。解決策は次のとおりです。クロールは Tier 1 の発見にとどめます。書き出した再現シナリオが、人間レビューを経て Tier 2 ゲートになります。これは通常の `record → run` 昇格です。クラッシュは、クロールとしてではなく、コミット済みシナリオとして CI に届きます。

**アプリのバイナリやソースの静的解析**で、実行せずに画面マップを作ります。スコープ外です。Bajutsu はアプリ非依存で、ビルド成果物だけを受け取ります（[DESIGN §1](../../DESIGN.md)）。また、静的解析では、価値の半分であるランタイムクラッシュを見つけられません。
