## はじめに

web（Playwright）[バックエンド](../../docs/ja/glossary.md#driver-backend-actuator-platform)は、常にデスクトップの
ブラウザを駆動します。どのコンテキストも、素の `browser.new_context(reduced_motion="reduce")` です。
既定のデスクトップ viewport を使い、タッチ入力はなく、`is_mobile` は false です。そのため、テスト対象の
web アプリが目にするのは、デスクトップのレイアウトとデスクトップの入力だけです。チームがテストしたい挙動が
モバイルのものであっても、同じです。

本提案は、ターゲット単位の**デバイスモード**を追加します。viewport、`is_mobile`、`has_touch`、デバイス
スケール、ユーザーエージェントによる、デスクトップまたはモバイルのエミュレーションです。web
[ターゲット](../../docs/ja/glossary.md#target-app-device)を、どちらとしても駆動できるようになります。
Playwright に組み込まれたデバイスエミュレーションを使います。

## 動機

レスポンシブな web アプリは、スマートフォンで異なる挙動を示します。レイアウトが変わり、上部ナビゲーションの
代わりにハンバーガーメニューが出ます。タッチスクロールやタッチ専用のジェスチャーが使われ、ユーザー
エージェントもモバイルのものになります。Bajutsu は今でも web を駆動できますが、デスクトップの顔だけです。
「このターゲットを iPhone としてテストする」と指定する方法がありません。しばしば主となるモバイルの体験が、
他の点では対応しているバックエンドの上で、ツールの手の届かないところに置かれています。

このギャップは、別の箇所での正しい修正も妨げます。対になる **web-swipe-scroll-fidelity** 項目は、ブラウザの
入力モードで分岐して `swipe` をスクロールさせます。デスクトップのポインターコンテキストでは wheel
スクロール、タッチコンテキストではタッチドラッグです。この分岐は `has_touch` で決まります。しかし、
タッチコンテキストを設定する方法がなければ、デスクトップ経路しか実行されません。

本項目は、モバイル（タッチ）モードを供給します。これでタッチ経路が実際に動くようになります。両項目が
合わさって、web の `swipe` にデスクトップとモバイルの双方で正しい挙動を与えます。

Playwright は、この仕組みをすでに備えています。`playwright.devices["iPhone 13"]`（ほかも同様）は、
viewport、`device_scale_factor`、`is_mobile`、`has_touch`、`user_agent` をまとめたプリセット記述子で、
`new_context` に適用します。作業は、この仕組みを決定的でアプリ非依存の設定として露出し、バックエンドの
コンテキスト生成に通すことです。エミュレーションを発明するわけではありません。

先に述べておくべきスコープの境界があります。本項目は、デスクトップ級のブラウザ（Chromium、Firefox、
WebKit）で、モバイルの viewport とタッチ入力を用いるエミュレーションです。Chrome DevTools のデバイス
ツールバーが行うのと同じものです。実機のモバイルブラウザやデバイスクラウドでは**ありません**。それらは
[DESIGN §1](../../DESIGN.md) とロードマップの「クラウドデバイスファーム」の非対象方針のとおり、スコープの
外にとどまります。本物のモバイル OS が必要な場合の経路は、Android バックエンド（BE-0007）です。本項目は
あくまで、web ターゲットのレンダリングと入力のモードに関するものです。

## 詳細設計

web ターゲットの設定に**デバイスモード**を追加し、Playwright バックエンドがブラウザコンテキストを生成する
ときに適用します。

**設定。** web ターゲットに任意のデバイス設定を持たせ、既存の設定の階層化（`bajutsu/config.py`）を通して
解決します。自然な形は、Playwright 自身のモデルに倣います。次の 2 つの形のいずれかを取ります。

- **名前付きデバイスプリセット**（例：`device: "iPhone 13"`）。`playwright.devices` に対して解決します。
  プリセットは、viewport、`device_scale_factor`、`is_mobile`、`has_touch`、`user_agent` に展開されます。
- 任意の viewport を伴う、明示的な**デスクトップ／モバイルのモード**。特定の機種を固定せずに、素のデスクトップ
  や汎用的なモバイルのコンテキストが欲しいチームのためのものです。

既定は**デスクトップ**で、今日から変わりません。既存の web シナリオは、今とまったく同じように動き続けます。

キー名の具体は、PR で詰める実装の細部です。プリセットと明示フィールドを 1 つの設定に同居させるかも同じです。
制約は、この設定がシナリオ単位やステップ単位ではなく、ターゲット単位（アプリ非依存）の設定であることです。

**コンテキスト生成。** `PlaywrightDriver._new_context` とスターターの初回コンテキストが、解決したデバイス
記述子を、既存の `reduced_motion="reduce"` と並べて `new_context(**kwargs)` の呼び出しにマージします。
リローンチ（BE-0077）と `reset_context`（クロールのクリーンな起点）は、同じ記述子を組み直します。そのため、
モードはブラウザのライフサイクル全体を通して安定します。`reduced_motion` と選択したエンジン（BE-0076）が
すでに守っているのと同じ不変条件です。

**入力との関係。** コンテキストが `has_touch` を true にして生成されれば、web-swipe-scroll-fidelity の
振り分けが、自動的に `swipe` を Chrome DevTools Protocol (CDP) のタッチドラッグへ通します。そこに
さらなる変更は要りません。本項目の責務は、正しく設定されたコンテキストを生み出すところまでです。その
コンテキストの中でジェスチャーをどう実現するかは、対になる項目のものです。

**ケイパビリティとプリフライト。** バックエンドのケイパビリティ集合とプリフライト（BE-0082）を見直し、
モバイルコンテキストが実際にできることを表明するようにします。`run`／CI の判定経路は変わりません。

作業分解（MECE）：

1. **設定の露出**：web ターゲット設定（`bajutsu/config.py`）にデバイスモードの設定を追加し、デスクトップを
   既定にします。設定は検証し、不明なプリセットには明確なエラーを返します。
2. **記述子の解決**：プリセット名を `playwright.devices` に対して解決します。明示的なデスクトップ／モバイルと
   viewport から、記述子を組むこともできます。設定の import が Playwright を import しないよう、遅延で
   行います。
3. **コンテキストへの配線**：記述子を `_new_context` とスターターの初回コンテキストに適用し、
   `reset_context` と `relaunch` をまたいで保ちます。
4. **ケイパビリティとプリフライトの見直し**：表明するケイパビリティとプリフライトが、モバイルコンテキストで
   正しいことを確認します。
5. **テスト**：プリセットの解決、デスクトップ既定（挙動不変）、記述子を載せたコンテキストの kwargs、
   reset と relaunch をまたいだ安定性を確認します。
6. **ドキュメント**：`docs/configuration.md` と `docs/drivers.md`（と日本語ミラー）にデバイスモードを記します。
   モバイルモードが実機ではなくデスクトップブラウザのエミュレーションである点も、明記します。

以下のとおり、いずれもプライムディレクティブの範囲内です。

- **決定性。** デバイス記述子は、コンテキスト生成時に適用される固定的なデータです。モデルには問い合わせず、
  `run`／CI ゲートには手を触れません。エミュレーションは、今日の固定デスクトップコンテキストと同じく再現
  可能です。viewport とスケールを固定の数値に定めるので、レンダリングされるレイアウトも実行のたびに再現
  できます。ウィンドウサイズが変わりうる実機よりも、むしろ安定します。
- **アプリ非依存。** モードはターゲット単位の設定で、設定がすでにターゲットごとの差分をモデル化している
  場所（`targets.<name>`）そのものです。ドライバーとランナーの形は変わりません。

## 検討した代替案

- **シナリオ単位・ステップ単位の viewport。** シナリオが実行の途中でデバイスモードを切り替えられると、同じ
  シナリオがステップごとに違う意味を持ちます。アプリ非依存の境界も曖昧になります。デバイスは、個々の
  アクションの性質ではなく、ターゲットをどう駆動するかの性質だからです。却下します。デバイスモードは
  ターゲット単位の設定で、設定がすでにターゲットごとの差分をモデル化しているやり方に合致します。
- **専用の `setViewport` / `emulate` ステップ。** 環境の性質を命令的なアクションに変え、シナリオ途中の
  非決定的なリサイズを招きます。同じ理由で却下します。両方の顔が必要なチームは、シナリオを 2 つの
  ターゲットのもとで実行します。
- **名前付きプリセットだけを露出する（明示的なデスクトップ／モバイルと viewport を出さない）。** プリセットは、
  よくあるスマートフォンは網羅しますが、チーム固有のブレークポイントは網羅しません。明示的な viewport にも
  対応すれば、よくあるケースは一語のままで、独自サイズを締め出しません。両方を残します。
- **本項目を web-swipe-scroll-fidelity に 1 つの項目としてまとめる。** 検討しましたが、両者は分けられます。
  デスクトップ経路で `swipe` を正しくスクロールさせることは、それ単独で価値があり、エミュレーションなしで
  出荷できます。一方でエミュレーションは、独自の設定とテストを伴う、より広いケイパビリティ（レイアウト、
  入力、ユーザーエージェント）です。それぞれが小さく独立してレビューできるよう、分割します。

  並びます。トップレベルの `device`（iOS シミュレータ名）とは別物です。プリセットは
  `PlaywrightDriver` の中で**遅延**して解決するため（`_device_context_kwargs` が `playwright.devices`
  に対して解決）、config 読み込みが Playwright を import することはありません。不明なプリセットは
  ドライバー起動時に `ValueError` で明示的に失敗し、解決した記述子は記憶するので `reset_context` /
  `relaunch` は同一のコンテキストを組み直します。`make_driver` / `WebEnvironment.start` /
  `doctor.probe_screen` に通しました。**ケイパビリティとプリフライトの見直し**：変更なし。モバイル
  コンテキストのタッチ入力は既存の `multiTouch` ケイパビリティが既に表しており、デバイスモードは
  シナリオ単位のケイパビリティではなくコンテキスト生成時の設定なので、決定的な run／CI 経路で新たに
  ゲートするものはありません。
