## はじめに

テスト対象アプリへの変更を受け取り、その変更が影響を与えそうなシナリオのステップを報告します。開発者は、リスクのあるステップだけを見直して修正できます。継続的インテグレーション（CI）のパイプラインは、影響を受けるステップを先に実行できます。

報告は決定論的に導きます。突き合わせるのは、2 つの[安定した id](../../docs/ja/glossary.md#シナリオのオーサリング)の集合です。各シナリオのステップが参照する id と、変更が触れた id です。大規模言語モデル（LLM）は経路に置かず、報告はいずれの run の合否判定にも影響しません。

変更は `git` の diff から直接読み取ります。開発者は、変更内容を手で列挙する代わりに、コミット範囲を指定します。この報告は、新しい `bajutsu impact` コマンドが提供します。

## 動機

テスト対象アプリを編集した開発者は、その編集がスイートのどのシナリオをリスクにさらすのかを、編集内容だけからは判断できません。今のところ確実な答えは、スイート全体を実行して失敗を読むことだけです。この答えは正確ですが、フィードバックが遅く、なぜそのシナリオが壊れたのかはわかりません。

逆向きの問い、「ここを変更したが、どのステップを見ればよいか」には、答える手段がありません。この問いは、画面を触った開発者が最初に立てる問いです。

Bajutsu は、この答えの素材をすでに持っています。静的シナリオ解析が、各シナリオの参照する安定した id、画面、アサート対象のエンドポイントを抽出します。[BE-0050](../BE-0050-e2e-coverage-map/BE-0050-e2e-coverage-map-ja.md) も、カバレッジマップに同じ解析を用います。BE-0050 はそのデータを順方向にたどります。スイートから、スイートがカバーするアプリ表面へとたどり、ギャップを可視化します。

同じインデックスを逆向きにすれば、影響の問いに答えられます。各安定 id から、その id を参照するシナリオのステップへのマップを作ります。安定 id に触れる変更は、その id を実行するステップを直接指し示します。

残る一片は、「変更」を触れた安定 id の集合へ変換することです。変換は、開発者に負荷をかけてはならず、app 非依存性も損なってはいけません。安定 id は、アプリのソースに単なる文字列リテラルとして現れます。たとえば、Swift の `accessibilityIdentifier` の `login_button`、Kotlin の `resource-id`、web の `testID` です。

`git` の diff の変更行を、スイートがすでに参照する安定 id で走査すれば、触れた集合を文字列照合だけで復元できます。この走査は、あらゆる backend にわたって使えます。アプリのソースを解析せず、app 固有の知識も埋め込みません。開発者はコミット範囲を指定し、あとはツールが行います。

影響の問いをこの方法で解くと、ワークフローの両側で効果があります。開発者は、変更がリスクにさらす正確なステップを見て、push する前に修正できます。CI のパイプラインは、影響を受けるステップを先に並べて、速いフィードバックを得られます。後述の安全策のもとでは、マージ前の実行を影響を受けるステップへ絞ることもできます。どちらの用途も、合否判定を決定論的なランナーから動かしません。

## 詳細設計

提案の粒度で述べます。`bajutsu impact` コマンドは、読み取り専用かつ advisory（助言的）です。`audit`、`coverage`、`stats`、run をまたぐフレーキネスのランキングと同じ系統に属します。これらは、[BE-0257](../BE-0257-layer-package-topology/BE-0257-layer-package-topology-ja.md) が整えた、読み取り専用の advisory な解析です。デバイスに触れず、LLM を呼ばず、CI をゲートしません。

- **逆インデックス（決定論的）**：各シナリオを解析し、ステップごとに 3 つを記録します。ステップが操作またはアサートする selector、`setup` やディープリンク経由で到達する画面、アサートするエンドポイントです。記録を反転して、マップを作ります。マップは、各安定 id、各画面、各エンドポイントから、それを参照する `(シナリオ, ステップ)` の組のリストへ向かいます。ステップ粒度は自然に得られます。シナリオが、各ステップをその selector に結び付けているからです。逆インデックスは selector 抽出を再実装せず、BE-0050 の静的シナリオ解析を再利用します。

- **`git` diff からの変更抽出（決定論的、app 非依存）**：開発者が指定したコミット範囲について、`git` diff の変更行を読みます。逆インデックスが知る各安定 id について、その id の文字列リテラルが追加行または削除行に現れるかを判定します。現れた id の集合が、**触れた集合**です。照合は、スイートがすでに宣言する id に対する単なる文字列検索です。言語固有の解析を要さず、app 固有の知識も埋め込みません。Swift、Kotlin、TypeScript のどの diff でも、同一に動きます。

- **出力（ステップ粒度）**：触れた集合を逆インデックスで結合して、影響を受ける `(シナリオ, ステップ)` の組を求めます。この組を、JSON と人間が読める一覧として報告します。影響を受ける各ステップには、そのステップを名指しした触れた id を添えます。読み手は、どのステップかだけでなく、なぜ印を付けられたのかもわかります。`bajutsu impact` は両方の形式を出力します。CI のパイプラインは JSON を消費し、開発者は一覧を読みます。

- **決定論と健全性**：どの出力も、diff とシナリオの決定論的な関数です。同じ入力は常に同じ影響集合を生み、モデルや判断は介在しません。ただし、健全性には限界が両方向にあります。
  - **偽陰性**：走査は、安定 id 自身の行を編集した変更を捕まえます。id リテラルに触れずに挙動を変える変更は、捕まえられません。たとえば、ハンドラのロジック、共有ヘルパー、ネットワークレスポンスの形の変更です。このような変更を**帰属不能**（unattributable）と呼びます。逆インデックスのどの id にも対応しないからです。
  - **偽陽性**：コメントや無関係な変更行に、短い id や汎用的な id が偶然現れることがあります。その場合、影響集合が、実際に影響を受けるステップより広がります。過剰選択は CI にとって安全な方向です。影響を受けるステップが、黙って飛ばされることはないからです。開発者は、少数の偽陽性を目にすることがあります。

  この設計は、両方の限界を隠さず名指しします。帰属不能な変更を CI がどう扱うかが、後述の安全性の核心だからです。

- **CI での用途、機構と安全なポリシー**：ツールは影響集合を提供し、どこまで攻めて使うかはチームが選びます。攻めた選択でも健全に保つ安全策が、2 つあります。
  - **保守的なフォールバック**：diff に帰属不能な変更が 1 つでも含まれるとき、ツールは影響集合を報告し、あわせて「不完全、全実行が妥当」という信号を出します。CI を影響ステップへ絞るチームは、この信号を受けたら全スイートに戻さなければなりません。そうすれば、走査が帰属できない変更を、黙って飛ばすことがありません。
  - **全スイートの安全網カデンス**：絞り込みは、速いマージ前フィードバックのためのものであり、最終判断のためのものではありません。全体の決定論的スイートは、より粗いカデンスで、依然として実行します。カデンスとは、メインブランチへのマージ時、夜間、リリース時です。走査がプルリクエスト時に取りこぼしたステップも、出荷前には捕まります。取りこぼしたまま永久に逃すことはありません。

  安全なデフォルトは additive（積み増し型）です。全スイートを実行しつつ、影響ステップを先に並べるか、人間へ印を付けます。マージ前の実行を影響集合まで絞るのは opt-in（任意選択）です。絞り込みは、上の 2 つの安全策があってはじめて健全です。いずれの場合も、合否判定は決定論的なランナーに残り（プライム指令 1）、解析自体は LLM を実行しません。

- **AI レイヤー、後続、advisory、ゲート外**：決定論的な逆インデックス走査を先に出荷し、それ単体で成立させます。id リテラルに触れないのに挙動を変える変更は、走査が取りこぼす帰属不能なケースです。diff を意味的に読んで、そうした間接的な影響を明らかにするのは、LLM に向く判断の仕事です。AI レイヤーを追加する場合は、AI triage（[BE-0021](../BE-0021-ai-triage/BE-0021-ai-triage-ja.md)）と並べて、調査側に位置づけます。AI レイヤーは、いずれの場合も advisory です。CI の実行を刈り込まず、合否判定の経路にも乗りません。AI レイヤーは最初の出荷ではスコープ外です。レイヤーがどこに位置するかを固定するために、ここへ記します。

## 検討した代替案

- **アプリのソースを解析して、変更された UI 要素を抽出する。** Swift、Kotlin、TypeScript の diff を抽象構文木へ読み込めば、文字列走査より多くを捕まえられます。たとえば、名前を変えたハンドラや、再構成したビューです。しかし、この方法は app 非依存性（プライム指令 3）を破ります。各アプリが UI をどう宣言するかについて、言語ごと、フレームワークごとの知識と解析器を要します。その知識はアプリ側にあるべきもので、Bajutsu にはありません。文字列走査は、スイートがすでに宣言する id だけで定義される照合と引き換えに、その到達範囲を意図して手放します。

- **開発者が変更 id を手で渡す。** `bajutsu impact --changed-id a,b,c` という入り口は、作るのが容易で、完全に決定論的です。しかし、何が変わったかを知る負荷を、開発者に戻します。その負荷を取り除くために、この項目は存在します。diff を読めば、開発者の入力はコミット範囲だけに保てます。

- **ソースの diff ではなく、2 つの run（前後）を比較する。** 変更前後の run の要素ツリーを比較すれば、文字列走査が取りこぼす挙動上の影響を捕まえられます。しかし、この方法はスイートを 2 回実行する必要があり、実行する前に何を実行するかを選ぶという目的に反します。run の比較は、別の、より重い機能です。この項目は、ソースの diff からの静的な選択にとどまります。

- **安全策なしで、CI にスイートを刈り込ませる。** すべての CI 実行を影響集合へ絞り、フォールバックも全スイートのカデンスも持たない方法は、もっとも速く、もっとも健全でない選択です。帰属不能な変更が、そのリグレッションを捕まえたはずのステップを、黙って飛ばします。保守的なフォールバックと安全網のカデンスは、そのリスクなしに絞り込みを opt-in とするためにあります。

- **何もしない（現状維持）。** 許容はできますが、逆向きの問いは未解決のままです。開発者は、変更が何を壊したかを知るために、全スイートを実行し続けます。CI は、プルリクエストごとに全スイートのレイテンシを払い続けます。この問いに答えるインデックスは、BE-0050 のために、すでに存在します。

> 作業分解（作業の単位ごとに 1 つ）に対応し、ログには変更内容と時期（古い順）を PR へのリンクと
> ともに記録します。

- [x] 逆インデックス — BE-0050 の静的シナリオ解析を `id / 画面 / エンドポイント → [(シナリオ, ステップ)]` へ反転する（`bajutsu/analysis/impact.py` の `reverse_index`。共有した `audit.step_matchable_ids` / `coverage.step_requests` のステップごとの走査を再利用）。
- [x] 変更抽出 — `git` diff の変更行を、参照される安定 id で走査し、触れた集合と帰属不能変更の信号を生成する（`parse_diff` + `impact`。どの参照リテラルにも一致しない変更ファイルはレポートを不完全と印付けます）。
- [x] 出力 — 影響を受ける `(シナリオ, ステップ)` の組へ結合し、名指しした id を各ステップに添えて JSON と人間が読める一覧を出力する（`bajutsu impact --json` / `render` によるテキスト）。
- [x] CI 連携 — 消費可能な選択の成果物（`complete` 信号つきの `--json`）と、安全なポリシー（保守的なフォールバック、全スイートのカデンス、additive なデフォルト）の文書化を [cli.md](../../docs/ja/cli.md#impact) と [ci.md](../../docs/ja/ci.md) に置きました。
