## はじめに

正規化された `[0,1]` の座標は、画面の大きさを掛けることでデバイスのポイント座標になります。Bajutsu
はその画面の大きさを2つの方法で求めています。`screen_size_from_elements`（`bajutsu/elements.py`）は
取得した要素ツリーの最大の広がりを取り、`Driver.viewport()` はバックエンド自身に問い合わせます
（[BE-0326](../BE-0326-scroll-to-element/BE-0326-scroll-to-element-ja.md)）。前者は、ツリーが画面外の
ノードを保持しているときに画面を超過します。BE-0326 はこの超過を確認し、それを避けるために後者を
導入しました。しかしその修正が届いたのは1つの呼び出し元、`scroll` アクションの停止条件だけです。
ほかの呼び出し元は今も超過する広がりを掛けており、そこには決定的な `run` の経路にある `tapPoint`
ステップも含まれます。本項目は、*画面*の大きさを必要とする呼び出し元をビューポート経由に切り替え、
ツリーの広がりは本当にコンテンツの大きさを必要とする呼び出し元に残します。

## 動機

2つの数値の差は、丸め誤差では済みません。ショーケースの SwiftUI アプリの Permissions タブ
（iPhone 17、iOS 26.5）で実測すると、`Driver.viewport()` は実際の画面である `(402, 874)` を報告し、
`screen_size_from_elements(driver.query())` は `(418, 2456)` を報告します。SwiftUI の `Form` が画面外
の行をアクセシビリティツリーに保持しているためです。したがって正規化された `(0.5, 0.5)` は
`(201, 437)` ではなく `(209, 1228)` に写り、y 座標は 874 ポイントの画面の下端をはみ出します。

これが周縁のバグに留まらないのは、同じ算術を共有しているステップがあるからです。`tapPoint` は
決定的なシナリオステップであり、そのハンドラ（`orchestrator/actions/handlers/gestures.py`）は作者が
書いた正規化座標に `screen_size_from_elements` を掛けています。ハンドラ自身のコメントも、アラート
ガードとクロールが「1つの画面サイズの定義」を共有していると述べています。つまりスクロールする画面で
`tapPoint` を使うと、作者が指していない場所か画面の外をタップし、それでも run はそのステップを実行済み
として記録します。アクチュエーションの記録は、デバイスが受け取ったものと食い違います。これは
prime directive 2 が防ごうとしている失敗の形そのものです。方向指定の `swipe` の距離も同じ値で
スケールされるため、同じ Permissions タブでは 2456 ポイントの何割かを進みます。874 ポイントの何割か
ではありません。
およそ 2.8 倍の行き過ぎです。

この欠陥は
[BE-0308](../BE-0308-alerts-guard-real-model-verification/BE-0308-alerts-guard-real-model-verification-ja.md)
のアラートフィクスチャを捕捉する途中で表面化しました。代償がもっとも鋭く出るのは、アラート
ガードです。BE-0308 では、実モデルが通知プロンプトに対して `(126.6, 517.8)` と答え、`Don’t Allow` の
中心 `(127, 518)` との差が 0.5 ポイント未満であることを実測しました。ガードはその答えに
`(418, 2456)` を掛けて `(132, 1456)`、つまり画面の外をタップします。正しい判断が、その下の写像に
よって壊されています。

BE-0326 はすでに正しい診断に到達しているので、ここで足りないのは着想ではなく適用範囲です。途中で
1つ直しておきたい細部があります。BE-0326 の `_viewport` ヘルパは、フォールバックの根拠を「ほかの
バックエンドは画面上の要素だけを取得するので、要素の広がりがビューポートである」と書いていますが、
上の実測は XCUITest についてこの前提を否定します。それでも `scroll` アクションは今のところ正しく
動きます。`XcuitestDriver` が `ViewportProvider` を実装しており、フォールバックに到達しないからです。
書かれた根拠のおかげではなく、それにもかかわらず正しいわけで、これはのちの読み手が土台にしてしまう
種類の記述です。

## 詳細設計

提案の粒度です。作業は以下の単位に沿って MECE に分かれます。

- **「正規化座標を写す先の画面」を求める共有ヘルパを1つ用意する**：`ViewportProvider` を優先し、
  なければツリーの広がりに退避するという形は、すでに
  `orchestrator/actions/handlers/scroll.py` の非公開ヘルパとして存在します。これを共有関数へ引き上げ、
  判断を呼び出し元ごとではなく1箇所で行うようにします。フォールバックの説明も正直に書き直します。
  ツリーの広がりは、ビューポートを報告できないバックエンドのための劣化した代替であり、そうした
  バックエンドのツリーが超過しないという主張ではありません。
- **`screen_size_from_elements` のすべての呼び出し元を棚卸しし、画面の大きさを必要とするものを
  切り替える**：各呼び出し元が必要としているのは画面（正規化座標、画面比で決まるジェスチャの距離）か
  コンテンツ（ツリー自身の広がり）のいずれかであり、本項目の価値は一括変換ではなく呼び出し元ごとに
  どちらかを明示することにあります。現時点で画面側と判明しているのは、`tapPoint` ハンドラと方向指定
  swipe の距離（`handlers/gestures.py`）、視覚アラートガード（`agents/alerts.py`）、クロールの座標
  タップの再生（`crawl/core.py`）です。アサーション、`serve`、パイプラインの読み取りについても、
  結論を決め打ちせず同じように個別に判断します。
- **切り替えた呼び出し元ごとに、高速ゲート上の回帰テストを1つ置く**：デバイスは要りません。
  `FakeDriver` は BE-0326 のスクロール可能なモデルの上で `ViewportProvider` を実装しているので、
  広がりがビューポートを超えるツリーを供給できます。各切り替えは、写った点がビューポート基準の点で
  あること、かつツリーの広がりで得られる点とは異なることの両方を検証して固定します。変更前に落ち、
  変更後に通るテストであり、新しいコードに単に同意するだけのテストではありません。
- **決定的な経路が直ったことを実機で1つ確認する**：iOS レーンで、スクロールするショーケース画面に
  対する `tapPoint` のシナリオを走らせます。その期待値は、正規化座標が指す場所にタップが着地した
  ときにだけ成り立ちます。算術は高速ゲートのテストが証明しますが、そこでツリーが本当に超過すること
  は実機だけが証明できます。算術はその前提の上に立っています。

ここにモデル呼び出し、固定 sleep、アプリ固有のノブはいずれも加わりません。既存のドライバインタフェース
の背後で幾何の取得元を1つ入れ替えるだけなので、決定的な `run` の判定は決定的なままであり、
フォールバックによってどのバックエンドも正しい答えを保ちます。

## 検討した代替案

- **`screen_size_from_elements` 自身がビューポートを返すようにする**：この関数は要素ツリーに対する
  純粋な関数で、問い合わせるバックエンドを持たないため、そもそもできません。加えて、コンテンツの
  広がりを本当に必要としている呼び出し元もあるので、意味を変えれば、各呼び出し元に選択させる代わりに
  すべての呼び出し箇所の意味を黙って変えてしまいます。
- **欠陥を実測したアラートガードだけを直す**：`tapPoint` ステップは同じヘルパと同じ算術を共有し、
  しかも決定的な判定経路の上にあります。AI の周縁を直してゲートの経路を誤ったままにするのは、
  両者の優先順位を逆にすることになります。
- **`viewport()` をオプトインの Protocol ではなく `Driver` の必須メソッドにする**：これは全実装に
  およぶドライバ API の変更であり、ここでは何も得られません。`ViewportProvider` 優先とツリーの
  広がりへの退避という形で、報告できるバックエンドではすでに正しい答えが得られ、報告できない
  バックエンドでも説明のつく答えが得られます。
- **`tapPoint` を直すのではなくシナリオスキーマから外す**：`tapPoint` はどのセレクタでも指定できない
  コントロールのために文書化された脱出口です。しかもアラートガードの dismiss は同じ写像に依存する
  ので、ステップを外しても欠陥はその場に残ります。
