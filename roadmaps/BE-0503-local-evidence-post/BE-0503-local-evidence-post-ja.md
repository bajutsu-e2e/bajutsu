## はじめに

> **却下（証跡は、サーバーのストアに置き、URL でリンクするほうが適しています）。**
> GitHub には、スクリプトが run の zip をコメントへ載せる、文書化された手段がありません。
> `gh --attach` が扱うのは画像と動画だけで、zip は投稿の前に拒否します。代わりの手段はリリースのアセットです。
> これはスレッドごとにリリースを1件ずつ残します。ドラフトのリリースを開けるのは、書き込み権限を持つ人だけです。
> Actions のアーティファクトにはランナーが要り、手元の実行にはそれがありません。
> 何かの解消を待っているわけではないので、この項目は保留ではなく却下とします。
> 後続の項目で、完了した run を `serve` のストアに保存し、そこで得た URL をコメントからリンクします。
> ドラフトのリリースでのスパイクは実施しました。アセット API は、各ファイルを添付ファイルとして返し、ドラフトのアセットの公開リンクは、書き込み権限がないと `404` を返します。

開発者の手元で終えた実行を、プルリクエストまたは Issue に投稿する補助スクリプト `scripts/post_evidence.py` を追加します。コメントには、失敗したシナリオ、失敗したステップ、その理由を載せ、実行の証跡へのリンクを付けます。スクリプトをもう一度実行すると、新しいコメントを増やさず、同じコメントを更新します。スクリプトは開発者自身の GitHub の認証情報を使い、判定のあとに動きます。そのため、実行が決めた結果を変えることはありません。

このスクリプトは、Bajutsu の機能ではありません。標準ライブラリだけを使い、`bajutsu` から何も import しない1つのファイルです。サブコマンドも `[project.scripts]` の項目も足さず、インストールされるパッケージにも同梱しません。ポータブルな GitHub Action `post-evidence` は、並行して出している別の提案が定義します。この Action は、現状、描画処理の独自のコピーを Action のディレクトリに持ちます。この1つのファイルへ揃えることは、下の作業項目であり、それが済むまでは、2つのコピーを手作業で同一に保ちます。揃えたあとは、実行がランナーで動いたか手元のノートパソコンで動いたかによらず、レビュアーは1つのコメント形式を読めます。

## 動機

Bajutsu の実行の多くは、CI に届きません。iOS のフローを変えた開発者は、手元のシミュレーターに対してシナリオを実行します。CI のレーンはスイートの一部しか覆わず、デバイスクラウドの実行には時間と費用がかかるからです。変更が動くという証跡は、そのノートパソコンの `runs/` に残ります。レビュアーに見せるために、開発者は `bajutsu export`（[BE-0060](../BE-0060-run-report-zip-export/BE-0060-run-report-zip-export-ja.md)）で zip を作ります。そして、ブラウザーでコメントにファイルを手作業でドラッグします。スクリーンショットも動画も、1つずつです。

CI 側の Action は、ここでは役に立ちません。ワークフローの実行とランナーが要りますが、手元の実行には、そのどちらもないからです。[BE-0110](../BE-0110-evidence-store-uri/BE-0110-evidence-store-uri-ja.md) は実行の証跡をオブジェクトストレージへアップロードしますが、アップロードしたファイルをコメントにする仕組みはありません。

この用途には、製品のコマンドよりスクリプトが向いています。理由は2つあります。`bajutsu` のサブコマンドにすると、文書化された CLI の契約になり、プロジェクトがバージョン管理と保守を引き受けます。しかも、その便利さは GitHub のウェブ上の挙動に依存し、Bajutsu はそれを制御できません。1つのスクリプトなら、持ち運べます。Bajutsu のチェックアウトを持たないリポジトリへ、ファイルをコピーするか、URL で取得して使えます。

導入後に確かめられる違いは、コマンド1つです。`python3 scripts/post_evidence.py runs/<runId> --to owner/repo#123` を実行すると、プルリクエストにコメントが1件付きます。コメントは、成功と失敗の件数を述べ、失敗した各シナリオを理由とともに示します。修正のあとにもう一度実行すれば、そのコメントが書き換わります。開発者は、コメントにファイルをドラッグするためにブラウザーを開かずに済みます。

## 詳細設計

### スクリプト

```
python3 scripts/post_evidence.py <run-dir | run-id> --to <target>
        [--runs DIR] [--sink none|release] [--publish]
        [--evidence-base-url URL] [--key KEY] [--author LOGIN]
        [--max-failures N] [--log-tail-kb N] [--size-warn-mb N]
        [--dry-run] [--yes]
```

`<run-dir | run-id>` は、1つの実行ディレクトリのパスか、`--runs`（既定は `runs`）の下から探す実行 ID です。`--to` は、`owner/repo#123`、またはプルリクエストか Issue の URL を取ります。`#123` だけの指定は受け付けません。フォークで作業する場合、`origin` は開発者のフォークですが、プルリクエストは上流にあります。2つのリポジトリは番号を共有しません。番号だけでは、非公開の画素を含む証跡が、別のスレッドへ届き得ます。しかも `--yes` を付けると、それを止める唯一の確認も省かれます。スクリプトは投稿するだけです。シナリオを実行せず、AI プロバイダーも呼びません。

`--max-failures`（既定は10）は、失敗したシナリオのブロック数の上限です。省いた件数は、コメントに書きます。

### 認証情報

スクリプトは、`GITHUB_TOKEN` または `GH_TOKEN` からトークンを読みます。どちらも未設定で、`gh` CLI が入っていれば、`gh auth token` に尋ねます。トークンをディスク、実行ディレクトリ、ログのいずれにも書きません。コメントには、プルリクエストまたは Issue への書き込み権限が要ります。`release` シンクには、リポジトリのコンテンツへの書き込み権限も要ります。

### 証跡の送り先

GitHub には、画像や動画をコメントの中へアップロードする、文書化されたエンドポイントがありません。そこでスクリプトは、テキストとリンクを投稿し、リンクの行き先を `--sink` で選びます。

| シンク | 動作 | リンクを開ける人 |
|---|---|---|
| `none`（既定） | 何もアップロードしません。コメントは、実行ディレクトリ内のパスで各ファイルを示します。`--evidence-base-url` を指定すると、そのパスを、開発者が配信するコピーへのリンクにします。 | ベース URL を開ける人。 |
| `release` | 失敗したスクリーンショット、動画、実行の zip を、対象ごとに1つのリリース（名前は `bajutsu-evidence #<number>`）のアセットとしてアップロードします。コメントは、各アセットへリンクします。 | 下書きのリリースは、リポジトリへの書き込み権限を持つ人だけが見られます。`--publish` を付けると、リポジトリを見られる全員に公開します。 |

既定を `none` にするのは、アップロードが外部へ向けた操作であり、開発者が求めない限り、スクリプトが行うべきではないからです。すでに `bajutsu run --evidence-store`（[BE-0110](../BE-0110-evidence-store-uri/BE-0110-evidence-store-uri-ja.md)）を実行した開発者は、ストアのプレフィックスの公開ベース URL（公開バケットのパスや、その前段の CDN）を `--evidence-base-url` に渡します。署名付き URL は1つのオブジェクトだけに署名するので、ベース URL にはなりません。すると、スクリーンショットがコメントの中にインラインで表示されます。描画処理は、パスの各セグメントをパーセントエンコードしてからベースに連結します。そのため、実行 ID やファイル名に空白、`#`、`?` が含まれても、リンクは正しく解決します。スクリプトは BE-0110 のアップローダーを呼びません。そのため、`s3` や `gcs` の extra は要りません。

書き込み権限のないレビュアーには、下書きのリリースのリンクが 404 になります。そのようなレビュアーや、外部の貢献者が立てた Issue を対象にするときは、`--publish` を渡します。プルリクエストと Issue は、リポジトリ内で1つの番号の空間を共有するので、同じリリースが両方に使えます。スクリプトはリリースを削除しません。再利用するリリースは計画に表示するので、後始末は、目に見える手作業として残ります。各リリースは、タグ `bajutsu-evidence-<number>` を使い、`prerelease: true` と `make_latest: "false"` で作成します。そのため、リポジトリの最新リリースにはなりません。公開すると、そのタグが作られ、リリースの公開を待ち受けるワークフローが動きます。既存のリリースは、リリースの一覧を取得し、タグ名の完全一致で探します。タグのエンドポイントは、下書きを返さないからです。再利用するリリースが下書きか公開済みかは、計画に書きます。`--publish` が既存の下書きを公開するときは、すでに載っているアセットも計画に挙げます。それらも公開されるからです。アセットの種類ごとに、ドラフトのリリースでのスパイクでは、アセット API が各ファイルを添付ファイルとして返すことと、ドラフトのアセットの公開リンクが、書き込み権限がないと `404` を返すことが分かりました。公開したリリースが画像をその場に表示するかは、測っていません。

### コメントの内容

描画処理は、Action と同じ Markdown を作ります。先頭に、判定、件数、実行 ID を置きます。失敗したシナリオごとのブロックには、シナリオ名、最初に失敗したステップ、失敗の理由を書きます。描画処理は `manifest.json` を読みます。マニフェストが残らなかった実行では、`<sid>/result.json` を読みます。実行からコピーするすべての文字列を、エスケープします。シナリオ名、失敗の理由、artifact のパスは、コードスパンに入れ、複数行にわたる文字列はフェンスつきブロックに入れます。区切りには、中の最も長いバッククォートの連続より1つ長い連続を使います。さらに `<!--` と `-->` を、残らなくなるまで繰り返し取り除きます。アプリ由来の文字列が、メンションや HTML、2つ目のマーカーを加えられないようにするためです。Action の項目も同じ規則を述べており、2つは同一に保ちます。

固定コメントは、1行目の隠しマーカー `<!-- bajutsu-evidence:<key> -->` を使います。比較は、末尾の空白と復帰文字を取り除いてから行います。`--key` の既定は `local` なので、同じプルリクエストの手元のコメントと CI のコメントは、別々に保たれます。`--key` は、値全体が `[A-Za-z0-9._-]+` に一致する必要があります。先頭だけに一致する `re.match` は、`local-->` を `local` の部分で通してしまうため、全体一致（`re.fullmatch`）で判定します。それ以外の値では、ネットワーク呼び出しの前に0以外で終了します。`-->` や改行が含まれると、マーカーが途中で閉じ、実行のたびに重複して投稿するからです。

スクリプトは、トークンに対して `GET /user` が返すログインで、自分のコメントを見つけます。GitHub App のインストールトークンのように、ユーザーを持たないトークンを使うときは、開発者が `--author` でログインを指定します。

### アップロードの前の確認

スクリーンショットや動画には、非公開のデータが写ることがあります。削除したリリースのアセットも、キャッシュに残ることがあります。スクリプトは、書き込みの前に計画を表示します。送り先、リポジトリの公開範囲、作成または再利用するリリースと `--publish` で公開するかどうか、公開によって作られるタグ `bajutsu-evidence-<number>` と、そのタグが動かす対象リポジトリの `release: published` やタグのプッシュのワークフロー、各ファイル、合計サイズを示し、確認を求めます。スクリプトからは `--yes` で確認を省けます。`--dry-run` は、計画と、投稿する Markdown を表示して、ネットワークへ何も書かずに止まります。

スクリプトは、実行ディレクトリを変更しません。アップロードするファイルを一時的な作業用ディレクトリへコピーし、そこで大きすぎる `deviceLog` を、末尾の `--log-tail-kb` KB に切り詰めて、そのコピーからアップロードします。実行ディレクトリには完全なログが残り、`report.html` のリンクも切れません。`release` シンクは、ステージした集合全体に `--size-warn-mb` を適用します。まず zip を省き、それでもしきい値を超える個々のスクリーンショットや動画があれば、それも省きます。そのため、上限のないアセットをアップロードする実行はありません。`none` シンクは何もアップロードしないので、この保護は `release` だけに適用されます。切り詰めたものと省いたファイルは、計画とコメントにすべて明記します。

実行は、各 artifact（`manifest.json`、`<sid>/result.json`、デバイスログを含む）を書く時点で、文字列を伏せ字にします（[BE-0331](../BE-0331-artifact-redaction-boundary/BE-0331-artifact-redaction-boundary-ja.md)）。スクリーンショットや動画の画素には、伏せ字処理がありません。確認があるのは、そのためです。

### 終了ステータス

開発者は投稿するためにスクリプトを実行したので、投稿に失敗したら、理由を示して0以外で終了します。実行の副作用であるアップロードが警告に落ちる `run --evidence-store` とは、ここが違います。終了ステータスは、実行の判定を反映しません。失敗した実行も投稿でき、投稿が成功すれば0で終了します。スクリプトのどこにも LLM は登場しません。

### 置き場所、テスト、ゲートの対象

スクリプトは、リポジトリの補助スクリプトの置き場である `scripts/` に置きます。そのため、`make typecheck`（`mypy bajutsu demos scripts`）と `ruff` は、変更なしで検査します。テストファイルは、`tests/test_devicefarm_submit.py` が Device Farm のサブミッターを import するのと同じ方法で、スクリプトを import します。テストは偽の GitHub HTTP サーバーに対して動くので、ゲートにネットワークは要りません。スクリプトは、`scripts/gh_cli.py` を意図して import しません。これは、ロードマップのスクリプトが `gh` を呼び出すときに共有するラッパーです。そのラッパーは `gh` CLI を動かします。一方、このファイルは、Bajutsu のチェックアウトを持たないリポジトリへ単独でコピーできる必要があり、標準ライブラリで REST API と直接やり取りします。`gh` の呼び出しは、トークンのフォールバックとしての `gh auth token` だけです。

カバレッジのラチェットが計測するのは `bajutsu/` だけなので、このスクリプトは守られません。スクリプトをパッケージの外に置くのが、この項目の狙いであり、テストがその費用を負います。[BE-0336](../BE-0336-serve-device-farm-bounded-fan-out/BE-0336-serve-device-farm-bounded-fan-out-ja.md) は、その計測を得るために、Device Farm の中核を `bajutsu/` へ移しました。スクリプトが育てば、後続の項目で同じことができます。

### 2つの入口に1つのスクリプト

Action の項目は、現状、スクリプトを Action のディレクトリに置いています。2つの項目は、1つのファイルに揃える必要があります。この項目は `scripts/post_evidence.py` を提案し、Action は自分のリポジトリのチェックアウトからそれを読み込みます。下の作業分解が、その手順を挙げます。

### ドキュメント

`docs/reporting.md` と `docs/ja/` のミラーに、手元の実行を、最初は `--dry-run` で、次に実際に投稿する例の節を足します。

## 検討した代替案

- **`bajutsu post` サブコマンド。** サブコマンドなら、レポートのコードを直接再利用できます。採用しなかったのは、GitHub に依存する便利さを、バージョン管理される CLI の契約にしてしまうからです。Bajutsu のチェックアウトを持たないチームは、コピーして使えません。スクリプトが安定すれば、後続の項目で昇格できます。
- **`run` に `--post` フラグを足す。** 1つのコマンドで、実行と投稿ができます。ただし、`run` がネットワークと GitHub の認証情報に依存します。途中で止まった実行は、投稿もされません。
- **`bajutsu export` を拡張する。** このコマンドはすでに zip を作ります。ただし、コメントの単位に zip は向きません。レビュアーが最初に見たいのは、失敗したスクリーンショットと理由だからです。
- **ブラウザーが使うウェブのアップロード用エンドポイント。** コメントに画像をインラインで置けます。ただし、文書化されておらず、予告なく変わり得ます。それに依存するツールは、気付かないうちに壊れます。
- **下書きのリリースを既定のシンクにする。** 下書きのリリースは、最も見えにくい選択肢です。書き込み権限のないレビュアーには、404 が見えます。そこで、`release` と `--publish` は、開発者が明示的に選ぶものにします。
- **証跡をブランチにコミットする。** ブランチなら、安定した URL が手に入ります。ただし、リポジトリが肥大化し、リポジトリの履歴へ書き込みます。そのため、既定には入れません。
