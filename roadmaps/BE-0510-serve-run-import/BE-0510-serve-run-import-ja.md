## はじめに

スクリプトが、完了した run を `serve` に渡せるようにします。新しいルート `POST /api/runs/import` が、run を zip として受け取ります。zip を検査し、`serve` が run を置く場所に保存し、run の履歴に記録して、run の URL を返します。小さな単体のスクリプト `scripts/upload_run.py` が、run のディレクトリから zip を作り、このルートを呼びます。この URL を開くと、その組織のメンバーに、run のレポートが表示されます。

## 動機

`serve` が run を保存するのは、ワーカーがその run を実行したときと、管理者の `rescan` が、サーバーのディスクにあるツリーを見つけたときです（[BE-0449](../BE-0449-server-runs-no-jobs/BE-0449-server-runs-no-jobs-ja.md)）。ワーカーは、署名付きのアップロード URL を求め、ツリーをアップロードし、結果を報告します。`run --evidence-store` は、バケットへ直接アップロードし、履歴には何も残しません（[BE-0110](../BE-0110-evidence-store-uri/BE-0110-evidence-store-uri-ja.md)）。開発者がノート PC で作った run には、入る手段がなく、証跡は、そのノート PC に残ったままです。

観察できる違いは、リンクです。`python3 scripts/upload_run.py runs/<runId> --server <url>` を実行したあと、`GET <server>/runs/<runId>/report.html` は、サインイン済みの組織のメンバーにレポートを返し、その run が、組織の履歴に現れます。壊れた zip には `400` が返り、何も保存されません。

## 詳細設計

### zip の受信

ルートは、`/api/upload` と同じく、`application/zip` の生の本文を受け取ります。`BoundedZipReceiver` と、2つの `_stream_bounded_body`（stdlib のハンドラーのものと FastAPI のアプリのもの）を、そのまま使います。ルートには、独自の上限 `MAX_RUN_IMPORT_BYTES` を 2 GiB で置きます。バンドルの上限の2倍にしているのは、スクリーンショットと動画がほとんど圧縮されないためです。`extract_bundle` が守る、展開後 4 GiB の上限は、別の上限で、この上限が保証するものではありません。ログと JSON だけの 2 GiB の本文は、それを超えることがあります。ルートは、その拒否を、サイズ超過の run として報告し、この関数の zip 爆弾という文言は使い回しません。ルートは両方のバックエンドで宣言するので、ルートレジストリのテストが両方を確かめます。

### run の検証

ルートは、何かを展開する前に、zip のエントリー一覧を検査します。zip には、run ID を名前とするトップレベルのディレクトリを、ちょうど1つ含めます。その名前は、`valid_run_id` を通る必要があります。そのディレクトリには、読める `manifest.json` と、後述の作り直しが読む `scenario.yaml` が要ります。`manifest.json` は、真偽値の `ok` と、リスト `scenarios` を持つ JSON オブジェクトです。マニフェストに `runId` がある場合は、ディレクトリ名と一致する必要があります。レポートが、別の run の名前を持たないようにするためです。ごみ箱にある run を示す墓標 `.deleted` という名前のエントリーは、拒否します。

ルートが残すのは、拡張子が、大文字と小文字を区別せずに、受動的な種類の一覧にあるエントリーだけです。一覧は、`.png`、`.jpg`、`.jpeg`、`.webp`、`.gif`、`.mp4`、`.webm`、`.json`、`.txt`、`.log`、`.yaml`、`.yml` です。それ以外のエントリーは取り除き、取り除いたパスを応答に一覧で示します。そのため、実際の run は、いつでも取り込めます。`serve` は、run のファイルを自分のオリジンから配信するので、クライアントがアップロードしたページ、XML 文書、SVG 画像は、開いた人の cookie で動きます。その人が管理者でも同じです。Android で、設定したときだけ動く `rawTree` の取得は、`hierarchy.raw.xml` と `hierarchy.parsed-input.xml` の2つの XML を書きます（`docs/evidence.md`）。ルートはこれを取り除き、レポートのリンクは `404` になります。`serve` は、すでに、すべての応答に `X-Content-Type-Options: nosniff` を付けています（`gate.HARDENING_HEADERS`）。ただし、ホストされたオブジェクトストアでは、run のファイルへの応答が、ストアの署名付き URL への `302` になり、`serve` が設定するヘッダーは、バイト列に届きません。そのため、許可リストが、そこでの防御のすべてになり、ヘッダーの陰に隠れた第2の層ではありません。

すべての run が書く `report.html`、`junit.xml`、`ctrf.json` も、アップロードされたものを取り除きます。ルートは、この3つを、`bajutsu/common/report/load.py` の `rebake(<staging>/<runId>)` で作り直します。[BE-0068](../BE-0068-regenerable-reports/BE-0068-regenerable-reports-ja.md) の再描画です。`rebake` が読むのは、`manifest.json` と `scenario.yaml` です。`rebake` が `OSError` か `ValueError` を出したときは、`400` を返し、ステージ用のディレクトリを消します。そのため、保存されるコピーは、いつもサーバーのものです。ホストされたストアには、表示のたびの描画がなく、保存された `report.html` を配信します。そこで、作り直しは、展開の直後に、マニフェストがまだツリーにあるうちに、その場で行い、アップロードの前に済ませます。

マニフェストと各 `<sid>/result.json` は、アーティファクトの名前を持ち、レポートのテンプレートは、その名前を `href` と `src` の属性に入れます。そのため、そのパスはすべて、スキームも先頭の `/` も `..` のセグメントも持たない相対 POSIX パスで、zip が持つエントリーを指している必要があります。この検査は、上の拡張子のフィルターより前に、zip のエントリー一覧の全体に対して行います。そのため、フィルターが取り除くアーティファクトは、`400` になりません。そのリンクは、代わりに `404` を返します。それ以外の値には、`400` を返します。

そのあと、ルートは、新しいステージ用のディレクトリへ、`extract_bundle` で zip を展開します。この関数は、zip-slip のパス、シンボリックリンク、多すぎるエントリー、zip 爆弾を疑わせる圧縮率を、すでに拒否します。失敗したときは `400` を返し、ステージ用のディレクトリを消します。

### ID の確保

run ID は、秒単位の粒度しか持たず、履歴は、ID を全体で1つのキーとして扱います。そのため、2台のマシンや2つの組織が、同じ ID を作ることがあります。ルートは、ファイルを置く前に、ID を確保します。その前に、まず、自分の組織の古い確保を削除し、次に、ID を持ちうるほかの場所を調べ、そのあとで確保します。古い確保の削除を先にするのは、クラッシュが残したものが、そのあとの再試行を、すべて失敗させるためです。置き先のプレフィックスに、すでにオブジェクトや `.deleted` の墓標がある場合は、`409` を返します。リポジトリがない場合は、ツリーが履歴を兼ねるので、`runs_dir/<runId>` か `runs_dir/.trash/<runId>` があれば `409` を返します。

確保は、`_record_run(..., if_absent=True)` の `if_absent` による挿入です。`persist_run` は、すべての例外を握りつぶすので使わず、`_record_run` を、この用途のために公開して、直接呼びます。`_record_run` は、今は `done` を書くので、`status` の引数を足します。ルートは、`importing` の状態で確保します。マニフェストが置かれたあとで、行を `done` に変えますが、これは、その行が、このリクエストが書いた `importing` の確保のままであるときだけ書き込まれる、比較して置き換える操作です。挿入が、有効な行がすでにあると報告したら、ルートは `409` を返します。どの組織が ID を持っていても、本文は同じにして、何も明かさないようにします。同時に2回取り込む場合の競合を閉じるのは、この挿入だけです。行の書き込みに失敗したときは、`5xx` を返します。ルートが、run を上書きすることはありません。名前の付け替えには、マニフェストの書き換えが要るので、この項目では扱いません。

この状態を安全にするために、3つの変更を入れます。`Repository` プロトコルと `sql_repository.py` の `list_runs` に、`importing` の行を除くフィルターを足し、履歴とフレーク分析の呼び出し元すべてが、それを引き継ぐようにします。確保から置き換えまでの間でクラッシュすると、`importing` の行と、場合によってはプレフィックスの下のオブジェクトが残ります。ルートの古い確保の削除が扱うのは、呼び出した組織の分です。`get_run(run_id)` を呼び、その行が、呼び出した組織のもので、状態が `importing` で、`created_at` が1時間以上前なら、`delete_keys(list_keys(<prefix><runId>/))` で、残ったオブジェクトを消し、`purge_run(run_id, org_id=...)` を呼びます。これで、その ID を再び使えます。`get_run` は、組織で絞られないので、ルートが、ほかの組織の行を削除することはありません。サーバーの起動時の掃除は、組織をまたいでよく、すべての組織の古い `importing` の行を、同じやり方で削除し、残ったステージ用のディレクトリを消します。

### run の配置

ローカルのファイルストアでは、`runs_dir` の隣の、同じファイルシステム上のステージ用のディレクトリへ展開し、`os.rename` で、1手で所定の場所へ移します。ホストされたストアでは、作り直しが済んだ `<staging>/<runId>/` で作業します。そのツリーから `manifest.json` を外へ移して、`upload_tree(store, <staging>/<runId>, <組織のアーティファクトのプレフィックス>)` を呼びます。そのあとで、`put_file` で `manifest.json` を置きます。コピーの途中の run が、完了した run に見えないようにするためです。`upload_tree` は、失敗を集めるだけで、例外を投げません。そのため、ルートは、結果の失敗に1件でも項目があれば、エラーとして扱います。その場合は、`5xx` を返し、`delete_keys(list_keys(<prefix><runId>/))` で、上げたものを消し、`purge_run(run_id, org_id)` で、確保した行を削除します。ローカルでの配置に失敗したときも、同じように行を削除します。

### run の記録

ルートは、保存するマニフェストの `provenance.source` を `import` にします。来歴は、run の素性を示すメタデータで、判定には含まれません。この印は、判定を主張したのがワーカーではなくクライアントであることを、読み手に伝えます。監査イベントには、取り込んだ主体として、`api-key:<id>` か、サインイン済みの editor のログインを載せます。履歴の行は、組織をプリンシパルから、ラベルをマニフェストから、`ok` を `bool(manifest["ok"])` から取ります。

### 応答と URL

応答は JSON で、`{runId, ok, url: "/runs/<runId>/report.html", archive: "/runs/<runId>/archive.zip"}` です。`serve` が知っているのは、自分のオリジンだけで、公開用のベース URL の設定もありません。そのため、応答はパスを返し、スクリプトが、渡されたサーバーのアドレスと結びます。

これらのルートはすでにあり、ゲートを通ります。読むには、組織のサインイン済みのセッションが要ります。run には共有リンクがないので、組織の外のレビュアーは、この URL を開けません。API キーも、run を読めません。ドキュメントに、この旨を書きます。

### 認可

ルートを呼べるのは、editor の権限を持つ呼び出し元です。`required_role` には、`/api/runs/` 以下のどの `POST` にも、権限を返さない早い分岐があり、`_EDITOR_PATHS` は、その分岐のあとでしか参照されません。そのため、早い分岐より前に、`POST /api/runs/import` を `editor` とする明示的なケースを置きます。ルートは、組織単位の API キーの項目が導入する、キーの許可リストにも入れます。

### アップロード用のスクリプト

`scripts/upload_run.py` は、標準ライブラリだけを使い、`bajutsu` から何も import しません。run のディレクトリか run ID を受け取り、run ID を唯一のトップレベルのディレクトリとする zip を作って、送ります。サーバーのアドレスは `--server` から、キーは環境変数 `BAJUTSU_SERVE_KEY` か `--key-file` から読みます。キーを引数で受け取ることはしません。引数は、シェルの履歴に残るためです。ホストがループバックでない限り、`http://` のサーバーを拒否します。キーが、平文でネットワークを通ることはありません。キーは、リダイレクトされないヘッダーで送るので、リダイレクトが、別のホストへキーを運ぶことはありません。run の URL とアーカイブの URL を、2行で表示します。`--dry-run` は、送る内容を表示するだけで、何も送りません。終了ステータスは、取り込みの成否を表し、run の判定は反映しません。

### マスク

run を作ったマシンは、各アーティファクトを書くときに、テキストをすでにマスクしています（[BE-0331](../BE-0331-artifact-redaction-boundary/BE-0331-artifact-redaction-boundary-ja.md)）。サーバーは、run をもう一度走査しません。スクリーンショットと動画の画素は、マスクの対象外です。ドキュメントは、アップロードの前に、開発者が確かめるよう案内します。

### テストとドキュメント

テストは、ローカルのストアと偽のオブジェクトストアでの正常な取り込みと、実際の run のツリーの取り込みを確かめます。各拒否（壊れた zip、トラバーサルのパス、シンボリックリンク、マニフェストがない、`scenario.yaml` がないか壊れている、不正な run ID、ディレクトリ名と違うマニフェストの `runId`、`.deleted` のエントリー、スキームや `..` のセグメントを含むアーティファクトのパス）も確かめます。取り除くエントリーも確かめます。大文字小文字を問わない HTML、SVG、XML のエントリーは、取り除かれ、応答に一覧で示されます。実際の run のツリーには `rawTree` の取得を含め、その2つの XML が取り除かれることを確かめます。ホストされたストアでは、取り込みのあとで `GET /runs/<runId>/report.html` が `200` を返します。呼び出した組織の古い `importing` の行は、残ったオブジェクトとともに削除され、ほかの組織の行には触れません。`done` への切り替えは、比較して置き換える操作です。展開後に大きすぎる zip には、サイズ超過の run のメッセージが返ります。組織をまたぐ `409` の衝突と、同時に2回取り込んだ場合、配置に失敗したあとのロールバック、権限の検査、キーの経路、`http://` のサーバーの拒否、リダイレクトの規則も確かめます。ルートレジストリのテストと、stdlib の import ガードが、新しいルートを対象にします。`docs/self-hosting.md`、`docs/cli.md`、および `docs/ja/` のミラーに、ルートを書きます。`docs/reporting.md` とそのミラーに、アップロード用のスクリプトの節を足します。

## 検討した代替案

- **`rescan` を広げる。** `rescan` は、サーバー自身のディスクを読み、呼べるのは管理者だけです。ノート PC は、そこへツリーを置けません。
- **ワーカーの署名付き URL の流れ。** この流れは、貸し出されたジョブとワーカーのトークンに結びついています。スクリプトには、どちらもありません。
- **`run --evidence-store`。** ノート PC にクラウドの認証情報が要り、履歴の行も残らないので、レポートは `serve` 上の URL を持ちません。
- **`/api/upload` を使い回す。** このルートは、設定のバンドルをセッションへ結びつけます。受信の仕組みは使えますが、置き場所は、run に合いません。
- **取り込んだファイルをサンドボックスの方針で配信する。** `Content-Security-Policy: sandbox` を付ければ、アップロードされたページを残せます。`file://` のストアは、すでにオブジェクトのルートでこれを付けています。しかし、ホストされたストアは、run のファイルへの応答を、署名付き URL への `302` にするので、`serve` は、そのバイト列にヘッダーを付けられません。入り口で受動的な種類の許可リストを適用する方法は、どちらのストアでも働きます。
