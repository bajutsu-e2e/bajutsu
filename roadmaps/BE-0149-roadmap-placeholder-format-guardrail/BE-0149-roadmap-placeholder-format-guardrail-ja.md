## はじめに

[PR #568](https://github.com/bajutsu-e2e/bajutsu/pull/568)は、**BE-0137**と**BE-0138**を修復するものでした。
両項目は、BE-0078／BE-0100より前のテンプレートのままマージされていました。廃止済みの`Track`メタデータ
フィールドが残り、`Progress`セクションがありません。そのため`main`は、`tests/test_roadmap_format.py`の検査に
落ちていました。

これは一度限りの見落としではありません。フォーマットのガードレールには`BE-0149`プレースホルダーをめぐる
構造的な死角があり、その死角が今回の事態を許しました。同じ穴は、テンプレートが今後変わるたびに再現しえます。
この項目では、互いに補い合う3つの変更で、この穴を塞ぎます。

- レビュー中にプレースホルダーの形を検査します。
- テンプレートが変わったのに誰も push しないまま放置される、open な PR のドリフトを捉えます。
- `main`への合流経路のうち、レビューを一切経ない採番処理そのものを堅牢にします。

## 動機

### フォーマット検査は設計上プレースホルダーを見ていない

`tests/test_roadmap_format.py`の`_items()`は、`^BE-(\d{4})-`にマッチするディレクトリだけを集めます。
`BE-0149-<slug>`というプレースホルダーはこの正規表現にマッチしません。そのため、フォーマット検査にも
インデックス生成にも現れません。

これは意図的な設計です。[BE-0089](../BE-0089-merge-time-be-id-allocation/BE-0089-merge-time-be-id-allocation-ja.md)の
Feasibility節は、まさにこの性質に頼っています。`BE-0149`のまま`main`にマージされてから、採番コミットが
`BE-NNNN`にリネームするまでの間に、赤くなる窓を作らないためです。

同じ除外には、BE-0089が想定していなかった副作用があります。プレースホルダーの構造（見出しの集合と順序、
許可されるメタデータフィールド）は、一度も検査されません。scaffold された瞬間から、レビューを経て、
マージされるまでです。正準なテンプレートが提案の作業中に変わり、そのブランチに二度と push が行われなければ、
どうなるでしょうか。プレースホルダーでなくなるまで、誰もそのズレを検査し直しません。

### 実際に起きたこと

BE-0137（[PR #530](https://github.com/bajutsu-e2e/bajutsu/pull/530)）とBE-0138
（[PR #536](https://github.com/bajutsu-e2e/bajutsu/pull/536)）は、次の2つの変更が`main`に着地するより前に
着手されました。

- [BE-0078](../BE-0078-roadmap-status-folders/BE-0078-roadmap-status-folders-ja.md)（2026-06-23）は`Track`を廃止しました。
- [BE-0100](../BE-0100-roadmap-progress-tracking-template/BE-0100-roadmap-progress-tracking-template-ja.md)（2026-06-30）は`Progress`を追加しました。

その後、どちらのブランチも`main`に追随して push し直されることはありませんでした。`make check`は両方の
PRで終始 green のままでした。プレースホルダー除外のせいで、検査すべき対象がそもそも存在しなかったからです。
両方とも2026-07-03に、旧いテンプレートのままマージされました。

その後、採番ワークフローが`BE-0149`を`BE-0137`と`BE-0138`にリネームし、インデックスを再構築しました。
採番ワークフローは、[`roadmap-id.yml`](../../.github/workflows/roadmap-id.yml)が実行する
[`scripts/allocate_roadmap_ids.py`](../../scripts/allocate_roadmap_ids.py)です。リネームは純粋に機械的で、
フォーマット検証を含みません。BE-0089自身の設計にも、リネームコミットが再トリガーする`roadmap-id`の実行は
「プレースホルダーが見つからず no-op で終わる」と明記されています。フォーマット検査を呼び直すという発想は
そもそもありません。

このリネームコミットは、採番処理の bypass App アイデンティティを通じて、保護された`main`に直接 push
されます。PR も required status check も、この経路を止めません。項目の形が初めて検査可能になる瞬間こそが、
違反が`main`に着地するのを誰も止められない瞬間でもあるのです。

`ci.yml`の`check`ジョブは、この`push: main`に対しても再実行されます。しかし、そこで結果が赤くなっても、
誰にも通知されません。今回は@hirosassaが、別件の提案を書いている最中に、たまたま8分後に手元で
`make check`を実行して発覚しただけでした。

### 穴の所在

プレースホルダーは、ライフサイクル全体を、一度も形を検査されないまま通過しえます。ライフサイクルとは、
scaffold、レビュー、テンプレートの変化に取り残されるドリフト、マージ、採番です。最初にようやく検査可能に
なる場所は、レビューを一切経ない`main`への直接 push です。この点に、穴の本質があります。

## 詳細設計

上記のライフサイクルのなかで、それぞれ別の窓を塞ぐ3つの変更を行います。3つを合わせることで、不適合な
項目が検知されずに`main`に到達する余地がなくなります。

### 1. レビュー中にプレースホルダーの構造を検査する

`^BE-(\d{4})-`という検査は単一ではありません。4か所に、独立してハードコードされたパターンです。

- `tests/test_roadmap_format.py`の`_items()`。
- [`scripts/build_roadmap_index.py`](../../scripts/build_roadmap_index.py)。すでに`NUMBERED_DIR_RE`、
  `ITEM_DIR_RE`、`TITLE_RE`という3種類の正規表現を抱えており、しかも`ITEM_DIR_RE`だけが`XXXX`を受け付ける
  というズレが、すでに生じています。
- [`scripts/allocate_roadmap_ids.py`](../../scripts/allocate_roadmap_ids.py)。
- [`scripts/promote_roadmap_items.py`](../../scripts/promote_roadmap_items.py)。

`test_roadmap_format.py`だけを直しても、残り3つは独立してズレ続けます。`promote_roadmap_items.py`の
`misfiled_items()`は、その実例です。同じ理由で`BE-0149`プレースホルダーを除外しています。そのため、未採番の
まま`Status`が変わったプレースホルダーは、誤ったカテゴリのフォルダに置かれたまま検知されません。根本の原因
は同じで、テンプレート形式のドリフトではなく、フォルダのドリフトとして表面化します。

そこで直すべきは、4つのスクリプトが共通で import する、stdlib のみで動く単一の述語です。5個目の場当たり的な
正規表現を増やすのではなく、これを共通化します。例えば`roadmap_ids.py`のようなヘルパーが、id の形を表す
正規表現と、`is_placeholder_dir`／`is_numbered_dir`の組を公開します。

そのうえで`tests/test_roadmap_format.py`の`_items()`を拡張し、番号付きディレクトリと並べて`BE-0149-<slug>`も
収集します。既存の`_check_file`による見出しとメタデータの検査は、実質的な内容を変えずにそのまま適用します。

調整が必要なのは、4桁の番号を前提にしているいくつかの正規表現だけです。対象は、`TITLE_RE`、二言語ヘッダー
リンク、`Proposal`／`提案`メタデータの値です。`BE-0149`ディレクトリにとって、`BE-0149`自体が正当な自己参照で
す。この点は、`test_no_unresolved_be_xxxx_references`がすでに同じ扱いをしています。そこでこれらの検査は、
`BE-0149-<slug>`ディレクトリに置かれている項目に限って、`BE-\d{4}`の代わりに`BE-0149`を許容します。

見出しの集合と順序、`Track`の禁止、`Progress`セクションの必須化は、プレースホルダーにも番号付き項目にも
同じ基準を適用します。

これにより、形が崩れたプレースホルダーは、次にCIが走った時点で`make check`に失敗するようになります。番号付き
項目が今日すでに得ているのと、同じレビュー時点のシグナルです。共通の述語を介して、`promote_roadmap_items.py`
も同じプレースホルダー対応を追加コストなしで得られます。

### 2. open な roadmap PR を、main の変化に合わせて再検査し、修正 PR を開く

対策1だけでは、以後 push が来ないPRを救えません。今回まさにそれが起きました。BE-0078とBE-0100はどちらも、
BE-0137／BE-0138がレビュー中のまま放置されている間に着地しました。両者のCIを再トリガーするものは、何も
なかったのです。

そこで、ワークフローを1つ追加します。共通の id 形状の述語や BE テンプレートの検査に関わるコミットが
`main`に push されたときに起動します。手動実行用の`workflow_dispatch`でも動きます。毎日無条件に走らせる
スケジュール実行ではありません。起点となる危険はテンプレートの変化であって、日付ではないからです。
このワークフローは次のことを行います。

- `roadmaps/**`を変更している open な PR のうち、head ブランチがこのリポジトリ自身にあるもの（フォークでは
  ないもの）を列挙します。フォークのブランチには push も、そこを対象にした同一リポジトリ内 PR も作れない
  ため、`roadmap-promote.yml`がすでに課しているのと同じ制約です。
- 各PRについて、ブランチには何も push せずに、PRのheadと現在の`main`先端をローカルでマージした結果を
  計算します。これは読み取り専用のマージシミュレーションです。そのマージ結果に対して、フォーマット検査と
  インデックス検査を実行します。どちらも、対策1でプレースホルダー対応済みの検査です。
- 検査に失敗したら、PR #568が手作業で行ったのと同じ機械的な修正を実行します。修正は、禁止されたメタデータ
  フィールドの削除と、欠けている必須の`## `セクションの挿入です。挿入するのはテンプレートの骨格で、
  `TBD`の本文と空のチェックリストです。そして、その修正を積んだ小さな pull request を開きます。base は
  stale なブランチです。元のPRには、その修正PRへのリンクを含む単一の目印コメントを投稿または更新します。
  著者は、直すのがまだ安いうちに、ドリフトとワンクリックの直し方の両方に気付けます。

この対策は対策1に依存します。未採番のPRのマージ結果を再検査しても、プレースホルダー対応のフォーマット
検査が存在して初めて、プレースホルダーの形のドリフトを捉えられるからです。対策2は対策1より先に出荷せず、
対策1と同時か、その後に出荷します。

検知の段階でブランチに push しないという制約は譲れません。BE-0089は、承認後にPRブランチへコミットが
push されると、branch protectionの「stale approvalの取り消し」が働き、auto-mergeが止まることを明らかに
しました。採番処理自体を承認時点の経路から外したのは、そのためです。読み取り専用のマージシミュレーション
であれば、ブランチに一切触れずにドリフトを報告できます。レビューの承認を取り消すことはありません。

修正そのものは事情が異なります。修正が実際に着地するのは、著者が修正PRを明示的にマージしたときだけで
あり、自動化された push によってではありません。採番処理のリネームは、実質を伴いません。レビュアーが
再承認すべき中身が何もないため、BE-0089はあえてレビューから見えないままにしています。ここでの修正は、
それとは違い、提案のテンプレート内容そのものを変えます。したがって、修正PRをマージしてブランチの通常の
レビュー要件が再度働くのは、許容できるというより、むしろ正しい振る舞いです。もとの承認は、レビュアーの
知らないうちにすでに形が崩れていたバージョンに対するものだったからです。

対策2が担うのはフィードバックの速さと直す手間であって、安全性そのものではありません。対策1と対策3を
合わせれば、不適合な項目が`main`に到達しないことはすでに保証されています。対策3は、ブランチがどれだけ
古くても、レビューを経ない唯一のタイミングで無条件に検証するからです。対策2は、古びたPRが検知されずに
放置される日数を縮めます。直す作業も、「PR #568のように差分を手で作り直す」から「生成済みのPRをレビュー
してマージする」に変わります。

### 3. 採番ワークフローに、main へ着地する前の自己検証を持たせる

`.github/workflows/roadmap-id.yml`は、採番コミットと push の間に、ガードを1つすでに実行しています。
[`scripts/check_renumber_diff.py`](../../scripts/check_renumber_diff.py)です。このガードは、コミットの
影響範囲を`roadmaps/**`に限定します（BE-0089）。

並行して2つ目のガードを追加するのではなく、この既存のガードを拡張します。`check_renumber_diff.py`の
直後、`git push`の直前に、対策1で導入する共通の述語／検査を、リネーム後の項目に対しても呼び出します。

検査に失敗した場合は、push を中止します。`main`はマージ直後の状態のまま残り、壊れたコミットは着地しません。
そのうえで、違反した項目とその内容を名指しして、ワークフローを目に見える形で失敗させます。これにより、
`main`が静かに赤いまま放置されるのではなく、人間がすぐに後続のPRで修正できるようになります。

ここで呼び出す検査は、対策1が`test_roadmap_format.py`から切り出す stdlib のみの関数のままにします。pytest
の呼び出しにしてはいけません。`roadmap-id.yml`は今日、依存パッケージのインストールを一切行わない設計です。
呼び出しているスクリプトはいずれも stdlib のみで動きます。対象は、`allocate_roadmap_ids.py`、
`build_roadmap_index.py`、`check_renumber_diff.py`です。この設計は、BE-0089の「bypass アイデンティティの
保護」節が掲げる目的に合致しています。特権を持つ、bypass トークン保持ジョブの依存関係を、できるだけ小さく
保つことです。テストファイルを再実行するためだけに`uv sync`と pytest を組み込めば、BE-0089が意図的に排除した
はずの「トークンと一緒にサードパーティ製コードが動く」という面を、また持ち込んでしまいます。

これは、レビューを一切経ない経路に対する多層防御です。採番コミットは bypass アイデンティティを通じて、
保護された`main`に着地します。PRも required check もありません。そのため、採番処理自身がゲートを内蔵する
必要があるのです。

## 検討した代替案

- **ブランチを最新化してからマージすることを必須にする、あるいは merge queue を使う。** 却下します。
  ブランチのリベースのために push を強制すると、BE-0089が採番処理を承認時点の経路から外したときに回避した
  「stale approvalの取り消し」と同じ問題が起きます。roadmapの運用が頼っているauto-mergeの流れそのものを、
  止めてしまいます。
- **フォーマット検査の拡張と採番ゲート（対策1・3）だけで済ませ、定期的な再検査（対策2）を省く。**
  対策1と対策3だけで、不適合な項目が検知されずに`main`に到達しないという中核の安全性は、すでに保証されて
  います。対策3は、ブランチがどれだけ古くても、マージ時点で無条件に検証するからです。この代替案が手放すのは
  フィードバックの速さです。対策2がなければ、BE-0137／BE-0138のようなブランチは、対策3がマージ時点で
  捕まえるまで、形が崩れたまま何日も静かに放置されえます。対策2は、「穴を塞ぐために必須」ではなく、それとは
  別に価値のある改善として位置づけます。
- **プレースホルダー除外そのものをやめ、どこでも4桁の番号の形を要求する。** 却下します。これはまさに
  BE-0089が避けようとした設計です。プレースホルダーは、まだ採番されていない状態が正当です。番号付き項目と
  同じ形を強制すれば、BE-0089が取り除いたマージから採番までの窓を呼び戻すことになります。
- **roadmap固有の対応ではなく、`push: main`のCIが赤くなったこと全般を通知する（すべてのワークフローを対象に
  したSlack通知など）。** それ自体は有用な多層防御ですが、論点が異なります。発見までの時間を縮めるだけで、
  壊れたコミットが着地すること自体は防げません。マージ前に表面化するドリフトには、何も効きません。単独では
  1から3の代替にはなりません。
- **対策2の機械的な修正を、修正PRを開く代わりに stale なブランチへ直接 push する。** 却下します。他人の
  ブランチにレビューを経ないbotのコミットが着地するのは、著者が任意のタイミングでマージできる修正PRよりも、
  驚きが大きいからです。しかも、採番処理についてBE-0089が回避した問題と同じく、著者が修正の中身を確認する
  機会もないまま stale approval を取り消してしまいます。修正PRであれば、同じ直し方を提供しつつ、マージする
  かどうか、その結果として再レビューが必要になるかどうかを、著者の明示的な選択に委ねられます。

## 進捗

> 開発の進行に合わせて常に最新の状態に保ってください。チェックリストは *詳細設計* の MECE な
> 作業分解（作業の単位ごとに 1 つ）に対応し、ログには変更内容と時期（古い順）を PR へのリンクと
> ともに記録します。

- [x] stdlib のみで動く共通の id 形状の述語を切り出し、`tests/test_roadmap_format.py`・`scripts/build_roadmap_index.py`・`scripts/allocate_roadmap_ids.py`・`scripts/promote_roadmap_items.py`に（プレースホルダー対応の形で）採用する
- [x] テンプレートに関わるコミットが`main`に着地したときに起動し、open な roadmap PR を現在の`main`に照らして読み取り専用で再検査し、ドリフトがあれば stale なブランチに対して修正PRを開くワークフローを追加する（上記に依存）
- [x] `roadmap-id.yml`における`scripts/check_renumber_diff.py`の呼び出しを拡張し、`git push`の前に共通の検査も実行する

対策1と対策3は先に着地しました（[#600](https://github.com/bajutsu-e2e/bajutsu/pull/600)）。共通の id 形状の述語は`scripts/roadmap_ids.py`に置き、フォーマット検査は stdlib のみで動く`scripts/check_roadmap_format.py`へ移して（プレースホルダー対応済み）、採番ワークフローは push の前に`scripts/check_renumber_diff.py`で自己検証します。続けて対策2も着地しました。`scripts/check_stale_roadmap_prs.py`が、open な同一リポジトリ内の roadmap PR ごとに、その PR 自身のファイルを現在のテンプレートに照らして読み取り専用のオーバーレイで再検査し（PR のブランチには push しません）、ドリフトを検知したら`scripts/fix_roadmap_drift.py`の機械的な修正（PR #568 が手作業で行ったのと同じ狭い形の修正）で、stale なブランチを base とする小さな修正PRを開きます。これらは`roadmap-drift-check`ワークフローが結びつけます。3つの対策がすべて揃い、この項目は完了しました。
