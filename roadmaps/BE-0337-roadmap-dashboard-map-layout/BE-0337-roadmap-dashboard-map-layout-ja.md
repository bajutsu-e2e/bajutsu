## はじめに

ロードマップダッシュボードの関係図表示について、その配置を路線図の形に置き換えます。次の形です。

- トピックごとに横1行を引く。
- その行の項目を ID 順に並べる。
- 関係を持つ項目どうしを曲線でつなぐ。

[BE-0335](../BE-0335-roadmap-dashboard-relationship-graph/BE-0335-roadmap-dashboard-relationship-graph-ja.md) が与えたものは、そのまま残ります。同じメタデータから読む3つの関係も、状態ごとの色も、検索ボックスとステータスチップとの組み合わせも変わりません。変わるのは、項目がどこに置かれるか、そして読者がどうたどるかだけです。表示の名前は、示すものに合わせて Graph から Map に改めます。

新しい配置からは2つのことが導かれます。

- レイアウトが、各項目のトピックと ID だけで決まる純粋な関数になります。計算はビルド時に Python が1度だけ行い、完成したスケーラブルベクターグラフィックス（SVG）の座標として配信します。ブラウザは力学モデルのシミュレーションをまったく動かしません。
- すべての項目が読者に予測できる位置を持つため、指し示すだけで内容が読めるようになります。ポインタを重ねた項目の名前と状態が図の下のキャプション行に出て、その項目と、つながっている線と、線の先の項目以外は暗くなります。

## 動機

力学モデルの配置が答えるのは「このグラフの形はどうなっているか」であり、それ以外にはほとんど答えません。配置は、1つの大きな塊と、その周りに散らばる小さな成分へ落ち着きます。個々の項目の位置は、読者が頼れる意味を持ちません。項目はシミュレーションに押された場所に座ります。「さっき見ていた項目はどこか」という同じ問いの答えが、ロードマップが変わるたびに変わります。1つの項目を探したい読者は、どこを見ればよいかを知るのではなく、探し回ることになります。

路線図は、それと引き換えに、読める固定の住所を項目へ与えます。行はトピックであり、読者が Cards 表示ですでにたどっている区分なので、目当ての行にはすぐ目が届きます。行の中では項目が ID 順に並ぶので、隣にいるのは近い時期に提案された項目です。もつれた塊だった図が、索引を持つ絵になります。項目のトピックを知っていれば行がわかり、番号を知っていれば行のどのあたりを見ればよいかがわかります。

配置を変えることで、検査できなかった部分も1つ消えます。力学モデルの出力はパラメータの出来次第なので、パラメータを変えるたびに図を目で見て判断するほかなく、その正しさをテストで固定できませんでした。トピックと ID から導いた座標は、ただのデータです。次の3つを、テストで主張できます。

- 項目の行が、そのトピックの行であること。
- 行の中で、項目が ID の昇順に並ぶこと。
- どの線も、描かれた項目2つで終わること。

この変更はドキュメントサイトに閉じるので、どの絶対的指針（[`CLAUDE.md`](../../CLAUDE.md)）にも抵触しません。

- 大規模言語モデル（LLM）は、このページの近くに一切現れません。
- `run` や継続的インテグレーション（CI）の合否判定の経路も、ここを通りません。
- レイアウトはメタデータが生む項目に対して汎用なので、テスト対象のアプリケーション固有の要素も持ちません。

配置をブラウザからビルドへ移すことは、決定性を曲げるのではなく強めます。同じロードマップからは同じ座標が出るようになり、それを信頼ではなくテストで確かめられます。

## 詳細設計

関係図表示は [`scripts/build_roadmap_dashboard.py`](../../scripts/build_roadmap_dashboard.py) が生成します。現在は、ノードと辺を JavaScript Object Notation（JSON）として出力し、配置をインラインのスクリプトに任せています。作業は、互いに重複がなく全体を覆う（MECE な）次の単位に分かれます。

1. **ビルド時のレイアウト計算**。描く項目を座標へ写す純粋な関数を追加します。
   - 項目をトピックごとにまとめる。
   - トピックの順序は、共有インデックスがすでに持つ順に従う。
   - 各トピックの項目を ID 順に並べる。
   - 行の *i* 番目の項目を、その行の一定の間隔の位置に置く。

   関数が受け取るのは項目だけで、返すのは行と、ノードの位置と、図全体の寸法です。メタデータ以外の入力を持たないので、同じロードマップからは常に同じ座標が出て、テストでそれを主張できます。
2. **行ごとに詰めること、そしてそれを明記すること**。項目は、描かれる全項目の中での順位ではなく、自分の行の *i* 番目の位置に置きます。すべての行で1本の共通した ID 軸を使うほうが、情報量では優れています。同じ列が、どの行でも同じ時期を意味するからです。10件程度のロードマップなら、その形になるでしょう。しかし、この規模では成り立ちません。約200件を1本の軸に並べると、図の幅は約14,000ピクセルになります。そのほとんどは、数件しか持たない行の余白です。行ごとに自分の項目だけを詰めれば、幅はその7分の1程度に収まります。代償として、列は行をまたいでそろわなくなります。キャプションには、配置をそのまま書きます。項目が ID 順に並ぶのは**行の中**である、と明記すれば、図にないそろい方を読者が読み取ることはありません。
3. **行**。描く項目を1つ以上持つトピックごとに、1本の行を描きます。行は、図の幅いっぱいに引いた罫線と、左の余白に右寄せで置いたトピック名からなります。描く項目を持たないトピックには行を与えないので、空の行は図に現れません。
4. **曲線のつなぎ**。関係は直線ではなくパスで描き、両端の位置に応じて形を変えます。
   - 2つの項目が同じ行にあれば、行の上に膨らむ弧を描く。
   - 別の行にあれば、一方の行から水平に出て他方の行へ水平に入る曲線を描く。

   どちらも、行を横切る斜め線ではなく、1本の連続した線として読めます。辺の意味は BE-0335 のまま変えません。相互に張られた `関連` は1本の無向線です。`由来` と `後継` は有向のままで、矢じりと破線の種類もそのままです。
5. **ノード**。各項目は、3つの部品を持つリンクとして描きます。
   - ポインタとタッチの両方で押しやすい大きさの透明な円
   - 状態の色を持つ小さなドット
   - その下に置く ID のラベル

   リンク先は項目の GitHub 上のファイルなので、キーボードからも辿れ、新しいタブでも開けます。
6. **項目を指し示したとき**。ポインタを重ねるかフォーカスを当てると、その項目と、触れている線と、線の反対側の項目以外のノードと線が暗くなります。図の下のキャプション行には、その項目の ID、タイトル、状態が書き込まれます。この行は既定の文を持つライブリージョンです。スクリーンリーダーを使う読者にも、目で見る読者と同じ内容が伝わり、図が黙って何も語らない状態になりません。
7. **シミュレーションの撤去**。力学モデルの計算、キャンバスに収めるための拡大縮小、そしてドラッグ・平行移動・拡大縮小の処理を、インラインスクリプトから削除します。残るのは、絞り込みとの組み合わせと、上の指し示しの挙動です。すべての項目が固定の住所を持つ地図は、ドラッグする必要がありません。容器の側がスクロールするので、平行移動と拡大縮小も、それらを必要にしていたシミュレーションと一緒に役目を終えます。これによって約200行のブラウザ側のコードが消え、同時に、出力をテストで固定できなかった唯一の部分もなくなります。
8. **図をページに収めること**。地図は横方向にスクロールする容器で包み、図には自然な大きさと同じ最小幅を与えます。ラベルが読めるように描いた大きさより小さく縮められることは、ありません。読者は、縮んだ図を目を細めて見るのではなく、広い図をスクロールします。
9. **表示の改名**。表示切り替えの3つ目を Graph から Map に改め、ページ冒頭の説明文も配置を説明するものに書き換えます。保存する設定はキーも `graph` という値もそのままにします。この変更より前にこの表示を選んでいた読者は、変わらずこの表示にたどり着きます。
10. **テスト**。BE-0335 のペイロードのテストを、レイアウトのテストに置き換えます。確かめる内容は次のとおりです。
    - 描く項目が、ちょうど1度ずつ配置されること。
    - 項目の行が、そのトピックの行であること。
    - 行の中で、項目が ID の昇順に並ぶこと。
    - どのパスの両端も、描かれた項目であること。
    - 項目を持たないトピックの行が、出力されないこと。
    - 図全体が、申告した寸法に収まること。

    ブラウザを必要としないので、ゲートは速いまま、LLM とも無縁のままです。

[`docs/`](../../docs/README.md) 配下のドキュメントに対応する修正は必要ありません。ダッシュボードに言及しているページは、ダッシュボードが何のためのものかを説明していて、どの表示を備えるかも、どう描かれるかも書いていないからです。将来そこに表示を列挙する記述が生まれたときは、同じ変更で更新します（[BE-0113](../BE-0113-design-doc-realignment/BE-0113-design-doc-realignment-ja.md)）。

## 検討した代替案

- **力学モデルの配置を残したまま、地図らしい操作部品を足す**。ズームボタン、ミニマップ、詳細パネルといったものです。採用しませんでした。この配置が答えようとしている不満は、項目に固定の位置がないことです。シミュレーションの周りにどんな部品を置いても、位置は定まりません。操作の補助は、予測できない絵を動かしやすくはしますが、読みやすくはしません。
- **すべての行で1本の共通した ID 軸を使う**。この規模では採用しませんでした。理由は作業単位2に書いたとおりで、幅が約14,000ピクセルになり、そのほとんどが余白になるためです。描く項目が桁違いに減れば再考の余地がありますが、ロードマップの方向からするとその見込みは薄いといえます。
- **行の中の順序を ID 以外にする**。関係の数の多い順に並べて中心の項目を先頭に置く案や、状態順に並べる案です。採用しませんでした。ID は、読者がページを開く前からすでに知っている唯一の手がかりで、位置が予測できるのはそのおかげです。関係の数も状態もロードマップが変われば変わるので、何も変わっていない項目まで動いてしまいます。
- **両方のレイアウトを残し、4つ目の表示にする**。採用しませんでした。1つの問いに対する答えをダッシュボードが2つ抱えることになり、しかもこの項目は、力学モデルのほうが劣ると主張しています。撤去すればそのコードも一緒に消え、使われないシミュレーションを保守し続けずに済みます。
