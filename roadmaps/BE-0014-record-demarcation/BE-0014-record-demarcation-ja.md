## はじめに

本提案は、Bajutsu が増やしつつある著述の入り口の役割分担を定義します。対象は、AI record ループ、操作キャプチャ（[BE-0012](../BE-0012-action-capture-record/BE-0012-action-capture-record-ja.md)）、シナリオ GUI（グラフィカルユーザーインタフェース）エディタ（[BE-0013](../BE-0013-scenario-gui-editor/BE-0013-scenario-gui-editor-ja.md)）です。シナリオがこれらの間をどう移動するかも明文化します。

*意図*からの著述、*実演*からの著述、既存シナリオの*編集*は、それぞれ別の問いに対する別の答えです。それでも 3 つとも、単一の `Scenario` を生成し消費しなければなりません。そうしてはじめて、著者は同じファイルに対して 3 つを自由に組み合わせられます。本提案は、どの入り口をいつ選ぶかを定めます。仕組みを要する唯一の変換も規定します。構造的にキャプチャした、または手で編集したシナリオに、意図推論だけが供給できるアサーションを補強する変換です。

## 動機

「人が検証してほしいこと」からシナリオへ至る経路は、これまで AI record ループだけでした。その後ろに、2 つの経路が続きます。

- 操作キャプチャ（BE-0012）は、実演からフローを著述します。オフラインで、API キー無しで動きます。
- GUI エディタ（BE-0013）は、既存シナリオを、スクリーンショット駆動の要素ピッカーで編集します。

3 つの著述の入り口が同時に到着することは、仮想ではなく現実のリスクです。境界を明示しなければ、シナリオの形が乖離して増えます。同じセレクタと保存の配管が 3 度重複します。どの入り口を開けばよいか分からない著者も残ります。3 つの入り口は実際に異なる問題を解くので、統合は答えになりません。答えは、境界を明示的に引き、シナリオファイルを 3 つの入り口の共有物にすることです。

境界は、著述の*入力*で引きます。

- **AI ループ**は、*意図*、つまり自然言語のゴールから著述します。著者が正確なステップをまだ知らないとき、フローに探索が要るとき、ゴールを実行するより述べるほうが容易なときに向きます。ステップと検証アサーションの両方を推論します。`ANTHROPIC_API_KEY` が必要で、LLM（大規模言語モデル）の往復を消費します。
- **操作キャプチャ**は、*実演*、つまり起動済みデバイス上の実操作から著述し、キャプチャ時に安定セレクタへ解決します。著者がすでにフローを知っているとき、オフラインで高速にしたいとき、記述より実演が容易なときに向きます。API キーは不要で、解決は純粋に構造的です。出力はステップのみで、アサーションは推論しません。
- **GUI エディタ**は、既存シナリオを*編集*します。著者がスクリーンショット上で要素をクリックすると、最も安定したセレクタを `doctor` スコア付きで得られます。著者は、ステップとアサーション DSL（ドメイン固有言語）をフィールド単位で調整できます。どの入り口が生成した下書きでも、生の YAML を手で書かずに磨くときや、脆いセレクタを直すときに向きます。

本提案は、この 3 つがもたらすリスク、すなわち乖離した形式、3 重化した配管、混乱する著者を、先回りして防ぎます。

## 詳細設計

### 単一のシナリオ、3 つの入力、単一の保存経路

境界は、出力ではなく、つねに著述の*入力*で引きます。3 つの入り口はいずれも、同一の `Scenario`（steps + `expect`）を生成し消費します。3 つとも、同じ決定的な `run`、`codegen`、レポートに供給します。下流は、どの入り口が生成したかを知る必要がありません。3 つのいずれも、[Tier 2](../../docs/ja/glossary.md#2-つの層) / CI ゲートには入りません。

3 つの入り口を、ばらばらな道具にせず互いに置換可能にするものは、**3 つとも単一の著者所有の保存経路を通って書く**ことです。その経路が `bajutsu/serve/scenarios.py:ScenarioScope.save()` / `.authored()` です。

- AI ループは、すでにこの経路で書きます（`record` → `authored()`）。
- キャプチャは、解決した各ステップを追記して、この経路で再保存します（BE-0012）。
- エディタは、同じ `*.yaml` をこの経路で読み書きします（BE-0013）。

保存経路が共有で、形式が単一です。したがって、`$EDITOR` での手編集、キャプチャしたステップ、AI が著述した下書き、ピッカーでの編集は、すべて同じ成果物です。成果物は PR でレビューでき、黙って書き換えられることはありません。書き込みはスコープが所有します。この性質は、ローカルのオンディスクストアでも、サーバ側のストレージストア（[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md)）でも同一に成り立ち、どの入り口も違いを知る必要がありません。

次の表は、役割分担を一度だけ示します。著者がどの入り口を開けばよいか分かるためのものです。

| 著述の入力 | 入り口 | 出力 | キーの要否 | 選ぶ場面 |
|---|---|---|---|---|
| *意図*（ゴール） | AI record ループ（`record.py`） | ステップ **と** アサーション | 必要 | まだ知らないアプリを探索する。実行するよりゴールを述べる |
| *実演*（操作） | 操作キャプチャ（BE-0012） | ステップのみ | 不要 | 知っているフローをオフラインで高速に再現する。記述より実演する |
| *編集*（既存ファイル） | GUI エディタ（BE-0013） | ステップ / アサーションの編集 | 不要 | 下書きを磨く。YAML を手で書かずに脆いセレクタを直す |

### キャプチャ / 編集 → アサーション補強（明文化すべき唯一の変換）

入り口どうしの変換は非対称で、仕組みを要するのは一方向だけです。

3 つの入り口は同じ `Scenario` を生むので、**キャプチャした、または編集したシナリオは、すでに第一級のシナリオ**です。著者は追加のステップ無しに、手編集、実行、`codegen` への投入ができます。「キャプチャ → シナリオ」の変換は恒等で、「エディタ → シナリオ」は保存そのものです。逆向きは、AI が著述したシナリオを、キャプチャし直すか編集し直す操作です。これは通常の編集または再記録であり、特別な仕組みは要りません。

設計を要する唯一の向きは、**構造的なシナリオをアサーションで補強する**ことです。キャプチャとエディタは*ステップ*を生みますが、`wait` や `expect` が検証すべき*意図*は推論できません。そのため、キャプチャした、または編集したばかりのシナリオは、ステップ列が完全でもアサーションが薄い、あるいは無いことがあります。そのシナリオを*検証済み*のシナリオに変えるのは意図推論であり、AI ループの仕事です。受け渡しは 3 手順です。

1. 著者は、ステップはあってもアサーションが薄いシナリオを持っています。シナリオは、キャプチャ由来、エディタ由来、または手書きのいずれかです。
2. 著者は、その既存のステップ列に対して AI ループを**補強モード**で起動します。ループはステップを再生または読み取り、各ステップが何を確立しようとしているかを推論します。アサーションを欠くステップに対して、検証アサーション（`expect` の項目、settle `wait`）を提案します。
3. 提案は、著者が承認または却下する**レビュー可能な差分**として届きます。黙って書き換えることはなく、「AI 出力は常に提案差分」と整合します。差分を承認すると、同じ `ScenarioScope.save()` を通って書き戻されます。補強済みシナリオは同じ成果物のまま、検証済みになります。

これにより、入り口どうしが端から端まで組み合わせ可能になります。著者は、キャプチャでフローを実演し（オフライン、キー不要）、エディタでセレクタを整えます。それから一度だけキーを使い、AI ループにアサーションを足してもらいます。最初から著述し直す必要はありません。

逆向きの境界は固いままです。**キャプチャは決して意図を推論しません。** ステップが何を検証すべきかの推論は、AI の著述・調査の役割です。キャプチャは純粋に構造的であり続けるので、オフラインで API キー不要という保証は無条件です。AI はアサーションを提案しますが、pass/fail を決めることは決してありません。

### serve における統合された著述面

3 つの入り口は、`serve` に取り付けた 3 つの別々の道具ではありません。**1 つの開いているシナリオ**に対する 3 つのモードです。`serve` UI は、すでにシナリオをホストしています（[BE-0011](../BE-0011-local-web-ui-serve/BE-0011-local-web-ui-serve-ja.md)）。シナリオビュー、生の YAML テキストエリア、画面ごとのスクリーンショットと要素ツリーを含む実行レポートです。残りの 2 つの入り口は、その同じビューを拡張するもので、新しいページは足しません。

- **エディタ**（BE-0013）は、シナリオビューを、フィールド単位の構造化編集に変えます。スクリーンショットが真実の源で、要素ピッカーがセレクタを解決します。
- **キャプチャ**（BE-0012）は、同じビューを「実演」モードにしたものです。著者がライブのスクリーンショット上でアクションをマークします。Bajutsu が各アクションをセレクタへ解決して代理実行し、開いているシナリオへステップを流し込みます。
- **補強**は、開いているシナリオに対するアクション（「アサーションを提案」）です。AI ループの差分を、同じビュー内にインラインで提示します。

著者は 1 つのシナリオを開き、その上で著述モードを切り替えます。最初に道具を選ぶのではありません。実演でステップを足し、ピッカーでセレクタを直し、提案でアサーションを足します。

ピッカーと `doctor` スコアのコンポーネントは、キャプチャとエディタで共有されます（BE-0012 と BE-0013 の双方がこれを明記しています）。すべてのモードが単一の `ScenarioScope` を往復するので、モードを切り替えても、ファイルの形は変わりません。

キャプチャには、アーキテクチャ上の逸脱が 1 つあります。起動済みターゲット向けに、リクエストをまたいで保持するライブの `Driver` です。この逸脱は、キャプチャモードのセッション内に閉じ、純粋な resolver / emitter コアの外に留まります（BE-0012）。エディタと生のテキストエリアは、実行が取得済みの成果物に対してステートレスなままです。

### prime directive、Tier 分け、ゲート

この構えは、すべての prime directive を保ちます。

- **AI は著述し調査するが、決して判定しない。** AI ループの関与は、[Tier 1](../../docs/ja/glossary.md#2-つの層) の著述（意図 → ステップ + アサーション）と、補強差分の*提案*に閉じます。キャプチャとエディタはモデルを呼びません。どの入り口も、決定的な `run` / CI ゲートに LLM 呼び出しを入れず、pass/fail は機械のみのままです。
- **まず決定性。** どの入り口も、同じ安定性ラダーを下って、安定 `id` で選択します。どの入り口も、固定 sleep ではなく条件待機を使い、曖昧なセレクタは推測せず提示します。`resolve_unique` のルールはどこでも同じです。キャプチャとエディタは著述時に、ランナーは実行時に適用します。
- **app-agnostic。** 単一の `Scenario` 形式と単一の保存経路が、ツールをターゲット非依存に保ちます。3 つの入り口はいずれも `targets.<name>` を読み、アプリのシナリオディレクトリへ、同じスコープを通して同じ方法で書きます。アプリ固有のものが入り口へ漏れることはありません。

Tier 分けは、キーの要否という境界で明快に割れます。**AI の部分はキーを要します**（`record` ループと補強モード）。**構造的な部分は要しません**（キャプチャ、エディタ、結果の実行）。いずれの入り口も、Tier 2 の run / CI ゲートへの経路ではありません。どの入り口も、決定的なランナーがその後で単独で判定するシナリオを、著述または編集するだけです。

## 検討した代替案

* **各入り口を、別々のシナリオ形を持つ別々のコマンドに分ける。** 不採用です。乖離した形式は `run`、`codegen`、レポートを断片化し、「人間が所有する単一の YAML」モデルを壊します。共有の単一 `Scenario` と単一の `ScenarioScope.save()` 経路こそが、入り口を競合ではなく相補にし、ばらばらではなく組み合わせ可能にします。
* **キャプチャ（またはエディタ）自身にも、ヒューリスティックに、またはインラインの AI 呼び出しで、アサーションを推論させる。** 不採用です。意図の推論は AI の仕事であり、結果はレビュー可能な提案として届かねばなりません。キャプチャした、または編集したファイルに黙って焼き込んではなりません。キャプチャとエディタを純粋に構造的に保てば、オフラインで API キー不要という保証を守れます。アサーション推論をすべて AI ループの補強モードに通せば、「AI は差分を提案し、人間が承認する」という約束を 1 か所にまとめられます。
* **1 つのシナリオに対するモードではなく、`serve` 内の 3 つの別々の道具にする。** 不採用です。別々の道具は、ピッカーと doctor スコアのコンポーネント、および保存の配管を重複させます。また、どの入力を持っているか分かる前に、著者へ道具を選ばせてしまいます。1 つの開いているシナリオに対するモードなら、コンポーネントを共有し、作業の都合に応じて切り替えられます。
* **棲み分けを文書化せず、運用に任せて自然に落ち着かせる。** 不採用です。3 つの著述の入り口が近接して登場する以上、境界を明示しないことこそが、重複コードとユーザーの混乱を生みます。本提案が先回りして防ごうとしているコストそのものです。
