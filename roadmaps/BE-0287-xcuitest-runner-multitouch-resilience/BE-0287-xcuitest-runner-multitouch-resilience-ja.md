## はじめに

オンデバイスのエンドツーエンド（E2E）ジョブ `xcuitest (multi-touch)` は、不安定に失敗します。二本指ジェスチャの実行中に XCUITest runner が到達不能になり、ドライバは、実行の途中で runner がクラッシュした状況と、操作がアプリに届かなかった状況とを区別できないからです。

本項目は、実行途中に起きた runner クラッシュに対して、runner チャネルを頑健にすることを提案します。

- runner が停止したことを検出します。
- 停止を、明確で決定論的な runner クラッシュの失敗として表面化させます。
- 冪等性が許す場合には、runner の復帰を待って処理を続けます。

この変更がなければ、取りこぼしたピンチや回転が、アサーションの不一致に化けてしまいます。

変更範囲は xcuitest バックエンドの内側に収まります。触れる面は、runner、リトライの継ぎ目、決定論的な判定の 3 つだけです。後続の単位では、オンデバイスの適合性スイートが後から表面化させた、別種の stale の原因を解消します。runner がタップ時に行う属性の再チェックが、まだ落ち着いていないレイアウトを「消えた要素」と読み違えていました。

## 動機

あるプルリクエストの iOS E2E ワークフローを一度再実行したところ、この不安定さが直接現れました。`xcuitest (multi-touch)` ジョブを 3 回試行して、1 回が成功し、2 回が別々の壊れ方で失敗しました。対象のシナリオは [`gestures_multitouch.yaml`](../../demos/showcase/scenarios/gestures_multitouch.yaml) です。showcase アプリの二本指ターゲットをピンチと回転で操作し、各ターゲットのミラーされたアクセシビリティ値が `pinched` または `rotated` に変わることをアサートします。

2 回の失敗は原因を共有しますが、現れ方が異なります。

- **runner のクラッシュ。** runner がホストするループバックサーバが接続を受け付けなくなり、`GET /screenshot` の呼び出しが `XcuitestChannelError: runner channel GET /screenshot failed: [Errno 61] Connection refused` を送出しました。
- **応答しなくなった runner。** runner が約 30 秒のあいだ `GET /health` に応答しませんでした。`runner channel GET /health failed ... Connection refused` のリトライが連続して現れました。runner が復帰したときには、ピンチがアプリに届いていませんでした。そのため、最終アサーションは `expect: expected equals='pinched' but actual='idle'` を読み取りました。

二本指の操作が runner を不安定にします。その乱れが、ハードなチャネルエラーとして出るか、静かに取りこぼされたジェスチャとして出るかは、タイミング次第です。

この不安定さは、3 つの意味で高くつきます。

- 必須の集約チェック `E2E (iOS)` がランダムに失敗すると、ゲートへの信頼が損なわれます。メンテナは、この失敗を本物の回帰と区別できません。そのため、反射的な再実行か、無駄な調査のどちらかを招きます。
- 再実行のたびに、macOS ランナーの従量課金枠を消費します。このジョブは、ジェスチャに到達する前に、アプリをビルドして Simulator を起動するからです。
- `actual='idle'` というメッセージは、調査者を誤った場所に向かわせます。ピンチという操作が壊れているかのように読めますが、実際に起きたのは、runner がジェスチャを取りこぼしたことです。

既存のリトライの継ぎ目（[BE-0207](../BE-0207-xcuitest-channel-transient-retry/BE-0207-xcuitest-channel-transient-retry-ja.md)）は、この状況を扱いません。もともと扱う設計でもありません。BE-0207 の継ぎ目は、1 回のチャネル呼び出しの中で起きる、*一時的な*ブレを吸収します。対象となる要求を計 3 回まで試行し、試行の間は 0.5 秒の指数バックオフを取ります。予算全体は、およそ 1.5 秒で尽きます。30 秒間いなくなった runner は、この予算を何倍も超えます。

この継ぎ目は、書き込みに対して意図的に保守的でもあります。すでに届いた副作用のある要求は、再送しません。届いたかもしれないピンチを再送すると、二重に操作してしまうおそれがあるからです。したがって、予算を大きくしても、継ぎ目だけでは取りこぼしたジェスチャを覆い隠せません。実行途中のクラッシュからの回復は、1 秒未満のブレをならすのとは別の問題です。専用の仕組みが必要です。

## 詳細設計

作業は 5 つの単位に分かれます。

- Unit 1 と Unit 2 は、runner 側の根本原因に対処します。実機での反復が必要です。
- Unit 3 と Unit 4 は、Python のドライバチャネルを強化します。模擬トランスポートに対して、テストできます。
- Unit 5 は、オンデバイスの適合性スイートが後から表面化させた、別種の stale の原因を解消します。

各単位は依存順に並びますが、別々のプルリクエストとして着地できます。

**Unit 1 — 二本指操作下での runner クラッシュを特徴づける。** 根本原因を、推測ではなく事実として突き止めます。runner ソースを静的に解析するか、Simulator で失敗を再現して runner 側の診断ログを取得します。未解決の問いには、3 つの候補があります。

- ピンチや回転の操作そのものが、XCUITest runner プロセスをクラッシュさせる。
- 操作が、runner がホストするループバック HTTP サーバをハングさせる。
- runner の下にある `idb_companion` が死ぬ。

実際には、ソースから答えを直接読み取れる場合があります。`HTTPServer` の直列 accept ループとバックログ 1 という構造から、ハングは必然的に起きます。その場合、3 つの候補のうちどれが実際に失敗するかを、新たなオンデバイス採取なしで確定できます。この単位が生むのは診断であり、コードではありません。

**Unit 2 — 根本原因をあるべき場所で直す。** Unit 1 が、runner 自身のジェスチャ処理（[`BajutsuKit/`](../../BajutsuKit) の XCUITest 側）の欠陥を示したとします。その場合は、そこで欠陥を直し、二本指の操作が runner を不安定にしないようにします。原因が、companion や、Bajutsu が所有しない下位層にある場合もあります。その場合、この単位では上流の制約を記録し、Unit 3 に引き継ぎます。Unit 3 が、その制約を致命的ではなく、耐えられるものにします。どちらの道を取るかは Unit 1 の診断が決めるので、2 つの単位は順に書きます。

**Unit 3 — 実行途中のクラッシュを検出し、決定論的に表面化させる。** チャネルが、1 回の呼び出しのリトライ予算を超えて到達不能なままだとします。このとき、ドライバは、実行を誤解を招くアサーションに漂わせず、2 つの結果のあいだを決定論的に選びます。

- 冪等な読み取り（`GET`、または runner に届かなかった書き込み）では、既存の `await_ready` のヘルスポーリングを再利用して runner の復帰を待ち、処理を続けます。読み取りの再発行は安全だからです。
- すでに届いた可能性のある、副作用を伴う書き込みでは、黙って再送しません。クラッシュを名指しする専用の runner クラッシュ診断で、失敗します。実行は `actual='idle'` ではなく、runner がジェスチャの途中で死んだという正直なメッセージで止まります。

この区別は、リトライの継ぎ目がすでに引いている `delivered` の分割そのものです。そのため、この単位は新しい仕組みを作らず、既存の継ぎ目を拡張します。

**Unit 4 — すべての回復を記録に残す。** [`CLAUDE.md`](../../CLAUDE.md) のプライムディレクティブ 2 は、決定論を優先します。本物の失敗を成功にならすことを禁じるので、回復を黙って済ませてはなりません。回復するたびに、リトライの継ぎ目が再送したブレを記録するのと同じくらいはっきりと、クラッシュを記録します。そうすれば、クラッシュして回復した実行が、一度もクラッシュしなかった実行と見分けられなくなることはありません。回復した実行は、再現可能で監査可能なままです。冪等に回復できないクラッシュは、Unit 3 が挙げる大きな失敗のままです。

届いた書き込みを再適用しないのは、Unit 3 の役割です。この単位が足すのは、可観測性の保証だけです。

**Unit 5 — まだ落ち着いていないレイアウトを「消えた要素」と読み違えないようにする。** オンデバイスの適合性スイートが、上記のマルチタッチのクラッシュとは別種の stale の原因を表面化させました。`test_text_selection` の最初の `tap` が、`element vanished (stale handle)` で断続的に失敗したのです。

runner はタップ時に、記録した位置パスから live な `XCUIElement` を再導出します。操作する前に、記録済みの属性を再チェックします（[BE-0105](../BE-0105-xcuitest-single-snapshot-query/BE-0105-xcuitest-single-snapshot-query-ja.md)）。この再チェックには、1 ポイントの許容差での frame の照合が含まれていました。

ところが、スナップショットは UI がまだ落ち着く途中で取られます。適合性画面の間を移動すると、フィールドがアニメーションで所定の位置へ動きます。同じフィールドがスナップショットとタップの間に縦へ 49 ポイント動き、frame の再チェックが、まだ有効な要素を stale と読み違えました。

修正は、identity の照合から frame を外します。位置パスと identifier、label、traits を合わせれば、本当に別の要素かどうかは十分に見分けられます。frame はレイアウトが落ち着くにつれて正当に変わるので、frame で照合すると、有効な要素を偽の stale に変えてしまうだけでした。

ほかの 2 つの容疑は、先に除外しました。generation ベースのハンドル方式と、HTTP サーバの並行性です。ストア自身の stale 経路は一度も発火せず、stale はすべて属性の再チェックから来ていました。そのため、この単位が触れるのは `attributesMatch` だけで、runner のトランスポートには触れません。

## 検討した代替案

**ジョブ全体を CI で隔離するか、自動再試行する。** `xcuitest (multi-touch)` を失敗許容にする、あるいはジョブ単位の再試行で包むと、クラッシュに触れないままチェックを緑にできます。次の 3 つの理由で、採用しません。

- 本物の runner の欠陥を、緑のチェックの裏に隠します。
- 静かな再試行のたびに、macOS の従量課金枠を消費し続けます。
- [BE-0281](../BE-0281-ios-on-device-actuation-coverage/BE-0281-ios-on-device-actuation-coverage-ja.md) が積み上げている実機アクチュエーションの網羅を、増やすどころか崩します。

**リトライの継ぎ目の予算を増やす。** `_MAX_ATTEMPTS` やバックオフを上げれば、1 回の呼び出しで 30 秒の停止を待ち切れます。それでも、肝心の状況は救えません。届いたピンチは、二重操作のおそれなしには再送できないからです。しかも、あらゆる本物のチャネル失敗を、30 秒の遅さに落とします。リトライの継ぎ目は、設計上、1 秒未満のブレをならすものです。クラッシュまで覆うように引き伸ばすと、2 つの別問題を混同します。

**各ジェスチャの後に固定の待機を入れる。** ピンチの後、アサートの前に待つのは、条件を無視した固定 `sleep` です。プライムディレクティブ 2 が明確に禁じています。そのうえ、効果もありません。シナリオの `expect` ブロックは、すでに期限まで木を読み直す、有界の条件待ちだからです。値が `idle` のままなのは、アサートが早すぎるからではなく、ジェスチャが取りこぼされたからです。届かなかった操作は、いくら待っても回復できません。

      ため、メインスレッドをふさぐ `POST /gesture`（`pinch`・`rotate`）が accept ループを止め、その間

- [x] Unit 2 — runner（`BajutsuKit/`）で根本原因を直す。accept ループは各接続を並行キューに渡し、
      `listen` バックログを広げたので、ジェスチャがメインスレッドをふさいでいる間も `/health`（共有
      状態に触れない）が応答できる。これはまさに Unit 3 のヘルスポーリング復帰が「runner が忙しい」と
      「runner が死んだ」を区別するための前提となる。並行化により、それまで直列だった `SnapshotStore`
      が 2 つのハンドラから同時に到達しうるようになったため、ロックで保護する。ジェスチャが落ちて
      `actual='idle'` になる事例は上流の XCUITest / idb のマルチタッチ配送の制約であり、Unit 3 の冪等な
      回復に委ねる。
- [x] Unit 3 — 呼び出しごとのリトライ予算を超えた実行途中のクラッシュを検出し、決定論的に表面化させる。
      読み取りと未達の書き込みは冪等に回復し、それ以外は専用の runner クラッシュ失敗とする。
- [x] Unit 4 — すべての回復を記録に残す。回復のたびに再送したブレと同じくらいはっきり記録し、
      クラッシュして回復した実行が、一度もクラッシュしなかった実行と見分けられないようにする

- [x] Unit 5 — runner がタップ時に行う属性の再チェック（`attributesMatch`）から frame を除外する。
      スナップショットとタップの間に動いただけの要素——まだ落ち着いていないレイアウト——を、消えた要素と
      読み違えないようにする。identifier・label・traits と位置パスで、本当に別の要素かどうかは依然として
      捕まえられる。
