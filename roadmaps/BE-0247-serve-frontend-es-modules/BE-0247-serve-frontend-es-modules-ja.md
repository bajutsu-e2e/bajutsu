## はじめに

BE-0202 は、一体だった `bajutsu/templates/serve.js` を 5 つのセクション別ファイルに分割しました。
`serve.core.js`、`serve.panels.js`、`serve.crawl.js`、`serve.metrics.js`、`serve.author.js` です。合計で
約 3,200 行あり、それぞれが独立したファイルとして読め、差分も確認できます。`bajutsu/serve/handler.py` は、
これらを固定順（`_JS_ASSETS`、`handler.py:657-663`）で連結し、1 つの `<script>` タグへ埋め込みます。
5 つのファイルは、1 ファイルだったころと同じく、モジュールシステムを持たない単一のグローバルスコープを
共有したままです。

本項目は、このセクション間の区切りに、ES モジュールという実在する言語機構を与えます。各ファイルは、
自分が何に依存しているかを、ファイル自身に宣言します。いまは、手作業で保守するタプル内の位置が、依存を
暗黙に表しています。

## 動機

分割後も、`serve.core.js`（約 1,017 行）と `serve.author.js`（約 1,079 行）は、単体で見て大きいままです。
どのファイルも、他のどのファイルの状態でも読み書きできます。状態はモジュールレベルの可変な `let`
グローバルとして存在し、セクション間に強制力のある境界がないからです。この状態は、すでに分割をまたいで
広がっています。

- `serve.core.js:35-41` とその設定関連のセクションにある、`poll`・`recPoll`・`selectedRun`・`recPath`・
  `scnFiles`・`targets`・`sims`・`recJobId`・`runJobId` と、`keyState`・`ccTokState`・`provState`・
  `gitCredState`・`projectsCache`
- `serve.crawl.js` の `crawlPoll`・`crawlJobId`・`crawlRunId`・`crawlGraphData`
- `serve.metrics.js` の `metricsCache`・`metricsSort`

`serve.author.js` が `serve.crawl.js` の `crawlPoll` を読みにいくことは、言語レベルでは止められません。
将来追加されるセクションが `selectedRun` を上書きすることも、止められません。いま 5 つのファイルの一貫性を
支えているのは、たまたま `_JS_ASSETS` が定義を使用より先に並べる順序になっているという事実だけです。

これは、重複したロジックの問題ではありません。各セクションが呼び出す共通のプリミティブは、BE-0202 の
`startJob` 統一によって、すでに `serve.core.js:48-96` に一本化済みです。該当するのは、`getJSON`、`postJSON`、
`streamJob`、`startJob`、`cancelJob`、`setStatus`、`esc` です。残っている負債は、もっと狭い範囲にあります。
フラットなグローバル名前空間と、使う側からは見えないのに挙動を左右している読み込み順です。

本プロジェクト自身の ESLint ガードレール（BE-0129、`eslint.config.mjs`）も、ツール側から同じ隙間を
記録しています。`no-undef` は意図的に無効化されており、理由は 2 つあります。

- **主たる理由。** 有効にすると、ブラウザと ES のグローバル一式を宣言する必要があります（`globals` という
  npm パッケージ）。この Python リポジトリに Node のツールチェーンを持ち込むことになります。
- **副次的な理由。** コメントが付け加えているとおり、ESLint は、セクション別ファイルが共有するファイル横断の
  グローバルが見えません。そのため、いずれにせよ誤検知になります。

グローバルの衝突や読み込み順の入れ替えミスを検出する lint は、存在しません。この脆さこそ、本項目が
取り除こうとしているものです。UI にパネルが増えるほど、脆さは悪化します。

## 詳細設計

1. **ネイティブの ES モジュールを採用します。** 各セクション別ファイルに公開面を `export` させ、他の
   ファイルから必要なものを `import` させます。`serve.core.js` が、`export function getJSON(...)` のような
   最初のモジュールになります。`serve.author.js` が、エントリモジュールになります。ビルドステップは不要です。
   ブラウザは `<script type="module">` をネイティブに実行できます。これは localhost 向けの開発ツールで、
   BE-0202 が保った「bundler なし」の方針をそのまま維持します。

   サーバ側で実際に変わるのは、配信方法だけです。`import` 指定子は URL に対して解決されます。そのため、
   5 つのファイルは、`_JS_ASSETS` のように 1 つのインライン `<script>` へ連結できません。代わりに、
   `bajutsu/serve/handler.py` が各セクションをそれぞれのパスで配信します。実体は、`bajutsu/templates/
   serve.*.js` を読む数個の静的な `GET` ルートで、`serve.html.j2` がすでに各ファイル名を把握しているのと
   同じ発想です。新しいアセットパイプラインではありません。ページは、エントリモジュールを
   `<script type="module" src="...">` で読み込みます。localhost では、1 つのインラインの塊の代わりに
   小さなリクエストが 5 つに増えるだけで、コストは無視できます。気になる場合は、`modulepreload` リンクで
   和らげられます。
2. **段階を踏む場合の最小構成として、明示的な名前空間を用意します。** (1) の配信方法の変更が、一度に
   行うには大きすぎると判断される場合を考えます。その場合は、こちらだけを先に着地させます。各セクションを
   即時実行関数式（IIFE）で包みます。トップレベルの裸の `let`・`function` 宣言の代わりに、
   `window.bajutsu.crawl = {...}` のような明示的な名前空間オブジェクトを代入します。いまのとおり、1 つに
   連結してインライン化した `<script>` のままで構いません。すると、ファイル横断の読み取りは、
   `bajutsu.crawl.crawlJobId` のような明示的なプロパティ参照になります。どのファイルのものか判別できない
   裸の識別子ではなくなります。`handler.py` がアセットを配信する方法には、手を付けません。この最小構成は
   (1) の厳密な部分集合です。同じ明示的な境界を設け、(1) の準備が整った時点で、実際の `import`・`export` へ
   移行します。
3. **読み込み順を、慣習ではなく強制されたものにします。** (1) と (2) のどちらを取るにせよ、目指すところは
   同じです。`_JS_ASSETS` のタプルの並び順という契約を、言語かツールが検査できるものに置き換えます。
   (1) を採用した場合、`import` のグラフそのものが読み込み順になります。どこからも `import` されていない
   モジュールは、単に読み込まれません。依存が欠けていれば、その `import` 文自体で、読み込み時に
   `ReferenceError` になります。どこかわからないグローバル参照の失敗にはなりません。

   変換したファイルについては、`eslint.config.mjs` の `languageOptions.sourceType` を `"script"` から
   `"module"` に変更します。これで ESLint が `import`・`export` 構文を解釈できます。各ファイルの入力が
   宣言されるようになった段階で、リポジトリ全体で無効化している `no-undef` を、ファイル単位で再度有効に
   できないかも検討します。ただし、これで取り除けるのは副次的な障害（ファイル横断のグローバル）だけです。
   `no-undef` を再度有効にすると、ブラウザのグローバル（`window`、`fetch`、`document` など）で、なお
   誤検知します。主たる障害を解決する必要があるためです。解決とは、それらを `globals` パッケージで宣言する
   ことです。したがって、入力を明示するのは必要条件ですが、それだけでは十分ではありません。

**検証について。** これはコードの構造的な整理です。決定的な `run` / CI ゲートは、このコードを実行しません
（prime directive 1 により、AI と UI のコードはその経路から外れています）。`make lint-js`（各ファイルへの
`node --check`）と既存の serve dogfood シナリオ（BE-0058、BE-0189）のほかに、自動的な合否判定はありません。

確立した手順に従い、人が手作業で変更を再現し、アプリ内ブラウザで確認します。各パネル（record、replay、
triage、crawl、metrics、author）を実際に読み込み、変更の前後で挙動が同じであることを確かめます。コードの
読解だけでは判断しません。serve の JS/CSS の変更は、コードレビューだけの判断で、誤ったまま出荷されたことが
過去にあるためです。UI の挙動は変わりません。本項目が変えるのは、フロントエンドのコードの組み立て方と
読み込まれ方だけです。

## 検討した代替案

- **bundler（Webpack、esbuild、Rollup など）の導入。** BE-0202 が不採用とした理由と同じ理由で、不採用とします。
  ここは Python のリポジトリで、この UI の価値はツールチェーン不要の単純さにあります。ネイティブの ES
  モジュールなら、依存関係を明示できるという同じ利点が得られます。ビルドステップも、`node_modules` の
  ツリーも、ソースと同期を保つ必要のあるコンパイル済み成果物も持ち込みません。
- **フラットなグローバルスコープを現状のままにする。** 本項目が取り組む現状そのものなので、不採用です。
  すでに 2 つのファイルが大きく、ファイル横断の状態には強制力のある境界がありません。serve に機能が追加
  されるたびにパネルが増えるので、フラットな名前空間は、時間が経つほど読み解きにくくなります。
- **ネイティブモジュールへは移行せず、名前空間オブジェクトだけを導入する。** *詳細設計* (2) で述べた
  段階的な着地点ではなく、恒久的な対応として検討しました。最終形としては不採用です。名前空間は、
  ファイル横断のアクセスを呼び出し箇所で明示します。しかし、読み込み順は依然として `_JS_ASSETS` 内の
  強制力のない慣習のままです。名前空間が読み込みより先に参照されても、何も大きな音を立てて失敗しません。
  ネイティブな `import`・`export` であれば、同じだけのコード変更量で、明示的なアクセスと強制された読み込み順の
  両方が手に入ります。したがって、ネイティブモジュールを目指す対象として残し、(2) は最終形にしません。
