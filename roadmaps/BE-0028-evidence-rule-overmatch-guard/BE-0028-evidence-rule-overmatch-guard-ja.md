## はじめに

`capturePolicy` の過剰マッチによって成果物が肥大するのを防ぎます。`--explain` ドライランと、既定ポリシーの軽量化を提案します。

## 動機

[`capturePolicy`](../../docs/ja/glossary.md#証跡-capturepolicy-trace-triage) のルールは、そのトリガーがマッチする「たびに」発火します（DESIGN §9 A、`docs/evidence.md`）。反復可能で決定的な証跡を得るというのがまさにその狙いです。しかし同時に、広すぎるルールが、run の終了まで見えない形で高コストになります。

`{ action: tap, idMatches: "*.submit" }` のようなトリガーは「送信ボタン」と読めます。ところが、緩い glob は、著者の意図よりはるかに多くのステップにマッチしえます。忙しいフローでの `event: screenChanged` ルールも同様です。そうしたルールに重い取得（`video`、`network`）を付けると、run は静かに数ギガバイトの成果物を生み、遅くなります。§9 が警告する観測者効果のリスクも招きます。

DESIGN §11 は、これを未解決のリスクとして直接挙げています。「証跡ルールの過剰マッチによる成果物肥大 → `--explain` ドライランと既定ポリシーの軽量化」という記述です。DESIGN §9 のコスト管理の注記も、両面を補強します。ルールはマッチ条件を絞るべきです。既定は `screenshot` + `elements` + `actionLog` の軽量 3 点とし、`video` / `network` はオプトインにすべきです。

今日の問題は 2 つあります。過剰マッチを run の*前に*可視化するものが何もありません。重い取得が静かに実効的な既定になるのを止めるものも、何もありません。本提案は、発火をプレビューする手段と、明示しない限り安価な既定で、その両方に対処します。

## 詳細設計

設計は、互いを補う 2 つのガードからなります。どちらも合否には触れません。

- **run 前の `--explain` ドライラン。** コマンド（§11 が名付けるとおり、たとえば `bajutsu trace --explain <scenario>`）が、シナリオを `capturePolicy` に対して静的に辿ります。各ルールが何回、どのステップで発火するかを報告し、広くマッチするルールに付いた重い取得（`video` / `network`）に印を付けます。このコマンドは、既存の事後的な `trace` の*run 前*の対応物です。既存の `trace` は完了した run の manifest を読みます。ドライランは、run が*何を取得するか*を事前に示します。そのため、著者はコストを払う前に glob を絞れます。ドライランは read-only かつ決定的です。run ループと同じ仕方でセレクタを解決し、トリガーをマッチさせます。したがって回数は実際の回数であり、LLM は関与しません。
- **軽量な既定ポリシー。** 暗黙の既定取得は、軽量 3 点（`screenshot` + `elements` + `actionLog`）のままです。加えて、ステップが実際に失敗したときだけ最大限を取得する `result: error` の安全網を保ちます。区間の重い種別（`video`、`deviceLog`、`network`）は、厳密にオプトインのままです。著者は、インラインの `capture:` か、狭くスコープしたルールで、意図的に付けます。こうして高コストの取得は、著者が求めた所でのみ走り、一般的なケースは構造上安価です。
- **決定性と app-agnostic を保つ。** どちらのガードも、run のアサーションを変えません。`--explain` は助言的な出力です。既定ポリシーの選択は、どの証跡を集めるかに影響するだけで、合否には決して影響しません。固定 sleep はなく、セレクタの厳格さも不変です。アプリ単位の取得の好みは、他の per-app 設定と並べて `apps.<name>` の下に置きます。ツールと runner は app-agnostic のままで、Tier-2 ゲートは LLM フリーのままです。

## 検討した代替案

- **成果物のサイズや件数にハードな上限を設ける。** バイトやファイルの予算を超えたら、run を中断または切り詰める案です。被害は抑えられますが、証跡を非決定的に捨てます。同じシナリオが、タイミング次第で異なる成果物を取得しうるからです。これは決定性第一に反します。発火回数をプレビューし、安価な取得を既定にするほうが、肥大に反応するのではなく未然に防げます。
- **ルールが「頻発しすぎ」たら run 時に警告する。** run 時のヒューリスティックは反応的です。しきい値に引っかかる頃には、成果物はすでに書かれています。「頻発しすぎ」という魔法の数値も、シナリオ間で恣意的です。run 前のドライランは、何のコストも払う前に著者へ正確な回数を渡します。より早く、より正確です。
- **すべての取得をオプトインにする（既定の証跡をなくす）。** 最大限に安価です。しかし、DESIGN §10 が要求する最低限の安全網、すなわち失敗時は必ずスクショと要素ダンプを残すという保証を取り除きます。軽量 3 点と `result: error` の網を既定として保つことで、その保証を維持しつつ、重い種別をオプトインに保てます。

## 進捗

- [x] `--explain` のドライラン（`bajutsu trace --explain`）。キャプチャ負荷を静的かつ決定的に下見し、広く一致する規則の重いキャプチャに印を付けます（[#90](https://github.com/bajutsu-e2e/bajutsu/pull/90)）。
- [x] 既定のキャプチャ方針の軽量化。暗黙のキャプチャを `screenshot` + `elements` + `actionLog` とし、区間的に重い種類は明示的なオプトインにします（[#91](https://github.com/bajutsu-e2e/bajutsu/pull/91)）。
