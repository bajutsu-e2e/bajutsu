## はじめに

同一性が一致する重複アクセシビリティノードのペアとは、識別子、ラベル、traits、value、frame がすべて同じ 2 つの要素を、XCUITest が報告する状態です。`UIAlertController` に典型的に現れる既知の挙動です。本項目は、このペアを XCUITest が実際にタップできる要素 1 つだけに絞り込み、runner の `/elements` の返信からもう一方を取り除きます。いまは両方がツリーに残り、runner の要素問い合わせの列挙順でたまたま先だった要素に、参照の割り当てを任せています。

[`bajutsu/drivers/base.py`](../../bajutsu/drivers/base.py) の `resolve_unique` は、この重複を 1 件の代表へすでに畳んでおり、`AmbiguousSelector` による即時失敗を防いでいます。しかし、`resolve_unique` が呼ぶ畳み込みの関数 `_collapse_identical_duplicates` 自身の docstring は、残る代償を「どちらの複製をタップするかは run ごとに入れ替わり、たまたま選ばれなかった複製では参照消失（stale handle）で失敗する」と述べています。

本項目は、この代償を源で取り除きます。重複ペアのうち一方だけが、[`ElementProviding.isHittable`](../../BajutsuKit/Sources/BajutsuRunner/ElementProviding.swift) でタップできると報告したとします。この判定は、バックエンドが、覆われている要素と本当の操作失敗とを見分けるためにすでに使っている、ネイティブな XCUITest の判定です。対象は要素のフレーム中心が画面内にあるときで、画面外かどうかは、この判定ではなく `scroll` の側の問題として、あえて外してあります。このとき runner は、どちらの要素も [`SnapshotStore`](../../BajutsuKit/Sources/BajutsuRunner/SnapshotStore.swift)（BE-0312）の参照の割り当てへ届く前に、もう一方を取り除きます。残る候補は 1 つだけなので、そのあとの解決や参照の割り当てで迷う余地がありません。

`SnapshotStore` 自体は変更しません。手直しは、`SnapshotStore` の入力を用意する問い合わせの段に閉じます。対象も、アプリ内のツリーの `/elements` の問い合わせだけです。BE-0316 が追加した SpringBoard のシステムアラート問い合わせには及びません（理由は *詳細設計* を参照）。

## 動機

`UIAlertController` の中のボタンへ `id` で `tap` すると、`element vanished (stale handle)` で失敗することがあります。直前のステップで取った evidence のスナップショットは、そのボタンを画面上で動かさず映しており、セレクタが指す識別子とも一致しているにもかかわらず、です。

そのスナップショットの中で、ボタン自身のアクセシビリティノードは 2 回登録されています。識別子、ラベル、traits、value、frame がすべて一致する 2 件が、同じ subtree の中の、他のいくつかの `"other"` trait の重複ノードと並んでいます。この二重登録は、`resolve_unique` の docstring がすでに「標準的な `UIAlertController` のボタンに対する既知の XCUITest の重複登録」と名づけているものです。

その docstring が述べる畳み込みは、シナリオの作者には見分けられない重複ペアでセレクタが即座に失敗するのを防ぎます。しかし、畳み込んだあとの一致がどちらの物理ノードを指すかまでは、決めません。`resolve_unique` は、`find_all` が返す並びのうち最初の要素、つまり runner の `/elements` の返信が列挙した順で最初のものを保持します。[`SnapshotStore.swift`](../../BajutsuKit/Sources/BajutsuRunner/SnapshotStore.swift) の `refreshSnapshot` も、その同じ最初の出現に対して、接尾辞のない参照を割り当てます。

どちらにも、片方の物理ノードを優先する根拠はありません。並び順は、その問い合わせで XCUITest 自身のアクセシビリティツリーの走査がたまたま重複ペアをどう列挙したかで決まります。`_collapse_identical_duplicates` の docstring 自身が、この並びを「run ごとに入れ替わる」と、不安定なものとして報告しています。

`UIAlertController` のボタンペアは、いったん画面が落ち着いたあとに、run の途中で位置を入れ替えることはありません。そのため、1 つのステップの中で BE-0289 が試す 3 回の再解決は、そのすべてが同じ「最初に列挙された複製」を導き直し、同じ結果を繰り返します。

- それが、XCUITest のネイティブな tap が解決してタップできる複製であれば、その重複の並びで run するかぎり、毎回成功します。
- それがもう一方の複製であれば、同じ問い合わせは、識別子、ラベル、traits、value、frame を完全に同じ内容で報告します。しかし XCUITest 自身のイベント合成は、この複製を解決できません。毎回のタップの試みが、ネイティブに "No matches found" を発生させ、[`Router.swift`](../../BajutsuKit/Sources/BajutsuRunner/Router.swift) の `onMainCatching` が、それを `stale` として報告します（[`xcuitest.py`](../../bajutsu/drivers/xcuitest.py) の `_actuate` のコメントが挙げる、`stale` を生む 2 つの経路のうち 2 つ目です）。その結果、ステップは、画面から一度も出ていないボタンに対して `element vanished (stale handle)` で失敗します。

結果として、このシナリオは run をまたぐと不安定で、1 回の run の中では決定的になります。タップの成否は、XCUITest 自身のツリーの走査が決める並び順に懸かっており、シナリオにも再解決にも、その並び順を動かす手立てがありません。

これは、BE-0312 が名指したうえで先送りした、2 つ目の不安定さの種類です。BE-0312 自身の「詳細設計」節は、この前提を直接認めています。同一性の一致する要素への出現番号の割り当ては、同じ要素の問い合わせ順がスナップショットをまたいで安定していることを前提としています。見た目の同じ要素の順がスナップショットのあいだで入れ替わる画面では、参照は振り直されることがあります。BE-0312 は、そのような画面はまれで、その要素はセレクタからも見分けられないという理由で、この隙間を塞ぐのを、実際のシナリオが必要になるまで見送っていました。

通常のアプリ内ナビゲーションから到達できる `UIAlertController` の確認ダイアログは、まさにその実際のシナリオです。そのボタンは、毎回の表示で二重に登録されます。シナリオの作者がどちらかを `tap` する動機は十分にあり、本項目が直す失敗は、その画面が一度スイートに入れば、稀な境界事例ではなくなります。

直さずに残すコストは、BE-0289 と BE-0312 の両方が測っている、同じものです。必須のオンデバイスの関門がランダムに失敗すると、要素が消えていないのに関門への信頼が損なわれ、反射的な再実行か無駄な調査のどちらかを招きます。再実行のたびに、アプリをビルドし Simulator を起動するジョブで、macOS を動かす費用がかかります。

## 詳細設計

手直しは、runner の要素問い合わせの段に閉じます。Python 側のドライバと `SnapshotStore` のどちらにもないものを、この段だけが持っているからです。持っているのは、2 つの重複それぞれへのネイティブな参照と、その特定のノードが今まさにタップできるかを XCUITest に問い合わせる既存の手段です。

**重複グループのうち、タップできない要素を取り除く。ただし、それで残る候補が 1 つだけになるときに限る。** [`Router.swift`](../../BajutsuKit/Sources/BajutsuRunner/Router.swift) の `handleElements` は、`queryElements()` を `caughtOnMain` のクロージャの中から呼んでいます。これは、[`ElementProviding.isHittable(backingElement:)`](../../BajutsuKit/Sources/BajutsuRunner/ElementProviding.swift) 自身がネイティブな XCUITest 呼び出しであり、メインスレッドの文脈を必要とするからです。絞り込みは、その同じクロージャの中で、結果を `elementsResponse` へ渡す前に行います。

本項目が対象とするのは `handleElements` と `/elements` だけです。`handleSystemAlertQuery` や、BE-0316 が追加した SpringBoard の `/systemAlert/query` は、対象としません。

- `isHittable` は、アプリ内の position-path をたどって、バッキング参照を解決します（[`XcuitestElementProvider.swift`](../../BajutsuKit/Runner/Sources/XcuitestElementProvider.swift) の `liveElement(for:)`）。
- それ以外の種類の参照では、すぐに `.notFound` を返します。`querySystemAlertButtons()` が作る、序数だけで指す `SystemAlertButtonBacking` もその 1 つです。アプリ外のアラートにはスナップショット上の position path を記録する手立てがない、という BE-0316 の設計によるものです。
- そのため SpringBoard 側の複製を確かめても、結果はつねに下の「どの要素も `.ok` を返さない」場合になります。何も絞り込めないまま、呼び出しを 1 回無駄にするだけです。
- *動機* が説明している二重登録は、そもそもアプリ内の `UIAlertController` のスナップショットの走査に備わる性質であり、システムアラートの経路にあるものではありません。そちら側に、本項目が塞ぎ残す場合はありません。

絞り込みは、返ってきた要素を、`_collapse_identical_duplicates` がすでに使っている同じ同一性でグループ化します。識別子、ラベル、traits、value、frame がすべて一致するものです。traits は集合として比較し、Python 側のキー `tuple(sorted(set(el["traits"])))` に合わせます。そうすれば、traits の並び順が違うだけの重複ペアも、グループ化できます。単純な `[String] ==` や、`SnapshotStore` の配列のハッシュでは、これができません。

1 件しかないグループは、判定の必要がなく、余分なコストもかかりません。2 件以上のグループでは、`/isHittable` エンドポイントがすでに使っている既存の `isHittable(backingElement:)` を、メインスレッドのままで各要素へ呼びます。この呼び出しが要素ごとに投げる例外は、要素ごとに捕まえます。`/isHittable` のエンドポイント自身がすでに、解決に失敗したという例外を素通りさせず、`stale` として扱っているのと同じ扱いです（[`Router.swift`](../../BajutsuKit/Sources/BajutsuRunner/Router.swift) の `onMainCatching`）。

2 つの要素を見分ける決め手は、`el.isHittable` です。これは、解決できて画面内にある要素へ、合成したイベントが今まさに届くかどうかを、XCUITest 自身が判定する真偽値です。`isHittable(backingElement:)` は、次のように返します。

- `el.isHittable` が `true` のとき、`.ok` を返します。
- `false` のとき、`.notHittable` を返します。
- 要素のフレーム中心が画面外にあるときは、確かめもせず `.ok` を返します。`tap` 自身の判定にそろえたものです。画面外かどうかは `scroll` の側の問題であり、タップできるかどうかの問題ではないからです。

例外は、2 つの要素を見分けるための手立てとして、本項目が見込むものではありません。どちらも同じ position-path の参照解決を通るので、どちらかが解決に失敗するとは見込んでいません。それでも要素ごとに例外を捕まえておくのは、あくまで防御です。どちらかの要素が何らかの理由で投げた例外が、`handleElements` 自身の `caughtOnMain([])` のフォールバックまで素通りすると、ツリー全体の代わりに空の画面を返してしまいます。これを防ぎます。例外を投げた要素は、単に `.ok` ではなかったものとして扱います。

ちょうど 1 件だけが `.ok` を返したときは、そのグループの他の要素を、リストから取り除きます。リストが `elementsResponse` へ届く前に、取り除きます。残った 1 件はそのグループの唯一の候補になるので、その 1 件を複製の相手と比べて並べるタイブレークは、出現番号のものも含めて、もう要りません。

どの重複グループにも属さない要素は、元の相対順を保ちます。以下の 2 つの場合に当たるグループも、同じです。これは、キーでグループ化した辞書から並べ直すのではなく、元のリストからその場で要素を取り除く実装を前提とします。辞書の反復順序を、Swift は保証しないからです。そのため、この絞り込みは、問い合わせの大半の要素に何の影響も与えません。絞り込みは、`_collapse_identical_duplicates` の 5 つの項目を鍵にした同一性で衝突する、まれなグループにだけ及びます。

本項目が対象とするこの場合について言えば、`SnapshotStore` も `elementsResponse` も変更する必要がありません。ただ 1 つ残った候補は、`_collapse_identical_duplicates` に畳み込むべき 2 件目がそもそも届かないまま、Python 側で一意に解決します。

`find_all` を `resolve_unique` を経由せず直接使うセレクタも、`resolve_unique` の呼び出し元と同じだけ、候補が減ります。`forEach`、`exists`、重複そのものの同一性より広いセレクタに対する `count`、`scroll` ステップの `within` によるコンテナ解決です。これらは `/elements` が返したものをそのまま読むだけなので、本項目では、それぞれを別個に導き直しません。

ただし、この候補の減り方は、そのときどきの判定結果に懸かっています。

- ペアがまだ覆われているあいだ、重複する同一性への `count` や `exists` は、2 件を報告します。どの要素も `.ok` を返さないため、グループは変わらないままです。
- いったん落ち着けば、1 件を報告します。ちょうど 1 件が `.ok` を返します。

この 2 つの値は、本項目自身のオンデバイスのテストが同じ画面について固定する値でもあります。その移り変わりのあいだにポーリングする assertion では、ツリーの同一性そのものは変わらないまま、結果だけ変わり得ます。しかも `tap` と違って、BE-0289 の再解決が吸収できる `stale` の返事もありません。*進捗* には、下の先送りにした限界と合わせて、これも記録します。

絞り込みがそもそもグループを狭められるかどうかは、2 つの要素が、同一性の 5 つの項目の 1 つである frame を、もともと共有していることにも懸かっています。どちらも `isHittable` の同じ画面内、画面外の分岐を通ります。そのため、画面外にある重複ペア、たとえば scroll view の折り返しの下にあるものは、両方が `.ok` を返し、絞り込まれずに、下の「複数の要素が `.ok` を返す場合」に当たります。

これは後退ではありません。その場合は、もともと問い合わせの順序が、今日とまったく同じように決めているからです。ただし、絞り込みが実際に効くのは、画面内にあって片方だけが実際にタップできるペアに限られます。これは *動機* が説明する `UIAlertController` の形そのものですが、シナリオが出会いうる同一性の一致するペアのすべてで保証されるわけではありません。

本項目が塞がない場合が、1 つあります。`SnapshotStore` 自身の出現番号のタイブレークは、上の 5 つの項目とは違う、より粗い同一性を鍵にしています。識別子、ラベル、traits の 3 つだけで、value と frame はあえて外しています（画面が落ち着きかけているときの理由づけは、BE-0312 自身のものです）。5 つの項目が一致する重複ペアは、当然この粗い 3 項目でも一致します。つまり重複ペアの 2 つの要素自身が、すでに互いに `SnapshotStore` のハッシュで衝突しています。衝突するのに、無関係な 3 つ目の要素は要りません。

これが問題になるのは、問い合わせをまたいで、取り除くかどうかの判定が入れ替わる場面です。あるグループを今日と変わらないままにする問い合わせ（下の 2 つの場合のいずれか）で、本項目が後で取り除く要素に、接尾辞のない参照が割り当てられ、呼び出し側がその参照を保持したとします。次の問い合わせでその要素が取り除かれれば、グループに残った生き残りだけが、同じ粗いハッシュに 1 件だけ属することになり、同じ接尾辞のない参照を得ます。`SnapshotStore.lookup` は、その参照に対して `.stale` ではなく `.found` を返し、生き残った要素を指してしまいます。

その結果、ある物理ノードのために発行された参照が、BE-0289 の再解決が頼る `.stale` という状態を一度も経由せずに、別の物理ノードへ黙って解決されます。取り除くかどうかは、そのたびの問い合わせで得る生きた判定結果に懸かっています。画面が落ち着きかけているあいだの `isHittable` の結果は、安定している保証がありません。そのため、これは、どちらの物理ノードも実際には動いておらず、同一性も変わっていなくても起こり得ます。

同じ粗いハッシュの衝突と、出現番号の入れ替わりは、生き残った要素と、この 3 つの項目だけを共有する無関係な 3 つ目の要素にも、同様に及びます（識別子を持たず、ラベルと traits だけが同じで、frame は別の場所にある操作対象など）。本項目は、どちらの場合も塞ぎません。*進捗* には、見過ごした隙間としてではなく、あえて先送りにした既知の限界として記録します。

絞り込みが手を付けずに残すべき場合が、2 つあります。

- **グループのどの要素も `.ok` を返さない場合。** 何も取り除きません。残すべき生き残りがないまま絞り込むと、グループを空にしてしまうか、タップできない要素をどれか 1 つ勝手に選ぶしかありません。どちらも、判定が実際には見つけていない区別をでっち上げることになります。グループを今日と変わらないままにしておけば、タップは結局失敗しますが、原因を正確に報告できる既存の経路を通ります。
  - 解決はできて画面内にあるが、今まさに覆われているノードなら、`.notHittable` です（現状の `ElementNotTappable`）。このケースは、要素が画面外にあることからは起こりません。`isHittable` は、画面外を `.notHittable` ではなく `.ok` として報告するからです（*詳細設計* を参照）。
  - XCUITest が一切操作できないノードなら、本物のネイティブな解決失敗であり、現状は `stale` として現れます。根本の状態が解消すれば、BE-0289 の再解決がなお正当に吸収できます。

  本項目も `SnapshotStore` も、どちらの結果の意味も変えません。
- **複数の要素が `.ok` を返す場合。** `UIAlertController` の二重登録ではありません。二重登録なら、実際に操作できるのはどちらか一方だけです。これは、同一性が一致する、独立にタップできる、正真正銘別々の 2 つの操作対象が存在することを意味します。この判定だけを根拠にどちらか一方を取り除くと、シナリオが `index` で狙う必要のある対象を、静かに消してしまうことになります。判定は、「たまたま重複した見せかけの要素」と「見た目は同じだが実際に独立してタップできる 2 つの対象」とを、区別できないからです。この場合も、グループを今日と変わらないままにしておきます。どちらが先頭に来て接尾辞のない参照を得るかは、今までと同じく問い合わせの順序が決め、今までと同じく問い合わせごとに変わることがあります。これほど曖昧なセレクタは、見分けのつかない独立した対象を実際に描いているアプリの、意図された挙動として読むべきです。その不安定さは、本項目が引き起こす後退でも、本項目が塞ぐつもりの隙間でもなく、そのようなセレクタにもともと備わっている性質です。

**コスト。** 追加するネイティブな呼び出しは、すでに内容で衝突している要素にしか走りません。`_collapse_identical_duplicates` の docstring 自身が、これをよくある場合とはせず、既知でまれな XCUITest の挙動として位置づけています。重複グループのない通常の問い合わせは、追加のコストを一切払いません。呼び出し自体は、`/isHittable` が今日すでにメインスレッドで行っているものと同じです。`handleElements` が `queryElements()` のために開いている同じ `caughtOnMain` のクロージャの中から呼ぶので、新しいスレッドの切り替えは増えません。

**確かめていない前提を、先に確かめる。** 実際の `UIAlertController` の二重登録が、実際にちょうど 1 件だけ `.ok` を返す形に解決しないなら、この絞り込みは何もしません。*詳細設計* は `el.isHittable` の区別からそう起こるはずだと述べていますが、この文書のどこにも、実機で確かめた記述はありません。下の Router とテスト整備の作業へ取りかかる前に、この前提を直接確かめます。

1. 実機の Simulator で `UIAlertController` を表示します。
2. `queryElements()` から両方の要素の `backingElement` を取り出します。
3. それぞれに対して `isHittable(backingElement:)` を呼びます。

ちょうど 1 件が `.ok` を返せば、この先の設計に取り組む価値があります。両方が返す、あるいはどちらも返さない場合は、*詳細設計* の前提が誤っており、ここで示す絞り込みでは、この場合を一切狭められません。それは絞り込みの実装上の欠陥ではなく、設計そのものを変える必要があるという結論です。

**テスト。** グループ化と、取り除くか残すかの判定そのものは、runner のロジックであり、ネイティブな挙動ではありません。そのため、実機なしで覆えます。ただし BE-0312 の Unit 3 と違って、`SnapshotStoreTests.swift` の中ではなく（`SnapshotStore` 自体には触れていません）、`GET /elements` を `FakeElementProvider` に対して一通り動かす `RouterTests.swift` の中で覆います。

この fake の `isHittableResult` は、今はすべての呼び出しが共有する単一の `TapResult` です。これを、fake の `backingElement` の `ObjectIdentifier` を（要素の内容ではなく）キーとする、小さな辞書に変えます。内容でキーにすると、下のテストで使う 2 つの fake 要素は、同一性が一致するという前提そのものにより、同じキーへ潰れてしまいます。別々の `isHittable` 結果を持たせられません。この辞書を使うと、次の 3 つのテストが、Simulator なしで、分岐の論理を決定的に固定します。

- 同一性が一致する fake の要素を 2 つ用意して `isHittable` の結果を互い違いにし、返信がタップできる要素だけを残すこと。
- 両方が `.ok` を返す場合に、返信が両方とも変えずに残すこと。
- 両方が `.ok` 以外を返す場合も、返信が両方とも変えずに残すこと。

4 つ目のテストが、上で述べた例外を要素ごとに捕まえる要件を、直接固定します。そのためには、別にもう 1 つ、`backingElement` ごとに例外を注入できる仕組みが必要です。`isHittable` には、今日そのような仕組みがありません（`tap` と `queryElements` は、`tapRaises` と `queryRaises` で持っています）。`TapResult` 自体にも、「例外を投げる」を戻り値として表すケースがありません。この仕組みがあれば、片方の fake の要素が例外を投げ、もう片方が `.ok` を返すときに、投げた要素だけが取り除かれることを確かめられます。

オンデバイスのテストは、実機でしか確かめられないことに絞ります。`Router.swift` と `ElementProviding.swift` には、まだ実機と実機なしを分けた前例がないので、これが最初の例になります。上の Spike が前提の成立をすでに確かめたあとで、次のことを確かめます。

- 実際に片方だけが覆われた `UIAlertController` の二重登録が、同じように再現すること。
- `id` への `tap` が、タップできる要素に着弾すること。
- その識別子に対する `count` の判定が、あとで 2 件ではなく 1 件になること。

本項目が防ごうとしている回帰は、誤った複製へのタップです。`count` の判定は、生き残った要素が単に並べ替えられただけではなく、本当に唯一の候補になっていることまで確かめます。

## 検討した代替案

**取り除くのではなく、並べ替えるだけにする。** 本項目の前の版は、タップできる複製をグループの先頭へ移すだけで、両方をツリーに残していました。BE-0312 が今持っている出現番号のタイブレークの形を変えず、その上に乗る設計です。並べ替えは、*動機* が説明する失敗そのものを直します。先頭の要素は、つねに接尾辞のない参照を得るからです。

しかし、それが効くのは、片方だけがタップできる場合だけです。両方タップできるときは、並べ替えるだけの設計でも、どちらを先頭にするかを問い合わせ順に頼るしかありません。今日と同じだけ非決定的な場合として残ります。片方だけがタップできる場合、タップできない複製を取り除けば、その複製と並べて生き残りを置く必要そのものがなくなります。並べ替える対象となる、同一性が一致する 2 件目が、もともと存在しないからです。

並べ替えだけの設計は、タップ不能な複製を、接尾辞つきの参照を持つ要素としてツリーへ残し続けることになり、`count` や `index` は、それを見続けます。取り除けば、`count` は、シナリオが実際に操作できる対象の数を報告するようになります。これは、最初から本物の 2 つ目の操作対象ではなかった挙動について、「ここに何個のボタンがあるか」を、より正しく言い当てているはずです。この代償は、*詳細設計* が名指すとおりのものです。取り除く設計は、その同一性について `/elements` が報告する内容を変えますが、並べ替えるだけの設計なら、報告される形をそのまま保っていました。

**タイブレークを `SnapshotStore` 自体で直す。** `SnapshotStore.refreshSnapshot` が受け取るのは、`ElementSnapshot` の値だけで、それぞれすでに、同一性、value、frame、不透明な `backingElement` 参照へ切り詰められています。この型は、実際にタップできるかどうかというネイティブな判定結果を運ぶ場を持ちません。その結果を求めるには、本項目がすでに提案している、同じネイティブな、メインスレッドの `isHittable` 呼び出しが要ります。

絞り込みを `SnapshotStore` の内部へ移すと、store にそのネイティブな能力を直接持たせることになります。BE-0312 があえて機器に依存させず、実機なしでテスト可能に保っていたクラスへ、ネイティブな XCUITest 呼び出しを持ち込むことになります。リストが store に届く 1 段手前で絞り込むほうが、どちらの点でも優れています。

**Python 側、`resolve_unique` や `_collapse_identical_duplicates` で直す。** Python 側のドライバは、1 件を超える内容を受け取ることが一切ありません。2 つの重複が、Python が比較する前に、すでに 1 件の論理的な一致へ畳み込まれているからです。また、ネイティブな参照をまったく持たない Python 側から、「どちらがタップできるか」を runner へ尋ねる経路もありません。尋ねるなら、重複グループごとに、しかも問い合わせごとに、1 回の追加往復が要ります。

runner がタップできる要素を告げたあとで、Python 側が候補を 1 つ捨てても、もう一方の複製の参照は、runner 側では生きたまま `index` で届くところに残ってしまいます。取り除くこと自体は、要素が実際に消える場所、つまり返信を組み立てる runner で行う必要があります。runner が送ったものしか見えない Python 側では足りません。

この理由づけは、参照を保つネイティブな runner のプロセスを持つバックエンドに固有のものです。`resolve_unique` と `_collapse_identical_duplicates` は、すべてのバックエンドが共有します。そのようなプロセスを持たないバックエンド（adb、Playwright、WebView のブリッジ、Appium 経由の live route）には、この手直しを移せる runner の層自体がありません。同じ理由づけは、そちらでは通りません。

**再解決の回数を増やす、あるいはドライバの外側でスクロールや再表示による回復を足す。** BE-0289 の再解決は、`stale` の返事に対してすでに再解決し、再操作しています。*動機* が示すとおり、これはこの失敗を回復できません。重複の並びは 1 回の run の中で安定しているため、どの試行も同じ複製を導き直し、同じ結果を繰り返すだけだからです。再解決の回数を増やしても、変わらない結果を再現する時間が増えるだけです。ドライバの外側でスクロールや、閉じてから開き直す回復を足すのは、`UIAlertController` 自身のレイアウトを壊れているものとして扱うことになります。ダイアログは、最初から問題ではありません。

**重複グループだけでなく、すべての要素で `isHittable` を計算する。** すべての要素について、タップできるかどうかをあらかじめ判定しておけば、重複の場合を特別扱いしなくて済みます。ただし、代償として、`/elements` のすべての返信で、要素 1 件につき 1 回のネイティブな呼び出しが必要になります。その大半は、重複の衝突に一度も関わりません。内容で衝突している要素だけに絞ることで、追加のコストは、本項目が対象とする挙動が実際に起きる頻度と釣り合うものにとどまります。
