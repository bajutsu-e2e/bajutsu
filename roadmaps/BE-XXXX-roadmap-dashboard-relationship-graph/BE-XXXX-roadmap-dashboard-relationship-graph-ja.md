## はじめに

ロードマップステータスダッシュボードに、項目どうしの関係を描く関係図を追加します。このダッシュボードは、
[BE-0094](../BE-0094-roadmap-status-dashboard/BE-0094-roadmap-status-dashboard-ja.md) が各項目の
メタデータから生成する GitHub Pages のページです。その後、
[BE-0219](../BE-0219-roadmap-dashboard-search/BE-0219-roadmap-dashboard-search-ja.md) は検索ボックスを、
[BE-0311](../BE-0311-roadmap-dashboard-table-view/BE-0311-roadmap-dashboard-table-view-ja.md) は
ソート可能なテーブル表示を追加してきました。ロードマップ項目のメタデータ欄には、その項目と関係を持つ
ほかの項目がすでに書かれています。`関連` はまとめて読むべき項目を並べ、`由来` はその項目が派生した
元の項目を記録し、`後継` は置き換えた項目を指します。しかし、記録されている関係を図として描く表示は
これまでありませんでした。関係図は、Cards と Table に並ぶ第3の表示としてその関係を描きます。1つの項目が
ノード1つになって状態の色を持ち、1つの関係は辺1つになります。配置は、読者のブラウザで動く力学モデルの
シミュレーションが決めます。読者はノードをドラッグでき、キャンバスを平行移動と拡大縮小で動かせ、
ノードにポインタを重ねると隣接する項目だけが明るく残ります。検索ボックスとステータスチップは、
ほかの2つの表示と同じように関係図も絞り込みます。

関係図は、新しいメタデータのフィールドを増やしません。書き手に新たな保守を求めることもありません。
描かれる辺はすべて、項目がすでに宣言している関係を読んだものなので、この図はコミット済みの
ロードマップをそのまま描画したものであり、ロードマップと食い違いうる第2の記録にはなりません。

## 動機

現在のダッシュボードは、項目を1つずつ見る問いに答える作りです。Cards はトピックごとに項目をまとめて
各項目の状態を示し、Table は ID・タイトル・トピック・状態・日付のいずれかで全項目を並べ替えます。
どちらもロードマップを一覧として扱う表示であり、一覧では**構造**についての問いに答えられません。
1つの機能のまわりにどの項目が集まっているのか、後続の項目がいくつもぶら下がっている中心の提案は
どれか、そしてロードマップのどの部分が孤立しているのか、といった問いです。

構造についての問いの答えは、すでにメタデータの中にあります。見る方法がないだけです。ある項目の
`関連` の行を読めば、その項目に隣接する項目はわかります。しかし、そのまわりのまとまり全体に届くには、
隣接する項目を1つずつ開き、積み上がった像を記憶に保ち続けなければなりません。ロードマップには約330件の項目があり、
そのうち約200件が少なくとも1つの関係を宣言しています。この規模になると、探索を手作業でこなせません。しかも、まさにこの探索こそ、貢献者が新しい作業の範囲を見積もるときに行うものです。
提案について最初に立つ問いは、それが何に触れるのか、だからです。

ダッシュボードはドキュメントサイトの静的な生成物なので、この変更はどの絶対的指針
（[`CLAUDE.md`](../../CLAUDE.md)）にも抵触しません。大規模言語モデル（LLM）はこのページの近くに
一切現れず、`run` や継続的インテグレーション（CI）の合否判定の経路もここを通りません。関係図は
メタデータが生む項目に対して汎用なので、テスト対象のアプリケーション固有の要素も持ちません。
判定の経路から離れていても、決定性はこの設計を形作ります。配置の初期位置は乱数生成器ではなく
各ノードの添字から決めるので、同じロードマップからは常に同じ図が得られ、読者が自分の画面と同僚の
画面を見比べても同じ形が見えます。

## 詳細設計

ダッシュボードは [`scripts/build_roadmap_dashboard.py`](../../scripts/build_roadmap_dashboard.py)
が生成します。各項目をトピックの節の中の `.be-card` として描き、同じ項目を `.be-row` のテーブル行に
写し、1つのインライン `<script>` ブロックで両方を段階的に拡張する作りです。関係図は、この既存の構造に
第3の兄弟要素として収まります。作業は、互いに重複がなく全体を覆う（MECE な）次の単位に分かれます。

1. **共有の項目モデルへの関係の追加**。
   [`scripts/build_roadmap_index.py`](../../scripts/build_roadmap_index.py) の `Item` に、項目の
   メタデータがすでに宣言している3つの関係 `related`、`origin_refs`、`superseded_by` を、項目 ID の
   タプルとして追加します。読み取りは、英語側のメタデータ欄の `Related`、`Origin`、`Superseded by`
   の値から `BE-NNNN` の形をした字句をすべて拾う方法で行います。値は書き手が書いた Markdown であり、
   1つ以上のリンクを含むので、字句を拾う読み方であれば書き手が選んだリンクの書き方に依存せずに済みます。
   読み込んだツリーにディレクトリが存在しない ID と、項目が自分自身を指す参照は落とします。こうすれば、
   1つのファイルの誤記から端点のない辺が生まれることはありません。英語ファイルだけから関係を読むのは、
   `Status` と `Topic` をすでにそう読んでいるのに合わせるためであり、日本語側だけの言い回しの修正で
   図が変わってしまうことも防げます。
2. **ページへのグラフデータの出力**。関係図が必要とするノードと辺を、`<script type="application/json">`
   要素の中の1つの JSON として出力します。既存のカードのマークアップに属性として散らさないのは、
   辺が項目の対に属するものであり、どちらか一方のカードに置く自然な場所がないからです。ノードは ID、
   タイトル、トピック、状態のバケット、そして GitHub 上のファイルへのリンクを持ちます。辺は2つの端点と
   種別を持ちます。`関連` は双方の項目が宣言することを期待される相互の関係なので、2つの向きは1つの
   無向辺にまとめます。`由来` と `後継` は有向のままにします。「そこから派生した」と「それに置き換え
   られた」は、どちらも一方向にしか読めない関係だからです。
3. **力学モデルによる配置**。配置は、このページのために書いた小さなシミュレーションがブラウザ上で
   計算します。力は3つです。すべてのノードの対にはたらく斥力、すべての辺にはたらく
   引力、そして連結していない部分がキャンバスの外へ流れ去らないようにする弱い中心への引力です。
   この3つを、決められた回数だけ冷却しながら回して停止します。初期位置は `Math.random()` ではなく、各ノードの添字から黄金角の螺旋上に
   決めるので、配置は再現します。あわせて、斥力は理想的な辺の長さの数倍を超えたところで打ち切り、
   落ち着いた結果をキャンバスに収まるよう拡大縮小します。ロードマップの関係は、1つの大きな連結成分と
   多数の小さな連結成分からなり、成分どうしを引き留めるのは中心への引力だけです。どちらの手当ても
   なければ、小さな成分は外へ流れ去り、大きな成分は読めない塊に潰れます。シミュレーションを回すのは、
   ページの読み込み時ではなく読者が最初に関係図を開いたときにします。Cards から動かない読者に計算の
   負担を負わせないためです。
4. **描画と操作**。結果はスケーラブルベクターグラフィックス（SVG）で描きます。辺ごとに線を1本、
   ノードごとに円を1つ描きます。円は項目の状態の色を持ち、大きさはその項目が宣言する関係の数で
   決まります。ラベルを常に出すのは中心となるノードだけにします。200個のラベルを同時に出せば読めなく
   なるからです。残りのノードは、ポインタを重ねたとき、フォーカスを当てたとき、そしてツールチップで
   自分の ID を示します。各ノードは項目の
   GitHub 上のファイルを指す SVG のアンカー要素で包み、クリックハンドラを付けた図形ではなく本物の
   リンクにします。こうすればキーボードからも辿れ、新しいタブでも開けます。ノードのドラッグは
   ノードを動かし、続いて発火するクリックを抑止するので、ドラッグでページを離れてしまうことは
   ありません。背景のドラッグは平行移動、マウスホイールは拡大縮小にあて、ノードにポインタを重ねるか
   フォーカスを当てると、そのノードと辺、そして辺の先の項目以外が暗くなります。
5. **既存の表示切り替えへの第3の選択肢の追加**。`Cards` と `Table` の隣に `Graph` のボタンを足します。
   1つの表示だけを見せて残りを隠し、読者の選択を `localStorage` に保存する仕組みは既存のものを
   そのまま使います。関係図は検索ボックスとステータスチップにも従います。絞り込みで外れた項目の
   ノードは辺ごと隠れ、残ったノードは外れた隣接項目のぶんだけ辺が減った姿になります。ダッシュボードの
   ほかの操作と同じく、関係図も段階的拡張です。関係図の領域はマークアップでは隠されていて表示の
   切り替えでしか現れないので、スクリプトを無効にした読者には現在とまったく同じ Cards 表示が見えます。
6. **関係を持たない項目の扱いを隠さないこと**。関係を1つも宣言していない項目は、関係図に描く場所を
   持ちません。約130個の孤立した点を図のまわりに並べれば、関係図が見せようとしている構造がその中に
   埋もれます。そこで、少なくとも1つの関係を持つ項目だけを描き、描かなかったことをページ上に明記します。
   関係図が何件を描き、何件が関係を1つも持たないのかは、図に添えるキャプションが伝えます。
   ダッシュボードが見せるデータについて、BE-0094 は2つの原則を立てました。メタデータに根拠のない
   数値を出さないことと、ある表示に実際にはない網羅性を読者へ暗示させないことです。作業単位6は、
   その2つを守るためにあります。
7. **スタイル**。関係図のキャンバス、ノード、辺、キャプションのスタイル規則を生成側のスタイルシートに
   足します。色は、カードとバッジがすでに使っている状態ごとの色を再利用します。ノードの色がページのどこでも
   同じ意味を持ち、明るいテーマと暗いテーマのどちらでも読めるようにするためです。
8. **テスト**。[`tests/test_roadmap_dashboard.py`](../../tests/test_roadmap_dashboard.py) と
   [`tests/test_roadmap_index.py`](../../tests/test_roadmap_index.py) を拡張して、機械的に検査できる
   成果を固定します。メタデータ欄から関係のフィールドが読めること、自分自身への参照と存在しない項目への
   参照がどちらも落ちること、相互に張られた `関連` の対がちょうど1本の無向辺になること、出力される
   すべての辺の端点が出力されたノードであること、出力されるノードの集合が関係を持つ項目そのもので
   あること、そしてページが3つ目の切り替えボタンと関係図の領域を描くことを確かめます。これらのテストは
   ブラウザを必要としないので、ゲートは速いまま、LLM とも無縁のままです。

ページ冒頭の説明文には、Cards と Table を説明している文の隣に、第3の表示を説明する一文を足します。
[`docs/`](../../docs/README.md) 配下のドキュメントに対応する修正は必要ありません。ダッシュボードに
言及しているページは、ダッシュボードが何のためのものかを説明していて、どの表示を備えるかは
書いていないからです。将来そこに表示を列挙する記述が生まれたときは、表示を追加する変更と同じ変更で
更新します（[BE-0113](../BE-0113-design-doc-realignment/BE-0113-design-doc-realignment-ja.md)）。

## 検討した代替案

- **Mermaid でビルド時に図を生成する**。ドキュメントサイトはすでに `mermaid` のコードフェンスを
  描画できるので、生成した `graph LR` のブロックを埋め込む案が変更としては最小です。採用しませんでした。
  Mermaid はこの規模のグラフを、縦横に長い階層として配置します。読者に残るのは探索ではなく
  スクロールであり、絞り込み、ドラッグ、隣接の強調のいずれも使えません。約200個のノードを持つグラフを
  読めるものにしているのは、まさにそうした操作です。Mermaid の図は項目ごとの要素ではなく1つの不透明な
  ブロックとして描画されるので、既存の検索ボックスとステータスチップも働きかける先を持ちません。
- **D3 や Cytoscape のようなグラフ描画ライブラリを導入する**。採用しませんでした。ドキュメントサイトは
  JavaScript のバンドラーを持たず、外部スクリプトへの依存も持っていません。ダッシュボード全体が、
  インラインのスタイルと1つのインラインスクリプトからなる1枚の生成ページとして意図的に作られています。
  数百個のノードのための力学モデルの配置は短く完結した処理です。バンドルされた依存を1つ増やし、
  その出所を検証すべき対象も増やすことになるので、得るものはわずかです。
- **関係を持たない項目も含めて全項目を描く**。採用しませんでした。関係を持つ項目のあいだの構造を
  見せるための図のまわりに、約130個の孤立した点を置くことになります。しかも、どの辺も引き留めない
  大きなノードの環と中心への引力が押し合うことになります。描かなかったことは、作業単位6のキャプションが
  黙らせずに伝えます。
- **依存の順序を描けるように `依存` のメタデータ欄を新設する**。この項目では採用しませんでした。
  依存を表す辺は `関連` とは異なる主張であり、約330件の既存項目についてそれを主張するには、書き手が
  1件ずつ埋め戻す作業が要ります。生成される表示が肩代わりできる作業ではありません。関係図は、
  ロードマップがすでに記録している関係を描くものです。新しい関係を提案するのは別の作業です。
- **Cards か Table を関係図で置き換える**。採用しませんでした。どちらの表示の役割も関係図では
  果たせません。Cards は「このトピックには何があり、どこまで進んでいるか」に答え、Table は「最近
  何が変わったか」に答えます。どちらの問いも、ノードと辺の図のほうが答えやすくなるものではありません。
