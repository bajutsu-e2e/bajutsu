## Introduction

Add a relationship graph to the roadmap status dashboard — the GitHub Pages page that
[BE-0094](../BE-0094-roadmap-status-dashboard/BE-0094-roadmap-status-dashboard.md) generates from
each roadmap item's metadata, that
[BE-0219](../BE-0219-roadmap-dashboard-search/BE-0219-roadmap-dashboard-search.md) gave a search
box, and that [BE-0311](../BE-0311-roadmap-dashboard-table-view/BE-0311-roadmap-dashboard-table-view.md)
gave a sortable table. A roadmap item's metadata block already names the other items it stands in a
relation to: `Related` lists the items it belongs with, `Origin` records the item it grew out of, and
`Superseded by` names the item that replaced it. No view has ever drawn those relations. The graph
draws them as a third view beside Cards and Table: one node per item, colored by status, and one edge
per relation, laid out by a force-directed simulation that runs in the reader's browser. A reader
drags a node, pans and zooms the canvas, and hovers a node to light up its immediate neighbors; the
search box and status chips narrow the graph exactly as they narrow the other two views.

The graph adds no new metadata field and asks no author to maintain anything new. Every edge it draws
is read from a relation an item already declares, so the picture is a rendering of the committed
roadmap rather than a second record that could disagree with it.

## Motivation

The dashboard answers questions about items one at a time. Cards view groups items by topic and shows
each item's status; Table view sorts every item by id, title, topic, status, or date. Both treat the
roadmap as a list, and a list cannot answer the questions a reader asks about *structure*: which items
form a cluster around one feature, which proposal is the hub that several later items hang off, and
which corners of the roadmap stand alone.

Those questions have concrete answers in the metadata today, and no way to see them. Reading the
`Related` row of one item tells a reader its immediate neighbors, but reaching the cluster around it
means opening each neighbor in turn and holding the accumulated picture in memory. Across a roadmap of
roughly 330 items, about 200 of which stand in at least one relation, that traversal is impractical by
hand — and it is exactly the traversal a contributor performs when scoping new work, because the first
question about any proposal is what it touches.

The dashboard is a static artifact of the documentation site, so this change stays clear of every
prime directive ([`CLAUDE.md`](../../CLAUDE.md)). No large language model (LLM) sits anywhere near the
page, no `run` or continuous integration (CI) verdict path passes through it, and the graph is generic
over whatever items the metadata produces, so nothing about it is specific to an application under
test. Determinism still shapes the design even away from the gate: the layout draws its starting
positions from each node's index rather than from a random number generator, so the same roadmap
always produces the same picture, and a reader comparing the page against a colleague's screen sees
the same shape.

## Detailed design

The dashboard is generated by
[`scripts/build_roadmap_dashboard.py`](../../scripts/build_roadmap_dashboard.py), which renders every
item as a `.be-card` inside a topic section, mirrors the same items as `.be-row` table rows, and
progressively enhances both with one inline `<script>` block. The graph slots into that existing
structure as a third sibling view. The work is mutually exclusive, collectively exhaustive (MECE)
across these units:

1. **Relation edges on the shared item model.** Extend
   [`scripts/build_roadmap_index.py`](../../scripts/build_roadmap_index.py)'s `Item` with the three
   relations an item's metadata already declares: `related`, `origin_refs`, and `superseded_by`, each
   a tuple of item ids. Read them from the English metadata block by extracting every `BE-NNNN`
   token from the `Related`, `Origin`, and `Superseded by` values — a value is author-written
   Markdown holding one or more links, so a token scan reads it without depending on the link syntax
   an author chose. Drop a token naming an item that the loaded tree has no directory for, and drop
   an item's reference to itself, so a typo in one file cannot produce an edge with no endpoint.
   Reading the relations from the English file alone matches how `Status` and `Topic` are already
   read, and keeps a Japanese-only wording fix from changing the graph.
2. **Graph data on the page.** Emit the nodes and edges the graph needs as one JSON payload in a
   `<script type="application/json">` element, rather than as attributes spread across the existing
   card markup, because an edge belongs to a pair of items and has nowhere natural to live on either
   one's card. A node carries its id, title, topic, status bucket, and the link to its file on
   GitHub; an edge carries its two endpoints and its kind. `Related` is a mutual relation that both
   items are expected to declare, so the two directions collapse into one undirected edge; `Origin`
   and `Superseded by` each stay directed, since "grew out of" and "was replaced by" both read in
   one direction only.
3. **Force-directed layout.** Lay the graph out in the browser with a small simulation written for
   this page — repulsion between every pair of nodes, attraction along every edge, and a weak pull
   toward the center that keeps a disconnected component from drifting off the canvas — cooled over a
   fixed number of steps and then stopped. Seed the starting positions from each node's index along a
   golden-angle spiral, never from `Math.random()`, so the layout is reproducible. Cut the repulsion
   off beyond a few ideal edge lengths and scale the settled result to fit the canvas: the roadmap's
   relations form one large component alongside many small ones, and nothing but the centering pull
   holds two components together, so without both measures the small components drift outward and
   squash the large one into an unreadable blob. Run the simulation the first time a reader opens the
   graph rather than on page load, so a reader who never leaves Cards view pays nothing for it.
4. **Rendering and interaction.** Draw the result as Scalable Vector Graphics (SVG): a line per edge,
   and a circle per node carrying its item's status color, sized by how many relations the item
   takes part in. Label only the hubs at rest — two hundred labels at once are unreadable — and let every
   other node name itself on hover, on focus, and through its tooltip. Wrap each node in an
   SVG anchor pointing at the item's file on GitHub, so a node is a real link — reachable by keyboard
   and openable in a new tab — rather than a shape with a click handler. Dragging a node moves it and
   suppresses the click that would otherwise follow, so a drag never navigates away. Dragging the
   background pans, the mouse wheel zooms, and hovering or focusing a node dims everything except
   that node, its edges, and the items on the other end of them.
5. **A third view in the existing toggle.** Add a `Graph` button beside `Cards` and `Table`, reusing
   the toggle that already shows one view and hides the others and already persists the reader's
   choice in `localStorage`. The graph honors the search box and the status chips: a node whose item
   is filtered out is hidden along with its edges, and the filtered-out neighbors of a visible node
   simply leave it with fewer edges. Like the rest of the dashboard's interactivity, the graph is
   progressive enhancement — its view is hidden in the markup and shown only by the toggle, so a
   reader with scripting off sees the Cards view exactly as they do today.
6. **Honest coverage of items outside the graph.** An item on no edge has no place in a
   relationship graph, and drawing roughly 130 unconnected dots around the picture would bury the
   structure the graph exists to show. Render the items that take part in at least one relation, and
   state the omission on the page: a caption reports how many of the roadmap's items the graph draws
   and how many take part in none. Word the caption as *participation* rather than *declaration*,
   because the two differ: `Origin` is one-directional, and `Related`'s expected reciprocity is a
   convention rather than a checked rule, so an item named only by another is drawn while declaring
   no relation of its own. Saying such an item "declares" a relation would be untrue, which is what
   BE-0094's rule about the data the dashboard shows forbids — never present a figure with no source
   in the metadata, and never let a view imply completeness it does not have.
7. **Styling.** Add the graph's canvas, node, edge, and caption rules to the generator's stylesheet,
   reusing the per-status colors the cards and badges already use so a node's color means the same
   thing everywhere on the page, and staying legible in both the light and the dark theme.
8. **Tests.** Extend [`tests/test_roadmap_dashboard.py`](../../tests/test_roadmap_dashboard.py) and
   [`tests/test_roadmap_index.py`](../../tests/test_roadmap_index.py) to pin the machine-checkable
   outcome: the relation fields parse out of a metadata block, a self-reference and a reference to a
   missing item are both dropped, a mutual `Related` pair yields exactly one undirected edge, every
   emitted edge names two emitted nodes, the payload's node set is exactly the items carrying a
   relation, and the page renders the third toggle button and the graph container. These tests need
   no browser, so the gate stays fast and free of any LLM.

The page's introductory prose gains a sentence describing the third view, next to the sentences that
already describe Cards and Table. No document under [`docs/`](../../docs/README.md) needs a matching
edit: the pages that mention the dashboard describe what it is for, not which views it offers. Should
a future sentence there enumerate the views, it is updated in the same change that adds one
([BE-0113](../BE-0113-design-doc-realignment/BE-0113-design-doc-realignment.md)).

## Alternatives considered

- **Render the diagram at build time with Mermaid.** The documentation site already renders
  `mermaid` fences, so a generated `graph LR` block would be the smallest possible change.
  Rejected: Mermaid lays out a graph of this size as a wide, deep hierarchy that a reader must scroll
  rather than explore, and it offers no filtering, no dragging, and no neighbor highlighting — the
  affordances that make a graph of about 200 nodes readable at all. The existing search box and
  status chips would also have nothing to act on, since a Mermaid diagram renders as one opaque
  block rather than as per-item elements.
- **Adopt a graph library such as D3 or Cytoscape.** Rejected: the documentation site ships no
  JavaScript bundler and no dependency on a third-party script, and the whole dashboard is
  deliberately one generated page with inline styles and one inline script. A force-directed layout
  for a few hundred nodes is a short, self-contained routine, so taking on a bundled dependency —
  and its supply-chain surface — buys little.
- **Draw every item, including those with no relation.** Rejected: it would put roughly 130 isolated
  dots around a picture whose point is the structure among the remaining items, and it would make the
  simulation's centering force fight a large ring of nodes that no edge holds in place. The caption
  in unit 6 keeps the omission visible instead of silent.
- **Add a `Depends on` metadata field so the graph can draw a dependency order.** Rejected for this
  item: a dependency edge is a genuinely different claim from `Related`, and asserting one across
  roughly 330 existing items would need an author-by-author backfill that no generated view can
  supply. The graph draws the relations the roadmap already records; proposing a new relation is
  separate work.
- **Replace Cards or Table with the graph.** Rejected: neither view's job is served by a graph.
  Cards answers "what is in this topic, and how far along is it", Table answers "what changed most
  recently", and neither question is easier to answer in a node-link picture.
