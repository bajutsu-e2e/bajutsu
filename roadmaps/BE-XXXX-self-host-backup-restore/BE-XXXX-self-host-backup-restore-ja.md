## はじめに

セルフホスト向けのサーバーバックエンドは、1台の Linux ノードで動いています。`deploy/self-host/` の
Docker Compose スタックは、各サービスを1つずつ動かします。ここで問題になるのは Postgres、MinIO
オブジェクトストア、Caddy リバースプロキシの3つです。3つとも予備がないため、どれか1つを失うとサービスが
止まります。もっとも影響が大きいのは Postgres です。Postgres は、ジョブキュー（`jobs` テーブル）、
セッション、クォータの状態、実行メタデータを抱えています。

この提案は、ディスクやマシンを失った単一ノードを、検証済みの手順で復旧できるようにします。追加するのは
次の3つです。

- リストアをリハーサル済みの Postgres のバックアップ
- 成果物バケットのバックアップ
- 予備のない構成要素と、それぞれを失ったときの損失の明示

この項目は BE-0168 を置き換えます。BE-0168 は、完全に冗長化した構成を定めていました。その構成には、
Postgres のレプリカ、分散配置の MinIO、2台のロードバランサが含まれていました。BE-0168 は却下とし、
バックアップと明示の2点をこの項目に引き継ぎました。理由は「検討した代替案」に書きます。

この項目は、セルフホストのアンブレラである
[BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md) から切り出したものです。
その後、[BE-0106](../BE-0106-post-completion-worker-model/BE-0106-post-completion-worker-model-ja.md)
が Redis を取り除きました。その結果、ステートフルなストアは Postgres だけになりました。

## 動機

現在のスタックには、バックアップの仕組みがまったくありません。`deploy/self-host/` の README には、
データベースをダンプするコマンドも、バケットを複製するコマンドもありません。セルフホストのガイドにも
ありません。どちらのページも、リストアの手順を示していません。このため、`pgdata` ボリュームの下の
ディスクが1つ壊れるだけで、キュー、セッション、クォータをまとめて失います。実行履歴もすべて失い、
文書化された復旧の道筋はありません。

リリースゲートとして Web UI に依存するチームにとっては、無停止よりもこの復旧の道筋のほうが先に必要です。
リストアがあれば、損失は最後のバックアップ以降の作業に限られます。数分から数時間の停止なら、多くの
セルフホストのチームが受け入れられます。実行履歴を際限なく失うことは受け入れられません。加えて、
バックアップはスタックに新しいサービスを足しません。レプリカや2台目のロードバランサは足します。

成果は運用者が確かめられます。運用者が新しいマシンで手順書に従うと、復元したスタックに、最後の
バックアップ時点の実行履歴と成果物が表示されます。

## 詳細設計

この項目は、すべてデプロイと運用の作業です。どの作業にも Python 側の面がないため、`make check` ゲートは
これらを動かしません。作業は次の3つの単位に分かれます。

| 作業単位 | 内容 |
|---|---|
| Postgres のバックアップとリストア | 定期的な `pg_dump` を Postgres コンテナで動かし、ダンプをノードの外へ複製します。手順書には、ダンプのコマンド、保持の規則、新しい `pgdata` ボリュームへのリストアを書きます。 |
| 成果物バケットのバックアップ | 定期的な `mc mirror` で、MinIO のバケットをノードの外の複製先へ写します。動画の証跡は容量が大きいので、複製先の容量の見積もり方を手順書に書きます。リストアでは、複製を新しい `miniodata` ボリュームへ書き戻します。 |
| 単一ノードのリスクの明示 | デプロイの README に、予備のない3つの構成要素（Postgres、MinIO、Caddy）を挙げます。それぞれについて、失ったときに止まるものと、再起動かリストアかの復旧方法を書きます。セルフホストのガイドの英語版と日本語版にも、同じ内容を載せます。 |

Postgres の手順書には、復旧時点も明記します。リストアは、最後のダンプより後に書き込まれた内容を
残しません。より新しい時点まで戻したい運用者に向けて、Postgres のトランザクションログを
アーカイブする方法も挙げます。

単一ノードのリスクの明示では、受け入れの条件も書きます。単一ノードが適するのは、これらのリスクを
受け入れ、リストアをリハーサル済みのセルフホストのチームです。

**検証。** ゲートはこの作業を担保しないため、運用者がデプロイを手で確かめます。リストアの訓練が本当の
テストです。

| 訓練 | 成功の条件 |
|---|---|
| 最新のダンプを新しいスタックへリストアする | サインインすると、実行履歴とセッションが残っています |
| バケットの複製をリストアする | 復元した実行のレポートを開くと、スクリーンショットと動画が読み込まれます |
| ダンプ時点でキューにあったジョブを調べる | リストアがジョブに与えた影響を手順書に記録してあります |

## 検討した代替案

**完全な高可用性の構成をこの項目で定める。** この項目では扱いません。理由は3つあります。

| 理由 | 内容 |
|---|---|
| Bajutsu に固有でない | フェイルオーバーを伴う Postgres のレプリカ、分散配置の MinIO、2台のロードバランサは、どれも一般的な運用の作法です。 |
| ゲートで検証できない | どの部品もスタックにサービスを足しますが、ゲートはそれらを確かめられません。 |
| 代わりの道がある | 無停止のフェイルオーバーが必要なチームは、マネージドの Postgres とオブジェクトストレージを使えます。マネージドのホスティング項目である BE-0015 は、そうした構成で動いています。 |

冗長化した構成は、セルフホストのチームから求めがあった時点で、新しい項目として扱えます。ロードバランサの
二重化は、複数レプリカの制御プレーンが入った後に組み合わせるのがもっとも自然です。その制御プレーンは
[BE-0167](../BE-0167-control-plane-scale-out/BE-0167-control-plane-scale-out-ja.md) が扱います。

**単一ノードを文書化しないまま残す。** 却下します。単一ノードは小規模なチームには十分です。しかし、
リスクを把握していない運用者は、ディスクの喪失に備えられません。リスクの明示とリストアの訓練は、少ない手間で
用意できます。

**Postgres ではなくアプリケーション側でキューを複製する。** 却下します。Postgres がすでに備えている
永続的な複製を、作り直すことになるからです。データベース1つのバックアップなら、キュー、セッション、
メタデータを1つの仕組みで一貫させられます。
