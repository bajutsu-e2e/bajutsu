## はじめに

本項目は、日本語の文章における**文体の乱れ**を検出するツールを追加します。`CLAUDE.md`と
[`japanese-document-writing`](../../.apm/skills/japanese-document-writing/SKILL.md)スキルは、
すべての`*-ja.md`ロードマップ項目と`docs/ja/`配下のページに敬体（ですます調）を求めています。
このツールは、文末の述語が敬体で終わっていない文を検出します。

検出方式は、列挙ではなく除外です。文末の述語を敬体の語尾のホワイトリストと照合し、一致しない
文をすべて検出対象とします。[GitHub Issue #1842](https://github.com/bajutsu-e2e/bajutsu/issues/1842)
は、常体の語尾を列挙する方式をすでに試しています。その試みは収束しませんでした。同じコーパスに
対する3回の試行が、3通りの異なる行数を返しています。

本項目は、コミット`5a586e4`が例外なく定めた規則も1つ狭めます。「箇条書きを含め、文書全体を
敬体で統一する」という規則です。`## Progress` / `## 進捗`のチェックリスト項目
（`- [ ]` / `- [x]`）は、この規則から名指しで除外されます。`japanese-document-writing`が
すでに持つ見出しと体言止めラベルの免除と同じ立場です。チェックリスト項目は作業を指すラベルで
あり、読者が追う地の文ではありません。

実装では、1つのファイルを完全に変換します。対象は
[BE-0089](../BE-0089-merge-time-be-id-allocation/BE-0089-merge-time-be-id-allocation-ja.md)です。
issue #1842は、このファイルの日本語版を常体が94％と記録しています。このファイルを変換すれば、
検出ツールと変換の手順が実際のファイルの上で噛み合うことを確認できます。

残りのコーパスを変換する作業は、本項目には含みません。この後も、およそ362ファイルが同じ変換を
待っています。本項目はこの残作業をあえて追跡しません。issue #1842を残作業の目印として開いた
ままにし、時間の空いたコントリビューターが1ファイルずつ変換し、検出ツールで確認してから小さな
PRを出す運用にとどめます。

## 動機

コミット`c34ed6110`（2026年6月24日）は、当時存在したロードマップ`*-ja.md`ファイル78件すべてを
敬体へ変換し、規範を5か所に明文化しました。`CLAUDE.md`と、日本語の文章スキル（現在の
`japanese-document-writing`）もその一部です。
[BE-0278](../BE-0278-tech-writing-skill/BE-0278-tech-writing-skill-ja.md)は、その後このスキルを
統括的な`document-writing`規範の下に位置づけ、コミット`5a586e4`が箇条書きにも明示的に広げ
ました。規範は3か月間、効力を保っています。

それでもコーパスは規範を超えて増え続けました。`main`上の現行ロードマップ`*-ja.md`ファイルは
425件です。そのうちおよそ347件は、敬体を求める規範がすでにある状態で`c34ed6110`より後に書かれて
います。残る78件は、同コミットが変換したファイルです。issue #1842は、その結果を計測しました。
コードフェンス、表、見出し、引用を除いて、363ファイル、2,193行が敬体の語尾で終わっていません。
BE-0089の日本語版は変換コミットの3日後に書かれ、常体94％と記録され、文書全体として一貫して
います。この乖離は、規範が間に合わなかった古い負債ではありません。規範がすでに及んでいた
新しい文章が、規範に従わず書かれた結果です。

信頼性の低い検出ツールは、本項目が避けようとしている失敗をそのまま引き起こします。過去に
BE-0089の一部を変換した試みは、一貫して常体だった文書を混在文書に変えてしまい、その編集は
元に戻されました。乱れを見逃す検出ツールは、同じ部分変換を再び招きます。正当な常体（連体修飾節、
条件や接続の形、体言止めのラベル）を確定した違反として報告するツールは、コントリビューターに
正しい文章を書き直させ、本物の乱れから注意をそらします。どちらの失敗も、本項目の設計が前提と
する規則を崩します。ファイルを完結させるか、手を付けないかのどちらかにするという規則です。

本項目が完了すると、変換済みファイルに対する検出ツールの結果そのものが、達成を確かめる材料に
なります。現時点で、検出ツールはBE-0089の日本語の文のほとんどを検出します。このファイルは常体が
94％を占めているためです。本項目の実装がこのファイルを変換した後は、検出ツールの結果に残るのは、
人が意図的に除外した候補だけになります。本物の乱れは残りません。

## 詳細設計

### 検出ツール

`scripts/ja_register_check.py`は、指定したファイル群を走査し、文体の乱れの候補となる文を
ファイル名と行番号ごとに報告します。対象は`*-ja.md`ロードマップ項目と`docs/ja/`配下の全ページで、
`japanese-document-writing`がすでに定めている範囲と同じです。

走査は、1文を見る前にコードフェンス、表、見出し、引用、そして`## Progress` / `## 進捗`の
チェックリスト項目を除外します。issue #1842自身の手動計測が使った除外範囲に、本項目が加える
チェックリストの除外を足したものです。次に、段落ごとに折り返された行をひとまとまりの
ブロックへ結合します。本リポジトリの文章はおよそ100桁で折り返されており、句点が付くのは段落の
最後の行だけです。行のまま分割すると、折り返しの途中行のほぼすべてが未終端の文として誤検出
されます。残ったブロックを、句点、感嘆符、疑問符で文に分割します。終端記号を持たないブロック
（多くは体言止めのラベル）は、そのまま1文として扱います。

検出方式は列挙ではなく除外です。各文を、日本語の形態素解析器にかけます。単純な語尾の文字列
照合では不十分です。文末の括弧書き、文末の助詞（「か」「ね」「よ」）、そして複数の形態素に
またがる助動詞の連なり（「ました」は「まし」と「た」に分かれます）は、いずれも敬体を実際に
担う形態素より後ろに現れます。文末の括弧書きは、閉じ括弧から対応する開き括弧までひとまとまり
として飛び越えます。「（BE-0089）」の中身が述語を隠さないようにするためです。ツールは文末から
形態素を遡り、これらを飛び越えます。遡った末尾の連なりに、「です」「ます」の形態素（見出し語で
判定）、または「ください」（見出し語は「下さる」）が含まれない文を候補として検出します。

このツールは、意図的に広く検出します。`japanese-document-writing`は、連体修飾節や、条件や
接続の形（「〜する場合」「〜すると」「〜であり」）を、文末の述語だけが文体を担うためすでに
除外しています。文末からの形態素の遡りは文中のこれらを見ないので、両方とも候補には現れません。
候補として現れるのは、純粋な体言止めのラベルです。見出しはすでに除外済みですが、地の文に
埋め込まれたラベルは除外されないためです。ツールはこれらを確定した違反ではなく候補として
報告します。ファイルを変換する作業は、正当な候補を人の手で取り除く作業でもあります。issue #1842
の提案自体が採った、広く検出してから絞り込むという2段階の設計と同じです。

検出ツールは`uv run scripts/ja_register_check.py <path>...`で実行します。
`make ja-register-check ARGS="<path>..."`でラップし、本リポジトリの他の`make`ターゲットと
形式を揃えます。`make check`には含めません。コーパスにはすでに約2,193行の検出候補が残っており、
この数をゲートにすると、バックログが片付くまで全コントリビューターのゲートが失敗し続けます。
これは、[`document-writing`](../../.apm/skills/document-writing/SKILL.md)がすでに文章の質を
レビュー時の規範として扱い、ゲートには置いていない方法と同じです。

### 依存はコミットしない

形態素解析器（`sudachipy`と辞書パッケージ）は、`pyproject.toml`と`uv.lock`のどちらにも加えません。
`scripts/ja_register_check.py`は、自分自身の依存関係をPython Enhancement Proposal（PEP）723の
インラインスクリプトメタデータとして持ちます。ヘッダーの形式は`# /// script`です。`uv run`はこの
ヘッダーを読み取り、実行のたびに隔離された環境を用意します。ベースのインストールも、他の
`uv sync`も、今のまま変わりません。このスクリプトを実行時にインポートするコードはなく、
パッケージのextraも不要です。開発者が直接実行するときだけ使う、開発用のツールです。

`mypy`はリポジトリ全体をstrictモードで検査しており、`scripts/`も対象に含まれます。そのため、
解決できない`sudachipy`のインポートにも対応が必要です。`[[tool.mypy.overrides]]`に
`sudachipy`と辞書パッケージの`ignore_missing_imports = true`を追加します。`boto3`や
`google-cloud-storage`が、型スタブを持たない外部ライブラリとしてすでに受けている扱いと同じ
仕組みです。
この仕組みは、`make check`がそもそもインストールしないパッケージに対しても同じように働き、
解析器を固定の開発環境にインストールしなくても、`typecheck`ステップは通ります。

この不在は、テストの形にも影響します。開発環境に`sudachipy`は入らないため、解析器は遅延
インポートの層の奥に置き、文末の形態素を遡る1つの関数からだけ呼び出します。
`tests/test_ja_register_check.py`は、事前の除外、文の分割、候補判定のロジックを、偽の
トークナイザーに対して検証します。[`pyproject.toml`](../../pyproject.toml)が`boto3`や
`google-cloud-storage`まわりの層についてすでに述べている「その周りのアダプタは型付けし、
テストする」という扱いと同じです。

### 方針変更: 進捗チェックリストの敬体を免除する

コミット`5a586e4`は、例外なくこう定めています。「箇条書きを含め、文書全体を敬体で統一する」。
文単位で見ると、`japanese-document-writing`はすでに3つの免除を持ちます。見出し、純粋な体言止め
のラベル、そして文末以外の節（連体修飾節や条件・接続の形）です。しかしどれも`## Progress` /
`## 進捗`のチェックリスト項目（`- [ ]` / `- [x]`）を覆いません。現行の文言のもとでは、
チェックリスト項目は地の文です。

本項目は、それでも4つ目の免除を加えます。見出しがすでに持つラベルの免除と同じ立場です。
作業を指すラベルは、読者が追う論証ではありません。見出しと体言止めラベルの2つの免除も、
ラベルと地の文というまさにこの区別に基づいています。この提案の調査で確認した実装済み項目は、
すでにこの書き方です。
[BE-0343](../BE-0343-prose-companion-pr/BE-0343-prose-companion-pr-ja.md)は各項目を作業ラベルと
して書き、[BE-0384](../BE-0384-record-issue-skill/BE-0384-record-issue-skill-ja.md)は常体の文
として書いています。書き方は2通りありますが、どちらも敬体の地の文ではないという点で同じです。
この免除は両方を覆います。この免除は、コーパスの実態を変えるのではなく言葉にするだけです。
現行の規範の文言どおりにこれらのチェックリストを変換すると、完了済みの作業ログに手を入れる
だけで、読者には何の益もありません。

改訂が必要な文は2つあります。textlint節の箇条書きの行に加え、文体節の「1つの文書のなかで
敬体と常体を混在させない」という一文もです。そのままでは、常体のチェックリスト項目が、敬体の
文書内で文体を混在させていると読めてしまいます。

### 手順を実証する: BE-0089

実装では、1つのファイルを完全に変換します。対象は
[BE-0089](../BE-0089-merge-time-be-id-allocation/BE-0089-merge-time-be-id-allocation-ja.md)の
日本語版で、issue #1842が常体94％と記録しているファイルです。変換の前後で検出ツールの結果を
比較することが、その証拠になります。変換前は、ファイル内の文のほとんどを検出します。変換後に
結果へ残るのは、人が意図的に除外した候補だけです。本物の乱れは残りません。

### 今回のスコープ外

残り約362ファイルの変換は、本項目には含みません。[検討した代替案](#検討した代替案)で述べる
とおり、この作業には専用の追跡の仕組みを設けません。

本項目は、変換したファイルが再び崩れることへの歯止めも加えません。BE-0089の日本語版が非準拠の
まま書かれたときも、規範はすでにこのファイルに及んでいました。本項目はその状況を変えません。
検出ツールは意図的に広く検出するため、その生の候補数は`coverage-floors.json`がカバレッジ数値を
ゲートするようにはファイルをゲートできません。ファイル単位の候補数によるラチェットは実在する
選択肢ですが、揺り戻しが仮説ではなく実際の問題だとわかった時点で、別項目に回します。

## 検討した代替案

| 代替案 | 概要 | 採らなかった理由 |
|---|---|---|
| 放置する | 新規執筆には規範が効いていることに頼り、既存ファイルは誰かが編集したときだけ敬体に近づくのを待ちます。 | コーパスは363ファイル、2,193行に及びます。日和見的な編集が年間に触れる範囲はごくわずかで、不整合は何年も残ります。 |
| PRがすでに触れているファイルに限って日和見的に直す | 検出ツールを作らず、PRがたまたま触れたファイルの文体を目視で直します。 | 敬体でない行を漏れなく見つける手段がなければ、目視による部分的な編集は、過去にBE-0089で実際に起きた結果を再現します。一貫して常体だった文書が混在文書になった結果です。 |
| 常体の語尾を列挙して検出する | 検出ツールを正規表現だけにとどめ、敬体のホワイトリストの代わりに既知の常体の語尾を列挙します。新規の依存は、一時的なものも含めて不要になります。 | issue #1842はまさにこの方式を試しており、収束させられませんでした。同じコーパスに対する3回の試行が1,254行、214行、424行という3通りの結果を返し、その後の除外方式での4回目の試行が2,193行を返しました。 |
| バックログに対してスケジュール実行でDraft PRを出す自動化 | [BE-0222](../BE-0222-daily-doc-freshness-pr/BE-0222-daily-doc-freshness-pr-ja.md)の毎日のdocs更新の仕組みを拡張します。AIが執筆したワークフローが、スケジュールに沿ってファイルをまとめて変換し、自らDraft PRを開きます。 | issue #1842は、この作業を一回限りの遡及的な片付けと位置づけており、BE-0222が対象とするような繰り返し発生する乱れではありません。ゼロになれば二度と動かなくなるバックログのために、ワークフローや権限、ジョブ内のガードといった常設の仕組みを維持するコストは、節約できる時間を上回ります。 |
