## はじめに

`manifest.json` や `report.html` などの実行結果を、エージェントが読める Model Context Protocol（MCP）のリソースとして公開します。

## 動機

MCP サーバはすでに `bajutsu_run` と `bajutsu_doctor` をツールとして公開しています。エージェントは run を*開始*できます。しかし run の価値は出力にあります。`manifest.json` は、各ステップが何をしたかを示す唯一の真実です。`report.html` は、人間向けの要約です。

現状では、ツールの応答からエージェントが得るのは manifest のファイルパスだけです。エージェントはそのファイルをプロトコルの外で読みにいきます。これはプロトコルの境界を壊します。

- エージェントがディスクへ直接アクセスできなければなりません。
- エージェントが run のレイアウト（`runs/<runId>/manifest.json`）を知っていなければなりません。
- MCP サーバを動かすホストとエージェントが、同じファイルシステムを共有しているとは限りません。

[証跡](../../docs/ja/glossary.md#証跡-capturepolicy-trace-triage)を MCP リソースとして公開すれば、この隔たりは埋まります。リソースは、ドキュメントをエージェントに渡すためのプロトコル本来の手段です。URI でアドレス指定でき、他のすべてと同じ経路で取得できます。run を起動したばかりのエージェントは、プロトコルを離れずに manifest を読み戻せます。これにより、「AI で書き、AI で調べる」ループが、ローカルシェルの上だけでなく MCP 越しにも機能します。

## 詳細設計

run の証跡を、`bajutsu://runs/...` という URI スキームの MCP リソースとして公開します。ツールを公開するのと同じ `bajutsu mcp` サーバが配信します。

- `bajutsu://runs/{run_id}/manifest.json`：指定した run の構造化 manifest です。
- `bajutsu://runs/{run_id}/report.html`：その run の自己完結した HTML レポートです。
- `bajutsu://runs/latest/manifest.json`：直近の run の manifest です。`bajutsu_run` を呼んだばかりのエージェントは、応答から run id を取り出さずに結果を読めます。

各ハンドラは、設定された `runs/` ディレクトリに対して run id を解決します。読み取りの前に、**パストラバーサルを拒否**します。リクエストが解決されるのはそのディレクトリ内のファイルだけで、上位へ抜けることはありません。存在しない run やアーティファクトに対しては、空のドキュメントではなくプレーンなエラーを返します。したがってエージェントは、「該当する run がない」と「run が manifest を生成しなかった」を区別できます。

この設計はプライムディレクティブの内側に収まります。リソースは**読み取り専用**です。決定的なランナーがすでに書き出した証跡を見せるだけで、LLM が合否に影響を与えうる経路は増えません。エージェントが読む manifest は、run／CI ゲートが判定に使ったものとまったく同じ `manifest.json` です。リソースは配信チャネルであり、第二の真実ではありません。リソースの配信は run ループと直交するので、ゲートは完全に LLM フリーのままです。

`runs/` ディレクトリはサーバ単位の設定（サーバに指定したディレクトリ）で、アプリ単位ではありません。どのアプリの証跡も同じ run ツリーの下に出力されるからです。

## 検討した代替案

**`bajutsu_run` から manifest をインラインで返す。** ツールが manifest 全体をテキスト応答に埋め込む案です。次の3点から却下しました。

- ステップごとの証跡を含む manifest は大きく、run とともに肥大化します。
- エージェントが詳細を必要とするかどうかにかかわらず、すべてのツール応答を膨らませます。
- 取得できるのは実行したばかりの run だけで、*過去の* run の証跡を取る手段がありません。

リソースはアドレス指定でき、必要なときに取得できます。

**エージェントにファイルパスを読ませる。** ツールがすでに manifest のパスを報告しているので、最も単純な選択肢です。却下しました。ファイルシステムの共有を前提とし、エージェントをプロトコルの外へ押し出すからです。MCP の窓口の眼目は、エージェントが Bajutsu のディスク上のレイアウトを知らずに済むことにあります。
