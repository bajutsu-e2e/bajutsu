## はじめに

継続的インテグレーション（CI）の `smoke (idb)` レーンが、シナリオの最初のステップで断続的に失敗します。
showcase の smoke シナリオは、冒頭で最初のリスト行（`stable.row.1`）を `wait` します。この待機が、操作を
一つも行わないうちに 10 秒でタイムアウトします。Simulator は boot し、アプリは起動し、起動後の準備完了判定も
通過しています。それでも起こります。この失敗は毎回バイト単位で同一で、再実行すれば解消します。PR #936 では
3 回続けて失敗し、4 回目でようやく緑になりました。

本項目は、この最初の待機の**根本原因を突き止めて硬化する**ことを提案します。目指すのは、手動の再実行なしに
レーンが 1 回目で緑になる状態です。

失敗したレーンを自動で再実行する仕組みは、あえて提案しません。ロードマップはそれを「取り込まない」に
挙げています。フラッキーさを隠してしまい、決定性優先の方針と緊張関係にあるからです。ここでの修正は、cold な
CI Simulator の settling に対して待機そのものを堅牢にすることです。再実行でタイムアウトを覆い隠すことでは
ありません。

## 動機

`smoke (idb)` レーンの再実行は、1 回あたり Simulator の boot、ビルド、実行でおよそ 7 分を要します。それ以上に、
ゲートへの信頼を損ないます。3 回再実行してようやく緑になるレーンは、赤いチェックを反射的に再実行する習慣を
貢献者に植え付けます。決定性優先の方針は、まさにこの習慣を避けるために存在します。4 回試してやっと得た緑は、
頼れる信号ではありません。

この flake は環境由来であり、プロダクトの欠陥ではありません。PR #936 で検証対象だった変更は、純粋に読み取り
専用の Python 集約です。ランナー、ドライバ、待機ロジック、デバイス経路のいずれにも触れません。同じ idb
バックエンドを同じ Simulator で走らせる姉妹レーン `conformance (idb + xcuitest)` は、その間ずっと緑でした。
したがって原因は、検証対象のコードとは独立に、cold boot した CI Simulator 上での smoke レーン自身の起動
タイミングにあります。

過去の作業は隣接する層を硬化しましたが、この層には及んでいません。

- **BE-0218** は、`_await_ready` を名前空間に基づく判定にしました。これにより、SpringBoard の名前空間外
  アイコンが準備完了判定を満たさなくなりました。準備完了判定の誤発火を修正したものです。
- **BE-0087** は、idb ドライバの操作経路に、投影に基づく settle と一時的な空ツリーへのバックオフを加えました。
- **BE-0207** は、XCUITest チャネルに一時的失敗のリトライを加えました。
- **BE-0088** は、Simulator の boot をクリティカルパスから外す並行化を加えました。

本項目が対象とする隙間は、準備完了判定とシナリオの最初の `wait` の受け渡しにあります。`_await_ready` は、
名前空間内の要素が現れた時点で、アプリを準備完了と判定できます。その判定は、シナリオが直後に待機する要素
（最初のリスト行）が、遅い cold boot の Simulator 上でレンダリングされて settle するより一瞬早く成立しえます。
10 秒の最初の待機は、そのレンダリングと競合し、ときおり負けます。

対策は、条件ベースにとどめる必要があります（固定の `sleep` を使わない。プライムディレクティブ 2）。
アプリ非依存にも保つ必要があります（ターゲットごとの差異は設定に置く。プライムディレクティブ 3）。

## 詳細設計

作業は、まず決定的な診断、次に的を絞った硬化、最後に機械検証可能な受け入れ条件、の順で進めます。各ユニットは
独立して出荷できます。

1. **失敗を再実行ではなく成果物から診断できるようにします。** 最初の待機がタイムアウトしたとき、候補となる原因の
   どれが発火したかを判別できるだけの状態を採取します。
   - タイムアウト時点の要素ツリー
   - 準備完了判定が通過していたか、どの信号で通過したか
   - 待機対象の要素がいつクエリ可能になったか（なった場合）

   この状態に、既存の BE-0049 の Run provenance（シナリオハッシュ、ツールバージョン、git リビジョン）を
   刻みます。これで、緑になるまでの再実行が証拠を捨ててしまう状況を解消します。このユニットは、後述の 3 つの
   仮説を、推測ではなくデータから判別します。

2. **準備完了判定から最初の待機への受け渡しを締めます。** シナリオが待機する内容が現れる前に準備完了判定が
   成立していると診断で示された場合は、その隙間を閉じます。方法は二つあります。showcase ターゲットの
   `readyWhen` を、シナリオが必要とする最初の内容を持つ要素に向けます。あるいは、名前空間の判定を強め、
   名前空間内の任意のノードではなく内容を持つ要素を要求します。変更は可能なかぎり設定を優先します
   （ターゲットの `readyWhen`）。共有の準備完了ロジックに触れるのは、隙間が一般的なときだけです。

3. **最初の `wait` を遷移途中の空ツリーに対して堅牢にします。** シナリオレベルの `wait_for` が、一時的な
   空ツリーや遷移途中のクエリを許容することを確認します。BE-0087 が操作経路で許容したのと同じ形です。起動遷移の
   最中に最初のポーリングが空ツリーに当たっても、待機の予算を静かに消費してはなりません。この経路が一時的な
   空ツリーへのバックオフでまだ覆われていなければ、拡張します。

4. **最初の待機の予算を cold な CI Simulator に見合う大きさにします。** cold boot した CI Simulator では
   （warm なローカルと比べて）レンダリングが本当に 10 秒を超えると診断で示された場合は、待機の予算を固定の
   定数ではなく、ターゲットや環境ごとに設定可能にします。待機は条件ベースのままです。速い環境は要素が現れ
   次第すぐ返り、遅い環境だけが大きな予算を使います。固定の `sleep` は導入しません。

5. **緑が続くことを証明します。** 受け入れ条件は機械検証可能にします。`smoke (idb)` レーンが、有界の回数だけ
   連続する CI 実行を通じて、手動の再実行なしに 1 回目で通過することです。これはゲート自身に対する決定的な
   チェックであり、LLM の判断ではありません。最後のユニットであり、ユニット 6 の硬化が入ったあとに観測します。

6. **アクセシビリティブリッジがアタッチに失敗した状態から回復します（ユニット 1 が明らかにした根本原因）。**
   ユニット 1 の診断が、発火していた原因を確定させました。それは上の 3 つのいずれでもありません。

   cold な CI Simulator の初回アプリ起動時に、`idb ui describe-all` が最上位の `application` 要素だけを、
   面積ゼロの frame で返すことがあります。idb のアクセシビリティブリッジが、アプリのウィンドウにアタッチ
   できていないのです。しかも、アプリ自体は完全にレンダリングされています。その実行のスクリーンショットには、
   待機対象の最初の行が写っています。準備完了判定と最初の `wait` は、内容の欠けたツリーをポーリングし、要素が
   画面に在るにもかかわらず、ともにタイムアウトします。

   ユニット 2〜4 が持ちこたえられなかった理由は、ここにあります。内容を持つ `readyWhen` も大きな予算も、
   `describe-all` が落とした要素を見ることはできません。

   この隙間を、idb ドライバで閉じます。クエリがこの兆候（面積ゼロの `application` ルートが 1 個だけ）を返した
   とき、そのデバイスの companion 接続をリセットします。リセットは `idb disconnect` に続けて `idb connect` を
   実行します。別の Simulator で走る並行 crawl レーンに触れないよう、グローバルな `idb kill` ではなく、
   デバイスごと（udid ごと）に実行します。リセットでアクセシビリティの再アタッチを促し、有界の回数だけ
   読み直します。

   本当に要素の少ない、しかしレンダリング済みの画面は、実際の frame を保つので、リセットしません。有界の
   リセットのあともツリーが同じ兆候のままなら、クエリはそれをそのまま返します。待機は、ユニット 1 の診断とともに
   loud に失敗します。回復が本物の失敗を覆い隠すことはありません。

   この回復は、構造的なツリーの形に基づく条件ベースなので、固定の `sleep` を導入しません（プライム
   ディレクティブ 2）。振る舞いはツリーを手掛かりにドライバ内に置くので、アプリとターゲットに非依存を保ちます
   （プライムディレクティブ 3）。判定経路に LLM を置きません（プライムディレクティブ 1）。

## 検討した代替案

- **失敗したレーンの自動再実行（reboot を伴う）。** 本項目の背骨としては採用しません。ロードマップは、すでに
  「失敗テストの自動リトライ」を「取り込まない」に挙げています。フラッキーさを隠し、決定性優先の方針と
  緊張関係にあるからです。仮にそうした仕組みを採用するなら、quarantine 用途に限ります。また、必ず loud で
  あり（アサーション失敗を静かに覆い隠さない）、provenance を刻む必要があります。そうすれば、隠れた flake が
  BE-0220 の Run 横断トリアージから見えるままになります。それは別に切り出して慎重に範囲を定める項目であって、
  本項目ではありません。
- **グローバルな待機タイムアウトを闇雲に引き上げる。** 採用しません。根本原因を覆い隠し、あらゆる環境の
  すべての実行を遅くします。ユニット 4 は、cold boot の真の分散が診断で示された箇所に限り、条件ベースかつ
  環境ごとの上限として予算を引き上げます。
- **boot 後に固定の `sleep` でウォームアップする。** 端的に採用しません。プライムディレクティブ 2 が固定の
  sleep を禁じており、待機は条件ベースのみです。
