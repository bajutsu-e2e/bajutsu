## はじめに

シナリオファイルの内部に、インラインの `components` ブロックを宣言できるようにします。各エントリは、名前を BE-0030 の**コンポーネント**（引数を取る再利用可能なステップ列）へ対応させます。有効範囲は、そのファイルの中だけです。同じファイル内の `use: { component: <name> }` ステップは、その名前を直接解決します。1つのファイルの中でしか使わないステップのまとまりに、別のコンポーネントファイルは不要になります。BE-0030 が定めたファイル参照形式の `use: { component: <path> }` は、変更なく動作し続けます。スイートをまたぐ再利用は、引き続きそちらが担います。

## 動機

BE-0030 は**コンポーネント**を定義しました。コンポーネントは、引数を取る再利用可能なステップ列です。`use` ステップが、run の前にコンポーネントを呼び出し元のステップ列へ展開します。コンポーネントは、常に専用のファイルに置く設計です。`use: { component: <path> }` ステップが、そのパスを解決します。

そのため、わずか3ステップ程度の短いまとまりを取り出すだけでも、新しいファイルが要ります。名前と、呼び出し元からの相対パスも要ります。この固定費用は、1つのシナリオファイルからしか呼ばれないコンポーネントでも、スイート内のすべてのファイルから呼ばれるコンポーネントでも、同じだけかかります。

再利用が1つのファイルの中だけで完結するとき、この固定費用は割に合いません。関連する複数のシナリオを1つのファイルにまとめて定義することは、よくあります。検索ボックスに異なるクエリを試す場合や、フォームに異なる入力の組み合わせを送信する場合です。こうしたファイルは、同じ短いステップのまとまりをそれらのシナリオ間だけで繰り返し、他のどこからも呼びません。

そのまとまりを別ファイルに切り出すと、ファイルが1つ増えます。読者は、`use` ステップの中身を確認するために、その新しいファイルを開かなければなりません。呼び出し元が1つのファイルしかないコンポーネントのために、その手間がかかります。この負担を避けたい作者は、各シナリオへステップを手で複製します。それは、BE-0030 がファイルをまたぐ場合について解消しようとした重複と、同じものです。

インラインでファイルに閉じた `components` ブロックは、この局所的な場合について負担を取り除きます。作者は、呼び出し元のシナリオと同じファイルの中にコンポーネントを定義できます。そのファイルだけで使う名前のために、スイートのディレクトリ一覧へ項目を1つ増やす必要はありません。

具体例を考えます。あるシナリオファイルが、`components` の下でコンポーネントを定義しています。同じファイル内の2つのシナリオが、`use: { component: <name> }` で呼び出します。このファイルは、ロード時に、手で複製した場合と同じステップ列へ展開されます。`bajutsu trace --explain` で展開後のステップを読めば、確かめられます。再利用のために2つ目のファイルが作られることもありません。

## 詳細設計

BE-0030 のファイル型コンポーネントに、ファイルに閉じた兄弟を追加します。解決には、同じ `use` ステップと、同じ `expand_components` マクロ（`bajutsu/common/scenario/expand.py`）を使います。ランナーは、これまでどおり展開済みのプレーンなステップだけを見ます。そのため、決定性は変わりません。

- **`ScenarioFile` への新しい `components` フィールド。** `ScenarioFile`（`bajutsu/common/scenario/models/scenario/scenario_file.py`）に、デフォルト値が空の `components: dict[str, Component]` を追加します。各エントリは `Component` モデル（`params` と `steps`）です。BE-0030 は、独立したコンポーネントファイルを同じモデルで検証しています。1つのスキーマで両方の形式を扱えます。
  - シナリオファイル自身にも、2つの記法があります（`docs/dsl-grammar.md` §2）。1つはシナリオを並べた素のリストで、もう1つは `{description, scenarios}` のマッピングです。
  - `components` を書けるのは、マッピングの側だけです。素のリストで書かれたファイルは、先に変換します。
- **名前はファイル内で解決し、パスはファイルとして解決します。両者は衝突しません。** `use: { component: <ref> }` のフィールドは、1つのままです。`ref` 自身の見た目が、解決方法を決めます。
  - `/` を含む `ref`、または `.yaml` か `.yml` で終わる `ref` は、ファイルとして解決します。BE-0030 がすでに、そのように解決しています。
  - どちらの印もない裸の名前は、そのファイル自身の `components` マップの中で、そのキーを探します。ただし、展開がまだそのファイル自身のスコープの中にある間だけです。いつそうであるかは、次の2つの項目で決めます。
  - 両者は、取り違えようがありません。シナリオファイル内の名前と、スイート内のファイル型コンポーネントは、同じ `use` ステップを共有できます。新しいフィールドと命名規約は要りません。
- **`ComponentResolver` オブジェクトが、`bajutsu run` とファイル非依存ツールの挙動をそろえます。** シナリオファイルを展開する経路は、今のところ2つあります。
  - `load_expanded_scenarios`（`bajutsu/common/scenario/load_expanded.py`）は、`trace --explain`、`audit`、`coverage`、`impact`、serve が使います。
  - `run/cli.py` の `_expand_file` は、決定的な run ゲート用に、独自の `resolve` クロージャを組み立てています。

  新しい `ComponentResolver` は、`load_expanded.py` に切り出します。ファイルシステムを扱わない設計の `expand.py` には置きません。`ComponentResolver` は、`resolve` 呼び出し可能オブジェクトを組み立てる唯一の場所になります。呼び出し可能オブジェクトは、ローカルな `components` マップ、`root`、`base` ディレクトリに束縛します。裸の名前かパスかの判定と、自分自身のキャッシュも持ちます。

  姉妹メソッドの `for_component_file()` は、空のマップに束縛した新しい `ComponentResolver` を返します。パス解決されたコンポーネント自身のステップを展開するためのものです。`expand_components` の引数 `resolve: Callable[[str], Component]` は、変更しません。`ComponentResolver` のインスタンスが、その条件をそのまま満たします。両方の経路がこれを組み立てて渡します。インラインの `components` ブロックは、どちらの経路でも同じように展開されます。

  2つの実装は、共有リゾルバがないせいで、すでに一度食い違っています。壊れたコンポーネントファイルを、`load_expanded_scenarios` は `invalid YAML in <file>` として報告します（BE-0150）。一方 `run/cli.py` は、同じ `yaml.YAMLError` をトレースバックのまま見せます。この例外は、`except (OSError, ValueError)` を通り抜けます。共有リゾルバは正規化する側に寄せるので、`run` も同じ明確なエラーを返すようになります。
- **コンポーネントファイルをまたぐと、同じ再帰の中で姉妹リゾルバへ切り替わります。** `expand_components` には、内部再帰 `expand(steps, stack)` があります（`bajutsu/common/scenario/expand.py`）。この再帰は、解決したコンポーネントの置換後ステップへ、すでに同じ呼び出しの中で再帰しています。パス形式の `ref` が解決された瞬間、その再帰呼び出しには、`resolve` の代わりに `resolve.for_component_file()` を渡します。
  - 切り替えは、`expand` 自身の `stack` と `max_depth` の管理の中で行います。新しく `expand_components` を呼び直すことはしません。呼び直すと、両方がリセットされるからです。本物のコンポーネント循環が、`RecursionError` になってしまいます。今日の `expand_components` は、代わりに明確なエラーを出します。
  - 空のマップの姉妹リゾルバの下で解決される裸の名前は、常に未定義です。プレーンな `Component`（`params` と `steps`）は、参照できる `components` を宣言しないからです。
  - 各 `ComponentResolver` のインスタンスは、自分自身のキャッシュを持ちます。今日の `expand_components` は、呼び出しごとに1つのキャッシュを持ちます。ここでは、そのキャッシュを展開全体で共有せず、リゾルバごとに分けます。2つの異なるリゾルバの下で解決される同じ裸の名前は、衝突しません。2つのリゾルバは、2つのコンポーネントファイルのものでも、シナリオファイルとコンポーネントファイルのものでもかまいません。
  - ファイル内コンポーネント自身のステップは、呼び出し元と*同じ*リゾルバの下で展開されます。そのため、ファイル内コンポーネントは、別のファイル内コンポーネントを引き続き `use` できます。ファイル型コンポーネントも `use` できます。パス形式の `ref` は、この切り替えの影響を受けないからです。
  - ファイル型コンポーネント自身のステップは、ローカルマップを一切持ちません。そのため、裸の名前を `use` できません。
- **setup プレリュードは、差し込む前に、自分自身の `use` ステップを展開します。** `setup` 参照（`Preconditions.setup`）も、シナリオファイルと同じ形をしたドキュメントを指します。`apply_setups`（`bajutsu/common/scenario/expand.py`）自体は、変更しません。呼び出し元から渡された `resolve: Callable[[str], list[Step]]` を受け取ります。その戻り値のステップを、呼び出し元シナリオのステップの前に差し込みます。
  - 変わるのは、`run/cli.py` の `resolve` クロージャです。`apply_setups` を呼ぶのは、このクロージャだけです。`load_expanded_scenarios` は、setup を一切適用しません。ファイル非依存の読み取り経路は、この項目の有無にかかわらず、シナリオの `setup` をもともと無視します。
  - クロージャは、これまでプレリュードのステップを未展開のまま返していました。今後は、次の4つを行います。
    1. プレリュードの `ScenarioFile` を読み込みます。
    2. プレリュード自身の `components` マップ、プレリュード自身のディレクトリ、同じスイートの `root` に束縛した `ComponentResolver` を組み立てます。
    3. そのリゾルバの下で、プレリュード自身のステップに `expand_components` を実行します。
    4. 結果を返します。
  - 未展開の `use` ステップが、プレリュードから、それを取り込むシナリオへ渡ることはありません。共有プレリュードの裸の名前は、常にプレリュード自身の `components` に対して解決されます。たまたまプレリュードを `setup` に指定したシナリオのマップに対しては、解決されません。
  - プレリュード自身のパス形式の `ref` は、引き続きプレリュード自身のディレクトリに対して解決されます。この点は、他の場所のパス形式の `ref` と同じで、BE-0174 の封じ込めの内側にとどまります。今日、このリポジトリのシナリオとプレリュードに、そのような `ref` は1つもありません。既存のスイートで見た目が変わるものはありません。
- **新しいパス封じ込めの対象は増えません。** ファイル内のコンポーネントは、ローダがすでに読んだシナリオファイルと一緒に、1回だけ解析されます。名前の解決が2つ目のファイルを開くことはありません。BE-0174 の封じ込めチェックが新たに守るべき対象は、ここにはありません。
- **ファイルに閉じます。** `components` は、ファイルごとに読み込まれます。スイートディレクトリ内の他のファイルへ合成されることはありません。`load_scenarios_dir` は、各ファイルを独立にロードするからです。あるファイルで宣言した名前は、他のファイルから見えないままです。ファイルをまたぐ再利用は、引き続き BE-0030 のファイル参照が担います。

この項目がない今日、その重複に直面した作者には、選択肢が2つあります。1つ目は、ステップを手で複製することです。

```yaml
# 1つのシナリオファイル。同じ3ステップを、必要とする各シナリオへコピーしている
scenarios:
  - name: 犬で検索すると1件返る
    steps:
      - type: { text: dog, into: { id: home.search }, submit: true }
    expect:
      - label: { sel: { id: home.status }, equals: "1 result" }
  - name: 猫で検索すると2件返る
    steps:
      - type: { text: cat, into: { id: home.search }, submit: true }
    expect:
      - label: { sel: { id: home.status }, equals: "2 results" }
```

2つ目は、このファイル1つからしか呼ばれないコンポーネントのために、BE-0030 のファイル1つ分の費用を払うことです。この項目のインラインな `components` ブロックは、第三の道を与えます。同じファイルの中で定義し、同じファイルの中で呼び出す道です。

```yaml
# 1つのシナリオファイル。別のコンポーネントファイルは不要
components:
  search:
    params: [query]
    steps:
      - type: { text: "${params.query}", into: { id: home.search }, submit: true }

scenarios:
  - name: 犬で検索すると1件返る
    steps:
      - use: { component: search, with: { query: dog } }
    expect:
      - label: { sel: { id: home.status }, equals: "1 result" }
  - name: 猫で検索すると2件返る
    steps:
      - use: { component: search, with: { query: cat } }
    expect:
      - label: { sel: { id: home.status }, equals: "2 results" }
```

## 検討した代替案

**スイート全体を暗黙に検索するレジストリ（裸の名前をすべてのファイルから探す）。** 不採用です。今回の項目が対象とする再利用は、もともと1つのファイルの中だけで完結します。スイート全体を検索しても、ファイルに閉じた規則以上のものは得られません。スイート全体から裸の名前を探す設計は、この境界を、BE-0030 のスイートをまたぐ役割へ押し戻してしまいます。BE-0174 が閉じたパス封じ込めの論点も、呼び戻します。実ファイルという答えがすでにある場合について、その論点を蒸し返す理由はありません。

**ファイル内再利用のための YAML アンカーとマージキー。** 不採用です。理由は、BE-0030 がスイートをまたぐ再利用について、同じ選択肢を退けた理由と同じです。アンカーは、`with` が `params` へ値を渡すような、名前付きで検証済みの引数を取れません。呼び出し元は、展開後のテキストを手で書き換えない限り、呼び出しごとに再利用ブロックの中身を変えられません。

**`use` に区別用の構文を足す案（例えば `component: "local:<name>"`）。** 不採用です。代わりに、`ref` 自身の見た目で判定します。パス的な `ref` か、裸の名前かを見ます。このリポジトリの既存シナリオが持つファイル参照は、すでにすべて `.yaml` か `.yml` で終わっています。見た目による判定なら、`use` に新しい構文を足す必要はありません。このリポジトリのシナリオは、すべて変更なく動作し続けます。

意味が変わる `ref` の形が、1つだけあります。`.yaml` / `.yml` の拡張子を持たず、`/` も含まない、コンポーネントファイルを指す裸の ref です。そのような ref は、ファイルとして解決される代わりに、未定義のコンポーネントとして大きな声で失敗するようになります。これは意図したトレードオフで、リスクは低いと見ています。このリポジトリのシナリオに、そのような ref は1つもありません。書きうるのは、このリポジトリの外にあるスイートだけです。

  `stack`／`max_depth` の管理の下で行うため、コンポーネントファイルをまたぐ循環も今までどおり
  きれいに失敗します。setup の `resolve` も書き換え、プレリュード自身の `use` ステップを
  裸の名前とパス参照の両方について、前置の前にプレリュード自身のスコープで展開するように
  しました。ドキュメントと両方の `docs/ja/` 鏡も更新しました。進捗のチェックボックスはすべて
  チェック済みになり、状態は実装済みへ移ります。
