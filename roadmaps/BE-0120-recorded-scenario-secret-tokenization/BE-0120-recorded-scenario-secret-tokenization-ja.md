## はじめに

`bajutsu record` は、作成した scenario をそのまま書き出します。そのため、探索中に authoring agent が入力したシークレットは、リテラルな平文として scenario ファイルに残ります。本提案は、記録されたシークレットをリテラル値のまま書く代わりに、`${secrets.*}` へトークン化します。

## 動機

`record`（`bajutsu/cli/commands/record.py:203`）は、完成した scenario を書き出します。呼び出しは `out_path.write_text(dump_scenarios([scenario]), encoding="utf-8")` です。書き出す `Step` オブジェクトは、record ループ（`bajutsu/record.py`）が積み上げたものそのものです。途中に秘匿や置換の処理は挟まりません。

record ループは、エージェントが入力したリテラルなテキストを保持する `type` ステップを追加します（`_describe_step`、`bajutsu/record.py:46` は `step.type.text` を読みます）。このテキストには、ログインや API キーのフローを実演する際に、パスワード欄やトークン欄へ入力した値も含まれます。

`${secrets.*}`（BE-0032）は、*実行時*の著者に対して、すでにトークンだけを持つ scenario を提供しています。実際の値は環境変数から解決され、エビデンスからもマスクされます。しかし `record` は、この仕組みよりも上流に位置します。人間または記録用エージェントが与えた生の入力を、シークレット束縛という概念が登場する前に捕捉するからです。

そのため、実際のログインに対して記録した scenario は、パスワードや API キーを YAML に平文で書き込みます。この値は、リポジトリへのアクセス権を持つ誰からも読めます。コミットすれば、コミット履歴にも残ります。さらに、その scenario ファイルを後から含むエビデンスや成果物にも、秘匿されないままコピーされます。

深刻度は Medium です。本レポートの他の項目（TOTP のシード漏えいやネットワークのシークレット漏えい）とは異なり、この漏えいは、実際の資格情報を扱う scenario の*主たる作成経路*上にあります。`record` は、ほとんどの scenario を作る方法そのものだからです。この露出は、特殊なステップ型でしか現れないまれな端例ではなく、通常のケースです。

## 詳細設計

1. **recorder が捕捉した入力の中から、束縛済みのシークレット値を検出する。** `type` ステップ（またはテキストを保持する他のステップ）を追加する前に、そのリテラル値を、ターゲットに宣言された `secrets:` の解決済みの値と比較します。`run` は、この環境変数の解決を `${secrets.X}` に対してすでに行っています（`bajutsu/cli/commands/run.py:335-338`）。`record` も同じ config を参照できます。そのため、新たなシークレット宣言の仕組みを追加せずに、同じ束縛を解決できます。
2. **一致した場合はリテラル値ではなくトークンを書く。** 捕捉した値が解決済みのシークレット束縛と一致した場合は、その値を `scenario.steps` へ追加する前に `${secrets.X}` へ置き換えます。こうすれば、`record` が書き出すファイルは、最初から BE-0032 が想定するトークン形式になります。完成した YAML に対する別個の後処理は不要です。
3. **一致しない値には手を加えない。** 宣言されたどのシークレットにも一致しない入力値は、これまでどおり記録します。記録される入力の大半は、タップやシークレットではないテキストで、これに当たります。本提案が変更するのは、`secrets:` に宣言済みの束縛に対応する入力だけです。そのため、通常のケースに新たな手作業は増えません。
4. **置換を著者に提示する。** `record` の既存の進捗の説明（`bajutsu/cli/commands/record.py` の `say` コールバック）で、あるステップのテキストがトークン化されたことを報告します。これにより、実行結果を確認する著者は、あるフィールドが黙って書き換えられたのではなく、`${secrets.X}` へ置き換わったことを把握できます。

## 検討した代替案

- **書き出した YAML に対する事後の scrub パスとして、記録済みシークレットを秘匿する。** 却下しました。このファイルには適さない形だからです。BE-0032 自身が持つ書き出し後の scrub（`_scrub_secret_values`）は、run がすでに実際の値を使ったあとで、*結果*のテキスト（アサーションの actual と expected）へ漏れ出たシークレット値を捕まえるためのものです。一方、scenario ファイルの `type.text` は、*次回*の run でそのステップが何をするかを決める正本そのものです。

  事後の scrub には、2 つの結末があります。検出できなければ、リテラルがそのまま残ります。プレースホルダーに置き換えれば、再生が壊れます。秘匿済みの scenario は、有効な資格情報をもう入力できないからです。動作する `${secrets.X}` トークンとして書き換えた場合に限り、scrub は機能します。それこそが、書き出し時点でのトークン化が直接行うことです。
- **記録した scenario を著者が手動で編集し、`${secrets.*}` に置き換えるよう求める。** 修正すべき現状そのものなので、却下しました。この方法は、記録した資格情報のたびに、すべての著者が編集を忘れずに行うことを前提とします。編集を 1 度でも見落とせば、現状とまったく同じように、平文のシークレットがファイルに残ります。
- **捕捉した値が宣言済みのシークレットと一致するステップの記録を拒否し、著者にプレースホルダーでの撮り直しを強制する。** 却下しました。この拒否は記録フローを壊します。エージェントは、実演しようとしている認証後の画面へ到達するために、本物の資格情報を必要とするからです。しかも、もともと必要だった値を透過的にトークン化するほうが、著者にとって明らかに望ましい結果です。

- 2026-07-04: 記録されたシークレットを書き出し時点でトークン化しました。`_secret_tokens`
  （`bajutsu/cli/commands/record.py`）がターゲットに宣言された `secrets:` を環境変数から解決し
  （`run` の `_resolve_secrets` の逆方向にあたります）、`record()` は一致した `type` ステップの
  テキストを、記録する前に `${secrets.X}` トークンへ書き換えます。アプリ自体は本物の値で操作
  するため、認証後の画面には従来どおり到達します。マスキングは実行中の進捗出力にも及び、
  ステップ行だけでなくエージェントの理由づけ（`note`）も対象にするため、リテラルがストリームや
  ファイルへ漏れることはありません。
