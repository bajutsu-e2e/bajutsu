## はじめに

`agents/alerts.py` のシステムアラートガードは、ライブの AI 操作が実デバイス上で予期しない
システムダイアログ（権限プロンプト、クラッシュ時のシート）へ盲目的に作用してしまうのを止めるために
存在します。`record` と `crawl` は同じ `_build_alert_guard`（`bajutsu/cli/_shared.py`）を共有しており、
決定的な `run --dismiss-alerts` 経路（`bajutsu/cli/commands/run.py`）も、このガードを利用します。
これに触れるテストはすべて、手組みの `AlertDecision` か、テスト作者が
座標を打ち込んだだけの `FakeBlock` による tool-use レスポンスを与えており、実モデルが実際の
スクリーンショットを見て判断したものではありません。本項目は、このガードが本来果たすべき役割、
すなわち本物のアラートが表示された本物の画面に対して、Claude が dismiss（閉じる）コントロールを
正しく特定できるかどうかの実モデル検証を追加します。

## 動機

`tests/test_alerts.py` の `StubLocator` と `FakeBackend(FakeBlock("resolve_alert", ...))` は、
このガードのコードが、受け取った `AlertDecision` を正しくアクションへ配線していることを証明します。
これは配線に対する実質的で有用な検証です。しかし、このガードが本来主張する安全性は別の話です。
実デバイスから捕捉した本物のアラートダイアログを実際に視覚モデルへ与えたとき、その判断が、隣にある
破壊的な「削除」ボタンなどではなく、正しい dismiss の座標へ確実に着地するかどうかは何も証明しません。
ここで実モデルが誤った判断を返すことは些細なバグではなく、このガードが本来防ぐべき当のものに失敗する
ことを意味します。しかも現行のテストスイートはそれを一切検出しません。実モデルに本物のアラートを
見せて判断させるテストが1つもないからです。

## 詳細設計

提案の粒度です。作業は以下の単位に沿って MECE に分かれます。

- **本物のアラートによるフィクスチャ一式を用意する**：ショーケースアプリ上の実際のシステム
  アラートのスクリーンショットを捕捉します（最低限、権限プロンプトを1つ。再現できるならクラッシュ
  /エラーシートも）。少なくとも1つは、近くに破壊的なコントロールがあるダイアログを含め、
  フィクスチャ一式が「*何らかの*ボタンを見つけた」と「*正しい*ボタンを見つけた」を区別できる
  ようにします。
- **API キーでゲートしたライブ検証テスト**：各フィクスチャに対して、実際の認証情報でガードの
  実際の視覚処理経路を呼び出し、返ってきた座標が正しい dismiss コントロールの frame 内に収まって
  いることを検証します。単に何らかの決定が返ってきたことだけを確認するのではありません。
- **まずゲート対象外のシグナルとして着地させる**：
  [BE-0282](../BE-0282-real-backend-network-coverage/BE-0282-real-backend-network-coverage-ja.md)
  の前例に従い、このガードの呼び出し元に触れる CI レーンへシグナルとしてまず組み込み、必須
  チェックにするのはそのあとで検討します。本項目が検証するのはガードの実際の精度のみであり、
  ガードの位置づけ（Tier 1、ライブの AI 操作）を変えたり、決定的な `run` の判定にガードを近づけたり
  することはありません（prime directive 1）。

## 検討した代替案

- **ガードの配線が正しいことを根拠に、ユニットテストを信頼する**：正しい配線は、ガードが渡された
  `AlertDecision` に従って行動することを保証しますが、実モデルが本物のアラートを見たときに常に
  *正しい*決定を出すかどうかについては何も語りません。それこそがここで問われている安全性の
  性質です。
- **`record` の一般的なライブ利用テストでカバーされているとみなす**：そのようなテストは現状
  存在しません。`record` 自体に実モデルによる CI カバレッジがないためです。したがって本項目が
  乗れる既存の安全網はありません。

**ログ**

- 起動済みの iPhone 17 Simulator（iOS 26.5）上のショーケース SwiftUI アプリから、4つのフィクスチャ
  すべてを捕捉し、`tests/fixtures/be0308/` にコミットしました。通知プロンプト、位置情報プロンプト
  （3つの選択肢が縦に並び、拒否するのは最下段だけ）、iOS のプロセス間ペースト同意、そしてアプリ自身の
  削除確認の4つです。最後のものは、赤い `Delete` が `Archive` と `Cancel` のあいだに座っており、
  これが破壊的コントロールのケースにあたります。しかも要件のより鋭い形になっています。このダイアログ
  は OS のプロンプトではないので、ガードはプロンプトなしと報告しなければなりません。ガードが手を
  伸ばしかけるボタンは、削除するボタンだからです。捕捉は
  `tests/test_alert_fixtures_ondevice.py` が行います。各ボタンの frame は目で採寸するのではなく
  デバイスから読み取ります。3つの OS プロンプトは `handleSystemAlert` が解決に使うのと同じ
  アクセシビリティクエリ（BE-0316）から、アプリ自身のダイアログはアプリの要素ツリーから取得します。
  期待するボタンがデバイスから実際に報告されなければフィクスチャの
  書き込みを拒むので、OS やロケールの変化は、正解データを黙って書き換えるのではなく捕捉の失敗として
  現れます。これは手動のローカル作業であり、CI のどのジョブも実行しません。
- API キーでゲートしたライブテスト（`tests/test_real_model_alerts.py`）を追加し、
  [`ai-smoke.yml`](../../.github/workflows/ai-smoke.yml) にゲート対象外の2つめのジョブ
  `accuracy (system-alert guard)` として組み込みました。BE-0282 の前例に従い、既存のジョブが引くのと
  同じ境界を共有します。起動は `workflow_dispatch` のみ、認証情報は `ai-smoke` Environment に
  スコープするので、フォークからの実行が認証情報を目にすることはありません。ダイアログは
  コミット済みの捕捉物なので、このライブテスト
  に Simulator は要らず、ライブなのはモデル呼び出しだけです。認証情報なしで毎回のゲートを走る決定的な
  3つの層が、この検証を空振りさせません。1つめは合成したダイアログに対するもので、スタブロケータを
  使い、判定ヘルパが dismiss コントロール上の答えを通し、その隣の許可ボタン上の答え、アプリ自身の
  ダイアログの破壊的なボタン上の答え、そして何も指さない答えを落とすことを証明します。2つめは
  コミット済みの各捕捉物に対するもので、記録された*誤った*ボタン上の答えがすべて落ちることを求め
  ます。記録された dismiss コントロールを狙っても何も証明できません。frame はつねに自身の中心を
  含むからです。3つめは、フィクスチャ自身の正規化座標からポイント座標への写像を
  `SystemAlertGuard.dismiss` 自身の算術に対して固定するテストで、これによりこの検証は自分自身では
  なく製品を測ります。認証情報なしのどの層でも捕捉できないのは、記録された dismiss コントロールが
  誤ったボタンを指している場合です。それを決められるのはスクリーンショットを見ることだけであり、
  ライブの層の役割になります。
- 検証の対象は、ガードの実機でのタップではなくロケータの答えに絞りました。捕捉の途中で2つの欠陥が
  表面化しましたが、どちらもガードの視覚判断ではなく*アクチュエーション*経路にあり、本項目の主題の
  外にあります。いずれもここに記録し、本項目で直すのではなく別項目に委ねます。1つめは、
  `SystemAlertGuard.dismiss` がモデルの正規化された答えを
  `screen_size_from_elements(driver.query())` を通して写している点です。遅延リストが画面外の行を
  ツリーに保持しているとこの値が画面を超過することは、BE-0326 がすでに確認しています。ショーケース
  アプリで実測すると、実際の画面が (402, 874) のところ (418, 2456) を報告します。その結果、通知
  プロンプトの `Don’t Allow` ボタンに対する完全に正しい答えが (127, 518) から (132, 1456) へ、つまり
  画面の下端の外へ移ります。まさにこのために BE-0326 が導入した `Driver.viewport()` が正しい取得元
  であり、ガード
  はそれを使っていません。2つめは、1つめと独立した欠陥です。アプリにスコープされた XCUITest の
  座標タップは、SpringBoard のプロンプトのボタンをそもそも押せません。どちらのボタンからも遠い
  (5, 5) へのタップが通知プロンプトを消し、アプリの状態は `authorized`、つまりプロンプトの許可側の
  デフォルトボタンになりました。一方、何も触らないプロンプトは15回のポーリングを通じて出たままでした。
  つまりプロンプトを解決しているのは座標ではなく操作そのものです。したがって、このツールチェイン上で
  視覚ガードが SpringBoard のプロンプトに対して発火した場合、結果はつねにプロンプトのデフォルトボタンに
  なります。これはガードが文書化している「もっとも破壊的でない選択」というデフォルトの逆であり、しかも
  レポートにはモデルが選んだボタンが記録されたままです。決定的なネイティブ経路（BE-0315 / BE-0316）は
  この影響を受けません。
