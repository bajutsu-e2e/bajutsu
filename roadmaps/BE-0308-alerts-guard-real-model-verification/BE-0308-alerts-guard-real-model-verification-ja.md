## はじめに

`agents/alerts.py` のシステムアラートガードは、ライブの AI 操作が実デバイス上で予期しないシステム
ダイアログへ盲目的に作用してしまうのを止めます。予期しないダイアログとは、権限プロンプトやクラッシュ時の
シートです。ガードを使う呼び出し元は2つあります。

- `record` と `crawl`。両者は同じ `_build_alert_guard`（`bajutsu/cli/_shared.py`）を共有しています。
- 決定的な `run --dismiss-alerts` 経路（`bajutsu/cli/commands/run.py`）。

このガードに触れるテストはすべて、手組みの `AlertDecision` か、テスト作者が座標を打ち込んだだけの
`FakeBlock` による tool-use レスポンスを与えています。実モデルが実際のスクリーンショットを見て判断した
ものを使うテストは、ありません。

本項目は、ガードが本来果たすべき役割の実モデル検証を追加します。本物のアラートが表示された本物の画面に
対して、Claude は dismiss（閉じる）コントロールを正しく特定できるか、という検証です。

## 動機

`tests/test_alerts.py` の `StubLocator` と `FakeBackend(FakeBlock("resolve_alert", ...))` が証明するのは、
ガードのコードが受け取った `AlertDecision` を正しくアクションへ配線していることです。これは配線に対する、
実質的で有用な検証です。

しかし配線の検証は、ガードが本来主張する安全性を何も証明しません。その主張とは、実デバイスから捕捉した
本物のアラートダイアログを実際の視覚モデルに与えたとき、判断が正しい dismiss の座標へ確実に着地する、
というものです。着地してはならない先は、dismiss コントロールの隣にある破壊的な「削除」ボタンの座標です。

ここで実モデルが誤った判断を返すことは、些細なバグではありません。ガードが本来防ぐべき当のものに失敗する
ことを意味します。現行のテストスイートは、その失敗を一切検出しません。実モデルに本物のアラートを見せて
判断させるテストが、1つもないからです。

## 詳細設計

提案の粒度です。作業は以下の単位に沿って MECE に分かれます。

- **本物のアラートによるフィクスチャ一式を用意する**：ショーケースアプリ上の実際のシステムアラートの
  スクリーンショットを捕捉します。最低限、権限プロンプトを1つ用意します。再現できるなら、クラッシュや
  エラーのシートも加えます。少なくとも1つは、近くに破壊的なコントロールがあるダイアログを含めます。
  これにより、フィクスチャ一式は「*何らかの*ボタンを見つけた」と「*正しい*ボタンを見つけた」を区別できます。
- **API キーでゲートしたライブ検証テスト**：各フィクスチャに対して、実際の認証情報でガードの実際の視覚
  処理経路を呼び出します。返ってきた座標が、正しい dismiss コントロールの frame 内に収まっていることを
  検証します。何らかの決定が返ってきただけでは足りません。
- **まずゲート対象外のシグナルとして着地させる**：
  [BE-0282](../BE-0282-real-backend-network-coverage/BE-0282-real-backend-network-coverage-ja.md)
  の前例に従い、ライブテストを、ガードの呼び出し元に触れる CI レーンへ組み込みます。必須チェックにする
  のは、まずシグナルとして走らせたあとで検討します。
  - 本項目が検証するのは、ガードの実際の精度だけです。
  - ガードの位置づけ（Tier 1、ライブの AI 操作）は変えません。
  - 決定的な `run` の判定に、ガードを近づけることもしません（prime directive 1）。

## 検討した代替案

- **ガードの配線が正しいことを根拠に、ユニットテストを信頼する**：正しい配線が保証するのは、ガードが渡された
  `AlertDecision` に従って行動することです。実モデルが本物のアラートを見たときに常に*正しい*決定を出すか
  は、何も語りません。それこそが、ここで問われている安全性の性質です。
- **`record` の一般的なライブ利用テストでカバーされているとみなす**：そのようなテストは現状存在しません。
  `record` 自体に実モデルによる CI カバレッジがないため、本項目が乗れる既存の安全網はありません。

- 削除確認は破壊的コントロールのケースにあたり、要件のより鋭い形になっています。ガードはプロンプトなしと

- 捕捉は `tests/test_alert_fixtures_ondevice.py` が行います。各ボタンの frame は、目で採寸せず、デバイスから

  - 3つの OS プロンプトは、`handleSystemAlert` が解決に使うのと同じアクセシビリティクエリ（BE-0316）から
    取得します。
  - アプリ自身のダイアログは、アプリの要素ツリーから取得します。
  - 期待するボタンがデバイスから報告されなければ、フィクスチャの書き込みを拒みます。OS やロケールが変わっ
    ても、正解データが黙って書き換わらず、捕捉の失敗として現れます。
  - この捕捉は手動のローカル作業であり、CI のどのジョブも実行しません。
- API キーでゲートしたライブテスト（`tests/test_real_model_alerts.py`）を追加しました。
  [`ai-smoke.yml`](../../.github/workflows/ai-smoke.yml) に、ゲート対象外の2つめのジョブ
  `accuracy (system-alert guard)` として組み込んでいます。BE-0282 の前例に従います。
  - このジョブは、既存のジョブが引くのと同じ境界を共有します。起動は `workflow_dispatch` のみで、認証情報は
    `ai-smoke` Environment にスコープします。フォークからの実行が認証情報を目にすることはありません。
  - ダイアログはコミット済みの捕捉物なので、ライブテストに Simulator は要りません。ライブなのはモデル呼び出し
    だけです。
- 認証情報なしで毎回のゲートを走る決定的な3つの層が、ライブテストを空振りさせません。
  - 1つめは、合成したダイアログに対する層です。スタブロケータを使い、判定ヘルパが dismiss コントロール上の
    答えを通すことを証明します。その隣の許可ボタン上の答え、アプリ自身のダイアログの破壊的なボタン上の答え、
    何も指さない答えを落とすことも、証明します。
  - 2つめは、コミット済みの各捕捉物に対する層です。記録された*誤った*ボタン上の答えが、すべて落ちること
    を求めます。記録された dismiss コントロールを狙っても、何も証明できません。frame はつねに自身の中心を
    含むからです。
  - 3つめは、フィクスチャ自身の正規化座標からポイント座標への写像を、`SystemAlertGuard.dismiss` 自身の
    算術に対して固定するテストです。これにより、検証は自分自身ではなく製品を測ります。
  - 認証情報なしのどの層でも捕捉できないのは、記録された dismiss コントロールが誤ったボタンを指している
    場合です。それを決められるのはスクリーンショットを見ることだけであり、ライブの層の役割になります。
- ライブの層を `claude-code` プロバイダ（BE-0176）経由で実モデルに対して実行しました。ロケータは、すべての
  捕捉物に正しく答えました。
  - 通知プロンプト：(126.6, 517.8) を返しました。`Don’t Allow` の中心 (127, 518) との差は、0.5 ポイント
    未満です。
  - 位置情報プロンプト：(200.7, 574.1) を返しました。縦に並ぶ3つの選択肢の最下段です。このケースが、「*何らか
    の*ボタンを見つけた」と「*正しい*ボタンを見つけた」を分けます。
  - ペースト同意：(200.7, 481.0) を返し、`Don’t Allow Paste` の内側に収まりました。
  - アプリ自身の削除確認：プロンプトなしと報告し、赤い `Delete` に手を伸ばしませんでした。
  - これらのダイアログについて、ガードの視覚判断は健全です。健全でないのは、その下のアクチュエーション経路
    であり、次に記録します。
- 検証の対象は、ガードの実機でのタップではなく、ロケータの答えに絞りました。捕捉の途中で2つの欠陥が表面化
  しました。どちらも、ガードの視覚判断ではなく*アクチュエーション*経路にあり、本項目の主題の外にあります。
  いずれもここに記録し、本項目で直さず、別項目に委ねます。
  - **画面サイズの写像**：`SystemAlertGuard.dismiss` は、モデルの正規化された答えを
    `screen_size_from_elements(driver.query())` を通して写しています。遅延リストが画面外の行をツリーに
    保持していると、この値が画面を超過することは、BE-0326 がすでに確認しています。ショーケースアプリで実測
    すると、実際の画面が (402, 874) のところ (418, 2456) を報告します。その結果、通知プロンプトの
    `Don’t Allow` ボタンに対する完全に正しい答えが、(127, 518) から (132, 1456) へ、つまり画面の下端の外へ
    移ります。まさにこのために BE-0326 が導入した `Driver.viewport()` が正しい取得元ですが、ガードはそれを
    使っていません。
  - **SpringBoard へのタップ**：1つめと独立した欠陥です。アプリにスコープされた XCUITest の座標タップは、
    SpringBoard のプロンプトのボタンをそもそも押せません。どちらのボタンからも遠い (5, 5) へのタップが
    通知プロンプトを消し、アプリの状態は `authorized`、つまりプロンプトの許可側のデフォルトボタンになりま
    した。一方、何も触らないプロンプトは、15回のポーリングを通じて出たままでした。プロンプトを解決している
    のは、座標ではなく操作そのものです。
  - したがって、このツールチェイン上で視覚ガードが SpringBoard のプロンプトに対して発火した場合、結果は
    つねにプロンプトのデフォルトボタンになります。これは、ガードが文書化している「もっとも破壊的でない
    選択」というデフォルトの逆です。しかもレポートには、モデルが選んだボタンが記録されたままです。決定的な
    ネイティブ経路（BE-0315 / BE-0316）は、この影響を受けません。
