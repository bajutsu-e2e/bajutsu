## はじめに

iOS の run は Simulator の画面を録画しており、その録画にはジェスチャのもたらした結果がすべて写る一方で、
ジェスチャそのものは写りません。録画を見る人は、画面の変化だけを手がかりに、どの画素が触られたのかを
推測することになります。この項目では、テスト対象アプリが実際に受け取ったタッチの位置に、アプリ自身の
プロセス内でマーカーを描画します。タッチは録画とステップごとのスクリーンショットの両方に、対応する
フレーム上の目に見える印として現れます。マーカーを描くもとになるのは、ドライバが送った座標ではなく、
アプリが取り出した `UIEvent` です。この違いによって、マーカーは操作の意図を描き直したものではなく、
タッチが届いたことの証跡になります。可視化は既定で無効であり、証跡専用で、どのアサーションも参照しない
ため、決定的な判定には一切影響しません。

## 動機

最近の 2 つの項目によって、run の成果物は「そのジェスチャはどこに落ちたのか」という問いにあと一歩の
ところまで近づきました。[BE-0345](../BE-0345-actuation-record/BE-0345-actuation-record-ja.md) は各
ステップが実際に操作した座標を記録し、[BE-0346](../BE-0346-video-timing-sync/BE-0346-video-timing-sync-ja.md)
は録画の確定した開始時刻へステップのタイムスタンプを合わせ、レポートの動画シークが正しいフレーム
へ着地するようにしました。2 つを合わせれば、表から座標を読み取り、対応する時刻まで動画をシークして、
目視で数値とフレームを突き合わせられます。ただし、その突き合わせは毎回読み手の作業です。しかも座標は
point 単位、動画のフレームは画素単位ですから、読み手が端末の倍率まで思い出さないかぎり数値は意味を
持ちません。

より深い欠落は、座標の記録では、失敗したタップが投げかける本当の問いに答えられないことです。
[BE-0345](../BE-0345-actuation-record/BE-0345-actuation-record-ja.md) が記録するのは
[driver](../../docs/ja/glossary.md#driver-backend-actuator-platform) がプラットフォームへ手渡した値で
あり、それが Bajutsu 自身に観測できる最後の地点です。タップが実行され、成功と報告され、しかし画面が
何も変わらなかったとき、run が生成するどの成果物とも矛盾しない説明が 2 つ立ちます。ドライバが狙った
点に目的のコントロールが存在しなかったのか、それともタッチがそもそもアプリに届かなかったのか、の
どちらかです。iOS では後者も珍しい話ではありません。iOS のドライバは通常、snapshot 済みの要素への
ハンドルを XCUITest に渡し、点の決定を XCUITest に委ねます。そのため記録には要素の矩形だけが残り、
座標は残りません。透明なオーバーレイにアプリが覆われていた run も、ウィンドウが first responder を
失っていた run も、正常に動作した run とまったく同じ記録を残します。

アプリの内側で描かれたマーカーは、2 つの説明を切り分けます。アプリがマーカーを描くのは、アプリが
タッチを受け取ったときだけだからです。`UIWindow.sendEvent(_:)` は、システムからアプリのジェスチャ
認識器やビューへ向かうすべてのタッチが通る単一の漏斗です。その地点にマーカーがあれば、タッチは届いて
おり、しかもアプリ自身が算出した位置を示しています。run が操作したと記録しているジェスチャの下に
マーカーがなければ、タッチは届かなかったことになります。どちらの事実も、現在の成果物からは復元でき
ません。

## 詳細設計

設計は、このコードベースに関する 1 つの既存の事実の上に成り立ちます。Bajutsu はすでに、テスト対象
アプリの内部で Swift のコードを動かしています。`BajutsuKit` は `BajutsuKit/` Swift パッケージの
ライブラリターゲットで、UIKit をリンクし XCTest はリンクしません。デモアプリはこれをパッケージ依存
として宣言しているため（`demos/showcase/ios/swiftui/project.yml:15-17`）、パッケージを採用したアプリ
は自身のプロセスに `BajutsuKit` を抱えます。もう一方の `BajutsuRunner` ターゲットは XCUITest の
ランナープロセスで動きます。ランナープロセスはアプリとは別のプロセスですから、アプリのウィンドウには
何も描画できません。以下で述べる実装は、すべて `BajutsuKit` に置きます。

### フックの位置と、サブクラス化ではなく swizzle を選ぶ理由

この項目が下敷きにする手法は、`sendEvent(_:)` を override した `UIWindow` のサブクラスを用意し、
アプリのウィンドウをそれで置き換えます。ここでは、割り込む地点だけを採用し、導入方法は採用しません。
アプリのウィンドウを差し替えることはアプリ自身のソースへの変更であり、プライム原則 3 はアプリごとの
差異をツールの外に置くことを求めているからです。代わりに `method_exchangeImplementations` を使い、
`-[UIWindow sendEvent:]` の実装をクラスそのものの上で入れ替えます。アプリのコードは一行も変わらず、
プロセス内のすべてのウィンドウがまとめて対象になります。

フレームワークのライフサイクルメソッドを swizzle する仕組みは、ここで新しく持ち込むものではありません。
`BajutsuScreen`（`BajutsuKit/Sources/BajutsuKit/BajutsuScreen.swift:84-97`）はすでに
`UIViewController.viewDidAppear(_:)` を入れ替えて画面遷移を報告しており、そのヘッダーには、この項目
がそのまま引き継ぐ論拠が記録されています。フレームワークのライフサイクルメソッドへのフックはアプリの
画面コードに一切触れないため、シグナルは app-agnostic なままだ、という論拠です。アプリが `UIWindow`
をサブクラス化して `sendEvent(_:)` を override している場合も対象に含まれます。その override が
`super` を呼ぶ以上、入れ替えた実装はスーパークラス側にあるからです。

### マーカーは `CALayer` で描き、`UIView` では描かない

Bajutsu はすべての[セレクタ](../../docs/ja/glossary.md#シナリオのオーサリング)を、`app.snapshot()` が
返すアクセシビリティ階層に対して解決します（`BajutsuKit/Runner/Sources/XcuitestElementProvider.swift:44`）。
そしてプライム原則 2 は、あいまいなセレクタが最初に一致したものを操作せず即座に失敗することを求めます。
したがって、その階層にノードを増やす可視化は、見た目だけの追加では済みません。要素数が変わり、
シナリオが一意だったセレクタをあいまいなセレクタに変えてしまう可能性が、どのアプリのどのステップにも
生じます。設計の要は、**マーカーがアクセシビリティ階層から見えないことを証明できる**という一点にあり、
素直な描画方法のうち条件を満たすものは 1 つだけです。

条件を満たすのは、`window.layer` に追加した `CALayer` です。`CALayer` は `UIResponder` ではなく、
アクセシビリティのプロトコルにも適合せず、ヒットテストにも参加しません。そのため `app.snapshot()` が
走査する階層に表現を持たず、セレクタから到達されることもありません。同等に見える 2 つの代替案が同等
ではない理由は、後述の *検討した代替案* に記録します。マーカーがビューではなくレイヤーであることは、
タッチの配送に関与しないことも意味します。可視化が、描こうとしているそのジェスチャを飲み込んだり
別の場所へ流したりする事態は起こりません。

レイヤーを選ぶ利点は、Android 側の可視化と比べるとはっきりします。showcase の Android のレーンは
OS の設定 `show_touches` と `pointer_location` を有効にしており
（`demos/showcase/android/Makefile:211-212`）、`pointer_location` は接点と移動の軌跡の両方を描きます。
この項目が iOS で揃えようとしている挙動が、まさにそれです。同じ Makefile は、ツリーを比較する
golden のレーンでも画素を比較する visual のレーンでも、この可視化を無効にしています。別のシステム
ウィンドウが描くオーバーレイは、スクリーンショットの画素とツリーのどちらにも影響しうるからです。
アプリ自身のウィンドウの中に置いた `CALayer` はツリーに影響しえないため、iOS の可視化は、
ツリーのゴールデンを検証しているあいだも有効のままにできます。後述の *作業分解* が
挙げる不変性の確認は、まさにこの性質に立っています。無効にしなければならないのは、画素を比較する
場面だけです。

### 有効化

有効化は起動時の環境変数 `BAJUTSU_TOUCH_MARKERS` で行い、可視化は値が `1` であることを要求します。
それ以外のいかなる条件でもフックは導入されず、変数を渡されないアプリの挙動は現在とまったく変わりません。
`BajutsuTouch.startIfEnabled(environment:)` は、デモアプリが起動時にすでに呼んでいる
`BajutsuNet.startIfEnabled()` から呼び出します。ただし呼ぶ位置は、`BajutsuScreen.startIfEnabled()` と
並ぶ後方ではなく、`BajutsuKit/Sources/BajutsuKit/BajutsuNet.swift:38` にある
`guard collectorURL != nil || !BajutsuMocks.shared.rules.isEmpty else { return }` よりも**手前**です。
この guard が存在するのは、ネットワークの観測とスタブがいずれもコレクタかモック規則を必要とするから
であり、タッチの可視化はどちらも必要としません。ネットワーク機能を一切使わない素の録画実行こそが、
この機能の使いどころです。

Python 側では、`bajutsu run` に `--touch-markers` フラグを追加し、シナリオの起動環境に変数を設定します。
やり方は `bajutsu/cli/commands/run.py:460` にある既存の `BAJUTSU_MOCKS` の注入と同じです。新しい伝送路
は要りません。起動環境はすでに `_launch_params()`
（`bajutsu/platform_lifecycle/environments/xcuitest.py:1262`）から `BAJUTSU_LAUNCH_ENV_*` の転送を経て
`RunnerServer.forwardedLaunchEnvironment`（`BajutsuKit/Sources/BajutsuRunner/RunnerServer.swift:56`）に
届き、ランナーがアプリを起動する前に `app.launchEnvironment` へ載ります
（`BajutsuKit/Runner/Sources/RunnerUITest.swift:54-57`）。

### 描画する内容

フックはイベントごとに `event.allTouches` を走査し、`UITouch` ごとに円のレイヤーと軌跡のレイヤーを
保持します。保持にはタッチのオブジェクト識別子を鍵にした辞書を使い、ロックは不要です。`sendEvent(_:)` は
メインスレッドでしか動かないからです。`.began` のタッチには `touch.location(in:)` の位置に半透明の
円を出します。`.moved` のタッチでは円を移動させたうえで軌跡を伸ばすので、スワイプは 1 点ではなく
経路を残します。`.stationary` のタッチでは円をその場に残し、長押しを読み取れるようにします。
`.ended` と `.cancelled` のタッチでは、円と軌跡をどちらも画面へ残します。円と軌跡は、タッチが
押されているあいだは緑、離れたあとは赤で描きます。この違いによって、フレーム 1 枚からでも、その瞬間の
ジェスチャと、前のジェスチャが残した跡とを区別できます。位置の更新は
暗黙のアニメーションを無効にした `CATransaction` の中で行うので、レイヤーは指の動きから遅れません。
フックが単一のタッチではなく `event.allTouches` を読むため、ピンチと回転では追加のコードなしに
2 つの接点と 2 本の軌跡が描かれます。

あるジェスチャの跡を消すのは次のジェスチャだけで、ほかの何ものでもありません。ほかにアクティブな
タッチが 1 つもない状態で `.began` が届いたとき、フックは新しい円を描く前に前のジェスチャのレイヤーを
取り除きます。タッチがまだ押されている最中に届いた `.began` は進行中のジェスチャに加わり、何も消し
ません。ピンチの 2 本目の指が 1 本目を消さずに済むのは、この規則によります。ここから 2 つの帰結が
生まれます。可視化はタイマーもフェードのアニメーションも時間の定数も持たないため、速い作業機と負荷の
かかった継続的インテグレーションのランナーとで挙動が変わる余地はありません。そしてステップが行った
ジェスチャの跡は、そのステップの終了時点でもまだ画面に残っています。この性質が、跡をそのステップの
スクリーンショットに写します。

したがってマーカーは、run がすでに取得している 2 つの成果物の両方に届きます。動画は
`xcrun simctl io <udid> recordVideo`（`bajutsu/simctl.py:191`）で取得され、Simulator の画面全体を
撮るため、アプリが描いたレイヤーはそのまま写ります。ステップごとのスクリーンショットは
`app.screenshot()`（`BajutsuKit/Runner/Sources/XcuitestElementProvider.swift:218`）で取得され、
アプリケーション要素に切り抜かれるため、アプリの矩形の内側にあるレイヤーはやはり写ります。
スクリーンショットはステップが落ち着いたあとに撮られますが、その時点でもそのステップ自身の
ジェスチャの跡は残っているので、`after.png` にはステップが触れた場所が写ります。長押しも同じです。
`press(forDuration:)` はタッチの離れたあとに戻るため、撮影の時点でタッチはすでに終わっていますが、
跡は残っているからです。スクリーンショット上のマーカーはフレーム上のマーカーと同じ証跡ですから、
抑制せず、意図した挙動として文書化します。

## 検討した代替案

**マーカーを `UIView` としてウィンドウに追加する。** 下敷きにした手法は半透明の `UIView` を
ウィンドウの subview として追加しますが、採用しませんでした。理由は *詳細設計* が土台に据えたものと
同じです。XCUITest はアクセシブルでない素のコンテナビューを `.other` 要素として露出させるため、
マーカーは、すべてのセレクタが解決対象とするツリーの要素数を変えてしまいます。
`accessibilityElementsHidden` を付けても救えません。隠れるのはビューの子孫であって、ビュー自身では
ないからです。

**マーカーを、高い window level の別の `UIWindow` に描く。** 専用のオーバーレイウィンドウは、subview
より優れているどころか劣ります。`app.snapshot()` が返すツリーの根はアプリケーション要素で、その直接の
子はウィンドウ群ですから、ウィンドウを 1 つ増やすことは、`app.windows` のクエリすべてから見える
トップレベルのノードを 1 つ増やすことになります。

**動的ライブラリとして注入し、`BajutsuKit` を採用していないアプリも対象にする。** 既存の起動環境を
通じて `DYLD_INSERT_LIBRARIES` を渡せば、パッケージを採用しなくても任意の Simulator アプリに届きます。
Xcode 自身も `libXCTestBundleInject.dylib` を同じ方法で注入しています。この案は却下ではなく保留と
しました。Simulator 向けに個別ビルドしてアドホック署名したライブラリ生成物と、それを作るビルドター
ゲットが必要になる一方で、このリポジトリの継続的インテグレーションが実際に動かすアプリはすでに
`BajutsuKit` を採用しているため、増やした仕組みがテストされないまま出ていくことになるからです。
この項目が追加する可視化のコードは自己完結していて `BajutsuKit` の他の部分に依存しないので、保留した
選択肢はいつでも取れます。

**アプリ内で描く代わりに、レポートの動画プレイヤーの上に座標を重ねる。** レポートにはすでに動画
プレイヤーが埋め込まれており、[BE-0345](../BE-0345-actuation-record/BE-0345-actuation-record-ja.md)
の座標と [BE-0346](../BE-0346-video-timing-sync/BE-0346-video-timing-sync-ja.md) の補正済みタイム
スタンプがあれば、Swift を一行も書かずにプレイヤー上へマーカーを描けます。主たる方式としては、
*動機* が述べた理由で採用しませんでした。ドライバの記録から描いたオーバーレイが示すのはドライバが
狙った場所ですから、狙いを外したタッチと、届かなかったタッチとを区別できません。加えて、オーバーレイ
は生成されたレポートの中だけのものです。書き出した動画ファイル（人が不具合報告に添付する成果物）に
は、依然として何も写りません。
