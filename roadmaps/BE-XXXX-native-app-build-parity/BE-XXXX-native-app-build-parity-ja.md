## はじめに

ターゲットの設定には、アプリをビルドするシェルコマンドを書けます。コマンドは `subject.build` に置き、
隣の `subject.path` には、実行時に端末へインストールするビルド済みアプリのパスを置きます。
現在の Bajutsu がこのコマンドを実行する場面は2つです。Git リポジトリから設定を読み込んだ実行と、
Web UI（`bajutsu serve`）から始めたジョブです。どちらの場面でも、実行するのは iOS ターゲットに限られ、
しかもビルド済みアプリが存在しないときだけです。

本項目は、`subject.build` の振る舞いを、すべてのネイティブプラットフォームとすべての入口で揃えます。
変更は次の3つです。

- **どこでも必要に応じてビルドする**：Android ターゲットのビルドも、iOS ターゲットと同じ場面で実行します。
  ローカルの設定ファイルから始めた実行でも、アプリがなければ失敗せずにビルドします。
- **要求があれば強制的に再ビルドする**：`bajutsu run --rebuild` と、Web UI の Replay パネルに加える
  チェックボックスは、ビルド済みアプリがあっても `subject.build` を実行します。
- **どのマシンがビルドできるかを宣言する**：worker の能力ファイル `worker.yaml` に、そのマシンが
  アプリをビルドできるプラットフォームを並べます。ビルドが必要な実行は、ビルドできないマシンでは理由を
  示して止まります。Web UI は強制ビルドを、ビルドできるマシンに振り分けます。

## 動機

スキーマは Android ターゲットの `subject.build` を受け付けますが、この値を読むコード経路がありません。
解決処理はコマンドを Android の設定へ写しますが、ビルドを実行する呼び出し元はどれも、先に iOS の設定型で
あるかを確かめています。そのため、この欄を書いた Android の利用者には、ビルドは行われず、警告も出ません。
実行は後になって、Android アプリのパッケージ（Android application package、APK）がないことで失敗します。設定リファレンスは両方のプラットフォームについて
`subject.build` を説明しているので、この食い違いは利用者の意図だけでなくドキュメントとも矛盾します。

ローカルの設定には、iOS でも同じ抜けがあります。Git の経路が必要に応じてビルドするのは、取得した直後の
checkout にバイナリがないからです。ローカルの checkout も、`git clean` の後や新しいマシンでは同じ状態に
なります。それでも `bajutsu run` はバイナリがないというエラーで止まります。設定にはすでにコマンドが
書いてあるのに、利用者は手でビルドしなければなりません。

必要に応じたビルドだけでは、ソースの変更を取り込めません。アプリが存在すれば実行はそれを使い回すので、
アプリのソースを直してシナリオを流し直した開発者は、古いビルドを検証することになります。現在の対処は、
実行の前にビルド済みアプリを消すことだけです。常にビルドするフラグがあれば、この手間は1回の指定で済みます。

どの入口でもビルドするようになると、ビルドを実行するマシンが問題になります。Android エミュレータを動かす
Linux の worker には、Xcode がないことがあります。Android SDK のない Mac では Gradle を実行できません。
こうしたマシンはビルドを始めて途中で失敗し、その失敗はアプリが壊れているように見えます。worker の能力ファイルは、
1台のマシンが何を実行できるかをすでに宣言しています。そこでビルドできるものも宣言すれば、実行は最初に
拒否でき、Web UI はビルドできるマシンを選べます。

この変更の後は、`subject.build` を持ち APK がない Android ターゲットも、ビルドしてから実行します。
コマンドラインと Web UI のどちらから始めても同じです。`--rebuild` を付けた実行は、アプリがすでにあっても、
最初のシナリオの前にビルドの出力を表示します。`worker.yaml` の `build` が target のプラットフォームを含まない
worker では、ビルドを始める前に、プラットフォーム名を示すメッセージを出して止まります。

## 詳細設計

作業は6つのユニットに分かれます。共通のビルド関数、コマンドラインの実行、Web UI のジョブ、
Web UI の操作部品、worker のビルド能力、ドキュメントです。

### ユニット 1：強制フラグを持つ単一のビルド関数

`bajutsu/common/runner/build.py` の `build_if_missing` を `build_app(build, app_path, *, cwd,
force=False)` に置き換えます。`force` がなければ、これまでと同じ振る舞いです。アプリのパスが設定されていて
ファイルがないときにコマンドを実行します。`force` を指定すると、コマンドが設定されている限り常に実行し、
アプリの有無は見ません。

この関数は、ホストでのコマンド実行を `serve` が信頼しない実行に付ける環境変数にも従います。
この環境変数 `BAJUTSU_WITHHOLD_RUNNER_BUILD` は、アップロードされた bundle と、
`--allow-remote-build` なしにアプリケーションプログラミングインターフェース（API）経由で結び付けた Git 設定について、すでに `driver.runner.build` を
差し止めています。環境変数が付いていれば、必要に応じたビルドは行わず、実行はこれまでどおりアプリがないことを
報告します。強制ビルドは、理由を示すメッセージとともに失敗します。この規則は、ローカルの設定でも
必要に応じてビルドするようになると欠かせません。この規則がないと、信頼しない bundle のために `serve` が
起動した実行が、`serve` 自身は実行を拒む bundle のビルドコマンドを実行してしまいます。

### ユニット 2：コマンドラインの実行

`bajutsu run` は、主ターゲットが iOS でも Android でも、設定の取得元を問わずアプリをビルドします。
作業ディレクトリは、設定リファレンスがすでに定めている規則に従います。

| 設定の取得元 | `subject.build` の作業ディレクトリ |
|---|---|
| Git リポジトリ | checkout のルート（変更なし） |
| ローカルファイル | 設定ファイル自身のディレクトリ |

同じ規則は、端末を扱う前に実行がビルドするほかのターゲットにも及びます。対象は端末グループの
メンバーです。後の `installApp` ステップがインストールするターゲットと、共有する端末で始まるターゲットが
これにあたります。これらのターゲットも、Android でもローカルの設定でもビルドするようになります。

`--rebuild` は、これらのビルドのすべてに `force` を渡し、各ターゲットのビルドは1回の実行につき1回です。
このフラグは、主ターゲットが `subject.build` を宣言していることを求めます。宣言がないと `--rebuild` は何も
ビルドしないので、実行は始めずにターゲット名を示して終了コード 2 で終わります。`subject.build` を持たない
グループのメンバーは、既存のアプリをそのまま使います。そのメンバーのアプリは端末にすでにある前提だからです。

worker の device provider から端末を受け取るターゲットは、ビルドしません。worker の設定が指定できる
2つの provider（`devicefarm-host` と `appium`）は、アプリをインストール済みの端末を渡すからです。
Device Farm のパッケージはビルド済みアプリを意図して含めないので、Device Farm のホストでビルドしても
実行を失敗させるだけです。このようなターゲットに `--rebuild` を指定すると、provider 名を示して終了コード 2 で
終わります。

### ユニット 3：Web UI のジョブ

ジョブにアプリのパスとビルドコマンドを渡す補助関数 `target_build_info` は、iOS の設定に加えて
Android の設定も読みます。`Job` には `rebuild` 欄を加えます。この欄はジョブ仕様に載って運ばれるので、
リモートのワーカーもローカルのサーバと同じように強制ビルドします。`_build_app` は、`rebuild` が
指定されているか、アプリがないときにビルドします。

`POST /api/run` は `rebuild: true` を受け付け、次の2つの場合はステータス 400 で拒否します。

- **強制する対象のビルドがない**：ターゲットは `subject.build` を宣言していないか、信頼しない結び付けの
  ために `serve` がコマンドを差し止めています。
- **保存済みのバイナリがビルドに代わる**：リクエストが `binaryArtifact` も持っています。この実行は
  保存済みのバイナリをインストールするので、再ビルドしても実行が使わないアプリをビルドするだけになります。

ビルドは、実行を起動する前に `serve` 自身が行います。そのため、起動された `bajutsu run` が
`--rebuild` を受け取ることはなく、1つのジョブがアプリをビルドするのは1回です。

### ユニット 4：Web UI の操作部品

Replay パネルに「rebuild the app first」チェックボックスを加え、`POST /api/run` の `rebuild` として
送ります。チェックボックスは、実行ごとのほかのオプションと並べて置きます。ファンアウトの Replay では、
ほかの実行ごとのオプションと同じくこのチェックボックスを隠すので、ファンアウトのリクエストは `rebuild` を
持ちません。Record と Crawl の振る舞いは変えません。どちらも引き続き、アプリがないときだけビルドします。
Android でもビルドするようになる点だけが変わります。

### ユニット 5：worker のビルド能力

`worker.yaml` に `build` キーを加えます。worker がアプリをビルドできるプラットフォームを、`ios` と `android` から
選んで並べます。キーを省くと両方とみなします。このキーができる前から、worker はどのアプリもビルドしていたからです。
`build: []` にすると何もビルドしません。同梱の既定ファイルには、両方のプラットフォームを明示的に書きます。

この宣言が効くのは、ビルドが必要なときだけです。`bajutsu run` は、ビルドすると決めるのと同じ場所で宣言を
確かめます。アプリが存在しないとき、または `--rebuild` がビルドを強制するときです。リストが target の
プラットフォームを含まなければ、実行はプラットフォーム名を示して終了コード 2 で終わります。アプリがすでに
あれば、リストの内容にかかわらず、これまでどおり実行します。

Web UI は、同じ宣言を次の2か所で使います。

| 場所 | 振る舞い |
|---|---|
| 振り分け | ローカルの worker は、自身が動かすプラットフォームのうちリストにあるものごとに、振り分けのトークン `build:<platform>` を広告します。`rebuild` を伴うジョブはこのトークンを要求するので、そのプラットフォームをビルドできる worker だけがジョブを受け取ります。 |
| worker | ジョブは target のプラットフォームを持ちます。ファイルがそのプラットフォームを含まない worker は、アプリが存在しないジョブを、ビルドせずに失敗させます。 |

`build:` の接頭辞は予約済みの振り分け接頭辞に加わります。手書きのトークンで、マシンが作れないビルドを
名乗ることはできません。必要に応じたビルドにはトークンを加えません。ジョブを受け取る worker の上にアプリが
あるかどうかを、コントロールプレーンからは確かめられないからです。

### ユニット 6：ドキュメント

設定リファレンス、コマンドラインのリファレンス、ドライバのガイド、セルフホスティングのガイドで、新しい
振る舞いを英語と日本語の両方で説明します。ローカルの `run` はビルドしないという記述を削り、iOS と並べて
Android を挙げ、`--rebuild`、Replay のチェックボックス、`worker.yaml` の `build` キーを説明します。

## 検討した代替案

- **フラグなしで毎回再ビルドする**：ビルドには数分かかることが多く、ほとんどの実行はソースの変更を
  伴いません。毎回ビルドするとすべての実行が遅くなるので、強制ビルドは明示的な要求にとどめます。
- **ソースとビルド済みアプリのタイムスタンプを比べる**：Bajutsu が、アプリをどのファイルからビルドするかを
  知る必要があります。その知識は `make` や Gradle のようなビルドツールが持つもので、ソースを列挙する設定欄は
  知識の二重管理になります。差分ビルドが欲しい利用者は、何を再ビルドするかを判断するビルドツールを
  `subject.build` に指定し、`--rebuild` と組み合わせられます。
- **`subject.build` の代わりに汎用の実行前フックを設ける**：フックはシナリオの前に任意のコマンドを
  実行できますが、ビルド欄が持つ「コマンドがどのパスを生成するか」という情報が失われます。Bajutsu は
  ビルドするかどうかの判断と成果物のインストールに、そのパスを必要とします。
- **ローカルの経路ではビルドしないままにする**：バイナリがないことで止まるローカルの実行は、設定に
  コマンドが書いてあるのに、利用者にコマンドを探して実行させます。Git の経路で必要に応じたビルドの
  安全性は確かめられており、ユニット 1 の差し止めの環境変数が、信頼しない結び付けでのビルドを防ぎます。
