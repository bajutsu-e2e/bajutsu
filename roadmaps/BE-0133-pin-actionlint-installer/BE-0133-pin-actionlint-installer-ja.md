## はじめに

[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) の `check` ジョブは、ゲートステップのうち `uv sync` の対象外である唯一のステップ、`actionlint` をインストールします。そのやり方は、可変な git タグから取得したスクリプトを、`bash` にそのまま流し込むものです。このリポジトリの CI にあるほかのサードパーティ依存は、すべてコミット SHA で固定されています。

本提案は、`actionlint` のインストーラをこの方針に合わせます。

## 動機

`ci.yml:66` は次のとおりです。

```yaml
- name: Install actionlint
  run: bash <(curl -fsSL https://raw.githubusercontent.com/rhysd/actionlint/v1.7.12/scripts/download-actionlint.bash) 1.7.12
```

この行は、`rhysd/actionlint` の `v1.7.12` という参照から `scripts/download-actionlint.bash` を取得し、そのまま実行します。スクリプト自体は、該当リリースに合わせて `actionlint` バイナリをダウンロードして展開します。

git タグは可変です。アップストリームのメンテナが付け替えることもあれば、アカウントが乗っ取られた場合には攻撃者が付け替えることもあります。コミット SHA は、不変です。取得したスクリプトは CI ランナー上でそのまま実行されます。そのため、`v1.7.12` が付け替えられれば、`check` ジョブの権限（`ci.yml` トップレベルの `permissions:` ブロックにある `contents: read`）の範囲で実行されることになります。範囲は限定されているとはいえ、レビューを経ないコード実行経路であることに変わりはありません。

`.github/` 内で参照されているほかのサードパーティアクションは、いずれも、バージョンをコメントで添えたフルコミット SHA で固定されています（例：`actions/checkout@9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0  # v7.0.0`）。該当するアクションは、`actions/checkout`、`astral-sh/setup-uv`、`actions/cache`、`actions/create-github-app-token`、`actions/upload-pages-artifact`、`actions/deploy-pages`、`maxim-lobanov/setup-xcode`、`actions/upload-artifact` です。

`actionlint` のインストーラは、この既存の方針から外れた唯一の例外です。しかも `uses:` によるアクション参照ではなく `curl | bash` という形なので、サプライチェーンの形として、アクション参照よりレビューしにくくなっています。

深刻度については、この指摘は**未確認**です。インシデントやアップストリームの侵害が実際に確認されているわけではなく、ジョブの権限もすでに読み取り専用に絞られているため、影響範囲には上限があります。それでも取り上げるのは、このリポジトリがほかのあらゆる箇所ですでに保持しているセキュリティ方針との間に、機械的に埋められる差分が残っているためです。実証された攻撃が動機ではありません。

## 詳細設計

修正は、`ci.yml:66` に閉じた、互いに独立な 2 つの作業からなります。

1. **インストーラスクリプト自体をコミット SHA で固定する。** `raw.githubusercontent.com` の URL にある `v1.7.12` タグを、そのタグが現在指しているコミット SHA に置き換えます。可読性のために、末尾にタグ名のコメントを添えます。形式は、`uses:` の固定ですでに使われている慣例（例：`@<sha>  # v1.7.12`）と同じです。これにより、タグが後で付け替えられても、取得されるスクリプトの内容は不変になります。
2. **可能であれば、ダウンロードしたバイナリ自体も検証する。** `download-actionlint.bash` が取得するバイナリのチェックサムを、すでに検証しているかを確認します。していない場合、あるいは `actionlint` の `1.7.12` リリースで公開されているチェックサムを別途固定できる場合は、その検証を追加します。これにより、インストーラスクリプトだけでなく、バイナリ自体も改ざん検知できるようになります。これは小さく独立した追加作業であり、項目 1（スクリプトの固定）だけを先に単独でマージできます。

どちらの変更も、`ci.yml` の 1 行に閉じており、`run`/CI の合否判定ロジックには触れません（`check` ジョブは、修正後も `actionlint` 自身の検出結果だけで合否を決めます）。したがって、プライムディレクティブ 1 は影響を受けません。プロダクトコードの対象範囲はなく、CI のサプライチェーン強化のみです。

## 検討した代替案

- **インストーラスクリプトの代わりに、`uses:` ベースの actionlint アクションに切り替える。** `actionlint` バイナリの取得をラップした、コミュニティ製アクションはいくつか存在します。それを使えば、この固定もほかのサードパーティステップと同じ SHA 固定の `uses:` パターンに揃えられます。ただし、この切り替えは、既存のものを単に固定するのではなく、1 つのサードパーティの信頼対象（rhysd のインストーラスクリプト）を別のもの（コミュニティ製アクション）に置き換えるだけです。そのため、本提案では見送ります。既存のインストーラスクリプトの固定が難しくなった場合にのみ、改めて検討する価値があります。
- **`actionlint` バイナリをリポジトリに同梱するか、CI 内でソースからビルドする。** 実行時の取得を完全になくせます。しかし、同梱バイナリの更新や Go ツールチェーンのステップといった、実際の保守コストが発生します。SHA 固定という 1 行の変更で解決できる問題に対しては、深刻度に見合わないコストです。
- **ジョブの権限がすでに読み取り専用であることを理由に、何もしない。** 影響範囲には上限があります。しかし、このリポジトリがすでに持っている SHA 固定という方針は、そもそも将来のあらゆるワークフロー変更で、その上限に頼らずに済むようにするためのものです。この 1 つの例外を残すことは、目先のジョブそのものよりも、その方針の一貫性を損ないます。
