## はじめに

Playwright バックエンドは `Driver.wait_for` を 1 回だけの即時チェックとして実装し、引数の `timeout` を黙って無視します。idb バックエンドは `timeout` が経過するまでポーリングします。このポーリングが本来の契約です。両者の食い違いは決定性に関わるバグです。Web 上では、待機を要求した呼び出し元が、要素がまだ現れていない瞬間に偽の `TimeoutError` を受け取ります。本提案は、すべてのバックエンドが同じ振る舞いをするよう契約を統一します。

## 動機

共有の `Driver` Protocol は、`bajutsu/drivers/base.py:114` で `def wait_for(self, sel: Selector, timeout: float) -> bool: ...` を宣言しています。Protocol 自体にドキュメント文字列はありませんが、idb の実装が実質的な契約を確立しています。`bajutsu/drivers/idb.py:306-319` は、`timeout` から作った単調増加のデッドラインに対してループでポーリングし、チェックの合間に `poll` 秒だけスリープします。ドキュメント文字列も明快で、「`sel` に一致する要素が現れるか `timeout` が経過するまでポーリングする」と書いています。理由として挙げているのは、「要素は呼び出しの直後より少し遅れて描画されることがある」ことです。

Playwright バックエンドは、この契約を守っていません。`bajutsu/drivers/playwright.py:546-547` は次のとおりです。

```python
def wait_for(self, sel: base.Selector, timeout: float) -> bool:
    return len(base.find_all(self.query(), sel)) >= 1
```

このコードは 1 回だけチェックして即座に返るので、`timeout` は使われないパラメータです。一方、`bajutsu/golden.py:190` は `golden_assert` の「drive-wait-query-compare」フローのなかで、`driver.wait_for(anchor, timeout)` を直接呼び出しています。戻り値が `False` のとき、`golden.py` は `TimeoutError(f"anchor {anchor!r} did not appear within {timeout}s")` を送出します。idb 上では、タイムアウトの全時間を待ち切ってから失敗します。Playwright 上では、最初のチェックの時点で失敗します。そのため、ページの描画がまだ終わっていない状態と競合する `golden` アサーションは、Web では偽のタイムアウトとして報告されます。同じ実世界の遅延でも、iOS では通ります。

深刻度は高く、設計上の隙間ではなく正真正銘のバグです。プライムディレクティブ 2（「決定性優先」）を直接損ないます。フレーキーな偽の失敗は、決定性優先が防ごうとしている種類の問題そのものだからです。しかもバックエンド固有の挙動なので、「プラットフォームはバックエンドの1つにすぎない」という前提への信頼も損ないます。同じシナリオが、対象アプリとは無関係な理由でバックエンドごとに異なる振る舞いをするからです。

## 詳細設計

各バックエンドに独自のデッドラインループを実装させるのをやめます。代わりに、契約上 `wait_for` を単発チェックのプリミティブと定め、ポーリングは共有のヘルパー 1 つに任せます。

1. **`Driver.wait_for` の契約を単発チェックとして定義し直す。** `bajutsu/drivers/base.py:114` のドキュメント文字列と契約を、`wait_for` は *1 回だけ* チェックして即座に返ると明記するよう変更します。`timeout` はシグネチャから外します。インタフェースの安定性のために残す場合は、未使用で予約済みだと明示します。新しい契約のもとでは、現在の Playwright の振る舞いはバグではなく、正しい実装になります。
2. **共有のポーリングヘルパーを追加する。** 小さな関数を導入します。例えば、`find_all` と並べて `bajutsu/drivers/base.py` に置く `wait_until` です。関数は `Driver`、`Selector`、`timeout`、ポーリング間隔 `poll` を受け取ります。そして単調増加のデッドラインに対して、`driver.wait_for(sel, ...)` をポーリングします。`orchestrator/waits.py` の既存の `_wait` パターンを踏襲して、`driver.query()` を直接ポーリングしてもかまいません。
   どちらの場合も、ループは idb の現行の `wait_for` がすでに実装しているものを、ドライバの外に引き上げたものです。
3. **idb のポーリングループを共有ヘルパーへ移す。** `bajutsu/drivers/idb.py:306-319` を、新しい契約に合わせて単発チェックに簡略化し、独自のデッドラインループを削除します。共有ヘルパーが、このループをすべてのバックエンドに一律に提供するためです。
4. **直接の呼び出し元を共有ヘルパーに向ける。** 調査で見つかった `driver.wait_for` の外部からの直接の呼び出し元は、`bajutsu/golden.py:190` だけです。これを、新しい共有ヘルパーを呼ぶように更新します。これで、`golden_assert` のタイムアウトは idb と Playwright で同一に守られます。
5. **リグレッションテストを追加する。** `wait_for` が最初は `False` を返し、しばらくしてから `True` を返すフェイクまたはスタブのドライバを使います。要素が遅れて描画される状況を模したものです。このテストは共有ヘルパーを検証し、今回のバグを検出できていたはずのものです。既存のドライバと golden のテスト群に追加します。

プライムディレクティブ 1 には触れません。`run` と CI の決定性は完全に保たれ、この経路に AI は一切入りません。この変更はプライムディレクティブ 2 に直接資します。修正後は、待機に与えた `timeout` が、どのバックエンドが駆動していても同じ実時間の秒数を意味します。

## 検討した代替案

- **共有ヘルパーを導入せず、Playwright の `wait_for` の内部だけでポーリングさせる。** 目先のバグは直ります。しかし、今後追加されるすべてのバックエンド（Android など）が、idb がすでに持っているデッドラインループを再実装する羽目になり、誰かがループを忘れた日に同じ種類のバグが再発します。共有ヘルパーなら、この重複を恒久的に取り除けます。
- **ポーリングの代わりに Playwright ネイティブの自動待機（`page.wait_for_selector`）を使う。** Playwright バックエンド単体としては魅力的です。しかし `wait_for` はバックエンド横断の契約であり、ポーリングモデルをバックエンド間で揃えておくほうが、1 つのバックエンドの実装方式だけを特別扱いするより、推論もテストもしやすくなります。将来の最適化として、単発チェックの *内部で* Playwright がネイティブ待機を使う余地は残ります。
- **`timeout` を `wait_for` のシグネチャに残したまま、契約の不整合には何もしない。** 却下します。現在のバグがまさにこの形だからです。単発チェックなのに `timeout` パラメータが存在し、しかも無視されています。シグネチャは、`timeout` を守る（ポーリングする）か、外す（単発チェックにしてポーリングは別の場所で行う）かのどちらかでなければなりません。`timeout` を黙って無視する状態を許してはいけません。
