## はじめに

壊れたシナリオを、全体を再記録せずに最小の差分で更新します。トリアージが構造化 fix（`renameId`、`addIndex`、`raiseTimeout`）を提案します。`--apply` でドライランの diff を表示し、`--write` で source に適用します。`--rerun` は、再実行して結果を検証します。rename と addIndex の閉ループは、実機で実証済みです。

## 動機

ちょっとした UI の変更は、シナリオを無効にせずに壊すことがあります。識別子のリネーム、新たに重複した部品、少し読み込みが遅くなった画面などです。1 行を直すためにシナリオ全体を再記録するのは無駄です。さらに悪いことに、それ以降に人間が YAML へ加えた手編集を捨ててしまいます。

欲しいのは、シナリオを再び決定的にする最小の差分です。それを他のコード変更と同じように、レビュー用に提示します。BE-0021 のトリアージは、すでに原因を言い当てています。本提案は、その診断を機械的に適用できる編集に変えます。これにより、fix のループは新規の記録ではなく、レビューできるパッチで終わります。

## 詳細設計

トリアージは、診断に構造化された `Fix` を付けられます。`Fix` は、シナリオ source に対する `find` -> `replace` で、種別は次の 3 つです。

* **`renameId`** は、セレクタ id をトークン単位で置換します。否定の先読みと後読みにより、`nav.setting` が `nav.settings` の内側に一致するのを防ぎます。そのため、どの出現箇所に適用しても安全です。リネームされた識別子に対する、古典的な自己修復です。
* **`addIndex`** は、失敗したステップの正確なセレクタ断片を書き換えて、`index:`（または `within:`）を追加します。追加したフィールドが、複数の要素に一致したセレクタを一意にします。
* **`raiseTimeout`** は、失敗した wait の正確な `timeout: N` 断片を、より大きな値に書き換えます。

`bajutsu triage --apply <file>` は、その source ファイルに fix を適用します。`apply_fix` は純粋関数で、パッチ後のテキストと置換回数を返します。CLI は unified diff（`diff_fix`）を表示します。

`--apply` の既定は**ドライラン**で、diff を出力するだけで何も書き込みません。ファイルを書くには `--write` が必要です。`--write` の後に `--rerun`（`--app` とデバイスを伴います）を付けると、パッチ済みのシナリオを通常の決定的な `run` で再実行し、fix が成立することを確認します。

`--apply` が与えられたときは、トリアージは run の正規化済みダンプではなく、ファイル自身のテキストに対して診断します。これにより、断片 fix の `find` が、パッチの編集対象のバイト列に一致します。

ここでは何ひとつ合否に触れません。fix は、人間がレビューするシナリオ source への編集です。検証は、変わらず決定的な `run` です。rename と addIndex の閉ループ（破損、トリアージ、適用、再実行、グリーン）は、実機で実証済みです。

## 検討した代替案

* **破損時にシナリオ全体を再記録する案。** 当初の M4 のフォールバックです。人間の編集を捨て、1 行の原因に対して大きくノイズの多い差分を生みます。最小の構造化 fix は、パッチを小さくレビューしやすく保ちます。
* **実行中に fix を自動適用する案。** 一部の競合ツールが行っています（BE-0039 を参照）。却下しました。実行の途中で黙ってシナリオを編集すると、誰の目にも触れずに条件が緩む恐れがあるからです。ここでは、すべての fix がまずドライランの diff になります。書き込まれるのは、明示的な `--write` のときだけです（防止策は BE-0023）。
* **モデルからの自由形式のテキストパッチ。** 任意の編集を許せば、モデルは何でも書き換えられます。fix は 3 つの正確な `find`/`replace` 種別に制約し、`find` は source の部分文字列に限ります。そのため fix は、きれいに適用されるか、目に見える no-op になるかのどちらかです。黙った広範な書き換えにはなりません。
