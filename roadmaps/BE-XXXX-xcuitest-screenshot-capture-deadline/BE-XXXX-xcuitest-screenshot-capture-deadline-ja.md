## はじめに

Bajutsu の iOS バックエンドは、iOS シミュレータの中でループバックポートに HTTP を提供する常駐の
XCUITest プロセス（テストホスト）を通してアプリを操作します。各
[ステップ](../../docs/ja/glossary.md#シナリオのオーサリング)が残す
[証跡](../../docs/ja/glossary.md#証跡-capturepolicy-trace-triage)を記録するために、
Bajutsu はそのプロセスにスクリーンショットを要求します（`GET /screenshot`）。iOS の継続的インテグレーション
（CI）レーンが下す `backend crashed mid-run` という判定は、ほぼすべてがこの 1 つのエンドポイントに
起因します。そして、その判定が下る時点でテストホストはたいてい生きています。クライアントの待ち時間
をはるかに超えて続く撮影の中で止まりながら、`/health` には答え続けています。

本項目は、根底にある原因を取り除きません。それはホストの資源枯渇であり、別の作業に属します。本項目
が取り除くのは、その上に重なった 2 つです。runner はアプリケーション要素ではなく画面から撮影する
ようになります。要素を解決する往復は得られる画像に何も寄与せず、アプリが不健全なときには `HTTP 200`
のまま 1×1 ピクセルの画像へと黙って劣化するからです。さらにスクリーンショットのハンドラに、クライアントのソケット
タイムアウトより短い期限を与えます。それでも撮影が長引いた場合には、今のように沈黙してチャネルに
解釈を委ねるのではなく、理由の明示された失敗を返します。前者は失敗が観測できている撮影に対処します。
後者はメインスレッドを解放しません。放棄された撮影がそれを握り続けるからです。ただし、停滞を引き起こした要求
そのものの上で失敗に名前を与え、クライアントがまだ聞いているうちに応答します。閉じられたソケットへ
遅れて書き込み、テストホストを終了させてしまう経路も、これで消えます。

## 動機

iOS レーンが記録する runner チャネルの失敗は、その大半が `GET /screenshot` です。ワークフロー実行
[31683047665](https://github.com/bajutsu-e2e/bajutsu/actions/runs/31683047665) の
`run (xcuitest)` ジョブでは、チャネルの失敗 48 件のうち **48 件** が `GET /screenshot` でした。
要素ツリーの読み取り（`GET /elements`）と操作は、どちらも 1 件ありません。同じ実行に含まれる 3 つの
ジョブでも、
それぞれ 18 件、21 件、51 件を記録しています。相関はレーンの内部だけでなくレーンをまたいでも成立
します。直近 40 回のワークフロー実行で `run (xcuitest)` は一度も成功しておらず、いっぽう
`conformance (xcuitest)` は 14 回中 14 回成功しました。そして conformance のテスト群は、
スクリーンショットを一度も要求しません。緑になったレーンでもこの失敗はジョブあたり 10 件記録されて
おり、復旧の予算内に収まっているだけです。

失敗している呼び出しを名指しするのは、runner 自身が残した出力です。`visual (xcuitest)` ジョブが
アップロードした runner のログは、スクリーンショットを撮る行そのものを指しています。

```
XcuitestElementProvider.swift:219: error: Failed to get screenshot: Timed out while requesting screenshot.
XcuitestElementProvider.swift:219: error: Element Application '…' cannot request screenshot data because it does not exist
```

219 行目は `app.screenshot().pngRepresentation` です。機構を特定するのは 2 つめのメッセージです。
これはアプリケーション要素の経路からしか出ないからです。`app.screenshot()` は要素スコープの撮影で
あり、XCUITest は画像を要求する前にアプリケーション要素を解決します。その解決自体が失敗すること
も、止まることもあります。クライアントが諦めた時点で runner がまさにその解決の中にいたことは、
アクティビティログが裏づけています。`Find the Application` が `t = 29.02s`（09:37:40.70）に始まり、
クライアント側の最初のタイムアウトは 09:37:55.75、つまり **15.05 秒** 後です。これはクライアント
自身の 15 秒の読み取り窓と 1/100 秒の桁まで一致します。

ただし、これで XCUITest の要求経路が *原因* になるわけではありません。測定された原因はその下に
あります。3 コア 7 GiB の GitHub の macOS ランナーは、起動したシミュレータが立ち上げる 257 個の
ゲストプロセスによって飽和します。BE-0361 の診断によれば、その圧力が Apple の `SimRenderServer` を
`com.apple.display.captureservice` キューでのトラップへ追い込みます。このキューは
`simctl io screenshot`、`recordVideo`、XCUITest のスクリーンショットのすべてを 1 つで受け持つため、
3 つの症状は同時に現れます。本項目はそれを直しませんし、直すと読める書き方もしません。ホストの資源
枯渇にはゲストプロセスの削減が必要で、それ自体が独立した作業です。本項目が変えるのは、その共有
キューが劣化していくあいだの runner の振る舞いです。撮影の形の一方はもう一方より明確に劣り、停滞に
対するハンドラの応答は、必要以上に劣っています。

被害が 1 枚の撮影の失敗と釣り合わない大きさになるのは、2 つの予算が食い違っているからです。XCUITest
が自身のスクリーンショット要求に与える猶予はおよそ 90 秒で、クライアントの読み取り窓は 15 秒です。
遅い撮影が吸収される余地はどこにもなく、そのすべてがクライアントの分類すべき失敗になります。ハンドラ
はその待ち時間のあいだ runner の直列化ロックを保持し続けるためチャネルが止まりますが、`/health` は
ロックを取らない設計なので `ready` を返し続けます。BE-0354 はこの組み合わせを、自身の定義どおりに
応答しなくなったセッションだと読み取り、シナリオの再試行は壊れていなかったデバイスに対して実行
単位の復旧予算 900 秒を費やします。こうして遅いスクリーンショット 1 枚が実行全体を終わらせます。
後続のシナリオが報告するのは
`an earlier scenario already exhausted the run-level crash-recovery budget` です。デバイスを確保する
ことさえありません。

## 詳細設計

作業は独立した 2 つの単位に分かれます。1 つめは撮影が何を要求するかを変え、2 つめはハンドラが
それをどれだけ待つかを変えます。

### 単位 1：アプリケーション要素ではなく画面から撮影する

`XcuitestElementProvider.screenshot()` は `app.screenshot().pngRepresentation` を返しています。この
要素スコープの撮影を、画面スコープの `XCUIScreen.main.screenshot().pngRepresentation` に置き換え
ます。画面スコープの撮影はディスプレイに直接届き、要素を解決しません。

この置き換えは、Bajutsu の iOS レーンが固定しているデバイスではピクセル単位で等価です。アプリの
ウィンドウがすでに画面全体を占めており、要素での切り出しが恒等操作になっているからです。独立した
2 つの測定が一致しています。コミット済みの iOS のベースライン画像は 1206×2622 です。ローカルで起動
した iPhone 17 に対して `app.screenshot()` が生成する画像も、すべて 1206×2622 です。402×874
ポイントに倍率 3 を掛けた、デバイスの完全なネイティブ解像度にあたります。検証ではこれを仮定せず、
同じ画面を変更の前後で撮影して画像を比較し、確認します。ここでずれが生じれば、コミット済みの
ベースラインすべてと、[BE-0171](../BE-0171-element-scoped-visual-assertions/BE-0171-element-scoped-visual-assertions-ja.md)
がスクリーンショットのピクセル空間で計算する要素スコープの切り出しが、黙って無効になるからです。

要素スコープの撮影は *黙って* 失敗もします。こちらのほうが、置き換える理由としては鋭いものです。
実行 31670480559 の `visual (xcuitest)` の成果物で測定しました。テスト対象のアプリが劣化すると、
runner は **1×1 ピクセル**、4232 バイトの PNG を載せて `HTTP 200` を返し、実行はそれを通常のステップ
の証跡として保存しました。Python 側のクライアントが守るのは、PNG でない本文か空の本文だけです。
妥当な 1×1 の画像は、すべての検査を通り抜けます。同じ runner のログには、記録された XCTest の失敗が
10 件並んでいました。そのすべてがスクリーンショットの要求です
（`cannot request screenshot data because it has an empty frame`）。どれもクライアントから見える応答
にはなりませんでした。`caughtOnMain` が捕まえるのは *raise* された `NSException` であって、
*記録* された `XCTIssue` ではないからです。つまり、いちばん欲しい瞬間に証跡が消えます。調査の対象は
まさにアプリの劣化だからです。画面スコープの撮影には、この退化した場合がありません。アプリがどの
状態であってもディスプレイを撮影し、アプリスコープの形では見えないシステムアラートや SpringBoard も
収められます。

要素ツリーの読み取りには意図して手を付けません。`queryElements()` が呼ぶ `app.snapshot()` は
アクセシビリティツリーへの問い合わせであり、要素の解決をおこないません。だからこそ、スクリーン
ショットが止まるまさにそのジョブで、ツリーの読み取りは健全なままでいられます。この非対称性が本単位の
根拠なので、そのまま保つことに意味があります。

### 単位 2：クライアントより短い期限でスクリーンショットのハンドラを区切る

スクリーンショットのハンドラは、メインスレッドを無期限に待ちます。ここにクライアントの 15 秒の
読み取り窓より厳密に短い期限を与え、runner が先に答えて理由を述べるようにします。

期限を与えてよいのは `GET /screenshot` だけです。この理由は正確に述べる価値があります。操作に期限を
与えるのは、安全側に寄せた選択ではなく正しさの欠陥になるからです。スクリーンショットは純粋な読み
取りなので、失敗を報告する応答が、後から届く副作用によって覆されることはありません。操作では覆され
ます。12 秒の時点で失敗を報告したハンドラが、合成したタップを 40 秒で着地させたとしましょう。画面
が変わっていても、変わっていないとクライアントへ伝えることになります。したがって操作はすべて、
無期限の待ちをそのまま保ちます。

直列化の不変条件は変わらず維持され、本単位の繊細な部分はここにあります。runner が XCUITest に触る
操作をすべて直列化しているのは、2 つの操作がメインスレッドで同時に走るとテストホストが異常終了する
からです。一方の呼び出しが内部で回すランループがメインキューを排出し、もう一方に再入しますが、
XCUITest に再入はできません。そこで、期限が解放するのは *クライアント* だけとし、*ロック* には
触れません。ハンドラは撮影をメインスレッドへ投入します。期限までセマフォで待ち、それ以上は待たずに
応答します。ロックの所有権は投入したブロックへ移り、撮影が実際に戻った時点でブロックが解放します。
メインキューに積まれる XCUITest の操作は、従来どおり常に高々 1 つです。ここから実装への制約が 1 つ
生まれます。ロックの取得と解放は別のスレッドになるので、直列化の道具は `NSLock` ではなく
カウンティングセマフォになります。`NSLock` の契約は、ロックしたスレッドが解放することを要求する
からです。

遅れて完了したブロックは、何も書き込んではいけません。その接続が受け取る唯一の応答は、待っていた
ハンドラがすでに送っています。クライアントが閉じたソケットへ 2 度目の書き込みをおこなうと `SIGPIPE`
が発生し、そのデフォルトの動作はテストホスト全体を終了させます。

期限の値はクライアントの読み取り窓と結びついており、その結びつきは機械的にではなく、両側のコメント
によって守られます。2 つの定数は異なる言語にあり、両方をまたぐ検査は存在しません。クライアントの
15 秒に対して 12 秒とすれば、応答がクライアントへ届く時間を残しながら、runner の答えを先に立てられ
ます。

### 機械的に検査できる成果

単位 2 が持つ 3 つの性質のうち 2 つは、Swift の高速なテスト群が担保します。ルーティング層と
プロバイダのプロトコルはどちらも、`swift test --package-path BajutsuKit` がビルドする SwiftPM の
ターゲットにあるからです。期限を超えて続く撮影を返すプロバイダに対して、`GET /screenshot` はその
撮影が戻るより前に応答しなければなりません。期限を取り除くと、この検査は落ちます。さらに、放棄
された撮影は最後に戻った時点でロックを渡さなければならず、次の操作はそれで動きます。受け渡しを
削るとロックは漏れ、テスト群はデッドロックします。どちらも通ることを見ただけでなく、変異させて
確認しました。

3 つめの性質は、意図して検査しません。撮影がメインスレッドを保持しているあいだ、2 つめの操作が
XCUITest へ再入しないことです。この性質は、いまのテスト環境では観測できません。ランループを回す
偽の撮影はメインのディスパッチキューを排出しないため、撮影がメインスレッドを握っていること自体が
ロックの有無によらず全体を直列化します。したがって、この不変条件を主張するテストは、期限の時点で
ロックを解放してしまう実装に対しても通ります。そのキューを排出するのは本物の XCUITest の
ランループだけです。それでも検査を書けば、得られるのは誤った安心です。この性質を託す先は、実機
レーンと、コードの傍に記録した論拠です。

単位 1 にもユニットテストはありませんが、理由はもっと単純です。`XcuitestElementProvider` は
xcodebuild だけが扱うテストターゲットにあります。`make check` と `swift test` のどちらも、この
ターゲットをコンパイルしません。担保するのは実機レーンと、本単位が述べた変更前後の画像比較です。

## 検討した代替案

**`simctl` を通してチャネルの外で撮影する。** `xcrun simctl io <udid> screenshot` は XCUITest プロセス
に入らずディスプレイへ届きます。このコマンドはすでにコードベースにあります
（`bajutsu/simctl.py`）。証跡の取得を操作チャネルから完全に外すのが、構造としてはもっとも強い
答えです。遅い撮影がチャネルを止めたり、
偽のクラッシュ判定を生んだりすることも、それならありえません。本項目としない理由は、ドライバの
プロトコルが今はバックエンドに置いている能力を、シミュレータ専用の側路へ移すことになり、それ自体の
設計を必要とする点にあります。XCUITest バックエンドは別のリース経路で実機も扱い、そこには `simctl`
が存在しません。独立した項目として扱う価値があります。

**クライアントの読み取り窓を XCUITest の約 90 秒より長くする。** これならクライアントが遅い撮影を
応答不能と読み違えることはなくなりますが、向きが逆です。1 つのステップが 1 分半にわたって停滞して
も、何ひとつ報告されないことになり、失敗したジョブを区切っている実行単位の予算が意味を失います。撮影を
区切ることが要点であり、窓を広げるのはその要点を手放すことです。

**期限の時点で直列化ロックを解放する。** 応答とロックの解放を同時におこなえばチャネルはより早く空き
ますが、ロックが防いでいるテストホストの異常終了を呼び戻します。最初の撮影がまだランループを回して
いるあいだに、2 つめの操作がメインキューへ積まれるからです。この理由で採りません。ロックの解放は、撮影の完了に結び付けたままとします。

**防ぐのではなく検出して段階的に対処する。** BE-0354 がすでにこの道を採り、応答しなくなった状態を
数秒で分類して、再発した再試行をデバイスの置き換えへと段階を上げています。そして BE-0361 の測定は、
その段階付けを裏づけます。`backboardd` を巻き込むトラップのあとには、respawn する先のゲストが残って
いないため、デバイスの置き換えだけが機能しうる段になります。本項目はこの層の代替ではなく、その価値を
下げるものでもありません。黙って失敗する撮影の形と、何も報告しない待ちを取り除くだけであり、どちらも
BE-0361 が指摘した資源枯渇の上に乗っています。
