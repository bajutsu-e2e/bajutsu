## はじめに

セルフホストの serve バックエンド（[BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md)）は、すでに秘密情報を伏せた**構造化 JSON ログ**を標準出力へ出しています（[BE-0055](../BE-0055-operational-logging/BE-0055-operational-logging-ja.md)）。このログをログ基盤へ送るのは、デプロイ側の役目です。

足りないのは**メトリクス**です。キューの深さ、組織ごとの実行中ジョブ数、実行時間、ワーカーの生存を、運用者が一目で見る手段がありません。この提案は、`/metrics` エンドポイントと、compose スタックへの任意の Prometheus コンテナおよび Grafana コンテナを追加します。この作業は、BE-0016 の「単一ノードをプールへ育てる」作業から切り出したものです。

## 動機

Mac プールの運用では、ログだけではうまく見えてこない問いに答えることになります。たとえば、キューが滞留していないか、いまどの組織がプールを消費しているか、実行がいつもより遅くないか、ワーカーが死んでいないか、といった問いです。

構造化ログ（BE-0055）はイベントを捉えます。育っていくプールを見守る運用者には、これに加えて**時系列の信号**が必要です。飽和や生存の問題が停止になる前に気付き、プールの規模を見積もるためです。スクレイプ可能なメトリクスエンドポイントとチャート基盤が、その信号を得る標準的な方法です。しかも、BE-0016 の可観測性の話で唯一まだ出荷されていない部分です。

## 詳細設計

Python 側の面を持つのはエンドポイントだけなので、ゲートで検証できる契約を持つのもエンドポイントだけです。コンテナはデプロイの関心事であり、手動で検証します。作業分解は次のとおりです。

1. **`/metrics` エンドポイント。** serve バックエンドから Prometheus 形式のメトリクスを公開します。少なくとも、**キューの深さ**（待機中のジョブ。組織別や能力別の数があればそれも）、**組織ごとの実行中ジョブ数**、**実行時間**、**ワーカーの生存**（リースとハートビートの新しさ）を含めます。メトリクスは、制御プレーンがすでに追跡している状態（`jobs` テーブルとリース・ハートビートの記録）から導きます。新しい記録を足さず、既存の状態を読みます。
2. **compose 配線。** `deploy/self-host/` へ、`prometheus` コンテナ（`/metrics` をスクレイプ）と `grafana` コンテナ（メトリクスを可視化）を追加し、初期ダッシュボードも加えます。これらのコンテナは既存の `caddy` プロファイルと同様に任意なので、最小構成のデプロイは変わりません。
3. **エンドポイントの認証。** `/metrics` は、認証なしの公開面ではないので、serve の他の部分と同じ公開ルール（BE-0051）に従わなければなりません。また、BE-0055 の秘匿と一貫して、秘密情報を決して漏らしてはなりません。

**検証。** `/metrics` エンドポイントは Python 側の面を持つので、Simulator を使わず単体テストで確かめます。既知の待機中ジョブと実行中ジョブを持つ `ServeState` に対して、描画されたメトリクスが期待どおりのキューの深さと組織別の実行中数を報告することを確認します。出力に秘密情報が現れないことも確認します。Prometheus と Grafana のコンテナは、デプロイ上で手動で検証します。スクレイプが成功し、ダッシュボードが時系列を描くことを確かめます。

**調整メモ。** `/metrics` ルートは `bajutsu/serve/` に触れるため、進行中のほかの serve 作業と同じ調整メモが付きます。その面を編集中の未マージ PR がマージされたあとにルートを入れるか、コンフリクトを避けるよう調整します。

## 検討した代替案

- **構造化ログだけに頼る。** 却下します。ログは時系列ではなくイベントです。キューの深さやワーカーの生存をログのスクレイプから導くのは、脆く、遅れます。第一級のメトリクスエンドポイントが、これらの信号を得るための標準的で摩擦の少ない情報源です。
- **スクレイプ可能なエンドポイントの代わりに、外部のホスト型 APM へメトリクスを送る。** セルフホストの既定としては却下します。セルフホストのスタックが避けようとしている外部依存を復活させるからです。Prometheus 形式の `/metrics` エンドポイントは、セルフホストの Prometheus および Grafana と組み合わせて使えます。運用者が望めば、ホスト型のスクレイパを向けることも可能です。
- **Prometheus と Grafana を、任意プロファイルではなく常時有効として同梱する。** 却下します。すべてのセルフホストが追加のコンテナを望むわけではありません。（`caddy` と同様に）任意にすれば、最小構成のデプロイを軽く保ちつつ、望むときには一式を提供できます。
