## はじめに

開発者の手元で終えた実行を、プルリクエストまたは Issue に投稿するコマンド `bajutsu post` を追加します。コメントには、失敗したシナリオ、失敗したステップ、その理由を載せ、実行の証跡へのリンクを付けます。コマンドをもう一度実行すると、新しいコメントを増やさず、同じコメントを更新します。コマンドは開発者自身の GitHub の認証情報を使い、判定のあとに動きます。そのため、実行が決めた結果を変えることはありません。

コメントの形は、CI から投稿するポータブルな GitHub Action `post-evidence` のコメントと同じです。この Action は、兄弟の提案が定義します。2つの入口は1つの描画処理を共有します。実行がランナーで動いたか手元のノートパソコンで動いたかによらず、レビュアーは1つの形式を読めます。

## 動機

Bajutsu の実行の多くは、CI に届きません。iOS のフローを変えた開発者は、手元のシミュレーターに対してシナリオを実行します。CI のレーンはスイートの一部しか覆わず、デバイスクラウドの実行には時間と費用がかかるからです。変更が動くという証跡は、そのノートパソコンの `runs/` に残ります。レビュアーに見せるために、開発者は `bajutsu export`（[BE-0060](../BE-0060-run-report-zip-export/BE-0060-run-report-zip-export-ja.md)）で zip を作ります。そして、ブラウザーでコメントにファイルを手作業でドラッグします。スクリーンショットも動画も、1つずつです。

[BE-0110](../BE-0110-evidence-store-uri/BE-0110-evidence-store-uri-ja.md) は、`bajutsu run` から実行の証跡をオブジェクトストレージへアップロードします。しかし、アップロードしたファイルをコメントにする仕組みはありません。CI 側の Action も、ここでは役に立ちません。ワークフローの実行とランナーが要りますが、手元の実行には、そのどちらもないからです。

導入後に確かめられる違いは、コマンド1つです。`bajutsu post <run> --to owner/repo#123` を実行すると、プルリクエストにコメントが1件付きます。コメントは、どのシナリオが成功し、どのシナリオがなぜ失敗したかを述べ、失敗したスクリーンショット、動画、レポートへのリンクを持ちます。修正のあとにもう一度実行すれば、そのコメントが書き換わります。開発者は、ファイルをドラッグするためにブラウザーを開かずに済みます。

## 詳細設計

### コマンド

```
bajutsu post <run-id | run-dir> --to <target> [--sink store|release|none]
             [--evidence-base-url URL] [--key KEY] [--max-failures N]
             [--log-tail-kb N] [--size-warn-mb N] [--dry-run] [--yes]
```

`<run-id | run-dir>` は、`bajutsu export` と同じ規則で解決します。`--to` は、`owner/repo#123`、プルリクエストか Issue の URL、または `#123` を取ります。`#123` は、現在のチェックアウトの `origin` リモートに対して解決します。このコマンドは投稿するだけで、シナリオを実行せず、AI プロバイダーも読みません。`run` は GitHub を知らないままにします。`run` の中に投稿のステップを置くと、判定がネットワーク呼び出しに結びつくからです。

### 認証情報

コマンドは、`GITHUB_TOKEN` または `GH_TOKEN` からトークンを読みます。どちらも未設定で、`gh` CLI が入っていれば、`gh auth token` に尋ねます。トークンをディスク、実行ディレクトリ、ログのいずれにも書きません。プルリクエストや Issue へのコメントには、プルリクエストまたは Issue への書き込み権限が要ります。`release` シンクには、リポジトリのコンテンツへの書き込み権限も要ります。

### 証跡の送り先

GitHub には、画像や動画をコメントの中へアップロードする、文書化されたエンドポイントがありません。そこでコマンドは、リンクが届く場所にファイルを置き、コメントにそのリンクを載せます。`--sink` オプションが、送り先を選びます。

| シンク | 動作 | 必要なもの |
|---|---|---|
| `store` | [BE-0110](../BE-0110-evidence-store-uri/BE-0110-evidence-store-uri-ja.md) のアップローダーで、実行ツリーを `--evidence-store` または `BAJUTSU_EVIDENCE_STORE` へアップロードします。コメントは、各ファイルを `--evidence-base-url` の下でリンクし、スクリーンショットはインラインで表示されます。 | `s3://` か `gs://` の URI と、それを配信するベース URL。 |
| `release` | 失敗したスクリーンショット、動画、実行全体の zip を、プルリクエスト用の下書きリリースのアセットとしてアップロードします。コメントは、各アセットへリンクします。 | リポジトリのコンテンツへの書き込み権限。 |
| `none` | 何もアップロードしません。コメントは各ファイルをパスで示します。手作業でファイルを添付する開発者向けです。 | コメント用のトークンだけ。 |

既定は、ストアの URI が設定されていれば `store`、なければ `release` です。リリースのアセットは、開くのにリポジトリへのサインインが要り、コメントにインライン画像としては描画できません。アセットの種類ごとに、ブラウザーが表示するのかダウンロードするのかは、未確認です。最初の作業項目をスパイクにして記録します。結果によっては、既定が変わります。

### コメントの内容

描画処理は、Action と同じ Markdown を作ります。先頭に、判定、件数、実行 ID を置きます。失敗したシナリオごとのブロックには、シナリオ名、最初に失敗したステップ、失敗の理由を書きます。描画処理は `manifest.json` を読みます。マニフェストが残らなかった実行では、`<sid>/result.json` を読みます。コピーするすべての文字列は、Action の項目の規則でエスケープします。固定コメントは、1行目の隠しマーカー `<!-- bajutsu-evidence:<key> -->` を使います。比較は、末尾の空白と復帰文字を取り除いてから行います。`--key` の既定は `local` なので、同じプルリクエストの手元のコメントと CI のコメントは、別々に保たれます。

コマンドは、トークンに対して `GET /user` が返すログインで、自分のコメントを見つけます。GitHub App のインストールトークンのように、ユーザーを持たないトークンは、`--author` でログインを渡します。

### アップロードの前の確認

スクリーンショットや動画には、非公開のデータが写ることがあります。リポジトリへのアップロードは、外部へ向けた操作です。削除したアセットも、キャッシュに残ることがあります。そこでコマンドは、アップロードの前に計画を表示します。送り先、リポジトリの公開範囲、各ファイル、合計サイズを示し、確認を求めます。スクリプトからは `--yes` で確認を省けます。`--dry-run` は、計画と、投稿する Markdown を表示して、ネットワークへ何も書かずに止まります。

コマンドは、アップロードの前に、大きすぎる `deviceLog` を末尾の `--log-tail-kb` KB に切り詰めます。実行全体の zip は、`--size-warn-mb` を超えると省きます。どちらも、計画とコメントに明記します。文字列の伏せ字処理は、実行が `manifest.json` を書く時点で行われます（[BE-0331](../BE-0331-artifact-redaction-boundary/BE-0331-artifact-redaction-boundary-ja.md)）。スクリーンショットや動画の画素には、伏せ字処理がありません。確認があるのは、そのためです。

### 終了ステータス

`bajutsu post` は、開発者が投稿するために実行するコマンドです。そのため、投稿に失敗したら、理由を示して0以外で終了します。実行の副作用であるアップロードが警告に落ちる `run --evidence-store` とは、ここが違います。`post` の終了ステータスは、実行の判定を反映しません。失敗した実行も投稿でき、投稿が成功すれば0で終了します。

### 2つの入口に1つの描画処理

CLI と Action は、ずれてはなりません。そのため、描画処理は、標準ライブラリだけを使い、Bajutsu の他の部分を import しない1つのモジュールに置きます。CLI はそれを import します。Action は、自分のリポジトリのチェックアウトから、同じファイルを読み込みます。Action の項目は、現状、スクリプトを Action のディレクトリに置いています。2つの項目は、置き場所を1つに揃える必要があり、下の作業分解がその手順を挙げます。

### ドキュメント

`docs/cli.md` と `docs/ja/` のミラーに、`post` の節を足します。シンクの表と、手元のシミュレーターでの実行を使った例を載せます。

## 検討した代替案

- **`run` に `--post` フラグを足す。** 1つのコマンドで、実行と投稿ができます。採用しなかったのは、`run` がネットワークと GitHub の認証情報に依存するからです。途中で止まった実行は、投稿もされません。別のコマンドなら、先に終えた実行も投稿できます。
- **`bajutsu export` を拡張する。** このコマンドはすでに zip を作るので、投稿までは小さな一歩です。ただし、コメントの単位に zip は向きません。レビュアーが最初に見たいのは、失敗したスクリーンショットと理由だからです。`export` は、純粋なアーカイブのままにします。
- **ブラウザーが使うウェブのアップロード用エンドポイント。** コメントに画像をインラインで置けます。ただし、文書化されておらず、予告なく変わり得ます。それに依存するツールは、気付かないうちに壊れます。採用しませんでした。
- **`gh` CLI を包む、文書化したスクリプト。** スクリプトの提供に費用はかかりません。しかし、描画処理、エスケープ、固定コメント、確認を、すべてのチームが書き直すことになります。CI と手元のコメントも、ずれていきます。
- **`serve` からアップロードする。** `serve` は、すでに実行を持っており、投稿もできます。ただし、デプロイと GitHub App が要ります（[BE-0500](../BE-0500-run-set-github-check/BE-0500-run-set-github-check-ja.md)）。ノートパソコンには、そのどちらも要りません。
- **証跡をブランチにコミットする。** ブランチなら、安定した URL が手に入ります。ただし、リポジトリが肥大化し、保持期間の方針が要り、リポジトリの履歴へ書き込みます。そのため、既定には入れません。

> 開発の進行に合わせて常に最新の状態に保ってください。チェックリストは *詳細設計* の MECE な
> 作業分解（作業の単位ごとに 1 つ）に対応し、ログには変更内容と時期（古い順）を PR へのリンクと
> ともに記録します。

- [ ] スパイク：スクリーンショット、動画、zip をリリースのアセットとしてアップロードし、サインイン済みの読み手に表示されるかダウンロードになるかを、種類ごとに記録する。
- [ ] 共有の描画処理：CLI と Action の両方が読み込む、標準ライブラリだけの1つのモジュール。Action の項目のスクリプトの置き場所と揃える。
- [ ] GitHub クライアント：トークンの解決、`GET /user`、ページをたどる固定コメントの検索と更新、`--author`。
- [ ] シンク：BE-0110 のアップローダーによる `store`、`release`、`none`。ベース URL と計画の一覧表示を含む。
- [ ] コマンド：`bajutsu post`。`--to` の解析、確認、`--dry-run`、`--yes`、ログの切り詰め、サイズの保護、終了ステータスを含む。
- [ ] テスト：ゲートがオフラインで動かす、偽の GitHub HTTP サーバー。固定コメント、CRLF のマーカー照合、マニフェストがない場合を扱う。
- [ ] ドキュメント：`docs/cli.md` の節と、`docs/ja/` のミラー。
