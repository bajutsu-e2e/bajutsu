## はじめに

`serve` に、組織単位の API キーを足します。管理者が、1つの組織のためにキーを発行します。スクリプトは、そのキーを bearer トークンとして送り、その組織として動きます。キーの権限は、最大で `editor` です。キーが開くのは、許可リストに載せたルートだけです。そのため、キーが、管理者ログインの代わりになることはありません。

この項目が対象にするのは、開発者の手元で動き、ブラウザーのセッションを持たないスクリプトです。完了した run を `serve` に取り込む項目が、キーの最初の利用者になります。

## 動機

OAuth を設定すると、`serve` は、共有の bearer トークンをワーカーのルートにしか許可しません（`bajutsu/serve/gate.py` の `_is_worker_route`）。人のセッションの cookie は、スクリプトから使えません。唯一の機械用の ID は、[BE-0414](../BE-0414-ci-oidc-machine-identity/BE-0414-ci-oidc-machine-identity-ja.md) の OpenID Connect（OIDC）による交換です。しかし、これには CI プロバイダーの ID トークンが要り、ノート PC にはありません。そのため、ノート PC のスクリプトは、ホストされた `serve` のほかのルートを、1つも呼べません。

観察できる違いは、1回のリクエストです。キーを持つスクリプトが、OAuth で守られた `serve` のキーの許可リストにあるルートを呼ぶと、`200` が返ります。許可リストは空で始まるので、テストが、ルートを1つ足します。管理者がキーを失効させたあとは、同じ呼び出しに `401` が返ります。テストは両方を確かめ、監査イベントが、使うたびに記録されます。

## 詳細設計

### キーの形式と保存

キーは、識別子と秘密の2つの部分からなり、`bajutsu_<id>_<secret>` の形です。識別子は `secrets.token_hex(8)` で、ランダムで、秘密ではなく、アンダースコアを含みません。そのため、`value.split("_", 2)` で、キーを曖昧さなく分けられます。秘密は `secrets.token_urlsafe(32)` です。サーバーは、識別子と、秘密の SHA-256 ハッシュを保存します。組織、権限、作成者、作成時刻、期限、最後に使った時刻も保存します。秘密そのものは、保存しません。リクエストは、識別子で行を引き、ハッシュを `hmac.compare_digest` で比べて検証します。

行は、リポジトリに置きます。テーブルは、新しい Alembic マイグレーション（`bajutsu/serve/server/migrations/versions/` の次の番号）が作ります。`Repository` プロトコルと `sql_repository.py` に、キーの作成、組織ごとの一覧、識別子による取得、失効、組織のキーの一括失効、最終使用時刻の更新の各メソッドを足します。テーブルは、組織の名前を持つほかのテーブルと同じく、通常の外部キーで組織を指します。

組織の廃止は、ソフトデリートなので、カスケードは働きません。そこで、`delete_org` が、`revoke_machine_sessions` の隣で、新しい `revoke_org_keys(org_id)` を呼びます。キーの照会も、組織が `get_org` で返らなくなったキーを、`401` で拒否します。

### 発行、一覧、失効

キーのために、3つのルートを置きます。パスに組織を含めるので、`/api/orgs/` をすでに守っている `required_role` の管理者向けの分岐が、3つの動詞すべてに適用されます。`machine-sessions/revoke` を守っているのと同じ形です。単数形の `/api/org` の下に置くと、その分岐を通らず、サインイン済みのどの viewer でも、キーを発行できてしまいます。

- `POST /api/orgs/<slug>/keys` は、名前、`viewer` か `editor` の権限、最長 365 日の期限（デフォルトは 90 日）からキーを作ります。応答にキーが載るのは1回だけで、あとの呼び出しでは、キーを返しません。
- `GET /api/orgs/<slug>/keys` は、各キーの識別子、名前、権限、作成者、期限、最後に使った時刻を一覧にします。
- `DELETE /api/orgs/<slug>/keys/<id>` は、キーを失効させます。そのキーを使う次のリクエストには、`401` が返ります。ほかの組織の識別子には `403` ではなく `404` を返し、キーの存在を確認させません。

キーが `admin` の権限を持つことはありません。そのため、キーがキーを発行したり失効させたりすることはできません。ローテーションは2段階です。新しいキーを発行し、そのあとで古いキーを失効させます。

### ゲートとプリンシパル

bearer の値をキーとして扱うのは、キーの形に合い、しかもその識別子が存在するときだけです。それ以外の値は、共有トークンの検査へ回します。そのため、運用者のトークンがたまたま `bajutsu_` で始まっても、使い続けられます。照会に失敗したキー、期限切れのキー、失効したキーには、どの部分が違うかを示さずに、`401` を返します。

有効なキーからは、新しい種類のプリンシパルができます。この項目は、`PrincipalKind` に値 `api-key` を、`Principal` に `role` フィールドを足します。このプリンシパルを作るのは、bearer の検査だけです。`kind_from_stored` は、保存された種類を、これまでどおり `human` か `machine` の2つに絞り、`Principal.from_stored` は `role` を読みません。そのため、セッションの行が、キーの種類を名乗って、下の権限のゲートを飛ばすことはできません。形は `Principal(kind="api-key", identity="api-key:<id>", org, role)` です。2つのバックエンドは、マシンの分岐と、`forbidden_for_role` の前で、この種類を分岐させます。`forbidden_for_role` は、キーにはないユーザーの行を読むためです。2つのバックエンドは、`_machine_org` が使う、リクエストごとのスロットに組織を入れます。そのため、`state.org_for` は、`default` ではなく、キーの組織を返します。2つのバックエンドは、マシンのセッションですでに行っているのと同じく、そのスロットをリクエストごとに空にします。

権限の検査は、`required_role(method, path)` が権限を返すときに行います。リクエストが通るのは、`role_allows(key.role, その権限)` が真のときだけです。監査と操作ログの実行者は、`api-key:<id>` です。

そのあとで、ゲートは、既定で拒否する許可リスト `_API_KEY_PATHS` を適用します。形は、既存の `_MACHINE_PATHS` と同じです。許可リストは空で始まり、キーで呼べるルートを足す項目が、そのルートを書き加えます。

### キーが使える場所

キーの行は、SQL のリポジトリに置きます。リポジトリがない `serve` には、組織ごとの ID がなく、共有トークンがすでに全権限を持ちます。そのため、キーのルートは、そこでは `409` を返します。

### 監査とログ

発行、失効、使用のたびに、監査イベントを書きます。イベントに載せるのは、キーの識別子で、秘密は載せません。`audit_log.actor_id` は `users.id` への外部キーで、キーにはユーザーの行がありません。そのため、`_record_audit` に、マシンの分岐の隣へ、`api-key` の分岐を足します。行の `actor_id` は null にし、キーの識別子は `detail` に入れます。最後に使った時刻の更新は、キー1つにつき、1分に1回までです。キーが、URL、ログの行、エラーメッセージに現れることはありません。

### テストとドキュメント

テストでは、次のケースを確かめます。

- 発行はキーを1回だけ返し、保存した行に秘密は含まれません。
- viewer のセッションと editor のセッションは、3つのルートのどれでも `403` になります。
- ほかの組織の識別子で削除すると、`404` になります。
- 有効なキーは許可リストのルートを通り、リクエストは `default` ではなくキーの組織に入り、載っていないルートは拒否されます。
- 期限切れのキー、失効したキー、秘密が違うキーは、どれも `401` になります。
- `bajutsu_` で始まる共有トークンでも、ワーカーは認証できます。
- キーは、キーのルートに届かず、viewer のキーは、editor 向けのルートを呼べません。
- 組織を廃止すると、そのキーは `401` になります。

`docs/self-hosting.md`、`docs/cli.md`、および `docs/ja/` のミラーに、ルートを書きます。

## 検討した代替案

- **OIDC トークンを交換する。** [BE-0414](../BE-0414-ci-oidc-machine-identity/BE-0414-ci-oidc-machine-identity-ja.md) は、プロバイダーがトークンを出す CI に向いています。ノート PC には、プロバイダーのトークンがありません。
- **ワーカーの bearer トークンを広げる。** ワーカーは、ユーザーではありません。そのトークンがユーザー向けのルートに届くと、`_is_worker_route` が引いている境界が消えます。
- **ユーザーごとの個人トークン。** 個人トークンは、特定の人の ID を持ち、辞めた人のためのライフサイクルも要ります。組織のキーは、チームが1つの認証情報を共有する実態に合い、管理者が管理できます。
- **相互 TLS。** 運用の負担が大きく、証明書から権限への対応づけも、別に要ります。
