## はじめに

iOS では、視覚アラートガードが何を判断しても SpringBoard のプロンプトを消せません。ガード
（`bajutsu/agents/alerts.py`）は最後に `driver.tap_point`、つまりアプリにスコープされた XCUITest の
座標タップを呼びます。しかし SpringBoard のプロンプトは別プロセスのものです。
[BE-0316](../BE-0316-ios-permission-alert-step/BE-0316-ios-permission-alert-step-ja.md) が2つめの
`XCUIApplication` を問い合わせているのは、まさにそのためです。実測された挙動は、外れるタップよりも
悪いものでした。プロンプトが出ているあいだにアプリへの操作を*何か*行うと、XCTest がプロンプトを自身の
デフォルトボタンで解決してしまい、権限要求ではそれが*許可*側になります。本項目は、ガードの判断を
BE-0316 のネイティブな SpringBoard タップへ流し、ボタンの特定は視覚に任せたまま、実際の操作は確実に
動く経路へ委ねます。

## 動機

ショーケースの SwiftUI アプリ（iPhone 17、iOS 26.5）での3つの実測が、仮説を切り分けます。通知
プロンプトを出したまま何も触らないと、15回のポーリングを通じて出たままで、アプリの状態も
`notDetermined` のままでした。つまり自然に消えるものではありません。どちらのボタンからも遠い
`(5, 5)` への座標タップは、プロンプトを消してアプリの状態を `authorized` にしました。`Don’t Allow`
の中心そのもの、`(127, 518)` への座標タップも同じく `authorized` でした。一方、アプリ*自身*の
ダイアログに対する座標タップは正常に動き、その下のボタンに着地しました。3つの読みが強制する結論は、
SpringBoard のプロンプトが出ているあいだ座標は何も決めていない、というものです。プロンプトを解決して
いるのは操作そのものであり、しかもプロンプトのデフォルトで解決しています。

したがって、ガードが掲げる挙動と実際の挙動は正反対です。文書化されたデフォルトは「もっとも破壊的でない、
拒否側のボタン」、つまり `Not Now`、`Don’t Allow`、`Cancel` です。ところが run が実際に得るのは許可側の
デフォルトであり、シナリオが求めていない権限が実行中に黙って与えられます。しかも run のレポートには
*モデル*の選んだボタンが記録されるので、証跡は一度も押されていない `Don’t Allow` を指します。起きた
ことと反対の内容を報告するテストツールは、失敗するツールよりも悪いものです。これが本項目を機能追加ではなく
欠陥の修正にしている理由です。

視覚の経路は、もはや誰も通らない死んだコードではありません。
[BE-0315](../BE-0315-ios-native-system-alert-handling/BE-0315-ios-native-system-alert-handling-ja.md)
はネイティブ経路を主として、ネイティブ経路が扱えない場合のフォールバックとして視覚を残しました。
バックエンドがその capability を持たない場合、ブロックしている面が列挙可能な `springboard.alerts` の
アラートではない場合、そしてアラートがポリシーの名指すボタンを持たない場合です。3つめは、視覚経路に
到達する本物の iOS SpringBoard アラートであり、まさに座標タップが機能しない場所にあたります。つまり
フォールバックは生きていて、iOS ではそれが不活性です。

一方で視覚の*判断*は健全であり、しかもそれは実測されています。
[BE-0308](../BE-0308-alerts-guard-real-model-verification/BE-0308-alerts-guard-real-model-verification-ja.md)
では、実モデルが通知プロンプトに対して `Don’t Allow` の中心との差 0.5 ポイント未満で答え、位置情報
プロンプトでは縦に並ぶ3つの選択肢の最下段を選び、アプリ自身の削除確認では赤い `Delete` に手を伸ばす
のではなくプロンプトなしと正しく報告しました。差し替えが必要なのは、すでに正しい判断の下にある操作の
部分であり、判断そのものではありません。

## 詳細設計

提案の粒度です。作業は以下の単位に沿って MECE に分かれます。

- **バックエンドがネイティブ経路を持つ場合、ガードにそれを使わせる**：ロケータは座標に加えてすでに
  ラベルを返しています（`AlertDecision.label`）。そして BE-0316 の `handle_system_alert` は、
  `resolve_unique` の「0件・曖昧・一意」の規律のもとで SpringBoard のボタンをラベルでタップします。
  バックエンドが `HANDLE_SYSTEM_ALERT` を広告し、プロンプトが列挙可能であるなら、ガードは座標を
  タップするのではなくそのラベルをネイティブなタップへ渡すべきです。そうすれば視覚は「どのボタンか」
  に答え、決定的な経路が「それを押す」に答えます。これは同時に、当てずっぽうの座標タップを、何にも
  一致しないときや複数に一致したときに明示的に失敗するセレクタへ置き換えることにもなります
  （prime directive 2）。
- **座標タップが本当に役立つ面のために残し、それがどれかを明記する**：上の実測では、アプリ自身の
  ダイアログに対する座標タップは正常に動きました。したがって座標の経路は、プロセス外のプロンプト
  *ではない*ブロック面、つまりアプリ内のオーバーレイや web バックエンド自身のダイアログについては
  今も正しいままです。この単位の作業は、1つの経路が黙って両方を覆っている状態をやめ、その境界を
  明示的に引くことです。
- **どちらの経路も動けないときは明示的に失敗する**：現在は、消せないプロンプトに対してタップが発行
  され、一度も押されていないボタンを名指す `AlertEvent` が残り、run はそのまま続きます。上の境界が
  どう決まるにせよ、ガードが操作できない場合は dismiss として記録するのではなく、操作できなかったと
  報告しなければなりません。ガードが run をクラッシュさせないことを選ぶのは構いません（設計上
  best-effort です）。しかし、行っていない操作をしたと主張してはいけません。
- **視覚の判断が本当にプロンプトを消すことを実機で確認する**：高速スイートはこの欠陥をまったく見られ
  ません。既存のテストはいずれもガードに `FakeDriver` を渡し、その `tap_point` は XCTest を駆動せず
  座標を記録するだけなので、この失敗の系統は実機を離れると不可視です。本物の SpringBoard プロンプトに
  対して視覚経路へ到達し、結果の認可状態が `authorized` ではなく `denied` であることを検証する
  シナリオが、この欠陥を捕まえられたはずのものであり、今後も捕まえ続けるものです。

ここでモデルが `run` の判定に載ることはありません。ガードは Tier 1 のライブ AI 操作のままで、その
出力は操作であって合否の判断ではありません。本項目はその操作を決定的なプリミティブへ移すだけで、
新しい場所にモデルを加えることはしません。

## 検討した代替案

- **座標タップが SpringBoard に届くように直す**：タップはアプリ自身の原点からのオフセットとして発行
  されます（ランナー内の `app.coordinate(withNormalizedOffset:).withOffset(...)`）。そして実測は、
  座標が意味を持つ前に操作が横取りされることを示しています。着地させられるオフセットは存在しません。
  SpringBoard に届くとは SpringBoard を宛先にすることであり、それは BE-0316 の2つめの
  `XCUIApplication` がすでに行っていることです。
- **iOS では視覚のフォールバックを完全に捨て、BE-0315 のネイティブ経路だけを残す**：上の単位で
  ネイティブ経路が見つからなかった場合の正直な下限であり、計画ではなく代替の立場として名前を挙げて
  おくべきものです。これは、決定的なポリシーが名指さないボタンを持つアラートに対する安全網を外すこと
  になり、その場合こそ視覚経路が存在する理由にあたります。ネイティブなタップを再利用すれば、その網を
  切らずに残せます。
- **SpringBoard のツリーではなく、アプリにスコープされたツリーでラベルからタップする**：アプリの
  アクセシビリティクエリは SpringBoard のプロンプトをまったく見られません。これは
  `agents/alerts.py` のモジュール docstring が冒頭で述べている前提であり、その側にはラベルを解決する
  相手の要素が存在しません。
- **BE-0276 の `permissions` による事前付与を広げ、プロンプトが出ないようにする**：BE-0315 がここで
  問題になっているプロンプトについてすでに却下しています。通知の認可は Transparency, Consent, and
  Control（TCC）のサービスではなく、App Tracking Transparency とプロセス間のペースト同意には
  `simctl` のトグルがありません。したがってこれらにリアクティブな経路は避けられません。
- **XCTest 自身のプロンプト解決を、バグではなく仕様として受け入れる**：たしかにプロンプトは消えるので、
  何も壊れていないと読む余地はあります。しかし押されるのはプロンプトのデフォルト、つまり権限要求では
  許可側であり、ガードが文書化している「もっとも破壊的でないデフォルト」の逆です。これを受け入れることは、
  シナリオが求めていない権限を run が黙って与え、しかも一度も押されていないボタンをレポートが名指す
  状態を受け入れることになります。
