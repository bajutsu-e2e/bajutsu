## はじめに

ホスティングされた `bajutsu serve` が今日認証する呼び出し元は、2種類です。

- 人間は GitHub OAuth（Open Authorization）でサインインし、身元を得ます。その身元を、ロールのゲートがエンドポイントごとに検査します（[BE-0313](../BE-0313-github-org-team-rbac/BE-0313-github-org-team-rbac-ja.md)）。
- worker は共有トークン（[BE-0051](../BE-0051-serve-hardening-for-hosting/BE-0051-serve-hardening-for-hosting-ja.md)）を提示し、身元は一切持ちません。

継続的インテグレーション（CI）のジョブは、そのどちらでもありません。ブラウザでのサインインを完了できません。OAuth を設定したデプロイでは、共有トークンが worker のトラフィック以外のエンドポイントへ届かなくなります。

本項目は、そうしたジョブに固有の身元を与えます。ジョブは、GitHub Actions がワークフローに発行する OpenID Connect（OIDC）トークンを、専用の交換エンドポイントへ一度だけ提示します。serve はそこでトークンを検証し、代わりに短命の機械セッションを発行します。そのセッションが振る舞う org は、トークンのクレームが名指すリポジトリで決まります。アクセス範囲は機械が必要とするものに絞り、人間のロールには決して寄せません。

## 動機

BE-0313 は、serve のログイン許可リストを GitHub 自身の organization と Team のメンバーシップに置き換えました。同じ変更で、共有トークンを worker のトラフィックへ絞りました。人間にとっては、これは正しい判断でした。ロールのゲートが検査できる身元は、すべてを許す秘密より優れています。しかし、機械には代替が残りませんでした。`docs/self-hosting.md` は、その結果をはっきり記録しています。トークンで worker 以外のエンドポイントをスクリプトしていたデプロイは、OAuth を有効にした時点でその経路を失います。

穴は、リクエストのゲートに現れています。`bajutsu/serve/handler.py` の `_gate` は、リクエストを認証したあと、それが身元を運ぶかどうかで分岐します。

- OAuth のセッションは身元を持つため、`forbidden_for_role` が検査します。
- bearer トークンのリクエストは身元を持ちません。その先は、コード自身のコメントが述べています。「stays full-access (the operator credential)」です。

つまり serve が知っている形は正確に2つで、CI のジョブはどちらにも当てはまりません。

| 呼び出し元 | 資格情報 | 身元 | アクセス |
|---|---|---|---|
| 人間 | GitHub OAuth セッション | GitHub ログイン | ロールで制限：viewer / editor / admin |
| worker | 共有トークン | なし | worker の経路で全権 |
| CI のジョブ | *（利用できるものがない）* | — | — |

共有トークンがまだ使えるデプロイでそれを CI に渡しても、この穴は閉じません。OAuth の場合を離れても、理由が2つあります。

- 共有の秘密は、どのパイプラインの操作なのかを言えません。そのため、監査の記録は「トークン」までで止まります。
- 共有トークンは身元を持たないため、全権で届きます。org の設定を差し替えたり、シークレットを埋め込んだ config の本文を読み出したりできる資格情報が、すべてのパイプラインに置かれることになります。

具体的には、CI のパイプラインが呼ぶ理由のあるエンドポイント5つが閉じています。

- `POST /api/artifacts/binary` と `GET /api/artifacts/exists` は、admin ロールを要求します。
- `POST /api/run` は、editor ロールを要求します。

本項目の兄弟にあたる、ジョブ単位の binary アーティファクト上書きの提案は、まさにこの順序を求めています。ビルドをアップロードし、それを名指して run を dispatch する順序です。しかし、その提案が前提にできるのは、トークン認証のデプロイがすでに信頼している資格情報だけです。OAuth のデプロイでは、前提にできるものがありません。

ビルドとあわせて設定やシナリオ一式を公開するパイプラインもあります。そうしたパイプラインには、さらに2つの admin 向けルート、`POST /api/artifacts/config` と `POST /api/artifacts/scenarios` が必要です。そのため、以下の許可リストは binary だけでなく、アーティファクトの3種類すべてを対象にします。

このパイプラインは、公開したものを人間が後から compose するための運び手ではありません。公開したものの利用者そのものです。アップロードしたばかりの3つ組に対して、シナリオを名指して実行します。その3つ組が、`POST /api/compose` が行う org 全体の差し替えなしにどう有効になるかは、単位3で述べます。

**検証可能な成果。** `permissions: id-token: write` を宣言し、**リポジトリのシークレットを一切持たない** GitHub Actions のワークフローが、OAuth を設定したデプロイに対して run を dispatch します。その run は、ワークフローのリポジトリが属する org に着地します。org が列挙していないリポジトリのワークフローは、403 で拒否されます。そして、run の監査記録にはそのリポジトリ名が残ります。トークンが提示されたという事実だけではありません。

## 詳細設計

作業は MECE（漏れなく重複なく）に4つの単位へ分かれます。

- トークンの検証。
- クレームから org への対応づけ。
- 機械に何を許すかの決定。
- テストとドキュメント。

### 単位1：トークンを一度だけ機械セッションに交換する

本項目が対象とするパイプラインは、3つのエンドポイントを順に呼びます。`GET /api/artifacts/exists`、`POST /api/artifacts/binary`、`POST /api/run` の順です。

OIDC トークンをリクエストのたびに検証し、一度見た `jti` を拒否する仕組みを考えます。この仕組みは、2回目の呼び出しでこの並びを拒否してしまいます。1回目の呼び出しですでに `jti` を使い切っているからです。使い捨ての再送防止をリクエストのたびに課す仕組みでは、このパイプラインを扱えません。

そこで serve は、専用の交換エンドポイント `POST /api/oidc/exchange` で、トークンを一度だけ検証します。そして代わりに、短命の**機械セッション**を発行します。この並びの後続の呼び出しは、すべてこのセッションを提示します。以下の各検査は内容をそのまま残しつつ、リクエストのたびにではなく、交換の一度だけになります。

GitHub Actions は、`permissions: id-token: write` を宣言したワークフローのジョブに対して、署名済みの JSON Web Token（JWT）を発行します。ジョブは、`$ACTIONS_ID_TOKEN_REQUEST_URL` へ `$ACTIONS_ID_TOKEN_REQUEST_TOKEN` を添えて要求します。どちらも、その権限を宣言したジョブから使えます。GitHub 側に GitHub App、OAuth app、Identity Provider の登録は一切必要ありません。

ジョブは、その結果を bearer トークンとして交換エンドポイントへ送ります。serve はそこで署名を検証してから、クレームを信頼します。

- **発行者。** `iss` は、設定された発行者と一致しなければなりません。GitHub がホストする Actions であれば `https://token.actions.githubusercontent.com` です。
- **署名。** 発行者の JSON Web Key Set（JWKS）に対する RS256 です。
  - JWKS は `/.well-known/openid-configuration` から辿り、有効期限つきでキャッシュします。交換のたびに鍵を取得しにいくことはしません。
  - 検証器は、許可するアルゴリズムとして RS256 だけを渡します。ヘッダーが別のアルゴリズムを名指すトークンは拒否します。アルゴリズムをトークン自身に選ばせることはありません。`alg: none` や、HS256 を RSA の公開鍵バイト列で検証させる、あの典型的な JWT 攻撃を防ぐためです。
  - 発行者の discovery ドキュメントは RS256 だけを広告しているため、この制約に費用はかかりません。
  - JWKS の各項目は、鍵の種類が RSA であり、広告されたアルゴリズムも一致する場合にだけ使います。
  - キャッシュにない鍵 ID（`kid`）は更新を発生させますが、最小の更新間隔を設けます（または、直近に見つからなかった鍵 ID を一定時間ネガティブキャッシュします）。そうしないと、交換エンドポイントへ到達できる人は誰でも、認証される前にランダムな `kid` を使ったリクエストで、外部への鍵取得を1回ずつ強制できます。これは、このキャッシュ自体が防ごうとしている増幅そのものです。
  - この増幅が及ぶ範囲は、今ではあらゆるリクエストではなく、交換エンドポイント1つに絞られています。それでも上限はなお重要です。このエンドポイントは事前の資格情報を必要とせず、誰でも到達できるからです（単位3）。
  - この鍵取得には、明示的なタイムアウトを設けます。ゲートは stdlib バックエンドで同期的に動くためです。
  - 鍵セットを取得できず、キャッシュも失効している場合は、古い鍵セットを信頼せず、交換を拒否します。ローテーションで外れた鍵を、有効なままにしておくわけにはいきません。それでも検証できない署名は、閉じる方向で失敗します。
- **想定利用者。** `aud` は、**デプロイ側**が設定した値と一致しなければなりません。これは、オペレーターが省略してはならない唯一の検査です。
  - 想定利用者は、ワークフローが自分で選べます（`core.getIDToken(audience)` が引数に取ります）。そのため、任意の `aud` を受け入れるデプロイは、無関係なサービス向けに発行されたトークンを受け入れることになります。
  - デプロイがどの想定利用者も設定していない場合は、OIDC の呼び出し形態そのものを無効にします。OIDC トークンを提示する交換のリクエストは、無条件に拒否します。任意の `aud` を受け入れる側へ倒れることはありません。
  - これは、運用者の注意力ではなく、閉じる方向の失敗に頼る設計です。
- **有効期間。** `exp`、`nbf`、`iat` を、わずかなずれの許容とともに検査します。この許容は、`bajutsu/common/github/app.py` が App JWT に署名するときすでに適用している60秒の遡りと同じ考え方です。`iat` を持たないトークンは、そのまま拒否します。下記の serve 側の経過時間上限が、`iat` がなければ測る起点を持てないためです。`jti` の欠落に適用しているのと同じ、閉じる方向の失敗規則です。
- **再送・使い捨て・レプリカ間の共有。** GitHub は数値の有効期間を文書化していません。トークンは bearer の資格情報であり、捕捉した者は有効な間ずっと再送できます。これは、代替案で述べた「ログに漏れる秘密がない」という利点と相性が悪い事実です。
  - serve は、トークンの `jti` クレームをキーにした再送検知キャッシュを保持します（GitHub は `jti` を一意な識別子として文書化しています）。このキャッシュは、トークン自身の `exp` で有効期限を区切ります。
  - さらに `exp` とは独立に、serve 側で定めた最大経過時間を超えたトークンも拒否します。
  - `jti` を持たないトークンは、そのまま拒否します。単位2が `environment` クレームの欠落に適用しているのと同じ、閉じる方向の失敗規則です。
  - このキャッシュは、共有の system of record、`Repository` という接続点に置きます。暗号化された組織ごとのシークレット保管が書き込む先と同じデータベースです。こちらは自らの `SecretStore` という接続点を経由します。`docs/self-hosting.md` は、ホスティングされた制御プレーンを、そのストアを共有する複数のレプリカとして記録しています。
  - プロセスごとのキャッシュだと、捕捉したトークンを別のレプリカへ再送すればすり抜けられてしまいます。実際の歯止めは、経過時間の上限だけになります。
  - 費用は、ジョブ1件につき書き込み1回です。交換はリクエストのたびにではなく、ジョブ1件につき一度だけ起きるからです。
  - 一度使われた `jti` が再び提示されると、最初に使い切ったレプリカでも別のレプリカでも拒否します。

検証には [`joserfc`](https://jose.authlib.org/) を使います。joserfc は、JWS、JWT、JWK 鍵セットを一通り扱う、保守が続いている JOSE（JavaScript Object Signing and Encryption）実装です。

joserfc は、`oauth` extra の依存として保証されているわけではありません。authlib の依存になったのは `authlib` 1.7.0 からです。`oauth = ["authlib>=1.3", "httpx>=0.27"]` は、それより前のリリースを下限として宣言しています。今日インストールされているのは、`uv.lock` がたまたま `authlib` 1.7.2 を固定しているからにすぎません。

そこで単位1は、authlib の推移的な依存に頼らず、`joserfc` を `oauth` extra へ直接宣言します。extra は、コードが実際に import するものをそのまま言うようになります。`joserfc` を残すためだけに authlib のアップグレードを強いることもなくなります。このライブラリは、現行の lock ではすでにインストールされています。この変更が保つのは、authlib 自身の依存関係が今後どちらへ動いても、その状態が変わらないという事実です。BE-0224 は、別の config ソースの関心事として App JWT に `cryptography` で署名しています。本項目は、その仕組みに触れません。

交換エンドポイント自身の検証は、専用のモジュールに置き、OIDC を設定したときにだけ遅延 import します。検証とは、JWKS の取得とそのキャッシュ、そして上記の各検査です。`bajutsu/serve/gate.py` が持つのは、機械セッションのポリシー判断（単位3）だけです。

理由は次のとおりです。`bajutsu/serve/__init__.py` は `gate` を無条件に import します。`joserfc` は `oauth` extra にしか付属しません。そのため、`gate.py` 内でモジュールレベルの `joserfc` を import すると、ベースインストールと worker extra のすべてで `import bajutsu.serve` が例外を送出します。

単位4は、`tests/serve/test_import_guard.py` の `FORBIDDEN` 集合へ `joserfc` を追加します。この集合は、今日 `authlib` を挙げていますが `joserfc` は挙げていません。この抜けを放置すると、この回帰には誰も気づけません。

**セッションストアは、この設計に必要なものを備え、保証できないものは交換そのものを拒否します。** `SessionStore.issue()` は、今日、有効期限の引数を取りません。有効期間はストア単位です（`BAJUTSU_SESSION_TTL`、デフォルトで7日間）。トークン自身の `exp` は、ストア単位の有効期間では表現できません。

そこで単位1は、Protocol と3つの実装すべてへ、機械セッションごとの有効期限を追加します。対象は次の3つです。

- `in_memory_session_store.py`
- `server/sessions/sql_session_store.py`
- `server/sessions/redis_session_store.py`

あわせて、`id`、`identity`、`expires_at` に加えて2つの列をセッションの記録へ加えます。解決済みの **org** と **principal kind** であり、単位3がこれをリクエストごとに読みます。

`InMemorySessionStore` は、有効期限を一切保証しません（`return sid in self._sessions`）。そのため、**セッションごとの有効期限を保証できないストアでは、交換そのものを拒否します**。想定利用者が未設定の場合と同じ、閉じる方向の失敗です。OIDC の呼び出し形態を、OAuth を設定しデータベースを配線したデプロイに絞ります。

発行する機械セッションの有効期間も、トークン自身の `exp` を上限とします。この交換がトークンをそのまま再利用するより優れているのは、発行する資格情報がトークンより短命な場合だけです。

上記の `sessions` の2つの列と `jti` の再送検知テーブルは、どちらもスキーマの変更です。これまでの追加と同じように、`bajutsu/serve/server/migrations/versions/` 配下の Alembic の revision を伴います。再送検知テーブルもキャッシュのように読めますが、他と変わらないテーブルです。

revision がないと、既存のデプロイを更新したときに、`sessions` テーブルにない列を選択するコードが動いてしまいます。存在しないテーブルへ行を書くコードも動きます。この設計が対象を絞っている、まさにデータベースを配線したデプロイで、交換が実行時に失敗します。

**この交換が買うもの、買わないもの。** どちらも TLS 越しの bearer 資格情報であり、捕捉された資格情報への耐性はほぼ変わりません。正直な違いは有効期間だけであり、だからこそ上記の上限が重要です。変わるのは次の4点です。

- 機械セッションは**取り消せます**。単位3が与える身元によってです。GitHub が発行したトークンは、serve が取り消せません。
- JWT の検証と JWKS の取得は、リクエストごとの経路から完全に外れます。そのコードが認証前に到達できるのは、交換の1回だけになります。
- 使い捨ての `jti` がそもそも可能になります。盗まれたトークンは、静かな成功から**目に見える失敗**へ変わります。攻撃者側の交換が `jti` を使い切るため、正規のジョブ側の交換は大きな音を立てて失敗します。
- 発行されたセッションは、他のどのサービスにも無価値です。`aud` を他のサービスも受け入れてしまう可能性があるトークンとは違います。

費用は、エンドポイントが1つ増えること、セッションの有効期間を正しく決めること、ジョブの間だけパイプラインに第二の資格情報が増えることです。

交換のあと、機械のリクエストは JWT を一切運びません。あらゆる人間のリクエストがすでに通っている経路と同じ、セッションの照合を通ります。照合先のセッションは、OAuth のコールバックが人間のセッションを発行するのとまったく同じ `state.auth.issue_session()` で発行されたものです。OAuth が無効にするのは `authz.login()`、つまりトークンによるサインインのほうです。機械に対しては、この交換がその代わりを担います。

### 単位2：クレームそのもので org へ対応づける

`OrgConfig`（`bajutsu/serve/orgs.py`）は、org に誰が属するかをすでに宣言しています。`members`、`githubOrgs`、`githubTeams`、`editorTeams`、そしてその org が所有する `targets` です。

本項目は、ここへ `allowedRepositories` を追加します。各項目は `"<owner>/<repo>"` という文字列です。この項目をさらに絞り込むオブジェクトにもできます（後述します）。

**交換のリクエストは、使いたい org を必ず名指します。** その org の `allowedRepositories` がトークンのリポジトリを列挙していれば、交換は成功します。列挙していなければ、拒否します。規則はこれだけです。

org の名指しは、**選ぶだけで、権限を与えません**。リクエストが言うのは、どの org に対してクレームを照合するかだけです。通すかどうかは、照合の結果が決めます。`worker_lease` の規律（org は検証済みの出所から取り、呼び出し元の申告からは取らない）を、一段上へ適用した形です。

名指しを求めることが、1つのリポジトリを複数の org で使えるようにします。これは実在する形で、異なるチームのアプリを検証する共有のパイプライン用リポジトリが該当します。推測に頼ると、この形を禁じるか、列挙している複数の org から勝者を選ぶかになります。

- 人間は、この曖昧さを事後に解消できます。`eligible_orgs` に裏打ちされたヘッダーの org セレクターがあり、どこに着地したか見えて切り替えられるからです。
- パイプラインには何も見えません。同じ事後の選択では、複数のテナントのどれかへ静かに着地します。

ワークフローで org を名指せば、狙う先はすでに書き記されている場所で明示され、判定は1回の所属確認に縮みます。機械セッションがその org を記録するので、交換時に決まり、リクエストごとに導出し直すことはありません。

**`allowedRepositories` が `"<owner>/<repo>"` という名前を使い続けるのは、意識して受け入れたトレードオフです。** 軽い注意書きではありません。`repository` は*可変の*名前です。名前の再利用こそ、GitHub が immutable な subject を導入した理由そのものです。列挙したリポジトリが削除、リネーム、または譲渡されると、その名前は空きます。次にその名前を得た人は、列挙した項目と一致する `repository` クレームを持つトークンを発行できてしまいます。

本項目は名前による形を維持します。そのため、運用者には責務が生まれます。リポジトリがリネーム、譲渡、または削除された瞬間に、項目を削除または更新しなければなりません。項目が認めているのは名前であって、リポジトリそのものではないからです。

**設定が効力を持つのは交換のときだけです。** リクエストごとに検証する設計であれば、項目の削除や `environment`／`ref` による絞り込みの強化は、次の呼び出しから効力を持ちました。一度きりの交換では、すでに発行された機械セッションが、古い絞り込みのまま、有効期限が切れるまでその org として振る舞い続けます。これが、上で述べた名前再利用という露出の実際の被害範囲です。

運用者の責務は、項目を削除または更新するだけでなく、その項目のために発行された機械セッションを取り消すことにも及びます。単位3が与える身元（`repo:<owner>/<repo>`）を使います。

**`sub` を解析するのではなく、個別のクレームで一致させます。** トークンは `repository` と `repository_owner`、さらに `repository_id` と `repository_owner_id` を運びます。認可は、`repository` を完全一致で比較します。`sub` を読むのが誤りである理由は2つあります。

- **`sub` の形式は、新しいリポジトリについてはすでに変わりました。**
  - 2026年7月15日より後に作られたリポジトリは、数値の ID を埋め込んだ immutable な subject を得ます。`repo:octo-org@123456/octo-repo@456789:ref:refs/heads/main` という形です。
  - GitHub は、その日付より後のリネームや譲渡も、immutable な形式へ移します。そのため、列挙済みのリポジトリが、誰も選んだ覚えのないまま形式を変えることがあります。これは、上で述べた名前再利用への注意を、いっそう必要にする事実です。
  - それ以前のリポジトリは、明示的に切り替えないかぎり以前の形のままです。
  - immutable な subject は、GitHub Enterprise Server では使えません。
  - `sub` を解析するデプロイは、あらゆる形式を扱わねばならず、どれかを黙って読み違えます。
- **`sub` はカスタマイズできます。**
  - リポジトリは、`include_claim_keys` という配列で、subject を構成するクレームを再定義できます。
  - organization が提供できるのはテンプレートだけです。すでに OIDC を使っているリポジトリがオプトインしないかぎり、organization のテンプレートはそのリポジトリに影響しません。
  - 権限は organization ではなく、リポジトリの側にあります。したがって `sub` の内容は、serve が前提にしてよいものではありません。

完全一致は、前方一致も排除します。ここでの典型的な失敗が前方一致です。`repo:acme/app` は `repo:acme/app-evil` にも前方一致するため、部分一致の判定はオペレーターが列挙していないリポジトリを通してしまいます。

**リポジトリは、信頼境界のすべてではありません。** 列挙されたリポジトリにワークフローの変更をマージできる人は、誰でも、そこからトークンを発行させられます。つまり `allowedRepositories` だけでは、「そのリポジトリのワークフローを書ける人は、この org として dispatch できる」という意味になります。

より厳しい境界が必要なデプロイは、トークンがすでに運んでいるクレームでさらに絞ります。`environment`（GitHub の Environment は、ジョブの実行前にレビュアーを要求できます）、`ref`、`job_workflow_ref` です。これらは**項目ごとに**設定します。org 全体にはかけません。

- `allowedRepositories` の各項目は、素の `"<owner>/<repo>"` という文字列か、オブジェクトのどちらかです。オブジェクトは、その名前に加えて独自の `environment`／`ref`／`job_workflow_ref` の境界を運びます。
- そのため、ある org が GitHub の Environment 配下で動くリポジトリと、そうでないリポジトリを並べて列挙できます。境界のない項目を置くためだけに別の org を用意する必要がありません。
- `environment` は*条件つきの*クレームです。GitHub は、ジョブが environment を参照するときにだけ、このクレームを発行します。そのため、`environment` の境界を設定すると、クレームの値が異なるトークンだけでなく、クレームを欠くトークンも拒否します。そうしないと、environment を宣言しないジョブが、この絞り込みをまるごとすり抜けてしまいます。

1つの危険は、コードではなくドキュメントに属します。fork からの pull request は、既定では `id-token: write` を受け取りません。しかし `pull_request_target` のワークフローは base リポジトリの文脈で動くため、受け取れます。

同じ危険は、fork 由来の pull request へ書き込み用のトークンを送るリポジトリ設定にもあります。この設定は、素の fork pull request でも `id-token: write` を再び有効にします。

`pull_request_target` を使うパイプライン、またはこの設定を有効にしたパイプラインを持つリポジトリを列挙するデプロイは、environment で絞るべきです。外部の貢献者が影響を与えた実行から、トークンを発行させないためです。

### 単位3：人間のロールではなく、機械の主体として扱う

交換が発行する機械セッションは、OAuth のセッションと共有トークンに並ぶ**3つ目の呼び出し元の形**です。セッションと同じく身元を運びます。しかも人ではないため、viewer / editor / admin というどの序列でも表せません。何を許すかは、エンドポイントの明示的な許可リストで決めます。

| 許可 | 拒否 |
|---|---|
| `POST /api/artifacts/{config,scenarios,binary}` | `POST /api/config`、`POST /api/compose`（org のアクティブな設定の差し替え。パイプラインが代わりに使うものは後述） |
| `GET /api/artifacts/exists` | `GET /api/config/content`（config の本文はシークレットを埋め込み得ます） |
| `POST /api/run` と、自分の org の run の読み取り | `POST /api/apikey`、`POST /api/claudecodetoken`（オペレーターのシークレット） |
| | `/api/orgs*`（誰がサインインし書き込めるか） |

**アーティファクトの公開は、パイプラインに必要なことの半分であり、その残り半分は `POST /api/compose` ではありません。** 実際のパイプラインは、ビルドと一緒に config とシナリオツリーをアップロードし、その3つに対してシナリオを名指して実行します。そのため、上記の3つのアップロード経路だけでは、有効化する手段のないバイトを抱えたままになります。`bind_artifact` は、それ単体では何もバインドしません。

とはいえ、`POST /api/compose` でその穴を塞ぐのは誤りです。この経路は、org の**アクティブな**設定をバインドします。さらに `remember_org_config_source` を通じて、org の記憶された設定も書き込みます。これには2つの問題があります。

- メンバーの次のセッションは、最後にパイプラインが compose したものを引き継いでしまいます。
- 同じリポジトリの同時実行ジョブは、それぞれが求めたものを実行するのではなく、1つのバインディングを取り合うことになります。

どちらも、姉妹提案であるジョブ単位の binary 上書きが、dispatch のたびに差し替えを求めることを拒否した理由そのものです。binary に当てはまるのと同じように、3つ組にも当てはまります。

したがって、パイプラインの3つ組は、その姉妹提案が binary を有効化するのと同じ方法で有効化します。**dispatch 時に名指す、ジョブ単位のアーティファクト参照**であり、run のためにマテリアライズされ、何もバインドしません。

`materialize_composition` は、`state.bind_upload` や `remember_org_config_source` とは独立に、3つ組を content-addressed なツリーへ組み立てます。そのため、ジョブ単位の3つ組に、新しい compose の仕組みもバインディングのスロットも要りません。これは、機械セッションが後述のセッションなしの `binding_for` の経路を保てる理由でもあります。

本項目は、そのフィールドを規定しません。姉妹提案が `binaryArtifact` の上書きを、binary のレッグから3つ組へ広げることに依存します。この拡張こそ、姉妹提案の「検討した代替案」が却下しているものです。その根拠は、CI が binary だけを変えて config とシナリオは固定するという前提です。本項目の動機となるケースは、その前提を満たしません。

`POST /api/oidc/exchange` 自体は、この許可リストの外にあります。入口そのものであるため、事前の serve の資格情報を必要とせず、検証可能な OIDC トークンだけを求めます。上の表を入口のゲートだと読んではいけません。この表が決めるのは、すでに発行された機械セッションが何をできるかであり、トークンがセッションになる経路ではありません。

そこへ実際に到達するには、別の変更が要ります。`gate.is_open` の POST の分岐（`bajutsu/serve/gate.py`）は、今日、`path == _LOGIN_PATH` そのものです。そのため、認証前のリクエストは他のどの経路でも、検証が走る前に 401 で拒否されます。

単位3は、`POST /api/oidc/exchange` をその分岐へ加えます。OIDC を設定したときにだけ有効にし、想定利用者を設定していないデプロイでは経路を閉じたままにします。上と同じ、閉じる方向の失敗規則です。

**機械セッションが運ぶ身元。** 機械セッションは、取り消し可能であるために、`None` ではない身元を必ず運びます。`revoke_identities` は身元の文字列で取り消しを行います。そのdocstringは、身元を運ばないセッションには一切触れないと述べています。

GitHub のログイン名と衝突しない予約形式を与えます。ログイン名は `/` を含めないため、`repo:<owner>/<repo>` とします（`users.id` ではありません。下の監査エントリを参照してください）。

- `revoke_identities` の今日の唯一の呼び出し元は、org の廃止です。単位3は、運用者が org そのものを廃止せずに、あるリポジトリの発行済み機械セッションだけを取り消せるよう、取り消しの経路を公開する責務を負います。
- 取り消しの粒度は、ジョブ単位ではなくリポジトリ単位です。あるリポジトリが発行するセッションはすべて同じ身元を共有します。そのため、取り消しはそのリポジトリの実行中のパイプラインもまとめて終了させます。この共有される身元こそが、単位2の運用者の責務が前提としているものです。
- 同じ理由で、org の廃止そのものにも手を入れる必要があります。`delete_org` が取り消すのは、`list_org_user_ids` が返す名簿です。これは `users` テーブルを読みます。機械にはそこに行がありません。
- そのため、org を廃止するときは、その org に紐づく機械セッションも取り消さなければなりません。さもないと、機械セッションは有効期限が切れるまで、廃止されたテナントとして振る舞い続けます。BE-0375 がこの取り消しを追加して塞いだ、まさにその漏れです。

run の読み取りは、**org** 単位であり、行為者ごとではありません。読み取りの経路は `org_id` を引数に取り、`created_by` では絞り込みません。`created_by` は、`runs` にすでに存在する、`users.id` への null を許す foreign key です（`bajutsu/serve/server/models/run.py`）。機械は、自分が始めた run だけでなく、所属 org 全体の run を読み取ります。

`bajutsu/serve/jobs.py` は、行為者が実在する user であるときにだけ `created_by` を書き込みます。トークンや CI の run には行為者がいないと、そのコード自身のコメントが述べています。そのため、機械が dispatch した run は、この列を null のままにして済みます。合成の `users` 行がなければ満たせなかったはずの、2つ目の foreign key です。それを超える、run 単位の帰属づけは、また別の変更になります。

この許可リストが、パイプラインへ渡して安全だと言える根拠です。開くエンドポイントのうち4つは今日 admin です。機械に admin という**序列**を与えると、設定の差し替えとシークレットの読み出しが付いてきます。エンドポイントを名指す方式なら、機械の手が届く範囲は、アーティファクトの公開と run の開始にとどまります。これはパイプラインが必要とするものの全体です。

`required_role` は、人間が必要とするものを決め続けます。この許可リストは、機械の主体に対してのみ参照され、他では参照されません。そのため、どちらのゲートも他方を広げることはありません。

この許可リストは、機械の主体に対して無条件に適用します。データベースの配線とは関係ありません。`forbidden_for_role` は、`state.repository` が `None` のとき許可を返します（`bajutsu/serve/authz.py` の「DB-less = full access」）。同じ接続点に許可リストを置いても、データベースの有無で条件分けすれば、この開いた振る舞いをそのまま受け継いでしまいます。

そもそも、データベースを持たないデプロイに機械セッションは存在し得ません。単位1の交換が拒否するからです。そのため、これは生きた経路ではなく、二重の安全策です。

両方のバックエンドが守る共有の方針は、`handler.py` の `_gate` だけではなく、`bajutsu/serve/gate.py`（BE-0253）にあります。stdlib の handler と FastAPI のアプリが、セキュリティ上の姿勢で食い違わないようにするための場所です。このモジュール自身の docstring は、以前の重複を「セキュリティ上の食い違いへ静かに至る道筋であり、それを検知する仕組みは何もない」と呼んでいます。`bajutsu/serve/server/app.py` は `handler.py` を1行ずつなぞっています。

単位3の機械セッションの許可リストは、`gate.py` がすでに守っている人間のロールゲートと並んで、そこに実装します。そのため、両方のバックエンドが同じ場所から機械の主体を得られます。単位1のトークン検証は、専用の遅延 import モジュール（前述）に置きます。交換エンドポイントだけがそこへ到達し、`gate.py` 自身は到達しません。

機械セッションは、人間のセッションとまったく同じ形で認証されます。有効なセッション Cookie であり、`gate.is_authorized` はすでに、そのどれに対しても真を返します。新しい分岐は `forbidden_for_role` の隣に置き、セッションの記録が運ぶ principal kind（単位1）で分けます。

- `forbidden_for_role` は、機械の主体に対して走らせてはいけません。身元不明のユーザーはデフォルトで viewer となり、viewer は `POST /api/run` を拒否するからです。
- 代わりに、エンドポイントの許可リストが決めます。
- 人間のセッションが決してそこへ到達しないようにしているのも、この principal kind です。

**org は機械セッションとともに運ばれ、`org_of` は経由しません。** 今日、`start_*` で始まる各エンドポイントは、`state.org_of(actor)` を通じて org を決めます。これは、行為者について永続化された user の行を読みます。許可リストが開くエンドポイントも同じです。

- `bind_artifact` と `artifact_exists`（`bajutsu/serve/operations/upload.py`）。
- `bajutsu/serve/operations/reads.py` の run 読み取りの経路。

どれも `org = state.org_of(actor)` を取り、object-store のキー、ローカルキャッシュのパス、監査の行、存在確認の probe に使います。

機械にはその行がないため、`org_of` は `allowedRepositories` にかかわらず、これらすべての呼び出しで `default` を答えてしまいます。マルチ org のデプロイでは、まさに許可リストが最初に開くこれらの経路が、テナントをまたぐ穴になります。そもそも `Repository.get_run(run_id)` は org 単位ではありません。`session.get(Run, run_id)` に `org_id` はなく、これを土台にした run 単位の読み取りは、それ自体のテナント境界を持ちません。

代わりに、許可リストにあるすべての操作は、交換（単位1）で一度解決した org を機械セッションから読みます。

機械セッションはまた、セッションごとのスロットを取りません。セッションを渡さずに `binding_for` を呼んで、設定を解決します。これは、CI からのリクエストについて `binding_for` がすでに文書化している、デプロイのフォールバックを読み、復元は行わない経路そのものです。

BE-0393 の単位2は、このスロットを保持するマップをメンバー向けに見積もっています（`MAX_SESSION_BINDINGS`、「1プロセスで同時に数千人のメンバー」）。その復元は Git または bundle の取得で、セッションごとに一度支払うものです。ジョブごとに1つのセッションを発行すると、この取得をジョブごとに支払い、さらにメンバーのスロットを追い出してしまいます。

合成の `users` 行を作らない理由も、ここで述べます。そのような行はロールの列も持ち、上と同じ viewer デフォルトの分岐を再び開いてしまいます。しかも、その機械は `/api/orgs` が開示する名簿に載ってしまいます。

同じ理由で、監査の記録はリポジトリを*行為者*としては受け取りません。`actor_id` は、`users.id` への null を許す foreign key です（`bajutsu/serve/server/models/audit_log.py`）。この制約を合成の行で満たそうとすれば、費用は先ほどと同じです。

`jobs.py` は、行為者に user の行があるかを確認してから `created_by` を書きます。`_record_audit` は違い、行為者をそのまま `actor_id` へ渡します。そこで単位3は、この接続点を変更し、機械の主体については、`users` に裏づけのないログイン名ではなく null を書くようにします。

エントリ自体は残します。`_record_audit` は、行為者が偽値なら早期に返すため（`bajutsu/serve/authz.py:408`）、単に None を渡すだけでは、列が null になるのではなく行そのものが記録されません。リポジトリは、監査エントリ自身の detail ペイロードに記録します。こうして、「どのパイプラインがこの run を始めたのか」を、偽のユーザー行なしに答えられます。

### 単位4：テストとドキュメント

交換エンドポイントの検証は、JWKS とローカルで署名したトークンを注入することで、ネットワークも Simulator も使わずにカバーします。

- 設定された鍵で署名され、設定された `aud` を持ち、列挙されたリポジトリから来たトークンは、そのリポジトリの org として振る舞う機械セッションに交換されます。
- `aud` がそれ以外のトークンは、交換の場で拒否されます。列挙されたリポジトリについて他の点では正当なトークンも同様です。
- 列挙されていないリポジトリのトークンは、403 で拒否されます。`repository` が列挙された項目と前方一致するだけのトークンも拒否されます。
- 2つの org に列挙されたリポジトリは、リクエストが名指した org へ交換されます。1つの共有パイプライン用リポジトリが、両方の org で使えます。
- トークンのリポジトリを `allowedRepositories` に列挙していない org を名指したリクエストは、拒否されます。org の名指しは選ぶだけで、権限を与えるものではありません。
- org を名指さない交換のリクエストは、推測せずに拒否されます。
- immutable な subject 形式のトークンは、`repository` クレームで認可されます。2つの `sub` の形は同じように振る舞います。
- 次のものは、古い鍵セットを信頼せず、それぞれ拒否されます。
  - 期限切れのトークン。
  - 更新しても JWKS に `kid` がないままのトークン。
  - 署名が壊れたトークン。
  - JWKS に到達できず、キャッシュも失効しているもの。
- ヘッダーが `none` を名指すトークンと、RSA の公開鍵バイト列で署名した HS256 のトークンは、どちらも拒否されます。アルゴリズムは設定から決まり、トークンからは決まりません。
- 再送の防止は、次の4点で成り立ちます。
  - 同じトークンを2回交換すると、1回目は受け入れられます。使い捨てはレプリカをまたいで成り立ちます。1回目のレプリカがすでに使い切った `jti` は、2回目のレプリカでも拒否されます。同じレプリカへの再提示だけではありません。
  - serve 側で定めた最大経過時間を超えたトークンは、自身の `exp` がまだ未来であっても拒否されます。
  - `jti` を持たないトークンは、キャッシュを素通りさせず、そのまま拒否されます。
  - `iat` を持たないトークンも、経過時間の起点を持てないため、そのまま拒否されます。
- 次の2種類のデプロイは、他の点では正当な OIDC トークンを、交換の場で拒否します。
  - 想定利用者を設定していないデプロイ。トークンが運ぶ想定利用者をそのまま受け入れることはありません。
  - セッションごとの有効期限を保証できないセッションストア（`InMemorySessionStore` を含む）を使うデプロイ。

  発行された機械セッションの有効期間は、提示されたトークン自身の `exp` を超えません。
- `import bajutsu.serve` は、`joserfc` を一切引き込みません。import guard の `FORBIDDEN` 集合が挙げる、他の server 専用の依存を引き込まないのと同じです。
- 機械セッションは、許可リスト上のすべてのエンドポイントへ到達します。`POST /api/config`、`POST /api/compose`、`GET /api/config/content`、オペレーターのシークレットのエンドポイントでは拒否されます。
  - データベースが配線されているかどうかで、この振る舞いは変わりません。
  - `POST /api/compose` が拒否されても、org のアクティブなバインディングと記憶された設定はそのまま残ります。メンバーの次のセッションが、パイプラインから何かを引き継ぐことはありません。
  - `POST /api/oidc/exchange` 自体は、事前のセッションもトークンも必要とせず、検証可能な OIDC トークンだけで到達できます。
- 両方のバックエンド（`handler.py` と `server/app.py`）は、どちらも `gate.py` を経由するため、機械セッションを同じように扱います。
- 境界の対象は、`environment`、`ref`、`job_workflow_ref` です。これらのいずれかを設定したデプロイは、対応するクレームが異なる実行から来た、他の点では正当なトークンを拒否します。`environment` については、クレームがないトークンも同様に拒否します。
- `environment` の境界を持つリポジトリと、境界を持たないリポジトリを並べて列挙した org は、そのどちらも交換できます。境界が効くのはその項目だけであり、org 全体には及びません。
- 機械のアップロード（`bind_artifact`）と存在確認（`artifact_exists`）は、`default` ではなく、そのリポジトリが列挙された org を解決します。マルチ org のデプロイでも、機械が dispatch した run でも、run の読み取りでも同様です。
- org を廃止すると、`list_org_user_ids` が返すメンバーのセッションだけでなく、その org の発行済み機械セッションも取り消されます。
- 機械が dispatch した run の監査記録には、detail ペイロードにリポジトリ名が残ります。`actor_id` には、`users` に裏づけのないログイン名ではなく null が書かれます。`bind_artifact` も監査を残すため、run だけでなくアーティファクトのアップロードでも同様です。

`docs/self-hosting.md` とその日本語ミラーに、次を扱う節を追加します。

- ワークフローの権限と2つの環境変数。
- オペレーターが設定すべき `aud`。省略すると OIDC の呼び出し形態そのものを無効にすることも含みます。
- 交換エンドポイントと、それが発行する機械セッション。セッションの TTL（有効期間）が、提示されたトークン自身の `exp` を超えないことも含みます。
- `allowedRepositories` の形と、交換のリクエストが照合先の org を名指すこと。
- 設定が効力を持つのは交換のときだけであるため、運用者が負う責務。リポジトリがリネーム、譲渡、削除されたとき、または絞り込みを強化したときに、項目を更新し、そのために発行された機械セッションを取り消します。
- 任意の `environment`／`ref`／`job_workflow_ref` による絞り込み。`environment` の境界は、クレームがない場合も、異なる場合と同様に拒否します。
- `pull_request_target` と、fork 由来の pull request への書き込みトークンの危険。
- パイプラインの後続の呼び出しは、すべて OIDC トークン自体ではなく、発行されたセッションを提示すること。

動作するワークフローの断片も、そこに置きます。GitHub 側の設定は2行であり、残りは serve 側の設定だからです。

## 検討した代替案

| 代替案 | 採用しなかった理由 |
|---|---|
| 毎回のリクエストで OIDC トークンを検証する方式（一度だけ交換する代わりに） | 対象のパイプラインは複数のエンドポイントを順に呼ぶため、使い捨ての `jti` では2回目以降の呼び出しをすべて拒否してしまいます。使い捨てをやめて再送を許せば、歯止めは経過時間の上限だけになります。リクエストごとの検証では、JWKS の取得と JWT の解析も、認証前に1つではなくすべての経路で到達可能なままになります。serve が発行していない資格情報を取り消すこともできません。 |
| 設定パネルから org ごとに長期の CI トークンを発行する | より単純ですが、本項目が避けようとしている秘密を再導入します。すべてのパイプラインに保存し、手で回転させ、ログから漏れ得るトークンです。しかも、どのリポジトリによる操作なのかを言えません。要点は保存場所ではなく、身元の欠落です。 |
| BE-0313 が絞った共有トークンを CI に再利用する | 意図的な決定を巻き戻します。共有トークンは身元を持たず全権であるため、worker 以外のエンドポイントに戻すと、config を差し替えシークレットを読む能力をすべてのパイプラインへ渡すことになります。 |
| CI の身元に admin ロールを与える | CI が必要とする5つのエンドポイントのうち4つが今日 admin なので、序列としては合っているように見えます。しかし、それは config の差し替え、`GET /api/config/content`、オペレーターのシークレットのエンドポイントを一緒に連れてきます。どれもパイプラインには不要で、しかもすべて手に入ってしまいます。 |
| `sub` クレームで認可する | subject の形式は、新しいリポジトリについてはすでに immutable な ID へ変わっています。しかもリポジトリ単位でカスタマイズできるため、その形は serve が前提にしてよいものではありません。前方一致の判定は、列挙した名前を単に延長したリポジトリも通します。個別のクレームなら、どちらの問題もなく同じことを言えます。 |
| `repository` の代わりに、immutable な数値クレーム（`repository_id`／`repository_owner_id`）で認可する | これらのクレームは immutable で、subject のカスタマイズの影響も受けないため、名前の再利用という露出を根本から閉じられます。代わりに、リポジトリ名だけでは読み書きできない設定になります。項目を追加するには参照が要り、監査でもその項目がどのリポジトリを指すのか手がかりがありません。名前による形は、この読みやすさのために残しました。上で述べた運用者の責務は、その代償です。 |
| OIDC ではなく GitHub App のインストールトークンを使う | Bajutsu はプライベートリポジトリの config ソースのために App JWT への署名をすでに行っており（BE-0224）、仕組みには馴染みがあります。しかし App の登録と、デプロイへの秘密鍵の配布が必要です。得られるトークンが認証するのはパイプラインではなく App であり、粒度の粗い身元を持つ共有の秘密に戻ります。 |
| 最初から任意の発行者の OIDC を受け入れる | GitLab、Buildkite、CircleCI も OIDC トークンを発行するため、org 単位で発行者を設定できれば一般化できます。ただしクレーム名が提供者ごとに異なり、汎用の対応づけは目の前の課題より大きな設計になります。まず GitHub Actions に絞れば、発行者は設定可能なまま残り、対応づけの設計は先に延ばせます。 |
