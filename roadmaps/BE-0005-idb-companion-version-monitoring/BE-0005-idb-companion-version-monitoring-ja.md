## はじめに

idb 自体のメンテナンス頻度と、最新ランタイムとの互換に追従します。CI で idb のバージョンを固定し、監視します。

## 動機

現状、実機で動く backend は idb のみです（`bajutsu/backends.py`）。そのため、実機経路の全体が、単一の外部依存の挙動の上に乗っています。外部依存とは、`idb` Python クライアントと `idb_companion` バイナリです。どちらも Bajutsu とは独立に、それぞれのメンテナンス頻度でリリースされます。ここから 2 種類の破綻が生じます。

- **駆動できないランタイム**：新しい iOS や Xcode のリリースが、古い `idb_companion` では駆動できないランタイムを載せてくることがあります。Bajutsu 側は何も変えていないのに、昨日まで green だった CI が今日は「no available actuator」になります。
- **describe-all スキーマの変化**：`idb_companion` のアップグレードが、`ui describe-all` の JSON スキーマを静かに変えることがあります。`parse_describe_all` が依存するキー名（`AXLabel`、`AXValue`、`AXUniqueId` など）が変われば、要素正規化は気づかぬうちに劣化します。

DESIGN §11 はすでに、「idb 自体のメンテナンス頻度と最新ランタイムとの互換」を未解決のリスクとして挙げています。`docs/drivers.md` は、describe-all のキー名が特定の fb-idb バージョンに対して実機検証されていると注記し、idb が変わったら再確認すべきだとしています。今日、その再確認は手作業の手順であり、忘れやすいものです。

本提案は、バージョンを「たまたまそのマシンに入っているもの」ではなく、追跡可能で観測可能な量にします。これにより CI は、互換性の破綻をそれが起きた当日に捕捉できます。提案がなければ、破綻は後になって、紛らわしい run 失敗として現れます。

## 詳細設計

idb のバージョンを、暗黙の前提ではなく、run の明示的で記録される入力にします。

- **バージョンを manifest に記録する。** 各 run は、`idb_companion` のバージョンと `idb` クライアントのバージョンを取得します。両方を、既存の run メタデータと並べて `manifest.json` に書き込みます。これにより、任意の成果物セットがどの idb で生成されたかを示せます。バージョンは来歴であってゲートではなく、合否には一切影響しません。Tier-2 の run/CI ゲートは、決定的かつ LLM フリーのままです。
- **環境ごとに期待バージョンを宣言する。** 検証対象として固定したい、既知の good なバージョン範囲を config に置きます。この範囲は、アプリ単位ではなく環境単位の事柄です。そのため、`apps.<name>` の下ではなく、他の backend 設定の隣に置きます。どのアプリを対象にしても pin は同じであり、app-agnostic の原則を保ちます。

`doctor` は範囲を読み、インストール済みバージョンを期待値と照合して報告します。既存の事前チェック面に、「idb_companion 1.2.3 がインストール済み、期待は >= 1.2.x」のような明確な行が加わり、下流での失敗にはなりません。
- **CI 専用の監視ジョブ。** スケジュール実行ジョブが、利用可能な最新の `idb_companion` と現行の Simulator ランタイムに対して、実機スモーク経路を走らせます。スキーマや挙動がずれたら、ジョブは大きく失敗します。このジョブは、高速かつ Simulator 不要を保つべき PR 単位のゲートとは別です。

ジョブは、`docs/drivers.md` が述べる手作業の再確認を自動化します。必要なバージョン更新は、その場限りの発見ではなく、こちらが制御する頻度で CI シグナルとして表面化します。
- **バージョン文字列だけでなくスキーマ検証も。** スモーク経路は、`describe-all` が `Element` 正規化に必要なフィールドを依然として返すことを検証します。バージョン互換の体裁は保ったまま JSON の形だけを変えるアップグレードも、捕捉できます。保証の対象は、単なる数値ではなく挙動です。

ここには固定 sleep も非決定的な選択も持ち込みません。監視ジョブは既存の条件待機済みスモークシナリオを再利用し、バージョン pin は静的な比較です。

## 検討した代替案

- **idb を 1 つの厳密なバージョンに固定して動かさない。** 単一のバージョンへの固定は再現性がありますが、Bajutsu を iOS と Xcode のリリース列車の後ろに凍結します。新しい `idb_companion` でしか駆動できない新しい Simulator ランタイムは、到達不能になります。私たちはこの頻度から降りるのではなく、追跡したいと考えます。そのため、ハードな凍結より監視付きの範囲を選びます。
- **PR 単位の e2e ワークフローだけに頼る。** 既存の実機 e2e run は、すでに idb を動かしています。ただし、runner にたまたま入っている `idb_companion` を使い、しかも PR がその経路に触れたときだけ走ります。上流の idb やランタイムのリリースだけに起因するずれは、誰かがそうした PR を開くまで気づかれません。スケジュール監視ジョブは、このチェックを PR 活動から切り離します。
- **スキーマ破綻を実行時に検出して適応する。** `parse_describe_all` で複数の describe-all スキーマを許容すると、問題を表面化させるどころか隠すことになります。決定性が要となる正規化経路にも、分岐が増えます。変更を CI で捕捉してパーサを意図的に更新するほうが、このコードを単一目的かつレビュー済みに保てます。
