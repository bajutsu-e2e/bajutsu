## はじめに

> **却下。この項目の前提はもう成り立たず、[BE-0518](../BE-0518-control-plane-replica-topology/BE-0518-control-plane-replica-topology-ja.md) が置き換えます。**
> この項目は、ワーカーがジョブの終了後に結果を送ると想定していました。その前提では、ログのストリームは
> レプリカをまたぎません。[BE-0449](../BE-0449-server-runs-no-jobs/BE-0449-server-runs-no-jobs-ja.md) がこの動作を変えました。現在のワーカーは、ジョブの実行中にログ行を送ります。
> そのため、レプリカには実行中のログを運ぶ共有の Redis のバスが要ります。この設計には、そのバスがありません。
> この項目が計画したアプリ側の作業も、大半はほかの項目ですでに入っています。残る作業は範囲が異なり、より小さく、
> BE-0518 が現在のコードに基づいてその範囲を定めます。待っても設計が成り立つ時期は来ないので、`Deferred`
> ではなく `Rejected` を選びます。

セルフホストの制御プレーンは、ジョブをキューに積み、Web UI を配信する `bajutsu serve` のアプリです。
制御プレーンのセルフホストは [BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md) が扱います。`deploy/self-host/` の Docker Compose スタックは、制御プレーンを
1つのアプリコンテナとして動かしています。処理は軽量な HTTP なので、水平にスケールできます。

この提案は、**ロードバランサの配下で N 個のアプリレプリカ**を動かします。制御プレーンは、レプリカを1つ失っても
止まらなくなり、より多くの同時利用者をさばけるようになります。プルベースのジョブ分配は変えません。
BE-0016 が「単一ノードをプールへ育てる」作業の一部として挙げた項目です。

## 動機

Mac プールを増やしても、制御プレーンは1つのコンテナのままです。その1つのプロセスが容量の上限になります。
ブラウザの要求、ワーカーのリース呼び出し、実行履歴の読み取りがすべてそこを通るからです。
可用性のリスクでもあります。プロセスが再起動すると、UI 全体が短時間使えなくなります。

制御プレーンは、共有のデータベースとオブジェクトストアの上に載るステートレスな HTTP です。レプリカを並べれば、
両方の制約がなくなります。作業の中身は、スティッキーなルーティングに頼らず、長く開いた接続を失わずに、
レプリカを正しく動かすことです。あわせて、ロードバランサの設定を文書化します。

## 詳細設計

この設計は、スタックについての2つの事実に立脚します。ログイン状態は **Postgres** にあります。[BE-0106](../BE-0106-post-completion-worker-model/BE-0106-post-completion-worker-model-ja.md) が
その保存先をデータベースへ移したからです。ワーカーは完了後に結果を送るので、実行中のログを別のレプリカへ
届ける必要はありません。作業分解は次のとおりです。

**1. スティッキーセッションのないステートレスなレプリカ。** 任意のレプリカが任意の要求を処理できなければ
なりません。署名付き Cookie が Postgres の行を指すので、一方のレプリカでログインした要求は他方でも通ります。
実機で確認します。一方のレプリカでログインし、もう一方で実行履歴を読みます。

**2. ロードバランサの方針。** レプリカの前段には Caddy か HAProxy を置き、ラウンドロビンではなく
**最小接続数**を使います。イベントストリームは長く開いたままです。ラウンドロビンでは、開いたストリームを
多く抱えたレプリカへ負荷が偏ります。Transport Layer Security（TLS）は、ロードバランサか既存の `caddy`
プロファイルで終端します。

**3. レプリカをまたぐワーカーの経路。** `bajutsu worker` は、任意のレプリカへ `POST /api/worker/lease`
を送れます。結果全体も、任意のレプリカの `/api/worker/result` へ送れます。ワーカーとリースを処理した
レプリカのあいだに結び付きはありません。ブラウザは完了した実行を共有のストアから読むので、ブラウザにも
結び付きは要りません。

**4. N レプリカのための compose 配線。** `deploy/self-host/` に、スケール係数とロードバランサの設定を加えます。
Postgres と MinIO は共有のまま変えません。運用者の手順を文書化します。

**検証。** このティアはデプロイと運用の作業です。`make check` のゲートは Docker も複数コンテナの構成も
動かさないので、このティアを検証できません。デプロイ上で、次の表の手順を手作業で確かめます。

| 手順 | 確かめること |
|---|---|
| 2つのアプリレプリカを立ち上げる | 両方が要求に応答すること |
| 一方のレプリカでログインする | 他方が次の要求を受け付けること |
| 一方のレプリカから実行をリースする | その結果を他方から読めること |

`bajutsu/serve/` に入るステートレス性の小さな補助には、ユニットテストを付けます。構成そのものには、ゲートの契約が
ありません。

## 検討した代替案

| 代替案 | 判断 | 理由 |
|---|---|---|
| ロードバランサでのスティッキーセッション | 採らない | レプリカごとの結び付きが戻り、再起動時に負荷が偏るから |
| ラウンドロビンの負荷分散 | 最小接続数を採る | 長く開いたストリームが一部のレプリカへ集まるから |
| 単一レプリカの垂直スケール | 出発点に限る | 容量の上限と可用性のリスクが残るから |

ログイン状態はすでに Postgres にあるので、スティッキーセッションで得られるものはありません。
