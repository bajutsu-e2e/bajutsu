## はじめに

セルフホストの制御プレーン（[BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md)）は、
現在 `deploy/self-host/` の compose スタックで、**単一**の `bajutsu serve --asgi --backend=server`
アプリコンテナとして動いています。処理は軽量な HTTP なので、水平にスケールできます。

この提案は、**ロードバランサ配下で N 個のアプリレプリカ**を動かす構成を定めます。プルベースのジョブ分配は変えません。
制御プレーンがレプリカ障害に耐え、より多くの同時利用者をさばけるようになります。
BE-0016 の「単一ノードをプールへ育てる」作業から切り出した項目です。

## 動機

Mac プールを増やしても、制御プレーンは1つのコンテナのままです。その単一のアプリプロセスは、容量の上限です。
すべてのブラウザセッション、ワーカーのリース呼び出し、実行履歴の読み取りがそこを通るためです。
可用性のリスクでもあります。再起動すると、UI 全体が短時間使えなくなります。

制御プレーンは、共有のデータベースとオブジェクトストアの上に載るステートレスな HTTP です。
複製することが、両方の制約を取り除く自然な方法です。作業は、その複製を正しくすることです。スティッキーセッションをなくし、長寿命の接続を失わないようにします。
あわせて、この構成が必要とするロードバランサの設定を文書化します。

## 詳細設計

この設計は、スタックについてすでに成り立っている2つの事実に立脚します。セッションは **Postgres** に存在します
（BE-0106 がセッションストアをデータベースへ畳み込みました）。ワーカーモデルは**完了後**であるため、
実行中のログストリームをレプリカ間へ分配する必要がありません。作業分解は次のとおりです。

1. **ステートレスなレプリカ、スティッキーセッションなし。** どのレプリカも、どの要求も処理できなければなりません。
   認証は署名付き Cookie で、セッションは Postgres に存在します。そのため、あるレプリカで認証された要求は、
   スティッキーなルーティングなしに別のレプリカでも受理されます。これは手動で検証します。
   あるレプリカでログインし、別のレプリカで実行履歴を読みます。
2. **ロードバランサの方針。** レプリカの前段には Caddy か HAProxy を置き、ラウンドロビンではなく**最小接続数**を使います。
   Server-Sent Events（SSE）の接続は長寿命です。ラウンドロビンだと、開いたストリームを多く抱えたレプリカへ負荷が偏ります。
   TLS はロードバランサ（または既存の `caddy` プロファイル）で終端します。
3. **レプリカをまたぐワーカーの経路。** ワーカーモデルは完了後です。そのため、`bajutsu worker` はどのレプリカからでも
   `POST /api/worker/lease` でき、結果全体をどのレプリカの `/api/worker/result` へでも送れます。
   ワーカーと、そのリースを処理したレプリカのあいだに、実行ごとの結び付きはありません。
   ブラウザは完了した実行を共有のデータベースとオブジェクトストアから読むため、ブラウザにも結び付きは不要です。
4. **N レプリカのための compose 配線。** `deploy/self-host/` を拡張し、ロードバランサ配下で N 個のアプリレプリカを動かします
   （スケール係数とロードバランサ設定）。ステートフルなサービス（Postgres、MinIO）は変えず、共有します。
   運用者の手順を文書化します。

**検証。** このティアはデプロイと運用の作業であり、Linux だけの `make check` ゲートでは動かせません
（Docker も複数コンテナの構成もないためです）。デプロイ上で手動で検証します。

- 2つのアプリレプリカを立ち上げます。
- 一方のレプリカでのログインが、他方のレプリカが処理する要求で受理されることを確認します。
- 一方のレプリカからリースした実行が完了し、その結果が他方を通じて読めることを確認します。

`bajutsu/serve/` に入るステートレス性の小さな補助（たとえばプロセス内のセッション状態を持たないことの表明）には、
単体テストを残します。構成そのものには、ゲートの契約がありません。

## 検討した代替案

- **スティッキーセッション（ロードバランサでのセッションアフィニティ）。** 却下します。レプリカごとの状態の結び付きを復活させ、
  レプリカ再起動時に負荷を偏らせます。セッションが Postgres に存在すれば、不要でもあります。
  ステートレスなレプリカのほうが、単純で堅牢です。
- **ラウンドロビンの負荷分散。** 最小接続数を採り、却下します。SSE のストリームは長寿命なので、
  ラウンドロビンでは、開いた接続が一部のレプリカへ徐々に集中します。最小接続数は、実際の負荷を追跡します。
- **単一レプリカのまま垂直方向にスケールする。** 出発点としては受け入れられますが、最終形としては却下します。
  1つのアプリコンテナは、可用性の単一障害点であり、容量の上限でもあります。水平方向のレプリカが、それを取り除きます。
