## はじめに

変更が実際に影響しうる End-to-End（E2E）のジョブだけを実行します。E2E の各レーンは、機能別と次元別のジョブ群を走らせます。iOS は Simulator 上で、Android はハードウェアアクセラレーション付きのエミュレータ上で、Web はヘッドレスブラウザ上で実行します。これらのジョブの一部は、自分が行使するシナリオを宣言しています。

現状では、レーンが関連ありと判定した変更は、レーン内のすべてのジョブを起動します。変更が触れてもいないシナリオのジョブも含まれます。本項目は、安全と証明できる唯一の場面について、この起動範囲を絞ります。その場面とは、変更がシナリオファイルだけにとどまるときです。このとき、変更されたシナリオを宣言するジョブだけを実行します。

それ以外のすべての場面は、従来どおりレーン全体を起動します。

- 共有のドライバや runner コードへの変更
- シナリオを宣言しないジョブ
- ジョブをシナリオで対応づけていないレーン

この判定は、`git` の差分と、各ジョブがすでに宣言しているシナリオから決まる決定論的な関数です。大規模言語モデル（LLM）を経路に含まず、いかなる実行の合否判定にも影響しません。判定は、ジョブを絞りすぎる側ではなく、フリート全体へ倒す側に安全側の余裕を取ります。そのため失敗は、マージ前に必ず捕まり、マージ後へ先送りされることはありません。

## 動機

iOS の E2E レーンは、10 個の実機ジョブを走らせます。各ジョブは、Linux の 10 倍に課金される macOS ランナー上で Simulator を起動します。Android のレーンは、ハードウェアアクセラレーション付きのエミュレータ上で 6 個のジョブを走らせます。

各レーンには、必須の集約チェック（`E2E (iOS)`、`E2E (android)`、`E2E (web)`）があります。報告されない必須チェックはマージをブロックするため、レーンをワークフローのトリガーではゲートできません。代わりに、各レーンはすべてのプルリクエストで起動します。[`scripts/e2e_changes.py`](../../scripts/e2e_changes.py) が、レーンごとに、課金対象のジョブをそもそも実行するかどうかを判定します。この判定が現在返すのは、レーン全体に対する 1 つの真偽値です。関連するパスが 1 つでもあれば、レーンのフリート全体が起動します。

この真偽値は、1 つのシナリオにとどまる変更に対して粗すぎます。シナリオファイルは 1 つのシナリオを記述し、他のシナリオからは独立しています。したがって `gestures_multitouch.yaml` を編集しても、`search.yaml` が検証する内容は変わりません。それにもかかわらず iOS レーンでは、`gestures_multitouch.yaml` への変更が、そのファイルを読み込まないジョブも含めて、10 個すべてを起動します。

iOS のジョブは、シナリオと 1 対 1 ではなく、機能と次元で構成されています。

- `actuation` ジョブは、4 つのシナリオを順に走らせます。
- `smoke.yaml` は、2 つのジョブで再利用されます。
- `codegen`、`conformance`、`visual` のジョブは、単一のシナリオファイルを読み込みません。

シナリオのみの変更でも、すべてのジョブの Simulator 起動コストと実行コストを支払います。そのコストの大半は、変更が届かないと証明できるジョブに費やされます。

起動範囲を絞るために必要な情報は、すでにワークフローの中にあります。シナリオを宣言する各ジョブは、自分が実行するシナリオを `scenarios:` 入力で名指ししています。変更されたシナリオファイルから、そのファイルを読み込むジョブへの対応づけは、ワークフローがすでに宣言している内容の参照であり、推論ではありません。レーン全体の真偽値をジョブ単位の判定へ反転させることは、その宣言を読むだけで済み、新たな真実の源を必要としません。

## 詳細設計

提案の抽象度で述べます。変更は、継続的インテグレーション（CI）のフィルタの中で完結します。具体的には、[`scripts/e2e_changes.py`](../../scripts/e2e_changes.py) の `git` 差分分類器と、E2E ワークフローファイルの `if:` ガードです。デバイスには触れず、LLM を呼ばず、合否判定を動かしません。各シナリオの結果は、引き続き決定論的な runner が決めます（プライム原則 1）。アプリ固有の知識は、シナリオファイルだけに置かれたままです（プライム原則 3）。

- **変更の分類（決定論的）**：プルリクエストの変更ファイルを、2 つのクラスへ分けます。フィルタが現在使っているマージベース（three-dot）差分が、これらのファイルをすでに集めています。
  - *共有コード*の変更は、run / codegen / record の表面、ドライバモジュール、アプリのソース、適合性ハーネス、ワークフローファイルに一致します。いずれも `e2e_changes.py` が、すでに関連ありとして列挙しているパスです。
  - *シナリオのみ*の変更は、レーンのシナリオファイルの外側には何も触れません。

  この区別は、フィルタがすでに認識しているパスの分割にすぎません。維持すべき 2 つ目のリストを増やさず、既存の許可リストの上に分類器を 1 つ加えます。

- **ジョブとシナリオの対応表**：各ジョブが宣言するシナリオへの対応表を、レーンのワークフローファイルにすでにある `scenarios:` 入力から読み取って作ります。1 つ以上のシナリオを宣言するジョブは、シナリオ対応づけ済みです。1 つも宣言しないジョブは、そうではありません。`codegen`、`conformance`、`visual` の次元ジョブは、1 つも宣言しません。この対応表は、ワークフロー自身の宣言の参照です。維持すべき 2 つ目の源を必要とせず、各ジョブが実際に走らせる内容から乖離しえません。

- **影響ジョブの選択**：シナリオのみの変更では、そのジョブが宣言するいずれかのシナリオを変更が編集したとき、シナリオ対応づけ済みのジョブを起動します。複数のジョブで再利用されるシナリオは、それを読み込むすべてのジョブを起動します。2 つの iOS ジョブが読み込む `smoke.yaml` は、その両方を起動します。2 つのジョブがそれぞれ `smoke.yaml` を行使するので、両方を起動するのは正しい判断です。影響ジョブの集合を、関連ありの判定に加えて、ワークフローの `GITHUB_OUTPUT` へ出力し、各ジョブが読み取れるようにします。共有コードに及ぶ変更では、従来どおりフリート全体を対象として合図します。

- **ワークフローの配線**：シナリオ対応づけ済みの各ジョブを、「共有コードの変更が起きた、またはこのジョブが影響集合に含まれる」でガードします。共有コードの変更は、従来とまったく同じく、すべてのジョブを起動します。シナリオのみの変更は、変更されたシナリオを読み込むジョブだけを起動します。各実機ジョブは、自分のアプリと runner を個別にビルドします。共有の「一度だけビルドするジョブ」はありません。そのため、絞られた実行は、落としたジョブのビルドと Simulator 起動をまるごと省きます。

- **集約チェックの健全性**：レーンの必須集約チェック（`E2E (iOS)` と、Android と Web の兄弟）は、絞られた実行が大半のジョブをスキップしても、成功を報告しなければなりません。スキップされたジョブは、失敗したジョブではありません。そこで集約チェックは、「すべてのジョブが成功した」ではなく、「失敗したジョブがない」でゲートします。集約チェック自身が、常に走って常に報告するよう、`if: always()` で評価します。これにより、本物のジョブ失敗をすり抜けさせず、絞られた実行でも必須チェックを緑に保ちます。

- **フリート全体へのフォールバック**：特定のシナリオへ帰属させられないものは、レーン全体の起動へフォールバックします。フォールバックする場面は 4 つあります。
  - 共有コードへの変更は、すべてのジョブを起動します。共有のドライバや runner コードは、どのシナリオにも影響しうるからです。
  - シナリオを宣言しない次元ジョブ（`codegen`、`conformance`、`visual`）は、1 つのシナリオではなく、ドライバやハーネスを行使します。そのため、シナリオのみの変更でも起動します。
  - ジョブをシナリオで対応づけていないレーンは、ジョブがシナリオを宣言するまで、従来の全発火を保ちます。Android レーンがこのレーンにあたります。ジョブが `scenarios:` 入力ではなく、次元で作業を選ぶからです。
  - 共有されるシナリオ断片（複数のシナリオが取り込む `setup` ファイル）は、1 つのジョブへ帰属せず、レーン全体を起動します。

  フリート全体へ倒す過剰選択は、安全な方向です。ジョブを無駄にはしますが、変更が壊しえたジョブを取りこぼすことはありません。

- **削減の範囲**：この絞り込みは、ジョブがシナリオで対応づけられている場面に適用されます。今日の iOS レーンでは、シナリオを宣言する 7 つのジョブが該当します。シナリオのみの iOS 変更は、7 つすべてではなく、変更されたシナリオを読み込むシナリオ対応づけ済みのジョブを起動します。`codegen`、`conformance`、`visual` のジョブと Android レーン全体は、従来どおり安全に走り続けます。Web レーンのジョブも、Android と同じくシナリオを宣言しません。Web レーンにも、絞るべきシナリオ対応づけの展開はありません。この利得は限定的ですが、正確です。明らかに無駄なジョブを取り除き、それ以外には手を触れません。

- **アプリソース起点のステップ選択との関係**：姉妹提案の [BE-0321](../BE-0321-test-impact-analysis/BE-0321-test-impact-analysis-ja.md) は、*被テストアプリ*への変更から、影響を受けるシナリオの*ステップ*を選びます。差分が触れる stable id を、各ステップが参照する id と照合する方式です。BE-0321 は、アプリ自身のソースを対象とし、開発者が見直すべきステップを報告します。

  本項目が対象とするのは、Bajutsu の CI 入力です。各ジョブが宣言するシナリオファイルと、共有のドライバ・runner コードを対象とします。そして、どの実機*ジョブ*を実行するかを決めます。両者は、「実行量を減らす」という同じ目標に対する補完的な層です。一方はアプリを読み、もう一方はスイートとそのハーネスを読みます。

- **今後の階層（明記のうえスコープ外）**：シナリオ単位のフィルタリングは、有用な範囲でもっとも粗い切り方です。この切り方が絞るのは、シナリオ対応づけ済みジョブのシナリオファイル変更です。共有コードの変更、次元ジョブ、非対応レーンでは、フリート全体を起動し続けます。こうした場面も絞りうる、より深い階層が 2 つ考えられます。
  - シンボル単位の選択：差分の hunk がどのドライバメソッドに触れたかを、各シナリオが行使するメソッドと照合します。
  - カバレッジベースのテスト影響分析：各シナリオが実行する製品コードの行を、差分が変更する行と照合します。

  どちらの階層も、古びうるマップを必要とします。そのため、マップが変更を帰属させられないとき、フリート全体への保守的なフォールバックを必要とします。これらの階層は、より重く、別個の機能です。本項目は、単独で成立するファイル単位の切り方を出荷し、より深い階層は後続の段階として残します。

## 検討した代替案

- **共有コードの変更を smoke の fast lane へ段階化する。** 共有コードの変更では、プルリクエスト時に smoke シナリオだけを起動し、フリートの残りは main へのマージ時の実行へ先送りします。この案は、シナリオ単位のフィルタリングよりも多く削減できます。デフォルトとしないのは、失敗の検出を、プルリクエストからマージ後へ移すからです。gestures シナリオだけを壊すドライバの変更が、smoke だけのプルリクエストを通過してマージされ、`main` を赤にします。実機レーンは、もともと起動のフレークが起きやすいものです。赤い `main` は、原因の切り分けが高くつき、revert を強います。シナリオ単位の切り方は、すべての失敗を、それを引き起こしたプルリクエストの中にとどめます（fail fast）。段階化はその性質を手放すため、スコープ外とします。

- **ワークフローのトリガーで、各ジョブを `paths:` によりゲートする。** 各ジョブのシナリオパスをジョブ単位のトリガーの下に列挙すれば、フィルタスクリプトは不要になります。しかし、ここでは成立しません。レーンの集約チェックは必須チェックであり、報告されない必須チェックはマージをブロックします。各レーンは、すべてのプルリクエストで起動し、実行の内側で関連性を判定しなければなりません。実行の内側で関連性を判定することが、フィルタスクリプトの存在理由です。

- **カバレッジベースのテスト影響分析を今行う。** 各シナリオが実行する製品コードの行を記録し、差分が変更した行をカバーするジョブだけを起動します。この案は、シナリオ単位のフィルタリングでは絞れない場面も絞れます。共有コードの変更、次元ジョブ、Android レーンです。ただし、カバレッジマップの構築と維持を必要とします。さらに、マップが帰属させられない変更へのフォールバックも必要とします。この機能は、詳細設計で、より重い今後の階層として述べました。本項目は、まずファイル単位の切り方を出荷します。

- **何もしない（現状維持）。** 許容できます。レーン全体の真偽値は、正しく安全で、ただ無駄が多いだけです。シナリオのみのプルリクエストは、あらゆる push のたびに、課金対象の macOS ランナー上で、10 個の iOS ジョブにわたってフリート全体の Simulator 起動コストと実行コストを支払います。そのコストの大半は、変更が届かないシナリオ対応づけ済みジョブに費やされます。ワークフロー自身の `scenarios:` 宣言が、それらのジョブを飛ばすための情報を、すでに持っています。

## 進捗

> 開発の進行に合わせて常に最新の状態に保ってください。チェックリストは *詳細設計* の MECE な
> 作業分解（作業の単位ごとに 1 つ）に対応し、ログには変更内容と時期（古い順）を PR へのリンクと
> ともに記録します。

- [x] 変更の分類 — `scripts/e2e_changes.py` で差分の変更ファイルを共有コードとシナリオのみに分割します。
- [x] ジョブとシナリオの対応表と影響ジョブの選択 — 各ジョブが宣言する `scenarios:` を読み取り、影響ジョブ集合を関連ありの真偽値とともに `GITHUB_OUTPUT` へ出力します。
- [x] ワークフローの配線 — シナリオ対応づけ済みの各ジョブを「共有変更、または 影響集合に含まれる」でガードし、ジョブがスキップされても必須集約チェックを緑に保ちます（`if: always()` と「失敗ジョブなし」）。
- [x] フォールバックと文書化 — 次元ジョブ・非対応レーン（Android）・共有断片ではフリート全体へフォールバックし、安全モデルと限定的な範囲を文書化します。

この絞り込みは統合後の iOS レーンに対して実装したため、シナリオ対応づけ済みのジョブは `run`・`actuation`・
`golden`・`bundled-runner` です（`smoke.yaml` は `run` と `bundled-runner` の両方が宣言しているので、その変更は
両方を発火させます）。ガードと対応表の一致を検証するテストが、各ジョブの `if:` ガードをワークフローの宣言する
`scenarios:` に突き合わせて固定するので、将来ジョブ名やシナリオが変わっても、レーンを黙って誤って絞り込むのでは
なくテストが失敗します。
