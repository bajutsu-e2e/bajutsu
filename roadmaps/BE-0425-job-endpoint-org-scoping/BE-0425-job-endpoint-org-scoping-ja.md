## はじめに

ホスティングされた `bajutsu serve` の4つの endpoint は、job を id だけで解決します。どの endpoint も、その job が呼び出し元の org のものかを確認しません。あるテナントのサインイン済みメンバーは、別のテナントの job を読めます。その run のキャンセル、handoff への応答、ライブログの受信もできます。必要なのは job の id だけです。本項目は、4つすべての endpoint を「呼び出し元が今いる org」でスコープして、この穴を塞ぎます。隣接する読み出しは、すでにこの規則を採用しています。

## 動機

serve のマルチテナンシーは、単一の門ではなく操作ごとに実施しています。どの読み出しも、呼び出し元の org を解決してから、自分が触るストアを絞ります。`list_scenarios`、`read_scenario`、アーティファクトの経路は、`state.org_of(actor)` を通ります。`runs_payload` は、後述の `state.org_for(actor, machine_org)` を通ります。どちらも対象に触れる前の処理です（[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md)）。job の endpoint だけが例外です。`state.jobs.get(job_id)` を読んで、そのまま仕事に入ります。

| endpoint | 操作 | 今日の org チェック |
|---|---|---|
| `GET /api/jobs/{job_id}` | `job_view` | 機械の主体のみ |
| `POST /api/jobs/{job_id}/cancel` | `cancel_job` | なし |
| `POST /api/jobs/{job_id}/respond-human` | `respond_human` | なし |
| `GET /api/jobs/{job_id}/events` | `job_sse`／`job_log_events` | なし |

role のゲートは、この隙間を覆いません。`required_role` は2つの書き込みを editor 限定にするので、viewer は拒否されます。しかしゲートが答えるのは「この呼び出し元は editor か」です。「この呼び出し元は*その job を持つ org の* editor か」には答えません。どこかのテナントの editor は、すべてのテナントの job に対してゲートを通ってしまいます。

[BE-0414](../BE-0414-ci-oidc-machine-identity/BE-0414-ci-oidc-machine-identity-ja.md) の単位3は、CI の機械の主体について表の1行目を塞ぎました。許可リストが job のポーリングを開けるので、パイプラインをトークンの交換先の org に閉じ込める必要があったからです。BE-0414 は、人間の経路には意図的に手を付けませんでした。人間の経路を絞るのは、それ自体がテナント境界の変更です。機械セッションの項目を広げて抱え込ませると、2つの判断が1つの変更に混ざります。本項目が、その後続にあたります。

露出は、id をすでに知っている呼び出し元だけの問題ではありません。job の id は、すべての org が共有する単一のカウンターを10進表記にしたものです。`JobRegistry._register` が `str(self._seq)` を割り当てます。このカウンターは、起動時に jobs テーブル全体から連番を引き継ぎます。そのため id は「1」「2」「3」と並びます。どこかのテナントの editor は、この範囲を歩くだけで、他のすべてのテナントの job に到達できます。つまり、秘密を握っていなければ通れない隙間ではなく、開いた扉です。扉の先にあるのは、開示だけではありません。別テナントの run のキャンセルは、進行中の作業を壊します。handoff への応答は、そのテナントが見ている run に入力を注入します。

**検証可能な結果。** org B が投入した job の id を持つ org A の **editor** を考えます。org A として振る舞っている間、この editor は4つの endpoint すべてで拒否されます。拒否は403ではなく404なので、その id が実在の job を指すことを応答が裏づけません。viewer は、この確認より手前の role のゲートで、2つの書き込みを拒否されます。こちらは403のままで、変わりません。同じメンバーが org B に切り替えれば、同じ job に通常どおり到達できます。境界は、呼び出し元が今いる org に追随します。そのメンバーを恒久的に締め出すものではありません。

## 詳細設計

作業は、互いに排他かつ網羅的（MECE）な3つの単位に分かれます。

- ルーティングの表が一様に扱う3つの操作
- 各バックエンドが自前の配管で提供するストリーミングの経路
- テストと文書

### 規則は「呼び出し元が今いる org」

4つの endpoint は、いずれも job 自身の org を `state.org_for(actor, machine_org)` と比べます。この `org_for` は、BE-0414 の単位3が導入したものです。人間の org と機械セッションの org が合流する、唯一の場所です。job は、投入時の org を `Job.org` に持ちます。`Job.org` には、`start_run`、`start_run_set`、`start_record`、`start_crawl`、`start_triage` が投入時に値を刻みます。値は job の仕様に載って、ワーカーまで運ばれます。そのため、比較に新しい状態は要りません。

**org を切り替えた呼び出し元は job を見失い、切り替え直せば戻ります。** この挙動は規則に逆らうものではなく、規則から出てくる帰結です。インタフェースの他の部分がすでに持っている挙動とも同じです。run の履歴、シナリオの一覧、ターゲットの一覧は、いずれもアクティブな org が変われば再びスコープされます。切り替えをまたいで答え続ける job の画面は、むしろ浮いた存在になります。

切り替えは、完全に元へ戻せます。この点が、2つの読み出しだけでなく2つの書き込みについても、規則を安全にしています。`set_active_org` は、`users.org_id` と `users.role` をまとめて書き換えます。そのため `user_role` は、常に「呼び出し元が今いる org で持つ role」を報告します。editor が org A で run を投入し、何かを見るために org B へ移り、A へ戻ってキャンセルする場面を考えます。このキャンセルは成立します。A へ戻れば org の比較は通り、editor の確認は A で持つ role に対して走るからです。可視性は「今どこにいるか」の関数です。「その呼び出し元がどこを通ってきたか」の関数ではありません。

**拒否は403ではなく404にします。** 多くを伏せられるからではありません。id は連番なので、列挙する呼び出し元は、どのみちどの id が生きているかを知れます。共有するカウンター自体も、テナントをまたいだ件数をすでに漏らしています。自分の id が41から58に飛んでいれば、その間に他のテナントが何件の job を投入したかがわかります。404を選ぶ理由は3つです。

- コストがかかりません。
- 4つのどの endpoint も、「そんな id の job はない」場合にすでに404を返しています。
- `job_view` が BE-0414 の下で機械の主体について採った答えと一致します。

ここで、job の id を推測できなくせよと述べているのではありません。id は資格情報ではありません。秘匿し続けることに安全性が依存する設計は、修正ではなく欠陥そのものです。欠けているのは、テナントの確認だけです。

### 単位1 — 一様な3つの操作

`job_view`（`bajutsu/serve/operations/reads.py`）は、すでに確認を持っています。ただし、機械の主体についてだけです。`job.org` を `machine_org` とだけ比べており、`actor` はそもそも受け取っていません。本単位は、隣の読み出しが取るのと同じ `actor` 引数を `job_view` に与えます。比較の相手は `state.org_for(actor, machine_org)` に変えます。これで確認は、呼び出し元が誰であっても、解決済みの org に対して走ります。

`cancel_job` は、今日 `(state, job_id)` だけを取ります。`respond_human` は、`(state, job_id, body)` だけを取ります。どちらも actor は受け取っていません。両方に、隣の読み出しが取るのと同じ `actor` と `machine_org` のキーワード引数を足します。ルーティングの表（`bajutsu/serve/routes/_shared.py`）は、`ctx.actor()` と `ctx.machine_org()` の両方を3つすべての操作に渡します。`job_view` が今日受け取っているのは、後者だけです。

機械の主体は、どちらの書き込みにも到達しません。BE-0414 の許可リストがどちらの経路も挙げていないので、実際には `machine_org` は None で届きます。それでも、2つの操作は引数を受け取ります。許可リストは別のゲートであり、後から経路を開ける余地があるからです。自分の org を自分で解決できる操作は、どのゲートがリクエストを通したかに依存しません。

`job_view` の docstring は、絞り込みを意図的なものとして記録し、広げる変更を別のものとして記録しています。本単位は、この docstring を上の規則に合わせて書き直します。

### 単位2 — ライブログのストリーム

`GET /api/jobs/{job_id}/events` は `off_loop` です。各バックエンドが、自前のストリーミングの配管で提供します。stdlib のハンドラは `_sse_job` から `ops.job_log_events` へ進みます。FastAPI のアプリは `ops.job_sse` へ進みます。どちらの入口も org を解決せず、actor も取りません。

両方の入口に、同じ引数の組と同じ確認を足します。確認は**最初のフレームの手前**で一度だけ行い、フレームごとには行いません。呼び出し元の org は、そのリクエストの間は固定です。フレームごとに確認すれば、1フレームあたり1回の解決を払います。それでも、途中で org を切り替えた呼び出し元のストリームを止められるわけではありません。開いた後で呼び出し元が org を切り替えたストリームは、job の終わりまで流れ続けます。この扱いは、切り替えが遡って効くのではなく次のリクエストから効くという、他の部分の扱いと揃います。

この等価性が覆わないのが、失効の場合です。`delete_org` は、メンバー全員のセッションを一度に落とします。管理者があるテナントを畳んでいる最中に、誰かがそのテナントの長時間の job のストリームを開いたままにしているとします。そのストリームは、job が終わるまでログの行を届け続けます。一度きりの確認は、セッションを取り直さないからです。本項目は、この限界を閉じずに受け入れます。失効した際にライブストリームを終わらせるのは、セッションのライフサイクルに関する変更です。テナントの確認ではなく、失効の経路に属します。

ストリームを開く前に拒否すれば、各バックエンドは通常の404で答えられます。クライアントがすでに読み始めたイベントストリームの中で、拒否を表現する必要がなくなります。

### 単位3 — テストと文書

Simulator もブラウザも使わず、高速な Python のスイートで次を覆います。

- org B が投入した job に対して、org A の editor は4つの endpoint すべてで拒否されます。拒否はいずれも404です。viewer は、それより先に role のゲートで2つの書き込みを拒否されます。こちらは403で、既存の挙動です。2つのゲートを見分けられる状態を保つために、この挙動も検証します。
- その拒否は、何も指さない job の id に対する答えと見分けがつきません。
- 同じメンバーが org B に切り替えれば、同じ job に4つの endpoint とも到達できます。
- org A で投入した run は、org B へ移って A へ戻った後もキャンセルできます。境界は一方通行の喪失ではなく、元に戻せるものです。
- org の内側では、editor のゲートが従来どおり効きます。org B の viewer は、org B 自身の job に対する2つの書き込みを拒否されます。
- 機械の主体は、自分の org の job だけを読みます。これは BE-0414 の単位3が定めたとおりです。許可リストは、2つの書き込みとストリームを引き続き拒否します。
- 単一テナントのデプロイ（ローカルの serve、データベースなし）は影響を受けません。どの呼び出し元も同じ `default` org に解決されるので、4つの endpoint は従来どおりに振る舞います。
- 2つのバックエンドは、ストリームの確認を同一に実施します。
- フロントエンドには、拒否を黙って通してしまう呼び出し箇所が2つあります。応答を破棄する `cancelJob` と、`EventSource` に `error` ハンドラを持たない `streamJob` です。この2つは、拒否を表示するように変えます。古い org のままのタブに残った Stop ボタンは、「停止中…」で固まる代わりに、job にもう到達できないことを表示します。最初のフレームより前に拒否されたストリームも、パネルが「実行中」のまま固まることがなくなります。handoff への応答は、すでに non-ok の状態を表示しているので、変更は不要です。

`docs/self-hosting.md` と日本語版には、マルチテナンシーの記述の下へ短い注記を足します。注記には2点を書きます。job の endpoint は、他の読み出しと同じくアクティブな org に従うことです。org を切り替えると、実行中の job は切り替え直すまで見えなくなることです。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| アクティブな org ではなくメンバーシップ（`eligible_orgs`）でスコープする | この案がアクティブな org による規則に勝る唯一の利点は、呼び出し元が自分の job を見失うことがない点です。しかし、これはすでに解決済みの問題に対する利点にすぎません。離れた呼び出し元は切り替え直せば job に戻れます。`set_active_org` が role を org と一緒に動かすので、editor の確認はすでに job 自身の org に対して評価されています。この案が持ち込むのは、隣接するどの読み出しも使っている規則の横に立つ、2つ目のスコープ規則です。解くべき問題が残っていない2つ目の規則は、得るもののない負担です。 |
| 404ではなく403を返す | 403は失敗の理由については正直ですが、その id が別テナントの実在の job を指すことを開示します。呼び出し元が持っているのは id だけなので、それを裏づけることこそ避ける価値のある漏洩です。`job_view` は BE-0414 の下ですでに404を選んでいます。揃えれば、4つの endpoint で答えが1つになります。 |
| 操作ごとではなく `ServeState.jobs`／`JobRegistry` の内側で org を確認する | 1つの門ですべての呼び出し元を覆えるので、魅力的です。レジストリは、すでに org を把握しています。`in_flight_by_org` は、`/metrics` のために org ごとに集計しています。しかしレジストリの鍵は id です。ランナー、ワーカーの結果の経路、メトリクスの読み出しは、いずれも actor なしで参照します。org を意識した参照にすると、それらすべてに任意の actor を通す必要が生じます。さらに、内部の呼び出し元に見えるものを黙って変えてしまいます。serve は他のどこでも、テナンシーを操作ごとに実施しています。本項目もそれに倣います。 |
| ライブストリームのフレームごとに org を再確認する | 途中で org を切り替えた呼び出し元のストリームを止めることになります。1フレームあたり1回の org 解決を払います。切り替えは、他のどこでも次のリクエストから効きます。途中で死ぬストリームは、他の部分より安全な規則ではなく、他の部分より厳しいだけの規則です。 |
| テナントの確認を足す代わりに job の id を推測できなくする | 不透明な id にすれば、動機で述べた総当たりは止まります。しかし、修理の仕方として誤っています。id は宛先を指す手がかりであって、資格情報ではありません。認可の代わりに秘匿を置いても、id を手に入れた呼び出し元には、これらの endpoint が応じ続けます。id は、ログ、共有されたリンク、ブラウザの履歴から手に入ります。識別子を当てられないことに安全性が依存する構成こそ、直す価値のあるものです。動機で連番の id に触れたのは、今日そこに秘匿による歯止めがないことを示すためです。秘匿を足すよう提案するためではありません。 |
| 2つの読み出しは残し、書き込みだけをスコープする | キャンセルと handoff への応答は破壊的な2つなので、書き込みのほうが重いのは確かです。それでも、別テナントの job の画面とライブログを読めれば、シナリオ名、ステップの進行、ログの出力が漏れます。これは、同じ境界の機密性の側です。分けても何も節約できないまま、項目が中途半端になります。 |

## 進捗

> 開発の進行に合わせて常に最新の状態に保ってください。チェックリストは *詳細設計* の MECE な
> 作業分解に対応し（作業単位ごとに1つ）、ログには何をいつ変えたかを古い順に記録し、PR を結びます。

- [ ] 単位1 — `job_view` を機械の主体からすべての呼び出し元へ広げます。`cancel_job` と `respond_human`
      には同じ `actor`／`machine_org` の引数と、同じ org の比較、同じ404を与えます。共有のルーティングの
      表から配線します。絞り込みを意図的なものとして記録している `job_view` の docstring も、上の規則に
      合わせて書き直します。
- [ ] 単位2 — ライブログのストリームの2つの入口（stdlib 側の `job_log_events`、FastAPI 側の `job_sse`）に
      同じ確認を与えます。確認は最初のフレームの手前で一度だけ行います。
- [ ] 単位3 — 各 endpoint と2つのバックエンドのテストを書きます。切り替えて戻る場合と、単一テナントで
      何も変わらない場合を含めます。`cancelJob` と `streamJob` が拒否を破棄せず、あるいはストリームを
      黙って固まらせずに表示するように変えます。あわせて self-hosting の注記を両言語に入れます。
