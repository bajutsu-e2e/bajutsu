## はじめに

Bajutsu のシミュレータ準備は、起動を依頼しますが、完了を待ちません。本項目は、デバイスを起動してそのまま使う2箇所に待機を挿入します。本プロジェクトの手元のハードウェアでは、初回起動で **39.4秒** の隔たりがありました。

Bajutsu が iOS シミュレータを操作するには、SpringBoard が起動の要求を受け付けられる段階まで、デバイスが立ち上がっている必要があります。SpringBoard は、ホーム画面を所有しアプリを起動する iOS のプロセスです。シミュレータの制御ツール `simctl` は、依頼と待機を分けています。

- `simctl boot` は、起動を*依頼*した時点で返ります。
- `simctl bootstatus` は、起動が実際に*完了*するまでブロックします。

現在のシミュレータ準備は、`boot` を呼んだあとにアプリをインストールし、テスト runner を起動します。この時点でデバイスは、まだ立ち上がりかけのことがあります。本項目は、次の2箇所に待機を挿入します。

- 共通のデバイス準備
- 新しいロケールを反映させるためにデバイスを再起動する、システムロケールの固定

継続的インテグレーション（CI）は、最初の立ち上げでこの隔たりを払いません。本項目もそう主張しません。iOS の端から端までのジョブはいずれも、実行の段より前に自前の `bootstatus` の段を走らせます。この段は、[BE-0088](../BE-0088-overlap-simulator-boot/BE-0088-overlap-simulator-boot-ja.md) の設計が意図どおり働いている姿です。待たれていない窓は、次の2箇所に現れます。

- 開発者の Mac では、毎回の実行
- CI では、erase を伴う再試行。この再試行は、先の段が返ったあとにもう一度起動します。

## 動機

デバイスを起動する4箇所のうち、2箇所はすでに待っています。そのため、残る2箇所は判断ではなく見落としに見えます。

[BE-0344](../BE-0344-xcuitest-device-recovery/BE-0344-xcuitest-device-recovery-ja.md) が追加した修復のはしごは、劣化したシミュレータを再起動し、消えたシミュレータを置き換えます。両方の段が、デバイスを引き渡す前に `bootstatus` を走らせます。ところが、その段が続いて呼ぶ共通の準備は待ちません。ロケール固定自身の再起動も待ちません。XCUITest のライフサイクルのモジュール全体で、`bootstatus` が現れるのはちょうど2箇所で、どちらもはしごの内側です。

この窓は理屈の上の話ではありません。Xcode 26.5 のもとで iOS 26.5 を載せた iPhone 17 のデバイスを新規に作り、計測しました。`simctl boot` は **0.56秒** で返りました。`bootstatus` は **39.94秒** まで完了しませんでした。この39.4秒のあいだに、準備はアプリのインストール、権限の付与、`xcodebuild` の起動へと進みます。

CI ランナーはさらに遅く、プロジェクトはそれをすでに知っています。iOS の端から端までを試すワークフローにあるクラッシュ復旧予算のコメントは、有界でない準備をおよそ80秒から150秒と見積もっています。根拠は、あるジョブ自身の80秒というシミュレータ起動の見積もりです。この値は起動に対する実時間の割り当てであり、起動との同期ではありません。

立ち上がりかけの SpringBoard へアプリを起動すると、見分けのつく失敗が起きます。XCUITest は、およそ40秒後に `Failed to launch <bundle id>: Timed out attempting to launch app` を報告します。この長さは計測した窓と十分近く、両者を結びつけて考える価値があります。この兆候は、2026年8月初旬まで iOS の支配的な flake でした。[BE-0344](../BE-0344-xcuitest-device-recovery/BE-0344-xcuitest-device-recovery-ja.md) の修復のはしご全体も、この兆候から生まれました。はしごは、ある試行が失敗した*あとで*デバイスを直します。

執筆時点で、この兆候は CI から消えています。本項目は現在の CI 失敗を主張しません。主張するのは、症状が退いたあいだに露出が広がったことです。

- CI は、erase の事前条件を抑制するフラグを渡していません。
- [BE-0353](../BE-0353-xcuitest-adb-crash-retry-device-recovery/BE-0353-xcuitest-adb-crash-retry-device-recovery-ja.md) は、クラッシュを契機とする再試行のたびに、その事前条件を強制するようになりました。
- そのため、再試行は `shutdown` → `erase` → `boot` の経路を通ります。
- erase 直後のデバイスは、真の初回起動の状態から立ち上がります。これは上で計測したもっとも遅い場合です。
- 再試行は、そのまま待たれていない窓へ進みます。

この隔たりのもっとも長い形が、再試行が吸収しようとしている失敗の直後の経路に載りました。

開発者自身の Mac は、ロケール固定を通して、より直接に露出しています。この固定は、SpringBoard が権限プロンプトのボタンを予測できる言語で描くために存在します（[BE-0320](../BE-0320-ios-system-alert-locale-determinism/BE-0320-ios-system-alert-locale-determinism-ja.md)）。動いている SpringBoard はグローバルドメインへの書き込みをその場では拾わないため、固定はデバイスを再起動します。

新規に作ったシミュレータは、ホスト自身の言語設定を引き継ぎます。地域が米国でないホストでは、引き継いだ値が固定の一致判定を通らず、固定が発火します。日本地域のホストでは、新しいデバイスが言語の項目を2つと、それに対応するロケールを引き継ぎました。項目が2つあると、固定の「項目はちょうど1つ」という判定を満たしません。したがって、固定は新しいデバイスのたびに発火して再起動し、待たれていない窓へ戻ります。

GitHub のランナーで固定が発火するかは、今日のログからは答えられません。固定は発火しても何も書かないからです。この沈黙は直す価値があり、直すための費用も小さく済みます。ログを1行足せば、開いた問いが、次に失敗したジョブ自身の答える事実に変わります。

## 詳細設計

作業は3つの単位に分かれます。単位1は独立しています。単位2と単位3は、単位1が用意する補助関数を使うためにだけ単位1に依存します。3つは同時に投入できます。

1. **待機に一度だけ名前を与える。** 引数を組み立てる関数は、すでに共有されていて名前もあります。`bootstatus_cmd` です。Web UI 側の起動待ちもこの関数を使います。したがって本単位は、2つ目の組み立てを増やしません。`-b` の指定は、これまでどおり1箇所に留まります。

   ライフサイクル側の2つの呼び出し箇所は、この組み立てを囲む2つの手順を重複させています。1つは組み立てた引数の実行で、もう1つは `simctl` の失敗をモジュールのデバイス障害の型へ変換する処理です。シミュレータの環境に、自身が保持するデバイスに対してその両方を行う小さな非公開の補助関数を持たせます。既存の2箇所をそこへ通します。こうすれば、下で追加する新しい呼び出し箇所が、この2つの手順をそれぞれ言い直す必要はなくなります。

   補助関数は `simctl` のモジュールではなく環境のクラスへ置き、その代償を引き受けます。`Env.boot()` は自身の失敗を抑制します。そのため、このクラスの外にいる将来の `Env.boot()` の呼び出し側は、この待機の外に留まります。既存の2つの呼び出し箇所は、すでにこの境界の内側にあります。境界を広げるには `Env.boot()` の契約を変える必要があり、本項目はそこを開きません。

2. **準備自身の起動のあとに待つ。** 共通のデバイス準備で、`boot` の呼び出しに続いて単位1の待機を置きます。位置は、デバイスの種別を記録する前、かつロケール固定が走る前です。コールドな立ち上げと修復のはしごによる再準備は、どちらもこの1箇所を通ります。1箇所の挿入で、すべての呼び出し側を覆えます。

   この待機は、準備のインストールと権限の手順がすでにそうであるように、有界にしません。立ち上がりに80秒かかるデバイスは失敗していません。決して立ち上がらないデバイスを縛るのは、この層より上にある実行単位とジョブ単位の上限です。

3. **ロケール固定の再起動のあとに待ち、固定が発火したことを述べる。** 固定は、グローバルドメインへの書き込みを反映させるためにデバイスを落として起動し直します。その後で値を読み返して確認します。その起動と読み返しのあいだに、待機を挿入します。こうすれば、確認は立ち上がりを終えたデバイスを読みます。呼び出し側も、立ち上がりかけではなく準備できたデバイスへ戻ります。

   ただし待機だけでは、再起動が実際に起きたことを確かめられません。そこで、修復のはしごの再起動の段がすでに行っている読み返しを組み合わせます。組み合わせが必要になる事実は3つあります。

   - `Env.shutdown()` と `Env.boot()` は、どちらも自身の失敗を抑制します。
   - `bootstatus -b` は、`Booted` から一度も出なかったデバイスに対しては即座に返ります。
   - plist の読み返しは、書き込みがすでに変えた値を読むだけで、SpringBoard が読み込んだ内容を読むわけではありません。そのため、デバイスが実際に再起動した場合と、`shutdown` を受け付けずに `Booted` のままだった場合を区別できません。

   `shutdown` を受け付けないほど CoreSimulator が応答しなくなっていると、そのままでは固定が「準備できた」デバイスを返します。SpringBoard が古い言語を描いたまま、確認済みの固定として記録します。これは [BE-0320](../BE-0320-ios-system-alert-locale-determinism/BE-0320-ios-system-alert-locale-determinism-ja.md) が存在する理由である決定性を損ないます。`shutdown` のあとにデバイスの起動状態を、はしごの段と同じく3値で読み返します。落ちなかったデバイスは、確認済みの固定ではなく未確認として扱います。

   あわせて、固定が書き込むと決めたときに、固定しようとしているロケールを名指しする情報ログを1行出します。固定は今日、読み返しが失敗したときを除いて沈黙しています。この沈黙のせいで、固定がそもそも発火したのかを CI のログから誰も判断できません。その答えが、単位2の露出のうちどれだけが開発者の Mac だけでなく CI にも当てはまるかを決めます。

本項目が根拠とする計測は、コマンド2つとストップウォッチで再現できます。新規に作ったデバイスに対する `simctl boot` と、それに続く `bootstatus -b` です。査読者は、CI を走らせずに窓を確認できます。挙動の変更は、既存のライフサイクルのテストが覆います。これらのテストは、準備と修復のはしごにおける `simctl` 呼び出しの順序をすでに検証しています。待機を1つ挿入するたびに、期待される呼び出しが1つ増えます。

## 検討した代替案

- **待機にタイムアウトを設け、期限切れで実行を失敗させる。** 止まったままの起動を、ジョブ単位のタイムアウトではなく名前のついた失敗に変えられます。本項目では却下します。`simctl` 自身のサブプロセス呼び出しは、どれもタイムアウトを持たないからです。この待機だけを縛ると、多数あるうちの1つの呼び出しに対処しながら、残りは縛られていると読ませてしまいます。`simctl` の呼び出しすべてを縛るのは、タイムアウトの値と失敗の形を自前で選ぶ、より大きな別の変更です。独立した項目に属します。
- **SpringBoard の準備完了をポーリングする。** SpringBoard への探査であれば、起動が報告する問いではなく、アプリの起動が実際に気にしている問いに答えられます。重複であるため却下します。`bootstatus` は、デバイス自身の起動完了をすでに待ちます。Apple がその目的のために提供しているツールでもあります。修復のはしごも、[BE-0344](../BE-0344-xcuitest-device-recovery/BE-0344-xcuitest-device-recovery-ja.md) 以来、より細かい信号を必要とせずにこれを使ってきました。
- **事前条件が erase を伴うときだけ待つ。** erase 直後のデバイスがもっとも遅いので、窓がもっとも広いところへ待機を置き、通常の経路には手を触れずに済みます。窓は erase に固有ではないため却下します。ジョブのなかで初めて起動するデバイスも、同じだけ影響を受けます。条件付きの待機は、本項目が取り除こうとしている非対称を、説明すべき条件を1つ増やしたうえで残してしまいます。
- **待機を入れる前に、まず固定の発火をログに出して計測する。** 考えうるもっとも安価な最初の一歩です。単位3のログ行がそれ自体で価値を持つ理由でもあります。項目の全体としては却下します。開発者の Mac では固定の発火が実証されており、計測はそこですでに窓を確立しました。CI の証拠を待てば、すでに証明されている場合に対する修正を留保することになります。

## 進捗

> 作業の進行に合わせて最新の状態に保ってください。チェックリストは*詳細設計*の MECE な作業分解を
> 反映し（作業単位ごとに1つ）、ログには何がいつ変わったかを古い順に記録し、PR へリンクします。

- [x] 単位1 — 共有の `bootstatus` 組み立てを実行し失敗を変換する非公開の補助関数をシミュレータの環境に
      追加し、既存の2つの呼び出し箇所をそこへ通す。XCUITest のライフサイクルのモジュールに
      `XcuitestEnvironment._await_boot` として追加しました。どちらの呼び出し箇所からも、変換のための
      `try` / `except subprocess.CalledProcessError` を取り除きました。その `try` の内側で
      `subprocess.CalledProcessError` を送出しうるのは `bootstatus` の実行だけだったからです
      （`Env.shutdown()`、`Env.boot()`、`device_booted` はいずれも自分で失敗を吸収します）。
- [x] 単位2 — 共通のデバイス準備の `boot` のあと、デバイス種別の記録とロケール固定より前に待つ。
- [x] 単位3 — ロケール固定の再起動のあとに待ち、`shutdown` のあとで起動状態を読み返して、落ちなかった
      デバイスを確認済みの固定として記録しないようにする。あわせて、固定が書き込むと決めたときに情報
      ログを1行出す。起動状態の判定は、plist の読み返しの代わりではなくその後ろに置きました。これにより
      判定は確認を取り下げる方向にだけ働きます。別のロケールを読み返したデバイスは、今までどおり run を
      はっきり失敗させます。判定を読み返しの代わりに置いていたら、shutdown の拒否がその失敗を覆い隠し
      かねませんでした。固まった CoreSimulator では、起動の一覧の読み取りも同時に失敗するからです。
      起動とその待機は、判定によらず必ず
      実行します。一覧を読めなかったデバイスは実際には停止していることがあり、呼び出し側はその直後に
      インストールを始めるからです。
