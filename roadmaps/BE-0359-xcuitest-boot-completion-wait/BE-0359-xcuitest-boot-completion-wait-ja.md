## はじめに

Bajutsu が iOS シミュレータを操作するには、デバイスが動いている必要があります。より正確には、ホーム
画面を所有しアプリを起動する iOS のプロセスである SpringBoard が、起動の要求を受け付けられる段階まで
立ち上がっている必要があります。シミュレータの制御ツール `simctl` は、依頼と待機を分けています。
`boot` サブコマンドは起動を*依頼*した時点で返り、別のサブコマンド `bootstatus` が起動の*完了*まで
ブロックします。

Bajutsu のシミュレータ準備は、依頼だけをして待ちません。`boot` を呼び、まだ立ち上がりかけのデバイス
に対してアプリをインストールし、テスト runner を起動します。本項目は、デバイスを起動してそのまま使う
2箇所に待機を挿入します。共通のデバイス準備と、新しいロケールを反映させるためにデバイスを再起動する
システムロケールの固定です。本プロジェクトの手元のハードウェアでは、2つのサブコマンドのあいだの隔たり
が初回起動で **39.4秒** ありました。

継続的インテグレーション（CI）は、最初の立ち上げでこの隔たりを払いません。本項目もそう主張しません。
iOS の端から端までのジョブはいずれも、実行の段より前に自前の `bootstatus` の段を走らせます。これは
[BE-0088](../BE-0088-overlap-simulator-boot/BE-0088-overlap-simulator-boot-ja.md) の設計が意図どおり
働いている姿です。Bajutsu が本当に待たずに過ごす窓は、開発者の Mac では毎回の実行であり、CI では
erase を伴う再試行です。後者は、その段が返ったあとにもう一度起動します。

## 動機

デバイスを起動する4箇所のうち2箇所はすでに待っており、だからこそ残る2箇所は判断ではなく見落としに
見えます。[BE-0344](../BE-0344-xcuitest-device-recovery/BE-0344-xcuitest-device-recovery-ja.md) が
追加した修復のはしごは、劣化したシミュレータを再起動し、消えたシミュレータを置き換えます。その両方の
段が、デバイスを引き渡す前に `bootstatus` を走らせます。しかし、その段が続いて呼ぶ共通の準備は待たず、
ロケール固定自身の再起動も待ちません。XCUITest のライフサイクルのモジュール全体で `bootstatus` が
現れるのはちょうど2箇所で、どちらもそのはしごの内側です。

この窓は理屈の上の話ではありません。Xcode 26.5 のもとで iOS 26.5 を載せた iPhone 17 のデバイスを新規に
作って計測しました。`simctl boot` は **0.56秒** で返り、`bootstatus` は **39.94秒** まで完了しません
でした。この39.4秒のあいだに、準備はアプリのインストール、権限の付与、`xcodebuild` の起動へと進みます。
CI ランナーはさらに遅く、プロジェクトはそれをすでに知っています。iOS の端から端までを試すワークフロー
にあるクラッシュ復旧予算のコメントは、有界でない準備をおよそ80秒から150秒と見積もっています。根拠は、
あるジョブ自身の80秒というシミュレータ起動の見積もりです。これは起動に対する実時間の割り当てであり、
起動との同期ではありません。

立ち上がりかけの SpringBoard へアプリを起動すると、見分けのつく失敗が起きます。XCUITest はおよそ40秒
後に `Failed to launch <bundle id>: Timed out attempting to launch app` を報告します。この長さは計測
した窓と十分近く、両者を結びつけて考える価値があります。この兆候は2026年8月初旬まで iOS の支配的な
flake であり、[BE-0344](../BE-0344-xcuitest-device-recovery/BE-0344-xcuitest-device-recovery-ja.md) の
修復のはしご全体を生んだ原因でした。はしごは、ある試行が失敗した*あとで*デバイスを直します。

執筆時点で、この兆候は CI から消えています。本項目は現在の CI 失敗を主張しません。主張するのは、症状が
退いたあいだに露出が広がったことです。CI は erase の事前条件を抑制するフラグを渡しておらず、
[BE-0353](../BE-0353-xcuitest-adb-crash-retry-device-recovery/BE-0353-xcuitest-adb-crash-retry-device-recovery-ja.md)
はクラッシュを契機とする再試行のたびにその事前条件を強制するようになりました。その結果、再試行は
`shutdown` → `erase` → `boot` の経路を通ります。erase 直後のデバイスは、上で計測したもっとも遅い
真の初回起動から立ち上がり、再試行はそのまま待たれていない窓へ進みます。つまり、この隔たりのもっとも
長い形が、再試行が吸収しようとしている当の失敗の直後の経路に載りました。

開発者自身の Mac は、ロケール固定を通してより直接に露出しています。この固定は、SpringBoard が権限
プロンプトのボタンを予測できる言語で描くために存在します
（[BE-0320](../BE-0320-ios-system-alert-locale-determinism/BE-0320-ios-system-alert-locale-determinism-ja.md)）。
動いている SpringBoard はグローバルドメインへの書き込みをその場では拾わないため、固定はデバイスを
再起動します。新規に作ったシミュレータはホスト自身の言語設定を引き継ぐので、地域が米国でないホストでは
引き継いだ値が固定の一致判定を通らず、固定が発火します。日本地域のホストで計測すると、新しいデバイスは
言語の項目を2つと、それに対応するロケールを引き継ぎました。項目が2つある時点で固定の「項目はちょうど
1つ」という判定を満たしません。したがって固定は発火し、再起動し、新しいデバイスのたびに待たれていない
窓へ戻ります。

GitHub のランナーで固定が発火するかは、今日のログからは答えられません。固定は発火しても何も書かないから
です。この沈黙それ自体を直す価値があり、しかも安価です。ログを1行足せば、開いた問いが、次に失敗した
ジョブ自身の答える事実に変わります。

## 詳細設計

作業は3つの単位に分かれます。単位1は独立しています。単位2と単位3は、単位1が用意する補助関数を使う
という意味でのみ単位1に依存し、単位1と同時に投入できます。

1. **待機に一度だけ名前を与える。** 引数を組み立てる関数はすでに共有されていて名前もあります。
   `bootstatus_cmd` であり、Web UI 側の起動待ちもこれを使います。したがって本単位は、その隣に2つ目の
   組み立てを増やしません。`-b` の指定はこれまでどおり1箇所に留まります。ライフサイクル側の2つの
   呼び出し箇所が重複させているのは、その組み立てを囲む2つの手順です。実行することと、`simctl` の失敗
   をモジュールのデバイス障害の型へ変換することです。シミュレータの環境に、自身が保持するデバイスに
   対してその両方を行う小さな非公開の補助関数を持たせ、既存の2箇所をそこへ通します。こうしておけば、
   下で追加する新しい呼び出し箇所が、この2つの手順をそれぞれ言い直す必要はなくなります。

   補助関数は `simctl` のモジュールではなく環境のクラスへ置き、その代償を引き受けます。`Env.boot()` は
   自身の失敗を抑制するため、このクラスの外にいる将来の `Env.boot()` の呼び出し側は、本項目が名前を
   与える待機の外に留まります。それは既存の2つの呼び出し箇所がすでに収まっている境界と同じであり、
   これを広げるには `Env.boot()` の契約を変える必要があります。本項目はそこを開きません。

2. **準備自身の起動のあとに待つ。** 共通のデバイス準備で、`boot` の呼び出しに続いて単位1の待機を置き
   ます。位置は、デバイスの種別を記録する前、そしてロケール固定が走る前です。準備は、コールドな立ち
   上げと修復のはしごによる再準備の両方が通る唯一の場所なので、1箇所の挿入がすべての呼び出し側を
   覆います。この待機は、準備のインストールと権限の手順がすでにそうであるのと同じく、有界にしません。
   立ち上がりに80秒かかるデバイスは失敗していませんし、決して立ち上がらないデバイスを縛るのは、この
   層より上にある実行単位とジョブ単位の上限です。

3. **ロケール固定の再起動のあとに待ち、固定が発火したことを述べる。** 固定は、グローバルドメインへの
   書き込みを反映させるためにデバイスを落として起動し直し、その後で値を読み返して確認します。その起動と
   読み返しのあいだに待機を挿入します。こうすれば、確認は立ち上がりを終えたデバイスを読みます。呼び出し
   側も、立ち上がりかけではなく準備できたデバイスへ戻ります。

   ただし待機だけでは、再起動が実際に起きたことを確かめられません。そこで、修復のはしごの再起動の段が
   すでに行っている読み返しを組み合わせます。`Env.shutdown()` と `Env.boot()` はどちらも自身の失敗を
   抑制しますし、`bootstatus -b` は `Booted` から一度も出なかったデバイスに対しては即座に返ります。
   したがって `shutdown` を受け付けないほど CoreSimulator が応答しなくなっている場合が問題になります。
   固定はそのままだと「準備できた」デバイスを返し、SpringBoard が古い言語を描いたまま、確認済みの固定
   として記録します。
   これは
   [BE-0320](../BE-0320-ios-system-alert-locale-determinism/BE-0320-ios-system-alert-locale-determinism-ja.md)
   が存在する理由である決定性を損ないます。plist の読み返しでは2つの場合を分けられません。書き込みが
   すでに変えた値を読むだけで、SpringBoard が読み込んだ内容を読むわけではないからです。`shutdown` の
   あとにデバイスの起動状態を、はしごの段と同じく3値で読み返し、落ちなかったデバイスは確認済みの固定
   ではなく未確認として扱います。あわせて、固定が書き込むと決めたときに、固定
   しようとしているロケールを名指しする情報ログを1行出します。固定は今日、読み返しが失敗したときを除い
   て沈黙しています。だからこそ、固定がそもそも発火したのかを CI のログから誰も判断できません。そして
   その答えが、単位2の露出のうちどれだけが開発者の Mac だけでなく CI にも当てはまるかを決めます。

本項目が根拠とする計測は、コマンド2つとストップウォッチで再現できます。新規に作ったデバイスに対する
`simctl boot` と、それに続く `bootstatus -b` です。査読者は CI を走らせずに窓を確認できます。挙動の
変更は既存のライフサイクルのテストが覆います。それらのテストは、準備と修復のはしごにおける `simctl`
呼び出しの順序をすでに検証しており、待機を1つ挿入するたびに、期待される呼び出しが1つ増えます。

## 検討した代替案

- **待機にタイムアウトを設け、期限切れで実行を失敗させる。** 止まったままの起動を、ジョブ単位の
  タイムアウトではなく名前のついた失敗に変えられる点で魅力があります。本項目では却下します。`simctl`
  自身のサブプロセス呼び出しはどれもタイムアウトを持たないため、この待機だけを縛ると、多数あるうちの
  1つの呼び出しに対処しながら、残りは縛られていると読ませてしまいます。`simctl` の呼び出しすべてを
  縛るのは、タイムアウトの値と失敗の形を自前で選ぶ、より大きな別の変更であり、ここに便乗させるのでは
  なく独立した項目に属します。
- **SpringBoard の準備完了をポーリングする。** SpringBoard への探査であれば、起動が報告する問いでは
  なく、アプリの起動が実際に気にしている問いに答えられます。重複
  であるため却下します。`bootstatus` はすでにデバイス自身の起動完了を待ちますし、Apple がその目的の
  ために提供しているツールです。修復のはしごも
  [BE-0344](../BE-0344-xcuitest-device-recovery/BE-0344-xcuitest-device-recovery-ja.md) 以来、より細かい
  信号を必要とせずにこれを使ってきました。
- **事前条件が erase を伴うときだけ待つ。** erase 直後のデバイスがもっとも遅いので、窓がもっとも広い
  ところへ待機を置き、通常の経路には手を触れずに済みます。窓は erase に固有ではないため却下します。
  ジョブのなかで初めて起動するデバイスも同じだけ影響を受けますし、条件付きの待機は、本項目が取り除こう
  としている非対称そのものを、説明すべき条件を1つ増やしたうえで残してしまいます。
- **待機を入れる前に、まず固定の発火をログに出して計測する。** 考えうるもっとも安価な最初の一歩であり、
  単位3のログ行がそれ自体で価値を持つ理由でもあります。項目の全体としては却下します。開発者の Mac では
  固定の発火が実証されており、計測はそこですでに窓を確立しました。CI の証拠を待つことは、すでに証明
  されている場合に対して修正を留保することにあたります。

## 進捗

> 作業の進行に合わせて最新の状態に保ってください。チェックリストは*詳細設計*の MECE な作業分解を
> 反映し（作業単位ごとに1つ）、ログには何がいつ変わったかを古い順に記録し、PR へリンクします。

- [x] 単位1 — 共有の `bootstatus` 組み立てを実行し失敗を変換する非公開の補助関数をシミュレータの環境に
      追加し、既存の2つの呼び出し箇所をそこへ通す。XCUITest のライフサイクルのモジュールに
      `XcuitestEnvironment._await_boot` として追加しました。どちらの呼び出し箇所からも、変換のための
      `try` / `except subprocess.CalledProcessError` を取り除きました。その `try` の内側で
      `subprocess.CalledProcessError` を送出しうるのは `bootstatus` の実行だけだったからです
      （`Env.shutdown()`、`Env.boot()`、`device_booted` はいずれも自分で失敗を吸収します）。
- [x] 単位2 — 共通のデバイス準備の `boot` のあと、デバイス種別の記録とロケール固定より前に待つ。
- [x] 単位3 — ロケール固定の再起動のあとに待ち、`shutdown` のあとで起動状態を読み返して、落ちなかった
      デバイスを確認済みの固定として記録しないようにする。あわせて、固定が書き込むと決めたときに情報
      ログを1行出す。起動状態の判定は、plist の読み返しの代わりではなくその後ろに置きました。これにより
      判定は確認を取り下げる方向にだけ働きます。別のロケールを読み返したデバイスは、今までどおり run を
      はっきり失敗させます。判定を読み返しの代わりに置いていたら、shutdown の拒否がその失敗を覆い隠し
      かねませんでした。固まった CoreSimulator では、起動の一覧の読み取りも同時に失敗するからです。
      起動とその待機は、判定によらず必ず
      実行します。一覧を読めなかったデバイスは実際には停止していることがあり、呼び出し側はその直後に
      インストールを始めるからです。
