## はじめに

シナリオが変数に保持している値を加工する `eval` ステップを追加します。
ステップは元になる文字列と、`split`、`filter`、`sort`、`pick`、`join` などの操作の並びを受け取り、結果を `${vars.*}` に格納します。
操作は固定の語彙から選びます。
パイプラインの途中で値は文字列かリストのどちらかであり、型のつながりは実行前にローダーが検査します。
結果がリストなら、コンパクトな JSON 配列テキストとして格納します。
入力のどれかが `${secrets.*}` に由来する場合、結果は成果物のマスキング対象に加わります。
したがって、派生した値が平文のままレポートに載ることはありません。

## 動機

シナリオが実行時の値を取り込む手段は、現在四つあります。
`extract` 修飾子は要素の `value`、`label`、`identifier` を読みます。
`http` ステップはレスポンス本文、または JSON の一つのフィールドを格納します。
`email` ステップは正規表現でコードを取り出します。
`generate` ステップは乱数や日時の値を計算します。
どの手段も、値を届いたままの形で格納します。
格納した値を変えるステップは存在しません。

ターゲットが表示する値と、後続のステップが必要とする値は、しばしば一致しません。
カート画面が `Apple, banana ,Cherry` という一つのラベルを表示し、シナリオは整列して空白を除いた項目を検証したい、あるいは二番目の項目を検索欄に入力したいとします。
バナーが `Order #A-1042 confirmed` と表示し、次の画面で必要なのは `A-1042` だけだとします。
二つの部分からパスワードを組み立てたい場合もあります。
現状、作成者に残る選択肢は三つです。
文字列全体を検証して壊れやすい比較を受け入れるか、ロジックを外部スクリプトに移してシナリオファイルから流れを隠すか、検証をあきらめるかです。

この項目が入ると、シナリオは一つの `eval` ステップにそのロジックを書けます。
シナリオファイルには取り込みから利用までの全ステップが現れ、実行レポートには生成された値が残ります。
観測できる変化は、取り込んだラベルを分割して一要素を検証するシナリオが、補助スクリプトも作業用サービスへの `http` 往復も要らなくなることです。

## 詳細設計

`eval` という名前は、任意のコードを実行するステップを連想させます。
実際は違います。
`eval` は文字列とリストに対する固定の操作語彙を実行するだけで、シナリオが操作を追加することはできません。
形は `generate`（[BE-0377](../BE-0377-dynamic-value-generation/BE-0377-dynamic-value-generation-ja.md)）にならいます。
一つのステップが、一つの `into: { var }` を持ち、`vars.<name>` に値を格納します。

### 記述の形

```yaml
- tap: { id: cart.open }
  extract:
    items: { sel: { id: cart.summary }, prop: label }   # "Apple, banana ,Cherry"

- eval:
    from: "${vars.items}"
    ops:
      - split: { by: "\\s*,\\s*", regex: true }
      - filter: { notEmpty: true }
      - sort
    into: { var: sortedItems }                           # ["Apple","Cherry","banana"]

- eval:
    from: "${vars.sortedItems}"
    ops: [json, { pick: first }]
    into: { var: firstItem }                             # Apple

- eval:
    from: "${secrets.API_TOKEN}"
    ops: [{ substring: { start: 0, end: 8 } }]
    into: { var: tokenPrefix }                           # すべての成果物でマスクされる
```

フィールドは次のとおりです。

- **`from`**：必須の文字列です。ほかのステップのフィールドと同じ `${...}` 補間を使えます。二つの変数をつなぐだけなら操作は要りません。`from: "${vars.a}-${vars.b}"` が結合済みの文字列を作るからです。
- **`ops`**：空でないリストです。各要素は直前の要素の結果に対して実行されます。引数のない操作（`trim`、`json`、`count`、`unique`、`reverse`、`sort`）は文字列だけで書きます。そのほかの操作は、キーが一つのマッピングです。
- **`into`**：`{ var: <name> }` です。`generate` と `totp` が使う `VarTarget` と同じです（`bajutsu/common/scenario/models/actions/var_target.py`）。すでに値のある名前に書くと、`extract` や `generate` と同様に値を置き換えます。
- **`into` には `{ vars: [<name>, ...] }` も書けます**。リストの結果を、先頭から順に複数の変数へ振り分けます。最初の要素は、最初の名前の変数が受け取ります。ローダが `vars` を受け付けるのは、パイプラインがリストで終わるときだけです。空の名前リストと重複した名前は拒否します。リストが `vars` より長ければ、余った要素は使いません。リストが短ければステップを失敗させます。値の入らない変数を残すと、後のステップで無関係な不一致として表面化するからです。この形は実装の途中で加えました。1つのラベルを複数の値に分けるシナリオが、要素ごとに `eval` ステップを1つずつ書かずに済むようにするためです。

### 値と型

パイプラインの値は、文字列、または文字列のリストです。
`from` は文字列としてパイプラインを始めます。
最後の値は次のように格納します。

- 文字列は、そのまま格納します。
- リストは、`["a","b"]` のようなコンパクトな JSON 配列テキストとして格納します。レンダラーは `json_text`（`bajutsu/common/assertions/dict_match.py`）で、`extractBody` と同じです。格納したリストは取り込んだ JSON 本文と同じ見た目になり、非 ASCII の文字はエスケープされません。

後続の `eval` は、`json` 操作でそのテキストをリストに戻します。
戻す操作を明示させるのは、推測を避けるためです。
JSON に見えるだけの文字列は、作成者が指示するまで文字列のままです。

### 操作

| 操作 | 形 | 入力 → 出力 | 動作 |
|---|---|---|---|
| `split` | `split: ","` または `split: { by, regex? }` | 文字列 → リスト | 文字列の区切りで分割します。`regex` が true なら正規表現で分割します。空の区切りはロードエラーです。 |
| `join` | `join: "-"` | リスト → 文字列 | 区切りを挟んで要素をつなぎます。空の区切りも指定できます。 |
| `filter` | `filter: { <述語>, not? }` | リスト → リスト | 述語を一つだけ指定し、満たす要素を残します。述語は `matches`（正規表現、任意の位置で検索）、`equals`、`contains`、`notEmpty` です。`not: true` なら満たさない要素を残します。結果が空のリストでも正常です。 |
| `pick` | `pick: first`、`last`、または添字 | リスト → 文字列 | 要素を一つ取り出します。添字は 0 から数える非負の整数です。 |
| `count` | `count` | リスト → 文字列 | 要素数を十進のテキストで返します。 |
| `sort` | `sort`、`sort: asc`、または `sort: { order, numeric? }` | リスト → リスト | Unicode のコードポイント順に並べます。`order` は `asc`（既定）か `desc` で、それ以外の値はロードエラーです。`sort: desc` は、`sort` の後に `reverse` を置いた場合と同じ結果になります。`numeric: true` なら十進の数値順に並べ、数値でない要素があると失敗します。 |
| `unique` | `unique` | リスト → リスト | 重複を除き、各要素の最初の出現を残します。 |
| `reverse` | `reverse` | リスト → リスト | 順序を逆にします。 |
| `json` | `json` | 文字列 → リスト | JSON 配列を解析します。文字列の要素はそのまま、そのほかの要素は `json_text` で文字列にします。 |
| `regex` | `regex: { pattern, group? }` | 文字列 → 文字列 | 最初のマッチのキャプチャ `group`（既定は 0）を返します。 |
| `replace` | `replace: { find, with, regex? }` | 文字列 → 文字列 | 出現するすべてを置き換えます。 |
| `substring` | `substring: { start, end? }` | 文字列 → 文字列 | `start` から `end` までの文字を取り出します。どちらも 0 から数えます。 |
| `trim` | `trim` | 文字列 → 文字列 | 前後の空白を取り除きます。 |
| `case` | `case: lower` または `upper` | 文字列 → 文字列 | 英字の大文字と小文字を変換します。 |

操作がリストの各要素に作用することはありません。
各要素の空白を除きたいシナリオは、最初の例のように、空白を含めて分割できる正規表現で分割します。

### ロード時と実行時の検査

ローダーは各 `ops` を順にたどり、`from`（文字列）から最後までの型のつながりを追跡します。
型に合わない操作は、シナリオのロードエラーになります。
たとえば `regex` の直後の `join` がそうで、エラーはステップと操作を名指しします。
ローダーはそのほかに、空の `ops`、空の `split` 区切り、述語が 0 個または複数の `filter`、負または整数でない添字、`asc` と `desc` 以外の `sort` の `order` を拒否します。
正規表現は、テキストに `${...}` トークンを含まなければロード時にコンパイルします。

操作の引数には、ほかのステップのフィールドと同じく `${vars.*}` と `${secrets.*}` のトークンを書けます。
トークンを含む引数はロード時に検査できません。
そのため実行時に、置換後のステップへ同じ検査をもう一度かけ、同じメッセージでステップを失敗させます。

次の場合、ステップは代替値を使わずに実行時に失敗します。

- `regex` のパターンがマッチしない、またはパターンにない `group` を指定した
- 添字がリストの範囲外である
- `substring` の `start` または `end` が文字列の長さを超える、あるいは `start` が `end` より後ろにある
- `json` の入力が JSON 配列でない
- `numeric: true` の `sort` が、十進数でない要素に当たった
- 入力または結果の文字列が 1,048,576 文字を超える、あるいは入力または結果のリストが 10,000 要素を超える（結果も検査するのは、`replace` や `join` が上限を超えて値を膨らませるのを防ぐためです）

失敗メッセージは、ステップ、操作の位置、操作を示します。
値は引用しません。
値が秘密値に由来する可能性があるからです。
空のリストは正常な結果です。
少なくとも一つの要素を期待するシナリオは、`count` と `assert` ステップでそれを検証します。

### 秘密値の扱い

実行は、既知の秘密値を隠すリダクター（`Redactor`、`bajutsu/common/evidence/redaction.py`）を通して証跡を記録します。
現状、その値の集合は実行の開始時に固定されます。
秘密値に由来する `eval` の結果は、新しい秘密値です。
元の値だけを隠しても、派生したテキストは見える状態で残ります。
そこで次の規則を加えます。**入力のどれかが秘密なら、結果も秘密である。**

- `from` または引数が `${secrets.*}` トークンを含むとき、入力は秘密です。`${vars.<n>}` トークンを含み、かつ実行が変数 `<n>` を秘密と印付けしているときも、入力は秘密です。
- 結果が秘密なら、ステップランナーは結果を実行の秘密集合に加えます。リダクターがすでに導出しているエンコード違いの形も含めます（[BE-0153](../BE-0153-encode-aware-secret-redaction/BE-0153-encode-aware-secret-redaction-ja.md)）。さらに `into.var` を秘密と印付けします。秘密でない結果は `into.var` の印を外します。変数が別の値を持つようになるからです。
- 登録は、ランナーがステップを記録する前に行います。ステップ自身のレポート行とトレースが、最初からマスク済みのテキストを示します。
- 結果は、どれほど短くても登録します。1 文字の秘密由来の結果は、以後の証跡でその 1 文字をすべてマスクするため、成果物が読みにくくなることがあります。この代償は受け入れます。長さの下限を設けると、秘密の断片が漏れるからです。
- 例外は `count` だけです。`count` の結果は要素数なので、入力の文字を一つも含みません。登録すると、以後のすべての成果物で数字一文字がマスクされます。この項目はリストの長さの検証に `count` を勧めているため、この場合は端の事例ではなく、よくある使い方です。`count` の結果は秘密として扱わず、`into.var` の印も外します。

### コア層への変更

秘密値の集合は、実行の開始時に複数の `Redactor` へ渡される `list[str]` です（`bajutsu/common/runner/pipeline.py`、`bajutsu/common/runner/pool.py`）。
`Redactor` は `__init__` で一度だけ検索語を組み立てます。
そのうちの一つ `result_redactor` は、frozen なシナリオランナーのフィールドです。
`workers > 1` のとき、`ThreadPoolExecutor` がこのランナーをワーカー間で共有します。
ランナーがシナリオごとの可変状態を持たないので、共有は安全です。
この設計はその性質を保ちます。

そのため、派生した秘密値はシナリオ単位で扱います。
実行全体で一つの可変集合を持つと、あるシナリオの派生値が、別のシナリオの証跡に現れる同じテキストまでマスクします。
シナリオごとの集合を共有の `result_redactor` が知らなければ、`<sid>/result.json` とマニフェストに値がマスクされずに残ります。
変更は、この二つをどちらも避けます。

1. `Redactor` に `with_values(extra)` を加えます。元の値に `extra` を足した新しい `Redactor` を返すメソッドです。共有のインスタンスは不変のまま残ります。
2. シナリオごとの実行状態に、`bindings` と並んで `derived_secrets`（生の値）と `secret_vars`（秘密と印付けした変数名）を加えます。この状態を扱うのは一つのワーカースレッドだけなので、ロックは要りません。ステップランナー（`bajutsu/common/orchestrator/loop/_step_runner.py`）が、`eval` ステップの秘密判定を置換前のステップから計算します。ハンドラーは置換後のテキストしか見られないからです。
3. シナリオの証跡を書き出すすべての箇所が、`redactor.with_values(derived_secrets)` でマスクします。対象は、トレース、ネットワークログ、`<sid>/result.json`、`manifest.json` のそのシナリオの項目です。シナリオの結果はマニフェストの書き出しのために `derived_secrets` をメモリー上で持ちますが、シリアライズはしません。

マスキングは `eval` ステップから始まります。
それより前に書き出した成果物は書き直しません。

### レポート

ステップランナーは、`generate` と同様に、生成された値をステップの結果へ写します（`outcome.generated`、`_step_runner.py`）。
パイプラインが失敗した場合、変数は設定されません。
マニフェストには `generated` フィールドがすでにあります（スキーマ v8）。
この項目がマニフェストのバージョンを上げることはありません。
秘密由来の結果は、リダクターを通ってマスクされた状態で現れます。

### コード生成、REPL、ドキュメント

`eval` は Bajutsu のランナーで動き、XCUITest、Playwright、UI Automator に相当するものを持ちません。
各コード生成器は、`generate`、`http`、`totp` と同様に、このステップにラベル付きの `// TODO` を出力します（[BE-0026](../BE-0026-shrink-unsupported-syntax/BE-0026-shrink-unsupported-syntax-ja.md)）。
REPL セッションは、`generate` の後と同様に、`eval` の後で格納した値を表示します（`bajutsu/repl/session.py`）。
表示の前に、値をリダクターへ通します。
`eval` はアプリに触れないため、`bajutsu/common/orchestrator/loop/app_crash_latches.py` の `OBSERVES_APP` には加えません。
`OBSERVES_APP` は、成功がアプリの応答を示すステップ種別だけを挙げる集合です。後から加わった種別は、既定では何も示さない扱いになります。
したがって、この集合を編集する必要はありません。

### 実装時の決定

実装の過程で、設計が決めていなかった点や、古いコードを前提に書かれていた点を次のように決めました。

| 論点 | 決定 |
|---|---|
| 置換を行う場所 | `_interp_step` は `eval` フィールドを書かれたまま残し、ハンドラーが置換します。置換後のステップをそこで再検証すると、secret のテキストを引用した検証エラーが出るからです。 |
| 値が束縛されていない `${...}` | ステップを失敗させ、そのトークンを名指しします。`${vars.x}` という文字列のまま処理すると、綴りの誤りが後の検証まで表に出ないからです。 |
| フラグ引数（`regex`、`not`、`numeric`） | リテラルの真偽値だけを受け付けます。文字列と添字の引数はトークンを受け付けます。 |
| `regex: true` の `split` | 結果には一致と一致の間のテキストだけを入れます。Python の `re.split` はキャプチャグループをリストに混ぜるからです。 |
| `ops` の途中にある `count` | 結果が secret かどうかは、`from` と、最後の `count` より後の引数だけで決めます。 |
| 短い派生値 | 1文字の値をシリアライズ済みの JSON に対して置換すると、`1.5` が `[REDACTED].5` になります。`Redactor` は派生値を設定済みの値と分けて持ち、自由文と構造の文字列値にだけ適用します。シリアライズ済みの文書全体には適用しません。 |
| マニフェストとレポート | シナリオの終了時に、ランナーが結果の値を含むテキスト（失敗理由、各ステップの理由と生成値、各アサーションの詳細）で派生値をマスクします。`result.json`、マニフェスト、レポート、CI の注記、Webhook はどれもこのテキストを読むので、マスクはシナリオ単位に保たれます。レポートのリンクが解決できるよう、成果物のパスはマスクしません。 |
| クラッシュ時の再試行 | シナリオごとに1つの `DerivedSecrets` がすべての試行にまたがります。再試行で借りたシンクは、前の試行が導いた値を最初からマスクします。クラッシュの証跡とドライバーのトレースもその値をマスクします。 |
| マスクできないシンク | `add_secret_values` は任意ではなく `EvidenceSink` プロトコルの一部です。このメソッドを持たない新しいシンクは、値を平文で書く代わりに型検査で失敗します。 |
| REPL | シェルは `${secrets.*}` を束縛しないので、secret を名指しする `eval` は未束縛のトークンとして失敗します。secret が出力に届くことはなく、シェルにリダクターは要りません。 |
| 正規表現の計算量 | 期限は加えていません。下の「レビューで確認したい点」のとおり、サイズの上限だけが歯止めです。 |

### 対象外

- **リストの各要素へのサブパイプライン適用**（`each` 操作）。語彙を平らに保つと、型のつながりを検査しやすくなります。正規表現で表せない要素ごとの操作が必要になった時点で加えます。
- **算術演算**（`add`、`sub`、`mul`）。小数の丸めと数値の書式を決める必要があります。別の項目として、同じ `ops` に加えられます。
- **格納したリストの反復**。`forEach` が歩くのは UI 要素だけです。リスト変数に対する `forEach` は、この項目に続く別の項目とします。
- **秘密値の遡及マスキング**。`eval` ステップより前に書いた証跡は、書いたままです。
- **`extract`、`http`、`email` に由来する派生値**。ターゲットから読んだ値を秘密でないものとして扱う現状は、変わりません。

## 検討した代替案

| 代替案 | 採用しなかった理由 |
|---|---|
| 操作ごとに一つのステップ（`split`、`join`、`filter`） | 操作の間に必ず変数が要るため、中間の変数名がシナリオにあふれます。操作が増えるたびにステップ種別も増えます。パイプラインなら、ステップ種別を増やさずに操作を足せます。 |
| トークン内の関数呼び出し（`${join(split(vars.x, ","), "-")}`） | `interp.py` の平らな参照を式のパーサーに変えてしまいます。[BE-0377](../BE-0377-dynamic-value-generation/BE-0377-dynamic-value-generation-ja.md) が同じ理由で同種の案を棄却しています。 |
| JMESPath や jq のような汎用の式言語 | [BE-0033](../BE-0033-scenario-variables-control-flow/BE-0033-scenario-variables-control-flow-ja.md) は、シナリオにできることの上限が弱まるとして汎用言語を棄却しました。[BE-0440](../BE-0440-http-step-field-extraction/BE-0440-http-step-field-extraction-ja.md) は、この種のパーサーが現在は直接の依存に入っていないと確認しています。 |
| 文字列操作だけ（`regex`、`substring`） | 取り込んだラベルを項目に分ける、項目をつなぐ、項目を絞り込む、という依頼の中心を表せません。 |
| リストを区切り文字でつないだ文字列として格納する | 区切りを含む要素があると、往復が壊れます。JSON 配列テキストなら、読み方が一通りに決まります。 |
| リストを一つのパイプライン内に限り、格納は文字列だけにする | 一度分割して、後続のステップで別々の要素を取り出す、という使い方ができません。 |
| `${secrets.*}` を `eval` の入力として禁止する | もっとも単純な規則です。ただし、二つの部分から認証情報を組み立てる使い方や、接頭辞を付けたトークンの送信も塞ぎます。 |
| 派生した秘密値に何もしない | 派生した値が平文でレポートに載ります。[BE-0153](../BE-0153-encode-aware-secret-redaction/BE-0153-encode-aware-secret-redaction-ja.md) と [BE-0331](../BE-0331-artifact-redaction-boundary/BE-0331-artifact-redaction-boundary-ja.md) の方針に反します。 |
| マッチしないとき空文字列を返す | 失敗が、後続ステップの無関係な不一致として現れます。決定性を最優先する方針に反します。 |
| 長さが下限未満の派生秘密値は登録しない | 秘密の短い断片が証跡に載ります。マスキングの目的を損ないます。 |

### レビューで確認したい点

- **正規表現のコスト**：Python の `re` モジュールにはマッチのタイムアウトがなく、入れ子の繰り返しを持つパターンは長い入力で長時間かかることがあります。上の上限はすべての値の大きさを抑えますが、マッチにかかる時間は抑えません。作成者が書いたパターンのリスクを受け入れるか、評価器に期限を設けるかの選択です。
- **上限の値**：1,048,576 文字と 10,000 要素は出発点です。実際のシナリオが取り込む最大のラベルや本文に照らして確認します。
- **`generated` の再利用**：マニフェストのフィールド名は `generate` に由来します。再利用すればマニフェストのバージョンは上がりません。名前を改めれば二つのステップに正確な名前がつきますが、バージョンが上がります。
- **短い秘密由来の結果**：秘密値に由来する 1 文字の結果は、そのシナリオの以後のすべての証跡でその 1 文字をマスクします（上のとおり `count` は除きます）。実際にレポートが読めなくなるなら、結果が一定の長さを下回るときに警告を出す手があります。
- **ステップ名**：簡潔さから `eval` を選びました。詳細設計の冒頭で、このステップがコードを実行しないことを断っています。レビューで任意の評価と読まれるなら、名前を見直します。
