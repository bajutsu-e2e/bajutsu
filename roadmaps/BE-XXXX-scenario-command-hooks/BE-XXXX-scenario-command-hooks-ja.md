## はじめに

本提案では、シナリオファイルのトップレベルに `hooks` ブロックを追加します。ブロックには外部コマンドの
リストが 2 つあります。`beforeScenario` と `afterScenario` で、そのシナリオ 1 本の前後にコマンドを実行します。

[BE-0491](../BE-0491-target-command-hooks/BE-0491-target-command-hooks-ja.md) は、ターゲットの
`targets.<name>.hooks` から、そのターゲットのすべてのシナリオの前後にコマンドを実行します。特定のアカウントを
用意するように、1 本のシナリオだけが必要とする準備を書く場所は、そこにはありません。本提案はシナリオ自身に
その場所を与えます。エントリのフィールド、出力ファイル、失敗時の扱いは BE-0491 と同じです。

シナリオ側のリストは、ターゲット側のリストの内側で実行します。シナリオの前ではターゲットのエントリが先に走り、
シナリオの後ではシナリオのエントリが先に走ります。

## 動機

BE-0491 が決めるのは、ターゲットがそのすべてのシナリオに向けてデータを用意する方法です。1 本のシナリオだけが
必要とするデータは扱えません。現状の回避策は 3 つあり、どれも適しません。

- **2 つ目のターゲット**：準備がターゲットに属するため、一度きりのシードがフック 1 件だけ違う 2 つ目の
  ターゲットになります。
- **`BAJUTSU_SCENARIO` で分岐する `beforeScenario` エントリ**：スクリプトが次に走るシナリオを調べ、
  そのシナリオの作業をします。シナリオが何を必要とするかという知識が、シナリオから離れたシェルスクリプトに
  置かれます。
- **`setup` の `http` ステップ**：リクエスト 1 本なら足ります。準備にファイルや 2 本目のリクエスト、
  応答による分岐が加わると足りなくなります。

3 つとも、シナリオを、それが依存する準備から引き離します。シナリオファイルを開いたレビュアーは、開始前に
何が必要かを読み取れません。別のプロジェクトへ写したシナリオは、準備を持たないまま届きます。

本提案が入ると、読者は 2 つの違いを確認できます。固有のデータを必要とするシナリオは、自身の
`hooks.beforeScenario` で宣言し、結果を `${hooks.<name>.<key>}` で読みます。そのシナリオが走るターゲットには、
その 1 本のためだけに存在するエントリがありません。

### BE-0036 を再び開くわけではない理由

[BE-0036](../BE-0036-utility-steps/BE-0036-utility-steps-ja.md) は `shell` / `exec` ステップを棄却しました。
任意のコマンドを走らせられるシナリオは、移植性とレビュー可能性を失うからです。`hooks` のコマンドも同じ代償を
負い、本提案はそれを 1 つの理由で受け入れます。1 本のシナリオに属する準備はシナリオの意味の一部なので、
別のスクリプトに探しに行くより、ファイルに見えているほうが読者の得になります。

コマンドはステップと 4 点で異なり、代償の範囲を限定します。

- **ステップではない**：コマンドは `steps`、`setup`、`cleanup` から離れた `hooks` に置きます。
  ステップの列は、ユーザーの操作と見え方だけを表し続けます。
- **判定に加わらない**：コマンドはアプリについて何も表明しません。前提または後始末が成り立たなかった場合に
  限って、シナリオを失敗させます。
- **レポートに見える**：各 hook フェーズは、コマンドのログとともに独立したブロックとして現れます。
- **worker が統制する**：コマンドを実行するか否かは worker のコマンドポリシーが決めます
  （「コマンドを実行してよいか」を参照）。

## 詳細設計

### シナリオの `hooks` ブロック

シナリオは、省略可能なトップレベルのフィールドを 1 つ得ます。

```yaml
name: checkout with an expired card
target: web
hooks:
  beforeScenario:
    - name: card
      cmd: "./scripts/create-expired-card.sh"   # $BAJUTSU_OUTPUT に cardId=... を書く
      timeout: 30
  afterScenario:
    - on: always
      cmd: "./scripts/delete-card.sh"           # $BAJUTSU_HOOK__card__cardId を読む
steps:
  - type: { text: "${hooks.card.cardId}", into: { id: checkout.card } }
```

ブロックが受け付けるのは `beforeScenario` と `afterScenario` だけです。シナリオは run ではないため、
`beforeRun` と `afterRun` を持ちません。どちらかを宣言したシナリオはロード時に失敗し、エラーは、run 単位の
コマンドは `targets.<name>.hooks` に属すると伝えます。

エントリのフィールドは、BE-0491 がシナリオ単位のリストに定めるものと同じです。

| フィールド | 意味 |
|---|---|
| `cmd` | コマンド。シェルと同じ規則で分割し、シェルを介さずに実行します。 |
| `use` | `cmd` の代わりに、worker が `namedCommands` に載せたコマンドの名前を書きます。エントリは両者のうち 1 つだけを設定します。 |
| `name` | BE-0491 のパターンに従う識別子。出力を読むエントリでは必須です。 |
| `cwd`、`env` | 作業ディレクトリと追加の環境変数。`cwd` はシナリオファイルのあるディレクトリを基準に解決します。 |
| `timeout` | コマンドに許す秒数。既定は 300 です。 |
| `on` | `afterScenario` のみ。`always`、`success`、`failure` のいずれかで、既定は `always` です。 |
| `mask` | true のとき、エントリの出力値を証跡でマスクします。既定は false です。 |

### ターゲットの hook との実行順

1 本のシナリオは次の順に実行します。

1. ターゲットの `beforeScenario` エントリを、宣言順に実行します。
2. シナリオの `beforeScenario` エントリを、宣言順に実行します。
3. デバイスの確保とアプリの起動を行います。
4. BE-0392 の `before` ステップ、`steps`、`expect`、`after` ルールを実行します。
5. 判定に一致する `on` を持つシナリオの `afterScenario` ルールを、宣言順に実行します。
6. 判定に一致する `on` を持つターゲットの `afterScenario` ルールを、宣言順に実行します。

2 つの階層は関数呼び出しのように入れ子になります。シナリオが用意したものは、ターゲットが用意したものの
内側にあるため、シナリオの後始末が先に走り、ターゲットのデータが既に消えている状況に出会いません。
シナリオが複数のターゲットを扱うときは、この列のうちターゲット側に BE-0491 の複数ターゲットの順序を適用し、
シナリオ自身のエントリは中心に置きます。

BE-0392 の `before` / `after` ステップは、アプリのセッションの内側に留まります。`hooks` のコマンドは
その外側で走ります。起動の前と、判定が出たあとです。コマンドはアプリの起動前にデータを用意できますが、
ステップにはできないため、2 つの仕組みは重なりません。

`preconditions.inheritSetup: false` を設定したシナリオは、BE-0491 の定めどおり、ターゲットの
`beforeScenario` と `afterScenario` を飛ばします。シナリオ自身の `hooks` は飛ばしません。このフラグは、
ターゲットが共有するものからシナリオを外す指定であり、シナリオ自身のエントリは共有物ではないからです。

### 名前、出力、トークン

BE-0491 の値の受け渡しの規則は、そのまま適用します。コマンドは `$BAJUTSU_OUTPUT` に `key=value` の行を書き、
後続のコマンドは `BAJUTSU_HOOK__<name>__<key>` として読みます。シナリオは `${hooks.<name>.<key>}` で読みます。

`name` は、1 本のシナリオから見えるエントリのあいだで一意でなければなりません。見えるエントリとは、
シナリオ自身のエントリと、シナリオが扱うターゲットのエントリです。別々の 2 本のシナリオが同じ名前を使って
かまいません。各シナリオの出力は、そのシナリオの内側に閉じるからです。ローダーは各トークンを静的に検査します。
見えている `beforeRun` または `beforeScenario` のどのエントリも指さないトークンは、ロードエラーです。

### 失敗と判定

BE-0491 の失敗の表は、そのまま成り立ち、1 点だけ追加します。

| 失敗する箇所 | 結果 |
|---|---|
| シナリオの `beforeScenario` エントリ | シナリオは `beforeScenario: <name>: …` で失敗し、起動とステップを飛ばします。一致する `afterScenario` ルールは、両方の階層で実行します。 |
| シナリオの `afterScenario` エントリ | 失敗は、成功したシナリオの判定になり、既存の失敗がある場合はその後ろに追記します。後続のルールは実行します。 |

ターゲット側の `beforeScenario` が失敗した場合も、シナリオ自身の `beforeScenario` エントリは飛ばします。
そのとき、シナリオ自身の `afterScenario` ルールは、開始したエントリに対応するものだけを実行します。
書かれなかった出力に後始末が作用することを防ぐためです。

### コマンドを実行してよいか

シナリオのコマンドは、ターゲットのコマンドと同じ worker ポリシーに従います。シナリオファイルと、ターゲットを
含む config は、同じ config source から届きます。config source は、アップロードされたバンドル、Git の
チェックアウト、ローカルのパスのいずれかです。
[BE-0492](../BE-0492-worker-command-execution-policy/BE-0492-worker-command-execution-policy-ja.md) は
config source ごとに判定するため、1 つの判定が両方を覆います。

`named` モードでは、シナリオの `cmd` エントリはターゲットの `cmd` エントリと同様に拒否され、`use` エントリは
実行されます。したがって、この worker は、インストール済みのスクリプトを名前で指すシナリオを受け入れ、
コマンドラインを書き下すシナリオを拒否します。本提案は、独自のポリシー軸を足しません。

`sandbox` モードでは、シナリオのエントリは、シナリオが最初に宣言したターゲットのコンテナで実行します。
コンテナは、BE-0491 の `hooks.sandbox` ブロックが定めます。

### コマンドを実行する場所と証跡

実行する場所は BE-0491 に従います。コマンドは、`bajutsu run` を実行するマシン上の `bajutsu run`
プロセスで走ります。Web UI のジョブでは、ジョブを確保した worker です。`run` と `audit` はシナリオ側の
リストを実行します。`record`、`crawl`、`repl` はシナリオファイルを実行しないため、どちらの階層も実行しません。

シナリオのコマンドの出力は、run ディレクトリの
`hooks/<list>/scenario/<scenario-index>/<name-or-index>.log` に置きます。`scenario` というディレクトリ名が、
BE-0491 のターゲット単位のログと区別します。マスクと生の領域の境界は BE-0491 の定めに従います。レポートは、
シナリオの hook フェーズを、由来の階層を示すラベルを付けた独立したブロックとして表示します。

### 基本原則

- **AI は判定しない**：hook はコマンドと終了コードです。実行にもゲートにも、大規模言語モデルの呼び出しは
  入りません。
- **決定性を優先する**：すべてのコマンドに上限つきの `timeout` があり、シナリオは固定の待機ではなく条件を
  待ちます。
- **アプリ非依存**：シナリオはプラットフォーム固有の仕組みを名指ししません。コマンドは runner から見て
  不透明で、実行するか否かは worker のポリシーが決めます。

### BE-0491 への依存

本提案は、BE-0491 が導入する hook ランナー、出力ファイル、ログのコピー、レポートのブロックの上に作ります。
BE-0491 の後に実装し、シナリオ側のスキーマ、ロード時のトークン検査、2 階層の実行順を足します。

## 検討した代替案

- **シナリオはターゲットの hook を名前で指し、コマンドは config に置く**：棄却しました。コマンドの定義が
  別ファイルにあるため、シナリオファイルだけでは読み切れないからです。ここでは、局所性のためにその代償を
  受け入れると決めました。worker が主に `named` モードで動くなら、`use` が同じ間接参照をすでに提供するため、
  この判断は逆転します。
- **シナリオの `steps` に `cmd` エントリを置く**：BE-0036 の理由で棄却しました。さらに、アプリの起動後に
  実行されるため、アプリが起動時に読むデータを用意できません。
- **BE-0392 の `before` / `after` がコマンドを受け付けるようにする**：棄却しました。これらのフェーズは
  起動後のアプリセッションの内側で動きます。シード用のコマンドは起動前に走る必要があります。
- **シナリオのリストがターゲットのリストを置き換える**：棄却しました。1 件足しただけのシナリオが、共有の
  エントリをすべて黙って落とします。共有のシードを書き忘れても、失敗は原因から遠い場所に出ます。
- **リストを `beforeRun` / `afterRun` と名付ける**：棄却しました。BE-0491 はこれらの名前を、run あたり 1 回だけ
  走るコマンドに使います。シナリオ単位の意味に再利用すると、1 つの語が 2 つの範囲を持ちます。
- **`cmd` の代わりにスクリプトファイルのパスを書く**：棄却しました。名前付きのファイルを実行することも、
  任意のプログラムを実行することに変わりなく、ポリシー上の問いは同じままです。それに `cmd` がすでに覆います。
