## はじめに

`serve` の UDID 検証用正規表現は先頭のハイフンを許可しており、クライアントから渡される `udid` が `-` で
始まりえます。本提案はこのパターンを厳格化し、UDID がサブプロセスへのフラグと誤認されないようにします。

## 動機

`bajutsu/serve/helpers.py:27` は `_UDID_RE = re.compile(r"^[A-Za-z0-9-]+$")` を定義しています。
`helpers.py:481` の検証は、この正規表現を使って、`serve` のリクエストボディから来た `--udid` トークンを
検証します。検証は、トークンを `bajutsu` のサブプロセス呼び出し（`run` / `record` / `crawl` / `doctor`）に
渡す前の段階で行われます。文字クラスはハイフンを、先頭を含むどの位置にも許可します。そのため、`-rf` や
`--config` のような値も、正当な UDID として通ります。

`serve` は検証済みトークンを、シェルを介さず単一の argv 要素として渡すため、古典的なシェルインジェクションは
成立しません。しかし、多くの CLI パーサ、とりわけ `idb` や `xcrun` は、先頭がハイフンの引数を位置引数
ではなくオプションとして扱います。そのため、細工した `udid` は、サブプロセスが呼び出す下流のツールに
フラグとして解釈される余地があります。

深刻度は Low です。攻撃者は、`serve` の `/api/run`（または `/api/record` / `/api/crawl`）に届く
リクエストを、まず RBAC・トークンのゲート（BE-0051）に通す必要があります。また、問題の引数はシェルでは
なく固定されたサブプロセス argv に渡ります。被害範囲は、任意コマンド実行ではなく、呼び出し先ツールでの
引数の誤認に留まります。

## 詳細設計

1. **`_UDID_RE` を厳格化する。** `^[A-Za-z0-9-]+$` から `^[A-Za-z0-9][A-Za-z0-9-]*$` に変更し、先頭文字を
   英数字に限定します。実在する UDID の形状は、新しいパターンでもすべて通ります。`simctl` のハイフン区切り
   UUID、物理デバイスの40文字の識別子、リテラルの `booted` のいずれも、`-` で始まらないためです。
2. **既存の検証呼び出し箇所は変更しない。** 対象は `helpers.py:481` と、その呼び出し元（`/api/run`、
   `/api/record`、`/api/crawl`、`/api/doctor` の各リクエストパス）です。修正は正規表現に閉じています。
   値がパターンに一致しない場合は、既存のバリデータ（`_valid_udid` 相当）がすでに値全体を拒否するためです。
3. **単体テストを追加する。** 先頭がハイフンの値（`-rf`、`--help` など）が拒否され、実在する UDID の形状と
   `booted` は引き続き通ることを確認します。

## 検討した代替案

- **標準的な UUID の位置以外にハイフンを含む UDID をすべて拒否する。** 却下しました。バリデータに
  8-4-4-4-12 の UUID 形状をハードコードすることになり、将来 UDID の形式が変わった場合に前方互換性を
  損ないます。先頭ハイフンの禁止を超えるインジェクション対策上の利点もありません。
- **先頭のハイフンを拒否ではなく除去して正規化する。** 却下しました。クライアントが指定した値を黙って
  書き換えると、意図しない別デバイスへサブプロセスをルーティングしかねません。リクエスト自体を失敗させる
  ほうが安全で、デバッグもしやすくなります。
