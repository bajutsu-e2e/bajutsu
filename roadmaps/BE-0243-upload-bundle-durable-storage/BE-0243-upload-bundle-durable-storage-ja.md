## はじめに

[BE-0073](../BE-0073-serve-zip-bundle-upload/BE-0073-serve-zip-bundle-upload-ja.md) は、ブラウザの利用者が `.zip`（config、シナリオ、ビルド済みアプリバイナリ）をアップロードし、`serve` の稼働中の config としてバインドできるようにしました。このとき生成されるのは、`upload` 種別の config source レコードです（`{kind: "upload", filename, sha256, size}`、`bind_upload_config`、`bajutsu/serve/operations/upload.py`）。

[BE-0225](../BE-0225-config-project-hub/BE-0225-config-project-hub-ja.md)（**実装済み**）は、このレコードをそのまま基盤にしています。登録した**プロジェクト**は、`git` や `file` と同じように、`upload` 種別の source にもバインドできます。BE-0225 は、`{kind, filename, sha256, size}` というレコード自体を、耐久性を持って永続化します。ホスト型なら `projects` 行に、そうでなければローカルの JSON ストアに保存します。

どちらの項目も、`sha256` が指す**バイト列そのもの**を永続化していません。`POST /api/upload` は、zip を `state.uploads_dir` 配下の serve 専有ディレクトリへ展開するだけです。この場所は、一時的で、プロセス単位で、ローカルディスク限りです。BE-0073 自身の「スコープ外」節にも、「アップロードは一時的なものであり、永続化やバージョン管理は Git source の役割である」と明記されています。

BE-0225 は、この結果生じる壁に、出荷済みのコードですでにぶつかっています。`activate_project`（`bajutsu/serve/operations/projects.py`）は、`upload` 種別のプロジェクトを再度有効にする操作を拒否し、`409` を返します（「アップロード済みバンドルのプロジェクトへは切り替えられません。設定を再アップロードしてバインドしてください」）。アップロードを受け付けたレプリカが失われた時点で、再展開できる対象が何も残っていないからです。

この隙間は、BE-0073 が対象とする単一 Mac の Tier A 向け `serve` では問題になりません。プロセスもローカルディスクも 1 つだけで、セッションの途中で再起動が起きないからです。問題になるのは、ホスト型でマルチテナントの `server` バックエンドです（[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md)）。このバックエンドは、ロードバランサーの背後で**ステートレスかつオートスケールするレプリカ**として動くことを前提に設計されています。BE-0015 は、この理由からセッションとジョブを Postgres へ移しました（「セッションは再起動を越えて維持され、レプリカをまたいで有効である」）。ところが、アップロードされたバンドルの*内容*は、アップロードを受け付けたレプリカのローカルディスクにしか存在しません。

本項目は、この隙間を塞ぎます。`upload` 種別の source が持つ `sha256` の指すバイト列を、耐久性のあるものにし、どのレプリカからでも取得できるようにします。BE-0063 の Git source の内容は、commit SHA によって、すでに同じ性質を持っています。これにより、アップロードにバインドされた BE-0225 のプロジェクトは、`409` にぶつかる代わりに、レプリカの再作成を乗り越えられます。

## 動機

BE-0073 の「設計上一時的である」という判断には、デプロイ環境に関する 2 つの事実が、異なる角度から効いてきます。

1. **オートスケールとレプリカの再作成。**
   - `server` バックエンドでは、再デプロイ、クラッシュ、スケールダウンによって、レプリカが再作成されることがあります。アップロードを受け付けたレプリカとは別のレプリカに、リクエストが届くこともあります。これは、BE-0015 がセッションとジョブをデータベースへ移した理由そのものです。
   - 現在、展開済みのバンドルは、それを展開したレプリカの `state.uploads_dir` にしか存在しません。このディレクトリは `ServeState` のフィールドで、プロセス内のローカルディスク上にあります。
   - 別のレプリカや、再起動後の同じレプリカに届いた run リクエストは、materialize する対象を何も見つけられません。
2. **BE-0225 は、この壁に、出荷済みのコードですでにぶつかっています。**
   - BE-0225 の `ProjectRegistry`（`bajutsu/serve/project_registry.py`）は、プロジェクトの config source レコードを、耐久性を持って永続化します。`upload` 種別のプロジェクトなら、`{kind: "upload", filename, sha256, size}` を、`projects` 行（ホスト型の場合）かローカルの JSON ストア（データベースがない場合）へ保存します。
   - Git にバインドされたプロジェクトを後で開き直すと、必要なレプリカ上で、保存済みの commit SHA から再度 clone します。アップロードにバインドされたプロジェクトを開き直そうとしても、再 materialize できる対象が何もありません。そのため `activate_project` は、これを頭から拒否します。`kind == "upload"` は、常に `409` を返します。
   - BE-0225 がすでに耐久性を持って保存している `sha256` は、その指すバイト列を取得するための、内容アドレス方式の正しい鍵です。レコードの形は何も変える必要がありません。ただ、そのバイト列を今のところどこにも耐久性を持って書き込んでおらず、鍵が解決する先が存在しません。

運用上の注意点が、BE-0063 だけでなく、本項目にも直接関わってきます。Git source のキャッシュルート解決（`bajutsu/config_source.py` の `_default_cache_root()`）は、`XDG_CACHE_HOME` の下を解決します。無ければ `Path.home() / ".cache"` にフォールバックします。このフォールバックは、外部から与えられたユーザー ID（UID）で動き、その UID に対応する `/etc/passwd` のエントリも `HOME` もないコンテナでは、実行時に例外を投げます。

`HOME` を書き込み可能な任意のパスへ明示的に設定すれば、この問題は完全に避けられます。キャッシュディレクトリの木は、必要に応じて作成されるため（`mkdir(parents=True, exist_ok=True)`）、あらかじめ存在している必要はありません。Git source を有効にするホスト型デプロイは、この理由から、すでに `HOME` を明示的に設定しているはずです。

後述の単位 2 では、本項目自身のローカル materialize 先ディレクトリを、この同じキャッシュルートへ移します。新しいディレクトリは、BE-0063 の `gitsrc` キャッシュと `.../bajutsu/` の下できょうだいになります。現在は、BE-0073 が出荷した、`--runs` を基準にした `state.uploads_dir` のデフォルトです。移すと、アップロードのキャッシュも、同じ前提を引き継ぎます。

これは、見落としではなく、意図したトレードオフです。ホスト型の `server` デプロイは、セキュリティ上の理由から、書き込み可能なパスをあらかじめ絞った小さな集合に制限して運用することが多いからです。運用者は、Git source のために、キャッシュルートを 1 つ用意しています。Git checkout もアップロードの展開先も、その下へ集約すれば、allowlist を最小限に保てます。代案は、`--runs` を基準にした 2 つ目の書き込み可能ディレクトリを、独自の権限管理ごと追加することです。

この修正は、コードベースがすでに 2 度採用している形をなぞるため、新しい仕組みを何も追加しません。

- **内容アドレス方式。** BE-0073 は、証跡のために zip の sha256 をすでに計算しており、`manifest.json` に記録します。BE-0225 は、それを `upload` 種別の source レコードの一部として、すでに永続化しています。このハッシュは、耐久性があり衝突しにくい鍵として、そのまま使えます。Git source にとっての、解決済み commit SHA と同じ役割です。
- **オブジェクトストレージの seam。** [BE-0204](../BE-0204-server-storage-gcs-support/BE-0204-server-storage-gcs-support-ja.md) は、`server` バックエンドに、認証済みの `ObjectStore`（`BAJUTSU_SERVER_STORE`、`s3://` / `gs://`）をすでに与えています。このストアは、レプリカより長生きし、どのレプリカからも読み取れる必要があるデータのためのものです。今日は、run のアーティファクト、シナリオ、visual baseline に使われています。アップロードされたバンドルの内容も同じ種類のデータであり、4 つ目の独自ストアではなく、同じ seam の背後に置くべきものです。

本項目は、pass/fail、runner、ドライバ、シナリオスキーマのいずれにも触れません。決定的な `run` より前の取得段階の配線にすぎないため、prime directive 1〜3（[CLAUDE.md](../../CLAUDE.md)）はそのまま成り立ちます。

AI provider・モデル設定の永続化にも触れません。これは、別に追跡されているギャップです（[BE-0184](../BE-0184-persist-serve-ai-provider-settings/BE-0184-persist-serve-ai-provider-settings-ja.md) の保留中の hosted DB バックエンド化）。

## 詳細設計

作業は、次の 3 つの単位に MECE に分かれます。

1. アップロード時の永続化。
2. `activate_project` の無条件な `409` を置き換える、オンデマンドの取得・展開フォールバック。
3. オブジェクトストレージを設定していない場合の段階的縮退。

config source の形を新設する必要はありません。BE-0225 は、`{kind: "upload", filename, sha256, size}` を、すでに耐久性を持って保存しています。本項目は、その `sha256` の指すバイト列を解決できるようにするだけです。

### 1. アップロード時に生の zip を内容アドレス方式で org 単位に永続化する

`bind_upload_config`（`bajutsu/serve/operations/upload.py`）は、`POST /api/upload` を扱います。現在の検証と展開の挙動は、そのまま変えません。一時ファイルへストリームし、検証し、`state.uploads_dir` 配下の新規ディレクトリへ展開します。

**`BAJUTSU_SERVER_STORE` が設定されている場合**には、`serve` の稼働中 config を切り替える `state.bind_upload(upload)` の**前**に、新しいステップを 1 つ挟みます。このステップは、生の（圧縮されたままの）zip バイトを、そのストアへ書き込みます。鍵は、すでに計算している sha256 から導きます。

鍵は、この seam が保存する他のオブジェクトがすべて使っているのと同じ、org 単位のプレフィックスの下にネストします。`artifact_prefix`・`scenario_prefix`・`baseline_prefix` は、いずれも `xxx_prefix(org_prefix(base, org))` という形で合成されます（`bajutsu/serve/server/object_store.py`、`_build_server_state` で配線）。これと同じ形で `upload_prefix` を定義すれば、鍵は `upload_prefix(org_prefix(base, org)) + f"{sha256}.zip"` になります。

`org_prefix` の下にネストすると、重複排除と解決は、1 テナントの範囲に留まります。他の兄弟ストアがすでに強制している分離境界と、一致します。org を問わない共有の名前空間にすると、ある org のアップロードが、内容が同一の別 org のアップロードと重複排除の対象になります。さらに、別 org のアップロードによって解決されうる状態にもなります。

展開済みツリーではなく生の zip を書き込む利点は、3 つあります。

- オブジェクトを小さく保てます。
- まだローカルにない `sha256` については、zip-slip・zip-bomb の検証を、レプリカが少なくとも一度は実際に走らせます（後述の単位 2）。たまたま最初に展開したレプリカだけが検証し、その結果を他のすべてのレプリカがそのまま再利用する、という形にはなりません。
- BE-0060 のエクスポートが run の束を単一の zip アーティファクトとして扱っている形に、合わせられます。

内容アドレス方式にすると、同一バンドルの再アップロードは、両方の層で no-op になります。

- オブジェクトストレージへの書き込みは、鍵がすでに存在するので、スキップされます。
- ローカルの展開も、単位 2 が sha256 で鍵付けするため、同じ理由でスキップされます。

これは、再度の `POST /api/upload` として来る場合でも、`activate_project` のフォールバック経由であっても、変わりません。

このオブジェクトストレージへの書き込みは、同期的かつブロッキングです。バインドより**前**に置きます。`bind_upload_config` は、書き込みが成功するまで `state.bind_upload(upload)` を一切呼びません。

書き込みは、ネットワークエラー、バケットへの到達不可、権限拒否などで失敗することがあります。その場合は、展開済みのローカルディレクトリを削除して、エラーを返します。既存の検証失敗の経路も、同じようにディレクトリを削除します。この時点で、共有状態には何も触れていません。`serve` の稼働中 config はリクエスト前のままなので、ロールバックすべきものがありません。

書き込みをバインドより前に順序づけると、この失敗経路が単純なまま保たれます。代案は、バインドを先にして、後で失敗したらロールバックする順序です。選んだ順序では、クライアントが受け取る結果は 2 つのどちらかです。耐久性のあるバイト列に裏付けられたバインド済み config か、エラーで状態は一切変わっていないか、のどちらかです。両者が食い違う状態には、なりません。

これは、run 完了後のエビデンスアップロードの best-effort な失敗処理（`bajutsu/object_store.py` の `upload_tree`）とは、意図的に異なります。あちらは、すでに確定した run の verdict が、アーティファクトアップロードの成否に依存してはならないために best-effort です。ここでは、まだ何も確定していません。best-effort な書き込みにすると、BE-0225 のプロジェクトを登録できてしまいます。そのプロジェクトの、すでに耐久性を持つ `{kind: "upload", sha256, ...}` というレコードは、何も書き込まれていない鍵を指すことになります。そのバンドル 1 つに限って、本項目が塞ごうとしている隙間が、気づかないうちに再現されます。耐久性を偽るプロジェクトレコードや、それを追い越して進んでしまう稼働中 config より、明確なアップロード失敗の方が安全です。

### 2. `activate_project` の upload 種別に対する `409` を、内容アドレス方式の取得・展開フォールバックに置き換える

この単位では、ローカルの materialize キャッシュの置き場所も移します。

`state.uploads_dir`（`bajutsu/serve/state.py`）は、今日、`--runs` を基準にしたきょうだいディレクトリをデフォルトにしています。`local` backend では `runs_dir.parent / "uploads"` です。`server` backend では、`_build_server_state` が一度も上書きしないため、たまたま素の `Path("uploads")` のままになっています。

本項目は、このデフォルトを、BE-0063 の Git checkout キャッシュのきょうだいへ変更します。両者は同じ `bajutsu` キャッシュ名前空間の下にあります。新しい場所は `<XDG_CACHE_HOME または ~/.cache>/bajutsu/uploads/` です。

`_default_cache_root()`（`bajutsu/config_source.py`）は、この解決ロジックを単独で再利用できる形では公開していません。`Path(...) / "bajutsu" / "gitsrc"` をそのまま返し、`gitsrc` という末尾が関数自体に焼き込まれています。これをそのまま呼んでアップロード用に使うと、`.../bajutsu/gitsrc/uploads/` に解決されます。Git キャッシュのきょうだいではなく、その配下になってしまいます。

修正は、共通の `XDG_CACHE_HOME`・`Path.home()` という前半部分を、専用のヘルパー `_bajutsu_cache_root() -> Path` に切り出すことです。このヘルパーは `.../bajutsu/` を返します。そのうえで、次のようにします。

- `_default_cache_root()` は `_bajutsu_cache_root() / "gitsrc"` になります。
- 新しいアップロードキャッシュのデフォルトは `_bajutsu_cache_root() / "uploads"` になります。

1 つの共通フォールバックルールの上に、2 つのきょうだいが乗る形です。代案は、どちらも劣ります。`_default_cache_root()` をそのまま再利用すると、パスを誤ります。ロジックを丸ごと複製すると、2 つのルールが食い違う可能性があります。

`state.uploads_dir` という名前と役割は、そのままです。`--root` とは別の、serve が所有するディレクトリであり、BE-0051 の封じ込め境界です。変わるのはデフォルトの置き場所だけです。その境界は、どの書き込み可能パスの上に乗っているかには依存しません。

`activate_project`（`bajutsu/serve/operations/projects.py`）に、`kind == "upload"` のときの 2 番目の解決経路を追加します。諦める前に、この経路を試します。

この経路と、単位 1 のローカル展開自体は、いずれも `state.uploads_dir` 配下の、固定された sha256 鍵付きディレクトリ（`state.uploads_dir / sha256`）を指します。Git source の checkout キャッシュについて、`materialize()`（`bajutsu/config_source.py`）がすでに使っている `<cache>/<host>/<owner>/<repo>/<sha>` という形を、なぞったものです。そのディレクトリがすでに存在していれば、展開はまったく行わず、既存のツリーをそのまま再利用します。`materialize()` の `if not root.exists(): _extract_into(...)` が、再 clone する代わりに、キャッシュ済みの Git checkout を再利用するのと同じ形です。

キャッシュミスのときにだけ、`activate_project` のフォールバックは、次のことをします。

1. source レコードの `sha256` を使い、プロジェクトの org に絞って、オブジェクトストレージから zip バイトを取得する。
2. そのパスへ展開する。
3. `bind_upload_config` がすでに適用している、zip-slip・zip-bomb・パス封じ込めの検証を、同じく走らせる。これは、activate のたびにではなく、レプリカごとに一意な `sha256` あたり 1 回だけ。
4. `bind_upload_config` が今日行っているのと同じ方法で、結果をバインドする。

オブジェクトストレージが設定されていない場合、あるいは鍵がそこにない場合にだけ、今日の `409` がそのまま残ります。

存在チェックだけでは、並行アクセスの下で安全にはなりません。同じ `sha256` に対してキャッシュミスが同時に起きる呼び出しが、2 つありうるからです。同時に走る 2 つの `activate_project` 呼び出しがその例です。あるいは、`bind_upload_config` 自身の展開が sha256 で鍵付けされた後で、それと競合する場合もあります。そのままでは、両方が `state.uploads_dir / sha256` へ直接展開し、互いに書きかけのツリーを目にします。

Git source のキャッシュでは、`materialize()` がこの競合を避けています。`bajutsu/config_source.py` の `_extract_into` が、きょうだいの一時ディレクトリへ展開してから、rename で本来の場所へ配置します。rename は原子的操作です。負けた側の呼び出しは、開始前にすでに `root` が存在するのを見つけるか、勝った側がすでに配置し終えているために自分の `rename` が失敗するか、のどちらかになります。後者の場合、その失敗をエラー扱いにせず、自分の展開結果を捨てます。2 つの展開は、同じ内容アドレス方式の鍵に対するもので、バイト単位で同一です。だから、これで安全です。

本単位が持ち込む 2 箇所の展開先は、どちらも、この同じ「一時ディレクトリへ展開してから rename」というパターンに従う必要があります。2 箇所とは、`bind_upload_config` 自身の展開と、`activate_project` のフォールバックです。鍵付きパスへ直接展開したのでは、同じ保証は得られません。

`sha256` でローカルのパスに鍵を付けると、`uploads_dir` は、耐久性のあるオブジェクトストレージの手前に立つ、実質的なキャッシュになります。これは、[BE-0063](../BE-0063-git-config-source/BE-0063-git-config-source-ja.md) のローカルで内容アドレス方式の Git checkout キャッシュ（`~/.cache/bajutsu/gitsrc/...`）が、リモートの origin に対して持っている関係と同じです。耐久性を持つのは、解決済みの SHA（Git の場合）や sha256（zip の場合）です。ローカルディスク上の checkout や展開済みツリーは、常に破棄可能で、そこから再現できます。

この単位の草案時点の案は、materialize のたびに、鍵を持たない新規ディレクトリへ展開する形でした。これでは、`uploads_dir` にこの性質は備わりません。同じレプリカが少し前に展開したばかりの `sha256` へ、同じプロジェクトを再度 activate するだけでも、オブジェクトストレージへの往復が毎回発生します。すでにローカルディスクにある内容に対して、検証のやり直しも毎回発生します。Git キャッシュのキャッシュヒット経路とは違う挙動です。

`sha256` によるキャッシュヒットは、単位 1 の「検討した代替案」が主張している検証を、弱めるものではありません。その主張とは、展開済みツリーを信頼するのではなく、materialize のたびに生の zip から再展開する、というものです。あの主張が扱っているのは、*別の*レプリカが展開・検証したツリーを、レプリカが信頼してしまう場合です。同じレプリカが、まったく同じ内容アドレス方式の鍵について、自分自身が検証したツリーを再利用する場合とは、話が別です。後者は、`materialize()` がキャッシュ済みの Git checkout について、すでに置いているのと同じ信頼境界です。

**`release_upload` への影響。** `ServeState.release_upload()`（`bajutsu/serve/state.py`）は、新しい config がバインドされるたびに、バインドされていたアップロードのディレクトリを無条件に `shutil.rmtree` します。1 バインドにつき 1 つの使い捨てサンドボックスという今日の設計に対しては、正しい挙動です。sha256 鍵付きのキャッシュがあると、同じ呼び出しが、切り替えのたびにキャッシュを消してしまいます。本単位が持ち込む再利用が、無になります。別のプロジェクトへ切り替えてから元へ戻すだけで、何も変わっていないのに、同じバンドルの再取得・再展開が毎回走ります。

そこで、`release_upload` は、展開済みツリーの削除をやめる必要があります。`state.upload`・`state.cwd`（いま何がバインドされているか）をクリアする役割は、そのまま残します。ディスク上のキャッシュの寿命は、個々のバインドから切り離します。掃除するとしても、ローカルキャッシュを統べる保持ポリシーに委ねます（後述の「保持期間」を参照）。config をバインド・アンバインドする操作が、Git source の `~/.cache/bajutsu/gitsrc/...` checkout キャッシュを一切掃除しないのと、同じです。

**起動時の一掃処理への影響。** `serve()`（`bajutsu/serve/__init__.py`）は現在、起動のたびに、`uploads_dir` ツリー全体を無条件に `shutil.rmtree` します。そのコメントが述べている理由は、起動時には何もバインドされていないので、前のプロセスから残ったディレクトリはただの無駄だ、というものです。

この理由づけは、バインドが外れた時点で意味を失う、名前のない `tempfile.mkdtemp` のディレクトリを前提にしたものです。本単位によって、すべてのエントリが内容の `sha256` で名付けられるようになると、この理由づけは当てはまりません。前のプロセスから残ったディレクトリは、孤立したごみではありません。少し前に展開したばかりのものと同じだけ有効なキャッシュエントリであり、Git checkout キャッシュのエントリが `serve` の再起動をまたいで持っているのと、同じ信頼境界を持ちます。

起動のたびに消すと、同じレプリカの再起動のたびに、すでにディスク上にある `sha256` を再取得・再展開させることになります。本項目が塞ごうとしている問題、つまり再起動によってローカルの状態が失われることを、より小さな規模で再現してしまいます。したがって、この一掃処理は取り除きます。Git source 自身のキャッシュを `serve` の起動時に何も一掃しないのと、同じ扱いです。

この仕組みによって、`activate_project` は、自分自身が受け取っていないバンドルについても、新しく起動した、あるいはこれまでと異なるレプリカ上で成功します。すでに `sha256` をディスク上に持っているレプリカは、再度の activate で、オブジェクトストレージに触れる必要が一切なくなります。ディスク上のコピーは、以前の activate によるものでも、直前の再起動より前からのものでも構いません。

### 3. オブジェクトストレージを設定していない場合の段階的縮退

`BAJUTSU_SERVER_STORE` を設定していないローカル `serve` では、機能面での挙動はまったく変わりません。これはデフォルトの構成で、ホスト型以外のすべての Tier A・セルフホストのデプロイが該当します。

- アップロードは、BE-0073 と BE-0225 が今日出荷しているとおり、一時的なままです。
- `activate_project` は、`upload` 種別のプロジェクトを、同じ `409` で拒否し続けます。

これは、任意のストア（[BE-0204](../BE-0204-server-storage-gcs-support/BE-0204-server-storage-gcs-support-ja.md)）や設定（[BE-0184](../BE-0184-persist-serve-ai-provider-settings/BE-0184-persist-serve-ai-provider-settings-ja.md)）について、すでに確立されているゼロコンフィグの前例と一致します。耐久性を持ち、レプリカをまたいで解決できるようにする仕組みは、加算的です。運用者が、アーティファクト・シナリオ・baseline のためにオブジェクトストレージの seam をすでに選んでいる場合にだけ、働きます。

ただし、単位 2 による `state.uploads_dir` のデフォルトを、共有の `.../bajutsu/` キャッシュルートへ移す変更だけは、例外です。これは無条件に適用されます。使い捨てのサンドボックスがどの書き込み可能パスの上に乗るかという話であり、耐久性の話ではないからです。ゼロコンフィグの `serve` も、挙動には他に何も変化がないまま、allowlist を小さく保てるという利点を受け取ります。

### 保持期間

内容アドレス方式にすると、org 単位の自然な重複排除が得られます。同じバイト列の再アップロードは、書き込みを伴わない no-op です。実際の削除は、バケット自身の lifecycle policy に委ねます。これは、`bajutsu/object_store.py` のモジュール docstring が、この seam が支えるすべての URI アドレス方式のストアを統べる保持機構として、すでに明記しているものと同じです。

`state.uploads_dir`（単位 2）配下の、sha256 で鍵付けされたローカルキャッシュも、同じく無統治のままにします。何も掃除しません。Git source 自身のローカル checkout キャッシュ（`~/.cache/bajutsu/gitsrc/...`）にも削除の仕組みがないという前例に、合わせるものです。

新しい保持や garbage collection のコードは、ローカル・オブジェクトストレージのどちらにも追加しません。

## 検討した代替案

- **zip（または展開済みツリー）を Postgres の BLOB として保存する。** 見送りました。
  - BE-0015 のスキーマは、大きなバイナリのペイロードを、すでにデータベースの外に置いています。アーティファクト、シナリオ、baseline はいずれも、BE-0204 でオブジェクトストレージへ移り、テーブルには入れていません。
  - 数メガバイトのアプリバイナリは、Postgres が不向きなペイロードの形です。
  - もう一つのインフラ依存を避けることより、既存のストレージ seam との一貫性の方を重視しました。デプロイは、そのインフラ依存をすでに持っています。
- **ローカルのアップロードキャッシュを `--runs` 基準のまま、BE-0073 が出荷した `state.uploads_dir` のデフォルトどおりにしておく。** 見送りました。
  - ホスト型の `server` デプロイは、セキュリティ上の理由から、書き込み可能なパスをあらかじめ絞った小さな集合に制限して運用することが多いためです。
  - Git source は、すでに書き込み可能なルートを 1 つ必要としています（`HOME`・`XDG_CACHE_HOME`、`~/.cache/bajutsu/gitsrc/...` 用）。
  - アップロードを `--runs` 基準の 2 つ目のルートに置いたままにすると、その集合を広げてしまいます。単位 2 で、Git の checkout と同じ `.../bajutsu/` キャッシュ名前空間の下に内容アドレス方式で置くようにしても、得るものがありません。
  - 運用者が一度用意するキャッシュルート 1 つの方が、独立に用意する 2 つよりも、allowlist として小さく済みます。
- **生の zip ではなく展開済みツリーを永続化する。** 見送りました。展開済みツリーは、より大きなオブジェクトになります。1 つではなく、多数の小さな鍵になります。また、将来の materialize が、展開時にしか走らない zip-slip・zip-bomb の検証をスキップしてしまう可能性があります。materialize のたびに生の zip から再展開すれば、その検証を一度だけ信頼するのではなく、常に効かせ続けられます。
- **永続的なシナリオ保存を、BE-0073 が当初意図していたとおり Git source だけに限定する。**
  - 再利用可能でバージョン管理されたスイートを望むチームにとっては、これが今も正しい答えです。この点は、本項目でも変わりません。
  - しかし、BE-0225 がすでに登録している場合には、力になりません。Git リポジトリを背後に持たない、一度限りのアップロードされたバンドルにバインドされたプロジェクトが、それでもレプリカの再起動を越えて生き残る必要がある場合です。
  - 2 つの source は、別々の問題を解いており、補完的な関係のままです。
- **出荷済みの `upload` 種別とは別に、新しく `zip` という config source 種別を導入する。** 見送りました。BE-0225 の `_KIND_TO_SOURCE` とフロントエンド（`serve.core.js` の `source.kind === 'upload'`）は、`upload` を、この形の source を表す唯一の識別子として、すでに扱っています。allowlist・UI・レジストリの全経路に通した、配線済みの識別子です。同じ形のデータに二つ目の名前を作れば、配線済みのその一本の経路を分断するだけで、得るものがありません。
- **BE-0225 のプロジェクトレジストリの永続化まで本項目の責務にする。** スコープの広げすぎとして見送りました。BE-0225 は、「どのプロジェクトがどの source レコードを指すか」と「そのレコードをどこに保存するか（データベース行かローカル JSON か）」を、すでに所有しています。本項目の役割はもっと狭く、すでに耐久性を持つ `sha256` が指すバイト列を、どのレプリカからでも解決できるようにすることだけです。両者を束ねると、BE-0225 が単独で実装しているレジストリの関心事に、オブジェクトストレージの関心事を結合してしまいます。

  す。ローカルの `state.uploads_dir` キャッシュは、ユニット 2 が述べる素の `sha256` ではなく、
  `<org>/<sha256>` で鍵付けしています。素の `sha256` は org を区別しない鍵であり、`server`
  backend では `state.uploads_dir` がすべての org で共有される一つのパスです。これは、ユニット 1
  がすでに `org_prefix` で org スコープにしているオブジェクトストレージの鍵とは対照的です。org
  セグメントがなければ、`activate_project` の取得・展開フォールバックは、あるプロジェクトの
  source レコードに書かれているだけの `sha256`（実際にその org がアップロードしたと検証された
  ものではありません）に対して、*任意の* org がすでに展開済みのツリーへそのままキャッシュヒット
  してしまい、オブジェクトストレージ自体の org スコープを迂回してしまいます。これは BE-0015 の
  マルチテナント分離を破る問題です。この修正では、ローカルパスにも同じ `org_prefix` ヘルパーを
  適用しています（`state.uploads_dir / org_prefix("", org) / sha256`）。単一テナントの
  `default` org では no-op となるため、ローカル serve の挙動には影響しません。

  レビューの過程で見つかった、本文書の記述からのさらなる逸脱が 2 点あります。

  1. **ユニット 1 の、書き込み失敗時のロールバック。** 「詳細設計」には、オブジェクトストレージ
     への書き込みが失敗した場合「展開済みのローカルディレクトリを削除する」と書かれています。実
     装ではこれをやめました。ローカルのキャッシュエントリは、オブジェクトストレージへの書き込み
     が成功したかどうかに関わらず、有効で再利用可能な内容だからです。加えて、`materialize_bundle`
     が「自分がこのエントリを作成したかどうか」を返さなくなった後は（理由は次の点で述べます）、
     `bind_upload_config` からは、ストアへの書き込みが失敗した時点で同じ `sha256` に対する別の並行
     バインドがすでにそのディレクトリに依存しているかどうかを知る手立てがありません。無条件に削
     除すると、並行して進行中の別のバインドが依拠している共有キャッシュエントリを、その足元から
     引き抜いてしまう恐れがあります。これはまさに、ユニット 2 自身の「使い捨てのサンドボックスで
     はなく共有キャッシュである」という設計が、そもそも避けようとしていた種類の不具合です。
     `materialize_bundle` は、いったん存在するようになったディレクトリを二度と削除しないようにしま
     した。呼び出し側で後続の失敗が起きても、そのディレクトリには一切触れずに失敗するだけです。
     `bind_upload_config` は、自分自身の*検証*失敗（不正なバンドルはそもそも耐久性のあるエントリ
     を得ません）に対しては、引き続き後始末を行います。取りやめたのは、ストアへの書き込み失敗時
     の後始末だけです。
  2. **`activate_uploaded_project` の `sha256` は、単なる不透明なキャッシュキーではなく、信頼で
     きない入力です。** この値は、プロジェクトが保存している `source` レコードから来ており、この
     レコードはクライアントが `register_project`（BE-0225）を通じて自由に組み立てられます。
     `_validate_source` は `kind` しか検証しておらず、`sha256` の形は一切見ていません。「詳細設
     計」も、当初の実装も、これを `uploads_dir / sha256`（ファイルシステムパス）やオブジェクトス
     トレージの鍵の末尾へ変換する前に検証していませんでした。`../` を含む `sha256` を使えば、登録
     済みのプロジェクトレコードが `materialize_bundle` をアップロード用キャッシュの外へ、たとえば
     ユニット 2 で同じ `.../bajutsu/` ルートのきょうだいになった BE-0063 の Git checkout キャッシ
     ュへ誘導し、そこにある任意の `bajutsu.config.yaml` をバインドしてしまう可能性があります。エラ
     ーもログも一切残らないまま、BE-0051・BE-0108 の封じ込めを回避してしまいます。この修正では、
     `sha256` がフルの小文字 16 進ダイジェスト（`^[0-9a-f]{64}$`）であることを、パスや鍵へ渡す前
     に要求するようにしました。これは、Git source がすでに解決済みの commit SHA に対して行ってい
     る `_FULL_SHA_RE` によるガード（`bajutsu/config_source.py`）と同じ考え方です。不正な形の値
     は、そこから何かをファイルシステムパスとして展開しようとする対象としてではなく、「復元でき
     るものが何もない」場合（既存の `409`）として扱われるようになりました。
