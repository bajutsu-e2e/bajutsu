## はじめに

この項目は、コマンド hook の各エントリに省略可能な `when` ブロックを追加します。`when` ブロックには
シナリオのタグを書きます。シナリオのタグが `when` ブロックに一致すればエントリを実行し、一致しなければ
スキップします。一致の規則は、シナリオを選ぶときに `--tag` と `--exclude` が使う規則と同じです。
列挙したタグのどれか1つを持つシナリオが一致し、除外するタグは常に優先します。

`when` ブロックは、hook エントリを置ける次の2か所の両方で使えます。

- [BE-0491](../BE-0491-target-command-hooks/BE-0491-target-command-hooks-ja.md) が
  `targets.<name>.hooks` に追加する4つのリスト（`beforeRun`、`afterRun`、`beforeScenario`、
  `afterScenario`）です。
- シナリオ自身の `hooks` ブロックにある2つのリスト（`beforeScenario` と `afterScenario`）です。
  この2つのリストは、兄弟提案「シナリオの前後に実行する外部コマンドをシナリオ内に宣言する」が追加します。

シナリオ単位のエントリは、これから実行するシナリオを調べます。run 単位のエントリは、その run が実行する
シナリオ集合全体を調べ、どれか1つが一致すれば実行します。エントリの出力を読むシナリオは、そのエントリの
条件に自分自身が一致していなければなりません。一致しないシナリオは、ローダーが読み込み時に拒否します。

## 動機

ターゲットのコマンド hook はシナリオのためにデータを用意し、BE-0491 はすべてのエントリをすべての
シナリオで実行します。しかし実際のスイートでは、準備の多くが一部のシナリオにしか関係しません。決済の
シナリオには、決済サービスのテスト用アカウントが要ります。データベースに書き込むシナリオには、数秒かかる
リセットが要ります。オフライン時の振る舞いを確かめるシナリオには、ほかのシナリオでは使わないモック
サーバーが要ります。

無条件のエントリは、そのコストを必要としないシナリオにまで払わせます。5秒かかるデータベースのリセットを、
200件のシナリオそれぞれの前に実行する場合を考えます。データベースに触れるシナリオが20件しかない場合、約17分のリセットのうち15分は、
リセットを必要としないシナリオのために費やされます。サーバーを起動する `beforeRun` エントリは、CI の `--tag smoke` の段階でも
実行されます。その段階が、サーバーを使うシナリオを1つも選んでいなくても実行されます。

現在の回避策は3つあり、どれも判断を見えない場所へ移してしまいます。

- **`BAJUTSU_SCENARIO` で分岐するスクリプト**：スクリプトは、自分で持つ一覧とシナリオ名を照合します。
  シナリオ名を変えると、照合はエラーを出さずに外れます。スクリプトが何もしなかった場合でも、レポートは
  そのエントリを実行済みと表示します。
- **2つ目のターゲット**：2つ目のターゲットは、1つ目と hook エントリ1件だけが異なります。スイートは
  2回の `bajutsu run` に分かれ、CI はその2回を揃えて保守する必要があります。
- **シナリオごとのエントリの複製**：兄弟のシナリオ hook 提案を使えば、1つのシナリオが自分のエントリを
  宣言できます。その場合、決済のシナリオが20件あれば複製も20件になります。run 単位のエントリには、
  置き場所になるシナリオがそもそもありません。

これらを判断する手がかりは、シナリオがすでに持っています。
[BE-0034](../BE-0034-tags-selective-runs/BE-0034-tags-selective-runs-ja.md) はすべてのシナリオに
`tags` のリストを与えました。作成者はシナリオを選ぶために、`payments` や `db` といったタグをすでに
付けています。同じタグを読む hook の条件なら、名前の付け方を別にもう1つ用意する必要がありません。
読み手は、条件をそれが守るコマンドのすぐ隣で読めます。

この項目が入ると、読み手は観測できる2つの違いを確かめられます。ターゲットは決済用のデータ投入を、
`when: { tags: [payments] }` を付けて1回だけ宣言します。`--tag smoke` の run のレポートは、その
エントリを条件によってスキップしたものとして表示します。また、すべてのシナリオを流す run では、
`hooks/beforeScenario/` のログは決済のシナリオの分だけ書かれ、条件でスキップしたシナリオの分は書かれません。

## 詳細設計

### `when` ブロック

両方の階層のすべてのリストで、各 hook エントリは省略可能なフィールドを1つ受け付けます。

| フィールド | 型 | 意味 |
|---|---|---|
| `when.tags` | 文字列のリスト | このタグのどれか1つ以上を持つシナリオに一致します。省略または空のときは、何も制約しません。 |
| `when.exclude` | 文字列のリスト | このタグのどれか1つでも持つシナリオには一致しません。`exclude` は `tags` より優先します。 |

`when` のないエントリは、BE-0491 の定めどおりに実行します。両方のリストを空にした `when` ブロックは、
読み込みに失敗します。何も制約しない条件は、意図よりも誤記を示すからです。どちらのリストのタグも
単なる文字列です。一致の判定は文字列全体の比較で、大文字と小文字を区別します。グロブ、正規表現、
式の構文は持ちません。

```yaml
targets:
  web:
    hooks:
      beforeRun:
        - name: mock
          cmd: "./scripts/start-mock.sh"
          when: { tags: [offline] }            # run が offline のシナリオを選んだときに起動する
      afterRun:
        - cmd: "./scripts/stop-mock.sh"
          when: { tags: [offline] }
      beforeScenario:
        - name: account
          cmd: "./scripts/create-payment-account.sh"
          when: { tags: [payments], exclude: [readonly] }
      afterScenario:
        - on: always
          cmd: "./scripts/delete-payment-account.sh"
          when: { tags: [payments], exclude: [readonly] }
```

この規則は、`bajutsu/common/scenario/select.py` の `select_scenarios` が `--tag` と `--exclude` に
適用している規則と同じです。実装では、この規則をシナリオのタグに対する1つの述語として切り出し、
シナリオの選択と hook の条件の両方から呼びます。述語を1つにしておけば、2つの意味がずれていくことは
ありません。

### 条件が読むタグ

条件は、コンポーネントとデータを展開した後のシナリオの `tags` を読みます。`--tag` による選択も、
同じ展開後のタグを読みます。データ展開はシナリオ全体の `${row.*}` を置き換え、その対象には `tags` も
含まれます。このため、データ駆動のシナリオは行ごとに異なるタグを持てます。

```yaml
name: checkout as ${row.plan}
tags: [checkout, "${row.plan}"]
data:
  - { plan: free }
  - { plan: premium }
hooks:
  beforeScenario:
    - name: subscription
      cmd: "./scripts/grant-premium.sh"
      when: { tags: [premium] }
```

この置き換えがあるので、シナリオ自身の hook でも `when` に使い道があります。すべての行がシナリオの
`hooks` ブロックを共有し、条件はコマンドを実行する行を選びます。データ行を持たないシナリオではタグが
固定なので、そのシナリオ自身のエントリの `when` は常に同じ結果になります。ローダーは、そうした
エントリもほかのエントリと同じように受け付けます。

### シナリオ単位のリスト

どちらの階層でも、`beforeScenario` と `afterScenario` のエントリは、自分のシナリオに対して `when` を
評価します。自分のシナリオとは、これから実行するシナリオ、または終わったばかりのシナリオです。
エントリは、そのエントリに当てはまるすべての条件を満たしたときに実行します。

1. `preconditions.inheritSetup` が、BE-0491 の定めどおりにターゲットのシナリオ単位のリストを残しています。
2. `when` がシナリオのタグに一致します。
3. `afterScenario` の場合は、`on` が判定結果に一致します。

`when` と `on` は互いに独立した条件で、両方を満たしたときに実行します。`when` はシナリオが何であるかを
見て、`on` はシナリオがどう終わったかを見ます。

`beforeScenario` のエントリと、そのデータを片付ける `afterScenario` のエントリは、同じタグを見ます。
同じ `when` を持つ組は、そろって実行するか、そろって実行しないかのどちらかになります。Bajutsu は
2つのエントリを結び付けません。ドキュメントでは、片付けのエントリにも同じ条件を写すよう案内します。
条件の広い片付けのエントリは、そのまま実行します。その場合、スキップしたエントリの
`BAJUTSU_HOOK__<name>__<key>` 変数は見つかりません。スキップしたエントリは出力を書かないからです。

### run 単位のリスト

`beforeRun` と `afterRun` のエントリには、調べるべき単一のシナリオがありません。そこで、run の
シナリオ集合に対して `when` を評価します。シナリオ集合は、展開と `--tag` と `--exclude` を経て残った
シナリオのうち、エントリのターゲットを操作するものです。そのターゲットを操作しないシナリオが、
ターゲットのエントリを実行させることはありません。集合のなかに一致するシナリオが1つでもあれば、
エントリは一致します。

run 単位のエントリに `exclude` だけの `when` を書くと、集合のすべてのシナリオが除外するタグを
持つときにしかスキップしません。そうした意図で書く人はいないので、`beforeRun` と `afterRun` の
`when` は、空でない `tags` の一覧を持たなければ読み込みに失敗します。

run は最初の `beforeRun` エントリの前に集合を1回だけ求め、その結果を run の終わりまで使います。
`afterRun` のエントリは、対になる `beforeRun` のエントリと同じ集合で判断します。キャンセルしても、
集合は変わりません。集合の範囲は、run 単位のリストを実行する範囲に従います。

| run の始まり方 | シナリオ集合 |
|---|---|
| `bajutsu run`（`--workers` の有無を問わない） | run が選んだシナリオのうち、エントリのターゲットを操作するものすべてです。すべての worker にまたがります。 |
| `serve` のジョブ | ジョブの選択です。worker はジョブを1回の `bajutsu run` として実行します。 |
| `audit` | 再生するシナリオです。 |
| `record`、`crawl`、`repl` | 空です。これらのコマンドはシナリオファイルを実行しません。 |

空の集合は、どの条件にも一致しません。条件付きの `beforeRun` エントリは、`record`、`crawl`、`repl` の
もとでは実行しません。これらのコマンドでも必要なサーバーは、条件を付けずに置きます。

### 条件付きエントリの出力

BE-0491 は、シナリオを読み込むときに `${hooks.<name>.<key>}` トークンをそれぞれ検査します。この項目は、
その検査に規則を1つ加えます。条件付きのエントリの出力を読むシナリオは、そのエントリの `when` に
一致していなければなりません。run 単位のエントリなら、そのエントリのターゲットを操作している必要も
あります。一致しない場合は読み込みに失敗し、エラーはエントリ、その条件、シナリオのタグを
示します。

この規則は両方の階層で成り立ちます。シナリオ単位のエントリは、一致するシナリオでだけ実行します。
run 単位のエントリは、集合に一致するシナリオがあれば必ず実行します。トークンを読むシナリオは
エントリのターゲットを操作するので、その集合に含まれています。したがって、検査を通ったトークンは常に実行済みのエントリを指します。
値の欠落は、run の途中ではなく読み込みの時点で表に出ます。

検査は展開後のすべてのシナリオに対して、データの行ごとに行い、`--tag` と `--exclude` は考慮しません。一致しない
組み合わせは、run がどの部分集合を選ぶかに関係なく、ファイルの欠陥だからです。そのシナリオを選ばない
CI の smoke の段階でも、欠陥を報告します。

### エビデンスとコマンドの実行ポリシー

スキップしたエントリは、レポートの hook のブロックに `skipped (when)` というラベルと条件を付けて
表示します。このエントリはコマンドを実行しないので、ログファイルと出力ファイルのどちらも書きません。

[BE-0492](../BE-0492-worker-command-execution-policy/BE-0492-worker-command-execution-policy-ja.md)
の worker のコマンド実行ポリシーは、デバイスを操作する前に、宣言されたすべてのエントリを検査します。
条件に一致しないエントリも検査の対象です。こうしておけば、worker が config を受け入れるかどうかは、
ジョブが選ぶタグに左右されません。`serve` は引き続き、config が宣言するコマンドを手がかりにジョブを
振り分けられます。BE-0492 の `commandExecutions` の記録では、4つ目の `decision` の値として `skipped` が
加わります。`skipped` は、条件に一致しなかったエントリを表します。

### 基本方針との整合

- **AI に判定させない**：条件は、シナリオファイルに書かれた文字列に対する集合演算です。大規模言語モデル
  （LLM）の呼び出しは、run とゲートのどちらにも入りません。
- **決定性を優先する**：同じファイルと同じ `--tag` と `--exclude` からは、常に同じエントリを実行します。
  run は最初の hook の前にシナリオ集合を確定させます。run 単位の判断が、どのシナリオが先に終わったかに
  左右されることはありません。
- **アプリに依存しない**：条件はシナリオのメタデータだけを読みます。アプリごとのロジックを runner に
  持ち込みません。

### 依存関係

この項目は、hook エントリとトークンの検査を導入する BE-0491 の後に入ります。シナリオ単位の部分は、
兄弟のシナリオ hook 提案の後に入ります。ターゲット単位の部分は、兄弟提案を待ちません。

## 検討した代替案

| 代替案 | この項目が採らない理由 |
|---|---|
| `when: "smoke and not wip"` のような論理式 | BE-0034 は選択のための式言語を退けており、同じ理由がここにも当てはまります。構文解析器と文書化すべき文法が増え、`--tag` と並ぶ2つ目のタグの意味が生まれます。選択がいずれ式を持つなら、hook の条件も同じ文法を採ります。 |
| `anyTags`、`allTags`、`noneTags` の3つのリスト | 論理積は表現できますが、意味が `--tag` と `--exclude` から離れます。作成者は1つのラベルについて2つの規則を覚えることになります。 |
| 単一の `tag` 文字列 | 複数のタグや除外を書くたびに、エントリの複製が必要になります。 |
| run 単位の条件が `--tag` フラグの値を読む | `--tag` のない run では条件が読むものがなく、フラグの値は `--exclude` を無視します。作成者が知りたいことには、選ばれたシナリオ集合のほうが答えます。 |
| `beforeRun` と `afterRun` には `when` を認めない | 選ばれたシナリオが必要とするときだけサーバーを起動する、というよくある場面が、回避策のまま残ります。 |
| スキップしたエントリのトークンを、実行時にステップの失敗とする | 誤りが run の途中、デバイスの操作の後で表に出ます。展開後のタグは静的なので、ローダーが誤りを検出できます。 |
| スキップしたエントリのトークンを空文字列に置き換える | 欠けた値が黙ってアプリに渡り、原因から遠い場所で失敗します。 |
| `afterScenario` のエントリが対応する `beforeScenario` のエントリに自動で従う | エントリを対にする新しい仕組みが必要になりますが、BE-0491 の平らなリストにはその仕組みがありません。`when` を1つ写すほうが単純で、2つのエントリはもともと同じタグを見ています。 |
| スクリプトが分岐に使う `BAJUTSU_SCENARIO_TAGS` 変数 | 判断がスクリプトのなかに隠れ、レポートはスキップを示せません。run 単位のスクリプトには、run のシナリオ集合も見えないままです。この変数は、必要とするスクリプトのために後の項目で足せます。この設計を変える必要はありません。 |
| 一致しないエントリをコマンド実行ポリシーの対象から外す | worker が config を受け入れるかどうかが、ジョブごとのタグに左右されます。`serve` は config だけを見てジョブを振り分けられなくなります。 |

- [ ] 共通の述語：タグの規則を `select_scenarios` から1つの関数に切り出し、選択と hook の条件の両方から呼ぶ
