## はじめに

Bajutsu の iOS バックエンドは、iOS シミュレータ上で `xcodebuild test-without-building` によって
常駐 runner を起動し、その runner を通してシナリオを実行します。このコールド起動は、失敗したときに
1 度だけ再試行されます。一度きりのばらつきで継続的インテグレーション（CI）のジョブ全体を赤くしない
ための仕組みです。この再試行は、**ホスト側**のリソースを試行ごとに分離します。runner が bind する
ループバックのポート、起動元となるパッチ済みの `.xctestrun`、出力を捕捉するファイルが、その対象です。
しかし再試行が起動する先のシミュレータは、1 回目の試行が失敗したのと同じシミュレータのままでした。
1 回目の試行を失敗させた原因が、まさにそのシミュレータが自動操作を受け付けなくなったことである場合、
再試行に成功の余地はありません。それでも発生するたびに数分をかけて、成功しないことを証明していました。

本項目は、コールド起動が試行のあいだにデバイスを修復するようにします。試行が失敗したあと、起動は
シミュレータを調べ、その試行が何で失敗したかに応じた対処を選びます。シミュレータ制御ツール `simctl`
が一覧しなくなったデバイスは新規作成したデバイスで置き換え、自動操作を受け付けなくなったデバイスは
再起動して再度整え、自ら終了した runner プロセスに対しては、すでに走った後片付け以上のことは何も
しません。修復されたデバイスには、readiness の上限をあらためて与えます。次の試行が走る先は、実際に
起動し直せたことを確認できたデバイスだからです。修復できないデバイスは、成功しえない試行にさらに
予算を使うのではなく、デバイスの障害として実行を失敗させます。

## 動機

2026-08-04 に、iOS の CI ジョブが 4 件、互いに独立に失敗しました。`actuation`、`run`、
`bundled-runner`、`golden` の 4 ジョブで、無関係な 2 つの pull request にまたがっています。その
すべてが、シナリオを 1 つも実行しないまま、同じ形で失敗していました。

```
XcuitestChannelError: xcuitest runner did not come up:
attempt 1/2: the xctest run ended (Test Suite 'All tests' failed) before the runner bound its port
attempt 2/2: health never ready within 166.9s
```

捕捉された runner の出力は、このメッセージだけではわからない経緯を伝えます。1 回目の試行では
`xcodebuild` がテストホストを起動し、runner のテストが始まり、そして対象アプリが前面に出てくること
はありませんでした。

```
    t =     2.27s Open com.bajutsu.showcase.ios.swiftui
    t =     2.28s     Launch com.bajutsu.showcase.ios.swiftui
<unknown>:0: error: Failed to launch com.bajutsu.showcase.ios.swiftui: Timed out attempting to launch app.
```

起動の完了を待ち終えたシミュレータの上で、アプリの起動が 40 秒後にタイムアウトします。これはビルドに
ついてではなく、デバイスについての事実です。同じコミットの他のジョブは、同じアプリを問題なく
インストールして起動しています。こうして 1 回目の試行は runner を破棄して終わり、再試行はその
デバイスへ、つまりたった今アプリを前面に出すことを拒んだデバイスへ、起動をかけます。

そこで再試行が何をしたのかが、今回の発見です。4 件のうち 3 件で、`xcodebuild` は destination を
解決し、それについて 2 行を出力し、そのあと出力を一切生まなくなりました。`Running tests...` にも
到達せず、150 〜 180 秒後に残りの予算が尽きるまで無言のままでした。4 件目では、約 70 秒でコード 70
を返して終了しています。

```
xcodebuild: error: Unable to find a device matching the provided destination specifier:
		{ platform:iOS Simulator, id:2A6DC5A9-CE8C-4BC5-959D-F98D5F4BD9AA }

	The requested device could not be found because no available devices matched the request.
```

このエラーとともに `xcodebuild` が出力した destination の一覧には、iOS シミュレータが 1 つも
含まれていませんでした。ジョブの実行中に、ホストの iOS デバイス群がまるごと消えていたのです。
クラッシュレポートは 1 件も収集されていないので、何かがクラッシュしたのではありません。シミュレータ
のデバイスを管理する macOS のサービスである CoreSimulator が、デバイスを提供しなくなっただけです。

どちらの結末も、再試行が吸収できるものではありません。再試行は、その結末を生んだ条件を何も変えない
からです。[BE-0319](../BE-0319-xcuitest-cold-spawn-resilience/BE-0319-xcuitest-cold-spawn-resilience-ja.md)
がその再試行を作り、2 度にわたって強化しました。`xcodebuild` プロセスが死んだ時点で即座に失敗し、
上限まで待つのではなくテスト実行が終わった時点で待機を終えるようになっています。しかしどちらの強化も、
見ているのは**起動**の側です。BE-0319 の「検討した代替案」の節は、別の修正案を退ける過程で、この穴を
言い当てる寸前まで来ていました。「すでに固まった XCTest の自動操作セッションを持つ runner の内部で
再起動しても、たった今タイムアウトしたそのセッションを使い回すことになる」という記述です。この論法は
記録されたものの、退けられた代替案にだけ適用されました。採用した設計、つまり同じ固まったデバイスに
向けて runner をまるごと作り直す再試行に、この論法を持ち越した人はいませんでした。

試行のあいだの後片付けにある 2 つの小さな穴が、この問題をさらに悪くしています。runner の終了は
`xcodebuild` プロセス 1 つへのシグナルで行われますが、実際にデバイスを操作する XCTest ホストの一連の
プロセスは `xcodebuild` が生成するため、親で止まる後片付けでは、その子プロセスが生き残ります。加えて、
対象アプリを終了させるものが何もありません。Swift の runner は、サーバを開く前の失敗では XCTest を
巻き戻すのではなく `_exit` を呼びます（`xcodebuild` が居残らないようにするための意図的な作りです）。
そのため XCTest がアプリを落とすこともありません。ある試行を失敗させたタイムアウトによって起動途中で
残されたアプリが、次の試行が `launch()` を呼ぶ対象そのものになります。

## 詳細設計

作業は 5 つのユニットに分かれます。ユニット 1 と 2 は互いに独立で、ユニット 3 はユニット 1 の失敗の
分類に、ユニット 4 はユニット 2 と 3 に、ユニット 5 はユニット 4 に依存します。

1. **試行が何で失敗したかを分類する。** 現在の readiness の待機は、失敗の理由を散文で返します。
   そのため失敗の**種類**に応じて動きたい呼び出し側は、その散文を解析するほかありません。代わりに
   小さなレコードを返すようにします。持たせるのは 2 つです。runner プロセスの終了／テスト実行の終了／
   待機の上限到達を表す `kind` と、失敗するエラーがすでに引用している文です。修復が見るのは `kind`
   だけなので、対処が文面に依存することはありません。テスト実行が終わったという理由には、捕捉した
   出力にアプリ起動のタイムアウトが現れていればそれも書きます。「このデバイスは再起動が必要だ」と
   「このビルドが壊れている」を読者が区別するために必要な兆候だからです。

2. **プロセスグループと対象アプリを終了させる。** `xcodebuild` プロセス 1 つではなく runner の
   プロセスグループ全体にシグナルを送り、XCTest ホストの子プロセスも一緒に終わらせます。そのシグナル
   を届けるため、起動時に runner へ独自のグループを与えます。グループに `SIGTERM` を送り、グループの
   リーダーについて猶予を待ち、そのあとグループへ `SIGKILL` を**無条件に**送ります。リーダーが猶予を
   超えて生きていた場合だけに限らないのは、リーダーの終了が子プロセスについて何も語らないからです。
   `xcodebuild` がすぐに巻き戻る一方で子プロセスが自動操作セッションを持ち続ける状態こそ、このユニット
   が防ごうとしているものです。そのうえで `simctl` によって対象アプリを終了させます。これはベスト
   エフォートで行い、すべての段を例外の抑制で包みます。後片付けは失敗の経路で走るため、ここで例外を
   投げると、その原因となったエラーを隠してしまいます。

3. **デバイスを調べて対処を選ぶ。** 試行のあいだに、貸し出されたデバイスを `simctl` がまだ一覧するか
   を尋ね、次のように選びます。

   - **デバイスが消えている場合。** 置き換えとなるデバイスを作成し、その初回起動を待ち切り、その
     デバイスに対してデバイスの準備（アプリのインストール、権限の付与、システムロケールの固定）を
     やり直します。置き換えのデバイス種別は、消えたデバイス自身の種別を複製します。この種別は、
     デバイスがまだ一覧されていた最初の準備のときに捕捉しておきます。置き換えが必要になった時点では、
     デバイスはもう尋ねられる場所にいないからです。続く 2 段の代替は、設定されたデバイスの機種、
     そしてこのホストの Xcode が持つ iPhone です。設定された機種は、それを備えた Xcode より長く
     残ることがあります。
   - **調査そのものが失敗した場合。** 何も変えません。自分のデバイスを一覧できないほど不調なホストで、
     その証拠だけを根拠にデバイスを置き換えるわけにはいきません。だからこの調査は真偽の 2 値ではなく、
     存在する、存在しない、不明の 3 値を返します。
   - **runner プロセスが自ら終了した場合。** 後片付け以上のことはしません。速く、自分の側で起きた
     終了は、この再試行がもともと想定していた一時的なばらつきであり、デバイスについて何も語りません。
   - **それ以外の場合。** アプリ起動のタイムアウト、または上限に達した待機です。シミュレータを
     シャットダウンし、起動し、起動の完了を待ち、デバイスの準備をやり直します。

   このはしご全体を、新しい `BAJUTSU_XCUITEST_RECOVERY_TIMEOUT`（デフォルト 180 秒）で区切ります。上限の
   検査は、段の内部ではなく段のあとで行います。`simctl` の各手順は途中で中断できないブロッキング呼び
   出しだからです。この検査が捉えるのは、戻ってくるのに異常に時間がかかったデバイスです。上限を
   超えた段は、そもそも再試行が必要とする予算を使い切っています。

4. **修復されたデバイスに readiness の上限をあらためて与える。** 現在の起動の上限は 2 回の試行で共有する
   予算であり、それは意図的な設計です。上限をまるごと使い切った試行は再試行のための予算を残しません。
   変わっていないデバイスに対して 2 度目のフル待機をしても新しい情報は得られず、最悪ケースが倍に
   なるだけだからです。しかしある段がデバイスを再起動または置き換えたなら、この論法は成り立たなく
   なります。そこで修復は、何かを変えたかどうかを報告し、修復に続く再試行は上限を再開します。これが、
   支配的なばらつきを修復可能にしている点です。アプリ起動のタイムアウトは 1 回目の試行を速く終わらせ
   ますが、そのあとに残るのは余った秒数ではなく、劣化したデバイスです。各段の記録は、試行ごとに捕捉
   した出力の末尾と並べて、失敗するエラーに織り込みます。どの対処が走り、デバイスがどのような状態
   だったかを、読者が見て取れるようにするためです。

5. **貸し出しを置き換え先のデバイスへ追随させる。** デバイスプールがデバイスの id で引いているものは
   5 つあります。デバイスごとのネットワークコレクタ、warm runner のキャッシュ、証跡の sink が行う
   `simctl` の捕捉、結果に記録するデバイス、空きデバイスのキューです。プールに伝わらないまま置き換えが
   起きると、この 5 つのすべてがもう存在しないデバイスを指し続けます。環境の Protocol に述語を 1 つ
   追加します。環境が移った先の id、または何もない、を返すもので、他のすべてのプラットフォームは何も
   ない、と答えます。そしてプールが、起動から戻ったあとに自分の保持する状態を貼り替えます。消えた
   デバイスは二度と解放されません。置き換えたデバイスがその場所を引き継ぎ、それが死んだデバイスの
   隔離になります。`crawl` コマンドはリセットの seam のために、貸し出しの生の id から 2 つ目の環境を
   組み立てており、置き換えが起きるとリセットの対象が別のデバイスになってしまうため、1 つの環境を
   共有する形に直します。

## 検討した代替案

- **各試行にそれぞれフルの上限を与え、ほかは何も変えない。** この調査が最初に検討した形であり、失敗の
  ログが誘う形でもあります。2 回目の試行は、1 回目の試行が使い切った予算のせいで短く切り上げられて
  いました。2 回目の試行が実際に何をしたかを測ったことで、この案は退けられました。4 件のうち 3 件で
  2 回目の試行は `Running tests...` にすら到達しておらず、予算を増やしても無言の時間が伸びるだけです。
  4 件目ではデバイスが消えており、どれだけ予算があっても助けになりません。コストも現実の問題です。
  この上限は iOS のすべてのレーンが共有しているため、最悪ケースを倍にすると各ジョブの
  `timeout-minutes` を圧迫します。デバイスを修復したあとであれば上限をあらためて与える価値があり、それが
  ユニット 4 です。
- **消えたデバイスでは置き換えを作らず、即座に失敗する。** シミュレータの作成にはランタイムが必要で、
  観測された失敗ではデバイスとともにランタイムも失われていたため、置き換えが不可能な場合はあります。
  加えて置き換えは貸し出しの途中でデバイスの id を変えるので、それを伝播させるためにユニット 5 が
  必要です。それでも置き換えを試みるほうを選びました。作成が成功したときはジョブが回復し、人手による
  再実行を必要としません。作成できないときも、原因を明記して数秒で失敗します。現状の無言の停滞より
  ましです。
- **調べずに、失敗した試行ごとにデバイスを作り直す。** はしごより書くのは簡単ですが、よくある場合に
  対して誤っています。単に固まっただけのシミュレータは、作成と初回起動にかかる時間のごく一部で、
  再起動によって修復できます。また調査が失敗しただけの場合に、一時的なばらつきごとに健全なデバイスを
  置き換えることになってしまいます。
- **Swift の runner の内部でアプリの起動を再試行する。** 再起動が固まった自動操作セッションを使い回す
  という理由で BE-0319 が退けた案であり、ここでも 2 つ目の理由で退けます。この修正は Swift の
  パッケージに入るため、取り込むにはすべてのレーンで runner を再ビルドする必要があります。ロジック
  コアに置く修復であれば、すべてのレーンに一度で届きます。
- **この失敗ではジョブ全体を再実行する。** ジョブの再実行は現在存在する運用上の逃げ道であり、本項目が
  その必要をなくす対象です。1 台の不調なデバイスから回復するために、人間の注意と課金対象の macOS
  ジョブ 1 本をまるごと使い、しかも何が悪かったのかの記録を残しません。
