## はじめに

本提案は、`bajutsu serve` の Web UI を、スマートフォンや幅の狭いタブレットといった小さい画面でも使えるようにします。UI はデスクトップ前提の多ペインです。一定の画面幅を境に、1 カラムのタッチ操作向けレイアウトへ組み替えます。マウス専用の操作には、タッチの経路を与えます。

変更は、インライン展開した `serve.*` テンプレートの**フロントエンドだけ**に閉じます。サーバのルートもジョブも設定も足さず、決定的なランナーの挙動も変えません。`serve` は決定的な CLI を起動するだけの Tier 1 の補助機能のままです。そのため、本提案はプライムディレクティブ（[CLAUDE.md](../../CLAUDE.md)）の内側に収まります。ゲートに大規模言語モデル（LLM）は入らず、合否にも触れず、アプリ固有の挙動は設定に残ります。

## 動機

`serve` の UI は、`bajutsu/templates/serve.html.j2` で `<meta name="viewport" content="width=device-width, initial-scale=1">` をすでに宣言しています。この宣言は、スマートフォンのブラウザに、ページを縮小したデスクトップとしてではなく実際の CSS 幅で描画せよと指示します。しかし、背後のスタイルシートがこの約束を守っていません。`bajutsu/templates/serve.css` には **`@media` クエリが 1 つもなく**、すべてのレイアウト規則が広い画面向けの 1 つのデザインに属しています。この食い違いは、具体的に 4 つの形で表れます。

1. **中心となるレイアウトがスマートフォンに収まらない。** Replay ビューは、パネルを 5 トラックのグリッドで並べます（`main{grid-template-columns:var(--rep-left,340px) var(--gw) var(--rep-mid,340px) var(--gw) 1fr}`）。グリッドは、約 340 px の左右カラム 2 つ、リサイズ用の溝、レポートのカラムで構成されます。レポートに幅を割り当てる前の時点で、すでに 390 px のスマートフォンより広くなります。カラムは横スクロールを強いるか、読めない幅まで潰れます。crawl のサイドパネルは `flex:0 0 22rem` で幅が固定されています。ヘッダーは、ブランド、`.toptabs` の行、`margin-left:auto` で右端へ押し出したテーマ切り替えで構成されます。ヘッダーは横 1 行に並ぶ前提で、折り返しません。

2. **操作がすべてマウス専用で、タッチのハンドラが 1 つもない。** この UI には、積み重なった 2 つのリサイズ機構と、パン可能なグラフがあります。どれもマウスイベントだけに結線されています。
   - カラムの溝は `mousedown` と `e.clientX` でリサイズします。レイアウトは `bajutsu-splits` として保存されます。
   - より高機能なタイリングレイアウトでは、パネルの `.tile-grip` をドラッグしてペインを分割したり入れ替えたりします。レイアウトは木構造として `bajutsu-tiles` に保存され、`mousedown` と `elementFromPoint` で駆動されます。
   - crawl のグラフは `mousedown` と `clientX` でパンし、`wheel` でズームします。

   `serve.js` には `touchstart` も `pointerdown` も **1 つも**登録されていません。スマートフォンでは、溝もグリップも動かない操作部品になります。押してドラッグするポインタが存在しないからです。ドラッグして分割するタイリングは、手のひらの画面では意味をなさない高機能です。グラフは、パンもピンチズームもまったくできません。

3. **縮小したデスクトップは使えるスマートフォン UI ではない。** 広いレイアウトしか存在しないため、スマートフォンにはデスクトップがビューポートへ押し込まれた姿が表示されます。左右のペインは共存する余地がありません。タップ対象はカーソル前提の大きさです。コンテンツには、ズームとパンでしか届きません。機能はすべてそこにありますが、親指で届くようには並んでいません。

4. **ホスティングがスマートフォンからのアクセスを現実の入り口にする。** ホスティングの取り組みは、`serve` を URL でアクセスできる共有サービスに変えていきます（[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting.md) が公開ホスティング、[BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting.md) がセルフホスティング）。すると、スマートフォンから開く場面は例外ではなくなります。「テストが落ちた」という通知を受け取ったレビュアーは、手元の端末でその run のレポートを開き、結果をひと目で確かめ、必要なら再実行を始めたいものです。いまは、それが横スクロールとの格闘になります。埋め込まれたレポートは、*すでに*半分近く対応しています。`bajutsu/templates/report.css` が自前の `@media` 規則を持つからです。レポートの中身は画面幅に追従しますが、それを囲む `serve` の外枠は追従しません。取り残されているのは外枠のほうです。

狙いは意図して控えめで、範囲も限られています。**機能も内容も同じ UI** を、狭いビューポートでは縮小されたデスクトップではなく、読めてタップできる 1 カラムとして並べ直します。

## 詳細設計

### 範囲と制約

変更はフロントエンドだけで、`bajutsu/templates/serve.css` に閉じます。唯一本当にインタラクティブな欠落（crawl グラフのタッチパン）のために、`bajutsu/templates/serve.js` へ小さく手を入れます。サーバのルートもジョブモデルも設定キーも変えません。UI はこれまでどおり決定的な CLI を起動するだけです。

[BE-0011](../BE-0011-local-web-ui-serve/BE-0011-local-web-ui-serve.md) からの 2 つの制約を守ります。

- レスポンスは、CSS と JS をインライン展開した**自己完結の HTML 1 枚**のままにします。`/static` ルートもアセットのパイプラインも持ちません。
- CSS は**ビルド工程を持たない手書き**のままにします。フレームワークは使いません。

### ブレークポイントの方針

`max-width` のブレークポイントを 1 つ、必要なら 2 つ導入します。1 つ目はスマートフォン向け（`≤ 640px` 程度）です。タブレット向けの調整が要るなら、2 つ目として狭い段（`≤ 900px` 程度）を足します。

狭い段の規則は、既存のデスクトップ規則の**後ろ**に重ね、変える必要のある部分だけを上書きします。広いレイアウトは手つかずの既定として残るので、デスクトップの体験は退行しません。正確なピクセル値は小さな未決事項です。要となる判断は、デスクトップのレイアウトを土台とし、狭い段をその上に足す上書きとすることです。

### 画面ごとの 1 カラム化

スマートフォンのブレークポイントを下回ると、多トラックのグリッドは 1 カラムに畳まれ、各ビューのペインは縦に積まれます。3 つのビューはいずれも複数のペインを抱えうるので、縦積みには「一度に 1 つのペインを全幅にする」手段を組み合わせます。

* **Replay**：5 トラックのグリッド（`--rep-left` / `--rep-mid` の左右カラム、溝、レポート）を 1 カラムにします。シミュレータと設定フォーム、ストリーミングされるログ、埋め込みレポートを縦に積みます。積んだペインの前面にセグメント切り替え（「フォーム、ログ、レポート」）を置き、選んだペインが全幅を使えるようにします。この段では、カスタムプロパティの幅と溝を使いません。
* **Record**：`.rec-stack` のエージェント進捗と出力の分割も、同じように積みます（「進捗、出力」）。
* **Crawl**：固定幅 `22rem` のサイドパネル（「プラン、コンソール」）とグラフを、縦積みのセクションにします。セクションの前面に切り替え（「グラフ、プラン、コンソール」）を置きます。パン可能なグラフは、選ばれているペインであるときに全幅を保ちます。

### 小さい画面でマウス専用の操作モデルを置き換える

ドラッグでリサイズする溝と、ドラッグで分割し入れ替えるタイリングは、デスクトップ向けの高機能です。タッチに対応物がなく、スマートフォンには置き場所もありません。狭い段では、これらを隠します。`.tile-divider`、`.tile-grip`、カラムの溝を `display:none` にし、保存された `bajutsu-splits` と `bajutsu-tiles` のレイアウトは適用しません。その役割は、1 カラムの縦積みとビューごとの切り替えが引き継ぎます。

残るタップ対象は、上部タブ、ビューごとの切り替え、実行ボタンと停止ボタン、履歴の行です。これらは、指で快適な最小寸法（おおむね 44 px）に整えます。作業はほぼ CSS だけで済みます。`serve.js` には、狭いメディアクエリが一致するときに保存済みのデスクトップ用レイアウトを適用しないガードを足します。

### crawl グラフ：唯一インタラクティブな変更

crawl グラフは、CSS ではなく `serve.js` の作業が本当に要る唯一の箇所です。パンが `mousedown` と `clientX` に、ズームが `wheel` に結ばれていて、どちらもタッチでは発火しないからです。変更は、既存のパンとズームの計算を再利用するタッチ対応の追加です。ビューはすでに平行移動と `zoom` の組み合わせのモデルなので、対応づけは変わりません。

- 1 本指のパンには、`touchstart` と `touchmove` を使います。
- ピンチ（2 本指の距離）は、既存の `zoomBy` に対応づけます。

グラフは調査の補助であり、ゲートの一部では決してありません。この変更は、インタラクティブ性を純粋に足すだけです。

### ヘッダーの組み替え

狭い段では、ヘッダー行（ブランド、上部タブ、テーマ切り替え）を折り返すか詰めて並べます。たとえば、ブランドの列を 1 行に、タブを次の行に置き、テーマ切り替えは届く位置に保ちます。ヘッダーは横スクロールを強いません。

### すでに可変な部分は作り直さず活かす

スクリーンショットのモーダルは、すでにビューポート基準で可変です（`.shotbox{width:min(960px,94vw);max-height:88vh}`、`.shotmain img{max-width:46vw}`）。本設計は、その可変なサイズ指定を活かします。スマートフォン幅で縦積みに直すのは、左右に並んだ画像と次手順リストだけです。

埋め込みレポートは、すでに `report.css` に自前の `@media` 規則を備えています。この項目はレポートの内部に触れず、レポートを枠取りする `serve` の外枠だけを扱います。

### 決定性、アプリ非依存性、ゲート

* **LLM を入れず、合否に触れない。** UI は決定的な `run` / `record` を起動するだけです。この変更はピクセルの並べ替えとタッチハンドラの追加であり、合否はここで計算しません。そのため、プライムディレクティブの 1 と 2 は構造上保たれます。
* **アプリ非依存。** レイアウトはビューポートに依存し、特定のアプリには依存しません。`apps.<name>`、ドライバ、ランナーのいずれも読みません。
* **Linux で検証できる。** 検証の経路は既存の Web バックエンドで、後述のとおり Linux のゲートで動きます。シミュレータも macOS も要りません。

### テストの契約（機械判定可能）

[BE-0058](../BE-0058-dogfood-web-ui/BE-0058-dogfood-web-ui.md) はすでに、Web（Playwright）バックエンドで `serve` UI を駆動し、決定的な Tier 2 の回帰ネットにしています。レスポンシブ対応は、そこで機械判定できます。Playwright が `viewport` を設定し、アサーションは構造的な事実にとどまるからです。「見た目が良い」という LLM の判断は使いません。

* **スマートフォン幅で横方向のあふれがない。** スマートフォンのビューポート（たとえば 390×844）で、ドキュメントのスクロール幅がクライアント幅を超えません。「何も横にはみ出さない」を決定的に言い換えたものです。
* **主要な操作部品に届く。** 実行ボタン、上部タブ、ビューごとの切り替えが、スマートフォン幅で見えていて見切れていません。既存のアサーションを、狭いビューポートで再実行します。
* **デスクトップのレイアウトが変わらない。** 広いビューポートでは、既存の Replay/Record/Crawl の UI シナリオがこれまでどおり通ります。追加した狭い段の規則が既定を損なっていないことを、これで固定します。

BE-0058 のネットをこのように広げれば、決定性ファーストの契約を保てます。レスポンシブの規則が知らぬ間に壊れることも防げます。

### 範囲外

- リサイズや折りたたみが可能なタイリングの、デスクトップ向けの広い再設計。この項目は小さい画面で隠すだけで、デスクトップ向けに作り直しはしません。
- `run` が捕捉し判定する内容への変更。
- レポートの内部。`report.css` ですでにレスポンシブです。

## 検討した代替案

* **モバイル専用テンプレート、あるいはモバイル専用アプリ。** 不採用です。`serve` の機能が増えるたびに同期を取るべき面が二重になります。BE-0011 が意図的に返している自己完結 HTML 1 枚とも噛み合いません。1 つのレスポンシブなテンプレートのほうが保守の負担は小さく、一度足した機能がどの画面でも動き続けます。
* **グリッドとブレークポイント目当てに CSS フレームワーク（Tailwind / Bootstrap）を採用する。** 不採用です。`serve` は標準ライブラリのみで、CSS は手書きでインライン展開し、アセットのビルド工程を持ちません（BE-0011 の「検討した代替案」）。素の `@media` クエリで、フレームワークの依存やビルドのパイプラインを抱え込まずにレスポンシブ対応が得られます。新規クローンからそのまま動かせる性質も保てます。
* **デスクトップ専用のまま、ブラウザのピンチズームとパンに頼る。** 不採用です。それがまさに、この項目が直そうとしている現状です。利用者は、縮小されたデスクトップをズームとパンで動き回らねばなりません。タッチハンドラが存在しないため、グラフはそもそもパンできません。
* **デスクトップでもペインを折りたたみとリサイズ可能にする（レイアウト全体の刷新）。** ここでは範囲外です。この項目は、小さい画面への組み替えに絞ります。デスクトップ向けにペインを可変かつ折りたたみ可能にする広い再設計は、望むなら別の提案とします。その提案が、狭い画面の対応を止めてはなりません。
* **マウスのドラッグハンドラをポインタイベントに変えて、タッチ対応を「ただで」得る。** 一見魅力的ですが、ポインタモデルに統一すると、ドラッグで分割するタイリングと溝のリサイズまでタッチに持ち込むことになります。どちらも、小さい画面ではぎこちなく無意味です。しかも、動作しているデスクトップの操作に対する、より大きく危うい変更でもあります。小さく安全なのは、それらの操作部品を狭い段で隠し、指の下で本当に動かしたい唯一のもの（グラフ）にだけタッチの経路を足す変更です。
