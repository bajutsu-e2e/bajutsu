## はじめに

BE-0322 が導入したシナリオ単位のエンドツーエンド（E2E）絞り込みを、意図的に対象外とされた 2 つの
iOS ジョブ、`codegen` と `visual` にも広げます。BE-0322 は、変更が影響しうる実機ジョブだけを起動
します。シナリオファイルだけに閉じた変更では、変更されたシナリオを宣言するジョブだけが走り、macOS
レーン全体は走りません。この絞り込みは、ワークフローから宣言シナリオを読み取れるフィーチャージョブ
にだけ適用され、`codegen` ジョブと `visual` ジョブは、走らせるシナリオを絞り込みが読む入力ではなく
`Makefile` のターゲットで宣言しているため、関連する変更すべてで起動したままになっています。本項目は、
BE-0322 を安全にしている性質を損なわずに、この 2 つのジョブを同じ絞り込みの対象にします。その性質
とは、ジョブとシナリオの対応表が各ジョブの実際の実行内容から導かれ、ジョブが走らせないシナリオを
走ると主張できないよう機械的に検証されていることです。結果として、どちらのジョブも走らせないシナリオ
だけを変えたときに、10 倍課金の macOS シミュレータを 2 台起動する無駄がなくなり、一方でどちらかの
ジョブが壊しうる変更では従来どおりそのジョブが走ります。

## 動機

iOS の E2E レーンは、実機ジョブを、Linux の 10 倍のコストがかかる macOS ランナー上で走らせます。
そのため、理由なく起動するジョブは 1 つずつが直接のコストです。レーンは必須の集約チェック（`E2E (iOS)`）で
守られており、報告されない必須チェックはマージをブロックします。したがってレーンをワークフローの
トリガーで止めることはできず、レーンはプルリクエストごとに起動し、
[`scripts/e2e_changes.py`](../../scripts/e2e_changes.py) がどのジョブを実際に走らせるかを決めます。
BE-0322 は、この判定をレーン全体の単一の真偽値から、ジョブが読む 3 つの出力へと精密化しました。
`relevant`（課金対象のジョブを 1 つでも走らせるか）、`shared`（どのシナリオにも影響しうるドライバや
ランナーのコードへの変更で、レーン全体を起動する）、`affected`（シナリオだけの変更が到達した、
シナリオ単位ジョブの JSON 配列）の 3 つです。`run` のようなフィーチャージョブは、`relevant` かつ
（`shared` またはそのジョブが `affected` に載っている）ときに走り、ジョブのどのシナリオも変えて
いない変更では対象から外れます。

`codegen` ジョブと `visual` ジョブは、この絞り込みに到達しません。どちらも `relevant` が真であるだけ
で走るため、関連する変更はすべて両方を起動します。どちらのジョブも走らせないシナリオだけを変えた
場合も同様です。`codegen` ジョブは、`components.yaml`（`make -C demos/showcase ui-test`）と、
`text_editing.yaml`、`gestures.yaml`、`gestures_multitouch.yaml`、`codegen_extra.yaml` の 4 つの
カバレッジシナリオ（`make ui-test-coverage`）から、ネイティブ XCUITest をビルドして走らせます。
`visual` ジョブは、コミット済みのピクセル視覚回帰テスト（VRT）を `visual/visual_ios.yaml` に対して
走らせます（`make e2e-visual`）。たとえばどちらのジョブも走らせない `smoke.yaml` を変えても、両方が
シミュレータを起動してネイティブテストを再ビルドします。変更が影響しえない作業です。

BE-0322 がこの 2 つのジョブに手を伸ばさなかった理由は、その絞り込みを安全にしている性質そのもの
です。BE-0322 の対応表は、各ジョブが共有アクション `bajutsu-e2e` にすでに渡している `scenarios:`
入力から読まれるため、対応表はジョブ自身による実行内容の宣言であり、そこから乖離しません。
`codegen` ジョブと `visual` ジョブは、代わりに `demos/showcase/Makefile` のターゲットでシナリオを
宣言しており、ワークフローだけを読む [`job_scenario_map`](../../scripts/e2e_changes.py) はこれを
一切見ません。したがって BE-0322 からは、この 2 つは何も宣言しないディメンションジョブに見えます。
何も宣言しないジョブは、安全側に倒す過剰選択として、関連する変更すべてで走らなければなりません。
この 2 つを絞り込む価値があるのは、対応表を、今日アクション入力に結び付いているのと同じ強さで
`Makefile` の実体に結び付けられる場合だけです。`Makefile` の編集が黙って古くしうる手書きのシナリオ
一覧は、実際に走らせる変更からジョブを外してしまいます。変更が壊しうるジョブをスキップするこの
挙動こそ、BE-0322 の設計が防ぐために存在する fail-closed 違反です。

## 詳細設計

作業は、`codegen` ジョブと `visual` ジョブのシナリオを、それらが名指しされる唯一の場所である
`Makefile` のターゲットからジョブへ対応づけることです。その対応づけを、乖離しないよう機械的に検証
したうえで、フィーチャージョブがすでに使うシナリオ単位の条件に 2 つのジョブを載せます。以下の内訳は、
*進捗* の 1 ボックスにつき 1 ユニットに対応します。

- **`Makefile` からの実体取得（ユニット 1）**：ディメンションジョブごとに、その `Makefile` ターゲット
  が実際に codegen または実行するシナリオファイルを抽出するリーダーを追加します。`codegen` では
  `components.yaml` と 4 つのカバレッジシナリオ、`visual` では `visual/visual_ios.yaml` です。リーダー
  はコミット済みのターゲットのレシピを解析するので、集合はレシピの写しではなくレシピ自体に追随します。

- **乖離ガード（ユニット 2）**：`e2e_changes` のテストスイートに、ワークフローが `codegen` と `visual`
  のそれぞれに対応づけるシナリオ集合が、その `Makefile` ターゲットの走らせる集合（ユニット 1）と
  等しいことを表明するテストを追加します。このテストは、絞り込みが BE-0322 の不変条件を保つための
  要です。`Makefile` の編集がどちらかのターゲットからシナリオを足したり減らしたりした日には、対応づけ
  も一緒に動かない限り、テストが `make check` を落とします。このテストがなければ、対応づけは BE-0322
  が禁じる乖離そのものです。このテストがあれば、対応づけはアクション入力の対応表と同じくらい実体に
  縛られます。

- **シナリオの対応づけ（ユニット 3）**：`e2e_changes.py` に、`codegen` と `visual` が `Makefile` で
  宣言するシナリオを、`affected` の計算がすでに使うジョブとシナリオの対応表へ畳み込ませます。これに
  より、どちらかのシナリオへの変更がそのジョブを `affected` に載せます。今日 `codegen` / `conformance`
  / `visual` を、関連する変更すべてで走るディメンションジョブとして記録しているモジュールの docstring
  を、シナリオ単位になった 2 つのジョブの新しい規則を述べるよう更新します。

- **ジョブの配線（ユニット 4）**：[`ios-e2e.yml`](../../.github/workflows/ios-e2e.yml) の `codegen` と
  `visual` の `if:` を、`needs.changes.outputs.relevant == 'true'` から、フィーチャージョブが使う
  シナリオ単位の形へ変えます。`relevant` かつ（`shared` または `contains(fromJSON(… affected),
  '<job>')`）の形にし、共有コードの変更、または自分のシナリオへの変更で走り、それ以外では外れる
  ようにします。

- **ドキュメント（ユニット 5）**：どのジョブが変更で起動するかを説明する日英の CI ドキュメントを更新し、
  本項目と BE-0322 を双方向にリンクします。

`conformance` はディメンションジョブのままです。シナリオの部分集合ではなくドライバ適合性ハーネス
全体を駆動するため、絞り込みの鍵にできるシナリオを宣言しておらず、関連する変更すべてで走り続け
なければなりません。本項目は iOS 専用です。Android と web のレーンはジョブをシナリオで絞っておらず、
その `codegen` と `visual` に相当するものは、シナリオ単位ジョブを持たないレーンについて BE-0322 が
定めるレーン全体の挙動に、すでにフォールバックしています。

## 検討した代替案

**乖離ガードなしでワークフローにシナリオを宣言する。** 各ジョブに素朴な `scenarios:` 一覧を足し、
今日と同じく読むだけなら、`Makefile` パーサーもなく、はるかに少ないコードでジョブを絞れます。この案
は、BE-0322 の設計が取り除いた乖離を呼び戻すため却下します。一覧と `Makefile` ターゲットは同じ事実の
独立した 2 つの写しになり、あるターゲットのシナリオを変える `Makefile` の編集が一覧を黙って古くし、
走らせる変更からジョブを外します。乖離ガード（ユニット 2）こそが、この絞り込みを安全に足せる理由の
すべてです。

**ワークフローから `Makefile` ターゲットへシナリオ一覧を渡す。** シナリオを `make` 変数
（`make ui-test SCENARIOS=…`）として渡せば、ワークフローの宣言がターゲットの走らせる実際の入力に
なり、宣言が生きたアクション入力を裏付けるフィーチャージョブと揃います。より整った最終形ですが、
今日シナリオをレシピ内に名指ししている `ui-test`、`ui-test-coverage`、`e2e-visual` のレシピを
作り直す必要があります。これらのレシピはローカルでも走るため、リーダーとガードによる案よりも影響
範囲とリスクが大きくなります。絞り込み自体が入ったあとの、望ましい後続作業として記録します。

**`codegen` と `visual` をディメンションジョブのままにする。** 現状は関連する変更すべてで両方を
起動します。乖離ガードが対応づけを `Makefile` に縛れば絞り込みは安全だと示せること、そしてこの 2 つ
はシミュレータを起動しネイティブテストをビルドするレーン随一の高コストのジョブであり、無駄な起動を
取り戻す価値があることから、却下します。
