## はじめに

Bajutsu のシナリオは、2つ以上の[ターゲット](../../docs/ja/glossary.md#target-app-device)を宣言し、
ステップをターゲットのあいだで交互に実行できます
（[BE-0428](../BE-0428-multi-target-scenario-execution/BE-0428-multi-target-scenario-execution-ja.md)）。
ただし、そうしたシナリオでは現在ステップを再利用できません。ローダーは、再利用可能なコンポーネントを
呼び出す `use:` ステップと、レポート上で折りたたむ区間に名前を付ける `group:` ステップを、どちらも
拒否します。この拒否は、推測せずに失敗させる（fail closed）ための意図的な判断でした。展開によって
生まれるステップへターゲットをどう伝えるかを、BE-0428 が未解決のまま残したためです。

この提案は、その未解決の問いに答え、2つの拒否を解除します。展開後のステップは、次のどちらかの
経路でターゲットを受け取ります。

- **呼び出し側から**：`use:` ステップと `group:` ステップに `target` を書けるようにします。展開は、
  生成するステップのうち `target` を省略したものすべてに、その値を刻み込みます（stamp します）。
- **コンポーネント側から**：呼び出し側が `target` を省略した場合、展開後の各ステップは自分の
  ターゲットを、直接またはターゲットグループを通じて指定します。どちらも指定しないステップは、
  シナリオに `primaryTarget` があればそれに解決されます。

```yaml
targets: [showcase-swiftui, web]
steps:
  # 呼び出し側がターゲットを固定する。`web-login` のステップはすべて `web` で実行される。
  - use: { component: web-login, with: { email: a@b.com } }
    target: web
  # コンポーネントが自分のステップを2つのターゲットへ振り分ける。
  - use: { component: like-and-verify }
```

展開は、これまでどおり読み込み時のマクロです。`bajutsu run` が受け取るのは、BE-0428 が検証する
ステップごとの `target:` を持つ平坦な形のままです。そのため、ランナー、レポート、
Command Line Interface（CLI）には変更が要りません。

## 動機

シナリオが2つ以上のターゲットを宣言すると、各ステップは実行先のターゲットを指定しなければ
なりません。ただし、シナリオが `primaryTarget` を宣言していれば、ステップは `target` を省略できます。
`use:` ステップは、このどちらの形でも規則を満たせません。展開は `use:` ステップをコンポーネントの
ステップ列で丸ごと置き換えるので、`use:` ステップに付けた修飾フィールドは何の知らせもなく
捨てられます。そのため `Step` モデルは、`target` も含めて、`use:` ステップへの修飾フィールドを
すべて拒否します（[`step.py`](../../bajutsu/common/scenario/models/steps/step.py)）。`group:`
ステップは `target` を受け付けますが、展開はその値を同じように捨てます。必須のフィールドを一方の
ステップは保持できず、もう一方のステップは黙って失います。BE-0428 はこの状況で、両方のステップを
一律に拒否しました（[`_targets.py`](../../bajutsu/common/scenario/models/scenario/_targets.py)）。
同じ領域を扱った後続の3項目も、この拒否を残しています。

- **プライマリターゲット**：[BE-0436](../BE-0436-primary-target-default/BE-0436-primary-target-default-ja.md)
  はステップが `target` を省略できるようにしました。ただし、`use:` ステップの展開後のステップがどのターゲットを
  受け取るべきかという問いには、`primaryTarget` では答えられないと本文に明記しています。
- **ターゲットグループ**：[BE-0437](../BE-0437-multi-target-step-groups/BE-0437-multi-target-step-groups-ja.md)
  は、ひとまとまりのステップに1つのターゲットを刻み込みます。グループの中に置いた `use:` は、
  刻み込まれた後で結局この拒否に当たります。
- **割り込み**：[BE-0438](../BE-0438-multi-target-interrupts/BE-0438-multi-target-interrupts-ja.md)
  は `interrupts` の各エントリにターゲットを与えましたが、復旧ステップ中の `use:` は拒否したままです。

この拒否は、再利用がもっとも必要な場面で、いちばん重くのしかかります。ターゲットをまたぐ流れでは、
サインイン、画面遷移、準備の手順をクライアントごとに繰り返すのが普通です。作者が真っ先に
コンポーネントへ切り出すのも、こうした手順です。showcase のデモ
[`cross_platform_app_web.yaml`](../../demos/showcase/scenarios/cross_platform_app_web.yaml) は、
5ステップの Web サインインをインラインで書き下しています。単一ターゲットのシナリオなら、
同じ手順は `use:` の1行で済みます。既存のシナリオに2つ目のターゲットを足す作者は、そのシナリオが
呼ぶコンポーネントもすべてインライン化しなければなりません。複製した手順は、時間とともに
食い違っていきます。

また、この拒否が実際に守っている安全は、見た目ほど大きくありません。`expand_components` は、
自分の出力に対してターゲットの検査をもう一度すべて実行します。BE-0428 が、`target` を省略した
ステップを持つコンポーネントを捕まえるために、この検査を加えました。つまり読み込み時の拒否が防いでいるものは、危険ではありません。
「展開後のステップがどのターゲットを受け取るべきか」という未解決の問いです。この提案がその答えを定めれば、既存の展開後の検査が、展開されたステップすべてに
ターゲットの規則を適用します。手書きのステップに適用するのと同じ方法です。ただし、抜けが1つ
残ります。`if`、`forEach`、`web:`、`app:` の本体の中にある `use:` ステップは、展開されません。
この提案は、後述の「制御フローの本体の中での展開」のとおり、この抜けも塞ぎます。

この提案が実現したことは、次の3つの観察できる事実で確かめられます。

- マルチターゲットの showcase シナリオが、Web サインインを手順の書き下しではなく、`use:` と
  `target: web` によるコンポーネント呼び出しで実行しています。
- 経路を正しく指定して `use:` や `group:` を呼ぶ2ターゲットのシナリオが、問題なく読み込めます。
  `use: is not yet supported when the scenario declares 2 targets` で失敗しなくなります。ターゲットの
  欠落や衝突は引き続き失敗しますが、構文そのものを理由に拒否されることはなくなります。
- [`docs/ja/scenarios.md`](../../docs/ja/scenarios.md) の制限事項の節と `group:` の段落のどちらも、
  マルチターゲットのシナリオで拒否される構文として `use:` と `group:` を挙げなくなります。

## 詳細設計

### 展開後のステップがターゲットを受け取る2つの経路

展開後のステップがターゲットを受け取る経路は2つあり、呼び出し側がターゲットを指定したかどうかで
決まります。

| 呼び出し側（`use:` / `group:` ステップ） | 展開後のステップが `target` を省略 | 展開後のステップが `target` を指定 |
|---|---|---|
| `target: X` を指定 | `X` を刻み込みます | `X` と同じなら受け付け、異なれば読み込み時に拒否します |
| `target` を省略 | 同じ位置の手書きのステップと同じく解決します。`primaryTarget` があればそれに、なければ読み込み時のエラーになります。割り込みの復旧ステップは例外で、監視が発火したランナーの上で動きます | 書かれたとおりに残し、宣言済みのターゲットと照合します |

1行目は、単一ターゲットのコンポーネントを扱います。サインインや画面遷移の補助のように、呼び出し元の
デバイスを前提としない手順です。2行目は、ターゲットをまたぐコンポーネントを扱います。
このコンポーネントは、自分のステップをシナリオのターゲットへ振り分けます。振り分けには、明示的な
`target` フィールド、ターゲットグループ、`target: ${params.device}` のようなパラメータのいずれも
使えます。パラメータの置換はターゲットの検査より先に走るので、パラメータを使う形に新しい仕組みは
要りません。

### `use:` ステップの `target`

`Step` モデルは、`use:` ステップに付く他の修飾フィールド（`capture`、`extract`、`name`、`from`）を
引き続き拒否します。展開は、これらを今後も捨てるからです。`target` だけが例外になります。今後の展開は
`target` を捨てずに引き継ぐからです。残る修飾フィールドを拒否するエラーメッセージは
変わりません。

[BE-0437](../BE-0437-multi-target-step-groups/BE-0437-multi-target-step-groups-ja.md) のターゲットグループは、自分のターゲットを直下の子ステップそれぞれに刻み込みます。したがって、ターゲットグループの中に
置いた `use:` ステップは、グループのターゲットを呼び出し側のターゲットとして受け取ります。
グループ自身の規則は変わりません。グループの子は、`use:` ステップも含めて、自分では `target` を
省略します。

### 衝突：同じターゲットなら受け付け、異なるターゲットなら拒否する

呼び出し側が `X` を指定していても、展開結果のステップが自分のターゲットを指定している場合が
あります。両者が同じターゲットを指すなら、読み込みはそのステップを受け付けます。共有の
コンポーネントファイルは、単独で読んでも意図がわかるようにターゲットを書いておけます。呼び出し側が
同じ値を重ねて書いても、実行先のデバイスに曖昧さは生じません。

両者が異なる場合、読み込みは失敗します。どちらの値を選んでも推測になるからです。

- **呼び出し側を優先する場合**：コンポーネントの作者は、意図してそのステップの実行先を選んで
  います。その選択を上書きすると、作者が想定していないデバイスでステップが動きます。
- **コンポーネント側を優先する場合**：呼び出し側は、すべてのステップを `X` で動かすよう求めて
  います。1つのステップだけが抜け出ると、その求めが何の知らせもなく破られます。

エラーは、コンポーネントの呼び出し連鎖とステップを示します。次のような形です。

```text
use: web-login > step 'submit': target 'showcase-swiftui' conflicts with the caller's target 'web'
```

展開は、循環検出のために、たどったコンポーネント名の連鎖をすでに記録して
います。そのため、このメッセージのために新たな記録は要りません。

同じ規則で、拒否を解除した後に現在の展開のままでは誤って扱われる場合も決着します。コンポーネント内のターゲット
グループが `use:` ステップを持つとき、`expand_components` は入れ子の呼び出しを展開した後で
グループのターゲットを刻み込みます。このとき、別のターゲットを指定した入れ子のステップは、その
ターゲットのまま残ります。この提案では、ターゲットグループが自分のターゲットを入れ子の `use:` へ渡します。
入れ子の `use:` は、受け取った値を呼び出し側のターゲットとして扱います。値が異なれば、読み込みは失敗するようになります。

### 制御フローの本体の中での展開

現在の `expand_components` は、各ステップ列の最上位だけをたどります。`if` / `else` の分岐、
`forEach` の本体、`web:` / `app:` のブロックには入り込みません。そのため、こうした本体の中の
`use:` ステップは展開されないまま残ります。2つ以上のターゲットがあるとき、`if` / `forEach` の本体では、読み込み時の拒否がこの抜けを
隠しています。ただし `web:` / `app:` のブロックの中のステップはこの拒否を通らないので、
隠れません。拒否が働かない場所では、シナリオは読み込めてしまいます。展開されて
いない `use:` ステップは、アクションを持たないステップとして実行ループに届きます。実行ループは、
1つのシナリオを失敗させるのではなく、実行全体を `AssertionError` で中断します。
[BE-0439](../BE-0439-step-groups-report-folding/BE-0439-step-groups-report-folding-ja.md) も、
コンポーネント経由でこうした本体に入った `group:` について、同じ抜けを記録しています。

マルチターゲットの拒否を解除すると、分岐を持つマルチターゲットのシナリオすべてが、この抜けに
さらされます。そこでこの提案は、`expand()` が本体の種類ごとに次のように再帰するようにします。

- **`if` / `else` と `forEach` の本体**：`use:` ステップを、最上位と同じように展開します。
- **`web:` / `app:` のブロック**：`use:` ステップをここでも展開します。ブロックがすでにデバイスを
  決めているので、`use:` ステップと、そこから生成されるステップはすべて `target` を省略します。
- **これらの本体の中で見つかった `group:`**：読み込み時のエラーにします。BE-0439 のネスト規則は
  もともとこの位置の `group:` を禁止しています。このエラーは、コンポーネントが持ち込んだ `group:`
  にもその規則を広げます。

この再帰は、現在同じ `use:` ステップが実行を中断させている次の場合も直します。

- ターゲットが0個か1個のときの、すべての本体です。
- ターゲットが2つ以上のときの、`web:` / `app:` のブロックです。

すでに読み込めて実行できているシナリオの、実行時の挙動は変わりません。実行ループが展開されない
`use:` に届くと現在は必ず中断するので、成功している実行がそうした `use:` に依存することは
ありません。ただし、読み込み時の挙動は1つの場合で変わります。条件が偽の `if` や、空のリストに対する
`forEach` のように、実行が通らない分岐の中の `use:` です。こうした `use:` は実行ループに届かない
ので、現在は中断しません。読み込み時に展開すると、そこにある壊れた参照が読み込み時の失敗になり、
今は成功しているシナリオが失敗するようになります。壊れた参照とは、未知のコンポーネント、不足または
未知のパラメータ、循環などです。この提案はこの変化を受け入れます。もともと正しくない参照は、
通らない分岐に隠すより、はっきり失敗させるほうがよいからです。

### 呼び出し側のターゲットが届く範囲

呼び出し側のターゲットは、展開が生成するすべてのステップに、深さを問わず届きます。刻み込みは、
`if` / `else` の分岐と `forEach` の本体に入り込みます。入れ子の `use:` にも入り込み、そこから先へ
もう一度ターゲットを渡します。刻み込みは、`web:` ブロックと `app:` ブロックで
止まります。これらのブロックの中のステップは、囲むブロックが解決したデバイスで必ず動くので、
`target` を省略しなければなりません。既存の展開後の検査が、この規則を展開後のステップにも
引き続き適用します。

この深さは、ターゲットグループと異なります。ターゲットグループは直下の子にだけ刻み込み、
`if` / `forEach` の本体を新しいスコープとして残します。ターゲットグループのステップはシナリオの中に
インラインで並ぶので、作者はすべての分岐を見渡せ、分岐ごとに別のターゲットを指定できます。
一方、コンポーネントの作者は、どの呼び出し側からも使える形で一度だけ書きます。コンポーネント内の
本体にターゲットの指定を求めると、コンポーネントが自分の実行先を知る必要が生じます。それでは
呼び出し側から指定する形の意味がなくなります。分岐の中で2つ目のターゲットを必要とする
コンポーネントは、ターゲットをまたぐコンポーネントであり、表の2行目の扱いになります。

### `group:` も同じ規則に従う

`group:` ステップは、すでに `target` を受け付けます。その意味を、`use:` ステップの `target` と
そろえます。展開は、グループが生成するすべてのステップにその値を刻み込み、深さと衝突の規則も
`use:` と同じです。`target` を省略した `group:` ステップでは、各子ステップが、同じ位置の手書きのステップと同じ
規則で解決されます。
[BE-0439](../BE-0439-step-groups-report-folding/BE-0439-step-groups-report-folding-ja.md) の
レポート上の折りたたみは変わりません。折りたたみは、展開がすでに書き込むタグを読むだけだからです。

### 規則を検査する場所

`_check_target_requirements` は、現在次の4か所で走ります。

1. `Scenario` モデルのバリデータ。読み込み時で、展開より前です。
2. `expand_components`。コンポーネントのステップを差し込んだ後です。
3. `apply_setups`。共有のセットアップ前処理を先頭に足した後です。
4. config レベルの `before` / `after` フックの折り込み。

1か所目の検査は、`use:` ステップと `group:` ステップを拒否しなくなります。ステップ自身の
`target` があれば、宣言済みのターゲットを指していることは引き続き確かめます。`target` がなくても
エラーにはせず、プライマリターゲットにも解決しません。また、この時点では `group:` ステップ自身の
`steps` の中には入り込みません。子ステップにはまだ呼び出し側のターゲットが刻み込まれていないので、
ここで検査すると `target` を持つ正しい `group:` を拒否してしまうからです。子ステップは2か所目で
検査します。解決は、展開が生成するステップの役目であり、後の検査がそれらのステップを見ます。

2か所目では、`expand_components` が展開後の各ステップに刻み込みを済ませてから、既存の検査を
走らせます。検査は、すべてのステップに通常のステップ単位の規則を適用します。2つ以上の
ターゲットがあれば必須、省略時は `primaryTarget` に解決、`web:` / `app:` の中では禁止、という
規則です。割り込みの復旧ステップは、次の節で述べる独自の規則に従います。

`run` をはじめ、シナリオを実行するすべての利用側は、
[`load_expanded.py`](../../bajutsu/common/scenario/load_expanded.py) か
[`run/cli.py`](../../bajutsu/run/cli.py) を通じてシナリオを読み込みます。どちらの経路も
`expand_components` を呼びます。上の再帰によって、この経路から展開されないまま出る `use:` ステップはなくなります。
そのため、拒否を解除しても、展開されないままランナーに届く経路は増えません。
`lint` や serve の audit のような静的な読み手は、展開前のファイルを解析します。これらは今後、
`target` を持つ `use:` や `group:` のステップを目にするので、テストでもその形を扱います。

### 割り込みの復旧ステップとライフサイクルフェーズ

2つ以上のターゲットを宣言したシナリオでも、`interrupts` エントリの復旧 `steps` に `use:` ステップと
`group:` ステップを置けるようになります。呼び出し側がターゲットを指定していれば、展開は他の場所と
同じように刻み込みます。呼び出し側が指定しなければ、`target` を省略した展開後の復旧ステップは、
[BE-0438](../BE-0438-multi-target-interrupts/BE-0438-multi-target-interrupts-ja.md) の既存の
復旧規則に従います。つまり、割り込みの監視が発火したランナーの上で動き、`primaryTarget` には
解決されません。

シナリオ自身の `before` と `after` のライフサイクルステップは、本体の `steps` と同じ規則に
従います。ターゲット config 側では、`_no_component_in_target_steps` が引き続き `use:` と `group:` を
一切拒否します。対象は `before`、`after`、`interrupts` です。
この拒否の理由は別にあります。ターゲット config はコンポーネントの展開を通らないため、
この提案は手を付けません。

### ターゲットを宣言しない、または1つだけ宣言するシナリオ

ターゲットの経路指定について変わるのは、新しいフィールドが増えることだけです。`use:` ステップの `target` は、他のステップと
同じ規則に従います。シナリオがターゲットを宣言しなければ省略し、1つだけ宣言すれば、省略するか、
そのターゲットを指定します。呼び出し側がそのターゲットを指定した場合、刻み込みは同じ値を展開後の各ステップに書くだけなので、
既存の検査はそのまま通ります。呼び出し側が省略した場合、展開は何も刻み込みません。なお、これらの
シナリオでも、「制御フローの本体の中での展開」で述べた再帰は働きます。本体の中の `use:` も展開され、
実行が中断しなくなります。

### 変わらないもの

ランナー、レポート、CLI、codegen は、展開後のシナリオを読みます。いずれもステップごとの
`target:` を持つ平坦な形をすでに扱えます。刻み込まれたステップと手書きのステップを区別することも
ありません。`Component` モデルに新しいフィールドは増えません。ターゲットを指定しない
コンポーネントは、単一ターゲットとマルチターゲットのどちらのシナリオからも引き続き使えます。

### 作業分解（MECE）

1. **スキーマ**：`Step` の `use:` に対する修飾フィールドの拒否から、`target` を除外します。
2. **読み込み時の検査**：`_check_step_target` で、`use:` / `group:` の拒否を、明示された `target` の
   照合に置き換えます。省略された `target` は未解決のまま残します。
3. **再帰**：上に挙げた制御フローの本体へ、`expand()` が入り込むようにします。
   そこで見つかった `group:` は、読み込み時のエラーにします。
4. **刻み込み**：`expand_components` で、呼び出し側のターゲットを `use:`、`group:`、ターゲットグループの
   展開を通じて引き継ぎます。深さの規則に沿って刻み込み、呼び出し連鎖を含む衝突エラーを出します。
5. **テスト**：次の各場合を扱います。
   - 各種の本体の中の `use:` を、単一ターゲットとマルチターゲットの両方のシナリオで確かめます。
   - コンポーネントが本体の中に持ち込む `group:` を確かめます。
   - 表の両方の行を、衝突する値と同じ値の両方で確かめます。
   - 深さの規則を確かめます。`web:` / `app:` で止まることも含みます。
   - 入れ子のコンポーネントと、パラメータで渡すターゲットを確かめます。
   - 復旧ステップと、`primaryTarget` への解決を確かめます。
   - `primaryTarget` のない2ターゲットのシナリオで、`target` を持つ `group:` を確かめます。
   - 実行が通らない分岐の中の壊れた `use:` が、読み込み時に失敗することを確かめます。
6. **ドキュメントとデモ**：「ドキュメント」の節に挙げたページを両言語で更新し、showcase の
   シナリオを書き換えます。

## 検討した代替案

- **呼び出し側だけでターゲットを指定する**：2つ以上のターゲットがあるとき `use:` ステップの
  `target` を必須にし、コンポーネントの中では禁止する案です。規則は単純になりますが、
  コンポーネントが2つのターゲットをまたげなくなります。アプリで操作して Web で確かめるような
  ターゲットをまたぐ手順こそ、マルチターゲットのシナリオが表現するための流れです。
- **コンポーネント側だけでターゲットを指定する**：`use:` ステップの `target` は拒否したまま、
  コンポーネントの各ステップに自分のターゲットを書かせる案です。すべてのコンポーネントが呼び出し側の
  ターゲット名を知る必要が生じ、1つのサインイン用コンポーネントを iOS と Web の両方のターゲットで
  使えなくなります。
- **衝突時にどちらかを黙って優先する**：上で退けました。どちらを選んでも、誰も求めていない
  デバイスにステップを送ることになります。決定性の原則は、推測するより失敗することを求めます。
- **値が同じでも衝突として拒否する**：ターゲットグループの子はグループのターゲットを書き直せない
  という、より厳しい規則にそろえる案です。ただし共有のコンポーネントファイルは、ターゲットグループの
  インラインの子と違い、呼び出し側とは別に読まれ、保守されます。ファイル内のターゲット指定は意図を
  記録するものであり、同じ値には拒否すべき曖昧さがありません。
- **制御フローの本体の中の `use:` は拒否したままにする**：最上位とターゲットグループの直下だけで
  拒否を解除する案です。提案は小さく済みますが、分岐を持つシナリオでは、サインインをやはり再利用
  できません。上で述べた単一ターゲットでの実行の中断も残ります。
- **ターゲットグループと同じく最上位だけに刻み込む**：コンポーネント内の `if` / `forEach` の本体を
  新しいスコープとして残す案です。上で退けました。分岐を持つ単一ターゲットのコンポーネントが
  自分のターゲットを指定しなければならなくなり、特定の呼び出し側に縛られます。
- **`Component` モデルにターゲットを宣言させる**：コンポーネントが想定するターゲットを列挙する
  フィールドを足し、呼び出し側が対応づける案です。この対応づけは新しい概念を持ち込みますが、
  同じ必要はパラメータの置換（`target: ${params.device}`）ですでに満たせます。
