## はじめに

`serve` の Settings モーダルに、読み取り専用の **Server** タブを追加します。このタブは、起動中のサーバがどう構成されているかを表示します。

- デプロイ形態
- 束縛している config とその由来
- 実行できる[バックエンド](../../docs/ja/glossary.md#driver-backend-actuator-platform)
- 実行結果の保存先、保持期間、同時実行数の設定

最も有用な情報として、このサーバが同梱の iOS XCUITest テストランナーを備えているかどうかも示します。表示する値はすべて、起動時に解決済みのサーバ状態と、ファイルシステムの探索 1 回から得られます。そのためこのタブは、Tier-1 で読み取り専用であり、AI を一切使いません。タブが表示するものは、`run` の判定に関与しません。

## 動機

`serve` は起動時に、コマンドラインフラグ、環境変数、束縛した config から、多くの設定を解決します。しかしブラウザ側は、そのほとんどを見せていません。UI を見ているだけでは、「このサーバは結局どんな設定で動いているのか」に、起動コマンドを見直さないかぎり答えられません。Settings モーダルは、すでに公開している 2 つの運用者向けの関心事（AI プロバイダとシナリオシークレット）をまとめています。サーバ自身の設定には、そこに置き場所がありません。

この欠落が最も鋭く現れるのが、iOS テストランナーです。[BE-0292](../BE-0292-xcuitest-bundled-runner/BE-0292-xcuitest-bundled-runner-ja.md) 以降、`xcuitest.testRunner` を指定しない iOS [シミュレータ](../../docs/ja/glossary.md#target-app-device)実行は、汎用 XCUITest ランナーへフォールバックします。このランナーは、wheel が package data として同梱します。フォールバックが働くのは、wheel が実際にランナーを同梱している場合です。素のソースチェックアウトと、macOS 以外向けの wheel は、ランナーを同梱しません。

XCUITest は、iOS の唯一のバックエンドになりました（[BE-0290](../BE-0290-xcuitest-default-ios-backend/BE-0290-xcuitest-default-ios-backend-ja.md)）。そのため、ランナーが配置されているかどうかが、iOS シミュレータ実行を開始できるかどうかそのものを左右します。今のところ、ランナーが配置済みかを知る唯一の手段は、実行を始めて結果を見ることです。

「iOS テストランナー: 配置済み（Xcode 16.2 / SDK 18.2 でビルド）」あるいは「未配置」という 1 行があれば、その混乱を未然に防げます。この 1 行は、読み取り専用でサーバ全体にかかわる事実であり、Settings モーダルが答えるべきものです。

## 詳細設計

この機能は、構造上 Tier-1 の読み取り専用で、AI に依存しません。解決済みの `ServeState` を読み、同梱ランナーの有無を wheel 上で探索するだけです。表示するものは実行ごとのシグナルではないため、決定論的な `run` / CI ゲートには一切触れません（プライムディレクティブ 1）。

作業は MECE な 4 つの単位に分かれます。

**単位 1：読み取り専用のサーバ情報エンドポイント。** `GET /api/server` → `ops.server_settings(state)` を追加します。このオペレーションは新設で、`bajutsu/serve/operations/config.py` の `config_info` の隣に置きます。両バックエンドがディスパッチできるよう、共有のルートテーブルに登録します（[BE-0253](../BE-0253-serve-route-registry-unification/BE-0253-serve-route-registry-unification-ja.md)）。

オペレーションは、起動中サーバの解決済み設定を JSON として組み立てます。含めるのは次のものです。

- デプロイ形態（ローカルかホスト型か）
- 束縛した config と、その取得元および provenance（`config_info` と `config_content` がすでに算出しているものを再利用）
- このサーバが実行できるバックエンド
- 実行結果と baseline の保存ディレクトリ
- ソフト削除の保持期間
- 同時実行数の上限（全体、ユーザ単位、org 単位）
- 起動中のバージョン文字列（BE-0272 のヘッダバッジ向けに `server_version` がすでに返している公開値）

このエンドポイントの認可の姿勢は `config_info` と同じで、どの閲覧者にも開かれています。したがって、その姿勢がすでに許すものだけを露出しなければなりません。`server_checkout` が返す admin 限定のコミットとブランチは、ここではあえて出しません。ブランチ名は進行中の作業の主題を漏らしうるため、`server_checkout` はまさにその理由で、ブランチを admin 呼び出しの背後に置いています。

エンドポイント自身のホストパスには、[BE-0108](../BE-0108-hosted-config-source-restriction/BE-0108-hosted-config-source-restriction-ja.md) の論拠を適用します。ホスト型の利用者は、ホストとファイルシステム上の関係を持ちません。ホストの絶対パスは無意味な情報であり、不要な露出です。そこで、config のパスと、実行結果および baseline の保存ディレクトリを、`state.hosted` のとき伏せます。

この規則は、`config_info` よりあえて厳しくしています。`config_info` は、自身の `config` パスを無条件で返します。より広いサーバ情報の面では、その挙動をそのまま真似ず、ホスト型ではホストパスを伏せます。パス以外の項目（デプロイ形態、バックエンド、保持期間、同時実行数の上限、バージョン）は、どちらでも表示します。公開するのは有無と設定内容だけで、シークレットの平文は決して含めません。

**単位 2：ペイロードへの同梱 iOS テストランナーの配置状態。** 単位 1 のペイロードに、`iosRunner` ブロックを追加します。ブロックは、同梱ランナーの探索（`bundled_products_dir()` と `bundled_runner_build_info()`）から得ます。ブロックが報告する事実は 3 点です。

- このビルドが、同梱の汎用 XCUITest ランナーを備えているか（`bundled_products_dir()` が `None` でないか）。
- 備えている場合に、ランナーがどのツールチェインでビルドされたか（`bundled_runner_build_info()` が返す Xcode とシミュレータ SDK のバージョン）。
- 束縛した config が、`xcuitest.testRunner` でランナーを明示的に上書きしているか。

これらの探索は、プライベートなサブモジュール `bajutsu.platform_lifecycle.environments._bundled_runner` にあります。そのサブモジュールを含む `environments` パッケージの `__init__` は、プラットフォーム個別のモジュールへ手を伸ばさず、パッケージルートから import するよう求めています。`server_settings` は別のパッケージにあります。そこでこの単位では、まず 2 つの探索を `environments` パッケージルートで再エクスポートし、そこから import します。再エクスポートによって、オペレーション層はプライベートなサブモジュールから切り離されます。

3 点を合わせれば、「ランナーを指定しない iOS シミュレータ実行はランナーを見つけられるのか、そのランナーは何を対象にビルドされたのか」に、実行を始めずに答えられます。同梱ランナーは設計上アプリ非依存なので（BE-0292）、この情報はアプリ単位ではなくサーバ全体にかかわるものにとどまります。

ここで iOS にだけ専用ブロックを設けるのは、iOS ランナーが、その不在でバックエンド 1 つ丸ごとを黙って塞いでしまう、サーバ全体の唯一の readiness の事実だからです。同じ形は、後からバックエンド単位の readiness マップ（Playwright のブラウザが入っているか、`adb` に到達できるか）へ一般化できます。一般化すれば、2 つ目の一回きりのフィールドを継ぎ足さずに済みます。ただしそれらの事実は、本項目が埋める欠落ではありません。そのため本項目は iOS ランナーだけを挙げ、一般化はフォローアップに委ねます。

**単位 3：Settings モーダルの Server タブ。** `bajutsu/templates/serve.html.j2` の AI タブと Secrets タブの隣に、3 つ目のタブ（`data-settab="server"`、パネル `#setpanel-server`）を追加します。このタブは、既存の 2 つとまったく同じように、`serve.core.mjs` の `showSettingsTab` に組み込みます。

`loadServerInfo()` 関数が、モーダルを開いたときに `/api/server` を取得します。関数は、各値をラベル付きの読み取り専用の行として描画します。iOS ランナーは、「配置済み / 未配置」の 1 行で示します。配置済みなら、その行に理由とビルド時のツールチェインを添えます。このタブに入力欄はありません。報告するだけで、何も変更しません。

**単位 4：テスト。** テストは 2 つの領域を覆います。

- `server_settings` のオペレーション単位のテスト：
  - ローカルとホスト型での、ホストパスの伏せ方。
  - 同梱の有無によるランナー分岐。products ディレクトリを注入した場合と、不在の場合を確かめます。
  - `xcuitest.testRunner` の上書きが、ペイロードに反映されること。
- `GET /api/server` が両バックエンドでディスパッチされることを確かめる、ルート登録のテスト。

いずれのテストも、決定論的でデバイス不要です。エンドポイントは、状態を読み、ファイルシステムを探索するだけです。そのためシミュレータは要らず、コアのゲートは Linux でも動きます。

## 検討した代替案

- **doctor パネル（BE-0148）に統合する。** 却下しました。doctor は*ターゲット単位*の問いに答えます。このターゲットは実行可能か、その画面はアドレス可能か、という問いです。doctor は、起動済みデバイスとライブ画面のクエリを必要とします。サーバ設定ビューは*サーバ全体*にかかわり、静的で、デバイス不要です。2 つのビューは、問いも入力も異なります。同居させれば両方が曖昧になります。
- **バージョンバッジ（BE-0272）を拡張する。** 却下しました。バッジは、起動中コミットを示すヘッダ上の単一の要素です。複数の値を持つ読み取り専用の設定面は、ヘッダに詰め込まず、他の運用者向けの関心事の隣、すなわち Settings モーダルに置くべきです。
- **Settings タブではなく新しいトップレベルビューにする。** 却下しました。このビューが示すのは運用者の設定で、Settings モーダルがすでにまとめている関心事（プロバイダ、シークレット）そのものです。別のトップレベルビューにすると、「どう設定されているか」を見る面が 2 か所に分裂します。
- **iOS ランナーの配置状態だけを表示する。** 検討のうえ、サーバ設定を網羅的に見せるビューを選んで、見送りました。ランナーは、ブラウザが起動中サーバの設定をほとんど見せていないという、一般的な欠落の最も鋭い一例です。タブはその欠落全体に対処しつつ、ランナーの配置状態を最も目立つ行に据えます。
