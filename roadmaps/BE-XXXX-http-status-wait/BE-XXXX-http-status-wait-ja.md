## はじめに

`http` ステップは、Hypertext Transfer Protocol（`HTTP`）のリクエストを 1 回送って次へ進みます。本項目は任意の `timeout` を追加します。指定すると、期待する状態コードが返るまでリクエストを繰り返します。

## 動機

テストは、サービスが後から終える処理に依存することがよくあります。たとえば、ボタンを押した数秒後に届く認証コードです。[BE-0036](../BE-0036-utility-steps/BE-0036-utility-steps-ja.md) の `http` ステップは、後から終わる処理を待てません。早すぎるリクエストは検査に失敗し、固定時間の待機は決定性の原則に反します。

[BE-0046](../BE-0046-otp-email-steps/BE-0046-otp-email-steps-ja.md) の `email` ステップは待機できますが、読めるのはメールだけです。

変更の効果は、応答の遅いサービスを `sleep` ステップなしで待つシナリオが成功することで確認できます。

## 詳細設計

### `timeout` の指定

`http` ステップに、秒単位の `timeout` を任意項目として追加します。

```yaml
- http:
    url: "${secrets.API}/codes/latest"
    status: 200
    timeout: 30
    saveBody: response
```

`timeout` を指定すると、応答が `status` と一致するまで約 1 秒間隔でリクエストを繰り返します。規則は次の表のとおりです。

| 状況 | 動作 |
|---|---|
| `status` のない `timeout` | シナリオの読み込みエラー |
| `GET` と `HEAD` 以外のメソッド | シナリオの読み込みエラー。再送でデータが重複して作られる恐れがあるため |
| 異なる状態コード | 次の試行へ進む |
| 接続エラー | 直ちに失敗 |
| 1 回のリクエストの上限 | 残り時間まで。最長 30 秒 |
| 成功 | 成功した応答の本文を `saveBody` に保存 |
| 期限切れ | 最後に受け取った状態コードを示して失敗 |
| 実行のキャンセル | ほかの条件待ちと同じく待機を中断 |

`timeout` を指定しない場合の動作は、現在と変わりません。成功の条件は状態コードだけです。データがそろう前から本文が空の 200 を返すサービスには、この待機を使えません。

また、`email` と違い、新しいデータかどうかは判定しません。古い値を拾わないためには、実行ごとに固有の対象を問い合わせます。たとえば `generate` ステップで作ったアドレスを使います。

### 最優先原則との関係

| 原則 | 本設計での守り方 |
|---|---|
| 合否の判定にモデルを使わない | 状態コードの数値を比較 |
| 決定性 | 待機は、期待する状態コードか必須の期限で終了 |
| アプリ非依存 | 接続先と状態コードはシナリオに書き、ランナーはアプリごとに変えない |

## 検討した代替案

| 代替案 | 採用しなかった理由 |
|---|---|
| 複数ステップを囲む汎用の再試行構文 | 画面操作まで繰り返せてしまい、必要を大きく超えて言語が広がる |
| 本文がパターンに一致するまで待機 | 要望は状態コードだけ。条件は後続の項目で追加できる |
| データがそろうまで応答を返さないサーバーを前提化 | そのような呼び出しを持たないサービスが多い |
