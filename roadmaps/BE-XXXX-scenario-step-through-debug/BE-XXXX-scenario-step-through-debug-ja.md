## はじめに

`bajutsu run` は、シナリオを最初のステップから最後のステップまで実行します。この項目では、`run` にデバッグ用の
モードを加えます。`--step` は各ステップの前で `step>` プロンプトに停止します。`--break` は指定したステップで停止します。
`--break-on-fail` は失敗したステップで停止します。停止しているあいだ、オペレーターは [`repl`](../../docs/ja/cli.md#repl)
のコマンドで動作中のアプリを読み取り、実行を続けるか、`quit` で終えます。停止の判断は、run 自身のステップ番号と名前
だけにもとづく決定的な処理です。判定は、これまでどおりシナリオのアサーションだけが決めます。

## 動機

失敗したシナリオからわかるのは、どのステップが失敗したかと、そのステップの証跡までです。セレクタが外れた理由を
知るには、デバイスを見ながらシナリオ全体を再実行するか、レポートを開いてスクリーンショットを見比べる必要があります。
`bajutsu repl` は要素ツリーを読み、id に対して操作できます。ただし毎回新しく起動し、シナリオを把握していないため、
14 番目のステップに着くには、1 から 13 番目までを手で打ち直すことになります。`serve` の Author ビューはライブの
スクリーンショットからセレクタを選べますが、対象のステップまでシナリオを実行してはくれません。現状、シナリオを
実行して途中で止めるコマンドはありません。

この項目の成果は、1 回の作業で確認できます。作者が `bajutsu run --scenario checkout.yaml --break-on-fail` を実行すると、
失敗したステップで画面を残したまま run が止まります。プロンプトで `tree` と打てば、そのステップのセレクタが照合された
要素の表が、再起動なしで表示されます。`next`、`continue`、読み取りコマンドだけを使った run は、フラグなしで同じ
シナリオを実行したときと同じアサーションで判定します。

## 詳細設計

### 振る舞い

1. **フラグ。** `run` に 3 つのフラグを加えます。`--step` は最初のステップを含め、すべてのステップの前で停止します。
   `--break <name-or-index>` は複数回指定できます。ステップに書かれた `name` か、run がネストしたステップ全体に
   振る 10 進のインデックスに一致します。このインデックスは、`step 3 (tap): …` のような失敗理由の `3` と同じ番号です。
   `--break-on-fail` は失敗したステップで 1 回だけ停止します。どれを指定してもプロンプトが開きます。
2. **プロンプト。** プロンプト `step> ` は stderr に出すため、stdout は `PASS|FAIL` の 1 行のままです。ステップの前では
   `⏸ before step N [name]: <label>` を、失敗の後では `✘ step N failed: <reason>` を表示します。
3. **コマンド。** `next`（`n`、または空行）はステップを実行し、次のステップの前でまた停止します。`continue`（`c`）は
   次のブレークポイントまで実行します。`quit`（`q`、`exit`、または入力の終端）は run を終えます。Ctrl-C も run を終えます。端末が
   run の録画やブラウザにも Ctrl-C を届けるためです。`help` で一覧を出します。
   これら以外の行は、そのステップの動作中のドライバーに結びついた `repl` のコマンド群に渡します。
4. **終了。** `quit` は `RunCancelled` を送出します。協調的なキャンセル
   （[BE-0370](../BE-0370-graceful-run-cancel/BE-0370-graceful-run-cancel-ja.md)）がすでに使っている例外です。
   シナリオは `cancelled` として報告し、証跡は既存の巻き戻し処理が仕上げ、終了コードは 1 です。
   失敗で止まっているときの `quit` は例外を送出せずに戻るため、シナリオは失敗理由をそのまま残します。
5. **判定。** アプリを操作するコマンド（`tap`、`type`、`scroll`、`back`、`step <yaml>`）を実行すると、その run は
   手動操作を含むものになります。最初の操作コマンドの動詞を `RunResult.interactive` と `result.json` に記録します。
   行の残りは保存しません。`type` や `step` は、設定済みのシークレットではない値を手で入力したものを含みうるうえ、
   結果は保存されアップロードもされるためです。すべてのステップが成功していたシナリオは、`interactive: <verb>` で失敗します。すでに失敗していたシナリオは、元の
   理由を保ちます。読み取り（`tree`、`find`、`screenshot`）とステップ送りは、判定に影響しません。コマンドは実行の
   前に記録します。例外で終わった操作でも、アプリの状態を動かしている可能性があるためです。
6. **拒否。** デバイスを確保する前に、`run` は次の場合に終了コード 2 で拒否します。stdin か stderr が端末でない場合、
   シナリオが複数ある場合、`--browsers` のエンジンが複数ある場合、`--workers` が 1 を超える場合です。誰にも見えない
   プロンプトは CI のジョブを止めてしまいます。スイートでは、1 つを除くすべてのシナリオがプロンプトの前で待たされます。
7. **打ち間違い。** run の後に、どのステップにも一致しなかったブレークポイントを stderr に表示します。

### 組み込む場所

| 部品 | 場所 | 役割 |
|---|---|---|
| `StepGate`、`StepPause` | `bajutsu/common/orchestrator/types/step_gate.py` | ループが呼ぶプロトコル。`before_step`、`after_failure`、`manual_action` を持ちます |
| `_LoopConfig.step_gate` | `bajutsu/common/orchestrator/loop/_loop_config.py` | `cancelled` や `progress` と並べて gate を運びます |
| `_StepRunner.exec_steps` | `bajutsu/common/orchestrator/loop/_step_runner.py` | キャンセル判定とルーティングの直後、`_run_one` の前で gate を呼びます |
| `StepLoopState.failure_paused` | `bajutsu/common/orchestrator/loop/step_loop_state.py` | 外側の `if` / `forEach` / `web` の階層ごとではなく、失敗ごとに 1 回だけ停止させます |
| `run_scenario` | `bajutsu/common/orchestrator/loop/_functions.py` | 結果に `interactive` と失敗理由を記録します |
| `PromptStepGate` | `bajutsu/run/step_gate.py` | プロンプト本体です。ブレークポイント、コマンド、ドライバーごとの `ReplSession` を扱います |
| `_build_step_gate` | `bajutsu/run/cli.py` | フラグを解釈し、上の拒否を適用します |

gate をステップの境界に置くのは、その位置ですでにキャンセルを判定しているためです
（[BE-0370](../BE-0370-graceful-run-cancel/BE-0370-graceful-run-cancel-ja.md)）。ステップはまだ動作しておらず、
中途半端な操作が残らず、画面も落ち着いています。gate はシナリオ自身のステップにだけ働きます。`before` と `after` の
フック段階と、`interrupts` の規則による回復ステップでは働きません。回復は実行中のステップの内側で
動くため、そこで止まると、そのステップのタイムアウトを消費してしまいます。停止は `_run_one` が時計を読み始める前に起きます。そのため、オペレーターがプロンプトに
どれだけ留まっても、ステップの記録上の所要時間と、各条件待ちのタイムアウトは変わりません。録画は停止中も続きます。経過時間に反応するアプリは、長い停止の後に異なる振る舞いをしうるため、
gate が止めたときは、キャッシュしていた `before` のツリーとスクリーンショットを捨てます。

プロトコルは `common/orchestrator` に、プロンプトは `run` に置きます。import の契約が、決定的なコアから
`bajutsu.run` と `bajutsu.repl` を切り離しているためです。コアはプロトコルとしてだけ gate を知っており、
`cancelled` と `progress` がすでにコアへ届いている方法と同じです。

### 対象外

- ステップ実行のための `serve` UI。停止のプロトコルは共有できるため、後続の項目でボタンを加えられます。
  この項目は端末から先に出します。
- ステップのやり直し、巻き戻し、プロンプトからのシナリオ編集。やり直しはステップの副作用を重ねて実行し、
  カウンターとレポートの整合を崩します。
- スイート、`--browsers` のマトリックス、ワーカープールのステップ実行。
- シナリオ単位の `expect` の不一致での停止。`--break-on-fail` が扱うのはステップの失敗です。`expect` はステップループが
  終わった後に評価されるため、gate を組み込んだ境界の外にあります。
- モデル呼び出し。プロンプトと停止の規則は、モデルを読みません。

## 検討した代替案

| 案 | 内容 | 採らなかった理由 |
|---|---|---|
| `repl` に `load <scenario>` を足す | シェルの中からステップを実行する | `repl` はアプリを自分で起動し、`run` のリース、証跡 sink、リトライ、アラートガードを持ちません。2 つ目のランナーを育てることになります |
| `--from-step N` フラグ | N 番目まで飛ばして実行する | ステップは前のステップ（ログインや抽出した `vars.*`）に依存するため、飛ばした先がシナリオの通らない画面になります |
| 失敗時の停止だけにする | もっとも小さい変更 | 失敗に至るまでのステップを見られません。デバッグに必要なのは、その部分がほとんどです |
| 毎ステップの停止だけにする | ブレークポイントを持たない | 30 ステップのシナリオで 28 番目に着くのに、`next` を 28 回押すことになります |
| 手動操作を含む run を通常どおり判定する | コードがもっとも少ない | オペレーターが手でやり直したステップが、シナリオでは再現できない成功として残ります |
| プロンプトでの操作を許さない | run を純粋に保つ | 修正の試行、たとえばセレクタが外した部品のタップは、止める主な理由です。許さなければ、終了して再実行することになります |
