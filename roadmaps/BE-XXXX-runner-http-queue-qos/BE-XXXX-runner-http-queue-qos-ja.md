## はじめに

Bajutsu の iOS バックエンドは、シミュレータの内側で動く小さな HTTP サーバと通信します。このサーバは
XCUITest のプロセスが抱えており、Apple の Dispatch ライブラリで作った2つのキューへ仕事を振り分けます。
ソケットの accept ループを回す直列キューと、受け付けた接続をそれぞれ処理する並行キューです。どちらの
キューも quality of service（QoS）を宣言していません。QoS とは、その仕事を他のすべてと比べてどう
スケジュールするかを、Dispatch が判断するための優先度の階級です。

本項目は、その QoS を宣言します。QoS を指定せずに作ったキューが、それによって低い優先度に固定される
わけではありません。Dispatch は、`async` による投入元スレッドの QoS をそうしたキューへ伝播させ、
`.userInitiated` を上限として引き継がせます。指定の欠落が実際に失っているのは、保証です。要求経路
全体の優先度は、accept ループを起動した文脈から引き継いだものであり、その投入の連鎖が変わらないあいだ
だけ正しさを保ちます。両方のキューに `.userInitiated` を宣言すれば、ドライバの準備完了のプローブと
生存確認のプローブが通る通信路の優先度を固定できます。サーバの起動位置をのちに動かす人が、優先度を
導き直し、しかも黙って違う値に導き直してしまう余地をなくせます。

## 動機

今日の優先度は決定ではなく結果であり、それを生む連鎖は壊れやすいほどに長いです。サーバは XCUITest の
テストメソッドからメインスレッド上で起動され、そのスレッドは高い QoS で走ります。accept ループは
`async` で QoS 未指定の直列キューへ投入されるため、その QoS を `.userInitiated` を上限として引き継ぎ
ます。各接続はさらに accept ループから `async` で QoS 未指定の並行キューへ投入され、順に引き継ぎます。
したがって実効の優先度は、おそらくすでに `.userInitiated` です。本項目が書き下そうとしているのは、
まさにその値です。しかしコードはそれをどこにも述べていないため、何もそれを保つ仕組みがありません。
サーバをバックグラウンドの補助処理から起動しても、投入に別のキューを経由させても、異なる QoS を持つ
Swift の並行性の文脈を採用しても、すべての接続処理の優先度は、診断もテストの失敗も伴わずに動きます。

この優先度が支配する経路は、runner の生存を判断する経路そのものです。ドライバの準備完了の待機は runner
が応答するまで `GET /health` を叩き、実行中のクラッシュ復旧は同じエンドポイントを期限つきで叩きます。
どちらも期限が過ぎたときに、runner が応答をやめたと結論します。したがって、この経路のスケジューリング遅延は
単に遅いだけではありません。混み合ったホストでは、死んだ runner と見分けがつきません。Bajutsu の iOS の
ジョブは GitHub が提供する macOS のランナーで走ります。Xcode 26 のもとでのシミュレータの資源の圧迫は
上流で文書化され、いまも解決していない問題であるため、混雑は例外ではなく想定される状態です。

接続経路は2箇所でブロックもします。だからこそ、その優先度は単に整えるだけでなく固定する価値があります。
接続の処理は、同時に走る処理を8つに抑える計数セマフォを待ちます
（[BE-0287](../BE-0287-xcuitest-runner-multitouch-resilience/BE-0287-xcuitest-runner-multitouch-resilience-ja.md)）。
また XCUITest の操作は、メインスレッドへ移る前に排他ロックを取り、メインスレッドの仕事が返るまで保持し
続けます
（[BE-0323](../BE-0323-xcuitest-readiness-crash-respawn/BE-0323-xcuitest-readiness-crash-respawn-ja.md)）。
保持している側が待っている側より低い優先度で動くブロックする待機は、Apple の Thread Performance Checker
が優先度逆転として報告する形です。そして2つの待機はいずれも、2つの接続処理のあいだで引き継いだ優先度に
食い違いが生じたときにこの形をとります。

そうした逆転が実際に起きたかは決着していませんし、本項目はそう装いません。accept ループを名指しする
Thread Performance Checker の報告は、以前の調査で失敗したジョブの捕捉出力に観測されました。しかしその
実行は記録されておらず、いま提示できません。直近の失敗した `ios-e2e` の実行12件を探してもその警告は
見つからず、2026年8月9日から8月12日までの失敗はいずれも実行中のクラッシュ復旧のタイムアウトを報告して
いました。コードだけから逆転を導いても隙間は埋まりません。セマフォとロックを待つのは他の接続処理だけで
あり、それらは同じ accept ループから QoS を引き継ぐため、通常は一致します。この基準を測り直すことは、
下の作業の前提ではなく最初の一歩です。

その基準がなくても本変更を正当化する根拠は、より狭く、それでも足ります。呼び出し側がブロックして待つ
仕事に対して QoS の明示は正しい宣言であり、遅延に敏感な経路のキューに対して Apple の道具が勧めるところ
でもあります。しかも、引き継いだ性質を明示した性質へ変える費用は2行であり、変更がスケジューリング以外の
挙動に及ぶことはありません。本項目は flake の減少を計測したとは主張しませんし、そう示唆するのは誤りです。

## 詳細設計

作業は2つの単位です。単位2は単位1に依存しないため、どちらが先に入ってもかまいません。

1. **Thread Performance Checker の基準を測り直す。** runner がいまも優先度逆転の報告を引き起こすか、
   引き起こすなら報告のスタックが何を名指しするかを確かめます。Checker は runner の捕捉出力へ書き出し、
   fault-injection と visual のジョブはその出力をすでにジョブの成果物として上げています。したがって
   この計測に新しい配線は要りません。それらのジョブを走らせ、捕捉出力を grep するだけです。結果は
   本項目に記録します。上の考察が予期している否定的な結果も含めて記録します。報告が出た場合、それは
   待っている側と保持している側のスレッドを名指しします。それこそが、逆転をコードが許す形から、記述に
   値する機構へ変えるものです。

2. **両方のキューに `.userInitiated` を宣言する。** runner の HTTP サーバには、accept ループの直列
   キューと接続の並行キューがあります。その構築時に `qos: .userInitiated` を渡します。このサーバが
   処理する要求はすべて、ドライバがその返答にブロックしているからこそ存在します。それがまさに
   user-initiated の意味するところです。あわせて、この水準が QoS の伝播がいま暗黙に与えているものを
   固定するために宣言されている、と記すコメントを添えます。のちの読み手が、明示された値を飾りと読む
   ことも、今日走っている優先度が変わったと思い込むことも避けるためです。

   `.userInteractive` ではなく `.userInitiated` にする根拠は2つです。第一に、`.userInteractive` は
   メインスレッド自身の階級であり、ユーザインタフェースの応答性を保つために1フレームのうちに完了し
   なければならない仕事のためのものです。ソケットの読み取りと要求の解析はそれにあたらず、そう名づける
   ことは要件を誤って述べます。第二に、処理は最大8つが同時に走ります。その処理のブロックしていない
   仕事はソケットからバイトを読んで解析する仕事です。それが、同じ処理がこのあと待つメインスレッドの
   仕事と対等な優先度で競合してしまいます。`.userInitiated` はメインスレッドの階級のすぐ下、既定の
   すぐ上に位置し、この経路が求める関係はそちらです。

   変更は2つのコンストラクタ呼び出しに限られ、要求の処理には触れません。したがって runner の挙動は、
   スケジューリングを除いて変わりません。Swift のパッケージは、端から端までのジョブがすでに走らせて
   いる iOS のツールチェーンの一部としてビルドされます。そしてそれらのジョブの最初の段は、runner が
   `/health` へ応答すること自体に依存しています。ここでの間違いは、わかりにくい形をとらず、即座に
   大きな音を立てて失敗します。

## 検討した代替案

- **両方のキューを宣言せずに、QoS の伝播に頼る。** 現状であり、今日のコードの上では筋が通ります。
  メインスレッドからの起動による伝播が、すでに `.userInitiated` を与えているからです。伝播は優先度を
  サーバの性質ではなく呼び出し箇所の性質にしてしまうため却下します。誰かが起動位置を動かすまでは
  成り立ち、動かした時点で黙って崩れます。2行で、偶然の代わりに保証が手に入ります。
- **保持しているスレッドに優先度を宣言する代わりに、ブロックする待機そのものを取り除く。** より深い
  修正です。何もブロックしなければ逆転は起こりません。意図的な設計に対するはるかに大きな変更であるため
  却下します。セマフォは、長いジェスチャのあいだにヘルスポーリングが積み上がらないよう同時に走る処理
  を抑えますし、ロックは XCUITest の操作がメインスレッドへ届く前に直列化します。それが防いでいる再入は、
  テストホストを即座に中断させるからです。どちらにも存在する理由があり、本項目はその理由を蒸し返し
  ません。
- **`.userInteractive` を宣言して、処理を最上位の階級に置く。** 資源が逼迫したホストでは、優先度は高いほど
  よいように見えるので魅力があります。単位2で挙げた2つの根拠により却下します。この階級はソケットの
  処理をフレームの期限を持つ仕事だと誤って述べますし、8つの処理がメインスレッド自身の優先度で競い合え
  ば、その処理が依存しているメインスレッドの仕事と競合します。
- **再現する逆転が得られるまで何も変えない。** 証拠に対するもっとも厳しい読み方であり、単位1を独立した
  単位として置いた理由でもあります。項目の全体としては却下します。QoS を宣言する根拠は逆転に依存して
  いないからです。生存を判断する経路の優先度が引き継ぎに任されている状態は、それがまだ実行1回を失わせて
  いなくても、固定する価値があります。
