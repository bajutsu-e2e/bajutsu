## はじめに

セルフホスト向けのサーバーバックエンド（[BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md)）は、現在単一の Linux ノードで動いています。Redis を取り除いたことで（[BE-0106](../BE-0106-post-completion-worker-model/BE-0106-post-completion-worker-model-ja.md)）、Postgres が唯一のステートフルな単一障害点（SPOF）になりました。Postgres は、ジョブキュー（`jobs` テーブル）、セッション、クォータの状態、実行メタデータを一度に抱えています。

この提案は、その SPOF を取り除く高可用性の構成を定めます。構成は、レプリカを伴う Postgres プライマリ、冗長化したロードバランサ、バックアップ済みのオブジェクトストアです。あわせて、単一ノードのデプロイが受け入れられるのはどのような場合か、そのトレードオフを明示します。この作業は、BE-0016 の「単一ノードをプールへ育てる」作業から切り出したものです。

## 動機

単一ノードは小規模なセルフホストには十分です。しかし、Postgres、ロードバランサ、MinIO ノードのいずれかが故障すれば、サービス全体が止まります。Postgres はキュー、セッション、クォータ、実行履歴をまとめて抱えているため、これを失うと4つすべてを一度に失います。

リリースゲートとして Web UI に依存するチームは、1つのディスクや1つのホストが原因の際限のない停止を受け入れられません。運用者が各 SPOF を意図的に取り除くには、文書化され検証された堅牢な構成が必要です。同時に、次の明確な記述も必要です。単一ノードが受け入れられるのは、運用者がそれを SPOF として明示的に受け入れ、検証済みのバックアップを持っている**場合に限り**ます。

## 詳細設計

このティアはすべてデプロイと運用の作業です。Python 側の面を持たないため、`make check` ゲートではまったく動かせません。価値は、文書化され検証された構成にあります。作業分解は、SPOF を1つずつ扱う次のとおりです。

1. **Postgres の高可用性。** 自動フェイルオーバーを伴うプライマリとレプリカ（たとえば Patroni）を置きます。少なくとも、検証済みのポイントインタイムバックアップとリハーサル済みのリストアを用意します。Postgres はキュー、セッション、クォータ、実行メタデータを抱えているため、最初に取り除く価値が最も高い SPOF です。
2. **オブジェクトストアの冗長化。** 冗長化した MinIO（分散配置や消去符号による構成）を使います。少なくとも、バックアップ済みのバケットを用意し、単一のディスク故障で成果物が失われないようにします。動画による証跡は容量が大きいため、バックアップ先はそれに見合う容量にします。
3. **冗長化したロードバランサ。** 浮動アドレスを持つ二台目のロードバランサを置きます。方式は、keepalived と Virtual Router Redundancy Protocol（VRRP）、または DNS ベースのフェイルオーバーです。これで入口そのものが SPOF ではなくなります。N レプリカによる制御プレーンのスケールアウト（兄弟項目の「制御プレーンのスケールアウト」）と組み合わせられますが、分離もできます。単一のアプリレプリカでも入口を堅牢にします。
4. **単一ノードのトレードオフの明示。** 単一ノードは、運用者がそれを SPOF として明示的に示し、検証済みのバックアップとリストアを持っている**場合に限り**受け入れられるセルフホストである、と文書化します。多くのセルフホストが単一ノードであるという正直な既定を保ちつつ、耐障害性があるかのようには装いません。

```
[DNS] → [HAProxy ×2 (VRRP)] → [FastAPI ×N] ─┬─ Postgres (primary+replica)  ← queue / sessions / quotas
                                            └─ MinIO (redundant / backed-up)
```

**検証。** ゲートによる担保がないため、運用者がデプロイ上で手動で検証します。フェイルオーバーの訓練が本当のテストです。

- Postgres プライマリを落とし、キューとセッションを保ったままレプリカが引き継ぐことを確認します。
- ロードバランサを落とし、浮動アドレスが移ることを確認します。
- オブジェクトストアをバックアップからリストアし、成果物が読めることを確認します。

成果物には、これらの訓練の手順書を含めます。

## 検討した代替案

- **単一ノードを恒久的なものとして受け入れる。** 最終形としては却下しますが、明示付きの選択肢としては残します。単一ノードは趣味のデプロイには十分ですが、チームのリリースゲートは単一ディスクの際限のない停止に耐えられません。折衷は、単一ノードのトレードオフを、高可用性であるかのように装うのではなく*文書化*することです。
- **セルフホストの高可用性の代わりに、マネージドクラウドの Postgres とオブジェクトストアを使う。** ここでは対象外です。それは完全なマネージド公開クラウドの話であり、このセルフホスト項目ではなく [BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md) の担当です。
- **Postgres の高可用性の代わりに、アプリケーション層でキューを複製する。** 却下します。Postgres がすでに十分に備えている永続的な複製を、作り直すことになるからです。Postgres の高可用性に寄せれば、キュー、セッション、メタデータを、複数ではなく1つの仕組みで一貫させられます。
