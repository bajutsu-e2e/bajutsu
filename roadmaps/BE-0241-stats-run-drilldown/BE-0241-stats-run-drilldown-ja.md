## はじめに

Stats ダッシュボード（[BE-0102](../BE-0102-run-stats-dashboard/BE-0102-run-stats-dashboard-ja.md)）は、スイート全体の傾向を見せます。日付・バックエンド別の合格率と、失敗の多いシナリオ、ステップのアクション、アサーションの種別です。ただし、表示される数値はすべて集計値にとどまります。「2026-07-10、idb、4 件失敗」というセルや「`LoginScenario > tap` が 12 回失敗」という行を見ても、どの run で起きたのかをたどる手がかりがありません。

現状では、Stats ページを離れる必要があります。`serve` のシングルページアプリケーション（SPA）が持つ run 履歴一覧（`#panel-history`）を開き、フィルタも並び替えもできない一覧を目で追って、該当しそうな run を探します。

本項目は、Stats ダッシュボードの日付、バックエンド、シナリオ、ステップ／アサーションのホットスポットという各軸をクリック可能にします。クリックすると、該当する run だけが並びます。そこから、既存の run 単位のレポート（BE-0068）へ進めます。

## 動機

- **BE-0102 は読み取り専用の設計であり、その性質は変わりません。** 本項目が足すのは、集計時にすでに計算済みのデータへのナビゲーションです。新しい判定も、新しい永続データも持ち込みません。
- **レポートビューアと run 履歴一覧は、すでにあります。** BE-0068 の `/runs/<id>/report.html` は、保存済みマニフェストから都度描画されます。履歴一覧は、`bajutsu/templates/serve.panels.js` の `loadHistory()` が `bajutsu/templates/serve.html.j2` の `#panel-history` に描画し、各行はクリックでレポートを開きます。新規に作るものはほとんどなく、欠けているのは次の二点だけです。第一に、Stats の集計処理は、ホットスポットを数え終えた時点で run id を捨てています。第二に、履歴一覧にはフィルタがなく、run id が分かっても絞り込む先がありません。
- **現状のフローは手作業で、間違いも起きやすいです。** 「`LoginScenario` の `tap` が 12 回失敗」と読んだ利用者は、フィルタも並び替えもない履歴一覧から、該当する 12 件を推測します。場合によっては、数百件の run が対象になります。日付・バックエンド単位のセルなら、`by_run` が各点に `day` と `backend` を持つため、手間がかかるだけで済みます。シナリオ・ステップ・アサーションのホットスポットは、生のマニフェストを手で読み返さない限り、現状では特定できません。

## 詳細設計

この設計は、既存のデータを既存の UI へつなぐだけのものです。新しい永続データも、新しいエンドポイントも、新しいレポートビューアも必要としません。

1. **ホットスポット集計に run id を残します**（`bajutsu/stats.py`）。`_failing_scenarios`、`_failing_steps`、`_failing_assertions` は、各 run のマニフェストを走査し、シナリオ、`scenario > action`、アサーション種別をキーに `Counter` を積み上げます。現状では、数え終えた時点でマニフェストの `runId` を捨てています。`Hotspot` に `run_ids: tuple[str, ...]` フィールドを追加し、決定性のためソート済みにします。各アグリゲータは、既存の理由の集計と並べて、キーごとの該当 run id も集めます。`_hotspots()` がすでに落とし込んでいるのと同じ形です。`by_day` と `by_backend` は変更不要です。`Stats.by_run` が各点に `run_id`、`day`、`backend` を持つためです。日付やバックエンドのクリックは、ページがすでに持つデータへのクライアント側の絞り込みだけで答えられます。
2. **各セルをサーバー側でディープリンクとして描画します**（`bajutsu/templates/stats.html.j2`）。`stats.html.j2` は、現状 `<script>` タグを一つも持たない純粋なサーバーレンダリングの Jinja ページです。本項目もその状態を保ちます。対象は、`by_day` の各行、`by_backend` の各行、`failing_scenarios` / `failing_steps` / `failing_assertions` の各行です。各セルを `<a href="/?tab=history&runs=id1,id2,…">` というリンクにし、クエリ文字列はテンプレートが直接組み立てます。日付・バックエンドの行は、テンプレート内で `stats.by_run` を絞り込んで id を導出します。ホットスポットの行は、新しい `Hotspot.run_ids` を使います。Stats ページには、新しい inline script を持ち込まず、追加の API 呼び出しもしません。クライアント側の振る舞いはすべて SPA 側（手順 3）に置き、BE-0102 が確立した「1 回の集計、1 枚のページ」という形を崩しません。
3. **既存の履歴一覧に絞り込んで着地させます。** `/stats` と `serve` の SPA は、現状では別ルートです。クリックすると、対象の run id を URL に載せて SPA へ遷移します。例は `/?tab=history&runs=id1,id2,…` です。読み込み時に、`serve.js` / `serve.panels.js` がこのクエリを読み取り、History タブへ切り替えます。そのうえで、`loadHistory()` の描画に新しいクライアント側の絞り込みを適用し、該当する行だけを表示します。履歴一覧は現状フィルタを持たないため、この絞り込みが本項目で履歴一覧に加える唯一の新しい振る舞いです。一覧の上部に「絞り込み：<ラベル>（N 件）・解除」という表示を添え、全件表示へ戻せるようにします。絞り込まれた行をクリックしたときの挙動は、今日と変わりません。その run の `/runs/<id>/report.html`（BE-0068）を開きます。
4. **ステップ・アサーション単位の粒度は run までにとどめます。** スコープを詰めた議論のとおり、ステップやアサーションのホットスポットをクリックすると、それが失敗した run まで履歴一覧を絞り込み、既存の run 単位のレポートを開きます。`report.html` 内の該当ステップにアンカーを張ったり、ハイライトしたりはしません。より細かい単位へのジャンプは自然な発展形ですが、本項目のスコープには含めません。

## 検討した代替案

- **Stats ページ自体に専用の絞り込み一覧やモーダルを作る案。** 却下しました。`serve` の SPA にある run 履歴一覧のレンダリングと、レポートへのクリック遷移を、重複して作ることになります。この点で、新しい面を作るより既存を再利用するというリポジトリの流儀に反します。BE-0102 自身が `report.html` や `audit` への合流を退けたときの論拠と同じです。既存の履歴一覧へ絞り込んで遷移させれば、レンダリング経路を一つに保ったまま、同じ結果が得られます。
- **オンデマンドで計算する新規の `/api/runs?matching=…` エンドポイント。** 却下しました。集計処理は、今日 `/stats` が描画している件数と同じ 1 回のパスの中で、各ホットスポットの該当 run id もすでに計算しています。新しいエンドポイントを設けると、ページがすでに持つデータを再計算するか、別途キャッシュすることになります。さらに、単一の自己完結したレンダリングが、ページ本体と追加のフェッチの 2 段構えに変わります。id を既存の `/stats` の HTML に埋め込むほうが、BE-0102 の「1 回の集計、1 枚のページ」という形を保てます。
- **ドリルダウン時に `report.html` 内の該当ステップにアンカーを張ってハイライトする案。** 却下ではなく保留です。あれば有用ですが、`report.html` には現状ステップ単位のアンカーや id がありません。本項目が届ける run 単位のドリルダウンを妨げるものではなく、切り離して後続作業にできます。
