## はじめに

この項目は、`POST /api/run-set` にオプトインのフラグ `failFast` を追加します。フラグを立てたグループでは、最初に失敗で終わったジョブが、同じグループの未完了のジョブをすべて取り消します。グループの `conclusion` は `failure` のままです。フラグで止まったジョブは止まった理由を記録するので、グループを読む側は、失敗したシナリオと実行されなかったシナリオを区別できます。

`run-set` は、ターゲットのシナリオごとに1つのジョブを、id を持つ**グループ**として登録します（[BE-0484](../BE-0484-job-group-lease/BE-0484-job-group-lease-ja.md)）。現在は、兄弟のジョブがどうなっても、グループのすべてのジョブが最後まで実行されます。

## 動機

ログインを壊したプルリクエストは、スイートの大半のシナリオを壊します。後続のシナリオは同じ画面で、同じタイムアウトを経て失敗します。40シナリオのグループは、最初の失敗で答えが出ているにもかかわらず、スイートの全体にわたってデバイスとワーカーの枠を占有します。デバイスクラウドでは、その実行のすべてにデバイス時間の課金も発生します。

止めるための部品は、グループにすでに揃っています。`POST /api/run-set/<groupId>/cancel` は、グループの未完了のジョブをすべて取り消します。キューにあるジョブはその場で `cancelled` になり、リース中のジョブはワーカーの次のハートビートで止まります。欠けているのは契機です。グループのジョブが失敗しても、この取り消しを呼ぶものがありません。呼び出し側がグループをポーリングして手で取り消すこともできます。しかしその場合は、呼び出し側ごとに同じポーリングのループを書くことになり、停止もポーリングの間隔だけ遅れます。

観測できる違いは2つあります。`failFast: true` で登録し、最初に終わったジョブが失敗したグループでは、その失敗が記録された時点でキューに残るジョブがなくなります。また、`GET /api/run-set/<groupId>` は、フラグで止まった各ジョブに `cancelReason: failFast` を付け、人が取り消したジョブと区別します。

## 詳細設計

### リクエストのフィールド

`POST /api/run-set` は、省略可能なフィールド `failFast` を1つ追加で受け取ります。真偽値で、既定値は `false` です。それ以外の型はステータス 400 で拒否します。グループは、このフラグを `job_groups` の新しい列 `fail_fast` に保存します。

グループキーの再送と別のリクエストを見分けるリクエストダイジェストに、このフラグを加えます。同じグループキーで `failFast` だけが異なるリクエストは別のリクエストとして扱い、現在ほかの違いに対してそうしているのと同じく、ステータス 409 を返します。

### 失敗に数えるもの

契機の判定には、グループの `conclusion` と同じ規則を使います。ジョブが取り消されずに終端の状態に達し、次のどちらかを満たすとき、停止の契機になります。

- ジョブの状態が `failed` です。リースがすべての試行で期限切れになった場合も含みます。
- ジョブの状態が `done` で、`exitCode` が 0 以外です。

取り消されたジョブは、停止の契機になりません。契機にすると、人がジョブを1つ取り消しただけでグループ全体が取り消されるからです。

### 停止する場所

取り消し以外で終端の状態に達する経路は、リポジトリに次の3つがあります。

- `complete_job`：ワーカーが結果を送ったとき
- `fail_job`：ワーカーがエラーを報告したとき
- `reclaim_expired_leases`：最後の試行でリースが期限切れになったとき

どの経路も、終端の状態を1つのストアのトランザクションで書き込んでいます。ジョブが `fail_fast` を立てたグループに属し、失敗の規則を満たすとき、同じトランザクションでグループのほかの未完了のジョブに印を付けます。キューにあるジョブは `cancelled` になります。リース中のジョブには取り消しのフラグを立て、現在の取り消しと同じく、ワーカーが次のハートビートでそのフラグを読みます。停止が働くのは、終端の状態の条件付きの書き込みがその行で成功したときだけです。`complete_job` と `fail_job` は古いワーカーの結果を拒否し、`reclaim_expired_leases` はハートビートが更新したリースを拒否します。拒否された書き込みは、何も取り消しません。終端の状態と印を1つのトランザクションで書くので、失敗が記録されたあとにワーカーが兄弟のジョブをリースする隙間は生じません。

各経路は、取り消したキューのジョブの id を返します。呼び出し側はコミットの後で、それぞれのジョブのライブのログのストリームを取り消しの結果で閉じます。現在の取り消しのルートと同じ処理です。これらのジョブの結果を送るワーカーはいないので、閉じなければ、ジョブは実行中のまま見え続けます。期限切れの回収の経路には、もう一段の手当てが要ります。`reclaim_expired_leases` は `lease_jobs` の中で動き、`lease_jobs` は現在その結果を捨てています。そのため、リースはそれらの id を、ログのバスを持つリースのルートへ返す必要があります。その方法は実装で決めます。

### 止まった理由の記録

各ジョブのレコードに、NULL を許す列 `cancel_reason` を追加します。取り消しのルートがキューにあるジョブを取り消すか、リース中のジョブに取り消しのフラグを立てたときは `user` を書き込みます。上の停止がそのどちらかを行ったときは `failFast` を書き込みます。誰も取り消さなかったジョブでは `NULL` のままです。

`GET /api/run-set/<groupId>` は、各ジョブでこの列を `cancelReason` として返します。グループの `conclusion` の規則は変えません。`failure` が `cancelled` に優先するので、フラグで止まったグループの `conclusion` は `failure` になります。

### 決定性

フラグは判定を変えません。失敗したジョブを含むグループの `conclusion` は、フラグの有無によらず `failure` です。停止の前にほかのどのシナリオが実行されたかは、リースの順序とワーカーの空き枠の数で決まります。そのため、同じグループを2回実行すると、実行されたシナリオの集合が異なることがあります。グループの報告はフラグで止まったジョブをすべて示すので、止まったシナリオを合格したシナリオと取り違えることはありません。

### ドキュメント

`docs/devicefarm.md` と `docs/self-hosting.md` は、両言語で `run-set` のリクエストを説明しています。両方のページに、このフィールドと `cancelReason` の値を追記します。

## 検討した代替案

- **N 回の失敗で止める（`maxFailures`）**：回数はフラグを一般化したものです。ただ、1以外のしきい値を求める呼び出し側はまだいません。真偽値にしておいても、後から `maxFailures: 1` で置き換えられ、`failFast: true` の意味は変わりません。
- **呼び出し側がポーリングして取り消す**：ルートは現在すでにあるので、サーバーの変更は要りません。しかし呼び出し側ごとに同じループを書くことになり、ポーリングの間隔のあいだにワーカーがリースしたジョブはそのまま実行されます。
- **ハートビートを待たずに、実行中のジョブを止める**：サーバーからワーカーへは接続できません。接続を張るのはワーカーで、ワーカーへ戻る経路はハートビートしかありません。ハートビートで取り消せば、グループの既存の取り消しのルートと同じ動きになります。
