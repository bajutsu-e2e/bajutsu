## はじめに

本項目は、同一性が一致する重複アクセシビリティノードのペアを、XCUITest が実際にタップできる側 1 つ
だけに絞り込み、runner の `/elements` の返信からもう一方を取り除きます。runner の要素問い合わせの
列挙順でたまたま先だった側に、参照の割り当てを任せたままにはしません。同一性が一致する重複ノードとは、
識別子・ラベル・traits・value・frame がすべて同じ 2 つの要素を XCUITest が報告する状態で、
`UIAlertController` に典型的に現れる既知の挙動です。[`bajutsu/drivers/base.py`](../../bajutsu/drivers/base.py)
の `resolve_unique` は、この重複を 1 件の代表へすでに畳んでおり、`AmbiguousSelector` による即時失敗を
防いでいます。しかし、`resolve_unique` が呼ぶ畳み込みの関数 `_collapse_identical_duplicates` 自身の
docstring は、残る代償を「どちらの複製をタップするかは run ごとに入れ替わり、たまたま選ばれなかった
側では参照消失（stale handle）で失敗する」と述べています。本項目は、この代償を源で取り除きます。
重複ペアのうち一方だけが
[`ElementProviding.isHittable`](../../BajutsuKit/Sources/BajutsuRunner/ElementProviding.swift)
（バックエンドが「今現在覆われている」ことと本当の操作失敗を見分けるためにすでに使っている、同じ
ネイティブな XCUITest の判定）でタップ可能だと報告されたとき、runner はその一方が
[`SnapshotStore`](../../BajutsuKit/Sources/BajutsuRunner/SnapshotStore.swift)（BE-0312）の参照の割り当てへ
届く前に、もう一方を取り除きます。残る候補は 1 つだけになるので、そのあとの解決や参照の割り当てで迷う
余地がありません。`SnapshotStore` 自体は変更しません。手直しは、その入力を用意する問い合わせの段に
閉じます。

## 動機

`UIAlertController` の中のボタンへ `id` で `tap` すると、直前のステップで取った evidence のスナップ
ショットがそのボタンを画面上で動かさず映しており、セレクタが指す識別子とも一致しているにもかかわらず、
`element vanished (stale handle)` で失敗することがあります。そのスナップショットの中で、ボタン自身の
アクセシビリティノードは 2 回登録されています。識別子・ラベル・traits・value・frame がすべて一致する
2 件が、
同じ subtree の中の他のいくつかの `"other"` trait の重複ノードと並んでいます。この二重登録は、
`resolve_unique` の docstring がすでに「標準的な `UIAlertController` のボタンに対する
既知の XCUITest の重複登録」と名づけているものです。

その docstring が述べる畳み込みは、シナリオの作者には見分けられない重複ペアでセレクタが即座に
失敗するのを防ぎますが、畳み込んだあとの一致がどちらの物理ノードを指すかまでは決めません。
`resolve_unique` は、`find_all` が返す並びのうち最初の要素、つまり runner の `/elements` の返信が
列挙した順で最初のものを保持します。[`SnapshotStore.swift`](../../BajutsuKit/Sources/BajutsuRunner/SnapshotStore.swift)
の `refreshSnapshot` も、その同じ最初の出現に対して接尾辞のない参照を割り当てます。どちら側にも、
片方の物理ノードを優先する根拠はありません。並び順は、その問い合わせで XCUITest 自身のアクセシビリティ
ツリーの走査がたまたま重複ペアをどう列挙したかで決まり、`_collapse_identical_duplicates` の docstring
自身がその並びを「run ごとに入れ替わる」と不安定なものとして報告しています。`UIAlertController` の
ボタンペアは、いったん画面が落ち着いたあとに run の途中で位置を入れ替えることはありません。そのため、
1 つのステップの中で BE-0289 が試す 3 回の再解決は、そのすべてが同じ「最初に列挙された側」を導き直し、
同じ結果を繰り返します。その側が XCUITest のネイティブな tap が解決してタップ可能と判定できる側で
あれば、その重複の並びで run するかぎり毎回成功します。その側がもう一方（識別子・ラベル・traits・
value・frame の報告は完全に同じでも、XCUITest 自身のイベント合成が解決できない側）であれば、状況が
変わります。
毎回のタップの試みがネイティブに "No matches found" を発生させ、
[`Router.swift`](../../BajutsuKit/Sources/BajutsuRunner/Router.swift) の `onMainCatching` がそれを
`stale` として報告します（[`xcuitest.py`](../../bajutsu/drivers/xcuitest.py) の `_actuate` のコメントが
挙げる、`stale` を生む 2 つの経路のうち 2 つ目です）。その結果、ステップは画面から一度も出ていない
ボタンに対して `element vanished (stale handle)` で失敗します。

結果として、このシナリオは run をまたぐと不安定で、1 回の run の中では決定的になります。タップの
成否は、XCUITest 自身のツリーの走査が決める並び順に懸かっており、シナリオ側にも再解決の側にも、その
並び順を動かす手立てがありません。これは BE-0312 が名指したうえで先送りした 2 つ目の不安定さの種類
です。BE-0312 自身の「詳細設計」節は、この前提を直接認めています。同一性の一致する要素への出現番号
の割り当ては、同じ要素の問い合わせ順がスナップショットをまたいで安定していることを前提としています。
見た目の同じ要素の順がスナップショットのあいだで入れ替わる画面では、参照は振り直されることがあります。
BE-0312 は、そのような画面は
まれで、その要素は条件からも見分けられないという理由で、この隙間を塞ぐのを実際のシナリオが必要になる
まで見送っていました。通常のアプリ内ナビゲーションから到達できる `UIAlertController` の確認ダイアログ
は、まさにその実際のシナリオです。そのボタンは毎回の表示で二重に
登録され、シナリオの作者がどちらかを `tap` する動機は十分にあり、本項目が直す失敗は、その画面が一度
スイートに入れば稀な境界事例ではなくなります。直さずに残すコストは、BE-0289 と BE-0312 の両方が
測っている同じものです。必須のオンデバイスの関門がランダムに失敗すると、要素が消えていないのに関門
への信頼が損なわれ、反射的な再実行か無駄な調査のどちらかを招きます。再実行のたびに、アプリをビルドし
Simulator を起動するジョブで、macOS を動かす費用がかかります。

## 詳細設計

手直しは、runner の要素問い合わせの段に閉じます。Python 側のドライバと `SnapshotStore` のどちらにも
ない、2 つの重複それぞれへのネイティブな参照と、その特定のノードが今まさにタップ可能かを XCUITest に
問い合わせる既存の手段を、この段だけが持っているからです。

**重複グループのうち、タップできない要素を取り除く。ただし、それで残る候補が 1 つだけになるときに限る。**
[`Router.swift`](../../BajutsuKit/Sources/BajutsuRunner/Router.swift) の `handleElements` と
`handleSystemAlertQuery` は、いずれも `queryElements()` / `querySystemAlertButtons()` を
`caughtOnMain` のクロージャの中から呼んでいます。この同じメインスレッドの文脈が必要なのは、
[`ElementProviding.isHittable(backingElement:)`](../../BajutsuKit/Sources/BajutsuRunner/ElementProviding.swift)
自身がネイティブな XCUITest 呼び出しだからです。絞り込みは、その同じクロージャの中で、結果を
`elementsResponse`（`/elements` と SpringBoard の `/systemAlert/query` が共有する、BE-0316 が追加した
ハンドラ）へ渡す前に行います。`elementsResponse` 自体は変更しません。返ってきた要素を、
`_collapse_identical_duplicates` がすでに使っている同じ同一性（識別子・ラベル・traits・value・frame が
すべて一致）でグループ化します。1 件しかないグループは判定の必要がなく、余分なコストもかかりません。
2 件以上のグループでは、`/isHittable` エンドポイントがすでに「今現在覆われている」ことと本当の
操作失敗を見分けるために使っている既存の `isHittable(backingElement:)` を、メインスレッドのままで
各要素へ呼びます。この呼び出しが要素ごとに投げる例外は、要素ごとに捕まえます。`/isHittable` の
エンドポイント自身がすでに、解決に失敗したという例外を素通りさせず `stale` として扱っているのと
同じ扱いです（[`Router.swift`](../../BajutsuKit/Sources/BajutsuRunner/Router.swift) の
`onMainCatching`）。本項目が取り除こうとしている見せかけの複製は、まさにネイティブな解決が例外を
投げる側のノードです。例外を要素ごとに捕まえるのは、1 件の例外が `handleElements`（SpringBoard の
アラート経路では `handleSystemAlertQuery`）自身の `caughtOnMain([])` のフォールバックまで素通りし、
ツリー全体の代わりに空の画面を返してしまうのを防ぐためです。ちょうど 1 件だけが `.ok` を返したときは、
そのグループの他の要素をリストから取り除き、
`elementsResponse` へ届く前に消します。残った 1 件はそのグループの唯一の候補になるので、その 1 件を
複製の相手と比べて並べるタイブレークはもう要りません。どの重複グループにも属さない要素と、以下の
2 つの場合に当たるグループは元の相対順を保ちます。これは、キーでグループ化した辞書から並べ直すの
ではなく、元のリストからその場で要素を取り除く実装を前提とします（辞書の反復順序を Swift は保証し
ません）。そのため、これは問い合わせの大半の要素に何の影響も与えません。絞り込みは、
`_collapse_identical_duplicates` の 5 つの項目を鍵にした同一性で衝突するまれなグループにだけ及びます。
本項目が対象とするこの場合について言えば、`SnapshotStore` も `elementsResponse` も変更する必要が
ありません。ただ 1 つ残った候補は、`_collapse_identical_duplicates` に畳み込むべき 2 件目がそもそも
届かないまま、Python 側で一意に解決します。`find_all` を `resolve_unique` を経由せず直接使う選択子
——`forEach`、`exists`、重複そのものの同一性より広い選択子に対する `count`、`scroll` ステップの
`within` によるコンテナ解決——も、`resolve_unique` の呼び出し元と同じだけ候補が減ります。これらは
`/elements` が返したものをそのまま読むだけなので、本項目ではそれぞれを別個に導き直しません。

本項目が塞がない場合は 1 つあります。`SnapshotStore` 自身の出現番号のタイブレークは、上の 5 つの
項目とは違う、より粗い同一性を鍵にしています。識別子・ラベル・traits の 3 つだけで、value と frame
はあえて外しています（画面が落ち着きかけているときの理由づけは BE-0312 自身のものです）。5 つの
項目が一致する重複ペアは、当然この粗い 3 項目でも一致します。つまり重複ペアの 2 つの要素自身が、
すでに互いに `SnapshotStore` のハッシュで衝突しています。衝突するのに無関係な 3 つ目の要素は要りません。
これが問題になるのは、問い合わせをまたいで取り除くかどうかの判定が入れ替わる場面です。あるグループを
今日と変わらないままにする問い合わせ（下の 2 つの場合のいずれか）で、本項目がのちに取り除く側の要素に
接尾辞のない参照が割り当てられ、呼び出し側がその参照を保持したとします。次の問い合わせでその要素が
取り除かれれば、グループに残った生き残りだけが同じ粗いハッシュに 1 件だけ属することになり、同じ
接尾辞のない参照を得ます。`SnapshotStore.lookup` はその参照に対して `.stale` ではなく `.found` を
返し、生き残った要素を指してしまいます。その結果、ある物理ノードのために発行された参照が、BE-0289 の
再解決が頼る `.stale` という状態を一度も経由せずに、別の物理ノードへ黙って解決されます。取り除くかどうかは
そのたびの問い合わせで得る生きた判定結果に懸かっており、画面が落ち着きかけているあいだの `isHittable`
の結果は安定している保証がないため、これはどちらの物理ノードも実際には動いていなくても起こり得ます。
同じ粗いハッシュの衝突と出現番号の入れ替わりは、生き残った要素とこの 3 つの項目だけを共有する無関係な
3 つ目の要素（識別子を持たず、ラベルと traits だけが同じで、frame は別の場所にある操作対象など）にも
同様に及びます。本項目はどちらの場合も塞ぎません。*進捗* には、見過ごした隙間としてではなく、あえて
先送りにした既知の限界として記録します。

絞り込みが手を付けずに残すべき場合が 2 つあります。

- **グループのどの要素も `.ok` を返さない場合。** 何も取り除きません。残すべき生き残りがないまま
  絞り込むと、グループを空にしてしまうか、タップ可能でない要素をどれか 1 つ勝手に選ぶしかなく、
  どちらも判定が実際には見つけていない区別をでっち上げることになります。グループを今日と変わらない
  ままにしておけば、タップは結局失敗しますが、原因を正確に報告できる既存の経路を通ります。解決は
  できるが今まさに覆われているか画面外にあるノードなら `.notHittable`（現状の `ElementNotTappable`）
  です。XCUITest が一切操作できないノードなら本物のネイティブな解決失敗であり、現状は `stale` として
  現れます（根本の状態が解消すれば BE-0289 の再解決がなお正当に吸収できます）。本項目も
  `SnapshotStore` も、どちらの結果の意味も変えません。
- **複数の要素が `.ok` を返す場合。** `UIAlertController` の二重登録（どちらか一方しか実際には操作
  できない場合）ではなく、同一性が一致する、独立にタップ可能な、正真正銘別々の 2 つの操作対象が存在
  することを意味します。この判定だけを根拠にどちらか一方を取り除くと、「たまたま重複した見せかけの
  要素」と「見た目は同じだが実際に独立してタップできる 2 つの対象」とを区別できないまま、シナリオが
  `index` で狙う必要のある対象を静かに消してしまうことになります。この場合もグループを今日と変わらない
  ままにしておきます。どちらが先頭に来て接尾辞のない参照を得るかは、今までと同じく問い合わせの順序が
  決め、今までと同じく問い合わせごとに変わることがあります。これほど曖昧な選択が起こるセレクタは、
  見分けのつかない独立した対象を実際に描いているアプリの、意図された挙動として読むべきです。その
  不安定さは、本項目が引き起こす後退でも、本項目が塞ぐつもりの隙間でもなく、そのようなセレクタにもと
  から備わっている性質です。

**コスト。** 追加するネイティブな呼び出しは、すでに内容で衝突している要素にしか走りません。
`_collapse_identical_duplicates` の docstring 自身が、これをよくある場合とはせず、既知でまれな
XCUITest の挙動として位置づけています。重複グループのない通常の問い合わせは、追加のコストを一切
払いません。呼び出し自体は `/isHittable` が今日すでにメインスレッドで行っているものと同じであり、
`handleElements` と `handleSystemAlertQuery` が `queryElements()` / `querySystemAlertButtons()` の
ために開いている同じ `caughtOnMain` のクロージャの中から呼ぶので、新しいスレッドの切り替えは
増えません。

**テスト。** グループ化と、取り除くか残すかの判定そのものは runner のロジックであり、ネイティブな
挙動ではないので、実機なしで覆えます。ただし BE-0312 の Unit 3 と違って `SnapshotStoreTests.swift`
の中ではなく（`SnapshotStore` 自体には触れていません）、`GET /elements` と `POST /systemAlert/query`
の両方を `FakeElementProvider` に対して一通り動かす `RouterTests.swift` の中で覆います。この fake の
`isHittableResult` は、今はすべての呼び出しが共有する単一の `TapResult` です。これを、fake の
`backingElement` の `ObjectIdentifier` で（要素の内容ではなく）キーとする小さな辞書に変えれば、次の
3 つを決定的に固定できます（内容でキーにすると、下のテストで使う 2 つの fake 要素は同一性が一致する
という前提そのものにより同じキーへ潰れてしまい、別々の `isHittable` 結果を持たせられません）。同一性
が一致する fake の要素を 2 つ用意して `isHittable` の結果を互い違いにすれば、返信はタップできる側
だけを残すこと。両方が `.ok` を返す場合は両方とも変えずに残すこと。両方が `.ok` 以外を返す場合も両方とも
変えずに残すこと。上で述べた例外を要素ごとに捕まえる要件を固定するには、別にもう 1 つ、
`backingElement` ごとに例外を注入できる仕組みが必要です。`isHittable` には今日そのような仕組みが
なく（`tap`/`queryElements` は `tapRaises`/`queryRaises` で持っています）、`TapResult` 自体にも
「例外を投げる」を戻り値として表すケースがありません。その仕組みがあれば、片方の fake の要素が例外を
投げ、もう片方が `.ok` を返すときに、投げた側だけが取り除かれることを確かめられます。オンデバイスの
テストは、実機でしか確かめられないことに絞ります（`Router.swift` / `ElementProviding.swift` には、
まだ実機／実機なしを分けた前例がないので、これが最初の例になります）。実際に片方だけが覆われた
`UIAlertController` の二重登録が、ちょうど片方だけタップ可能として再現すること、`id` への `tap` が
その側に着弾すること、そしてその識別子に対する `count` の判定が、あとで 2 件ではなく 1 件になること
です。本項目が防ごうとしている回帰は誤った複製へのタップですが、`count` の判定は、生き残った要素が
単に並べ替えられただけではなく本当に唯一の候補になっていることまで確かめます。

## 検討した代替案

**取り除くのではなく、並べ替えるだけにする。** 本項目の前の版は、タップできる側をグループの先頭へ
移すだけで、両方をツリーに残していました。BE-0312 が今持っている出現番号のタイブレークの形を変えず、
その上に乗る設計です。並べ替えは、*動機* が説明する失敗そのものを直します。先頭の要素はつねに接尾辞
のない参照を得るからです。しかし、それが効くのは片方だけがタップ可能な場合だけです。両方タップ可能
なときは、並べ替えるだけの設計でもどちらを先頭にするかを問い合わせ順に頼るしかなく、今日と同じだけ
非決定的な場合として残ります。片方だけがタップ可能な場合、タップできない側を取り除けば、その複製と
並べて生き残りを置く必要そのものがなくなります。並べ替える対象となる、同一性が一致する 2 件目は、
もともと存在しないからです。
並べ替えだけの設計は、タップ不能な複製を、接尾辞つきの参照を持つ要素としてツリーへ残し続けることに
なり、`count` や `index` はそれを見続けます。取り除けば、`count` はシナリオが実際に操作できる対象の
数を報告するようになります。これは、最初から本物の 2 つ目の操作対象ではなかった挙動について、
「ここに何個のボタンがあるか」をより正しく言い当てているはずです。この代償は、*詳細設計* が名指す
とおりのものです。取り除く設計は、その同一性について `/elements` が報告する内容を変えますが、並べ
替えるだけの設計なら報告される形をそのまま保っていました。

**タイブレークを `SnapshotStore` 自体で直す。** `SnapshotStore.refreshSnapshot` が受け取るのは
`ElementSnapshot` の値だけで、それぞれすでに同一性・value・frame・不透明な `backingElement` 参照へ
切り詰められています。この型は、実際にタップできるかどうかというネイティブな判定結果を運ぶ場を
持ちません。その結果を求めるには、本項目がすでに提案している同じネイティブな、メインスレッドの
`isHittable` 呼び出しが要ります。絞り込みを `SnapshotStore` の内部へ移すと、BE-0312 があえて機器に
依存させず実機なしでテスト可能に保っていたクラスへ、ネイティブな XCUITest 呼び出しを直接持ち込む
ことになります。リストが store に届く 1 段手前で絞り込むほうが、どちらの点でも優れています。

**Python 側、`resolve_unique` や `_collapse_identical_duplicates` で直す。** Python 側のドライバは、
2 つの重複が Python が比較する前にすでに 1 件の論理的な一致へ畳み込まれているため、1 件を超える
内容を受け取ることが一切ありません。また、ネイティブな参照をまったく持たない側から、重複グループ
ごとに、しかも問い合わせごとに 1 回の追加往復なしに「どちらがタップ可能か」を runner へ尋ねる経路も
ありません。runner がタップ可能な側を告げたあとで Python 側が候補を 1 つ捨てても、もう一方の複製の
参照は runner 側では生きたまま `index` で届くところに残ってしまいます。取り除くこと自体は、要素が
実際に消える場所、つまり返信を組み立てる runner で行う必要があり、runner が送ったものしか見えない
側では足りません。この理由づけは、参照を保つネイティブな runner のプロセスを持つバックエンドに
固有のものです。`resolve_unique` と `_collapse_identical_duplicates` はすべてのバックエンドが共有
しますが、そのようなプロセスを持たないバックエンド（adb、Playwright、WebView のブリッジ、Appium
経由の live route）には、この手直しを移せる runner の層自体がなく、同じ理由づけはそちらでは通り
ません。

**再解決の回数を増やす、あるいはドライバの外側でスクロールや再表示による回復を足す。** BE-0289 の
再解決は、`stale` の返事に対してすでに再解決し、再操作しています。*動機* が示すとおり、これはこの
失敗を回復できません。重複の並びは 1 回の run の中で安定しているため、どの試行も同じ複製を導き直し、
同じ結果を繰り返すだけだからです。再解決の回数を増やしても、変わらない結果を再現する時間が増える
だけです。ドライバの外側でスクロールや、閉じてから開き直す回復を足すのも、`UIAlertController` 自身の
レイアウトを壊れているものとして扱うことになりますが、ダイアログの側は最初から問題ではありません。

**重複グループだけでなく、すべての要素で `isHittable` を計算する。** すべての要素について、タップ
できるかどうかをあらかじめ判定しておけば、重複の場合を特別扱いしなくて済みます。ただし、代償として、`/elements` と
`/systemAlert/query` のすべての返信で、要素 1 件につき 1 回のネイティブな呼び出しが必要になります。
その大半は重複の衝突に一度も関わりません。内容で衝突している要素だけに絞ることで、追加のコストは、
本項目が対象とする挙動が実際に起きる頻度と釣り合うものにとどまります。
