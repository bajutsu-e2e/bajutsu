## はじめに

[`scripts/e2e_changes.py`](../../scripts/e2e_changes.py) は、あるプルリクエストが3つの実機
エンドツーエンド（E2E）レーンを走らせるかどうかをレーンごとに決めます。3つのレーンとは、Simulator 上の
iOS と、エミュレータ上の Android と、実ブラウザ上の web です。各レーンは必須のステータスチェックを
持ちますが、トリガの `paths:` フィルタではゲートできません。`paths:` フィルタで飛ばされた必須チェックは
保留のまま残り、マージを永久に止めてしまうからです。そこで各レーンは全プルリクエストで起動します。
課金の対象となるジョブを実際に走らせるかどうかは、人手で書いたパスの許可リストであるこのフィルタが
決めます。許可リストが言及していないパスは、1つのジョブも発火させません。そして常に結果を報告する集約
チェックは、**変更を1度も動かさないまま**合格します。

「ゲート対象外」という既定値は、すでに3件の別々の見落としを生み、いずれも個別に見つけて直してきました。
本項目は、このクラスを構造的に終わらせることを提案します。提案は2つの部分から成ります。1つは、
**`bajutsu/` の既定値を反転させ、認識できないファイルが1つもレーンを発火させないのではなく全レーンを
発火させるようにする**ことです。もう1つは、周辺コードとして分類したファイルが黙って run 経路に入って
いないかを静的に相互検査することです。分類を誰も決めていないファイルは、`make check` を落とします。
従来は「ゲート対象外」に既定で倒れ、数か月後に「なぜか緑の必須チェック」として現れていました。

## 動機

許可リストは、コードがすでに知っている事実を人手で複製したものです。その事実とは、run 経路がどのファイルを
import するかです。複製はドリフトします。既定値が「ゲート対象外」の側に倒れているため、ドリフトは静かに
起きます。

記録に残っている見落としは3件で、失敗のしかたは2種類に分かれます。

| 見落とし | 原因 | 気付かれなかった期間 |
|---|---|---|
| `bajutsu/config` | BE-0252 がパッケージへ分割したため、`\.py$` でアンカーした名前指定の項目が一致しなくなった | 約2週間 |
| `bajutsu/platform_lifecycle` | 同じパッケージ分割 | PR [#1403](https://github.com/bajutsu-e2e/bajutsu/pull/1403) が XCUITest のコールド起動を変更し、macOS のレーン全体が飛ばされるまで |
| BE-0304 の doctor ゲート | 3レーンとも `bajutsu doctor --environment-only` を走らせるのに、`bajutsu/doctor.py` と `cli/commands/doctor.py` と `preflight.py` が最初から未登録だった | ゲートが着地して以来ずっと |

上記の修正とともに入れたガードは、3つの狭いクラスを塞ぎます。

- 名前指定のモジュールがパッケージになる場合
- パスがリネームまたは削除される場合
- バックエンドごとの2つのディレクトリ（`bajutsu/drivers/` と `bajutsu/platform_lifecycle/environments/`）
  にファイルが増える場合

残るクラスは2つあります。1つめは、run 経路上に**新しく**足したトップレベルの `bajutsu/*.py` モジュールや
コマンドラインインタフェース（CLI）のコマンドです。このクラスは依然として既定で1つも発火させません。
2つめは、すでに閉包の中にありながら発火しないファイル群です。run 経路の import 閉包を実測すると、現在
1つもレーンを発火させないファイルが54件あります。`runner/pipeline.py` を通じて毎回の run が書き出す
`bajutsu/report/` は、54件の1つです。ほかに `deprecations.py`、`object_store.py`、`record_capture.py`、
`requirements.py`、`trace.py` が含まれます。

真っ先に思いつく修正は、許可リストを import 閉包から自動導出する案です。しかし成り立ちません。否定する
根拠は実測にあります。run 経路の閉包は `bajutsu/ai/`、`bajutsu/analytics/`、`bajutsu/github/` へ
届きます。`record.py` がエージェント工場を import するためです。さらに `runner/pipeline.py` がレポート
書き出しを import し、レポート書き出しが analytics の台帳を import します。素の閉包でゲートすると、配信する
web ユーザインタフェースだけに閉じた変更で3つの課金レーンすべてが発火します。PR
[#936](https://github.com/bajutsu-e2e/bajutsu/pull/936) が直した過剰発火そのものです。import の辺は、
あるモジュールが別のモジュールへ到達しうることを記録するだけで、そのモジュールの振る舞いが run の結果を
変えうることは記録しません。そして、その線を引けるのは人だけです。したがって本項目は、人の判断を保った
まま、決定していないファイルがどちらへ倒れるかを変えます。

## 詳細設計

4つのユニットに分け、それぞれ単独で着地できるようにします。

### ユニット1：`bajutsu/` の既定値を反転する

共有のコアで `bajutsu/` を一括して拾い、E2E が1度も動かさない周辺の接頭辞だけを明示的に除外します。
除外の対象は6つです。配信する web ユーザインタフェースとそのテンプレート、analytics と analysis の
スタック、Model Context Protocol（MCP）サーバ、AI プロバイダのアダプタ、GitHub 連携、そして run が
import しない crawl と agents のモジュールです。PR
[#1409](https://github.com/bajutsu-e2e/bajutsu/pull/1409) がバックエンドごとの2つのディレクトリに
適用した形を、ユニット1はパッケージのルートまで広げます。

効いてくる性質は、既定値の向きです。除外リストに接頭辞を書くことは、**既知の**ファイルを絞るだけで、
**新しい**ファイルが見られるかどうかを決めません。`bajutsu/` の下のどこかにモジュールを足すと、誰かが
分類するまで3レーンすべてが発火します。忘れたときの代償は、動かされない必須チェックではなく無駄な
ジョブになります。

除外リストのキーの取り方には注意が必要です。`bajutsu/serve/` のような接頭辞は、まるごと除外しても
安全です。web レーンが serve UI のドッグフードのために `bajutsu/serve/` を別途名指ししているからです。
混在したパッケージは、まるごと除外できません。`bajutsu/report/` は、毎回の run が呼ぶ manifest の書き出しと、
どのレーンも必要としないレポート描画を同居させています。したがって `bajutsu/report/` は、ファイル単位で
除外するか、まったく除外しないかのどちらかになります。

### ユニット2：run 経路の import 閉包に対する静的な相互検査

ユニット1は新しいファイルを過剰発火させますが、逆向きの誤りは捕まえられません。逆向きの誤りとは、除外
リストに載っているモジュールを run 経路が**新たに** import し始める場合です。そこで、import 閉包を
`ast` で静的に歩くテストを足します。閉包の中にフィルタも除外項目も拾わないファイルがあれば、このテストは
落ちます。

この歩行は import ではなく構文解析でなければなりません。`changes` ジョブは依存を1つも入れていない素の
`python3` で走り、テストは Simulator 不要の高速な `make check` ゲートの中に置くべきだからです。import
グラフの静的解析は、`lint-imports` がレイヤ契約に対してすでに使っている手法です。ユニット2は新しい
種類のツールを持ち込まず、判定の近くに大規模言語モデルを置くこともありません。

### ユニット3：場当たり的な parity テストの退役

現在、1回限りの除外判断を散文で記録しているテストが2つあります。1つは
`test_agent_factory_is_not_relevant_by_parity` です。もう1つは、`bajutsu/report/` を「関連なし」として
固定している `test_untouched_subpackage_is_not_relevant` です。2つのテストをどちらもユニット1の除外
リストの項目として、それぞれの理由を添えて書き直します。そうすれば、意図的な除外はすべて1か所に集まり、
過去についての assertion ではなく決定として読めるようになります。

### ユニット4：新しい既定値の代償の計測

既定値の反転は、動かされない必須チェックを無駄な課金ジョブと引き換えにします。この取引が成り立つのは、
無駄が小さいあいだだけです。直近の期間にマージされたプルリクエストを標本として、新しいフィルタが発火
させるレーンと、古いフィルタが発火させていたレーンを分類し、差を報告します。ある周辺の接頭辞の変更頻度が
問題になるほど高ければ、その接頭辞の除外をより細かくキーする合図になります。

## 検討した代替案

- **許可リストを import 閉包から自動導出する。** 原理ではなく実測にもとづいて却下します。閉包は AI と
  analytics と GitHub のスタックに届くので、それでゲートすると PR #936 が直した過剰発火が復活します。
  読者が最初に思いつく案なので、ここに記録します。
- **閉包を CI 実行時に `e2e_changes.py` の中で計算する。** 却下します。`changes` ジョブは意図的に依存
  なしの素の `python3` で走ります。モジュール自身のシナリオ走査が、設定ファイルの構文解析ではなく行単位の
  走査になっているのも同じ理由です。そのうえ、分類をレビューの外へ移すと、ユニット1が保つ人の判断を捨てて
  しまいます。
- **許可リストを保ったままレビューに頼る。** 現状がこれであり、約6週間で3件の見落としが出たことが反証に
  なります。3件はいずれもレビューではなく偶然に見つかりました。2件は無関係な飛ばされたレーンの調査中に、
  1件は先の2件の監査中にです。
- **必須チェックを広げて全レーンを無条件に走らせる。** クラスをまるごと消せますが、フィルタが存在する
  理由である節約を手放します。ドキュメントだけのプルリクエストでも Simulator とエミュレータを起動して
  しまうので、釣り合わないものとして却下します。

ログ（古い順）:

- 4つのユニットを実装 PR でまとめて出荷します。
  - ユニット1：`scripts/e2e_changes.py` は `bajutsu/` を一括で拾い、導出した2つの除外集合だけを差し引きます。
    `_PERIPHERY_EXCLUSIONS` は、どのレーンも実行しない周辺を持ち、各項目が除外の理由を持ちます。
    `_LANE_CLAIMED` は、各レーンが再主張する backend 固有のリーフを持ちます。未分類のファイルは「何も
    発火しない」のではなく、全レーンを過剰発火させます。毎 run が書き込むマニフェスト書き出し
    `bajutsu/report/` と、これまで未掲載だった `deprecations`、`object_store`、`record_capture`、
    `from_grouping` も発火するようになりました。
  - ユニット2：`tests/test_e2e_changes.py` は run パスの静的な `ast` import 閉包を辿ります。到達した
    ファイルがゲート対象でも分類済み周辺項目でもなければ、テストは落ちます。
  - ユニット3：従来の場当たり parity アサーション2つは、`_PERIPHERY_EXCLUSIONS` の理由つき項目へ置き換えました。2つとは `test_agent_factory_is_not_relevant_by_parity` と `test_untouched_subpackage_is_not_relevant` です。
    この置き換えが包摂する「名前ベースのパッケージ分割」ガードは撤去しました。
  - ユニット4：`scripts/e2e_overfire_report.py` は基準コミットに対して過剰発火のトレードオフを計測します。
    直近80件のマージ済みプルリクエストでは、新しい既定は3レーンすべてで旧来と**完全に同一**に発火しました。
    過剰発火は0、過小発火も0です。新たにゲート対象になったファイルが、すでに他の run パスコードで発火して
    いる PR の外で単独に現れなかったためです。受け入れたコストは、将来の report 単独または object-store
    単独の変更では実在しますが、直近の履歴では無視できる水準です。
