## はじめに

[`scripts/e2e_changes.py`](../../scripts/e2e_changes.py) は、あるプルリクエストが3つの実機
エンドツーエンド（E2E）レーンを走らせるかどうかをレーンごとに決めます。3つのレーンとは、Simulator 上の
iOS と、エミュレータ上の Android と、実ブラウザ上の web です。各レーンは必須のステータスチェックを
持ちますが、トリガの `paths:` フィルタではゲートできません。そうして飛ばされた必須チェックは保留のまま
残り、マージを永久に止めてしまうからです。そこで各レーンは全プルリクエストで起動します。代わりにこの
フィルタ、すなわち人手で書いたパスの許可リストが、課金の対象となるジョブを実際に走らせるかどうかを
決めます。許可リストが言及していないパスは1つのジョブも発火させません。そして常に結果を報告する集約
チェックは、**変更を1度も動かさないまま**合格します。

この既定値は、すでに3件の別々の見落としを生み、いずれも個別に見つけて直してきました。本項目は、この
クラスを構造的に終わらせることを提案します。提案は2つの部分から成ります。1つは、**`bajutsu/` の既定値を
反転させ、認識できないファイルが1つもレーンを発火させないのではなく全レーンを発火させるようにする**ことです。
もう1つは、周辺コードとして分類したファイルが黙って run 経路に入っていないかを静的に相互検査すること
です。分類を誰も決めていないファイルは、「ゲート対象外」に既定で倒れて数か月後に「なぜか緑の必須チェック」
として現れる代わりに、`make check` を落とします。

## 動機

許可リストは、コードがすでに知っている事実を人手で複製したものです。その事実とは、run 経路がどのファイルを
import するかです。複製はドリフトします。そして既定値が「ゲート対象外」の側に倒れているため、ドリフトは
静かに起きます。

記録に残っている見落としは3件で、失敗のしかたは2種類に分かれます。

| 見落とし | 原因 | 気付かれなかった期間 |
|---|---|---|
| `bajutsu/config` | BE-0252 がパッケージへ分割したため、`\.py$` でアンカーした名前指定の項目が一致しなくなった | 約2週間 |
| `bajutsu/platform_lifecycle` | 同じパッケージ分割 | PR [#1403](https://github.com/bajutsu-e2e/bajutsu/pull/1403) が XCUITest のコールド起動を変更し、macOS のレーン全体が飛ばされるまで |
| BE-0304 の doctor ゲート | 3レーンとも `bajutsu doctor --environment-only` を走らせるのに、`bajutsu/doctor.py` と `cli/commands/doctor.py` と `preflight.py` が最初から未登録だった | ゲートが着地して以来ずっと |

上記の修正とともに入れたガードは、3つの狭いクラスを塞ぎます。名前指定のモジュールがパッケージになる
場合、パスがリネームまたは削除される場合、そしてバックエンドごとの2つのディレクトリ
（`bajutsu/drivers/` と `bajutsu/platform_lifecycle/environments/`）にファイルが増える場合です。
残るクラスは2つあります。1つめは、run 経路上に**新しく**足したトップレベルの `bajutsu/*.py` モジュールや
コマンドラインインタフェース（CLI）のコマンドで、依然として既定で1つも発火させません。2つめは、すでに
閉包の中にありながら発火しないファイル群です。run 経路の import 閉包を実測すると、現在1つもレーンを
発火させないファイルが54件あります。`runner/pipeline.py` を通じて毎回の run が書き出す
`bajutsu/report/` は、その1つです。ほかに `deprecations.py`、`object_store.py`、`record_capture.py`、
`requirements.py`、`trace.py` が含まれます。

真っ先に思いつく修正は、許可リストを import 閉包から自動導出する案です。しかし成り立ちません。否定する
根拠は実測にあります。run 経路の閉包は `bajutsu/ai/`、`bajutsu/analytics/`、`bajutsu/github/` へ
届きます。`record.py` がエージェント工場を import するためです。さらに `runner/pipeline.py` が
レポート書き出しを import し、そのレポート書き出しが analytics の台帳を import します。素の閉包で
ゲートすると、
配信する web ユーザインタフェースだけに閉じた変更で3つの課金レーンすべてが発火します。PR
[#936](https://github.com/bajutsu-e2e/bajutsu/pull/936) が直した過剰発火そのものです。import の辺は、
あるモジュールが別のモジュールへ到達しうることを記録するだけで、その振る舞いが run の結果を変えうることは
記録しません。そして、その線を引けるのは人だけです。したがって本項目は、人の判断を保ったまま、決定して
いないファイルがどちらへ倒れるかを変えます。

## 詳細設計

4つのユニットに分け、それぞれ単独で着地できるようにします。

### ユニット1 — `bajutsu/` の既定値を反転する

共有のコアで `bajutsu/` を一括して拾い、E2E が1度も動かさない周辺の接頭辞だけを明示的に除外します。
除外の対象は6つです。配信する web ユーザインタフェースとそのテンプレート、analytics と analysis の
スタック、Model Context Protocol（MCP）サーバ、AI プロバイダのアダプタ、GitHub 連携、そして run が
import しない crawl と agents のモジュールです。PR
[#1409](https://github.com/bajutsu-e2e/bajutsu/pull/1409) がバックエンドごとの2つのディレクトリに
適用した形を、ユニット1はパッケージのルートまで広げます。

効いてくる性質は、既定値の向きです。除外リストに接頭辞を書くことは、**既知の**ファイルを絞るだけで、
**新しい**ファイルが見られるかどうかを決めません。`bajutsu/` の下のどこかにモジュールを足すと、誰かが
分類するまで3レーンすべてが発火します。したがって、忘れたときの代償は、動かされない必須チェックではなく
無駄なジョブになります。

除外リストのキーの取り方には注意が必要です。`bajutsu/serve/` のような接頭辞は、まるごと除外しても
安全です。web レーンが serve UI のドッグフードのために別途名指ししているからです。混在したパッケージは
そうはいきません。`bajutsu/report/` は、毎回の run が呼ぶ manifest の書き出しと、どのレーンも必要と
しないレポート描画を同居させています。したがってファイル単位で除外するか、まったく除外しないかの
どちらかになります。

### ユニット2 — run 経路の import 閉包に対する静的な相互検査

ユニット1は新しいファイルを過剰発火させますが、逆向きの誤りは捕まえられません。逆向きの誤りとは、除外
リストに載っているモジュールを run 経路が**新たに** import し始める場合です。そこで、import 閉包を
`ast` で静的に歩き、閉包の中にフィルタも除外項目も拾わないファイルがあれば落ちるテストを足します。

この歩行は import ではなく構文解析でなければなりません。`changes` ジョブは依存を1つも入れていない素の
`python3` で走り、テストは Simulator 不要の高速な `make check` ゲートの中に置くべきだからです。import
グラフの静的解析は、`lint-imports` がレイヤ契約に対してすでに使っている手法です。したがってユニット2は
新しい種類のツールを持ち込まず、判定の近くに大規模言語モデルを置くこともありません。

### ユニット3 — 本項目が吸収する場当たり的な parity テストを退役させる

現在、1回限りの除外判断を散文で記録しているテストが2つあります。1つは
`test_agent_factory_is_not_relevant_by_parity` です。もう1つは、`bajutsu/report/` を「関連なし」として
固定している `test_untouched_subpackage_is_not_relevant` です。どちらもユニット1の除外リストの項目として、
それぞれの理由を添えて書き直します。そうすれば、意図的な除外はすべて1か所に集まります。そして、過去に
ついての assertion ではなく決定として読めるようになります。

### ユニット4 — 新しい既定値の代償を測る

既定値の反転は、動かされない必須チェックを無駄な課金ジョブと引き換えにします。この取引が成り立つのは、
無駄が小さいあいだだけです。直近の期間にマージされたプルリクエストを標本として、新しいフィルタが発火
させるレーンと、古いフィルタが発火させていたレーンを分類し、差を報告します。ある周辺の接頭辞の変更頻度が
問題になるほど高ければ、それがその除外をより細かくキーする合図になります。

## 検討した代替案

- **許可リストを import 閉包から自動導出する。** 原理ではなく実測にもとづいて却下します。閉包は AI と
  analytics と GitHub のスタックに届くので、それでゲートすると PR #936 が直した過剰発火が復活します。
  読者が最初に思いつく案なので、ここに記録します。
- **閉包を CI 実行時に `e2e_changes.py` の中で計算する。** 却下します。`changes` ジョブは意図的に依存
  なしの素の `python3` で走ります。モジュール自身のシナリオ走査が、設定ファイルの構文解析ではなく行単位の
  走査になっているのも同じ理由です。そのうえ、分類をレビューの外へ移すと、ユニット1が保つ人の判断を捨てて
  しまいます。
- **許可リストを保ったままレビューに頼る。** 現状がこれであり、約6週間で3件の見落としが出たことが反証に
  なります。3件はいずれもレビューではなく偶然に見つかりました。2件は無関係な飛ばされたレーンの調査中に、
  1件は先の2件の監査中にです。
- **必須チェックを広げて全レーンを無条件に走らせる。** クラスをまるごと消せますが、フィルタが存在する
  理由である節約を手放します。ドキュメントだけのプルリクエストでも Simulator とエミュレータを起動して
  しまうので、釣り合わないものとして却下します。
