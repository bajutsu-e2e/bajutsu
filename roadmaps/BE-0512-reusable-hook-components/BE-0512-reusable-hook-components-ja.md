## はじめに

本項目は**フックコンポーネント**を追加します。準備と後片付けを1つにまとめたファイルです。
引数を受け取り、複数の場所から適用できます。

書ける内容は次の2種類です。

- 実行全体やシナリオの前後で実行する外部コマンド
- `setup` と `cleanup` の各フェーズで実行するステップ

ターゲットは `targets.<name>.hooks.use` で適用します。シナリオは自身の `hooks.use` で適用します。
Bajutsu はファイルの読み込み時にコンポーネントを展開します。
実行ループが受け取るコマンドとステップは、これまでと同じ形です。シナリオごとにタグで絞ります。
展開はモデルを呼ばず、待機も追加しません。合否を決めるアサーションは変わりません。

## 動機

Bajutsu の
[フック](../../docs/ja/configuration.md#run-とシナリオの前後で実行する外部コマンドhooksbe-0491)には2種類あります。
ステップのリストである `setup` と `cleanup` には、シナリオのステップを書きます。
このステップからは、`use` で[コンポーネント](../../docs/ja/scenarios.md#コンポーネントuse--再利用ステップ)を呼び出せます。

コマンドのリストには外部コマンドを書きます。
対象は `beforeRun`、`beforeScenario`、`afterScenario`、`afterRun` の4つです。
コマンドのエントリを再利用する仕組みはありません。

ターゲットのテンプレート（`extends`）は、ターゲット定義の一部を共有できます。
ただし、テンプレートは引数を取りません。後の層のリストは、前の層のリストを置き換えます。
シナリオからは使えません。

作成済みのユーザーを必要とするシナリオが、いくつもあるスイートを考えます。
準備は次の4か所に分かれます。

- ユーザーを作る `beforeScenario` コマンド
- サインインする `setup` ステップ
- サインアウトする `cleanup` ステップ
- ユーザーを削除する `afterScenario` コマンド

その結果、次の困りごとが生じます。

| 困りごと | 起こること |
|---|---|
| 前後の対が崩れる | 作成と削除のコマンドは別々のリストにあります。Bajutsu は両者を関連づけないので、`when` を2回書きます。片方だけを直してしまう可能性があります |
| 同じ内容を複写する | ユーザーを必要とする場所は、4か所をそのつど書きます。スクリプトの引数が変われば、すべての複写を直します |
| 少しの違いでも複写する | free と premium のユーザーは、値が1つ違うだけです。それでも一式をもう1組書きます |

本項目の実装後は、スイートのファイルで効果を確かめられます。
ユーザーの準備と後片付けは、1つのファイルに収まります。
必要な箇所に残るのは、ファイル名と値を指定する `use` の1項目です。

## 詳細設計

### 1. コンポーネントのファイル

フックコンポーネントは、1つのマッピングです。
各項目は省略できます。ただし、6つのリストのうち1つには中身が必要です。

| 項目 | 内容 |
|---|---|
| `params` | 呼び出し側が与える名前。`${params.<name>}` で参照する |
| `beforeRun`、`afterRun` | ターゲットのエントリと同じ項目を持つコマンド |
| `beforeScenario`、`afterScenario` | 同じ形のコマンド |
| `setup` | シナリオの `setup` と同じステップ |
| `cleanup` | シナリオの `cleanup` と同じルール |

```yaml
# hooks/seeded-user.hook.yaml
params: [plan]
beforeScenario:
  - name: user
    cmd: "./create-user.sh ${params.plan}"   # userId=... を $BAJUTSU_OUTPUT に書く
setup:
  - type: { text: "${hooks.user.userId}", into: { id: login.username } }
  - tap: { id: login.submit }
cleanup:
  - on: always
    steps:
      - tap: { id: session.logout }
afterScenario:
  - cmd: "./delete-user.sh"                  # $BAJUTSU_HOOK__user__userId を読む
```

ファイル内のステップは、`use` でステップのコンポーネントを呼び出せます。
別のフックコンポーネントは適用できません。`interrupts` と `sandbox` も書けません。
ターゲットの `setup` に今ある制限は、同じように適用します。`group` と `setMocks` は使えません。

引数は読み込み時に代入します。対象は `cmd`、`env` の値、ステップです。
`cmd` では、行を引数に分割してから、引数ごとに代入します。
空白や引用符を含む値は、その引数の中に収まります。
コマンドの実行方針は、代入後の行を確認します。
引数の不足や未知の引数があれば、読み込みを止めます。
代入されずに残った `${params.*}` も同様です。

相対 `cwd` は、コンポーネントファイルのディレクトリを基準にします。
`cwd` のないエントリも、同じディレクトリで実行します。
コンポーネントとスクリプトは、まとめて移動できます。

ファイルはステップのコンポーネントと同じく、スイートのルート内に置きます。
シナリオディレクトリの直下には置きません。
直下の `.yaml` ファイルは、Bajutsu がシナリオファイルとして読み込みます。

サンドボックス内のコマンドから見えるのは、config のディレクトリだけです。
サンドボックスを使う方針で、コンポーネントがその外にある場合は、デバイス操作の前に止めます。

### 2. 適用のしかた

ターゲットの `hooks` とシナリオの `hooks` の両方に、`use` リストを追加します。

```yaml
targets:
  web:
    hooks:
      use:
        - hook: ./hooks/seeded-user.hook.yaml
          with: { plan: free }
```

```yaml
- name: upgrade offer
  hooks:
    use:
      - hook: ../hooks/seeded-user.hook.yaml
        with: { plan: premium }
        as: premium
        when: { tags: [payments] }
```

| 項目 | 意味 |
|---|---|
| `hook` | コンポーネントファイル。この項目を書いたファイルからの相対パス |
| `with` | 引数の値 |
| `as` | 2回の適用を区別するための別名 |
| `when` | 適用全体のタグ条件。`tags` と `exclude` を持つ |

`beforeRun` や `afterRun` を持つコンポーネントは、シナリオから適用できません。
シナリオは実行全体ではないからです。読み込みは止まり、該当する項目名を示します。

ターゲットのテンプレートにも `hooks.use` を書けます。
テンプレートファイル内のパスは、ほかのパスと同様にそのファイルを基準にします。
`defaults`、テンプレート、ターゲットの `use` は、層の順に連結します。
解決後の `hook` のパスと `as` が一致する項目は、後の層が置き換えます。
他のリストは連結せず、置き換えます。
`use` を連結するのは、置き換えると共通のコンポーネントが気づかないまま消えるためです。
`null` はリスト全体を消します。

### 3. 名前と別名

現在、コマンド名は実行が操作する全ターゲットで一意にします。
直接書いたエントリは、この規則のままです。
コンポーネント由来の名前は、ターゲットごとの範囲で扱います。
テンプレートを通じて2つのターゲットが共有しても、衝突しません。

| 名前の種類 | 重複できない相手 |
|---|---|
| ターゲットに直接書いたエントリ | 現在と同じく、実行内のほかのすべての名前 |
| シナリオに直接書いたエントリ | 現在と同じく、シナリオから見えるすべての名前 |
| ターゲットが適用したコンポーネント由来 | 同じターゲットのほかの名前と、すべての直接の名前 |
| シナリオが適用したコンポーネント由来 | シナリオから見えるすべての名前 |

トークンは、読み取るステップやアサーションのターゲットで解決します。
例として、web と iOS の2つのターゲットが、同じユーザー作成のコンポーネントを適用するとします。
web のステップの `${hooks.user.userId}` は、web の値になります。
iOS のステップでは、同じトークンが iOS の値になります。
`target` のないステップは、複数ターゲットシナリオの現在の規則に従います。

ステップは、ほかのターゲットのコンポーネント由来の名前を読めません。
該当するトークンがあれば読み込みを止め、名前を持つターゲットを示します。
コマンドの範囲も同じです。
ターゲットのコマンドが受け取るのは、そのターゲットのコンポーネントの出力です。
実行単位の出力も、同じようにターゲットごとに保持します。

シナリオのコマンドから見て、操作する2つのターゲットが同じ名前を持つ場合があります。
この場合は読み込みを止め、2つのターゲット名を示します。
一方の適用に `as` を指定すると解消できます。
コマンドが何を読むかに関係なく、自身のコマンドを持つシナリオを確認します。
Bajutsu がどちらかの値を選ぶことや、黙って変数を省くことはありません。

#### `as` が必要になる状況

2つのものが同じ名前で呼ばれてしまう場合に、`as` が必要です。

| 状況 | `as` を書く場所 |
|---|---|
| 1つのターゲットまたはシナリオが、同じコンポーネントを2回適用する | 2つの項目の一方 |
| ターゲットが適用したコンポーネントを、そのターゲットを操作するシナリオも適用する | どちらか一方 |
| 同じ範囲の2つの適用が、同じコマンド名を宣言する | 2つの項目の一方 |
| コンポーネントが、直接のエントリで使用済みの名前を宣言する | 適用側。または直接のエントリの名前を変える |
| 自身のコマンドを持つシナリオが、同じコンポーネント由来の名前を持つ2つのターゲットを操作する | 一方のターゲットの適用 |

1行目は、名前付きのコマンドがないコンポーネントにも当てはまります。
適用は `hook` と `as` の組で識別します。層を連結する場合も同じです。
後の層が同じ組を書くと、項目は追加されず、前の項目を置き換えます。
テンプレート由来の適用の値は、`as` なしで変更できます。
両方を残すには、後の層で `as` を指定します。

残りの行は、コマンド名に関する条件です。
名前付きのコマンドがないコンポーネントは、該当しません。

次の場合、`as` は不要です。

- 2つのターゲットが同じコンポーネントを適用し、シナリオのコマンドが両方の名前に出会わない
- 別々のシナリオが、それぞれ同じコンポーネントを適用する
- 1つの範囲で、コマンド名が異なる2つのコンポーネントを適用する

`as` が変えるのは、コンポーネント由来の名前だけです。
直接のエントリ同士が同じ名前の場合は、一方の名前を変える必要があります。

2行目の例を示します。
ここで使うコンポーネントは、ユーザーの作成と削除だけを行い、ステップを持ちません。
コマンド名は `user` です。
ターゲットは free ユーザー用に適用します。
あるシナリオは、追加で premium ユーザーを必要とします。

```yaml
# config
targets:
  web:
    hooks:
      use:
        - hook: ./hooks/account.hook.yaml
          with: { plan: free }
```

```yaml
# シナリオ
- name: invite a premium user
  hooks:
    use:
      - hook: ../hooks/account.hook.yaml
        with: { plan: premium }
        as: premium
  steps:
    - type: { text: "${hooks.premium.user.userId}", into: { id: invite.userId } }
```

`as` がなければ、2つの適用がどちらも `user` を宣言するので、読み込みを止めます。

#### `as` が変えるもの

例として `as: premium` を指定した場合を示します。
コンポーネントの外のステップは、`${hooks.premium.user.userId}` と書きます。
外のコマンドは `BAJUTSU_HOOK__premium__user__userId` を読みます。

コンポーネント内のステップとコマンドは、元の名前 `user` を使います。
Bajutsu は展開時にステップのトークンを書き換えます。
書き換えは入れ子のステップコンポーネントを展開した後なので、その中のトークンにも及びます。
同じ適用に属するコマンドには、元の名前の環境変数を渡します。
外側に同じ名前のエントリがある場合は、トークンと環境変数の両方で元の名前を優先します。
書き換えるのは、コンポーネント自身が宣言した名前だけです。

別名は、エントリの名前と同じ規則に従います。
シナリオから見えるエントリの名前と同じ別名は使えません。
名前はドットを含まないので、3区切りと4区切りのトークンは区別できます。

### 4. 実行順

コンポーネントは、同じ場所に直接書いたエントリの外側を包みます。

| リスト | 順序 |
|---|---|
| `beforeRun`、`beforeScenario`、`setup` | コンポーネント（`use` の順）、次に直接書いたエントリ |
| `cleanup`、`afterScenario`、`afterRun` | 直接書いたエントリ、次にコンポーネント（`use` の逆順） |

後片付けは、準備の逆順になります。

例として、ターゲットがユーザー作成のコンポーネントを適用する場合を示します。
同じターゲットは、`beforeScenario`、`cleanup`、`afterScenario` に直接のエントリも1つずつ書きます。
1つのシナリオは、次の順に実行します。

1. `beforeScenario` で、コンポーネントの `create-user.sh`、直接のエントリを実行する
2. アプリを起動する
3. `setup` で、コンポーネントのサインイン、シナリオ自身の `setup` を実行する
4. シナリオの `steps` と `expect` を実行する
5. `cleanup` で、シナリオのルール、直接のルール、コンポーネントのサインアウトを実行する
6. `afterScenario` で、直接のエントリ、コンポーネントの `delete-user.sh` を実行する

2つの階層の入れ子は、現在と同じです。ターゲット側がシナリオ側の外側になります。
エラー時の扱いも変わりません。
同じ階層では、`beforeScenario` が非ゼロで終了しても `afterScenario` はすべて実行します。
ターゲット側が非ゼロで終了した場合、シナリオ自身のリストは従来どおり飛ばします。
シナリオが適用したコンポーネントも飛ばします。

### 5. 条件

適用に付けた `when` は、コンポーネントが加えるコマンドとステップのすべてに及びます。
`setup` と `cleanup` のステップにタグの条件が届くのは、本項目が最初です。
手書きのステップには、引き続き `when` を付けられません。
絞り込むのは、ターゲットの `setup` と `cleanup` を各シナリオに組み込むときです。
タグは静的なので、読み込みの時点でリストが確定します。

コンポーネント内のコマンドは、自身の `when` を持てます。その場合は両方の一致が必要です。

`beforeRun` や `afterRun` を持つコンポーネントの適用では、`when.tags` を空にできません。
実行単位のエントリに、現在課している条件と同じです。

出力を読むシナリオは、適用の `when` に一致する必要があります。
読み込み時の確認は、コマンドのエントリと同じです。

シナリオは `preconditions.inheritSetup: false` を指定できます。
指定したシナリオでは、ターゲット側の各部分を次のように扱います。

| 部分 | 直接書いた場合 | ターゲットのコンポーネントが加えた場合 |
|---|---|---|
| `setup` | 飛ばす | 飛ばす |
| `beforeScenario`、`afterScenario` | 飛ばす | 飛ばす |
| `cleanup` | 現在と同じく実行する | 適用が `setup` か `beforeScenario` を持つ場合は飛ばす |
| `beforeRun`、`afterRun` | 実行する | 実行し、出力も読める |

扱いが異なるのは、準備も持つ適用の `cleanup` だけです。
この後片付けは、自身の準備が作ったものを読みます。
準備を飛ばして後片付けだけを実行すると、後片付けは失敗します。
`setup` と `beforeScenario` のどちらも持たない適用には、この依存がありません。
`cleanup` を実行するので、直接のルールをコンポーネントに移しても挙動は変わりません。
シナリオ自身が適用したコンポーネントは実行します。

### 6. 報告とコマンドの実行方針

報告には、追加したコマンドとステップの横に、コンポーネントファイル名を併記します。
[worker のコマンド実行方針](../../docs/ja/self-hosting.md#worker-が実行する-config-のコマンドbe-0492)は、
直接書いたエントリと同じく、デバイス操作の前にすべて確認します。
コマンドには、適用元のファイルとコンポーネントファイルの2つが関わります。
実行方針は、2つの出どころのうち厳しいほうのモードを使います。
クライアントがアップロードした内容は、config のモードを得られません。

### 作業分解

1. ファイルのモデル、`use` リスト、引数の代入、パスの封じ込め
2. ターゲットとシナリオの展開（実行順、テンプレート、実行単位のリストの拒否）
3. 名前（ターゲットごとの範囲、別名、トークンの解決、コマンドの環境変数）
4. 適用単位の `when` と `inheritSetup: false` の扱い
5. 報告、コマンドの実行方針、サンドボックスの確認、worker へのコンポーネントの配布
6. スキーマと、展開後の `setup` と `cleanup` の `codegen`
7. 設定、シナリオ、シナリオ言語の文法のドキュメント

## 検討した代替案

| 代替案 | 採らない理由 |
|---|---|
| ステップのコンポーネントに `before` と `after` を足す | ステップのコンポーネントは `use` の位置に展開されます。コマンドはアプリの起動前に実行されるので、書いた位置と実行順が食い違います |
| コマンドのリストを1つずつ再利用する | 変更は小さく済みます。前後を別々に適用する形が残り、動機の1つ目を解消できません |
| 同じコンポーネントの2回目の適用を拒否する | 別名が不要で簡単です。プランが違うユーザー2人には、ファイルの複写が必要になります |
| 適用に `when` を許さない | 各コマンドに条件を書くことになります。ステップには条件を付けられず、対が崩れます |
| 直接書いたエントリを外側にする | サーバを直接起動し、コンポーネントがデータを入れる使い方に合います。本項目は共通のコンポーネントを外側に置き、固有のエントリをその内側で実行します。逆順が必要なら、サーバの起動もコンポーネントにして先に並べます |
| ターゲットのテンプレートを拡張する | テンプレートは引数を取らず、リストを置き換え、シナリオに届きません |
| コンポーネント由来の名前も実行全体で一意にする | 範囲は増えません。テンプレートを共有する2つのターゲットで、実行が止まります |
| トークンにターゲット名を書く | ほかのターゲットの値を読めます。別名と同じ形になり、追加の規則が必要です |
| コンポーネントから別のコンポーネントを適用する | 共通の土台を重ねられます。循環の検出と、順序や別名の規則が増えます |
| コンポーネントに `interrupts` を許す | ダイアログの処理を機能と一緒に配れます。ただし、準備と後片付けの対ではありません |
