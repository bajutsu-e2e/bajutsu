## はじめに

この項目は、`visual` アサーション（BE-0029）を2つの方向に拡張します。1つ目は、比較の対象を画面全体ではなく**単一の要素にスコープ**できるようにすることです。2つ目は、**除外領域を生のピクセル矩形ではなくセレクタで指定**できるようにすることです。

どちらも完全に決定的なままです。比較は依然として保存済みベースラインに対するピクセル差分であり、モデルは関与しません。

## 動機

BE-0029 は決定的な `visual` アサーションを出荷しました。しかし比較の対象は**画面全体**であり、動的なコンテンツをマスクする手段はハードコードしたピクセル矩形（`{ x, y, w, h }`）だけです。ここから2つの制約が生じます。どちらも、MagicPod や mabl の要素単位ビジュアルテストがまさに解こうとしている問題です。

1. **画面全体の比較は壊れやすく、精度も粗いです。** 関心が1つのコンポーネント（グラフ、ボタン、アバター）だけにあるテストでも、画面上の*ほかの何か*が変わるたびに失敗します。たとえば、無関係なバナーや、行が1つ増えたリストです。作者は「*この*カードだけを回帰テストし、残りは無視する」と指定できません。ベースラインが頻繁に差し替わり、信号がノイズに埋もれます。競合が要素単位の画像比較を提供しているのは、ビジュアル回帰の多くが局所的だからです。

2. **ピクセル矩形のマスクは、端末やレイアウトをまたぐと脆いです。** `exclude` 領域は絶対座標で書くため、レイアウトが折り返したとき、端末の解像度が変わったとき、ロケールによってラベルが広がったときに、気付かないままずれます。作者が実際に無視したいのは、たいてい固定された箱ではなく*要素*です。たとえば、時計、「最終更新」のタイムスタンプ、ランダムに差し替わる広告枠です。セレクタで指定すれば、座標を壊すのと同じ条件のもとでも安定します。

どちらの追加も、プライムディレクティブに無理なく収まります。要素を境界矩形に解決し、ピクセル差分の前に切り出しまたはマスクするのは、純粋で決定的な機械操作だからです。`run`/CI ゲートに AI は入り込まず、同じ画面は毎回同じ判定を返します。同じ論理によって、BE-0029 は「曖昧すぎる」として棚上げされずに受け入れられました。

## 詳細設計

`VisualMatch` スキーマ（`bajutsu/scenario/models/assertions.py`）への追加は2つです。どちらも任意で後方互換であり、既存の `visual:` ブロックは、これまでどおり画面全体を比較する挙動を保ちます。

**1. `element:`：比較を1つの要素の境界矩形にスコープする。**

```yaml
expect:
  - visual:
      element: { id: "summary-card" }   # Selector。一意に解決する
      baseline: summary-card.png
      threshold: 0.1
```

セレクタは既存の一意解決ルール（[DESIGN §5](../../DESIGN.md)）で解決します。**曖昧なセレクタは即座に失敗し**（プライムディレクティブ 2）、最初に一致したものを切り出すことは決してしません。要素のフレームはドライバの要素ツリーから読み取ります。撮影したスクリーンショットをそのフレームに切り出し、切り出した画像をベースラインと比較して差分を取ります。つまりベースラインは画面ではなく*要素*そのものになるため、無関係な変化に強くなります。

**2. セレクタによるマスク：`exclude` の要素に、矩形の代わりにセレクタを指定できるようにする。**

```yaml
expect:
  - visual:
      baseline: home.png
      exclude:
        - { selector: { label: "last updated" } }   # この要素のフレームをマスク
        - { x: 0, y: 0, w: 390, h: 54 }              # 生の矩形も引き続き使える
```

`ExcludeRegion` を共用体にします。現在の `{ x, y, w, h }` 矩形**または** `{ selector: <Selector> }` の形です。セレクタによるマスクは、評価時に要素のフレームへ解決し、現在の矩形とまったく同じようにマスクします。何にも一致しないセレクタは、マスクの無操作です。画面上に隠す対象がないためです。曖昧なセレクタは失敗し、ディレクティブ 2 と整合します。

### 作業分解（MECE）

- **スキーマ**：`VisualMatch` に `element: Selector | None` を追加します。`ExcludeRegion` は、ピクセル矩形と `{ selector: Selector }` 形式の共用体にします。どちらも任意にして、BE-0029 のシナリオを変更せずに保ちます。
- **フレーム解決**：`Selector` をドライバの要素ツリー経由でピクセルフレームに解決する、小さなヘルパーを用意します。既存の一意解決経路を再利用します（曖昧なら失敗）。
- **フレーム解決**：`Selector` をドライバの要素ツリー経由でスクリーンショットのピクセルフレームに解決する、小さなヘルパーを用意します。既存の一意解決経路を再利用します（曖昧なら失敗）。要素のフレームはポイント単位、スクリーンショットはデバイスピクセル単位なので、スクリーンショットとポイントの比（スクリーンショットのサイズをポイント空間の画面範囲で割った値）でスケールします。
- **比較エンジン**（`bajutsu/visual.py`）：変更しません。ベースラインは*要素*の切り出し画像（下記）なので、評価段階で actual を要素フレームに切り出します。既存エンジンは、要素サイズの2つの画像を比較します。解決済みのセレクタマスクは、既存のマスク経路に渡す `ExcludeRegion` 矩形が増えるだけです。ピクセル差分の中核はそのままです。
- **評価**（`bajutsu/assertions.py` の `_eval_visual` / `VisualContext`）：`element` とセレクタマスクをピクセルフレームへ解決します。actual を要素に切り出し、その切り出しをエビデンスの `actual` として記録します。マスクは切り出しの局所座標へ変換し、要素サイズのベースラインと比較します。
- **エビデンスとレポート**：`visual` のエビデンスに、比較が要素スコープだったか（`element_scoped`）と、どのセレクタがマスクしたか（`masked_selectors`）を記録します。HTML レポートの baseline / actual / diff の並びには、切り出し後の画像（記録されたパスそのもの）と、由来のバッジを描画します。レビュアーは、何を比較したのかをそのまま見られます。
- **承認ワークフロー**：`bajutsu approve` は、要素スコープのベースラインを画面全体の場合と同じ手順で昇格させます。エビデンスの `actual` が指すものをコピーするだけで、要素スコープでは切り出し画像を指すため、特別扱いは不要です（確認済み）。
- **ドキュメントとスキーマリファレンス**：`element` とセレクタマスクを、シナリオスキーマと `docs/` および `docs/ja/` に記載します。showcase のビジュアルシナリオに例を追加します。
- **テスト**：要素スコープの成功と失敗、曖昧なセレクタの失敗、動的な要素を隠すセレクタマスク、変更していない画面全体の `visual:` ブロックの後方互換性を確認します。

## 検討した代替案

- **`visualElement` という別のアサーション種別。** 却下しました。`baseline`、`threshold`、`exclude` を重複させ、スキーマを分断してしまいます。既存の `visual` に任意の `element` フィールドを足せば、概念は1つに保てます。
- **関心領域の自動検出。** ここでは却下しました。「関心のある部分」を推論するのは判断を要する作業で、LLM に近づきますが、LLM はゲートに入れられません（ディレクティブ 1）。作者が要素を明示的に指定することで、決定性を保ちます。
- **セレクタマスクだけ、または要素スコープだけを入れる。** 却下しました。2つは同じフレーム解決ヘルパーを共有し、同じ脆さを両端から解きます（何を*比較する*かと、何を*無視する*か）。まとめて出荷するほうが片方ずつより安く、競合が提供する要素単位の機能を、作者に一通り届けられます。
