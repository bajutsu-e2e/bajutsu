## はじめに

[BE-0503](../BE-0503-local-evidence-post/BE-0503-local-evidence-post-ja.md) が用意する補助スクリプト `scripts/post_evidence.py` に、3つ目のシンク `--sink attach` を足します。このシンクは、失敗したステップのスクリーンショットと、失敗したシナリオの動画を、GitHub CLI（`gh`）の `--attach` フラグに渡します。ファイルは GitHub がホストするので、コメントではスクリーンショットがその場に表示され、動画はプレーヤーとして表示されます。開発者がファイルを配信する必要はなく、リリースも作りません。

スクリプトは、判定のあとに投稿するという性質を変えません。標準ライブラリだけを使うことも変わりません。足すのは、このシンクのときだけ `gh` をサブプロセスとして実行することです。

## 動機

BE-0503 は、テキストとリンクだけのコメントを投稿します。GitHub には、コメントへ画像を載せる文書化された手段がないと考えたためです。この前提は、もう成り立ちません。`gh` 2.105.0 では、`gh pr comment` と `gh issue comment` のヘルプが `--attach` を文書化しています。このフラグは、画像や動画をアップロードし、コメント本文の参照をアップロード後のファイルに書き換えます。このフラグを解説する公開の記事には、ヘルプにない詳細も載っています。導入されたバージョン、受け付ける種類、サイズの上限、対応するプラットフォームです。この項目は、それらをスパイクで測るまで未検証として扱います。

既存の2つのシンクには、それぞれ弱点があります。`none` は、開発者がホストする写しを必要とします。`release` はブラウザーでの表示にならずダウンロードになり、ドラフトのリリースは、書き込み権限のない人に 404 を返します。ドラフトのリリースでのスパイクが、この2点を記録しています。

観察できる違いは、コメントそのものです。`--sink attach` を使うと、失敗したスクリーンショットがプルリクエストの中に表示され、レビュアーはリンクを開かずに失敗を見られます。この違いを生む仕組みは、テストで確かめられます。スクリプトが組み立てる `gh` のコマンドラインは、ステージしたファイルごとに `--attach` を1つ持ち、本文は各ファイルを置くべき場所で参照します。

## 詳細設計

### シンク

`--sink attach` は、`none` と `release` に並ぶ3つ目の値です。失敗したシナリオごとに、`--max-failures` までを対象にします。失敗したステップのスクリーンショットとシナリオの動画を、一時ディレクトリへステージします。描画した Markdown を入れた本文ファイルも、同じディレクトリに置きます。本文は、ほかのシンクと同じ描画処理で作り、各ファイルのリンクを `./<name>` にします。ステージするファイルには一意な名前を付けるので、2つのシナリオが衝突することはありません。

スクリーンショットは `--attach './name#alt'` で渡します。ヘルプによると、動画には代替テキストを付けられません。そのため、動画は `#` を付けずに `--attach './name'` で渡します。動画の参照を `[Video](./name)` と `![video](./name)` のどちらで書いたときに、`gh` が書き換えるのかは、まだ測っていません。決めるのはスパイクです。本文が参照しないファイルはコメントの末尾に付け足される、とヘルプが述べており、これが代わりの手段になります。

このシンクが扱うのは、画像と動画だけです。zip、デバイスログ、JSON ファイルは対象外なので、コメントに実行全体へのリンクは載りません。zip が要る開発者は、`release` シンクを使います。

### `gh` の呼び出し

スクリプトは、投稿先からサブコマンドを選びます。`GET /repos/<owner>/<repo>/issues/<number>` は、プルリクエストにも Issue にも答えます。プルリクエストのときだけ、応答に `pull_request` のキーが付きます。その結果に応じて、`--repo`、`--body-file`、ファイルごとの `--attach` を付けて、`gh pr comment` か `gh issue comment` を実行します。

`gh` を、計画が示したインスタンスとファイルに留めるために、3つの規則を置きます。

- スクリプトは `--repo github.com/<owner>/<repo>` を渡します。子プロセスの環境は、`GH_TOKEN` を設定し、`GH_HOST`、`GH_ENTERPRISE_TOKEN`、`GITHUB_TOKEN`、`GITHUB_ENTERPRISE_TOKEN` を取り除いて作ります。トークンは、コマンドライン、計画、ディスクのどこにも現れません。
- スクリプトは、ステージ用のディレクトリを作業ディレクトリにして `gh` を実行します。これで、`./name` が `--attach` でも本文でも同じファイルを指します。
- このシンクが対象にするのは `github.com` だけです。`GITHUB_API_URL` がほかのホストを指す場合は、リクエストの前に終了します。`gh` が見つからない場合や、下限より古い場合は、書き込みの前に理由を示して、非ゼロで終了します。

### 保護

ヘルプが述べる上限は1つで、1コマンドあたり 50 ファイルです。残りの上限は公開の記事に由来し、スパイクが確かめます。受け付ける種類は PNG、JPEG、GIF、WebP、SVG、MP4、MOV、WebM です。上限は、画像が 10 MB、動画が 10 MB または 100 MB（リポジトリの所有者のプランによる）で、バージョンの下限は 2.99.0 です。スクリプトは、ほかの種類のファイル、10 MB を超える画像、`--attach-video-mb`（デフォルトは 10）を超える動画、51 個目以降のファイルを除外します。除外したものは、すべて計画とコメントに記します。スパイクで `gh` 自身がそのようなファイルを拒否すると分かれば、後続の項目で、対応する保護を外せます。

### 固定コメント

`gh` はコメントを作ります。`--edit-last` で編集できるのは、現在のユーザー自身の最後のコメントだけで、それは別のツールのものかもしれません。`--edit-last` が `--attach` と組み合わせられるかも、まだ測っていません。そこでスクリプトは、新しいコメントを先に投稿し、古いコメントはあとで削除します。

削除には、4つの規則があります。

- スクリプトは、投稿の前にスナップショットを取ります。対象は、同じキーで同じ書き手のコメントで、BE-0503 のマーカーの規則で見つけます。削除するのは、そのスナップショットの id だけで、あとから照会し直すことはありません。
- 削除は、独自の REST クライアントによる `DELETE /repos/<owner>/<repo>/issues/comments/<id>` で行います。`gh --delete-last` は使いません。`gh` が作ったばかりのコメントを消してしまうからです。
- `gh` が新しいコメントについて表示した URL と一致する id は、削除しません。
- 削除に失敗しても、残りの削除は続けます。スクリプトは、失敗した id とエラーを報告し、非ゼロで終了します。新しいコメントはすでに投稿されており、次回の実行が、残ったコメントをもう一度並べます。

したがって、再実行するとコメントはスレッドの末尾へ移り、購読者へ通知がもう一度届きます。計画には削除するコメントを1件ずつ載せ、確認では削除も含めて承認を求めます。

`gh` が非ゼロで終わった場合、スクリプトは何も削除せず、非ゼロで終了します。`gh` のエラーを表示し、一部の添付だけを載せたコメントがすでにある可能性と、アップロード済みのファイルが URL ですでに見られる可能性を警告します。一部の失敗でも Issue を作り、その URL を表示することは、`gh issue create` のヘルプが述べています。この項目は、`gh ... comment --attach` も同じ挙動だと推定します。測るのはスパイクです。

### プライバシー

公開の記事によると、公開リポジトリへアップロードしたファイルは、サインインしなくても見られます。公開リポジトリでは、計画がこの旨を示します。確認の手順があるのは、そのためです。`--yes` を付けると、この露出を受け入れたことになります。

コメントを削除しても、消えるのはコメントだけです。そのコメントがアップロードしたファイルを、GitHub が URL で配信し続ける可能性があります。これもスパイクで確かめます。計画は、公開リポジトリの行の隣にこの旨を書きます。固定コメントの削除で、古い証跡が消えたと読めないようにするためです。伏せ字の処理が対象にするのは実行のテキストで、BE-0503 が述べるとおり、画素には及びません。

### テストとドキュメント

テストは、偽の `gh` の実行ファイルを `PATH` に置き、BE-0503 の偽の GitHub サーバーを再利用します。確かめるのは、コマンドライン、ステージしたファイル、サブコマンドの選択、バージョンとホストの拒否、各保護、成功後の削除、失敗後に削除しないこと、実行ディレクトリが変わらないことです。`docs/reporting.md` と `docs/ja/` のミラーに、このシンクを足します。

## 検討した代替案

- **ブラウザーが使うアップロードのエンドポイント。** 文書化されておらず、予告なく変わりうるので、BE-0503 が同じ理由で退けています。`gh --attach` が、同じ結果を得る文書化された経路です。
- **`release` シンクだけを残す。** リリースは表示ではなくダウンロードになり、ドラフトは、書き込み権限のないレビュアーに 404 を返します。このシンクは、zip と、`gh --attach` が対象にしないホストのために残します。
- **`--edit-last` で最後のコメントを編集する。** 編集できるのは現在のユーザーの最後のコメントだけで、別のツールのものかもしれません。スパイクで `--attach` と組み合わせられると確かめられれば、後続の項目で最適化として使えます。
- **アップロードのプロトコルをスクリプトに書く。** 文書化された API はなく、文書化されていない API を写すことになります。
