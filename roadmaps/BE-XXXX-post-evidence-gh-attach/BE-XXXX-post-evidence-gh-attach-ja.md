## はじめに

> **却下（証跡は、サーバーのストアに置き、URL でリンクするほうが適しています）。**
> GitHub には、スクリプトが run の zip をコメントへ載せる、文書化された手段がありません。
> `gh --attach` が扱うのは画像と動画だけで、zip は投稿の前に拒否します。代わりの手段はリリースのアセットです。
> これはスレッドごとにリリースを1件ずつ残します。ドラフトのリリースを開けるのは、書き込み権限を持つ人だけです。
> Actions のアーティファクトにはランナーが要り、手元の実行にはそれがありません。
> 何かの解消を待っているわけではないので、この項目は保留ではなく却下とします。
> 後続の項目で、完了した run を `serve` のストアに保存し、そこで得た URL をコメントからリンクします。

[BE-0503](../BE-0503-local-evidence-post/BE-0503-local-evidence-post-ja.md) が用意する補助スクリプト `scripts/post_evidence.py` に、3つ目のシンク `--sink attach` を足します。このシンクは、失敗したステップのスクリーンショットと、失敗したシナリオの動画を、GitHub CLI（`gh`）の `--attach` フラグに渡します。ファイルは GitHub がホストするので、コメントではスクリーンショットがその場に表示され、動画はコメントの末尾で再生されます。このシンクは、run 全体を zip にして上げ、コメントからリンクします。プレビュー以上を見たいレビュアーは、zip を開けます。スクリプトが上げる単位は、run のままです。単体のファイルは上げません。

スクリプトは、判定のあとに投稿するという性質を変えません。標準ライブラリだけを使うことも変わりません。足すのは、このシンクのときだけ `gh` をサブプロセスとして実行することです。

## 動機

BE-0503 は、テキストとリンクだけのコメントを投稿します。GitHub には、コメントへ画像を載せる文書化された手段がないと考えたためです。この前提は、もう成り立ちません。`gh` 2.105.0 では、`gh pr comment` と `gh issue comment` のヘルプが `--attach` を文書化しています。このフラグは、画像や動画をアップロードし、コメント本文の参照をアップロード後のファイルに書き換えます。このフラグを解説する公開の記事には、ヘルプにない詳細も載っています。使い捨てのリポジトリでのスパイクは、その大半を測りました。見つかったことと、手が届かなかったことは、後述の「測定した挙動」に記します。

既存の2つのシンクには、それぞれ弱点があります。`none` は、開発者がホストする写しを必要とします。`release` はブラウザーでの表示にならずダウンロードになり、ドラフトのリリースは、書き込み権限のない人に 404 を返します。ドラフトのリリースでのスパイクが、この2点を記録しています。

観察できる違いは、コメントそのものです。`--sink attach` を使うと、失敗したスクリーンショットがプルリクエストの中に表示され、レビュアーはリンクを開かずに失敗を見られます。この違いを生む仕組みは、テストで確かめられます。スクリプトが組み立てる `gh` のコマンドラインは、ステージしたファイルごとに `--attach` を1つ持ち、本文は各ファイルを置くべき場所で参照します。

## 詳細設計

### シンク

`--sink attach` は、`none` と `release` に並ぶ3つ目の値です。失敗したシナリオごとに、`--max-failures` までを対象にします。失敗したステップのスクリーンショットとシナリオの動画を、一時ディレクトリへステージします。描画した Markdown を入れた本文ファイルも、同じディレクトリに置きます。本文は、ほかのシンクと同じ描画処理で作り、各ファイルのリンクを `./<name>` にします。ステージするファイルには一意な名前を付けるので、2つのシナリオが衝突することはありません。

スクリーンショットは `--attach './name#alt'` で渡し、本文では `![alt](./name)` で参照します。動画は `--attach './name'` で渡し、本文では参照しません。スパイクでは、動画への代替テキストを `gh` が拒否することと、動画の参照を `gh` がただのリンクに書き換え、GitHub はそれを再生しないことが分かりました。参照のない動画は、裸の URL としてコメントの末尾に付け足され、この形ならプレイヤーとして表示されます。そのため、コメントではシナリオの下に動画のパスだけを示し、動画はコメントの末尾にまとめて再生されます。

`gh --attach` が扱うのは画像と動画だけで、スパイクでは、zip を投稿の前に拒否することが分かりました。そのため、run の zip は、リリース `bajutsu-evidence-<number>` のアセットとして上げます。規則は、BE-0503 の `release` シンクと同じです。リポジトリの最新リリースにならないドラフトのプレリリースを作り、`--publish` は任意で付け、公開で動くワークフローを計画に並べます。スクリプトは、zip を先に上げ、コメントを後で投稿します。そのため、アップロードに失敗した場合は、何も投稿されません。コメントは、zip を `Whole run` としてリンクします。`--size-warn-mb` を超える zip は、メモを残して除外し、その場合のコメントにはリンクを載せません。デバイスログや JSON ファイルを、単体で上げることはありません。リリースには、リポジトリの内容への書き込み権限が要り、ドラフトを開けるのは、書き込み権限を持つ人だけです。

### `gh` の呼び出し

スクリプトは、投稿先からサブコマンドを選びます。`GET /repos/<owner>/<repo>/issues/<number>` は、プルリクエストにも Issue にも答えます。プルリクエストのときだけ、応答に `pull_request` のキーが付きます。その結果に応じて、`--repo`、`--body-file`、ファイルごとの `--attach` を付けて、`gh pr comment` か `gh issue comment` を実行します。

`gh` を、計画が示したインスタンスとファイルに留めるために、3つの規則を置きます。

- スクリプトは `--repo github.com/<owner>/<repo>` を渡します。子プロセスの環境は、`GH_TOKEN` を設定し、`GH_HOST`、`GH_ENTERPRISE_TOKEN`、`GITHUB_TOKEN`、`GITHUB_ENTERPRISE_TOKEN` を取り除いて作ります。トークンは、コマンドライン、計画、ディスクのどこにも現れません。
- スクリプトは、ステージ用のディレクトリを作業ディレクトリにして `gh` を実行します。これで、`./name` が `--attach` でも本文でも同じファイルを指します。
- このシンクが対象にするのは `github.com` だけです。`GITHUB_API_URL` がほかのホストを指す場合は、リクエストの前に終了します。`gh` が見つからない場合や、下限より古い場合は、書き込みの前に理由を示して、非ゼロで終了します。

### 保護

ヘルプが述べる上限は1つで、1コマンドあたり 50 ファイルです。スパイクでは、`gh` が、ほかの種類のファイルと 10 MB を超える画像を、どちらも投稿の前に拒否することを確かめました。11 MB の動画は、テスト用のアカウントでは通ったので、動画の上限はリポジトリの所有者のプランによります。スクリプトは、デフォルトを 10 MB に保ちます（`--attach-video-mb`、1〜100）。そのうえで、51 個目以降、ほかの種類のファイル、10 MB を超える画像、上限を超える動画を除外します。除外したものは、すべて計画とコメントに記します。バージョンの下限 2.99.0 は公開の記事に由来します。手元にあるのは `gh` 2.105.0 だけなので、スパイクでは測れませんでした。

### 固定コメント

`gh` はコメントを作ります。`--edit-last` で編集できるのは、現在のユーザー自身の最後のコメントだけで、それは別のツールのものかもしれません。スパイクでは、`--edit-last` が `--attach` と組み合わせられると分かりました。そのため、このキーのコメントが最後にあるときの最適化として、後続の項目で使えます。スクリプトは、古いコメントがどこにあっても使えるように、新しいコメントを先に投稿し、古いコメントはあとで削除します。

削除には、4つの規則があります。

- スクリプトは、投稿の前にスナップショットを取ります。対象は、同じキーで同じ書き手のコメントで、BE-0503 のマーカーの規則で見つけます。削除するのは、そのスナップショットの id だけで、あとから照会し直すことはありません。
- 削除は、独自の REST クライアントによる `DELETE /repos/<owner>/<repo>/issues/comments/<id>` で行います。`gh --delete-last` は使いません。`gh` が作ったばかりのコメントを消してしまうからです。
- `gh` が新しいコメントについて表示した URL と一致する id は、削除しません。
- 削除に失敗しても、残りの削除は続けます。スクリプトは、失敗した id とエラーを報告し、非ゼロで終了します。新しいコメントはすでに投稿されており、次回の実行が、残ったコメントをもう一度並べます。

したがって、再実行するとコメントはスレッドの末尾へ移り、購読者へ通知がもう一度届きます。計画には削除するコメントを1件ずつ載せ、確認では削除も含めて承認を求めます。

`gh` が非ゼロで終わった場合、スクリプトは何も削除せず、非ゼロで終了します。`gh` のエラーを表示し、一部の添付だけを載せたコメントがすでにある可能性と、アップロード済みのファイルが URL ですでに見られる可能性を警告します。スパイクで測れたのは1つの場合です。`gh` は、投稿の前にすべてのファイルを検査するので、非対応のファイル、存在しないファイル、サイズ超過の画像があっても、コメントは1件も作られません。アップロードの途中で起きる失敗は、起こせなかったので、警告はそのまま残します。

### プライバシー

公開リポジトリでは、アップロードしたファイルへの匿名の要求に、`200` とメディアの種類が返り、添付ファイルとしての指定はありません。URL を知っていれば、誰でも見られます。公開リポジトリでは、計画がこの旨を示します。確認の手順があるのは、そのためです。`--yes` を付けると、この露出を受け入れたことになります。

コメントを削除しても、消えるのはコメントだけで、ファイルは残ります。スパイクでは、コメントを削除したあとで画像を匿名で取得しました。応答は、そのまま `200` でした。計画は、公開リポジトリの行の隣にこの旨を書きます。固定コメントの削除で、古い証跡が消えたと読めないようにするためです。伏せ字の処理が対象にするのは実行のテキストで、BE-0503 が述べるとおり、画素には及びません。

### 測定した挙動

スパイクは、使い捨ての公開リポジトリで、`gh` 2.105.0 を使い、トークンは `GH_TOKEN` だけで渡し、空の `gh` 設定ディレクトリに対して実行しました。使ったのはダミーのファイルだけです。

| 問い | 結果 |
|---|---|
| `gh` は `GH_TOKEN` だけで動くか。 | 動きます（`gh issue create` と `gh issue comment` で確認）。 |
| マーカーは本文の先頭行に残るか。 | 残ります。 |
| 画像の参照はどう書き換わるか。 | `![alt](./name)` が `![alt](<ホストされた URL>)` になり、ページに画像が表示されます。 |
| 動画の参照はどう書き換わるか。 | `![v](./name)` も `[v](./name)` もただのリンクになり、再生されません。裸のパスは書き換わりません。 |
| 動画はどう再生されるか。 | 参照のない動画は、裸の URL として末尾に付け足され、その形ならプレイヤーとして表示されます。 |
| 動画に代替テキストを付けられるか。 | 付けられません。`gh` が、投稿の前に拒否します。 |
| `gh` が受け付ける種類とサイズは。 | png、jpg、jpeg、gif、webp、svg、mp4、mov、webm を挙げています。10 MB を超える画像は拒否します。 |
| 非対応のファイルを渡すとどうなるか。 | `gh` が投稿の前に拒否し、コメントは作られません。 |
| `gh --attach` は zip を受け付けるか。 | 受け付けません。投稿の前に拒否します。 |
| `--edit-last` は `--attach` と組み合わせられるか。 | 組み合わせられます。 |
| アップロードしたファイルは誰が開けるか。 | 公開リポジトリでは、誰でも開けます。 |
| コメントを削除してもファイルは残るか。 | 残ります。 |

手が届かず測れなかったのは、バージョンの下限 2.99.0、GitHub Enterprise Server、無料プランでの動画の上限、アップロードの途中で起きる失敗です。

### テストとドキュメント

テストは、偽の `gh` の実行ファイルを `PATH` に置き、BE-0503 の偽の GitHub サーバーを再利用します。確かめるのは、コマンドライン、ステージしたファイル、サブコマンドの選択、バージョンとホストの拒否、各保護、成功後の削除、失敗後に削除しないこと、実行ディレクトリが変わらないことです。`docs/reporting.md` と `docs/ja/` のミラーに、このシンクを足します。

## 検討した代替案

- **ブラウザーが使うアップロードのエンドポイント。** 文書化されておらず、予告なく変わりうるので、BE-0503 が同じ理由で退けています。`gh --attach` が、同じ結果を得る文書化された経路です。
- **`release` シンクだけを残す。** リリースは表示ではなくダウンロードになり、ドラフトは、書き込み権限のないレビュアーに 404 を返します。このシンクは、zip と、`gh --attach` が対象にしないホストのために残します。
- **`--edit-last` で最後のコメントを編集する。** 編集できるのは現在のユーザーの最後のコメントだけで、別のツールのものかもしれません。スパイクで、`--attach` と組み合わせられると確かめられたので、後続の項目で最適化として使えます。
