## はじめに

この項目は、ロードマップステータスダッシュボードに、カードグリッド表示の代替としてテーブル表示を追加します。ダッシュボードは、[BE-0094](../BE-0094-roadmap-status-dashboard/BE-0094-roadmap-status-dashboard-ja.md) で公開し、[BE-0219](../BE-0219-roadmap-dashboard-search/BE-0219-roadmap-dashboard-search-ja.md) で検索を追加した GitHub Pages のページです。

読者は Cards と Table を切り替えられます。Table では、各項目が1行になり、ID、タイトル、トピック、状態、作成日、更新日の6つのソート可能なカラムを持ちます。カラム見出しをクリックすると、テーブル全体がそのカラムで昇順または降順にソートされます。

選んだ表示モードは、ブラウザの `localStorage` に保存され、次回訪問時にも復元されます。既存の検索ボックスとステータスチップは、両方の表示モードでそのまま機能します。

作成日と更新日は、これまでダッシュボードになかった2つのカラムです。ビルド時に、項目の Git の履歴から日付を導出します。導出に使うのは、項目の2つの言語ファイルにまたがる最初のコミットと最新のコミットです。手作業で設定する新しいフィールドは追加しません。今後のすべての編集が2つの日付を実際の履歴と一致させ続けてくれる、と信頼する必要はなくなります。

## 動機

カードグリッドは、トピックごとに項目をグループ化し、各項目の状態をバッジで示します。この表示は、1つのカテゴリを順に眺める用途に向いています。一方で、別の問いには答えられません。最近更新された項目はどれか、トピックを問わず ID 順に並べるとロードマップ全体はどう見えるか、という問いです。カードグリッドには、ソートの軸となる列がありません。全項目を1つのフラットなテーブルの行として扱って初めて、ソートは意味を持ちます。

貢献者の作業には、フラットでソート可能なテーブルを必要とする場面が2つあります。

- 最近の変更を確認する作業では、更新日でソートして上位を見ます。現状では、カテゴリを1つずつ開いて、ページに存在しない日付を目で比較しなければなりません。
- 提案がどれだけ放置されているかを確認する作業では、作成日でソートします。

現状のカードレイアウトは、どちらの作業も満たせません。ブラウザの Ctrl+F やダッシュボード自身の検索ボックスも解決しません。両者は「どのカードを表示するか」を絞り込むだけで、「どの順序で並べるか」を変えないからです。

この項目は、ドキュメントと貢献者ワークフロー上の改善にとどまり、いずれのプライムディレクティブ（[`CLAUDE.md`](../../CLAUDE.md)）にも抵触しません。

- ダッシュボードは静的な docs サイトの成果物なので、大規模言語モデル（LLM）は関与しません。
- `run` や CI の合否判定の経路は存在しません。
- 決定性に関わる面には触れません。
- テーブルはメタデータが持つ項目に対して汎用的に働くため、アプリ固有の要素を含みません。

## 詳細設計

ダッシュボードは [`scripts/build_roadmap_dashboard.py`](../../scripts/build_roadmap_dashboard.py) が生成します。`render_html` は、`.be-cat` というトピックごとのセクションの中に、項目ごとの `.be-card` を1つずつ出力します。各セクションは、`状態` のみから導出した進捗バーを持ちます。`<script>` ブロックは、検索ボックスとステータスチップ（BE-0219）をプログレッシブエンハンスメントで有効化します。

テーブル表示は、この既存の構造を置き換えず、そこへ追加する形で組み込みます。作業は MECE（互いに排他的で全体として網羅的）な次の単位に分解できます。

1. **Git 履歴からの作成日と更新日の導出。** [`scripts/build_roadmap_index.py`](../../scripts/build_roadmap_index.py) の `Item` に、ISO 8601 形式の日付を2つ追加します。ビルド時に、`git log --follow --format=%aI -- <path>` を、英語ファイルと `-ja.md` ミラーのそれぞれに対して1回ずつ実行し、2つの結果を合わせます。`created` は、どちらかのコマンドが報告するもっとも古い行で、各ファイルの最初のコミットです。`updated` は、もっとも新しい行で、いずれかのファイルの最新のコミットです。

   2つのファイルを別々に、それぞれ `--follow` 付きで実行するのは、意図的な設計です。`--follow` は1つのパスしか受け付けません。それでも、CI が実際の ID を割り当てる際に全項目が経るリネーム（`BE-0311-<slug>` → `BE-NNNN-<slug>`）を越えて、ファイルの履歴を正しく追跡できます。両方のファイルの結果を合わせると、片方だけが更新された場合にも `updated` が正しく保たれます。例は、日本語側だけの表現の修正です。

   ダッシュボードには、データについて守る原則が1つあります（BE-0094 の「データの正直さ」）。メタデータに根拠のない数値を作り出さない、という原則です。項目が設定していればそのまま描画される `Origin` は、この原則を満たします。`状態` のみから導出するトピックごとの進捗率も、満たします。手作業で設定する作成日と更新日のペアは、初日にはこの原則を破りません。しかし `Origin` は、執筆時に一度書かれて、めったに見直されません。日付のペアは、項目へのすべての将来の編集で、正しく書き換えられる必要があります。そのため、実際の履歴から気付かないうちにずれていく可能性が、もっとも高いフィールドです。両方の日付を `git log` から導出すれば、このフィールドを新設せずに済みます。

   この導出には、前提が1つ加わります。[`.github/workflows/docs.yml`](../../.github/workflows/docs.yml) の checkout ステップを、現状の浅いクローンから、完全な履歴を取得する `fetch-depth: 0` に変更する必要があります。1コミットだけの checkout では、`git log` がすべての項目を同じ日に作成および更新されたものと報告するためです。代償は、以後のすべての docs ビルドで checkout にかかる時間が、わずかに増え続けることです。一度きりのコストではありません。

   項目1つにつき `git log --follow` を2回実行すると、現在のロードマップ全体で約600回の実行になり、もう1つ別の継続的なコストが加わります。どの実行も、すでに取得済みの履歴に対するローカルな読み取りで、ネットワーク通信を伴いません。checkout 自体に比べれば、無視できる範囲にとどまると見込んでいます。ビルドを目に見えて遅くするようであれば、より安い代替案があります。リポジトリ全体を1回だけ `git log --name-status -M` で走査し、全項目の日付を1パスで解決する方式です。
2. **表示モードの切り替え。** 既存の `.be-filters` 行の隣に、`Cards` と `Table` を切り替えるコントロールを配置します。両方の表示モードは、同じレンダリング済みの項目データを読みます。切り替えは、兄弟関係にある2つのコンテナ（`.be-cards-view` / `.be-table-view`）の一方を表示し、他方を隠すだけです。読者が切り替えても、何かを取得し直したり再計算したりしません。
3. **テーブルのマークアップ。** 項目集合ごとに `<table>` を1つ、項目ごとに `<tr>` を1つ描画します。テーブルは、ID、タイトル、トピック、状態、作成日、更新日の6つの `<th>` を持ちます。各 `<th>` には、`data-sort-key` とクリックハンドラを付けます。各カードがすでに持つフィールド（id、タイトル、トピック、状態）をそのまま再利用し、2つの日付カラムを加えます。

   各行は、対応するカードと同じ `data-status` / `data-topic` 属性を持ちます。検索ボックスとステータスチップ（BE-0219）は、別のマッチングロジックを新設せずに、カードと同じようにテーブルの行を絞り込みます。

   Cards 表示で読者が頼りにしているトピックごとの進捗バーも、失われません。テーブルの上に、コンパクトな帯を描画します。帯は、全トピックを、既存の積み上げバーとパーセンテージとともに列挙します。帯は、カードのセクションがすでに使う `_progress_bar` の計算を再利用します。
4. **クライアントサイドのソート。** 既存のフィルタスクリプト（`_SCRIPT`）に、ソート処理を追加します。`<th>` をクリックすると、そのカラムでテーブルの `<tr>` を並べ替えます。比較の方法は、カラムごとに異なります。
   - タイトル、トピック、状態は、文字列として比較します。
   - ID は、数値として比較します。
   - 作成日と更新日は、日時として比較します。

   同じカラムを再度クリックすると、昇順と降順が切り替わります。現在ソート中のカラムと向きは、`aria-sort` 属性で示します。ソートが並べ替えるのは、すでにステータスと検索のフィルタを通過して表示されている行です。どの行を表示するかには、影響しません。
5. **表示モードの永続化。** Cards と Table を切り替えるたびに、選択を専用のキーで `localStorage` に書き込みます。ページ読み込み時には、そのキーを読み、最初の描画より前に、対応する表示モードを反映します。キーが存在しない場合や `localStorage` が使えない場合は、現状のデフォルトである Cards にフォールバックします。

   ダッシュボードの他のインタラクティブな要素と同様に、この永続化はプログレッシブエンハンスメントとして働きます。JavaScript が無効な環境では、現状と変わらず常に Cards 表示になります。
6. **スタイリング。** テーブル、切り替えコントロール、進捗帯の CSS を `_STYLE` に追加します。CSS は、既存のチップやカードのスタイルに合わせ、MkDocs のライトテーマとダークテーマの両方で読みやすくします。
7. **テスト。** [`tests/test_roadmap_dashboard.py`](../../tests/test_roadmap_dashboard.py) を拡張し、4つの結果を検証します。
   - 各項目が、6カラムを持つ行を1つ描画すること。
   - 各日付カラムの値が、ISO 8601 形式であること。
   - 表示モードの切り替えコントロールと2つのコンテナが、存在すること。
   - ソートスクリプトが、各 `<th>` にクリックハンドラを配線していること。

   これらは機械的に検証できる結果です。ブラウザを必要とせず、ゲートを高速かつ LLM 抜きに保ちます。

ページが**内容として持つもの**は変わりません。2つの日付カラムが増える以外、項目集合とそのフィールドはそのままです。同じ項目群を並べる方法が、もう1つ増えるだけです。`docs/architecture.md` と `docs/ja/` の更新は不要です。これらの文書が説明しているのは、ダッシュボードの目的であって、表示モードの選択肢ではないためです。そこにダッシュボードの表示モードを列挙する一文があれば、同じ PR で更新します（[BE-0113](../BE-0113-design-doc-realignment/BE-0113-design-doc-realignment-ja.md)）。

## 検討した代替案

- **切り替えではなく、カードグリッドをテーブルで完全に置き換える。** 却下しました。カードグリッドがすでにうまく提供している、トピックごとの進捗バーとカテゴリ単位の閲覧という使い方が、失われるか、テーブルの行の中で作り直す必要が生じます。この項目が狙うソートという用途には、何の利点もありません。切り替え式であれば、両方の使い方を損なわずに済みます。
- **`ideation` / `implement-be` スキルが更新のたびに手で書き換える、`作成日` / `更新日` のメタデータフィールドを項目ファイルに追加する。** 却下しました。理由は2つあります。既存の約300項目に対して、一度きりのバックフィルが必要です。また、`Origin` は執筆時に一度書かれてめったに見直されない事実ですが、日付のペアは、以後のすべての編集で、実際の履歴とのずれを生む機会になります。両方の日付をビルド時に `git log` から導出すれば、ずれのリスクはなくなります。代償は、docs ワークフローの checkout が、今後すべてのビルドで浅いクローンではなく完全な履歴取得になり、その分だけ時間が延び続けることです。
- **フラットなテーブルではなく、トピックごとのカードセクションの中だけでソートする。** 却下しました。「最近何が変更されたか」と「この提案はどれだけ放置されているか」という2つの動機は、どちらもロードマップ全体にまたがる問いです。ソートを1つのトピックの中に閉じ込めると、トピックをまたいで比較するために、結局すべてのセクションを手で開く必要が残ります。フラットなテーブルであれば、どちらの問いにも1回のソートで答えられます。
- **サーバーサイド・ビルド時のソート（生成したページに固定の並び順を焼き込む）。** 却下しました。読者が見たい並び順は、そのときどきで変わります。ID 順のときも、更新日順のときもあります。静的なページに焼き込める並び順は、1つだけです。描画済みの行に対するクライアントサイドのソートであれば、ビルド時のコストなしに、読者が欲しいどの並び順にも応えられます。
