## はじめに

本項目は、項目のトラッキング Issue（BE-0109）へのリンクを追加します。Issue は、担当者（Assignees）や
議論が実際に存在する場所です。リンクは、読み手が項目を目にする二つの場所の両方に追加します。

- [ロードマップ状況ダッシュボード](https://bajutsu-e2e.github.io/bajutsu/api/roadmap.html)
  （BE-0094）の各カードに追加する、もう一本小さなリンク
- 項目自身のメタデータブロック（`roadmaps/` 配下の `.md` ファイル）に追加する新しい行

どちらも同じ、GitHub の Issue 検索 URL です。URL は項目の ID だけから機械的に組み立てます。特定の
Issue 番号をそのつど取得することはありません。ダッシュボードのビルドも項目のファイルそのものも、
ネットワーク通信、GitHub トークン、ファイル作成後に変わり得る状態のいずれにも依存しません。

## 動機

BE-0094 は、すでに各カードから 1 本のリンクを出しています。GitHub 上にある、項目の Markdown 版の
提案本体へのリンクです。一方 BE-0109 は、`状態` が `承認済み` または `実装中` であった（あるいは今も
そうである）項目ごとに、`[BE-NNNN] タイトル` という形式の Issue を起票します。その担当者は、「すでに
誰かが取り組んでいるか」の一次情報として扱われます。

ところが今は、項目からその Issue へ繋がる場所がどこにもありません。読み手は一度その場を離れて、
リポジトリの Issues タブを開く必要があります。さらに、`roadmap-tracking` ラベルと `in:title BE-NNNN`
という検索の慣習をあらかじめ知っているか、その場で組み立てるほかありません。

この隙間が問題になるのは、読み手が続けて二つの問いを抱くからです。「この項目は何か」（提案本体）と、
「すでに誰かが取り組んでいるか」（Issue、その担当者）です。今は前者にしか、読み手がいるその場で答え
られません。

しかも隙間は一箇所だけではありません。読み手は、項目自身のファイルにも、ダッシュボードと同じくらいの
頻度で直接たどり着きます。経路は、別のドキュメントからのリンク、PR の本文、GitHub 上のコード検索、
プレーンテキストの [`roadmaps/README.md`](../README-ja.md) 索引などです。これらの経路は、どれも
ダッシュボードを経由しません。リンクをダッシュボードという派生した表示だけに置けば、こうした経路の
すべてがリンクを持たないままになります。

隙間を出典である項目のファイル自身で埋めれば、たどり着き方によらず、すべての読み手に届きます。
ダッシュボードのリンクは、その同じ事実を、すでに表示している提案本体へのリンクの隣にもう一度出す
だけになります。

## 詳細設計

1. **機械的に組み立てる検索 URL であり、Issue のそのつどの取得ではありません。両方の表示先で
   共有します。** BE-0109 が起票する Issue のタイトルは常に `[BE-NNNN] 項目のタイトル` で、常に
   `roadmap-tracking` ラベルを持ちます。そのため、項目の ID だけから、Issue 番号を知らなくても Issue を
   見つけられる GitHub の検索 URL を組み立てられます。
   `https://github.com/bajutsu-e2e/bajutsu/issues?q=is%3Aissue+label%3Aroadmap-tracking+in%3Atitle+"BE-NNNN"`
   このクエリには `is:open` を含めません。Issue がまだオープンでも、後でクローズされていても見つかり
   ます。`承認済み` や `実装中` を経て出荷された項目は、クローズ済みの Issue を持ち続けます。URL の
   組み立てに必要なのは ID の文字列だけです。`gh` の呼び出しも、GitHub トークンも、ビルド時や起草時の
   ネットワーク通信も要りません。
2. **ダッシュボード側はカードの変更だけです。** `scripts/build_roadmap_dashboard.py` の `_card()` に、
   既存の提案本体へのリンクと並べて、もう一本小さなリンクを追加します（たとえば「Issue」と書いた
   小さなピル状のリンクです）。このリンクは、上記の検索 URL へつなぎます。カードの主たるクリック
   対象である提案本体へのリンクは変えません。新しいリンクは追加するだけです。
3. **項目ファイル側は、新しい「トラッキング Issue」メタデータ行です。** 番号を持つすべての項目の
   `.md` ファイルに、フェンスで囲んだメタデータブロックの新しい行「トラッキング Issue」を追加します。
   値は、同じ検索 URL へのリンクにします（`| トラッキング Issue | [検索](…) |`）。

   「実装 PR」は、PR が出荷されて初めて手で埋めます。この行は違い、著者の判断をまったく必要としません。
   値は、ファイル自身が持つ `BE-NNNN` の ID だけから決まる純粋な関数です。冒頭の言語切り替えリンクや
   `# BE-NNNN — …` というタイトルと同じくらい、機械的に決まります。

   この行は、BE-0109 がすでに退けた「Issue 番号を書き戻す」という発想ではありません（後述の
   *検討した代替案* を参照）。値は、Issue が後で起票されようと、担当者が付こうと、クローズされようと、
   一度書いたきり変わりません。保守も、Issue のライフサイクルに合わせた書き戻しも必要ありません。
4. **正規のスキーマ、生成時のひな形、既存項目への反映。** 「トラッキング Issue」は、
   `tests/test_roadmap_format.py` が固定する正規のフィールド順（`ORDER_EN` / `ORDER_JA`）に加わります。
   位置は `状態` の直後、`実装 PR` の手前です。`提案`、`提案者`、`状態`、`トピック` と並ぶ必須
   フィールドにもなります。
   - `scripts/new_roadmap_item.py` の生成内容にもこの行を追加し、新規に起草するすべての項目が最初から
     持つようにします。生成時点では、プレースホルダー `BE-0139` から値を計算します。採番前は
     `…in:title+"BE-0139"…` のままです。冒頭の言語切り替えリンクや `提案` 行がすでにそうしているのと
     同じです。
   - 既存の番号を持つ項目には、一度きりの機械的な反映用スクリプトで、両言語のファイルに行を追加します。
     各値は、そのファイル自身がすでに持っている ID だけから計算できます。ここでも著者の判断は要らず、
     スクリプトを一度走らせるだけで済みます。およそ 120 件を手で編集する必要はありません。
   - CLAUDE.md の正規フィールド順を説明する一文も、新しいフィールド名を含むように更新します。
5. **`BE-0139` プレースホルダーは、追加の仕組みなしに解決します。** この行の値は、採番されるまで
   `BE-0139` を含む文字どおりのテキストです。`scripts/allocate_roadmap_ids.py` がすでに行っている
   ファイル全体の `text.replace(old_token, new_token)`（BE-0089）が、実際の `BE-NNNN` への書き換えも
   済ませます。言語切り替えリンクやタイトルを書き換えるのと同じ、一回の処理です。採番処理側に新しい
   ロジックは要りません。
6. **検証。** 既存のフィールド順と必須フィールドのチェックに加えて、`tests/test_roadmap_format.py` に
   チェックを追加します。番号を持つすべての項目の「トラッキング Issue」の値が、その項目自身の ID から
   導かれる検索 URL とちょうど一致するかを確かめます。機械的なだけのフィールドが崩れ得る唯一の失敗、
   すなわち別項目のファイルからのコピー貼り付けで古い値が残ってしまう事態を、捕まえるためです。
7. **BE-0109 の同期処理やラベル、ワークフローは変更しません。** 検索 URL は、ID と、BE-0109 が
   すでに保証しているタイトルとラベルの慣習だけから導けます。GitHub から何かを読み戻す必要が
   ありません。`sync_roadmap_tracking_issues.py` と `roadmap-tracking-issues.yml` はそのままです。
8. **このリンクは、検索結果が 0 件になり得ます。** BE-0109 が Issue を起票するのは、同期処理が走った
   時点でその項目が `承認済み` または `実装中` だった場合だけです。追加された時点ですでに `実装済み` と
   して出荷された項目、いわば生まれながらに実装済みの項目は、オープンな状態を一度も経ません。Issue を
   持たず、検索リンクは 0 件になります。

   ダッシュボードも項目ファイルも、これを事前に知る手立てを持ちません。GitHub に問い合わせれば分かり
   ますが、それは 1. で避けたネットワーク依存を呼び戻します。そこで、両方のリンクとも「Issue そのもの」
   ではなく「Issue の検索」だと明示します。0 件のページに着地した読み手が、理由を理解できるように
   します。
9. **ドキュメント。** 変更するのは次の三点です。
   - 本項目のファイル自身。
   - BE-0109 の `参考` 節への、短い相互参照。BE-0109 の検討した代替案には、「ダッシュボード（BE-0094）は、読み取り専用の `gh issue list` から項目と Issue のリンクを描画できる」という記述があります。この記述は、本項目が採る設計に置き換わるものとして扱います。本項目は、後述のとおり `gh issue list` を使いません。
   - 4. で触れた CLAUDE.md の更新。

## 検討した代替案

- **`gh issue list` によるそのつどの取得。** ダッシュボードのビルド時であれ、「トラッキング Issue」行を
  起草する時点であれ、検索 URL の代わりに実際の Issue 番号を解決する方法です。ダッシュボードについては、
  BE-0109 の `参考` 節がすでに見込んでいた方向です（「ダッシュボード（BE-0094）は、読み取り専用の
  `gh issue list` から項目と Issue のリンクを描画できる」）。両方の表示先について退けました。
  - 今の `make docs` と `make docs-serve` は、ダッシュボードを stdlib だけで再生成しており、
    ネットワーク通信も `gh auth` も要りません。`docs` ワークフローに至っては、`issues` 権限を一切
    持たずにビルドしています。そのつどの取得に切り替えると、ローカルでの `gh` セッションと、CI 側の
    新しい `issues: read` 権限の両方が必要になります。
  - 項目ファイルの行をそのつどの取得で埋める方法は、さらに分が悪くなります。新規の提案では、実際の
    Issue 番号がまだ存在しません。BE-0109 は、ID が `main` で採番されて初めて Issue を起票するから
    です。起草の時点では、そもそも埋められません。
  - 検索 URL なら、どちらの依存も増やしません。プレースホルダー ID が存在した瞬間から埋められます。
- **ダッシュボードだけに留め、項目自身のファイルには追加しない方法。** 本項目が当初持っていた範囲
  です。退けました。項目のファイルには、ダッシュボードと同じくらいの頻度で直接たどり着きます。経路は、
  別のドキュメントからのリンク、PR の本文、コード検索、プレーンテキストの索引などで、そのどれも
  ダッシュボードを経由しません。リンクを派生した HTML の表示だけに置けば、出典であるファイル自身と、
  そこへ直接たどり着くすべての読み手が、リンクを持たないままになります。
- **Issue の実際の「番号」を項目のメタデータブロックに書き戻す方法**（値が実際に解決された Issue への
  リンクである「トラッキング Issue」行）。BE-0109 自身が、すでに一度退けています。どの Issue が開いて
  いるか、誰が担当しているかという状態は、項目のメタデータの他の部分よりずっと頻繁に変わります。
  その状態のために、保護された `main` への、bypass 用 App を介したコミットを強いることになり、
  「GitHub を唯一の一次情報にする」という BE-0109 の設計を崩します。

  本項目の「トラッキング Issue」行は、見た目こそ似ていますが、中身は違います。不変の `BE-NNNN` の ID
  から一度だけ計算する URL で、どの読み手にとっても同一です。その先の Issue に何が起きようと、二度と
  書き換わりません。そのつどの取得も、Issue のライフサイクルに合わせた書き戻しも要らず、BE-0109 が
  すでに決着させた論点を蒸し返すものでもありません。
- **既存のリンクや行を Issue へのリンクに置き換える方法。** ダッシュボードなら提案本体へのリンクを、
  項目ファイルなら既存のいずれかの行を置き換える案です。退けました。提案本体と、項目の既存の
  メタデータは、読み手がまず欲しいものです。Issue は、担当状況と議論への薄い副次的な導線にすぎません。
  追加のリンクや行として足せば、既存のクリック対象や行はどれも変わらずに済みます。
