## はじめに

Bajutsu の実行パイプラインは、シナリオの途中で起きたバックエンドのクラッシュを判定ではなく基盤の障害として
扱います。死んだリース（準備済みの1台のデバイスと、その上の runner のプロセスをパイプラインが押さえて
いる状態）を破棄し、新しいデバイスをリースし、シナリオ全体を再実行します。再試行の回数と実時間の予算が
その繰り返しを縛ります。
[BE-0353](../BE-0353-xcuitest-adb-crash-retry-device-recovery/BE-0353-xcuitest-adb-crash-retry-device-recovery-ja.md)
以降は、再試行がデバイスの修復も強制するようになりました。シナリオが `preconditions.erase: true` を
宣言したときにだけ得られる修復です。iOS シミュレータのバックエンドでは `simctl shutdown`、`erase`、
`boot` を実行し、テスト対象のアプリを入れ直します。この準備そのものが失敗することもあり、そのとき
パイプラインは*降格*で応えます。デバイスの障害を捕まえ、erase を強制せずに同じデバイスをもう一度リース
し、シナリオを走らせます。降格が守っているのは実行全体です。障害をそのまま通せば再試行のループを抜け、
すべてのシナリオを打ち切って、すでに得られた判定まで捨ててしまうからです。

[BE-0363](../BE-0363-simctl-subprocess-timeout/BE-0363-simctl-subprocess-timeout-ja.md) は、一度きりの
`simctl` の呼び出しすべてに期限を与えます。したがって、応答しなくなった CoreSimulator（シミュレータの
デバイスを所有する macOS のサービス）は `simctl.DeviceTimeout` という名前のついた例外を投げます。
継続的インテグレーション（CI）のジョブ自身の `timeout-minutes` がジョブを打ち切るまで止まったままには
なりません。しかし降格の分岐は、この新しい型を他のデバイス障害と区別していません。`shutdown` に一度も
応えなかったデバイスが、拒否という形で応えたデバイスのために書かれた条件のまま再試行されます。

本項目は、降格の分岐に欠けているその区別を入れます。クラッシュ再試行のデバイス準備がタイムアウトしたら、
降格せずにそのシナリオ1つを名前のついた失敗で終わらせます。あわせて実行に印を残し、以降のシナリオが
同じ応答しないホストへ自分の試行を費やさないようにします。実行全体ではなくシナリオを終わらせることに意味があります。
すでに得られた判定がすべて残るからであり、それこそ降格がもともと守ろうとしていた性質だからです。この区別
を立てるには、プラットフォームに依らない障害の名前が必要です。パイプラインはバックエンドから独立して
おり、捕まえる例外に名前を付けるために iOS のバックエンドのモジュールを import するわけにはいきません。

## 動機

降格の理由は特定の障害についての主張であり、
[BE-0353](../BE-0353-xcuitest-adb-crash-retry-device-recovery/BE-0353-xcuitest-adb-crash-retry-device-recovery-ja.md)
はそれをはっきり書いています。「この試行が当たった障害は、実行全体の問題ではなくこの試行の問題にとどまる」。
`erase` を拒否したデバイスは応えています。その拒否は、1台のデバイスの1つの操作についての証拠であり、
シナリオは、erase の強制が入る前に受け取っていたはずの素の再起動を受ける値打ちがあります。一度も応えない
デバイスは、操作について何の証拠も出していません。出しているのは、あらゆる操作の背後にあるサービスが
応答をやめたという証拠だけです。その証拠の上で再試行することは、タイムアウトが否定した当のことを前提に
置く行いです。

2つの障害を同じに扱うと、2つの費用が生じます。深刻なのは2つ目です。1つ目は実時間の浪費です。降格された
リースは同じホストの同じ `simctl` の面へ入り直すため、自分の期限を使い切ってから同じように失敗します。
最初の期限がすでに確かめたことを、もう1つの期限を丸ごと払って学び直すことになります。

2つ目の費用は、その2度目の失敗が何をするかです。降格されたリースは強制した erase を落とします。それは、
XCUITest の環境がデバイスをコールドに準備せず、暖まったまま常駐している runner を再利用する条件の1つ
です。ただし、その再利用の経路は `simctl` と無縁ではありません。`simctl` を避けるのは健全性の確認だけ
です。`_healthy_resident_driver()` は `poll()` と、runner 自身のチャネル越しの期限つきの `/health` の
問い合わせにすぎません。その先の `_resume_warm` は、`_prepare_simulator(cold=False)` のアンインストール、
インストール、権限の書き込みを実行します。続いて `terminate`、`launch`、`openurl` も実行します。いずれも
[BE-0363](../BE-0363-simctl-subprocess-timeout/BE-0363-simctl-subprocess-timeout-ja.md) が縛る `simctl`
の呼び出しです。したがって降格されたリースの行き着く先は2つであり、本項目はそのどちらよりも優れています。
これらの呼び出しでもホストが応答しないなら、2度目のタイムアウトは `run_one` と `run_all` のあいだで誰も
捕まえない `device_errors.DeviceError` です。実行は打ち切られ、得られた判定はすべて失われます。降格が
避けようとしている当の費用を、期限1つ分あとで払うことになります。ホストが応えるなら、シナリオは最後
まで走ります。そして、`shutdown` に応えられなかった直後のホストで作られた `ok` か失敗を報告します。
判定はその事実を示さず、レポートにも残りません。第2の大原則である決定論優先は、この2つ目の行き先を許しません。
曖昧な結果は、機械がたまたま倒れた方向へ落ち着くのではなく、失敗するからです。

そのシナリオ1つを失敗させるだけでは足りません。応答しなくなった CoreSimulator はホストの性質であって、
たまたま出会ったシナリオの性質ではないからです。以降のシナリオはそれぞれ自分の最初のクラッシュに達し、
自分の erase を強制し、同じサービスに対して自分の期限を費やします。実行パイプラインには、この形の問題
のための仕組みがすでにあります。実行全体の復旧予算が拘束条件となってシナリオが失敗したときには、
以降のシナリオをリースの前に失敗させる印が立ちます。デバイスが復旧していないという本物の証拠だから
です。戻ってこなかった `simctl` の呼び出しは、同じ種類の証拠を、より早く、より直接に与えます。

パイプラインから見える場所に障害の名前を置くことは、細部ではなく前提です。`bajutsu/runner/pipeline.py`
は第3の大原則によりバックエンドから独立しています。プラットフォームはバックエンドの1つであり、決定論的な
中核は対象が変わっても変わりません。したがってパイプラインが捕まえるのは、
[BE-0260](../BE-0260-cli-bringup-consolidation/BE-0260-cli-bringup-consolidation-ja.md) がこの目的の
ために加えた共通の基底である `bajutsu/device_errors.DeviceError` です。`bajutsu/simctl.py` を import
することはありません。ところが
[BE-0363](../BE-0363-simctl-subprocess-timeout/BE-0363-simctl-subprocess-timeout-ja.md) が導入する
タイムアウトの型は iOS のバックエンドのモジュールにあります。つまりパイプラインには、その分離を壊さずに
「この障害はタイムアウトか」と問う手立てがありません。Android のバックエンドにも同じ形が控えています。
`bajutsu/adb.py` は iOS のものと並んで自前の `adb.DeviceError` を投げます。したがって、パイプラインが
タイムアウトに対して覚えたふるまいは、adb の呼び出しが自前の期限を持った日に Android のエミュレータへ
そのまま効くべきです。

## 詳細設計

作業は3つの単位に分かれます。単位2は単位1に、単位3は単位2に依存します。

1. **デバイスのタイムアウトに、プラットフォームに依らない名前を与える。** `bajutsu/device_errors.py`
   に `DeviceError` の派生として `DeviceTimeout` を加えます。各バックエンドが、デバイスの
   操作の失敗ではなく期限の超過に対して投げるものとして記述します。そのうえで `simctl.DeviceTimeout` に、
   `simctl.DeviceError` を第1の基底に残したまま、新しい型を第2の基底として与えます。iOS のタイムアウト
   は今日と同じ型のままです。`simctl.DeviceError` であり、それを通じて `device_errors.DeviceError` でも
   あります。そのうえで、プラットフォームに依らない名前を得ます。基底を置き換えるのではなく足すからこそ、既存の
   処理はすべてそのまま動きます。
   [BE-0363](../BE-0363-simctl-subprocess-timeout/BE-0363-simctl-subprocess-timeout-ja.md) が個別に
   検討した3つの群も同じです。`subprocess.CalledProcessError` だけを鍵にしているためタイムアウトを
   そのまま通す意図的な抑制、タイムアウトを文書化された代替の値へたたみ込む best-effort な読み取り、
   そして、すべてのシナリオが成功した実行がきちんと判定を報告できるようにタイムアウトを警告として吸収
   する teardown の防護がこれにあたります。

   `bajutsu/adb.py` には本項目では手を入れません。Android には配置すべきタイムアウトの型がありません。
   `_real_run` は `subprocess.run` に `timeout` を渡しておらず、今日はどの adb の呼び出しもタイムアウト
   を投げられないからです。adb の面を縛る作業は
   [BE-0363](../BE-0363-simctl-subprocess-timeout/BE-0363-simctl-subprocess-timeout-ja.md) の Android
   側の対応物であり、独自に計測した期限と、失敗を抑制している呼び出し箇所の洗い出しを伴う項目を必要と
   します（*検討した代替案*を参照）。生成元が1つのままここで中立な型を定めておくことが、のちの項目が
   その下に `adb.DeviceTimeout` を加え、パイプラインを1行も変えずに本項目の方針を引き継ぐための継ぎ目
   になります。

2. **タイムアウトした準備を降格させず、シナリオを失敗させる。** `bajutsu/runner/pipeline.py` の
   `_ScenarioRunner.run_one` は、erase を強制したリースの周りで `device_errors.DeviceError` を捕まえて
   素の再起動へ降格します。この処理を分けます。`device_errors.DeviceTimeout` は降格のリースをせず、
   それ以外のデバイス障害は今日と同じく降格します。拒否の側については何も変わっていないからです。

   シナリオの失敗は、再試行のループを抜けて `ok=False` の `RunResult` を返す形にします。失敗の文面は
   タイムアウトを名指しします。これは、シナリオが成功しないままクラッシュからの復旧が終わったときに
   `run_one` がすでに組み立てている形です。タイムアウトを `run_one` の外へ伝播させてはいけません。
   `run_one` と `run_all` のあいだに `device_errors.DeviceError` を捕まえる処理はないため、伝播は実行
   全体を打ち切り、すでに成功したシナリオの判定をすべて捨てます。それは
   [BE-0353](../BE-0353-xcuitest-adb-crash-retry-device-recovery/BE-0353-xcuitest-adb-crash-retry-device-recovery-ja.md)
   が払うことを拒んだ費用そのものであり、降格が存在する理由でもあります（伝播させる案は*検討した代替案*
   で単独に扱います）。

   ループがすでに行っている記帳はそのまま残します。シナリオ自身の復旧時間は再試行のループを囲む
   `finally` で計上され、進捗のコールバックが失敗を作業者へ報告します。ループを早く抜ける return は、
   その両方を迂回せず必ず通します。ただし、そのコールバックの文面は今日は固定の文
   （`(backend crashed mid-run)`）です。したがってタイムアウトの分岐は、失敗の文面だけでなくそこでも
   自前の文面を必要とします。失敗の文面には、コマンドと超えた期限を含めます。どちらも
   `bajutsu/simctl.py` の実行補助関数が投げる例外がすでに運んでいるため、レポートを読んだ作業者は、
   シナリオが理由の説明されない失敗をしたのではなく、ホストが応答しなくなったのだと知ることができます。

   この分岐は、エスカレーションされたリースも対象にします。それは意図したふるまいです。
   [BE-0354](../BE-0354-xcuitest-wedge-fastfail-device-replacement/BE-0354-xcuitest-wedge-fastfail-device-replacement-ja.md)
   は、繰り返しクラッシュした再試行を、強制した erase の上へ、プールが作成または複製する交換用の
   デバイスへとエスカレーションさせます。そうした試行も、強制した erase を載せたまま同じ処理に届きます。
   戻ってこない `simctl create` や `clone` は、戻ってこない `shutdown` と同じ応答しない状態なので、
   同じ扱いを受けます。シナリオは失敗し、実行に印が立ちます。その呼び出しからの `DeviceError` は今日
   どおり降格します。検証では、erase を強制した場合から一般化できると仮定せず、エスカレーションされた
   リースを独立した場合として覆います。

3. **準備がタイムアウトしたら実行に印を立てる。** `bajutsu/runner/recovery.py` の
   `RunCrashRecoveryBudget` にはすでに印があり、`bajutsu/runner/pipeline.py` はリースの前にそれを読んで
   います。`mark_given_up()` はこの実行で復旧を諦めたことを記録し、`given_up()` は、復旧していないと
   示したデバイスに対して最初のコールドな起動を丸ごと払わせる代わりに、以降のシナリオを最初のリースの
   前に失敗させます。単位2のタイムアウトの分岐からこの印を立て、応答しない状態を一度だけ確定させて、
   残りのシナリオそれぞれに見つけ直させないようにします。

   タイムアウトでは印を無条件に立てます。実行全体の予算が拘束条件だったときにだけ印を立てる経路とは
   異なります。予算は計測であり、遅いながらも成功した復旧でも越えうるため、その経路には条件が要ります。
   一方、戻ってこなかった `simctl` の呼び出しは遅さの計測ではなく、サービスが応答をやめたという直接の
   観測なので、条件は要りません。

   印の立った実行でシナリオが報告する文面は、今日は予算を名指ししています。しかしタイムアウトで印が
   立った実行に予算という原因はありません。`BAJUTSU_RUN_CRASH_RECOVERY_BUDGET` は未設定でありえます。
   その場合 `run_crash_budget.budget` は `None` であり、リース前の失敗はそれを `:g` で整形するため
   `TypeError` を `run_one` の外へ投げます。`run_all` は打ち切られ、実行が得ていた判定はすべて失われ
   ます。したがって、印に原因を持たせることは文面の問題ではなく正しさの要件です。そこで
   `mark_given_up()` に原因を渡し、印がそれを保持して `given_up()` を読む側が報告するようにします。リース前の失敗は、デバイスの
   操作がタイムアウトしたのか実行全体の予算を使い切ったのか、実際に起きたほうを述べます。印を増やさず
   1つに保つのは意図的です（*検討した代替案*を参照）。

検証はシミュレータを必要とせず、決定論的なゲートに収まります。パイプラインの既存のテストは、差し替えた
リースの呼び出し可能オブジェクトで `run_one` を動かしています。したがって、erase を強制した試行で
`simctl.DeviceTimeout` を投げるリースは、3つを一度に検証します。シナリオが失敗すること、降格の2度目の
リースが行われないこと、実行全体の印が立つことです。通常の `simctl.DeviceError` を投げるリースは、降格
が今日どおり起きることを検証します。交換用のデバイスのリースがタイムアウトするエスカレーションされた
試行も同じ3つを検証し、
[BE-0354](../BE-0354-xcuitest-wedge-fastfail-device-replacement/BE-0354-xcuitest-wedge-fastfail-device-replacement-ja.md)
の段のふるまいを推測ではなく固定します。最後の1つは、`BAJUTSU_RUN_CRASH_RECOVERY_BUDGET` が未設定の
まま印が立ったあとに走る2つ目のシナリオです。タイムアウトを原因として名指ししたまま、最初のリースの前
に失敗することを検証します。今日は `None` の予算を整形してしまう場合です。

## 検討した代替案

- **タイムアウトを `run_one` の外へ伝播させ、実行を打ち切る。** 本項目のきっかけになった指摘を字義
  どおり読んだ案です。降格が誤りなら降格をやめればよい、という形です。伝播が聞こえのうえで何を意味する
  かではなく実際に何をするかにより却下します。`run_one` と `run_all` のあいだに
  `device_errors.DeviceError` を捕まえる処理はないため、例外は `run_all` を抜け、実行は何も報告しません。
  当該のシナリオが失敗として報告されるのではなく、それ以前のすべてのシナリオがすでに得ていた判定が失われ
  ます。
  [BE-0353](../BE-0353-xcuitest-adb-crash-retry-device-recovery/BE-0353-xcuitest-adb-crash-retry-device-recovery-ja.md)
  が検討して拒んだ結末であり、タイムアウトだからといって以前のシナリオの判定が偽になるわけでもありません。
  シナリオ1つを失敗させて実行に印を立てる案は、同じだけ大きく速く診断可能な失敗を与えたうえで、それらの
  判定を残します。
- **降格を続け、実行全体の復旧予算に止めさせる。**
  [BE-0353](../BE-0353-xcuitest-adb-crash-retry-device-recovery/BE-0353-xcuitest-adb-crash-retry-device-recovery-ja.md)
  の予算は復旧に費やせる時間を縛るため、応答しないホストもいずれは捕まります。2つの理由で却下します。
  予算は既定で未設定であり、導入していないレーンでは何も縛りません。設定されている場合でも、止まるのは
  無駄な期限を使い切ったあとであり、そのあいだに暖まった runner の再利用の経路が、応答しないホストから
  判定を公表してしまいます。予算が縛るのは悪い結末をどれだけ被ってよいかであって、すでに手にした証拠に
  基づいてその結末に入らないと決めることとは違います。
- **シナリオの最初の、erase を強制しないリースでのタイムアウトにも同じ方針を適用する。** 応答しない
  ホストはどのリースが出会っても応答しないため、対称性の上では魅力があります。最初のリース自身の
  `device_errors.DeviceError` は今日 `run_all` の外へ伝播します。意図的に範囲外とします。それは通常の
  リースの経路の既存のふるまいであり、
  [BE-0353](../BE-0353-xcuitest-adb-crash-retry-device-recovery/BE-0353-xcuitest-adb-crash-retry-device-recovery-ja.md)
  も明示的に触れていません。変えれば、大きく失敗するという確立した経路を、タイムアウトだけでなくあらゆる
  デバイス障害についてシナリオ単位の失敗へ変えることになります。本項目の範囲は、erase を強制する再試行が
  加えた分岐です。そこでは降格が新しく、その根拠がタイムアウトを覆っていないことを示せます。通常のリース
  の経路が同じ扱いを求めるかどうかは、別の保証についての別の問いです。
- **本項目で adb の呼び出しも縛り、中立な型を生成元2つで出す。** 別の項目の作業に本項目の名前を着せる
  ことになるため却下します。`bajutsu/adb.py` はどこにも `timeout` を渡していません。期限を与える作業は
  3つあります。adb のコマンドの面に対して値を選ぶこと、失敗を抑制している呼び出し箇所をすべて洗い出す
  こと、best-effort な読み取りがタイムアウトで何を返すかを決めることです。
  [BE-0363](../BE-0363-simctl-subprocess-timeout/BE-0363-simctl-subprocess-timeout-ja.md) が `simctl`
  に対して行ったことの全体を、コマンドの費用がまだ計測されていないバックエンドで行うことになります。
  生成元が1つの中立な型に費用はかからず、のちの項目が差し込む継ぎ目になります。
- **準備がタイムアウトしたら、実行を諦めずに CoreSimulator を再起動する。** 応答しないサービスが呼び込む
  対処であり、そうした段が置かれる先は
  [BE-0344](../BE-0344-xcuitest-device-recovery/BE-0344-xcuitest-device-recovery-ja.md) の修復のはしご
  です。
  [BE-0363](../BE-0363-simctl-subprocess-timeout/BE-0363-simctl-subprocess-timeout-ja.md) が同じ対処を
  退けたときの理由により、ここでも却下します。これまで見直した失敗のなかに、再起動が狙うサービス水準の
  兆候を示すものはなく、期限のある呼び出しこそが、いずれそれをデータから決めるための前提です。本項目は、
  応答しない状態をパイプラインが行動の根拠にできる事実にします。それを修復する段は、ここで決めたことを
  見直さずにあとから加えられます。
- **タイムアウトの印を `RunCrashRecoveryBudget` ではなく新しいオブジェクトで持つ。** 応答しないホストは
  予算の関心事ではありません。`RunCrashRecoveryBudget` も記帳のための名前なので、整理としては筋が
  通ります。
  しかし、その持つ印はすでに記帳ではないため却下します。`given_up()` が答えるのは「この実行で復旧を
  諦めたか」であり、予算の使い切りは今日ただ1つの原因にすぎません。オブジェクトを増やせば、3つを自前で
  用意することになります。リース前の同じ確認での読み取り、`run_all` の並列の経路での排他、失敗の文面
  での居場所です。すでにある仕組みを3つ複製して、1つのフィールドに値を1つ足すのと同じことを表します。
  既存の印が記録する原因を広げれば、1つの問いに対する答えは1つのまま保てます。

## 進捗

> 作業の進行に合わせて最新の状態に保ってください。チェックリストは*詳細設計*の MECE な作業分解を
> 反映し（作業単位ごとに1つ）、ログには何がいつ変わったかを古い順に記録し、PR へリンクします。

- [ ] 単位1 — `device_errors.DeviceTimeout` を加える。`simctl.DeviceTimeout` に、`simctl.DeviceError`
      と並ぶ第2の基底としてその中立な型を与える。既存の処理と `bajutsu/adb.py` は変えない。
- [ ] 単位2 — `run_one` で erase を強制した準備を捕まえる処理を分ける。`device_errors.DeviceTimeout`
      は降格せず、名前のついた失敗と専用の進捗の文面でシナリオを終わらせ、それ以外のデバイス障害は
      今日どおり降格させる。同じ処理に届く BE-0354 の交換用デバイスのリースも対象に含める。
- [ ] 単位3 — その分岐から `mark_given_up()` で実行に印を立てる。印に原因を持たせ、未設定の予算を
      整形して `TypeError` を投げる代わりに、印の立った実行のシナリオがタイムアウトを報告するように
      する。
