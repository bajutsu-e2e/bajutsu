## はじめに

`http` ステップ（[BE-0036](../BE-0036-utility-steps/BE-0036-utility-steps-ja.md)）は、すでに
ランナーからリクエストを発行し、レスポンス本文全体を実行時変数として保存できます。この項目は
`extractBody` を追加します。`extractBody` は、同じステップに指定できる任意のリストです。JSON
レスポンスのパスを指定して、1つ以上のフィールドを取り出し、それぞれを `vars.*` へ直接格納します。
JSON のフィクスチャを取得するシナリオは、本文全体を保存する必要がなくなり、必要なフィールドの
名前だけを指定できます。

## 動機

テストデータ用サービスのレスポンスは、単一の値ではなく JSON オブジェクトであることが一般的です。
ログインエンドポイントは `{"data": {"token": "...", "user": {"id": 42}}}` のような形式を返し、
トークン単体は返しません。`saveBody` はそのオブジェクト全体をテキストとして保存するため、
`data.token` だけを必要とするシナリオでも、包んでいるオブジェクトへの対処が要ります。本文の中の
このフィールドには、現在どのステップも届きません。対処法は、サービスが提供しているとは限らない、
より狭いレスポンス形式を求めるか、必要なフィールドの取得をあきらめるかのどちらかです。`extractBody`
が実装されれば、シナリオは `http`
ステップから JSON API に直接アクセスし、ネストしたフィールドを `${vars.token}` へそのまま読み込め
ます。

## 詳細設計

`extractBody` は同じ `http` ステップ上で `saveBody` と並びます。ステップは、どちらか一方、両方、
またはどちらも指定しない形を取れます。

```yaml
- http:
    method: POST
    url: "${secrets.API}/login"
    body: '{"user": "e2e"}'
    status: 200
    extractBody:
      - { var: token, path: "data.token" }
      - { var: userId, path: "data.user.id" }
- type: { text: "${vars.token}", into: { id: auth.token } }
```

フィールドと契約：

- **`extractBody`**：`{ var, path }` のリストです。各エントリはレスポンス本文を JSON として
  解析し、`path` をたどった先の値を `vars.<var>` として保存します。文字列値はそのまま保存します。
  文字列以外の JSON の値は、次のいずれであっても `_json_text` と同じ形式で文字列化して保存します。
  この関数は `bajutsu/common/assertions/evaluate/_functions.py` にあります。同じ概念のために、
  2つ目の文字列化ルールを新たに定義することは、しません。

  - 数値
  - 真偽値
  - `null`
  - オブジェクト
  - 配列

  文字列化した例は `42`、`true`、`null`、`{"id":42}` です。こうすることで、後の `${vars.*}` の
  比較は、API が返した形そのままを読みます。`None` や `True` のような Python 固有の表記を読むこと
  は、ありません。
- **`path`**：オブジェクトのキーと `[n]`（0始まりの添字）を、任意の順序で任意の数だけ並べた列です。
  キーから始まるパスは、先頭にドットを付けずに書きます（`data.token`）。添字は、キーの直後
  （`items[0].id`）にも、別の添字の直後（`rows[0][1]`）にも続けられます。レスポンス本文自体が
  JSON の配列であれば、パスを添字から始められます（`[0].id`）。添字は0以上の10進整数です。`[-1]`
  は、Python のリストのように末尾から数える添字としては扱わず、不正なパスとします。負の添字や
  数値でない添字、空のセグメント（`a..b`）、末尾のドットを含む不正なパスは、`var` と `path` を
  示すエラーでステップを失敗させます。文法はここまでです。ワイルドカードやフィルタ、計算による
  セグメントは持ちません。BE-0036 は、任意のコマンドを実行する汎用 `shell`／`exec` ステップを、
  同じ理由で
  すでに退けています（BE-0036 の *検討した代替案* を参照）。小さく固定した文法なら、シナリオ
  ファイルだけを見て監査できますが、汎用の式言語ではそうはいきません。
- レスポンス本文が JSON として解析できない場合や、`path` が解決しない場合は、ステップを失敗させ
  ます。`path` が解決しない場合とは、次のいずれかです。
  - キーがありません。
  - 添字が範囲外です。
  - オブジェクト以外（配列、文字列、数値、真偽値、`null`）にキーを適用しました。
  - 配列以外（オブジェクト、文字列、数値、真偽値、`null`）に添字を適用しました。

  エラーには、解決できなかった `var` と `path` を含めます。シナリオが、求めたフィールドの代わりに
  空の値や置き換え値を読むことは、ありません。
- `extractBody` と `saveBody` は、同じレスポンス本文をそれぞれ独立に読みます。両方を指定すると、
  1回のリクエストで本文全体と指定したフィールドの両方を保存します。本文全体は `saveBody` の名前へ、
  指定したフィールドは `extractBody` の名前へ、それぞれ保存されます。`extractBody` のエントリ同士で
  `var` が重複した場合や、`var` が `saveBody` と同じ名前だった場合は、シナリオの読み込みエラーに
  します。書き込む順序が値を静かに決めることは、ありません。この検証はシナリオローダー自体で行い、
  `Step` のモデル検証としては行いません。モデル検証にすると、後述する置換後のステップでも再度
  発火し、ハンドラ自身によるきれいなステップ失敗の代わりに、捕捉されないエラーになります。
- 他のどのステップのフィールドとも同じく、`path` と `var` 自体にも `${vars.*}`／`${secrets.*}` の
  シナリオ変数置換を書けます。例えば `path: "items[${vars.i}].id"` のように書けます。ランナーは
  `url` や `saveBody` と同じように、`path` を解析する前にこのトークンを置換します。置換された値は
  1つのパス区分としてのみ扱い、新しいパス構造としては扱いません。`.`、`[`、`]` を含む値に置換
  された場合は、同じ不正なパスのエラーでステップを失敗させます。したがって、レスポンス本文から
  シナリオへ届いたフィールド名が、たどり先を別のフィールドへすり替えることは、できません。
  「計算によるセグメントは持ちません」の意味は、文法自体がレスポンス本文の中身を見て分岐しない
  ということです。シナリオが宣言した変数でフィールドをパラメータ化できない、という意味では
  ありません。パス文法の検証は、置換後のステップだけに適用し、読み込んだ時点のシナリオには
  適用しません。読み込み時の `path` には、まだ置換していない `${vars.*}` のトークンが残っている
  場合があるためです。上記のローダーレベルの `var` 重複検証は、置換後のステップにもあらためて
  適用します。置換して初めて現れる衝突は、実行時に、その `var` を示す同じエラーでステップを
  失敗させます。

prime directive の保持：

- **run パス上に LLM を置かない。** パスの解決は、解析済みの JSON をたどるだけの決定的な処理
  です。合否判定は、この処理だけから得られ、モデル呼び出しを経ません。
- **決定性。** 解析できない本文や、解決しないパスは、きれいなステップ失敗になります。黙った空の
  値や、近そうな別のフィールドで済ませることは、ありません。
- **アプリ非依存。** ステップとその文法はターゲットをまたいで同一です。異なるのは URL と JSON の
  形、シナリオが指定するパスだけです。

## 検討した代替案

- **JSONPath や JMESPath のような、フルの式文法を採用する。** どちらも、上記のドット／添字の
  文法を超えて、ワイルドカードやフィルタ、計算によるセグメントを使えます。ただし、どちらも本プロジェクト
  の直接依存ではありません。JMESPath は、任意の AWS 系 extras が引き込む `boto3`／`botocore` の
  推移的依存としてのみ存在し、JSONPath のライブラリはまったく入っていません。採用すれば、実際には
  固定した1つのフィールドしか指定しないシナリオのために、新しく直接依存するパーサを増やすことに
  なります。JSONPath や JMESPath は却下し、`extractBody` の小さな文法を採用します。ドット／添字の
  形で書けないパスが実際に必要になれば、フルの文法は再検討の対象として残ります。
- **`email` の `bodyMatches` 正規表現を、JSON パスの代わりに使う。**
  [BE-0046](../BE-0046-otp-email-steps/BE-0046-otp-email-steps-ja.md) の `email` ステップは、
  マッチしたメッセージの本文を正規表現で抽出します。同じ手段を `http` にも使えますが、シリアライズ
  された JSON への正規表現は、キーの並び順や空白の無害な変更だけで壊れます。ネストしたフィールド
  を取るには、レビュー担当がレスポンスの形と見比べて確認できない正規表現が要ります。`http` が
  対象とする典型的なサービスの形である JSON API に対しては、主たる抽出手段として却下します。
- **`saveBody` を拡張し、文字列か `{ var, path }` のリストかのどちらも取れるようにする。** 導入
  するフィールド名は減ります。ただし、渡す値の型によって形が変わる1つのフィールドは、独立した
  仕事を1つずつ持つ2つのフィールドより、検証しづらく読みづらくなります。`extractBody` を分けて
  おけば、既存の `saveBody: <name>` を使うシナリオも、変更なしで動き続けます。

- [ ] `http` ステップのシナリオモデルへ、`saveBody` と並ぶ形で `extractBody` フィールドを追加します。
      `extractBody` のエントリ同士で重複する `var` や、`saveBody` と衝突する `var` は、シナリオ

      エラーや不正なパス（`.`、`[`、`]` を含む値に置換された場合を含む）、未解決のパスはステップ
      失敗にします。解決した値が文字列でなければ、既存の `_json_text` ヘルパー
      （`bajutsu/common/assertions/evaluate/_functions.py`）で文字列化します。ローダーの `var` 重複
      検証を置換後のステップにも再度実行し、置換だけで現れる衝突をステップ失敗にします。
- [ ] `docs/scenarios.md`（`saveBody` の隣）と `docs/dsl-grammar.md` の `http` 生成規則へ
      `extractBody` を記載し、両方の `docs/ja/` 対訳も更新します。
- [ ] シナリオレベルのテストを追加します。対象は次のとおりです。
      - 解決できるネストしたフィールドです。
      - 配列添字から始まるパスと添字連鎖です。
      - 文字列以外の値です（`_json_text` による文字列化）。
      - ないキーと範囲外の添字です。
      - オブジェクト以外へのキー適用、または配列以外（文字列を含む）への添字適用です。
      - 不正なパス（負の添字）です。
      - JSON でない本文です。
      - 重複する `var` です。2つのエントリが同じ名前を持つ場合と、`saveBody` と衝突する場合の
        両方です。
      - `${vars.*}` で書いた `path` と `var` です。置換だけで現れる衝突と、`.`／`[`／`]` を含む
        値に置換される場合を含みます。
