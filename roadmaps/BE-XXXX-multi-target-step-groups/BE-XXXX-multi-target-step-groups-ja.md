## はじめに

[BE-0428](../BE-0428-multi-target-scenario-execution/BE-0428-multi-target-scenario-execution-ja.md)
は、1つのシナリオに2つ以上の`targets`を宣言できるようにしました。宣言した複数のターゲットに対して、
ステップを自由に行き来させて実行できます。各ステップは、自分がどのターゲットに対して実行されるかを
`target`で名指しします。

この提案は、その仕組みの上に1つの構文を追加します。**ターゲットグループ**です。ターゲットグループとは、
ターゲットを一度だけ名指しして、そのターゲットに対して実行するアクションをまとめて並べるステップです。
`target: <名前>`を1行ごとに繰り返す必要がなくなります。

```yaml
targets: [showcase-app, showcase-web]
steps:
  - target: showcase-app
    steps:
      - tap: { id: post.like }
      - wait: { for: { id: post.count }, timeout: 5 }

  - target: showcase-web
    steps:
      - assert:
          - value: { sel: { id: post.count }, equals: "1" }
```

ターゲットグループは、読み込み時に展開される純粋な記法上の糖衣構文です。新しい読み込み時のパスが、
バリデーションの前にターゲットグループを展開します。展開の結果は、BE-0428がすでに検証し実行している、
フラットな1ステップ1`target: <名前>`の形になります。

`bajutsu run`はターゲットグループを一度も目にしません。今日すでに扱っている形のシナリオだけを見ます。

この提案が変えるのは、シナリオのスキーマと、その読み込み時の展開だけです。Command Line Interface
（CLI）も、起動と終了処理の手順も、ランナーも、レポートも変わりません。BE-0428がすでに作ったこの4つを、
この提案はそのまま再利用します。

## 動機

シナリオが2つ以上の`targets`を宣言すると、すべてのステップが自分の`target`を設定しなければなりません。
これは`if`・`forEach`・`web`・`app`のラッパーにも及びます。単なる葉ノードのアクションだけの話では
ありません（[`docs/ja/scenarios.md`](../../docs/ja/scenarios.md)の`targets` / `target`節）。
この規則は`_check_target_requirements`が強制します
（[`bajutsu/common/scenario/models/scenario/_targets.py`](../../bajutsu/common/scenario/models/scenario/_targets.py)）。

BE-0428自身が挙げた2つ目の実例が、この規則の代償をそのまま示しています。仮想の例ではなく、実在する
2つのフィクスチャから組み立てた例です。10個の連続したステップが、`target: showcase-swiftui`か
`target: web`のどちらかを繰り返します。値が変わるのは、4ステップと6ステップの連続する区間ごとに1回
だけです
（[BE-0428、124〜148行目](../BE-0428-multi-target-scenario-execution/BE-0428-multi-target-scenario-execution-ja.md)）。
`expect`の中でさらに2回、同じ繰り返しが続きます（150〜152行目）。合計12行がターゲットを名指しして、
表しているのは2つのグループだけです。

この繰り返しは、正しさの欠陥ではありません。BE-0428のバリデーターは、誤ったターゲットや設定漏れを
すでに読み込み時に検出します。この繰り返しが生むのは、バグではなく手間です。`target:`という行は、
10個連続するステップのどれを見ても同じ値です。1行上にすでに見えている値を、もう一度書いているだけ
であり、新しい情報は運んでいません。その行が存在するのは、規則がそう要求しているからにすぎません。
diff の中でも、同じキーで始まる行が並ぶせいで、ステップ本来のアクションが埋もれます。同じターゲットが
続く区間の中で並べ替え・挿入・コピーをすると、`target:`だけがずれて食い違う事故が起きやすくなります。
バリデーターはその食い違いを検出しますが、それは著者がすでに間違え、気づいて直したあとの話です。
ターゲットグループは、この種の編集事故をまるごと取り除きます。著者はターゲットを一箇所に一度だけ
書きます。ネストしたステップ自身は`target`フィールドを持たないので、ずれようがありません。

この提案が実装されると、著者は同じターゲットが続く区間ごとに一度だけターゲットを書けばよくなります。
今日の規則では、ステップごとに一度書く必要があります。BE-0428自身の2つ目の実例も、10回ではなく
2回ターゲットを書くだけで済むようになります。

## 詳細設計

### 構文：`Step`に`steps`を追加する

`Step`に新しいフィールドを1つ追加します。`steps: list[Step] | None = None`です。BE-0428が
追加済みの`target: str | None = None`の隣に置きます
（[`bajutsu/common/scenario/models/steps/step.py:131`](../../bajutsu/common/scenario/models/steps/step.py)）。
`steps`を設定したステップは、ターゲットグループになります。ターゲットグループ自身はアクションを
持ちません。持つのは、ネストした普通のステップのリストだけです。

`Step`はすでに、`_MODIFIERS`以外のすべてのフィールドを、互いに排他的なアクションの1つとして扱って
います。この規則を強制しているのが`_exactly_one`です
（[`bajutsu/common/scenario/models/_base.py`](../../bajutsu/common/scenario/models/_base.py)）。
アクションの集合`_STEP_ACTIONS`は、`Step.model_fields`から計算されます
（[`bajutsu/common/scenario/models/steps/step.py`](../../bajutsu/common/scenario/models/steps/step.py)）。
`steps`は、`web`や`app`と同じやり方でこの集合に加わります。`_MODIFIERS`に含めないのです
（[`bajutsu/common/scenario/models/steps/_shared.py:8`](../../bajutsu/common/scenario/models/steps/_shared.py)）。
そのため、1つのステップで`steps`と`tap`や`wait`のような葉ノードのアクションを組み合わせることは
できません。

`target`は引き続き修飾フィールドのままです。葉ノードのアクションと組み合わせられるのと同じように、
`steps`とも組み合わせられます。

### グループには`target`を必須にし、それ以外の修飾フィールドを禁止する

葉ノードのアクションでは、シナリオが2つ以上のターゲットを宣言したときにだけ`target`が必須になります。
2つ未満なら、このフィールドは省略できます。これはBE-0428自身の規則です
（[`_check_target`](../../bajutsu/common/scenario/models/scenario/_targets.py)）。

ターゲットグループでは、シナリオがいくつターゲットを宣言していても、`target`を無条件に必須とします。
ターゲットグループの目的は、自分がまとめるステップのためにターゲットを一度だけ名指しすることです。
`target`を持たないターゲットグループは、その子ステップが代わりに何を実行対象とするかという、
独自の継承規則を必要とします。それは、この提案が採らなかった暗黙のデフォルトという設計に逆戻り
することを意味します（「検討した代替案」を参照）。この規則は`Step`自身が、新しい`model_validator`
の中で強制します。葉ノードのアクションにかかる規則と違い、この規則は囲むシナリオを参照する必要が
ありません。グループに`target`が必要かどうかは、シナリオが宣言するターゲットの数に左右されない
からです。

同じバリデーターは、ターゲットグループに対してさらに4つのフィールドを禁止します。`capture`・
`extract`・`name`・`from_`です。どれも、ランナーが実行する1つのステップから読み取られる修飾
フィールドです。スクリーンショットの取得、変数の抽出、レポート上のラベル、由来のメモがそれに
あたります。ターゲットグループは、ランナーまで届くことが一度もありません。後述する展開が、
シナリオの読み込みが終わる前に、ターゲットグループをその子ステップへ置き換えてしまうからです。
この4つのどれかをターゲットグループに設定すると、エラーや痕跡を残さず消えてしまいます。
これらを読み込み時に禁止しておけば、その静かな消失が、フィールド名を示す読み込み時エラーに
変わります。

### ネスト：グループの子は`target`を省略する、グループは`web:`・`app:`の中には置けない

ターゲットグループ自身の`steps`リストに直接ネストしたステップは、どんな種類のステップであっても
`target`を省略しなければなりません。葉ノードのアクションでも、`if`でも、`forEach`でも、`web`・
`app`ブロックでも同じです。ターゲットはすでにグループが固定しています。BE-0428は、`web:`や`app:`
の中にネストしたステップにも、すでに同じ形を採用しています。囲むブロックがすでにターゲットを
解決済みなので、そのステップも`target`を省略しなければなりません
（[`docs/ja/scenarios.md`](../../docs/ja/scenarios.md)の`targets` / `target`節）。ターゲット
グループは、この省略の規則を新たに作るのではなく、自分の子ステップにもそのまま広げます。子ステップ
が自分の`target`を設定してしまった場合は、読み込み時エラーになります。静かに上書きされることは
ありません。上書きを許すと、グループの奥深くにある1行だけが、周りのすべての行と違うターゲットを
指してしまいます。それこそが、グループが取り除こうとしている混乱そのものです（「検討した代替案」を
参照）。この規則は、ターゲットグループが別のターゲットグループの中にネストされるケースも、新しい
チェックを足さずに退けます。ネストしたグループは必ず自分の`target`を設定しますが、それこそが直接の
子ステップに禁止されていることだからです。

グループが子ステップに要求する省略は、浅いものであり、再帰しません。グループに直接ネストした`if`
や`forEach`は、自分の条件式についてはグループのターゲットを継承します。葉ノードのアクションと同じ
扱いです。しかし、その`then`・`else`・本体の中のステップは、別の新しいスコープです。それぞれが、
自分自身の明示的な`target`か、自分自身のターゲットグループを必要とします。グループの外にあるときと
同じです。グループに直接ネストした`web`・`app`ブロックも、同じようにグループのターゲットを継承し、
グループがすでに名指ししたターゲットに対してブリッジを開きます。そのブロックの中にネストしたステップ
は、BE-0428のもとの規則どおり`target`を省略し続けます。この規則はグループとは無関係です。

ターゲットグループは、`web:`や`app:`ブロック自身のネストしたステップの中に置くことを、無条件に
拒否します。それらのブロックの中では、すべてのステップがすでにブロック自身の解決したターゲットに
対して実行されます
（[`docs/ja/scenarios.md`](../../docs/ja/scenarios.md)の`targets` / `target`節）。そこにターゲット
グループを置いても、同じターゲットを無意味に繰り返すか、ドライバの開いていない別のターゲットを
指すかのどちらかにしかなりません。`if:`・`forEach:`にはこの制限がありません。`then`・`else`・
本体の中にターゲットグループをネストするのは、ごく普通のことです。それらは、他と変わらない普通の
ステップのリストだからです。

### 展開：ランタイムの仕組みではなく、読み込み時のパスとして実装する

この展開は、新しいパス`_expand_target_groups`が担います。既存の`_check_target_requirements`の隣、
[`bajutsu/common/scenario/models/scenario/_targets.py`](../../bajutsu/common/scenario/models/scenario/_targets.py)
に置きます。このパスは、シナリオの`steps`・`before`・`after`の各ルールの`steps`をたどります。`if`の
`then`/`else`と`forEach`の`steps`にも再帰します。`_check_target_requirements`自身が持つ`walk_steps`
ヘルパーと同じたどり方です。ターゲットグループに行き着くと、そのステップを自分の子ステップに置き換え、
グループの`target`を子ステップそれぞれにその場でスタンプします。`web`・`app`ブロックに行き着くと、
そのブロック自身のネストしたステップにも再帰します。このとき、`_check_target_requirements`がすでに
自分のたどり方に通している`inside_web`フラグを、同じように運びます。そこでターゲットグループを
見つけた場合だけは、上記のネスト規則どおりこのパスが拒否し、展開しません。このパスが終わったあとは、
シナリオのどこにもターゲットグループが残りません。生成されるステップはすべて、すでにスタンプ済みの
普通のステップであり、著者が手で書いたものと見分けがつきません。

`_check_target_requirements`は、今日すでに4か所で実行されています。あとの2か所は、検証済みの
`Scenario`をその場で書き換える処理です。pydanticは、プレーンな属性の書き換えに対しては
`model_validator`を再実行しません。そのため、この2か所はそれぞれ自分でこのチェックを呼び直して
います。

1. `Scenario`自身の読み込み時`model_validator`
   （[`bajutsu/common/scenario/models/scenario/scenario.py:159`](../../bajutsu/common/scenario/models/scenario/scenario.py)）。
2. `expand_components`が、`use:`コンポーネント自身のステップをつなぎ込んだ直後
   （[`bajutsu/common/scenario/expand.py:118`](../../bajutsu/common/scenario/expand.py)）。
3. `apply_setups`が、共有のセットアップの前段ステップを先頭に加えた直後
   （[`bajutsu/common/scenario/expand.py:236`](../../bajutsu/common/scenario/expand.py)）。
4. 設定レベルの`before`/`after`フックの折り込みが、`model_copy`でフックをつなぎ込んだ直後
   （[`bajutsu/common/runner/pipeline.py:1415`](../../bajutsu/common/runner/pipeline.py)）。

`_expand_target_groups`は、この4回の呼び出しそれぞれの直前に、もう一度実行されます。自分専用の
5つ目のチェックポイントを新しく足すのではありません。コンポーネントやセットアップの前段ステップも、
シナリオ自身のステップと同じようにターゲットグループを含みえます。だからこそ、つなぎ込んだばかりの
ステップリストをすでに再検証しているこの4か所こそが、先に展開しておくべき場所になります。展開を
先に済ませておけば、`_check_target_requirements`自身には変更が要りません。この関数がツリーをたどる
時点で、ターゲットグループはすでに消えています。グループから生まれたステップも、著者が手で書いた
ステップも、そのときにはまったく同じ形をしているので、同じ規則を同じやり方でチェックされます。

この順序のおかげで、既存のターゲット規則はすべてグループの子ステップにも適用されます。新しい
コードは1行も足しません。グループにネストした`use:`ステップは、展開されスタンプされたあとで、
BE-0428の既存の規則にかかります。この規則は、2つ以上のターゲットを宣言した場合に`use:`を拒否する
もので、手書きの`use:`ステップと同じようにかかります
（[`docs/ja/scenarios.md`](../../docs/ja/scenarios.md)の「制限」節）。宣言したターゲットが0個か1個
のシナリオでグループを使った場合も、既存のチェックにそのままかかります。「target is set but the
scenario declares no targets」、あるいは「target does not match the scenario's one declared
target」というチェックが、グループのスタンプ済みの子ステップそれぞれに対して働きます。手書きの
ステップにうっかり残った`target:`が今日失敗するのと同じ形です。

### 変わらないもの

ランナーとレポート、CLIには変更が要りません。`run_scenario`・`_run_one`・`StepOutcome`・
`RunResult`、そしてBE-0428が追加・変更したすべてのCLIフラグは、展開がすでに終わったあとのシナリオ
を読みます。どのステップがターゲットグループから来たのか、著者が最初からフラットに書いたのかを、
これらのどれも見分けられません。どれが見る時点でも、シナリオはすでにフラットなリストになっている
からです。`record`・`crawl`・`codegen`も、逆の理由で変わりません。これらが生成するものを、この
提案は何も変えません。今日と同じ、1ステップに1つの`target:`が並ぶフラットな形を生成し続けます。

### ドキュメント

[`docs/scenarios.md`](../../docs/scenarios.md)の`targets` / `target`節に、ターゲットグループの
構文と、そのネスト・省略の規則、実例を追加します。実例は、BE-0428自身の2つ目の例を、10回の繰り返し
の代わりに2つのグループへ書き換えたものがふさわしいでしょう。書き換えれば、削減の効果がそのまま
示せます。`docs/ja/`のミラーにも同じ内容を追加します。

## 検討した代替案

- **「直前のステップと同じターゲットを、明示しなければ引き継ぐ」という暗黙のデフォルト。**
  新しい構文をまったく足さない案です。`target`を省略したステップは、直前のステップが名指しした
  ターゲットをそのまま引き継ぎます。却下しました。あるステップのターゲットを確かめたい読者は、
  直前の明示的なターゲットを見つけるまでファイルを遡らなければなりません。挿入や並べ替えによって、
  あとのステップの引き継ぐターゲットが変わってしまうこともあります。そのステップ自身のどこにも、
  それが継承なのか宣言なのかを示す印がありません。BE-0428も、似た理由で近い案`switchTarget`を
  却下しています。`switchTarget`は、ステップ列全体を通して読者が追いかけなければならない命令的な
  ルーティング操作として読めてしまいます。そのステップ自身に見える性質にはなりません（BE-0428の
  「検討した代替案」）。この提案が、グループの子ステップにターゲットの上書きを許さない理由
  （「ネスト」節を参照）も、同じ反論を読み込み時のエラーという形にしたものです。ステップの実効的な
  ターゲットは、そのステップ自身から見えていなければなりません。
- **専用のラッパーキーワード。** `group:`や`section:`のように、`target`と`steps`を自分自身の
  フィールドとして持つ案です。`web:`が`within`と`steps`を持つのと同じ形になります。却下しました。
  `target`と`steps`が`Step`の上ですでに直接表せているアイデアに、もう1つ語彙を足すだけで、表現力
  は増えません。`target`をネストした`steps`リストと並べて書くだけで、すでに「このターゲットに、
  これらのステップを」と読めます。間にラッパーの名前を挟む必要はありません。
- **ランタイムに実在する仕組みとして実装する案。** `web`・`app`と同じように、実行を通してランナーと
  レポートが見る実在のノードとしてグループを残す案です。問題の大きさに対して不釣り合いだとして
  却下しました。BE-0428がランタイムの仕組みを必要としたのは、`web`・`app`が、他に代わりのない
  実在のドライバコンテキストを開くからです。ターゲットグループは、実行について何も変えません。
  同じ1ステップ1`target`を、何度も書く手間を省くだけです。だからこそ、読み込み時の展開だけで
  同じ記述上の利点が得られます。ランナー・レポート・CLI、そのどれにも触れずに済みます。
- **子ステップがグループのターゲットを上書きできるようにする案。** 完全な継承と完全な省略の中間
  を狙った案です。同じターゲットが続く区間の中の1ステップだけ、本当に必要なときに違うターゲットへ
  逸れられるようにします。却下しました。これでは、グループが取り除こうとしているあいまいさが
  そのまま戻ってきます。読者は、あるステップのターゲットを、グループ自身の見出し行から読み取れなく
  なります。編集の名残で残ってしまった上書きは、今日の「うっかり残った`target:`」と同じ形で失敗
  します。しかも、その失敗が起きるのは、まさにその種の間違いを二度と起こさせないはずだった場所です。
