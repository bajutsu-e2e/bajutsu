## はじめに

現状、文字入力を扱う[ステップ](../../docs/ja/glossary.md#シナリオのオーサリング)は、`type`（`bajutsu/orchestrator/actions/handlers/gestures.py`）だけです。`type` は、どのバックエンドでも `driver.type_text()` を通じて文字を追記します。シナリオでは、フィールドをクリアする、一部だけ削除する、テキストを選択する、選択内容をクリップボードへコピーするといった操作を、表現できません。

本項目は、この隙間を埋める 4 つのステップ、`select`、`clear`、`delete`、`copy` を追加します。4 つのステップは、既存の決定性モデルの枠内に収まります。

## 動機

実際のフォーム操作は、一度入力して終わりではありません。フィールドをクリアして入力し直す、打ち間違いをバックスペースで直す、値を選択して別の場所へコピーする、既存の値の一部だけを置き換える、といった操作が日常的に発生します。これらは、現状のシナリオでは表現できません。唯一の代替手段は、`tap` や `longPress` を、成否の定義もないまま無理やり組み合わせることです。これは、ドライバ抽象がそもそも排除しようとしている非決定性そのものです。

ここで陥りやすい設計上の罠は、「選択」を「いま何文字が選択されているか」という状態として扱うことです。ステップがその状態を設定し、後続のアサーションが検証できるようにする設計です。しかし、どのバックエンドも、選択範囲を問い合わせ可能な状態としては公開していません。

- `Element`（`DESIGN.md` §5）は `value` を持ちますが、選択範囲は持ちません。
- idb、adb、XCUITest のいずれにも、選択状態を取得する手段がありません。

選択を状態としてモデル化すると、`query()` では一切検証できない、バックエンド固有の新しい状態が必要になります。これは、決定性優先の方針（プライムディレクティブ 2）や、既存のセレクタ解決が守る「曖昧なら推測せず失敗する」という契約と衝突します。

そこで、`select`（および `copy`）は、**状態ではなく操作**として位置づけます。フィールドの内容とステップのパラメータが同じであれば、操作の結果は常に同じになるため、決定的です。**操作それ自体の結果を、アサーション対象にはしません。** 検証は、常に「その後に何が起きたか」に委ねます。

- 選択後に `type` で置き換えた結果は、既存の `value` アサーションで検証できます。
- `copy` は、BE-0052 がすでに実装したクリップボードの読み戻し（`expect: - clipboard: { equals | matches }`）で検証できます。

`clear` と `delete` には、新しいアサーションすら不要です。どちらも `value` に対するバックスペース相当の変更だからです。`value` は、すでに `Element` の一フィールドであり、既存の `Assertion` の一種（`bajutsu/scenario/models/assertions.py`）として、アサーションできます。

## 詳細設計

4 つの新しいステップは、既存の `type` と同じ形に沿います。`into` で対象フィールドを指定してから、ステップ自身の効果が実行されます。

```yaml
- select: { into: form.note, mode: all }   # フィールドの現在の内容を全選択する
- copy: {}                                  # 選択中の内容をクリップボードへコピーする
- clear: { into: form.note }                # フィールドの内容を全消去する
- delete: { into: form.note, count: 3 }     # 末尾から 3 文字削除する
```

- **`select`** は、本項目では `mode: all` のみをスコープとします。プラットフォームの「全選択」操作を実行します。iOS Simulator ではハードウェアキーの ⌘A に相当するキーイベント、Android では長押し ▸「すべて選択」、web では `Ctrl+A` やトリプルクリックです。単語単位や範囲単位の選択（`mode: word` やオフセット指定の範囲）は、意図的にスコープ外とします。
  - どのバックエンドも、ドラッグハンドルやカーソル位置を操作するプリミティブを、現状では公開していません。
  - 「単語」の境界の扱いは、ロケールや OS に依存します。
  - その結果、決定性を保ちにくい、大きな作業になります。具体的な要望が出た時点で、改めてスコープ化できます。
- **`copy`** は、現在選択されている内容に対して、プラットフォームの「コピー」操作を実行します。`select` が作った選択状態に作用するため、自身は対象セレクタを取りません。結果は、既存のクリップボード読み戻しで検証します。このステップは、新しい状態を導入しません。
  - **何も選択されていない場合**、`copy` は、そのステップを決定的に失敗させます。何も選択されていないのは、先行する `select` がない場合や、選択を解除するステップが挟まった場合です。`copy` は、黙って何もコピーしたり、クリップボードの以前の内容を残したりしません。
  - 選択のない「コピー」は、シナリオ記述上の誤りです。プライムディレクティブ 2 に従えば、後続のクリップボードアサーションが成功と誤読しかねない無言の no-op ではなく、失敗として表面化させる必要があります。
  - この判定は Bajutsu 側で行います。前回の選択解除以降に、選択が確立されたかを見ます。各バックエンドのネイティブなコピーが、空の選択に対して何をするかには委ねません。そのため、バックエンドをまたいで同じ失敗になります。
- **`clear`** は、指定したフィールドの内容を全消去します。`query()` がすでに返している `Element.value` から、現在の文字列が分かります。actuation は、決め打ちの回数ではなく、その文字列長ぶんだけ文字を除去します（バックスペース相当）。そのため、フィールドが何を保持していても対応できます。
- **`delete`** は、フィールドの現在の値の末尾から、`count` 文字を削除します。`clear` と同じバックスペース相当の仕組みを、より小さい回数に限定したものです。スクリプト化した打ち間違いの修正や、フィールド全体をクリアしない部分編集に使えます。

**バックエンドごとの actuation。** 具体的な実現方法は、実装時に確定させる、バックエンド固有の詳細とします。BE-0052 でも、4 つのプリミティブのうち 2 つが、実装時のトリアージで初めて実現可能な手段を見つけています。この経緯に倣います。検討すべき方向性は、次のとおりです。

- **idb。** `driver.type_text()`（`bajutsu/drivers/idb.py`）は、すでに `idb_companion` のテキスト gRPC 呼び出し経由で、フォーカス中のフィールドに届いています。制御文字（`\b` など）が、ハードウェアのバックスペースキーと同じ意味で解釈されるかは、実装時の検証が必要です。解釈されない場合の代替は、テキスト注入とは別の、companion の HID キーイベント呼び出しです。
- **adb。** 既存の `KEYCODE_BACK` 呼び出し（`bajutsu/adb.py`）と同じ経路で、`input keyevent KEYCODE_DEL`（67）を `count` 回実行します。`select` の「全選択」に対応する単一のキーイベントはなく、長押しのコンテキストメニュー経由になる見込みです。
- **XCUITest。** `type` が使っている HTTP トランスポート（`/type`）と同じ形を使います。同じ形の `/select` と `/copy`、または汎用の `/keyEvent` に相当するエンドポイントを、ランナー側（`BajutsuKit`）に追加できるか検討します。`XCUIElement` は、テキストの置き換えとキーボードのキーイベントの両方を、ネイティブに公開しています。
- **Playwright。** 最も素直に実現できるバックエンドです。
  - `clear` は `page.fill(selector, "")`
  - `delete` は `keyboard.press("Backspace")` の繰り返し
  - `select` は `selectText()` やトリプルクリック
  - `copy` は、クリップボード権限つきの `navigator.clipboard`（または `Ctrl+C` のキーイベント）

設計は、プライムディレクティブを保ちます。

- **決定性。** どのステップも、固定の変更です。バックスペース相当の回数、またはプラットフォームの全選択やコピー操作です。結果は、既存の `value` と `clipboard` のアサーションで、機械的に検証できます。新たに検証不能な状態を持ち込まず、`sleep` も LLM も使いません。
- **アプリ非依存。** アプリ固有のコードは不要です。`into` は、他のセレクタベースのステップと同じ方法で、対象を指定します。
- **codegen。** これらのステップには、XCUITest、Espresso、Playwright のネイティブ操作に、直接対応するものがあります。そのため、codegen は `// TODO` のスタブではなく、実際の呼び出しを出力できます（`simctl` にしか対応先がない BE-0052 のプリミティブとは異なる点です）。

## 検討した代替案

- **`select` を、問い合わせ可能な状態（`Element` 上の選択範囲）としてモデル化する。** 却下しました。どのバックエンドも、要素とクエリの表面から選択状態を公開していないため、それに対するアサーションは検証不能になります。これは、実装上の抜けではなく、決定性優先そのものへの違反です。
- **`select` と `copy` を 1 つの `copySelection` ステップにまとめる。** 検討しました。本項目が出荷するフローは、「全選択してからコピーする」だけだからです。それでも 2 つのステップに分けたのは、次の 2 つの理由によります。
  - 選択内容を使う他のアクションが加わると、`select` は単体で意味を持ちます。たとえば、選択中に `type` すると、選択内容が置き換わります。
  - `copy` を分けておくと、`type` の「`into` + 効果」という、既存の 1 ステップ 1 操作の慣習に沿います。この組み合わせだけを、特別扱いせずに済みます。
- **新しい `clear` ステップの代わりに、`type` に `mode: replace` や `clear: true` のような修飾子を足す。** 却下しました。`type` は `text` を必須とするため、「入力し直さずにクリアだけしたい」という意図を、空文字列に仮託することになります。「フォーカスする、任意でクリアする、任意で入力する」を 1 つのステップの修飾子に詰め込むと、シナリオとしても読みにくくなります。単一の役割を持つ小さなステップを順に並べるほうが、読みやすくなります。
