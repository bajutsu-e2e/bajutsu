## はじめに

`request` アサーションと `event` アサーションで、クエリ文字列と本文をキーと値の辞書で検査できるようにします。たとえば `query: { page: "2" }` や `body: { user: { id: "42" } }` と書きます。入れ子のフィールドは YAML の入れ子のマップでそのまま書くので、照合の記述が検査対象の JSON と同じ形になります。末端の値は、リテラル（テキストの完全一致）か、小さな演算子マップ（正規表現の `$matches`、存在を問う `$exists`）のどちらかです。両アサーションは1つの共通の照合関数を使います。変更はアサーション側に限り、`mocks` の文法は今のまま据え置きます。

## 動機

現在の `request` アサーションは、クエリ文字列と本文を正規表現でしか検査できません。`urlMatches: "page=2&sort=asc"` は、アプリがパラメーターの順序を入れ替えると壊れます。`bodyMatches: '"id":\s*42'` は、JSON が整形されたりキーの位置が動いたりすると壊れます。シナリオの作者が言いたいのは「リクエストが `page=2` を運んだ」ことなのに、直列化の形まで意識しなければなりません。

`event` アサーションには、すでにより扱いやすい形があります。`body: { name: purchase_completed, amount: "300" }` は JSON のリクエスト本文を解析し、キーの順序や空白に関係なく各キーをテキストとして比較します。ただし、この辞書が扱えるのは JSON 本文のトップレベルのキーだけで、比較は等価のみ、使えるのも `event` の中だけです。クエリ文字列には辞書の書き方がそもそもありません。

本項目は、`request` と `event` に、クエリパラメーターと本文フィールドを検査する共通の辞書文法を与えます。入れ子のフィールドは YAML の入れ子のマップで書き、完全一致では厳しすぎる値には正規表現や存在チェックを使えます。

実装後に確かめられる違いは、パラメーターの順序や JSON の整形が無害に変わってもシナリオが通り続けることです。エスケープした正規表現を `bodyMatches` に書いていた検査は、`body: { user: { id: "42" } }` で書けるようになります。エンドポイントに届いた候補のリクエストが1件のとき、失敗時のメッセージは `query.page: expected "2", got "3"` のように食い違ったキーを示します。一致しなかった正規表現を表示するより、作者に多くを伝えます。

## 詳細設計

本項目で加わる書き方を、次のシナリオにすべて含めました。

```yaml
expect:
  - request:
      method: POST
      path: /api/orders
      query: { page: "2", sort: { $matches: "^(asc|desc)$" } }
      body:
        user: { id: "42", email: { $exists: true } }
        items: [ { sku: A-1, qty: "1" } ]
        coupon: { $exists: false }
```

### フィールド

| フィールド | 対象 | 意味 |
|---|---|---|
| `query` | `request`、`event` | 各 `key: value` が URL のクエリ文字列について成り立つ必要があります。キーと値はどちらも URL デコードしてから比べます（`+` は `urllib.parse.parse_qs` と同じく空白として読みます）。値が空または値のないキー（`?debug`、`?page=`）も、`URLSearchParams` と同じく値 `""` を持つキーとして存在するとみなします（`parse_qs(..., keep_blank_values=True)`）。同じキーが繰り返し現れる場合は、いずれか1つが値を満たせば一致とします。 |
| `body` | `request`（新規）、`event`（拡張） | 各 `key: value` が、解析した JSON のリクエスト本文について成り立つ必要があります。入れ子のマップとリストは再帰的にたどります。 |

条件はすべて、既存のフィールドと AND で結合します。`bodyMatches` と `urlMatches` はそのまま動きます。`query` か `body` だけを指定した照合も条件を持つとみなすので、「条件が少なくとも1つ必要」という検証を通ります。`requestSequence`、`responseSchema.request`、`until: { request }` も同じ `RequestMatch` モデルと `match_request` を使うので、これらでも `query` と `body` を使えるようになります。テストとドキュメントもこれらを対象に含めます。

### 値の文法

照合の値は次の4つの形のどれかです。比べる相手は、取得した本文の同じ位置にある JSON の値です。

| 形 | 例 | 成り立つ条件 |
|---|---|---|
| スカラー | `id: "42"` | JSON の値のテキスト表現がスカラーと等しいとき |
| 演算子マップ | `id: { $matches: "^4" }` | すべての演算子が成り立つとき（後述） |
| 通常のマップ | `user: { id: "42" }` | JSON の値がオブジェクトで、列挙した各キーが再帰的に成り立つとき。列挙していないキーは無視します。 |
| リスト | `tags: [a, b]` | JSON の値が同じ長さの配列で、各要素が同じ位置の照合を満たすとき |

スカラーの比較は、今の `event.body` と同じです。`amount: "300"` は JSON の数値 `300` に一致し、真偽値と null は `true`、`false`、`null` として読みます。照合側のスカラーは、今の `event.body` と同じく YAML の文字列に限ります。引用符のない数値、真偽値、null（`qty: 1`）はロード時の検証エラーになるので、作者は引用符で囲みます（`qty: "1"`）。型を誤ったスカラーが黙って一致しなくなる事故を防ぐためです。真偽値を書くのは `$exists` 演算子だけです。

演算子は次の2つです。

- **`$matches: <正規表現>`**：JSON の値のテキスト表現が、正規表現に一致する部分を含む必要があります。`urlMatches` と同じ扱いです。
- **`$exists: <真偽値>`**：`true` は値を問わずキーが存在すること、`false` はキーが存在しないことを求めます。

空でなく、すべてのキーが単独の `$` で始まるマップを演算子マップとし、それ以外を通常のマップとします。`$$` で始まるキーは通常のキーとして扱います。`$` の接頭辞が両者を区別します。接頭辞がなければ、`{ matches: "x" }` が演算子なのか `matches` という名前の JSON フィールドなのかを決められません。名前が `$` で始まる JSON フィールドは、接頭辞を重ねて書きます（`$$ref` はフィールド `$ref` を検査します）。未知の演算子や、`$` で始まるキーと通常のキーを混ぜたマップは、シナリオの検証エラーにします。検証は、ほかの照合と同じくロード時に行います。`query` と `body` の直下のマップは常にキーの辞書として扱い、演算子マップにはしません。直下でも、名前が `$` で始まるフィールドは `$$x` のように書きます。`query` と `body` の直下に単独の `$` で始まるキーを書くと検証エラーになります。

`query` の値には、スカラーか演算子マップを書けます。クエリ文字列には入れ子がないので、`query` の下に通常のマップやリストを書くと検証エラーになります。

### 入れ子のマップとリスト

通常のマップは、JSON オブジェクトの部分集合を表します。列挙したキーはすべて成り立つ必要があり、照合に書かれていないキーは無視します。リストだけは例外で、要素ごとに照合します。したがって `[a, b]` は `[a, b, c]` に一致しません。長い配列のうち1つの要素だけを検査したい作者は、配列のテキスト表現に `$matches` を書くか、インデックス指定の書き方を後続の項目として求めることになります。

今の `event.body` の文法は、この文法の平坦な特殊例にあたります。そのため、既存の `event` シナリオの意味は変わりません。ただし、本文の直下で `$` から始まるキーは `$$` で書き直す必要があります。本文が JSON でない場合、オブジェクトでない場合、存在しない場合は、今の `event` と同じく `body` の条件がすべて不一致になります。フォームエンコードされた本文への `body` 条件は、本項目の範囲外です。

### 共通の照合関数とレポート

辞書の条件を1つの交換（exchange）に対して評価する純粋な関数を1つ用意し、`match_request` と `event` の計数処理の両方から呼びます。アサーションのラベルと、HTML レポートでの照合の表示（`richtext.py`）にも新しいフィールドを出します。失敗の詳細に食い違ったキーを示すのは、エンドポイントとメソッドの条件を満たす交換がちょうど1件のときに限ります。その場合は、最初に一致しなかったキーと、実際に観測した値を示します。その候補で辞書のキーがすべて成り立つ場合（失敗の原因が `status`、`bodyMatches`、または一対一の割り当てにある場合）は、今の件数のメッセージのままにします。候補が0件または複数件のときは、今の件数のメッセージのままにします。作者がどの候補を意図したかを推測して示すと、かえって誤解を招くからです。照合に `count` を指定した場合も、件数の不足は1つのキーでは説明できないので、今のメッセージのままです。値には `${vars.*}` や `${secrets.*}` のトークンを書けます。今の `event.body` と同じ扱いです。検証後の照合は作者が書いた文法のまま保持し（`$$` のエスケープは評価時にだけ外します）、`${...}` のトークンを置換するときのダンプと再検証（`orchestrator/substitution.py`）を経ても同じ照合に戻るようにします。この往復はテストで確かめます。

### モックとバックエンド

モックはアプリの内側でリクエストを照合します。iOS では `BajutsuMocks.swift`、Web では `web_network.py` が照合を受け持ちます。モックの `match` に `query` や `body` を書いても iOS の照合はそれを無視するので、モックが書いた内容より広く一致してしまいます。そこで `Mock` モデルは、両フィールドを明確な検証エラーで拒否します。モックへの対応は、Swift 側の照合とあわせて後続の項目で追加できます。

Playwright のコード生成は、`match_request` を JavaScript で再現しています。新しいフィールドを翻訳するか明示的に拒否するかしないと、生成したテストが条件を黙って落としてしまいます。文法が小さいので、本設計では翻訳します。JavaScript 側は、数値の書式も含めて、ランナーと同じ JSON の値のテキスト表現（`_json_text`）を再現する必要があります。両者が揃っていることはパリティテストで確かめます。

## 検討した代替案

- **正規表現（`urlMatches`、`bodyMatches`）を残し、書き方の例を文書化する案**：順序や整形の変化で壊れる性質が残るので採りません。意図もエスケープの陰に隠れたままです。
- **文字列の部分一致を見る `queryContains` と `bodyContains` を足す案**：キーを名指しできず、正規表現と同じ部分一致の弱さを繰り返すので採りません。
- **ドット区切りのパスをキーにする案（`user.id: "42"`）**：深い1つのフィールドを短く書けます。しかし JSON のキー自体にドットが含まれると壊れ、配列のインデックスにも専用の書き方が要ります。入れ子の YAML マップなら、作者がすでに書いている文法のまま JSON の形を写せるので、こちらを採ります。
- **JSONPath や JMESPath の式をキーにする案**：表現力が必要を超えているので採りません。新しい問い合わせ言語を入れると、学ぶ範囲と検証する範囲が広がります。
- **接頭辞のない演算子キー（`{ matches: ... }`）を使う案**：演算子と、`matches` という名前の JSON フィールドを区別できないので採らず、`$` の接頭辞を使います。
- **同じ変更でモックにも文法を適用する案**：Swift 側の実装と、バックエンド間で振る舞いが揃うことを確かめるテストが必要になります。アサーション側だけでも主な価値は届くので、モックは後続に回します。
- **`$in`、`$not`、`$gt` のような演算子を足す案**：演算子が増えるたびに、学ぶ文法と試験する範囲が増えます。集合は `$matches` で表せ（`^(a|b)$`）、不在は `$exists: false` で表せるので、小さな演算子の集合にとどめます。
