## はじめに

実行のパイプラインには、erase では回復しないところまで劣化した iOS Simulator から、シナリオを別のデバイスへ
移す仕組みがあります。次の起動時に交換用のデバイスを要求する形で、
[BE-0354](../BE-0354-xcuitest-wedge-fastfail-device-replacement/BE-0354-xcuitest-wedge-fastfail-device-replacement-ja.md)
が入れたものです。この昇格はクラッシュのハンドラの内部、`run_one` の `except BackendCrashError`
(`bajutsu/runner/pipeline.py:452`)だけに置かれているため、到達できるのは試行が**クラッシュした**
シナリオに限られます。respawn 後の試行が最後まで走り、通常のアサーションで失敗したシナリオは、
昇格に到達しません。昇格が読むのは、動画の録画で開始を確認できなかったという合図です。その合図が
その時点で立っていても、結果は変わりません。劣化したデバイスはそのままプールへ戻り、その実行の後続シナリオは
すべてそれを借ります。本提案は、通常の失敗の経路でも同じ合図を読み、その場でデバイスを隔離します。再実行は行わず、
どのシナリオの判定も変えません。失敗したシナリオは失敗のままで、合図が決めるのは、後続のシナリオに
**デバイス**を使わせ続けるかどうかだけです。

## 動機

劣化したデバイスは、いつもクラッシュという形で自分を明かすわけではありません。プルリクエスト
[#1556](https://github.com/bajutsu-e2e/bajutsu/pull/1556) の `actuation (xcuitest)` ジョブに、その一部始終が
記録されています。最初のシナリオは `GET /screenshot` のハングに2度当たり、チャネルの fast-fail と
パイプラインの respawn は設計どおりに働きました。そのうえで、respawn 後の試行は普通に走り、待機で
失敗しました。

```
step 1 (for_each): step 3 (wait): wait timeout: for {'id': ['horse.title', 'horse_title']} (20.0s)
```

健全なホストなら1秒足らずで終わる push 遷移に対して、20秒は長すぎます。同じジョブのログには、その理由が
10本のシナリオすべてについて1回ずつ残っています。

```
recordVideo produced no new bytes in runs/.../scenario.mp4 within 20.0s
```

この警告は、証跡レイヤーがすでに記録している動画開始の確認です。
[BE-0354](../BE-0354-xcuitest-wedge-fastfail-device-replacement/BE-0354-xcuitest-wedge-fastfail-device-replacement-ja.md)
は、まさにこの劣化を名指す合図として、これをリースに載せました。キャプチャのサービスが出力していないということは、
デバイスが描画もしていないということです。再試行が失敗した時点でこの合図は立っていましたが、その失敗が
クラッシュではなかったため、誰も読みませんでした。デバイスは交換されず、2本目から10本目までのシナリオは
そのデバイスの上で走りました。

ここから2つの損失が生じます。本提案はこの2つを別々に扱います。1つ目は、後続のシナリオがすべて、
すでに劣化していると分かっているデバイスを引き継ぐことです。1台の不調なデバイスが、ジョブ全体にわたる
信頼できない結果の連なりに変わるのは、これが原因です。本提案が直すのはこちらです。2つ目は、実行の判定が
シナリオを責めることです。`horse.title` の待機タイムアウトは、アプリまたはシナリオの欠陥として読めます。
デバイスが描画していなかったという証拠は同じログの中にありながら、両者を結ぶものがありません。本提案は
こちらについては、両者の結びつきを記録するにとどめます。これは意図した限定です。インフラ側の合図を根拠に
赤い判定を緑へ変えることは、本提案が決してしてはならない唯一のことだからです(*遵守する原則* を参照)。

## 詳細設計

### 現在は読まれずに捨てられている合図

`Lease.video_start_stalled()`(`bajutsu/runner/pool.py:290`)は、そのリースの動画録画が開始を確認できたか
どうかを、リースごとにすでに報告しています。`run_one` がこれを読むのは1箇所だけで、クラッシュのハンドラの
内部、強制 erase よりも交換の段を選ぶ場所です(`bajutsu/runner/pipeline.py:484`)。通常の経路、つまり
`return self._run_on_lease(lz, handler, i, s, sid)`(`bajutsu/runner/pipeline.py:451`)は、この合図を
参照せずにシナリオの `RunResult` を返します。

変更は、そこでも参照することです。結果を受け取り、シナリオが**成功しなかった**うえで合図が立っている
ときに、クラッシュのハンドラが要求したはずの交換を同じように要求し、結果はそのまま返します。

この条件は、クラッシュのハンドラがすでに計算している `can_replace` の判定
(`bajutsu/runner/pipeline.py:360`)の内側に置きます。オペレータの `--no-erase`、シナリオの
`reinstall: overwrite`、そして `device_replacement_supported`(`bajutsu/backends.py`)が定める
udid 固定の実行と `appPath` の除外は、そのまま適用されます。要求するかどうかは呼び出し側が判定します。
環境側が要求を再検査しなくて済むように、除外はすべて設定だけで決まる形になっているためです。そして、
この判定が保証するデバイス1台のプールこそが、後続のリースへ届く救済策を、その実行で唯一のデバイスへ着地させます。

### 再試行ではなく隔離

要求はリース自身の `request_device_replacement`(`bajutsu/runner/types.py:73`。環境側のメソッドとの
配線は `bajutsu/runner/pool.py:520`)を通します。
[BE-0354](../BE-0354-xcuitest-wedge-fastfail-device-replacement/BE-0354-xcuitest-wedge-fastfail-device-replacement-ja.md)
がすでに作った仕組みです。要求はその場では何も実行せず、記録だけを残します。応じるのは**次の**起動で、劣化した
デバイスをシャットダウンし、交換用のデバイスを作り、プールが保持しているものを新しい udid で付け直します。
失敗したシナリオについては何も変わりません。走ったデバイスも、証跡も、判定もそのままです。変わるのは、
そのあとのシナリオがどのデバイスを借りるかだけです。

対処が後続のリースへ着地するので、本提案は約束ではなく構造として判定から独立します。この合図から
再実行へ至る経路が存在しないため、合図を上げたシナリオの成否が変わる経路も存在しません。

### 失敗した判定を条件に含める理由

引き金は合図だけではありません。シナリオが失敗していることも条件です。成功したシナリオは、動画がどうで
あれ自動操作の経路が機能したことの証拠なので、その下でデバイスを交換するのは、うまくいっている実行に
デバイスを1台費やすことになります。両方を求めることで、デバイスの新規作成は、すでにうまくいっていない
実行に限られます。
[BE-0354](../BE-0354-xcuitest-wedge-fastfail-device-replacement/BE-0354-xcuitest-wedge-fastfail-device-replacement-ja.md)
が一度きりのクラッシュに対して erase の段を先に置くときの抑制と同じ考え方であり、
[BE-0344](../BE-0344-xcuitest-device-recovery/BE-0344-xcuitest-device-recovery-ja.md) が、
`bajutsu-recovered-*` デバイスが開発者の Mac に残す痕跡を検討した理由でもあります。

同じ理由で、許容量にも上限が要ります。ただし、BE-0354 のシナリオ単位の許容量が抑えるのは1本のシナリオが
作れる台数だけなので、その下でも慢性的に止まるホストは失敗したシナリオごとに1台ずつ作ります。シナリオ
単位の上限で実際に足りるのか、この経路には実行単位の上限が要るのかを、Unit 0 で決めます。

### Unit 0 が先に確かめること

`_run_on_lease` は自身の `finally` でリースを解放するため、その `RunResult` が `run_one` に戻る時点では
リースがすでに解放されている場合があります。`request_device_replacement()` は、その背後でプールが保持する
環境にフラグを立てます。解放の後に出す要求は、`Lease` がもともと想定している呼び出し方です。プール側には、
どちらの呼び出しもリースの解放後にクラッシュ再試行から読まれ、ウォームな環境が要求を次の起動まで運ぶことが
記録されています(`bajutsu/runner/pool.py:516`)。この経路で異なるのは間隔です。次の起動は後続の
シナリオのものなので、BE-0354 が要求の取りこぼしとして受け入れている退去の窓(`end_lease` の失敗、
次のシナリオによる actuator の切り替え)が開く時間も長くなります。要求がこの間隔を実際に生き延びるかを
レーン上で確かめ、許容量の問いとあわせて、Units 1 と 2 が実装を始める前に Unit 0 で決めます。

### 作業分解(`MECE`)

相互に排他的で網羅的(Mutually Exclusive, Collectively Exhaustive、`MECE`)な作業の単位は次のとおりです。

0. **スパイク。** `_run_on_lease` がリースを解放したあとに出した交換の要求が、シナリオ間の間隔を越えて
   次の起動まで生き延びるかを、レーン上で確認します。この経路が消費する許容量(BE-0354 のシナリオ単位の
   ものか、実行単位の上限か)も決めます。どちらの知見も上の *詳細設計* に記録します。Units 1 と 2 を
   ブロックします。
1. **隔離。** `run_one` の通常の失敗の経路で `video_start_stalled()` を読み、シナリオが成功しなかった、
   かつ `can_replace` が成り立つときに交換を要求します。上限は Unit 0 の決定に従います。再実行はせず、
   判定も変えません。
2. **結びつきの記録。** 失敗したシナリオ自身の診断に、立っていた合図を出します。結果を読む人が、
   無関係に見える2つのログ行を自分で突き合わせなくても、デバイスが疑わしい理由を見られるようにします。
3. **テスト。** パイプラインのテストを分岐ごとに1つずつ用意します。合図が立った状態で失敗したシナリオは
   交換を要求すること、同じ合図でも成功したシナリオは要求しないこと、合図のない失敗も要求しないこと、
   そして失敗したシナリオの判定がどちらの場合もまったく同一であること。最後のものが、判定への中立性を
   固定する回帰テストです。
4. **ドキュメント。** [`docs/architecture.md`](../../docs/architecture.md) と
   [`docs/run-loop.md`](../../docs/run-loop.md)、およびその `docs/ja/` 側を更新します。どちらの
   ページも現在は、合図をクラッシュ再試行の段の選択としてだけ記述しています。この合図が通常の失敗でも
   デバイスを隔離すること、シナリオの再実行も判定の変更も行わないことを明記します。BE-0113 の規範に
   従い、Unit 1 と同じ変更で入れます。

### 遵守する原則

- **AI は判定しない。** 合図は動画の録画について記録された事実であり、それを読むのは決定的なコードです。
  この値を作る経路と読む経路のどちらにも、モデルの呼び出しは入りません。
- **決定性を最優先する。** 本設計を形作った軸がこれです。ここで赤い判定が緑になることはありません。
  何も再実行せず、失敗したシナリオの結果はそのまま返します。合図が決めるのは後続のシナリオがどのデバイスを
  借りるかだけで、これは判定ではなく割り当ての決定です。
- **アプリに依存しない。** 条件が読むのはパイプライン自身のリース単位の合図であり、アプリごとの分岐は
  ありません。交換に応じられないバックエンド(`device_replacement_supported` が除外する経路で、現状は
  Simulator の XCUITest 以外のすべて)は影響を受けません。

## 検討した代替案

- **失敗したシナリオを交換用デバイスで再実行する。** 誤った判定を記録するだけでなく実際に正す変更は
  これであり、本提案が拒否するのもこれです。自身のアサーションで失敗したシナリオは正直な判定を出して
  います。インフラ側の合図がたまたま立っていたことを理由に再実行するのは、赤から緑への経路であり、
  [`DESIGN.md`](../../DESIGN.md) の決定性の原則が禁じるものです。しかも、本当に不安定なアプリを、
  ツールがそれを暴くべきまさにその場所で覆い隠します。保留ではなく、意図して外します。
- **判定にかかわらず、合図が立っていれば隔離する。** 記述は単純になり、成功したシナリオの最中に劣化して
  次のシナリオだけを傷つけるデバイスも捕まえられます。デバイス作成の費用のため却下します。慢性的に止まる
  ホストでは毎シナリオ後の交換になってしまいます。また、成功したシナリオは自動操作の経路がまだ機能して
  いる証拠でもあります。成功したシナリオの下で合図が立つことは稀だと Unit 0 の実測が示した場合は、再考する
  価値があります。
- **再試行の通常の失敗をクラッシュとして扱い、既存のハンドラに昇格させる。** 昇格をそのまま再利用でき、
  新しい呼び出し箇所も要りません。ハンドラが前提としている区別を壊すため却下します。
  `BackendCrashError` は「リースが死んでおり、シナリオは判定を得られなかった」を意味するのに対し、
  待機のタイムアウトは「シナリオが走って答えを出した」を意味します。両者をひとまとめにすると、通常の
  失敗がすべてクラッシュ回復を通り、正直に失敗したシナリオを再実行することになります。これは最初の
  代替案に別の道から行き着いたものです。
- **待機のタイムアウトを延ばして、遅いデバイスでも成功させる。** 失敗した20秒の待機は、1秒足らずの遷移に
  対してすでに十分な長さです。これ以上長くしても、得られるのは情報ではなく沈黙です。
  [BE-0354](../BE-0354-xcuitest-wedge-fastfail-device-replacement/BE-0354-xcuitest-wedge-fastfail-device-replacement-ja.md)
  と [BE-0344](../BE-0344-xcuitest-device-recovery/BE-0344-xcuitest-device-recovery-ja.md) が
  それぞれの予算について実測したのと同じ取引であり、本提案が対処しようとしている劣化を隠してしまいます。
- **同じ隔離を Android エミュレータへ広げる。** adb バックエンドも動画の開始は確認しており
  (`start_screenrecord` がデバイス側のプロセスを待つため、リースは合図を報告できます)、欠けているのは
  対処の側です。エミュレータや実機は外部で起動されるため、`request_device_replacement` はそこでは何も
  行いません(`bajutsu/platform_lifecycle/environments/android.py`)。
  [BE-0353](../BE-0353-xcuitest-adb-crash-retry-device-recovery/BE-0353-xcuitest-adb-crash-retry-device-recovery-ja.md)
  がエミュレータのプロセス再起動を先送りしたときのままです。
