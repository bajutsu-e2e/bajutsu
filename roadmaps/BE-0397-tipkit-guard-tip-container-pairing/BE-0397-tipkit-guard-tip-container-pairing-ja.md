## はじめに

Apple の TipKit は popover 形式の tip を表示し、その tip がシナリオの操作対象を覆うことがあります。
[BE-0389](../BE-0389-ios-native-tipkit-guard/BE-0389-ios-native-tipkit-guard-ja.md) は、この tip を
検知して閉じる opt-in のガードを iOS の XCUITest バックエンドに追加しました。ガードが手がかりに
しているのは 1 つだけです。popover の表示に伴って現れる、画面全体を覆う「外側をタップして閉じる」
ための領域、アクセシビリティ識別子 `PopoverDismissRegion` を持つノードです。BE-0389 は、この識別子が
TipKit だけのものかどうかを確かめきれないまま、実際に衝突が見つかったときに実施する追加作業として、
本提案が行う絞り込みを名指ししていました。衝突は実際に見つかり、しかも BE-0389 が想定していた特殊な
ケースではありませんでした。SwiftUI の `confirmationDialog`、つまりアプリが「削除しますか」と尋ねる
ごく普通の手段でした。この確認ダイアログは、同じ識別子と同じ全画面のフレームを持つ、まったく同一の
領域を設置します。本提案は、
この領域に tip 自身のコンテナ `TipView` を組み合わせます。ガードが TipKit の tip を判定する手がかりを
1 つではなく 2 つのノードにして、それ以外の popover には手を触れないようにします。

## 動機

ガードは領域をタップして tip を閉じるので、そのタップは領域の持ち主が何であれ、その持ち主を閉じます。
領域の持ち主が tip ではなくアプリ自身の確認ダイアログだった場合、ガードはシナリオがこれから操作する
はずのダイアログを閉じてしまいます。続くステップは目的のボタンを見つけられずに失敗し、実行結果には
ボタンを消した閉じる操作ではなく、要素が見つからないという理由が残ります。orchestrator がドライバから
受け取るのは真偽値だけなので、失敗理由にはガードの名前も `PopoverDismissRegion` という識別子も現れま
せん。

衝突を裏づけたのは推論ではなく実測です。showcase アプリに対する Simulator の実行で 3 つの状態の
アクセシビリティツリーを採取したところ、3 つはきれいに分かれました。

| 画面の状態 | `PopoverDismissRegion` | `TipView` |
|---|---|---|
| TipKit の tip、SwiftUI の `.popoverTip` | あり。ラベルは "dismiss popup"、フレームは `[0, 0, 402, 874]` | **あり** |
| TipKit の tip、UIKit の `TipUIPopoverViewController` | あり。ラベルもフレームも同一 | **あり** |
| SwiftUI の `confirmationDialog` | あり。ラベルもフレームも同一 | なし |
| 長押しで出るネイティブの編集メニュー | なし | なし |

この表からは、衝突そのもの以外に 2 つの事実が読み取れます。1 つは、確認ダイアログの設置する領域と
tip の領域が似ているどころではないという事実です。ラベルとフレームが完全に一致するため、領域ノード
自身のどの属性を見ても 2 つのケースは区別できず、区別できるのは別のノードだけです。もう 1 つは、
長押しで出るネイティブの編集メニュー（Paste、Select、Select All、AutoFill）がこの領域をそもそも
設置しないという事実です。編集メニューのノードは識別子とラベルのどちらも持たないため、編集メニューが
ガードを起動することはなく、tip と区別する必要もはじめからありませんでした。

衝突の影響はガードの外にも及びます。同じ識別子は、
[`interrupts`](../BE-0314-scenario-interrupt-handlers/BE-0314-scenario-interrupt-handlers-ja.md)
のエントリを手で書くとき、真っ先に思いつく手がかりでもあるからです。tip を閉じるつもりで
`condition: { exists: { id: PopoverDismissRegion } }` を書くとします。できあがったエントリは、
アプリ自身の確認ダイアログにも反応します。しかもシナリオの DSL には、この条件を絞る手立てがありません。
`Assertion` は 1 つの条件につき 1 種類しか許さないので、「かつ tip のコンテナがある」を足す論理積が
書けません。target の設定から引き継いだエントリを、シナリオ側で無効にする手立てもありません。手がかりに
すべき条件が `TipView` であるとドキュメントに書けば、コードを変えずに手書きのエントリからこの罠を
取り除けます。そこで本提案は、ドライバの変更とあわせてドキュメントの修正も行います。

本提案が実装されたかどうかは、実機での観察 1 つで判別できます。`iosTipKitHandling` を有効にした
シナリオが確認ダイアログを開き、そのダイアログ自身のボタンを検査したときに、ボタンがまだそこに
あります。変更前は、ガードがダイアログを閉じてしまい、検査は要素が見つからずに失敗します。

## 詳細設計

作業はドライバ側の絞り込み、それを固定する実機のフィクスチャ、ユニットテスト、ドキュメントの修正に
分かれます。

1. **ドライバで領域と tip のコンテナを組み合わせる。**
   [`bajutsu/drivers/xcuitest.py`](../../bajutsu/drivers/xcuitest.py) の
   `dismiss_blocking_tip()` は現在、`PopoverDismissRegion` があれば tip が出ていると判断しています。
   これを改め、`PopoverDismissRegion` と `TipView` の両方があるときにだけ tip と判断し、領域しか
   ないときはタップもエラーもなしに `False` を返します。タップする対象は変わりません。BE-0389 が定めた
   とおり領域が閉じる対象のままで、コンテナは検知のための手がかりにとどまります。BE-0389 はこれを
   計測せずに述べていたので、本提案で計測しました。`TipView` をタップしても tip は残り、ツリーは
   29 要素のままでコンテナと領域のどちらも消えません。閉じるボタンをタップすると tip は片付き、
   ツリーは 118 要素に戻ります。コンテナは tip を見つけるためには使え、閉じるためには使えません。呼び出し元のツリーによる早期判定と、取得し直したツリーに対する再確認の
   どちらもこの組み合わせで判定するので、確認ダイアログが出ている画面の問い合わせ回数は、tip の
   ない画面と変わりません。`resolve_unique` が守るのは引き続き領域だけです。領域が複数ある状態は
   TipKit が作らないはずの形なので、1 つを選ばずに大きく失敗させます（原則 2）。一方コンテナは存在の
   有無だけを見ます。アプリが 1 つのツリーに複数の tip コンテナを正当に表示することはありえますし、
   ガードが必要としているのは個数ではないからです。

   この絞り込みが裏目に出る道筋として真っ先に思い浮かぶのは、本物の tip を取りこぼすことです。
   計測は、その道筋を議論で回避するのではなく実際に閉じます。`TipView` を生成するのは SwiftUI の
   `.popoverTip` です。そこで、UIKit のアプリが `TipUIPopoverViewController` で表示する tip は別に
   確かめる価値があります。SwiftUI 自身のビューのコードでしか付かないコンテナ名であれば、UIKit がホストする
   tip はすべて認識されなくなるからです。実機で計測したところ、UIKit がホストする tip も `TipView`
   を持っていました。同じ `PopoverDismissRegion` の scrim と同じ `xmark.circle.fill` の閉じるボタンも
   伴います（前掲の表に記録しました）。このコンテナは SwiftUI のラッパーではなく TipKit 自身のもので
   あり、組み合わせは両方のホストで成立します。

   同じ計測は、作者が代わりに立てそうな別の問いにも答えます。アプリが自分の tip へ名前を付ければ、
   内部の識別子に頼らず済むのではないかという問いです。答えは、いちばん効いてほしい側では
   できないというものでした。UIKit のアプリは popover のコントローラのビューへ
   `accessibilityIdentifier` を設定でき、その名前はツリーにも届きます。ただし `TipView` を置き換える
   のではなく、それを包む独立したノードとして現れます。SwiftUI はそうした取っ手を与えません。
   `.popoverTip` へ `.accessibilityIdentifier` を付けるとアンカー側が装飾されるだけです。tip 自身の
   表示はフレームワークのものなので、その識別子は tip のツリーにまったく現れません。アプリが与える
   名前は、必要のない側でだけ手に入ります。だからガードは TipKit 自身のコンテナを手がかりにします。

2. **手を触れてはいけないケースを固定する実機のフィクスチャ。** showcase アプリには現在、本物の
   確認ダイアログがありません。Log タブのアクションシートは `ZStack` のオーバーレイで組まれています。
   SwiftUI の `confirmationDialog` はボタンのアクセシビリティ要素を重複して生成するため、一意に
   タップするフィクスチャとして使えません。オーバーレイはその理由で選ばれた形です。検知の確認に一意なタップは要ら
   ないので、一意にタップするフィクスチャになれない `confirmationDialog` でも、本提案のフィクスチャには
   なれます。
   [`demos/showcase/ios/swiftui/Sources/LogView.swift`](../../demos/showcase/ios/swiftui/Sources/LogView.swift)
   に専用のボタンを添えて 1 つ追加し、ガードを有効にしてダイアログを開き、ダイアログ自身のボタンが
   まだあることを確かめるシナリオを
   [`demos/showcase/scenarios/tipkit.yaml`](../../demos/showcase/scenarios/tipkit.yaml) に追加します。
   反対方向、つまり閉じるべき tip と、シナリオが opt-in していないときに残すべき tip は、既存の
   tipkit のシナリオがすでに押さえています。しかも 3 本目のシナリオは `TipView` を名指しで待って
   おり、本設計が手がかりにするコンテナがツリーに確実に現れることの実機での裏づけになっています。

3. **組み合わせの両側を押さえるユニットテスト。** TipKit 内部の識別子は XCUITest ドライバの中にしか
   置かないので、組み合わせを固定する場所は
   [`tests/test_xcuitest.py`](../../tests/test_xcuitest.py) です。両方のノードを含むツリーでは
   これまでどおり閉じること、領域しかないツリーでは閉じずタップも発行しないこと、呼び出し元の
   ツリーによる早期判定が領域だけのツリーを問い合わせなしで除外することを確かめます。
   [`bajutsu/drivers/fake.py`](../../bajutsu/drivers/fake.py) の fake ドライバは、iOS の識別子を
   自前で持たずテストがツリーに入れた識別子を受け取る作りなので、コンテナ用の識別子を受け取る口を
   1 つ増やします。[`tests/orchestrator/test_tipkit_guard.py`](../../tests/orchestrator/test_tipkit_guard.py)
   の orchestrator 側のテストは、その両方を渡すようにします。

4. **ドキュメントを修正し、手がかりにすべき条件を明示する。**
   [`docs/scenarios.md`](../../docs/scenarios.md) は TipKit の tip を、アプリがセレクタを与えられ
   ないフレームワーク所有の popover であり、`interrupts` のエントリでは名指しできないものと説明して
   います。この説明は、本提案にとって見過ごせない形で誤っています。tip のノードは安定した識別子を
   持っており、`interrupts` のエントリで名指しできます。そして領域だけを手がかりにしたエントリこそ、
   本提案が書き残そうとしている罠そのものです。この説明を事実に置き換えます。すなわち、ガードが
   あるのはシナリオごとに同じ回避策を手で書かずに済ませるためであり、あえて手で書く作者は
   `PopoverDismissRegion` ではなく `TipView` を手がかりにします。同じ修正を `docs/ja/scenarios.md`
   にも反映し、ガードを 1 行で説明する
   [`docs/architecture.md`](../../docs/architecture.md) とその日本語版も、領域だけを手がかりとして
   挙げている記述を直します。

## 検討した代替案

- **opt-in なのだから、ガードを現状のままにする。** 採用しません。opt-in が限定するのは誰が影響を
  受けるかであって、影響を受けた側に何が起きるかではありません。tip を閉じるために opt-in した
  シナリオは、自分の確認ダイアログを閉じられることまで同意したわけではありません。しかも、そのとき出る
  失敗は、原因である閉じる操作ではなく要素の欠落を理由として報告します。BE-0389 がこのリスクを
  受け入れたのは、再現できなかったという根拠に基づいていました。前掲の実測はその根拠を取り除きます。

- **コンテナではなく閉じるボタン（`xmark.circle.fill`）を手がかりにする。** 採用しません。理由は
  BE-0389 がすでに述べています。この識別子は SF Symbol の名前であり、アプリ側が書いた無関係な
  ボタンで同じ名前を使うことは十分ありえて、ガード自身の探索が `AmbiguousSelector` になります。
  `TipView` は TipKit 内部のコンテナ名であり、そうした別の使われ方をしません。

- **tip を特定するのではなく衝突を除外する。つまり `sheet` の trait を持つノードが同じツリーに
  あるときは領域を無視する。** 採用しません。除外する方式は、アプリが表示しうる popover を
  すべて数え上げる必要があります。ここで実測した確認ダイアログは 1 つの事例であって、問題の
  境界ではありません。次の衝突が見つかれば、また 1 つ足すことになります。tip 自身のコンテナを
  求める方式はガードの目的そのものを言い表すので、数え上げていない popover はデフォルトで手つかずの
  まま残ります。

- **絞り込むのではなくガードそのものをやめる。手書きの `interrupts` エントリが同じ仕事をするため。**
  本提案の範囲外ですが、見た目より筋の通る話なので明記します。BE-0389 のスパイク自身が、
  `tap: { id: "PopoverDismissRegion" }` というステップだけで tip が閉じたと記録しています。
  新しいコードは一切足していません。しかも `interrupts` のエントリは、ステップが失敗した後だけでなく、すべての act
  ステップの事前読み取りでも評価されます。つまり失敗を 1 回払う前に、act より先に tip を片付け
  ます。代償は、素の act 1 つあたり問い合わせが 1 回増えることです。それでもガードが買っている
  ものは、TipKit の内部の名前を 1 箇所に集める点です。Apple がノードの名前を変えたとき、1 つの
  ドライバの 2 行がすべてのシナリオを覆います。手書きのエントリなら、それぞれを直すことになり
  ます。本提案の計測は、この取引の両側を照らします。名前の変更を吸収してくれるはずの中心は、
  誤った dismiss が出てきた場所でもあったからです。ですからガードをやめて、ドキュメント化した
  `interrupts` のエントリに委ねる立場も成り立ちます。ただしそれは本提案とは別の決定です。BE-0389
  が下した結論を覆すものであり、本提案は今日あるガードの欠陥を直すものです。

- **`Interrupt.condition` に論理積を追加し、手書きのエントリで 2 つの手がかりを求められるように
  する。** 本提案では採用せず、独立した課題として残します。論理積は `interrupts` のエントリを書く
  作者の助けになりますが、シナリオの条件を評価しないドライバ側のガードには何の効果もありません。
  しかも、1 つの assertion に 1 種類という規則が本件をはるかに超えて効いている assertion の DSL を
  広げることになります。手がかりにすべき条件が `TipView` であるとドキュメントに書けば、この変更を
  伴わずに手書きの場合を解決できます。

起動済みの Simulator で `demos/showcase/scenarios/tipkit.yaml` を実行して確認しました。組み合わせを
要求する状態では 4 本すべてが成功し、ドライバを scrim だけの判定に戻すと新しい 1 本が失敗します。その
manifest には settle のステップの中で `tap PopoverDismissRegion [0, 0, 402, 874]` が記録されます。
続く検査は `expected present but was absent` を報告します。新しいシナリオは、たまたま成功しているのでは
なく、実際に判定を支えています。

このシナリオには機能しない書き方が 2 つあり、どちらの理由も記録に残す価値があります。1 つは、
ダイアログ自身のボタンを待つ形（`wait: { for: { label: "Remove note" } }`）です。これは修正前の
ドライバでも成功します。待機中の dismiss のフックが動くのは、待機がブロックされている間だけだから
です。すでに画面にあるボタンの待機は最初のティックで成功し、ガードに何も尋ねません。そこでシナリオは
settle を使い、ダイアログが出ている間ツリーを取得し続けます。もう 1 つは、ダイアログを開くボタンへ
スクロールせずに手を伸ばす形です。このボタンは画面のいちばん下、フローティングのタブバーの裏側で
解決されます。タップが届くのはドライバが自分でスクロールして回復するからで、manifest には
`y = 828.7` での失敗、スクロール、`y = 174.3` での再試行が記録されていました。明示的な `scroll` を
置くとタップは 1 回目に `y = 171` で届き、フォールドの位置に依存しなくなります。
