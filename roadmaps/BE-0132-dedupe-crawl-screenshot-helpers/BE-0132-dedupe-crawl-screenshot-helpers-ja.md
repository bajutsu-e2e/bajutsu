## はじめに

クロール周辺のコードは、現在の画面をベストエフォートでスクリーンショットに撮る処理を、複数箇所に持っています。そのうち2つのキャプチャ用ヘルパーは、完全に同一の実装へと重複しており、どちらも自身の失敗を隠してしまっています。

本項目は、この2つのヘルパーを1つに統合し、キャプチャの失敗を握りつぶさずに表面化させます。エラーを黙って飲み込むのではなく大きく失敗させるという、決定性優先の原則に沿った対応です。

## 動機

`bajutsu/record.py:52` は `_screenshot_bytes` を定義し、`bajutsu/alerts.py:48` は `_screenshot_png` を定義しています。両者の本体は完全に同一で、次の処理を行います。

1. 一時ファイルへ PNG を書き出す。
2. それをバイト列として読み戻す。
3. 一時ファイルを削除する。
4. 例外が起きた場合は `None` を返す。

`bajutsu/crawl_guide.py:82` と `bajutsu/enrich.py:92` は、いずれも `record.py` の `_screenshot_bytes` をインポートして、自前のベストエフォートキャプチャに使っています。つまり、同じロジックが、別々に保守されている2つのコピーを通じて、すでに四箇所の呼び出し元から依存されています。

重複そのものに加えて、両方のコピーは、キャプチャ処理全体を素の `except Exception: return None` で囲んでいます。この書き方は、実際の失敗原因（古くなったシミュレータ、権限エラー、ディスクの空き容量不足など）を握りつぶします。しかも、それを「そもそもキャプチャすべきものが何もなかった」場合とまったく同じ形で報告してしまいます。

`None` を受け取ってスクリーンショットの利用をスキップする呼び出し元には、アラートロケーターのプロンプト、クロールガイドの注釈、エンリッチメントの記録があります。これらの呼び出し元は、実際の失敗と想定内の不在を区別できません。これは、ツールがシグナルとして扱うものについて、決定性優先の原則が排除しようとしている、まさにその種の曖昧さです。

作業の規模はサイズ M/S です。自己完結した 10 行ほどのヘルパーを統合し、その4つの呼び出し元に反映させる変更です。

## 詳細設計

修正は、重複解消とエラー処理という2つの独立した部分から成ります。ヘルパーを統合する機会に合わせて、失敗時の挙動もあわせて直します。

- **2つのヘルパーを1つに統合する。** 実装を1つに絞ります。呼び出し面がすでに広い `bajutsu/record.py` の `_screenshot_bytes` を残します。`bajutsu/alerts.py` は、独自の `_screenshot_png` を定義する代わりに、これをインポートして使います。重複は削除します。`screenshot_bytes` という名前は、PNG オブジェクトではなくバイト列を返す関数の名前として、`_screenshot_png` より実態に即しています。そのため、呼び出し元で意味上の調整は不要です。
- **エラーを黙って握りつぶすのをやめる。** 素の `except Exception: return None` を、次のいずれかに置き換えます。
  - 例外をそのまま伝播させる。キャプチャの失敗が、呼び出し元の処理全体を中断させても構わない場合です。
  - `None` を返す前に、例外をログに記録する。呼び出し元が、本当にキャプチャの失敗をベストエフォートとして扱い、処理を続ける必要がある場合です。

  どちらを選ぶかは、`bajutsu/record.py:249`、`bajutsu/alerts.py:86`、`bajutsu/crawl_guide.py:82`、`bajutsu/enrich.py:92` の各呼び出し元を、実際に調べたうえで決めます。要点は、実際の失敗を空のキャプチャと区別できるようにすることであり、両者を1つに混ぜないことです。
- **4つの呼び出し元とそのインポートを更新する。** `bajutsu/alerts.py` は、独自の `_screenshot_png` から、統合後のヘルパーのインポートへ切り替えます。`bajutsu/crawl_guide.py` と `bajutsu/enrich.py` は、すでに `record.py` からインポートしています。インポート自体の変更は不要で、（名前が変わる可能性のある）統合後の関数に対して動き続けるようにするだけです。
- **統合後のヘルパーに対するユニットテストを追加または拡充する。** テストは、成功パスと失敗パス（`screenshot()` が例外を送出するドライバ）の両方をカバーします。新しいエラー表面化の挙動を固定して、黙って握りつぶす挙動へ後戻りしないようにします。

## 検討した代替案

- **両方のヘルパーを残しつつ、一方をもう一方に委譲する。** 却下しました。この方法でも、1つの挙動に2つの名前が残ります。重複をそのまま削除するのに比べて、余計な間接層が増えるだけで、得るものがありません。
- **重複解消はせず、両方のコピーでその場のまま握りつぶしだけを直す。** 却下しました。決定性の懸念には対処できますが、実際の重複そのものは残ります。次に挙動を変更する際にも、2つのファイルへ反映する必要が生じます。これはより根深いリスクです（BE-0064、BE-0066、BE-0092 はいずれも周辺のクロールコードに手を入れていますが、誰もこの重複には気づいていませんでした）。
- **重複は解消するが、素の `except Exception: return None` はそのまま残す。** 却下しました。保守負担は解消できますが、今回の指摘がまさに問題視しているサイレント障害はそのまま残ります。スクリーンショットの失敗は、`None` の中に消えるのではなく、大きく失敗するべき性質のものです。
- **統合後のヘルパーを、`record.py` に残さず新しい共有モジュール（例えば `screenshots.py`）へ移す。** 検討しましたが、着手する人の実装判断に委ねます。`record.py` はすでにこの関数を所有しており、4つの呼び出し元のうち三つは既存のインポート経路のままで問題ありません。新しいモジュールを作る価値があるのは、実際に結合度を下げる効果が確認できた場合に限られます。
