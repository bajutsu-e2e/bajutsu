## はじめに

ホスティングされた Bajutsu は、1 つのプロセスを 2 つに分けて動きます。Control plane が Web のユーザーインタフェース（UI）を提供し、ジョブのキューを持ちます。別プロセスの `bajutsu worker` が、そのジョブを HTTP 経由でリースします。Worker は、実機やシミュレーターを操作できるマシンの上でジョブを走らせます。両者はファイルシステムを共有しません。

利用者は、zip バンドルを Web UI にドロップして設定を開きます。その zip には、`bajutsu.config.yaml`、シナリオのツリー、設定の `appPath` が指すビルド済みアプリバイナリを収めています。Compose ピッカーを使うと、同じ 3 つを個別のアーティファクトとしてアップロードできます。どちらの経路でも、Control plane は、アップロードを自分のディスク上のツリーへ展開してバインドします。

本項目は、バインドされたツリーを、ジョブのリース先の Worker へ届けます。実行が始まったとき、設定が指す場所にバイナリが存在する状態を作ります。

## 動機

現在の Worker は、アップロードされたバンドルを実行できません。ジョブ仕様は、設定とシナリオを `materials` としてテキストで運びます。ジョブ仕様は `app_path` も運びますが、`app_path` は文字列です。バイナリの実体を運ぶ経路がありません。

そのため、実行は Worker 上に存在しないパスに対して始まり、オンデマンドのビルドも肩代わりしません。Bajutsu はビルド済みアプリを受け取り、ビルドはしません。そのため `_governed_build` は、アップロードのバインドの `build:` を方針として無効にします。`_build_app` は、ビルドせずに成功を返します。失敗が表に出るのはインストールの時点で、原因から遠く離れた不明瞭なエラーになります。

アップロードの 2 経路は、どちらも同じ壁に当たります。

| バインドの種類 | Control plane が持つもの | 現在 Worker が受け取るもの |
|---|---|---|
| 単一 zip（BE-0073） | 展開済みツリーと、オブジェクトストレージ上の raw zip | 設定とシナリオのテキストだけ |
| 三つ組（BE-0268） | 合成済みツリーと、オブジェクトストレージ上の各成果物 | 設定とシナリオのテキストだけ |

**確認できる結果**：この変更のあと、アップロードされたバンドルから投入したジョブは、リモートの Worker 上でアプリを導入して実行できます。読み手は、Web UI から違いを確かめられます。アプリの複製を持たない Worker を備えたホスティング環境で、実行を 1 本投入します。

## 詳細設計

設計は、BE-0160 がビジュアルベースライン向けに作った仕組みをそのまま使います。Control plane が URL に署名します。Worker は、自前のクラウド認証情報を持たないまま、平文の HTTP で取得します。

リース応答には新しい `bundle_urls` フィールドが加わり、既存の `baseline_urls` の隣に並びます。このフィールドは、バンドルを構成する保存済みオブジェクトごとに、presigned GET URL を 1 本ずつ運びます。

### 単位 1：どちらのバインドでも通じる、1 つの記述

どちらのバインドも、バインドされたツリーを識別する `sha256` を持つ `Upload` を作ります。ただし、そのもとに置いてあるものが違います。

- 単一 zip のバインドは、ツリー全体を 1 つのオブジェクトとして、org プレフィックス配下の `uploads/<sha256>.zip` に保存済みです。
- 合成のバインドは、成果物ごとに 1 つのオブジェクトを持ち、ツリー全体のオブジェクトを持ちません。

`Upload.worker_ref` は、そのバインドが作ったほうを名指しします。次の 3 つを保持します。

- ツリーの `id`
- 成果物ごとの sha である `artifacts`（単一 zip のバインドでは None）
- 単一 YAML の `scenarios` 成果物を置くときの表示名

1 つの値がどちらの種類も記述するので、以降の単位は、バインドの経緯ではなく、この値の中身で分岐します。

合成ツリーを zip 化して単一 zip の形に寄せれば、分岐は消えます。ただし、代償を比べる価値があります。合成 1 通りごとにアプリバイナリの複製を持つので、BE-0268 の成果物ごとの重複排除を打ち消します。さらに、bind のリクエスト内で数百 MB の zip 圧縮を同期実行します。成果物を名指しする形なら、その重複排除は保たれ、bind 時の負担もありません。

### 単位 2：その記述をジョブに載せ、リース時に署名する

`_register_and_dispatch` は、すべての dispatcher が通る唯一の末尾です。呼び出し元のバインドからジョブの作業ディレクトリを凍結する処理も、すでにここにあります。単位 2 は、同じ場所で `Upload.worker_ref` を刻みます。新しい `Job.bundle` フィールドが値を保持し、`job_spec` が直列化するので、記述はキュー経由で Worker へ届きます。

`worker_lease` は、その記述が名指しするオブジェクトごとに、presigned GET URL を署名します。単一 zip のバインドでは `bundle` の 1 本、合成の 3 つ組では成果物の種類ごとに 1 本です。org は、Worker から送られた値ではなく、リース済みジョブから解決します。どの sha も、ストレージキーになる前に 16 進ダイジェストとして再検証します。署名した URL は、同じ経路をすでに通っている `baseline_urls` の隣に、`bundle_urls` として並びます。

### 単位 3：Worker 上でバンドルを展開し、そのルートからジョブを走らせる

Worker は、リースが署名したものをダウンロードし、Control plane 自身の関数でツリーを組み直します。

- 単一 zip のバインドは、`validate=validate_bundle_config` を添えた `materialize_bundle` を通ります。この検証が、各 target のパスをツリー内へ閉じ込めます（BE-0051）。
- 合成の 3 つ組は、`materialize_composition` を通ります。bind 自身が実行したのと同じ組み立てで、同じ検証を適用します。

続いて `find_bundle_config` が、ツリーから設定を見つけます。この関数は、すべてを 1 つのフォルダで包んだ zip も許容します。設定の親ディレクトリが、そのジョブの作業ディレクトリになります。

このルートから走らせることで、残りのパスが解決します。設定の相対の `appPath`、`scenarios`、`baselines` は、いずれもツリーの内側を指します。実行は、パスの書き換えなしにそれらを読めます。Worker のループは、同じルートをコンソールログの書き出しと証跡アップロードにも渡すので、1 つの作業ディレクトリがジョブ全体をまかないます。

バンドル識別子がツリーの鍵になるので、同じバンドルの 2 本目以降のジョブは、何もダウンロードしません。1 つの作業ディレクトリが、そのバンドルのすべてのジョブをまかない、実行は `runs/` ツリーをその中に書きます。

この識別子は内容のダイジェストであって、ファイル名ではありません。そのため、2 つのビルドは取り違えられません。バイナリのパスが同じで中身が違う 2 つのバンドルは、2 つの識別子になり、各実行は自分のバイナリを入れます。ランナーの `reinstall` 前提条件は、デフォルトで、その実行が始まった作業ディレクトリからのクリーンインストールです。

ジョブごとにツリーを複製すれば、`runs/` の書き込みも分離できます。ただし、そのためだけにアプリバイナリを毎回コピーするのは重すぎます。

ツリーは org ごとに分けます。理由は、コントロールプレーンのキャッシュと同じです。ツリーは可変なので、あるテナントの run の証跡が、別のテナントのディレクトリに落ちてはなりません。org の識別子は運用者が決めるものなので、2 つの異なる識別子が同じ安全なセグメントに落ちることがあります。次の 3 つの場合です。

- 許可外の文字が取り除かれる場合
- 64 文字を超える場合
- 大文字小文字だけが違い、区別しないファイルシステム（macOS の既定のもの）に置く場合

どの場合も、この分離を崩します。キャッシュは、すでに安全なセグメントである識別子はそのまま使い、それ以外は元の識別子のダイジェストで区別します。

取得は、実行と同じバックグラウンドスレッドで、同じハートビートの下で走ります。取得はジョブの中で最大の転送です。リースのタイムアウトより遅い取得は、Worker が気づかないまま回収を招きます。しかも Worker は、そのままジョブを実行し、再リースを獲得した別の Worker と並走します。

回収に気づくことと、間に合って手を打つことは別です。取得が戻った直後に一度だけ確認するフラグが、実際に実行の開始を止めます。フラグがなければ、回収の直後に取得が終わったとき、実行用のスレッドは、そのままアプリを導入して実機を操作してしまいます。再リースを獲得した Worker と並走したうえで、実行の結果だけが後から捨てられます。取得の直後は、まだ実機に何も触れていない唯一の地点です。そこで早期に戻っても、コストはかかりません。

各パーツは、着地後に、ジョブが名指しした sha256 に対して検証します。本文が途中で切れても `http.client` はエラーにしないので、ほかに切り詰めに気づく仕組みがありません。切り詰められた生バイナリは、誰にも読まれないまま、壊れたツリーがキャッシュに残ります。以降のジョブは、そのバンドルの壊れたツリーを再利用します。

ダウンロードの失敗とそれ以降の失敗は、例外の型ではなく段階で切り分けます。ダウンロードの失敗は、何も報告せず、リースを失効させます。たとえば、接続リセット、`503`、ダイジェスト不一致です。キュー自身の再リースが別の試行を与えるので、1 回のネットワークの揺らぎが赤い run になりません（指針 2）。

ダウンロード後の処理は、検証済みのバイトに対して決定的です。そこでの失敗は恒久的なものとして、Worker が報告します。`404` と `410` も恒久的です。オブジェクトは存在せず、再試行しても現れません。型で切り分けると、両方向に誤分類します。`HTTPError` も、壊れたツリーが投げる `FileExistsError` も、どちらも `OSError` だからです。

運用者が知っておくべき帰結が 2 つあります。

- ツリーを削除する仕組みがありません。ビルドごとにバンドルをアップロードする環境では、ビルドごとに 1 つのツリーが Worker のディスクに積もります。コントロールプレーン自身の展開キャッシュと同じ性質が、ジョブを走らせるマシンの側にも出ます。本項目では方針を決め切れないので、`docs/self-hosting.md` に、`.bundles/` を自分で刈る旨を書きます。
- バンドルの run は、org の保存済みベースラインをダウンロードしなくなります。バンドルが自前のものを同梱するためです。serve でベースラインを承認しつつバンドルもアップロードしている環境では、視覚アサーションの比較対象が、バンドルの `baselines/` に変わります。

`_get_file` は、応答全体をメモリに読み込まず、ディスクへストリームします。このヘルパーがもともと想定していたベースライン画像に比べ、アプリバイナリははるかに大きいためです。

バンドルは自前のベースラインも同梱するので、dispatcher は、org 側の保存済みベースラインを上書きするのをやめる必要があります。`_download_baselines` は、書き込み先ディレクトリを先に消します。作業ディレクトリがバンドルの内側にある状態では、同梱物を削ってしまいます。dispatcher は、アップロードのバインドに対してすでに `--baselines` を省いており、単位 3 は `materialize_baselines` の側もそれに揃えます。

### 単位 4：テストとドキュメント

ゲートは、ネットワークとシミュレーターのどちらも使わずに、各接合部を覆います。

- `worker_lease` が、単一 zip のバインドではツリー全体の zip を、3 つ組では成果物ごとに署名します。
- `worker_lease` が、バンドル識別子を持つジョブ仕様に対して `bundle_urls` を返します。
- Worker が、ダウンロードした zip を作業ディレクトリのルートへ解決します。平坦な zip と、包まれた zip の両方を試します。
- Worker が 3 つ組を成果物から組み直し、config が指す `appPath` にバイナリを置きます。
- バイナリのパスが同じで中身が違う 2 つのバンドルが、2 つの作業ディレクトリに解決します。
- バンドル識別子を持たないジョブは、素の作業ディレクトリのままです。Git 由来の実行は影響を受けません。
- リースが署名できなかったバンドル識別子を持つジョブは、盲目のまま走らせず失敗します。
- 取得中に届いた回収を検知するので、ハートビートがダウンロードを覆うことを証明します。
- 取得中に見た回収は実行の開始を止め、単なる結果の破棄では終わりません。
- 切り詰め結果が同じになる 2 つの org 識別子でも、衝突しない別々のディレクトリになります。
- 切り詰められたパーツと不一致の成果物ダイジェストを検知し、再利用されるツリーを残しません。
- 取得時の `503` は再試行し、`404` とバイト着地後の失敗は報告します。
- `_get_file` は 1 回の read に収まらない応答をディスクへ書き、バンドルをメモリに溜めません。
- アップロードのバインドは `materialize_baselines` を切って投入し、同梱ベースラインを残します。

`docs/self-hosting.md` と日本語版に、Worker が新たに取得する対象の説明を 1 段落加えます。

## 検討した代替案

| 代替案 | 採用しなかった理由 |
|---|---|
| バイナリを `materials` に入れる | `materials` はパスからテキストへの写像であり、Mach-O バイナリはテキストではありません |
| 合成ツリーを zip 化して 1 つのオブジェクトを署名する | 合成 1 通りごとにアプリバイナリを保存し、BE-0268 の重複排除を打ち消します |
| Worker にオブジェクトストレージの認証情報を渡す | 認証情報を持たない Worker という BE-0160 の主眼を覆します |
| ホスティング対象の全 [target](../../docs/ja/glossary.md#target-app-device) に `build:` を必須にする | ビルド済みバイナリを前提とするアップロードの筋書きが壊れます |
| 分割の両側で共有ストレージをマウントする | HTTP だけで足りている現在の Worker に、インフラ要件を増やします |

成果物を個別に署名すると、Worker が扱う形は 1 つではなく 2 つになります。とはいえ負担は小さく、どちらの形も新しいコードではありません。`materialize_bundle` と `materialize_composition` は Control plane 自身の関数で、Worker は、ジョブの `Upload.worker_ref` が名指しするほうを呼びます。
