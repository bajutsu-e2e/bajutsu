# iOS step-execution performance: request paths, fixed costs, and bottlenecks

Read-only investigation. "Measured" numbers are quoted from code comments/roadmap; everything else is marked **(est)**.

## 1. `query()` request path

**Python transport.** `XcuitestDriver.query()` → `_query_with_handles()` → `self._transport("GET", "/elements", None)` (`bajutsu/common/drivers/xcuitest.py:731-742, 892-894`). The transport stack is `_with_crash_recovery(_with_retry(_raw_http_transport))` (`:640-647`):

- `_raw_http_transport` (`:576-612`) creates a **new `http.client.HTTPConnection` per request**, calls `conn.connect()`, `request()`, `getresponse()`, `read()`, then `conn.close()` in `finally`. No keep-alive; the Swift side also emits `Connection: close` (`BajutsuKit/Sources/BajutsuRunner/HTTPServer.swift:326`). Socket timeout 15 s for GET, 30 s for POST (`:115, :123, :126-133`).
- `_with_retry` (`:286-329`) only acts on `_TransportFailure`; `_with_crash_recovery` (`:428-573`) only on `XcuitestRunnerCrashError`. **Neither adds a `/health` or liveness round trip on the normal path**; `/health` bypasses recovery entirely (`:485-486`). Liveness (`runner_alive`) is only asked after a crash is declared (`:535, :546`).
- Cost of the loopback connect + one HTTP exchange: ~1 ms **(est)**.

**Second channel per query (BE-0355).** `_apply_native_z` (`:744-768`) calls `self._zorder.positions()` on every query when the environment built a `ZOrderResponder` (`platform_lifecycle/environments/xcuitest.py:168-178`, requires `BAJUTSU_ZORDER_PORT/TOKEN` in `extra_env`). That is a separate `urllib.request.urlopen(..., timeout=2)` to the **in-app** `_ZOrderServer` (`drivers/zorder.py:36-106`), which hops to the app's main thread and walks every window's `subviews` recursively (`BajutsuKit/Sources/BajutsuKit/BajutsuZOrder.swift:55-108, 217-235`). Latched off after one refused connection (`zorder.py:75-85`), so apps not linking BajutsuKit pay it once; apps that do link it pay a main-thread view walk on every query: 5-30 ms **(est)**, and it contends with the app's own animation work.

**Swift HTTP server.** `HTTPServer` (`HTTPServer.swift:31-351`): one serial accept queue (`:57, :141-169`); each accepted connection is handed to a concurrent queue bounded by a `DispatchSemaphore(8)` (`:63, :72, :161-167`). `readRequest` reads the header **one byte per `recv` syscall** (`:246-262`) — ~150 syscalls per request, ~0.1 ms **(est)**. The handler chain is `LegacyBackedTransport.respond` (`LegacyBackedTransport.swift:60-74`) → `blocking` (spawns a `Task`, waits on a semaphore, `:89-105`) → generated OpenAPI handler → `APIHandler.queryElements` (`APIHandler.swift:95-103`) → `caught` → `serialized` → serial `operations` queue → `DispatchQueue.main.sync` (`:331-339`). Four thread hops per request (connection thread → cooperative pool → `operations` → main → back), each sub-millisecond **(est)**. JSON: `elementsReply` builds generated Codable structs (`:278-297`), encoded by OpenAPIRuntime, then `Data(collecting:)` (`LegacyBackedTransport.swift:125`) — ~1-3 ms for ~100 elements **(est)**. `Router.swift` is dead code kept for parity tests (`Router.swift:4-11`).

**Serialization point.** Every XCUITest-touching operation is serialized on `operations` (`APIHandler.swift:27-51`); `/health` and `/interruptionPolicy*` bypass it. So a `/screenshot` in flight blocks the next `/elements`, and a SpringBoard probe blocks both.

**`XcuitestElementProvider.queryElements`** (`BajutsuKit/Runner/Sources/XcuitestElementProvider.swift:44-89`):
1. `try? app.snapshot()` — **one** XPC snapshot (`:49`). Measured in BE-0105: `GET /elements` median **~0.034 s** on iPhone 17 Pro Max / iOS 26.5 for a ~112-element screen (`roadmaps/BE-0105-.../BE-0105-xcuitest-single-snapshot-query.md:140-143`), down from ~18.6 s. The same snapshot waits for the app to idle (`xcuitest.py:110-114`), so during an animation it stretches to hundreds of ms or more **(est)**.
2. `safariViewService.state == .runningForeground` (`:50`) — an `XCUIApplication.state` read for `com.apple.SafariViewService` **on every query**, an XPC round trip to testmanagerd: 5-50 ms **(est)**. Only when foreground does it take a second `safariViewService.snapshot()` (`:62`) and merge/prune (`:59-88`).
3. SpringBoard is **not** snapshotted on `/elements`; only `/systemAlert/query` touches it (`:302-320`).
4. `flattenSnapshot` (`PositionPath.swift:98-131`) walks the snapshot values in-process; `SnapshotNodeAdapter` reads attributes off the snapshot (no XPC, `XcuitestElementProvider.swift:459-476`). Each node allocates a `PositionPathBacking` with `RecordedAttributes`. No z-order computation in the runner.
5. `SnapshotStore.refreshSnapshot` hashes identifier/label/traits per element under a lock (`SnapshotStore.swift:51-69`). Negligible.

**Where the milliseconds go for one idle-screen query (est):** snapshot ~30-35 ms (measured median) · `safariViewService.state` 5-50 ms · zorder second request 5-30 ms (BajutsuKit apps only) · server hops + JSON encode ~2-4 ms · Python connect + decode + `_to_element` ~1-2 ms. Roughly **45-120 ms**, of which the snapshot proper is a third to a half.

## 2. `tap` request path

Python `tap` (`xcuitest.py:896-901`): `_resolve_handle` = one full `query()` (+zorder) + `resolve_unique` (`:789-802`); then `_actuate("/tap")` (`:804-874`). Runner: `APIHandler.tap` → `actOnHandle` → `store.lookup` (in-memory) → `provider.tap` (`XcuitestElementProvider.swift:127-151`). Counting XCUI round trips on the happy path (each attribute read re-resolves the query against a fresh app snapshot — the file's own comments treat every read as a round trip, `:10-12, :395-406`; BE-0019 measured ~600 trips ≈ 12 s, i.e. **~20 ms/trip** on that device, `roadmaps/BE-0019-.../BE-0019-xcuitest-backend.md:116`):

| Step | Reads |
|---|---|
| `liveElement`: `element(at:)` builds a lazy `children(matching:).element(boundBy:)` chain (`:426-430`); `el.exists` (`:356`) | 1 |
| `recordedAttributes(of:includingValue:false)`: `identifier`, `label`, `elementType`, `isEnabled`, `isSelected`, `frame` (`:410-422`) | 6 |
| `centerIsOnScreen`: `el.frame` again + `app.frame` (`:122-125`) | 2 |
| `el.isHittable` (`:131`) | 1 |
| `target.tap()` — resolve + event synthesis + wait-for-idle (`:148`) | 1 + synthesis |

**≈ 11 XCUI resolutions per tap** ≈ 200-350 ms **(est, at 20-35 ms/trip)** plus tap synthesis 100-300 ms **(est)**. Add the preceding `/elements` (~50-100 ms) → **~0.4-0.8 s per tap actuation** before any orchestrator-level capture.

Fallback when the position path no longer resolves (`uniquelyIdentifiedElement`, `:376-393`): `descendants(matching:.any).matching(identifier:)[.matching(label predicate)]` → `allElementsBoundByIndex` (1 resolve, materializes N elements) → `.filter { $0.exists }` (N reads) → `recordedAttributes(includingValue: true)` (7 reads each) → `resolvableMatchingIndex` (`PositionPath.swift:200-217`). ~1 + 8N reads.

Not-hittable path: runner answers `not-hittable` (`:131`) → Python `_tap_sole_reachable_descendant` (`xcuitest.py:903-955`): one more `/elements`, then `/isHittable` per named candidate (each = `liveElement` 7 + `centerIsOnScreen` 2 + `isHittable` 1 = 10 reads, `XcuitestElementProvider.swift:153-158`), then `/tap` again. If that still fails, the orchestrator's `_tap_with_recovery` (`orchestrator/actions/handlers/gestures.py:32-90`) runs `scroll_until_tappable` down then up; each scroll step is a `/scroll` drag at 200 pt/s — **~0.9 s per full-size step, measured** (`XcuitestElementProvider.swift:210-229`) — plus `is_tappable` = `/elements` + `/isHittable` per iteration (`xcuitest.py:972-997`).

Stale retries (`xcuitest.py:143-149, :848-853`): up to 3 attempts, **fixed sleeps 0.5 s then 1.0 s** before re-querying. Note the runner maps *any* NSException in an actuation to `.stale` (`APIHandler.swift:374-376`), so a transient "No matches found" during an animation costs ≥0.5 s of sleep + a re-query + a re-tap.

`GestureRetry` (`GestureRetry.swift:46-56`) is only used for pinch/rotate with `BAJUTSU_GESTURE_RETRY=1` (`XcuitestElementProvider.swift:189-197`): `el.value` read before and after each of up to 4 attempts. `long_press` is `press(forDuration:)` — a real wall-clock hold by design (`:143-144`). `setPickerValue` reads `el.value` up to 5 times (`:289-300`).

## 3. Waits, alerts, tips, screenshot, typing, swipe

- **`wait_for` is client-side.** The driver's `wait_for` is single-shot `base.default_wait_for` (`xcuitest.py:1251-1257`, `drivers/base.py:904-921`). No `waitForExistence`/`XCTNSPredicateExpectation` exists anywhere in the runner (grep confirms). `docs/drivers.md:157` ("uses the runner's native condition waiting") is **inaccurate**; so is `:161` ("`screenshot`: `simctl io screenshot`") — see below.
- **Orchestrator `_wait`** (`orchestrator/waits.py:737-905`): loops `driver.query()` with `_adaptive_sleep` to a 50 ms cadence (`_POLL`, `:31`; `:209-218`). Since a query costs ≥45 ms, waits run **back-to-back snapshots** at ~10-20 Hz, each paying the full path in §1 (connect, `safariViewService.state`, snapshot, zorder).
- **`settled`** (`:926-1000`): tree-diff needs `_SETTLE_POLLS=2` consecutive equal non-empty trees → ≥3 queries. Signal path (`_wait_settled_by_signal`, `:1003-1062`) still calls `driver.query()` every tick until `_TRANSITION_QUIESCENCE=0.3 s` (`:38`) elapses since the last transition → ≥0.3 s and ~6 queries. The transition signal is **push** from the app (`BajutsuScreen.viewDidAppear` swizzle → fire-and-forget POST `/transitions`, `BajutsuScreen.swift:55-97`, `BajutsuNet.swift:133-145`) into Python's `ThreadingHTTPServer` collector (`evidence/network.py:349`), which Python polls in memory (`transitions_snapshot_timed`). `BajutsuScreenTransitionStore` is only an in-app `ObservableObject` for the host UI (`BajutsuScreenTransitionStore.swift:15-33`).
- **`settled_query`**: `XcuitestDriver` does not implement `SettledReadProvider`/`ReadLagProvider` (adb only); `_directional_endpoints` falls back to a bare `query()` (`gestures.py:212`); `_settle_extracts` in `loop.py:200-235` still polls ≥2 queries per extracting `assert`.
- **`system_alert_labels`** (`xcuitest.py:1128-1137`) → `/systemAlert/query` → `querySystemAlertButtons` (`XcuitestElementProvider.swift:302-320`): `springboard.alerts.buttons.count` (a **SpringBoard** snapshot) + `.label` and `.frame` per button (2 SpringBoard reads each) → 1+2n cross-process reads, 100-500 ms **(est)**, serialized on `operations` so it stalls concurrent `/elements`. Driven every `guard.poll_interval` inside guarded waits (`waits.py:290-302`) and every `_SYSTEM_ALERT_POLL=0.2 s` in `wait_for_system_alert` (`:591, :677-679`), which additionally does a `driver.query()` per tick for the gate (`:701`). `handle_system_alert` (`xcuitest.py:1092-1126`) is `/systemAlert/query` + `/systemAlert/tap` (`exists` + `tap`, `:322-328`). The XCTest interruption monitor (`RunnerUITest.swift:45-59`) fires only when XCUITest finds an alert interrupting an interaction: `buttons.count` + n labels + tap.
- **`dismiss_blocking_tip`** (`xcuitest.py:1178-1218`): zero queries when the caller's tree shows no tip (the common per-poll case, `loop.py:957-988`); a real tip costs `/elements` + `/tap`. Post-failure call with no tree = one query (`loop.py:942-953, :1491`).
- **`screenshot`** (`xcuitest.py:1259-1264`) → `GET /screenshot` → `app.screenshot().pngRepresentation` (`XcuitestElementProvider.swift:330-332`), i.e. **XCUITest, not `simctl io`**. Full-resolution PNG (1-4 MB on a 3x device) encoded on-device and shipped over loopback: 150-400 ms **(est)**, serialized on `operations`. The run loop takes **two per step**: `screenshot.before` in the pre-step baseline (`orchestrator/loop.py:1274, :1320`) and `screenshot.after` unconditionally after the action (`:1584-1601`), whenever a real sink is attached.
- **`type_text`** (`xcuitest.py:1225-1230`) → `app.typeText` (`XcuitestElementProvider.swift:252-255`): keyboard-driven, ~50 ms/char **(est, XCUITest characteristic)**; `_do_type` first pays a full tap on `into` (`gestures.py:134-140`). `delete_text` types N delete keys (`:257-263`). `select_all`/`copy` are single `typeKey` chords (`:265-276`).
- **`swipe`** = `press(forDuration: 0.1, thenDragTo:)` at default velocity (`:205-208`); **`scroll`** = 0.1 s press + 200 pt/s drag, ~0.9 s per full step measured (`:229-250`).
- **Sleeps in Swift on the request path: none.** `Thread.sleep` only in the accept-error backoff (`HTTPServer.swift:157`); `asyncAfter` only for the launch watchdog (`RunnerUITest.swift:132`), mock delays, and the control-channel poll. Python fixed sleeps: stale backoff (0.5/1.0 s), transport retry backoff (0.5/1.0 s), and the ≤50 ms `_adaptive_sleep` remainder.

## 4. Per-scenario fixed costs

- **Cold spawn** (`environments/xcuitest.py:746-815`): `_prepare_simulator` (`:1308-1353`) = `simctl boot` + `simctl bootstatus` (unbounded wait, `:912-932`) + `device_type_of` (`simctl list`, once) + `_pin_system_locale` (`simctl spawn defaults …`, skipped when matching) + optional `uninstall`/`install` (scales with app size) + `simctl privacy` per permission. Then `_resolve_runner` → `materialize` (copytree once per digest, cached, `_bundled_runner.py:120-178`) → `.xctestrun` patch → `Popen xcodebuild test-without-building` (`:1190-1240`). XCTest host boot + `app.launch()` "routinely exceeds 10 s on a loaded CI runner"; ceiling 120 s (`:193-197`). Typical 15-40 s **(est)**. Readiness polled every 0.1 s with `health_ready` (raw transport, `:81, :387-421`).
- **Warm reuse** (`:719-745`): `_healthy_resident_driver` = one `/health` (`:1497-1522`); `_resume_warm` (`:1273-1306`) re-runs reinstall + permissions, `simctl terminate` + `simctl launch` (+ `openurl`). Each `xcrun simctl` subprocess ~0.2-0.5 s process overhead **(est)**; `launch` 1-3 s **(est)**. **`_MAX_WARM_REUSES=3`** (`:259-268`) forces a cold respawn every 4th scenario, so the amortized cold cost is ~4-10 s/scenario **(est)**.
- **Readiness** (`runner/launch.py:104-112` → `readiness.py:63-170`): `driver.query()` polls with 0.1→0.5 s backoff, then `_await_settled` up to 3 more queries; the `screenChanged` rung needs the app to link BajutsuKit.
- Per scenario also: `set_interruption_policy` (1 POST, `orchestrator/types.py:554`), `simctl terminate` at lease end (`environments/ios.py:88-89`).
- **simctl on the step path: none** for query/tap/wait/screenshot. Only device-control steps (`device_control.py:31-60`) and `relaunch` (`relaunchers.py:63-79`: terminate + launch + `await_ready`) shell out. **Video** (`simctl io recordVideo`, `evidence/intervals.py:43-55, :398-430`) and device log stream start only when a capture policy, inline `capture`, or config default requests them (`evidence_rules.py:142-162`, `pool.py:365-370`); video stop waits for finalize. `simctl io screenshot` is used only by stall diagnostics on failure (`stall_diagnostics.py:320`).

## 5. What BajutsuKit can already do in-process

- **Inbound channels that exist:** (a) `_ZOrderServer` — a loopback HTTP listener (`GET /zorder`, bearer token, single-threaded accept loop, `BajutsuZOrder.swift:114-300`) that hops to main and walks `UIWindowScene.windows` → `subviews` recursively, emitting only `accessibilityIdentifier` + paint ordinal (`:55-108`); no frames/labels/values/traits. (b) `_BridgeServer` for WKWebView (`BajutsuWebView.swift:167-467`): `GET /webview/dom`, `POST /webview/tap|type|scroll`, `GET /health`, unauthenticated, JS-level only (`el.click()`, `activeElement.value +=`). (c) `BajutsuControlChannel` (`BajutsuControlChannel.swift`): **compiled out** unless `-DBAJUTSU_ENABLE_CONTROL_CHANNEL` (`:3-9`), activated by `BAJUTSU_CONTROL_CHANNEL=1`; **opens no socket** — it polls the Python collector's `GET /commands` every 150 ms (`:78, :154-200`), applies on main, acks via `/commands/ack`. Sole capability: `touch_visualization` on/off (`:224-239`). Its contract explicitly forbids driving app state (`:54-57`).
- **Touch synthesis: none.** `BajutsuTouch` swizzles `UIWindow.sendEvent(_:)` to *observe* delivered events and draw `CAShapeLayer` markers (`BajutsuTouch.swift:105-136, :219-237`). No `UITouch` subclass, no `UIEvent` fabrication, no private API, no `sendActions`.
- **Tree enumeration:** only the ZOrder view walk above (UIKit `subviews` + `accessibilityElements`; SwiftUI content inside `UIHostingController` is reachable only where it surfaces as identified views/AX elements — partial). No accessibility-tree dump with frames.
- **Transitions:** push (`viewDidAppear` swizzle → POST), not polled from the device.
- **Network:** `BajutsuURLProtocol` observes/stubs URLSession traffic; mocks are loaded from the launch env only (`BajutsuMocks.swift:45-51`).

**Verdict for an in-process scenario executor:** the SDK has the *plumbing* pattern (loopback server + main-thread hop + token) but none of the executor pieces: no event injection, no keyboard entry (`UIKeyInput.insertText` on the first responder would be the in-process substitute), no full AX/frame tree, no in-process screenshot (`UIGraphicsImageRenderer`/`drawHierarchy` would be), no YAML/step interpreter, no persistent command socket (only the 150 ms collector poll). Out of reach in-process by construction: SpringBoard permission alerts, `SFSafariViewService` content, the system keyboard, notification banners, other apps, and the process-boundary isolation that makes a crash observable. Both prime directive 3 and BE-0365's scope comment position the SDK as observation-plus-instrumentation, so an in-app executor is a design reversal, not a gap fill.

## 6. Ranked bottleneck hypotheses (per tap step unless noted)

1. **Per-attribute XCUI reads on actuation** — ~11 resolutions ≈ 200-350 ms + tap synthesis **(est)**. *Cheap:* take one `try el.snapshot()` after `element(at:)` and read identifier/label/type/enabled/selected/frame off it (drops `exists` + 7 reads to 1); cache `app.frame` (screen size is fixed per run, `screenSize()` already assumes so). *Radical:* tap by `app.coordinate` at the handle's recorded frame center (1 call), verifying identity only when a stale is suspected.
2. **Two XCUITest screenshots per step** — 0.3-0.8 s **(est)**, serialized against the tree reads. *Cheap:* drop `screenshot.before` when the previous step's `after.png` is fresh (same screen), or make it policy-gated; encode JPEG/downscale in Swift. *Radical:* capture off the runner channel (`simctl io screenshot` in a Python thread, or frames from the video interval) so it never holds `operations`.
3. **Extras on every `/elements`** — `safariViewService.state` XPC (5-50 ms), the zorder second request + main-thread view walk (5-30 ms), fresh TCP per request (~1 ms) **(est)**; multiplied by 10-20 Hz wait polling. *Cheap:* consult `safariViewService.state` only when the app snapshot contains a remote-view boundary node or on a slow cadence; make zorder lazy (only when a selector's z-disambiguation is actually needed); HTTP keep-alive on both sides. *Radical:* a persistent length-prefixed stream replacing HTTP.
4. **Wait polling density and `settled` minimums** — ≥3 queries for tree-diff, ≥0.3 s + ~6 queries on the signal path **(est ~0.2-0.6 s per wait)**. *Cheap:* on the signal path sleep to quiescence and query once; accept the transition signal without re-diffing. *Radical:* server-side waits (`XCTNSPredicateExpectation` on `exists` inside the runner, one request per wait) or app-pushed "tree changed" notifications.
5. **Scenario fixed costs** — cold respawn every 4th scenario (~15-40 s) plus per-scenario reinstall/permissions/terminate/launch (2-6 s) **(est)**. *Cheap:* raise `BAJUTSU_XCUITEST_MAX_WARM_REUSES` now that the `viewDidAppear` main-thread cause is off-thread (`:259-266`); skip reinstall when the installed digest matches; skip `simctl privacy` when unchanged. *Radical:* keep the app process alive across scenarios with in-process state reset (sacrifices isolation).
6. **Stale-retry fixed sleeps** — ≥0.5 s whenever an animation raises "No matches found" (`.stale` mapping). *Cheap:* re-query immediately on the first stale (the comment at `xcuitest.py:146` already says the re-query is the wait), back off only from the second. *Radical:* runner-side re-resolution by identity before answering `stale`.
7. **SpringBoard probes in guarded waits** — 1+2n cross-process reads per probe, blocking app queries (100-500 ms **est**). *Cheap:* `springboard.alerts.firstMatch.exists` first, enumerate buttons only when true, or read them off one `alerts.firstMatch.snapshot()`. *Radical:* rely on the interruption monitor + `simctl privacy` pre-grants and drop the polling probe.
8. **Character-by-character typing** — ~50 ms/char **(est)** after a full tap. *Cheap:* `simctl pbcopy` (machinery exists, `simctl.py:842-878`) + `typeKey("v", .command)`. *Radical:* in-process `insertText` via a control command (prime-directive-3 tension).
9. **Deterministic slow scroll** — ~0.9 s/step measured, by design; only larger steps help cheaply.
10. **Server internals** (thread hops, OpenAPI encode, byte-wise header parse) — ~2-4 ms total; not a bottleneck.

**Rough per-tap-step budget (est):** `screenshot.before` 0.15-0.4 s · `/elements` 0.05-0.12 s · tap resolution + synthesis 0.3-0.65 s · `screenshot.after` 0.15-0.4 s · post-step `elements` read 0.05-0.12 s → **~0.7-1.7 s**, with screenshots and per-attribute reads accounting for well over half. The snapshot the code optimized in BE-0105 is now a minority of the step.
