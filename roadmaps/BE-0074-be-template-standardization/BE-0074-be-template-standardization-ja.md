## はじめに

ロードマップの各項目は、英語の `BE-NNNN-<slug>.md` と日本語の `BE-NNNN-<slug>-ja.md` という 2 つのファイルの組です。両方のファイルが、決まった 1 つの形を共有します。

- 対訳のヘッダリンク
- H1 のタイトル
- メタデータブロック
- Swift-Evolution 形式の 5 つの節（Introduction / Motivation / Detailed design / Alternatives considered / References）

この形は、[`CLAUDE.md`](../../CLAUDE.md)、[`roadmaps/README.md`](../README-ja.md)、[`ideation`](../../.claude/skills/ideation/SKILL.md) スキルの散文で説明されています。索引テーブルのほうは、すでに各項目のメタデータから生成され、ゲートで検査されています（[`scripts/build_roadmap_index.py`](../../scripts/build_roadmap_index.py)、`tests/test_roadmap_index.py`）。

各項目ファイルの本体は、まだ何にも固定されていません。メタデータのラベル、見出しの文言、どの節を必須とするかが該当します。著者は人間も AI も、その都度近くのファイルから形を組み立て直しています。その結果、細かなばらつきが入り込んでいます。

本項目は、この形を固定します。言語ごとに正規のスケルトンを 1 つ書き下し、規範となるフィールド集合と節見出しを定めます。あわせて、隣にある索引検査と同じく `make check` で走る決定的な検査を提案します。この検査は、`BE-NNNN-*` のファイル組がスケルトンから逸脱したときに失敗します。対象はすべて文書とテストです。ツールの挙動は変えず、どの経路にも大規模言語モデル（LLM）を持ち込みません。

## 動機

両言語 69 項目を走査すると、形は「ほぼ」一様です。次の 4 点は、どこでも一致しています。

- ヘッダリンク
- タイトル行
- メタデータの並び順（`Proposal` → `Author` → `Status` → 任意の `Implementing PR` → `Track` → `Topic` → 任意の `Origin`。`Origin` は常に末尾）
- Status の語彙

逸脱は、現状どの生成器もテストも見張っていない、ごく一部の箇所に限られます。

- **ある日本語見出しが 2 通りに訳されています。** `## 検討した代替案` が 66 ファイルにあります。同じ語を並べ替えた `## 代替案の検討` は 2 ファイル（`BE-0064-ja`、`BE-0066-ja`）にあります。
- **ある日本語ファイルだけ、見出しが未翻訳のままです。** `BE-0044-ja` は、兄弟ファイルが使う日本語見出しではなく、英語の `## Introduction` / `## Motivation` / …（以下同様）を今も持ちます。
- **ある項目が、必須の節を落としています。** `BE-0017`（両言語）には `## Motivation` / `## 動機` がありません。
- **ある項目が、メタデータのフィールドを落としています。** `BE-0064`（両言語）には Author（提案者）の行がありません。
- **あるメタデータのラベルが、68 ファイルで単数、1 ファイルで複数になっています。** `BE-0051` を除く全ファイルが `* Implementing PR:` と書きます。`BE-0051` だけが、2 つの PR を並べるために `* Implementing PRs:` と書きます。
- **提案者のラベルは、日本語側で唯一英語のまま残るフィールドです。** 日本語側は、ほかのメタデータラベルをすべて訳しています（`提案`、`状態`、`トラック`、`トピック`、`実装 PR`、`由来`）。提案者の行だけが `* Author:` のままです。今は揃っていますが文書化されておらず、決定の結果ではなく見落としのように読めます。

どれも単独では小さなものです。まとめて見れば、「隣をコピーして目視で揃える」やり方が生む当然の帰結です。散文の指針は、逸脱を防ぎません。コミット時にその散文を読み直す者がいないからです。

衝突に強いファイルフロー（[BE-0043](../BE-0043-conflict-resistant-file-flow/BE-0043-conflict-resistant-file-flow-ja.md)）は、この種の問題に対する本プロジェクトの答えをすでに確立しています。不変条件を機械検査にかけ、「ローカルで緑なら CI も緑」を成り立たせることです。ロードマップの*索引*はそのように守られていますが、項目の*本体*は守られていません。本項目は、同じ扱いを本体へ広げます。

## 詳細設計

### 正規のメタデータ

メタデータブロックは、`| Field | Value |` の表です。マーカーの対 `<!-- BE-METADATA -->` … `<!-- /BE-METADATA -->` が表を囲みます。このマーカーは、索引の `<!-- GENERATED:* -->` 領域に倣います。ブロックは、`| Field | Value |` の見出し行（日本語側は `| 項目 | 値 |`）と `|---|---|` の区切り行で始まるので、表として描画されます。メタデータの場所を示すのは見出しではなく、囲みです。

要となるのは、この囲みです。パーサは、囲みのおかげで、これらの行だけを読み、本文の同形の行を決して読まずに済みます。箇条書き（`* Key: value`）は、素の 1 行に境界がないので、これを与えられませんでした。フィールドごとに 1 行という形は、自由な箇条書きより形を保ちやすくもあります。

ブロックは、以下のフィールドをこの順で持ちます。

- `Proposal`、`Author`、`Status`、`Track`、`Topic` は必須です。
- `Implementing PR` の行は、項目が実装されてから現れます。
- `Origin` の行は、競合調査やドッグフード調査に由来する項目だけに現れます。常に末尾に置きます。

| 順 | 英語フィールド | 日本語フィールド | 必須 |
|---|---|---|---|
| 1 | `Proposal` | `提案` | 常に |
| 2 | `Author` | `提案者` | 常に |
| 3 | `Status` | `状態` | 常に |
| 4 | `Implementing PR` | `実装 PR` | 実装後 |
| 5 | `Track` | `トラック` | 常に |
| 6 | `Topic` | `トピック` | 常に |
| 7 | `Origin` | `由来` | 調査由来のみ |

フィールドに関する 2 つの決定を、ここで確定します。

- `Implementing PR` は **PR の数によらず単数**とします。値のセルはリンクのコンマ区切りで、フィールド名は複数形にしません。これで `BE-0051` が解消します。
- 日本語の提案者フィールドは **`提案者`** とします。英語のまま残っていた唯一のフィールドを訳したものです。`提案`（提案リンク）と衝突せず、その隣で自然に読めます。

`Status` は固定された集合から 1 つの値を取り、言語間で対にします。

| 英語 | 日本語 |
|---|---|
| `**Implemented**` | `**実装済み**` |
| `**Accepted, in progress**` | `**可決・実装中**` |
| `**Proposal**` | `**提案**` |
| `**Proposal (deferred)**` | `**提案（保留）**` |

### 正規の節

どの項目も、同じ 5 つの H2 節を同じ順で持ち、見出しは次のとおりとします。

| 英語 | 日本語 |
|---|---|
| `## Introduction` | `## はじめに` |
| `## Motivation` | `## 動機` |
| `## Detailed design` | `## 詳細設計` |
| `## Alternatives considered` | `## 検討した代替案` |
| `## References` | `## 参考` |

`## 検討した代替案` を、日本語の正規見出しとします（66 ファイルの多数派）。`## 代替案の検討` は使いません。5 節はすべて必須です。まだ書くことのない節も省略せず、1 行の `TBD` を置きます。これで `BE-0017` の欠けた `Motivation` が解消します。

### 正規のスケルトン

英語ファイル。

```markdown
**English** · [日本語](BE-NNNN-<slug>-ja.md)

# BE-NNNN — <Title>

<!-- BE-METADATA -->
| Field | Value |
|---|---|
| Proposal | [BE-NNNN](BE-NNNN-<slug>.md) |
| 提案者 | [@handle](https://github.com/handle) |
| Status | **Proposal** |
| Topic | <one of the index topics> |
<!-- /BE-METADATA -->

## Introduction
...
```

日本語ファイルは同じ形ですが、3 点が異なります。

- ヘッダリンクは日本語向けです（`[English](BE-NNNN-<slug>.md) · **日本語**`）。
- フィールド名（`提案` / `提案者` / `状態` / `トラック` / `トピック`）、Status の値、節見出しは日本語です。
- タイトル行は `BE-NNNN — <タイトル>` の形を保ちます。ここのダッシュは固定されたタイトル書式の一部であり、地の文ではありません。

H1 のタイトル行は、両ファイルとも `# BE-NNNN — <タイトル>` とします。ID、空白、前後を空白で挟んだ em ダッシュ（`—`、U+2014）、タイトルの順です。番号が未確定の新規項目は、`ideation` スキルと [`README.md`](../README-ja.md) が説明するプレースホルダのディレクトリ名で起草します。CI（[`scripts/allocate_roadmap_ids.py`](../../scripts/allocate_roadmap_ids.py)）が、プレースホルダを実番号へ書き換えます。本テンプレートは、ファイルのそれ以外をすべて律します。

### メタデータのパーサ

メタデータブロックは、2 つのスクリプトが読みます。

- 索引生成器である [`scripts/build_roadmap_index.py`](../../scripts/build_roadmap_index.py) の `parse_metadata` が、全フィールドを読みます。
- [`scripts/promote_roadmap_items.py`](../../scripts/promote_roadmap_items.py) の `read_status` が、`Status` フィールドを読みます。

両者の規約は、次の 3 点です。

1. **囲みに限定します。** `<!-- BE-METADATA -->` と `<!-- /BE-METADATA -->` の間のテキストだけを読みます。マーカーがなければ、パーサは本文にも現れる形（`* Key:` 行や `| a | b |` 行）を手掛かりにするため、誤った行に食いつきえます。囲みはメタデータ領域を明示します。索引テーブルを `<!-- GENERATED:* -->` で囲うのと同じやり方です。
2. **行ごとに 1 フィールドを読みます。** 囲みの中の各 `| field | value |` 行を、`field` から `value` への対応として読み、値の `**` 強調は除きます。`| Field | Value |` の見出し行（日本語側は `| 項目 | 値 |`）と、その `|---|---|` 区切り行は読み飛ばします。見出し行はキーで除外します。区切り行は、先頭のパイプの後ろに空白がないため、行パターンに一致しません。
3. **未移行の項目には代替の読み方を用います。** 囲みのないファイルは、既存の `* Field: value` 箇条書き規則で読みます。まだ変換していない項目も、移行のあいだ読めつづけます。

両パーサは、この規約に従います。囲みの行を読み、箇条書き形式もフォールバックとして動きます。手で編集した項目が箇条書きへ戻っても、ビルドを壊さず読めつづけます。

### 決定的な検査

新しいテスト `tests/test_roadmap_format.py` を、既存の索引テストの隣で `make test` の下に走らせます。`roadmaps/{implemented,proposals}/BE-*/` の各項目について、言語ごとに次を検証します。

1. 先頭行が、そのファイルの言語と slug に対する正確な対訳ヘッダリンクであること。
2. H1 が、em ダッシュつきの `# BE-NNNN — …` であること。
3. メタデータブロックが `<!-- BE-METADATA -->` … `<!-- /BE-METADATA -->` で囲まれていること。ブロックは `| Field | Value |` の見出し行（日本語側は `| 項目 | 値 |`）とその区切り行で始まります。その言語の必須 `| field | value |` 行を正規の順で並べ、未知のフィールド行を含みません。
4. `Status` が 4 つの正規値のいずれかであり、英語と日本語の値が組内で一致すること。
5. 5 つの H2 見出しが、正規の文言で、順に存在すること。

この検査は、**整形器ではなくゲート**です。違反したファイルと行を報告して失敗し、修正は著者に委ねます。書き換えずに報告する `format-check` と `lint` に倣います。テストは組の 2 ファイルを一緒に検証するので、英語と日本語の Status の不一致を捉えられます。

### 実装したこと

本項目は、1 つの変更として入りました。

- すべてのロードマップ項目を、囲みメタデータブロックへ移しました。
- 両パーサを、ブロックを軸に再定義しました。旧来の `* Field: value` 形式はフォールバックとして残し、手で編集した項目も読めるようにしています。
- `tests/test_roadmap_format.py` を `make test` に組み込みました。

「動機」に挙げた逸脱も、同じ変更で直しました。2 つの `## 代替案の検討` の見出し、`BE-0044-ja` の未翻訳見出し、`BE-0017` の欠けた `## 動機`、`BE-0064` の欠けた提案者フィールド、`BE-0051` の複数形 `Implementing PRs`、日本語側で英語のまま残っていた著者フィールド（現在は `提案者`）です。`CLAUDE.md` と `roadmaps/README.md`（および日本語版）の散文も、囲みブロックを説明する形に更新しました。ツリーは、新しい検査の下で緑です。

## 検討した代替案

- **CLAUDE.md / README の散文に委ねる。** これは現状であり、先の逸脱一覧がその結果です。コミット時に誰も読み直さない指針は、形を保てません。索引を手作業ではなく生成にした理由と同じ理由で、却下します。
- **失敗する検査ではなく、ファイルを形に書き換える整形器**（`make format` の方式）。最初の一歩としては却下します。散文を含むファイルを書き換えると、内容に触れる危険があります。逸脱は、手で直せる程度に小さいものです。自動修正は、検査ができたあとの利便として、後続にできます。
- **[BE-0069](../BE-0069-executable-contributor-guardrails/BE-0069-executable-contributor-guardrails-ja.md)（実行可能なコントリビュータガードレール）に統合する。** 近縁の項目です。どちらもコントリビュータの手続きを機械検査にかけるからです。ただし、対象が異なります。BE-0069 は複数手順の**手続き**をコマンド化します。本項目は、1 つの**ファイル書式**とその検証器を固定します。別項目として保ち、相互参照します。
- **日本語の提案者フィールドを `提案者` ではなく `著者` に訳す。** 却下します。`提案者`（提案した人）は、`提案`（提案そのもの）の隣で自然に読め、項目の枠組みにも合います。`著者`（書いた人）は、記録としての著者を表すフィールドには、やや緩い訳です。
- **メタデータを `* Field: value` の箇条書きのまま保つ。** 現状の形であり、`CLAUDE.md` と `README.md` が「Swift-Evolution の提案形式」として示す字義どおりの形です。本項目は、この形から意図して外れます。箇条書きの行には境界がないので、箇条書きに限定したパーサは、本文の箇条書きへ逸れえます。箇条書きは、行ごとの形よりも自由にばらつきます。囲みブロックは、この両方をふさぎ、索引自身の `<!-- GENERATED:* -->` の慣習にも合います。この逸脱は小さく、ここに文書化します。`CLAUDE.md` と `README.md` の散文は、実装フェーズで囲みブロックへ更新します。
