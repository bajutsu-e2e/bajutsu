## はじめに

自己修復が合否の基準を緩めてしまうリスクに対応します。fix は**必ず人間が diff としてレビューし、`--write` で明示的に適用します**。自動適用はしません。断片が一致しない場合は、安全な no-op になります。

## 動機

自己修復には、よく知られた失敗モードがあります。テストをグリーンに保つうちに、こっそりテストを弱くしてしまうのです。例を 3 つ挙げます。

- リネームされた id が、画面上の任意の id へ「修正」される。
- 実際の遅延を覆い隠すまで、タイムアウトがじりじり伸びる。
- アサーションが、常に通るまで緩められる。

一つひとつは無害に見えます。しかし合わさるとスイートが空洞化し、回帰を捕まえられなくなります。

Bajutsu の前提は、決定的ゲートが信頼できることです。防御のない fix の機構は、このツールが守るべき唯一のものを掘り崩します。本提案は、自己修復が fix を提案できる一方で、テストが何を検査するかをこっそり緩めることは決してできないようにする、防止策の集合です。

## 詳細設計

防止策は助言的ではなく、構造的です。

* **自動適用は一切しない。** fix は、まず人間が読む unified diff として提示します。ファイルへの書き込みには、明示的な `--write` が必要です。既定は、何も変えないドライランです。検証はモデルの言い分ではなく、決定的な `run`（`--rerun`）で行います。
* **fix の種別を制約する。** fix は `renameId`、`addIndex`、`raiseTimeout` のいずれかで、シナリオ source に対する `find` -> `replace` として表現します。モデルは任意の書き換えを出せません。できるのは、トークンのリネーム、セレクタの一意化、wait の延長だけです。さらに `find` は、source の正確な部分文字列でなければなりません。
* **断片の不一致は安全な no-op にする。** `find` 断片が source に一致しなくなった場合を考えます。ファイルが先に進んだか、fix が古くなったときです。このとき `apply_fix` は置換回数 0 を返し、テキストを変更しません。CLI は no-op を報告するので、黙って中途半端に適用されることはありません。
* **AI は調査役の側にとどまる。** モデルは提案するだけで、合否を決めません。判定は、決定的な `run` の `expect` アサーションだけから生まれます。ここのどの防止策も、アサーションを緩めません。そもそもトリアージは、アサーションを緩める fix を出さないからです。`raiseTimeout` は wait を延ばしますが、何をアサートするかは変えません。期待値を弱める fix 種別は存在しません。

これらの防止策により、fix が引き起こしうる最悪の結果は、レビューされて却下されることに限られます。人間が diff を読んで opt-in しない限り、fix がコミット済みの YAML に届くことはありません。

## 検討した代替案

* **信頼度のしきい値つきの自動適用。** 魅力的ですが、どれほど確信があっても、自動の書き込みはレビューなしに条件を緩めうるものです。それはまさに、本提案が防ごうとする失敗モードです。防止策は、人間を介する diff です。しきい値は線を動かすだけで、線を保てません。
* **より強い警告つきで、アサーションを弱める fix を許す案。** 却下しました。期待値を緩めることは、テストを甘くするもっとも直接的な方法です。そのため、どの fix 種別もそれを生みません。アサーションの失敗に対しては、人間向けの提案を出すだけで、適用できる fix は出しません。
* **レビューだけを信頼して、no-op の安全策をやめる案。** 断片不一致の no-op がなければ、古い fix が部分的に適用されたり、思わぬ形でファイルを壊したりしかねません。不一致を目に見える no-op にすることで、却下された fix や古い fix でも害を及ぼしません。
