## はじめに

Bajutsu の iOS バックエンドは、シミュレータの内側で動く小さな HTTP サーバと通信します。このサーバは XCUITest のプロセスが抱えており、Apple の Dispatch ライブラリで作った2つのキューへ仕事を振り分けます。

- ソケットの accept ループを回す直列キュー
- 受け付けた接続をそれぞれ処理する並行キュー

どちらのキューも quality of service（QoS）を宣言していません。QoS とは、その仕事を他のすべてと比べてどうスケジュールするかを、Dispatch が判断するための優先度の階級です。

本項目は、その QoS を宣言します。QoS を指定せずに作ったキューは、低い優先度に固定されるわけではありません。Dispatch は、`async` による投入元スレッドの QoS をそうしたキューへ伝播させ、`.userInitiated` を上限として引き継がせます。指定の欠落が失っているのは、優先度ではなく保証です。要求経路全体の優先度は、accept ループを起動した文脈から引き継いだものであり、その投入の連鎖が変わらないあいだだけ正しさを保ちます。

両方のキューに `.userInitiated` を宣言すれば、[ドライバ](../../docs/ja/glossary.md#driver-backend-actuator-platform)の準備完了のプローブと生存確認のプローブが通る通信路の優先度を固定できます。宣言がなければ、サーバの起動位置をのちに動かす人が、優先度を黙って導き直し、違う値にしてしまう余地が残ります。

## 動機

今日の優先度は決定ではなく結果であり、それを生む連鎖は壊れやすいほどに長いです。

1. サーバは、XCUITest のテストメソッドからメインスレッド上で起動されます。そのスレッドは高い QoS で走ります。
2. accept ループは、`async` で QoS 未指定の直列キューへ投入されます。その QoS を、`.userInitiated` を上限として引き継ぎます。
3. 各接続は、accept ループから `async` で QoS 未指定の並行キューへ投入されます。順に引き継ぎます。

したがって実効の優先度は、おそらくすでに `.userInitiated` です。本項目が書き下そうとしているのは、まさにその値です。しかしコードはそれをどこにも述べていないため、何もそれを保つ仕組みがありません。サーバをバックグラウンドの補助処理から起動した場合を考えます。投入に別のキューを経由させた場合や、異なる QoS を持つ Swift の並行性の文脈を採用した場合も同じです。すべての接続処理の優先度は、診断もテストの失敗も伴わずに動きます。

この優先度が支配する経路は、runner の生存を判断する経路そのものです。ドライバの準備完了の待機は、runner が応答するまで `GET /health` を叩きます。実行中のクラッシュ復旧は、同じエンドポイントを期限つきで叩きます。どちらも期限が過ぎたときに、runner が応答をやめたと結論します。したがって、この経路のスケジューリング遅延は単に遅いだけではありません。混み合ったホストでは、死んだ runner と見分けがつきません。

Bajutsu の iOS のジョブは、GitHub が提供する macOS のランナーで走ります。Xcode 26 のもとでのシミュレータの資源の圧迫は、上流で文書化され、いまも解決していない問題です。そのため、混雑は例外ではなく想定される状態です。

接続経路は2箇所でブロックもします。だからこそ、その優先度は単に整えるだけでなく固定する価値があります。

- 接続の処理は、同時に走る処理を8つに抑える計数セマフォを待ちます（[BE-0287](../BE-0287-xcuitest-runner-multitouch-resilience/BE-0287-xcuitest-runner-multitouch-resilience-ja.md)）。
- XCUITest の操作は、メインスレッドへ移る前に排他ロックを取ります。メインスレッドの仕事が返るまで、そのロックを保持し続けます（[BE-0323](../BE-0323-xcuitest-readiness-crash-respawn/BE-0323-xcuitest-readiness-crash-respawn-ja.md)）。

保持している側が待っている側より低い優先度で動くブロックする待機を、Apple の Thread Performance Checker は優先度逆転として報告します。2つの待機はいずれも、2つの接続処理のあいだで引き継いだ優先度に食い違いが生じたときに、この形をとります。

そうした逆転が実際に起きたかは決着していません。本項目はそう装いません。以前の調査で、accept ループを名指しする Thread Performance Checker の報告が、失敗したジョブの捕捉出力に観測されました。しかしその実行は記録されておらず、いま提示できません。直近の失敗した `ios-e2e` の実行12件を探しても、その警告は見つかりませんでした。2026年8月9日から8月12日までの失敗は、いずれも実行中のクラッシュ復旧のタイムアウトを報告していました。

コードだけから逆転を導いても、隙間は埋まりません。セマフォとロックを待つのは他の接続処理だけです。それらは同じ accept ループから QoS を引き継ぐため、通常は一致します。この基準を測り直すことは、下の作業の前提ではなく最初の一歩です。

その基準がなくても本変更を正当化できる根拠は、より狭く、それでも足ります。

- 呼び出し側がブロックして待つ仕事に対して、QoS の明示は正しい宣言です。
- 遅延に敏感な経路のキューに対して、Apple の道具が勧めるところでもあります。
- 引き継いだ性質を明示した性質へ変える費用は2行であり、変更がスケジューリング以外の挙動に及ぶことはありません。

本項目は flake の減少を計測したとは主張しませんし、そう示唆するのは誤りです。

## 詳細設計

作業は2つの単位です。単位2は単位1に依存しないため、どちらが先に入ってもかまいません。

1. **Thread Performance Checker の基準を測り直す。** runner がいまも優先度逆転の報告を引き起こすか、引き起こすなら報告のスタックが何を名指しするかを確かめます。

   fault-injection と visual のジョブは、runner の捕捉出力をすでにジョブの成果物として上げています。ただし、Checker が黙っているあいだは、捕捉出力を探しても何も決まりません。Checker が報告を標準エラーへ書き出すのは、runner のプロセスの環境が `PERFC_LOG_REPORTS_TO_STDERR` を持つときだけです。この2つのジョブが走らせる `.xctestrun` は、この変数を持ちません。

   この変数を runner のプロセスへ渡したうえで、それらのジョブを走らせ、捕捉出力を探します。結果は本項目に記録します。上の考察が予期している否定的な結果も含めて記録します。報告が出た場合、それは待っている側と保持している側のスレッドを名指しします。それこそが、逆転をコードが許す形から、記述に値する機構へ変えるものです。

   その報告を、単位2ですでに対処済みとして閉じるわけにはいきません。単位2が扱うのは、報告が取りうる2つの形のうち1つだけだからです。

   - 両方のキューに1つの水準を宣言すれば、*食い違い*は消えます。異なる QoS の文脈から投入された2つの接続処理、つまり引き継ぎが許し、宣言は禁じる状態のことです。
   - ただし宣言で消せるのはそこまでです。すべての接続処理は互いに対等になりますが、接続処理の群の外にいる待ち手との差は残ります。

   accept ループ自身の listen 記述子のロックが、その2つ目の形にあたります。`stop()` は、このロックをテストメソッドのスレッドから取ります。そのスレッドは、accept ループの引き継ぐ水準より上にあります。したがって、accept ループのキューに `.userInitiated` を宣言しても、`.userInteractive` の呼び出し側より下に留まります。

   今日のコードに、このロックを問題になるほど長く保持する箇所はありません。だからこそ本項目はそこへ手を入れません。もし報告がそれを名指ししたなら、求められるのは、保持している側を待ち手の階級へ引き上げるか、待機そのものを取り除くことです。そのどちらも単位2は行いません。

2. **両方のキューに `.userInitiated` を宣言する。** runner の HTTP サーバには、accept ループの直列キューと接続の並行キューがあります。その構築時に `qos: .userInitiated` を渡します。このサーバが処理する要求はすべて、ドライバがその返答にブロックしているからこそ存在します。それがまさに user-initiated の意味するところです。

   あわせて、この水準が QoS の伝播のいま暗黙に与えているものを固定するために宣言されている、と記すコメントを添えます。のちの読み手が、明示された値を飾りと読むことも、今日走っている優先度が変わったと思い込むことも避けるためです。

   `.userInteractive` ではなく `.userInitiated` にする根拠は2つです。

   - `.userInteractive` は、メインスレッド自身の階級です。ユーザインタフェースの応答性を保つために、1フレームのうちに完了しなければならない仕事のためのものです。ソケットの読み取りと要求の解析はそれにあたらず、そう名づけることは要件を誤って述べます。
   - 処理は最大8つが同時に走ります。その処理のブロックしていない仕事は、ソケットからバイトを読んで解析する仕事です。それが、同じ処理がこのあと待つメインスレッドの仕事と、対等な優先度で競合してしまいます。`.userInitiated` は、メインスレッドの階級のすぐ下、既定のすぐ上に位置します。この経路が求める関係は、そちらです。

   変更は2つのコンストラクタ呼び出しに限られ、要求の処理には触れません。したがって runner の挙動は、スケジューリングを除いて変わりません。Swift のパッケージは、端から端までのジョブがすでに走らせている iOS のツールチェーンの一部としてビルドされます。それらのジョブの最初の段は、runner が `/health` へ応答すること自体に依存しています。ここでの間違いは、わかりにくい形をとらず、即座に大きな音を立てて失敗します。

## 検討した代替案

- **両方のキューを宣言せずに、QoS の伝播に頼る。** 現状であり、今日のコードの上では筋が通ります。メインスレッドからの起動による伝播が、すでに `.userInitiated` を与えているからです。伝播は優先度をサーバの性質ではなく呼び出し箇所の性質にしてしまうため、却下します。誰かが起動位置を動かすまでは成り立ち、動かした時点で黙って崩れます。2行で、偶然の代わりに保証が手に入ります。
- **保持しているスレッドに優先度を宣言する代わりに、ブロックする待機そのものを取り除く。** より深い修正です。何もブロックしなければ、逆転は起こりません。意図的な設計に対するはるかに大きな変更であるため、却下します。セマフォは、長いジェスチャのあいだにヘルスポーリングが積み上がらないよう、同時に走る処理を抑えます。ロックは、XCUITest の操作がメインスレッドへ届く前に直列化します。それが防いでいる再入は、テストホストを即座に中断させるからです。どちらにも存在する理由があり、本項目はその理由を蒸し返しません。
- **`.userInteractive` を宣言して、処理を最上位の階級に置く。** 資源が逼迫したホストでは、優先度は高いほどよいように見えるので魅力があります。単位2で挙げた2つの根拠により却下します。この階級は、ソケットの処理をフレームの期限を持つ仕事だと誤って述べます。さらに、8つの処理がメインスレッド自身の優先度で競い合えば、その処理が依存しているメインスレッドの仕事と競合します。
- **再現する逆転が得られるまで何も変えない。** 証拠に対するもっとも厳しい読み方であり、単位1を独立した単位として置いた理由でもあります。項目の全体としては却下します。QoS を宣言する根拠は逆転に依存していないからです。生存を判断する経路の優先度が引き継ぎに任されている状態は、それがまだ実行1回を失わせていなくても、固定する価値があります。
