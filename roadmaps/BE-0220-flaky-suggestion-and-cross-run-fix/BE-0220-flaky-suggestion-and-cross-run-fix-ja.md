## はじめに

ホスト版またはセルフホスト版の `serve` は、データベース（DB）上に Run 履歴を蓄積します。この項目は、その履歴を
採掘して、実際にフラッキーな[シナリオ](../../docs/ja/glossary.md#シナリオのオーサリング)を洗い出します。
フラッキーとは、シナリオ自体は変わっていないのに合否が揺れることです。

洗い出した各シナリオについては、AI の調査役が成功 Run と失敗 Run の**両方**の証跡を読みます。Run 間で何が
変わっているのかを説明し、具体的な修正を提案します。修正はシナリオ YAML の全体書き直しまで含みます。

サジェスト側は完全に決定的で、AI を必要としません。どのシナリオがフラッキーか、どの程度か、その順位を決める
側です。修正側は、人間がレビューして取り込む助言的な提案です。自動編集はせず、合否判定の経路にも一切入りません。

この項目は、すでに出荷済みの 2 つのコマンドに対する、履歴全体を対象とした縦断的な対応物です。
[BE-0049](../BE-0049-determinism-flakiness-audit/BE-0049-determinism-flakiness-audit-ja.md) の `audit --history`
による分類を、「各シナリオの分類はこうです」から**順位付きで行動につながる提示面**へ拡張します。
[BE-0021](../BE-0021-ai-triage/BE-0021-ai-triage-ja.md) と
[BE-0022](../BE-0022-update-structured-fixes/BE-0022-update-structured-fixes-ja.md) のトリアージは、
「1 つの失敗 Run を診断する」から「同一シナリオの多数の Run にまたがる**パターン**を診断する」へ拡張します。

## 動機

Bajutsu はすでに 2 通りの方法でフラッキーさを検出します。`audit` はシナリオを `K` 回実行して結果を差分比較します。
ある時点での証明です。`audit --history` は蓄積した Run を `(scenarioHash, name)` でグループ化し、各グループを
`flaky` / `deterministic` / `unproven` に分類します（BE-0049）。

しかし検出は分類で止まっています。ホスト版 `serve` を数百のシナリオと増え続ける Run の DB とともに運用している
チームには、依然として 2 つの作業が残ります。1 つ目は、分類をシナリオごとに探しにいくことです。2 つ目は、
フラッキーなシナリオを見つけるたびに、Run 横断の読み解きを手作業でこなすことです。成功 Run と失敗 Run を並べて開き、
何が違ったのかを読み解く退屈な作業です。ここから 2 つのギャップが生じます。

**第一のギャップは、フラッキーさが分類されても提示されていないことです。** どのシナリオがどれだけフラッキーかで
スイートを順位付けするものはありません。「今週のワースト 5 はこれです」を、チームが行動を起こす場所に届けるものも
ありません。シグナルは DB に存在します。ただ提示されていないだけです。

**第二のギャップは、トリアージが失敗ごとであってパターンごとではないことです。** `triage` は**1 つの**失敗 Run の
証跡を読み、その失敗を説明します。間欠的な失敗は別の問いです。チームが問うのは「この Run はなぜ失敗したか」では
ありません。「このシナリオは同一の content hash のもとでなぜ成功したり失敗したりするのか」です。

これにうまく答えるには、複数の Run の証跡を一度に読み、成功したものと失敗したものの**差分**について推論する必要が
あります。たとえば、Run A では解決したセレクタが Run B では曖昧だった場合です。5 回中 4 回はスピナーより待機が先に
成立した場合や、ネットワーク応答が Run ごとに違った場合もあります。

Run 横断の読み解きは、LLM が得意とする判断を伴わない調査作業です。既存のトリアージの境界を自然に延長したものでも
あります。

2 つのギャップを埋めれば、決定性優先の立場は証明可能（BE-0049）であるだけでなく、**保守可能**にもなります。
チームはもっともフラッキーなテストを順位付きで見られ、それぞれに対して具体的でレビュー可能な修正を得られます。その間、
合否判定は決定的ランナーの中にとどまり続けます。

**境界に関する注記。** BE-0049 と同様、この項目は決定性優先を損なうのではなく強化します。サジェスト側は、履歴から
採掘したフラッキーさを*報告する*だけです。テストを再試行して緑にすることはなく、合否を変えることもありません。
修正側は、人間がレビューする編集を*提案する*だけです。

[BE-0023](../BE-0023-self-healing-guards/BE-0023-self-healing-guards-ja.md) に従い、アサーションを弱める提案は
「テストを甘くするもの」として明示し、黙って提示することはありません。弱める提案とは、`expect` の削除、`value` の
緩和、一意性を超えたセレクタの拡張です。この項目のどこにも、LLM を `run` / CI の合否判定経路に置く要素はありません。

## 詳細設計

提案レベルの粒度で述べます。設計は 2 つの半分から成ります。前半は決定的で、後半の前提になります。

### 前提：DB の Run レコードへの Run provenance の付与

DB を対象とした Run 横断のフラッキー検出では、「同一シナリオ」を明確に定義するために、各 Run にスタンプが必要です。
BE-0049 はすでに `manifest.json` に `provenance` ブロック（`scenarioHash`、`toolVersion`、`gitRevision`）を付与して
います。フォローアップとして、同じ provenance を serve の DB の Run レコードにも載せる必要があると記しており、
[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md) 配下で追跡しています。

この項目は、そのスタンプが DB レコード上に存在することに依存します。まだ出荷されていなければ、スタンプを届けることが
ここでの最初の作業単位になります。列を追加し、可能な範囲で保存済みの `manifest.json` からバックフィルします。

### 前半：フラッキーサジェスト（決定的、AI 不要）

- **DB を対象とした Run 横断のフラッキースコア。** DB の Run レコードを `(scenarioHash, name)` でグループ化し、
  設定可能なウィンドウ（直近 `N` 件、直近 `D` 日など）にわたって、シナリオごとのフラッキー指標を計算します。指標は、
  content hash が変わらないままの合否反転率です。シナリオが編集された場合（hash が変化）や、アプリまたはツールの
  バージョンが動いた場合とは切り分けます。これは BE-0049 と同じ区別の再利用です。土台は `bajutsu audit --history`
  の分類（`flaky` / `deterministic` / `unproven`）で、その上に順位付けを重ねます。
- **serve Web UI の順位付き提示面。** フラッキーさで並べ替えたシナリオ一覧を、パネルに表示します。各行は成功 / 失敗の
  件数、ウィンドウ、分類を示し、代表的な成功 Run と失敗 Run の証跡へリンクします。これは「CLI 機能を serve Web UI に
  露出する」パターンを、履歴ビューに適用したものです。同じ順位付けを CI やスクリプトから使えるよう、`--json` / CLI
  形式も用意します。
- **合否への影響なし。** この提示面は Run 履歴に対して読み取り専用です。合否を計算せず、何もゲートしません。

### 後半：Run 横断の修正提案（AI 調査役、助言的）

- **Run 横断の TriageContext。** 既存の `assemble` ステップ（BE-0021）を拡張します。現在のステップが読むのは「1 つの
  Run の最初の失敗シナリオ」です。拡張後は「1 つのフラッキーシナリオを、その複数 Run にまたがって」読みます。
  代表的な**失敗** Run から、失敗メッセージ、失敗ステップ、要素ツリー、スクリーンショットを集めます。あわせて、
  代表的な**成功** Run から対応する証跡を集め、さらにシナリオ定義と関係するセレクタ id を加えます。この context が、
  差分を読み解く材料になります。
- **並行プロトコルの背後でのパターン診断と修正提案。** `TriageAgent` のパターンを踏襲し、`CrossRunTriageAgent`
  プロトコルを用意します。プロトコルの `triage_flaky` が、Run 横断の context を受け取ります。`ClaudeTriageAgent` 系の
  実装がこの context を読み、構造化されたツール呼び出しによって、2 つを返すよう強制されます。間欠性の根本原因
  カテゴリ（`selector-ambiguity` / `timing` / `network-variance` / `state-leak` / `unknown` のいずれか）と、
  提案する修正です。修正は、的を絞った構造的編集から、**シナリオ YAML 全体の書き直し**までにわたります。的を絞った編集とは、`label`
  セレクタを `id` へ昇格する、`wait` 条件を追加または厳格化する、曖昧さ解消のため `within` スコープを足すなどです。全体書き直しは、シナリオが構造的に脆いときに使います。
- **常にレビュー可能な提案であり、自動編集ではない。** BE-0022 および DESIGN §6.5 と整合し、出力は人間がレビューして
  取り込む提案差分です。コミット済みの YAML がひとりでに変わることはありません。全体書き直しも、現在のシナリオに
  対する差分として提示し、黙って上書きしません。
- **甘くしないためのガード。** BE-0023 に従い、テストのアサーションを弱める提案はいずれも「テストを甘くするもの」
  として明示します。弱める提案には、`expect` の削除、`value` / `label` 一致の緩和、一意性を超えたセレクタの拡張、
  `wait` タイムアウトの除去が含まれます。レビュー担当者はトレードオフを明示的に把握でき、修正が「通すため」に静かに
  カバレッジを削ることを防げます。

### 提示面

後半の提示面は、採用時に委ねる実装上の選択です。新しいサブコマンド（`bajutsu triage --flaky <scenario>` など）に
するか、既存の `audit --history` のモードにするか、純粋に serve Web UI のアクションにするかを、そのときに決めます。

serve のパネル（前半）を主たる提示面とします。CLI 形式によって、CI とスクリプトを第一級に保ちます。

## 検討した代替案

* **フラッキーテストの自動再試行または隔離（業界で一般的な答え）。** BE-0049 と同じくゲートでは却下します。再試行で
  通すことは、フラッキーさを隠すためです。この項目は逆に、洗い出して修正します。
* **AI に書き直しを自動適用させる。** 却下します。非決定的なモデルに、コミット済みのテストを黙って変えさせることに
  なります。DESIGN §6.5（「AI の出力は常に提案差分」）と BE-0023 の甘くしないガードに反します。書き直しは常に
  レビュー可能な差分とします。
* **ある時点での repeat-and-diff のみ（現状の BE-0049 `audit`）。** 許容できますが不完全です。`K` 回実行すれば、
  1 つのシナリオのフラッキーさをその場で証明できます。しかし、チームの実際の Run 履歴がすでに含んでいるフラッキーさは
  採掘できず、スイートの順位付けもできません。蓄積された成功 / 失敗のペアをまたいだ推論もできません。
* **失敗ごとのトリアージのみ（現状の BE-0021）。** 単一の失敗はうまく診断しますが、間欠性を見ることはできません。
  間欠性とは、同一シナリオが 1 つの content hash のもとで成功したり失敗したりすることです。これを露わにできるのは、
  Run 横断のビューだけです。
* **DB の Run レコードではなく専用のフラッキー用ストアを設ける。** 却下します。Run 履歴はすでに DB に蓄積されており、
  並行するストアを足すと記録の源が二重になります。この項目が足すのは、既存レコードに対するクエリと提示面だけです。
  加えて、BE-0049 がすでにスコープした provenance のスタンプを使います。
* **2 つの項目に分割する（前半：フラッキーサジェスト提示面、後半：Run 横断修正提案）。** 検討に値する選択肢です。
  同じトピックのトリアージ関連作業が、BE-0021、BE-0022、BE-0023 の 3 項目に分かれて出荷されたからです。それでも
  1 項目にまとめたのは、2 つの理由によります。1 つ目は、前半単独では価値が限定的なことです。フラッキーな
  シナリオの順位付き一覧を提示しても、ユーザーがすぐに行動できなければ意味が薄く、その行動（Run 横断修正提案の
  レビュー）こそが後半です。2 つ目は、両者が同じ Run 横断証跡組み立てのステップを共有していることです。前提となる
  DB への provenance スタンプと、`TriageContext` の拡張です。分割すると、同じ前提を 2 つの提案にまたがって調整する
  必要が生じます。後半の AI エージェント設計が前半より著しく成熟に時間がかかると判明した場合は、その時点で分割する
  のが適切です。Progress のチェックリストは、前半のみを先に完了できる構造になっています。
