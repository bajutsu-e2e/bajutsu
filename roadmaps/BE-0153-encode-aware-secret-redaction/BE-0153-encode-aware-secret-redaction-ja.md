## はじめに

`Redactor` は、既知の秘密情報の値を完全一致の文字列置換でマスクしています。同じ値のエンコード
された別形式は、マスクされずに素通りします。URL エンコード、Basic 認証の base64、HTML・JSON
エスケープ、複数チャンクに分割された値などです。本項目は、redaction をエンコード考慮型にします。
既知の秘密情報の値を、そのバイト列だけでなく一般的なエンコード形式でも照合できるようにします。

## 動機

`Redactor.redact_text`（`bajutsu/redaction.py:63`）は、既知の秘密情報の値を
`text.replace(value, PLACEHOLDER)` という単純な部分文字列置換でマスクしています。テキスト中に
値がそのまま完全一致で現れる場合は捕捉できますが、それ以外は捕捉できません。同じ秘密情報の
よくある変換形式のいくつかが、すり抜けます。

1. **パーセントエンコーディング。**
   URL のクエリパラメータやフォームエンコードされたボディとして渡された秘密情報
   （`token=p%40ssw0rd`）は、`p@ssw0rd` という値をそのまま含んでいません。
   エンコードされた形式は別の文字列なので、置換処理はマッチしません。
2. **`Basic base64(user:pass)`。** HTTP の Basic 認証は
   `Authorization: Basic <base64(username:password)>` を送信します。パスワードの生の値は
   ヘッダーのテキストに現れません。現れるのは、base64 でエンコードされコロンで結合された形式です。
   完全一致のパスは、この形式に触れません。そのため、捕捉された `network.json` の exchange に、
   容易にデコードできる認証情報がそのまま残ります。
3. **HTML・JSON エスケープ。**
   HTML でエスケープされた属性（`&quot;`、`&amp;`）や JSON でエスケープされた文字列（`\"`、`\/`、`\uXXXX`）に埋め込まれた秘密情報は、生の値とバイト単位で
   一致しません。置換処理は、これもマッチしません。
4. **複数チャンクに分割された値。**
   複数回の読み取りやチャンクから組み立てられた証跡（ストリーミングされたボディや、逐次的に構築されるテキストなど）では、秘密情報の値のバイト列が
   チャンクの境界をまたぐことがあります。置換処理は、それを一つながりの文字列として認識できません。

これらはいずれも、本物の秘密情報が、エンコードの形式だけを変えてほぼそのままの形で証跡に残る
現実的な経路です。秘密情報とは、`${secrets.*}`（BE-0032）でバインドされたパスワード、トークン、
API キーを指します。証跡はディスクに書き出されます。AI による authoring・調査の経路では、設定済みの
AI プロバイダーにも送られます（BE-0047）。`secrets:` を正しくバインドした著者は、値が証跡から
除かれると期待します。ところが実際に保護されるのは、ツールがたまたま文字列一致で捕捉できる
1 つのエンコード形式だけです。

## 詳細設計

1. **既知の各秘密情報の値について、リテラルな文字列だけでなく一般的なエンコード形式も照合する。**
   `Redactor.redact_text` と `redact_exchange` の両方で、以下を扱います。
   - パーセントエンコーディング。値を `urllib.parse.quote` した形式です。エンコーダーによって
     エスケープしない安全文字の扱いが異なるため、いくつかの一般的な設定で照合します。
   - Basic 認証の base64。Basic 認証のパスワードになりうる各秘密情報の値について、
     `Authorization: Basic ` の後に現れる `base64(...)` 形式もマスクします。両方が既知の
     秘密情報である場合は、`user:pass` の全体についても同様です。
   - HTML エスケープ形式と JSON エスケープ形式（`html.escape`、引用符を除いた `json.dumps`）。
     すでにリテラルなテキスト検索を行っている箇所すべてで、対象にします。
   - 変換は、*既知の*秘密情報の値に適用する、固定で列挙可能な集合にとどめます。あらゆるものを
     総当たりでデコードして走査するわけではありません。コストと誤検知の範囲を抑えられます。
2. **キーに基づくパターンマッチングは弱めない。** ヘッダー・フィールドのキーに基づくパターン
   （`_patterns`、`bajutsu/redaction.py:21`）は、そのまま維持します。本項目が拡張するのは、
   キーや Basic 認証の文脈が値のおおよその位置を特定したあと、*値*そのものをどう認識するかです。
3. **チャンク境界の分割は、ベストエフォートで対策する。** 保証はしません。
   redaction が実行される前に証跡が組み立てられる経路があります（ライブストリームではなく
   完全なボディ文字列である場合など）。その経路では、redaction がすでに完全なテキストを見るため、
   問題は起きません。実際に断片化した証跡が存在する場合は、完全なカバレッジを主張せず、
   その制約を明記します。
4. **テスト。** 次の3つの値が、それぞれ正しくマスクされることを検証します。
   URL・クエリでパーセントエンコードされた値、`Basic base64(...)` ヘッダーに含まれる値、
   ボディ中で HTML・JSON エスケープされた値です。
5. **ドキュメント。** redaction に関するドキュメント（`docs/` と `docs/ja/` の両方）に、
   エンコードを考慮したマッチングを記載します。既知の限界（実際に断片化したストリーミング証跡など）も
   記載します。

「そもそもどのヘッダーを redact 対象にするか」という既定マスキングの欠落は、別の兄弟項目
（default network secret redaction）で扱います。本項目のスコープは、どのヘッダー・フィールドが
検索のきっかけになったかにかかわらず、既知の秘密情報の*値*をどう照合するかに限られます。
本項目は、決定的な `run`・CI ゲートには触れず、LLM も導入しません。変更は、証跡書き込み経路の
内部で完結する、純粋なテキスト変換です。

## 検討した代替案

- **証跡中に見つかったすべての文字列をデコードし、秘密情報の値と比較する。** 範囲が広すぎ、
  遅すぎるので却下しました。任意のテキストをあらゆるエンコードに対してデコードして比較するのは
  高コストです。たまたま何かにデコードできてしまうゴミデータによる誤検知も生みます。逆方向の
  ほうが安価で精度も高くなります。既知の秘密情報の値をエンコードし、その既知のエンコード形式を
  検索する方法です。
- **著者にはヘッダー・フィールド名のみによる redaction を求め、値に基づくマッチングを
  完全に廃止する。** 却下しました。値に基づくマッチング（BE-0032 の `values` リスト）は、
  著者が想定していなかった場所（ログの一行、レスポンスボディなど）にアプリが秘密情報を
  エコーしてしまうケースを捕捉するために存在します。これを取り除くと、エンコードの欠落を
  修正するどころか、その保護自体を後退させてしまいます。
- **マッチャーを修正する代わりに、AI data sovereignty の警告（screenshot-secret-capture-warning）に
  任せる。** 却下しました。その項目は画像の証跡を対象としており、画像は本当にピクセル単位では
  redact できません。一方でテキストの証跡は正しく照合できます。したがって、修正はマッチャー側で
  行うべきであり、開示に頼るべきではありません。
