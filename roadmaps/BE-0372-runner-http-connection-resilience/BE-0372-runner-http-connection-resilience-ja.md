## はじめに

Bajutsu は iOS シミュレータを、XCUITest のプロセスが抱える小さな HTTP サーバ経由で操作します。この
HTTP サーバを **runner** と呼びます。Python 側は
[driver](../../docs/ja/glossary.md#driver-backend-actuator-platform) です。driver は、Bajutsu で唯一
プラットフォームに依存するインタフェースを実装します。操作ごとにループバック接続を1本開き、それぞれに
上限つきのソケットタイムアウトを与えます。読み取りには15秒、操作の実行には30秒です。

本項目では、runner のサーバが接続を扱う部分にある4つの不具合を修正します。

- 1つはサーバのプロセスを落とします。
- 2つはプロセスを生かしたまま、サーバを機能停止させます。
- 残る1つは、クライアントが送り終えていないリクエストをハンドラまで通してしまいます。

4つすべてを修正し、修正が外れたら落ちる回帰テストを併せて追加しました。

4つの不具合をまとめて扱う理由は、症状が1つに収束するからです。どれが起きても runner は
`GET /health` に応答しなくなります。他に生存を知る手段のない driver は、原因を説明できないままタイム
アウトを報告します。保守する側には、どの不具合が起きたかによらず、同じ情報量のない失敗として届きます。

## 動機

もっとも深刻な不具合は、runner のプロセスごと落とします。Darwin は、相手がすでに閉じたソケットへ書き
込むと `SIGPIPE` を発生させます。このシグナルのデフォルトの動作は、プロセスの終了です。サーバは、受け
付けたソケットに `SO_NOSIGPIPE` を設定していません。シグナルを無視する設定もしていません。立ち去った
相手への応答の書き込みは、そのまま致命傷になります。

そのような相手が生まれる競合は、例外的な状況ではなく日常的に起こります。

1. driver 側のソケットタイムアウトが、接続を閉じます。
2. その時点でハンドラは、まだメインスレッド上で止まっているか、XCUITest の操作を直列化する排他ロック
   の待ちで止まっています。
3. そのハンドラが後から、driver がすでに見捨てたソケットへ応答を書き込みます。

この機構は、議論ではなく2つの実測で確かめました。

- サーバの書き込み経路を再現した単体のプログラムは、異常終了で閉じた相手へ応答すると、signal 13
  （`SIGPIPE`）で終了します。`SO_NOSIGPIPE` を設定すると、同じ書き込みは `EPIPE` を返し、プログラムは
  生き延びます。
- サーバ本体から修正を外すと、テストターゲットでも同じ死に方を再現できます。XCTest のプロセスは、
  アサーションで失敗する代わりに signal 13 で終了します。

「Foundation がすでにこのシグナルを抑止している」という通説も確認しましたが、成り立ちません。プロセス
の開始時点で `SIGPIPE` は無視設定になっておらず、`URLSession` を作っても設定は変わりません。

2つめの不具合は、プロセスを落とさずにサーバを機能停止させるので、より診断しにくいものです。accept
ループは `accept()` の失敗をすべて致命的なものとして扱い、ループを抜けていました。ループを抜けても
listen 中のソケットは開いたままなので、カーネルはハンドシェイクを完了させてバックログへ積み続けます。

その結果、driver が開く接続はすべて成功し、accept されず、応答も返りません。何も処理しない生きた
プロセスは、この経路から見るかぎり、死んだプロセスと区別できません。

ここで想定すべき失敗は `ECONNABORTED` です。相手がハンドシェイクの完了からサーバの accept までの間に
切断すると、カーネルはこの値を返します。driver 側の health ポーリングがバックログへ積まれたまま自身の
タイムアウトへ達したときに、この失敗が起きます。`EINTR` も同様によく起こります。どちらも listen 中の
ソケットについては、何も語りません。

3つめの不具合は、接続を処理する枠を枯渇させます。受け付けたソケットへ `SO_RCVTIMEO` と `SO_SNDTIMEO`
のどちらも設定していないため、ハンドラが行う2つのブロッキング呼び出しは無制限に待ちます。接続だけして
リクエストを送らない相手は、そのハンドラを `recv` でプロセスの生存期間中ずっと止めます。ハンドラは、
[BE-0287](../BE-0287-xcuitest-runner-multitouch-resilience/BE-0287-xcuitest-runner-multitouch-resilience-ja.md)
が導入した8つの同時ハンドラ枠のうち、1つを占有し続けます。

そうした相手が8つあれば、全枠が埋まります。長いジェスチャの最中でも応答できるように BE-0287 が並行化
した `/health` が、ふたたび応答不能になります。

4つめの不具合は範囲こそ狭いものの、規模から想像されるより悪い性質を持ちます。ヘッダの解析は、8 KiB の
上限で読み取りを打ち切ります。ヘッダを終端する空行が実際に届いたかどうかを確かめずに、読めた分を解析
していました。ヘッダが上限を超えたリクエストもそのまま解析され、そこから得たメソッドとパスが振り分け
られます。

修正を外すと、結果を直接示せます。クライアントが送り終えていないリクエストで、ハンドラが呼ばれます。
操作の実行を担うエンドポイントであれば、それは端末を実際に操作することを意味します。

同じ穴は本体にも通っており、そちらのほうが結果は鋭くなります。

- 宣言された `Content-Length` に届かないまま読み取りが終わっても、本体が空のままリクエストは振り分け
  られていました。
- 64 KiB の上限を超える長さの宣言は、黙って上限へ丸められていました。先頭の 64 KiB を読んだ時点で数が
  満たされ、途中までの本体が完全なものとして通っていました。

多くの経路は `400 missing or invalid JSON body` を返すので、失敗は目に見えます。ところが `/selectAll`
と `/copy` は、本体をまったく読みません。どちらも、途中までのリクエストで端末を実際に操作します。

3つめの作業単位で入れる受信タイムアウトは、この経路の到達範囲を狭めるどころか広げます。タイムアウトを
入れる前は、閉じた相手しかここへ来ませんでした。入れたあとは、単に止まっただけの相手も来ます。

一方で、継続的インテグレーションで観測された特定の失敗との因果は主張しません。上の証拠が確立したのは、
次の3点までです。

- 4つの不具合は、いずれも実在します。
- 1つめは、プロセスにとって致命的です。
- 4つとも、iOS のジョブがすでに失敗している症状と同じ形を作ります。

過去のある実行でどれが起きたかを特定するには、すでに残っていない runner の出力が必要になります。本項目
は、そこまで主張しません。

## 詳細設計

不具合ごとに1つ、合わせて4つの作業単位に分けます。互いに独立しており、4つとも runner の HTTP サーバ
（[`BajutsuKit/Sources/BajutsuRunner/HTTPServer.swift`](../../BajutsuKit/Sources/BajutsuRunner/HTTPServer.swift)）
に入ります。

1. **受け付けたすべての接続で `SIGPIPE` を抑止する。** accept ループの中で、受け付けたソケットごとに、
   ハンドラが触れる前に `SO_NOSIGPIPE` を設定します。
   - この設定により、立ち去った相手への書き込みはただの `EPIPE` になります。既存の送信ループは `EPIPE`
     を「書き込みを止める」合図としてすでに扱うので、他のコードは変わりません。
   - プロセス全体のシグナル設定は書き換えず、ソケット単位で設定します。ライブラリが、自分の抱える
     ホストプロセスの依存しうる大域の状態を書き換えるわけにはいかないからです。

2. **接続単位の `accept()` の失敗では、ループを終えずに再試行する。** 失敗を `errno` で分類し、listen
   中のソケット自体が壊れたときだけ、ループを終えます。
   - `EINTR`、`ECONNABORTED`、`EAGAIN`、`EPROTO` は、1本の接続に関する失敗です。ループは直ちに再試行
     します。
   - 開けるファイル数の上限とメモリの枯渇も、一過性です。該当するのは `EMFILE`、`ENFILE`、`ENOMEM`、
     `ENOBUFS` です。直ちに再試行すると、時間の経過でしか解消しない状態に対して空回りします。そこで
     短く待ってから再試行します。
   - それ以外は、従来どおりループを終えます。`stop()` が listen 中のソケットを閉じたときに生じる
     `EBADF` も含みます。

3. **2つのブロッキング呼び出しにソケットタイムアウトで上限を与える。** 受け付けたソケットごとに
   `SO_RCVTIMEO` と `SO_SNDTIMEO` を、それぞれ10秒と30秒で設定します。
   - リクエストのバイト列は、接続の直後にループバック上をマイクロ秒の単位で届きます。10秒止まる読み取り
     は、死んだ相手か、そもそもリクエストを送っていない相手です。単に遅い相手ではありません。
   - 応答の書き込みは、応答を待っている相手へ書きます。送信が止まるのは、閉じないまま読み取りをやめた
     相手がいる場合だけです。
   - 30秒は、driver 自身が持つ2つの上限のうち、広いほうと一致します。2つの上限とは、読み取りの15秒と、
     操作の実行の30秒です。30秒は、それを超えません。それで足りるのは、この上限に近づくほど大きな応答が
     スクリーンショットの PNG だけであり、その応答は15秒の読み取り経路を通るからです。
   - タイムアウトした読み取りは `EAGAIN` として現れます。解析器は、その値を閉じた相手と同じ扱いで
     すでに処理しています。

4. **クライアントが送り終えていないリクエストを受け付けない。** ヘッダと本体の双方に、同じ規則を通します。
   - ヘッダを終端する空行を解析器が見つけたかどうかを保持します。見つからなかった場合は、リクエストを
     解析不能として報告します。
   - 本体も同じ規則に従わせます。宣言された `Content-Length` に届かないまま読み取りが終わった場合は、
     リクエストを失敗とします。宣言された長さが解析できない場合、負の場合、64 KiB の上限を超える場合も
     同じです。
   - 本体を欠いたリクエストを返す形では、判断が経路ごとに委ねられてしまいます。`/selectAll` と `/copy`
     は本体をまったく読まないので、途中までのリクエストで端末を実際に操作します。
   - 解析不能なリクエストに 400 を返す処理は、呼び出し側にすでにあります。修正は解析器の内側に収まります。

テストは4つの作業単位をそれぞれ覆い、どのテストも、対応する修正を戻すと失敗します。`SIGPIPE` の作業
単位については、失敗ではなく、テストのプロセスが落ちます。

2つの作業単位は、実際の失敗を起こさずに検証します。1つは、設定済みのソケットからオプションを読み戻す
形です。もう1つは、`errno` の分類を直接列挙する形です。`SIGPIPE` の抑止も `accept()` の失敗も、実際の
listen 中のソケットに対して確実に起こせないからです。

残る2つの作業単位は、動作中のサーバに対する end-to-end のテストです。応答の途中で消える相手と、8つの
ハンドラ枠に対する9つの沈黙した相手を使います。

## 検討した代替案

- **`signal(SIGPIPE, SIG_IGN)` でプロセス全体のシグナルを無視する。** 1行で済みます。このサーバが受け付けた
  ソケットだけでなく、プロセスの持つすべてのソケットを覆えます。採用しなかったのは、`BajutsuRunner` が、
  自分の所有しないホストプロセスにリンクされるライブラリだからです。大域のシグナル設定を変えると、その
  ホストの無関係なコードの動作を黙って変えてしまいます。`SO_NOSIGPIPE` なら、効果をこのサーバが作った
  ソケットに限ったまま、同じ結果が得られます。
- **`accept()` の失敗を無条件に再試行する。** `errno` で分類するより単純で、機能停止も同じように防げます。
  採用しなかったのは、唯一の本当に致命的な場合を無限ループに変えてしまうからです。`stop()` が listen 中の
  ソケットを閉じたあと、`accept()` は `EBADF` で即座に、しかも永久に失敗し続けます。無条件の再試行は、
  プロセスの生存期間中、スレッドを全速で空回りさせます。
- **相手がすでに切断したリクエストを捨てる。** 一見すると魅力的な案です。メインスレッドのロック待ちに
  並んだハンドラは、driver が諦めたずっとあとに完了し、その操作が後続のステップの最中に届くことが
  あります。本項目の範囲外としたのは、2つの理由からです。
  - 切断を検出できるのは、ハンドラが動き出す前だけです。実際に見捨てられることが多いロック待ちの最中
    には検出できないので、この検査は不完全なものにとどまります。
  - より重要な理由として、操作するかどうかを競合の結果に委ねる設計は、第2のプライムディレクティブで
    ある決定性に反します。この論点は、耐障害性の修正の内側で操作の意味論を黙って変えるのではなく、
    独立した項目として扱うに値します。
- **リクエストのヘッダを1バイトずつではなくまとめて読む。** 解析器は1バイトごとに `recv` を発行して
  おり、典型的なリクエストのヘッダでおよそ150回のシステムコールを費やします。採用しなかったのは、
  ループバック上では1ミリ秒に満たない費用であり、本項目が扱う数秒単位のタイムアウトを説明できないから
  です。読み取り方を変えると、同じまとまりで届く本体のバイト列を、解析器が扱う必要も生じます。実測された
  利得のないまま、変更が大きくなります。
