## はじめに

ホスティングされた `bajutsu serve` の4つの endpoint は、job を id だけで解決します。その job が
呼び出し元の org のものかを確認しません。あるテナントのサインイン済みメンバーが、別のテナントの job を
読めます。その run のキャンセル、handoff への応答、ライブログの受信もできます。必要なのは job の id
だけです。本項目は、4つすべてを「呼び出し元が今いる org」でスコープして、この穴を塞ぎます。この規則は、
隣接する読み出しがすでに採用しているものです。

## 動機

serve のマルチテナンシーは、単一の門ではなく操作ごとに実施しています。どの読み出しも呼び出し元の org を
解決してから、自分が触るストアを絞ります。`list_scenarios`、`read_scenario`、アーティファクトの経路は
`state.org_of(actor)` を、`runs_payload` は後述の `state.org_for(actor, machine_org)` を、それぞれ通って
から対象に触れます（[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md)）。job
の endpoint だけが例外です。`state.jobs.get(job_id)` を読んで、そのまま仕事に入ります。

| endpoint | 操作 | 今日の org チェック |
|---|---|---|
| `GET /api/jobs/{job_id}` | `job_view` | 機械の主体のみ |
| `POST /api/jobs/{job_id}/cancel` | `cancel_job` | なし |
| `POST /api/jobs/{job_id}/respond-human` | `respond_human` | なし |
| `GET /api/jobs/{job_id}/events` | `job_sse`／`job_log_events` | なし |

role のゲートはこの隙間を覆いません。`required_role` は2つの書き込みを editor 限定にするので、viewer は
拒否されます。しかしゲートが答えるのは「この呼び出し元は editor か」であって、「この呼び出し元は*その job を
持つ org の* editor か」ではありません。どこかのテナントの editor であれば、すべてのテナントの job に
対して通ってしまいます。

[BE-0414](../BE-0414-ci-oidc-machine-identity/BE-0414-ci-oidc-machine-identity-ja.md) の単位3は、CI の機械の
主体について表の1行目を塞ぎました。許可リストが job のポーリングを開けるので、パイプラインをトークンの
交換先の org に閉じ込める必要があったからです。人間の経路は意図的に手を付けませんでした。そこを絞るのは
それ自体がテナント境界の変更であり、機械セッションの項目を広げて抱え込ませると、2つの判断が1つの変更に
混ざるからです。本項目がその後続にあたります。

露出の範囲は job の id で抑えられています。id は不透明で推測できないので、これは扉が開いている状態では
なく、機密性と完全性の欠落です。それでも読み出しよりは遠くまで届きます。別テナントの run のキャンセルは
進行中の作業を壊し、handoff への応答はそのテナントが見ている run に入力を注入します。

**検証可能な結果。** org B が投入した job の id を持つ org A のメンバーは、org A として振る舞っている間、
4つの endpoint すべてで拒否されます。拒否は403ではなく404なので、その id が実在の job を指すことを応答が
裏づけません。同じメンバーが org B に切り替えれば、同じ job に通常どおり到達できます。境界は呼び出し元が
今いる org に追随するのであって、その人を恒久的に締め出すものではありません。

## 詳細設計

作業は互いに排他かつ網羅的（MECE）な3つの単位に分かれます。ルーティングの表が一様に扱う3つの操作、各
バックエンドが自前の配管で提供するストリーミングの経路、そしてテストと文書です。

### 規則は「呼び出し元が今いる org」

4つの endpoint はいずれも、job 自身の org を `state.org_for(actor, machine_org)` と比べます。この
`org_for` は BE-0414 の単位3が導入したもので、人間の org と機械セッションの org が合流する唯一の場所です。
job は投入時の org を持つので（`Job.org` には投入時に `start_run`、`start_run_set`、`start_record`、
`start_crawl`、`start_triage` が刻み、job の仕様に載ってワーカーまで運ばれます）、比較に新しい状態は要りません。

**org を切り替えた呼び出し元は job を見失い、切り替え直せば戻ります。** これは規則に逆らう挙動ではなく、
規則から出てくる帰結です。そして、インタフェースの他の部分がすでに持っている挙動と同じです。run の履歴、
シナリオの一覧、ターゲットの一覧は、いずれもアクティブな org が変われば再びスコープされます。切り替えを
またいで答え続ける job の画面は、むしろ浮いた存在になります。

切り替えは完全に元へ戻せます。この点が、2つの読み出しだけでなく2つの書き込みについても、この規則を安全に
しています。`set_active_org` は `users.org_id` と `users.role` をまとめて書き換えます。そのため
`user_role` は常に「呼び出し元が今いる org で持つ role」を報告します。org A で run を投入し、何かを見る
ために org B へ移り、A へ戻ってキャンセルする流れは、したがって成立します。A へ戻れば org の比較は通り、editor の確認は A で
持つ role に対して走ります。可視性は「今どこにいるか」の関数であって、「その呼び出し元がどこを通ってきた
か」の関数ではありません。

**拒否は403ではなく404にします。** job の id は不透明なので、「権限がありません」と答えれば、その id が
別テナントの生きた job を指すことを裏づけてしまいます。拒否が伏せようとしている当の事実です。`job_view` は
BE-0414 の下で機械の主体に対してすでに404を返しており、残り3つの endpoint も同じ答えを採ります。これは、
どの endpoint も「そんな id の job はない」場合に返している答えでもあります。2つが見分けられなくなること
自体が狙いです。

### 単位1 — 一様な3つの操作

`job_view`（`bajutsu/serve/operations/reads.py`）はすでに確認を持っていますが、機械の主体についてだけです。
`job.org` を `machine_org` とだけ比べており、`actor` はそもそも受け取っていません。本単位は、隣の読み出しが
取るのと同じ `actor` 引数を与え、`state.org_for(actor, machine_org)` と比べるようにします。これで確認は、
呼び出し元が誰であっても解決済みの org に対して走ります。

`cancel_job` は今日 `(state, job_id)` だけを取り、`respond_human` は `(state, job_id, body)` だけを取ります。
どちらも actor は受け取っていません。両方に、隣の読み出しが取るのと同じ
`actor` と `machine_org` のキーワード引数を足します。ルーティングの表（`bajutsu/serve/routes/_shared.py`）は、
`job_view` にすでに渡している `ctx.machine_org()` に加えて、3つすべてに `ctx.actor()` を渡します。

機械の主体はどちらの書き込みにも到達しません。BE-0414 の許可リストがどちらの経路も挙げていないので、実際
には `machine_org` は None で届きます。それでも引数は受け取ります。前提にしないためです。許可リストは別の
ゲートであり、後から経路を開ける余地があります。自分の org を自分で解決できる操作は、どのゲートが
リクエストを通したかに依存しません。また、絞り込みを意図的なものとして、広げる変更を別のものとして記録
している `job_view` の docstring も、上の規則に合わせて書き直します。

### 単位2 — ライブログのストリーム

`GET /api/jobs/{job_id}/events` は `off_loop` です。各バックエンドが自前のストリーミングの配管で提供します。
stdlib のハンドラは `_sse_job` から `ops.job_log_events` へ、FastAPI のアプリは `ops.job_sse` へ進みます。
どちらも org を解決せず、actor も取りません。

両方の入口に、同じ引数の組と同じ確認を足します。ただし確認は**最初のフレームの手前**で一度だけ行い、
フレームごとには行いません。呼び出し元の org はそのリクエストの間は固定なので、フレームごとに確認すれば
1フレームあたり1回の解決を払うことになります。しかも、途中で org を切り替えた呼び出し元のストリームを
それで止められるわけでもありません。開いた後で呼び出し元が org を切り替えたストリームは、job の終わりまで
流れ続けます。切り替えが遡って効くのではなく次のリクエストから効く、という他の部分の扱いと揃います。

ストリームを開く前に拒否すれば、各バックエンドは通常の404で答えられます。クライアントがすでに読み始めた
イベントストリームの中で拒否を表現する必要がなくなります。

### 単位3 — テストと文書

Simulator とブラウザのどちらも使わず、高速な Python のスイートで覆います。

- org B が投入した job に対して、org A のメンバーは4つの endpoint すべてで拒否されます。拒否はいずれも404
  です。
- その拒否は、何も指さない job の id に対する答えと見分けがつきません。
- 同じメンバーが org B に切り替えれば、同じ job に4つとも到達できます。
- org A で投入した run は、org B へ移って A へ戻った後もキャンセルできます。境界は一方通行の喪失ではなく、
  元に戻せるものです。
- org の内側では editor のゲートが従来どおり効きます。org B の viewer は、org B 自身の job に対する2つの
  書き込みを拒否されます。
- 機械の主体は自分の org の job だけを読みます。BE-0414 の単位3が定めたとおりで、許可リストは2つの書き込み
  とストリームを引き続き拒否します。
- 単一テナントのデプロイ（ローカルの serve、データベースなし）は影響を受けません。どの呼び出し元も同じ
  `default` org に解決されるので、4つの endpoint は従来どおりに振る舞います。
- 2つのバックエンドは、ストリームの確認を同一に実施します。
- 拒否をそのまま黙って通してしまうフロントエンドの呼び出し箇所は2つあります。応答を破棄する `cancelJob` と、
  `EventSource` に `error` ハンドラを持たない `streamJob` です。この2つは拒否を表示するように変えます。古い
  org のままのタブに残った Stop ボタンは、「停止中…」で固まる代わりに job にもう到達できないことを表示し
  ます。最初のフレームより前に拒否されたストリームも、パネルが「実行中」のまま固まることがなくなります。
  handoff への応答はすでに non-ok の状態を表示しているので、変更は不要です。

`docs/self-hosting.md` と日本語版に、マルチテナンシーの記述の下へ短い注記を足します。job の endpoint は他の
読み出しと同じくアクティブな org に従うこと、そして org を切り替えると実行中の job は切り替え直すまで
見えなくなることを書きます。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| アクティブな org ではなくメンバーシップ（`eligible_orgs`）でスコープする | この案がアクティブな org による規則に勝る唯一の利点は、呼び出し元が自分の job を見失うことは決してない、という点です。ですが、それはすでに解決済みの問題に対する利点にすぎません。離れた呼び出し元は切り替え直せば job に戻れますし、`set_active_org` が role を org と一緒に動かすので、editor の確認はすでに job 自身の org に対して評価されています。この案が持ち込むのは、隣接するどの読み出しも使っている規則の横に立つ、2つ目のスコープ規則です。解くべき問題が残っていない2つ目の規則は、得るもののない負担です。 |
| 404ではなく403を返す | 失敗の理由については正直ですが、その id が別テナントの実在の job を指すことを開示します。呼び出し元が持っているのは id だけなので、それを裏づけることこそ避ける価値のある漏洩です。`job_view` は BE-0414 の下ですでに404を選んでおり、揃えれば4つで答えが1つになります。 |
| 操作ごとではなく `ServeState.jobs`／`JobRegistry` の内側で org を確認する | 1つの門ですべての呼び出し元を覆えるので魅力的です。しかしレジストリは id を鍵にした素朴な写像で、ランナー、ワーカーの結果の経路、メトリクスの読み出しが、いずれも actor なしで参照します。org を意識した参照にすると、それらすべてに任意の actor を通す必要が生じ、内部の呼び出し元に見えるものを黙って変えてしまいます。serve は他のどこでもテナンシーを操作ごとに実施しており、本項目もそれに倣います。 |
| ライブストリームのフレームごとに org を再確認する | 途中で org を切り替えた呼び出し元のストリームを止めることになります。1フレームあたり1回の org 解決を払ううえ、切り替えは他のどこでも次のリクエストから効きます。途中で死ぬストリームは、他の部分より安全な規則ではなく、他の部分より厳しいだけの規則です。 |
| 2つの読み出しは残し、書き込みだけをスコープする | キャンセルと handoff への応答は破壊的な2つなので、書き込みのほうが重いのは確かです。それでも、別テナントの job の画面とライブログを読めれば、シナリオ名、ステップの進行、ログの出力が漏れます。同じ境界の機密性の側です。分けても何も節約できないまま、項目が中途半端になります。 |

## 進捗

> 開発の進行に合わせて常に最新の状態に保ってください。チェックリストは *詳細設計* の MECE な
> 作業分解に対応し（作業単位ごとに1つ）、ログには何をいつ変えたかを古い順に記録し、PR を結びます。

- [ ] 単位1 — `job_view` を機械の主体からすべての呼び出し元へ広げます。`cancel_job` と `respond_human`
      には同じ `actor`／`machine_org` の引数と、同じ org の比較、同じ404を与えます。共有のルーティングの
      表から配線します。絞り込みを意図的なものとして記録している `job_view` の docstring も、上の規則に
      合わせて書き直します。
- [ ] 単位2 — ライブログのストリームの2つの入口（stdlib 側の `job_log_events`、FastAPI 側の `job_sse`）に
      同じ確認を与えます。確認は最初のフレームの手前で一度だけ行います。
- [ ] 単位3 — 各 endpoint と2つのバックエンドのテストを書きます。切り替えて戻る場合と、単一テナントで
      何も変わらない場合を含めます。`cancelJob` と `streamJob` が拒否を破棄せず、あるいはストリームを
      黙って固まらせずに表示するように変えます。あわせて self-hosting の注記を両言語に入れます。
