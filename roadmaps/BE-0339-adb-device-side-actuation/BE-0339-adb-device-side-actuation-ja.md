## はじめに

Bajutsu の Android バックエンドは、ジェスチャを 3 つの段階で実行します。ホストがアクセシビリティ
ツリーを読み、ホストが対象のピクセル中心を計算し、ホストがその座標へタッチを注入します。第 2 段階
と第 3 段階のあいだには、座標の出どころとなったツリーと画面がまだ一致していることを保証するものが、
何もありません。読み取りを新しく保つ試みは、ロードマップ項目 6 件ぶん積み上がりました。常駐
リーダー、実時間で上限を切った settle のポーリング、アクチュエーションを基準とするバリア、そして
デバイス時計の読み取りマークです。それでも継続的インテグレーション（CI）の `smoke (adb)` ジョブ
では、`gestures` シナリオが今も間欠的に落ちます。読み取りを新しくする工夫では、読み取りの後に開く
隙間を閉じられません。

本項目は、隙間を短くするのではなく取り除きます。デバイスが対象を解決し、同じ 1 回のデバイス側の
操作としてジェスチャを注入するので、タッチが着地する bounds は、注入の瞬間にデバイスが保持している
bounds そのものになります。決定的なコアが担う判断は、すべてホストに残します。セレクタがどの要素を
指すのか、そのセレクタが曖昧でないか、という判断です。他の 2 つのバックエンドは、すでにこの形で
動いています。Android バックエンドだけが外れており、本項目でその状態を終わらせます。

もう 1 つ、バリアの整備が開けたまま残した具体的な穴も、独立した最初の作業として塞ぎます。方向付きの
`swipe` が、バリアを通らない settle 前の読み取りからアンカーを解決している、という穴です。

## 動機

仕組みの説明よりも、落ちた実行のほうが欠陥を正確に指し示します。実行
[30746759314](https://github.com/bajutsu-e2e/bajutsu/actions/runs/30746759314) は、`smoke (adb)` で
[`gestures`](../../demos/showcase/scenarios/gestures.yaml) シナリオを落としました。

```
expect: expected equals='pressed' but actual='idle'; expected equals='1' but actual='0'
```

シナリオが実行した 2 つのジェスチャは、どちらも結果を残していません。このシナリオは、片方の対象を
長押しするとそのアクセシビリティ値が `pressed` を映し、もう片方をダブルタップするとその値が `1` を
映す、という作りです。2 つの値はどちらも、ジェスチャの前にシナリオ自身が assert し終えていた状態の
ままでした。

待ちの数字が、古い読み取りという説明を否定します。Android レーンは `BAJUTSU_MIN_WAIT_TIMEOUT=15`
を設定しており、末尾の `expect` ブロックは条件待ち（`_poll_asserts`、`bajutsu/orchestrator/loop.py`）
として、assert が通るかその予算を使い切るまでツリーを読み直します。15 秒遅れたツリーというのは、
このリポジトリのどの計測値よりもはるかに大きな遅れです。2 つのジェスチャはツリーに映る機会を逃した
のではありません。タッチが対象ではない場所に着地したために、2 つのジェスチャはそもそも起きていません。

実行自身が残した警告も、同じことを示します。シナリオの内側で、読み取り遅延のバリアが期限切れに
なった記録が 2 回出ています。

```
read lag: the last gesture did not change the projection within 4.0s — either the tree never
published it, or it moved no frame … Resolving from the current screen
```

このメッセージは、バリアが設計として認めた譲歩です。期限切れのときドライバは、確認できなかった座標
のまま先へ進みます。そうしない場合、frame を正当に動かさないジェスチャがすべて落ちてしまい、正しい
シナリオを落とすことになるからです。期限切れで譲歩せざるをえない予算は、保証にはなりません。

シナリオが意図しないスクロール位置からジェスチャに入る経路は、バリアの守備範囲に開いた穴 1 つで
説明できます。adb ドライバはセレクタ指定のアクチュエータを 5 つ持ちます。`tap`、`doubleTap`、
`longPress`、`pinch`、`rotate` です。いずれも `_center()` を通して対象を解決し、`_center()` は
`_settle()` を呼び、`_settle()` はまず保留中の追いつきバリアを待ち切ります。方向付きの `swipe`
だけが、そこを通りません。端点はドライバの外側の `_directional_endpoints`
（`bajutsu/orchestrator/actions/handlers/gestures.py`）で、素の `driver.query()` から計算されます。
読み取りは 1 回、settle なし、バリアなしです。ドライバは 2 つの座標を受け取るだけで、その座標が
どの要素に由来するのかを知りません。`AdbDriver.scroll` は `_pan_baseline` でバリアを待ちますが、
そのときには端点はもう確定しています。

`gestures` シナリオは、その穴がちょうど効く形をしています。対象を画面内へ送り込むために、
`swipe: { on: …, direction: up }` を 2 回続けます。2 回目の swipe は、1 回目の直後に取った 1 回きり
の無防備な読み取りからアンカーを解決します。
[BE-0332](../BE-0332-read-lag-barrier/BE-0332-read-lag-barrier-ja.md) が計測したとおり、Android の
ツリーがまだジェスチャ前の画面を表している、まさにその窓の内側です。`AdbDriver._READ_LAG_S` に記録
された計測値は具体的です。ある swipe が Log フォームを 73 ピクセル動かしたにもかかわらず、その
ジェスチャから 1.2 秒にわたる 4 回連続の読み取りが、いずれも swipe 前の frame を返していました。
73 ピクセルずれたアンカーは 2 回目の swipe を誤った位置から始めさせ、フォームはシナリオが意図しない
位置で止まります。

この穴 1 つを塞ぐことには単独の価値があり、以下の作業単位 1 がそれにあたります。ただし、それで欠陥
の系統が閉じるわけではありません。アンカーがバリアを通り、読み取りが完璧だったとしましょう。それ
でもホストは、ツリーを読み、そこから座標を計算し、その座標を `adb shell input` に渡しています。
`adb shell input` 自身のプロセス起動にも、タッチが画面へ届くまでにさらにコンマ数秒かかります。
その窓の内側で画面が動けば、タッチはその時点でその座標を占めているものに着地します。動く理由は
珍しくありません。fling が収まりきる、再コンポーズが走る、システムダイアログが出る、といったこと
です。窓は小さく、CI のエミュレータは遅く、レーンは関係する pull request のたびにツールキットごと
に 17 シナリオを走らせます。それだけ繰り返し標本を取れば、小さな窓は flake になります。

他の 2 つのバックエンドには、そもそもこの窓がありません。しかもその違いは、偶然ではなく構造から
来ています。XCUITest バックエンドは、セレクタを一意の要素へホスト側で解決し、デバイスにはその要素
への**ハンドル**を渡します。ランナーはハンドルを生きた要素ツリーに対して解決し、その瞬間に要素が
持っている bounds に対して操作します（`bajutsu/drivers/xcuitest.py` の `_resolve_handle` と
`_actuate`）。要素が消えたハンドルは `stale` として返り、ドライバは座標に触れる代わりに再解決します
（[BE-0289](../BE-0289-xcuitest-stale-handle-reresolve/BE-0289-xcuitest-stale-handle-reresolve-ja.md)）。
ハンドルは要素の同一性から導かれるので、変化していない画面ではハンドルが有効なまま保たれます
（[BE-0312](../BE-0312-xcuitest-content-addressed-snapshot-handle/BE-0312-xcuitest-content-addressed-snapshot-handle-ja.md)）。
Playwright バックエンドは座標を計算しますが、ブラウザは読み取りに同期的に答え、ページはレイアウトを
読み取りの裏で非同期に publish しないので、同等の窓は存在しません。非同期に publish されるツリーから
ピクセル座標を計算し、それを目隠しで注入しているのは、adb バックエンドだけです。

隙間を閉じるための継ぎ目は、Android 側にすでにあり、Bajutsu もその上で動いています。常駐
UI Automator サーバ
（[BE-0245](../BE-0245-adb-resident-uiautomator-server/BE-0245-adb-resident-uiautomator-server-ja.md)）
は、暖まった `UiAutomation` を保持し、ループバックのソケット越しに `GET /source` へ答える、長命な
instrumentation セッションです。階層をダンプするそのセッションは、ノードを探してクリックすることも、
同じプロセスの中で数マイクロ秒の間隔でできます。読み取りは速度のためにデバイスへ移しました。
アクチュエーションをデバイスへ移すのは、正しさのための同じ一手です。

## 詳細設計

本設計は、決定的なコアを今ある場所に置いたまま、座標の計算だけを動かします。セレクタの意味づけは
ホストに残ります。`resolve_unique` がセレクタの指す要素を決め、曖昧なセレクタは最初の一致に対して
操作せず、即座に失敗します（原則 2）。デバイスへ渡るのは、すでに選び終えた 1 つの要素の**同一性（identity）**です。ダンプしたツリーと
生きたノードの双方が持つ 4 つのアクセシビリティ属性と、それらを共有する兄弟のなかでの序数
（index と count）を、ダイジェストにせずそのまま送ります。ホストとデバイスがハッシュで合意する
必要をなくすためです。デバイスが下す判断は、その同一性がいまも `count` 個のノードを指し、
`index` がその範囲に収まるかどうか、それだけです。指さないときは `stale` と答え、座標へ退避する
ことはありません。

すべての作業単位を、2 つの制約が縛ります。原則 3 により、変更はアプリ非依存に保ちます。同一性は
ツリーがすでに持っているアクセシビリティ属性から組み立て、アプリごとのつまみは 1 つも導入しません。
原則 2 は固定の `sleep` を禁じます。デバイス側の経路は待ちを足すのではなく減らすものであり、待ちが
残る箇所も上限付きの条件待ちのままにします。

### 作業分解（`MECE`）

以下は、相互に重複せず全体を覆う（Mutually Exclusive, Collectively Exhaustive、`MECE`）作業単位です。

1. **方向付きジェスチャのアンカーを、ドライバのアクチュエーション用の読み取りから解決します。**
   方向付きの `swipe` と `drag` は、`_directional_endpoints` で素の `driver.query()` からアンカー
   要素を解決しており、セレクタ指定のアクチュエーション経路のうち、他がすべて通る settle と追いつき
   バリアを唯一通りません。「アクチュエーション対象を解決してよいツリーを読む」という手段を、
   `bajutsu/drivers/base.py` の `ViewportProvider`、`ReadLagProvider`、`ReadOrderProvider` と並ぶ
   狭い構造的プロトコルとして、ドライバに任意で持たせます。adb ドライバは既存の settle でこれを
   実装し、他のバックエンドは実装せず、1 回の読み取りをそのまま保ちます。この作業単位は残りから
   独立しており、最初に出します。
2. **常駐 UI Automator サーバから、同一性指定でアクチュエーションを提供します。** 常駐サーバに
   `POST /act` を追加します。リクエストは動作（`tap`、`doubleTap`、時間つきの `longPress`）と、
   対象の同一性および序数を指定します。サーバは `UiDevice` を通して
   その同一性を生きたアクセシビリティツリーに対して解決し、ノードの現在の bounds を読み、暖まった
   同じ `UiAutomation` セッションからジェスチャを注入します。どのノードにも一致しない同一性、
   あるいはホストが数えたのと異なる個数に一致する同一性には、注入せずに `stale` と答えます。
   ダブルタップはプロセス内で注入するので、2 回のタップは生の `sendevent` 列と、それが必要とする
   `adb root` なしに、プラットフォームのダブルタップ判定時間へ収まります。
3. **要素を生のアクセシビリティ属性で指し示し、adb ドライバのアクチュエータをそこへ通します。**
   同一性は、ダンプしたツリーと生きたノードの双方が持つ 4 つの属性、すなわちリソース識別子、
   content description、クラス、テキストを、ダイジェストにせずそのまま送るものです。ホストと
   デバイスがハッシュで合意する必要をなくすためです。この 4 つを共有する兄弟のなかでどのノードを
   指すかは、別立ての序数（index と count）が決めます。変化していない画面では同一性が有効なまま
   保たれるという性質は、BE-0312 が XCUITest のダイジェストベースのハンドルで確立したのと同じ
   ものです。`AdbDriver.tap`、`long_press`、`double_tap` は、セレクタをホストで解決してから、
   その同一性と序数を送ります。`pinch` と `rotate` は座標のままです。2 本指のジェスチャが必要
   とするのは中心ではなく frame だからです。`stale` の応答は、BE-0289 と同じく上限つきで再照会
   して送り直します。一致が 0 個または複数の場合は、従来どおりホストから `ElementNotFound`
   あるいは `AmbiguousSelector` を送出し、再試行を 1 回も消費しません。
4. **座標の経路は、デフォルトではなく明示された縮退モードとして残します。** 常駐チャネルを持たない
   デバイス、たとえば古いサーバや実行中に死んだチャネルでも、動き続ける必要があります。座標の
   アクチュエータは残し、チャネルが使えないときにだけ到達するようにして、読み取りチャネルの縮退が
   すでにそうしているのと同じ形で記録します。残してはならないのは、2 つの経路が黙って切り替わる
   ことです。実行は、どちらのアクチュエーション経路を使ったのかを報告します。
5. **読み取り遅延のバリアを、今も必要とする読み取りだけへ絞ります。** アクチュエーションがデバイス
   側で解決されるようになると、追いつきバリアはもう座標を守っておらず、アクチュエータの経路は
   バリアを張るのをやめます。バリアが残るのは、満たすべき assert を持たないまま読み取りがアクション
   より後であることを本当に必要とする箇所、すなわち `extract` のポーリングと `scroll` の停止条件
   です。これは BE-0332 の作業単位 1 が主張する、より狭い範囲そのものです。`tap`、`long_press`、
   `double_tap` からバリアを外すことで、frame を動かさないときにそれらが払っていた 4 秒の譲歩も
   なくなります。
6. **契約を、決定的なスイートと実機の双方で覆います。** 高速ゲートは、同一性の一致、
   `stale` の再解決ループ、座標への縮退、そして新しいプロトコルの不採用（実装しないバックエンドが
   従来どおり振る舞うこと）を覆います。ドライバ適合性スイート（BE-0114）は、高速ゲートが届かない
   契約を足します。ジェスチャの後、デバイスが操作した要素が、セレクタの指した要素であることです。
   Android レーンでは `gestures` シナリオを繰り返し実行します。3 回に 1 回ほど現れる欠陥は、1 回の
   緑では否定できないからです。

### 検証

この欠陥は開発機では再現しません。Apple シリコンの `bajutsu_api34` エミュレータはすべての読み取りに
最新の状態で答え、Android レーン全体がローカルでは通ります。遅れも flake も、CI の x86_64
エミュレータに属する現象です。したがって検証はそちらで行い、`gh workflow run android-e2e.yml --ref
<branch>` で dispatch します。ブランチではレーンを `gestures` へ絞り、1 回の dispatch のなかで、
1 回の試行ではなく失敗率を標本化できるだけの回数を繰り返します。修正を証明する計測は、欠陥を計測
したものと同じです。アクチュエーションのたびに、ホストが解決した bounds とデバイスが操作した bounds
を記録し、両者が同じ要素を指すことを要求します。

作業単位 1 と 5 には、高速ゲートに関わる帰結が 1 つあり、明示しておく価値があります。どちらも、
読み取り遅延を申告しないバックエンドの挙動を変えるわけにはいきません。決定的なスイートがそれを
固定するので、不採用側の退行はエミュレータではなく Linux 上で落ちます。

## 検討した代替案

**読み取り遅延の予算を広げる。** 予算はすでに 4 秒あり、独立した 2 つの計測から寸法を取っています。
そして落ちた実行は、ツリーがジェスチャを確認しないまま予算を 2 回使い切りました。予算を広げること
は、実行時間と引き換えに失敗率を下げるだけで、期限切れの譲歩には手が届きません。frame を正当に
動かさないジェスチャは、どれだけ長く待ってもバリアを満たせないからです。

**バリアが期限切れになったら、先へ進まず実行を落とす。** これは flake を明確な失敗へ変えるもので、
正直ではありますが修正ではありません。バリアが区別できない無害な場合、すなわち内容の末尾にすでに
達している pan や、映した値だけを変えるタップは日常的に起きるので、レーンは正しいシナリオで落ちる
ようになります。ドライバはツリーだけからこの 2 つを区別できません。答えがデバイスから来なければ
ならない理由が、まさにそこにあります。

**事後に検証する。すなわち何かが変わったかを確認し、変わっていなければジェスチャを再試行する。**
すでに適用済みである可能性のあるアクチュエーションの再試行は、一般には安全ではありません。半分だけ着地
したダブルタップは、3 回のタップになります。しかもこの確認には健全な停止条件がありません。正しい
ジェスチャが観測可能な変化を何も起こさないことがあるからです。デバイス側の経路は、結果を疑わしい
まま残さないことで、この問いそのものを回避します。

**座標を注入する直前に読み直す。** これは窓を閉じずに狭めるだけで、しかもジェスチャのたびに追加の
読み取りを払います。読み取りは adb における 1 ステップあたりの支配的なコストであり、
[BE-0234](../BE-0234-adb-run-performance/BE-0234-adb-run-performance-ja.md) はまさにその主題なので、
この取引は同じ flake を小さくする代わりに実行を遅くするものになります。

**セレクタの解決までデバイスへ移し、同一性ではなくセレクタを送る。** これは同じ考えをさらに進め
たもので、原則 2 によって退けます。セレクタがちょうど 1 つの要素に一致すると判定することは、決定性
コアの判断です。それを Kotlin のサーバへ移せば、決定的なスイートの手が届かなくなり、1 つの規則が
2 つの言語に分かれます。同一性は判断をホストに残し、その結果だけを送ります。

  のないジェスチャにだけ固定の費用がかかるわけで、しかも `_await_catchup` のタイムアウトの文言自身が、
  そうしたジェスチャを珍しくないものとして扱っています。確認が取れたジェスチャのほうで窓が買うのは、
  読み取り 1 回です。バリアを張れば `_settle` は `_await_catchup` のポーリングの sleep と、まるごと
  1 回分の `query()` から始まります。このバックエンドではステップあたりの費用の大半がそこにあります
  （BE-0234）。窓を短く取るのはこの交換であって、ただ得をする話ではありません。窓が決めないのは、
  バリアを省略してよいかどうかです。

  ヘッダが運ぶマークは、数えるだけでなく比較します。`since` と publish のマークはどちらも
  `SystemClock.uptimeMillis` の値なので、報告されたイベントが本当にジェスチャより後かをドライバが
  確かめます。ヘッダがあることだけを信用すると、後になっていない値（ヘッダを転用したサーバ、前の
  inject から持ち越された値）でバリアを外してしまうからです。

  高速ゲートは規則の両側を固定するので、差し戻された形が黙って戻ってくることはありません。確認が
  取れたデバイスタップはバリアを張らず、次の読み取りに `?since=` を持たせないこと。確認が取れなかった
  ものは従来どおり張ること。確認が取れたタップの後の `swipe` は、自分のバリアを自分で張ること。
  作業単位 2、作業単位 3、作業単位 6 のときと違い、この変更はリリース前にコンパイラと実機の両方に
  当たっています。今回の執筆環境には JDK と Android SDK がそろっています。そのため Kotlin をローカルで
  コンパイルでき、Compose のレーンを `bajutsu-api34-arm64` のエミュレータで実行できました。`gestures`
  の実行は、この仕組みが両方向に働くことを示しています。長押しは `publish confirmed at 82535; no
  catchup barrier armed` を記録しました。続く読み取りは何にもブロックされずに 0.20 秒で返り、まさに
  そのマークを持っていました。ダブルタップは確認が取れずにバリアを張り、その次の読み取りはデバイス側の
  `since` の予算を使い切りました。このダブルタップで省略していたら誤りでしたが、規則は省略しません
  でした。ローカルの実行が示せないのは残存率です。前掲の**検証**がすでに記録しているとおり、この flake は
  Apple シリコンのエミュレータでは再現しません。したがってここでの証拠が覆うのは、仕組みが働くことと
  回帰がないことまでです。

  作業単位 6 はこの変更の影響を受けません。実機の適合性ケースの実現と、flake の残存率を測る Android
  レーンの繰り返しディスパッチが、依然としてそこに残っています。
