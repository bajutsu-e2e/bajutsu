## はじめに

Bajutsu はアプリのネットワーク通信を、ループバック上に立てた小さなコレクタ経由で観測します。被テスト
アプリは自分が出したリクエストごとに1件のレコードを POST し、コレクタはそれをメモリに保持して
ステップの `request` アサーションに検査させ、証拠として `network.json` に書き出します。同じ受信側は
`/transitions` という別のパスで画面遷移の報告も受け取り、readiness ゲートと `settled` の待機が
「画面遷移が完了した」という肯定的な信号として参照します。

本項目では、コレクタが解釈できない報告を拒否するようにします。これまでは渡された JSON オブジェクトを
すべて受け入れていました。2つのレコード型はどちらも全フィールドにデフォルト値を持ち、未知のキーを
無視するため、検証は決して失敗しません。その結果、ある型のフィールドを1つも共有しないペイロードは、
エラーではなくその型の空のレコードになっていました。今後はそうしたペイロードを捨て、キー名だけを
ログに出します。

## 動機

2つの帰結が実際に観測されており、それぞれ代償の重さが違います。

軽いほうは証拠を無駄にします。2026-08-13 の `visual (xcuitest)` ジョブは、あるシナリオの
`network.json` に全フィールドが空のレコードを99件書き出しました。メソッドも、アドレスも、パスも、
ヘッダもありません。このファイルは証拠として役に立たず、レコードは互いに区別できないため、何が送った
のかを示すものは1つも残っていませんでした。手元で形を再現すると機構が確認できます。
`{"kind": "screenChanged", "timestamp": 12345.6}` を、あるいは `{}` でさえ、exchange のモデルで
検証すると、その99件とバイト単位で一致する出力が得られます。送信元は依然として不明ですが、これは
無関係な欠落ではなく欠陥の後半です。コレクタはペイロードを拒否せず、ログにも残さなかったので、由来を
示す証拠がどこにも残っていません。

重いほうは readiness ゲートに届きます。遷移のレコードは `kind` しか持たないので、`/transitions` へ
誤って送られたネットワーク交換は、`kind` が空の遷移として検証を通ります。ゲートはそのレコードを本物
として扱います。遷移の受信時刻だけを参照し、`kind` を決して検査しないからです。つまり誤送信が1件でも
あれば、画面遷移が起きていないのに完了したと結論します。ゲートは決定的な条件待ちであり、それが待って
いる信号こそ、空のレコードが捏造するものです。

一方で、どちらの失敗も今日のアプリ側コードからは到達しません。本項目は `BajutsuKit` の不具合を主張
しません。`BajutsuKit` の2つの報告経路は本来のパスへ POST しており、コレクタの振り分けもそのパスに
従います。どちらも動作中のコレクタに対して確認しました。変更を正当化するのは、検証の層が誤送信
された報告と本物を区別できないという点です。将来の報告経路、エンドポイント、あるいは
ソフトウェア開発キット（SDK）のいずれかがパスを間違えれば、捕まらずに保存されます。理解できなかった
ペイロードからコレクタが作り出したレコードは、レコードがないことより悪いのです。読む側が両者を
区別できないからです。

## 詳細設計

1つのヘルパを共有する2つの作業単位で、どちらも
[`bajutsu/evidence/network.py`](../../bajutsu/evidence/network.py) に入ります。

1. **検証の前に、認識できるキーを少なくとも1つ要求する。** レコード型ごとの認識キー集合を、モデル
   自身（フィールド名とその JSON エイリアス）から導出し、記述対象のモデルから乖離しないようにします。
   ある型のキーを1つも共有しないペイロードは捨てます。先へ進むには認識キーが1つあれば十分で、これに
   よって `extra="ignore"` をモデルへ与えた目的である前方互換性が保たれます。フィールドを追加した
   新しい SDK は依然として検証を通り、共通点がまったくないペイロードだけが拒否されます。

2. **捨てたペイロードのキー名をログに出す。** warning レベルで、ペイロードが持っていたキーを挙げて
   ログに出します。次に起きたときに、帰属不明の空レコードを残す代わりに送信元を特定できるようにする
   ためです。ログに出すのはキー名だけで、値は決して出しません。報告はリクエストとレスポンスの本体や
   ヘッダを運び、それはまさに redaction の層が共有される証拠から排除するために存在するものです。
   ログに出すキーの個数には上限を設け、極端なペイロード1件がログを埋め尽くさないようにします。

捨てたペイロードに対しても、コレクタは 400 ではなく 204 を返し続けます。2つの報告経路はどちらも
fire-and-forget で状態コードを読まないため、状態コードは誰にも届きませんが、ログは失敗した実行を
読む保守担当者に届きます。

## 検討した代替案

- **モデル側で識別用フィールドを必須にする。** exchange のモデルに `method` を、遷移のモデルに
  `kind` を必須で持たせ、追加のコードなしに検証で異物を拒否させる案です。採用しなかったのは、
  フィールドの欠落が不正な値と同じ扱いで失敗してしまい、この2つは扱いを分けるに値するからです。
  不正な値は意図的に黙って捨てており、そうすることで SDK の変更が実行を途中で壊さないようにして
  います。一方、まったく認識できないペイロードこそログに出す価値がある場合です。必須化はまた、
  正当な理由でそのフィールドを省く SDK まで失敗させます。
- **ログではなく 400 で拒否する。** 原理的にはより目立ち、診断を送信側に置けます。採用しなかったのは、
  2つの報告経路がどちらも fire-and-forget でレスポンスを読まないためです。状態コードは観測可能な
  違いを何も生まず、バッチのエンドポイントは混在したバッチに対して単一の状態を決めなければならなく
  なります。
- **パスではなくペイロードの形で振り分ける。** フィールドが示す先へ各報告を保存し、パスの誤りを
  無害にする案です。採用しなかったのは、明示的な契約を推測へ置き換えてしまい、しかも本項目が
  表面化させようとしている誤送信を黙って修復するからです。誤ったエンドポイントへ POST する
  報告経路は、保守担当者が見るべき欠陥であって、受信側が覆い隠すものではありません。
- **捨てたペイロード全体をログに出す。** 診断にはもっとも有益です。採用しなかった理由は作業単位2に
  挙げたとおりで、報告の値は本体とヘッダ、すなわち実行のもっとも機微な証拠であり、キー名だけで
  すでに送信元は特定できます。
