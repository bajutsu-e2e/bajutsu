## はじめに

ロードマップステータスダッシュボードに、項目どうしの関係を描く関係図を追加します。このダッシュボードは GitHub Pages のページで、これまでに3つの変更を重ねています。

- [BE-0094](../BE-0094-roadmap-status-dashboard/BE-0094-roadmap-status-dashboard-ja.md) が、各項目のメタデータからページを生成します。
- [BE-0219](../BE-0219-roadmap-dashboard-search/BE-0219-roadmap-dashboard-search-ja.md) が、検索ボックスを追加しました。
- [BE-0311](../BE-0311-roadmap-dashboard-table-view/BE-0311-roadmap-dashboard-table-view-ja.md) が、ソート可能なテーブル表示を追加しました。

ロードマップ項目のメタデータ欄には、その項目と関係を持つほかの項目がすでに書かれています。`関連` はまとめて読むべき項目を並べ、`由来` はその項目が派生した元の項目を記録し、`後継` は置き換えた項目を指します。しかし、これらの関係を図として描く表示はありませんでした。

関係図は、Cards と Table に並ぶ第3の表示として関係を描きます。1つの項目がノード1つになって状態の色を持ち、1つの関係が辺1つになります。配置は、読者のブラウザで動く力学モデルのシミュレーションが決めます。読者はノードをドラッグでき、キャンバスを平行移動と拡大縮小で動かせます。ノードにポインタを重ねると、隣接する項目だけが明るく残ります。検索ボックスとステータスチップは、ほかの2つの表示と同じように関係図も絞り込みます。

関係図は、新しいメタデータのフィールドを増やしません。書き手に新たな保守を求めることもありません。描かれる辺はすべて、項目がすでに宣言している関係を読んだものです。したがってこの図は、コミット済みのロードマップをそのまま描画したものであり、ロードマップと食い違いうる第2の記録にはなりません。

## 動機

現在のダッシュボードは、項目を1つずつ見る問いに答える作りです。Cards はトピックごとに項目をまとめて、各項目の状態を示します。Table は ID・タイトル・トピック・状態・日付のいずれかで全項目を並べ替えます。どちらもロードマップを一覧として扱う表示です。一覧では、**構造**についての次の問いに答えられません。

- 1つの機能のまわりに、どの項目が集まっているのか。
- 後続の項目がいくつもぶら下がっている中心の提案は、どれか。
- ロードマップのどの部分が孤立しているのか。

構造についての問いの答えは、すでにメタデータの中にあります。見る方法がないだけです。ある項目の `関連` の行を読めば、その項目に隣接する項目はわかります。しかし、そのまわりのまとまり全体に届くには、隣接する項目を1つずつ開き、積み上がった像を記憶に保ち続けなければなりません。ロードマップには約330件の項目があり、そのうち約200件が少なくとも1つの関係に加わっています。この規模の探索は、手作業ではこなせません。しかもこの探索は、貢献者が新しい作業の範囲を見積もるときに行うものです。提案について最初に立つ問いは、それが何に触れるのかだからです。

ダッシュボードはドキュメントサイトの静的な生成物なので、この変更はどの絶対的指針（[`CLAUDE.md`](../../CLAUDE.md)）にも抵触しません。

- 大規模言語モデル（LLM）は、このページの近くに一切現れません。
- `run` や継続的インテグレーション（CI）の合否判定の経路も、ここを通りません。
- 関係図はメタデータが生む項目に対して汎用なので、テスト対象のアプリケーション固有の要素も持ちません。

判定の経路から離れていても、決定性はこの設計を形作ります。配置の初期位置は、乱数生成器ではなく各ノードの添字から決めます。同じロードマップからは常に同じ図が得られ、読者が自分の画面と同僚の画面を見比べても同じ形が見えます。

## 詳細設計

ダッシュボードは [`scripts/build_roadmap_dashboard.py`](../../scripts/build_roadmap_dashboard.py) が生成します。各項目をトピックの節の中の `.be-card` として描き、同じ項目を `.be-row` のテーブル行に写します。1つのインライン `<script>` ブロックが、両方を段階的に拡張します。関係図は、この既存の構造に第3の兄弟要素として収まります。作業は、互いに重複がなく全体を覆う（MECE な）次の単位に分かれます。

1. **共有の項目モデルへの関係の追加**。[`scripts/build_roadmap_index.py`](../../scripts/build_roadmap_index.py) の `Item` に、メタデータがすでに宣言している3つの関係を追加します。`related`、`origin_refs`、`superseded_by` で、それぞれ項目 ID のタプルです。
   - 英語側のメタデータ欄の `Related`、`Origin`、`Superseded by` の値から、`BE-NNNN` の形をした字句をすべて拾います。値は書き手が書いた Markdown で、1つ以上のリンクを含みます。字句を拾う読み方なら、書き手が選んだリンクの書き方と無関係に読めます。
   - 読み込んだツリーにディレクトリが存在しない ID と、項目が自分自身を指す参照は落とします。1つのファイルの誤記から、端点のない辺が生まれることはありません。
   - 英語ファイルだけから関係を読むのは、`Status` と `Topic` をすでにそう読んでいるのに合わせるためです。日本語側だけの言い回しの修正で図が変わることも防げます。
2. **ページへのグラフデータの出力**。関係図が必要とするノードと辺を、`<script type="application/json">` 要素の中の1つの JSON として出力します。既存のカードのマークアップに属性として散らさないのは、辺が項目の対に属するもので、どちらか一方のカードに置く自然な場所がないからです。
   - ノードは、ID、タイトル、トピック、状態のバケット、GitHub 上のファイルへのリンクを持ちます。
   - 辺は、2つの端点と種別を持ちます。
   - `関連` は双方の項目が宣言することを期待される相互の関係なので、2つの向きを1つの無向辺にまとめます。
   - `由来` と `後継` は有向のままにします。「そこから派生した」と「それに置き換えられた」は、どちらも一方向にしか読めない関係だからです。
3. **力学モデルによる配置**。配置は、このページのために書いた小さなシミュレーションがブラウザ上で計算します。力は3つです。
   - すべてのノードの対にはたらく斥力
   - すべての辺にはたらく引力
   - 連結していない部分がキャンバスの外へ流れ去らないようにする、弱い中心への引力

   決められた回数だけ冷却しながら回し、その後で停止します。細部は次のとおりです。
   - 初期位置は `Math.random()` ではなく、各ノードの添字から黄金角の螺旋上に決めます。配置は再現します。
   - 斥力は、理想的な辺の長さの数倍を超えたところで打ち切ります。落ち着いた結果は、キャンバスに収まるよう拡大縮小します。ロードマップの関係は、1つの大きな連結成分と多数の小さな連結成分からなり、成分どうしを引き留めるのは中心への引力だけです。2つの手当てがなければ、小さな成分は外へ流れ去り、大きな成分は読めない塊に潰れます。
   - シミュレーションは、ページの読み込み時ではなく、読者が最初に関係図を開いたときに回します。Cards から動かない読者に、計算の負担を負わせないためです。
4. **描画と操作**。結果はスケーラブルベクターグラフィックス（SVG）で描きます。辺ごとに線を1本、ノードごとに円を1つ描きます。円は項目の状態の色を持ち、大きさはその項目が加わっている関係の数で決まります。
   - ラベルを常に出すのは、中心となるノードだけです。200個のラベルを同時に出せば読めなくなるからです。残りのノードは、ポインタを重ねたとき、フォーカスを当てたとき、そしてツールチップで自分の ID を示します。
   - 各ノードは、項目の GitHub 上のファイルを指す SVG のアンカー要素で包みます。クリックハンドラを付けた図形ではなく、本物のリンクになります。キーボードからも辿れ、新しいタブでも開けます。
   - ノードのドラッグはノードを動かし、続いて発火するクリックを抑止します。ドラッグでページを離れてしまうことはありません。
   - 背景のドラッグは平行移動、マウスホイールは拡大縮小にあてます。
   - ノードにポインタを重ねるかフォーカスを当てると、そのノードと辺、そして辺の先の項目以外が暗くなります。
5. **既存の表示切り替えへの第3の選択肢の追加**。`Cards` と `Table` の隣に `Graph` のボタンを足します。1つの表示だけを見せて残りを隠し、読者の選択を `localStorage` に保存する既存の仕組みを、そのまま使います。
   - 関係図は、検索ボックスとステータスチップにも従います。絞り込みで外れた項目のノードは、辺ごと隠れます。残ったノードは、外れた隣接項目のぶんだけ辺が減った姿になります。
   - ダッシュボードのほかの操作と同じく、関係図も段階的拡張です。関係図の領域はマークアップでは隠されていて、表示の切り替えでしか現れません。スクリプトを無効にした読者には、現在とまったく同じ Cards 表示が見えます。
6. **図に描かない項目の扱いを隠さないこと**。どの辺にも乗らない項目は、関係図に描く場所を持ちません。約130個の孤立した点を図のまわりに並べれば、関係図が見せようとしている構造がその中に埋もれます。そこで、少なくとも1つの関係に加わっている項目だけを描き、描かなかったことをページ上に明記します。関係図が何件を描き、何件がどの関係にも加わっていないのかは、図に添えるキャプションが伝えます。

   キャプションの言い回しは「宣言している」ではなく「加わっている」にします。両者は一致しないからです。`由来` は一方向です。`関連` に期待される相互宣言は、検査されない慣習にすぎません。そのため、自分では関係を1つも宣言していないのに、ほかの項目から名指しされて描かれる項目があります。そうした項目について「関係を宣言している」と書けば、事実に反します。ダッシュボードが見せるデータについて、BE-0094 は2つの原則を立てました。メタデータに根拠のない数値を出さないことと、ある表示に実際にはない網羅性を読者へ暗示させないことです。作業単位6は、その2つを守るためにあります。
7. **スタイル**。関係図のキャンバス、ノード、辺、キャプションのスタイル規則を、生成側のスタイルシートに足します。色は、カードとバッジがすでに使っている状態ごとの色を再利用します。ノードの色がページのどこでも同じ意味を持ち、明るいテーマと暗いテーマのどちらでも読めるようにするためです。
8. **テスト**。[`tests/test_roadmap_dashboard.py`](../../tests/test_roadmap_dashboard.py) と [`tests/test_roadmap_index.py`](../../tests/test_roadmap_index.py) を拡張して、機械的に検査できる成果を固定します。
   - メタデータ欄から関係のフィールドが読めること。
   - 自分自身への参照と、存在しない項目への参照がどちらも落ちること。
   - 相互に張られた `関連` の対が、ちょうど1本の無向辺になること。
   - 出力されるすべての辺の端点が、出力されたノードであること。
   - 出力されるノードの集合が、関係を持つ項目そのものであること。
   - ページが3つ目の切り替えボタンと関係図の領域を描くこと。

   これらのテストはブラウザを必要としないので、ゲートは速いまま、LLM とも無縁のままです。

ページ冒頭の説明文には、Cards と Table を説明している文の隣に、第3の表示を説明する一文を足します。[`docs/`](../../docs/README.md) 配下のドキュメントに対応する修正は必要ありません。ダッシュボードに言及しているページは、ダッシュボードが何のためのものかを説明していて、どの表示を備えるかは書いていないからです。将来そこに表示を列挙する記述が生まれたときは、表示を追加する変更と同じ変更で更新します（[BE-0113](../BE-0113-design-doc-realignment/BE-0113-design-doc-realignment-ja.md)）。

## 検討した代替案

- **Mermaid でビルド時に図を生成する**。ドキュメントサイトはすでに `mermaid` のコードフェンスを
  描画できるので、生成した `graph LR` のブロックを埋め込む案が変更としては最小です。採用しませんでした。
  Mermaid はこの規模のグラフを、縦横に長い階層として配置します。読者に残るのは探索ではなく
  スクロールであり、絞り込み、ドラッグ、隣接の強調のいずれも使えません。約200個のノードを持つグラフを
  読めるものにしているのは、まさにそうした操作です。Mermaid の図は項目ごとの要素ではなく1つの不透明な
  ブロックとして描画されるので、既存の検索ボックスとステータスチップも働きかける先を持ちません。
- **D3 や Cytoscape のようなグラフ描画ライブラリを導入する**。採用しませんでした。ドキュメントサイトは
  JavaScript のバンドラーを持たず、外部スクリプトへの依存も持っていません。ダッシュボード全体が、
  インラインのスタイルと1つのインラインスクリプトからなる1枚の生成ページとして意図的に作られています。
  数百個のノードのための力学モデルの配置は短く完結した処理です。バンドルされた依存を1つ増やし、
  その出所を検証すべき対象も増やすことになるので、得るものはわずかです。
- **関係を持たない項目も含めて全項目を描く**。採用しませんでした。関係を持つ項目のあいだの構造を
  見せるための図のまわりに、約130個の孤立した点を置くことになります。しかも、どの辺も引き留めない
  大きなノードの環と中心への引力が押し合うことになります。描かなかったことは、作業単位6のキャプションが
  黙らせずに伝えます。
- **依存の順序を描けるように `依存` のメタデータ欄を新設する**。この項目では採用しませんでした。
  依存を表す辺は `関連` とは異なる主張であり、約330件の既存項目についてそれを主張するには、書き手が
  1件ずつ埋め戻す作業が要ります。生成される表示が肩代わりできる作業ではありません。関係図は、
  ロードマップがすでに記録している関係を描くものです。新しい関係を提案するのは別の作業です。
- **Cards か Table を関係図で置き換える**。採用しませんでした。どちらの表示の役割も関係図では
  果たせません。Cards は「このトピックには何があり、どこまで進んでいるか」に答え、Table は「最近
  何が変わったか」に答えます。どちらの問いも、ノードと辺の図のほうが答えやすくなるものではありません。
