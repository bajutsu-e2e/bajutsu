## はじめに

本項目は、デバイスの OS バージョンを表示用の文字列から**実行とともに運ばれる解析済みの事実**へ変え、
2 つの決定性の判定面がそれを見てグループ化するようにします。実行はすでにシナリオごとに
`device_runtime`、すなわち `"iOS 18.6"` という文字列を記録しています。しかしこの文字列を読むのは
レポートだけなので、同じシナリオを 2 つの OS バージョンで実行すると 1 つの履歴に入り、**バージョンが
違うから**違った判定が flaky として数えられます。そこで小さな解析済みの型を用意し、2 つの判定面の
グループ化のキーに加え、解析済みのバージョンをドライバへ渡す経路を 1 本引きます。OS によって本当に
振る舞いを変えざるをえない判断が現れたとき、バージョンにまったく手が届かない状態ではなく、読む先が
1 か所ある状態にしておくためです。

## 動機

Bajutsu の決定性の監査は、本物の flake、つまり何も変えていないのに判定が反転する事象を、再現する失敗
から区別するために存在します。OS バージョンをまたぐと、いまはその区別ができません。しかも誤判定は
簡単に再現します。

1 つのシナリオファイルを、あいだで編集せずに 2 つの Simulator で実行しました。

| 実行 | デバイス | 判定 | `provenance.scenarioHash` |
|---|---|---|---|
| `20260812-013907` | iOS 18.6 | 成功 | `sha256:c6b97d3d1…` |
| `20260812-014335` | iOS 26.5 | 失敗 | `sha256:c6b97d3d1…` |

両方の manifest を [`longitudinal`](../../bajutsu/analysis/audit.py) に渡すと、こう報告されます。

```
flaky          runs=2 passed=1  native alert can be tapped
flaky          runs=2 passed=1  native alert cancel leaves a distinct result
```

どちらのシナリオも flaky ではありません。実行した OS の上ではそれぞれ完全に決定的で、iOS 18.6 では
毎回成功し、iOS 26.5 では毎回失敗しました。その理由は、2 つの OS バージョンがアラートのボタンの
アクセシビリティノードをどう登録するかという具体的な差として、すでに突き止められています。監査が
flaky と呼ぶのは、グループ化のキーが `(scenarioHash, シナリオ名)` であり、分類の規則が
`classify_stability` 自身の言葉で「**同じ** fingerprint での成功と失敗の混在が本物の flakiness」だから
です。fingerprint はシナリオファイルの内容のハッシュです。そのファイルがどのデバイスに対して走ったかは、
そこに入っていません。

代償はラベルの見た目にとどまりません。決定性の監査は、何を追いかけるかをチームが決めるための計器です。
追いかけてほしいからこそ flaky の指摘を先頭に並べています。再現する OS の差を flake として差し出せば、
チームは存在しないレースを探しに行き、その一方で本当の指摘、すなわち「このシナリオはその OS では動かない」
は、レポートが唯一述べないものになります。同じ読み違いはホスト側にも届きます。
[`flakiness.py`](../../bajutsu/serve/flakiness.py) の `rank_flakiness` は `scenario_hash` だけで
グループ化するので、
1 つのスイートをデバイスの組み合わせにわたって走らせるフリートは、その中の本物の OS 差をすべて flakiness
として採点します。フリートとは、まさにそのために存在するものです。

この誤判定の下には、もっと素朴な欠落があります。**レポートより下では、OS バージョンをそもそも読めません。**
`simctl.runtime_label`（と adb 側の対応物）が文字列を作り、pool が `Lease` へ書き込み、pipeline がシナリオの
実行後に `RunResult` へ写します。消費者はレポート（Environment タブと CTRF 出力）と manifest だけです。どのドライバも
これを受け取らず、解析済みの形も存在せず、バージョンを比較する補助関数もリポジトリのどこにもありません。
実測した OS 差にぶつかったドライバは、分岐するにせよ失敗にそう書くにせよ、いま自分がどの OS の上にいるかを
名指す手段を持っていません。

## 詳細設計

3 つの単位に分けます。小さいものから並べ、最初の 1 つを残りの 2 つが使います。

**解析済みのデバイス OS。** 小さな凍結 dataclass、すなわちプラットフォーム（`ios` / `android`）・
`major`・`minor`・由来となった生のラベルを持つ型と、`runtime_label` がすでに作るラベル（`"iOS 18.6"`、
`"Android 14"`）を読む解析関数です。純粋でデバイスを必要としないので高速なゲートでユニットテストでき、
小さなデバイス同一性の補助関数の既存の置き場所は [`device_id.py`](../../bajutsu/device_id.py) なので、
その隣へ置きます。**認識できないラベルとラベルの不在は、推測ではなく `None` に解析します。** web バックエンドと
WebDriver のグリッドは今日どちらも空のデバイスカタログを返すので、不在は通常の状態であり、下記の消費者は
いずれもすでにそれを扱えなければなりません。本項目ではこの型に比較演算子を持たせません。ここでは何も
バージョンを比較しませんし、誰も使わない順序は、本項目があえて作らないバージョンゲートへの誘いになる
からです（*検討した代替案* を参照）。

**2 つの判定面のグループ化のキー。** `longitudinal` はグループを `(scenarioHash, 名前)` でキーにして
います。ここへ解析済みの OS を加えると、1 つのシナリオを 2 つの OS バージョンで実行した記録は 2 つの
履歴に分かれ、それぞれが自分の証拠だけで分類されます。ラベルが欠けているか解析できない実行は、どれかの
バージョンの履歴に混ぜず、「不明」という別のキーの下に置きます。1 つに混ぜれば本項目が取り除こうとして
いる混同がそのまま戻りますし、捨てれば監査がまだ分類できる実行を失うからです。manifest はシナリオごとの
項目に `device_runtime` をすでに持っているので、この単位に新しい記録項目は要りません。ホスト側の `rank_flakiness`
は `scenario_hash` だけでキーにしているので、同じ要素を加えます。ただしこちらは新しく記録する項目を
必要とします。`RunRecord` はランタイムを持たず、`summary` のマッピングを作る `_run_summary` も実行の
id・判定・レポート・シナリオ名・成功数しか残さず、`device_runtime` はその継ぎ目で落ちるからです。その項目を
`_run_summary` への追加にするか専用の列にするかは、実際のスキーマに当たって単位の中で決めます。
`rank_flakiness` には manifest から縮約した記録も届きます。ファイルを読む `bajutsu flakiness` コマンドと
データベースなしの serve が `records_from_manifests` を通すからです。この縮約も、同じ項目をシナリオごとの
`device_runtime` から同じ「不明」の規則で埋めなければなりません。さもないと、この 2 つの呼び出し元では
すべての実行が「不明」へ入り、他の 2 つの面が直ったあとも今日の誤判定が残ります。加えて
この記録は**実行**ごとであるのに対しラベルは**シナリオ**ごとなので、シナリオが OS バージョンをまたぐ
実行には単一の OS がありません。そうした実行は、解析できないラベルと同じ「不明」のキーの下に置きます。
混在した実行は、どのバージョンをも代表できないからです。2 つの面は粒度としてはあえて異なったままで、
DB 側は実行ごと、ファイル側はシナリオごとです。それでも**同じ** OS の要素と**同じ**「不明」の規則を
得なければなりません。そうしてはじめて、シナリオに同じラベルを付け続けられます。両者が
`classify_stability` を共有しているのは、そもそもそのためです。

**OS はキーだけでなく出力にも届かなければなりません。** グループを分けるのは修正の半分です。いまの
`ScenarioHistory` は `scenario_hash` と名前と件数しか持たず、`render_longitudinal` は名前と分類しか
印字しません。ホスト側の `FlakyScenario` も同じ形です。したがって OS で分かれた 2 つの履歴は、名前も
ハッシュも同じで区別の手がかりがない 2 行として並び、`--json` も同じだけ曖昧になります。どちらの
ソートキーもこの組では同点になるので、順序は入力順まかせです。そこで OS を各レコードと各表示に加え、
両方のソートキーへ名前より前に入れます。これで組の順序も決まります。「このシナリオは flaky だ」が、
*動機* が本当に欲しい指摘、すなわち「このシナリオはその OS では動かない」に変わります。

**項目が入る前に記録された行。** `serve` がすでに保存した実行はランタイムを持たないので「不明」に入り、
以後に記録された実行は OS ごとに入ります。シナリオの履歴が導入の境界で割れます。境界をまたぐ本物の
flake は二重に隠れます。古い成功と新しい失敗が別のグループに入り、どちらも 2 件未満なので `unproven`
になるからです。これは本項目が取り除こうとしている誤判定の符号を逆にしたものなので、黙って残すわけには
いきません。望ましいのは、各実行が保存している manifest から項目を埋め直すことです。シナリオごとの
`device_runtime` はそこにあります。manifest を保持していない配備では行を「不明」のままとし、割れている
ことをレポートで開示します。証拠であるかのように渡しません。
**解析済みの OS を、必要とする 1 つのドライバへ届ける。** `Driver` のメンバーにはしません。この Protocol
は基底クラスを持たない `@runtime_checkable` なので、そこにデータメンバーを置くと、すべてのバックエンドと
インラインのテストダブルが同じ宣言を繰り返すことになり、宣言し損ねたものに対する `isinstance` の検査が
落ち始めます。かわりに `make_driver` のキーワードとして運びます。XCUITest の分岐だけが読み、ほかの
アクチュエータは無視します。`runner_port`・`runner_alive`・`act` がすでに採っている形です。XCUITest の
環境は、デバイスの複製のためにすでに取得しているランタイム識別子から、2 か所のドライバ構築地点で導きます。

この置き場所のほうが正確でもあります。デバイスの差し替えは実行の途中で lease を別の Simulator へ移せます
が、差し替え後は 2 か所とも新しいドライバを作るので OS も追随します。`Lease` に一度だけ押した事実なら
古いまま残ります。本項目ではこの値で何も分岐しません（最初の分岐は別項目です）。それでもドライバの層で
起きた失敗はどの OS で起きたかをすでに名指せますし、将来の OS ごとの判断は経路を発明せず 1 か所を読めます。

**本項目が作らないもの。** OS ごとの振る舞いを*宣言する*仕組みは作りません。バージョンの比較も、
ドライバの中の「iOS が N 未満なら X」という表も、シナリオスキーマや `targets.<name>` の OS 条件も
作りません。リポジトリの既存の立場は、OS の差は分岐するより吸収するほうがよい、というものです。
[BE-0006](../BE-0006-idb-element-tree-normalization/BE-0006-idb-element-tree-normalization-ja.md) は
iOS の更新が要素ツリーを変えることをゴールデン判定で捉えるべき事象として扱い、
[BE-0316](../BE-0316-ios-permission-alert-step/BE-0316-ios-permission-alert-step-ja.md) と
[BE-0320](../BE-0320-ios-system-alert-locale-determinism/BE-0320-ios-system-alert-locale-determinism-ja.md)
はどちらも、座標と固定ラベルを避ける理由として OS バージョンの差を挙げています。本項目はこの立場を
覆しません。この立場が検証されるために必要な事実を供給し、振る舞いの差はそれぞれの是非で直すことに
委ねます。実際にこの基準に照らして計測された差が 1 件あり、そちらは基準を満たしませんでした。`back` が
使う識別子を iOS 18 のナビゲーションバーが持たない件です。そこで別項目が、iOS の戻る操作をメジャー
バージョンごとの実装として用意し、インタフェースの背後に置いて、ファクトリ 1 か所で選ぶ形にします。
1 つのドライバの 1 つのメソッドに限られ、計測から論じたものであり、本項目の事実があってはじめて可能に
なる形です。上で退けた宣言の仕組みとは別物です。

**capability の preflight は対象外であり、ここを担えません。** シナリオが対応可能かを決める preflight は
`pipeline.py` の中で、デバイスを lease する**前**に走ります。`capabilities_for` はドライバを構築せずに
トークンの集合を読みます。preflight が Simulator を必要としないように、というのが docstring の挙げる
理由です。その時点でデバイスの OS バージョンは存在しません。この順序を逆さにしないかぎり、どの
capability トークンもそこへ依存できません。本項目はその反転を試みません。

**テスト。** 解析関数は純粋なので、ラベルと解析結果の表で覆います。解析できない場合と不在の場合も含め
ます。2 つのグループ化の変更も manifest と記録に対する純粋な関数です。決め手になるのは *動機* が測った場合です。
すなわち 1 つのシナリオ・1 つの fingerprint・2 つの OS バージョン・反対の判定で、いま 1 つの `flaky` の
履歴になるところが 2 つの `deterministic` の履歴になることを確かめます。加えて、同じ OS の中で
成功と失敗が混ざる場合はこれまでどおり `flaky` に分類されることも確かめ、絞りすぎていないことを固定
します。ドライバの属性は、lease が設定すること、および lease を経ずに構築したドライバが `None` を返す
ことで覆います。

## 検討した代替案

**OS をシナリオの fingerprint 自体に混ぜる。** fingerprint は実行したシナリオファイルの内容のハッシュと
定義されており、監査はその定義に頼っています。シナリオを編集すれば新しい fingerprint になって新しい
グループができるので、「編集が flake に見えることはありえない」わけです。デバイスの属性を内容のハッシュへ
畳み込むと、この刻印が 2 つの意味を同時に持ち、その保証が壊れます。fingerprint を内容のままにして OS を
別のキー要素として足せば、どちらの読みも保てます。

**解析せず、生の `device_runtime` の文字列でグループ化する。** 新しい型が要らず、今日の誤判定はこれでも
直ります。ただし `"iOS 18.6"` と `"iOS 18.6.1"` が別のグループになり、観測された差が何もないパッチ
リリースのあいだで 1 つのシナリオの履歴が割れます。そのうえ 3 つ目の単位には、ドライバへ渡すものとして
文字列しか残りません。1 か所で 1 度だけ解析すれば安く済み、両方の面が「同じ OS」の同じ定義を持てます。

**将来のゲートに備えて、解析済みの型にバージョンの比較を持たせる。** 順序があれば、着地したその日から
`os >= (26, 0)` と書けます。しかし本項目にそれを必要とするものはなく、ドライバから見える型に使われない
比較演算子が居座ることは、バージョン非依存の代替を退けた事例が現れる前に、本項目が作るべきでないと論じて
いる OS 分岐の表への誘いになります。それを正当化する最初の事例とともにあとから足すなら、関数 1 つの費用
で済みます。

**OS ごとの振る舞いの仕組みをいま作り、戻るボタンと Stepper を最初の利用者にする。** どちらも実測された
本物の iOS 18 の差です。`back` は識別子 `BackButton` をタップしますが、その OS のナビゲーションバーは
この識別子を持ちません。SwiftUI の Stepper はその OS では hittable でないと報告します。バージョン非依存
で足りるところを OS で分岐させれば、リリースのたびに育ち、しかも古い側を誰も再検証しない組み合わせ表を
抱えることになるので、分岐は 1 件ずつ根拠を要します。その後の計測が両者を反対の向きに決着させました。
Stepper に分岐は要りません。container が一方の OS で拒まれ他方で受理されるのは事実ですが、直す場所は
バージョンではなくアクチュエーションの経路です。バージョン非依存とされた直し方のほうも当たりません。
runner の `typeName` で今日 `other` に落ちている `.stepper` を分類しても、変わるのは trait のトークン
だけで frame も `isHittable` も変わらないため、タップは拒まれたままです。戻るボタンのほうは、*詳細設計*
に述べた理由で分岐に値しました。どちらの修正も、それぞれの項目に属します。

## 進捗

> 開発の進行に合わせて常に最新の状態に保ってください。チェックリストは *詳細設計* の MECE な
> 作業分解（作業の単位ごとに 1 つ）に対応し、ログには変更内容と時期（古い順）を PR へのリンクと
> ともに記録します。

- [ ] `device_id.py` の隣に解析済みの型とその解析関数を置く。プラットフォーム・major・minor・生の
      ラベルを持ち、ラベルが不在または認識できない場合は `None` を返し、比較演算子は持たない。ラベルの
      表からユニットテストで固定する。
- [ ] `ScenarioHistory` と `FlakyScenario` に解析済みの OS を持たせ、表示と `--json` の出力に出し、
      両方のソートキーへ名前より前に入れる。
- [ ] `longitudinal`（`bajutsu/analysis/audit.py`）で解析済みの OS を含めてグループ化する。ラベルが
      欠けているか解析できない実行には「不明」のキーを与える。`rank_flakiness`
      （`bajutsu/serve/flakiness.py`）にも同じ要素を加え、この単位が記録へ足す項目から読む。`_run_summary`
      は今日ランタイムを残していない。`records_from_manifests` の縮約でも同じ項目を埋める。シナリオが OS バージョンをまたぐ実行は「不明」のキーへ入れる。
      両者が同じ要素と同じ「不明」の規則を得ることを確かめる。
- [ ] 項目が入る前に記録された行を、各実行が保存している manifest から埋め直す。manifest を保持して
      いない配備では行を「不明」のままとし、境界をまたぐ flake が 2 つの `unproven` に見えることを
      レポートで開示する。
- [ ] 解析済みの OS を `make_driver` のキーワードとして XCUITest のドライバへ渡す。環境がすでに取得
      しているランタイム識別子から、2 か所の構築地点で導く。`Driver` のメンバーもテストダブルも増やさない。
      本項目ではこれで分岐しない。
- [ ] 文書：flakiness の履歴が OS バージョンごとになったこと、および解析済みの OS はドライバから読めるが
      それは分岐の許可ではないことを `docs/`（と `docs/ja/` の対）に記す。振る舞いの OS 差は、項目が別途
      論じないかぎりバージョン非依存で直す。
