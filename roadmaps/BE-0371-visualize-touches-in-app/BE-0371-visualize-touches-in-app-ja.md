## はじめに

iOS の run は Simulator の画面を録画します。録画にはジェスチャがもたらした結果がすべて写りますが、
ジェスチャそのものは写りません。録画を見る人は、画面の変化だけを手がかりに、どの画素が触られたのかを
推測することになります。

この項目では、テスト対象アプリが実際に受け取ったタッチの位置に、アプリ自身のプロセス内でマーカーを
描画します。タッチは、録画とステップごとのスクリーンショットの両方に、対応するフレーム上の目に見える
印として現れます。

マーカーを描くもとになるのは、ドライバが送った座標ではなく、アプリが取り出した `UIEvent` です。
この違いによって、マーカーは操作の意図を描き直したものではなく、タッチが届いたことの証跡になります。
可視化は既定で無効で、証跡専用です。どのアサーションも参照しないため、決定的な判定には影響しません。

## 動機

最近の 2 つの項目によって、run の成果物は「そのジェスチャはどこに落ちたのか」という問いにあと一歩の
ところまで近づきました。

- [BE-0345](../BE-0345-actuation-record/BE-0345-actuation-record-ja.md) は、各ステップが実際に操作した
  座標を記録します。
- [BE-0346](../BE-0346-video-timing-sync/BE-0346-video-timing-sync-ja.md) は、録画の確定した開始時刻へ
  ステップのタイムスタンプを合わせます。レポートの動画シークは、正しいフレームへ着地します。

2 つを合わせれば、表から座標を読み取り、対応する時刻まで動画をシークして、目視で数値とフレームを
突き合わせられます。ただし、その突き合わせは毎回読み手の作業です。座標は point 単位、動画のフレームは
画素単位です。読み手が端末の倍率まで思い出さないかぎり、数値は意味を持ちません。

より深い欠落は、座標の記録では、失敗したタップが投げかける問いに答えられないことです。
[BE-0345](../BE-0345-actuation-record/BE-0345-actuation-record-ja.md) が記録するのは、
[driver](../../docs/ja/glossary.md#driver-backend-actuator-platform) がプラットフォームへ手渡した値です。
それが Bajutsu 自身に観測できる最後の地点です。

タップが実行され、成功と報告され、しかし画面が何も変わらなかったとします。run が生成するどの成果物と
も矛盾しない説明が、2 つ立ちます。ドライバが狙った点に目的のコントロールが存在しなかったのか、それとも
タッチがそもそもアプリに届かなかったのか、のどちらかです。

iOS では後者も珍しい話ではありません。iOS のドライバは通常、snapshot 済みの要素へのハンドルを XCUITest
に渡し、点の決定を XCUITest に委ねます。そのため記録には要素の矩形だけが残り、座標は残りません。
透明なオーバーレイにアプリが覆われていた run は、正常に動作した run と同じ記録を残します。ウィンドウが
first responder を失っていた run も同じです。

アプリの内側で描かれたマーカーは、2 つの説明を切り分けます。アプリがマーカーを描くのは、アプリが
タッチを受け取ったときだけだからです。`UIWindow.sendEvent(_:)` は、システムからアプリのジェスチャ認識器
やビューへ向かうすべてのタッチが通る、単一の漏斗です。

- その地点にマーカーがあれば、タッチは届いています。マーカーは、アプリ自身が算出した位置を示します。
- run が操作したと記録しているジェスチャの下にマーカーがなければ、タッチは届かなかったことになります。

どちらの事実も、現在の成果物からは復元できません。

## 詳細設計

設計は、このコードベースに関する 1 つの既存の事実の上に成り立ちます。Bajutsu はすでに、テスト対象
アプリの内部で Swift のコードを動かしています。`BajutsuKit` は `BajutsuKit/` Swift パッケージの
ライブラリターゲットで、UIKit をリンクし、XCTest はリンクしません。デモアプリはこれをパッケージ依存
として宣言しているため（`demos/showcase/ios/swiftui/project.yml:15-17`）、パッケージを採用したアプリは
自身のプロセスに `BajutsuKit` を抱えます。

もう一方の `BajutsuRunner` ターゲットは、XCUITest のランナープロセスで動きます。ランナープロセスは
アプリとは別のプロセスですから、アプリのウィンドウには何も描画できません。以下で述べる実装は、すべて
`BajutsuKit` に置きます。

### フックの位置と、サブクラス化ではなく swizzle を選ぶ理由

この項目が下敷きにする手法は、`sendEvent(_:)` を override した `UIWindow` のサブクラスを用意し、
アプリのウィンドウをそれで置き換えます。ここでは、割り込む地点だけを採用し、導入方法は採用しません。
アプリのウィンドウを差し替えることは、アプリ自身のソースへの変更です。プライム原則 3 は、アプリごとの
差異をツールの外に置くことを求めています。

代わりに `method_exchangeImplementations` を使い、`-[UIWindow sendEvent:]` の実装をクラスそのものの上で
入れ替えます。アプリのコードは変わらず、プロセス内のすべてのウィンドウがまとめて対象になります。

フレームワークのライフサイクルメソッドを swizzle する仕組みは、ここで新しく持ち込むものではありません。
`BajutsuScreen`（`BajutsuKit/Sources/BajutsuKit/BajutsuScreen.swift:84-97`）は、すでに
`UIViewController.viewDidAppear(_:)` を入れ替えて画面遷移を報告しています。そのヘッダーには、この項目が
引き継ぐ論拠が記録されています。フレームワークのライフサイクルメソッドへのフックはアプリの画面コードに
触れないため、シグナルは app-agnostic なままだ、という論拠です。

アプリが `UIWindow` をサブクラス化して `sendEvent(_:)` を override している場合も、対象に含まれます。
その override が `super` を呼ぶ以上、入れ替えた実装はスーパークラス側にあるからです。

### マーカーは `CALayer` で描き、`UIView` では描かない

Bajutsu はすべての[セレクタ](../../docs/ja/glossary.md#シナリオのオーサリング)を、`app.snapshot()` が
返すアクセシビリティ階層に対して解決します（`BajutsuKit/Runner/Sources/XcuitestElementProvider.swift:44`）。
プライム原則 2 は、あいまいなセレクタが最初に一致したものを操作せず、即座に失敗することを求めます。

その階層にノードを増やす可視化は、見た目だけの追加では済みません。要素数が変わります。一意だった
シナリオのセレクタが、あいまいなセレクタに変わる可能性も、どのアプリのどのステップにも生じます。
設計の要は、**マーカーがアクセシビリティ階層から見えないことを証明できる**という一点にあります。
素直な描画方法のうち、この条件を満たすものは 1 つだけです。

条件を満たすのは、`window.layer` に追加した `CALayer` です。`CALayer` は `UIResponder` ではなく、
アクセシビリティのプロトコルにも適合せず、ヒットテストにも参加しません。`app.snapshot()` が走査する
階層に表現を持たないため、セレクタから到達されることもありません。同等に見える 2 つの代替案が同等では
ない理由は、後述の *検討した代替案* に記録します。

マーカーはビューではなくレイヤーなので、タッチの配送にも関与しません。可視化が、描こうとしているその
ジェスチャを飲み込んだり、別の場所へ流したりする事態は起こりません。

レイヤーを選ぶ利点は、Android 側の可視化と比べるとはっきりします。showcase の Android のレーンは、
OS の設定 `show_touches` と `pointer_location` を有効にしています
（`demos/showcase/android/Makefile:211-212`）。`pointer_location` は、接点と移動の軌跡の両方を描きます。
この項目が iOS で揃えようとしている挙動です。

同じ Makefile は、ツリーを比較する golden のレーンでも、画素を比較する visual のレーンでも、この可視化を
無効にしています。別のシステムウィンドウが描くオーバーレイは、スクリーンショットの画素とツリーの
どちらにも影響しうるからです。

アプリ自身のウィンドウの中に置いた `CALayer` は、ツリーに影響しえません。iOS の可視化は、ツリーの
ゴールデンを検証しているあいだも有効のままにできます。後述の *作業分解* が挙げる不変性の確認は、
この性質に立っています。無効にしなければならないのは、画素を比較する場面だけです。

### 有効化

有効化は、起動時の環境変数 `BAJUTSU_TOUCH_MARKERS` で行います。可視化は、値が `1` であることを要求します。
それ以外の条件では、フックは導入されません。変数を渡されないアプリの挙動は、現在と変わりません。

`BajutsuTouch.startIfEnabled(environment:)` は、デモアプリが起動時にすでに呼んでいる
`BajutsuNet.startIfEnabled()` から呼び出します。呼ぶ位置は、その関数の
`guard collectorURL != nil || !BajutsuMocks.shared.rules.isEmpty else { return }` よりも**手前**です
（`BajutsuKit/Sources/BajutsuKit/BajutsuNet.swift:38`）。`BajutsuScreen.startIfEnabled()` と並ぶ後方では
ありません。

この guard が存在するのは、ネットワークの観測とスタブがいずれもコレクタかモック規則を必要とするから
です。タッチの可視化は、どちらも必要としません。ネットワーク機能を一切使わない素の録画実行こそが、
この機能の使いどころです。

Python 側では、`bajutsu run` に `--touch-markers` フラグを追加します。フラグは、シナリオの起動環境に
変数を設定します。やり方は、`bajutsu/cli/commands/run.py:460` にある既存の `BAJUTSU_MOCKS` の注入と
同じです。新しい伝送路は要りません。起動環境は、すでに次の経路をたどっています。

1. `_launch_params()`（`bajutsu/platform_lifecycle/environments/xcuitest.py:1262`）
2. `BAJUTSU_LAUNCH_ENV_*` の転送
3. `RunnerServer.forwardedLaunchEnvironment`（`BajutsuKit/Sources/BajutsuRunner/RunnerServer.swift:56`）
4. `app.launchEnvironment`（ランナーがアプリを起動する前に載ります。
   `BajutsuKit/Runner/Sources/RunnerUITest.swift:54-57`）

品質を落として動かすのではなく、自動的に無効になる組み合わせが 1 つあります。判定でスクリーンショットを
比較するシナリオです。`visual` アサーションが読むのは、マーカーが描き込まれた画像そのものです。跡は
設計上残り続けるので、ベースラインは決して一致しません。フラグが、アプリと無関係な理由で、緑のシナリオを
赤にしてしまいます。

そこで `_apply_touch_markers` は、各シナリオの `expect` と各ステップの `assert` を走査します。該当する
シナリオを対象から外し、その名前を標準エラー出力に示します。マスクは代替になりません。マーカーは
ジェスチャに追従して動き、決まった領域を占めないからです。

この除外は run 単位ではなくシナリオ単位です。その粒度は、プラットフォームがすでに与えています。
アプリはシナリオごとに、そのシナリオ自身の起動環境で終了と再起動を経ます。温存したランナーを再利用する
経路（`_reuse_live_runner`、BE-0291）でも、コールドの経路でも同じです。除外されたシナリオはフックが
導入されていないプロセスで走り、同じ run の他のシナリオは変わらず描画します。

これ以上細かく分けるには、走っているアプリへの通信経路が必要です。たとえば、あるシナリオのジェスチャ
には描いて、`visual` のステップだけ描かない、という分け方です。BajutsuKit が持つ入力は、プロセスの
生存期間中固定の起動環境だけです。コレクタへの経路は、送信専用の投げっぱなしです。アプリ内の制御
チャネルは、この項目の細部ではなく、別の項目として立てるべき事柄です。

### 描画する内容

フックは、イベントごとに `event.allTouches` を走査し、`UITouch` ごとに円のレイヤーと軌跡のレイヤーを
保持します。保持にはタッチのオブジェクト識別子を鍵にした辞書を使い、ロックは不要です。`sendEvent(_:)` は
メインスレッドでしか動かないからです。

タッチのフェーズごとの描画規則は、次のとおりです。

- `.began`：`touch.location(in:)` の位置に、半透明の円を出します。
- `.moved`：円を移動させ、軌跡を伸ばします。スワイプは 1 点ではなく経路を残します。
- `.stationary`：円をその場に残します。長押しを読み取れるようになります。
- `.ended` と `.cancelled`：円と軌跡をどちらも画面へ残します。

円と軌跡は、タッチが押されているあいだは緑、離れたあとは赤で描きます。この違いによって、フレーム 1 枚
からでも、その瞬間のジェスチャと、前のジェスチャが残した跡とを区別できます。

位置の更新は、暗黙のアニメーションを無効にした `CATransaction` の中で行います。レイヤーは指の動きから
遅れません。フックが単一のタッチではなく `event.allTouches` を読むため、ピンチと回転では、追加の
コードなしに 2 つの接点と 2 本の軌跡が描かれます。

あるジェスチャの跡を消すのは次のジェスチャだけで、ほかの何ものでもありません。ほかにアクティブな
タッチが 1 つもない状態で `.began` が届いたとき、フックは新しい円を描く前に、前のジェスチャのレイヤーを
取り除きます。タッチがまだ押されている最中に届いた `.began` は、進行中のジェスチャに加わり、何も消しま
せん。ピンチの 2 本目の指が 1 本目を消さずに済むのは、この規則によります。

この規則から、2 つの帰結が生まれます。

- 可視化は、タイマーもフェードのアニメーションも時間の定数も持ちません。速い作業機と、負荷のかかった
  継続的インテグレーションのランナーとで、挙動が変わる余地はありません。
- ステップが行ったジェスチャの跡は、そのステップの終了時点でもまだ画面に残っています。この性質が、
  跡をそのステップのスクリーンショットに写します。

したがってマーカーは、run がすでに取得している 2 つの成果物の両方に届きます。

- **動画**：`xcrun simctl io <udid> recordVideo`（`bajutsu/simctl.py:191`）で取得され、Simulator の画面
  全体を撮ります。アプリが描いたレイヤーは、そのまま写ります。
- **ステップごとのスクリーンショット**：`app.screenshot()`
  （`BajutsuKit/Runner/Sources/XcuitestElementProvider.swift:218`）で取得され、アプリケーション要素に
  切り抜かれます。アプリの矩形の内側にあるレイヤーは、やはり写ります。

スクリーンショットはステップが落ち着いたあとに撮られますが、その時点でも、そのステップ自身のジェスチャ
の跡は残っています。`after.png` には、ステップが触れた場所が写ります。長押しも同じです。
`press(forDuration:)` はタッチが離れたあとに戻るため、撮影の時点でタッチはすでに終わっていますが、
跡は残っています。スクリーンショット上のマーカーはフレーム上のマーカーと同じ証跡ですから、抑制せず、
意図した挙動として文書化します。

## 検討した代替案

**マーカーを `UIView` としてウィンドウに追加する。** 下敷きにした手法は、半透明の `UIView` を
ウィンドウの subview として追加します。採用しませんでした。理由は、*詳細設計* が土台に据えたものと
同じです。XCUITest は、アクセシブルでない素のコンテナビューを `.other` 要素として露出させます。
マーカーは、すべてのセレクタが解決対象とするツリーの要素数を変えてしまいます。
`accessibilityElementsHidden` を付けても救えません。隠れるのはビューの子孫であって、ビュー自身では
ないからです。

**マーカーを、高い window level の別の `UIWindow` に描く。** 専用のオーバーレイウィンドウは、subview
より優れているどころか劣ります。`app.snapshot()` が返すツリーの根はアプリケーション要素で、その直接の
子はウィンドウ群です。ウィンドウを 1 つ増やすことは、`app.windows` のクエリすべてから見えるトップ
レベルのノードを 1 つ増やすことになります。

**動的ライブラリとして注入し、`BajutsuKit` を採用していないアプリも対象にする。** 既存の起動環境を
通じて `DYLD_INSERT_LIBRARIES` を渡せば、パッケージを採用しなくても任意の Simulator アプリに届きます。
Xcode 自身も、`libXCTestBundleInject.dylib` を同じ方法で注入しています。

この案は、却下ではなく保留としました。Simulator 向けに個別ビルドしてアドホック署名したライブラリ生成物と、
それを作るビルドターゲットが必要になります。このリポジトリの継続的インテグレーションが実際に動かす
アプリは、すでに `BajutsuKit` を採用しています。増やした仕組みは、テストされないまま出ていくことに
なります。この項目が追加する可視化のコードは自己完結していて、`BajutsuKit` の他の部分に依存しません。
保留した選択肢は、いつでも取れます。

**アプリ内で描く代わりに、レポートの動画プレイヤーの上に座標を重ねる。** レポートには、すでに動画
プレイヤーが埋め込まれています。[BE-0345](../BE-0345-actuation-record/BE-0345-actuation-record-ja.md)
の座標と、[BE-0346](../BE-0346-video-timing-sync/BE-0346-video-timing-sync-ja.md) の補正済み
タイムスタンプがあれば、Swift を一行も書かずにプレイヤー上へマーカーを描けます。

主たる方式としては、*動機* が述べた理由で採用しませんでした。ドライバの記録から描いたオーバーレイが
示すのは、ドライバが狙った場所です。狙いを外したタッチと、届かなかったタッチとを区別できません。
加えて、オーバーレイは生成されたレポートの中だけのものです。書き出した動画ファイル（人が不具合報告に
添付する成果物）には、依然として何も写りません。
