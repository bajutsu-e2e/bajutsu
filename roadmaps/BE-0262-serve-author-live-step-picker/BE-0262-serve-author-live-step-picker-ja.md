## はじめに

Author タブの Edit モード（[BE-0013](../BE-0013-scenario-gui-editor/BE-0013-scenario-gui-editor-ja.md)）では、スクリーンショットをクリックして、ステップのセレクタを直せます。クリックは要素ツリーに対して解決され、選ばれたセレクタが YAML に書き戻されます。

現状、この流れは*過去の run*が残した成果物に完全に依存します。

- ステップ一覧は `/api/scenario?…&runId=…` から来ます。run を選ばないと、ステップは 0 件になります。
- ピッカーの解決呼び出し（`/api/scenario/resolve`）は、`runId` と `stepId` を必須とします。どちらかがなければ、`invalid or missing runId` を返します。
- ピッカーを支える Run ドロップダウンは、**target やシナリオで絞らず、ハブ内の全 run** を並べます（`/api/runs`）。

その結果、一度も実行していないシナリオでは、Edit の目玉であるスクリーンショット・ピッカーが使えません。run が存在する場合でも、ピッカーは、step id の噛み合わない無関係なシナリオの run を並べます。

本項目は、過去の run がなくても Edit を使えるようにします。あわせて、run ピッカーを、実際に噛み合う run だけに絞ります。

## 動機

Edit モードの約束は、「シナリオを開き、画面をクリックし、セレクタを直す」ことです。しかし実際には、まずどこかでシナリオを実行して成果物を作らなければなりません。そのあとで戻ってきて、グローバルな run 一覧が正しい run を出してくれることを期待する、という手順を踏まされます。

これを避けられる入口が 1 つありました。取り込んだばかりのシナリオを、そのまま Edit に流す `auOpenSaved` です。ただし、その起点となる Capture 自体が `[ios]` target で壊れています（姉妹提案のアクチュエータ選択が対処します）。したがって大半のシナリオでは、スクリーンショット・ピッカーが機能しません。ピッカーは、平文編集に対する Edit の差別化機能です。

次の 2 つの修正で、ピッカーを動くようにします。

1. **ステップ選択のライブな供給源。** Capture と同様に、Edit も実機ドライバを起動して、現在のスクリーンショットと要素ツリーを取れます。これにより、セレクタを、凍結された過去の run に対してだけでなく、*いま*に対して解決できます。前提となる run がなくても、Edit のピッカーは動きます。
2. **run ピッカーを絞ること。** 特定の過去状態を確認するために、run を使う場面は残ります。その場合、Run ドロップダウンは、選択中の target とシナリオの run だけを並べるべきです。選んだ run の step id が、読み込み中のシナリオと揃い、黙って噛み合わない事態を防げます。

どちらの修正も、判定経路には触れません。解決は、人が Apply して Save するためのセレクタを提案する、オーサリング支援です。`run` は、決定的で AI を含まないままです。ライブドライバは target の config に従って選ばれ、Capture と同じ選択を再利用します。そのため、決定性とアプリ非依存性も影響を受けません。

## 詳細設計

1. **target とシナリオで絞った run 一覧。** Author の Run ドロップダウンを、現在の選択と target・シナリオが一致する run だけに絞ります。絞り込みは、`/api/runs` の scope 用クエリパラメータ、または Author 専用の runs エンドポイントによって、サーバ側で行います。グローバル一覧をクライアント側で絞るより、サーバ側のほうが望ましいです。ペイロードが小さく保たれ、絞り込みの基準がサーバ側に一元化されるためです。
2. **run なしのライブなステップ選択。** Edit にライブ解決経路を追加します。この経路は、選択中の target のドライバを起動し、スクリーンショットと query を取得し、画面クリックをライブなツリーに対して解決します。Capture の `mark` 解決を写したものです。
   - ドライバは、共通のコスト順アクチュエータ選択から得ます（姉妹提案のアクチュエータ選択を参照）。そのため、同じ `[ios]` クラッシュを再導入しません。
   - 選ばれたセレクタは、run 由来の経路がすでに使う Apply → YAML 書き込みに、そのまま流れます。
3. **モードの依存を UI で明示します。** run 未選択で、ライブセッションも未開始のとき、Edit の画面は、無反応なプレースホルダの代わりに、ピッカーを得る方法（ライブセッションの開始）を示します。run を選んだときは、既存のステップごとのスクリーンショット・ナビゲーションを保ちます。
4. **セッションと安全性を再利用します。** capture セッションの仕組みを再利用します。単一のアクティブセッション、actor ごとの所有、後片付けです。これにより、ライブな Edit セッションが、ドライバを漏らしたり、利用者間で衝突したりしません。Capture のセッション管理と一貫します。
5. **テストを書きます。** 次の 3 つを確認します。
   - 絞った run 一覧のフィルタです。別シナリオの run は除かれます。
   - ライブ解決経路が、クリックに対してセレクタを返すことです。stub の driver factory を経由します。
   - run なし、セッションなしのプレースホルダ状態です。

## 検討した代替案

- **Edit のピッカーに run を前提とし続ける（現状）。** Edit を、純粋な run 後の仕上げ道具に留めます。しかし、それがまさに本項目の取り除く摩擦です。run なしのケースは平文編集がすでに担うため、ライブで動けないなら、ピッカーは何も足しません。
- **グローバル run 一覧のクライアント側フィルタだけにする。** 単純ですが、全 run を毎回ブラウザに送ることになり、絞り込みの基準もクライアント実装任せのままです。サーバ側で絞った一覧のほうが、きれいで小さくなります。
- **必要時にシナリオを自動実行して、成果物を作る。** オーサリングのクリックの中で決定的な run を回すため、重くなります。オーサリングと判定経路も混同します。セレクタの解決には、ライブなスクリーンショットで足ります。

  - Unit 1 は、`/api/runs` をシナリオ名で絞ります（`runs_payload` のフィルタと、`serve.author.mjs` の `auLoadRuns`）。

  - Unit 5 は、絞り込み、ライブ解決、プレースホルダ状態のテストを追加します。

  - 抽出した `_resolve_point` と `_feedback_payload` の型を、`Any` から `CaptureResult` に絞りました。
