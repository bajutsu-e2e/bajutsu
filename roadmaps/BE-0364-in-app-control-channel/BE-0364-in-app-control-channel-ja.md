> 書かれ、別々の提案として `main` に入りました。そのため、この項目は保留ではなく却下とします。この項目が

bajutsu がテスト対象アプリを設定するのは、起動時の 1 回だけです。`BajutsuKit` は `startIfEnabled()` で起動環境を読みます。それ以降、bajutsu からアプリへ何かを送る手段はありません。アプリ側の接続は送信方向だけで、応答を待たずに送るだけだからです。そのため、アプリ内の機能は、プロセスが動いているあいだ固定されます。

この項目では、逆方向のチャネルを追加し、コマンドを 1 つだけ載せます。アプリ内のタッチ可視化を隠す、または再び表示する、というコマンドです。配送は、アプリがすでに報告を送っているコレクタをポーリングする形で行うので、アプリはポートを開きません。載せるコマンドを 1 つに限るのは、可視化が証跡専用であり、その表示状態がステップの合否を変えないからです。

## 動機

`visualize-touches-in-app` の項目が、アプリ内のタッチ可視化を提案しています。まだ `main` には入っていません。可視化は、アプリが受け取ったタッチの位置にマーカーを描きます。跡は次のジェスチャまで画面に残るので、ステップのスクリーンショットにも入ります。

`visual` アサーションは、ステップのスクリーンショットを、リポジトリに置いたベースライン画像と比較します。可視化が有効だと、マーカーはそのスクリーンショットに写り、ベースラインには含まれません。そのため、アプリとは無関係な理由で比較が失敗します。

正しい振る舞いは、その 1 回の撮影のあいだだけマーカーを隠し、終わったら再び表示することです。しかし起動環境が唯一の入力なので、可視化の項目は代わりにシナリオ全体で自分を無効にします。これは問題より粒度が粗く、しかも調査対象のシナリオからタッチの証跡を取り除いてしまいます。

マーカーの領域を比較から除外する方法は、代わりになりません。

- マーカーはジェスチャに合わせて動くので、除外する領域はステップごとに計算しなければなりません。
- 除外すれば、タッチが落ちた領域を比較から外すことになります。その領域は、たいていアサーションが確かめたい領域です。

リクエストのスタブにも、同じ制限があります。`BajutsuNet.startIfEnabled()` は、シナリオのモック規則を起動環境から 1 回だけ読み込みます（`BajutsuKit/Sources/BajutsuKit/BajutsuNet.swift:29`）。前半と後半で違う応答を返したいシナリオは、2 つに分けるほかありません。この項目はその事例を扱いません。理由は後述の *対象範囲* に書きます。

## 詳細設計

アプリと bajutsu のあいだには、すでに認証済みの HTTP 接続があり、その片方向しか使っていません。`NetworkCollector`（`bajutsu/evidence/network.py:116`）の動作は次のとおりです。

- ループバック上で `BaseHTTPRequestHandler` を動かします。
- run ごとにトークンを生成し（`:207`）、トークンを持たない POST を拒みます。トークンの比較は定数時間で行います（`check_token`、`:167`）。
- アプリは、コレクタの URL とトークンを `BAJUTSU_COLLECTOR` と `BAJUTSU_COLLECTOR_TOKEN` で受け取ります。exchange はコレクタのルートパスへ、transition は `/transitions` へ POST します（`:305`）。
- ハンドラには `do_GET` が定義済みですが、`200` を返すだけで何もせず（`:315-317`）、呼び出しているコードもありません。

したがって、このチャネルに新しいサーバや新しいポート、新しい認証方式は要りません。必要なのは、その `GET` が返すコマンドのキューだけです。

### コマンドの受け渡し

bajutsu がキューにコマンドを追加します。アプリはコレクタをポーリングしてコマンドを受け取り、適用します。そのあと、すでに使っている接続で完了報告を POST します。アプリはソケットを開かず、コレクタを守っているトークンがコマンドも守ります。

完了報告は必須です。コマンドを送ってから一定時間待つ実装は、プライム原則 2 が禁じる固定 sleep になります。そうではなく、実行ループは完了報告を条件として待ち、届かなければメッセージを出して失敗します。これにより、コマンドは次のステップより前に効いているか、さもなければステップがその旨を述べて失敗します。スクリーンショットを撮るのは、マーカーを隠したとアプリが報告したあとだけです。

### コマンドを 1 つに限る理由

このチャネルは、複数種類のコマンドを運べます。それでも 1 つに限ります。そのぶん、設計の他の部分が単純になります。

**このチャネルでは合否の判断をやり取りしません。** コマンドが変えられる状態は、証跡専用のオーバーレイを描くかどうかだけです。チャネル上のものがステップの合否に影響することはなく、どのアサーションもここから読みません。そのため、テスト対象アプリが自らの判定に加わることはありません。これはプライム原則 1 のより厳しい形です。`run` のゲートが機械的に検査可能で、アプリに依存しないという性質が保たれます。

2 つめのコマンドが必ずこの性質を壊すわけではありませんが、壊さないことを別に論じる必要が出ます。候補としてわかりやすいのは、シナリオ途中でのスタブ差し替えですが、これは意図して外します。モックの応答を変えることは、`request` アサーションが見るものを変えることです。望む理由はありますが、別の項目で論じるべき事柄です。

**求められない限り無効で、起動環境だけでは有効になりません。** `BajutsuKit` の README は現在、2 つの選択肢を示しています。パッケージをリリースビルドから外すか、`BAJUTSU_COLLECTOR` のガードに頼るかです。この項目は後者を外します。そのガードが十分でなくなるからです。`BajutsuKit` をリリースビルドに組み込み、そのガードを頼りにしている採用者は、そうでなければ、環境変数 1 つでアプリの振る舞いの遠隔操作が有効になるバイナリを出荷することになります。

そこでポーリングは、ビルド設定で選ばれない限りコンパイル対象から外します。これにより、起動環境だけで有効になることはありません。README もその内容に書き直す必要があります。

**アプリケーションの状態には触れません。** このチャネルが制御するのは、bajutsu 自身のアプリ内計測であり、アプリケーションではありません。アプリのデータを仕込んだり画面遷移を操作したりするコマンドは、アプリ固有の知識をツールに持ち込みます。それは、伝送方式が何を許すかに関わらず、プライム原則 3 を壊します。

### ポーリングによる遅延

ポーリングを使えばリスナーは不要になりますが、その代わりに遅延が生じます。コマンドが効くのは、早くても次のポーリングのときです。スクリーンショットを比較するステップは、この遅延を隠すときと表示するときの 2 回払います。それぞれが完了報告の待ちの後ろで直列になります。すでに画像を比較しているステップとしては、許容できます。

またポーリングは、テスト対象アプリの中でタイマーを回します。そのため、チャネルが有効なときだけ動かす必要があります。コマンドがないときのポーリングが、アプリ自身のタイミングを変えないことを、実装で示す必要があります。アプリ自身のタイミングは、テストが測っているものです。

この設計には、書いておくべき依存が 1 つあります。タッチ可視化は今日コレクタを必要とせず、ネットワーク機能を使わない録画実行が通常の使い方です。コマンドをコレクタ経由で配送すると、撮影中の切り替えを望むシナリオは、本来要らないコレクタも起動することになります。専用の第 2 のエンドポイントを立てればこれは避けられますが、守るべきサーバが 2 つになります。この項目がその選択を採らない理由は、*検討した代替案* に書きます。

### 作業分解

以下の単位は、互いに排他で、全体を尽くしています（MECE）。

| 単位 | 作業 |
|---|---|
| 1 | キュー：`NetworkCollector` に保留コマンドの一覧、それを引き取る認証付き `GET`、そして完了報告のエンドポイントを置く。完了報告の経路は `do_POST` の既定の分岐（`/transitions` 以外のすべての経路をネットワーク exchange として保存する）より**前**で一致させ、完了報告が `request` アサーションの読む exchange に入らないようにする。トークン検査は今日 `do_POST` が行っているのとまったく同じように適用し、`clear()` は exchange とともに保留キューも破棄するので、あるシナリオが引き取らずに終えたコマンドが次のシナリオへ届くことはない |
| 2 | アプリ側：`BajutsuKit` にポーリングとコマンドの振り分けを置く。明示的なビルド設定で選ばれない限りコンパイル対象から外し、コンパイルされた場合にかぎり専用の起動環境キーで有効化して、キーがなければ何もしない。これにより起動環境だけで有効になることはない。完了報告は既存の報告用セッションで POST する |
| 3 | 待ちと 1 つのコマンド：実行ループに完了報告の条件待ちを置き、タイムアウトではメッセージを出して失敗させる。スクリーンショットを比較するステップの前後で表示と非表示を切り替え、`visualize-touches-in-app` の項目が持つシナリオ単位の無効化を置き換える。待ちはパイプラインがすでに駆動している `Collector` プロトコルを通ってアプリへ届くので、この単位ではどのコレクタがチャネルを持つのかも定め、持たないコレクタに対して発行されたコマンドは、黙って飛ばすのではなくメッセージを出して失敗させる。この単位には順序依存があり、`visualize-touches-in-app` の項目より先には入れられない。それまで切り替える対象の可視化が存在しないためである |
| 4 | 日英両言語のドキュメント：チャネル、そのビルド設定と起動環境キー、コマンドを 1 つに限る範囲とその理由、そしてこの項目が必須にするリリースビルドからの締め出し |

## 検討した代替案

**アプリの中にリスナーを開く。** テスト対象アプリの中に小さな HTTP サーバを立てれば、コマンドを直接受け取れ、ポーリングのレイテンシもありません。この案を採らなかったのは、工学面ではなくセキュリティ上の理由です。テスト対象アプリケーションの内部で待ち受けるソケットは、ポーリングするループバックのクライアントより、攻撃を受ける範囲が広くなります。専用のポート割り当てと端末ごとの転送も必要になります。認証を間違えれば、アプリは端末上の何からでもコマンドを受け付けます。ポーリングのレイテンシは小さく、上限もあります。

**コレクタから独立した第 2 の制御サーバを立てる。** 上に書いた結合は解け、切り替えを望む run がネットワークのコレクタを起動する必要もなくなります。一方で、正しく作らねばならない認証付きサーバが 2 つになります。トークン、ループバックへの束縛、ポート衝突の処理、定数時間比較を、それぞれ 2 度書くことになります。コレクタのサーバを再利用するほうが変更は小さく、結合が実際に問題となったとき、エンドポイントを後から分けるのは限定的な手直しで済みます。アプリ側のコマンドの振り分けは、どのサーバが答えたかに依存しないからです。

**マーカーの座標を報告し、その領域をビジュアル比較から除外する。** アプリは、すでに持っている接続で各マーカーの矩形を POST でき、比較はその領域を除外できます。受信方向のチャネルは要りません。この案を却下したのは、*動機* に書いた理由からです。ジェスチャが落ちた領域を比較から外すことになり、しかもそれが表に出ません。加えて、証跡専用の機能が、機械的に検査可能なアサーションの見てよい範囲を決めてしまいます。

**粒度をシナリオ単位に留める。** これが現在の振る舞いで、有用でもあります。アプリは、シナリオごとに、そのシナリオ自身の起動環境で終了と再起動を経ます。温存したランナーを再利用する経路（`_resume_warm`、[BE-0291](../BE-0291-xcuitest-runner-reuse-across-scenarios/BE-0291-xcuitest-runner-reuse-across-scenarios-ja.md)）でも、コールドの経路でも同じです。そのため、機能はすでにそのままでシナリオごとに変えられます。それでも先へ進む理由は、*動機* の事例が 1 つのシナリオの内側で起きることです。そのシナリオが積み上げた状態も試験の一部であり、分割すれば試験しているものが変わってしまいます。
