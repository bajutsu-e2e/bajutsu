## はじめに

ホスト型の `bajutsu serve` は **2 インスタンス構成**です。制御プレーン（Web UI と API、Linux）がブラウザに応答します。実際にテストを実行するのは、別の **worker**（idb / Playwright、Mac）です。両者は Redis とオブジェクトストレージでつながります
（[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md)、
[BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md)）。

run 中、ブラウザは 3 つのライブな面を表示します。

- **コンソールログ**
- **最終結果とレポート**
- [`crawl`](../BE-0038-autonomous-crawl-exploration/BE-0038-autonomous-crawl-exploration-ja.md)
  の探索が進むにつれて育つ**探索グラフ**

このうち 2 つはすでにインスタンスの分割を越えています。探索グラフだけが越えていません。

本提案は、この欠落を埋めます。run の**実行中（ライブ）アーティファクト**を、制御プレーンと worker の分割をまたいで見えるようにします。最初の利用者は **crawl の途中グラフ**です。スコープを絞るため、すでに分割を越えている 2 つの面は**あえて再提案しません**。

- **コンソールログ（すでに越えている）。** ライブな run 出力は **LogBus シーム**を通ります。worker が stdout の各行を Redis（`RedisLogBus`）に publish します。制御プレーンがその行を SSE（server-sent events）でブラウザに中継します。本提案の対象ではありません。
- **最終結果とレポート（すでに越えている）。** 終端の状態は永続化されます。worker は `runs/<id>/` ツリーをオブジェクトストレージにアップロードし、run record を書きます。UI は run 後に両方を読みます。本提案の対象ではありません。

欠けているのは **crawl の途中グラフ**です。途中グラフは共有ファイルシステムを前提にしており、worker の分割がその前提を壊します。

## 動機

**ギャップの具体。** crawl は `runs/<id>/screenmap.json` を*逐次*書き出します。エンジンは発見のたびに `on_event` コールバックを発火し、コールバックがファイルを書き換えます（`bajutsu/cli/commands/crawl.py`）。ブラウザは SSE のログ行が来るたびに `GET /runs/<id>/screenmap.json` をポーリングして再描画します（`bajutsu/templates/serve.js` の `loadGraph`）。**local** モードでは、ファイルを書くプロセスと配信するサーバが 1 つのファイルシステムを共有するので、この仕組みが成立します。

**server** モードでは壊れます。worker は `screenmap.json` を*自分の*ディスクに書きます。しかしアーティファクトがオブジェクトストレージに届くのは job の終了時だけです。`_upload_runs` は `run_job` が返った後、つまり crawl のサブプロセスがすでに終了した後に走ります（`bajutsu/serve/server/worker_job.py`）。crawl の進行中、制御プレーンの `ObjectStorageArtifactStore.get` はキーを見つけられず **404** を返します。ブラウザのポーリングは失敗し、グラフは **crawl が終わるまで**空のままです。

**根因。** ログには、分割を越える伝送路（LogBus）があります。実行中アーティファクトには、その伝送路がありません。アーティファクトストアは、終了時にアップロードし、要求のたびに読む作りです。この作りはレポートには合いますが、**変化している最中に UI が読む**ファイルには合いません。crawl グラフが最初の「live artifact」であり、分割の向こうへ運ぶ仕組みはまだありません。

**なぜ重要か。** crawl は長時間かかり、育っていくグラフがユーザー体験（UX）の中心です。ユーザーは、カバレッジが積み上がり、画面が現れ、フロンティアが縮んでいく様子を見られます。チームが実際に運用するのはホスト型のトポロジです（[BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md)）。ホスト型では、UX が「ログのスクロールを眺め、最後にグラフ全体を見る」形へ静かに劣化します。local の dogfood では完成して見え、本番では気づかれないまま退行します。

## 詳細設計

### スコープ：live artifact

**live artifact** は、run が実行*中*に更新し、UI が*途中で*読むファイルです。終端アーティファクト（レポート、証跡）は別物で、UI は run 後にだけ読みます。live artifact は今、`screenmap.json` の 1 つだけです。

本設計は、**live artifact のパスを明示した小さな allowlist** を置きます。allowlist のおかげで、仕組みは一般化されます。将来のライブな進捗ファイルも再利用できます。一方で、すべてのアーティファクトをストリーム対象にする事態は避けられます。

### 主設計：live artifact の逐次アップロード

worker はすでに適切な境界を持っています。発見のたびに `screenmap.json` を worker のディスクへ書き換える `on_event` コールバックです。本設計は**同じ**境界をフックして、アーティファクトをオブジェクトストレージにも `put` します。すると制御プレーンの `ObjectStorageArtifactStore.get` が、run の途中でアーティファクトを見つけられます。ブラウザは**同じ** `/runs/<id>/...` のルートをポーリングし続けます。変わるのは*バイトの出所だけ*で、次の 4 つの帰結があります。

- **UI 変更なし、GET ルート変更なし。** local モードは影響を受けず、従来どおりディスク上のライブファイルを配信します。server モードでは同じファイルがオブジェクトストレージに見えます。1 つのコード経路で両モードを賄います。
- **イベントごとではなく throttle する。** chatty な crawl は多くのイベントを発火します。worker はアップロードを、短い間隔につき最大 1 回に合体させます（約 1〜2 秒。ブラウザのポーリング間隔に合わせます）。加えて、job 終了時に確定の書き込みを 1 回行います。グラフはもともと約 1 秒に 1 回更新されるので、体感の UX を損なわずにオブジェクトストレージへの PUT を抑えられます。
- **整合性は心配いりません。** S3 と R2 の上書きは read-after-write の強整合です。アップロード後に発行したポーリングは新しいスナップショットを返すので、古い値を読む窓を設計で塞ぐ必要はありません。
- **終端アップロードが最終権威のまま。** job 終了時の `_upload_runs` は、完全な `runs/<id>/` ツリーの権威であり続けます。逐次アップロードは*ライブ*なアーティファクトを早く見せるだけで、ほかは何も変えません。

### 契約：機械チェック可能な不変条件

Linux ゲートが、in-memory の fake オブジェクトストレージでこれらの不変条件を検証します。Mac も Simulator も使いません。

1. **途中可視化（退行）。** fake worker が、終了前に N 個の screen-map スナップショットを出します。制御プレーンのアーティファクト `get` は、job が done になる**前**に k 番目のスナップショットを返します。今は、このケースが 404 を返します。
2. **終端権威。** job 完了後、保存された `screenmap.json` はディスク上の最後のスナップショットと一致します。終端の一括アップロードは、逐次の書き込みと整合します。
3. **アップロード上限。** ある期間に M 個の発見があっても、アップロードは高々 `ceil(duration / interval) + 1` 回です。PUT はイベント数ではなく実時間に比例します。
4. **local モード等価。** local モードでは、ライブグラフが従来どおりディスクから配信されます。すでに動いている経路は退行しません。
5. **ゲートを汚さない。** 既定経路は大規模言語モデル（LLM）を呼ばず、重い依存も足しません。決定的コアは不変です。

### prime directive への適合

この変更は **Tier-1 の `crawl` と serve の配管**に閉じます。`run` / CI ゲートに LLM は入りません（[DESIGN §2](../../DESIGN.md)）。決定性は保たれます。変えるのは*いつバイトが見えるか*であり、*crawl が何を探索するか*は変えません。crawl の探索は、要素ツリーの純関数のままです。仕組みは app 非依存です。対象アプリに関係なく、ファイルを動かすだけです。

## 検討した代替案

- **ファイルをポーリングする代わりに、進捗イベントを bus に流す（SSE で差分配信）。** より汎用な「進捗チャネル」です。worker が新しいノードやエッジを構造化イベントとして出します。制御プレーンがログ行と並べて SSE で中継し、ブラウザは payload から更新します（ポーリングなし）。すでに分割を越えている伝送路（LogBus）に統一でき、差分はマップ全体を取り直すよりずっと小さい点が魅力です。**却下ではなく見送り**です。変更が大きいからです。新しいイベント種別が要り、UI のデータ経路がポーリングからイベントへ移り、local と server の両モードを賄う必要があります。逐次アップロードは、既存のシームと既存の UI を保ちます。将来この進捗チャネルが見合うようになれば、ポーリングを置き換えられます。
- **worker → 制御プレーンの artifact proxy。** 制御プレーンが worker から実行中ファイルを HTTP で読む案です。**却下**です。worker は **pull 型**で、Redis から job を lease します。アドレス可能なサーバではありません。worker にファイルを配らせると lease モデルが反転します。アップロードに対する利点がないまま、ネットワークとセキュリティの面が増えます。
- **server モードで終端のみのグラフを受け入れる（何もしない）。** **却下**です。ライブグラフは crawl の主たる UX であり、ホスト型は実際に運用されるトポロジです。local の dogfood でしか動かない機能は、本番での静かな退行です。
- **全イベントでアップロード（throttle なし）。** **却下**です。chatty な crawl では PUT が無制限になります。ポーリング間隔に合わせて合体させても、UX は同じです。

**見送り（2026-07-02）。** 本提案の前提だった「`crawl` がリモート worker で動き、ライブグラフが
制御プレーンから見えなくなる」という状況は成立しなくなりました。crawl は分散しません。分散するのは
テスト実行だけであり、分散テスト実行の設計は worker 上で実行が完了した後に結果をオーケストレータに
連携する方式を採ります。分割をまたいで運ぶべき実行中のライブアーティファクトが存在しないため、本
提案が解く問題自体がなくなりました。将来、分散実行の途中で真にライブなアーティファクトが必要に
なった場合には、再検討できます。
