## はじめに

シナリオ YAML にはバージョンを示すマーカーがなく、その pydantic モデルは未知のフィールドを一律で拒否します。そのため、古い `bajutsu` が新しいシナリオを読み込むと、わかりやすいメッセージではなく不透明なバリデーションエラーで失敗します。本提案では、シナリオに明示的な `schema` フィールドを追加し、対処法を示すエラーを出すバージョンチェックを導入します。前例となるのは、レポートマニフェストの `schemaVersion` です。

## 動機

`bajutsu/scenario/models/_base.py:49` は、すべてのシナリオモデルが継承する共有ベースを定義しています。`model_config = ConfigDict(populate_by_name=True, extra="forbid")` です。`extra="forbid"` は、シナリオ作成時のタイプミスや未対応フィールドを検出するうえで正しい選択です。タイプミスが黙って無視されるより、明示的に拒否されるほうがましだからです。

同時に、この設定は、新しいフィールドをトップレベルやステップレベルに追加した新しい `bajutsu` 向けのシナリオを、古い `bajutsu` では一切パースできないことも意味します。失敗は汎用的な pydantic の `ValidationError`（「Extra inputs are not permitted」）として現れます。このエラーは、実際の問題がバージョンの不一致であることも、どう対処すればよいかも、ユーザーに伝えません。

この隙間は、現在はさほど問題になりません。シナリオファイルとそれを読む `bajutsu` が、ほぼ常に同じチェックアウトに由来するからです。問題になるのは、シナリオの読み込みが日常的にバージョンをまたぐようになったときです。BE-0063（Git 設定ソース）は、Git の ref から config とそのシナリオツリーを取得します。その ref は、ローカルの `bajutsu` インストールより古い、あるいは新しいコミットに固定されている場合があります。すると、ツールとシナリオツリーの間のスキーマ不一致は、エッジケースではなく通常の出来事になります。

この修正は今のうちなら安価です。バージョンマーカーを持たないシナリオファイルが存在し続けるほど、後から手当てするコストは上がります。これまでに書かれたバージョンなしのシナリオはすべて、曖昧な「バージョン 0」となり、移行ロジックが特別扱いしなければならなくなるからです。

レポートマニフェストは、自身のスキーマで同じ問題をすでに解決しています。`bajutsu/report/manifest.py:29` は `SCHEMA_VERSION = 4` を定義し、すべてのマニフェストに書き込みます（`manifest.py:111`）。`bajutsu/report/load.py:8` は、本提案がシナリオにも求めたい読み込み側の規律を明文化しています。「欠けているフィールド（古い `schemaVersion`）はデフォルト値にフォールバックし、未知の新しいフィールドは無視する。こうすることで、古い実行結果もそのまま描画できる」。

深刻度は中です。現時点で発生しているバグではありませんが、予見できる問題です。BE-0063 によってこの問題は日常的に起こるようになるので、その読み込みが生まれる前に直しておくのがもっとも安上がりです。

## 詳細設計

1. **シナリオファイルのトップレベルに `schema` フィールドを追加する。** 追加先は `ScenarioFile`（`bajutsu/scenario/models/scenario.py`）です。マニフェストの `SCHEMA_VERSION` に倣い、`schema: int`（デフォルト `1`）を置きます。`schema` キーを持たないシナリオファイルは、スキーマ `1` として扱います。現存するすべてのシナリオファイルは暗黙にバージョン 1 です。そのため、現行のコーパスに移行作業は不要です。
2. **ドキュメント全体の検証より先にバージョンを確かめる。**
   `load_scenario_file`（`bajutsu/scenario/load.py`）は、パース済みの生の YAML から `schema` を読み取ります。この読み取りは、`ScenarioFile.model_validate` にドキュメント全体を渡す *前に* 行います。読み取った値は、現在の `bajutsu` が理解しているシナリオスキーマの定数と比較します。この `bajutsu` が理解できるより新しい `schema` の場合は、明快で対処可能な `ValueError` を送出します。メッセージの例は「このシナリオファイルはスキーマ 2 を使用していますが、この bajutsu が理解できるのはスキーマ 1 までです。bajutsu をアップグレードするか、より古いシナリオ／config のバージョンに固定してください」です。
   このチェックがなければ、生のフィールド検証が先に失敗します。そのとき出るのは、`extra="forbid"` による、わかりにくいエラーです。
3. **同一バージョンのドキュメントに対しては `extra="forbid"` を維持する。** バージョンチェックが変えるのは、バージョン不一致のときの失敗の *仕方* だけです。この `bajutsu` が対応しているスキーマを宣言しているシナリオについて、`extra="forbid"` を緩めることはしません。サポート範囲内のシナリオにおける本物のタイプミスは、今までどおり明示的に失敗し続けなければなりません。
4. **バージョン更新の運用ルールを文書化する。** `schema` をいつ上げるべきかを短く記した注記を、`_base.py` の `_Model` の近く、あるいは `docs/` に追加します。次の変更は、定数を上げる対象です。
   以前必須だったフィールドの意味を取り除く変更と、古い `bajutsu` が単に拒否するのではなく誤解してしまう変更です。純粋に追加的なオプションフィールドは、古いツールが新しい振る舞いを持たないだけであれば、必ずしも版上げを必要としません。この場合は、変更ごとに個別に判断します。マニフェストの `SCHEMA_VERSION` が、`report/load.py` の運用ルールに従って、読み込みを壊す変更のときだけ上げられているのと同じ扱いです。

この変更が閉じているのは、パース部分、つまりプライムディレクティブ 2 の「明示的に失敗する」という関心事です。バージョン不一致は、古い前提のまま実行される（あるいは静かに誤動作する）のではなく、即座に、かつ明確に失敗します。ここでの変更は `run` の合否判定ロジックに一切触れず、AI への依存も持ち込まないため、プライムディレクティブ 1 と 3 には影響しません。

## 検討した代替案

- **BE-0063 が出荷され、バージョンをまたぐ読み込みが目に見える失敗を起こすまで何もしない。** 却下します。それまでの間に、`schema` フィールドを持たないシナリオファイルが未知の数だけ生まれます。本提案が確立したい規約、つまり「バージョンなしはすべて暗黙のバージョン 1」を、事後的に正当化するのが難しくなります。それらのファイルの一部は、すでに新しい未文書化の振る舞いを前提にしている可能性があるからです。読み込みが日常化する前にバージョンを付けるコストは、フィールド 1 つとチェック 1 つです。後からでは、現存するすべてのシナリオファイルの監査が必要になります。
- **ファイルを書いた `bajutsu` のバージョンからスキーマバージョンを推定する（スキーマバージョンではなくツールバージョンを埋め込む）。** 却下します。ツールバージョンは、スキーマとは無関係なリリースとスキーマの変更を混同させます。シナリオのフィールドに一切触れないリリースが多いからです。さらに、すべての読み込み側に、バージョン範囲とスキーマ形状の対応表を保守させることになります。スキーマに関係する変更のときだけインクリメントする明示的な整数の `schema` フィールドは、マニフェストがすでにうまく使っている手法です。
- **`extra="forbid"` を `extra="ignore"` に緩め、新しいフィールドをエラーにせず落とす。** それ単体では却下します。バージョンをまたぐ読み込みは直りますが、`extra="forbid"` が存在する理由であるタイプミス検出を犠牲にします。タイプミスしたフィールドが黙って消え去るのは、「明示的に失敗する」の正反対です。実際の不一致にだけ明確に失敗するバージョンチェックを置き、同一バージョンのドキュメントには `extra="forbid"` を維持すれば、両方の性質を満たせます。
