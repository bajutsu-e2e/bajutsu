## はじめに

実行を終えた `bajutsu run` の結果を、プルリクエストまたは Issue に投稿する composite GitHub Action `post-evidence` を追加します。コメントには、失敗したシナリオ、失敗したステップ、その理由を載せます。さらに、この Action が GitHub Actions の artifact としてアップロードした証跡へのリンクを載せます。実行全体は、zip の artifact 1つにまとめます。失敗した最初の3シナリオについては、失敗ステップのスクリーンショットとシナリオの動画を、zip にしない別々の artifact としてもアップロードします。ブラウザーが、それぞれをそのまま表示します。再実行したときは、新しいコメントを増やさず、同じコメントを更新します。

この Action が Bajutsu から読むのは、`manifest.json` と、マニフェストが残らなかった実行での `<sid>/result.json` だけです。Bajutsu のパッケージを入れず、Bajutsu のコマンドも呼びません。Bajutsu の実行ディレクトリを出力するリポジトリなら、`uses:` を1行足すだけで使えます。

## 動機

Bajutsu のチェックが赤くなったプルリクエストで、レビュアーが証跡を見るまでの手間は大きいままです。Actions の実行を開き、ジョブを探し、artifact を開き、zip をダウンロードして展開し、`report.html` を開きます。最後の手順まで進むレビュアーは多くありません。失敗の理由はジョブのログにあり、それを説明するスクリーンショットは zip の中にあります。

[BE-0500](../BE-0500-run-set-github-check/BE-0500-run-set-github-check-ja.md) は、`serve` を運用するチームにとってこの状況を改善します。ただし、失敗したシナリオと理由を並べるチェックにとどまります。スクリーンショット、動画、レポートへのリンクは載りません。`serve` の運用と GitHub App も必要です。[BE-0161](../BE-0161-ctrf-report-export/BE-0161-ctrf-report-export-ja.md) は、外部のレポーターが表示できる結果の表を出力します。証跡そのものをプルリクエストへ添える経路は、どちらにもありません。[BE-0110](../BE-0110-evidence-store-uri/BE-0110-evidence-store-uri-ja.md) はオブジェクトストレージへ証跡をアップロードします。しかし、アップロードしたファイルをプルリクエスト上でレビュアーに見せる仕組みはありません。

実行全体の zip は、大きさの上限もなく膨らみます。Bajutsu はデバイスログ（iOS は `simctl log stream --level debug`、Android は `logcat`）を、そのまま `device.log` へ流し込み、上限を設けません。レポートに埋め込むのは末尾2000行だけですが、ディスク上のファイルは全行を残します。動画は zip にしても縮みません。MP4 と WebM はすでに圧縮されているからです。zip の artifact だけでは、この隔たりを埋められません。GitHub には、zip の中身をブラウザーで見る機能がありません。`report.html` は CSS と JavaScript をインラインで持ちますが、スクリーンショットと動画は相対パスで参照します。単独でアップロードすると、画像が壊れた状態で開きます。画像や動画のファイル単体なら、この問題は起きません。ブラウザーがそのまま表示するからです。

導入後に確かめられる違いは、プルリクエストのページに現れます。失敗した実行のあとには、コメントが1件付きます。コメントは、どのシナリオがなぜ失敗したかを述べます。レビュアーは、スクリーンショットのリンクをクリックすれば画像を見られ、動画のリンクをクリックすれば再生できます。ダウンロードも展開も要りません。実行全体は、zip として1クリックの先に残ります。再実行するとコメントが書き換わるので、会話に残るコメントは、実行ごとではなくジョブごとに1件です。読み手にはリポジトリの読み取り権限が要ります。artifact の URL は、サインインを必要とするからです。

## 詳細設計

### Action の置き場所と前提

Action は、このリポジトリの `.github/actions/post-evidence/` に置きます。ほかのリポジトリは `bajutsu-e2e/bajutsu/.github/actions/post-evidence@<ref>` として使います。描画処理は、標準ライブラリだけを使う Python スクリプト1本です。Action は `actions/setup-python` でリポジトリの Python（3.13）を固定し、`update-environment: false` を指定して、ステップの出力 `python-path` からスクリプトを起動します。ランナーのシステム Python は使わず、呼び出し側のジョブの Python も変えません。そのため、`uv sync` も Bajutsu のチェックアウトも要りません。

呼び出すジョブには、プルリクエストなら `pull-requests: write`、Issue なら `issues: write` を与えます。この Action は `pull_request_target` を必要としません。このトリガーは書き込み権限つきのトークンをジョブに与えますが、フォークのシナリオを実行するにはフォークのコードをチェックアウトして動かすことになります。そのため、ドキュメントでは非対応と明記します。すべての入力は、インラインの `${{ }}` ではなく `env:` を通して、シェルのステップとスクリプトに渡します（[BE-0123](../BE-0123-composite-action-input-indirection/BE-0123-composite-action-input-indirection-ja.md)）。

### 入力と出力

| 入力 | 既定値 | 意味 |
|---|---|---|
| `run-dir` | `runs` | 1つの実行ディレクトリか、複数の実行を収めたルートです。ルートを渡すと、直下の `*/manifest.json` をすべて読み、実行ごとに1節を描画します。 |
| `artifact-name` | `${{ github.workflow }}-${{ github.job }}` | zip の artifact の名前で、zip にしない artifact の名前の接頭辞でもあります。1回のワークフロー実行は同名の artifact を2つ持てないため、マトリクスのジョブは名前にマトリクスの値を足します。アップロードの前に、`actions/upload-artifact` が受け付けない文字（`" : < > | * ? \ /`、CR、LF）を `-` に置き換えます。 |
| `retention-days` | `14` | GitHub が、この Action のアップロードする artifact をすべて保持する日数です。1から90の範囲で指定し、短いほど早く容量が空きます。 |
| `compression-level` | `6` | 実行全体の zip の Zlib レベルで、0から9です。ほとんどが動画の実行は、どのレベルでもほぼ縮みません。その場合は `0` にすると、アップロードが速くなります。 |
| `log-tail-kb` | `1024` | これより大きい `deviceLog` のファイルは、zip の中では末尾の `log-tail-kb` KB だけを残します。`0` にすると、すべてのログを全量のまま残します。 |
| `size-warn-mb` | `500` | ステージした内容が、圧縮前でこのサイズを超えたときは、実行全体のアップロードを省き、コメントで警告します。`0` にすると、この保護を無効にします。 |
| `upload` | `true` | `false` にすると、何もアップロードせず、`artifact-url` を実行全体のリンクとして使います。既存の `bajutsu-e2e` Action のように、`runs/` をすでにアップロードしたステップのあとで使います。そのときコメントは、スクリーンショットと動画をパスで示し、ファイルごとの artifact にはリンクしません。`false` のときは、何もステージしません。そのため、ログの切り詰め、`size-warn-mb`、`retention-days`、`compression-level` は適用されず、コメントも切り詰めに触れません。パスはすべて `<runId>/<マニフェストが記録する名前>` の形で示します。これは、`runs/` をアップロードした場合のレイアウトです。`artifact-url` が空なら、ワークフロー実行へリンクします。 |
| `artifact-url` | 空 | `upload` が `false` のときにリンクする artifact の URL です。 |
| `issue-number` | イベントのプルリクエスト番号 | コメントを付けるプルリクエストまたは Issue です。プルリクエストのイベント以外では省略でき、省略したときはジョブサマリーだけを書き、コメントは投稿しません。 |
| `github-token` | `${{ github.token }}` | コメントを書き込むトークンです。 |
| `comment-key` | `${{ github.workflow }}-${{ github.job }}` | 固定コメントのキーです。キーが異なる2つのジョブは、2件のコメントを保ちます。マトリクスのジョブは、キーにマトリクスの値を足します。足さないと、各レグが前のレグのコメントを上書きします。 |
| `comment-author` | `github-actions[bot]` | 固定コメントを所有するアカウントのログインです。`github-token` が GitHub App のものなら、App のボットのログインを指定します。 |
| `max-failures` | `10` | 詳しく列挙する失敗シナリオの上限です。残りは件数だけを示します。 |
| `evidence-base-url` | 空 | 実行ディレクトリを HTTP で配信する任意のベース URL です。[証跡のベース URL で見た目を完全に保つ](#証跡のベース-url-で見た目を完全に保つ)を参照してください。 |

出力は `artifact-url` の1つで、実行全体の artifact の URL です。

### Action の動作

1. **選択。** スクリプトが `manifest.json` を読み、アップロードするファイルを選びます。失敗した最初の3シナリオについて、失敗したステップのスクリーンショットとシナリオの動画を選び、それらのパスをステップの出力に書きます。
2. **ステージとアップロード。** Action は、[zip を小さく保つ](#zip-を小さく保つ)の方法で、`run-dir` のコピーをランナーの一時ディレクトリにステージします。コピーは、`run-dir` が1つの実行を指す場合も、複数の実行を収めたルートを指す場合も、すべてのエントリーが `<runId>/<マニフェストが記録する名前>` の形になるように根を決めます。そのコピーを `actions/upload-artifact` で、zip の artifact 1つとしてアップロードし、`overwrite` は既定の `false` のままにします。同名のマトリクスのレグは、互いを置き換えず、ジョブのログで衝突として見えます。zip にしないアップロードは、1つの artifact につき1ファイルです（`archive: false`）。composite action はステップを繰り返せません。そこで Action は、スクリーンショット用3つと動画用3つの、計6つの固定アップロードのステップを持ちます。各スロットは、選択のステップが埋めたときだけ動きます。
3. **描画と投稿。** スクリプトは Markdown を描画し、ジョブサマリーに書きます。そのため、プルリクエストのない実行でも結果が見えます。`issue-number` が決まるときは、1行目から末尾の空白と復帰文字を取り除いたものが、隠しマーカー `<!-- bajutsu-evidence:<comment-key> -->` と等しいコメントを探します。完全一致で比べると、手作業の編集のあとに GitHub が改行を CRLF に正規化したコメントを見逃し、重複して投稿します。照合の対象は、作者のログインが `comment-author` と等しいコメントに限ります。Issue のコメントをすべてたどる（`per_page=100`）ので、会話が長くなってもマーカーを見つけられます。見つかれば更新し、なければ新規に作ります。

描画するコメントの形は次のとおりです。先頭には、判定、成功と失敗のシナリオ数、コミットの SHA（`github.sha`）、ワークフロー実行へのリンクを置きます。協定世界時の最終更新日時も置きます。その下に、失敗したシナリオごとのブロックを置きます。ブロックには、シナリオ名、最初に失敗したステップの番号とアクション、失敗の理由を書きます。`steps` に失敗したエントリーがないときは、シナリオ単位の `failure` の要約を書き、ステップとスクリーンショットは示しません。スクリーンショットと動画には、zip にしない artifact へのリンクを付けます。最初の3シナリオに入らないシナリオは、実行全体の artifact 内のパスで、スクリーンショットと動画を示します。パスは `<runId>/<マニフェストが記録する名前>` の形です。

描画処理は、シナリオ名、失敗理由、artifact のパスをそれぞれコードスパンに入れ、複数行にわたる文字列はフェンスつきブロックに入れます。コードスパンの区切りには、文字列の中で最も長いバッククォートの連続より1つ長い連続を使い、両端に空白を1つずつ入れます。フェンスつきブロックのフェンスも、中のどのバッククォートの連続より長くします。コードスパンとフェンスにより、アプリ由来の文字列はメンションや HTML を加えられません。さらに `<!--` と `-->` を残らなくなるまで繰り返し取り除き、2つ目のマーカーを偽造できないようにします。

スクリプトが読むのは、マニフェストがすでに記録しているフィールドだけです。マニフェストに載っていないスクリーンショットや動画は、コメントから省きます。省略はエラーにしません。描画処理は、理解できる `manifest.json` の `schemaVersion` の下限を固定し、ファイル自身の値と比べます。値が下限より低いか、認識できないときは、コメントがその旨を明示します。将来 `bajutsu/common/report/manifest.py` でスキーマが変わっても、空のブロックではなく、目に見える通知として現れます。

### zip を小さく保つ

これらの措置は、`upload` が `true` のときに適用します。Bajutsu は、記録中に `device.log` へ上限を設けません。そのため、Action がステージしたコピーの中で、ログに上限をかけます。取得時にログへ上限を設けると Bajutsu 本体の変更になるため、この項目では扱いません。別の項目で追加できます。

- **大きすぎるログを切り詰める。** ステージしたコピーでは、`log-tail-kb` を超える `deviceLog` の artifact（`manifest.json` が挙げるもの。マニフェストがなければ `<sid>/result.json` が挙げるもの）を、末尾の `log-tail-kb` KB に置き換えます。切り詰めたファイルの1行目には、元のサイズと残したサイズを書きます。コメントも、ログを切り詰めたことを述べます。元のファイルはどこにもアップロードされず、ジョブのランナーが破棄されると失われます。失敗の痕跡はログの終わり近くに残るため、末尾を残します。
- **収まらないアップロードの前に警告する。** スクリプトは、ステージしたファイルのサイズを、圧縮前で合計します。合計が `size-warn-mb` を超えたら、実行全体のアップロードを省きます。コメントは合計としきい値を示し、小さなファイルごとの artifact には引き続きリンクします。この保護は、リポジトリ所有者の共有ストレージ枠を守ります。枠はすべての artifact を数え、満杯になると以後のアップロードが失敗します。合計は圧縮前の値なので、zip がよく縮むログの多い実行では、実際より大きく見えます。ログを全量で残す `log-tail-kb: 0` のチームは、`size-warn-mb` を上げるか、`0` にします。既定のしきい値は、控えめな見積もりであり、GitHub の上限ではありません。この項目を書いた時点では、artifact 1つの最大サイズとプランごとの容量枠を、公式ページで確認できていません。各チームが、自分のプランに合わせて調整します。実行全体のアップロードを省いたときや失敗したときは、コメントがその中のパスを列挙せず、出力の `artifact-url` も空になります。
- **保持期間を短くする。** `retention-days` の既定は14です。GitHub の既定の90日より短くしています。プルリクエストの証跡は、マージ後に価値が下がるからです。
- **圧縮を調整する。** `compression-level` は、既定の6のままにします。ログはよく縮むからです。ほとんどが動画の実行では、`0` にすると、サイズをほとんど増やさずにアップロードが速くなります。

切り詰めで `manifest.json` を書き換えることはありません。展開した `report.html` を開いた読み手には、ログのリンクが短くなったファイルを指して見えます。その旨を伝えるのは、コメントの役割です。

### ブラウザーで証跡を見る

PNG、MP4、WebM を zip にせずにアップロードすると、ブラウザーはそれをそのまま表示します。表示に JavaScript は要りません。この性質のため、ファイルごとの artifact を、素早く確かめるための主な経路にします。ただし、zip にしない artifact が、すべてのブラウザーで表示用に配信されるのか、ダウンロード用に配信されるのかは、GitHub のドキュメントに書かれていません。そこで、最初の作業項目はスパイクにします。スクリーンショットと動画を `archive: false` でアップロードし、サインイン済みの読み手に何が見えるかを記録します。表示されずにダウンロードになるファイル形式があっても、リンクからファイルは届きます。その結果は、ドキュメントに明記します。

この Action は、`report.html` を zip にしない artifact としてはアップロードしません。動機で述べたとおり、相対パスの画像と動画が壊れるからです。レポート全体を見たい読み手は、実行全体の zip をダウンロードして展開し、`report.html` を開きます。これはオフラインでも動きます（[BE-0060](../BE-0060-run-report-zip-export/BE-0060-run-report-zip-export-ja.md)）。

### サイズと失敗時の動作

GitHub のコメントには、約65,000字の上限があります。描画処理は、`run-dir` 配下のすべての実行を通して数え、`max-failures` 件を超えるシナリオの列挙をやめ、省いた件数を書きます。本文全体も、上限より低い決まった長さで切ります。各失敗理由も、決まった長さで切り詰めます。

実行ディレクトリに `manifest.json` がないときは、スクリプトが各 `<sid>/result.json` を読みます。Bajutsu は、シナリオが終わるたびにこのファイルを書きます。終えたシナリオと、切り詰める `deviceLog` の artifact は、このファイルから分かります。そのうえで、実行全体を、ステージしてアップロードします。クラッシュやジョブのタイムアウトで途中で止まった実行には、マニフェストが残りません。Bajutsu は、すべてのシナリオが終わってからマニフェストを書くからです。コメントは、実行が完了しなかったことを書き、ワークフロー実行へリンクします。そのため、クラッシュした実行のあとに、以前の判定が残り続けることはありません。複数の実行を収めたルートでは、マニフェストのないディレクトリをすべてコメントに名指しし、読み飛ばしません。

すべてのアップロードのステップは `continue-on-error: true` で動かします。アップロードに失敗しても、ほかの失敗と同じく警告を出すだけにとどめます。そのときコメントは、証跡のアップロードに失敗したことを書き、artifact の代わりにワークフローの実行へリンクします。Action がジョブの結果を変えることはありません。合否は、すべての Bajutsu の実行と同じく、テストのステップ自身の終了コードが決めます。トークンに書き込み権限がない場合（フォークからのプルリクエストのトークンは読み取り専用です）や、API 呼び出しが失敗した場合は、スクリプトが警告を出します。サマリーだけを書き、終了コード0で終わります。Action のどこにも LLM は登場しません。コメントが運ぶのは、決定的な実行がすでに確定した判定です。

### シークレット

ログの切り詰めは伏せ字処理ではなく、ステージしたコピーには、ログがすでに持つ内容がそのまま残ります。Action が投稿するのは、`manifest.json` がすでに持っている文字列です。その文字列は、実行がマニフェストを書く前に伏せ字にしています（[BE-0331](../BE-0331-artifact-redaction-boundary/BE-0331-artifact-redaction-boundary-ja.md)）。Action は、デバイスログや `network.json` のような新しい文字列の出所を足しません。コメントにファイルの中身を埋め込むこともありません。artifact には、リポジトリのアクセス規則がそのまま適用されます。開くにもダウンロードするにも、読み取り権限が必要です。スクリーンショットと動画はアプリ自身の画面であり、文字列の伏せ字処理は及びません。アップロードできないチームは、`upload: false` を設定し、画像と動画は自分たちの方法で扱います。

### 証跡のベース URL で見た目を完全に保つ

artifact のリンクは、サインインを必要とする URL なので、コメントの中に画像を描画できません。実行を HTTP でも配信しているチームは、この制約を埋められます。`evidence-base-url` を設定すると、描画処理は、スクリーンショットを `![](<base>/<path>)` として、動画をリンクとして、さらに `<base>/report.html` へのリンクとして出力します。いずれも同じベースの下に置きます。パスの各セグメントは、ベースに連結する前にパーセントエンコードします。Action がその場所へアップロードすることはありません。[BE-0110](../BE-0110-evidence-store-uri/BE-0110-evidence-store-uri-ja.md) のアップロードを済ませたジョブが、公開 URL か署名付き URL のベースを渡します。この入力は認証情報を運びません。署名付き URL は、期限が切れると画像が壊れます。この点も、ドキュメントに明記します。

### ドキュメントと導入

`docs/reporting.md` と `docs/ja/` のミラーに、そのままコピーできるワークフローの節を足します。実行のステップに続けて、`if: always()` つきで `post-evidence` を置く形です。最初の利用者として、このリポジトリの web E2E ワークフローに Action を導入します。実際の失敗を使って、コメントの形を CI で確かめるためです。

## 検討した代替案

- **コメントを投稿する `bajutsu` のサブコマンド。** サブコマンドなら、レポートのコードを直接再利用でき、GitHub Actions の外でも動きます。採用しなかったのは、目標が Bajutsu 本体を変えないポータブルな形だからです。さらに、コメントを投稿するためだけに、利用側の全ジョブが Bajutsu を入れる必要が出ます。
- **[BE-0500](../BE-0500-run-set-github-check/BE-0500-run-set-github-check-ja.md) の拡張。** チェックはすでに `serve` 上で動くので、証跡のリンクを足すのは自然です。それでも分けたのは、BE-0500 が `serve` の運用と GitHub App を必要とし、この Action はどちらも要らないからです。Markdown の描画処理を将来共有する余地はありますが、ここでは扱いません。
- **`ctrf.json` を読む CTRF レポーターの Action。** [BE-0161](../BE-0161-ctrf-report-export/BE-0161-ctrf-report-export-ja.md) のファイルから、結果の表を描画するレポーターはすでにあります。ただし、添付ファイルの扱いはレポーターごとに異なります。失敗と artifact 内のスクリーンショットを結ぶ保証もありません。自分たちで制御できる描画処理を選びました。両方を使うことも妨げません。
- **`report.html` を単独で、zip にしない artifact としてアップロードする。** ページは開きますが、相対パスの画像と動画は行き先がなく表示されません。artifact のページが、インラインの JavaScript を実行させるかどうかも、未確認です。
- **画像を `data:` URI で埋め込んだ単一ファイルの `report.html`。** Bajutsu のレポートを変えることになり、この項目はそれを避けます。動画は大きすぎて埋め込めません。上の JavaScript の問題も同じく当てはまります。artifact のページがスクリプトを実行するとスパイクで分かれば、後続の項目で見直せます。
- **スクリーンショットを `data:` URI でコメントに埋め込む。** GitHub のサニタイザーが取り除きます。コメントのサイズ上限にも収まりません。
- **サードパーティの artifact ビューアー（artifact.ci の GitHub App など）。** artifact 全体を閲覧できるリンクを作れますが、実行のスクリーンショットと動画を第三者に渡すことになります。既定には含めず、各チームの判断に委ねます。
- **証跡を孤立ブランチやリリースにコミットする。** どちらでも、安定した画像 URL が手に入ります。ただし、リポジトリが肥大化します。コンテンツへの書き込み権限と、保持期間の方針も要ります。任意のベース URL なら、チームがこの選択を自分で行えます。
- **`report.html` を GitHub Pages に公開する。** Pages なら、レポート全体をブラウザーで見られます。一方で、多くのリポジトリで実行結果が既定で公開されます。プルリクエストごとの削除方針も要るため、後続の項目に回します。設定済みのチームは、ベース URL で同じ結果を得られます。
- **記録中に Bajutsu 側でデバイスログへ上限を設ける。** 取得時の上限は、[BE-0060](../BE-0060-run-report-zip-export/BE-0060-run-report-zip-export-ja.md) の zip の書き出しを含む、すべての利用者に効きます。ただし記録処理を変えることになり、この項目はそれに手を付けません。独立した項目にするのが筋です。
- **`device.log` を zip から外す。** zip は小さく保てますが、ログはクラッシュを説明する証跡です。末尾を残せば、失敗を運ぶ部分を保てます。
- **既存の `bajutsu-e2e` Action の隣で、二重にアップロードすることを許容する。** その場合、iOS の全ジョブが実行を二重に保存します。`upload` と `artifact-url` の入力を使えば、そうしたジョブは最初のアップロードにリンクできます。
