## はじめに

補助スクリプト `scripts/post_run_url.py` を追加します。`serve` にある run の URL を、プルリクエスト、Issue、リリースへ書き込みます。プルリクエストと Issue には、コメントを1件書きます。コメントには、判定、失敗したシナリオごとの最初に失敗したステップとその理由、run へのリンクを載せます。もう一度実行すると、同じコメントを書き換えます。リリースには、同じ内容を、リリースノートの区切られたブロックとして書きます。

このスクリプトは、何もアップロードしません。run はすでに `serve` にあり、run を `serve` に取り込む項目が、その URL を返します。このスクリプトは、run の場所を人に知らせるだけです。標準ライブラリだけを使い、`bajutsu` から何も import せず、判定のあとに動くので、判定を変えることはありません。

## 動機

レビュアーが読むのは、サーバーの履歴ではなく、プルリクエストです。エンジニアが run を取り込んだあとも、リンクをレビュアーに届ける作業が残り、今日は手で貼っています。貼ったリンクだけでは、何も分かりません。run が通ったのか、どのシナリオが失敗したのかは、開いてみるまで分からないからです。

GitHub には、スクリプトが run の zip や動画をコメントに添付する、文書化された手段がありません。そのため、証跡は `serve` に残し、コメントには、テキストとリンクを載せます。観察できる違いは、コメントそのものです。`python3 scripts/post_run_url.py runs/<runId> --url <url> --to owner/repo#123` を実行すると、プルリクエストに、件数、各失敗、リンクを載せたコメントが1件できます。再実行すると、そのコメントがその場で書き換わり、テストがそれを確かめます。

## 詳細設計

### コマンド

```
python3 scripts/post_run_url.py <run-dir | run-id> --url URL --to TARGET
        [--archive-url URL] [--runs DIR] [--marker NAME] [--author LOGIN]
        [--max-failures N] [--dry-run] [--yes]
```

`<run-dir | run-id>` は、コメントが判定と失敗を報告する run を指します。run ID は、`--runs`（デフォルトは `runs`）の下から探します。スクリプトは `manifest.json` を読み、マニフェストがない場合は、各 `<sid>/result.json` を読みます。`--url` は必須で、取り込みが返した run の URL です。パスに `/runs/<runId>/` を含まない URL は、拒否します。ある run の判定に、別の run のリンクを組み合わせたコメントを、作らないためです。スキームが `http` か `https` であることも求め、空白、`<`、`>`、`)` を含む URL は拒否します。リンクが、コメントの Markdown を壊さないようにするためです。ユーザー情報（`user:password@`）やクエリ文字列を持つ URL も拒否します。`--url` に貼られた認証情報が、公開のスレッドに載らないようにするためで、下で `--marker` が `bajutsu_` の接頭辞を拒否するのと同じ理由です。`--archive-url` は任意で、run の zip へのリンクを1行足します。

`--to` には、`owner/repo#NUMBER`、プルリクエストか Issue の URL、または `release:owner/repo@TAG` を渡します。`#NUMBER` だけの指定は受け付けません。fork を使う開発では、`origin` が fork を指し、リポジトリを推測すると、別のスレッドに投稿しかねないためです。スクリプトがリクエストを送るのは `https://api.github.com` だけで、`--to` の URL は `https://github.com/` のものだけを受け付けます。ほかのホストは、トークンを読む前に拒否します。貼り付けた URL によって、トークンがほかへ送られることはありません。

### コメント

コメントの先頭には、見えないマーカー `<!-- bajutsu-run:<name> -->` を置きます。比較は、末尾の空白とキャリッジリターンを取り除いてから行います。`--marker` は、マーカーの名前を指定します。デフォルトは `local` で、値の全体が `[A-Za-z0-9._-]+` に完全一致する必要があります。`serve` の API キーの接頭辞である `bajutsu_` で始まる値も、拒否します。取り違えたユーザーが、公開のスレッドの見えないマーカーに、秘密を載せてしまわないようにするためです。

そのあとに、判定と件数、`--max-failures`（デフォルトは 10）までの失敗したシナリオごとのブロック、run へのリンクを書きます。省いたブロックの数も記します。

run から来る文字列は、すべてコードスパンに入れ、複数行にわたる場合はフェンス付きのブロックに入れます。区切りには、中にある最も長いバッククォートの連続より1つ長い連続を使います。文字列がバッククォートで始まるか終わる場合は、CommonMark の規則どおり、コードスパンの内側に空白を1つ足します。さらに、`<!--` と `-->` を、残らなくなるまで取り除きます。アプリ由来の文字列が、メンションや HTML、2つ目のマーカーを加えられないようにするためです。run 由来の文字列は、1つにつき 500 文字で切り、省略記号を付けます。そのうえで、本文全体を、コメントでは 60,000 文字、リリースノートでは 120,000 文字より短く切り、切ったときはメモを添えます。GitHub は、65,536 文字を超えるコメントと、125,000 文字を超えるリリースの本文を拒否するためです。コメントには、スクリーンショットを埋め込みません。ログインを求める URL の画像は、GitHub が取得できないためです。

### プルリクエストと Issue への投稿

スクリプトは、マーカーと、トークンのユーザーのログイン（`GET /user` が返します）で、自分のコメントを見つけます。ユーザーを持たないトークンの場合は、`--author` でログインを指定します。スレッドのコメントはページをたどって調べ、見つかれば書き換え、見つからなければ作ります。

### リリースへの投稿

リリースにはコメントがないので、リリースノートにブロックを書きます。ブロックは、`<!-- bajutsu-run:<name> -->` と `<!-- /bajutsu-run:<name> -->` の間に置きます。同じブロックがあれば置き換え、なければ末尾に追記します。リリースは、一覧に対するタグ名の完全一致で探します。タグのエンドポイントは、ドラフトを返さないためです。リリースを作ることも、削除することもありません。リリースがない場合は、エラーにします。

### 認証情報と安全

トークンは、`gh` と同じ順序で、`GH_TOKEN`、`GITHUB_TOKEN` の順に読み、どちらもなければ `gh auth token` に尋ねます。トークンは、リダイレクトされないヘッダーで送るので、リダイレクトが、別のホストへトークンを運ぶことはありません。トークンを、ディスクにもログにも書きません。コメントには、プルリクエストまたは Issue への書き込み権限が要り、リリースの編集には、リポジトリの内容への書き込み権限が要ります。

書き込みの前に、スクリプトは計画を表示します。内容は、投稿先、作る内容か編集する内容、本文です。そのうえで確認を求めます。`--yes` は質問を省き、`--dry-run` は、何も書き込まずに、計画と本文を表示します。終了ステータスは、投稿の成否を表し、run の判定は反映しません。

### テストとドキュメント

テストは、偽の GitHub の HTTP サーバーに対して動くので、ゲートにネットワークは要りません。確かめるのは、固定コメント（作成、編集、キャリッジリターンをまたぐ一致）、`--marker` の規則、`#NUMBER` だけの指定、ほかのホストの `--to` の URL、別の run、壊れた文字、ユーザー情報、クエリ文字列を含む `--url`、バッククォートの空白を含むエスケープ、長さの切り詰め、リリースのブロック（置き換えと追記）、リリースがない場合、トークンの順序とリダイレクトの規則、終了ステータスです。`docs/reporting.md` と `docs/ja/` のミラーに、アップロード用のスクリプトの節に続く節を足します。

## 検討した代替案

- **アップロードと投稿を1つにまとめたスクリプト。** 2つの手順は、失敗する理由も、必要な認証情報（`serve` のキーと GitHub のトークン）も違います。別々のスクリプトにすれば、チームはどちらか一方だけを使え、それぞれを小さく保てます。
- **コメントにスクリーンショットを埋め込む。** 画像は `serve` のログインの内側にあるため、GitHub は表示できません。リンク付きのテキストのコメントなら、この制約を隠さずに伝えられます。
- **zip を GitHub にアップロードする。** [BE-0503](../BE-0503-local-evidence-post/BE-0503-local-evidence-post-ja.md) が、リリースのアセットと固定コメントを提案しました。リリースのアセットは、スレッドごとに1件の痕跡を残し、`gh --attach` は zip を拒否します。この却下は、別の変更が記録します。
- **`scripts/gh_cli.py` を使い回す。** このラッパーは、ロードマップのスクリプトの `gh` の呼び出しを、1か所にまとめています。`scripts/` に2つ目の GitHub クライアントを置くと、このラッパーが防ごうとしたことを繰り返し、トークンの順序や再試行の修正を、2か所に入れる必要が出ます。このスクリプトは、チームがリポジトリの外へ写して使える、単一のファイルのままにします。そのため、隣のモジュールを import できず、標準ライブラリで REST API と直接やり取りします。テストでトークンの順序を固定し、写しを持つ費用は、受け入れます。
- **GitHub Action。** [BE-0504](../BE-0504-pr-evidence-comment-action/BE-0504-pr-evidence-comment-action-ja.md) は、CI の実行を対象にします。このスクリプトは、ワークフローがないノート PC での実行を対象にします。2つの描画処理は、意図して別にしています。Action は CI のアーティファクトをリンクし、このスクリプトは `serve` の run をリンクするので、コメントの形式が違います。エスケープの規則は、どちらも同じです。
