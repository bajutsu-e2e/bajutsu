## はじめに

補助スクリプト `scripts/post_run_url.py` を追加します。このスクリプトは、`serve` にある run の Uniform Resource Locator (URL) を、次の3つの投稿先へ書き込みます。

- プルリクエスト
- Issue
- リリース

プルリクエストと Issue には、コメントを1件書きます。コメントには、判定と run へのリンクを載せます。失敗したシナリオごとに、最初に失敗したステップとその理由も載せます。もう一度実行すると、同じコメントを書き換えます。リリースには、同じ内容を、リリースノートの区切られたブロックとして書きます。

このスクリプトは、何もアップロードしません。run はすでに `serve` にあり、run を `serve` に取り込む項目が、その URL を返します。このスクリプトは、run の場所を人に知らせるだけです。標準ライブラリだけを使い、`bajutsu` から何も import しません。判定のあとに動くので、判定を変えることはありません。

## 動機

レビュアーが読むのは、サーバーの履歴ではなく、プルリクエストです。エンジニアが run を取り込んだあとも、リンクをレビュアーに届ける作業が残り、今日は手で貼っています。貼ったリンクだけでは、何もわかりません。run が通ったのか、どのシナリオが失敗したのかは、開くまで不明だからです。

GitHub には、スクリプトが run の zip や動画をコメントに添付する、文書化された手段がありません。そのため、証跡は `serve` に残し、コメントには、テキストとリンクを載せます。観察できる違いは、コメントそのものです。次のコマンドを例にします。

```
python3 scripts/post_run_url.py runs/<runId> --url <url> --to owner/repo#123
```

実行すると、プルリクエストに、件数、各失敗、リンクを載せたコメントが1件できます。再実行すると、そのコメントがその場で書き換わり、テストがこの動作を確かめます。

## 詳細設計

### コマンド

```
python3 scripts/post_run_url.py <run-dir | run-id> --url URL --to TARGET
        [--archive-url URL] [--runs DIR] [--marker NAME] [--author LOGIN]
        [--max-failures N] [--dry-run] [--yes]
```

`<run-dir | run-id>` は、コメントが判定と失敗を報告する run を指します。run ID は、`--runs`（デフォルトは `runs`）の下から探します。スクリプトは `manifest.json` を読み、マニフェストがない場合は、各 `<sid>/result.json` を読みます。

`--url` は必須で、取り込みが返した run の URL です。スクリプトは、URL を次のように検査します。

| `--url` の検査 | 理由 |
|---|---|
| パスに `/runs/<runId>/` を含むこと | ある run の判定に、別の run のリンクを組み合わせたコメントを作らないため |
| スキーム（Scheme）が `http` か `https` であること | リンクがコメントの Markdown を壊さないようにするため |
| 空白、`<`、`>`、`)` を含まないこと | リンクがコメントの Markdown を壊さないようにするため |
| ユーザー情報（`user:password@`）やクエリ文字列を持たないこと | `--url` に貼られた認証情報が、公開のスレッドに載らないようにするため |

最後の検査の理由は、下で述べる、`--marker` が `bajutsu_` の接頭辞を拒否する理由と同じです。`--archive-url` は任意で、run の zip へのリンクを1行足します。

`--to` には、次のいずれかの形式を渡します。

- `owner/repo#NUMBER`
- プルリクエストか Issue の URL
- `release:owner/repo@TAG`

`#NUMBER` だけの指定は受け付けません。fork を使う開発では `origin` が fork を指すため、リポジトリを推測すると、別のスレッドに投稿しかねないからです。スクリプトがリクエストを送るのは `https://api.github.com` だけです。`--to` の URL は、`https://github.com/` のものだけを受け付けます。ほかのホストは、トークンを読む前に拒否します。貼り付けた URL によって、トークンがほかへ送られることはありません。

### コメント

コメントの先頭には、見えないマーカー `<!-- bajutsu-run:<name> -->` を置きます。比較は、末尾の空白とキャリッジリターンを取り除いてから行います。`--marker` は、マーカーの名前を指定します。デフォルトは `local` で、値の全体が `[A-Za-z0-9._-]+` に完全一致する必要があります。

`bajutsu_` で始まる値も、拒否します。`bajutsu_` は、`serve` の Application Programming Interface (API) キーの接頭辞です。取り違えたユーザーが、公開のスレッドの見えないマーカーに、秘密を載せてしまわないようにするためです。

そのあとに、次の内容を書きます。

- 判定と件数
- 失敗したシナリオごとのブロック（`--max-failures` まで、デフォルトは 10）
- 省いたブロックの数
- run へのリンク

run から来る文字列は、すべてコードスパンに入れ、複数行にわたる場合はフェンス付きのブロックに入れます。区切りには、中にある最長のバッククォートの連続より1つ長い連続を使います。文字列がバッククォートで始まるか終わる場合は、CommonMark の規則どおり、コードスパンの内側に空白を1つ足します。さらに、`<!--` と `-->` を、残らなくなるまで取り除きます。アプリ由来の文字列が、メンションや HTML、2つ目のマーカーを加えられないようにするためです。

run 由来の文字列は、1つにつき 500 文字で切り、省略記号を付けます。そのうえで本文全体を切り詰め、切ったときはメモを添えます。

| 投稿先 | スクリプトが本文を切る長さ | GitHub が拒否する長さ |
|---|---|---|
| コメント | 60,000 文字未満 | 65,536 文字超 |
| リリースノート | 120,000 文字未満 | 125,000 文字超 |

コメントには、スクリーンショットを埋め込みません。ログインを求める URL の画像は、GitHub が取得できないためです。

### プルリクエストと Issue への投稿

スクリプトは、マーカーと、トークンのユーザーのログイン（`GET /user` が返します）で、自分のコメントを見つけます。ユーザーを持たないトークンの場合は、`--author` でログインを指定します。スレッドのコメントはページをたどって調べ、見つかれば書き換え、見つからなければ作ります。

### リリースへの投稿

リリースにはコメントがないので、リリースノートにブロックを書きます。ブロックは、`<!-- bajutsu-run:<name> -->` と `<!-- /bajutsu-run:<name> -->` の間に置きます。同じブロックがあれば置き換え、なければ末尾に追記します。リリースは、一覧に対するタグ名の完全一致で探します。タグのエンドポイントは、ドラフトを返さないためです。リリースを作ることも、削除することもありません。リリースがない場合は、エラーにします。

### 認証情報と安全

トークンは、`gh` と同じ順序で、`GH_TOKEN`、`GITHUB_TOKEN` の順に読み、どちらもなければ `gh auth token` に尋ねます。トークンはリダイレクトされないヘッダーで送るので、リダイレクトによって別のホストへ運ばれることはありません。トークンを、ディスクやログに書き出すことはありません。コメントには、プルリクエストまたは Issue への書き込み権限が要ります。リリースの編集には、リポジトリの内容への書き込み権限が要ります。

書き込みの前に、スクリプトは計画を表示して確認を求めます。計画の内容は、投稿先、作る内容か編集する内容、本文です。`--yes` は質問を省き、`--dry-run` は、何も書き込まずに、計画と本文を表示します。終了ステータスは、投稿の成否を表し、run の判定は反映しません。

### テストとドキュメント

テストは、偽の GitHub の HTTP サーバーに対して動くので、ゲートにネットワークは要りません。確かめるケースは次のとおりです。

| 対象 | ケース |
|---|---|
| 固定コメント | 作成、編集、キャリッジリターンをまたぐ一致 |
| 引数 | `--marker` の規則、`#NUMBER` だけの指定 |
| URL の検査 | ほかのホストの `--to` の URL |
| URL の検査 | 別の run の `--url`、壊れた文字を含む `--url` |
| URL の検査 | ユーザー情報やクエリ文字列を含む `--url` |
| 描画 | バッククォートの空白を含むエスケープ、長さの切り詰め |
| リリース | リリースのブロック（置き換えと追記）、リリースがない場合 |
| 認証情報 | トークンの順序とリダイレクトの規則 |
| 結果 | 終了ステータス |

`docs/reporting.md` と `docs/ja/` のミラーに、アップロード用のスクリプトの節に続く節を足します。

## 検討した代替案

**アップロードと投稿を1つにまとめたスクリプト。** 2つの手順は、失敗する理由も、必要な認証情報（`serve` のキーと GitHub のトークン）も違います。別々のスクリプトにすれば、チームはどちらか一方だけを使え、それぞれを小さく保てます。

**コメントにスクリーンショットを埋め込む。** 画像は `serve` のログインの内側にあるため、GitHub は表示できません。リンク付きのテキストのコメントなら、この制約を隠さずに伝えられます。

**zip を GitHub にアップロードする。** [BE-0503](../BE-0503-local-evidence-post/BE-0503-local-evidence-post-ja.md) が、リリースのアセットと固定コメントを提案しました。リリースのアセットは、スレッドごとに1件の痕跡を残し、`gh --attach` は zip を拒否します。この却下は、別の変更が記録します。

**`scripts/gh_cli.py` を使い回す。** このラッパーは、ロードマップのスクリプトの `gh` の呼び出しを、1か所にまとめています。`scripts/` に2つ目の GitHub クライアントを置くと、このラッパーが防ごうとしたことを繰り返します。トークンの順序や再試行の修正を、2か所に入れる必要が出ます。このスクリプトは、チームがリポジトリの外へ写して使える、単一のファイルのままにします。そのため、隣のモジュールを import できません。標準ライブラリで、GitHub の Representational State Transfer API と直接やり取りします。テストでトークンの順序を固定し、写しを持つ費用は受け入れます。

**GitHub Action。** [BE-0504](../BE-0504-pr-evidence-comment-action/BE-0504-pr-evidence-comment-action-ja.md) は、CI の実行を対象にします。このスクリプトは、ワークフローがないノート PC での実行を対象にします。2つの描画処理は、意図して別にしています。Action は CI のアーティファクトをリンクし、このスクリプトは `serve` の run をリンクするので、コメントの形式が違います。エスケープの規則は、どちらも同じです。

ログは次のとおりです。

[#2599](https://github.com/bajutsu-e2e/bajutsu/pull/2599) で 6 つの単位をまとめて実装しました。実装が設計と異なる点は、次の表のとおりです。

| 対象 | 実装した内容と理由 |
|---|---|
| run id の参照 | フラグ名は `--runs-dir` にしました。同じ参照に、アップロード用のスクリプトがこの名前を使うからです |
| `--archive-url` | パスの検査を除き、`--url` と同じ検査をします。署名付きの zip のアドレスは、署名を公開してしまうからです |
| 長さの切り詰め | 上限の近くでは、失敗のブロックを丸ごと省きます。コードスパンの途中で切ると、残りが Markdown として描画されるからです |
| `--dry-run` | トークンがなければ、オフラインのまま計画を表示します。計画には、何も問い合わせていないことを書きます |
| リリースのブロック | 開始のマーカーだけがあって終了のマーカーがなければ、投稿を止めます。リリースノートの文章を失わないためです |
