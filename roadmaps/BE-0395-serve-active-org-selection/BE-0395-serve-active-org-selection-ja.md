## はじめに

**org** とは、ホスティングされた `serve` があらゆるものを分割する単位となるテナントのことです。実行結果と証跡、シナリオとシークレット、登録されたプロジェクト、サインインしたユーザーが到達できる[ターゲット](../../docs/ja/glossary.md#target-app-device)は、いずれも org ごとに分かれています。ところが現在、ユーザーはそのうちちょうど 1 つにしか所属できません。GitHub OAuth のサインインは、ログインを 1 つの org に解決して `users.org_id` 列に書き込みます。それ以降のすべてのリクエストは、`ServeState.org_of` を通じてその 1 列だけを読みます。

この 1 列は、GitHub 上のメンバーシップが複数の org に一致するユーザーにとって誤った表現です。解決処理は最初に一致した org を選び、その選択を二度と見直しません。したがって残りの org には到達できません。到達しにくいという程度の話ではなく、Web UI 上にその org の存在を示すものが何もないため、見えないのです。

そこで、メンバーシップを集合にし、org を選択の対象にすることを提案します。サインイン時に、ログインが所属するすべての org を、それぞれで持つロールとともに記録します。ユーザーは Web UI のヘッダーにある選択欄から、現在のテナントを表示している既存の org バッジの位置で、操作する org を選びます。次回のサインインは、その選択を上書きせずに尊重します。所属する org が 1 つだけのデプロイに変化はありません。適格な org が 1 つであれば、バッジは今日とまったく同じように表示されます。

## 動機

Bajutsu のマルチテナントな `serve` は、軸を 1 つずつ足しながら作られてきました。BE-0015 が org を導入し、各ユーザーに所属先を示す列を与えました。[BE-0313](../BE-0313-github-org-team-rbac/BE-0313-github-org-team-rbac-ja.md) は、ログインが org に所属する経路を 3 つに広げました。1 つは `members` への明示的な記載です。もう 1 つは org が `githubOrgs` で主張する GitHub organization への所属です。残る 1 つは、その org が `githubTeams` または `editorTeams` で主張する GitHub Team への直接の所属です。[BE-0375](../BE-0375-serve-org-lifecycle-management/BE-0375-serve-org-lifecycle-management-ja.md) はメンバーシップの名簿全体をデータベースへ移し、管理者が編集できるページを与えました。どの段階も重複を起こりやすくしましたが、重複を解消できるようにした段階はありません。

重複は、これらの項目が想定するデプロイの形において、稀な例外ではありません。1 つの Bajutsu デプロイを複数の顧客テナント向けに運用しているコンサルティング企業が、あるエンジニアを 2 つのテナントへ割り当てます。プラットフォームチームが自分たちの org を持ちながら、自分たちも所属する GitHub organization を持つプロダクトの org にも属します。どちらの場合も、その人は 2 つの org の正当なメンバーでありながら、たまたま先にソートされたほうでしか作業できません。BE-0375 自身がそう書き、行き止まりの原因も名指ししています。本当の答えは、複数の org へ所属するログイン自身に選ばせることです。そのためには `users.org_id` が単一の列であることをやめる必要がある、とも書いてあります。

制限そのものよりも問題なのは、制限の周りが無言であることです。ヘッダーのバッジは 1 つの org を表示するだけで、2 つ目が存在する気配を示しません。そのため、実行結果が意図しないテナントに入ってしまったユーザーには、デプロイの設定が誤っているのか、それとも単に同点処理が選んだテナントを見ているだけなのかを区別する手立てがありません。ブラウザから見ると 2 つは同じに見えますが、後者はそもそも障害ではありません。

この項目が実装されると、2 つの org に所属するユーザーはサインインしてヘッダーの選択欄を開けます。2 つ目の org を選ぶと、そのテナントの実行結果とプロジェクトとターゲットが見えます。そのうえでサインアウトして再びサインインすると、同点処理が選んだであろう org ではなく、自分が選んだ org に着地します。1 つの org にしか所属しないユーザーが見るヘッダーは、今日と同じです。

## 詳細設計

### 用語

**org** はテナントであり、データベースの行 id を兼ねるスラッグで識別します。**アクター**はリクエストの背後にある GitHub のログインで、セッションから復元されます。**ロール**は `viewer`、`editor`、`admin` のいずれかで、アクターがどのエンドポイントに到達できるかを決めます。**適格な org** とは、宣言されたメンバーシップがそのログインを受け入れる org のことです。**アクティブな org** とは、そのアクターのリクエストが現在解決される先の org です。`ServeState.org_of` が返す唯一の適格な org であり、すべてのタブはこの org の実行結果、証跡、シナリオ、シークレット、プロジェクトを表示します。

### 1. メンバーシップを集合にし、サインイン時に求める

`bajutsu/serve/orgs.py` は 3 つのメンバーシップの軸を `_match_org` という 1 箇所で順位付けし、最初に一致した org を返します。順位は、`members` への明示的な記載が最優先、次に org の `githubOrgs` との交わり、最後にその org が受け入れる Team への直接の所属です。この順位付けはそのまま残し、返す値だけを変えます。新しい `orgs_for_identity` は、一致するすべての org を同じ順位のまま返します。`org_for_identity` はその先頭要素となり、`identity_matches_org` は結果が空でないことの判定になります。順位付きリストの先頭は従来の関数が返していた org そのものですから、呼び出し側の振る舞いは変わりません。

この集合は OAuth のコールバックより長く生き延びる必要があります。ログインの GitHub organization と Team の所属が判明する場所は、そのコールバックだけです。Bajutsu はその後 GitHub のトークンを保持しないため、セッションの後続の処理では計算し直せません。集合は新しい `user_orgs` 表に記録します。`(user_id, org_id)` の組ごとに 1 行を持ち、その組が解決するロールを併せて持ちます。ロールをユーザーではなく行に置くのは、ロールが構造上 org ごとのものだからです。`editorTeams` はある org の中でメンバーを `editor` に昇格させますが、別の org については何も述べません。

サインインのたびに、そのユーザーの行はまとめて置き換えます。統合ではなく再計算にするのは、GitHub organization から抜けたことが次のサインインで反映されるようにするためであり、BE-0313 がロールに与えたのと同じ自己修復の性質です。

### 2. アクティブな org は、次のサインインが尊重する選択になる

`users.org_id` は 1 列のままで、すべての読み手にとっての意味も変わりません。アクティブな org です。変わるのは、誰が書くかです。現在の `oauth_callback` はサインインのたびに最初の一致で上書きします。今後は、記録済みの値がもはや適格でない場合にだけ上書きします。選んでいた org から外されたユーザーは、新しい適格リストの先頭に着地します。それ以外の場合は、記録された選択をそのまま残します。どちらの場合も、サインインが `users.role` に書くのは、最初の一致ではなくアクティブな org 自身の `editorTeams` から求めたロールです。別のテナントの `editorTeams` が与えたロールを持ち越さないためです。

列を維持することが、この変更を小さく保ちます。`ServeState.org_of(actor)` は、実行結果の一覧から org ごとのシークレットストアまで、org で区切られたすべての読み書きがすでに通る唯一の接合点です。そのメソッドがすでに読んでいる場所に選択を置けば、新しい配線は要らず、あるタブだけが別のテナントに向くこともありません。

選択をセッションではなくユーザーに持たせるのは意図的であり、代替案が退けられる理由も文体の好みではなく具体的です。セッション単位の選択はセッションのレコードに載せる必要がありますが、ホスティングされたデプロイではそのレコードは複数のレプリカで共有されるデータベースの行（`SqlSessionStore`）です。一方で `org_of` はアクターをキーに取り、セッションを受け取りません。`org_of` のすべての呼び出し側にセッションを通すのは、この機能が正当化できる範囲をはるかに超えた変更です。加えて、再ログインのたびに選択が消えることになり、1 週間を通じて 1 つのテナントで作業するユーザーが望むものの逆になります。

### 3. org を切り替える

新しいエンドポイントは 1 つ、切替先のスラッグを受け取る `POST /api/org` です。切替の可否は、サインイン時に書かれた `user_orgs` の行で判定します。そのユーザーの行が存在しないスラッグは 403 で拒否し、行の集合そのものが見つからない場合は、緩い側に倒さずすべてを拒否します。ただし管理 Team のメンバーは例外で、その適格な集合は行として保存されず、4 節のとおり読み取り時に求めます。成功時には `users.org_id` と `users.role` の両方をその行から書き込みます。サインイン時と同じように、ロールがテナントに追随します。

この切替は管理者専用の操作ではなく、認証済みユーザーの通常の操作です。すでに自分を受け入れている org のあいだを移動するだけであり、前回のサインインが確立した以上のものは何も与えません。前回のサインインが持つ待ち時間は、両方向に受け継ぎます。その後に取り消されたメンバーシップは、次にサインインするまで切替を受け入れ続けます。すでに振る舞っている org を受け入れ続けるのと同じです。これは `serve` のメンバーシップ変更がもともと持つ待ち時間です。BE-0313 はログインごとに配置とロールを計算し直しますし、`update_org_membership` も自身の書き込みについて同じことを書いています。それでも、`serve` の運用上重要なほかの操作と同じように記録します。`oplog` を通じた `org.switch` イベントと、切替先のスラッグを対象とする `Repository.record_audit` の監査行です。監査ログを後から読む人は、アクターが操作した時点でどのテナントにいたのかを知る必要があり、サインインの記録だけではその問いに答えられなくなるからです。

起動時に読む `GET /api/config` には、すでに返している `actor` と `org` に加えて `orgs` フィールドを足します。中身は適格なスラッグをスラッグ順に並べたものです。順位が決めるのはログインの出発点だけなので、保存する集合には持ち込まず、選択欄の並びは単に安定させます。メンバーシップからこの一覧を生み出した当人にそれを開示しても、切り替えれば得られる以上の情報は渡りません。同じエンドポイントが自分自身のログインとアクティブな org を返す一方で、org の名簿全体は管理者専用の `GET /api/orgs` の背後に留まっているのも、同じ理由によります。

### 4. 管理 Team のメンバーはすべての org に適格とする

`BAJUTSU_OAUTH_ADMIN_TEAMS` で指定するサーバー全体の管理 Team のメンバーは、どの org も自分を受け入れない場合でもサインインできます（[BE-0352](../BE-0352-admin-team-bootstrap-bypass/BE-0352-admin-team-bootstrap-bypass-ja.md)）。そのため、順位付きの適格リストはしばしば空になります。何もしなければ、選択欄はヘッダーのバッジがもともと想定していた相手からこそ隠れてしまいます。複数の org を管理し、自分の作業がどこに入るのかを見る必要のある管理者です。

そこで管理 Team のメンバーの適格な集合は、そのデプロイが持つすべての org とし、行として保存せず `Repository.list_orgs` から読み取り時に求めます。保存してしまうと、管理者が Orgs のページで org を作った瞬間に古くなります。作成は、そうしたユーザーが切替を望む直前にもっとも起こしやすい操作です。管理 Team のメンバーかどうかの判定には `users.role == "admin"` を使います。この条件はちょうど管理 Team のメンバーに対して成り立ちます。`role_for` が `admin` を返すのは管理 Team への所属によるときだけであり、ほかの理由で返すことはないからです。切替後も管理者のロールは `admin` のままです。そのロールはサーバー全体の Team に由来し、どの org のメンバーシップにも由来しないためです。

### 5. ヘッダーの選択欄

Web UI のヘッダーにはすでに org バッジ（`#orgbadge`）があり、起動時の読み込みで内容が入り、誰もサインインしていないときは隠れます。適格な org が 2 つ以上あるとき、このバッジをそれらを並べたネイティブの `<select>` にします。同じ行にはすでに同じ仕組みで動くプロジェクトの切替欄があり、その隣に並びます。適格な org が 1 つのときは今日と同じ読み取り専用のバッジのままなので、単一テナントのデプロイと単一 org のユーザーには何の変化もありません。

選択を変えると `POST /api/org` を呼び、ページを再読み込みします。ビューごとの部分更新ではなく再読み込みにするのは、すべてのタブが暗黙にアクティブな org で区切られているためです。部分更新では、すでに描画済みのビューが前のテナントの実行結果とプロジェクトを表示したままになり、この項目が取り除こうとしている混乱そのものが残ります。

### 6. 切替が動かさないもの

切替が変えるのは、そのアクターの次の操作がどこに入るかだけで、すでに起きたことは何も動かしません。実行中のジョブは、投入時に決まった org を保持します。ジョブの仕様は投入時に一度解決された `job.org` を持ち、リモートのワーカーまで運ばれます。そのため、実行中にアクターが切り替えても、証跡もデータベースの行も、実行を開始した org に入ります。すでに記録された実行結果、監査エントリ、アップロード済みのバンドルは、記録された場所に留まります。

既存の振る舞いのうち 1 つは到達しやすくなるので、後から発見されるのに任せず、ここに記録しておきます。設定をバインドすると、プロセス全体で共有される `state.config_org` がバインドした側の org から設定されます（`bajutsu/serve/operations/config.py`）。そのため、2 つの org がどちらも設定をバインドするデプロイでは、最後にバインドした側がサーバー全体に対して勝ちます。切替欄はこの振る舞いを生み出しもしませんし、変えもしません。1 人のアクターがログアウトせずにそこへ到達できるようにするだけです。これを直すには org ごとに固有の設定を持たせる必要があり、それは [BE-0393](../BE-0393-per-org-config-memory/BE-0393-per-org-config-memory-ja.md) が提案していることそのものです。したがってこの項目は、相互作用を記録するところで立ち止まります。2 つは独立しています。バインドが org ごとかどうかに関わらず選択欄は機能します。ログインが切り替えられるかどうかに関わらず、BE-0393 の org ごとの記憶には価値があります。

## 検討した代替案

**サインイン時に曖昧な一致を拒否する。** 2 つの org に一致するログインを追い返せば、重複は無言ではなく声を上げるようになります。誰も選んでいない同点処理に対する、正直な失敗の形ではあります。しかし同点処理で満足している運用者のデプロイにおいて、今日は問題なくサインインできているログインまで追い返すことになり、無言の制限を明確な後退と引き換えにしてしまいます。

**org に順序を与えて同点処理を意図的なものにする。** org の表に順序の列を足せば、複数に一致するログインに対してどの org を勝たせるかを運用者が決められます。変更としてはこちらのほうが小さいものの、答えている問いが違います。決めるのが*デプロイ*になってしまい、今日どのテナントで作業したいかを知っているのはユーザーのほうです。

**org を URL またはリクエストヘッダーに載せる。** リクエストごとにクライアントが指定する org で区切れば、2 つのタブで 2 つのテナントを同時に開けます。しかしそれは、テナントの境界をサーバー側の 1 つの接合点から、すべてのリクエストのパラメーターへ移すことでもあります。値の欠落や偽装は、1 つのメソッドではなくエンドポイントごとに防がなければなりません。まだ誰も求めていない利便性のために足すには、広すぎる面です。

**適格な集合を表ではなくセッションに置く。** セッションのレコードはすでに有効期限を持ち、すでに複数のレプリカにまたがるので、寿命としては適切であり、再ログインが集合を無料で更新してくれます。ただし `SessionStore` のプロトコルにはインメモリと Redis と SQL の 3 つの実装があり、集合はその 3 つすべてに通す必要があります。そのうえ切替のエンドポイントは org ごとのロールを必要としますが、これはセッションの状態ではなくユーザーの状態です。表であれば、マイグレーション 1 つで済み、触れる実装も 1 つで済みます。

      フィールドも足す。テスト：移動とそのロール、監査行とイベント、拒否された切替が何も記録しない
      こと、org 未指定と identity 不在とデータベース不在の拒否。
- [x] 4 — `ServeState.eligible_orgs` が、`users.role == "admin"` の呼び出し元に対して生存している
      すべての org を答えるようにする。保存ではなく `list_orgs` から読む。テスト：自分の `user_orgs`
      行を持たない admin がすべての org に適格であること、サインイン後に作られた org へ切り替え
      られること。
- [x] 5 — 適格な org が 2 つ以上のとき、ヘッダーの `#orgbadge` が `#orgsw` の `<select>` に道を
      譲るようにする。切替は 1 つのビューの更新ではなくページの再読み込みで行う。テスト：選択欄が
      隠れた状態で出荷されること、2 つの表示のうち片方だけが見えること、再読み込みの結線。
- [x] 6 — `docs/web-ui.md` と `docs/self-hosting.md`、およびそれぞれの `docs/ja/` の対応版を書く。
      選択欄、エンドポイント、保持される選択、admin のデプロイ全体にわたる適格性、そして切替が元の
      場所に残すもの。
