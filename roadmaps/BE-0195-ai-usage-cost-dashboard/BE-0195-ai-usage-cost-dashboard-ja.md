## はじめに

本項目は、読み取り専用の **AI 使用量ダッシュボード**を serve の Web UI に追加します。このページは、
属性付きの使用量台帳（`ai-usage-cost-ledger` 項目が定義します）を読み、Bajutsu の AI のトークンとドルが
どこに向かっているかを示します。使用量は、プロバイダ、モデル、コマンド、シナリオごとに分解し、時系列の
傾向として表示します。

本項目は、*AI usage and cost observability* トピックのうち、可視化を担う半分です。記録を担う半分が
データを生み、本項目がそのデータを、行動に移せるほど読みやすくします。

## 動機

台帳は増え続ける JSONL ファイルです。永続的で完全ですが、チームが手で読むものではありません。
属性付きの使用量を記録する意義は、それを*見る*ことにあります。見ることで、チームは次のことに気付けます。

- あるシナリオが crawl の予算を占めていること。
- あるモデルが、返す価値に比べて不釣り合いに高いこと。
- あるコマンドのプロバイダを切り替えれば、結果を損なわずにコストを下げられること。

生のログは、これらのどれにも一目では答えません。ダッシュボードは答えます。

Bajutsu には、すでにこのためのパターンがあります。BE-0102 は、読み取り専用の実行統計ダッシュボード
（テスト実行履歴の合否の集計）を serve に導入しました。BE-0169 は、`/metrics` の可観測性エンドポイントを
追加しました。AI 使用量ダッシュボードは、同じ形を新しいデータソースに適用したものです。また、これは
まったく存在しない唯一の AI 使用量サーフェスでもあります。`bajutsu/usage.py` は CLI の標準出力に出力する
だけで、`serve.js` はトークンやコストについて何も表示しないからです。

ダッシュボードは、可観測性にとどまります。コストを*報告し*、人がより良いプロバイダやモデルを選べる
ようにします。実行時には何も決めず、`run` や CI の合否判定に大規模言語モデル (LLM) を持ち込みません。

## 詳細設計

作業は、次の相互排他かつ網羅的（MECE）な単位からなります。

1. **集計済み使用量の読み取り API。** serve のエンドポイント（例：`GET /api/usage`）が台帳を読みます。
   要求された時間範囲について、台帳のディメンション（プロバイダ、モデル、コマンド、シナリオ）ごとに集計した値と、
   合計を返します。集計はサーバ側で行うので、ブラウザは生のイベントストリームではなく、コンパクトな要約を
   受け取ります。エンドポイントは、実行統計ダッシュボード（BE-0102）が使う既存の serve API の慣例に従います。

2. **使用量ダッシュボードのビュー。** `bajutsu/templates/serve.js` に新しいビューを追加し、デスクトップ
   タイラーのレイアウト規則に沿って、保持されるペインの中に描画します。表示するのは次のとおりです。
   - 見出しの合計（期間のトークンとコスト）。
   - プロバイダ別とモデル別の内訳のテーブルまたはチャート。
   - コマンド別とシナリオ別の内訳。
   - 時系列の傾向。

   `cost = null` のサブスクリプションプロバイダは、捏造したドルの値ではなく、トークン数と「トークン単価
   なし」の明示的な印を添えて表示します。

3. **プロバイダ/モデルの比較ビュー。** 最適化の目標に直接応えるビューです。呼び出しあたりのコストと
   シナリオあたりのコストをプロバイダとモデルで比較し、ある種類のタスクにどのプロバイダとモデルが最も
   効率的かを、チームが読み取れるようにします。このビューは記録されたデータを提示するだけです。ビューが
   助ける判断を下すのは、人（またはのちには決定的な設定）であり、ダッシュボードではありません。

4. **台帳が空、または存在しない場合の扱い。** 台帳がまだ存在しない場合（AI 経路が一度も動いていない、
   または永続化を無効にしている）、ビューはエラーにせず、使用量の記録を有効にする方法を説明する明快な
   空状態を描画します。doctor/readiness パネルも、同じように緩やかに縮退します。

5. **テスト。** 集計エンドポイント（グループ化、時間範囲のフィルタ、`cost = null` 経路、空台帳のケース）を、
   フィクスチャの台帳に対してユニットテストします。テストは純粋で Simulator を必要としないので、標準の
   ゲートで動きます。JS のビューは、ほかの `serve.js` のビューと同じやり方で検証します。

## 検討した代替案

- **新しいビューではなく BE-0102 の実行統計ダッシュボードを流用する。** 採用しません。実行統計は
  テストの合否履歴を集計するもので、データソースも答える問いも異なります。AI のコストをそこに畳み込むと
  1 つのページが過積載になります。同じ serve のダッシュボードパターンに従う姉妹ビューのほうが素直です。
- **使用量を BE-0169 の `/metrics` だけで公開し、Grafana は各自で用意してもらう。** すでに Prometheus を
  運用しているチームには妥当で、小さなフォローアップとして取り組む価値があります。ただし、主たる
  サーフェスとしては採用しません。外部のツールを必要とするうえ、実行統計ダッシュボードが前例を作った、
  セットアップ不要の「serve を開けば自分の AI コストが見える」体験を提供しないからです。両者は共存できます。
  スクレイプには `/metrics`、人が見るにはこのダッシュボードを使います。
- **Web UI のビューではなく CLI サブコマンド（`bajutsu usage`）を作る。** 安価ですが、親トピックの動機は
  *可視化*のサーフェスであり、Bajutsu が集計履歴をすでに提示しているのは serve です。CLI のレポータは、
  同じ台帳と読み取り API の上に、のちの追加として作れます。
