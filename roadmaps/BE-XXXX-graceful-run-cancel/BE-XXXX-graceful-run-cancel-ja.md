## はじめに

`serve` の Web UI では、実行中の run job（`bajutsu run` によるシナリオ一式の実行）を操作者が
途中でキャンセルできます。今の実装では、このキャンセルは判定結果を書き出す前にプロセスをその場で
終了させてしまうため、キャンセルされた run は実行履歴に何も残さず、最初から実行されなかったかの
ように消えます。本項目は、この終了を強制的なものから協調的なものに変えます。run のパイプラインは
安全な境界でキャンセル要求に気付き、完了していなかったシナリオをすべて理由 `"cancelled"` の失敗
として確定させ、通常の失敗した run と同じ `manifest.json`・`report.html`・データベースの記録を
書き出します。これにより、シナリオの実行を開始した後にキャンセルされた run は、必ず失敗した run
として履歴に残り、記録の空白を作りません。

## 動機

Web UI の Cancel ボタンは `Job.cancelled` をセットし、run プロセスのプロセスグループ全体に
`SIGTERM` を送ります（[`jobs.py:99`](../../bajutsu/serve/jobs.py) の `cancel_job` が
[`jobs.py:79`](../../bajutsu/serve/jobs.py) 経由で送信します）。Python は `SIGTERM` を受け取ると、
既定では自前の終了処理を一切実行せずにプロセスを即座に終了させます。そのため `bajutsu run` の
サブプロセスは、たいていシナリオの実行中という中途半端な地点で終了し、`pipeline.py` の
`run_and_report` が `_assemble_report` を呼んで `manifest.json` を書き出すよりも前に、そして
プロセスが最後の1行 `PASS/FAIL  runs/<id>/manifest.json` を出力するよりも前に消えます。

この最後の1行こそが、履歴保存の要です。run の `RunRecord` をデータベースに書き込む `jobs.py` の
`_persist_run` は、正規表現 `_RUN_ID_RE`（[`jobs.py:39`](../../bajutsu/serve/jobs.py)）でその1行を
マッチさせて run の id を知ります。job がその1行を一度も出力しなかったとき、`_persist_run` は
即座に return し、何も永続化しません（[`jobs.py:279`](../../bajutsu/serve/jobs.py)）。実行中に
キャンセルされた run は、`manifest.json` も `report.html` もデータベースの行も一切残さないため、
run 履歴一覧・フレーキネスのランキング・triage ビュー
（[BE-0147](../BE-0147-serve-triage/BE-0147-serve-triage-ja.md)）のどこにも現れません。まるで
一度も実行されなかったかのように扱われます。

止まってしまった、あるいは動きの遅いシナリオ一式をキャンセルした操作者は、それを試みたという記録
そのものを失います。履歴上は「このシナリオはまだ一度も実行されていない」のか「実行を始めたが
キャンセルされた」のかを区別できません。この違いは、同じ操作者や別のメンバーが後で「このシナリオ
にはカバレッジがあるのか」を確かめたいときに重要になります。キャンセルした試みを失敗した run と
して記録すれば、この空白は解消します。キャンセルされた run が成功扱いになるわけではないので、
操作者はもともと選んでいた以上の負担を負いません。そして run 履歴を利用するダッシュボード、
フレーキネスのランキング、夜間バッチの実行結果の確認といった先のすべてが、一貫した答えを得られ
ます。

## 詳細設計

キャンセルは、ランナー自身が短い猶予期間の範囲内で完結させる協調的な終了に変わります。`SIGTERM`
がその場でプロセスを終わらせる今の動作とは異なります。

- **シグナルを捕まえ、それで終了しない。** `bajutsu run` のエントリーポイントに `SIGTERM`
  ハンドラーを追加し、Python の既定の挙動（即時終了）に頼らず `threading.Event` をセットします。
- **プロセスグループ全体ではなく、まず run プロセス自身にだけシグナルを送る。** `serve/jobs.py`
  は、`run`・`record`・`crawl` のどの job も自身のセッションで起動します
  （`start_new_session=True`）。今のキャンセル経路はこのグループ化を利用しており、`_terminate`
  のグループ全体への `killpg` は、`record` job の実行エージェントが起動する子プロセス
  （`claude -p`）を孤立させずに回収します（[`jobs.py:71`](../../bajutsu/serve/jobs.py)、[`jobs.py:417`](../../bajutsu/serve/jobs.py)）。
  `run` job では、この同じグループ化が
  バックエンドドライバー（シナリオが実際に操作している Playwright 起動のブラウザや
  `xcodebuild test` プロセス）もたまたま含んでしまいます。そのためグループ全体を殺すと、実行中の
  シナリオの下でこのドライバーも一緒に殺してしまい、次の安全な境界より前にそのシナリオが
  クラッシュします。これは本項目が取り除こうとしているまさにその唐突な失敗です。そこで `run`
  job のキャンセル経路は、まずリーダープロセスだけにシグナルを送ります（`proc.send_signal`）。
  グループ全体には送りません。ドライバーは、ランナー自身が次の境界でイベントに気付き、自分の
  通常のシナリオ終了処理を通じて後始末するまで動き続けます。リーダーが終了した後（正常な終了で
  あれ、後述する猶予期間切れのエスカレーションであれ）も、キャンセル経路はグループ全体に
  `killpg` を送ります。これにより、その後始末より長く生き残ったドライバーの子プロセスは、
  孤立させられるのではなく回収されます。どちらの経路を使うべきかを判断するには、今の `Job` には
  無い判別材料が必要です。`Job` には job の種別を表すフィールドがなく
  （[`state.py:54`](../../bajutsu/serve/state.py)）、`job.proc` はオンデマンドビルドのサブ
  プロセスと起動された run のどちらか一方を保持します（[`state.py:71`](../../bajutsu/serve/state.py)、
  [`jobs.py:192`](../../bajutsu/serve/jobs.py)）。そこで本項目はこの判別材料を新たに追加し、
  リーダーだけにシグナルを送る経路は `job.proc` が run 自身であるときにだけ適用します。
  `_terminate` のグループ全体への `killpg` は、`record`/`crawl` job と `run` job のビルド段階に
  ついては、本項目が変更せず今のまま残ります。
- **安全な境界でイベントを確認する。** このイベントは、`run_all` のディスパッチループ
  （[`pipeline.py:822`](../../bajutsu/runner/pipeline.py)）における各シナリオの先頭、シナリオ内
  の各ステップの間、そして既存のすべての条件待ちポーリングループの中で確認します。条件待ちを
  しているシナリオは、次のポーリングの間隔でキャンセルに気付けます。一方、単一のドライバー呼び
  出し（`xcuitest` の HTTP リクエスト、`adb` の `subprocess.run`、Playwright の呼び出し）の中で
  止まっているシナリオは、その呼び出しが返ってくるまで気付けません。そのため、後述する猶予期間
  は、こうした呼び出しのうちもっとも長いものより長く取らなければ、協調的な終了ではなくエスカ
  レーションのほうが先に起きてしまいます。新しい待機を追加するのではなく、境界のある既存の
  ポーリングループに終了条件を1つ追加するだけです。
- **キャンセルされたシナリオは、失敗したシナリオとして扱う。** こうして中断されたシナリオ、
  あるいはイベントがすでにセットされていたために一度も開始しなかったシナリオは、
  `RunResult(ok=False, failure="cancelled", ...)` になります。これは `pipeline.py` がクラッシュや
  プリフライトの失敗に対してすでに作っている形と同じです
  （[`pipeline.py:271,281,313,545`](../../bajutsu/runner/pipeline.py)）。`run_all` はこれまでと
  変わらず、宣言順にシナリオ1つにつき1つの結果を返すので、後段の処理はキャンセルが起きたことを
  一切知る必要がありません。そのため、長いシナリオ一式の早い段階でキャンセルした操作者には、
  一度も実行されなかったシナリオもすべて、レポート上とフレーキネスのランキング上の両方で失敗
  として数えられます。これは、キャンセルされた run をそもそも失敗として扱うことの当然の帰結
  であり、キャンセルが実行前に届いたシナリオだけを特別に除外するものではありません。
- **`run_all` より後段に変更は不要。** `run_and_report` は、完結していて通常の run と見分けが
  つかない `results` のリストを受け取るので、`_assemble_report` は `manifest.json`・
  `report.html`・JUnit の XML を通常の run と同じ手順で書き出します。少なくとも1つのシナリオが
  `ok=False` を持つため、`manifest["ok"]` はすでに `False` になっています
  （[`manifest.py:145`](../../bajutsu/report/manifest.py)）。`_finish`
  （[`run.py:746`](../../bajutsu/cli/commands/run.py)）は他の失敗した run と同じく `FAIL
  <manifest>` の行を出力して終了コード1で終わるので、`_RUN_ID_RE` はマッチし、`_persist_run` は
  データベースへの書き込み処理そのものを変更しなくても、他の失敗と同じように run を記録します。
- **終了は、`serve` が見ていなくても境界内に収まる。** `SIGTERM` ハンドラーは、`serve` 専用の
  関門の内側にあるのではなく、`bajutsu run` のエントリーポイントに存在します。そのため、
  `cancel_job` が送る `SIGTERM` だけでなく、プロセスが受け取るどの `SIGTERM`（`docker stop` や
  systemd の unit 停止、CI 側のジョブキャンセルなど）にも同じように応答します。`serve` 側の
  境界は外部から与えられるものです。シグナルを送った後、猶予期間はリクエストのスレッドとは別の
  ところで進み、その期限を過ぎればグループ全体への今の無条件の `killpg` にエスカレーションします。
  これは `record` の human-in-the-loop ハンドオフがすでに守っている「境界がありキャンセル可能」
  という保証（[BE-0179](../BE-0179-record-human-handoff/BE-0179-record-human-handoff-ja.md)）と
  同じです。そうしなければならない理由があります。`POST /api/jobs/{job_id}/cancel` は `cancel_job`
  を同期的に呼び出しており（[`routes.py:492`](../../bajutsu/serve/routes.py)、
  [`reads.py:636`](../../bajutsu/serve/operations/reads.py)）、この猶予期間は前項の単一のドライバー
  呼び出しよりも長く取らなければなりません。つまり `xcuitest` の HTTP タイムアウトや
  `xcodebuild test` では数十秒に及びます。この間レスポンスをブロックしてしまうと、Cancel ボタンは
  応答がないまま止まって見え、操作者はもう一度クリックしてしまいます。そこで `cancel_job` は、
  シグナルを送った時点で今と同じように即座に return します。猶予期間とそのエスカレーションは、
  `proc.wait()`（[`jobs.py:445`](../../bajutsu/serve/jobs.py)）をすでに担っている job 側のスレッド
  とは別のタイマー上で進みます。`serve` を経由せずに実行した `run` には、この外部のエスカレー
  ション役がいません。
  そこでハンドラー自身も同じ境界を自分に課します。イベントがセットされた時点で内部の2つ目の
  タイマーを起動し、その期限までに協調的な終了が完了しなければ、`SIGTERM` の既定の挙動を復元して
  シグナルを再送します。これにより、本当に止まってしまったランナーは、本項目を導入する前と同じ
  ように終了し、シグナルを受け取った後もいつまでも生き続けることはありません。この2つの期限は、
  互いに無関係に決めてはなりません。ハンドラー側の内部期限が `serve` 側の猶予期間より短ければ、
  run は `_assemble_report` がマニフェストを書く前に自ら終了してしまい、本項目が取り除こうとして
  いるまさにその記録の空白を、ごく普通の `serve` からのキャンセルでも再現してしまいます。`serve`
  側の猶予期間がいくら長くても、すでに自ら終了した run を救うことはできないからです。そこで
  `cancel_job` は自身の猶予期間を（ジョブの spec 上の環境変数として）起動した run に渡し、
  ハンドラーは受け取った値より必ず長くなるように内部期限を決めます。独立に選んだ定数同士には
  しません。`serve` を経由せずに実行され、この値を受け取らない `run` は、もっとも長いドライバー
  呼び出しを単独で乗り切れるだけの長さを持つ既定値にフォールバックします。どちらの場合も、キャンセル
  要求が今の即時終了より遅れるのは、猶予期間1回分までです。
- **対象は `run` job のみ。** 本項目が対象とするのは `run` job と、クロスブラウザのマトリクス
  実行における各エンジンのパスです。`run_matrix_and_report` はエンジンごとに `run_all` を1回
  呼び、各パスは同じ `RunResult` の形を返します。このエンジンのループ
  （[`pipeline.py:938`](../../bajutsu/runner/pipeline.py)）も、次のパスを始める前にイベントを
  確認します。各パスはまず `device_pool` をまるごと1つ組み立てます。環境の解決、デバイス
  カタログの読み込み、デバイスごとのコレクターの起動までを事前に行います
  （[`run.py:653`](../../bajutsu/cli/commands/run.py)、[`pool.py:128`](../../bajutsu/runner/pool.py)）。
  この確認がなければ、最初のエンジンの途中で
  キャンセルしても、run が終わるまでに残りのすべてのエンジンの立ち上げと後始末を待たされ、
  マトリクス実行では猶予期間を超えてしまいます。`record` job と `crawl` job には、そもそも
  保存すべき pass/fail の判定がありません。`record.py` はシナリオファイルを執筆するだけで、
  `RunResult` もマニフェストも一切作りません。そのため、これらの job をキャンセルしたときの
  動作（`Job.cancelled` がセットされ、プロセスが終了する）は今のまま変わりません。キャンセル
  された `record`/`crawl` job を別の方法で可視化すべきかどうかは、本項目の範囲外の別の課題です。
  ここで決めているのは、協調的な終了をどの job **種別**が受けるかであり、どの `SIGTERM`
  **送信者**がそれを引き起こすかではありません。`bajutsu run` のエントリーポイントに追加する
  ハンドラー（前項）は、`serve` の Cancel ボタンだけでなく、どの送信者にも応答します。
- **パイプラインが始まる前は、キャンセルは今もその場で強制終了になる。** `_run_job` は、run
  プロセスを起動するより前にデバイスの起動とアプリのビルドを行います
  （[`jobs.py:399,401`](../../bajutsu/serve/jobs.py)）。また `_register_proc`
  （[`jobs.py:85`](../../bajutsu/serve/jobs.py)）は、登録が済む前にキャンセルされたプロセスを
  その場で強制終了します。この経路は `proc.stdout` を一度も読まずに `proc.wait()` を呼ぶため、
  この狭い競合状態を協調的な終了に乗せてしまうと、ランナーは誰も読んでいない満杯のパイプへの
  書き込みでブロックされてしまいます。デバイスの起動中、アプリのビルド中、あるいはこの短い登録前
  の間にキャンセルした場合は、今の動作のままです。`Job.cancelled` がセットされ、プロセスはその場
  で強制終了され、何も残りません。本項目が埋める空白は、run がシナリオの実行を始めた後のもの
  であり、それを始める前の間は対象外です。

本設計はプライムディレクティブをそのまま満たします。キャンセルされた run が受け取る判定は、
あくまで決定的なパイプラインから来ます。完了しなかったシナリオは失敗と判定されるだけで、大規模
言語モデル（LLM）が判定するわけではありません。新しい不確定な待機を追加するのではなく、既存の
待機に終了条件を1つ追加するだけです。そして、ここにアプリ固有の要素はありません。シグナルの
扱いも `RunResult` の形も、どのターゲットでも同じです。

## 検討した代替案

- **キャンセルされた job が run id を一度も生成しなかったとき、`serve/jobs.py` の中で FAIL の
  `RunRecord` を作り出す。** 採用しません。Replay ビューや triage ビューが依拠する証拠
  ——`manifest.json`・`report.html`・スクリーンショット・各ステップの証拠——を何も持たない
  「失敗」という行だけがデータベースに残ることになり、リンク先が何もないラベルになってしまい
  ます。しかもこの作り出しは Web UI の job 層にしか存在しないため、`serve` を経由せず直接実行
  した `bajutsu run` には何の効果もありません。
- **ステップやポーリングの境界ではなく、シナリオの途中で即座に中断する。** 採用しません。
  アクチュエーションの途中や、ネットワークの通信内容を証拠として書き込んでいる途中で止めると、
  ドライバーのセッションや保存済みのファイルが不整合な状態のまま残りかねません。これは決定性
  優先（プライムディレクティブ2は固定の sleep を禁じており、同じ理屈で、実行中のアクチュエー
  ションを任意の地点で切り落とすことも禁じます）と対立します。現在のステップやポーリングの
  間隔、あるいはドライバー呼び出しが終わるのを待つほうが、パイプラインがもともと一時停止を
  許容している地点で止められます（せいぜい1回分のポーリング間隔か1回のドライバー呼び出し分で、
  シナリオ自身のタイムアウトほどではありません）。
- **キャンセルを、成功・失敗とは別の第三の run レベルの判定として扱う。** 本項目では採用しま
  せん。キャンセルされた run をシナリオ一式の失敗として数えることは、操作者が履歴を読むときの
  感覚——キャンセルされた run は成功ではない——と一致します。`failure: "cancelled"` は、レポート
  と Web UI がアサーションの失敗とは異なるラベルやアイコンを示すために必要な情報を、すでにすべて
  与えています。新しい判定の種類を追加すると、データベースのスキーマ、フレーキネスのランキング
  （[BE-0049](../BE-0049-determinism-flakiness-audit/BE-0049-determinism-flakiness-audit-ja.md)）、
  そして `ok: bool` を前提とするすべてのレポートのレンダラーに影響が及びます。
- **`SIGINT` も捕捉し、ターミナルから Ctrl-C でキャンセルした素の `bajutsu run` にも同じ扱いを
  与える。** 本項目の範囲外とします。本項目が結び付けるのは `SIGTERM` だけであり、これだけで
  外部からのキャンセル経路（`serve` の Cancel ボタン、`docker stop`、systemd、CI 側のジョブ
  キャンセル）はすべて届きます。ただし仕組みは同じ「シグナルからイベントへの橋渡し」なので、
  後続の項目が同じ `threading.Event` に `SIGINT` を結び付けるだけで済み、新たな設計は不要です。

## 進捗

> 開発の進行に合わせて常に最新の状態に保ってください。チェックリストは *詳細設計* の MECE な
> 作業分解（作業の単位ごとに 1 つ）に対応し、ログには変更内容と時期（古い順）を PR へのリンクと
> ともに記録します。

- [ ] `bajutsu run` のエントリーポイントへ `SIGTERM` ハンドラーを追加し、プロセスを即時終了させず
  `threading.Event` をセットするようにする
- [ ] 今の `Job` に無い判別材料（job の種別を表すフィールドなど）を追加し、`run` job のキャンセル
  経路が `job.proc` がオンデマンドビルドのサブプロセスか起動された run 自身かを判別できるように
  する
- [ ] `run` job のキャンセル経路を、その判別材料が「`job.proc` は run 自身である」と示すときに
  だけ、まず run プロセス自身だけへのシグナル送信に変更する。リーダーが終了した後（正常な終了で
  あれ、猶予期間切れのエスカレーションであれ）、グループ全体へ `killpg` を送って生き残った
  ドライバーの子プロセスを回収する。ビルド段階は今のグループ全体への強制終了のままにする
- [ ] `run_all` のディスパッチループの各シナリオ先頭、シナリオ内の各ステップの間、既存の条件待ち
  ポーリングループでのイベント確認
- [ ] 中断された、または一度も開始しなかったシナリオに対する `RunResult(ok=False,
  failure="cancelled")` の生成
- [ ] `serve/jobs.py` の `cancel_job` への猶予期間の追加。リクエストのスレッドとは別のタイマー上
  で（job 側のスレッドの `proc.wait()` と並行して）進めて `POST /api/jobs/{job_id}/cancel` の
  レスポンスを止めたままにせず、期限を過ぎた場合のみ今の無条件の強制終了にエスカレーションする
- [ ] `SIGTERM` ハンドラー自身に `serve` とは独立した内部の終了期限を持たせる。`serve` を経由
  しない `run`（`docker stop`、systemd、CI 側のジョブキャンセル）でも、外部の監視役がいなくても
  境界内で終わるようにする。`cancel_job` 自身の猶予期間を（ジョブの spec 上の環境変数として）
  起動した run に渡し、ハンドラーの内部期限がその値より必ず長くなるようにして、2つが競合しない
  ようにする。値を受け取らない場合は既定値にフォールバックする
- [ ] `run_matrix_and_report` のエンジンのループで、次のパスを始める前にキャンセルのイベントを
  確認するようにする。これがなければ、1つのエンジンの `device_pool` の立ち上げ中にキャンセル
  しても、残りのすべてのエンジンの立ち上げと後始末を待たされてしまう
- [ ] `_persist_run` と run 履歴のサマリーが、生成された `manifest.json` を変更なしに正しく読める
  ことの確認
