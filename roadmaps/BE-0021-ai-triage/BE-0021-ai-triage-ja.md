## はじめに

失敗の証跡を AI が読み、原因の要約と修正の提案を出します。結果は人間がレビューする前提です。コマンドは 2 段構成で、`bajutsu triage`（ルールベース）と `--ai`（Claude。失敗時のスクリーンショットも読みます）があります。決定的な [`trace`](../../docs/ja/glossary.md#証跡-capturepolicy-trace-triage) コマンドは、その下の層です。

## 動機

決定的な run が失敗したとき、生の証跡は正しいものの、読み解くのに手間がかかります。証跡とは、失敗メッセージ、失敗したステップ、アクセシビリティ要素ツリー、スクリーンショット、ログです。これを原因と次の具体的な編集に変える作業は、判定を伴わない読解作業で、LLM が得意とするところです。この作業は、境界の調査役の側にはっきり位置します。トリアージは失敗を説明するだけで、判定することはありません。

この層がなければ、失敗のたびに人間が証跡を手作業で掘り起こしてから、ようやく修正に取りかかることになります。狙いは、合否の判定をすべて決定的なランナーに残したまま、このループを短くすることです。

## 詳細設計

トリアージは**助言的**であり、`run`／CI ゲートの完全に外側にあります。ここでは何ひとつ合否を決めません。流れは 3 つの部品からなります。

* **`assemble`（純粋、AI なし）** は、保存済み run の `manifest.json` を読み、最初に失敗したシナリオの `TriageContext` を再構成します。コンテキストには次の項目が入ります。
  * 失敗メッセージ
  * 失敗したステップ
  * 失敗した期待値
  * 失敗箇所のもっとも近くにあるアクセシビリティ要素ツリー
  * 失敗箇所のもっとも近くにあるスクリーンショット
  * シナリオ定義
  * 失敗したステップが操作したセレクタ id

  `assemble` は決定的なファイル読み取りで、API キーなしのオフラインでも動作します。
* **`TriageAgent` プロトコルと 2 つの実装。** どちらも、要約、カテゴリ、最小限の提案を出します。
  * 既定は `HeuristicTriageAgent` です。ルールベースの決定的なエージェントで、AI は使いません。失敗を `selector`、`timing`、`assertion`、`unknown` に分類します。target id が見当たらず、似た id が取得した画面にあるときは、「もしかして」のヒントを出します。これが古典的な id リネームの自己修復です。
  * `ClaudeTriageAgent`（`--ai`）は、同じプロトコルの背後で Claude に問い合わせます。Claude は、失敗時のスクリーンショットを含む同じ証跡を読みます。単一の `diagnose` ツールを必ず呼び出す形で、同じ構造化された `Triage` を返します。AI 版は、手書きのルールなしで推論します。
* **`render`** は、人間が読んで対処するための診断を出力します。

決定的な `trace` コマンドは、トリアージの下の層です。`trace` は証跡を解釈せずに並べ、トリアージがその証跡を解釈します。LLM が呼ばれるのはトリアージだけで、失敗の後に人間が実行する調査役の経路に限られます。`run` の中で LLM が呼ばれることはありません。

## 検討した代替案

* **run を読んで直接判定する LLM。** 即座に却下しました。非決定的なモデルを合否の経路に置くことになり、プライムディレクティブに反します。トリアージの本質は、決定的なランナーがすでに宣言した失敗を説明することです。
* **ルールベースのみで、AI の選択肢を持たない案。** ヒューリスティクスは、よくある形を決定的に捉えます。id のリネーム、曖昧なセレクタ、タイムアウトした wait です。しかし、スクリーンショットを読むことも、未知の失敗を推論することもできません。2 つのエージェントを同じプロトコルの背後に置けば、ルールベースをコストゼロのオフライン既定として残せます。より深い読解が必要な失敗には、`--ai` を使います。
* **構造化されたツール呼び出しの強制ではなく、自由形式の LLM の文章。** 単一の `diagnose` ツールを強制すれば、出力を `Triage` データクラスと、BE-0022 が適用する構造化 fix にきれいに対応づけられます。文章から構造を復元するパーサに頼る必要はありません。
