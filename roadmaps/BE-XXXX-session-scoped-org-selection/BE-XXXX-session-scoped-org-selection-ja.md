## はじめに

本項目では、複数の org に属する利用者が、いま使っているブラウザのセッションがどの org として振る舞う
かを選び、サインインし直さずに切り替えられるようにします。org は `serve` のマルチテナンシーの単位で
あり、run、シナリオ、シークレット、project、証跡の範囲を区切る境界です
（[BE-0015](../BE-0015-web-ui-public-hosting/BE-0015-web-ui-public-hosting-ja.md)）。今日そのような
選択肢はありません。サインインが GitHub のメンバーシップから org を1つ解決してユーザ行に書き込み、
以後のリクエストはその値を読み直すだけなので、正当に2つの org に属する login も、解決順が先に到達した
ほうに固定されます。本項目では、答えを持つ場所をユーザ行からセッションに移します。セッションは、
サインイン時に観測した GitHub organization と GitHub Team、いま振る舞っている org、その org で与え
られるロールを記録します。login と選択中の org とロールを持つ `Caller` を認証ゲートでリクエストごとに
1度だけ解決し、org で範囲を区切るすべての操作に明示的に渡すことで、操作ごとにユーザ行を引き直す形を
置き換えます。ヘッダで振る舞い中の org を示しているバッジは、その login が振る舞える org を並べた
セレクトボックスになり、切り替えのエンドポイントは現在の org の名簿に照らして選択を検証してから反映
します。org が1つだけのデプロイ、GitHub OAuth のサインインを使わないデプロイ、データベースを持たない
デプロイの挙動は今日のままです。

## 動機

Bajutsu が利用者の org を解決するのは、サインインの1度だけです。`org_for_identity` は、`members` に
その login を挙げている org を返し、なければサインインが報告した GitHub organization と `githubOrgs`
が交差する最初の org を返し、それもなければ `default` を返します。`upsert_user` がその答えを
`users.org_id` に保存し、テナントの範囲を必要とするリクエストは毎回 `ServeState.org_of` でその値を
読み直します。解決自体は安定していて、同じ login は毎回同じ org に入ります。ただし、条件に合う org が
2つあるときにタイブレークを決めているのは、利用者の意図ではなくデプロイ側の並び順です。

この隙間には、すでにこのリポジトリ自身が名前を与えています。org のメンバーシップを設定ファイルから
データベースへ移した
[BE-0375](../BE-0375-serve-org-lifecycle-management/BE-0375-serve-org-lifecycle-management-ja.md)
は、タイブレークを既知の限界として記録し、本当の答えがどこにあるかまで書きました。複数の org に属する
login が、そのどれとして振る舞うかを選べるようにすること、そのためには `users.org_id` が答えを持つ
唯一の場所であることをやめる必要があること、の2点です。BE-0375 がその作業を先送りしたのは、振る舞い
中の org をどこから読むかを変えると、`serve` の org で範囲を区切る読み書きのすべてに波及するからです。

この隙間で困るのは、マルチテナントのデプロイがまさに想定している人たちです。2社のアプリケーションをテスト
する業務委託の開発者、社内の org と顧客の org の両方に属する運用担当者、テナントをまたいで確認する
レビュアーは、いずれも GitHub の login を1つ、ブラウザのセッションを1つ持っています。今の回避策は、
解決がもう一方の org に到達するように管理者にメンバーシップを書き換えてもらうことだけです。書き換えは
その利用者のセッションを一斉に動かし、しかも元の org への到達を取り上げてしまいます。

選択をユーザではなくセッションに置くのは、同じ人が2つのテナントを同時に必要とすることがあるからです。
一方のウィンドウで顧客の run を見ながら、もう一方で社内の org を見る、という使い方をそれぞれ正しい
範囲で成り立たせます。選択をユーザ行に置くと、2つのウィンドウが1つの値を奪い合い、どちらかでの切り替え
がもう一方を黙って動かします。

## 詳細設計

作業は7つの単位に分かれます。単位ごとに独立してレビューでき、全体で変更のすべてを覆います。

### 1. セッションがサインイン時の GitHub の事実と現在の選択を持つ

`serve` がログインセッションを保持する継ぎ目である `SessionStore` は、不透明なセッション id と、
そこに紐づく GitHub の login だけを記録しています。ここを広げて、サインイン時に観測した GitHub
organization と GitHub Team、セッションがいま振る舞っている org、その org で与えられるロールも持たせ
ます。GitHub の事実こそが後からの切り替えを成り立たせます。候補となる org もロールもその事実から導かれ、
そして `serve` がその事実を受け取れるのは OAuth のコールバックの中だけだからです。

広げた継ぎ目を担う実装は2つあります。ローカルの `serve` が使うインメモリの実装と、サーバのデプロイが
使うデータベース版の `SqlSessionStore`
（[BE-0106](../BE-0106-post-completion-worker-model/BE-0106-post-completion-worker-model-ja.md)）です。
データベース版には Alembic のマイグレーションで NULL 可の列を4つ足すので、既存のセッション行は値を
持たないまま移行され、「GitHub の事実の記録なし、選択なし」として読まれます。その場合の挙動は今日と同じ
で、ユーザ行から解決します。

`SqlSessionStore` が置き換えた `RedisSessionStore` は、同じ変更で退役させます。この実装を組み立てる
デプロイ経路はなく、組み立てているのは自身のテストだけです。誰も動かしていない実装にセキュリティ上の
意味を持つ選択を運ばせても、読み手を増やさずに選択を落とす場所だけを増やします。

### 2. リクエストごとに1度だけ解決し、明示的に渡す `Caller`

`gate.actor_for` は「このリクエストはどの login か」に答え、テナントの範囲を必要とする操作はそのあと
`ServeState.org_of` にユーザ行から org を引かせています。本項目では後半を置き換えます。ゲートが login、
振る舞い中の org、ロールの3つをセッションから読んだ凍結値 `Caller` として解決し、リクエストはその値を
持ち回ります。stdlib のハンドラと FastAPI のアプリケーションはどちらも、リクエストごとの文脈オブジェクト
に `actor()` を備えているので、`Caller` は login がすでに通っている経路をそのまま通ります。

org で範囲を区切る操作は `Caller` を受け取り、人に行為を帰属させるだけの操作は今までどおり login の
文字列を受け取ります。`ServeState.org_of` は、尊重すべき選択が存在しない2つの場合のために残します。
identity を持たない共有トークンのセッションと、本変更より前に発行されて記録を持たないセッションです。
どちらも今日と同じくユーザ行が答えます。

暗黙のリクエスト文脈に束縛せず明示的に渡すのは、stdlib の `serve` がスレッドをリクエストのあいだで
使い回すからです。早い段階で戻るリクエスト（拒否された `Host` ヘッダ、401、403、ストリーミング応答、
JSON のエラー境界）が置き去りにした束縛は、同じスレッドの次のリクエストに読まれます。そこで起きる
故障は、ある org が別の org の成果物を読むことです。

### 3. ロールは選択中の org と一緒に動く

このデプロイにおいて、ロールは login の属性ではなく、org の中での login の属性です。`editorTeam` が
org ごとに宣言されるからです
（[BE-0313](../BE-0313-github-org-team-rbac/BE-0313-github-org-team-rbac-ja.md)）。したがってロールは
選択と一緒に動く必要があります。動かないままだと、ある org では editor、別の org では viewer である
利用者が、どちらか一方の答えを両方に持ち込んでしまいます。

ロールが足りないリクエストは、操作が走る前にトランスポートのゲートが拒否します。ゲートは今日そのロール
をユーザ行から読んでいますが、これを `Caller` のロールを読む形に変えます。ロールは切り替えのたびに、
セッションが記録した Team、切り替え先の org の `editorTeam`、サーバ全体の管理者 Team から再計算します。
入力が同じであれば、サインインがすでに適用している `role_for` の方針と同じ答えになります。

### 4. 候補の一覧と切り替えのエンドポイント

Web UI が起動時に読む `GET /api/config` に、このセッションが振る舞える org を加えます。一覧はセッション
が記録した GitHub の事実を、その時点の org のモデルに照らしてサーバ側で算出するので、管理者による
メンバーシップの編集は次の読み取りから効きます。サインイン時の状態に凍結されることはありません。一覧に
入るのはその login 自身が振る舞える org だけです。名簿の全体は管理者だけが読める `GET /api/orgs` の
後ろに残ります。設定の読み取りが振る舞い中の org について引いている境界と同じ線です。

切り替えは `POST /api/session/org` が担います。候補を同じ手順で計算し直し、そこに含まれない slug は
拒否します。古い一覧を送り返すクライアントも、任意の slug を送るクライアントも、そのセッションが資格を
得たことのない org には届きません。成功したときは新しい org と再計算したロールをセッションに書き、
切り替えを audit log に記録します。「誰がいつどのテナントとして振る舞ったか」に答えるための記録です。
エンドポイントは、サインイン済みの identity を持つ利用者であれば誰でも使えます。すでに資格のある org のあいだで選ぶことは、
新しい権限を与えないからです。

### 5. ヘッダのバッジをセレクトボックスにする

ヘッダは、振る舞い中の org を、対象としている設定の隣に表示しています。セッションの候補が2つ以上ある
ときは、バッジを候補を並べたセレクトボックスにします。選ぶと切り替えのエンドポイントを呼び、org で範囲
を区切っているビューを読み直します。候補が1つだけのときの見た目は今日と同じなので、単一テナントの
デプロイに新しい操作部品は現れません。

### 6. org の廃止とメンバーシップの編集が、生きているセッションに届く

org を削除するときは、その org のメンバーのセッションを失効させます。対象は `users.org_id` から探して
います
（[BE-0375](../BE-0375-serve-org-lifecycle-management/BE-0375-serve-org-lifecycle-management-ja.md)）。
ユーザ行に記録されない選択は、その探索から漏れます。ユーザ行が org A を指しながら、いまのセッションで
org B として振る舞っている利用者は、org B が削除されたあとも org B として振る舞い続けてしまいます。
セッションストアに「選択中の org で失効させる」問い合わせを足し、org の削除が既存の失効と並べて呼びます。
org として振る舞う2つの道が、同じ瞬間に閉じます。

org のメンバーシップの編集は、今日は何も失効させません。生きているセッションがメンバーシップに依存して
いなかったからです。ロールは次のサインインで再計算され、振る舞い中の org はユーザ行から都度読まれて
いました。本項目ではどちらも成り立たなくなります。セッションは、サインイン時に観測した GitHub Team から
計算したロールと、もはや資格を失ったかもしれない org を抱えます。そこで編集は、答えが変わるセッション
だけを失効させます。キャッシュが古くなった利用者はサインインし直し、その場で答えが計算し直されます。
そうしなければ、`editorTeam` がもう自分を挙げていない org を、editor のまま編集し続ける利用者が残ります。

対象のセッションを見分けるのは、答えの再計算です。エンドポイントは `members`、`githubOrgs`、
`editorTeam` を一括で置き換え、書き込みの前に org の現在の行を読むので、編集の前後の名簿がどちらも手元
にあります。その org に紐づく生きているセッションは、それぞれ自身のサインイン時に観測した GitHub
organization と GitHub Team を持っています。そこでサーバは、その org に紐づくセッションのすべてについて、
このセッションはまだこの org として振る舞えるか、振る舞えるならどのロールか、の2つを計算し直し、答えが
動いたセッションだけを失効させます。`members` の項目を1つ落とせばその login のセッションに届き、その org
の他のメンバーはそのままです。付与だけの編集は誰の答えも動かさないので、編集している管理者本人を含めて、
誰もサインアウトしません。

メンバーシップを編集せずに特定の利用者のセッションだけを失効させることは、本項目には含めません。GitHub
側での Team の変更をセッションの期限切れより前に反映させたい管理者は、上記のメンバーシップの編集か org
の削除を通して反映させます。

### 7. 変わるセキュリティ上の前提と、その逃げ道

サインイン時の Team をセッションに記録することは、権限の入力をキャッシュすることでもあります。今日は
ロールをログインのたびに、かつログインのときにだけ再計算するので、GitHub の Team を離れた効果は次の
サインインで反映されます。Team を記録すると、すでに開いているセッションは、その Team が与えたロールを
セッションが期限切れになるまで保ちます。既定では7日です。

この期間を抑える手段は2つあります。管理者が org を削除するか、答えが変わるようにメンバーシップを編集
すると、そのセッションはその場で失効します（作業単位6）。古いロールはその時点で終わります。期間が本当に意味を持つ
のは、こちらでの編集を伴わずに GitHub 側だけで Team が変わった場合です。デプロイがその変更を知るのは次の
サインインなので、利用者が離れた Team に由来するロールは、セッションが期限切れになるか管理者が失効させる
までは生き続けます。運用者に推測させないよう、この期間と2つの手段はホスティングのドキュメントに明記し、
同じ変更で `docs/` と `docs/ja/` の両方を更新します。

## 検討した代替案

**選択をユーザ行に置く。** 選んだ org を `users.org_id` に書き戻せば、新しいセッションの状態も `Caller`
の持ち回りも要りません。一方で、あるウィンドウでの選択がその login の他のすべてのセッションを動かし、
別のテナントを見るために意図して開いたもう1つのウィンドウまで巻き込みます。監査の記録も、そのセッション
がそのときどのテナントとして振る舞っていたかを言えないままです。

**振る舞い中の org を暗黙のリクエスト文脈に束縛する。** ゲートで設定して `ServeState.org_of` の中で
読む文脈変数にすれば、変更は org で範囲を区切る操作ではなく2つのファイルに収まります。stdlib の `serve`
はスレッドを使い回し、ディスパッチの前に戻る経路をいくつも持つので、リクエストより長く生き残った束縛は
次のリクエストに読まれます。そこで生じる故障は、ログの取り違えではなくテナントをまたぐ読み取りです。

**文字列のサブクラスに org を載せ、シグネチャを変えない。** login の文字列でありながら org の運び手でも
ある値にすれば、既存の呼び出し箇所はすべて今のまま置けます。ただし値を複製したり整形したりする操作
（文字列補間、前後の空白除去、JSON の往復）を通ると素の文字列になり、org は黙ってユーザ行の値に戻り、
あるテナント向けの書き込みが別のテナントに落ちます。サブクラスは文字列が通る場所をすべて通るので、
静的型検査はその箇所を1つも指摘できません。

**リクエストごとに GitHub へ候補を問い合わせ直す。** その login の organization と Team をリクエスト
ごとに GitHub へ問い合わせれば、権限の入力を一切キャッシュせずに済みます。同時に、すべてのリクエストの
経路にネットワーク呼び出しを置くことになり、自前のデータベースが名簿を知っているデプロイでも GitHub の
障害がサービス停止になります。

**ユーザと org を結ぶメンバーシップのテーブルを導入する。** BE-0375 は、`users.org_id` が単一の列で
あることをやめる形として問題を立てており、多対多のテーブルとして読めます。メンバーシップは org の名簿と
セッションの GitHub の事実からすでに導けるので、テーブルを置くとその写しをデプロイが管理している名簿と
同期し続ける必要が生まれます。メンバーシップのテーブルが費用に見合うのは、GitHub では表せない org ごと
利用者ごとの付与が要るときです。本項目にその要求はありません。
