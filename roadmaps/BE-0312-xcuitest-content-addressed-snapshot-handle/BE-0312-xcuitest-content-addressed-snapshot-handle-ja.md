## はじめに

XCUITest バックエンドは、画面の要素が1つも動いていない状況でも、tap を `element vanished (stale handle)` というエラーで失敗させることがあります。参照が古いという返事を受けたら探し直す [BE-0289](../BE-0289-xcuitest-stale-handle-reresolve/BE-0289-xcuitest-stale-handle-reresolve-ja.md) のやり直しでも、この種の失敗は塞げません。

原因は、アプリやシナリオではなく、オンデバイスの runner の参照の決め方にあります。runner は、要素の情報を取り直すたびに、画面上のすべての要素に新しい参照を発行します。以前の参照は、すべて無条件に無効にします。参照が表しているのは、要素そのものの同一性ではなく、要素を見た「取り直しの世代」だからです。

そのため、余分な `GET /elements` が1回あるだけで、世代は進みます。通信のやり直しの仕組みは、読み取りが一瞬途切れたように見えると `GET /elements` を送り直すので、余分な `GET /elements` は容易に起こります。要素を探してから操作するまでのあいだに、画面は何も変わっていません。それでも、送り直しによって世代が進み、これから使おうとしている参照が無効になります。

本項目は、参照を、回数を数えるカウンタからではなく、要素の安定した同一性（識別子、ラベル、traits）から決定的に導くことを提案します。画面に残っている要素は、情報を何度取り直しても同じ参照を保ちます。runner が余分に情報を取り直しても、参照は有効なままです。

挙動の変更は、runner の `SnapshotStore` だけで完結します。参照はどの利用者にとっても不透明な文字列のままなので、Python 側のやり取りと runner の HTTP ルータは、ロジックを変えません。doc コメントだけを合わせます（BE-0113）。

## 動機

この不安定さは、BE-0289 を入れたあとでも、参照を使って操作する経路で再現します。`id` を使った tap が、大きな画面遷移の直後（たとえばフルスクリーンのモーダルが出た直後）に、`element vanished (stale handle)` で失敗します。対象の要素は、そのあいだずっと画面に存在しています。次の4つの観測は、原因が画面の変化ではなく runner 側にあることを示します。

- 要素への `wait` が成功した瞬間に取った evidence のスナップショットと、続く tap が `stale` で失敗したときに取った evidence のスナップショットでは、対象の要素の frame が1ピクセルまで一致します（どちらも `[16.0, 784.0, 370.0, 40.0]`）。要素は、動いても、大きさが変わっても、画面から出てもいません。
- `dismissAlerts: false` にしても、不安定さは止まりません。人工知能（AI）の経路も、画像認識の経路も、関わっていません。
- 参照を持たない座標指定の tap である `tapPoint` では、この不安定さは一度も再現しません。原因は、tap そのものではなく参照にあります。
- 同じシナリオの中でも、大きな画面遷移の直後ではない tap のステップは成功します。不安定さは、条件ではなく runner の混み具合に連動します。

参照の決め方が、余分な読み取りを古い参照に変えます。[`BajutsuKit/Sources/BajutsuRunner/SnapshotStore.swift`](../../BajutsuKit/Sources/BajutsuRunner/SnapshotStore.swift) の `refreshSnapshot` は、呼ばれるたびに、単調増加する `generation` カウンタを進め、`currentElements` を空にします。そして、要素ごとに `h-<generation>-<index>` を発行します。あるスナップショットの参照は、画面が変わったかどうかに関わらず、次のスナップショットで無効になります。

新しいスナップショットの唯一のきっかけは、`GET /elements` です。参照を使うステップでは、1回の `GET /elements`（`_resolve_handle` を経由）に続いて、1回の `POST /tap`（`_actuate` を経由）が送られます。ふつうのタイミングでは、探してから操作するまでのあいだに、世代は動きません。世代を動かすのは、余分な `GET /elements` です。

余分な読み取りは、通信のやり直しの仕組みから生まれます。[`bajutsu/drivers/xcuitest.py`](../../bajutsu/drivers/xcuitest.py) の `_is_retry_eligible` は、すべての `GET` に対して真を返します（`return not delivered or method == "GET"`）。読み取りは何度実行しても同じ結果になり、BE-0207 が一瞬の通信のブレを吸収するために、この仕組みを入れたからです。`GET /elements` がクライアント側で時間切れに見えると、`_with_retry` が送り直します。

大きな画面遷移の直後は、runner のメインスレッドが、落ち着きかけの画面の情報を取り直すのに忙しくなります。読み取りが遅くなり、ちょうど途切れたように見えます。2つの効果が重なって、古い参照が生まれます。

1. 1回目の `GET /elements` がクライアント側で通信の失敗と判定され、`_with_retry` が送り直します。
2. クライアントは、送り直した読み取りの応答（世代 N+1）から条件を絞り込みます。そして、runner が世代 N+1 で発行した参照を付けて、`POST /tap` を送ります。
3. 1回目の読み取りは、忙しい runner の上で、実際にはまだ動いています。送り直しの**後**で完了して、`refreshSnapshot` を実行します。世代は N+2 に進み、`currentElements` はまるごと入れ替わります。
4. クライアントが送った世代 N+1 の参照は、もう `currentElements` のキーではありません。runner は `stale` を返し、バックエンドは要素消失のエラーを送出します。画面から一度も出ていないボタンに対するエラーです。

BE-0289 のやり直しは、この場合を回復できません。回復できない理由が、別の直し方を選ぶ動機になります。BE-0289 のやり直しは、条件からなお1つの要素だけが見つかるあいだ、問い合わせ直して操作をやり直します。この作りは、参照が古くなった原因を、新しい問い合わせに映る画面の変化だと見なしています。

ここでは、画面は変わっておらず、runner が忙しいだけです。やり直しが送る問い合わせ直しは、それ自体が `GET /elements` であり、同じ送り直しと割り込みのタイミングのずれにさらされます。runner が忙しいあいだ、つまり遷移の直後は、BE-0289 の上限まで数えた試行のどれもが、同じように理由もなく `stale` になりえます。ステップは失敗します。

2つの項目は、別々の層を扱います。BE-0289 は、クライアント側で本物のタイミングのずれを許します。本項目は、参照から世代を取り除き、変わっていない要素にそもそも新しい参照を割り当てないようにします。

この不安定さは、BE-0289 が記したのと同じ3つの意味で負担になります。

- 必須のオンデバイスの関門がランダムに失敗すると、関門への信頼が損なわれます。反射的な再実行か、無駄な調査のどちらかを招きます。
- 再実行のたびに、アプリをビルドして Simulator を起動するジョブで、macOS を動かす費用がかかります。
- `element vanished` というメッセージは、調査を誤らせます。要素がずっと存在しているのに、要素が存在しないかのように読めるからです。

## 詳細設計

作業は4つの単位に分かれます。Unit 1 は、参照の導き方を変える作業です。Unit 2 は、BE-0289 のやり直しが拠り所にする `stale` と `notFound` の区別を保つ作業です。Unit 3 は、実機なしで変更を確かめる作業です。Unit 4 は、文書を実際の動きに合わせる作業です。各単位は依存順に並び、別々のプルリクエストとして着地できます。

**Unit 1：参照を、世代のカウンタからではなく要素の安定した同一性から導く。** `SnapshotStore` で、`h-<generation>-<index>` の方式を、要素の安定した同一性（`identifier`、`label`、`traits`）から決定的に導いた参照に置き換えます。

参照は、`h-` の接頭辞を不透明な参照の名前空間として保ちます。変わるのは、接頭辞のあとの部分だけです。世代と番号から、同一性の符号化に変わります（たとえば `h-<同一性のハッシュ>`）。接頭辞に依存するもの（テストやログのフィルタ）が壊れないよう、接頭辞はあえて残します。

スナップショットが持つフィールドのうち、3つは導出からあえて外します。

- `backingElement` は、外します。同じ画面上の要素でも、`queryElements` を呼ぶたびに新しいオブジェクト参照が返ります。`backingElement` を含めると、スナップショットのたびに参照が変わります。本項目が取り除こうとしているまさにその欠陥です。
- `value` と `frame` は、どちらも画面が落ち着きかけるあいだに変わるので、外します。落ち着きかけているときこそ、runner が情報を取り直します。`frame` は、遷移のアニメーションで1ピクセル未満でもずれます。`value` は、ローディングのラベルが確定する、カウントダウンが進む、スピナーが回る、といったときに刻々と変わります。

どちらを含めても、割り込む2つの読み取りのそれぞれで、変わっていない1つの要素に新しい参照を発行します。本項目が対象とする局面で、タイミングのずれが再発します。どちらのフィールドも、操作の精度を上げません。参照は `backingElement` に解決され、runner はその参照を通じて操作するからです。記録された `value` や `frame` を通じて操作することはありません。

この選び方は、パッケージにとって新しいものではありません。[`BajutsuKit/Sources/BajutsuRunner/PositionPath.swift`](../../BajutsuKit/Sources/BajutsuRunner/PositionPath.swift) の `attributesMatch` は、2つの観測が同じ要素かどうかを、すでに `identifier`、`label`、`traits` で判断しています。同じ落ち着きかけの理由で、`value` と `frame` は外しています（[BE-0287](../BE-0287-xcuitest-runner-multitouch-resilience/BE-0287-xcuitest-runner-multitouch-resilience-ja.md)）。同一性から導いた参照は、同じ要素かどうかの判断基準を新しく作らず、パッケージにすでにある判断基準を再び使います。

`refreshSnapshot` は、今までどおり、呼ばれるたびに `currentElements` を空にして作り直します。参照が指す `backingElement` は、常に最新の問い合わせのオブジェクト参照です。変わるのは、キーが同一性から導いた参照になる点だけです。同一性が変わらない要素は、スナップショットをまたいで同じ参照の文字列に対応します。

そのため、余分な `GET /elements` は、変わらない要素に同一の参照を再発行します。*動機* で述べた割り込みは、もう参照を無効にできません。クライアントの参照がどのスナップショット由来であっても、要素が画面にある限り、参照は生きたキーのままだからです。

同じ画面上に、同一性が完全に一致する要素が複数ありうるので（識別子のない「Delete」ボタンが2つある場合など）、参照を区別する必要があります。1つのスナップショットの**中**での衝突には、問い合わせの順に出現番号を付けます。最初の出現は接尾辞のない参照を保ち、あとの出現は番号を付けた変種を取ります。

**Unit 2：`stale` と `notFound` の区別を保つ。** BE-0289 のやり直しは、runner の返事で分岐します。`stale` の返事は探し直しのきっかけになり、`not-found` の返事はすぐに失敗させます。参照の方式を変えたあとも、2つを見分けられなければなりません。

現在、この2つを見分けているのは、世代のカウンタです。`lookup` が参照を解析し、正しい形式で世代が最新でない参照は `stale`、解析できない参照は `notFound` と読みます。

同一性から導いた参照には、解析すべき世代がありません。そこで `SnapshotStore` は、これまでに発行したすべての参照の集合を記録します。`lookup` は、3つの結果のどれかを返します。

- `.found`：参照が生きたキーである場合。
- `.stale`：参照を以前に発行したが、生きたキーではない場合。参照が名指した要素は、画面から出たか、同一性が変わっています。
- `.notFound`：参照を一度も発行していない場合。形式が不正か、でっち上げの文字列です。

runner の HTTP ルータは、結果に対する今の3分岐をそのまま保ちます。BE-0289 のドライバ側のやり直しも、そのまま動きます。本当の消失は、以前に発行した参照を今までどおり `.stale` に対応させます。やり直しは探し直し、条件がもう見つからないと分かって、大きく失敗します。

**Unit 3：実機なしで変更を確かめる。** `SnapshotStore` を、[`BajutsuKit/Tests/BajutsuRunnerTests/SnapshotStoreTests.swift`](../../BajutsuKit/Tests/BajutsuRunnerTests/SnapshotStoreTests.swift) の Swift ユニットテストで覆います。テストは、Simulator のいらない runner の実機なしテスト群で動きます。

中心となる追加は、本項目が防ごうとしている回帰です。変わらない同じスナップショットを2回以上取り直したうえで、**最初**の取り直しの参照を `.found` に解決します。古い世代の方式は、2回目の取り直しでその参照を古くするので、この場合に失敗します。対になるテストは、出現番号のタイブレークを固定します。1つのスナップショットの中で同一性が一致する2つの要素が、別々の参照に解決することを確かめます。

既存のテストは、今の形のまま新しい方式でも通り続けます。テスト群は、既存のテストに依存します。

- **別の**要素での取り直しは、最初の要素の参照をなお古くします（本当の消失、`.stale`）。
- 一度も発行していない参照は、なお `.notFound` を読みます。
- 発行した参照は、なお `h-` の接頭辞を持ちます。
- 並行実行テストも、なお通ります。

したがって、同一性からの導出は、Unit 2 が保つ `.stale` と `.notFound` の約束を壊さず、競合状態も再び持ち込みません。

**Unit 4：文書を実際の動きに合わせる（BE-0113）。** `SnapshotStore` のクラスの説明は、いま「`refreshSnapshot` のたびに前のスナップショットを置き換え、以前の参照はすべて古くなる」と述べています。本項目が変えるのは、まさにこの動きです。同一性から導いた参照と、参照がなお古くなる条件（参照の名指す要素が画面から出たか、同一性が変わったこと）を述べる説明に、書き直します。

同じチャネルの Python 側も、旧モデルを説明したままです。コードと一緒に動かす必要があります。BE-0113 が禁じるのは、ファイルをまたいだ食い違いです。

- [`bajutsu/drivers/xcuitest.py`](../../bajutsu/drivers/xcuitest.py) のモジュールの説明は、参照を「per-snapshot handle」と呼びます。そして、「探してから操作するまでに画面が取り直されると古くなりうる」と述べています。
- [`bajutsu/drivers/xcuitest_live.py`](../../bajutsu/drivers/xcuitest_live.py) は、WebDriver の要素 id を、2箇所で runner の「per-snapshot handle」と呼んでいます。

この3箇所を、同一性から導くモデルに合わせます。このモデルは、変わらない画面の取り直しをまたいで安定しています。[`DESIGN.md`](../../DESIGN.md) と [`docs/architecture.md`](../../docs/architecture.md) が runner の参照の古さの扱いを述べているなら、説明が実際の動きに合うように更新します。

既知のフォローアップが2つあり、あえて範囲の外に置きます。

- これまでに発行した参照の集合は、runner プロセスの寿命のあいだ増え続けます。とても長い run では、参照の文字列が単調に積み上がります。増え方は小さく（これまでに見たそれぞれの要素につき短い文字列が1つ）、run はプロセスの寿命に閉じています。計測で問題だと分かれば、上限をあとから足せます。たとえば、直近のいくつかのスナップショット分の参照だけを保ちます。
- 同一性が一致する要素への出現番号の割り当ては、同一性の同じ要素の問い合わせ順が、スナップショットをまたいで安定していることを前提とします。見た目が同じ要素の順がスナップショットのあいだで入れ替わる画面では、参照が振り直されることがあります。そのような画面はまれで、その要素は条件からも見分けられません。この隙間を塞ぐのは、実際のシナリオが必要とするまで見送ります。

## 検討した代替案

**`GET /elements` をやり直しの対象から外し、余分な読み取りを送らせない。** 読み取りを BE-0207 の通信のやり直しの仕組みから外せば、*動機* の具体的なきっかけは消えます。しかし、その代償として、BE-0207 が塞ぐために入れた一過性のブレの不安定さが、再び開きます。読み取りに本物の一瞬の通信のブレが起こると、ステップはまた即座に失敗します。

やり直しは、余分なスナップショットの唯一のきっかけとも限りません。将来 runner が別の理由で情報を取り直すようになれば、不安定さは再び戻ります。やり直しを外すのは、原因ではなく1つの症状に対処するだけです。同一性から導いた参照は、余分なスナップショットがどこから来ても、無害にします。

**BE-0289 のやり直しだけに頼る。** *動機* が、やり直しがこの場合を回復できない理由を示しています。やり直しは、新しい問い合わせに映る画面の変化を前提とします。ここでは画面が変わっておらず、問い合わせ直しはそれ自体が同じ送り直しのタイミングのずれにさらされます。そのため、上限まで数えた試行のどれもが、同じように理由もなく `stale` になりえます。

2つの項目は、代わりではなく補完し合います。BE-0289 は、クライアント側で本物のタイミングのずれを許します。本項目は、作り出されたタイミングのずれを源で取り除きます。

**最新の世代だけでなく、直近の複数の世代の参照を有効に保つ。** 直近のいくつかの世代の参照を生きたものとして扱えば、方式を変えずに割り込みを覆い隠せます。しかし、この案は恣意的な範囲を広げるだけで、食い違いを直しません。参照は、その要素が画面にあるあいだちょうど有効であるべきです。これは同一性についての言明であって、いくつのスナップショットが経ったかについての言明ではありません。同一性から参照を決めれば、この不変条件を直接述べられます。遅い runner が追い越しうる調整用の数値も、必要ありません。

**要素の `frame` や `value` を参照のキーに含める。** 位置や生きた値もキーにすれば、同一性の一致する2つの要素に、出現番号なしで別々の参照を割り当てられます。しかし、本項目が閉じるまさにその race を、開き直します。遷移のあとに画面が落ち着きかけるあいだ、runner は何度も情報を取り直します。割り込む2つの読み取りのあいだで、`frame` がずれるか、`value` が刻々と変わると（ローディングのラベル、カウントダウン、スピナー）、変わっていない1つの要素に2つの参照を発行します。余分な読み取りが、本項目が対象とする局面で、再び参照を古くします。

出現番号のタイブレークは、1つのスナップショットの中で同一性の一致する要素を、すでに区別します。また、どちらのフィールドも操作の精度を上げません。runner は、記録された `value` や `frame` ではなく、`backingElement` を通じて操作するからです。どちらのフィールドも、設計が避けようとする代償を払うだけで、設計が必要とするものを何も生みません。パッケージの `attributesMatch`（BE-0287）も、同じ理由でどちらも外しています。
