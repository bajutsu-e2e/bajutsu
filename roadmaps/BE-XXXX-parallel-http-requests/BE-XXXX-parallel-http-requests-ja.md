## はじめに

シナリオは、ステップを 1 つずつ順に実行します。現在の並列実行は、シナリオ単位の `--workers` だけです。シナリオどうしは変数を共有しません。そのため、2 つのリクエストを同時に送って応答を突き合わせるシナリオは書けません。

本項目は `parallel` ステップを追加します。このステップは `http` ステップの並びを持ち、それらを同時に送ります。すべてのリクエストが終わるまで待ちます。各リクエストの結果は、それぞれの変数に残ります。実行記録には、各リクエストの開始時刻が残ります。

任意の `statusCounts` は、期待する状態コードの組を指定する検査です。どのリクエストがどの状態コードを受け取るかは、指定しません。

## 動機

2 つのリクエストが重なったときにだけ現れる不具合があります。バックエンドは、次の場合を扱えなければなりません。

| 場合 | 期待する結果 |
|---|---|
| 同じ注文の二重送信 | 注文が 1 件だけ作られ、もう一方は競合の状態コードを受け取る |
| 同じレコードへの同時更新（楽観ロック） | 勝者が 1 つ、競合が 1 つになる |
| 短い時間に上限を超えるリクエスト | レート制限が超過分を拒否する |
| 2 人のユーザーが同時に送るリクエスト | 互いのデータが応答に混ざらない |

現在のシナリオは、これらを確かめられません。`--workers` で回す 2 つのシナリオは、無関係な時刻に始まります。結果を突き合わせる手段もありません。ライフサイクルのスクリプトならリクエストを同時に送れますが、結果と検査がシナリオの外に出ます。シナリオの変数や実行記録からは見えなくなります。

出荷後は、1 つの `parallel` ステップで同じ注文を 2 回送るシナリオが書けます。2 つの応答が「201 が 1 つ、409 が 1 つ」であれば、順序によらず合格します。実行記録には両方の交換が開始時刻の差つきで残るため、後から読む人が、リクエストが重なっていたことを確かめられます。

## 詳細設計

### `parallel` ステップ

```yaml
- parallel:
    steps:
      - http: { method: POST, url: "${secrets.API}/v1/orders", body: '{"key":"k1"}', saveStatus: first }
      - http: { method: POST, url: "${secrets.API}/v1/orders", body: '{"key":"k1"}', saveStatus: second }
    statusCounts: { 201: 1, 409: 1 }
```

`parallel` は、`steps` のリストと、任意の `statusCounts` を取ります。読み込み時の規則は次の表のとおりです。

| 場合 | 結果 |
|---|---|
| `http` ステップ以外の子 | 読み込みエラー。画面操作を競合の検証に混ぜる意味がないため |
| `name` と `from` 以外の修飾を持つ子（`extract`、`capture`、`target` など） | 読み込みエラー。`extract` と `capture` は画面を読み、子は `parallel` ステップの対象に対して動くため |
| `timeout` を持つ子 | 読み込みエラー。繰り返す待機は、各リクエストの開始時刻を曖昧にするため |
| 子が 2 つ未満、または 32 を超える | 読み込みエラー。32 は安全のための上限で、後続の項目で引き上げられる |
| 同じ変数を指す 2 つの保存（1 つの子の中でも、子どうしでも） | 読み込みエラー。最終的な値がタイミングで変わるため |
| `statusCounts` の合計が子の数と違う | 読み込みエラー。検査がすべての子を覆う必要があるため |

`parallel` ステップ自身は、通常の `target` の規則に従います。対象の検査は、ターゲットグループ（[BE-0437](../BE-0437-multi-target-step-groups/BE-0437-multi-target-step-groups-ja.md)）が中のステップを自分の対象に解決するのと同じく、子をこのステップの対象に解決します。

`parallel` ステップは、ステップを置ける場所ならどこにでも置けます。たとえば、`if`、`forEach`、コンポーネントの中です。

### 状態コードの保存

`http` ステップに、任意の `saveStatus` を追加します。応答の状態コードを、10 進数の文字列として `vars.<name>` に保存します。`saveBody` と並べて使えます。`status` のないステップは、どの状態コードも受け入れます。`saveStatus` があれば、後続のステップは、シナリオが予測しなかった状態コードを読めます。この指定は、`parallel` の外の `http` ステップでも使えます。1 つのステップの `saveStatus` と `saveBody` には、別々の変数名を指定します。同じ名前なら、モデルが読み込み時に拒否します。

### 子の同時実行

ステップが始まる時点で、ランナーはすべての子の `${...}` を置換します。子が、兄弟の保存した変数を読むことはありません。次に、すべてのリクエストを用意し、1 つの開始ゲートで同時に放ちます。リクエストは、ごく短い間隔で出ていきます。各リクエストの上限は、`http` ステップと同じ 30 秒です。ステップは、すべての子が終わるまで待ちます。

ランナーは、最後の子が終わってから結果を保存します。保存の順は、シナリオに書かれた順です。最終的な変数は、どのリクエストが先に終わったかに左右されません。`${secrets.*}` から読んだ値は、単独の `http` ステップと同じく、マスクされたままです。

ステップが合格する条件は、次の 3 つがすべて成り立つことです。

| 条件 | 内容 |
|---|---|
| 応答の受信 | すべてのリクエストが応答を受け取った |
| 子の `status` | `status` を持つ子が、その状態コードを受け取った |
| `statusCounts` | 指定がある場合、受け取った状態コードの多重集合が一致した |

条件を満たさないときは、すべての子が終わってからステップが失敗します。理由には、子ごとに位置と状態コード（またはエラーの種類）を並べ、受け取った状態コードごとの個数を添えます。エラーの種類は、許可されないスキーム、リクエストのエラー、時間切れの 3 つです。

エラーメッセージ、Uniform Resource Locator（URL）、本文は、理由に引用しません。どれも秘密やホスト名を含みうるためです。

実行がキャンセルされると、待機はすぐに終わります。すでに送ったリクエストは、それぞれの上限の範囲内で終わります。ランナーは、その結果を捨てます。

`sleep` や `timeout` の待機と同じく、このステップはアクションのハンドラーではなく、実行ループが直接実行します。そのため、実行の時計とキャンセルの通知を受け取れます。実行記録の開始時刻の差も、その時計から取ります。

### 重なりの証跡

実行記録には、子ごとに 1 つの項目が加わります。項目は、子の位置、ステップの開始からの開始時刻の差、所要時間、状態コードまたはエラーを持ちます。レポートは、項目をステップの下に表示します。合否の経路は、開始時刻の差を読みません。リクエストが本当に重なったかを知りたい読み手のための情報です。

### 文書に明記する事項

どのリクエストが勝つかは、サーバーが決めます。ランナーは、その選択に影響できません。

シナリオは、どの順序でも成り立つ性質を検査します。「201 が 1 つ、409 が 1 つ」は、そうした性質です。シナリオは、勝者を名指ししません。文書は、最初の例の隣にこのことを書きます。

文書は、次の 2 つの限界も明記します。

| 限界 | 内容 |
|---|---|
| 重なりの保証 | 同時に送っても、サーバーが 1 件ずつ処理する場合がある。合格は、見えた並び方で性質が成り立ったことを示すだけで、競合が起こりえないことの証明ではない |
| 負荷で崩れる性質 | 負荷で時々崩れる性質は、シナリオではなくサービスの問題を指している |

### 最優先原則との関係

| 原則 | 本設計での守り方 |
|---|---|
| 合否の判定にモデルを使わない | 状態コードの数値と個数を比較 |
| 決定性 | 合否は結果の集合で決まり、到着順に依存しない |
| アプリ非依存 | 接続先と状態コードはシナリオに書き、ランナーはアプリごとに変えない |

決定性の規則が対象とするのは、待機とセレクターです。対象のアプリが毎回同じように振る舞うことまでは、約束しません。競合のテストは、まさにその振る舞いを調べるためにあります。このステップは、自分の側を決定的に保ちます。固定時間の待機は使わず、待機に上限を設け、合否は到着順を無視します。

## 検討した代替案

| 代替案 | 採用しなかった理由 |
|---|---|
| ライフサイクルのスクリプトでリクエストを送る | 結果と検査がシナリオの外に出て、変数と実行記録から見えなくなる |
| `--workers` で複数のシナリオを回す | 開始時刻が揃わず、結果を突き合わせるステップもない |
| `forEach` に並列のオプションを付ける | 画面操作まで並べて実行することになり、どのドライバーも対応していない |
| 「最初のリクエストが 201」のように勝者を名指しする | 勝者はサーバーが決めるため、検査が不規則に崩れる |
| 需要が見えるまで Unsorted ideas に置く | 設計が決定性との衝突を避けているため、待つ利点がない |
