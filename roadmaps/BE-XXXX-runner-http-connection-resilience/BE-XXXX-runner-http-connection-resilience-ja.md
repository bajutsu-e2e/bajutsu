## はじめに

Bajutsu は iOS シミュレータを、XCUITest のプロセスが抱える小さな HTTP サーバ経由で操作します。この
HTTP サーバを **runner** と呼びます。Python 側の driver（Bajutsu で唯一プラットフォームに依存する
インタフェースの実装）は、操作ごとにループバック接続を1本開き、それぞれに上限つきのソケット
タイムアウトを与えます。読み取りには15秒、操作の実行には30秒です。

本項目では、runner のサーバが接続を扱う部分にある4つの不具合を修正します。3つはサーバの動作そのものを
止め、残る1つは、クライアントが送り終えていないリクエストをハンドラまで通してしまいます。4つすべてを
修正し、修正が外れたら落ちる回帰テストを併せて追加しました。

4つの不具合をまとめて扱う理由は、症状が1つに収束するからです。どれが起きても runner は
`GET /health` に応答しなくなり、他に生存を知る手段のない driver は、原因を説明できないまま
タイムアウトを報告します。つまり保守する側には、どの不具合が起きたかによらず、同じ情報量のない
失敗として届きます。

## 動機

もっとも深刻な不具合は、runner のプロセスごと落とします。Darwin は、相手がすでに閉じたソケットへ書き込むと
`SIGPIPE` を発生させ、このシグナルのデフォルトの動作はプロセスの終了です。サーバは受け付けたソケットに
`SO_NOSIGPIPE` を設定しておらず、シグナルを無視する設定もしていないため、立ち去った相手への応答の
書き込みは、そのまま致命傷になります。そのような相手が生まれる競合は、例外的な状況ではなく日常的に
起こります。driver 側のソケットタイムアウトが接続を閉じるとき、ハンドラはまだメインスレッド上、または
XCUITest の操作を直列化する排他ロックの待ちで止まっていることがあり、そのハンドラが後から、driver が
すでに見捨てたソケットへ応答を書き込むからです。

この機構は、議論ではなく2つの実測で確かめました。サーバの書き込み経路を再現した単体のプログラムは、
異常終了で閉じた相手へ応答すると signal 13（`SIGPIPE`）で終了します。`SO_NOSIGPIPE` を設定すると、
同じ書き込みは `EPIPE` を返し、プログラムは生き延びます。サーバ本体から修正を外すと、テストターゲットでも
同じ死に方を再現でき、XCTest のプロセスはアサーションで失敗する代わりに signal 13 で終了します。
「Foundation がすでにこのシグナルを抑止している」という通説も確認しましたが、成り立ちません。
プロセスの開始時点で `SIGPIPE` は無視設定になっておらず、`URLSession` を作っても設定は変わりません。

2つめの不具合は、プロセスを落とさずにサーバを機能停止させるので、より診断しにくいものです。accept
ループは `accept()` の失敗をすべて致命的なものとして扱い、ループを抜けていました。ループを抜けても
listen 中のソケットは開いたままなので、カーネルはハンドシェイクを完了させてバックログへ積み続けます。
その結果、driver が開く接続はすべて成功し、accept されず、応答も返りません。何も処理しない生きた
プロセスは、この経路から見るかぎり死んだプロセスと区別できません。ここで想定すべき失敗は
`ECONNABORTED` です。相手がハンドシェイクの完了からサーバの accept までの間に切断すると、カーネルは
この値を返します。この失敗は、driver 側の health ポーリングがバックログへ積まれたまま自身のタイムアウトへ
達したときに起きます。`EINTR` も同様によく起こり、どちらも listen 中のソケットについては何も
語りません。

3つめの不具合は、接続を処理する枠を枯渇させます。受け付けたソケットへ `SO_RCVTIMEO` と
`SO_SNDTIMEO` のどちらも設定していないため、ハンドラが行う2つのブロッキング呼び出しは無制限に待ちます。接続だけして
リクエストを送らない相手は、そのハンドラを `recv` でプロセスの生存期間中ずっと止め、
[BE-0287](../BE-0287-xcuitest-runner-multitouch-resilience/BE-0287-xcuitest-runner-multitouch-resilience-ja.md)
が導入した8つの同時ハンドラ枠のうち1つを占有し続けます。そうした相手が8つあれば全枠が埋まり、長い
ジェスチャの最中でも応答できるように BE-0287 が並行化した `/health` が、ふたたび応答不能になります。

4つめの不具合は範囲こそ狭いものの、規模から想像されるより悪い性質を持ちます。ヘッダの解析は 8 KiB の
上限で読み取りを打ち切りますが、ヘッダを終端する空行が実際に届いたかどうかを確かめずに、読めた分を
解析していました。したがってヘッダが上限を超えたリクエストもそのまま解析され、そこから得たメソッドと
パスが振り分けられます。修正を外すと結果を直接示せます。クライアントが送り終えていないリクエストで
ハンドラが呼ばれ、操作の実行を担うエンドポイントであれば、それは端末を実際に操作することを意味します。

同じ穴は本体にも通っており、そちらのほうが結果は鋭くなります。宣言された `Content-Length` に届かない
まま読み取りが終わっても本体が空のままリクエストは振り分けられ、64 KiB の上限を超える長さの宣言は黙って
上限へ丸められるので、先頭の 64 KiB を読んだ時点で数が満たされ、途中までの本体が完全なものとして通って
いました。多くの経路は `400 missing or invalid JSON body` を返すので失敗は目に見えますが、`/selectAll`
と `/copy` は本体をまったく読みません。どちらも、途中までのリクエストで端末を実際に操作します。3つめの
作業単位で入れる受信タイムアウトは、この経路の到達範囲を狭めるどころか広げます。タイムアウトを入れる前は
閉じた相手しかここへ来ませんでしたが、入れたあとは単に止まっただけの相手も来るからです。

一方で、継続的インテグレーションで観測された特定の失敗との因果は主張しません。上の証拠が確立したのは、
4つの不具合がいずれも実在すること、1つめはプロセスにとって致命的であること、そして4つとも iOS の
ジョブがすでに失敗している症状と同じ形を作ることまでです。過去のある実行でどれが起きたかを特定するには、
すでに残っていない runner の出力が必要になるため、本項目はそこまで主張しません。

## 詳細設計

不具合ごとに1つ、合わせて4つの作業単位に分けます。互いに独立しており、4つとも runner の
HTTP サーバ（[`BajutsuKit/Sources/BajutsuRunner/HTTPServer.swift`](../../BajutsuKit/Sources/BajutsuRunner/HTTPServer.swift)）に
入ります。

1. **受け付けたすべての接続で `SIGPIPE` を抑止する。** accept ループの中で、受け付けた
   ソケットごとに、ハンドラが触れる前に `SO_NOSIGPIPE` を設定します。この設定により、立ち去った
   相手への書き込みはただの `EPIPE` になり、既存の送信ループはその値をすでに「書き込みを止める」合図と
   して扱うので、他のコードは変わりません。プロセス全体のシグナル設定を書き換えるのではなくソケット
   単位で設定するのは、ライブラリが、自分の抱えるホストプロセスが依存している可能性のある大域の状態を
   書き換えるわけにはいかないからです。

2. **接続単位の `accept()` の失敗では、ループを終えずに再試行する。** 失敗を `errno` で分類し、listen
   中のソケット自体が壊れたときだけループを終えます。`EINTR`、`ECONNABORTED`、`EAGAIN`、`EPROTO` は
   1本の接続に関する失敗なので、ループは直ちに再試行します。開けるファイル数の上限とメモリの枯渇
   （`EMFILE`、`ENFILE`、`ENOMEM`、`ENOBUFS`）も一過性ですが、直ちに再試行すると、時間の経過でしか
   解消しない状態に対して空回りするため、短く待ってから再試行します。それ以外は、`stop()` が listen 中の
   ソケットを閉じたときに生じる `EBADF` を含め、従来どおりループを終えます。

3. **2つのブロッキング呼び出しにソケットタイムアウトで上限を与える。** 受け付けたソケットごとに
   `SO_RCVTIMEO` と `SO_SNDTIMEO` を、それぞれ10秒と30秒で設定します。リクエストのバイト列は、接続の
   直後にループバック上をマイクロ秒の単位で届くので、10秒止まる読み取りは、死んだ相手か、そもそも
   リクエストを送っていない相手であって、単に遅い相手ではありません。応答の書き込みはこれとは事情が
   異なり、応答を待っている相手へ書くのですから、送信が止まるのは、閉じないまま読み取りをやめた相手が
   いる場合だけです。30秒は driver 自身のリクエスト単位の上限より十分に大きいので、driver がまだ
   受け取るつもりでいる応答をこのタイムアウトが打ち切ることはありません。タイムアウトした読み取りは
   `EAGAIN` として現れ、解析器はその値を、閉じた相手と同じ扱いですでに処理しています。

4. **クライアントが送り終えていないリクエストを受け付けない。** ヘッダと本体の双方に同じ規則を通します。
   ヘッダを終端する空行を解析器が見つけたかどうかを保持し、見つからなかった場合はリクエストを解析不能と
   して報告します。本体も同じ規則に従わせ、宣言された `Content-Length` に届かないまま読み取りが終わった
   場合と、宣言された長さが解析できない場合、負の場合、64 KiB の上限を超える場合は、リクエストを失敗と
   します。本体を欠いたリクエストを返す形では、判断が経路ごとに委ねられてしまい、`/selectAll` と
   `/copy` は本体をまったく読まないので、途中までのリクエストで端末を実際に操作します。解析不能な
   リクエストに 400 を返す処理は呼び出し側にすでにあるため、修正は解析器の内側に収まります。

テストは4つの作業単位をそれぞれ覆い、どのテストも、対応する修正を戻すと失敗します。`SIGPIPE` の作業
単位については、失敗ではなくテストのプロセスが落ちます。このうち2つは、設定済みのソケットから
オプションを読み戻す形と、`errno` の分類を直接列挙する形で検証します。`SIGPIPE` の抑止も
`accept()` の失敗も、実際の listen 中のソケットに対して確実に起こせないからです。残る2つは動作中の
サーバに対する end-to-end のテストで、応答の途中で消える相手と、8つのハンドラ枠に対する9つの沈黙した
相手を使います。

## 検討した代替案

- **`signal(SIGPIPE, SIG_IGN)` でプロセス全体のシグナルを無視する。** 1行で済み、このサーバが受け付けた
  ソケットだけでなく、プロセスの持つすべてのソケットを覆えます。採用しなかったのは、`BajutsuRunner` が、
  自分の所有しないホストプロセスにリンクされるライブラリだからです。大域のシグナル設定を変えると、その
  ホストの無関係なコードの動作を黙って変えてしまいます。`SO_NOSIGPIPE` なら、効果をこのサーバが作った
  ソケットに限ったまま同じ結果が得られます。
- **`accept()` の失敗を無条件に再試行する。** `errno` で分類するより単純で、機能停止も同じように防げます。
  採用しなかったのは、唯一の本当に致命的な場合を無限ループに変えてしまうからです。`stop()` が listen 中の
  ソケットを閉じたあと、`accept()` は `EBADF` で即座に、しかも永久に失敗し続けるので、無条件の再試行は
  プロセスの生存期間中スレッドを全速で空回りさせます。
- **相手がすでに切断したリクエストを捨てる。** メインスレッドのロック待ちに並んだハンドラは、driver が
  諦めたずっとあとに完了し、その操作が後続のステップの最中に届くことがあるので、一見すると魅力的な案です。
  本項目の範囲外としたのは、2つの理由からです。切断を検出できるのはハンドラが動き出す前だけであり、
  実際に見捨てられることが多いロック待ちの最中には検出できないので、この検査は不完全なものにとどまります。
  より重要な理由として、操作するかどうかを競合の結果に委ねる設計は、第2のプライムディレクティブで
  ある決定性に反します。この論点は、耐障害性の修正の内側で操作の意味論を黙って変えるのではなく、独立した
  項目として扱うに値します。
- **リクエストのヘッダを1バイトずつではなくまとめて読む。** 解析器は1バイトごとに `recv` を発行しており、
  典型的なリクエストのヘッダでおよそ150回のシステムコールを費やします。採用しなかったのは、ループバック上
  では1ミリ秒に満たない費用であり、本項目が扱う数秒単位のタイムアウトを説明できないからです。読み取り方を
  変えると、同じまとまりで届く本体のバイト列を解析器が扱う必要も生じ、実測された利得のないまま変更が
  大きくなります。
