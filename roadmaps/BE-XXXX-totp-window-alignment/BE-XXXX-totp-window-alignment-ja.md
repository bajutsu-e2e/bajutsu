## はじめに

`totp` ステップ（[BE-0046](../BE-0046-otp-email-steps/BE-0046-otp-email-steps-ja.md)）に、省略可能な `minRemaining` フィールドを追加します。
現在の 30 秒の窓の残りが `minRemaining` 秒に満たないとき、ステップは次の窓が始まるまで待ち、そのあとでコードを生成します。
この方法で生成したコードは、後続のステップが使い終えるまで有効なままです。
そのため、`totp` から `type` までのあいだに窓が閉じてサインインが失敗することはなくなります。

## 動機

時刻ベースのワンタイムパスワード（TOTP）のコードは、時計の 30 秒の窓ひとつのあいだだけ有効です。
現在の `totp` ステップは、現在時刻のコードを計算するだけで、窓があとどれだけ残っているかを見ません（[`handlers/totp.py:23`](../../bajutsu/common/orchestrator/actions/handlers/totp.py)）。
シナリオはそのあとで、コードをアプリへ届けるステップに時間を使います。
コード欄への `type`、送信ボタンへの `tap`、アプリがサーバーへ問い合わせる往復がそれにあたります。

この時間は短くても、ゼロではありません。
`totp` ステップが窓の最後の数秒に当たった実行は、期限切れとして拒否されるコードを送ります。
同じシナリオを次に試すと、窓の別の位置から始まるため、通ることが多くなります。
したがってこの失敗は断続的に起き、好きなときに再現することはできません。

現在あるステップでは、シナリオの作者がこれを直せません。
`sleep` ステップは固定秒数だけ止まり、上限は 30 秒で、長さを時計に応じて変えられません。
窓の境界は実行のたびに動くため、固定の待ち時間では境界に合わせられません。

検証できる成果は次のとおりです。
コード入力の前に `totp: { …, minRemaining: 10 }` を置いたシナリオを、窓のどの位置から始めて実行しても、コードは 10 秒以上の有効期間を残して生成され、アプリへ届けるステップの時間をまかなえます。
窓の端で失敗していたサインインが、最初の試行で通ります。
ステップの待機には上限もあり、1 つの窓と 1 スライスを足した長さを超えません。

## 詳細設計

### シナリオから見える形

`Totp`（[`models/actions/totp.py`](../../bajutsu/common/scenario/models/actions/totp.py)）に、省略可能なフィールドを 1 つ足します。
綴りは、隣り合うステップの camelCase の別名に合わせます。

```yaml
- totp: { secret: "${secrets.TOTP_SEED}", into: { var: code }, minRemaining: 10 }
- type: { text: "${vars.code}", into: { id: auth.code } }
- tap: { id: auth.submit }
```

| フィールド | 型 | 意味 |
|---|---|---|
| `minRemaining` | 整数、`1 ≤ n ≤ 30`、strict | コードを生成する時点で、窓に残っていなければならない最小の秒数です。省略すると待機せず、現在の動作と同じになります。 |

範囲外の値は、`sleep` が上限超えを拒否するのと同じように、読み込み時にモデルが拒否します。
上限は窓の長さです。ステップは `period` を公開しないため、窓の長さは 30 秒に固定されています。
値 30 には意味があります。ちょうど境界にいる場合を除き、ステップが必ず次の窓の境界まで待つようになります。

### 待機の意味

TOTP の窓は UNIX 時間で定義されるため、ステップは壁時計から残り時間を計算します。

```
remaining = 30 - (now % 30)
if remaining < minRemaining: 次の窓が始まるまで待つ
```

待機が終わると、ステップは従来と同じ関数（[`common/totp.py`](../../bajutsu/common/totp.py) の `totp()`）でコードを生成します。
コードは始まったばかりの窓のものなので、有効期間は少なくとも `30 - ε` 秒あります。
`ε` は、起床時のわずかな遅れです。

この待機は、「窓が始まった」を条件とする条件待ちです。
長さは作者が選ぶのではなく時計から算出され、1 つの窓と 1 スライスを足した長さを超えません。
そのため、決定性の監査には `fixed-sleep` の指摘として載せません。監査の規則は現状のままで、この待機のための情報提供の指摘も足しません。
監査が待ち時間を挙げるのは、作者がそれを条件待ちに置き換えられるからです。
この待機には置き換え先がありません。TOTP の窓が待機を強いるためです。
したがって、指摘を出しても取れる対処がありません。
待機にかかった時間は、ライブログのステップのラベルと、レポートのステップの所要時間で見えます。

待機関数は、最初に次の境界 `target = (floor(now / 30) + 1) * 30` を一度だけ計算します。
そのあと、スライスを 1 つ終えるたびに壁時計を読み直し、`wall() >= target` になるまでスリープします。
終了条件を `remaining >= minRemaining` ではなく境界そのものに置くため、`minRemaining: 30` でも待機が終わります。
境界を越えた直後の残り時間は `30 - δ` であり、30 には届きません。

壁時計を読み直すので、単調時計の sleep が境界の少し手前で返った場合にも対応できます。
さらに、単調時計の期限でも待機を打ち切ります。
期限は、開始時に `clock.now() + (target - now) + _SLEEP_SLICE` として一度だけ決めます。
そのため、ネットワーク時刻プロトコル（NTP）の補正で壁時計が動いても、待機は 1 つの窓と 1 スライスを超えません。

ただし、壁時計が大きく動くと、待機のあとでも残り時間が `minRemaining` に届かないことがあります。
壁時計が巻き戻ると、壁時計が `target` に達する前に単調時計の期限が来ます。
壁時計が進むと、後の窓の終わり際に入ることがあります。
そこで待機関数は、待機のあとに、壁時計が進んだ量と単調時計が進んだ量を比べます。
両者の差が 1 スライスを超えていれば、壁時計が動いたと判断します。
このときもステップはコードを生成して続行し、両方の測定値を書いた警告を結果に残します。
警告はたとえば `totp: wall clock jumped 12s during window wait; 4s left` とします。
後のサインインが期限切れで失敗したとき、レポートでその原因がステップの横に見えます。

一方、負荷の高いホストなどで起床が遅れただけなら、2 つの時計は同じだけ進むので、警告は残しません。
コードは始まったばかりの窓のものであり、遅れはその長さの分しか有効期間を削りません。
残り時間だけで警告を決めると、`minRemaining: 30` では起床が遅れるたびに警告が出て、起きていない時計の変化を原因として記録してしまいます。

警告は、新しく設ける証跡専用の欄 `StepOutcome.warnings: tuple[str, ...]`（[`step_outcome.py`](../../bajutsu/common/orchestrator/types/step_outcome.py)）で運びます。デフォルトは空です。
この欄は `ok` と `reason` に触れないので、成功したステップが失敗の理由を持つことはありません。
欄を複数形にしておけば、後の項目が致命的でない別の警告を足しても、この項目の警告を上書きしません。
manifest がこの欄を記録し、HTML レポートがステップの上に表示します。

### 待機を実行する場所

待機は、アクションのハンドラではなく、実行ループが持ちます。
ハンドラのシグネチャは `Clock` も中断の通知元も運ばないためです。
`sleep` と `email` が [`_run_step_body`](../../bajutsu/common/orchestrator/loop/_functions.py) の中で処理されている（`_do_sleep` は 373 行目）のも、同じ理由です。
`totp` の待機も、同じ置き場所に従います。

- ハンドラを呼ぶ前に、ループが `step.totp.minRemaining` を調べます。値があれば、新しい `_wait_for_totp_window(min_remaining, clock, cancelled, wall) -> str | None` を呼びます。この関数は警告の文を返し、壁時計が動かなかったときは `None` を返します。`bindings` が `None` のときは、ハンドラ自身の早期 return に合わせて待機を省きます。
- この関数は、`clock.sleep` を通して `_SLEEP_SLICE` 単位のスライスでスリープします。各スライスの前に `cancelled()` を確認し、中断されていれば `_do_sleep` と同じく戻り値で返さずに `RunCancelled` を送出します。中断された実行は、`sleep` と同じく 1 スライス以内に抜けます（BE-0370）。
- `_run_step_body` の戻り値のタプルには、警告を入れる場所がありません。そこでループは、返された文を新しい出力引数 `warnings: list[str] | None` に追加します。既存の `alerts` 引数や `system_alert_taps` 引数と同じ形です。ステップの実行側がこのリストを渡し、`StepOutcome.warnings` に写します。戻り値の型も、その呼び出し元も変わりません。
- `wall` は `Callable[[], float]` で、デフォルト値は `time.time` です。テストは偽物を注入するため、実時間で 30 秒待たずに境界の計算を検証できます。`RealClock.now()` は単調時計であり（[`real_clock.py`](../../bajutsu/common/orchestrator/types/real_clock.py)）、窓の位相を与えられません。`Clock` が受け持つのはスリープだけです。
- ハンドラは変更せず、待機のあとに `time.time()` からコードを計算します。

[`actions/_registry.py`](../../bajutsu/common/orchestrator/actions/_registry.py) の `_step_label` が、ラベルに条件を表示します。ライブログで、見えている停止の理由が分かるようにするためです。
ステップに `name` があれば、`sleep` の分岐と同じく、条件をその名前のあとに続けます。
名前のないステップは `totp (≥10s left)`、名前のあるステップは `Sign in code (totp ≥10s left)` と表示します。

### 基本原則との関係

- **実行経路に LLM を置きません。** 変更は時計の算術です。合否は、これまでどおりアサーションだけが決めます。
- **決定性。** 待機は時計が決める条件で終わり、上限は 1 つの窓と 1 スライスです。無制限のポーリングも、作者が選ぶ固定の待ち時間も導入しません。
- **アプリ非依存。** フィールドはステップごとに付けます。ターゲットやアプリの設定は関係しません。

### 互換性

デフォルトは「待たない」なので、既存のシナリオの動作もタイミングも変わりません。
フィールドは省略可能であり、設定しないシナリオは従来と同一にダンプされます。
証跡のスナップショット（`redact_totp_secrets`）がマスクするのは `secret` だけで、影響を受けません。
コード生成は `totp` にすでに `// TODO` を出しており（[`codegen/xcuitest.py:365`](../../bajutsu/codegen/xcuitest.py)）、変更は要りません。

### 対象外

- `period` と `digits` をステップで公開すること。生成関数は両方を受け付けますが、ステップは 30 秒と 6 桁に固定しています。拡張は別の項目で行えます。そのとき `minRemaining` の上限は `period` になります。
- `minRemaining` のデフォルト値を設けること。0 でないデフォルト値は、既存のすべての実行をその秒数まで延ばします。
- `email` ステップの変更。`email` にはまたぐべき窓がありません。

### 作業分解

1. **モデルと検証。** `Totp` に `min_remaining`（別名 `minRemaining`）を足します。範囲の検査と分かりやすいエラーメッセージを付け、モデルから JSON スキーマを生成している場合はそれも更新します。
2. **待機関数。** `_do_sleep` の隣に `_wait_for_totp_window` を足します。壁時計は差し替えられるようにします。テストでは、`minRemaining: 30`、起床の遅れ、待機中に壁時計が巻き戻る場合と進む場合、中断を扱います。壁時計が動いた 2 つの場合は、待機が上限の内側で終わり、警告が出ることを確かめます。`minRemaining: 30` と起床の遅れでは警告が出ないことを確かめます。中断では `RunCancelled` が送出されることを確かめます。
3. **ループへの接続とラベル。** `_run_step_body` からハンドラの前に待機を呼び、`actions/_registry.py` の `_step_label` を拡張します。
4. **ステップ結果の警告。** `StepOutcome.warnings` と、`_run_step_body` の出力引数 `warnings` を足し、ステップの実行側でリストを結果に写します。manifest に記録し、`bajutsu/common/report/manifest.py` の `SCHEMA_VERSION`（現在は 15）を上げます。古い実行のステップに `warnings` がなければ、その実行がこの欄より前のものだという注記を添えます。HTML レポートで表示します。警告のある成功したステップが、`ok` を真のまま保ち、`reason` が空であることをテストで確かめます。
5. **ドキュメント。** [`docs/scenarios.md`](../../docs/scenarios.md)、[`docs/dsl-grammar.md`](../../docs/dsl-grammar.md)、`docs/ja/` の対応する文書を更新し、`totp` ステップを説明している [`docs/architecture.md`](../../docs/architecture.md) の箇所に短い補足を足します。

## 検討した代替案

| 案 | 採らなかった理由 |
|---|---|
| 常に次の境界まで待つ真偽値 `alignToWindow` | 毎回、平均 15 秒、最大 30 秒かかります。常に待ちたい作者は `minRemaining: 30` で表せるため、数値のフィールドがこの場合も満たします。 |
| 別ステップ `waitForTotpWindow` の新設 | 1 つの意図が 2 つのステップに分かれます。間に別のステップが挟まれると、待機は意味を失います。生成と保証は 1 つのステップに置くべきです。 |
| 既存の `sleep` ステップ | 待ち時間は時計に依存し、境界は実行のたびに動きます。`sleep` は固定長で上限が 30 秒であり、監査は `fixed-sleep` として報告します。 |
| アプリがコードを拒否したらサインインを再試行する | 再試行は、本物の失敗を 2 回目の試行の陰に隠します。多くのアプリは誤ったコードをロックアウトの回数に数えるため、再試行が実行の前提となるアカウントを壊すことがあります。 |
| 待機のあとに残りが `minRemaining` に届かなければステップを失敗させる | まれな壁時計の補正だけで、他に問題のない実行が失敗します。コードはそれでも受け付けられることがあり、結果に警告を残せば、実行を止めずに原因を見せられます。 |
| 0 でない `minRemaining` のデフォルト値 | 既存のすべてのシナリオのタイミングが変わり、YAML の読み手から待機の理由が見えなくなります。明示的なフィールドなら、原因が見えたままになります。 |
