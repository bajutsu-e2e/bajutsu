## はじめに

制御プレーンは、ジョブをキューに積み、Web UI を配信する `bajutsu serve` のアプリです。
制御プレーンのセルフホストは [BE-0016](../BE-0016-web-ui-self-hosting/BE-0016-web-ui-self-hosting-ja.md) が扱います。`deploy/self-host/` の Docker Compose スタックは、
制御プレーンを1つのアプリコンテナとして動かしています。処理は共有のデータベースとオブジェクトストアに対する
軽量な HTTP なので、水平にスケールできます。

この提案は、**ロードバランサの配下で N 個のアプリレプリカ**を動かします。制御プレーンは、レプリカを1つ失っても
止まらなくなり、より多くの同時利用者をさばけるようになります。プルベースのジョブ分配は変えません。
この項目は、同じ目標を古い前提の上で提案していた [BE-0167](../BE-0167-control-plane-scale-out/BE-0167-control-plane-scale-out-ja.md) を置き換えます。

アプリ側の作業の大半は、ほかの項目ですでに入っています。残るのはデプロイの構成と、その構成を実機で確かめる作業です。
*詳細設計* では、この2つを分けて書きます。

## 動機

Mac プールを増やしても、制御プレーンは1つのコンテナのままです。その1つのプロセスが容量の上限になります。
ブラウザの要求、ワーカーのリース呼び出し、実行履歴の読み取りがすべてそこを通るからです。
可用性のリスクでもあります。プロセスが再起動すると、UI 全体が短時間使えなくなります。

レプリカを並べれば、両方の制約がなくなります。作業の中身は、レプリカを正しく動かすことです。
どの要求もスティッキーなルーティングに頼らず、実行中のログ行はレプリカのあいだで失われないようにします。
あわせて、この構成が必要とするロードバランサの設定を文書化します。

変更が届いたことは、1つの観察できる違いで確かめられます。運用者が、2レプリカ構成のうち1つのアプリレプリカを
止めます。それでも UI は、もう1つのレプリカを通じて使えます。実行をライブで見ている閲覧者には、ログ行が
届き続けます。ワーカーがどちらのレプリカへログ行を送っても、結果は変わりません。

## 詳細設計

### アプリがすでに備えているもの

実装済みの項目が、要求を1つのレプリカに縛っていたプロセス内の状態を、すでに取り除いています。
次の表は、関心事ごとに、現在の動作と、その動作を入れた項目を示します。

| 関心事 | 現在の動作 | 項目 |
|---|---|---|
| ログイン状態 | 署名付き Cookie がデータベースの行を指す | [BE-0106](../BE-0106-post-completion-worker-model/BE-0106-post-completion-worker-model-ja.md) |
| ジョブのキュー | すべてのジョブが jobs テーブルでワーカーを待つ | [BE-0449](../BE-0449-server-runs-no-jobs/BE-0449-server-runs-no-jobs-ja.md) |
| ワーカーのリースと結果 | どのレプリカもジョブの行を見て処理する | [BE-0449](../BE-0449-server-runs-no-jobs/BE-0449-server-runs-no-jobs-ja.md) |
| アップロードしたバンドル | 手元にないバンドルはオブジェクトストアから取得する | [BE-0243](../BE-0243-upload-bundle-durable-storage/BE-0243-upload-bundle-durable-storage-ja.md) |
| 実行中のログ行 | Redis のバスがレプリカ間で行を運ぶ | [BE-0449](../BE-0449-server-runs-no-jobs/BE-0449-server-runs-no-jobs-ja.md) |
| データベース | バケットを使う構成では共有データベースの指定が必須 | [BE-0449](../BE-0449-server-runs-no-jobs/BE-0449-server-runs-no-jobs-ja.md) |

BE-0167 は、いまは成り立たない前提に立っていました。BE-0167 では、ワーカーはジョブの終了後に
結果を送るだけで、レプリカをまたぐログストリームはありませんでした。現在のワーカーは、ジョブの実行中に
ログ行を送ります。各行は、長く開いたままのイベントストリームでブラウザへ届きます。デフォルトのインメモリのバスでは、
ワーカーが別のレプリカへ送った行をブラウザは受け取れません。

Redis のバスが、この欠落を埋めます。各レプリカは `BAJUTSU_REDIS_URL` から共有の Redis を見つけます。
[`docs/ja/self-hosting.md`](../../docs/ja/self-hosting.md) は、複数レプリカの構成向けにこの設定をすでに説明しています。ただし、compose スタックにはまだ
Redis のサービスがありません。

一部の状態は、設計どおりレプリカごとに残ります。表の2行に示すとおり、どちらもアフィニティを必要としません。

| レプリカごとの状態 | アフィニティが要らない理由 |
|---|---|
| 実行中のログ行の上限 | プロセスごとに数え、各レプリカのメモリを抑える |
| 展開済みバンドルのキャッシュ | 手元にないレプリカはオブジェクトストアから取得する |

### 作業分解

**1. ステートレスなレプリカの実機確認。** 任意のレプリカが任意の要求を処理できることは、コードがすでに満たしています。
残るのは、実際の構成での確認です。一方のレプリカでログインし、もう一方で実行履歴を読みます。

**2. ロードバランサの方針。** レプリカの前段には Caddy か HAProxy を置き、ラウンドロビンではなく
**最小接続数**を使います。イベントストリームは長く開いたままです。ラウンドロビンでは、開いたストリームを
多く抱えたレプリカへ負荷が偏ります。現在のスタックの `Caddyfile` は、1つの `bajutsu:8765` へ転送しています。
レプリカ構成では、この `Caddyfile` に転送先としてレプリカの一覧を書きます。Caddy がロードバランサになり、
Transport Layer Security（TLS）もそこで終端します。

**3. レプリカをまたぐ実行中のログ。** compose スタックに Redis のサービスを足します。
制御プレーンのイメージには `redis` パッケージも入れます。`deploy/self-host/Dockerfile` が入れるのは現在
`.[server,worker,db,oauth]` で、このパッケージを含む extra はありません。パッケージがないまま `BAJUTSU_REDIS_URL`
を設定すると、最初のログ行でライブのバスがエラーになります。すべてのアプリレプリカに `BAJUTSU_REDIS_URL`
を設定し、一方のレプリカの閲覧者に、ワーカーが他方へ送った行が届くことを確かめます。

**4. N レプリカのための compose 配線。** `deploy/self-host/` に、スケール係数とロードバランサの設定を加えます。
現在のアプリサービスは、ポート 8765 をマシンへ直接公開しています。レプリカ構成では、ロードバランサが代わりに
ポート 8765 を公開し、各レプリカは自分のポートをロードバランサにだけ公開します。推奨のテールネット限定の前段
`tailscale serve --bg 8765` は、コマンドを変えずにロードバランサへ届きます。Postgres と MinIO は共有のまま
変えません。運用者の手順は、`deploy/self-host/README.md` とセルフホストのガイドに書きます。

**検証。** このティアはデプロイと運用の作業です。`make check` のゲートは Docker も複数コンテナの構成も
動かさないので、このティアを検証できません。デプロイ上で、次の表の手順を手作業で確かめます。

| 手順 | 確かめること |
|---|---|
| ロードバランサの配下に2つのレプリカを立ち上げる | 両方が要求に応答すること |
| 一方のレプリカでログインする | 他方が次の要求を受け付けること |
| 一方のレプリカから実行をリースする | その結果を他方から読めること |
| 他方へログが送られる実行を一方で見る | ログ行が届くこと |
| レプリカを1つ止める | UI が使い続けられること |

このティアは `bajutsu/serve/` にコードを追加しないので、新しいユニットテストもありません。構成そのものには、
ゲートの契約がありません。

## 検討した代替案

| 代替案 | 判断 | 理由 |
|---|---|---|
| ロードバランサでのスティッキーセッション | 採らない | レプリカごとの結び付きが戻り、再起動時に負荷が偏るから |
| ラウンドロビンの負荷分散 | 最小接続数を採る | 長く開いたストリームが一部のレプリカへ集まるから |
| Redis なしの実行中のログ | 採らない | 別のレプリカへ送られた行がブラウザに届かないから |
| 単一レプリカの垂直スケール | 出発点に限る | 容量の上限と可用性のリスクが残るから |

ログイン状態はすでにデータベースにあるので、スティッキーセッションで得られるものはありません。
Redis がなくても、アップロードされた `console.log` は最後に届きます。失うのはライブの表示で、ログそのものではありません。
