# Android per-step performance investigation (read-only)

All paths under the repo root. "≈" = estimate; "measured" = figure from a roadmap item. Hierarchy of cost on this backend: **a read (`query()`) dominates everything; how many reads a step pays is decided by the settle/catch-up machinery, not by the actuator.**

## 1. The `query()` path

**Call chain.** `CoordinateTreeDriver.query()` (`bajutsu/common/drivers/coordinate_tree.py:60`) → `_read_settled_tree()` (:71) → `AdbDriver._describe()` (`bajutsu/common/drivers/adb.py:678`) → `_read_source()` (:694) → parse → `_record_tree()` (:782) → `_advance_catchup()` (:859).

**Transient-empty retry** (`coordinate_tree.py:43-46`): `_READY_MIN = 2`, `_EMPTY_RETRIES = 5`, backoff `0.05·2^i` capped at `0.2` s (≈0.75 s total sleep, plus up to 5 extra reads). Only fires after a ≥2-element tree has been seen.

**Dump fallback** (`adb.py:773`): one subprocess `adb -s S exec-out uiautomator dump /dev/tty` (`backend_cli/adb.py:89-91`) via `real_run` = `subprocess.run(..., capture_output=True)` (`backend_cli/adb.py:55`). One spawn per read, no cat/pull. Measured **≈2.3–2.5 s** (BE-0234 table, `roadmaps/BE-0234-adb-run-performance/BE-0234-adb-run-performance.md:39-43`; `--compressed` and dump-to-file+cat are no better, :40-41; bare `getprop` round trip ≈0.04 s, :43). The cost is instrumentation startup + UiAutomation connect + waitForIdle + teardown (BE-0245 md:19-22).

**Resident channel** (`adb.py:713`, `backend_cli/adb_resident.py:105-146`): `fetch_source` opens a **new `http.client.HTTPConnection` per call** (:125), `GET /source[?since=]`, reads body, `conn.close()` (:145). The server replies `Connection: close` (`ResidentServerTest.kt:544`) and is a **single-threaded accept loop** (:83). So every read = TCP connect to localhost → adb server → `adb forward` → adbd → server socket; **no keep-alive, no pipelining**. Timeout 5 s. Measured **≈0.1–0.3 s** per read (BE-0245 md:44, :127; `docs/drivers.md:187`), 0.20 s observed on a real run (BE-0339 md:426).

Device side per `GET /source` (`ResidentServerTest.kt:354-393`):
1. `device.waitForIdle()` (:358) — UiAutomator's default idle wait (up to 10 s internally if the a11y stream never quiets; typically ms).
2. If `?since=`: `readMark.awaitPostdate(since, POSTDATE_BUDGET_MS=2000)` (:365, :642) then another `waitForIdle()` (:366).
3. `settledDump` (:378 → :482-490): `dumpWindowHierarchy` **at least twice** (previous + current must be byte-equal), up to `SETTLE_DUMPS = 4` (:649), each preceded by `waitForIdle()` (:485). So a quiet screen pays **2 dumps + 2 waitForIdle** per read; an animating one 4.
4. `nativeZHeader` (:380 → :427-457): a **second full `AccessibilityNodeInfo` walk over every node** (`rootInActiveWindow`, `getChild(i)` per node — each an IPC to the app process) on **every read**, even when no app opted in (the doc comment at :420-423 admits this). Estimate ≈20–100 ms on a few-hundred-node tree.

Host side after the body arrives: `narrow_to_active_window` (`adb_resident.py:78-102`) does `ET.fromstring` + `ET.tostring` (a full parse+serialize), then `parse_hierarchy_with_identities` (`adb.py:404-417`) parses **the same XML again** via `slice_hierarchy_root` (:419-437). Two XML parses + one serialize per read; ≈5–30 ms for a 50–200 KB dump — small versus transport, but pure waste.

**Catch-up barrier** (`adb.py:454-478`, `_Catchup`): armed by `_arm_catchup` (:835) with `deadline = now + _READ_LAG_S` (`_READ_LAG_S = 4.0`, :536). `_advance_catchup` (:859-919) runs on every read: mark path closes when `read_mark > actuation_mark`; dump path needs projection ≠ `pre_key` **and** held ≥ `_CATCHUP_DWELL_S = 0.5` (:543). `_await_catchup` (:941-972) loops `while self._catchup is not None`: checks `time.monotonic() >= catchup.deadline` (:952), `sleep(_SETTLE_POLL_S=0.1)` (:971), `query()` (:972). Bound: 4 s wall clock; on the resident path each poll itself blocks up to 2 s device-side (`POSTDATE_BUDGET_MS`), so a gesture that moves no frame costs ≈2 s (device) + host re-poll until 4 s.

**`_settle`** (`adb.py:983-1047`, reached via `settled_query` :974 and every actuator's `_resolve_frame_and_screen` :1119 / `_device_act` :1262 / `is_tappable` :1160 / `_scroll_into_view` :1183): `_await_catchup()` → one `query()` → fast-path return only if key == `_settled_key` (a key **proved** by two consecutive agreeing reads, BE-0351). Otherwise `deadline = now + _SETTLE_DEADLINE_S` (`8.0`, :505, :1018), loop `while time.monotonic() < deadline` (:1020): `sleep(0.1)` (:1021), `query()`, return on two equal consecutive keys. **Minimum after any actuation: 2 reads + 0.1 s sleep** (the actuator cleared `_settled_key` via `invalidate_settled_cache`, :639-657). Worst case: 8 s + one read.

**`_resolve`** (`coordinate_tree.py:151-177`): `timeout=_RESOLVE_TIMEOUT_S=3.0` (`adb.py:513`), `poll=0.2`; not-found re-queries until the deadline (up to ≈10 reads on the resident path). Then `_scroll_into_view` (:1167-1195) — `_SCROLL_RETRIES = 3` swipes, each followed by a full `_settle()` (:1183).

**Scroll constants**: `_SCROLL_SPEED_PX_PER_S = 550`, `_SCROLL_MIN_DURATION_MS = 600` (:524-525); `_scroll_duration_ms` (:1554-1559) → a full-screen pan on a 2400-px panel is ≈1.6–2.6 s of gesture, a small one 600 ms. `_scroll_toward` swipes from 0.7 h to 0.3 h with `swipe_cmd`'s default **300 ms** (`backend_cli/adb.py:519`).

## 2. Actuator path

**Resident `tap` / `longPress` / `doubleTap`** (`adb.py:1408-1412, 1468-1475, 1419-1445` → `_device_act` :1239-1406):
- Host: `_settle()` (≥1 read, ≥2 after a prior actuation) → `_resolve` → `raise_if_covered` → build `ActRequest` with identity (`resource-id, content-desc, text, class`) + ordinal/count → `_capture_mark()` = **`GET /clock` (one more HTTP connection)** (:822, `adb_resident.py:261-280`) → `POST /act` (new connection, timeout 10 s, `adb_resident.py:183`).
- Device (`ResidentServerTest.kt:171-229`): `waitForIdle` (:185) → if `since`: `awaitPostdate(≤2 s)` + `waitForIdle` (:187-188) → `settledActBounds` (:190 → :516-524): **≥2 `dumpWindowHierarchy` + XmlPull parse** until the target's bounds agree (≤4) → `UiDevice.click(x,y)` (:207; internally injects down/up then `waitForIdle` again) / `UiDevice.swipe(x,y,x,y, ms/10 steps)` (:213; `SWIPE_STEP_MS=10`, :687) / stamped `MotionEvent`s with `TAP_HOLD_MS=40`, `INTER_TAP_MS=60` (:270-286, :693-694) → `publishHeader` (:245-247): **blocks up to `ACT_PUBLISH_BUDGET_MS = 500`** (:625) waiting for an a11y event postdating injection.
- On `409 stale`: host re-settles and re-resolves, `_STALE_MAX_ATTEMPTS = 3` (:1237), then falls to the coordinate path.
- After success: `invalidate_settled_cache()`; barrier armed **unless** `published_mark > mark` (:1341-1364). So a confirmed tap makes the next `_settle` pay 2 reads (not the 4 s barrier); an unconfirmed one (no frame moved, e.g. a counter tap) pays 500 ms device-side, then the next read blocks ≤2 s on `?since=`, then re-polls up to 4 s.

Per confirmed resident tap on the host: **3 HTTP round trips (`/source` ×≥1, `/clock`, `/act`) + device-side ≥4 dumps** (2 for the host's settle read, 2 for `settledActBounds`) — estimate ≈0.5–1.2 s for the tap step body before the runner's own post-step read.

**Coordinate fallback** (dump path or no `/act`): `_center` → `_settle` (dump: ≥2 × 2.4 s) → one `adb shell input tap X Y` (`backend_cli/adb.py:230`, measured ≈0.07 s, BE-0234 md:42) → `_arm_catchup` with no mark → next resolve pays the dwell heuristic (≥0.5 s + reads). `long_press` = `input swipe x y x y ms` (:1475). `double_tap` non-root = `input tap ; input tap` in one shell (:239-250, JVM start per `input` so the gap overruns 300 ms); root = one shell with a `sendevent` script (:364).

**`swipe`/`scroll`** (`adb.py:1477-1484, 1534-1552`): `_pan_baseline()` (:788-810) — drains a pending barrier, then `query()` only if `_tree_current` is false (a swipe right after another swipe: one read); `_capture_mark()` (`/clock`); one `adb shell input swipe` subprocess (≈50–150 ms spawn + the gesture's own 300 / ≥600 ms); `_arm_catchup`. Always arms the barrier — no device confirmation exists for pans, so the next coordinate resolve pays the `?since=` block (≤2 s) if the tree lags. The orchestrator's directional swipe calls `settled_query()` first (`orchestrator/actions/handlers/gestures.py:212`), so ≥2 reads before the gesture.

**`back`** (:1562-1566): one `input keyevent 4` subprocess, no barrier. **`type_text`** (:1671-1684): one `adb shell` with `input text …` on stdin via `subprocess.run` (:1684), no barrier, but invalidates the settled cache (next actuator: 2 reads). `delete_text`/`select_all`/`copy_selection`: one `input keyevent`/`keycombination` each.

## 3. Screenshot and interval captures

`screenshot` (:1702-1703 → `backend_cli/adb.py:975-990`): one subprocess `adb exec-out screencap -p` (:94-96), PNG on stdout, no pull. Estimate ≈0.2–0.6 s on an emulator (PNG encode of a 1080×2400 frame device-side + transfer). **Taken on every step**: `screenshot.after` unconditionally (`orchestrator/loop.py:1601`) and `screenshot.before` in the pre-step baseline (:1279-1324). So **2 screencap subprocesses per step**, ≈0.5–1.2 s, comparable to a resident read pair.

Video: `screenrecord` is one background `adb shell` spawned once per scenario (`environments/android.py:288-296` → `evidence/intervals.py:655-733`), with `confirm_started=True` → `pgrep` polls at 0.2 s (`intervals.py:497-535`) and a `stat` growth check (:586-620, poll 1 s). Stop = SIGINT + `pgrep` polling + `adb pull` + `rm`. Logcat: one background `adb logcat` per scenario (:736-742). **No per-step subprocess spawn** for either. The 180 s `screenrecord` ceiling (`intervals.py:650`) truncates long scenarios.

## 4. Per-step / per-poll hooks

- `system_alert_labels` (:1661) returns `[]`, `dismiss_blocking_tip` (:1665) returns `False` — both O(1), no device call. The native alert gate is only entered when `HANDLE_SYSTEM_ALERT` is advertised (`orchestrator/waits.py:288-300`), which adb never does. The tip hook still runs per poll but is free.
- `wait_for` (`coordinate_tree.py:179` → `base.default_wait_for` :904-915): one `query()` per poll; the runner's `_wait` loop (`waits.py:832, 860, 900-905`) polls with `_POLL = 0.05` (:31) via `_adaptive_sleep` (:209) — on the resident path that is **≈4–8 reads/s** each costing ≥2 device dumps; effectively the device is dumping continuously during any `wait`.
- `is_tappable` (:1139-1165): a full `_settle()` + `_resolve` (3 s not-found retry) per call; `scroll_until_tappable` calls it once per scroll step (`handlers/scroll.py:609`).
- `viewport()` (:1486-1494): `wm size` once per driver, cached — fine.
- `drain_actuations` (:1049): in-memory.
- `fetch_clock`: one HTTP round trip **per barrier-arming gesture** (tap/long/double/swipe/scroll/pinch/rotate), never per poll.
- Runner extra reads per step: `before` for `screenChanged` policies reuses `prev_after` (`loop.py:1367-1374`); the always-on post-step `elements.json` forces `screen.get()` (:1640-1641, `_ScreenRead` docstring :250-253: "makes the read unconditional under any sink that writes"). Non-mutating steps seed it; **mutating steps pay one fresh read per step** on top of the actuator's own reads. `assert` = `_poll_asserts` (`loop.py:143-146`) with deadline `_timeout_floor()` — zero unless `BAJUTSU_MIN_WAIT_TIMEOUT` is set (the Android CI lane sets 15 s, :132).

**Realistic resident-path `tap` step cost** (estimate): pre-step baseline screenshot ≈0.4 s; `_settle` 2 reads ≈0.4–0.6 s; `/clock` + `/act` incl. ≥2 device dumps + 500 ms publish wait ≈0.6–0.9 s; `screenshot.after` ≈0.4 s; post-step `elements` read ≈0.2–0.3 s (blocking ≤2 s if the barrier stayed armed). **≈2–3 s per tap step**, of which the semantic "tap" is <100 ms. On the dump path the same step is ≈8–12 s (BE-0234 md:66-78: 2–4 reads at 2.4 s).

## 5. Per-scenario fixed costs (`environments/android.py:93-175`)

Sequential subprocesses: `await_boot` (`readiness.py:48-59`, `getprop` poll 0.5 s, 60 s ceiling; one call when booted) → optional `uninstall` + `install` (seconds) → `pm clear` → `am force-stop` → one `pm grant` **per permission** (`backend_cli/adb.py:891-925`) → `_prestart_video` (`pgrep` baseline + `stat` + spawn + `pgrep` poll ≥1 + `stat` ≥1 ≈ 5 spawns, ≈1 s) → `resolve_activity` + `am start -W` (2 spawns; `-W` blocks until the activity is displayed, ≈1–3 s cold) → `_begin_resident` → `await_ready` (`readiness.py:63-171`: `query()` poll 0.1→0.5 s, 10 s ceiling, plus `_SETTLE_POLLS = 3` confirming reads, :34).

Resident server start (`adb_resident.py:383-399, 478-502`): **2 `uninstall` + 2 `install` every lease** (:395-397, ≈2–6 s total on an emulator), `am instrument -w` spawn (:398), `adb forward tcp:0` (:399), then `_await_ready` polls `fetch_source` at `_READY_POLL_S = 0.2` up to `_READY_TIMEOUT_S = 20` (:356-357). Instrumentation bring-up ≈2–4 s. `has_reusable_resident()` returns False (:367-370) — the whole thing is torn down (`force-stop`, `forward --remove`, :424-447) and rebuilt **per lease**, i.e., per scenario. Estimate **≈6–12 s fixed per scenario** for the resident lifecycle alone, plus ≈5–10 s for install/clear/launch/readiness.

## 6. What the resident server can already do

Endpoints (`ResidentServerTest.kt:97-107`): `GET /source[?since=]`, `POST /act?kind=tap|longPress|doubleTap&rid&desc&text&cls&index&count[&since][&durationMs]`, `GET /clock`. It already:
- runs as an instrumentation with a live `UiAutomation` (:65-68) and registers `setOnAccessibilityEventListener` (:73) — it **already has the event stream**; it only records `eventTime` (`ReadMark`, :558-587).
- re-finds an element by identity against a fresh dump and clicks/swipes via `UiDevice` (:190-215), injects raw `MotionEvent`s via `UiAutomation.injectInputEvent` (:288-305).
- walks `AccessibilityNodeInfo` directly (`rootInActiveWindow`, :428-457) — i.e., **it can read the tree without XML serialization** today, it just uses that walk only for `nativeZ`.

It cannot yet: wait for a selector, evaluate a selector (matching is `resource-id/content-desc/text/class` equality only, :317-350), read the hierarchy incrementally (every read is a full `dumpWindowHierarchy` serialization, twice), keep a connection open, serve pans/keys/text, or take a screenshot (`UiAutomation.takeScreenshot()` is available but unused).

To move a scenario's step loop on-device you would need: (a) a selector matcher in Kotlin equivalent to `base.find_all`/`resolve_unique` (`bajutsu/common/drivers/base.py`), including `within`, `idMatches`/`labelMatches`, trait derivation, and the `_derived_label` rule (`adb.py:251-282`); (b) a `wait`/`assert` evaluator with the same deadline/poll semantics and the transient-empty rule; (c) an event-driven "tree changed" signal (`TYPE_WINDOW_CONTENT_CHANGED`/`WINDOWS_CHANGED` from the listener) so polls become wake-ups rather than dumps; (d) a batch protocol (`POST /steps` with a list of `{action, selector, wait}`; a streamed outcome per step with actuation records, read marks, and an on-device `takeScreenshot`); (e) the host still doing pass/fail over the returned evidence (prime directive 1 is untouched — the device is a deterministic executor, not a judge). Ambiguity must fail on-device with the same message, and `raise_if_covered` (document-order occlusion, `base.py:928`) must be replicated or bounds returned for the host to check.

## 7. Ranked bottleneck hypotheses

| # | Hypothesis | Est. cost | Cheapest fix | Radical fix |
|---|---|---|---|---|
| 1 | **Device-side dump amplification**: every `/source` = 2–4 `dumpWindowHierarchy` + 2–4 `waitForIdle` + nativeZ walk (`Kt:358-380, 482-490`); every `/act` adds 2–4 more (`:516-524`). A tap step ≈6 device dumps. | ≈0.1–0.2 s per dump ⇒ ≈0.6–1.2 s/step | Skip `settledDump`'s second dump when no a11y event arrived between the two (`ReadMark` already knows: compare `current()` before/after dump #1). Gate `nativeZHeader` on a request flag or on the app having opted in (cache "no node advertises the key" per window id). | Build the tree from `AccessibilityNodeInfo` directly (the `:428-457` walk) into a compact JSON/binary once; replace "two equal dumps" tearing check with `WINDOW_CONTENT_CHANGED` quiescence from the listener. |
| 2 | **Host `_settle` minimum of 2 reads after every actuation** (`adb.py:1015-1031`; cache cleared by `invalidate_settled_cache` on every gesture) plus the runner's post-step `elements` read (`loop.py:1640`) ⇒ ≥3 host reads per mutating step. | ≈0.6–0.9 s/step resident; ≈7 s dump | Let a `published_mark`-confirmed act (`adb.py:1341`) set `_settled_key` from the read the device already settled (`settledActBounds` proved rest of the target; returning the settled XML with the `/act` reply would give the host a free post-act tree). Reuse `_ScreenRead` as the next step's settle read #1 (it is: `prev_after`) — but `_settle` ignores it because `_tree_current` is only a baseline flag; a "proved-stable by device settle" bit on the read would let `_settle` take the fast path. | Server-side `waitForSettled(selector)` returning the tree once — one round trip per step for settle+resolve. |
| 3 | **Barrier waits on gestures that move no frame**: `ACT_PUBLISH_BUDGET_MS = 500` (`Kt:625`) spent inline, then the next read blocks ≤`POSTDATE_BUDGET_MS = 2000` (`Kt:642`), then host re-polls to `_READ_LAG_S = 4.0` (`adb.py:536`). Pans always arm it (`:1484, 1552`). | 0.5–4 s on a "quiet" tap; ≤2–4 s after each swipe | Shrink `POSTDATE_BUDGET_MS` for reads that follow a *confirmed-unpublished* act; on pans, have `/act` support `kind=swipe` so the same publish confirmation applies (no barrier when confirmed). | Event-driven barrier: the listener knows the exact event types; only `WINDOW_CONTENT_CHANGED`/`VIEW_SCROLLED` count, and a `/act` that observes `VIEW_CLICKED` with no layout event can answer "moved no frame" immediately instead of timing out. |
| 4 | **Two screencap subprocesses per step** (`loop.py:1279, 1601`; `backend_cli/adb.py:975-990`). | ≈0.5–1.2 s/step | Make `screenshot.before` opt-in or derive it from the previous step's `after.png` (same device state — the same argument BE-0234 used for `prev_after`). | Add `GET /screenshot` on the resident server (`UiAutomation.takeScreenshot()` → JPEG/PNG over the open channel), removing the adb spawn and the PNG-via-exec-out transfer. |
| 5 | **One TCP connection per request + single-threaded server + `Connection: close`** (`adb_resident.py:125, 183, 269`; `Kt:83, 544`). 3 connects per tap, each through adb's forward. | ≈10–40 ms each ⇒ ≈50–150 ms/step; larger on a loaded CI host | Keep one `HTTPConnection` per lease with HTTP/1.1 keep-alive (server: stop sending `Connection: close`, loop `handle` on the same socket). | Persistent length-prefixed binary stream over the forward; multiplex reads/events/acts. |
| 6 | **`_wait` polls at 50 ms** (`waits.py:31, 209`) ⇒ continuous device dumping during waits; each poll ≥2 device dumps. | Device CPU saturation slows the app under test (emulator, 2 cores in CI); wall-clock hidden | Raise `_POLL` for backends whose read is device-bound, or long-poll: `GET /source?since=<last mark>` already blocks until the tree changes — let `wait_for` pass the last read mark so polls return only on change. | Server-side `wait_for(selector, timeout)` driven by a11y events. |
| 7 | **Per-lease resident install/uninstall + instrumentation start** (`adb_resident.py:395-399, 478-502`; `has_reusable_resident` False, `android.py:367`). | ≈6–12 s per scenario | Skip uninstall/install when the installed APK's signature/version matches (`pm dump` or `pm path` + sha check); reuse the running instrumentation across leases within one `run`. | Keep the server resident across the whole `run`/`serve` process; a `/ping` + version handshake replaces reinstall. |
| 8 | **Double XML parse on the host** (`adb_resident.py:78-102` + `adb.py:404-437`). | ≈10–40 ms/read | Have `narrow_to_active_window` return the parsed root and let `parse_hierarchy_with_identities` accept an `ET.Element`. | Server emits only app windows (it already knows `SYSTEM_DECOR_PACKAGES`, `Kt:335`), so no narrowing at all. |
| 9 | **Fixed gesture durations**: `swipe_cmd` 300 ms (`backend_cli/adb.py:519`), `_SCROLL_MIN_DURATION_MS` 600 / 550 px/s (`adb.py:524-525`), long-press default 700 ms (`Kt:688`), plus `input` JVM start ≈70 ms (measured). | 0.3–2.6 s per pan | Not much: these are fidelity choices (BE-0400). `/act kind=swipe` would remove the `input` spawn (≈70 ms) and give pans the publish confirmation from #3. | — |
| 10 | **`uiautomator dump` fallback** (2.4 s/read, `adb.py:773`) whenever APKs are not built or the channel faults — silently ~10× slower. | ≈7–12 s/step | Nothing cheap beyond keeping the resident path healthy (log already warns). | Ship the server APKs as a package data file so the resident path is the only path. |

**Bottom line.** On the resident path a mutating step is ≈2–3 s wall clock, of which ≈70 % is redundant tree serialization (hypotheses 1–2), ≈15 % screenshots (4), and the rest transport/barriers (3, 5). Hypotheses 1, 2 and 4 are addressable without protocol changes; 3 and 6 want the server to use the a11y event *types* it already receives; 7 is a lifecycle policy change. The radical end — a server-side step executor with selector matching and event-driven waits, returning per-step evidence for the host to judge — would collapse a step to one round trip plus the gesture's own duration.
