## はじめに

**オープンな**ロードマップ項目のすべてに、GitHub Issue を起票します。オープンな項目とは、`状態` が
`承認済み` または `実装中` の項目です。出荷も保留もされていない項目を指します。

起票した Issue の標準機能である担当者（Assignees）を、「誰かがその項目に取り組んでいるか、取り組んで
いるなら誰か」を示す一次情報とします。項目は提案として存在した時点で Issue を持つので、担当者のいない
Issue は、今のロードマップに欠けているシグナルそのものになります。まだ誰も拾っていない項目です。

Issue の起票とクローズは自動で行います。決め手は、項目の `状態` と、トラッキング Issue がすでに記録
されているかどうかの二つです。専用フィールドもダッシュボードも、人手の運用も新設しません。

## 動機

このリポジトリでは、複数の人間とエージェントが同時に作業します（CLAUDE.md の「並行作業で壊し合わない
ために」）。「自分の担当範囲にとどまる」という指針はありますが、オープンな項目のうち、すでに誰かが
取り組んでいるものと、まだ手つかずのものを一目で確認する手段はありません。

次に取り組む項目を選ぶ開発者は、人間でも AI セッションでも、重複作業を避けるために開いている PR を
検索したり周囲に確認したりする必要があります。「何が未着手か」に答える場所は、一つもありません。

ロードマップの `提案者` 欄も、この問いには答えません。この欄が記録するのは項目を最初に*提案した*人物
です。実際に*実装する*人物とは別であることが多く、一度設定されると変わりません。項目が `実装中` の
まま、あるいは提案が拾い手を待ったまま、誰の担当かわからない状態で置かれることもあります。

GitHub には、この用途に合う所有権の仕組みがすでにあります。Issue の担当者（**Assignees**）です。
`assignee:` と `no:assignee` で絞り込めます。Issue 一覧と通知に表示され、
`gh issue list --assignee <user>` でも参照できます。

オープンな項目のそれぞれに Issue があれば、Issue 一覧がロードマップに必要なボードになります。担当者の
付いた Issue は、誰が何に取り組んでいるかを示します。`no:assignee` のフィルタは、未着手のバックログを
一覧にします。専用の「担当者」欄もステータスダッシュボードも考案する必要はありません。実際に欠けて
いるのは、BE 項目と Issue を結び付ける仕組みだけです。

## 詳細設計

この設計は、追跡する二つの事実の両方について、**GitHub 自身を一次情報**とします。一つ目は、誰が項目を
担当しているか（Issue の担当者）です。二つ目は、トラッキング Issue がすでに存在するか（項目の BE ID を
タイトルに持つ、ラベル付きの Issue）です。

リポジトリ側には何も書き戻しません。したがって同期処理には、`main` へのコミットも、`roadmap-id` の
main への push が必要とする bypass 用 App も要りません。デフォルトトークンの `issues: write` だけで
足ります。

1. **Issue の存在判定は、リポジトリ側の欄ではなく GitHub をキーにします。** `BE-NNNN` のトラッキング
   Issue とは、`roadmap-tracking` ラベルを持ち、タイトルに `BE-NNNN` を含むオープンな Issue です。
   同期処理は、BE ファイルから欄を読むのではなく、その Issue が存在するかを GitHub に問い合わせます
   （`gh issue list --label roadmap-tracking --state open --search "BE-NNNN in:title"`）。

   この方式のおかげで、リポジトリへの書き戻しが要りません。最も頻繁に変わる状態である担当者も、
   GitHub がすでに管理している場所だけに置けます。
2. **ライフサイクル規則は、項目の現在の `状態` だけを見る関数です。** 番号の付いた各項目について、
   次のとおり処理します。
   - `状態` が `承認済み` または `実装中`（オープンな項目）で、対応するオープンな Issue が存在しなければ、
     同期処理が Issue を起票します。
   - 対応するオープンな Issue が存在するのに、`状態` が `実装済み`、`保留`、`却下` のいずれか（出荷済み
     または保留）であれば、同期処理が Issue をクローズします。保留の解除（`保留` → `承認済み`）は項目を
     再びオープンにするので、次の実行で Issue が再作成されます。

   Issue の存在は、PR の差分ではなく現在の `状態` だけから導きます。そのため、同期処理は BE-0043 や
   BE-0061 と同じく、自己修復的かつ冪等になります。すでに整合した集合に対して二度実行しても結果は
   変わりません。マージ競合で一つの項目に Issue が二つ生まれることもありません。二度目の実行が、一度目
   の作った Issue を見つけるからです。
3. **`main` で、ID が確定してから実行します。`BE-0109` はスキップします。** 新しい提案は、PR のあいだ
   `BE-0109` プレースホルダのままです。実番号 `BE-NNNN` は、マージ後に `roadmap-id` が `main` で割り当て
   ます（BE-0089）。そのため、実番号をタイトルに持つ Issue は PR 上では作成できません。

   そこで同期処理は `push: main`（パス `roadmaps/**`）で実行し、`BE-0109` の項目をスキップします。
   プレースホルダを改名する割り当てコミットは、それ自体が `main` 上の `roadmaps/**` への変更です。
   このワークフローが再び起動し、二度目の実行で番号の付いた項目を拾います。`roadmap-id` との実行順の
   依存も、改名すべきプレースホルダ Issue も生じません。
4. **新規スクリプト `scripts/sync_roadmap_tracking_issues.py`。** このスクリプトは
   `promote_roadmap_items.py` と同じ形です。四つのフォルダすべての番号付き項目を走査し（同スクリプトの
   `read_status` を再利用）、`gh` コマンド（`gh issue create` と `gh issue close`）を介してライフ
   サイクル規則を適用します。

   `--check` モードは、ずれを報告します。ずれとは、Issue が欠けているオープンな項目と、クローズすべき
   Issue です。読み取り（`gh issue list`）だけを使い、何も変更しません。メンテナやダッシュボードが
   監査として実行できます。
5. **Issue の形式。** タイトルは `[BE-NNNN] <項目のタイトル>` とします。本文は、項目の英語ファイルへの
   リンクと、その `Introduction` の引用です。ラベルは新設する `roadmap-tracking` とします。このラベルで、
   `bug` や `enhancement` とは別に絞り込め、存在判定も一意になります。

   同期処理は、Issue を**担当者なし**で起票します。着手する人が、他の GitHub Issue と同じように自分を
   アサインします。こうして Issue 一覧が、ロードマップの求めるボードになります。
   `label:roadmap-tracking assignee:<user>` は一人の担当分です。`label:roadmap-tracking no:assignee` は
   未着手のバックログです。
6. **新規ワークフロー `roadmap-tracking-issues.yml`。** `push: main`（パス `roadmaps/**`）で、一つの
   ジョブがチェックアウトしたツリーに対して同期スクリプトを実行します。ジョブの権限は `issues: write`
   と、チェックアウト用の `contents: read` です。

   ブランチへの push し返しも、`main` へのコミットも、bypass 用 App もありません。`roadmap-promote` や
   `roadmap-id` がすでに行っていることの、厳密な部分集合です。集合がすでに整合していれば、ジョブは何も
   せずグリーンのままです。
7. **一度きりのバックフィル。** ロードマップには、実番号を持つオープンな提案と実装中の項目のバック
   ログがすでにあります。同期処理の最初の実行（または手動の `gh workflow run`）が、それらの Issue を
   一度に起票します。ライフサイクル規則は冪等なので、特別扱いは要りません。
8. **`make check` には含めません。** このスクリプトはネットワーク越しに `gh` を呼び出すため、決定的な
   ゲートの内側では実行しません。`--check` モードは、読み取りだけでずれを報告する任意実行のコマンド
   にとどめます。`gh auth` とネットワークアクセスを要求するので、ゲートに入れる条件を満たしません。
   ゲートはそれらを意図的に要求しません。
9. **ドキュメント。** `docs/ai-development.md` に、既存の `roadmap-id` の説明と並べて短い小節を追加します。
   小節では、ライフサイクル規則と二つのフィルタを説明します。開発者向けの案内も添えます。項目に着手する
   前にトラッキング Issue の担当者を確認し、拾うときには自分をアサインします。

## 検討した代替案

- **トラッキング Issue を `実装中` の項目に限定する案。** この提案の初期の形は、作業が始まってはじめて
  Issue を起票するものでした。提案の大半は着手されないので、提案ごとの Issue はノイズだと考えたため
  です。

  この考え方は、本来の目的を逆にしています。狙いは、*どの提案が未着手か*を見えるようにすることです。
  Issue が一つも無い項目は「着手可能」ではなく、そもそも見えません。オープンな項目（提案でも実装中
  でも）すべてに Issue を起票すれば、未着手のバックログが、絞り込める一級の一覧（`no:assignee`）に
  なります。開発者が自力で再構成する必要はなくなります。ノイズの懸念には、`roadmap-tracking` ラベルと
  担当者フィルタで答えます。Issue を出さないことでは答えません。
- **Issue の代わりに、BE のメタデータブロックに「担当者」欄を設ける案。** 採用しません。担当者は、
  項目の提案文やトピックといった他のメタデータに比べて、はるかに頻繁に変わります。担当を引き継ぐたびに
  ファイルを編集することになり、レビューと差分が生じ、マージ競合の種も増えます。しかも、GitHub が
  すでに無償で追跡している情報のためにです。担当者と Issue の存在の両方を GitHub にキーづけることで、
  同期処理はリポジトリに一切触れずに済みます。
- **BE のメタデータに「トラッキング Issue」の逆参照欄を持つ案。** ファイルを読む人が Issue へのリンクを
  見られるので、便利さの面では魅力的です。しかし、解決済みの Issue *番号*を書き戻すには、保護された
  `main` へのコミットが必要で、bypass 用 App も必要になります。GitHub を一次情報とする設計が取り除いた
  依存を、呼び戻してしまいます。逆リンクは向きを逆にして、Issue の本文からファイルへ張るほうが適切
  です。

  のちに BE-0139 が、この難点を避ける「トラッキング Issue」行を追加しました。その値は、項目の不変の ID
  から組み立てる GitHub の Issue*検索* URL です。この行はそのつどの取得を必要とせず、Issue が起票されても、
  担当者が付いても、クローズされても変わりません。生成されるダッシュボード（BE-0094）も、同じ検索 URL を
  カードごとに出します。ここでかつて見込んでいた、読み取り専用の `gh issue list` は使いません。
- **Issue の代わりに GitHub Projects のボードを使う案。** プロジェクトボードを使えば、かんばん風の一覧が
  「無償で」手に入ります。ただし、項目とプロジェクトを同期する仕組みを別途持つ必要があり、より重い
  Projects v2 の GraphQL API も必要になります。さらに、今の環境にない `read:project` の OAuth スコープが
  要ります。この提案を検討する過程で確認したところ、`gh project list` はそのスコープの不足で失敗
  しました。

  Issue はすでにこのリポジトリで使われており（`bug_report` / `feature_request` テンプレート）、より
  単純で、今回の目的には十分です。将来 Projects のボードを使うことは妨げません。同じ Issue の上に
  重ねられるので、今回の設計を変更せずに済みます。
- **同期処理を `main` ではなく PR（`roadmap-promote`）で実行する案。** 採用しません。新しい提案は、PR の
  あいだ `BE-0109` プレースホルダのままなので、実番号を持つ Issue をそこで作成できません。割り当て後の
  `main` で実行し、`BE-0109` をスキップすれば、すべての Issue のタイトルを不変の ID のまま保てます。
