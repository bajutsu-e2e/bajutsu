## はじめに

iOS Simulator では、XCUITest が合成したタッチがテスト対象のアプリに届かないことがあります。
それでも XCUITest はタッチを届けたと報告するので、`tap` ステップは何もしないまま成功します。
本提案では、XCUITest バックエンドがこの取りこぼしを Simulator 自身のログから検出します。
そのうえで、タッチを最大 2 回まで打ち直します。2 回打ち直しても取りこぼした場合は、取りこぼしを理由として名指ししてステップを失敗させます。

取りこぼしの原因は 1 つで、外から観測できます。XCUITest のテスト管理プロセス（`testmanagerd`）は、
タッチを合成するたびに新しい仮想タッチデジタイザーを `backboardd` に接続します。`backboardd` は、
タッチをアプリへ振り分ける Simulator のプロセスです。この `backboardd` が、まれに 1 つのデジタイザーを
2 つのサービスとして登録します。すると touch down が片方のサービスのタッチ状態に入り、残りのイベントは
もう片方に入ります。`backboardd` は残りのイベントを捨ててその旨をログに残し、デジタイザーが外れるときに
途中まで届いたタッチをキャンセルします。アプリが受け取るのはキャンセルされたタッチなので、どのコントロールも
反応しません。このログ行はタッチ 1 回ごとの決定的なシグナルです。本提案は、runner が合成するすべての
タッチについて、このシグナルを判定に変えます。

## 動機

取りこぼされたタッチは誤った成功を生みます。決定的なゲートにとって、もっとも高くつく結果です。
タッチを取りこぼしたステップは成功を報告します。誰かが気付くかどうかは、シナリオがその後に何を確かめるかで
決まります。後続の `wait` が時間切れになれば、取りこぼしは別のステップの失敗として現れます。
後続の確認がないシナリオは、何も検証しないまま成功し続けます。

取りこぼしは仮定の話ではありません。CI の `app-crash (xcuitest)` ジョブは、アプリをクラッシュさせる
ボタンをタップし、次のステップが失敗することを期待するシナリオを実行します。このジョブは
[#2154](https://github.com/bajutsu-e2e/bajutsu/pull/2154) で 2 回続けて失敗しました。クラッシュボタンの
タップがアプリに届かず、失敗するはずのシナリオが成功したためです。その後の実行では、
`actuation (xcuitest)` ジョブが `paste_system_alert` のタブを開くタップを取りこぼしました。20 秒後には、
そのステップの `wait` が時間切れになりました。採取したすべての取りこぼしで、Simulator の統合ログに同じ行が出ています。

| 実行 | 取りこぼしたタッチ | `backboardd` のログ行 |
|---|---|---|
| 38198619020、attempt 1 | クラッシュボタン（最初のタップ） | `digitizer event … from unsupported service` の後に `skipping event` |
| 38198619020、attempt 2 | クラッシュボタン（最初のタップ） | `unknown digitizer` の後に `skipping event` |
| 38241318813、attempt 1 | `perm` タブ（実行開始から 62 秒後） | `unknown digitizer` の後に `skipping event` |

3 件目と同じ実行の正常なタップ 82 回には、これらの行が 1 つも出ていません。シグナルと取りこぼしは
1 対 1 で対応しています。ログの詳しい分析は [#2157](https://github.com/bajutsu-e2e/bajutsu/issues/2157) に
あります。

最初の 2 件からは「セッションの最初のタッチだけが取りこぼされる」と読めます。しかし、この競合は最初の
タッチに限りません。3 件目は先にウォームアップのタッチを済ませた後で起きており、デジタイザーの接続も 32 ミリ秒で
終わっていました。このため、ウォームアップのタッチでは競合を防げません（ウォームアップを試した
[#2160](https://github.com/bajutsu-e2e/bajutsu/pull/2160) はクローズしました）。タッチの合成をやめることも
できません。XCUITest には、アプリを操作する手段がほかにないからです。

取りこぼしたタッチを打ち直しても安全です。デジタイザーが外れるときに `backboardd` が途中までのタッチを
キャンセルするので、アプリが完了したタッチを見ることはありません。コントロールは反応せず、
2 回目のタッチが 1 回目の操作を二重に実行することはありません。ただし条件が 2 つあります。
1 つの判定がちょうど 1 回の合成タッチを対象にすることと、取りこぼしがそのタッチで最初に届いたイベントより前に起きることです。
以下の設計は、1 つ目を保証します。ユニット 1 は、2 つ目を実測します。連続的なジェスチャー認識器は、キャンセルの前に
`.changed` を報告することがあるためです。対象は、`/swipe`、`/scroll`、ピッカーのドラッグの背後にあるパンと、
`/gesture` の背後にあるピンチと回転です。その場合、打ち直すと移動量が上乗せされます。ユニット 1 が、取りこぼしは
ドラッグの途中に起きないと示すまで、ドライバーが打ち直すのは離散的なタッチ、つまり `/tap` と `/systemAlert/tap` だけです。
判定が `dropped` の連続的なジェスチャーは、打ち直さずに、名指しでステップを失敗させます。

もう 1 つ限界が残ります。touch down で動くコントロール（たとえば `.touchDown` に結び付けた `UIControl`）は、
タップが取りこぼされた時点で down をすでに受け取っています。このため、打ち直すと同じ操作が繰り返されます。
標準のコントロールは touch up で動くので、本提案はこの限界を受け入れ、記録にとどめます。

この変更が入ったかどうかは、2 か所で確かめられます。1 つは実行の証跡で、打ち直したタッチが、それを要した
操作に結び付けて記録されます。もう 1 つは iOS CI の繰り返し実行で、上で挙げた誤った成功が再発しなくなります。
`app-crash (xcuitest)` は、クラッシュボタンを押さないまま成功しなくなります。

## 詳細設計

### 対象範囲

runner のエンドポイントのうち、タッチを合成するものはすべて対象にします。具体的には、`/tap`（ハンドル指定、
座標指定、タップ回数指定、長押し）、`/gesture`（ピンチと回転）、`/swipe`、`/scroll`、ピッカーホイールの
調整、システムアラートのボタンのタップです。文字入力はタッチデジタイザーではなくキーイベントを使うので、
対象外とします。

既存の動作のうち 2 つは、1 つの判定の中に複数のタッチを入れてしまうので、設計で取り除くか封じ込めます。
1 つ目は `/gesture` です。シナリオが `BAJUTSU_GESTURE_RETRY=1` を設定すると、runner の中でピンチや回転を最大 4 回実行します（打ち直しは最大 3 回です）。ユニット 4 がこのループを廃止するのは、ドライバーの打ち直しが `/gesture` を対象にした後に限ります。つまり、ユニット 1 が、取りこぼされたピンチや回転は取りこぼしの行を出し、ジェスチャーの途中には起きないと示した後です。それまでループは残し、各試行に専用のマーカーを付けます。判定の対象は最後の試行だけです。
2 つ目は runner の割り込み監視です。割り込み監視は、外側の操作の途中でアラートのボタンをタップしたり、
通知バナーをスワイプして消したりします。これらのタッチには、後で述べる専用のマーカーを付けます。

取りこぼしの検出は、上のすべてのエンドポイントが対象です。ドライバーが打ち直すのは離散的なタッチ、つまり
`/tap` と `/systemAlert/tap` だけです。連続的なジェスチャーは、ユニット 1 の結果を待ちます。

ピッカーホイールの調整は、1 回の呼び出しで複数のドラッグを合成することがあります。これは連続的なジェスチャーなので、
上の規則に従います。ユニット 1 が許せば、打ち直しは安全です。調整は目標の値を指定する操作なので、
同じ値への 2 回目の調整は、1 回目で設定した値を変えません。

この仕組みは、XCUITest バックエンドで iOS Simulator を使うすべての実行で、設定なしで動きます。誤った成功は
誰も注意していない場所で起きるので、利用者が有効にするのを待っていては守れません。実機は対象外です。
実機の統合ログは同じ方法ではホストに届かず、実機での取りこぼしも観測されていません。

### runner は合成の前後にマーカーを出す

runner（`BajutsuKit/Runner/Sources/XcuitestElementProvider.swift`）の対象ハンドラーは、タッチの合成を
挟んで 2 行の `os_log` を出します。出力先は専用のサブシステムとカテゴリーです。

```
bajutsu.synthesis begin <nonce>/<id>
bajutsu.synthesis end <nonce>/<id>
bajutsu.synthesis fence <nonce>/<id>
```

`<id>` は runner が持つカウンターで、runner プロセスが生きている間は一意です。各マーカーは、runner が
起動時に生成するノンスを持ちます（`<nonce>/<id>`）。このため、1 つのデバイスセッションの中で環境が runner を
再起動した場合も、前の runner の ID が同じストリームの中で衝突しません。再起動は、クラッシュの後や、
ウォーム再利用の上限を使い切った後に起きます。割り込み監視も、
内側で入れ子になります。対象エンドポイントの応答には、
省略可能な `synthesisId` フィールドを足します（`BajutsuKit/Sources/BajutsuRunner/openapi.yaml`）。
割り込み監視が処理した `labels` と `banners` を返す応答には、`tappedAlerts` と同じく、要素ごとに
対応する配列を足します。対象は `/interruptionPolicy/drain` の応答と、同じ記録を取り込む `tap` と
`resolveAlerts` の応答です。配列には、各要素の元になった割り込み監視のタッチの合成 ID を入れます。
応答にこのフィールドがなければ、タッチは合成されていません（ハンドルが古くなっていた場合など）。
その場合、検証するものはありません。

### ホストは Simulator のログを監視する

XCUITest の環境（`bajutsu/common/platform_lifecycle/environments/xcuitest/`）は、デバイスのセッションごとに
`xcrun simctl spawn <udid> log stream` プロセスを 1 つ起動します。起動するのは runner と同時です。このプロセスは、runner の
サブシステムと `backboardd` の `TouchEvents` カテゴリーに絞り込みます。証跡の `deviceLog` 採取は、同じ
コマンドをすでに組み立てています（`bajutsu/common/evidence/intervals/_functions.py` の `device_log_cmd`）。
パーサーはストリームを小さな表に変換します。表には、合成 ID ごとの開始時刻と終了時刻、取りこぼしの行ごとの
時刻を記録します。

パーサーは、取りこぼしの行を、その時刻にいちばん内側で開いている区間に帰属させます。割り込み監視のタッチが
取りこぼされても、外側の操作が取りこぼしと判定されることはありません。

パーサーは、`backboardd` の次の 3 種類のメッセージを取りこぼしと分類します。

- `unknown digitizer`
- `digitizer event for display <main> from unsupported service`
- `didn't see a previous touch down or range-in event … skipping event`

### 合成ごとの判定

対象エンドポイントが `synthesisId` 付きで応答すると、ドライバーはその ID の判定をモニターに問い合わせます。
モニターはその ID の終了マーカーを待ちます。この待ちは上限付きの条件待ちで、固定時間の待ちではありません。
その後、次の 3 つのいずれかの判定を返します。

| 判定 | 意味 | ドライバーの対応 |
|---|---|---|
| `delivered` | その ID の開始マーカーと終了マーカーの間に取りこぼしの行がなく、その後に終了マーカーより後の時刻を持つ行がすでに届いている。区間の取りこぼしの行が、まだ届く途中にあることはない。 | そのまま進めます。 |
| `dropped` | その区間に、取りこぼしの行が 1 つ以上ある。 | 離散的なタッチは、同じリクエストを打ち直します。連続的なジェスチャーは、ユニット 1 が許さない限り、名指しでステップを失敗させます。 |
| `unverified` | 終了マーカー、またはそれより後の時刻の行が、上限時間内に届かなかった。 | そのまま進め、判定を記録します。 |

runner は終了マーカーの直後にフェンスマーカーを出すので、後の時刻の行は必ず続きます。

`unverified` の判定では、実行は現在と同じ動きをします。ログの流れが止まっても、健全なシナリオが
失敗することはありません。上限時間は、ユニット 1 の実測から決めます。

動いたことのないモニターは別の扱いです。runner は配信を始めるときに起動マーカーを出します。
このマーカーが上限時間内に届かなければ、実行はモニターを名指しして失敗します。原因は、`log stream` プロセスの
起動失敗や終了、または新しい iOS で何にも一致しなくなった述語です。すべてのタッチを `unverified` のまま通すと、
上で述べた誤った成功が黙って戻ってしまいます。

割り込み監視のタッチが取りこぼされても、打ち直しはしません。
バナーのスワイプは、割り込みを処理したと答える前に消えたことを確かめ、消えていなければ処理を断ります。
アラートは、処理したと答えた後も残っていれば、XCUITest が次の操作で割り込み監視を再び呼び出します。
取りこぼされたボタンのタップは、そこで押し直されます。変わるのはレポートだけです。
アラートへの応答やバナーの消去は、その表示に対して割り込み監視が合成したタッチがすべて取りこぼされた場合に限り、
未確認として報告します。こうして実行は、アプリに届いていない応答を「答えた」と報告しなくなります。

### 打ち直し、それでも届かなければ名指しで失敗させる

`XcuitestDriver`（`bajutsu/common/drivers/xcuitest/xcuitest_driver.py`）は、`dropped` と判定された離散的な
リクエスト（`/tap` と `/systemAlert/tap`）を最大 2 回まで打ち直します。打ち直しは元のリクエストと同じ経路を通ります。
`stale` の応答で起きるハンドルの再解決（BE-0289）も、この経路に含まれます。3 回目も `dropped` なら、
新しい `TouchNotDelivered` エラーを送出します。エラーの理由には、セレクターではなく Simulator の競合を書きます。
要素が見つからなかった失敗と取り違えないためです。判定が `dropped` の連続的なジェスチャーは、ユニット 1 が
許さない限り、打ち直さずに、同じエラーをすぐに送出します。

実行の証跡に残る各操作の記録には、その操作がたどった判定を加えます。打ち直したタップは、ふつうのタップでは
なく、取りこぼしの記録とともにレポートに現れます。

### 基本方針との関係

- **AI は判定しない。** 判定は決まったログメッセージと時刻から下し、大規模言語モデル（LLM）は使いません。
- **決定性を優先する。** モニターは終了マーカーという条件を、上限付きで待ちます。上限付きの打ち直しは、
  BE-0289 の古いハンドルに対する上限付きの再試行と同じ形です。
- **アプリに依存しない。** シグナルは `backboardd` と runner から得ます。テスト対象のアプリからは何も得ません。

### 作業分割

1. **CI ホストでマーカーの経路を実測する。** 使い捨ての runner ビルドからマーカーを出します。そのうえで、iOS CI ホストで
   2 つの値を記録します。1 つは、終了マーカーが出てからホストに届くまでの遅れです。もう 1 つは、`backboardd` の行が、それより
   後に出た runner のマーカーよりも遅れて届くことがあるかどうかです。前者で上限時間を決めます。後者で、判定が
   到着順を比べてよいか、時刻を比べる必要があるかを決めます。3 つ目として、`backboardd` の行が自身の時刻に対して
   どれだけ遅れるかと、logd が、それより後の時刻を持つ runner の行より遅れて `backboardd` の行を届けることが
   あるかを測ります。あるならフェンスだけでは区間を閉じられないので、ユニット 3 の前に設計を見直します。
   2 本指のピンチや回転が取りこぼされた場合にも、同じ `backboardd` の行が出ることを確かめます。
   最後に、スワイプ、スクロール、ピッカーのドラッグ、ピンチ、回転で、touch down が届いた後のドラッグの途中に
   取りこぼしが起きうるかを測ります。この結果で、連続的なジェスチャーを打ち直しに加えるかどうかが決まります。
2. **runner のマーカーと `synthesisId`。** 対象のすべてのハンドラーと、割り込み監視のタッチに、起動時のノンスを持つ
   `os_log` のマーカーを足します。終了マーカーの直後にはフェンスマーカーを、配信を始めるときには起動マーカーを出します。
   `openapi.yaml` と対象の応答には、省略可能な `synthesisId` フィールドを足します。
   割り込み監視のタッチの ID は、`labels` と `banners` を返すすべての応答
   （`/interruptionPolicy/drain`、`tap`、`resolveAlerts`）に、要素ごとに対応する配列として足します。
   `BAJUTSU_GESTURE_RETRY` のループが残る間は、その試行ごとに専用のマーカーを付け、応答には最後の試行の ID を入れます。
   ID のカウンターと応答のフィールドは `swift test` で検証します。
3. **ホストのログモニター。** `log stream` プロセスをデバイスのセッションに合わせて起動と停止し、出力を解析して
   判定を返します。取りこぼしの行はいちばん内側の区間に帰属させ、割り込み監視が合成したタッチがすべて取りこぼされた表示への応答は、
   未確認として報告します。起動マーカーが上限時間内に届かなければ、モニターを名指しして実行を失敗させます。
   パーサー、入れ子、3 種類の判定、壊れたモニターは、記録したストリームを使って高速スイートで
   検証します。
4. **ドライバーの打ち直しと `TouchNotDelivered`。** 対象の操作のたびに判定を確かめます。離散的なタッチは最大 2 回まで打ち直し、
   それでも届かなければ新しいエラーを送出します。判定が `dropped` の連続的なジェスチャーは、ユニット 1 が許さない限り、
   同じエラーですぐに失敗させます。判定は操作の証跡に記録します。ユニット 1 が、取りこぼされたピンチや回転はジェスチャーの
   途中に起きないと示した後に限り、`/gesture` にも打ち直しを広げ、`BAJUTSU_GESTURE_RETRY` のループを廃止し、
   `demos/showcase/scenarios/gestures_multitouch.yaml` からその有効化設定とコメントを削除します。それまでループと有効化設定は残します。
   打ち直しの上限とエラーは、偽のモニターを使って高速スイートで検証します。
5. **ドキュメント。** 判定と打ち直し、新しいエラーを `docs/` とその `docs/ja/` ミラーに書きます。XCUITest の
   操作の経路を説明している `DESIGN.md` や `docs/architecture.md` の箇所も更新します。
6. **CI で確かめる。** `app-crash (xcuitest)` と `actuation (xcuitest)` を繰り返し実行します。誤った成功や
   取り違えた時間切れの代わりに、打ち直しが記録されることを確かめます。

## 検討した代替案

| 代替案 | 採らなかった理由 |
|---|---|
| runner が配信を始める前にウォームアップのタッチを打つ | 競合は最初のタッチに限りません。ウォームアップを実装した [#2160](https://github.com/bajutsu-e2e/bajutsu/pull/2160) でも、同じ CI 実行の後半のタップが取りこぼされました。 |
| ホストの時刻で突き合わせ、一定の猶予を置く | 固定の待ちは基本方針 2 に反します。遅いホストでは猶予が切れた後に取りこぼしの行が届き、見落とすこともあります。 |
| ステップの境界でまとめてログを調べる | タッチごとのコストは下がりますが、取りこぼしがわかるのは後続の操作が動いた後です。その時点ではタッチを安全に打ち直せないので、ステップを失敗させることしかできません。 |
| 取りこぼしたら打ち直さずに失敗させる | 誤った成功は消えますが、競合に当たったシナリオはどれもフレークとして失敗し続けます。アプリはキャンセルされたタッチを受け取っているので、打ち直しは安全です。 |
| 取りこぼしを証跡に記録するだけにする | 誤った成功が残ります。取りこぼしに気付けるのは、実行後に証跡を読んだ人だけです。 |
| 設定で明示的に有効にする | 誤った成功は誰も予期しない場所で起きるので、有効にした利用者、つまりすでに競合を知っている利用者しか守れません。 |
| 壊れたモニターを、タッチごとの `unverified` と同じに扱う | 保護がまるごと黙って外れ、それでもすべての実行が成功のままになるためです。 |

- [#2169](https://github.com/bajutsu-e2e/bajutsu/pull/2169) — ユニット 2。runner が合成するすべてのタッチにマーカーを付けるようにしました。マーカーを読むホスト側の
  コードは、まだありません。
  - `BajutsuRunner` パッケージに `SynthesisLedger` を加えました。`begin`、`end`、`fence` の各マーカーと、
    ソケットの bind 後に出す `serving` マーカーを書きます。出力先は unified log で、サブシステムは
    `bajutsu.runner`、カテゴリは `synthesis`、レベルは `.notice` です。`.notice` は永続化されるので、
    後から `log show` で取り出しても残ります。
  - 操作の途中で Swift のエラーや `NSException` を投げたタッチは、終了マーカーまで届きません。
    Swift のエラーには `mark` 自身が `abort` マーカーを書きます。`NSException` には、それを捕まえる
    ハンドラーが、開いたまま残ったマーカー区間ごとに内側から順に `abort` マーカーを書きます。設計に
    このマーカーはありません。書かなければ、ストリームの中でマーカー区間がずっと開いたままになりえます。
  - タッチを合成するエンドポイントの返信は、任意項目 `synthesisId` を持ちます。drain する割り込みの
    記録には `tappedSynthesisIds` と `bannerSynthesisIds` が加わりました。2 つの配列は、それぞれ
    `labels` と `banners` に並行します。
  - CI 診断がゲストの unified log を取り出すとき、runner のサブシステムも選ぶようにしました。マーカーが
    `backboardd` の行と同じ抽出に並ぶので、ユニット 1 は使い捨てのビルドではなく、この診断証跡で
    マーカーの経路を実測できます。
  - 実装は次の 4 点で設計と異なります。
    - ピッカーの調整は、呼び出し全体を 1 つのマーカー区間で囲みます。XCUITest は 1 回の
      `adjust(toPickerWheelValue:)` 呼び出しの中でホイールを動かすので、ドラッグごとには囲めません。
    - `resolveAlerts` 専用の返信はありません。記録は `GET /elements?resolveAlerts=` と
      `/systemAlert/resolve` の返信に載ります。
    - 割り込みの監視だけでなく、解決付きの読み取りもアラートのボタンを押します。その押下も、同じように
      記録へ id を残します。
    - バナーの id のリストは、そのバナーを消したスワイプではなく、runner がそのバナーに向けて合成した
      スワイプを示します。スワイプの後もバナーが残り、やがて自然に消えた場合も、リストにはスワイプの
      id が入ります。runner がスワイプしなかったバナーのリストは空です。

  - 回答済みの表示をもう一度押すと、その表示の記録がまだ drain されていなければ、記録へ id を足します。
    drain の後に押した場合は、足す先の記録がありません。この欠けが「未確認」の判定に響くかどうかは、
    ユニット 3 で決めます。
