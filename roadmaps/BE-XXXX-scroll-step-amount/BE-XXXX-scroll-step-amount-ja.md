## はじめに

`scroll` アクションに `amount` という省略可能なフィールドを追加します。`amount` は、1 回の
スクロールステップがビューポートのうちどれだけの割合を進むかを指定します。`swipe` と `drag` は、
すでに自分自身のジェスチャ向けに同じ名前のフィールドを持っています。画面が速くスクロールする、
あるいは対象が通り過ぎやすいとあらかじめわかっている作者は、ステップ幅を直接小さく指定できる
ようになります。対象を一度通り過ぎてしまってから、スクロールループ自身のリカバリだけに頼る必要は
なくなります。`amount` を省略した場合、挙動は今までと変わりません。ループはこれまでどおり
デフォルトのステップ幅から始まり、通り過ぎを検知したときだけそのステップを縮めます。

## 動機

[BE-0326](../BE-0326-scroll-to-element/BE-0326-scroll-to-element-ja.md) は
`scroll: { to: <selector> }` を追加しました。これは、ビューポートの 0.6 という固定のステップ幅で
スクロールし、UI 要素ツリーを再取得し、対象の
[selector](../../docs/ja/glossary.md#シナリオのオーサリング)がビューポート内に frame の中心を
持つ状態で解決されたら停止する、境界付きの非慣性なループです。ステップ幅は
[`bajutsu/orchestrator/actions/handlers/scroll.py`](../../bajutsu/orchestrator/actions/handlers/scroll.py)
のモジュール定数 `_STEP_FRACTION` であり、`scroll` シナリオステップのどのフィールドからも
この定数には届きません。そのため、どの画面をスクロールする呼び出しも同じステップ幅で進みます。

[BE-0329](../BE-0329-scroll-observed-motion-decisions/BE-0329-scroll-observed-motion-decisions-ja.md)
は、大きなステップが 2 回のクエリの間で対象をビューポートの外まで運んでしまい、シナリオがループの
報告どおり対象に到達できなくなる場合があることを明らかにしました。その修正は事後対応です。ループは
連続する 2 回の読み取りを比較し、直前の読み取りと共通する要素が 1 つもないと判断すると、ステップを
半分に縮め、`swipe` 自身のデフォルトの移動量である 0.125 を下限として、通り過ぎた範囲を見るために
1 回だけ逆方向にステップを戻します。このリカバリが働くには、まず通り過ぎが起きている必要があります。
リカバリの各ステップも、その呼び出しが持つ `maxScrolls` の予算を消費します。そのため、ステップが
十分小さくなるまでに何度も半減する必要がある画面では、後続のステップに残る予算が減ります。下限に
達したステップがそれでも直前の読み取りと何も共有しなければ、その呼び出し全体が、対象に到達した
のではなく通り過ぎを名指しして失敗します。

どのバックエンドについても、1 ステップが実際に完全な非慣性かどうかは、それ自体まだ確定していません。
iOS では、常駐ランナーが指を離す前に、固定 0.3 秒だけ接触を静止させています
（[`BajutsuKit/Runner/Sources/XcuitestElementProvider.swift`](../../BajutsuKit/Runner/Sources/XcuitestElementProvider.swift)
の `scrollSettleDuration`）。これは、スクロールビューが実際に止まったことを確認する条件待ちでは
ありません。この固定のホールドが `UIScrollView` 自身の減速より常に長く続くかどうかは、オンデバイスの
物理挙動にかかわる問いであり、ソースを読むだけでは答えが出ません。それを裏付ける計測もまだありません。
driver conformance suite の重なりの検査
（[BE-0329](../BE-0329-scroll-observed-motion-decisions/BE-0329-scroll-observed-motion-decisions-ja.md)）
も、わずかなドリフトだけでは検知できません。この検査が確認するのは、1 ステップの前後で共有される
要素があるかどうかだけであり、領域がステップの終えた位置でぴったり止まったかどうかではないからです。
より小さい `amount` は、原因が何であれ、このようなドリフトが通り過ぎうる範囲を狭めます。それは、
検知済みの通り過ぎからの回復が及ぶ範囲を狭めるのと同じことです。

行の密度が高い、あるいは静止時にも操作できる状態を保つ必要があるコントロールを持つなど、画面に
小さいステップが必要だとあらかじめわかっている作者にも、今日それを伝える手段がありません。小さい
ステップに至る唯一の経路は上記の事後的な半減であり、その経路はループが 0.6 で一度通り過ぎたあとに
しか開きません。本項目は、直接の経路を追加します。`scroll` シナリオステップの省略可能なフィールド
である `amount` が、`_STEP_FRACTION` の代わりにループの開始ステップ幅を指定します。事後対応の
リカバリはそのまま変わらず動作します。`amount` がどこから始まっていても、ループはそこからさらに
半減できます。

この変更が入ると、テストでフィールドの効果を直接示せます。`FakeDriver` 上で、デフォルトの 0.6
ステップでは 2 回の読み取りの間に共有される要素が何もなくなるよう組んだスクロールでも、`amount`
を、どの読み取りも対象を飛ばさない大きさまで小さくすれば、BE-0329 の巻き戻しリカバリを一度も
起動せずに対象へ到達します。通常の使い方でフリングする（慣性で飛ばす）ことが確認されたバックエンドは
現在ありません。これは BE-0329 自身が記録している事実です。そのため、`amount` を、今日実際に
失敗しているシナリオへの対処としてここに書くわけではありません。現時点で具体的な根拠となるのは、
前段で述べた iOS の未確定の論点です。残留ドリフトを疑う画面には、その大きさがどうであれ、対象を
運びうる範囲が小さくなるだけのステップ幅を与えられます。

## 詳細設計

### `amount` フィールド

```yaml
- scroll:
    to: { id: log.row.42 }
    amount: 0.2   # デフォルトの 0.6 ではなく、1 ステップでビューポートの 0.2 だけ進む
```

`amount` は省略可能です。範囲は `0 < amount ≤ 1` で、`swipe` と `drag` が自分自身の `amount`
フィールドですでに検証しているのと同じ範囲、同じ単位（スクロール軸に沿ったビューポートの割合）です。
省略した場合、ループは現在のデフォルトである 0.6 のままです。

この範囲は 0.6 で止まっていないため、`amount` は今日のループより大きいステップも要求できます。
[BE-0326](../BE-0326-scroll-to-element/BE-0326-scroll-to-element-ja.md) の *検討した代替案* は、
大きいステップが通り過ぎを再び招くことを懸念して、まさにこのノブを見送っていました。
[BE-0329](../BE-0329-scroll-observed-motion-decisions/BE-0329-scroll-observed-motion-decisions-ja.md)
は、デフォルトのステップに限らず、どのステップ幅についてもその隙間をふさいでいます。直前の読み取り
と何も共有しないステップをループがすでに検知して反応する仕組みは、そのステップをどの `amount` が
生み出したかによりません。1 に近い `amount` も、`_STEP_FRACTION` から生じた大きなステップと同じ
リカバリに捕まって縮められるのであり、通り過ぎが見逃されるわけではありません。

`amount` が指定するのは、ループの開始ステップ幅だけです。
[BE-0329](../BE-0329-scroll-observed-motion-decisions/BE-0329-scroll-observed-motion-decisions-ja.md)
のリカバリは変わりません。通り過ぎを検知すると、ループは開始位置によらず、現在のステップを 0.125
という下限に向けて半減し続けます。`amount` がその下限以下であれば、リカバリが縮める余地はもう
残っていません。そのため、ループが最初に通り過ぎを検知した時点で、より小さいステップで対象に到達
するのではなく、通り過ぎを名指しして呼び出し全体が失敗します。そこまで小さい `amount` を指定する
作者は、そもそもリカバリを必要としないほど小さいステップを選んでいることになります。下限そのものを
`amount` に連動させず固定のままにする理由は、*検討した代替案* に記録します。

### 作業分解（`MECE`）

Mutually Exclusive, Collectively Exhaustive（`MECE`、互いに排他的かつ全体として網羅的）な作業の
単位は次のとおりです。

1. **シナリオのスキーマ。**

   [`bajutsu/scenario/models/actions.py`](../../bajutsu/scenario/models/actions.py) の `Scroll`
   に `amount: float | None = None` を追加します。`Scroll` には今日バリデータがなく、
   `max_scrolls` は `Field(gt=0)` で直接制約されています。`amount` も同じやり方で
   `Field(gt=0.0, le=1.0)` として制約するか、`Swipe` と `Drag` が自分自身の `amount`
   フィールドに対してすでに行っている `0 < amount ≤ 1` の検証にならう小さなバリデータを
   追加します。

2. **ハンドラの配線。**

   [`bajutsu/orchestrator/actions/handlers/scroll.py`](../../bajutsu/orchestrator/actions/handlers/scroll.py)
   の `_do_scroll` から `scroll_to_target` まで `s.amount` を通します。ループの
   `fraction = _STEP_FRACTION` という初期化を
   `fraction = amount if amount is not None else _STEP_FRACTION` に変えます。`fraction` を
   `_MIN_STEP_FRACTION` に向けて縮めるリカバリの経路は、今までと同じ変数を読み、変わりません。
   変える必要がある行が1つあります。下限での通り過ぎメッセージは `_MIN_STEP_FRACTION` を直接
   名指ししていますが、下限を下回る `amount` は縮められる前にその下限に達するため、メッセージは
   その定数ではなく、失敗したステップが実際に取った `fraction` を名指しする必要があります。

3. **テスト。**

   `FakeDriver` を使い、次を確認します。デフォルトより小さい `amount` を指定した呼び出しが、
   デフォルトのステップでは通り過ぎてしまう対象に、リカバリの経路を一度も通らずに到達すること。
   `amount` を省略した呼び出しが今日とまったく同じ挙動になること（リグレッションの防止）。下限以下の
   `amount` を指定した呼び出しが、最初に検知した通り過ぎでさらに縮めるのではなく、通り過ぎを
   名指しして失敗すること。スキーマのテストでは、既存の `swipe`/`drag` の amount テストにならって、
   新しいフィールドの範囲検証を確認します。

4. **ドキュメント。**

   [`docs/scenarios.md`](../../docs/scenarios.md) とその日本語訳に、`direction`、`within`、
   `maxScrolls` と並べて `amount` を記載します。デフォルト値（0.6）と単位（ビューポートに対する割合）
   を明記し、`swipe` と `drag` 自身の `amount` を、共通する規約として相互参照します。

### プライムディレクティブの遵守

- **AI は判定しない。**

  `amount` はシナリオの作者が与える数値であり、ループは今日の `max_scrolls` と同じ方法でこれを
  読みます。このフィールドの経路にモデルの呼び出しは入りません。

- **決定性が第一。**

  このフィールドが変えるのは、すでに `maxScrolls` で上限が定められ、各ステップのあとに再取得が
  行われているステップの大きさだけです。固定の `sleep` は追加しません。新しい失敗の種類も
  追加しません。作者が指定した `amount` がリカバリの下限以下であれば、デフォルトのステップが
  その下限ですでに出しているのと同じ通り過ぎの失敗に達します。名指しするのは、デフォルトの値
  ではなく、実際に実行されたステップです。

- **アプリに依存しない。**

  `amount` は `scroll_to_target` という単一のループを通じてすべてのバックエンドに届きます。値に
  よって分岐するバックエンドはありません。

## 検討した代替案

- **`amount` にリカバリの下限も指定させる。**

  却下しました。下限が存在するのは、動きをまったく示せないほど小さいステップが、際限なくゼロへ
  向かって縮み続けるのではなく、その場ではっきりと失敗するようにするためです。下限を `amount` に
  連動させると、非常に小さいステップを要求した作者が、その下限自体もさらに下げてしまうことになり、
  下限が果たしている役割が失われます。下限は `amount` の値によらず、`swipe` 自身のデフォルトの
  移動量に固定したままにします。下限以下のステップを要求した作者は、今日ループがその下限で出して
  いるのと同じ、通り過ぎによる即座の失敗を受け入れることになります。

- **フィールドを追加する代わりに `_STEP_FRACTION` 自体を小さくする。**

  却下しました。グローバルなデフォルトを小さくすると、小さいステップを必要としないすべての
  `scroll` 呼び出しを遅くしてしまいます。
  [BE-0329](../BE-0329-scroll-observed-motion-decisions/BE-0329-scroll-observed-motion-decisions-ja.md)
  はすでに、通常のケース向けに 0.6 を選んでいます。これは、何でもない画面で事後対応のリカバリを
  招くことなく、2 回の読み取りの間に実質的な重なりを残すのに十分な大きさです。本項目は加算的な
  変更であり、`amount` を省略するシナリオを変えることはありません。

- **`amount` をビューポートの割合ではなく、絶対距離（ポイントやピクセル）で表す。**

  `swipe` と `drag` がすでにこれを却下しているのと同じ理由で却下しました。絶対距離は、小さい
  スマートフォンの画面と、タブレットやデスクトップのブラウザウィンドウとで意味が変わってしまいます。
  そのため、あるデバイスで調整したシナリオが、別のデバイスでは通り過ぎたり届かなかったりしかね
  ません。ビューポートの割合であれば、どの画面サイズでも同じ意味で読めるため、対象を横断してこの
  アクションを移植可能なまま保てます（プライムディレクティブ 3）。

- **`amount` に 1 未満の上限（例えばデフォルトの 0.6）を設け、BE-0326 がこのノブを見送る
  理由になった通り過ぎのリスクを再び招かないようにする。**

  却下しました。
  [BE-0329](../BE-0329-scroll-observed-motion-decisions/BE-0329-scroll-observed-motion-decisions-ja.md)
  の検知と回復のループは、デフォルトのステップに限らず、どのステップについてもすでにそのリスクを
  抑えています。直前の読み取りと何も共有しないステップは、それを生み出した `amount` が何であれ、
  同じ半減と巻き戻しのリカバリを起動します。上限を設けると、画面のスクロールが普段より遅く、
  1 回の大きなステップを望む作者の正当な用途をふさぐことになり、その一方でリカバリがすでに
  与えている保護以上のものは何も加えません。
