## はじめに

`${secrets.X}` を環境変数から解決して入力に使用し、その実値を証跡で自動的にマスクします。マスクは、既存の `redact` を入力値まで拡張するものです。シークレットは config の `secrets:` で宣言します。

## 動機

実際のフローには、本物の認証情報が必要です。API トークン、パスワード、ワンタイムのログインなどです。これらをシナリオファイルに直書きすると、リポジトリにアクセスできる誰もがそのシークレットをレビューでき、コミット履歴に漏れます。さらに悪いことに、同じ値が証跡（ログ、要素ツリー、ネットワーク交信、manifest）にも現れます。そして、ディスクにコピーされ、レポートで共有されてしまいます。

そこで、ランタイムでステップにシークレットを供給する手段が必要です。値をシナリオに書いてはならず、取得した証跡に残してもなりません。

## 詳細設計

シークレット変数名は、config の `secrets:` 下に宣言します。環境変数名のリストです（`bajutsu/config.py`）。run の開始時、CLI は宣言された各名 `X` をプロセス環境から解決し、束縛 `secrets.X → <値>` を作ります（`bajutsu/cli.py`）。シナリオファイルが持つのは常にトークン `${secrets.X}` だけで、値ではありません。

ロード時に展開される `${params.*}` / `${row.*}` とは異なり、`${secrets.X}` はアクション時に run ループが解決します。`_interp_step`（`bajutsu/orchestrator/`）が、アクション実行の直前に、シークレット束縛を置換したステップのコピーを作ります。実値を見るのは、ライブのドライバだけです。元のステップは manifest とレポートのために保持されるので、そこにはトークンが記録されます。トークンを含まないステップでは、コピーを省く高速なサブストリング／トークンチェックが入ります。

マスキングは、既存の `redact` の仕組みを再利用して拡張します（`bajutsu/redaction.py`）。`Redactor` はシークレットの実値（`values=secret_values`）で構築され、それらが現れる箇所すべてをマスクして `[REDACTED]` に置き換えます。対象は、フリーテキスト（device log や app trace）、要素ツリー、ネットワーク交信です。長い値から先にマスクするため、ある値が別の値の部分文字列であっても、部分的な漏れは起きません。これは値ベースのマスキングです。アプリがログやレスポンスに反映し返したシークレットも捕捉でき、キー名ベースのマスキングだけでは見逃すケースを拾います。

最後の安全網として、レポート書き出し後に `_scrub_secret_values`（`bajutsu/runner/`）が動きます。全シークレットの実値を、run レベルの成果物（`manifest.json`、`junit.xml`、`report.html`、`scenario.yaml`）に対して走査します。アサーションの期待値／実値といった結果テキストに到達したシークレットを、これで捕捉します。

画像（スクリーンショット／動画）はテキストマスクできないため、そのまま残ります。画面に表示されるシークレットを撮らないことは、作成者の責任です。

これらすべてに LLM は関与しません。解決もマスキングも決定的であり、シークレットが run/CI の判定を変えることはありません。

## 検討した代替案

**シナリオにシークレットの値を直書きする（あるいはリテラルの別ファイルを置く）。** 不採用です。値は依然としてコミットされ、レビューでき、証跡にもコピーされます。環境から解決すれば、値はバージョン管理から完全に外れ、ファイルにはトークンだけが残ります。

**キー名ベースのマスキングのみ（設定したヘッダ／フィールド／ラベルでマスク）。** 単独では不採用です。予期しないキーの下にアプリが出すシークレットや、ログ行のより大きな文字列に埋め込まれたものを、捕捉できません。実値が現れる箇所すべてをマスクすれば、その隙間を塞げます。一般的な（シークレットでない）ケースには、キー名ベースのマスキングが引き続き適用されます。

**暗号化されたシークレットストア／vault 連携。** 範囲外として不採用です。環境は認証情報の慣例的で CI ネイティブな経路であり、追加の依存やデーモンを必要としません。vault は後から同じ環境変数を埋める形で組み込めます。シナリオの表層を変えずに済みます。
