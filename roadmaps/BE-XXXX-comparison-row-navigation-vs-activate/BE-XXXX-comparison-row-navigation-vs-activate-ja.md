## はじめに

`bajutsu serve` の Web UI にある比較ビューは、ハブに登録された複数のプロジェクトを横に並べて
順位づけする画面です。いまは行をクリックするとそのプロジェクトが有効化され、デプロイ全体が読む
config が張り替わります。本項目は、この1つの操作を2つに分けます。行のクリックは、選んだ
プロジェクトの実行履歴を読み取り専用で開く操作にします。いまの行に欠けているキーボード操作でも、
同じ画面へ入れるようにします。デプロイの張り替えは、確認をともなう行ごとのボタンへ移します。使う権限のない読み手には、押した
あとではなく押す前にそのことを伝えます。あわせてタブの名前を改め、同じサーバが `/metrics` で
公開する Prometheus 向けのエンドポイントと取り違えられないようにします。

## 動機

移動に見える操作が書き込みを行ってはいけません。比較ビューの行には、ポインタの形が変わる以外に
操作を示すものが何もないので、合格率で順位を眺めている読み手が行のクリックを「この
プロジェクトを見せてほしい」と読むのは自然です。実際にそのクリックが送るのは
`POST /api/projects/<name>/activate` で、ハブの有効なプロジェクトを張り替えます。張り替わるのは
サーバ側の状態であり、そのデプロイにつながっているすべてのタブが共有します。閲覧者ごとの設定では
ありません。順位を眺めていただけの人が、同僚の Run タブが対象にするプロジェクトを変えてしまい
ます。書き込みを予告するものは何も押していません。

同じ行に、ポインタなしでは到達できません。行は click のリスナーを持つだけの素の表の行です。
`tabindex`、役割、キー操作のハンドラのどれも持たないので、キーボードだけの操作では飛ばされ
ます。
比較ビューが提供するはずの詳細への入口が、一部の読み手にだけ開いています。

小さな引っかかりが2つ付いてきます。1つは、自分が有効化してよいのかどうかを知る手立てが
どこにもない点です。UI は転送層の `forbidden` を事後にそのまま出すだけで、何を拒まれたのかも、
何があれば通るのかも読み取れません。
もう1つは、タブの名前が `/metrics` の Prometheus 向けエンドポイントと重なる点です。ビューの
見出しはすでに `Project comparison` を名乗っています。同じデプロイの中で、無関係な2つの面が
同じ言葉で呼ばれています。

本項目が入ったあとは、読み手は比較ビューを開き、キーボードですべての行をたどり、どの
プロジェクトの履歴へも入れます。そのあいだ、ハブの有効なプロジェクトは動きません。有効な
プロジェクトを変えるには、ボタンを押して確認に答える必要があります。変える権限を持たない
読み手には、ボタンが理由を添えて無効の状態で見えます。

## 詳細設計

### 1. 行からの読み取り専用の詳細

行をクリックすると、比較ビューの中にプロジェクトごとのパネルが開きます。パネルには、選んだ
プロジェクトの実行履歴が新しい順に並び、各実行の合否と対象シナリオが出ます。パネルは読み取り
専用で、順位の一覧へ戻る操作を持ちます。

データは `GET /api/projects/{name}/runs` から取ります。このエンドポイントはプロジェクトハブが
すでに提供していて、UI のどこからも使われていません。返る実行サマリの形は Replay タブの履歴が
描いているものと同じなので、パネルは新しい形を定義せずにそれを再利用します。サーバ側には経路、
引数、処理のいずれも足しません。

### 2. 明示的な有効化の操作

有効ではない行に `Activate` ボタンが付きます。有効な行はボタンを持たず、`active` の印だけを出し
ます。Projects ページが2つの状態を描き分けている形にそろえます。ボタンを押すと確認が出ます。
確認の文には、対象のプロジェクト名と、デプロイの config が全員の分まで張り替わるという結果を
書きます。確認に答えた押下だけが、既存の有効化の経路を呼びます。有効化そのものは変えません。
同じリクエストを送り、同じ管理者向けの制限を受け、config 表示と切り替え欄を同じように取り直し
ます。

### 3. 押す前に誰が使えるかを告げる操作

有効化はサーバ側では管理者だけの操作のままです。読み手はそれを、拒否ではなく起動時の読み取りから
知ります。`GET /api/config` はすでに capability ブロックを載せています。この呼び出し元に対して
このデプロイが何を提供できるかを報告するもので、提供できない項目には、無効の操作が示すための理由が
添えられます。ここに `activate` の項目を `capture` と `orgs` の隣へ足します。転送層が有効化の経路へ
当てているのと同じ `forbidden_for_role` で判定するので、この報告とエンドポイントの答えは食い違え
ません。押す権限のない読み手には、ボタンがその理由を添えて無効の状態で描かれます。capability
ブロックは報告するだけで、何も遮りません。エンドポイントは自分で拒み続けます。

拒否はその次の線として残ります。起動後に役割が変わった場合のためです。どちらの転送層も、役割で
弾いたリクエストには 403 と `{"error": "forbidden"}` を返します。共有の切り替えヘルパは、この
1つの値を管理者が必要だと述べる文へ読み替えます。ゴミ箱の完全削除がすでに自分の 403 を読み替えて
いるのと同じ形です。読み替えを共有のヘルパに置くので、ヘッダのプロジェクト切り替えと Projects
ページの `Switch` ボタンも同じ文を出します。この2本立ては、Orgs ページが同じ問いをすでに
扱っている形と同じです。

### 4. キーボードからの操作

詳細を開く操作は、行の名前セルに置いた本物の `button` です。そのセルがもともと持っていた見た目を
そのまま着せ、フォーカスの表示を足します。ボタンである以上 Enter と Space は最初から付いてくるので、
独自のキーハンドラはいりません。行のそれ以外の場所のクリックは、これまでどおりポインタ向けの
近道として残します。

`tr` 自体に `tabindex` とボタンのロールを与えれば行数は減りますが、2つの意味で誤った取り引きに
なります。1つは、行が持つ表としての意味を上書きしてしまう点です。このビューが見せようとしている
順位そのものを、スクリーンリーダーが行とセルの単位でたどれなくなります。もう1つは、行の中にある
有効化の操作を Accessible Rich Internet Applications（ARIA）のボタンの内側へ入れ子にしてしまう
点です。ARIA の仕様はそれを禁じています。
はじめから操作である要素を使えば、どちらも起きません。

### 5. 重ならない名前

タブを `Comparison` にします。衝突していたエンドポイントの側ではなく、開くビューの側から採った
名前です。見出しはすでに `Project comparison` を名乗っているので、そこには同じサーバが公開する
Prometheus 向けのエンドポイントとは別物だと断る一文を添えます。要素の id と `data-testid` の値は
いまの名前のままにします。既存のテストとビュー切り替えのコードが握っている手がかりであり、
読み手の目に触れない面を書き換えても揺らしただけになるからです。

### 6. テスト

このリポジトリは JavaScript のテスト実行環境を持たないため、serve の UI のモジュールは、配信
された本文を取得して文字列を確かめる構造テストで固定しています。既存の比較ビューのテスト
モジュールに、分割後の形を確かめるケースを足します。行のハンドラから有効化の経路へ届かないこと、
行に表としての意味が残ることを確かめます。キーボードから到達できる名前セルのボタン、有効化の操作
とその確認が配信されることも確かめます。拒否が管理者向けの文へ読み替えられること、新しい名前が
届くことも同様です。いまのディープリンクを固定しているテスト
は残さずに置き換えます。本項目が取り除く動作を固定しているテストだからです。

## 検討した代替案

- **`/stats` にプロジェクトの絞り込みを足す。** 却下しました。`/stats` は1つの組織の実行履歴
  全体を集計する画面で、プロジェクトを指定する引数を持ちません。ここを詳細の入口にするには引数を
  足すことになります。[BE-0226](../BE-0226-cross-project-metrics-dashboard/BE-0226-cross-project-metrics-dashboard-ja.md)
  はこのダッシュボードをその場で広げる案をすでに検討し、比較は1つの設定のダッシュボードを
  絞り込んだものではなく独立した面だという理由で却下しています。プロジェクトごとの実行履歴の
  エンドポイントを使えば、サーバへ手を入れずにその理由を保てます。
- **有効化のディープリンクを残し、確認だけ足す。** 却下しました。行のクリックに確認を挟むと、この
  ビューが本来提供する操作をするたびに読み手がダイアログを閉じることになります。しかも読み取り
  専用の経路は依然としてありません。問題は移動と書き換えが1つの操作を共有している点にあり、
  ダイアログはそこを分けません。
- **権限のない読み手から有効化の操作を完全に隠す。** 却下しました。上の設計が読む capability
  ブロックは、無効にするのと同じ手軽さで隠すこともできます。つまりこの選択は、サーバが何を報告
  できるかではなく、何が読み手のためになるかの問題です。消えた操作は、その機能が存在するのか
  どうかという問いを読み手に残します。理由を添えて無効になっている操作は、その問いに答えます。
  `serve_capabilities` 自身が述べている立場、すなわち使えない操作はただ灰色になるのではなく理由を
  述べるべきだという立場に、本項目は従います。
- **拒否の文言だけを出し、ボタンは全員に同じ形で描く。** 却下しました。サーバ側の追加はいりま
  せんが、押して確認に答えたあとで初めて読み手に伝わります。確認は操作をいったん止めるために
  あるのですから、伝える順序が逆です。ただし拒否の読み替えそのものには価値があり、起動後に役割が
  変わった場合のために上の設計へ残します。
- **管理者向けの読み取りを叩いて可否を推し量る。** 却下しました。ある権限の有無を別の
  エンドポイントの答えから推測する形だからです。capability ブロックは有効化の経路が当てている
  判定そのものを報告するので、推測する余地がありません。
- **行のクリックをやめ、ボタンだけ残す。** 却下しました。移動に見える書き込みという問題は消え
  ますが、比較ビューを入口たらしめていた詳細への導線まで消えます。得るものがないまま失うだけに
  なります。
