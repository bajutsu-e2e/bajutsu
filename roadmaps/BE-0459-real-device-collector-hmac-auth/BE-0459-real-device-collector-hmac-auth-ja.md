## はじめに

iOS の実機では、アプリが Bajutsu のネットワークコレクターへ平文の HTTP（Hypertext Transfer
Protocol）で報告します。どのリクエストにも、実行ごとの共有トークンが Bearer ヘッダーとして載ります。
その通信を読める者はトークンを写し取れます。トークンを得た者は、捏造した通信記録を実行の証跡へ書き込めます。

本項目は、トークンを両端に保持したまま経路から外します。アプリは各リクエストに、トークンを鍵とする
HMAC（keyed-hash message authentication code、鍵付きハッシュによるメッセージ認証コード）で署名します。
コレクターも応答に同じ方式で署名します。そのうえで、ループバックの外に bind したコレクターは Bearer
ヘッダーを一律に拒否します。ループバックの経路（iOS Simulator と Android）は変更なしで動き続けます。

## 動機

コレクターは、実行中のアプリから報告を受け取るホスト上の HTTP サーバーです。報告の中身は、ネットワーク
通信の記録、画面遷移、制御チャネルの通信です。
[BE-0115](../BE-0115-inprocess-collector-auth/BE-0115-inprocess-collector-auth-ja.md) は、コレクターに
実行ごとのトークンを導入しました。アプリはそのトークンを `Authorization: Bearer <token>` として送ります。
BE-0115 は、コレクターがループバックだけで待ち受けることを前提にしていました。ループバック上でトークンを
読めるプロセスは、もともと同じマシンを共有しています。

実機向けのホストチャネルの項目は、この前提を意図して崩します。その実装 PR
[#2143](https://github.com/bajutsu-e2e/bajutsu/pull/2143) によって、iPhone がホストへ報告できるように
なりました。iPhone は Mac とループバックを共有しません。そこでコレクターはすべてのインタフェース（`::`）に
bind し、アプリは起動時に渡されたホストアドレスでコレクターへ到達します。その結果、トークンは平文の
ままネットワークを渡ります。渡るリクエストは 2 種類あります。

- **プローブ。** アプリはコレクターを選ぶ前に、トークン付きの `GET /ping` を候補アドレスすべてへ同時に
  送ります。アドレスを明示していない場合、候補はホストのインタフェースにある経路可能なアドレスすべてです。
  そのため、トークンはどのコレクターのものでもないアドレスへ届くことがあります。
- **以降のすべてのリクエスト。** 報告、`GET /commands` の取り出し、確認応答のたびに、選ばれた経路の上で
  Bearer ヘッダーが繰り返されます。

これらのリクエストを 1 つでも読んだ者は、実行が終わるまでトークンを握ります。そこから 3 つの脅威が
生じます。1 つ目は、Bajutsu が提供する決定的な合否判定そのものを壊します。

| 脅威 | 手口 | 実行への影響 |
|---|---|---|
| 証跡の偽造 | 盗んだトークンで、捏造した通信記録や画面遷移を POST する | 実際には起きていない通信によって、`request` や `response` のアサーションが成功または失敗します |
| コマンドの横取り | アプリより先に `GET /commands` を取り出す | 制御チャネル（[BE-0365](../BE-0365-in-app-control-channel/BE-0365-in-app-control-channel-ja.md)）のコマンドがアプリに届かず、そのステップはタイムアウトします |
| 経路上の改ざん | 経路上で `/commands` の応答を書き換える | シナリオが宣言していないスタブ表やトグルを、アプリが適用します |

3 つ目の脅威にはトークンが要りません。応答の中に、コレクターが書いたことを証明するものが何もないため、
経路上の者が自由に書き換えられます。

実機向けのドキュメントは緩和策を示しています。共有ネットワークでは、`BAJUTSU_HOST_ADDRESS` を
CoreDevice トンネルのアドレスに固定する、というものです。固定によって経路は狭まりますが、その経路を
読める者には依然としてトークンが見えます。また、チームが管理しないネットワークでは固定も役に立ちません。
Amazon Web Services（AWS）の Device Farm では、予約したデバイスはファームのネットワーク上にあります
（[BE-0238](../BE-0238-ios-device-cloud-execution/BE-0238-ios-device-cloud-execution-ja.md)）。

観察できる成果は 3 つです。いずれも、USB で接続した iPhone で showcase の `network_mock` シナリオを
実行したときに成り立ちます。

- ホスト上で取得した実行のパケットキャプチャには、どのリクエストにもトークンの値が現れません。
- そのキャプチャから再送した報告は 409 を受け、`network.json` に何も加えません。
- ネットワークに bind したコレクターへ Bearer ヘッダーを提示したリクエストも、401 を受けます。

同じシナリオは、Simulator と Android でも変更なしに成功します。

## 詳細設計

### 本項目が守るものと、範囲外とするもの

想定する攻撃者は、デバイスとホストのあいだの HTTP 通信を読み、再送し、書き換えられます。候補アドレスの
1 つを攻撃者が保持している場合も想定します。本設計は次の 4 つの性質を守ります。

- **トークンが秘密に保たれます。** リクエストと応答のどちらにも、トークンやトークンを明かす値は載りません。
- **リクエストが本物です。** コレクターは、トークンの保持者からのリクエストだけを受け付けます。
- **リクエストが新しいものです。** コレクターは、一度受け付けたリクエストを拒否します。
- **応答が本物です。** アプリが信頼する `/commands` とプローブの応答は、トークンの保持者が書いたものです。
  しかも、まさにそのリクエスト向けに書かれた応答だけを信頼します。

本文の秘匿は範囲外とします。記録した通信の本文は、引き続き平文で流れます。本文の秘匿には TLS（Transport
Layer Security）が向いており、「検討した代替案」で条件付きの後続として残します。

可用性も範囲外とします。経路上の者は、どのリクエストも落としたり遅らせたりできます。リクエストを読んだ者は、
その写しをアプリより先にコレクターへ届けられます。いずれの場合も、そのリクエストに依存するステップは既存の
タイムアウトで明示的に失敗し、偽造した通信記録やコマンドが合否判定に届くことはありません。そのため
「コマンドの横取り」の脅威は、消えるのではなく、この明示的な失敗にまで縮小します。

トークンの受け渡し方法も変えません。トークンは起動時の環境変数（`BAJUTSU_COLLECTOR_TOKEN`）でアプリに
届きます。`xcodebuild` はその環境変数を、Xcode 自身のペアリング済みデバイスとの接続（USB、または CoreDevice
トンネル）の内側でデバイスへ渡します。その接続は報告が使う平文の HTTP ではなく、報告のリクエストに
トークンが現れることはありません。

### リクエストへの署名

BajutsuKit は、コレクターへ送るすべてのリクエストに署名します。

- 通信記録と画面遷移の報告の POST
- `GET /commands` と `POST /commands/ack`
- `GET /ping`

リクエストは次のヘッダーを 1 つ持ちます。

```
Authorization: Bajutsu-HMAC-SHA256 nonce=<nonce>, signature=<signature>
```

- `nonce` はリクエストごとに新しく生成する 16 バイトの乱数で、パディングなしの base64url で表します。
- `signature` は `HMAC-SHA256(token, canonical)` で、パディングなしの base64url で表します。
- `canonical` は、次の 5 行をこの順に改行でつないだ文字列です。
  1. リテラルの `bajutsu-request-v1`
  2. HTTP メソッド
  3. リクエスト行に載ったままのパス（パーセントエンコードは保ち、クエリ文字列は除く。URL にパスがなければ `/`）
  4. ノンス
  5. 本文の SHA-256 ダイジェストを小文字の 16 進で表したもの（GET では空文字列のダイジェスト）

正規形にはホストとポートを含めません。コレクターはすべてのインタフェースに bind しており、リクエストが
どのアドレス宛てだったかを確かめられません。署名にアドレスを含めても、検査できるものは増えません。
プローブは、ほかのリクエストと同じく、候補ごとに別のノンスで `GET /ping` に署名します。複数の候補が
1 つのコレクターに届くことがあります。たとえば Wi-Fi 経由と CoreDevice トンネル経由です。ノンスを共有
すると、コレクターは先に届いた写しを受け付けて残りを拒否します。候補はホストが決めた優先順位ではなく、
到着順で決まってしまいます。先頭のバージョン行は、
将来の方式が正規形を変えても、どちらの側も読み違えないようにするためのものです。

コレクターはまずヘッダーを検査します。ヘッダーが欠けているか形式が不正な場合は、本文を読む前に 401 を
返します。すでに受け付けたノンスには、やはり本文を読む前に 409 を返します。この 2 つの応答はリクエストの
本文を読まずに残します。そのため、現在の Bearer の拒否と同じく、どちらも `close_connection` を設定します
（`bajutsu/common/evidence/network/_functions.py`）。本文を読み飛ばした応答は再利用された接続の同期を崩します。
設定しておけば、ハンドラーがどのプロトコルのバージョンで話しても、拒否の経路は安全なままです。次に本文を読み、署名を計算し直し、
定数時間で比較します（`hmac.compare_digest`）。一致しなければ、現在トークンが誤っていたときと同じく 401 を
返します。

コレクターがノンスを記録するのは、署名が一致した後に限ります。ノンスの確認と記録はロックの下で 1 つの
操作として行い、その競争に負けた写しには 409 を返します。これにより、サーバーのスレッドで同時に処理された
同じリクエストの写しが、両方とも通ることはありません。経路上で読んだノンスを再利用した偽のヘッダーも、
署名が一致しないので、本物のリクエストを締め出せません。

判定の前に本文を読むことが、新たに生じる唯一の露出です。Bearer の検査は、何も読まずに部外者を拒否できました。
本文に固定の上限を設けるのが素直な対策ですが、それではキャプチャが壊れます。BajutsuKit は本文を意図して
そのまま報告します。途中で切れた JSON の本文は、正しいペイロードに対する `responseSchema` のアサーションを
失敗させるからです。そこでコレクターは上限を設けません。本文を読みながら SHA-256 に流し込み、一定量までは
メモリに、それを超えた分は一時ファイルに退避します（`tempfile.SpooledTemporaryFile`）。トークンを持たない
送信者が消費させられるメモリは一定量に収まり、署名付きの大きな本文も `network.json` にそのまま届きます。
署名が一致しなければ、コレクターは退避した内容を捨てます。部外者でも、不一致が判明する前に大きな退避
ファイルを書かせることはできます。これは可用性のコストであり、本項目の範囲外です。

### 時計に頼らない再送の検出

コレクターは、一度受け付けたノンスを拒否します。受け付けたノンスは、コレクターの存続期間（1 回の実行）の
あいだ集合に保持します。シナリオ間の `clear()` はこの集合を消しません。あるシナリオで盗まれたリクエストは、
次のシナリオでも拒否され続ける必要があるからです。

そのため集合は、実行が受け付ける署名付きリクエストのたびに大きくなります。対象は、報告、画面遷移、確認応答、
そして `/commands` のポーリングです。メモリは Python の集合でノンス 1 個あたりおよそ 100 バイトずつ線形に
増え、固定の上限はありません。このコストを見合ったものに保つ事実は 2 つあります。

- **報告。** 通信記録や画面遷移の報告は、もともと記録全体をコレクターのメモリに残します。その記録はノンスより
  はるかに大きいので、ノンスが加えるのは、実行がすでに払っているコストのわずかな割合です。
- **ポーリング。** 制御チャネルは 0.15 秒ごと、1 時間におよそ 24,000 回 `/commands` をポーリングします。
  ポーリングはほかに何も保存しないので、これが下限になります。ポーリング 1 時間あたりおよそ 2.4 MB です。

したがって、署名付きリクエストが 100,000 件の実行では、ノンスはおよそ 10 MB になります。実装は集合の
大きさを実行ログに記録するので、ノンスのメモリが問題になる実行は、推測ではなくログで確認できます。

正規形にタイムスタンプを含めれば集合の大きさを抑えられますが、デバイスの時計はホストの時計と一致しません。
許容幅を設けると、遅れた時計が不安定な拒否を生みます。これはプライムディレクティブ 2 に反します。
実行ごとのカウンターは、別の理由で使えません。BajutsuKit は並行する `URLSession` のタスクで報告を送るので、
リクエストは順不同で届きます。単調増加を要求するカウンターは、正当なリクエストを拒否してしまいます。

再利用されたノンスに 401 ではなく 409 を返すのは、BajutsuKit のためです。制御チャネルは 401 を終端とみなし、
プロセスが終わるまでポーリングを止めます。誤ったトークンは、再試行しても直らない設定ミスだからです。
一方、ノンスの再利用は、リクエストの写しが先に届いたことを意味します。転送された 1 回のポーリングで、
以降のすべてのシナリオの制御チャネルを止めるわけにはいきません。そこで BajutsuKit は 409 を「応答なし」と
みなしてポーリングを続け、プローブも同じように扱います。

### 応答への署名

コレクターは、署名付きリクエストに返すすべての応答に署名します。本文のない 204 も対象です。応答は
次のヘッダーを 1 つ持ちます。

```
X-Bajutsu-Signature: <HMAC-SHA256(token, answer-canonical)>
```

値は、リクエストと同じくパディングなしの base64url で表します。`answer-canonical` は、次の 4 行をこの順に
改行でつないだ文字列です。

1. リテラルの `bajutsu-answer-v1`
2. リクエストのノンス
3. 10 進のステータスコード
4. 応答本文の SHA-256 ダイジェストを小文字の 16 進で表したもの

リクエストのノンスによって、各応答は 1 つのリクエストに結び付きます。盗んだ応答は、後のどのポーリングに
対しても検証に失敗します。401 と 409 には署名を付けません。401 では、応答を結び付けるべきリクエストをコレクターが認証できていません。
409 では、そのノンスがすでに別の写しで使われています。

署名のないステータスは偽造でき、そのうち 2 つは終端扱いです。BajutsuKit の制御チャネルは 401 か 404 で
ポーリングを終えるので、`/commands` の応答を 1 つでもどちらかに書き換えた者は、プロセスが終わるまで
チャネルを止められます。本項目は両方のステータスを署名なしのまま残し、この結果を受け入れます。
書き換えた者は偽のコマンドや通信記録を得られず、ホスト側の確認応答の待機は既存のタイムアウトで明示的に
失敗します。この結果は「コマンドの横取り」と同じく、可用性の除外に含まれます。401 にも署名する案では、
きれいには塞げません。本当にトークンが誤っている場合も検証できない 401 になるため、検証できたときだけ終端と
みなすと、設定ミスのアプリがプロセスの寿命までポーリングを続けてしまいます。

BajutsuKit は、応答を使う前に検証します。

- **`GET /commands`。** 検証に失敗した応答を BajutsuKit は破棄し、破棄したことをデバイスログに記録します。
  アプリは何も適用しません。ホスト側の確認応答の待機は既存のタイムアウトで失敗し、確認されなかった
  コマンドを示します。
- **`GET /ping`。** 有効な署名付きの 204 を返した候補が、探索に勝ちます。候補アドレスで署名のない 204 を
  返すだけのホストは、もう勝てません。
- **報告の POST と確認応答。** アプリはこれらの応答を現在も読み捨てており、どれも検証しません。それでも
  コレクターは、規則を一律に保つため、これらの応答も署名の対象とします。

### チャレンジ・レスポンスとしてのプローブ

上の 2 つの仕組みによって、プローブは新しいルートなしでチャレンジ・レスポンスとして働きます。アプリは
各候補へ署名付きの `GET /ping` を送り、その新しいノンスがチャレンジになります。そのノンスと結び付いた
応答へ署名できるのは、本物のコレクターだけです。コレクターでない候補が得るのはノンスと署名であり、
どちらからもトークンはわかりません。ただし、プローブを本物のコレクターへ中継する候補は、コレクター自身の
署名付き応答で探索に勝ちます。正規形がホストとポートを含まないからです。その場合、アプリは実行が終わるまで
その中継者を経由して報告します。中継者は署名付きのリクエストや応答を偽造できず、改変もできません。そのため、得られるものは
本項目が範囲外とした 2 つの性質に限られます。本文を読むことと、リクエストを落としたり遅らせたりすることです。

実機向けの項目は、プローブについて別の後続案を記録していました。認証なしの `/ping` が実行ごとのノンスを
返す、という案です。その案では、トークンを送る先が、本物と確かめたコレクターだけになります。署名付きの
プローブは、認証なしの 2 本目のルートを加えずに、同じ目的を果たします。

署名付きの `/ping` を読んだ者は、それを本物のコレクターへ転送できます。その場合、2 つの写しのうち先に
届いた一方が受け付けられ、コレクターはもう一方を拒否します。転送された写しが先に届くと、アプリ自身の
プローブは 409 を受けます。アプリはプローブを 1 回分失いますが、もともと 2 分間、毎秒再試行しています。

### Bearer トークンはループバックだけで受け付ける

コレクターは、ループバックでは両方の方式を、それより外では署名方式だけを受け付けます。

| コレクターの bind | `Bajutsu-HMAC-SHA256` | `Bearer` |
|---|---|---|
| ループバック（`127.0.0.1`）：Simulator、`adb reverse` 経由の Android | 受け付けます | 受け付けます |
| すべてのインタフェース（`::` または `0.0.0.0`）：iOS の実機 | 受け付けます | 401 |

コレクターは、`start()` で bind したアドレスから判断します。この判断のために、プールと環境のどちらにも新しい設定キーは要りません。
ループバックで Bearer ヘッダーを使い続けるクライアントは 2 つです。

- **Android。** `BajutsuAndroid` の `BajutsuNet.kt` は、`adb reverse` 越しに Bearer ヘッダーを送ります。
  この経路はホストのループバックで終わり、ネットワークを渡りません。
- **古い BajutsuKit でビルドしたアプリ。** アプリを再ビルドする前に Bajutsu を更新したチームでも、
  Simulator での実行は動き続けます。

実機では、古い BajutsuKit の Bearer ヘッダーは 401 を受け、実行は通信を何も記録しません。この結果は
原因を示す必要があります。コレクターは、拒否した Bearer ヘッダーのうち、値が実行のトークンと一致するもの
だけを数えます（比較は定数時間で行います）。それ以外の Bearer ヘッダーにも同じ 401 を返しますが、数えません。
すべてのインタフェースの待ち受けへ到達できるホストが、でたらめな値を送って誤った警告を出させることは
できません。その数が 0 より大きいとき、
実行ログに警告を 1 件出します。警告は、アプリの BajutsuKit が署名付きリクエストより古く、実機で実行する
には再ビルドが必要だと伝えます。

### ホストによる方式の通知

逆方向のずれにも注意が要ります。アプリは BajutsuKit を別のパッケージとして取り込むので、駆動する Bajutsu
より新しい BajutsuKit をリンクすることがあります。常に署名するキットは、古いコレクターに対して、Simulator
でもすべてのリクエストで 401 を受けます。古いコレクターは警告を出さず、実行は何も記録しません。

そこでホストが方式を通知します。プールは、すべての経路で `BAJUTSU_COLLECTOR_TOKEN` と並べて
`BAJUTSU_COLLECTOR_AUTH=hmac` を注入します。BajutsuKit は、この変数が `hmac` のときに署名し、変数がない
ときは Bearer ヘッダーを送ります。古い Bajutsu は変数を注入しないので、新しいキットは古いキットと同じように
振る舞います。通知はトークンと同じく起動時の環境変数で届き、ネットワーク経路上の者には取り除けません。
そのため、このフォールバックがダウングレード攻撃の入口になることはありません。

### 変更箇所

**コレクター（Python）。** コレクターの変更は `bajutsu/common/evidence/network/` に、方式の通知は
`bajutsu/common/runner/pool.py` に入ります。

- 小さなモジュールに、2 つの正規形、署名、検証をまとめます。コレクターとそのテストは、この 1 つの定義を
  共有します。
- プールは、トークンと並べて `BAJUTSU_COLLECTOR_AUTH=hmac` を注入します。
- `NetworkCollector` に、ノンスの集合、拒否した Bearer の数、bind に応じた Bearer の扱いを加えます。
  `check_token` は、ループバックでの Bearer の経路のために残します。
- ハンドラーの `_authenticated` は、`Authorization` の方式で処理を振り分けます。本文を読みながらハッシュ
  を計算して退避し、検証済みのノンスを返します。応答を返すすべての経路が、そのノンスで署名します。
- 標準ライブラリ（`hmac` と `hashlib`）で両方の部品をまかなえます。基本インストールに依存は増えません。

**BajutsuKit（Swift）。** 署名には CryptoKit の `HMAC<SHA256>` を使います。CryptoKit は iOS 13 から
利用でき、BajutsuKit の対応下限は iOS 15 です。

- `BajutsuNet.postJSON` と `BajutsuNet.pingCollector` がリクエストに署名します。`BajutsuScreen` の
  画面遷移の報告と、制御チャネルの確認応答は、すでに `postJSON` を通っています。
- `BajutsuControlChannel` の取り出しは、`GET` に署名し、応答をデコードする前に検証します。
- プローブは、候補をコレクターとみなす前に応答の署名を検証します。
- BajutsuKit は `BAJUTSU_COLLECTOR_AUTH` を読み、ホストが `hmac` を通知したときに署名します。現在の
  Bajutsu は Simulator を含むすべての経路で通知します。これにより、Simulator のエンドツーエンドの
  ジョブが毎回の実行で署名の処理を通り、Bearer の経路は古いホストのためだけに残ります。
- 制御チャネルとプローブは、409 を「応答なし」とみなして処理を続けます。

**ドキュメント。** 両言語で次を更新します。

- `docs/ios-device-cloud.md` の平文に関する警告を置き換えます。経路が新たに守るものと、依然として
  さらされるもの（本文）を記します。
- `docs/architecture.md` のコレクターの説明に、2 つの方式と bind による規則を加えます。

### プライムディレクティブとの関係

この変更はモデルの呼び出しを追加しません。検証は、トークン、リクエスト、ノンスの集合だけで決まる純粋な
関数です（プライムディレクティブ 1）。待機も時計の読み取りも追加しません（プライムディレクティブ 2）。
設定キーも追加しません。通知の環境変数は注入するもので、設定するものではありません。bind だけが扱いを決めるので、どのターゲットも同じように振る舞います
（プライムディレクティブ 3）。

### 検証

高速なゲートは、デバイスなしでコレクターを検証します。

- 署名が一致するリクエストを、コレクターが受け付けること。
- 署名が本文、メソッド、パスと一致しないリクエストを、コレクターが拒否すること。
- 以前に受け付けたノンスを持つリクエストに、コレクターが 409 を返すこと。
- 署名付きの同じリクエストの写しを 2 つ同時に送ると、コレクターがちょうど 1 つだけを受け付けること。
- 署名が一致しない大きな本文を読むあいだはメモリ使用量が退避の上限に収まり、その後に退避した内容を
  捨てること。署名付きの大きな本文はそのまま記録すること。
- ループバックの bind では、Bearer ヘッダーを受け付けること。
- すべてのインタフェースへの bind では、実行のトークンを持つ Bearer ヘッダーを拒否し、数え、警告を出すこと。
- すべてのインタフェースへの bind では、それ以外の値の Bearer ヘッダーを拒否し、数えず、警告も出さないこと。
- 認証済みのすべての応答が、リクエストのノンスに対して検証できる署名を持つこと。
- 固定のベクターで両方の形式を固定すること。コレクターの URL そのものへ送る報告の POST（パスは `/`）も
  含めます。リクエストのベクターはトークン、メソッド、パス、ノンス、本文、
  期待する署名を、応答のベクターはトークン、ノンス、ステータス、本文、期待する署名を持ちます。

BajutsuKit のユニットテストは、同じベクターを Swift から検証し、両側がバイト単位で一致することを確かめます。
応答の側と方式の通知については、Swift のテストをさらに加えます。

- 署名が不正な応答を、制御チャネルが破棄すること。
- 署名のない 204 を返す候補を、プローブが退けること。
- 制御チャネルが、409 の後はポーリングを続け、401 の後は止まること。
- `BAJUTSU_COLLECTOR_AUTH` がないとき、キットが Bearer ヘッダーを送ること。

デバイスでの確認は手動です。「動機」で挙げた 3 つの観察を確かめます。

- ホストのパケットキャプチャにトークンが現れないこと。
- 再送した報告が拒否されること。
- Bearer のリクエストが拒否されること。

### 範囲外

- **本文の暗号化。** 必要とする運用のために、「検討した代替案」でピン留めした TLS を後続として残します。
- **Android。** Android の経路はホストのループバックで終わり、ネットワークを渡りません。
- **ホストからデバイスへのチャネル。** ランナー、`nativeZ` のレスポンダー、WebView ブリッジは、デバイスの
  ループバックで待ち受けます。これらの通信は usbmuxd に乗り、ネットワークには出ません。
- **実行中のトークンの更新。** トークンはもともと 1 回の実行のあいだだけ有効です。ノンスの集合も、
  その期間全体を対象にしています。

## 検討した代替案

- **実行ごとの証明書をピン留めする TLS。** ホストが実行ごとに自己署名の証明書を発行し、その公開鍵の
  ハッシュをトークンと並べて注入します。BajutsuKit はそのハッシュをピン留めします。
  - 利点：本項目が守るものすべてに加えて、本文も守れます。
  - ホスト側のコスト：証明書の生成手段が要ります。`cryptography` を基本依存に加えるか、`openssl` を
    呼び出すことになります。
  - BajutsuKit 側のコスト：すべての `URLSession` に信頼評価のデリゲートが要ります。プローブも、すべての
    候補と TLS のハンドシェイクを終える必要があります。
  - 位置づけ：不採用ではなく、条件付きの後続です。本文の秘匿を求める運用は、今後現れる可能性があります。
    たとえば、共有された Device Farm のネットワーク上で、実在の個人データを含む通信をテストするアプリです。
    その場合に TLS を重ねます。署名方式は、TLS の内側でリクエストの認証として残すことも、TLS に置き換える
    こともできます。
- **認証なしの `/ping` が返すノンスだけを使う案。** 実機向けの項目が後続のメモで提案していた案です。
  プローブがトークンを送る先は、本物と確かめたコレクターだけになります。しかし以降のリクエストは
  トークンを平文で運び続けるので、経路を読める者は結局トークンを得ます。
- **すべての経路で HMAC を必須にし、Bearer ヘッダーを廃止する案。** 認証の経路が 1 つになり、考えやすく
  なります。その代わり、得るもののない 2 者にコストがかかります。
  - `BajutsuAndroid` は、ループバックから出ない経路のために Kotlin 側の書き直しが必要になります。
  - Simulator の利用者のアプリは、再ビルドするまで何も記録しなくなります。
- **署名を有効にする設定項目を設ける案。** 互換性は完全に保てます。しかしデフォルトのままでは、本項目が
  取り除こうとしている露出が残ります。実機のターゲットそれぞれで忘れずに設定すべきキーも増えます。
- **ノンスの集合の代わりに、タイムスタンプや実行ごとのカウンターを使う案。** 理由は「時計に頼らない
  再送の検出」で述べたとおりです。デバイスの時計はホストの時計と一致せず、並行する報告は順不同で届きます。
