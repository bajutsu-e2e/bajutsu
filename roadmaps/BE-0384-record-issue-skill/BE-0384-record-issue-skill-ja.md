## はじめに

今回提案するのは、作業中に気づいた軽微な不具合や、小さな改善案をGitHub Issueとして起票する
`record-issue`スキルです。気づいた内容を分類し、既存Issueとの重複を検索し、本リポジトリ自身の
Issueテンプレートから件名と本文を下書きします。起票者が明示的に承認した場合に限り、
`gh issue create`で起票します。共通の手順は1つのワークフロー文書にまとめてあります。そのため、人が
直接呼び出す独立したスキルとしても動作します。`pr-followup`など他のスキルが「今回の変更のスコープ外
だが指摘しておきたい」気づきを見つけた際に呼び出すサブステップとしても、同じ手順で動作します。
[`claude-review`](../../.agent-workflows/claude-review/workflow.md)のような判定専用のスキルは、
このスキルを直接呼び出しません。`claude-review`は編集と起票のどちらも行わないため、その指摘は呼び出し元を
経由してはじめて`record-issue`に届きます。

## 動機

Bajutsuでは、アイデアの重みをすでに2段階に分けています。本格的な機能は
[ロードマップ(BE)プロセス](../../.agent-workflows/ideation/workflow.md)を通ります。`ideation`は
動機と詳細設計を備えたスコープの定まった提案を起草し、人間がマージした後にCIが実際のBE番号を
割り当てます。一方、軽微な不具合や小さな改善はこの重さを必要としません。
[`feature_request.yml`](../../.github/ISSUE_TEMPLATE/feature_request.yml)自身が「軽量な要望や
議論のきっかけにはこのissueを使ってください」と書いています。設計と呼べるほどまとまっていない
アイデアを、この一文がロードマッププロセスから切り離しています。

しかし、この軽量な側を実際に動かす仕組みは今のところありません。作業中に無関係な軽微な不具合に
気づいたコントリビューターやエージェントには、3つの選択肢しかありません。その場で直して
スコープを広げるか、そのまま作業を続けて忘れるか、手を止めてIssueを手で書くかです。最後の選択肢が
正しいやり方ですが、どのテンプレートを使うか思い出し、重複を検索し、報告文を整えるという手間が
あるため、軽微な気づきは起票されるより見過ごされることのほうが多くなります。

Claude Codeのハーネス自体には、この問題の前半に対応する仕組みがすでにあります。`spawn_task`
ツールは、スコープ外の気づきを、現在のターンを止めずに後で対応できるチップとして残します。ただし
このチップはセッションに閉じた一時的なもので、セッションを越えて残らず、チーム全体には見えません。
GitHub Issueでもないため、[`task-select`](../../.agent-workflows/task-select/workflow.md)からは
拾えません。`task-select`は、ロードマップと並んで、開いているGitHub Issueをすでに候補の1つとして
扱っているスキルです。`record-issue`は、このセッションローカルな仕組みに対応する、リポジトリ
レベルで永続する側です。誰でも、別のセッションから、別のマシンからでも`task-select`を通じて
見つけられる、チームに見えるIssueを起票します。

`record-issue`はIssueを起票するだけで、修正を出荷することはありません。
[`fix-issue`](../BE-0380-fix-issue-skill/BE-0380-fix-issue-skill-ja.md)が、起票済みのIssueの実装を
担う受け手であり、典型的には`task-select`が候補として提示した後にその実装を引き受けます。両者の
スコープは重なりません。

## 詳細設計

**スキルの構成。** [`CLAUDE.md`](../../CLAUDE.md#agent-skill-layout)は3層構成の規約を定めています。
これに従い、共通の手順は`.agent-workflows/record-issue/workflow.md`に置きます。Claude用アダプターは
`.claude/skills/record-issue/SKILL.md`に置きます。Codex用アダプターは
`.agent-hosts/codex/skills/record-issue/SKILL.md`に置きます。既存のCodexアダプターがすべて持つ
`agents/openai.yaml`のインターフェースメタデータも、ここに含めます。どちらも共通の手順を読み込み、
各ホスト固有の呼び出し方だけを追加します。

**入力。** 気づいた内容の説明です。呼び出す人が直接入力する場合も、呼び出し元のスキルが自分の
スコープ外で見つけた気づきを渡す場合もあります。加えて、ファイルと行番号、再現するコマンド、
発生した環境など、手元にある補足情報も入力に含めます。呼び出し元のスキルは、人がそのターンに
いるかどうかも伝えます。このスキル自身にはそれを観測する手段がないからです。`pr-followup`にも
観測できません。`pr-followup`自身の手順は「サブエージェントの中で動くときも、直接呼び出された
ときも同じです」。わかるのはループ層だけです。`implement-be`の手順12がサブエージェントに
`pr-followup`の手順を渡す際にこれを伝えます。`pr-followup`はそれをサブステップの呼び出しへ
そのまま渡します。フラグがなければ人がいるものとして扱います。もう1つの入力の形は、再開の呼び出し
です。承認済みの新規Issue用の下書き(タイトル、本文、ラベル)を受け取り、`gh issue create`を
実行する手順5から直接再開します。承認はすでに、ループの報告で下書きを見た人間が後のターンで
与えているからです。この入力を運べるのは有人のターンだけです。無人のまま再開すれば承認なしに
起票してしまい、それは承認の手順がまさに防ごうとしている事態そのものです。そこでスキルは、
無人フラグが立った状態で届いた再開の呼び出しを拒否し、下書きを起票せずpending-draftとして
返し直します。無人フラグは、スキルが有人かどうかを知る唯一の手がかりだからです。
無人実行が持ち帰った候補への手動コメントは、そこから先は人間自身のフォローアップで
あり、この再開の対象外です。

**手順1: 分類する。** 3つの行き先のどれに当たるかを判断します。`feature_request.yml`が示すのは
「まとまっていないアイデアはロードマップへ回さない」という方向だけなので、この基準自体はスキル自身が
定めます。詳細設計や、トレードオフの議論、あるいは複数のモジュールにまたがる変更が要る内容かどうかです。要るなら、
これは軽微な気づきに当たりません。Issueを
起票せず、`ideation`(設計がすでに固まっている小さな項目であれば`propose-and-build`)へ誘導して
ここで終了します。要らない場合は、気づいた内容を**不具合**(意図した動作と異なる)か、軽量な
**改善**(小さく閉じた改善案)のどちらかに分類します。

**手順2: 重複を検索する。** 気づいた内容から取り出したキーワードで検索します。実行するコマンドは
`gh issue list --search "<キーワード> -label:roadmap-tracking" --state all --limit 10`です。
候補となる既存Issue(番号、タイトル、状態、ラベル)を起票者に提示します。この検索は
`roadmap-tracking`のIssueを除外します。作成・クローズは
[BE-0109](../BE-0109-roadmap-tracking-issues/BE-0109-roadmap-tracking-issues-ja.md)が行います。
これらはボットが管理するIssueなので、そこへコメントするのは行き先として成立しません。
ただし、この除外によって、開いているBE項目がすでにこの気づきをカバーしているという唯一の
手がかりも消えてしまいます。そこでこの手順では、
[`roadmap-filter`](../../.agent-workflows/roadmap-filter/workflow.md)を使います。
`Proposal`用と`In progress`用にそれぞれ1回ずつ実行します。1回の実行で扱えるstatusは
1つだけだからです。返ってきたタイトルを同じキーワードで照合します。
一致すれば、その項目を起票者に提示します。
その項目がすでにこの気づきをカバーしているなら、Issueを起票しても重複になるだけなので、
その時点で止めて何も下書きしないか、そのまま起票を進めるかを尋ねます。キーワードがタイトルに一致しただけでは、気づきがすでに
カバーされている証拠にはならず、判断できるのは起票者だけだからです。開いている
似たIssueが見つかれば、新しく起票する代わりに
既存Issueへコメントするか、そのまま起票を進めるかを尋ねます。候補がどこまで近いかを判断できるのは
起票者だけだからです。クローズ済みのIssueへは報告を回しません。`task-select`が調べるのは開いている
Issueだけなので、そこにコメントしても候補として二度と浮上しないからです。代わりに、クローズ済みの
Issueを経緯としてリンクしながら、新しくIssueを起票します。

**手順3: 下書きする。** 不具合なら`bug_report.yml`、改善なら`feature_request.yml`を読みます。
そのテンプレートの入力欄(テキストエリアと、`bug_report.yml`では必須のドロップダウン)の各項目に
対応する見出しを持つMarkdown本文を作ります。
`gh issue create`はテンプレートのYAMLフォームを描画せず、素のMarkdownを投稿するだけなので、
フォームの各項目はスキル自身が埋めます。テンプレートに必須の`checkboxes`欄は例外です。手順2の
重複検索など、スキルが実際に確認した内容を文章で示す欄として使います。あらかじめチェックを
入れた欄としては使いません。`feature_request.yml`の3つのプライムディレクティブ確認欄は、
起票者自身の判断だからです。ラベルは`bug`か`enhancement`のどちらか対応するものを選びます。
新しいラベルは不要です。その理由は
本項目の「検討した代替案」に記載しています。手順2で既存の開いているIssueへのコメントを選んでいた場合は、
代わりにそのコメント文を別に下書きします。気づきの内容、根拠、気づいた経緯だけを書きます。
`gh issue comment`にはタイトルとラベルのどちらもないからです。対象のIssueが`bug`と
`enhancement`のどちらも持たない場合にかぎり、選んだラベルを手順5で`gh issue edit --add-label`
として追加するよう書き留めます。手順2は各候補のラベルを番号、タイトル、状態と
並べて示しているので、コメントによって他人が起票したIssueを勝手に再分類することはありません。

**手順4: 承認を得る。** これから投稿する内容のすべてを起票者に見せます。新規Issueならタイトル、
本文、ラベルを、既存Issueへのコメントならそのコメント文と追加するラベルを見せます。投稿を
実行する前に明示的な承認を待ちます。GitHub Issueへの起票やコメントはチーム全体に見える
公開行為であるため、この手順はセッションで最初に使うときだけでなく、毎回実行します。

**手順5: 起票して報告する。** 承認を得たら実行に移ります。新規Issueなら
`gh issue create --title <タイトル> --body-file <ファイル> --label <ラベル>`を実行します。
手順2で選んだ既存Issueへのコメントなら、
`gh issue comment <番号> --body-file <コメント用ファイル>`を実行します。手順4で承認した
ラベルを追加する場合は、続けて`gh issue edit <番号> --add-label <ラベル>`を実行します。
作成または更新されたIssueのURLを起票者に報告します。サブステップとして呼び出された場合は、
呼び出し元のスキル自身の出力にも書き戻し、レビューやフォローアップの結果に、その場で直した
内容と並べて起票した内容も列挙できるようにします。

ワークフロー文書は呼び出し元によらず1つの手順だけを記述しているため、独立した呼び出しも他の
スキルからの呼び出しも同じ手順、特に承認の手順をたどります。呼び出し元のスキルが起票者に代わって
この手順を省略できません。再開の呼び出し(「入力」参照)もこの手順を省略するものではありません。
承認は、ループの報告で下書きを見た人間が、有人のターンですでにその下書きそのものに対して
与えているからです。人がターンにいないとき、たとえば`pr-followup`が`implement-be`の
ハンズフリーループ(BE-0230)の1回として動くときは、このスキルは起票せず、停止もしません。代わりに、
完成した下書きを、イテレーションの構造化サマリーの新しい**pending-draft**フィールドで返します。
このフィールドは、`implement-be`の手順12がすでに読んでいるエスカレーション用フィールドとは
別のものです。エスカレーション用フィールドは、`pr-followup`の手順4がセルフレビューのみの
指摘を通す先です。ループはエスカレーション用フィールドを停止信号として扱います。下書きが返るのは
停止信号ではないpending-draftフィールドなので、ループは止まりません。下書きはループが報告する際に
人間の目に触れ、後のターンで承認できます。ループは、各イテレーションが返したpending-draftを、
それ以前のイテレーションがすでに返したものと重複排除したうえで、すべて自分自身の最終報告へ
持ち越します。各イテレーションは記憶を持たない新しいサブエージェントなので、同じ気づきを
繰り返し見つけてしまうからです。そのため報告には、イテレーションの回数分ではなく気づきごとに
1件だけ残ります。早いイテレーションで返った下書きも、こうして人間が読む報告まで残ります。
手順2が問う、新規起票とコメントの
どちらにするかという選択があります。ロードマップとの一致が見つかった時点で止めるか、
そのまま起票を進めるかという選択もあります。どちらも無人では確定させず、同じように保留します。スキルは
新規Issueとして下書きし、見つかった候補(似たIssueと、一致したロードマップ項目)をすべて
添えます。人間は、承認するか、候補のどれかに手動でコメントするか、その気づきを見送るかを
選びます。起票を承認すると、スキルは、人間が実際に見た下書きに対して手順5から直接再開します。
作り直しはしません。下書きが承認待ちであること自体は、意図的にエスカレーションとして扱いません。
BE-0230のエスカレーション一覧の各項目はどれもループを停止して
人間にPRを渡すものです。スコープ外の気づきという付随的な指摘だけで、健全に動いているフォローアップ
ループを止めるべきではありません。

**呼び出し元への組み込みとドキュメントの更新。** 呼び出し元のスキルは、自身のワークフローが名指しする
サブステップだけを実行します。`be-progress-tracker`が動くのは、`ideation`と`implement-be`がそれぞれ
名指ししているからです。同じ形で、`pr-followup`(および他の呼び出し元スキル)に`record-issue`の
サブステップを名指しします。あわせてドキュメントも更新します。対象は`docs/ai-development.md`
(日本語版含む)と`CLAUDE.md`で、Claude用アダプターの既定の`model:`層(BE-0103)も含みます。

## 検討した代替案

**承認なしで起票する。** 却下しました。Issueの作成はチーム全体に見える公開行為であり、承認を
省くと、誰も確認しないままノイズの多い、あるいは誤診断された報告が他のコントリビューターに
届いてしまいます。

**`ideation`を拡張して軽微な気づきも扱う。** 却下しました。`ideation`が担っているのはBEロードマップ
項目の起草であり、仮のID、詳細設計、CIレビュー契約に対するセルフレビューまで含みます。軽微な
気づきにこの重さは要りません。両者を1つのスキルにまとめると、`ideation`の手順が過負荷になるか、
大きさの異なる2種類のアイデアに対して一貫しない使われ方をすることになります。

**GitHub Issueの代わりに`spawn_task`のようなセッションローカルなチップを使う。** 却下しました。
セッションローカルなチップはセッションを越えて残らず、チーム全体には見えず、`task-select`が読む
候補にもなりません。この項目が埋めようとしている隙間を埋められません。

**これらのIssueを軽量だと示す新しいラベルを追加する。** 検討しました。`roadmap-tracking`
ラベルが付いていないこと自体が、`record-issue`による起票とBEに紐づくIssueをすでに区別して
います。また既存の`bug` / `enhancement`ラベルが、気づきの種類をすでに示しています。ラベルを
追加しても手順が増えるだけで、伝わる情報は増えません。

## 進捗

> 開発の進行に合わせて常に最新の状態に保ってください。チェックリストは *詳細設計* の MECE な
> 作業分解（作業の単位ごとに 1 つ）に対応し、ログには変更内容と時期（古い順）を PR へのリンクと
> ともに記録します。

- [ ] `.agent-workflows/record-issue/workflow.md`を執筆する(分類 → 重複検索 → 下書き → 承認 →
      起票)。
- [ ] Claude用アダプター`.claude/skills/record-issue/SKILL.md`を追加する。
- [ ] Codex用アダプター`.agent-hosts/codex/skills/record-issue/SKILL.md`を追加する。
- [ ] 呼び出し元に組み込む: `ideation` / `implement-be`が`be-progress-tracker`を名指しするのと
      同じ形で、`pr-followup`(および他の呼び出し元スキル)に`record-issue`のサブステップを
      名指しする。
- [ ] ループ層に組み込む: `implement-be`の手順12は、サブエージェントに`pr-followup`の手順を渡す
      際に人がターンにいるかどうかを伝える。その構造化サマリーの契約に承認待ちの下書き用
      フィールドを追加する。このフィールドはエスカレーション用フィールドとは別にし、下書きが
      ループを止めないようにする。手順12は、各イテレーションが返したpending-draftを、
      それ以前のイテレーションの分と重複排除したうえで、すべて自分自身の最終報告へ持ち越す。
      早く返った下書きも、イテレーションごとに重複せず人間へ届く。
- [ ] ドキュメントの更新: `docs/ai-development.md`(日本語版含む)と`CLAUDE.md`。Claude用アダプターの
      既定の`model:`層(BE-0103)も含む。
- [ ] 独立した呼び出しと、呼び出し元スキルからの呼び出し(例: `pr-followup`がスコープ外の気づきを
      見つけた場合)の両方で、承認の手順が働くことを確認する。あわせて、無人の実行
      (`implement-be`のハンズフリーループ内の`pr-followup`)を確認する。起票やエスカレーションを
      せず、下書きを構造化サマリーで返すことを確かめる。承認する人間が後のターンで、その下書きに
      対して手順5から再開すること(作り直さないこと)も確かめる。
